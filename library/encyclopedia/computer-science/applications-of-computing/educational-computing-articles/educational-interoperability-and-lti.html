Definition, Scope, and Educational Purpose

This ninth Level 5 specialist article extends the Educational Computing parent overview and follows the authoritative Educational Computing unit index. The first eight specialist articles are already complete. This article examines cross-system technical contracts and educational workflows rather than replacing the sibling treatments of grade validity, identity administration, accessibility, institutional procurement, and academic records.

Educational interoperability is the ability of independently developed learning systems to exchange information and coordinate legitimate institutional work through agreed technical and organizational interfaces. A student may begin in a student information system (SIS), enter an LMS course, launch a third-party learning tool, submit an exercise, and see a result returned to a course gradebook. Each transition raises questions of identity, permission, meaning, provenance, and failure handling. A collection of individually functional products is not an interoperable educational environment unless these boundaries are controlled and tested together.

This article examines Learning Tools Interoperability (LTI), with emphasis on LTI 1.3 and the services associated with LTI Advantage, while locating OneRoster, QTI, Common Cartridge, and learning-event exchange in their appropriate roles. The distinctive educational problem is preserving instructional intent and trustworthy academic workflows across systems. It is not a general guide to building an OAuth application, designing an entire course, or establishing official student records; those subjects belong respectively to security and software-engineering references and the adjacent Educational Computing specialist articles. The intended reader should be able to describe what an integration is authorized to do, why a launch may succeed while grade synchronization fails, and which evidence makes a deployment institutionally acceptable.

Historical Development and Standards Landscape

Earlier LMS integrations frequently relied on custom username provisioning, shared passwords, vendor-specific file exports, signed launch parameters, or proprietary browser redirects. They could solve immediate needs but required repeated reinvention when products changed. Standardization sought to make a learning tool portable between platforms without forcing every institution to write a new connector. LTI 1.0 and 1.1 popularized external tool launches; later specifications expanded content selection, grade return, and membership features. The LTI 1.3 security model adopted modern OpenID Connect and OAuth-based patterns rather than preserving the older launch-signing model.

Interoperability standards evolved along several parallel tracks. OneRoster focuses on roster and related educational data exchange. QTI addresses the structure and processing of assessment items and tests. Common Cartridge concerns packaging learning resources. Caliper Analytics describes learning activity events. These projects arise from overlapping educational ecosystems, but their data objects, time horizons, permissions, and authoritative sources differ. A procurement document that says “supports open standards” without naming versions, features, directions of exchange, conformance scope, and test evidence leaves the critical contract unspecified. This article therefore treats standards as components of an operating arrangement rather than interchangeable badges.

Institutional Systems and Participants

A typical integration includes the institution, identity provider, SIS, LMS, external tool provider, browser or mobile client, and optional analytics and reporting services. The institution defines permitted educational purposes and contractual safeguards. The SIS may own official enrollment identifiers; the LMS owns course delivery context and operational gradebook states; the tool owns its instructional activity and local results. Identity services authenticate people; administrators register and enable integrations; instructors choose activities; students use them. The provider's infrastructure may reside outside the institution's network, but technical distance never removes institutional accountability for the learning task.

Vendor support may diagnose an API failure but cannot unilaterally decide that a disputed grade becomes part of the official academic record. A successful implementation names the decision owner for every transition and provides escalation when ownership is contested or unavailable.

Architectural Layers and Trust Boundaries

It is useful to distinguish five layers: identity and session establishment; authorization and access to resources; semantic data exchange; application workflow; and operational assurance. Authentication answers who participated in a launch. Authorization answers which integration may act and what it may read or change. Semantics determine whether two fields mean the same thing. Workflow defines when a score may be transmitted and interpreted. Assurance detects failure, supports audit, and restores service. The layers depend on one another, but success at one layer does not imply success at the others.

A platform-to-tool boundary is particularly important because the tool may receive a signed launch assertion and later request data through separate API calls. Browser navigation and server-to-server API access are not the same channel. A claim that a learner belongs to a course is a context assertion, not perpetual authority to view every learner in that course. An access token for grade services is not permission to fetch institutional admissions data. Every boundary should be drawn with the actor, data class, permission scope, expected recipient, retention rule, and error behavior identified. This prevents an architecture diagram from obscuring the actual disclosures.

Educational Workflow and Interface Contract

A usable interface contract begins with an educational sentence: “An enrolled student opens an assigned simulation, completes its activity, and the instructor can review its result in the LMS.” Engineering then decomposes the sentence into course creation, resource selection, student launch, local activity state, line-item creation, score posting, learner feedback, and authorized grade review. It specifies which steps happen synchronously, which may lag, and which are irreversible. The institution should decide whether a tool is allowed to create a gradebook column or only post to an already-approved one.

The contract must also describe negative paths. What occurs if the course is renamed after a link is created, a student moves sections midterm, a teacher loses course access, the provider endpoint is temporarily offline, or a score arrives after the instructor has certified final grades? Data-field specifications alone cannot resolve these operational issues. Write acceptance criteria from the learner, instructor, administrator, and records-steward perspectives. For each important state change, record the owner, event, permitted action, observable success condition, retry rule, and recovery path.

LTI 1.3 Core: Platform and Tool Model

Learning Tools Interoperability 1.3 defines an interoperable mechanism for a learning platform to initiate secure interactions with an external learning tool in a recognized learning context. In ordinary LMS terminology, the platform is often the LMS and the tool is the external assessment, simulation, reading, video, or practice service. These roles are protocol roles: the platform presents the integration context and the tool consumes it; a product could conceivably support different roles in different deployments. The launch is not a universal data-sharing agreement, and LTI Core does not by itself guarantee grade services or class-wide roster access.

The modern model uses an OpenID Connect third-party-initiated login and a signed ID token to convey launch claims. Other services use appropriately scoped OAuth access tokens. The presence of both approaches can confuse implementations: the browser-mediated signed launch establishes a particular user/context interaction, while a subsequent machine-to-machine request may require independent credentials, scopes, and authorization. Institutions should ask vendors whether they implement LTI 1.3 Core, which LTI Advantage services they support, whether those services are enabled for the purchased product, and which features have been tested in their exact LMS environment.

Tool Registration and Institutional Deployment

Registration and deployment must be distinguished. A registration establishes security and configuration information shared between a platform and tool, potentially including a client identifier, permitted redirect URIs, launch or login-initiation URLs, public-key information, and the platform authorization or token endpoints. A deployment is a particular authorization of that registered tool in an institutional or organizational context. LTI 1.3 includes a deployment identifier that helps distinguish an enabled integration from other uses of the same registration.

This separation matters for multi-campus organizations, staging and production systems, and vendors that serve many institutions. An administrator might register a vendor centrally but approve deployments for only selected units. A change in vendor domains or signing keys may require a configuration change without altering the educational course resource itself. The configuration inventory should therefore store issuer, client ID, deployment ID, approved tool endpoints, key sources, service scopes, support contact, contract identifier, environment, approval date, and intended institutional owner. Never assume that copying a test registration into production preserves the same identity, permissions, or trust contract.

Launch Sequence from Browser to Tool

A conventional LTI 1.3 launch starts when a learner or instructor selects a configured resource inside a platform. The platform initiates the OpenID Connect flow, the tool participates in the authentication request and response, and the platform returns a signed ID token to the tool's registered redirect endpoint. The tool validates the assertion and establishes a session for the specified user, role, context, and resource. The final learning activity is shown only after that validation. The complete interaction includes browser transitions, nonce and state handling, trusted URLs, time limits, and application session management.

The precise messages depend on the registered integration, but the key conceptual point is that a tool must not treat a query-string label or arbitrary launch URL as proof of institutional authority. It should validate the signed claims and bind the user session to the verified issuer and deployment. An instructor may select a reading while a learner later opens the same resource; these are different launch experiences and may involve different role claims or service availability. A flow diagram should distinguish the learner's browser, platform server, external tool server, and authorization/token endpoints; otherwise the diagram can suggest incorrectly that all exchange is performed by the student's browser.

OpenID Connect Initiation and State Handling

The login-initiation phase communicates the information needed to begin an OIDC authentication request, typically including an issuer, client information or launch hint, target, and login context according to the registered workflow. The tool must use its trusted registration to determine which issuer and authorization endpoint it will accept. It should generate an unpredictable state value that binds the browser flow to the initiating session and an unpredictable nonce to bind the returned signed authentication message to the expected request. These are independent defenses even though they are often created together.

State validation protects against one browser session receiving or consuming a response intended for another. Nonce validation guards against replay and stale authentication assertions. Short token lifetimes, secure cookies, and explicit session renewal reduce the window for misuse. When third-party cookies or browser storage policies complicate the round trip, an institution should test the supported browsers and embedded display modes rather than disabling protections as a quick fix. Robust implementations treat failed state, nonce, issuer, audience, or signature validation as a rejected launch with a traceable error, never as an opportunity to fall back to an unverified identity.

Signed ID Tokens and LTI Claims

The signed ID token is a JSON Web Token containing standard identity claims and LTI-specific namespaced claims. Depending on the launch, it can describe the message type, LTI version, deployment, course context, user role, resource link, and endpoints or service capabilities available to the tool. A signed token does not make every included attribute academically authoritative. For instance, a displayed user name can be a convenient label while the issuer-scoped subject identifier is the appropriate technical reference for an account relationship. Context and resource-link identifiers should be preserved as distinct dimensions.

Documentation should identify mandatory claims, optional data, and fields that a platform will intentionally omit. A vendor must not assume that email addresses or a full roster are always available, nor should a recipient interpret the absence of a field as proof that a user is not enrolled. The underlying privacy policy determines whether names, emails, organization details, or custom claims are disclosed. Academic roles also vary: an instructor may be authorized to manage a course but not to alter final records. Data minimization and explicit contract definitions make the message useful without treating it as a container for unrestricted student profiles.

Token Validation and Audience Controls

Before accepting a launch, a tool must validate the ID token against the registered platform's issuer and trusted verification keys. It checks the signature and signing algorithm policy, intended audience or client identity, token lifetime and issuance plausibility, nonce, deployment identifier, message context, and any applicable authorized-party condition. Key selection should be bound to the issuer's configured JSON Web Key Set (JWKS) rather than to an arbitrary address supplied by the token itself. Successful cryptographic verification against the wrong issuer would still be a trust failure.

Practical controls include rejecting unsupported signing algorithms, unknown deployments, unregistered redirect relationships, excessive clock skew, and reuse of consumed nonces. Tests should deliberately tamper with one claim at a time and confirm rejection without disclosure of raw assertions to the learner. Log a correlation identifier and bounded failure reason rather than full signed tokens containing personal information. Time synchronization, key rotation procedures, and certificate management are part of the production security posture. The tool's subsequent application session should inherit only verified privileges and must not outlive institutional authorization indefinitely.

Public Keys, Rotation, and Configuration Drift

LTI security depends on the integrity of public-key configuration and responsible management of the corresponding private keys. A platform may publish a JWKS endpoint for verifying its launch signatures, and a tool may publish its own keys for service-client authentication. A normal key rotation can make a previously cached key obsolete. A sound implementation periodically refreshes trusted key material, accepts only appropriate key identifiers, and supports overlap during controlled transitions. It should not fetch verification keys from untrusted locations based solely on token-provided text.

Institutional configuration drift is subtler than outright attack. An administrator changes the production tool hostname; a vendor adds a new redirect URI; a campus copies staging configuration; or a key-rollover notification reaches only one support queue. The interface begins to fail even though neither system's course content changed. Maintain an integration register with change owners, tested environments, rotation contacts, and rollback procedures. Certificate or key expiry should be monitored before it affects students. A vendor support ticket showing “signature invalid” is an operational symptom to investigate, not permission to weaken token validation.

Context, Resource Link, and Course Membership

An LTI launch can carry a context describing the educational container, such as a course or section, and a resource link that identifies an assigned activity. These identifiers answer different questions: a context groups educational work; a resource link identifies a specific placement or resource launch inside it. One course may contain multiple tool links, and a reused instructional tool may appear in many courses. The resource link is not necessarily a unique assessment item or student attempt identifier, and course identifiers may be scoped to one platform.

A stable mapping table should connect platform issuer and deployment, context ID, resource-link ID, local tool resource, and optional gradebook line item. Human-readable course titles are poor primary keys because they change and may collide. Cross-listing and course copying complicate the mapping: copied links may retain configuration while representing a new instructional context. An integration should define whether copy operations create a fresh activity, duplicate associated settings, or expose prior learners' work. Context identifiers must be treated as verified but scoped claims, not as universal institutional course identifiers.

Roles, Permissions, and Educational Authority

LTI roles communicate a user's relationship to a learning context, such as learner or instructor. Platforms may emit one or more roles, and institutional labels do not always map cleanly to vendor permissions. A teaching assistant may manage submissions but not release a final grade; an academic support advisor may view selected progress data without participating as an enrolled learner. A tool should therefore translate supplied roles into its own least-privilege capabilities under an institutional policy rather than assuming that every instructor role grants every administrative operation.

Role mapping must be tested as a changing lifecycle. When a course assistant becomes the instructor of record, access may expand; when a former instructor loses appointment, access must contract. A user can hold an institution-wide administrative role and a learner role in a specific course without the latter implying global privileges. Institutions should maintain representative role-based test accounts and permission matrices; mere login success is not a sufficient access test. The specialized sibling article on educational identity owns the full identity and deprovisioning architecture, while this article analyzes the integration's claim interpretation and downstream permissions.

Launch Session, User Linking, and Account Provisioning

A tool may create a local record on first verified launch, a form of just-in-time account provisioning. It must decide whether the platform issuer plus subject identifier identifies an existing user and whether a deployment change requires a new association. Email-based matching alone can merge unrelated people or split the same person after an address change. An institutional relationship should be linked only through approved, unambiguous identifiers, with supervised resolution for collisions and account transitions.

A launch can also arrive for a user whose access has just been withdrawn; cached tool sessions and local activity accounts must follow a defined authorization lifetime. If a learner can reach a bookmarked external URL without a new verified launch, the provider must evaluate whether continuing access is permitted and how authorization changes are detected. Account provisioning should request the minimum necessary personal attributes and should define separate retention and deletion policies for the local tool profile, submitted educational work, grade-related data, and support logs. Interoperability does not require storing an unrestricted duplicate of the SIS.

Third-Party Cookies, Browser Context, and Mobile Clients

The browser mediates many LTI launches, and real behavior depends on top-level navigation, embedded frames, cookie controls, cross-site tracking restrictions, and authentication state. An iframe that works in one desktop browser may fail in another or on a managed mobile device. Institutions should test launches under realistic privacy settings rather than assume that enabling every third-party cookie is an acceptable institutional requirement. Some tools may need a supported top-level launch or alternate workflow, especially when nested browsing contexts or accessibility technology interfere.

Mobile applications add additional handoff concerns: an LMS app may open an embedded browser, a system browser, or a vendor app; each has different return-navigation and session properties. Learners need a comprehensible error and recovery route when the launch fails. Browser compatibility is an operational and accessibility issue, not a reason to bypass signature checks. Test at least initial launch, resumption, expiry, course navigation, deep-linked content, and return to the LMS on representative managed devices. The Online, Hybrid, and Mobile Learning Systems specialist treats broader low-bandwidth delivery; this article confines itself to launch and cross-application interoperability.

Privacy-Minimizing Launches and Claims

For each attribute included in a launch, an institution should document the specific service purpose. A tool that needs only to deliver an anonymous practice exercise may not need legal names, emails, or demographic attributes. A graded service may need a stable learner reference and course placement, but that does not justify a wholesale student profile. Data minimization works at registration and deployment, through platform configuration, vendor behavior, and contract enforcement. Optional LTI claims should be treated as optional; absence must have an intentional interface behavior.

Minimization also requires purpose limitation. A provider may need a user identifier to record a course attempt but not to build a cross-institution marketing profile. The institution should decide whether tools may retain activity histories after course completion, which support personnel may access them, whether data may train unrelated models, and how records are removed or exported. For some uses, an authorized pseudonymous identifier and a bounded mapping kept by the school may reduce exposure. Privacy protections must be validated with real launch payload inspection and vendor documentation, not inferred from the use of a widely adopted standard.

Deep Linking: Course Content Selection

LTI Deep Linking 2.0 supports an authoring workflow in which a platform user launches a tool to select or configure learning content and returns structured information that the platform can use to create a link or other supported content placement. The distinction from an ordinary learner launch matters: an instructor selecting a simulation has different intentions and permissions from a student attempting it. Deep Linking helps reduce manual copying of opaque URLs and enables a more consistent resource-selection experience across compatible platforms and providers.

The platform and tool still need to agree on the content types, return destination, handling of titles and descriptions, and whether grade-related settings accompany a resource. A deep link can successfully appear in a course while later launches fail because of deployment, permissions, or vendor-state changes. Institutions should test selection, creation, preview, duplication, course-copy behavior, deletion, and republishing. The tool should verify Deep Linking messages and return information through the specified trusted channel; it must not accept arbitrary return URLs or treat an instructor's selection screen as authorization for the tool to read an entire campus roster.

Deep Linking Validation and Resource Lifecycle

A content placement is part of a lifecycle. Once selected, its resource identifier may be referenced by a course template, copied into another section, moved between modules, or archived with a course. Deep Linking responses should be validated for allowed resource types, required metadata, intended target, and gradebook associations. When a provider changes its activity catalog, it must distinguish cosmetic changes from alterations that would invalidate already assigned learning objectives or scores.

Testing should cover deleted tool resources, stale deep-link references, unpublished activities, multiple selected items, and a copied course whose new instructor does not have vendor-authoring rights. When the same link is launched by different cohorts, learner data must not spill across contexts. Institution-specific resource inventories help identify which courses depend on a vendor before contract expiration or migration. A portable placement requires not only a saved identifier but also a workable way to reconstruct or replace the educational task if the external provider ceases operation.

Names and Role Provisioning Services

LTI Names and Role Provisioning Services (NRPS) 2.0 allows an authorized external tool to obtain membership information associated with a context, subject to available service claims, permissions, and platform implementation. It is useful where a tool needs to prepare a class roster, show participants to an instructor, or reconcile users rather than waiting for each learner to launch separately. The service is not automatically present in every LTI 1.3 deployment, and a launch token alone does not authorize unlimited enumeration of learners.

Membership responses may include institutional roles and selectively disclosed attributes. Tool developers must understand pagination, update frequency, withdrawn users, and whether current membership differs from the last reported roster. A roster snapshot can be stale by the time a student opens an activity. An instructor's ability to see a membership list should not be silently extended to the vendor's unrelated analytics or marketing applications. The administrative contract needs to state the service scopes, permissible uses, storage period, deletion process, and whether the same student identifier remains stable across terms and contexts.

OneRoster and Class Data Exchange

OneRoster 1.2 supports educational data exchange in CSV-style files and through REST APIs. It can represent organizational information, classes, enrollments, users, and related resource or gradebook information within the defined exchanges and implementation profile. OneRoster is particularly useful where SIS, LMS, and other institutional services need class and membership information without requiring individual tool launches first. The chosen version, exchange mode, endpoints, fields, and refresh cadence must be written into the interface agreement.

A nightly roster export and a near-real-time API may both satisfy a broad marketing claim of “OneRoster support” while producing different educational experiences. A student added moments before class may launch successfully in one environment and be missing until the following day's sync in another. File-based exchanges need secure transport, schema checks, sequencing, and clear rules for correcting old rows. API exchanges need access controls, pagination, error handling, and rate-limit expectations. The SIS's authority over enrollment must be preserved; downstream vendors should not silently convert a transient failed import into an institutional enrollment change.

NRPS and OneRoster: Distinct Membership Functions

NRPS and OneRoster can both involve class membership, but they address different integration arrangements. NRPS is part of the LTI ecosystem and is associated with tool access to members in a particular platform context. OneRoster defines broader structured roster-related exchange that may connect SIS, LMS, and multiple services independently of a current LTI tool launch. The organization supplying data, available fields, timing, scope, and authorized recipient may differ. Neither standard eliminates the need to identify an authoritative enrollment source.

If the two sources disagree, the institution needs an explicit precedence and reconciliation policy. Assignment and Grade Services

LTI Assignment and Grade Services (AGS) 2.0 supports defined interactions with a platform's gradebook, including line items, score posting, and result retrieval where implemented and authorized. A tool can use AGS to associate a resource with a gradebook column or report a learner's score. This is distinct from the signed browser launch: AGS uses authenticated service requests with appropriate access scopes. Support for LTI Core does not imply support for AGS, and support for one AGS operation does not guarantee all permitted operations.

The institution must decide which gradebook actions the provider may perform. Some instructors may approve a tool's creation of a line item but require manual release of grades; other contexts may allow scores to appear automatically as unposted drafts. A provider should communicate maximum possible points, progress, scoring status, and relevant timestamps according to the service contract. It must not assume that a returned HTTP success means the learner has seen the feedback or that an official grade has been certified. The platform gradebook and the registrar's official academic record remain distinct layers of authority.

Line Items, Scores, and Result Semantics

In an AGS workflow, a line item identifies a gradebook activity or assignment record, scores communicate evaluated learner performance, and results represent the platform's available grade information under the service. Concepts that look equivalent in a user interface can differ at the protocol level. A line item might have a maximum possible score, while individual score reports supply earned points and activity progress. The tool and platform must agree on numerical precision, supported status values, treatment of late attempts, and consequences of subsequent rescoring.

Consider a 40-point quiz inside an LMS course graded on a 100-point weighted scale. The tool sends a score of 32 out of 40: the normalized proportion is 80 percent, but that does not tell the platform whether the activity counts for 2 percent or 20 percent of the final course grade. Gradebook category weights and instructor policy govern that subsequent calculation. A technically correct score can still be educationally wrong if it is attached to the wrong line item, a draft attempt, or another learner's identifier. Every interface should retain both score provenance and mapping evidence.

Grade Return, Feedback, and Certification Boundaries

An external tool may record multiple attempts, provisional scores, rubrics, comments, and human revisions. The integration must decide which events produce a grade update and whether results are released before an instructor checks them. For formative work, immediate feedback may be desirable. For high-stakes work, an instructor may need to review accommodations, suspected item defects, or manual scoring before publishing a result. A platform can receive a score without acquiring responsibility for the underlying assessment validity; institutions must preserve review and appeal processes.

When a course grade is later transferred from the LMS to a SIS, another authority boundary is crossed. AGS is not itself a system for certifying final academic records, and sending a score through AGS does not transform it into a transcript entry. A grade amendment requires a separately controlled institutional process. Integration documentation should specify whether a score is local draft, submitted assessment result, released LMS grade, instructor-approved final grade, or registrar-certified record. Distinct statuses help avoid accidental overwriting when a provider resends an old score after a final-grade deadline.

Grade Sync Retries, Duplication, and Conflict Resolution

Networks fail at inconvenient points. A tool may send a score, lose the acknowledgment, and retry even though the platform accepted the first request. Retry design must avoid duplicate gradebook columns or unintended repeated actions; where supported, stable identifiers and carefully defined idempotent updates can distinguish a retried operation from a genuinely new score. A timestamp alone may not establish which score is authoritative, especially after an instructor manually corrects an error. OAuth Access Tokens and Least-Privilege Scopes

LTI Advantage services typically involve OAuth 2.0 client-credentials requests and short-lived bearer access tokens scoped to permitted service operations. The tool authenticates as the registered integration rather than impersonating a learner by reusing the ID token from a browser launch. Service permissions may distinguish reading line items, managing line items, posting scores, or reading roster membership. A tool should request only the scopes required by its approved educational function, protect the returned bearer token, and honor its expiration.

A token valid for a grade service is not a general-purpose school data credential. Keep it out of browser logs, client-side script storage, error pages, analytics collectors, and support screenshots. Token caches must bind credentials to the correct issuer, client, scope set, deployment or institutional environment as required. When a service replies with an authorization failure, investigate the actual configured permissions rather than making the tool use a more powerful administrator credential. Separate test and production credentials, rotate compromised secrets, and log API actions in a way that supports accountability without leaking student records.

Enrollment Changes, Withdrawals, and Term Boundaries

An enrollment record is time-dependent. A learner may register, wait for a course to open, change sections, withdraw, re-enroll, or receive a grade after the term closes. These changes can arrive through different pipelines: SIS-to-LMS roster exchange, LMS membership APIs, and new LTI launches. The tool must distinguish a person who no longer has permission to start new work from a person whose earlier submissions must be retained under academic records policy. Removing access and deleting records are not automatically the same operation.

For a transfer between sections, the contract should define whether prior attempts move, whether the instructor can still review the old record, and whether a new line item should be created in the destination course. If an inactive learner can access cached tool sessions, the risk may persist after roster removal. Build tests around effective dates and source-system change order. Reconciliation reports should identify people present in the vendor tool but absent from the authorized class list, and vice versa, without automatically erasing disputed records. Records stewardship belongs with the institution; interoperability supplies evidence and controls for executing it.

Data Contracts and Interface Ownership

A data contract is an agreed description of who sends or requests information, its structure and meaning, permitted purpose, lifecycle, and behavior when assumptions fail. For educational interfaces, it should identify the authoritative system for every field. For example, a course title may originate in the SIS but be customized by an instructor in the LMS; an assignment score originates in a tool while the instructor retains the power to approve its interpretation. A contract that describes only JSON property names cannot settle these differences.

The contract should record version, schema, identifier scopes, timing, access scopes, required and optional fields, supported status changes, retries, error meanings, monitoring, and retention. It should name the technical owner and academic decision owner. Changes should proceed through a review process that records backward compatibility and required regression tests. An integration catalog allows staff to answer which departments use a particular endpoint and what would break if the provider changes it. Versioned contracts make migrations more controlled and reduce the risk that a quiet vendor update alters an instructional assessment or exposes a new data category.

Field Meaning, Vocabulary, and Semantic Drift

Two systems can exchange structurally valid messages while disagreeing about meaning. “Active” may describe an enrolled person in an SIS, an enabled account in an identity provider, or a currently open assignment in a learning tool. “Score” may mean raw points, percentage, mastery level, or weighted grade contribution. “Course” may refer to a catalog offering, term section, cross-listed group, or LMS shell. Semantic mapping documents these distinctions explicitly, with examples and authorized transformations.

A field dictionary should state the business definition, unit, allowed values, null behavior, date timezone, source authority, and destination interpretation. Transformations should be reversible where feasible or accompanied by a recorded rule. If the LMS uses a letter-grade symbol while the tool reports numeric points, the institution must provide an approved conversion instead of leaving the vendor to infer one. Version changes need tests that detect new enumeration values and altered interpretations. Interoperability is not merely the absence of parser errors: it is preserving the educational decision that a field represents.

Time, Effective Dates, and Event Ordering

Educational transactions frequently happen near deadlines. Enrollment may become effective at midnight in the institution's timezone, while a vendor records a timestamp in UTC. A learner may submit at 11:59 p.m. and receive a score after the deadline, or a teacher may update a due date while the tool's cache still holds the old value. If interfaces do not specify event time, processing time, and effective time separately, they can produce contradictory records without a network defect.

Use unambiguous timestamps with timezone information and document the institutional rule governing deadlines. For change feeds, define ordering and how an out-of-order event is handled. A late-arriving “withdrawn” record must not remove a student who has since re-enrolled unless the effective state actually supports that action. For grades, a new attempt and a retransmission of an older attempt require distinct treatment. Testing should simulate daylight saving transitions, date-only enrollment boundaries, clock skew, and delayed batches. Where complete ordering is not possible, reconciliation against the authoritative current state is safer than trusting arrival order.

QTI and Assessment Interoperability Boundary

Question and Test Interoperability (QTI) concerns assessment content and associated processing information, including item structures, interactions, and scoring logic within its supported model. LTI enables an LMS to launch an assessment tool; AGS may carry results afterward. These capabilities can be used together but do not substitute for one another. An instructor who exports QTI content may be able to move questions to a compatible assessment engine, while an LTI-linked remote assessment may remain unavailable without the external provider even if the LMS course shell survives.

The institution should distinguish item portability, test-session state, item bank ownership, respondent evidence, scoring fidelity, and downstream grade reporting. QTI version support must be identified and tested with actual item types, especially adaptive interactions, math content, accessibility settings, partial credit, and question dependencies. A correct grade transfer through AGS cannot compensate for an imported item that changes its correct answer or omits an accommodation. The specialist Digital Assessment and Item Interoperability article owns psychometric validity and detailed QTI treatment; the concern here is integration boundaries and where failures become visible.

Caliper, xAPI, and Educational Event Exchange

Learning-event specifications describe activity records that can be used by analytics and support systems. Caliper Analytics and xAPI employ their own information models and delivery arrangements; neither is a synonym for an LTI launch. A tool may launch securely through LTI and independently emit Caliper events to an approved collector. The destination, purpose, user identifiers, and disclosure authority for that stream require separate governance. An LMS receiving a score does not automatically receive every click, interaction, or mastery estimate recorded by a provider.

The institution should map event types, actor identifiers, timestamps, learning activities, and contextual dimensions with explicit consent or other lawful basis as applicable. An event stating that a student opened a page is not proof that the student learned the concept. Some vendors generate high-frequency events and others report only assessment completion; analytics comparisons must account for differences in instrumentation. Event pipelines need retention limits, sampling policies, error handling, and privacy review. Competencies, Outcomes, and Learning Standards Exchange

Some educational interfaces exchange curricular relationships as well as people and scores. 1EdTech CASE addresses structured academic standards and competency frameworks, which can support mappings between resources, assessments, and learning objectives. An LMS integration may reference such identifiers, but having a link to a competency does not demonstrate mastery. Institutions need an explicit policy for who publishes or approves the framework, how revisions are versioned, and how an assessment claim is connected to evidence.

For example, a tool may tag an exercise to a science outcome and later transmit a grade. The receiving platform must determine whether that score is sufficient evidence for the outcome, whether rubrics or prerequisites apply, and whether the link refers to a valid framework version. If the competency definition changes, historical records should retain their original meaning rather than silently inheriting revised criteria. This is another case where syntactic interoperability differs from educational equivalence. Tool contracts should record provenance and maintain references to stable, governed identifiers whenever cross-system mastery reporting is required.

Security Threat Model for Learning Tool Integrations

A learning integration crosses trust boundaries that can expose identities, grades, course activity, and administrative permissions. Threats include a forged launch, replayed token, incorrect issuer acceptance, overbroad grade-service scopes, compromised provider keys, cross-tenant data leakage, and unauthorized account linking. Technical defenses must be matched to actual attacker actions and the educational consequence. A stolen learner token and a vendor's overprivileged back-end credential produce different risks and require different containment responses.

An institutional threat model should identify assets, entry points, actors, system authority, possible misuse, and evidence needed to detect incidents. Consider both deliberate attacks and configuration mistakes: a staging deployment accidentally connected to live student accounts can produce serious exposure without hostile intent. The institution should validate signing-key management, transport security, session handling, service scopes, tenant isolation, error redaction, and support access. It should also plan how an integration can be disabled rapidly without destroying educational evidence. Security assessment does not end when the tool passes an LTI conformance check.

Authorization Failures and Safe Error Handling

An integration must respond predictably when claims or credentials are missing, expired, or inconsistent. If a learner's role is insufficient, the tool should explain that the activity is not currently available and offer a school-controlled support path, not display sensitive platform diagnostics. If an AGS token lacks the required scope, the grade-synchronization worker should record a bounded failure and stop repeated unauthorized calls. If a nonce or issuer fails validation, the launch should be rejected without a fallback mechanism that trusts unsigned query parameters.

Technical support requires enough evidence to diagnose the issue while respecting student privacy. Correlation IDs, integration IDs, sanitized event types, retry counts, and anonymized mapping references are often sufficient. Support logs should not routinely store complete ID tokens, access tokens, grades, or full roster files. Error pages ought to work with keyboards, screen readers, and mobile browsers. A safe failure preserves the learner's work locally when permissible, avoids creating duplicate grades, makes the unresolved state visible, and does not grant excessive access as a workaround.

Data Retention, Export, and Vendor Exit

External tools can accumulate student submissions, feedback, attempt histories, annotations, and grades over many semesters. A vendor's retention policy may differ from the institution's legal and educational obligations. The contract must specify which data the tool holds, how long each category is retained, who may request export, and what happens after a course ends or procurement terminates. Deleting an account may be appropriate while preserving a required academic record under authorized custody. Keeping every event forever merely because storage is inexpensive can increase exposure without educational benefit.

An exit plan needs more than a promise of CSV export. It should identify formats, object relationships, historical identifiers, grade provenance, attachments, accessibility information, and any proprietary assets that cannot be transferred. Test a sample export and a practical reconstruction of the educational task before the contract ends. Verify deletion or restricted archival when required, and document backup schedules and legal holds. LTI portability can make launching alternative tools simpler, but it does not guarantee ownership or portability of content and student evidence locked inside a commercial service.

Procurement, Certification, and Capability Claims

An institutional request for proposals should name LTI 1.3 Core and individual LTI Advantage services as separate requirements, with version and operational evidence. A statement that a product is “LTI-compliant” is ambiguous without identifying the particular specification, role, certified feature set, and current integration configuration. Vendor demonstrations should include an instructor selecting content, a learner completing it, a grade returning, access revocation, and recovery from a failed service call. Buyers should review certification records and their scope rather than assuming certification covers every optional operation.

The contract should include data terms, availability objectives, incident notification, support responsibilities, accessibility evidence, integration change notices, documented endpoints, and export rights. A bid evaluation matrix can compare actual user outcomes, deployment complexity, long-term maintenance, and exit cost. Certification can reduce uncertainty about protocol behavior; it cannot certify a specific institution's pedagogical choices, privacy compliance, staff training, or production performance. The Educational Technology Procurement and Governance sibling owns broader acquisition policy. Here procurement evidence is focused on whether promised interface functions work safely in the designated educational workflow.

A tool might pass a protocol suite but return grades to the wrong LMS assignment because a course-copy mapping is defective. Another might launch correctly for a test instructor but fail when actual student role claims are withheld. These are not contradictions: protocol conformance is a narrower claim than service reliability in context.

Contract Testing and Schema Compatibility

Automated contract tests use representative requests and responses to verify fields, type constraints, status values, scopes, and error codes. Tests should include optional and omitted claims, pagination, renamed contexts, changed roles, deleted memberships, duplicate score submissions, and mismatched identifier scopes. A test that uses one perfectly formed teacher account is too narrow to detect the operational failures that arise during a real term. Where possible, build reusable fixtures for student, instructor, teaching assistant, inactive learner, withdrawn learner, and administrator relationships.

Schema validation should reject malformed payloads but also verify domain-specific invariants. A score may be numerically valid yet exceed the documented maximum; a roster may contain two records with the same system-specific identifier; a Deep Linking response may point to a resource outside the registered provider domain. Contract tests should explain the policy interpretation as well as the technical comparison. When a vendor adds an optional field, an integration should not fail unnecessarily; when the meaning of an existing field changes, an integration should not silently accept it. Record test outcomes in the versioned integration inventory.

Staging, Synthetic Data, and Safe Pilot Design

A staging environment should resemble production in roles, launch pathways, service scopes, accessibility controls, and failure behavior without exposing actual student records unnecessarily. Use synthetic users, courses, and grade records whenever possible. Test data should include duplicate names, missing emails, cross-listed courses, withdrawn learners, grade changes, long titles, unusual characters, and multiple timezones. A pilot should limit the number of departments and tool purposes while maintaining the full institutional support and incident process.

A useful pilot produces evidence about both technology and instruction. Metrics include successful authorized launches, roster discrepancies, grade-reconciliation defects, learner task completion, support burden, accessibility blockers, and instructor time spent resolving errors. A technically fast launch does not establish improved learning. Define stop conditions before beginning, such as unexplained cross-course disclosure, wrong-student grade mapping, or an inaccessible required assessment. Pilots should avoid turning enrolled learners into involuntary security testers; provide a valid alternative path when a tool cannot reliably support the course objective.

Production integrations require monitoring across several distinct paths: browser launch, tool session establishment, roster service access, grade-service calls, content selection, and optional event delivery. A single uptime check on the vendor home page cannot show whether a particular institution's deployment is functioning. Service Level Objectives and Calendar Sensitivity

Educational demand is episodic. A short outage before an assignment deadline or during a campus examination period can have disproportionate impact. Define service objectives separately for interactive launch availability, membership refresh, grade-delivery timeliness, support response, and recoverability. A vendor can meet its general monthly availability target yet fail a critical course process at the worst possible time. Institutions should therefore identify protected instructional windows, exception handling, and alternative submission mechanisms.

Capacity planning needs realistic peak scenarios: simultaneous student launches before a quiz, large overnight roster imports, and bulk grade posting at the term close. Some interfaces operate asynchronously; students should receive accurate confirmation about whether work was saved locally, accepted by the provider, transmitted to the LMS, or posted for instructor review. Those are distinct milestones. Establish escalation contacts and communication templates before the term begins. When availability is degraded, a controlled pause and recorded alternative can protect fairness better than repeated uncontrolled submission attempts.

Release Management and Version Compatibility

LMS and tool vendors update independently. A change to browser authentication, an endpoint, JWT claim interpretation, API paging, content return format, or grade status handling can break a previously working integration. Each release should be assessed against the institution's registered versions and test matrix. A critical compatibility change needs notification, an owner, a regression plan, and a rollback or feature-disable strategy. Avoid automatic migration from older LTI launch models without explicit security and data mapping review.

Regression tests should include copied courses, changed instructors, renewed authentication sessions, old resource links, active line items, and prior grades. Production configuration must not be overwritten casually by staging defaults. When a vendor retires an API feature, identify affected courses from the dependency inventory and plan instructional substitutions. Version compatibility is a moving state, not a permanent attribute granted by a certification badge. Historical grade records and content links may still need to function or remain interpretable after a service is retired; this should be reflected in institutional change control.

Failure Recovery and Transaction Reconciliation

A recovery plan should distinguish what can be replayed safely from what requires human authorization. Retrying an idempotent roster read is different from resending a score after an instructor has edited a grade. For each transaction, preserve enough evidence to determine whether it was attempted, accepted, applied, and later modified. Retry bounded transient failures; quarantine unresolved permanent errors; and provide an explicit reconciliation workflow for conflicting state. Never make the absence of an acknowledgment alone trigger mass record rewrites.

Recovery after a vendor outage may require a list of learners who attempted assignments, a verified completion receipt, a gradebook comparison, and an instructional accommodation for missed deadlines. The institution should determine whether grading policy permits a manual entry or alternative assessment. Evidence should remain auditable, and a later automated retry should not override that decision. During incident closure, compare the vendor's completion records with the LMS's line items and the instructor's approved roster. A system is recovered only when the educational state is coherent, not merely when the HTTP endpoint answers again.

Multi-Tenancy, Cross-Campus Deployments, and Governance

A vendor may serve multiple institutions and campuses from shared infrastructure. The LTI issuer, client identifier, deployment identifier, and platform context are critical to keeping those relationships distinct. In a university system, one department may approve a tutoring tool while another does not. A multi-campus deployment may share a registration but require different data terms, grade policies, and service administrators. Local policy must be represented in configuration rather than inferred from broad network membership.

Isolation tests should attempt to access another tenant's resource link, roster, grade endpoint, and support records using otherwise valid credentials from the wrong deployment. A failure in organizational mapping can be as consequential as a cryptographic defect. Roles granted in one campus must not automatically authorize a user in another. A shared procurement arrangement should include a cross-campus incident plan, common monitoring expectations, and the ability to revoke one deployment without disabling unaffected sites. Institutional federation is a governance project as much as a single sign-on feature.

Migration from Older LTI and Custom Connectors

Older LTI 1.0/1.1 integrations and bespoke connectors may rely on security and data semantics different from LTI 1.3. Migration must inventory current resource links, shared secrets or signing arrangements, identifiers, grade-return features, roles, and content-selection workflows. A direct replacement of a legacy launch URL with a modern redirect URL is not a complete security upgrade. The new registration, keys, deployment, OIDC state, audience validation, and scoped service credentials must be implemented and tested deliberately.

A controlled migration may run old and new integrations in parallel for selected courses, but double posting and duplicate gradebook columns must be prevented. Instructors need to know whether existing content links will continue working and whether learner histories transfer to the new tool identity. Test copied courses and archived resources as well as current ones. Preserve auditability of grades created by the old connector. Retire legacy credentials only after required records are exported or safely retained and all planned educational workflows have a verified replacement or acceptable manual alternative.

Build Versus Buy and Integration Maintenance Economics

A custom connector can appear inexpensive when only the initial launch is considered. Long-run costs include security updates, platform-version changes, key rotation, support, monitoring, roster reconciliation, grade corrections, accessibility, vendor outages, and data exports. A standards-based integration may reduce bespoke work but still requires governance and testing. Compare the total cost of a vendor-certified product, an open-source connector, and a locally maintained custom integration over a realistic service lifetime rather than comparing only procurement prices.

An illustrative four-year planning model might budget $28,000 for initial integration, $9,000 per year for operations and testing, and $12,000 for migration and exit. The modeled total is $28,000 + (4 × $9,000) + $12,000 = $76,000 before discounting, licensing, and contingency. These amounts are fictional instructional assumptions, not market prices. The analysis should add potential outage cost, training, staff turnover, and support for high-stakes assessment. Decisions should reflect how many courses depend on the connector and what educational losses follow from failure, not simply the number of lines of code written.

Worked Case 1: A Successful Launch with a Failed Grade Return

A fictional biology department launches a remote microscopy activity through LTI 1.3. Students enter the tool successfully, complete their tasks, and see scores on the provider's website. The instructor's LMS gradebook remains empty. The first diagnosis should not assume the launch was insecure or that the activity was ungraded. LTI Core launch and AGS grade exchange are distinct paths. The team inspects approved service scopes, the presence of the AGS claim and endpoint information, the registration and deployment, line-item creation, score-delivery logs, and the mapping between the provider's activity and LMS gradebook column.

Suppose the provider reports that 128 of 130 submissions received an LMS acknowledgment, while the LMS shows only 126 current grades. The difference of four records requires transaction-level reconciliation, not automatic publication of four missing scores. Two may be delayed acknowledgments, one may be a withdrawn student, and one may have an instructor override; the numbers are illustrative, not a diagnosed incident. The academic owner confirms approved final results, the integrator investigates each state, and only authorized corrections are applied. Acceptance evidence includes matching line-item identifiers, valid score denominators, the preservation of manual edits, and notices to affected students where appropriate. The case shows why “students can open the tool” is a necessary but insufficient integration test.

Worked Case 2: Course Copy and Cross-Term Resource Mapping

An instructor copies a fall course containing 12 deep-linked laboratory activities into a spring section. The LMS creates a new context, but several external links retain a relationship to the earlier provider activity. A student who launches one link sees last term's discussion data. The probable concern is not just a bad URL: the resource placement and local vendor state were not correctly isolated by course context. The incident response disables the affected resource until the institution confirms that no other student's records are exposed, then investigates how the provider maps issuer, deployment, context, and resource-link IDs.

A correct migration procedure should establish whether the copy operation is supposed to clone a blank activity, reuse a shared read-only resource, or transfer an instructor's configuration. Tests should include a new learner, new teaching assistant, changed module location, and a prior learner who is no longer enrolled. Resource IDs may intentionally remain the same for shared content, but learner work and grades require appropriate separation. The institution documents the expected behavior in the tool contract, not just the LMS copy checklist. This case illustrates the difference between content reuse and unauthorized transfer of academic context.

Worked Case 3: A Withdrawn Student and Two Roster Sources

An engineering student withdraws at 10:15 a.m. The SIS publishes a roster update at 10:30, the LMS processes it at 11:00, and a simulation vendor refreshes NRPS membership at noon. The student has an earlier browser session that remains active. At 11:20 the student attempts to submit additional graded work. The institution must decide, under approved policy, when participation rights cease and how the provider should validate current authorization. Simply checking whether the original launch token was valid hours earlier does not settle the question.

A controlled implementation records effective enrollment time, LMS access revocation time, vendor session expiration, and the resulting submission state. It distinguishes access to previously completed work from the right to create new academic evidence. If the student later re-enrolls, mapping should not merge the new participation period blindly with the old one. Reconciliation reports identify differences between the SIS roster, LMS context, and vendor's current membership. The case demonstrates that OneRoster and NRPS may serve different points in the same lifecycle, and that delayed synchronization must be anticipated in both policy and technical controls.

Worked Case 4: An Accessibility Accommodation Across Platforms

A learner has an authorized extended-time accommodation for a required assessment. The LMS records the accommodation, but the externally launched testing tool does not receive a usable time adjustment or does not apply it. The learner's secure LTI launch succeeds and the score may ultimately return through AGS, yet the assessment opportunity is unequal. The institution should not treat success in token validation or grade delivery as evidence that the learner had equivalent access. Disability-related details should be limited to personnel and systems with a legitimate need to know.

Before the assessment, the instructor, accessibility office, and tool administrator should verify the actual timed workflow in a controlled test with the authorized accommodation applied. An operational solution may involve a confidential configuration mechanism, an accessible alternative assessment, or another approved adjustment. The institution should not send an unnecessary medical diagnosis in LTI claims to solve a timer problem. After an incident, the academic owner determines fair remediation and whether any recorded score is valid for evaluation. This case shows the necessity of end-to-end instructional testing and privacy-by-design, beyond either an LTI certification or an accessibility checklist alone.

Worked Case 5: Replayed Scores After an Integration Outage

At the end of a term, a statistics practice service is temporarily disconnected from the LMS. Instructors manually enter verified grades for affected students. When connectivity returns, the vendor's delayed retry queue begins sending older scores. If the integration treats every retry as a latest authoritative update, it can overwrite legitimate manual corrections. The technical restoration of API access would then create an academic integrity problem. The correct approach is to pause replay until the institution establishes whether each queued event is a duplicate, a new attempt, or a record now superseded by authorized review.

A reconciliation report includes learner mapping, assessment identifier, tool score and maximum, effective attempt time, LMS line-item state, last authorized edit, and the proposed action. The instructor or approved records steward resolves conflicts, and the integrator releases only safe transactions. Durable idempotency and version awareness reduce repeated-action errors; human authorization remains necessary for genuine grade disputes. The institution records the closure decision and tests that another retry will not reverse it. This case emphasizes that delivery acknowledgment and academic correctness must be monitored separately.

Worked Case 6: Replacing an External Tool During Procurement

A school district plans to replace a commercial reading tool with a new provider before the next academic year. Both vendors advertise LTI 1.3 support. The procurement team discovers that the existing courses depend on Deep Linking placements, some tool-specific progress histories, and gradebook mappings that are not contained in the LMS's ordinary course export. The new vendor implements LTI Core and AGS but uses a different content catalog and cannot import the old provider's annotations directly. Standards support lowers integration friction but does not provide automatic instructional continuity.

The district inventories each course's links, publisher licenses, learning objectives, student evidence, accessibility features, roster dependencies, and records-retention requirements. It assigns replacement tasks to academic departments, tests the new registration and deployment, verifies assignments and grade return, and provides an approved path to historical data. Some data may be migrated, some archived under institutional custody, and some require a teaching redesign. Before turning off the old integration, staff test a sample grade appeal, learner access to permitted prior work, and a complete course on accessible mobile devices. The case demonstrates that an exit plan must include both interface portability and the substance of instruction.

Measuring Integration Quality and Educational Impact

Engineering measures include accepted launch rate, time-to-activity, invalid-token rejection, roster mismatch prevalence, grade-posting lag, duplicate transactions, unresolved score conflicts, and time to restore service after a failure. They should be defined with precise denominators and scopes. “99.9 percent availability” can mean the vendor website answers requests while an institution's specific AGS integration is broken. A meaningful metric therefore names the transaction, environment, time window, affected user group, and successful outcome. Monitor exceptional cohorts and accessibility barriers, not just averages.

Educational measures ask different questions. Does the integration remove manual work without introducing grading errors? Can learners complete the intended assessment and obtain timely, accessible feedback? Do instructors know which results are provisional? Do students have a usable appeal and support route? An increase in click events or tool launches alone is not proof of better learning. Use a baseline, appropriate comparisons, and evidence from academic outcomes and user experience when assessing institutional value. The strongest integration measures combine correctness, confidentiality, availability, accessibility, staff workload, and learning opportunity rather than maximizing only transaction volume.

Common Failure Modes and Corrective Controls

Frequent implementation defects include using email as a universal identifier, treating launch success as grade-sync success, enabling unnecessary claims, ignoring missing NRPS membership, reusing staging keys in production, accepting unverified token parameters, and allowing stale scores to overwrite academic corrections. Other failures are less obviously technical: unclear ownership of final grades, missing accommodation propagation, insufficient staff training, untested course copies, and no exit plan for linked content. The controls vary, but each requires named ownership and observable acceptance evidence.

Glossary of Educational Interoperability Terms

Academic authority: Institutionally recognized responsibility for a decision or record state.

Access token: Credential for a bounded service request, commonly with scopes and expiration.

AGS: LTI Assignment and Grade Services, a set of defined gradebook-related APIs.

API contract: Agreed request, response, meaning, permission, version, and failure behavior.

Audience: The intended recipient or client identity asserted in a signed token.

Authentication: Verification that a subject or client is who it claims to be.

Authorization: Determination of permitted actions and accessible resources.

Bearer token: A credential whose possession can authorize access under its applicable rules.

Caliper Analytics: Standardized model for exchanging learning activity event data.

CASE: Competencies and Academic Standards Exchange standard for structured competencies or standards.

Client ID: A registered identifier assigned to an integration client.

Common Cartridge: A family of specifications for packaging and exchanging digital learning resources.

Conformance test: Test of compliance with a named technical specification or profile.

Context ID: Platform-scoped identifier for a learning context such as a course section.

Course copy: Creation of a new course environment using information from an existing one.

Credential rotation: Scheduled or incident-driven replacement of trusted keys or secrets.

Data contract: Agreement on ownership, structure, semantics, permissions, timing, and changes.

Deep Linking: LTI workflow that supports selecting or configuring external content placements.

Deployment ID: Identifier of a particular LTI tool deployment authorized by a platform.

Effective date: Time when an institutional state or policy change takes effect.

Event schema: Defined structure and meaning for activity records.

FERPA: U.S. Family Educational Rights and Privacy Act, applicable under its scope and conditions.

Grade reconciliation: Comparison and authorized resolution of inconsistent grade states.

Gradebook line item: Platform object representing an assessment or scored activity.

Idempotency: Property by which retrying an operation does not unintentionally repeat its effect.

Identity provider: Service authenticating participants for connected systems.

Issuer: Authority identified as producing a signed identity assertion.

JWT: JSON Web Token, a structured claims format that may be cryptographically signed.

JWKS: JSON Web Key Set used to publish trusted public keys.

Learning event: Record of an interaction or activity, not automatically a learning outcome.

LMS: Learning management system, the learning platform in many LTI integrations.

LTI: Learning Tools Interoperability, a standard for interactions between platforms and external tools.

LTI Advantage: Associated service specifications including Deep Linking, NRPS, and AGS.

Mapping: Governed correspondence between identifiers or meanings across systems.

NRPS: LTI Names and Role Provisioning Services for authorized context membership data.

Nonce: Single-use or otherwise replay-resistant value binding a returned authentication message to a request.

OAuth 2.0: Authorization framework used for scoped service access in modern LTI arrangements.

OIDC: OpenID Connect, an authentication protocol layered on OAuth 2.0 patterns.

OneRoster: Standard for structured educational roster and related data exchange.

Platform: LTI component that provides a learning context and launches an external tool.

Provenance: Evidence of the source and history of data or a decision.

QTI: Question and Test Interoperability specification for assessment content and processing models.

Registration: Security and configuration relationship established between platform and tool.

Resource link: Platform placement identifying a specific launchable resource.

REST API: Resource-oriented web interface using HTTP methods and defined representations.

Roster: Membership and role information for an educational organizational unit.

Scope: Bounded authorization for a service capability or resource.

Semantic interoperability: Preservation of data meaning across independently developed systems.

SIS: Student information system, often authoritative for enrollment and academic records.

SSO: Single sign-on, identity access arrangement that may support multiple applications.

State parameter: Flow-binding value used to defend an authentication request/response round trip.

Tenant isolation: Separation of data and permissions between customers or deployments.

Tool: External application receiving verified LTI launches or associated service access.

Trust boundary: Point across which the identity, authorization, or stewardship assumptions change.

Version compatibility: Ability of specified software and protocol versions to interoperate correctly.

WCAG: Web Content Accessibility Guidelines for web content and interface conformance.

Webhook: Event-driven HTTP notification endpoint, used in some proprietary integrations but not synonymous with LTI.

xAPI: Experience API, a specification for representing and communicating learning experience statements.
