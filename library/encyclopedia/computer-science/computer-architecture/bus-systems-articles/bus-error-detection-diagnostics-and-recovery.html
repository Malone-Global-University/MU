Scope and place within the Bus Systems unit

The Bus Error Detection, Diagnostics, and Recovery article completes the Bus Systems unit of the MGU Computer Science Encyclopedia. The parent Bus Systems overview introduces interconnect communication; this specialist article explains how an implementation recognizes failures, determines which requests and data remain trustworthy, contains their effects, restores service, and proves that recovery was successful. It treats the error-handling path of an interconnect, not the whole discipline of data-center incident management or the internal defect physics of a semiconductor.

The reader should distinguish a physical signaling error, a malformed or disallowed transaction, a destination-side processing failure, a timeout, and a software-visible data-integrity failure. They can trigger similar symptoms but call for different responses. A cyclic redundancy check (CRC) that detects a damaged link frame does not correct arbitrary data, and a completion status showing that a device rejected a command does not prove that the electrical link failed. Likewise, reestablishing a link does not prove that an interrupted write was safely undone.

This article complements Bus Signal Integrity and Electrical Constraints, Interconnect Isolation and Device Security, and Transaction Ordering and Memory Coherence. The emphasis here is observable error behavior, protocol guarantees, operational diagnosis, and safe return to service.

The reliability contract of an interconnect

A well-designed bus or fabric defines not just how successful transfers are performed, but what each participant may assume when something fails. The reliability contract identifies the integrity checks applied to control fields and payloads; which protocol participant detects failure; whether corrupt traffic is discarded; how errors are acknowledged or reported; whether the initiator may retry; and which reset or containment boundary applies if progress is no longer possible. The contract is part of an interface specification, not a convenience added by diagnostic software.

An interconnect may guarantee error detection without correction, local recovery without transparent end-to-end completion, or transaction completion with an explicit failure status. An application may demand stronger guarantees, such as storage durability or an exactly-once effect, that the bus does not supply. Engineers must enumerate these layers and avoid allowing a successful link-level replay to stand in for application-level confirmation.

A useful design record includes the requesting agent, addressed target, operation, data size, ordering context, state before failure, failure detector, resulting status, retry authority, and recovery owner. Without those particulars, a statement such as “the bus recovered” is ambiguous: the link might have trained again while the driver still owns stale descriptors.

Error detection, reporting, correction, containment, and recovery

These five terms describe distinct stages. Detection discovers that an invariant has been violated, for example a CRC mismatch. Reporting conveys evidence to a component able to act, such as an error-status register, interrupt, or kernel event. Correction reconstructs or replaces bad information, often through forward-error correction, retry, or a redundant source. Containment prevents a failure from spreading beyond a defined boundary. Recovery restores a coherent state and resumes permitted operation. Verification then checks that the intended work actually completed and no hidden corruption remains.

Some stages may be fused in hardware. A link receiver can check a protected packet, reject a corrupted copy, and participate in a replay without any visible software interrupt. That is local correction through retransmission, not necessarily error-free underlying signaling. Other events require software coordination: when an endpoint stops responding, blindly repeating a command risks duplicate side effects if the first attempt actually executed but its response was lost.

An end-to-end failure timeline

A single request may pass through software, an I/O translation unit, a root complex, switches, a device endpoint, DMA memory, and back again. The first detector along that path may not be the original cause. For example, a damaged PCIe link could cause a retry storm, followed by high tail latency, a driver timeout, and a storage command failure. The driver sees the timeout; the root port may hold the earlier link evidence. Root-cause analysis must connect these observations by topology and time rather than treat every symptom as independent.

The diagnostic timeline should capture the first error, not merely the loudest final alarm: initial CRC or link-training anomaly; retry count increase; transaction timeout; interrupt absence; queue reset; user-visible failure. A reliable trace notes timestamps from different clocks, counter baselines, power-state changes, workload identity, and firmware revisions. Root-port and endpoint clocks are not automatically synchronized; correlation must allow uncertainty.

Safe recovery often runs in reverse order of dependency: stop admitting new work, quiesce producers, determine which operations reached the destination, isolate a bad path, restore or reset affected components, reestablish address mappings and queues, validate delivery, then restart traffic. If the hardware lacks a reliable completion record, software must treat in-flight operations as outcome unknown rather than assume they all failed.

Fault taxonomy: physical, protocol, transaction, and software

Physical faults include weak signal margins, crosstalk, connectors with intermittent contact, clock or power instability, and temperature-sensitive components. Protocol faults include invalid framing, bad sequence numbers, illegal packet types, credit-accounting mistakes, ordering violations, or a transfer that never satisfies handshake rules. Transaction faults include inaccessible addresses, permission violations, unsupported requests, and target-side failures. Software and firmware faults include incorrect descriptor addresses, stale mappings, inappropriate timeouts, and inconsistent reset sequencing.

These categories intersect. A malformed address sent by faulty device firmware may lead to an IOMMU fault, yet the underlying root cause lies in descriptor construction. A marginal physical lane can produce framing errors, retransmissions, and eventually a software timeout without ever corrupting a packet delivered to the transaction layer. Conversely, a successful CRC does not validate that the sender placed the correct address or data in the frame.

A useful diagnostic hypothesis names both the layer where evidence appears and the layer where causation is suspected. For example: “Completion timeouts at the device driver correlate with increasing Data Link Layer retries on the upstream PCIe port during high-temperature stress.” This is more testable than “the bus is unstable.”

Transient, intermittent, permanent, and systematic errors

A transient fault is observed briefly and may disappear when the initiating condition ends. An intermittent fault returns under particular conditions, such as thermal expansion, vibration, or traffic bursts. A permanent fault persists until hardware, configuration, or software changes. A systematic fault results from a reproducible design or logic mistake, such as an unsupported burst sequence or an incorrectly programmed queue length.

The distinction informs recovery. A single corrected event may justify monitoring; a high and increasing corrected-error rate suggests deteriorating margin or a recurring configuration problem. Repeatedly resetting a device that deterministically misinterprets a valid command is not a repair. Conversely, immediately replacing hardware after one uncorrelated corrected bit error may be unjustified if the platform's documented operating model tolerates isolated corrections.

Fault persistence is also not equivalent to fault severity. One transient burst can cause data loss if an unsafe write crosses a protection boundary; a recurring correctable link retry can consume bandwidth for hours without exposing bad data. Assign severity from consequence and containment, not simply from recurrence.

Error domains and the limits of local checks

Error detection is meaningful only for the information protected over a specified domain. A link-level CRC might cover each transmitted packet between adjacent PCIe partners. After the receiving partner accepts the packet, a new hop or buffer may have its own protection domain. If a payload is corrupted before a checksum is calculated, the checksum can faithfully protect the wrong content. End-to-end protection must therefore sometimes cover data from an authoritative producer to its final consumer, including intermediate storage and transformation steps.

A designer should draw boundaries for physical hop, protocol transaction, cache-coherence message, DMA buffer, and application object. Each may use different integrity fields and recovery policies. End-to-end checksums, transaction IDs, memory ECC, and transport CRCs complement rather than replace one another. Scope labels matter: a system claiming “end-to-end CRC” should specify both endpoints and every buffer or transformation outside that coverage.

Correlating error events across boundaries also requires identity. A CRC failure at one switch port, a completion error at another port, and a timeout in a driver cannot be stitched into a causal chain without knowing which link, address, requester, function, or queue was involved.

Signal integrity and sampling failures

Hardware links convey symbols through electrical channels that have limited noise and timing margins. Reflections, intersymbol interference, jitter, skew, crosstalk, inadequate termination, or power-supply disturbances can cause a receiver to sample an incorrect symbol. The resulting symptom depends on the coding and protection layer: a CRC mismatch, decoder violation, disparity error, failed link training, or a burst of retransmissions.

Signal integrity testing seeks the underlying physical margin, while protocol error logging records digital consequences. A clean application workload does not prove the eye opening is generous: a link may silently retry marginal frames. Likewise, a poor-looking eye plot does not independently prove that a specific logical transaction failed; the measurement setup, equalization state, and receiver criteria must match the implementation.

Evidence is strongest when controlled changes isolate a variable: shorten or replace a cable, reduce signaling rate, move to another connector, measure equalization settings, or vary ambient temperature with all other parameters documented. A link-speed reduction that lowers error counts is a clue about margin, not a final diagnosis of which physical feature failed.

Parity checks and their coverage

A parity bit is often chosen so a group of data bits has even or odd parity. With even parity, the transmitter appends a bit that makes the total number of one-bits even; the receiver recomputes the parity. A one-bit corruption changes parity and is detected. Any odd number of flipped bits changes overall parity, while an even number leaves parity unchanged. Thus parity cannot guarantee detection of all multi-bit errors and does not identify which bit is wrong.

Parity remains useful for inexpensive local storage and control structures where the system can halt or recover by replaying the affected unit. It is not a general substitute for error-correcting codes or strong transaction integrity. Adding one parity bit to every 64 data bits consumes 1/64, or 1.5625%, of additional raw bits before any framing overhead; whether that overhead affects an external bus depends on its physical representation.

A parity alarm should be attributed to a specific protected unit, such as a FIFO entry, tag array, or bus beat. Reporting only “parity error” discards the location and history needed to distinguish a bad storage cell from a transmission defect.

Cyclic redundancy checks and error-detection guarantees

A cyclic redundancy check (CRC) treats a protected bit sequence as a polynomial over a two-element field and computes a remainder under a chosen generator polynomial. Its effectiveness depends on polynomial selection, message length, framing, initial/final conventions, and the fault patterns under consideration. A CRC is an error-detection code, not cryptographic authentication, and not an error-correcting code on its own.

A well-selected CRC can guarantee detection of particular error classes under specified lengths and detect many others with high probability. The frequently cited residual random-error approximation of roughly 1 in 2^r for an r-bit CRC requires a suitable random-error model; it is not a universal bound for adversarial modifications or all possible burst patterns. For link engineering, use the exact polynomial and maximum protected data length defined by the interface specification rather than treating “CRC-32” as one unambiguous design.

CRC mismatch handling must state what happens next: discard the frame, request replay, count the event, report a threshold violation, or enter recovery. A receiver that detects damage but still presents the bytes as valid to higher layers has not fulfilled a meaningful data-integrity contract.

CRC boundaries, headers, payloads, and stored state

A packet may include route information, type identifiers, lengths, payload, and integrity fields. Coverage is not necessarily identical for all fields. Some protocols protect only a link-layer representation; others add separate end-to-end digest fields. Data modified legitimately by routers or bridges must be accounted for when designing a check over end-to-end content. A valid link CRC after translation merely confirms the transmitted bytes matched the check calculated on those bytes.

Engineers should inspect whether a check covers payload length, transaction ID, byte enables, addressing, poison flags, and any transformations that occur after verification. An unprotected length field can lead to unsafe parsing or truncated delivery even when the payload check itself passes. On-chip fabrics also need consideration of buffer and crossbar corruption that may occur after a link check is validated.

A strong verification plan injects controlled faults into each meaningful field and observes whether the correct error status is reported without a silent commit. Simply changing the payload at one stage and watching CRC rejection proves only that one insertion point is covered.

Forward-error correction and retransmission

Forward-error correction (FEC) adds redundancy that allows a receiver to correct certain errors without waiting for a fresh transmission. Automatic repeat request (ARQ) instead relies on error detection, acknowledgement, and retransmission. These mechanisms can coexist in a high-speed interface: FEC addresses likely symbol errors, and a retry or higher-level recovery path handles residual failures or lost control information.

FEC performance should be described by code rate, corrected symbol-error patterns, residual error rate, latency, and behavior after an uncorrectable block. Stronger correction can cost throughput, logic area, and pipeline delay. ARQ costs additional bandwidth and delay under error conditions and needs duplicate recognition and bounded buffers. Neither method makes permanently failed hardware trustworthy.

A reliability design must specify which errors are corrected and invisible, detected but not correctable, reported to software, and escalated to reset. Without this separation, counter names such as corrected_errors can mislead operators into thinking they measure the same category across different link technologies.

ECC in registers, SRAM, DRAM, and fabric storage

Error-correcting codes (ECC) are widely used to protect stored data in caches, register arrays, queues, and external memory. A common single-error-correction/double-error-detection (SECDED) scheme can correct an isolated bit error and detect certain larger errors within a protected codeword, but its behavior on multiple simultaneous faults must be understood from its code definition. An uncorrectable ECC event should not be treated as though a receiver can reconstruct the lost data by wishing it away.

The interconnect relevance is twofold. First, a fabric itself buffers request and response information in FIFOs, arbitration queues, and switch memories that may need ECC or parity. Second, a transaction may receive an error, poison indication, or fault notification because a downstream memory element detected uncorrectable data. A successful bus transfer can carry an error indication rather than valid application data.

Memory scrubbing can periodically check and correct supported errors in storage, reducing accumulation of correctable faults between accesses. It is not a replacement for link-level integrity checking, since an in-flight corrupted packet and a corrupted stored cache line occupy different protection domains.

End-to-end data integrity and address protection

An interconnect can transfer bytes correctly yet place them in the wrong location because of faulty addressing, translation, or command metadata. Data integrity therefore includes correct data at the correct destination for the correct operation. Technologies may attach logical block addresses, sequence identifiers, reference tags, or application checksums to data so later consumers can detect misdirection or stale delivery.

Protection needs to survive translation and storage rules. A block-level integrity tag that references a logical block address may need controlled transformation when data is remapped or replicated; otherwise a legitimate move can trigger a false alarm. Conversely, a translation layer that silently drops the reference tag creates a gap in end-to-end coverage. This matters when an NVMe controller or accelerator performs DMA into memory through a PCIe fabric.

An engineering review should map every place data can be copied, transformed, cached, or persisted, and record which actor verifies each integrity field. Without named verification points, an “end-to-end” claim is not testable.

Sequence numbers, duplication, and replay buffers

Sequence numbers allow a transport to distinguish new packets from retransmissions and detect missing or reordered link units within the protocol's permitted window. A replay buffer retains sufficient transmitted information until its delivery is acknowledged. On a negative acknowledgement or timeout, the transmitter may resend unacknowledged units according to the protocol rules. This is a link-local recovery mechanism when implemented by the data-link layer.

Sequence numbers have finite width and wrap; comparisons must follow the protocol's modular arithmetic and maximum outstanding window. A naïve ordinary integer comparison can misinterpret a legal wraparound as a backward jump. The receiver must also avoid executing the same transaction twice merely because a packet was delivered again. Link-layer retry normally suppresses duplicate acceptance within its protection domain; the application still needs its own idempotency strategy after broader connection failure.

Correct replay-buffer sizing depends on link latency, acknowledgment timing, throughput, and the maximum unacknowledged window. A buffer that fills may throttle new traffic rather than corrupt it, but a failure in credit or acknowledgment bookkeeping can turn backpressure into a deadlock or timeout.

Detecting lost progress and transaction timeouts

A timeout is an inference from absent progress over a specified period, not direct proof of a corrupted bit. Possible causes include a stalled destination, congestion, bridge deadlock, lost interrupt, device reset, software scheduling delay, or a legitimate operation exceeding an unrealistic threshold. Timeouts are useful because a broken component may never generate an explicit error response.

Timers must be attached to the correct stage: request acceptance, response arrival, link acknowledgment, command completion, or software-visible notification. Starting a timer before arbitration and then blaming the endpoint for bus congestion confuses layers. An operation may also have multiple legal response phases with different deadlines.

Timeout policy should explicitly distinguish detecting slow service from declaring the outcome unknown. If a posted write was accepted somewhere upstream, the fact that software has not observed completion may not establish whether the ultimate side effect occurred. Recovery must consider ordering, the target's own error model, and whether the operation can be safely retried.

Retry safety, idempotence, and exactly-once assumptions

A retried read from a stable, side-effect-free address is often safer than retrying a register write that acknowledges an interrupt, increments a counter, launches a DMA engine, or erases storage. The repeated write may have a second effect even if the original response was lost. Idempotent operations can be repeated without changing the final intended state; non-idempotent operations require an outcome-reconciliation method or unique command identifier.

Hardware link replay is usually designed so receivers do not expose duplicate accepted frames to higher protocol layers. That guarantee does not extend automatically to arbitrary software retries after a device reset or network loss. The driver should consult its interface's completion and reset semantics before resubmitting a descriptor or command whose execution status is uncertain.

The basic review question is: If this operation executed but its reply was lost, what would a second execution do? If the answer is “allocate another resource,” “write a second value,” or “advance the ring twice,” blind retry is unsafe. Record a generation number, stable transaction identity, or explicit post-failure readback where the protocol supports it.

Acknowledgments, negative acknowledgments, and backpressure

Acknowledgments serve different purposes at different layers. A link-layer ACK may establish that a frame was correctly received by a neighboring component, not that an application committed its data. A transaction-level completion may establish that a target responded, not necessarily that a storage device persisted every buffered write across power loss. A software notification may simply indicate that the device placed a completion record in memory.

Negative acknowledgments trigger correction or fault handling only if the protocol defines how a sender responds. In credit-based systems, a sender can be blocked while waiting for receiver buffer space even if there is no corruption. Treating credit starvation as a corrupted-link event may provoke unnecessary resets and loss of useful diagnostic evidence.

A robust monitor distinguishes CRC errors, replays, credit waits, response timeouts, and application completion failures. These have different root causes, and their counters should not be combined into a single “bad transfers” figure without classification.

Error severity and escalation policy

Severity should express the ability to continue trustworthy service, not merely the presence of an error bit. A corrected error may require no immediate software intervention but should be counted. A nonfatal uncorrectable transaction may cause one operation to fail while the path remains usable. A fatal error can make the link or hierarchy unreliable until containment and reset. The exact names and rules differ by protocol.

An escalation policy typically uses the rate, distribution, affected criticality, recovery success, and correlation with neighboring faults. A single corrected error on a noncritical peripheral may merit a baseline record; steadily rising CRC failures across a common upstream port can justify withdrawing traffic and inspecting the physical segment. An error affecting privileged DMA transactions or trusted storage metadata may require more urgent action than the same raw event on a disposable test path.

Escalation thresholds must document observation intervals, counter wrap and resets, device power cycles, and which events are expected under intentional fault testing. Rates without denominators can be misleading because a bus carrying 100 times more traffic has more opportunities for the same per-bit failure probability.

AXI response signals: OKAY, EXOKAY, SLVERR, and DECERR

AMBA AXI uses response encodings that communicate transaction results. OKAY indicates an ordinary successful response, EXOKAY relates to successful exclusive-access behavior under applicable rules, SLVERR reports an error associated with a subordinate response, and DECERR generally reports a decode or routing failure. Precise meanings, containment annotations, and side effects depend on the revision and profile of the Arm specification. A bridge must propagate or translate failures in a way that preserves relevant semantics.

AXI read responses can include per-beat response information; write response handling is separate. The protocol defines how bursts continue or terminate under errors; an implementation must not arbitrarily abandon the remaining required handshakes and deadlock the initiating manager. In particular, error status is not permission to leave valid/ready channels permanently stalled.

Software-visible interpretation must also be cautious: an AXI SLVERR does not prove which physical transistor failed. It might mean the addressed device rejected an unsupported access, encountered an internal condition, or could not complete a requested operation. See the official Arm AMBA AXI Protocol Specification for exact rules.

APB error signaling and peripheral register accesses

The AMBA Advanced Peripheral Bus (APB) commonly uses a setup phase and an access phase. A transfer completes when the protocol's selection, enable, and ready conditions are met; an implementation that provides PSLVERR can indicate an error associated with the completing transfer. The signal is optional in some APB versions and configurations, so the absence of an error signal must not be misread as evidence that every peripheral reports all failures.

APB is often used for control and status registers, where a rejected operation may have important semantics. A write to a reserved register address, an access while a device is unpowered, or a peripheral bus bridge fault may be mapped to a controller-visible error response if the design provides that behavior. A timeout watchdog may be needed for a peripheral that never asserts ready, but the timeout response is a system integration policy and not automatically furnished by every APB endpoint.

The official Arm AMBA APB Protocol Specification documents optional error signaling and the protocol's timing rules. Designers must define safe default responses for unmapped addresses and avoid allowing a defective subordinate to hold an entire peripheral hierarchy indefinitely.

PCIe Physical and Data Link Layer error handling

PCI Express separates physical signaling, Data Link Layer protection, and transaction delivery. Physical coding and link training establish a viable connection. In conventional non-FLIT operation, the Data Link Layer uses sequence information, acknowledgments, and link CRC checks to support reliable delivery of Transaction Layer Packets across an individual link. Failed checks can lead to replay without changing the transaction semantics visible to the endpoint.

Modern PCIe revisions introduce different framing and error-control details, including FLIT-mode operation in applicable generations. Do not assume that one historical LCRC/replay description applies unchanged to every signaling mode. The right diagnostic source is the implemented generation, negotiated mode, device capability, and documented error register. Link-layer correction is also not an end-to-end guarantee covering every device buffer, application object, or persistence boundary.

Repeated correction can be a diagnostic symptom even if software requests remain successful. Rising Bad TLP, Bad DLLP, replay, or receiver-error counts should be correlated with link speed, width, connectors, equalization, temperature, and workload. A damaged packet rejected by the Data Link Layer normally must not be delivered as valid higher-layer payload.

PCIe transaction and completion errors

At the transaction level, an endpoint or bridge may return a completion indicating that a request could not be fulfilled, or a request may encounter routing, support, or access limitations. Unsupported Request, Completer Abort, and Completion Timeout have different meanings: a request can be structurally or functionally unsupported, a completer can reject or abort service, or a requester can fail to receive the expected completion before its applicable timeout.

A completion timeout does not establish that an underlying frame had a CRC error. It may arise from an inaccessible target, incorrect requester behavior, reset in progress, congestion, or a response dropped elsewhere. Conversely, a properly reported Unsupported Request can be a deterministic programming fault rather than a failing interconnect. These conditions should be reported with requester identity, target context, address information where available, and the operation being attempted.

Transaction error diagnostics must distinguish posted and non-posted requests. A posted memory write has no normal completion packet reporting its success to the originating requester, so software may need device-specific status, ordering, or readback mechanisms to validate a higher-level effect. An interrupt that follows a write cannot by itself prove storage durability.

Advanced Error Reporting in PCI Express

PCI Express Advanced Error Reporting (AER) provides standardized extended error capabilities on supporting hardware. Relevant registers and messages help classify correctable and uncorrectable conditions, with uncorrectable errors categorized by severity into nonfatal and fatal cases. Operating systems may collect and route this information to the platform and affected device drivers. AER evidence is valuable because it distinguishes a path that corrected an error from a request that failed or a hierarchy that became untrustworthy.

Correctable errors are generally recovered at hardware level and need not terminate software transactions. A nonfatal uncorrectable event may leave the link operating while the affected transaction becomes unreliable. A fatal event may require coordinated isolation and reset of the affected hierarchy. Classification is protocol-defined; application seriousness can still differ—for example, failure of one storage command may be operationally critical despite a nonfatal link classification.

The Linux kernel's PCIe AER guide describes error classes, messages, statistics, and driver recovery integration. Deployment details vary with firmware ownership, platform configuration, device capabilities, and kernel version; no universal OS console message format should be assumed.

Downstream Port Containment and fault isolation

Downstream Port Containment (DPC) is a PCIe containment mechanism that can limit the spread of certain downstream errors by isolating a port or hierarchy, depending on supported features and platform policy. Containment is a protective interruption: it may prevent further harmful transactions, but it also makes the affected devices temporarily inaccessible. A downstream accelerator or SSD may disappear from normal software operations while containment and recovery run.

Containment is not the same as successful recovery. The platform must decide whether to reset the affected link or device, restore configuration, invalidate stale DMA assumptions, notify drivers, and determine which outstanding operations were lost or have unknown outcomes. Devices behind a common switch path may be affected together even if only one endpoint originated the error.

The fault domain should be measured explicitly. A port-level containment event that interrupts three healthy endpoints behind a switch has a different availability impact from a recoverable endpoint-local fault. Good topology design provides meaningful isolation boundaries and avoids unnecessarily coupling critical and noncritical services.

Error reporting in switches, bridges, and networks-on-chip

A bridge can detect an invalid address, an unsupported burst, response corruption, or a downstream timeout. It may synthesize an upstream error response, log a local fault, or trigger a reset. The bridge should preserve enough information to distinguish the upstream initiator, the failing downstream resource, and the operation's completion state. Returning a generic error with no fault location makes hierarchical diagnosis difficult.

Networks-on-chip add router buffers, virtual channels, credit flow, packet routing, and possible path redundancy. Error cases include packet-integrity failure, invalid route, buffer overflow or underflow, credit mismatch, deadlock, livelock, and failure to make forward progress. Their detection and recovery are implementation-specific; there is no single standardized NoC equivalent of a PCIe AER record across all SoC fabrics.

Coherent fabrics have additional obligations: a lost ownership response, duplicated invalidation, or poisoned line can threaten multiple agents' views of memory. The recovery strategy must respect cache-state invariants and may need to quarantine a line or stop a coherent domain, rather than merely retry a data transfer. Fabric correctness depends on both byte integrity and protocol-state integrity.

Cache coherence, poisoned data, and data integrity

A coherent fabric can carry an explicit indication that a data beat, cache line, or transaction is poisoned or otherwise untrustworthy, when supported by its protocol. The meaning of a poison indication is not “data is corrected”; it warns consumers that the associated content must not be treated as ordinary valid data. A receiver may raise an architectural exception, record a fault, or decline to consume it based on the machine's reliability architecture.

Poison propagation is a deliberate alternative to silently substituting arbitrary data. It lets downstream components distinguish a detected uncorrectable error from a legitimate zero value or a normal completed read. However, systems need clear rules for how poison travels through queues, caches, copy engines, and memory controllers, and where it becomes a software-visible failure. A poison flag lost at a bridge can convert a contained detectable problem into silent data corruption.

Verification must include the flag's lifetime, the data path it qualifies, and behavior when an operation carries both valid and invalid portions. Cache-coherence state transitions and writeback ordering cannot be casually skipped during recovery without risking a second, independent error.

DMA faults and incomplete data movement

DMA transfers are often long-lived operations with descriptors, multiple outstanding reads or writes, and completion queues. An error can occur while fetching a descriptor, translating an I/O virtual address, reading a source buffer, routing an interconnect request, or writing the destination. The driver must identify which descriptor and which byte range can be trusted before reusing a buffer or reporting success.

An IOMMU translation fault is not necessarily a link-integrity fault; it may indicate an invalid mapping, out-of-range DMA, stale address-space identity, or malicious request. Error recovery should first preserve and inspect the requester information, mapping generation, address, and permission. Simply retrying the same request against the same invalid map can create an infinite fault loop.

DMA completion is also not equivalent to a safe application commit. Software may need coherent mapping rules, cache synchronization on noncoherent platforms, and fences that publish memory before reading completion records. Reinitializing rings or resetting a device too early can cause DMA into buffers that have been returned to another owner.

NVMe and storage transport error boundaries

An NVMe command issued by software can fail at several distinct layers: software submission, PCIe transport, controller command execution, flash media, or host memory delivery. A PCIe CRC or link issue is different from an NVMe command completion status reporting a controller or media error. NVMe health information and error logs can provide evidence of media or command-level failures, but they should be correlated with PCIe AER and host diagnostics rather than assumed to identify the only cause.

The NVMe Base Specification documents health and error information structures, while Microsoft's NVME_ERROR_INFO_LOG describes a host-facing representation of error entries. Specific data, completion status, and log behavior depend on revision and controller implementation.

A storage write that did not receive normal completion may have reached volatile controller memory or persistent media, depending on controller guarantees and command status. A recovery plan must use the storage interface's durability, flush, queue, and reset rules; bus-level reconnect alone is insufficient to resolve uncertainty about durable state.

Operating-system and driver recovery coordination

The operating system often owns the sequencing between low-level hardware containment and device-driver recovery. A driver may have to stop new submissions, freeze queues, acknowledge an error condition, release or invalidate descriptors, restore configuration, retrain or reset the device, and rebuild its software view of outstanding work. Recovery callbacks are therefore state-machine transitions, not mere notifications.

Linux documents PCI error-recovery callbacks such as error_detected(), mmio_enabled(), slot_reset(), and resume() for supporting drivers and platforms. The callback path depends on error severity, platform capability, and driver responses. Importantly, the point at which MMIO becomes available may precede safe resumption of DMA, and a successful reset does not automatically reconstruct all queues and mappings. See Linux PCI Error Recovery.

Other operating systems have different reporting paths and driver interfaces, but the engineering requirement is the same: no component should resume producing traffic before the next component has reestablished its required state. The contract should identify who declares the device healthy and who reconciles operations with uncertain completion.

Error telemetry and trustworthy counters

Useful telemetry has location, class, time, rate, workload, and recovery outcome. A count of corrected PCIe errors may be divided by link, port, function, and event type; an SoC bridge might log initiator ID, address, error code, and cycle timestamp. The first event after a clean baseline is often more informative than the last message in a noisy cascade. Counters must be read before reset or cleared only after capture.

A telemetry system should record bit width and wrap behavior, reset provenance, accumulation interval, sampling frequency, and possible dropped or rate-limited messages. Difference two snapshots of a monotonically incrementing counter only after confirming they belong to the same device generation and operating epoch. A counter that resets during hotplug may appear to decrease and produce a fictitious negative rate if treated naively.

Correlating retry counts with throughput and latency can reveal an otherwise hidden degradation. For instance, rising replay counts and falling goodput during elevated temperature indicate a likely integrity margin or retry-cost problem, but the observation still must be isolated from simultaneous workload changes and thermal throttling.

Evidence collection before reset or power cycling

A reset can destroy the most useful state: error status, first-failure address, device logs, link-negotiation history, outstanding descriptor IDs, and volatile firmware traces. Diagnostic practice therefore prefers collecting a bounded evidence set before reset when doing so is safe and permitted. If a device is actively corrupting memory, immediate containment may take precedence over preserving logs; safety and data integrity outweigh perfect observability.

A useful incident record includes host identity and topology, affected BDF or stream identity, upstream port, negotiated link speed and width, firmware and driver revisions, status and syndrome registers, error counter snapshots, temperature and power conditions, recent changes, a precise timeline, and a statement of which operations are unknown. Record any containment, reset, or downgrade action with its timestamp so subsequent measurements have context.

Treat error telemetry as sensitive where it reveals device topology, memory addresses, or tenant activity. Diagnostic access should be restricted and logs redacted appropriately before publication outside the system's trusted operations team.

Topology-first fault localization

Fault localization begins with the communication route. Draw the initiator, local bus, bridge, uplink, switches, downstream port, and endpoint. Then place each error observation on that map. A common upstream port whose errors increase across several endpoints suggests a different failure domain from one endpoint whose internal error counter rises while the shared upstream link stays clean.

Use controlled contrasts: same device on another slot; same slot with a known-good device; lower data rate with identical traffic; one outstanding transaction instead of many; cold versus hot operation. Each contrast changes one likely causal variable while keeping a baseline. Interconnect failures often depend on channel length, connector quality, power delivery, software version, and traffic pattern together.

Do not replace parts solely because the component nearest to the user-visible failure is named in the log. A storage driver timeout can originate in the PCIe path, controller firmware, IOMMU configuration, or platform reset sequence. The investigation must identify the first violated invariant and its layer.

Status registers, timestamps, and error syndromes

A status register may report whether a condition occurred, whether it remains active, or how many times it happened. Sticky bits preserve a historical event until explicitly cleared. Write-one-to-clear fields are not normal read/write bits: writing one clears them, and an indiscriminate register write can erase multiple pieces of evidence. Error syndromes may encode a faulting address, data-bit position, tag, queue, or completion ID, but the interpretation is implementation-specific.

Timestamp analysis must account for CPU time, device-local counters, wall-clock time, and frequency changes. When a device reports a time value in clock ticks, the conversion to seconds requires knowing the tick period. When the clock frequency changes during the incident, a simple constant-rate conversion may be wrong. A trace should preserve the raw counter and its domain along with any transformed time.

Before clearing logs, verify whether reading a register itself has side effects. Read-to-clear registers, DMA status queues, and reset-cleared counters can alter the investigation. Driver documentation should define an evidence-capture order, especially during automated recovery.

Reset scopes and recovery state machines

Recovery is safest when the reset affects the smallest domain consistent with correctness. Candidates include retrying one transaction, resetting a queue, resetting a function or controller, retraining a link, resetting a downstream port, or rebooting the platform. Larger resets disrupt more healthy work and can erase evidence; smaller resets may leave persistent protocol or hardware state unrepaired.

A recovery state machine might transition through RUNNING → QUIESCING → ISOLATED → RESETTING → RECONFIGURING → VALIDATING → RUNNING. Each transition should have preconditions and a bounded timeout. On failure, the machine should escalate or leave the endpoint quarantined, not loop indefinitely through half-initialized states. A device generation or epoch number helps distinguish stale completions from a new post-reset instance.

Resetting a PCIe function, for example, is not necessarily the same as power-cycling a physical device or resetting everything behind a switch. The choice must follow device capabilities and driver requirements, including preservation or invalidation of configuration, DMA mappings, and interrupt resources.

Recovery after link loss and hot-plug events

A lost link can invalidate previously established routing and device reachability. Hot-plug or surprise-removal paths must prevent accesses to unmapped registers, cancel or fail pending work according to the driver contract, and release resources only when no outstanding actor can still access them. Reappearance of a device with the same visible name or address is not proof that it is the same uninterrupted execution context.

Software should treat reconnect as a new lifecycle event when the device or fabric can have lost state. Enumerate capabilities, restore only valid configuration, recreate queues, reestablish permissions, and verify firmware/device identity as required. Completion events from the previous epoch must not be mistaken for evidence of newly submitted work.

For storage or coherent accelerators, recovery includes higher-level ownership decisions. A device that vanishes during an in-flight write can leave the host without a definitive answer; the storage or application layer may need consistency checks or a journal replay independent of the bus reinitialization.

Fault injection and verification strategy

Fault injection intentionally exercises detectors, error paths, and recovery transitions without relying on random field failures. Depending on the hardware and platform, controlled tests may introduce malformed responses in simulation, flip protected bits in an RTL testbench, withhold ready/acknowledge, force queue overflow, inject software-visible AER test events, or simulate link removal. Injection into production systems is risky because it can trigger reset, data loss, or service interruption.

Tests must verify both positive behavior—the correct event is detected and contained—and negative behavior—unrelated traffic remains valid, no duplicate side effects occur, stale completions are rejected, and correct data is never silently changed. A test that simply confirms an interrupt fires does not prove that the response has safe semantics or that recovery preserves ordering.

A meaningful coverage matrix spans fault layer, duration, active transaction type, in-flight concurrency, reset scope, observability, and post-recovery verification. Repeat tests under realistic queue depths, mixed reads/writes, DMA, SMT or multicore traffic, and power-state changes; some race conditions appear only during overlap.

Reliability engineering metrics and reporting

Engineering metrics should be attached to a service and observation model. Examples include raw bit-error ratio, corrected events per transferred terabit, uncorrectable transaction rate, mean time between observed failures, recovery duration, percentiles of degraded latency, and the number of operations with uncertain outcome. A ratio without traffic volume and confidence interval can conceal important context.

Availability concerns whether a service can be used; data integrity concerns whether results remain correct; service reliability concerns successful operation over time. A design can have high uptime with unacceptable silent data corruption, or strict containment that briefly disconnects a device to preserve integrity. The goals should not be collapsed into one scalar.

Use a before/after comparison when evaluating an engineering change. If a firmware update reduces retransmissions but increases completion timeouts, the result is not automatically an improvement. Measure corrected and uncorrectable events, workload throughput, tail latency, resets, and application-level correctness together.

Worked example 1 — Parity detects one flipped bit, but not two

Consider an eight-bit data value 1011 0010. It contains four one-bits, so even parity appends 0. If transmission changes one bit—say the last data bit becomes 1—the total one-bit count becomes five while the parity field remains zero; the receiver detects a mismatch. If two data bits flip, however, the total parity remains even and the simple parity check can miss the event. The actual bit positions do not matter: the parity check sees only the odd/even number of changes.

Engineering conclusion: parity provides inexpensive detection of odd-weight corruption patterns but cannot locate or repair the flipped bit. If a control FIFO reports parity failure, the consuming pipeline should treat the record as untrustworthy. A replay path or reset may restore valid state if supported, but the parity flag alone does not specify recovery. Choosing a stronger code requires describing its protected word length and guaranteed error classes.

Worked example 2 — CRC overhead and scope

A fictional point-to-point transport appends a four-byte CRC to each fixed 1,024-byte payload and has no other overhead. Its raw frame size is 1,024 + 4 = 1,028 bytes. The maximum payload efficiency attributable to this field is 1,024 / 1,028 ≈ 99.611%; CRC overhead is 4 / 1,028 ≈ 0.389% of the transmitted frame. Actual throughput would be lower if the protocol also carries headers, idle symbols, encoding overhead, acknowledgments, or retransmissions.

Suppose the sender's DMA engine reads the wrong memory address, then constructs a valid CRC for that wrong data. The receiver sees a matching CRC: the communication channel delivered the bytes consistently, but the application got the wrong content. Engineering conclusion: integrity checks must be interpreted by coverage domain. Add command identity, address validation, or application-level verification where misdirected or stale data is a concern; do not interpret link CRC success as a complete end-to-end correctness certificate.

Worked example 3 — Residual random-error approximation

For illustration, assume a well-chosen 32-bit CRC and an error model in which undetected random corruptions are distributed approximately uniformly among all possible syndromes. The idealized probability of an undetected error conditional on an error having occurred is about 1 / 2^32, or 2.33 × 10^-10. This figure is not the rate of errors per packet; it is a conditional approximation under a model, and the actual guarantees depend on packet length and polynomial properties.

If a designer simply multiplies this number by an overall link bit-error ratio, the result can be misleading because one packet can have several bit flips, errors can be bursty, and packet-level errors are not equivalent to independently sampled single-bit events. Engineering conclusion: state the fault distribution, protected length, generator polynomial, and action after detection when analyzing residual integrity risk. A malicious sender who can construct the CRC is not constrained by the same random-corruption model; use authentication for adversarial tampering.

Worked example 4 — Converting a bit-error ratio into a diagnostic expectation

A hypothetical link sends 8 × 10^9 bits each second and experiences an independently modeled raw bit-error ratio of 10^-12. Its expected count of erroneous transmitted bits is 8 × 10^9 × 10^-12 = 0.008 per second, or approximately 28.8 per hour. This is a pre-correction illustrative expected value, not a prediction of user-visible transaction failures. A coding or replay layer can detect and correct some errors, and errors may be clustered rather than independently distributed.

If the receiver reports only two corrected events in an hour, the difference does not necessarily mean the counter is wrong: its event definition may count affected frames rather than bit flips, traffic may have been below full line rate, and the assumed error ratio may not describe actual conditions. Engineering conclusion: compare error counters only after normalizing by transmitted bits, negotiated mode, counting domain, and observation interval. Do not infer application reliability directly from the physical BER.

Worked example 5 — Replay reduces goodput without exposing corruption

Assume each packet attempt carries 4,096 payload bytes and 64 bytes of total framing and integrity overhead. Suppose each attempt independently succeeds with probability 0.995, and unsuccessful attempts are retransmitted until acknowledged. Under this simplified model, average attempts per successfully delivered packet are 1 / 0.995 ≈ 1.00503. Useful payload per attempted wire byte is therefore (4,096 / 4,160) × 0.995 ≈ 97.97% of the assumed gross byte rate.

This example excludes acknowledgement traffic, credit waits, link idles, and replay-buffer limitations. It also assumes the receiver never delivers a failed attempt as accepted payload. Engineering conclusion: goodput can decline even while all higher-layer requests eventually succeed. Diagnostic tooling should compare retransmission counts with throughput and latency rather than treating a successful user request as evidence of a clean physical path.

Worked example 6 — A timeout without a corrupt frame

A synthetic control interface uses a response timeout of 200 microseconds measured from request acceptance. A downstream device legally needs 150 microseconds for a conversion, but a bridge adds 80 microseconds of congestion-related queueing before the request reaches that device. If the timer starts at acceptance upstream, the total elapsed service time becomes 230 microseconds and the requester times out, even though every physical symbol and CRC was correct.

Whether the operation had already executed by the time of timeout depends on the bridge, target, and completion protocol. Increasing the threshold to 300 microseconds might prevent this particular false timeout, but could delay detection of a permanently stalled device. Engineering conclusion: define the timeout's start event, stop event, admissible queueing, maximum normal service time, and safe post-timeout action. Monitor congestion separately from corruption before changing thresholds.

Worked example 7 — PCIe corrected-error cascade

During a long DMA transfer, a PCIe link begins reporting corrected physical or Data Link Layer errors. The endpoint still receives valid higher-layer transactions because damaged attempts are rejected and replayed. The stream eventually slows enough that a software command exceeds its completion timeout. The driver reports “device not responding,” even though the earliest evidence is a rising corrected-error counter on the upstream port.

A practical investigation gathers the port's link width and rate, AER event class, replay-related counters where available, device and switch topology, recent thermal conditions, and a workload timeline. It then tests whether the error rate follows the physical path or endpoint by changing one controlled variable. Engineering conclusion: a final driver timeout is not always the primary fault. Correlate events across layers before replacing the storage device or suppressing the timeout.

Worked example 8 — AXI read error with continued handshakes

A fictional AXI interconnect forwards a four-beat read burst to a subordinate that reports an error on an access. The relevant AXI rules require valid response behavior and completion of prescribed transfer handshakes even when an error is indicated. The manager must not simply stop accepting remaining required read beats and leave the channel in an unresolved condition. The exact reported RRESP values follow the applicable protocol version and subordinate implementation.

If the transfer has already caused side effects, a returned SLVERR is not a universal guarantee that no state changed. The safe procedure is to mark the affected transaction failed, drain it correctly, preserve tag information, and apply device-specific recovery. Engineering conclusion: failure signaling is part of the normal protocol state machine. Error handling must not itself create a permanent stall, and data accompanying a failed response should not be treated as valid without a defined guarantee.

Worked example 9 — APB transfer with two wait cycles and an error

A fictional APB peripheral sees a setup phase, followed by an access phase in which PREADY remains low for two sampling edges. On the next access edge, it asserts PREADY and PSLVERR. Under the assumed APB configuration, the transfer completes on that edge with an error indication. The error should be attributed to the completing access; the two preceding wait edges were not failures by themselves.

A control bridge receiving this event may map it into an upstream error response, set a fault register, or notify software as defined by the system integration. The mere presence of PSLVERR does not prove an electrical defect. Engineering conclusion: separate waiting, acceptance, and terminal error status when investigating peripheral accesses. For designs that omit optional error signaling, provide alternative diagnostics for unsupported or failed peripheral operations.

Worked example 10 — Partial DMA completion after a device fault

A hypothetical descriptor orders a device to transfer 64 KiB into a host buffer. The engine performs four independent 16 KiB requests and completes the first three before an IOMMU translation fault prevents the fourth. Assume the engine's documented status record explicitly identifies the first 48 KiB as completed and visible under the required synchronization rules. Only under those assumptions may the driver trust the first 48 KiB; the remaining 16 KiB must be treated as invalid or incomplete.

If the engine reports only a generic descriptor failure, it may be unsafe to infer which bytes were written. Software must consult the device's completion granularity and possibly discard or reinitialize the entire buffer. A second attempt must not overwrite memory already released to another owner. Engineering conclusion: recovery depends on a documented partial-completion contract, not the number of bytes the driver expected to be transferred.

Worked example 11 — A posted write with an uncertain side effect

A CPU writes a doorbell register to launch device work over a posted-write-capable interconnect. Soon afterward, the link fails before software can perform a device-status readback. The CPU may know that the outbound write was accepted into an upstream buffer, but that does not automatically prove that the endpoint processed the doorbell. Repeating the same doorbell after reset might launch duplicate work if the first effect happened.

A safe design uses a descriptor generation or command sequence number that the endpoint checks before executing side effects, together with a documented way to recover or reconcile pending work after reset. For an existing device without such capabilities, its driver must follow vendor-specified reset semantics rather than assume exactly-once execution. Engineering conclusion: distinguish transport acceptance, destination execution, and application completion. Blind replay of side-effectful writes is not a universal recovery operation.

Worked example 12 — Correctly interpreting a wrapping error counter

A 16-bit hardware counter increases modulo 65,536. Before a test its value is 65,530; afterward its value is 14. If at most one wrap occurred and no reset intervened, the increment is (14 − 65,530) mod 65,536 = 20 events. The naïve signed difference is negative and plainly wrong. If several wraps occurred, the two snapshots alone cannot recover the true count.

Suppose the sample interval was 10 minutes and the link transferred 2 terabits during that interval. The observed normalized rate is 20 / 2 = 10 events per terabit, based on this counter's event definition. It is not a bit-error ratio unless each event corresponds to exactly one erroneous bit and the denominator is appropriate. Engineering conclusion: preserve counter width, reset epoch, wrap assumptions, and traffic volume with each error-rate report.

Worked example 13 — Finding the common failure domain in a switch tree

A root port feeds a switch with three downstream endpoints. All three begin showing transaction delays while the switch's single upstream link reports rapidly increasing corrected errors. The three devices are unlikely to have developed the same independent physical fault at precisely the same time. A common upstream link, switch power rail, or shared fabric resource becomes the first isolation target.

A reasonable investigation records the endpoint-to-port map, separates traffic to each endpoint, checks whether the shared uplink's counters rise while any one endpoint is active, and inspects the upstream channel and switch configuration. The evidence does not prove the uplink alone is defective: the switch firmware or power system could cause correlated symptoms. Engineering conclusion: use topology and correlated first events to prioritize tests, not to prematurely declare a unique root cause.

Worked example 14 — Rejecting stale completions after reset

A device's old queue has command slot 7 occupied by request A when a failure occurs. Recovery resets and recreates the queue, then reuses slot 7 for request B. If an old completion for A emerges late and the software matches only the slot number, it may falsely report B complete. One defense is to associate completions with a generation or phase discipline supported by the hardware protocol and to invalidate all old-epoch state during queue reset.

Not every device exposes an arbitrary epoch field, so implementations must follow their specific queue and reset guarantees. A driver can use internal generation tracking and carefully ordered queue recreation where possible. Engineering conclusion: resetting hardware and zeroing software counters is insufficient unless the recovery contract ensures that old work cannot masquerade as new work.

Worked example 15 — Redundant paths and correlated faults

Imagine two independent fabric paths, each having a 1% probability of being unavailable during a specified observation window. If their failures were statistically independent and a system could use either path, the probability of both being unavailable would be 0.01 × 0.01 = 0.0001, or 0.01%. This simple benefit disappears if both paths share a failed power source, switch firmware defect, or administrative configuration error.

Real designs therefore inspect common-mode dependencies: redundant cables that terminate on one backplane are not full path redundancy; two storage controllers sharing one corrupted namespace may provide availability without integrity. Failover itself must preserve ordering and determine what happens to outstanding requests. Engineering conclusion: state independence assumptions, recovery coordination, and consistency rules before claiming a redundancy-related reliability gain.

Worked example 16 — Measuring the availability cost of recovery

Suppose a synthetic device experiences eight recoverable link outages per hour. Each recovery interrupts service for 30 milliseconds and outages never overlap. Total interruption in an hour is 8 × 0.030 = 0.24 seconds. The fraction of the hour unavailable from these events is 0.24 / 3,600 ≈ 0.0000667, or 0.00667%, corresponding to about 99.99333% availability for this narrowly defined cause alone.

This arithmetic ignores data reconstruction, retries that remain visible to applications, unplanned queue drainage, and unrelated outages. A server might have a higher service-level impact if brief interruptions violate a low-latency contract, even when time-based availability remains high. Engineering conclusion: report both duration-based availability and transaction correctness/latency impact. A successful automatic reset is not proof that an application met its service objective.

Worked example 17 — An on-chip credit-accounting stall

A fictional NoC link has eight downstream receive credits. The transmitter sends eight flits, consumes all credits, and waits. The receiver properly frees buffer entries but a faulty credit-return path reports only seven releases. Eventually the sender waits forever despite available downstream storage. There is no required data-bit corruption; the failure is in flow-control bookkeeping and forward progress.

An appropriate design monitor tracks credits granted, consumed, and returned and asserts that the outstanding count remains within [0, 8]. A watchdog can detect prolonged inactivity, but resetting every router without determining in-flight packet ownership may violate ordering. Engineering conclusion: protocol-state integrity and conservation rules are as important as payload checks. Inject lost-credit and duplicate-credit faults during verification, not merely flipped data bits.

Worked example 18 — Diagnostic decisions with incomplete evidence

A workstation reports occasional SSD timeouts after a firmware update. AER corrected-error counts are unchanged, but command-level errors appear in the NVMe error log. A careless diagnosis would blame PCIe just because the device uses PCIe transport. The available evidence instead supports investigating controller firmware behavior, queue state, storage command interpretation, and whether the failures occur without transport anomalies.

Next steps include preserving exact error statuses, comparing firmware revisions, testing a known-good workload with controlled settings, checking the command timeout path, and observing whether errors follow the device or platform. It may still be possible for a link defect to evade a particular counter or log, so the absence of an AER increase is not a mathematical exclusion. Engineering conclusion: make the next test discriminate among competing hypotheses; do not call a root cause confirmed merely because it is plausible.

A practical diagnostic decision framework

A disciplined investigation begins by asking what failed first and where. If a CRC or receiver error precedes a timeout, inspect the physical link and its replay behavior. If the physical link is quiet but the target returns SLVERR or a storage command status, inspect the subordinate's legal access range, internal state, and firmware. If a device generates DMA translation faults, inspect address mappings, access rights, and descriptor ownership before replacing cables. If many endpoints degrade together, map their common uplink, switch, or power domain.

After the initial classification, preserve the event evidence and choose a reversible discriminating test. Keep a known-good baseline for throughput, latency, error count, temperature, and firmware. Use rate or width reduction, lower queue depth, device substitution, topology isolation, and controlled thermal variation one at a time. Where no reliable isolation test exists, report the uncertainty and the next observation that would reduce it.

Escalation decisions should prioritize integrity and safety over convenience. If hardware reports uncorrectable data, device misdirection, or uncontrolled DMA, cease affected operations and contain the device according to platform policy. If only recoverable local link errors are observed, ongoing monitoring may be reasonable while investigating the trend. In all cases, verification after recovery should include a functional data-integrity check, not merely an absence of fresh console errors.

Recovery design checklist

Design question Required evidence before declaring success
Was the original failure located? First-fault evidence, path, timestamp, and classification
Is the fault domain contained? Confirmed protection against additional unsafe transactions
What happened to in-flight work? Completed, failed, or explicitly outcome-unknown records
Can operations be repeated safely? Documented idempotence or reconciliation mechanism
Was device and link state reinitialized? Reset scope, reenumeration, queue recreation, and mapping restoration
Are old completions harmless? Epoch/phase discipline and invalidated stale state
Is traffic ordering valid? Required barriers, ownership, and protocol-state verification
Did data survive correctly? Readback, checksums, application or storage consistency validation
Is the repair durable? Error-rate trend under representative load and conditions
Are remaining risks recorded? Known limitations, follow-up monitoring, and escalation owner

No single passed check replaces the others. A system may come back online while operations remain unaccounted for, or a valid command stream may coexist with an escalating correctable-error trend. The recovery criterion must be specific to the system: an industrial controller may require bounded reaction time, a scientific cluster may prioritize checkpoint integrity, and a storage system may require strong persistent-data guarantees. The interconnect supplies building blocks but not an automatic guarantee of all higher-level objectives.

Specialist glossary

  • Acknowledgment (ACK): Protocol signal or message reporting receipt under a defined layer's rules.
  • Advanced Error Reporting (AER): PCIe extended error-reporting facility on supporting functions and ports.
  • Automatic repeat request (ARQ): Error recovery that requests or performs retransmission after failed delivery.
  • Backpressure: Mechanism by which a receiver or downstream resource delays more traffic.
  • Bit-error ratio (BER): Ratio of received erroneous bits to transmitted bits under a defined test.
  • Bridge: Component connecting distinct bus or protocol domains.
  • Burst: Transaction with multiple transfer beats under one protocol operation.
  • Bus fault: Error affecting communication, access, or progress in a bus or fabric.
  • Cache coherence: Rules maintaining compatible views of shared cacheable data.
  • Completion: Protocol response marking a defined stage or operation outcome.
  • Completion timeout: Failure to see an expected completion before a deadline.
  • Containment: Restriction preventing an error from spreading beyond a target boundary.
  • Correctable error: Fault that a defined mechanism can remedy while preserving supported guarantees.
  • CRC: Cyclic redundancy check used to detect protected-message corruption.
  • Credit: Receiver-advertised capacity allowing a sender to transmit additional units.
  • Data Link Layer: Protocol layer managing certain link-local delivery functions.
  • DECERR: AXI response related to unsuccessful decode or route selection.
  • Descriptor: Control record defining a DMA or device operation.
  • Device epoch: Software or hardware generation distinguishing work across reinitialization.
  • DMA: Direct Memory Access, device- or engine-initiated movement of data.
  • DPC: Downstream Port Containment capability in PCIe on supporting systems.
  • ECC: Error-correcting code protecting information with redundant bits.
  • End-to-end integrity: Protection that spans a named producer and ultimate consumer.
  • Error syndrome: Encoded information resulting from an integrity or fault check.
  • Error telemetry: Measured records of faults, severity, identity, and timing.
  • FEC: Forward-error correction using redundancy to reconstruct some corrupt data.
  • Fatal error: Error classification indicating an affected domain may be unusable without recovery.
  • Fault domain: Set of components exposed to a common error and recovery action.
  • Flit: Flow-control unit, often a small transferable part of a packet or fixed-size mode unit.
  • Forward progress: Assurance that accepted work can eventually advance under stated conditions.
  • Goodput: Rate of useful delivered application or protocol payload excluding unwanted overhead.
  • Handshake: Exchange that establishes when a transfer is accepted or progresses.
  • Idempotence: Property that repeated execution leaves the same intended final result.
  • In-flight operation: Transaction initiated but not definitively completed or failed.
  • IOMMU: I/O memory-management unit enforcing address translation and permissions for devices.
  • Link retraining: Process of reestablishing selected link operating parameters.
  • LCRC: Link CRC used in applicable PCIe Data Link Layer modes.
  • MSI: Message-signaled interrupt used to signal device events over interconnect mechanisms.
  • Nonfatal error: Error classification permitting continued service with defined failed work.
  • NoC: Network-on-chip communication fabric connecting SoC blocks.
  • Outcome unknown: State in which an operation may or may not have had its intended effect.
  • Parity: Single-bit redundancy recording even/odd count of one-bits.
  • Payload: Useful transfer data distinct from protocol control overhead.
  • Poison: Indication that associated information is untrustworthy under a protocol.
  • Posted write: Write that normally does not generate a completion back to its originator.
  • PSLVERR: Optional APB error signaling associated with a completing access.
  • Quarantine: State in which a component is prevented from performing normal operations.
  • Receiver error: Observed condition at the receive side of a link requiring interpretation.
  • Replay buffer: Retained transmitted information available for link retransmission.
  • Reset scope: Set of hardware and software components affected by a recovery reset.
  • Retry: Attempt to repeat work after error or lack of progress.
  • Sequence number: Number used to identify ordered units and detect duplicates or gaps.
  • Signal integrity: Physical-channel ability to deliver samples within electrical/timing margins.
  • Silent data corruption: Incorrect data accepted or used without a relevant detected fault.
  • SLVERR: AXI response indicating a subordinate-associated failure.
  • Sticky status: Fault indicator retained until explicit clearing or reset.
  • Store-and-forward: Switch operation that buffers a complete unit before forwarding.
  • Syndrome: Result of an ECC or parity check used to detect or locate faults.
  • Tail latency: High-percentile service delay, often reflecting congestion or recovery.
  • Timeout: Declared lack of expected progress before a deadline.
  • Transaction ID: Identifier used to associate requests and responses.
  • Uncorrectable error: Error for which the supported correction mechanism cannot restore valid data.
  • Virtual channel: Logically separated traffic class using shared physical links and buffers.
  • Watchdog: Timer or monitor that detects a failure to make expected progress.
  • Write-one-to-clear: Register field whose asserted write bits clear recorded status.
