Scope: What Bandwidth Numbers Actually Describe

Bus width, transfer rate, and efficiency describe different properties of a hardware communication path. Width states how much data a transfer can carry under a specified interface definition. Transfer rate states how frequently those transfers can occur. Efficiency states what fraction of the available opportunity becomes useful payload for a specified workload. Multiplying a width by a transfer rate can produce an important capacity estimate, but it does not by itself predict the time a program or device needs to finish its work.

A processor, memory controller, peripheral bridge, or switched fabric may support a high headline rate while delivering less data because the transaction contains addresses and response traffic, transfer opportunities are idle, a target cannot respond promptly, or several initiators share one downstream resource. Conversely, a narrower bus with efficient bursts can outperform a wider bus burdened by fixed handshakes and sparse traffic. A defensible comparison therefore specifies the interface, direction, clocking or signaling assumptions, encoding, transferred units, payload definition, and source of any measured value.

This Level 5 article extends the Data, Address, and Control Buses and Bus Transactions and Protocol Phases specialists. It concentrates on capacity arithmetic, usable transfer efficiency, and performance interpretation. Detailed arbitration, PCI Express transaction formats, interconnect congestion, and signal-integrity calculations remain in their dedicated sibling articles. All numerical devices and clocks in the worked scenarios below are intentionally fictional unless identified as a named-standard example.

Vocabulary: Width, Rate, Bandwidth, Throughput, and Latency

Width is often measured in data bits per transfer; rate in transfers per second; bandwidth in bits or bytes per second; throughput in successfully delivered work per second; and latency in elapsed time between defined events. These quantities describe related dimensions but cannot be substituted freely. A 64-bit bus width is not a speed, 1 GHz is not necessarily one billion data transfers per second, and a device with a 4 GB/s interface is not guaranteed to deliver 4 GB/s to application memory.

Physical or line rate characterizes signaling on a connection. Protocol data rate may exclude line coding and physical framing. Payload bandwidth measures the user-defined useful bytes. Application throughput may count only completed file data, database records, or application-visible bytes after software overhead. One measurement can be correct while another is smaller: their boundaries differ.

A practical worksheet should state each numerator and denominator explicitly. “Bytes transmitted divided by elapsed seconds” can mean transmitted physical bytes, protocol payload bytes, bytes committed to memory, or bytes consumed by a program. For credible results, the duration must cover the same observation interval as the counted bytes.

Physical Width, Logical Width, and Effective Payload Width

A parallel interface may have 32, 64, 128, or another number of data conductors. Its logical transfer can differ when lanes are time-multiplexed, encoded, reserved for control, or grouped into multiple protocol beats. Some standards report width in physical lanes, others in payload bits per beat, while still others use symbols over serial lanes. These distinctions must be resolved before multiplying by a rate.

A nominal 64-bit data interface carries at most eight data bytes during one fully used beat. However, a write with only three valid byte strobes carries three architecturally meaningful bytes even though the full data bus is physically driven or sampled according to the interface rules. Transfer-size fields and byte-enable masks establish the useful width of that operation. The width of an address bus, by contrast, primarily determines addressing capability and must not be inserted as a payload byte count.

For packet-based links, logical width may describe an internal datapath, a serializer's input bus, or a protocol word. It is not necessarily the instantaneous number of information bits sent over the wire. A width specification is meaningful only with its interface layer and transfer unit attached.

Data, Address, and Control Information Consume Different Resources

The three classical bus roles—data, address, and control—do not automatically provide three simultaneously independent data pipes. Address information can be presented on separate wires, time-multiplexed with data, or encoded in packet fields. Some protocols have distinct address and data channels that can operate concurrently; others serialize them through the same link. An engineer must map the roles to physical resources before calculating utilization.

A read can require a request carrying an address and a response carrying the data. A write may require address information, data, write strobes, and a response acknowledging acceptance or failure. If request and response share a half-duplex wire, each consumes serial capacity. If an interconnect is full duplex, requests in one direction can overlap responses in the opposite direction subject to the protocol and endpoint. Address and response traffic should not be silently discarded from the overhead model.

Even when a separate address channel eliminates the need to put addresses on the data channel, allocation, ready/valid handshakes, target service, and response acceptance can still determine achieved throughput. {link('memory-mapped-io-and-address-decoding','Memory-Mapped I/O and Address Decoding')} explains the address map; this article accounts for how the transaction's communication work affects bandwidth.

The Fundamental Parallel-Bus Capacity Equation

For a simple interface where every transfer opportunity carries a full data beat, the ideal one-direction payload capacity is:

ideal bytes/second = (data bits/transfer ÷ 8) × transfers/second.

This equation must not be used until the effective data bits per transfer and number of transfers per second are established. For a fictional 32-bit bus supporting 100 million useful data beats per second, the ideal result is (32 ÷ 8) × 100,000,000 = 400,000,000 bytes/s = 400 MB/s. The result is a ceiling assuming continuous full-width payload beats and no relevant overhead, not a measured application speed.

When transfers occur only a fraction of available cycles, multiply by that fraction. When only some byte lanes are valid, account for the valid bytes per beat. When a downstream link is narrower or slower, the whole route may have a lower limit despite the source-interface calculation. The equation is a beginning, not the end, of system analysis.

Clock Frequency Is Not Automatically Transfer Frequency

Hertz measures cycles per second of a periodic signal, but the transfer opportunities per cycle depend on the interface. A single-data-rate link may transfer one beat per clock, a double-data-rate interface may transfer on two clock edges, and a four-beat-per-cycle internal bus may use multiple lanes or phases. Modern serializers may have clock recovery instead of a separate clock wire visible to the host. Clock rate alone is thus insufficient to determine the data rate.

For a simple clocked bus, write transfers/second = clock cycles/second × transfer opportunities/cycle, then apply transfer occupancy. If a 64-bit interface has a 200 MHz clock and can move one beat each cycle, its ideal rate is 8 B × 200 million/s = 1.6 GB/s. If it moves two beats per clock under stated assumptions, the ideal capacity becomes 3.2 GB/s. Whether both opportunities are occupied depends on protocol and target readiness.

A clocked link's interface documentation should identify whether rate notation describes command clocks, interface clocks, PHY symbols, data beats, or actual transfers. Mixing those layers creates factor-of-two or factor-of-four errors that can survive into purchasing and performance decisions.

Single-Data-Rate, Double-Data-Rate, and Multiphase Transfers

Single-data-rate (SDR) means one data transfer opportunity per relevant clock cycle for the described datapath. Double-data-rate (DDR) means two opportunities, commonly associated with edges of a clock or strobe. Neither label specifies how many bus bits are available or how protocol restrictions affect sustained delivery. A DDR interface with a narrow datapath may have lower bandwidth than an SDR interface with a sufficiently wider one.

Consider a 16-bit SDR bus at 300 MHz: 2 B × 300 million/s = 600 MB/s. A hypothetical 16-bit DDR bus at the same 300 MHz has 2 B × 600 million transfers/s = 1.2 GB/s of ideal data transfer capacity. This comparison isolates transfer multiplicity; it says nothing about real device timing, setup/hold constraints, turnaround costs, or energy.

In memory documentation, rates such as DDR4-3200 generally indicate millions of transfers per second per data pin, not a 3,200 MHz core clock. Memory channels have additional rules regarding access timing, activation, refresh, command scheduling, and read/write direction. Do not multiply a stated MT/s rate by two a second time merely because the product is named DDR.

MT/s, GT/s, MHz, and Interface Marketing Labels

MT/s means million transfers per second; GT/s means billion transfers per second. In a parallel DDR memory context, one transfer may mean one data bit per pin or one data beat across the full channel. For a high-speed serial protocol, a transfer unit may be a physical symbol and may not equal one information bit, particularly when multi-level modulation is used. Marketing terms sometimes give nominal protocol grades rather than directly measured data throughput.

Compare quantities only at the same layer. A bus described as 400 MT/s across 32 data bits offers a simple ideal capacity of 400 million × 32 ÷ 8 = 1.6 GB/s. But 400 MT/s per serial lane cannot be converted into 1.6 GB/s simply by assuming a 32-bit word unless that width is genuinely the transfer payload and the encoding is accounted for.

Include units in every intermediate calculation. A symbol-rate number multiplied by raw physical bit count may describe line signaling, while a transaction-level number multiplied by payload bytes describes software-relevant delivery. These must be labeled separately, not combined under one ambiguous “bus speed.”

Bits, Bytes, Decimal Prefixes, and Binary Prefixes

A bit is a binary information unit; a byte commonly contains eight bits in the contemporary architectures considered here. Lowercase b denotes bits and uppercase B denotes bytes in conventional rate notation: 8 Gb/s equals 1 GB/s in the absence of overhead under decimal units. Confusing the two produces an eightfold error.

Decimal prefixes are powers of 1,000: 1 MB = 1,000,000 bytes and 1 GB = 1,000,000,000 bytes. Binary prefixes are powers of 1,024: 1 MiB = 1,048,576 bytes and 1 GiB = 1,073,741,824 bytes. Thus 1 GB/s is approximately 0.931 GiB/s, while 1 GiB/s is approximately 1.074 GB/s. Both can legitimately describe the same traffic under different unit conventions.

Use decimal units consistently for advertised link rates and binary units when describing memory capacities or applications that count powers of two, explicitly converting at comparison boundaries. Never divide binary GiB by decimal GB/s without converting the numerator to bytes first.

Bus Utilization, Beat Occupancy, and Payload Efficiency

Define beat occupancy as the fraction of potential data beat positions that are actually used. Define payload efficiency as useful payload bytes divided by the relevant capacity or transmitted-byte denominator. The first tracks timing occupancy; the second may also account for padding, byte-lane masks, protocol overhead, and retries. They agree only under carefully chosen conditions.

For an ideal-capacity bus moving 8 bytes per clock at 250 million clocks/s, capacity is 2 GB/s. If the data channel accepts a full beat on 60% of clock cycles, the transfer rate is 1.2 GB/s. If 10% of the accepted byte lanes are not meaningful payload, application-useful bytes fall to 2 × 0.60 × 0.90 = 1.08 GB/s. This simple multiplicative model assumes the factors are measured over compatible intervals and does not introduce other overhead.

In practice, utilization should be measured per direction, channel, port, and contention domain. A 90% busy data channel can still deliver poor response time to one requestor because of arbitration or queue position. Utilization indicates load; it is not proof of good service quality.

Serial Links: Lane Rates, Symbols, and Encoding

Serial interconnects carry information over one or more lanes at a defined signaling rate. A lane commonly comprises a transmission path and, for bidirectional links, a distinct receive path. Multi-lane links increase aggregate capacity when lane bonding and the protocol permit useful parallel transport. The physical signaling rate may be stated in GT/s rather than payload bytes/s because symbols, coding, framing, and error mechanisms consume part of the physical capacity.

A general calculation is line symbols/s × information bits/symbol × coding efficiency ÷ 8, multiplied by the count of equivalently operating lanes in the given direction. This representation is appropriate only if the symbol and encoding interpretation is documented. It must be adapted for modulation schemes that carry multiple bits per symbol, block/flit overheads, and FEC. No universal “GT/s = Gb/s” rule applies to every generation of every serial standard.

Even after line coding is removed, packet headers, sequence numbers, link control, checksums, retry or replay traffic, flow-control packets, and idle intervals may lower the useful payload rate. Physical capacity, transport data capacity, and application throughput are three separate layers of accounting.

8b/10b and 128b/130b Line-Coding Efficiency

Under 8b/10b coding, ten transmitted bits represent eight data bits for the coded stream, giving a nominal coding efficiency of 8/10 = 80%. Under 128b/130b block coding, 130 transmitted bits convey 128 bits of block content, giving 128/130 ≈ 98.46%. These ratios describe line coding, not the share of final application payload; packets and other protocol traffic still consume capacity.

For a simplified NRZ lane at 5 GT/s with 8b/10b, nominal post-coding rate is 5 × 8/10 = 4 Gb/s, or 500 MB/s in one direction. For an NRZ lane at 8 GT/s with 128b/130b, nominal post-coding rate is 8 × 128/130 = 7.8769 Gb/s, or approximately 984.6 MB/s. Neither result guarantees that a software transfer will achieve the full value.

These coding examples apply to the respective link families and versions, not automatically to newer modulation designs. In particular, modern PAM4 and flit-based links require their own physical encoding and FEC accounting. Published capacity figures should be accompanied by the generation, number of lanes, direction, and which overhead classes were already removed.

PCI Express: Generation, Lane Count, and Direction

PCI Express illustrates why both signaling generation and lane count must accompany a bandwidth claim. PCIe 2.x uses 5 GT/s with 8b/10b coding; PCIe 3.0 uses 8 GT/s with 128b/130b coding; PCIe 4.0 uses 16 GT/s and the latter coding model for the simple post-encoding arithmetic. A PCIe lane's transmission and reception directions are independent physical paths; a full-duplex aggregate figure should not be mistaken for the capacity available to a one-way transfer.

For example, PCIe 3.0 x4 has ideal post-encoding capacity of about 0.9846 GB/s/lane × 4 = 3.938 GB/s per direction before transaction overhead. PCIe 4.0 x4 under the same model provides about 7.877 GB/s per direction before transaction overhead. Actual usable rate depends on transaction size, completion traffic, credits, topology, negotiated width, device behavior, and platform limits. A connector or slot advertised as x16 does not guarantee that the active link negotiated sixteen lanes.

The primary authoritative distinction between 8b/10b and 128b/130b is documented by PCI-SIG. Detailed ordering, transaction-layer packets, and completion behavior belong to PCI Express Architecture and Transaction Flow. This article uses PCIe as a measured-units case study rather than reproducing a generation-by-generation proprietary specification.

Link Direction: Simplex, Half Duplex, and Full Duplex

A simplex link carries data in one direction. A half-duplex link alternates directions over a shared resource. A full-duplex link can carry traffic in both directions concurrently when the endpoint and protocol permit. In bandwidth reporting, “total aggregate” sometimes adds the two directions; that number should not be used as the one-direction download, upload, or DMA rate.

If an ideal full-duplex link supports 2 GB/s toward the device and 2 GB/s toward the host, it has an aggregate bidirectional signaling-data capacity of 4 GB/s by addition, but a host-to-device-only transfer still has at most 2 GB/s. If a one-way workload simultaneously requires return traffic that shares some other port, effective throughput may be lower even though the physical send and receive links are distinct.

Always record a direction on graphs and comparison tables. A bandwidth claim without direction can overstate file-copy performance, processor-memory transfer capability, or peripheral throughput by a factor of two if the original figure summed both directions.

Multi-Lane Aggregation and Width Negotiation

When lanes have comparable rate and encoding and the link distributes data evenly, ideal capacity can scale approximately with lane count. An eight-lane link can offer twice the post-encoding capacity of a four-lane link of the same generation. Practical scaling is not guaranteed when the endpoint has insufficient outstanding operations, the workload contains small transactions, or a common upstream link or controller is saturated.

High-speed links typically train or negotiate operating speed and width within limits supported by both ends and the channel. An advertised x8-capable component might run at x4 after a negotiated downgrade, configuration choice, or hardware fault. The width to use in calculations is the active negotiated width, not necessarily the maximum connector designation. Measurements must also indicate whether lanes are used symmetrically and whether the standard's overhead model changes by mode.

A bridge or switch can create a shared bottleneck: four devices with dedicated local links may all compete for one narrower uplink. Summing edge-link rates overstates end-to-end transfer capacity across the shared section. {link('bus-topologies-and-interconnect-hierarchies','Bus Topologies and Interconnect Hierarchies')} describes where such aggregation points occur.

Burst Transfers and Amortized Fixed Overhead

A burst groups multiple data beats under transaction-control information instead of repeating all setup for every individual payload beat. When a protocol and target can sustain consecutive beats, fixed address and authorization costs are spread over more useful data. This often improves efficiency for sequential memory transfers compared with many small independent transactions. Burst size alone does not guarantee benefit if the target inserts stalls or a narrow link must serialize each beat.

A simple model is payload efficiency = payload-beat cycles ÷ (setup cycles + payload-beat cycles + other nonoverlapped cycles) for full-width beats. If a fictional interface needs two nonoverlapped setup cycles and eight one-cycle payload beats, ideal beat-time efficiency is 8/(2+8) = 80%. With sixteen payload beats, it rises to 16/(2+16) ≈ 88.9%. This pedagogical model should not be misread as an AXI rule, since AXI uses independent channels and can overlap work.

Large bursts can increase latency experienced by urgent small requests, exhaust finite buffers, or create fairness problems under certain schedulers. Burst sizing is therefore a traffic-engineering decision involving throughput and service latency, not merely the maximization of a numerical efficiency ratio.

Address and Response Overhead in Bus Transactions

A transaction may carry a request header, one or more data beats, and a completion or response. The fixed request and completion costs are proportionally largest for small payloads. Some bus systems overlap address and data phases; others devote distinct slots or packets to them. Accordingly, “three cycles per transfer” is not a universal formula. A valid model identifies which operations share a channel and which can execute concurrently.

For an abstract serialized connection that transfers one 8-byte control unit, one 64-byte data payload, and one 8-byte acknowledgment, the useful-byte share is 64/(8+64+8) = 80% before any physical coding or idle time. The example does not claim that every memory read has a separate 8-byte acknowledgment; it illustrates how a declared message accounting boundary produces an efficiency calculation.

For AXI-like designs, address, read-data, write-data, and response channels are logically distinct. Arm's Introduction to AMBA AXI explains burst transfers and independent handshakes. Model the actual channel of interest rather than adding all control-channel bytes to one data-channel denominator that does not physically carry them.

Packet Headers, Tail Fields, and Framing Overhead

Packetized interconnects spend some physical capacity on headers, length or type fields, identification, checksums, framing, and any required control packets. The payload fraction under a simplified no-retry serialized model is payload bytes ÷ total transmitted bytes. If a packet has 256 payload bytes and 32 bytes of combined headers and trailers, efficiency is 256/288 = 88.89%. If payload is 32 bytes with the same 32-byte overhead, efficiency falls to 50%.

Real protocols may contain alignment padding, flit boundaries, sequence numbering, ordered sets, credit returns, and separate acknowledgment traffic. A packet-level fraction should not be equated to full physical-link efficiency until all counted layers are listed. Some framing is amortized over a block, some appears once per packet, and some is workload-dependent.

Combining small requests or selecting a larger supported maximum payload size can improve efficiency, but large packets may increase queueing delays or fragment scarce buffers. Protocol-specific segmentation rules and endpoint capabilities determine which optimizations are permissible.

Byte Enables, Partial Writes, and Underfilled Beats

Width-based capacity assumes every payload lane is useful. Hardware frequently performs subword accesses on a wider interface: an 8-byte bus might carry a 1-byte register write using one valid byte lane, giving only 12.5% meaningful payload relative to the occupied data beat. The presence of eight physical lanes does not turn one byte of program data into eight useful bytes.

Byte masks or write strobes identify the lanes meant to modify target state. Their interpretation must be coordinated with address alignment and endianness rules. Some devices cannot accept arbitrary subword writes, and software must use register widths specified by the device. Coalescing adjacent writes can save bandwidth only when semantics permit it—two independent side-effecting MMIO registers are not interchangeable with one wide combined write.

Distinguish bus bytes occupied from application bytes consumed. A profiling system that only counts data-channel beats may report high transfer volume even though repeated partial writes deliver little useful information. This is especially relevant for control-plane workloads that prioritize prompt access over aggregate bandwidth.

Alignment, Padding, and Transfer Granularity

Alignment describes the relationship between an address and the boundary of a transfer unit. Unaligned accesses can require split transactions, altered lane masks, additional internal work, or may be disallowed, depending on architecture and device. Even an aligned logical operation can be split by a cache-line boundary, page boundary, or maximum supported burst size.

In a fictional system with 16-byte beats, a 32-byte record aligned to a 16-byte boundary may fit in two full beats. If the same record begins twelve bytes before a required boundary and the protocol cannot combine the adjacent fragments into one logical beat, it can occupy three beats or require separate operations, depending on the interface. The additional bus work is a consequence of boundary rules, not an inherent property of the record's 32-byte content.

Overhead can also arise when payload lengths are rounded to a packet block or link flit. Analysts should report whether transmitted bytes include padding and whether the denominator counts occupied bus beats, encoded bits on the wire, or requested application bytes.

Flow Control: Ready/Valid, Wait States, and Backpressure

A synchronous data channel commonly moves information only when a sender presents valid information and the receiver accepts it under the channel's handshake rules. A wait state or deasserted ready signal means a nominal clock opportunity carries no newly accepted beat. The clock continues to tick, but useful throughput declines. Flow control can prevent overflow and preserve correctness; it is not an implementation defect merely because it reduces measured occupancy.

In an AXI transfer, a beat is accepted at the interface when both VALID and READY are asserted at the required sampling edge, according to the protocol. Holding VALID while READY is low is not a new accepted transfer on every cycle. Count handshakes—not just observed valid cycles—to estimate data-channel beat throughput. For a bridge or peripheral using a different protocol, use that protocol's actual acceptance condition.

Backpressure can originate far beyond the local link: a congested memory controller, full queue, outstanding-response limit, or destination service delay may cause an upstream stall. Local data width upgrades will not solve a bottleneck elsewhere unless the changed capacity improves the limiting stage of the end-to-end route.

Bus Arbitration, Fairness, and Shared Capacity

On a shared interconnect, multiple initiators compete for a finite set of transfer opportunities. If two requestors each demand 1.5 GB/s of one-direction payload through a bus capped at 2 GB/s, the combined demand of 3 GB/s exceeds capacity. Under an ideal equally fair allocation, each may receive approximately 1 GB/s; under priority scheduling, one could obtain more while the other receives less. Neither outcome implies that either device's local link is incorrectly rated.

Arbitration overhead can include grant delays, turnaround cycles, and queue management. Fixed-priority schemes may serve urgent traffic promptly but risk starvation of lower-priority flows, while round-robin-like policies can spread opportunities more evenly at the cost of some scheduling flexibility. Protocol-level timing and the number of eligible targets affect achievable concurrency.

Bandwidth efficiency and service fairness should be evaluated together. A bus kept nearly 100% busy by one bulk transfer is efficient in the narrow utilization sense but may be unsuitable for real-time control if small requests cannot obtain bounded access. The dedicated {link('bus-arbitration-and-access-priority','Bus Arbitration and Access Priority')} subarticle analyzes those policies.

Transaction Concurrency, Pipelining, and Outstanding Requests

Throughput can improve when the initiator submits another request before the earlier one completes, provided the protocol, target, and buffers support multiple outstanding transactions. Pipelining overlaps stages of several operations, while concurrency permits multiple transactions to be in flight. Neither eliminates finite resource limits, ordering constraints, or the need to match responses to requests.

Consider a path with 200 ns of average request-to-completion latency and 64 bytes per completed operation. A system that permits only one request in flight can sustain at most 64 B/200 ns = 0.32 GB/s under a sequential nonoverlapped model. If ten independent requests can be outstanding and the downstream path has sufficient capacity, the latency-limited upper bound becomes roughly 3.2 GB/s. The link itself may cap throughput below that rate.

More depth helps only when operations are independent enough to overlap and downstream resources can execute them. Dependency chains, credit scarcity, target serialization, and protected ordering domains can prevent the theoretical benefit of a large outstanding-request limit.

Latency and Bandwidth Are Not Interchangeable

Latency measures time from a defined start to a defined completion event. Bandwidth measures amount of data delivered per unit time. A bus can offer high bandwidth for long sequential transfers while imposing substantial per-operation latency. Another interface can have excellent single-register response time but low maximum aggregate throughput. The preferable architecture depends on whether the workload transfers large blocks, performs dependent reads, or sends short control messages.

A 1 MB copy and a one-byte MMIO read are not comparable transactions. The copy may amortize setup cost across large contiguous data and achieve near the path's steady-state bandwidth; the one-byte read may spend nearly all its time waiting for address translation, arbitration, target response, and software synchronization. Peak data rate alone predicts neither operation's completion time.

A useful performance model separates fixed time and transfer time: T ≈ Tfixed + bytes/effective_streaming_rate, subject to overlap and concurrency. When bytes are small, fixed cost dominates. When bytes are large, the streaming term and shared capacity dominate.

Little’s Law as a Concurrency Sanity Check

Little's law expresses a stable system relationship as average in-flight work = throughput × average time in system, when units and observation boundaries match. For fixed-size transactions, a useful form is necessary outstanding requests ≈ (target bytes/s × average transaction latency) ÷ bytes/request. This estimate can expose when a high-bandwidth link is starved by a shallow request window.

To sustain a target rate of 3.2 GB/s with 200 ns latency and 64-byte transactions, the ideal average concurrency is 3.2×10⁹ × 200×10⁻⁹ ÷ 64 = 10 outstanding operations. This is not a guarantee that ten queue slots will achieve the target: arbitration, service-rate variation, head-of-line blocking, and burstiness can require more headroom. Nor does it mean that unrelated latency components are independent.

For very small transfers, the required request rate may be the limiting resource. A nominal byte-oriented link can have abundant bit capacity while the target can accept only a modest number of distinct operations per second. Distinguish transactions/s, data beats/s, and bytes/s throughout analysis.

Clock-Domain Crossing and Width Conversion

Bridges often connect subsystems with different clocks or data widths. A width converter can combine multiple narrow beats into a wide beat or split a wide beat into multiple narrow beats, subject to alignment, byte enables, transaction length, and legal boundaries. A clock-domain bridge typically uses handshaking or buffering to transfer work safely across independently timed domains. Both introduce finite buffering and potential stalls.

If a 128-bit upstream interface operates at 250 million full beats/s, its simple ideal capacity is 4 GB/s. A 32-bit downstream interface at 500 million beats/s has capacity 2 GB/s. A stream crossing both has no more than 2 GB/s one-direction payload capacity under these assumptions, even with a perfect width converter and infinite source traffic. Conversion overhead or target stalls can reduce it further.

Do not multiply widths and clocks from different sides of the bridge and assume the resulting numbers describe a single uninterrupted data pipe. Identify the narrowest service point and any buffering-induced differences between burst peak and sustainable throughput.

On-Chip Datapaths and Off-Chip Interconnects

An on-chip 256-bit data channel at 1 GHz can have high ideal local capacity: 32 bytes per beat multiplied by one billion beats per second equals 32 GB/s. That number says little about the bandwidth available to external DRAM or a network interface, which must pass through other controllers, PHYs, and package pins. Wide internal paths are economical in some chip layouts but require wiring, buffers, and power.

Off-chip connections face signal-integrity, package, connector, energy, and reach constraints. Designers may choose high-speed serial lanes instead of wide parallel buses to reduce skew and wiring complexity. Coding and framing can reduce useful payload relative to physical signaling, while robust error handling can improve reliable delivered throughput under adverse conditions.

Compare like for like: an internal crossbar's peak aggregate bandwidth counts potentially independent paths, whereas a single off-chip link's bandwidth counts one connection. Neither is automatically the maximum throughput one application can obtain across the complete system.

DRAM Channel Bandwidth and Timing Limits

For a conventional 64-bit-wide DDR4 data channel rated at 3200 MT/s, the familiar theoretical transfer ceiling is 3.2×10⁹ transfers/s × 8 B = 25.6 GB/s, excluding separate ECC width in configurations that have it. This is an ideal data-pin rate, not a guarantee of sustained application bandwidth. The calculation already uses the DDR transfer rate; it should not be doubled again.

Actual DRAM throughput can be reduced by activate/precharge operations, refresh, read/write turnarounds, bank conflicts, access locality, controller scheduling, and contention from other agents. Multiple memory channels can expand aggregate capacity when traffic is distributed suitably, but asymmetrical loading or a shared controller can prevent ideal scaling.

A workload's cache behavior also changes how much DRAM traffic it generates. A computation repeatedly served from processor caches may use little external bandwidth even while executing quickly. A benchmark with write-allocate or read-for-ownership traffic may cause more memory transfers than the application's nominal useful bytes.

PCIe, Storage, and Device End-to-End Ceilings

Storage and peripheral throughput often traverses multiple components: device media, controller firmware, DMA engine, local memory, PCIe link, switches, host root complex, and main memory. The advertised PCIe generation and width establish one potential ceiling, but the sustained application rate can be limited at any stage of this route. A nominally fast interface does not accelerate a slow target that processes data serially.

Controller queue depth, descriptor setup, completion interrupts or polling, command size, and software buffers matter. Sequential large-block transfers often reach higher byte rates than small random I/O even over the same link. For small operations, operations per second and tail latency can be more informative than MB/s.

When diagnosing storage throughput, check negotiated PCIe speed and width separately from the device's media speed. Interpret read and write directions independently, since a device can have asymmetric behavior and a platform may share uplinks across multiple endpoints.

Error Detection, Retries, and Reliable Delivered Data

Electrical corruption, protocol errors, packet drops, and recoverable retries consume time or link capacity without necessarily delivering new useful payload. A system can therefore show high physical activity while making poor forward progress. The effective goodput denominator includes the elapsed time during retransmission or recovery, while the numerator counts data successfully delivered at the chosen layer.

If a link sends 1.0 GB of new payload plus 0.1 GB of retransmitted material during a fixed interval, and its available transfer rate is otherwise the same, the new-payload fraction of that simplified volume is 1.0/1.1 ≈ 90.9%. Actual retry accounting may involve frame headers, error-control packets, pause time, and different replay units. Error counters alone should not be converted to lost bytes without the protocol's retry behavior.

Link errors often increase with poor signal margin, marginal connectors, power instability, or environmental conditions. Correct diagnosis measures error records, negotiated link mode, relevant traffic, and retest results rather than assuming low performance always indicates insufficient nominal link width.

Compression, Offload, and What Counts as Useful Bytes

Compression changes the relationship between bytes transported and bytes represented to software. If a device compresses 2 GB of logical data into 1 GB of transmitted bytes, the physical link might move 1 GB while an application reports 2 GB of logical input processed. Both can be correct; claiming “200% bus efficiency” without explaining the numerator is misleading. Compression also consumes compute resources and depends on data entropy.

Encryption, checksums, framing, and protocol offloads likewise move work among components. Offloading a checksum can reduce CPU cycles but does not necessarily reduce wire bytes. Encryption may add metadata, tags, alignment, or fixed framing costs. Some implementations use in-line processing that preserves stream rate; others have a slower compute pipeline that becomes the bottleneck.

Always decide whether the metric is physical wire bytes, protocol payload bytes, logical uncompressed bytes, or application records completed. Comparing figures across these definitions without normalization can create artificial performance wins.

Power, Area, and the Cost of Higher Bus Bandwidth

Higher data width and transfer rate often require greater wiring capacity, more flip-flops or buffers, stronger clock distribution, serializer/deserializer logic, and greater switching energy. Broadening a bus may also complicate placement and timing closure; increasing frequency can tighten signal-integrity and power constraints. A theoretical bandwidth increase is valuable only when the workload uses it enough to justify the implementation cost.

Energy efficiency may be expressed as joules per useful transferred byte, subject to a defined measurement boundary. A link that runs at high instantaneous power but completes a large transfer quickly can use less total energy than a lower-power link kept active much longer, or the reverse. Link idle states, wakeup penalties, and thermal throttling all affect the result.

Architecture selection should consider bandwidth per watt, bandwidth per silicon area, latency, reliability, and opportunity cost alongside raw GB/s. Physical and electrical limits are developed further in {link('bus-signal-integrity-and-electrical-constraints','Bus Signal Integrity and Electrical Constraints')}.

Peak Capacity, Sustainable Throughput, and Goodput

Three summary figures should be kept separate. Peak capacity is the ideal link or data-channel limit under explicit assumptions. Sustainable throughput is an achieved stable transfer rate over an extended observation interval. Goodput counts successfully delivered useful information at a defined layer, excluding chosen overhead or retransmitted duplicates. A single workload can yield three different, valid numbers.

Short burst tests can be misleading when data are served from caches or buffers that refill more slowly than they drain. A 1 ms sample may capture the bus's burst capacity, while a 30-second transfer exposes target service limitations and thermal behavior. Conversely, a whole-program average may hide short intervals where the link saturates. Report both measurement interval and workload phase.

When a software benchmark reports fewer bytes per second than a physical link promises, that difference is not, by itself, evidence of malfunction. A credible explanation isolates where the time and bytes go—protocol overhead, small payloads, limited outstanding work, memory contention, device compute, software scheduling, or errors.

Bandwidth Measurement: Counters, Counters’ Scope, and Sampling

Hardware performance counters may count accepted beats, transferred bytes, transactions, stalls, credits, link utilization, retries, or DMA completions. Counter names are not self-explanatory: some include speculative or replay traffic, some count encoded symbols, and some count only successful payload bytes. Read the event definition and determine whether it applies per port, lane, direction, controller, or entire fabric.

The usual measurement formula is average rate = count difference × unit size ÷ elapsed seconds. If an interface reports 250 million accepted eight-byte beats over one second, the observed beat volume is 2 GB/s. If the counter increments for all accepted beats, it does not reveal how many byte lanes were actually useful. A separate strobe or payload-byte counter may be necessary.

Counter wraparound, sampling uncertainty, event multiplexing, frequency changes, and observation windows can corrupt comparisons. When using software timers, align the start and stop boundaries with the transfers being measured. Always present method, duration, counted layer, and configuration with the reported result.

Benchmark Design and Sustainable Bandwidth Tests

A reproducible bandwidth experiment should control payload size, warmup, buffer placement, concurrency, transfer direction, clock or power state, and destination behavior. For memory bandwidth, the STREAM family of benchmarks deliberately measures sustainable transfer rates for selected vector kernels and has a different interpretation from a processor's raw memory-channel arithmetic. For peripheral links, DMA transfer size and device capabilities must be documented.

Repeat trials and report variability rather than only the highest short-lived observation. Include small and large transfers to distinguish fixed-latency overhead from steady-state streaming behavior. Examine simultaneous flows if the system is expected to carry concurrent traffic. A single-threaded benchmark cannot reveal all potential link capacity if the architecture requires many outstanding requests or several independent agents.

A result should be accompanied by counters or other evidence that identifies its bottleneck. High link utilization, high target-busy time, queue stalls, and declining useful payload can coexist. Testing only larger packets is not enough when the root limitation is downstream service rather than packet overhead.

Bottleneck Analysis Across Multi-Stage Paths

An end-to-end data path consists of stages with finite service capacity. Under steady conditions and compatible traffic definitions, sustained throughput cannot exceed the limiting stage: source production, channel transport, bridge conversion, target acceptance, storage media, or host consumption. More complex queueing can create additional losses, but no downstream optimization can overcome an upstream fixed cap by arithmetic alone.

Trace the entire route and construct a capacity ledger. Record each stage's ideal one-direction rate, achieved occupancy, overhead mechanism, outstanding-work limit, and shared traffic load. Be cautious when converting aggregate fabric figures into single-flow capacity or when summing bidirectional rates. A crossbar may support several independent high-speed flows while one flow remains limited to its individual source and target port rates.

The detailed interconnect-latency and congestion model belongs to {link('interconnect-latency-throughput-and-contention','Interconnect Latency, Throughput, and Contention')}. Here the central rule is simpler: every advertised number must be tied to a defined path and traffic accounting boundary.

Worked Example 1 — A 64-Bit Bus at 250 Million Beats per Second

Problem. A fictional bus moves up to one full 64-bit data beat on each of 250 million transfer opportunities per second. What is its ideal one-direction payload capacity? What does 70% occupied-beat time imply if every accepted beat is full?

Step 1: Convert width. 64 bits/beat ÷ 8 = 8 bytes/beat. Step 2: Calculate the ceiling. 8 × 250,000,000 = 2,000,000,000 bytes/s = 2.0 GB/s. Step 3: Apply occupancy. 2.0 × 0.70 = 1.4 GB/s.

Interpretation. The 2.0 GB/s figure is ideal capacity, while 1.4 GB/s is a modeled accepted-beat rate under stated occupancy. If some byte lanes are masked, if the counter includes replayed traffic, or if payloads must be reassembled elsewhere, application goodput is smaller. The address-channel width is irrelevant to this direct data-volume multiplication.

Worked Example 2 — Why a DDR-3200 Channel Is 25.6 GB/s

Problem. A conventional 64-bit-wide DDR4-3200 data channel operates at 3200 million transfers per second per data pin. Estimate the ideal data transfer rate, and explain a common mistake.

Calculation. 64 bits/transfer ÷ 8 = 8 bytes; 8 × 3.2×10⁹ = 25.6×10⁹ bytes/s = 25.6 GB/s. The stated 3200 MT/s already accounts for the two edge-associated data transfers of DDR signaling. Multiplying the result by two again would double-count the same physical operation and incorrectly assert 51.2 GB/s for a single channel under these assumptions.

Limitations. The ideal figure does not deduct refresh, activate/precharge commands, bank conflicts, read/write turnaround, or controller scheduling overhead. Nor is it the same as a measured multi-threaded memory-copy rate. If a system has two properly utilized channels with the same characteristics, their arithmetic aggregate ceiling is 51.2 GB/s, but real scaling is workload-dependent.

Worked Example 3 — 8b/10b Versus 128b/130b

Problem. Compare one NRZ serial lane at 5 GT/s using 8b/10b coding with one NRZ lane at 8 GT/s using 128b/130b coding. Count only coding efficiency, not transaction overhead.

First lane. 5 GT/s × 8/10 = 4 Gb/s, or 4/8 = 0.5 GB/s. Second lane. 8 GT/s × 128/130 ≈ 7.876923 Gb/s, or approximately 0.984615 GB/s. The second lane's post-coding capacity is roughly 1.97 times the first's, despite raw transfer rate rising only from 5 to 8 GT/s.

Interpretation. Coding efficiency is a significant part of protocol-generation improvements. A statement that “8 GT/s means 1 GB/s per lane” is a useful rounded shorthand for the second configuration, but is not a claim of 1 GB/s of application payload. Headers, link maintenance, completions, and other effects remain to be considered.

Worked Example 4 — PCIe 4.0 x4 and Full-Duplex Accounting

Problem. Estimate the ideal post-128b/130b data capacity of a PCIe 4.0 x4 link at 16 GT/s, assuming the conventional NRZ coding model. Distinguish one-way from bidirectional aggregate capacity.

Per lane, one direction: 16 × 128/130 ÷ 8 ≈ 1.96923 GB/s. Four lanes, one direction: 1.96923 × 4 ≈ 7.8769 GB/s. Sum of both directions: approximately 15.754 GB/s, assuming both directional paths can be fully utilized. It would be incorrect to use 15.754 GB/s as the expected one-direction upload or download rate.

Practical note. Actual payload throughput is lower once transaction-layer packets, link activity, device capabilities, negotiated operating mode, and bus topology are considered. The example is deliberately limited to the coding-layer arithmetic, which keeps the one-direction question answerable without inventing packet sizes or completion policy.

Worked Example 5 — Small Packets and Fixed Header Cost

Problem. A fictional packet link carries 32 bytes of combined header/trailer material for each packet. Compare useful-byte efficiency with a 32-byte payload and a 512-byte payload. Assume both are already the final on-wire byte counts aside from the stated overhead.

Small packet: 32/(32+32) = 50%. Large packet: 512/(512+32) = 512/544 ≈ 94.12%. A fixed protocol cost is therefore much more expensive for small operations. At 1 GB/s of total encoded packet bytes under these narrow assumptions, the corresponding maximum useful rates would be 0.50 and 0.941 GB/s before other restrictions.

Design trade-off. Larger payloads may increase total streaming efficiency, but aggregation can delay small urgent requests and can cause fragmentation at a receiver with limited buffer space. Real packet formats may include additional padding or physical coding, so a documented protocol's own accounting replaces this toy model.

Worked Example 6 — Burst Length and Setup Amortization

Problem. A simplified nonoverlapped bus needs two setup cycles per burst and accepts one full eight-byte beat per subsequent cycle. Compare four-beat and sixteen-beat bursts at a 200 MHz clock.

Four beats: payload 4 × 8 = 32 B; total cycles 2 + 4 = 6; efficiency 4/6 ≈ 66.67%; average payload rate 32 B / (6/200 million s) ≈ 1.067 GB/s. Sixteen beats: payload 128 B; total cycles 18; efficiency 16/18 ≈ 88.89%; average rate 128/(18/200 million) ≈ 1.422 GB/s.

What it demonstrates. Longer bursts amortize nonoverlapped fixed overhead and approach the ideal 8 B × 200 MHz = 1.6 GB/s ceiling. It does not demonstrate how AXI behaves in every implementation, since address and data activities may overlap and other bottlenecks may intervene.

Worked Example 7 — Width Conversion and a Narrow Downstream Port

Problem. An internal 128-bit fabric sustains up to 250 million full beats/s and is connected through a bridge to a 32-bit peripheral channel sustaining up to 500 million full beats/s. What is the upper bound for a large one-direction transfer across both?

Upstream capacity: (128 ÷ 8) × 250 million = 4 GB/s. Downstream capacity: (32 ÷ 8) × 500 million = 2 GB/s. Since every transferred payload byte must pass through both sides, end-to-end steady-state throughput cannot exceed 2 GB/s under the assumptions. The bridge can buffer data temporarily, but it cannot create additional downstream service capacity.

Practical implication. A faster upstream bus may reduce contention among other paths but does not double this transfer's sustained rate. Adding a second independent downstream link, raising its legal beat rate, or reducing unnecessary bus work could help if other resources permit.

Worked Example 8 — Partial Byte Lanes and Application Goodput

Problem. A 64-bit data bus accepts 100 million beats/s, but each operation is a three-byte MMIO transfer that occupies one beat. Estimate the meaningful payload throughput relative to the full-bus ceiling.

Full-beat capacity: 8 B × 100 million/s = 800 MB/s. Useful payload: 3 B × 100 million/s = 300 MB/s. Lane efficiency: 3/8 = 37.5%. The bus may be fully occupied in the data-beat sense while delivering only 300 MB/s of meaningful register data.

Caution. This computation assumes each three-byte transfer is legal and accepted at the modeled rate. MMIO devices often impose additional restrictions or side effects that make arbitrary batching invalid. The lesson is not to combine register writes recklessly but to distinguish beat accounting from valid application bytes.

Worked Example 9 — Outstanding Requests Needed to Hide Latency

Problem. A device completes fixed 64-byte independent transactions with 200 ns average latency. How much concurrency is needed to support 3.2 GB/s, assuming the downstream path itself has that capacity?

Compute rate in transactions: 3.2×10⁹ B/s ÷ 64 B ≈ 50 million transactions/s. Concurrency under Little's law: 50 million/s × 200 ns = 10 average transactions outstanding. With only one in flight, the simple sequential bound is 64/200 ns = 320 MB/s. Ten or more independent in-flight requests are a plausible requirement to approach the target under ideal service assumptions.

Interpretation. Queue capacity, credit handling, completion order, and workload independence all matter. Ten slots do not mathematically guarantee 3.2 GB/s during bursty arrivals or high tail latency; the result is an initial engineering sanity check.

Worked Example 10 — Two Devices Contending for an Uplink

Problem. Two devices each have a local connection capable of 1.5 GB/s in the upstream direction, but both reach host memory through one shared uplink capped at 2 GB/s. How much can they deliver simultaneously?

Demand: 1.5 + 1.5 = 3.0 GB/s. Shared capacity: 2.0 GB/s. The combined end-to-end steady rate cannot exceed 2.0 GB/s under the assumptions. An ideal equal-share allocator might give each 1.0 GB/s, while a different scheduler could give one 1.5 GB/s and the other 0.5 GB/s. Their local link capabilities have not changed.

What to measure. Collect directional uplink occupancy, per-device transferred bytes, arbitration grants, target service time, and queueing. The correct remedy may involve topology or scheduling, not replacing either local device.

Worked Example 11 — Converting GiB and GB/s to Elapsed Time

Problem. A transaction system delivers a steady 2.0 GB/s of useful one-direction payload. How long would it take to transfer exactly 1 GiB of data, ignoring setup and finalization?

Convert capacity units: 1 GiB = 1,073,741,824 bytes; 2 GB/s = 2,000,000,000 bytes/s. Divide: 1,073,741,824 / 2,000,000,000 ≈ 0.53687 s. Dividing 1 by 2 and writing 0.5 seconds would incorrectly treat 1 GiB as 1 GB.

Practical limitation. A real transfer can require startup latency, interrupts, protocol trailers, file-system bookkeeping, cache management, and other work. Report the ideal streaming term separately from the measured wall-clock time.

Worked Example 12 — Retries and the Goodput Ratio

Problem. During a fixed interval, a link carries 900 MB of new successful payload plus 100 MB of retransmitted copies of already attempted payload. Ignore additional framing and link idle time. What fraction of transported payload-volume equivalents is newly delivered data?

Compute: 900/(900+100) = 90%. If the physical accounting measured a steady 1 GB/s for one second including both categories under these assumptions, the newly delivered data rate would be 0.9 GB/s. Errors do not have to change the link's negotiated speed to reduce goodput.

Diagnosis. The count of link errors is not necessarily the count of complete packet replays. Determine the protocol's actual retransmission unit and whether the counter excludes framing or retransmitted headers. Check physical error conditions separately from target congestion and application behavior.

Worked Example 13 — A 64-Byte Read with a Fixed Round-Trip Cost

Problem. A hypothetical device completes one nonoverlapped 64-byte read in 400 ns, including request, target service, return, and software-visible completion. What is its sequential throughput? How might concurrency change the limit?

Sequential bound: 64 B / 400 ns = 160 million B/s = 160 MB/s. This says nothing about the physical link's streaming ceiling: it may be much higher. If sixteen similar independent operations can be in flight and the target services them concurrently, an optimistic latency-limited product would be 16 × 160 MB/s = 2.56 GB/s, before link, queue, and target-capacity limits.

Lesson. Higher nominal bandwidth does not automatically fix a latency-limited serial dependency chain. Improve the number of independent operations, reduce round-trip latency, or change request granularity only when the workload's correctness and device semantics permit.
