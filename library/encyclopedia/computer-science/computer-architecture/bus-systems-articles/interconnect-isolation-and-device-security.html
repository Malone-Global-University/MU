Scope and place in the Bus Systems unit

This specialist article examines the security of communication between hardware agents: processors, controllers, accelerators, expansion devices, memory, and the switches or bridges that join them. Its organizing question is not simply whether an interface can move data, but which initiator may access which address, with what permissions, through which route, and under whose authority. A device can be electrically compatible, correctly enumerated, and capable of transferring valid packets while still being an inappropriate participant in a given trust domain. Conversely, a fault reported by an isolation mechanism does not automatically prove hostile conduct; software configuration errors and stale mappings can produce the same symptom.

The parent Bus Systems article introduces interconnect functions. The DMA and Bus Mastering specialist treats transfers and buffer ownership; Transaction Ordering and Memory Coherence treats visibility. Here, the primary subject is authorization, hardware enforcement, containment, and evidence of compliance. This Level 5 page is article 19 of 20 in the Bus Systems specialist directory. The next and final sibling treats error detection, diagnostics, and recovery broadly rather than access control alone.

Why an interconnect is a security boundary

A system bus or fabric allows one component to send requests that change the state of another. A processor may read a controller's registers, a network adapter may write packets into host memory, and a storage controller may fetch command descriptors. Each operation crosses a boundary between agents with different privileges and responsibilities. Permission checks performed by an application are not sufficient if a device can issue memory transactions without passing through the application's software checks. That is why the path from a device's request to a memory controller must be examined independently of the CPU's virtual-memory path.

Modern systems employ layered authorization: firmware and operating-system policy decide which device or driver is trusted; I/O address translation constrains device access to system memory; fabric rules govern peer routes; interrupt-remapping facilities govern device-generated interrupt destinations; and physical-link security may protect traffic on exposed connections. These controls have different failure modes. A platform with an IOMMU that is disabled during early boot, bypassed by a peer transaction, or configured with an overly broad domain is not equivalent to a platform enforcing narrow mappings throughout the device lifecycle.

Security objectives: confidentiality, integrity, availability, and containment

Confidentiality means one agent must not read another agent's protected data. Integrity means an agent must not modify data or control state beyond its authorization. Availability means the platform should continue providing service despite failures, congestion, or abusive traffic, subject to its resource and fault model. Containment means damage from a failing agent remains inside an intended boundary; it is not a synonym for error detection. An IOMMU permission fault may stop an unauthorized write but cannot by itself guarantee that the device will stop submitting requests or that an upstream switch remains responsive.

Trust boundaries must also be time-dependent. A buffer legitimately writable during an incoming packet transfer should stop being writable once the host revokes that grant and all relevant device translations have been invalidated. A hot-plugged device has different privileges before authorization, after driver binding, during operation, and after shutdown. The strongest designs define behavior at all of these transitions rather than checking only steady-state access.

Threat model and assumptions

Security design starts with a threat model. Relevant agents include a malfunctioning peripheral, compromised device firmware, a driver that supplies incorrect DMA addresses, an untrusted tenant assigned a virtual function, an externally attached PCIe-capable device, and a physically present adversary able to observe an exposed link. Their capabilities differ: an ordinary device may issue transactions using permitted requester identities, whereas a malicious bridge or hardware design might evade assumptions about identifiers or routing. A compromised kernel typically has much broader control than an isolated user-space application, and a physical attacker with access to unprotected memory chips falls outside what an interconnect IOMMU alone can solve.

An effective threat statement records the accessible ports, whether the device is hot-pluggable, its firmware update authority, expected request types, peer-to-peer paths, DMA windows, interruption privileges, and consequences of failure. It then identifies what the hardware actually enforces. A security conclusion valid for an integrated SoC IP block with immutable stream identification may not carry over to an arbitrary expansion bridge or an endpoint sharing routing resources with other devices.

Four independent security questions

A useful review separates four questions. Identification: how does the fabric label the origin of a request? Authorization: which addresses and operations are permitted for that identity? Transport protection: can parties on the link view or alter data in transit? Recovery: what happens if the requester violates a rule or fails mid-transaction? PCIe Requester IDs or Arm StreamIDs serve an identification role; an IOMMU domain and permission bits serve an authorization role; mechanisms such as PCIe Integrity and Data Encryption serve certain transport-protection roles; and error reporting, reset control, and device quiescence support recovery.

No single affirmative answer proves the whole system secure. A correctly tagged requester whose firmware is compromised can still misuse its allowed memory region. An encrypted link can convey a perfectly authenticated transaction to a memory address that the device should never have been authorized to reach. A system may prevent unauthorized DMA yet allow a device to exhaust shared bandwidth. Isolation policy must therefore name every protected asset and the control that enforces it.

CPU access, MMIO, and device-initiated DMA

Processor-generated memory transactions are usually interpreted through CPU privilege and virtual-memory rules. Memory-mapped I/O (MMIO) lets a CPU access a device's control registers through an address aperture, typically with special memory attributes and ordering requirements. DMA reverses the direction of agency: an I/O component initiates a read or write to an address it was given or derived. PCIe bus mastering and many on-chip DMA engines can perform this work without a CPU instruction for each transferred byte.

Therefore, a CPU page table marking a process page inaccessible does not alone prevent an attached device from reaching the underlying physical memory. The I/O side needs an enforcement mechanism that understands the device's requester and permissions. Likewise, an IOMMU that restricts DMA to RAM does not automatically prevent a privileged CPU driver from writing unsafe values into the device's own MMIO control registers. These are related but separate control planes; both require appropriate software policy.

Device-visible, physical, and virtual addresses

A DMA-capable device may receive an I/O virtual address (IOVA) that is not the CPU virtual address and need not equal the host physical address. The operating system or virtualization software arranges an I/O translation from the device-visible address to permitted target pages. A driver ordinarily uses its platform's DMA-mapping interface rather than assuming that the pointer used by the CPU can be placed directly in a hardware descriptor. Devices may also be limited by address width, bus bridge apertures, alignment requirements, and coherent versus streaming mapping rules.

An address is only meaningful inside its domain. The same numeric IOVA can refer to different physical buffers in two isolated DMA domains. For example, IOVA 0x4000 may map to physical page A for one adapter and physical page B for another, or be unmapped in the second domain. Such reuse does not imply a collision if requester identification and translation contexts are correctly enforced. The dangerous condition is a mistaken domain assignment, bypass path, or stale translation that causes a request to be interpreted using a more privileged mapping than intended.

End-to-end DMA authorization path

A typical authorized write follows this conceptual route: device endpoint → fabric request carrying requester information → routing and isolation checks → IOMMU translation and permission check → memory target. In a system with IOMMU translation, the IOVA is looked up in the appropriate device domain; an allowed write obtains its host-physical destination; a disallowed write should be rejected or faulted according to platform rules. Exact order and placement of checks depends on the root complex, integrated bridge, IOMMU hardware, and whether the transaction targets RAM or another device.

For a driver-created mapping, the lifecycle begins earlier. The software allocates or pins a buffer, establishes a DMA mapping, places the resulting device-visible address into a descriptor, and allows the engine to run. After completion and appropriate synchronization, it revokes or reuses the mapping according to the API contract. Linux's DMA API HOWTO explicitly describes why drivers should use device-specific DMA mapping and why mappings have a controlled lifetime. This software/hardware contract is as important to security as the translation table's nominal permissions.

IOMMU architecture and purpose

An input/output memory management unit (IOMMU) associates incoming DMA requests with translation and protection rules. It can provide address remapping, access-permission enforcement, translation caching, reporting of forbidden accesses, and—in supported configurations—features used by virtualization or shared address spaces. Analogous facilities appear under names such as Intel VT-d, AMD IOMMU/AMD-Vi, and Arm SMMU. The feature set, isolation granularity, and path coverage vary by product and firmware configuration.

An IOMMU is not a general-purpose firewall for every packet in a platform. Its primary remit is selected I/O address and protection operations; devices may have MMIO paths, peer routes, special windows, or privileged platform channels governed elsewhere. A deployment review should identify which requester identifiers reach which translation contexts, what regions can be accessed without translation, and whether the IOMMU is enabled at the point an untrusted device can initiate traffic. Presence of the hardware feature does not prove that it was used effectively.

Translation domains, page tables, and permissions

An I/O domain contains a set of permitted device-visible address ranges and their backing mappings. Hardware page-table entries commonly encode a target physical page together with permissions such as read or write; actual formats vary. A read-only descriptor region, for example, need not be writable by the consuming engine. Device requests that fall outside an enabled mapping, or attempt disallowed access types, may generate IOMMU faults. Enforcement depends on correctly associating each request with its domain and ensuring stale device-side or IOMMU-cached translations cannot persist after a revocation.

Permissions should be least-privilege and purpose-specific. A storage device reading a command queue should not automatically receive write access to that queue. A network receive buffer may legitimately need device write access but not arbitrary access to kernel page tables. Coarse identity-based domains that map all of host RAM for convenience defeat much of the expected protection even though the platform's IOMMU might technically be active.

Mapping granularity, padding, and adjacent memory

IOMMU permissions commonly operate at page-based granularity, such as 4 KiB base pages on a particular platform. A small logical buffer can share a translation page with unrelated bytes. If an entire page is mapped to a device, an implementation that does not provide finer subpage controls can expose all bytes in that mapped page to the device regardless of the logical object length. Correct buffer layout therefore matters. Sensitive and untrusted DMA data should not inadvertently occupy the same device-accessible page when that would violate the intended isolation boundary.

Guard pages, separate allocations, copy buffers, page-aligned rings, and suitably limited mappings can reduce unnecessary exposure, though they add memory or copying overhead. Large IOMMU pages may reduce translation pressure while increasing the minimum range of access. Alignment and isolation are distinct: a 64-byte-aligned descriptor need not reside alone on a 4 KiB page; an engineer must explicitly account for the allocation and mapping granularity that is actually enforced.

Default-deny mapping and controlled lifetimes

A robust design begins with no broad DMA access for an untrusted device, introduces only the ranges required for its current operation, and revokes mappings when the operation completes or the device loses authorization. Real operating systems may optimize this model through reusable mappings, pinned memory pools, or long-lived coherent allocations. Those choices can be valid, but they change the window of exposure and should be documented instead of described simply as temporary grants.

Revocation is not necessarily instantaneous. Software may need to stop new submissions, wait for outstanding operations, invalidate IOMMU translation caches, invalidate device address-translation caches if used, and ensure the hardware has acknowledged the relevant invalidation before reclaiming or reassigning memory. Otherwise, a buffer could be mapped to a new owner while an old device still holds a usable translation or pending write. The details follow the IOMMU implementation and operating system; security checks must assess the full transition rather than just the page-table update.

Requester identity and provenance

PCIe commonly uses a Requester ID based on bus/device/function identification for transactions. On-chip systems may use stream IDs, protection IDs, privilege attributes, or source labels propagated through the fabric. The intended result is a stable association between an initiator and the permissions selected for its traffic. Identity used for routing is not the same as authenticated identity. A configuration-space identity tells system software how a PCIe function is addressed; it does not by itself prove the firmware's provenance or that the endpoint behaves honestly.

Provenance also depends on the path. Bridges and switches must preserve or appropriately transform origin information. If a fabric accepts device-supplied identifiers without enforcing that they correspond to the input port, malicious or defective hardware may create attribution problems. ACS source validation and platform-specific request filtering are relevant here. A security review should ask who sets the source identifier, who can change it, and at which hardware boundary the asserted identity becomes trustworthy.

PCIe Access Control Services and routing boundaries

PCI Express Access Control Services (ACS) provides standardized controls used by capable components to constrain and redirect certain peer traffic and validate certain source characteristics. For example, peer-to-peer request or completion routing decisions can determine whether traffic reaches an upstream path where other protections operate, instead of moving directly between endpoints below a switch. ACS capability and configuration vary among root ports, switches, and endpoints; not all topologies expose the same isolation behavior.

An IOMMU guarding the path to system memory does not automatically inspect a peer-to-peer transaction handled entirely within a downstream switching hierarchy. A routing review must therefore ask whether peer transactions are possible, which ACS controls apply, and whether the device is in an isolation group with other functions. ACS is not encryption or device firmware authentication. The Linux PCI peer-to-peer DMA documentation emphasizes topology and ACS effects when reasoning about path support and routing.

IOMMU groups and the practical isolation unit

An individual PCIe function is not always independently isolatable. Two functions may share hidden state, an insufficiently isolated upstream path, or a bridge that permits traffic to bypass the expected boundary. The Linux IOMMU group concept represents the set of devices that cannot safely be separated for a particular DMA-isolation purpose under the known hardware topology. This is why device assignment to a virtual machine can be rejected or constrained even when a distinct PCI function number exists for each endpoint.

The group is a platform isolation assessment, not merely a numbering convenience. An operating-system listing with two devices in one group is a reason to investigate shared paths, not to assume either device is malicious. Conversely, manually splitting groups through unsafe overrides does not create missing hardware isolation. The Linux VFIO documentation explains these group-based concerns and the role of ACS-capable bridges. Newer software interfaces may represent device ownership differently, but the underlying hardware isolation question remains.

Address Translation Services (ATS)

Address Translation Services (ATS) can let a compatible PCIe device request translations and retain them in a device-local address translation cache. This can improve some workloads by avoiding repeated host translation work, but it changes the security and maintenance model. A cached translation must remain bound to the proper requester context and be invalidated when the host changes or revokes access. Hosts must not treat a device's claim about translation status as proof that a memory access is authorized.

ATS support, enablement, and filtering are platform-dependent. In particular, translated requests and any associated source/context metadata must be evaluated against the host's supported security model. A firmware or driver configuration that enables translation caching without reliable invalidation or domain separation can undermine revocation. The lesson is not that ATS is intrinsically unsafe, but that its performance benefit carries an explicit translation-lifecycle obligation.

Page Request Interface and demand paging

The PCIe Page Request Interface (PRI) permits supported devices to request assistance when a translation is unavailable or needs software intervention, enabling more flexible memory-management arrangements. A page request is not an authorization to ignore protection or to invent physical mappings. The host's memory manager decides whether the requested access is valid and, if appropriate, establishes or resolves the backing translation before the device proceeds.

PRI introduces queues, delays, and failure paths: a request might need a page to be made resident; it might be rejected for insufficient permissions; or it might time out when a process exits. A device that supports many outstanding memory operations may generate heavy page-request traffic. Rate limiting, attribution, orderly cancellation, and clear fault reporting are necessary to ensure the paging mechanism does not become an uncontrolled resource or availability risk.

Process Address Space IDs and shared virtual addressing

A Process Address Space ID (PASID) can distinguish address spaces or subcontexts for transactions from a compatible device. In a shared virtual addressing arrangement, a device may participate in processing memory references associated with a host process, subject to the supported translation, permission, and lifetime controls. Multiple processes can thereby use a device without necessarily putting all their memory into one undifferentiated DMA domain.

This feature is not automatic isolation. The platform must bind a PASID to the right process or translation context, prevent a request from selecting an unauthorized identity, coordinate page invalidations, and retire activity before the process address space disappears. Some devices and operating-system configurations support only a subset of ATS, PRI, PASID, and shared virtual memory features. The correct security assessment is feature-specific rather than a blanket claim that all modern PCIe devices offer per-process DMA protection.

Arm SMMU streams and contexts

In Arm-based systems, the System Memory Management Unit (SMMU) associates an incoming transaction with a stream and its applicable translation or protection configuration. SMMUv3 uses structures such as stream table entries, and may use context descriptors and multiple translation stages depending on configuration. The StreamID is a sideband origin label supplied by system integration; its trustworthiness depends on how the fabric generates and preserves that label. Platform integration can be as important as the SMMU's page-table engine.

For example, a shared DMA controller might generate traffic on behalf of multiple clients. If it always uses one StreamID, the SMMU may see a coarser security domain than the software considers distinct. Some designs use substream information to provide finer differentiation. Arm's SMMU Software Guide describes the translation flow. Reviewers must examine the actual SoC wiring and stream assignments rather than assuming one device, one stream, one trust domain.

Intel VT-d, AMD IOMMU, and implementation variance

On many x86 platforms, Intel VT-d or an AMD IOMMU provides the machinery used by operating systems and hypervisors to manage device address translation and, when supported, interrupt remapping. Support varies by chipset, processor generation, firmware configuration, driver, and topology. Even products from the same vendor can differ in how many domains or address widths they support, whether external ports are protected early enough, and how faults are reported.

Practical verification therefore starts with the platform's exposed capabilities and operating-system status, not marketing labels. It should identify which devices are translated, whether pass-through or identity-mapping exceptions exist, whether trusted devices are intentionally granted broad windows, and whether assignments preserve separation across all relevant transaction types. Translation is a necessary building block for many secure DMA deployments; it is not a guarantee of secure firmware, safe drivers, confidential links, or freedom from denial of service.

Device lifecycle from discovery to decommissioning

Every DMA-capable component passes through distinct trust states. During discovery, the platform identifies the device and determines its available resources. Before substantial bus mastering, firmware or the OS must establish a suitable isolation context or intentionally classify the hardware as trusted. Driver initialization configures MMIO apertures, DMA masks, descriptor rings, interrupt routes, and potentially device-specific firmware. Normal operation maps controlled buffers. Suspension, reset, hot-unplug, and device assignment change which requests remain valid.

A secure lifecycle is not simply allow once, trust forever. Changing from a host driver to a guest driver or restarting an accelerator can leave outstanding transactions and cached translations. A correct handoff ordinarily stops new work, reaches a quiescent state or enforces isolation despite misbehavior, revokes mappings, reinitializes device state, and grants new access. The exact ordering varies by platform. A useful engineering artifact is a state table showing, for every lifecycle phase, whether the device can initiate DMA and which protections are active.

Descriptor rings, doorbells, and limited authority

A DMA descriptor is a compact statement of the device's work: a buffer address, length, direction, and control flags. Submission and completion rings provide a software/hardware contract that may be memory-mapped to the host or managed through coherent allocations. The driver must not publish descriptors containing stale or unauthorized device-visible addresses. The DMA mapping must exist, be correctly sized, and have the intended access permissions before a doorbell or tail-pointer update tells the device that work is available.

The descriptor is not itself a security token unless the hardware and host enforce its scope. A buggy or malicious engine might ignore a length field or follow an altered next pointer. The IOMMU is valuable precisely because it constrains what is reachable even if the device behaves incorrectly. Descriptor validation, page layout, queue ownership, and hardware-enforced DMA windows work together; none is a complete substitute for the others.

Cache coherence, buffer visibility, and isolation

Cache coherence and access authorization answer different questions. Coherence coordinates which agent sees an up-to-date memory value; the IOMMU determines whether an agent may access a mapped region. A coherent DMA device still needs a valid mapping and should still respect authorization boundaries. A noncoherent DMA device can have perfectly appropriate IOMMU permissions and nevertheless read stale data if the host fails to synchronize CPU caches or use the required DMA API ownership transitions.

Memory visibility can also affect security. An old descriptor left visible to a device after software believes the ring has been retired may point to memory that is now allocated for something else. Systems should establish the required ordering between data initialization, descriptor publication, doorbell writes, completion observation, and unmapping. Do not confuse a completed MMIO store at the CPU with the device having finished all DMA writes; posted transactions, store buffers, and endpoint-specific completion rules make those events distinct.

Memory ordering and revocation races

Suppose a driver updates an IOMMU page table to remove a buffer and immediately returns the physical page to an allocator. A device might still have a transaction in flight or hold an older cached translation until invalidation is complete. A separate synchronization sequence can be needed to ensure that no permitted old transaction can touch the reclaimed page. The same challenge arises when transitioning a device from one VM to another or when freeing a long-lived ring during driver unload.

A robust review asks four questions: Was the device stopped from issuing new requests? Were in-flight requests drained or otherwise contained? Were relevant translation caches invalidated with completion established? Was the physical memory recycled only afterward? A successful software call to remove a mapping is only one part of this end-to-end guarantee. Different architectures offer different fencing and invalidation mechanisms, so the article states the general obligation rather than implying a universal instruction sequence.

Interrupt remapping and event injection

Some peripherals notify processors with message-signaled interrupts, in which an interrupt request is represented by a write-like bus transaction. Interrupt remapping can help restrict or translate the target of device-originated interrupt traffic and provide a boundary relevant to virtual-machine assignment. A device's DMA read/write permissions and its allowed interrupt destinations are not identical; mapping a memory buffer does not necessarily authorize arbitrary interrupt vectors.

On platforms with suitable interrupt-remapping support, software can associate an interrupt source with permitted targets and manage the assignment as a device moves between guests or CPU cores. On other platforms, device notification is controlled through different interrupt controllers or fabric-specific mechanisms. The distinction is especially important for pass-through virtualization, where an assigned guest may legitimately receive device events but must not thereby gain control of unrelated host or guest interrupt state. Consult the neighboring Interrupt Signaling article for the full event-delivery model.

SR-IOV physical and virtual functions

Single Root I/O Virtualization (SR-IOV) permits supported PCIe devices to expose a physical function (PF) and multiple virtual functions (VFs). A hypervisor can potentially assign different VFs to different guests while the underlying adapter shares scheduling logic, queues, firmware, on-card memory, and a physical upstream link. The IOMMU can help segregate host-memory addresses by function; the device itself must correctly enforce any isolation promised between virtual functions and the privileged PF.

A VF being a distinct PCIe function does not imply the physical adapter is free from cross-tenant leakage or denial-of-service concerns. PF firmware defects, shared buffers, insufficient internal access checks, and contention can compromise separation. Tenant workloads may observe performance changes even when memory permissions are correctly enforced. Reviews should therefore combine IOMMU mappings, PCIe topology, firmware provenance, on-device isolation architecture, and resource-governance testing.

Whole-device assignment to a virtual machine

With PCIe device pass-through, a guest is allowed to operate real hardware through a virtualization boundary. The hypervisor typically controls assignment, memory pinning and I/O mappings, while the guest manages device queues and MMIO within approved constraints. A secure configuration considers not just the endpoint's PCI address, but its IOMMU group, reset behavior, interrupt routing, peer-to-peer pathways, and any platform firmware services touching the hardware.

Whole-device assignment trades software emulation overhead for stronger guest access to the device. The guest is not thereby entitled to arbitrary host memory. It should have access only to the guest's permitted backing pages, and the host must ensure stale device activity cannot survive reassignment. If an endpoint cannot be reliably reset or belongs to a nonisolatable group, refusing the assignment may be safer than treating the presence of a separate PCI function as sufficient proof of isolation.

Nested translation and virtual IOMMUs

A guest operating system may believe it controls a virtual IOMMU and its own device-visible translations. The host hypervisor must still enforce the outer security boundary that prevents a guest or assigned device from reaching host or other guests' memory. Systems can compose or translate guest-managed views into a physical IOMMU configuration, subject to hardware support for nested translation and the virtualization interface being used.

Terminology matters: guest virtual address, guest physical address, device-visible IOVA, and host physical address can represent different stages in one request. A mapping correct at the guest level may not be legal in the host. If a nested path permits a guest to select unauthorized host mappings, the virtualization boundary has failed. Linux's IOMMUFD documentation explains hardware page-table and virtual-IOMMU abstractions used in contemporary userspace-managed I/O virtualization.

Mediated devices and shared accelerators

Not every shared device exposes independent PCIe virtual functions. A mediated device, a kernel-managed accelerator context, or a driver-operated command queue may multiplex a physical resource across users or VMs. Software can be responsible for validating commands, partitioning buffers, assigning translation contexts, and serializing access to privileged control registers. Hardware may add per-context address translation, protected execution queues, or internal memory firewalls.

The security boundary must be evaluated at the actual enforcement point. If all contexts share one DMA requester identity and one broad memory domain, claims of strong per-process isolation require additional on-device enforcement. If a device can select a PASID or equivalent substream, the platform must prevent a tenant from using another tenant's identifier. Performance fairness is another separate concern: an authenticated client might still overwhelm common hardware queues without quotas or scheduling controls.

External peripherals and hot-plug exposure

Thunderbolt and USB4 systems can expose PCIe-tunneled peripherals through physically accessible ports, depending on platform and configuration. An adversary with physical access may connect a device capable of requesting memory transactions. Security controls can include device authorization, IOMMU remapping, hot-plug policy, and restrictions that apply before a trusted driver is ready. The vulnerable window may be during boot, sleep transition, wake, or before user sign-in, not only when the desktop is fully operational.

Microsoft's Kernel DMA Protection documentation explains Windows policy for capable external DMA devices, while the Linux USB4 and Thunderbolt guide describes authorization and IOMMU-related behavior on supported systems. Neither document implies every machine or peripheral supports identical protection. Platform firmware, boot policy, driver compatibility, and device topology must be assessed together.

On-chip interconnect firewalls and protection attributes

Systems-on-chip often contain a fabric controller or interconnect firewall that accepts or rejects transactions by initiator identity, target address, privilege, security state, or protection attributes. This can protect on-chip SRAM, boot ROM, cryptographic engines, and control registers from devices that share the same SoC. These mechanisms sometimes operate independently of, or in addition to, an SMMU. An IP block may have permission to access its designated buffer but not the key-storage region or another subsystem's control space.

The hardest question is frequently who supplies the protection attribute. A bit carried on an internal bus is not a trustworthy security label if an untrusted master can freely set it to privileged. The SoC integration must bind the attribute to a hardware-enforced origin, enforce filtering at trustworthy points, and define defaults for unmapped or malformed requests. Designs should also address bridge translation, debug ports, boot-time ownership, and DMA engines that service multiple clients with different permissions.

MMIO register access and control-plane security

Memory-mapped device registers can confer enormous authority: enabling bus mastering, resetting a security engine, changing interrupt destinations, reprogramming descriptor bases, or exposing sensitive diagnostics. The operating system must restrict which drivers and privilege domains can map those register ranges, even if the DMA engine's access to RAM is independently constrained by an IOMMU. Device register windows can also be aliased, remapped through bridges, or opened by firmware before the OS establishes its final policy.

A good register-security plan separates normal operational registers from privileged configuration; validates register ranges and reserved fields; avoids mapping entire physical address regions to untrusted processes; and defines how control is transferred during virtualization. It also recognizes that read access may disclose secrets and that write access may alter later DMA policy, not just immediate device state. The companion Memory-Mapped I/O and Address Decoding article covers decoding details.

Peer-to-peer memory transactions

Peer-to-peer (P2P) DMA allows one device to access resources associated with another without necessarily sending the payload through main memory. This can be valuable for storage-to-accelerator transfers and other data-intensive workflows. Yet a P2P route changes the security observation path. A request that stays inside a PCIe switch hierarchy may not traverse the IOMMU that protects system RAM. Permission decisions can instead depend on ACS routing, endpoint capability, device-local access controls, and the topology of the host bridge.

Fast path does not mean safe path. Two devices belonging to different tenants must not become implicitly authorized to read or modify one another's BAR memory merely because their switch supports direct routing. A design review should draw the complete path for each approved P2P transfer and identify the enforcement point along that path. Where a trustworthy check is absent, the appropriate answer may be to disallow direct P2P or co-locate the participants within a shared trust domain rather than pretending the normal host-memory IOMMU provides coverage.

Device firmware and the difference between identity and trust

An endpoint's advertised vendor and device identifiers identify a product interface for enumeration; they do not cryptographically establish its current firmware, manufacturing provenance, or configuration. Device firmware may parse host command queues, manage internal memory, run embedded processors, and hold persistent state. Its failure or compromise can influence permitted DMA operations even when external permissions are enforced correctly. A malicious device need not violate an IOMMU mapping to steal data if software legitimately gives it sensitive buffers for processing.

Defensive controls include appropriately scoped device privileges, authenticated updates where supported, signed and measured firmware, controlled recovery modes, secure boot chains, and auditability of hardware inventory. NIST SP 800-193 provides broader guidance on platform firmware resiliency. It does not replace vendor-specific device-security validation, but it is useful for structuring protection, detection, and recovery expectations for firmware components.

Component authentication and measurement: SPDM

The Security Protocol and Data Model (SPDM) developed by DMTF offers mechanisms for component authentication, measurement reporting, key exchange, and secured messaging when supported by the relevant transport and device implementation. An attestation flow can provide evidence about a component's cryptographic identity and measured state to a verifier applying a policy. However, the verifier still must decide which identities, measurements, versions, and security claims it accepts.

Attestation is not I/O authorization. A successfully authenticated device should not automatically receive broad DMA mappings, and a device with carefully restricted mappings is not thereby proven genuine. Certificate-chain verification, measurement freshness, replay protection, and protection of the attestation keys all matter. See DMTF's SPDM Architecture White Paper and PCI-SIG's Component Measurement and Authentication work for standards context.

PCIe DOE and link confidentiality with IDE

PCIe's Data Object Exchange (DOE) provides a standardized device communication facility that can carry supported data objects used by protocols such as component measurement/authentication. PCIe Integrity and Data Encryption (IDE) targets selected physical-link security threats, providing confidentiality and integrity protection for supported traffic under the specified deployment model. Key establishment and provisioning are separate operational duties; standards can define mechanisms without guaranteeing that a given link has them enabled.

An encrypted and integrity-protected link still carries transactions that must obey IOMMU and peer-routing permissions. Likewise, an IOMMU does not protect a cable against physical eavesdropping. IDE should not be confused with the ordinary link CRC: a CRC is intended to detect accidental corruption, whereas cryptographic integrity addresses an adversary who can deliberately modify traffic. PCI-SIG's IDE revision document discusses the physical-link threat model and related secured-message considerations.

Coherent I/O, shared memory, and CXL-style fabrics

Coherent interconnects can permit devices, accelerators, and processor clusters to observe shared memory with additional cache-state coordination. Coherence does not eliminate authorization; it means valid accesses are kept appropriately synchronized under the memory model. Memory expansion and accelerator fabrics may add endpoint-managed memory, multiple address spaces, routing, or host-managed regions that require separate ownership and access checks. The security design must identify which agent owns a page, who can map it, and when ownership changes.

A coherent device can still be compromised, a shared-memory aperture can still be too broad, and high-speed access can still produce denial of service. The specific isolation techniques depend on the implementation's translation units, switch controls, coherency protocol, management firmware, and device capability. It would be inaccurate to infer that every coherent fabric offers the same IOMMU or encryption semantics as PCIe, or that support for a newer interconnect generation automatically enables stronger cross-tenant isolation.

Denial of service and shared resource exhaustion

Address-based isolation primarily protects which memory can be accessed; it does not necessarily limit how often an authorized device can access it. A misbehaving endpoint may saturate an uplink, create bursts of IOMMU faults, exhaust page-request queues, overload interrupt delivery, or consume arbitration slots. Such behavior can degrade unrelated workloads even when no confidential data is directly exposed. A security evaluation that checks only whether out-of-range addresses fault misses this availability boundary.

Possible controls include QoS policies, interrupt moderation, request-rate limits, fault-rate limits, PCIe or SoC traffic-class scheduling, partitioned queues, and administrative device quarantine. Their effectiveness is topology-dependent. If two tenants share a physical function, independent IOMMU domains will not necessarily prevent shared scheduler or firmware contention. Service guarantees require workload measurements as well as permission tests.

Handling unauthorized transactions and hardware faults

An unauthorized request can produce an IOMMU fault, a fabric permission error, an unsupported request completion, or another platform-specific outcome. An error report should ideally identify the source, offending IOVA or address, access type, translation context, and reason. However, device firmware, bridges, and host controllers may report errors at different layers; not every transaction failure is attributable to a security policy. Error logs should be correlated with outstanding work, reset state, and the expected memory map.

Fault handling policies distinguish a recoverable driver mistake from repeated suspicious behavior. A system might reject one request and log it, then quarantine a device after repeated violations. A fatal error might require an endpoint reset or whole-bus recovery. Resetting without first controlling outstanding transactions can create new hazards, especially if shared memory is recycled or another tenant is assigned the device. Recovery must preserve the same isolation guarantees that normal operation depends on.

Quarantine, reset, and safe reassignment

Device quarantine means reducing an endpoint's ability to affect the rest of the platform while investigation or recovery proceeds. It may include blocking bus mastering, removing DMA mappings, disabling interrupts, preventing new queues from starting, or detaching a port. Exact containment tools vary: a faulty endpoint may ignore software commands, so isolation cannot rely exclusively on cooperation from its firmware. Hardware-level blocking at a trustworthy root or interconnect boundary is preferable where available.

Before reassigning the device, the platform should determine whether function-level reset, bus reset, power cycle, or firmware recovery actually clears its internal queues and translation caches. Some reset types affect sibling functions or devices sharing a bridge. An engineer should document which other workloads are disrupted by a containment action. Device availability, host integrity, and fault containment must be treated as related but distinct objectives.

Observability and auditable security state

A defensible isolation claim needs measurable evidence. Relevant artifacts include enabled IOMMU status; which endpoints use which protection domains; mapping lifetimes; ACS capability and policy along the route; interrupt-remapping status; assigned guest or process contexts; device firmware and attestation state; hot-plug authorization policy; and fault counters. A kernel log that simply reports "IOMMU enabled" is insufficient to prove every external port is covered or that every peer path is filtered.

Good telemetry preserves timestamps, device identifiers, domain or PASID context where available, transaction direction, and error reason without exposing sensitive memory contents unnecessarily. Diagnostics should be designed to handle a device that creates an error flood: reporting must not itself exhaust the host. Periodic configuration review is necessary because firmware upgrades, new adapters, bridge replacements, and hypervisor settings can change isolation topology even when no application software has changed.

Performance costs and security trade-offs

Translation adds lookup and management work, though IOMMU caches and efficient mapping strategies can reduce steady-state overhead. Mapping and unmapping many tiny buffers may cost more CPU time than reusing carefully managed pools, while long-lived mappings expose memory for longer periods. Large pages can improve translation reach but also increase the minimum accessible region. ATS reduces some translation traffic at the cost of stronger invalidation obligations. Peer-to-peer routing can save data movement while bypassing an enforcement point otherwise present on a host-memory path.

No single performance number describes all deployments. Evaluate throughput, small-message latency, mapping rate, translation misses, IOTLB behavior, device context switches, CPU overhead, and isolation-fault behavior under representative workloads. Optimization should start from the minimal required security boundary, then choose engineering mechanisms that preserve it. Deliberately disabling DMA protection to improve benchmark scores is not a neutral optimization when devices or tenants are untrusted.

Security design checklist

For a new platform or integration, record (1) each DMA-capable initiator; (2) each protected target; (3) which identity labels a request; (4) the trustworthy hardware point that enforces that label; (5) the permitted address ranges and permissions; (6) IOMMU or firewall mapping and invalidation procedures; (7) peer paths, bridges, and ACS policy; (8) interrupt routes; (9) firmware and authentication assumptions; (10) reset and reassignment sequence; and (11) fault reporting and resource-exhaustion limits. This is a threat-modeling checklist, not proof that every platform exposes identical features.

Require testable acceptance statements. For example, "Adapter A can write only its allocated receive-buffer pages while its queue is active," or "A VM-assigned function cannot perform DMA to a host-only page and cannot signal another guest's interrupt route." These are much stronger than the vague statement "DMA security is enabled." Each claim should name the protected memory, lifecycle phase, tested action, and evidence source.

Worked example 1 — An allowed DMA range and its boundary

Constructed scenario: Device A has permission to write one 4 KiB IOVA page beginning at 0x00004000. Because 4096 decimal equals 0x1000, the authorized half-open interval is [0x4000, 0x5000), or 0x4000 through 0x4FFF inclusive. A four-byte write beginning at 0x4FFC addresses bytes 0x4FFC–0x4FFF and is wholly inside the mapped page. A four-byte write beginning at 0x4FFE extends through 0x5001 and crosses the boundary.

Interpretation: A correctly enforced boundary must not permit the unauthorized part of the crossing write. The precise outcome—rejection of the whole request, partial processing, or an error reported by a particular hardware layer—depends on transaction rules, so software must never assume a cross-boundary access is safely atomic. A descriptor length check in device firmware is not sufficient; the hardware mapping supplies a second, independent boundary. The example is a teaching address calculation, not a characterization of any particular IOMMU's split-request behavior.

Worked example 2 — Two domains reuse the same IOVA

Constructed scenario: A network adapter in Domain A and an accelerator in Domain B both receive IOVA 0x20000. A maps 0x20000 to host physical 0x810000, while B maps the same IOVA to host physical 0x940000. Both address ranges are valid within their own translation domains. If A's request is tagged and translated as A, it reaches 0x810000; if B's request is tagged and translated as B, it reaches 0x940000.

Interpretation: Unique numeric DMA addresses across the entire computer are not necessary when translation identities provide separation. The failure mode is not the repeated IOVA, but misattribution: an A request using B's translation context, an accidental shared domain, or a bypass path. This example shows why security logging should capture both the offending IOVA and its requester or protection-domain context. A bare address value without the domain is insufficient to diagnose the violation.

Worked example 3 — Mapping a tiny object exposes a full page

Constructed scenario: A 128-byte command record sits somewhere inside a 4096-byte page. An IOMMU implementation allows or denies access at 4096-byte page granularity, and software maps the containing page writable for a device. The intended object occupies 128 / 4096 = 3.125% of the page. The remaining 4096 - 128 = 3968 bytes may be writable at the same hardware permission granularity, even if device software is told to ignore them.

Interpretation: A logically small buffer can have a much larger hardware access envelope. The designer can place DMA-visible records in dedicated pages, use guarded pools, or copy data through an isolated buffer when the trust boundary requires it. These techniques spend memory or CPU work to reduce unintended access. Some architectures provide finer controls or different page sizes; the example specifically assumes page-granular permission checking and no additional subpage firewall.

Worked example 4 — Permission directions on a descriptor queue

Constructed scenario: Host software publishes a list of transmit descriptors and expects the device only to read them. Payload buffers should likewise be readable by the device; a completion-status page must be writable. An idealized design creates three permissions: descriptors: device read, payload: device read, status: device write. If the same broad domain marks all three regions read/write, a malfunctioning endpoint can modify data the host intended it only to consume.

Interpretation: Separating read and write permission can narrow damage without changing the function of the bus. Real hardware may require writable ownership bits or in-place completion descriptors, so a specific implementation can use a combined ring with careful layout. The engineering task is to assign each range the minimum rights required by the actual protocol, not to impose a universally read-only descriptor format. A design review should state those protocol requirements explicitly.

Worked example 5 — A buffer revoked before the transfer is drained

Constructed scenario: A driver posts a receive buffer, then sends an unmap request immediately after observing a software timeout. Unknown to the driver, a DMA write is already in flight; a device address-translation cache may also retain a translation. If the allocator reuses the physical page for secret host state before transaction draining and invalidation are complete, the old device may still reach that page under an earlier authorization.

Interpretation: Revocation is a sequence, not merely a page-table edit. The platform must establish which operations have committed, control subsequent requests, process IOMMU/ATS invalidation, and only then release the memory for a different use. Some architectures make portions of this ordering automatic; others require explicit driver and platform operations. The correct implementation must follow the documented DMA API and device reset semantics. This is a hypothetical race analysis, not instructions for exploiting a particular system.

Worked example 6 — Peer-to-peer routing avoids the host-memory path

Constructed scenario: SSD S and accelerator G reside beneath one PCIe switch. The platform allows a direct transaction route between their endpoint resource windows. A request from S to G can be switched locally rather than traveling upstream through the host-memory IOMMU. Even if S has a narrow IOMMU domain for system RAM, that domain alone does not decide whether G should accept S's peer memory request.

Interpretation: The review must inspect switch ACS controls, peer resource ownership, endpoint-local access rules, and any host policy that governs the route. If the devices belong to different guests and the platform cannot demonstrate appropriate separation, the safe design may prohibit such P2P traffic. Whether the route exists at all depends on the actual topology and software support. The example illustrates a protection-path gap, not a blanket claim that every PCIe switch routes peer traffic in this way.

Worked example 7 — Group assignment in virtualization

Constructed scenario: A platform presents a four-function adapter. The OS finds that two functions share an IOMMU group because their upstream path does not provide adequate independent isolation, while the other two functions are independently groupable. A proposed assignment would give Function 0 to VM A and Function 1 to VM B, even though both are in the first group.

Interpretation: Distinct function numbers are not enough to establish two independent security boundaries. The operator should reject or redesign the assignment unless the platform offers a validated means of separation. Placing both functions in one VM, assigning the whole group to one trusted owner, or choosing hardware with stronger function isolation are examples of different policy responses. Unsafe topology overrides do not create missing physical enforcement. The result is a group-level review, not evidence that the adapter's function numbering is invalid.

Worked example 8 — Translation-table size and permission trade-off

Constructed scenario: A device needs temporary access to a 64 KiB buffer using 4 KiB IOMMU pages. The mapping requires 64 KiB / 4 KiB = 16 base-page translations, ignoring upper-level page-table structures. If a hypothetical hardware implementation instead uses one supported 64 KiB mapping, fewer leaf entries might be involved. However, a single large mapping may be undesirable if only a subset of the 64 KiB is intended for the device.

Interpretation: Translation efficiency is not an automatic reason to widen a security boundary. The designer should weigh mapping operations, IOTLB reach, alignment, and the amount of extra memory exposed. Other IOMMU page sizes and table formats exist, so the number 16 applies only to this simplified 4 KiB setup. Page-table entry counts are not a direct measurement of power, latency, or actual memory consumption.

Worked example 9 — Tiny DMA buffers and mapping cost

Constructed scenario: A driver submits 100,000 DMA transfers per second. Each transfer requires a map and unmap cycle, and together those operations take an assumed 0.6 microseconds of CPU time per transfer. The mapping work therefore consumes 100,000 × 0.6 µs = 60,000 µs, or 60 milliseconds of CPU time per second. That equals 6% of one CPU core's time under the stated serial accounting. This excludes interrupt handling, descriptor setup, and application work.

Interpretation: Batching or reuse of appropriately protected buffers might reduce the management overhead, but can keep pages mapped longer. A performance optimization should compare reduced CPU work with the changed lifetime and scope of device access. The 0.6-microsecond cost is fictional and not a benchmark claim. Actual mapping cost depends on the DMA API, IOMMU implementation, invalidation pattern, CPU, and workload.

Worked example 10 — IOTLB miss cost in a simplified model

Constructed scenario: An engine performs 256 independent DMA address translations, of which one misses in an I/O translation cache. Assume the miss adds 100 nanoseconds of serialized, nonoverlapped delay while cache hits add no additional modeled delay. The mean extra cost is 100 ns / 256 = 0.390625 ns per request. If the misses or accesses overlap, this mean-cost model no longer predicts observed completion time directly.

Interpretation: This simple average shows why translations can matter to throughput without implying that each DMA transaction stalls for a full page walk. Real effects also depend on request concurrency, ATS caching, prefetching of translations, memory hierarchy, and queue occupancy. Security-relevant design choices—page size, protection domains, and invalidation policy—can affect translation performance. The measurement must isolate those effects rather than assuming a universal IOMMU penalty.

Worked example 11 — A hot-plug authorization sequence

Constructed scenario: An unfamiliar PCIe-capable external device is attached to a laptop through a supported tunneling interface. The device becomes visible to the system, but policy does not yet authorize unrestricted DMA. The OS evaluates whether it has a compatible driver and a protected DMA-remapping path. Only after establishing the accepted policy does the device receive the limited access needed for its normal function.

Interpretation: Enumeration, driver binding, and authorization are different lifecycle steps. On an unprotected platform, early-boot or wake transitions might have different risk. On a protected platform, a newly attached device can legitimately be blocked even if it is electrically functional. This example illustrates why a security check should record firmware settings and OS state at the exact moment of attachment rather than only testing after the machine has been running for several minutes.

Worked example 12 — Attested but overprivileged device

Constructed scenario: A PCIe storage controller presents a valid SPDM identity and acceptable firmware measurements. The host then erroneously grants that controller write access to every host-physical page. The attestation result can be genuine and the memory-access policy still dangerously broad. If the controller malfunctions, it has the opportunity to corrupt memory outside its workload even though its component identity was checked successfully.

Interpretation: Trust evidence and permission scope must be separate approvals. A useful policy is authenticate the endpoint, assess its state, then grant only the resources needed for its task. The converse also matters: a device may have narrowly scoped DMA permissions yet lack cryptographic provenance. Neither condition independently satisfies a security requirement that demands both. This example distinguishes authentication from runtime authorization without presuming any particular firmware vulnerability.

Worked example 13 — Fault-rate monitoring

Constructed scenario: A controller reports 120 IOMMU permission faults in a 30-second interval. Its average fault rate is 120 / 30 = 4 faults per second. That number alone does not identify the cause. It could reflect a broken descriptor ring, stale address mapping, a race during device reset, or a device trying to access a forbidden region. The timing, requester identity, and access type must be correlated with driver and application activity.

Interpretation: A useful monitoring policy may look for sudden changes in fault rate or repeated accesses to host-only regions. Quarantine should consider whether the device is needed for essential I/O, whether isolation remains intact, and the risk of leaving it active. A single numerical threshold should not be presented as a universal standard. Rate measurement is an entry point for diagnosis, not a substitute for incident context.

Worked example 14 — Shared-bandwidth denial of service

Constructed scenario: Two accelerator tenants share a 32 GB/s upstream data path. A device belonging to Tenant A generates 28 GB/s of sustained traffic, while Tenant B wants 12 GB/s. The combined demand is 40 GB/s, exceeding the path's nominal 32 GB/s limit by 8 GB/s before protocol overhead. At least one workload must be throttled, queued, or denied part of its demand; memory permissions can remain correct throughout.

Interpretation: This is an availability and scheduling problem, not necessarily a DMA address-isolation violation. Fair-share arbitration, per-tenant quotas, and traffic-class policies may be needed to enforce a service objective. The actual outcomes depend on direction, payload efficiency, competing resources, and hardware arbitration. The example illustrates why a multi-tenant security assessment must measure interference in addition to testing for unauthorized memory reads and writes.

Worked example 15 — A defensible virtual-function handoff

Constructed scenario: A network VF is reassigned from VM A to VM B. The host prevents new submissions from A, waits for or contains outstanding DMA, clears or resets the function state using a platform-validated method, revokes A's mappings and translation caches, reprograms interrupt-remapping and I/O domains, and then allows B to initialize its queues and buffers. The host also verifies that the PF and sibling VFs cannot access the new guest's state through shared internal resources contrary to policy.

Interpretation: Merely changing the guest's PCI device assignment is not sufficient. The trust boundary includes in-flight transactions, on-device queues, cached translations, interrupt targets, and shared-function firmware. A device with unreliable reset isolation may not be suitable for frequent reassignment. This is an illustrative sequence; concrete implementations must use documented OS and hardware APIs and may require additional steps or different ordering.

Worked example 16 — A complete isolation acceptance test

Constructed scenario: A design specification states that Controller C may read a 16 KiB descriptor table, write a 64 KiB receive pool, and signal a dedicated completion interrupt. The acceptance test first verifies those intended operations work. It then exercises a read from the receive pool where read permission is intentionally absent, a write outside the pool, an invalid requester context, a revoked mapping after transaction drain, and an interrupt to a disallowed destination. Each negative test should be performed in a safe, isolated validation environment that cannot corrupt production data.

Interpretation: Passing the positive cases proves function, not enforcement. Passing the negative cases provides stronger evidence, but only for the paths and states actually tested. The test must also consider peer-to-peer routes, reset, hot-plug, firmware state, and concurrency if they are in scope. Reviewers should record observed faults, whether the device was contained, and whether legitimate traffic recovered. This is the difference between checking a feature flag and validating an end-to-end hardware security contract.

Specialist glossary

  • Access Control Services (ACS): PCIe facilities for selected peer-routing and source-validation controls, implemented and configured according to component capability.
  • Address aperture: Region of an address space through which particular memory or device resources can be reached.
  • Address Translation Services (ATS): PCIe capability that allows supported endpoints to request and cache translations under host-managed rules.
  • Attestation: Protocol-backed process in which a component provides evidence about identity or measured state for evaluation by a verifier.
  • Authorization: Decision about which operations an identified actor may perform on a specified resource.
  • Backpressure: Flow-control signal or mechanism that delays new work when downstream resources are occupied.
  • BAR (Base Address Register): PCIe configuration-space register that describes a function's requested memory or I/O aperture.
  • Bounce buffer: Intermediate memory used when device addressing or coherence limitations prevent direct use of an original buffer.
  • Bus mastering: Capability of a hardware agent to originate bus transactions rather than only respond to host requests.
  • Cache coherence: Mechanisms governing consistent views of cached memory values among participating agents.
  • CMA: Component Measurement and Authentication, a PCI-SIG-defined adaptation of relevant component security protocols.
  • Completion queue: Data structure through which a device records finished operations for software consumption.
  • Context descriptor: A configuration structure associated with a particular SMMU or other I/O translation context where supported.
  • Data Object Exchange (DOE): PCIe communication facility for standardized device data objects used by supported protocols.
  • Default deny: Policy under which access is refused unless a specific rule permits it.
  • Descriptor ring: Reusable sequence of DMA work descriptions managed between host and device.
  • Device identity: Label or cryptographic identity representing a hardware endpoint; the term must be qualified by how it is established.
  • Device quarantine: Policy and mechanism that restrict a failing or untrusted endpoint's effects while diagnosis or recovery proceeds.
  • DMA: Direct memory access, a device or controller transfer that does not require CPU copying of every individual payload item.
  • DMA domain: Security and translation context specifying what DMA operations an associated requester may perform.
  • DMA mapping: Authorized association between a device-visible address and underlying memory according to a platform's DMA rules.
  • Doorbell: Register or notification mechanism by which software tells a device that new work is ready.
  • Endpoint: Device-side participant at a termination point of an interconnect connection.
  • Firmware: Software or data embedded in or loaded into a hardware component for low-level operation.
  • Function-level reset (FLR): Standardized reset capability for certain PCIe functions, subject to implementation and shared-resource limits.
  • Guest physical address: Address used to represent memory from a virtual machine's perspective, potentially translated further by the host.
  • Hardware firewall: Interconnect protection logic that allows or rejects transactions according to source, target, and privilege rules.
  • Host physical address: Physical memory address used at the host or system-memory level.
  • Hot plug: Attachment or removal of a device while the platform is powered and capable of detecting the change.
  • Identity mapping: Translation arrangement in which input and output address values are equal over a configured range.
  • Input/output memory management unit (IOMMU): Hardware that provides selected I/O address translation, protection, and related features.
  • Integrity and Data Encryption (IDE): PCIe security mechanism designed to protect selected link traffic against supported confidentiality and integrity threats.
  • Interrupt remapping: Hardware and software control over translation or restriction of device-generated interrupt targets.
  • IOVA: I/O virtual address used by a DMA requester, interpreted in the appropriate I/O translation context.
  • IOTLB: I/O translation lookaside buffer, a cache of address-translation information used by an IOMMU or related engine.
  • Isolation domain: Set of initiators and target resources intentionally placed within one trusted enforcement boundary.
  • Least privilege: Principle of granting only the access needed for a defined task and duration.
  • Link encryption: Cryptographic protection of data transported across a link; does not by itself authorize the carried operation.
  • Mediated device: Software-managed abstraction of hardware resources shared among multiple consumers under additional controls.
  • Memory consistency: Rules describing the order in which operations become observable to participants in a memory system.
  • Memory-mapped I/O (MMIO): Address-based access to device control or data registers through a processor-visible space.
  • MSI/MSI-X: PCIe interrupt mechanisms that deliver device events through message-signaled transactions.
  • Nested translation: Composition of translation stages, often used in virtualized I/O address spaces.
  • Noncoherent DMA: Device memory access for which explicit cache synchronization may be required.
  • On-chip interconnect: Communication fabric connecting processor, memory, and peripheral blocks within an SoC.
  • Page Request Interface (PRI): PCIe capability for supported device page requests and translation-resolution workflows.
  • PASID: Process Address Space ID, used to distinguish supported device address-space contexts.
  • Peer-to-peer DMA (P2P): Device-to-device data movement that may avoid a path through system DRAM.
  • Permission fault: Event indicating an attempted access violates the configured access rules.
  • Physical function (PF): Privileged physical PCIe function that may control underlying SR-IOV resources and virtual functions.
  • Posted write: Write transaction whose transport may not provide a matching end-to-end completion response to the initiator.
  • Protection attribute: Metadata conveying a request's privilege, security state, or other filtering category.
  • Requester ID: PCIe origin identifier used in transaction routing, translation and control; not necessarily cryptographic identity.
  • Reset domain: Set of components whose state is affected by a particular reset operation.
  • Root complex: Host-side PCIe structure that connects processor/memory resources and the PCIe hierarchy.
  • SMMU: Arm System Memory Management Unit, implementing I/O translation and protection as supported by the design.
  • SPDM: DMTF Security Protocol and Data Model, supporting component authentication and secured communication mechanisms.
  • SR-IOV: Single Root I/O Virtualization, a capability for exposing virtual PCIe functions from supported physical hardware.
  • StreamID: Identifier attached to applicable Arm SMMU transactions, commonly selecting the stream-level protection context.
  • Substream: Finer transaction identity below a stream, used by certain I/O translation arrangements.
  • Submission queue: Host/device work queue holding commands or descriptors ready for device consumption.
  • Translation cache invalidation: Operation that makes old address translations unusable in affected caches according to architecture rules.
  • Translation context: Hardware-selected rules for interpreting an IOVA and access permissions.
  • Trusted path: Route whose participants and enforcement points satisfy the relevant system's threat model.
  • Virtual function (VF): Lightweight PCIe function exposed by an SR-IOV-capable device for separate assignment or use.
  • Virtual IOMMU: Guest-visible abstraction of I/O translation facilities managed by virtualization software.
  • VFIO: Linux device access and assignment infrastructure emphasizing controlled device ownership and DMA isolation.
