Scope and Fundamental Definition

An interrupt is a request for a processor or execution environment to attend to an event. In a computer interconnect, the source may be a network controller that has finished filling a receive buffer, a storage device that has completed commands, a timer, an error-monitoring block, or another processor. The event may be conveyed by an electrical signal, a controller input, or a specially directed memory-write transaction. In each case, an interrupt tells the system that something deserves service; it does not itself transport the associated packet, sector, sample, or computation result. Those payloads ordinarily travel by separate memory or I/O transactions.

This Level 5 specialist article treats interrupt signaling as an interconnect and delivery mechanism. It explains what initiates notifications, how they are represented and routed, when an interrupt becomes pending or active, and how software safely observes the event and returns the device to a serviceable state. Interrupt-handler programming, process scheduling, CPU exception architecture, and detailed PCIe transactions have their own disciplinary treatments. Examples below are illustrative models, not certified timing data for a named processor or board. An interrupting source, an interrupt controller, and an interrupt handler have different responsibilities and should not be used as interchangeable terms.

Interrupts, Events, and Data Transfer Are Different Operations

A device may move a thousand data bytes by DMA, place one completion descriptor into a host-memory ring, and then send one interrupt. The data movement, completion-record publication, and interrupt signaling are three logically distinct actions. A software handler typically uses the notification to discover which queues need service; it must inspect the actual device or ring state, rather than assuming that one interrupt corresponds to exactly one payload, packet, or completion record. Coalescing can cause one signal to represent many events, while shared interrupt mechanisms can require a handler to determine which device caused the signal.

An event is an underlying condition such as a buffer reaching a threshold or a DMA write finishing. Interrupt status is the hardware-recorded representation of that condition, possibly in registers, pending-bit arrays, or controller state. Interrupt delivery is the path that informs a processing element. Service is the software or firmware action that resolves the condition. Conflating these layers causes common bugs: acknowledging the controller does not necessarily clear a device's pending reason; clearing a device status register does not necessarily mean all submitted work is consumed; and receiving a message-signaled interrupt is not equivalent to a complete software memory-ordering contract.

Why Systems Use Interrupts Instead of Continuous Polling

Polling repeatedly reads a device's completion status or memory ring. It can give low latency when the polling loop is scheduled continuously and the data is cache-resident, but it consumes execution resources and may generate interconnect traffic. Interrupts permit the processor to do other work or enter a low-power state until hardware requests service. The economic trade-off concerns the event rate, cost of checking for work, wakeup and context overhead, required tail latency, and how long a burst of events lasts.

Many production systems mix strategies. For example, a network driver may begin processing after an interrupt, then temporarily suppress further interrupts while it drains a receive queue by polling. This avoids an interrupt per packet during a burst without committing a core to busy-waiting during idle periods. Neither mode is universally superior. The interrupt arrangement is a mechanism for directing attention, whereas the device completion contract defines what work is available and when its memory is valid. Design studies must measure both event-to-service latency and the CPU time used for notifications.

End-to-End Interrupt Delivery Lifecycle

A useful seven-stage model is (1) a device detects an event, (2) the source latches or qualifies its status, (3) it asserts an interrupt line or emits an MSI write, (4) the interrupt controller records and prioritizes the incoming request, (5) a CPU or virtual CPU accepts delivery, (6) software identifies and services the event, and (7) the source and controller are acknowledged or deactivated according to their respective protocols. Some stages overlap, and not every controller uses each state label. The model nevertheless provides a disciplined way to localize an interruption in service.

A device may continue performing DMA while a notification is pending. Several events may accumulate into the same status bit or queue. Another interrupt may arrive before the handler has finished, subject to masking, priorities, processor context, and source signaling semantics. The controller's acceptance of an interrupt is only one step in a larger lifecycle: a driver may need to quiesce or clear the source, drain a completion ring, and make a release or acknowledgment visible to hardware. If a fault happens midway, checking which of the seven stages actually occurred is more reliable than assuming that a missing handler invocation proves a broken physical link.

Interrupt Sources and Architectural Categories

Sources include external peripherals, on-chip timers, interprocessor signaling, fault reporting, and software-generated notifications. External devices commonly ask a central interrupt controller to forward an event to one or more CPUs. On-chip peripherals may have dedicated interrupt lines into a SoC controller. PCI Express devices normally use MSI or MSI-X when supported and configured; legacy compatibility pathways can emulate pin-based INTx behavior. Interprocessor interrupts support activities such as translation-cache invalidation, work rescheduling, or coordination among cores, but they are not ordinary peripheral completion events.

The distinction between external interrupts and exceptions matters. A synchronous page fault is caused by the currently executing instruction under processor-defined rules, while a storage completion interrupt is typically asynchronous to the instruction stream. The handler entry mechanism may look similar because both involve privileged control transfer, but source identity, timing, prioritization, and retry semantics differ. This article focuses on externally requested or interconnect-mediated interrupts and mentions exceptions only to clarify their separation. Interrupt delivery designs should be assessed for the event's urgency, quantity, targeting, masking, security domain, and whether a pending condition survives a temporary disable.

Edge-Triggered Interrupt Lines

An edge-triggered input requests service on a specified transition, for example low-to-high. The controller may latch a pending bit after observing the edge, but the source can subsequently return to its inactive voltage without continuously asserting the request. This lets a brief pulse cause an interrupt even if the processor is busy. Whether additional edges are counted, merged, or discarded while already pending is implementation-specific. Designers cannot assume that every electrical transition becomes a separate software callback.

A device must keep sufficient information in its own completion registers or queues to avoid losing business events when notifications merge. A race occurs if a driver clears an event and then an edge arrives while the relevant mask or state is changing; the exact avoidance technique depends on the device and controller. Edge behavior is particularly sensitive to pulse-width requirements, synchronizers, and the semantics of unmasking. Document the source's polarity and trigger type before connecting it to a controller: configuring an edge source as level-sensitive, or vice versa, can produce a stuck interrupt or missing notifications.

Level-Triggered Interrupt Lines

A level-triggered input remains asserted while an interrupt condition is present. The controller can keep or renew the pending indication until the device deasserts its request. Typical devices expose status bits that software clears only after handling the underlying event. This makes source clearing central to correctness: acknowledging the interrupt controller while the device still holds the line active can cause immediate redelivery and apparent interrupt storms.

Level triggering can be useful for shared signals because several devices can hold the same line active, although sharing is not required. Handler ordering differs across hardware: some designs mask the source, read and clear status, and then end service at the controller; others allow a different sequence defined by the platform. A read-modify-write to a status register must respect write-one-to-clear, read-to-clear, and other device-specific semantics. Software should not treat a write to a controller's end-of-interrupt register as a substitute for clearing the peripheral's state. Both operations may be necessary, but they act at different ownership levels.

Shared Interrupt Lines and Source Identification

A shared line means several devices can trigger one interrupt-controller input or share a host IRQ resource. When the handler runs, software cannot infer the precise source from the line number alone. It must test each participating device's status, or use a platform-specific demultiplexer, and service only a device that actually reports pending work. On a shared handler interface, the handler must be able to report that its device did not cause the interrupt rather than claiming all notifications.

Shared lines introduce contention and diagnostic ambiguity. An aggressive device can repeatedly reactivate the line and reduce service to quieter devices; a misconfigured device can keep the level asserted. They also increase the cost of source discovery, particularly if reads traverse slow PCI bridges or serialized control interconnects. Per-queue MSI-X vectors often mitigate these problems by routing events more precisely, but multiple logical causes can still share a message vector. A vector identifies a configured notification stream, not necessarily one semantic application event.

Pending, Enabled, Active, and Masked States

Interrupt controllers usually retain some combination of pending state, enable or mask state, priority, target configuration, and active or in-service state. A pending interrupt has been recognized as eligible for eventual handling. An enabled source is permitted to be delivered under current masking and priority conditions. An active interrupt is already being serviced in a controller model that distinguishes active from pending. These dimensions can coexist: for example, a second request may become pending while one instance remains active, subject to controller rules.

A global CPU interrupt mask is not the same as a device-side enable bit. A controller mask may stop delivery to a CPU while the peripheral keeps accumulating completion records; a device mask may stop its outgoing notification generation; and an MSI-X table mask has specified pending behavior different from merely stopping software's handler. Masking is therefore not always cancellation. When software unmasks a line or vector, it must expect accumulated status or a newly pending event and should have a clear plan for draining the device. Reliable designs distinguish the condition that triggers the request from the controller mechanism that prioritizes it.

Interrupt Priority and Nesting

Controllers commonly support priority classes, programmable thresholds, target routing, and preemption or nesting controls. A high-priority interrupt can be delivered while a lower-priority one is waiting, or even while one is in service, if the CPU and controller permit that behavior. A processor's local interrupt disable state, the controller's priority grouping, and the device's own masking may each limit nesting. A priority value is not necessarily comparable across different controller architectures.

Priority is an allocation policy, not a guarantee of bounded completion time. A highest-priority event can still wait for a long non-preemptible handler, interconnect latency, or a disabled interrupt window. Mismanaged priorities permit starvation of less urgent work; excessive nesting raises stack demand and makes worst-case execution time difficult to bound. Real-time analysis should budget the delay from event assertion through controller routing, interrupt acceptance, interrupt-disabled regions, and handler execution. When multiple handlers contend for locks or memory bandwidth, the effective priority seen by a device may differ from its nominal vector priority.

Acknowledgment, End-of-Interrupt, and Deactivation

The phrase interrupt acknowledgment has several meanings. Some controllers require software to read an interrupt-acknowledge register that returns the highest-priority pending source. Others deliver an interrupt identifier through CPU architectural state. An end-of-interrupt (EOI) operation often tells the controller that a handler has finished its active service interval. Certain designs also separate priority drop from interrupt deactivation. The details must come from the relevant controller's programming model.

Device-side acknowledgment is independent: a receive queue may require a status clear, completion-index update, or enable rearm before it stops requesting attention. A single EOI is not proof that the event has been serviced, nor is one status clear proof that the source cannot reassert immediately. Conversely, repeatedly writing an EOI without checking source status can hide a persistent device fault. A correct lifecycle states who owns each state transition: peripheral, bridge, controller, CPU, or driver. It then tests reentry, simultaneous events, masked events, and recovery during an in-flight handler.

Pin-Based Interrupts and Legacy PCI INTx

Classic PCI used interrupt pins, often labeled INTA# through INTD#, with platform routing and sharing that could combine multiple devices at an interrupt-controller input. PCI Express preserves a compatibility model for legacy INTx signaling, but this is not identical to assigning a dedicated parallel wire from each PCIe endpoint to a CPU. In PCIe, legacy INTx signaling is represented through protocol mechanisms such as assert and deassert messages and is routed by the platform's PCIe hierarchy. The important invariant is still a logical interrupt condition with compatibility-oriented sharing and service behavior.

A driver using a legacy line needs to test the device's status, clear the cause, and obey platform-specific ordering. It should not assume that an interrupt has occurred merely because a programmed transaction is late. Modern operating systems generally prefer MSI/MSI-X for capable devices because they can reduce shared-line ambiguity and offer better targeting. However, older devices, firmware settings, unsupported interrupt domains, and compatibility requirements can lead to INTx mode. Correct operation requires the actual configuration and platform contract, not an assumption based on the device's advertised maximum feature set.

Message-Signaled Interrupts as Transactions

A message-signaled interrupt (MSI) conveys notification by a special address-and-data write that the platform interprets as an interrupt request. For PCI/PCIe devices, operating-system and platform software configure the target address and data values through the device's MSI capability. When the device generates the message, its write traverses an interconnect toward the interrupt-delivery mechanism. The resulting interrupt may carry a vector identity and routing information without a dedicated legacy interrupt pin per event.

MSIs remain logically different from ordinary writes to data buffers. A write to an interrupt-controller doorbell region has notification semantics, whereas a write of a completed disk block to RAM stores payload data. Both may be physical memory-write transactions, but they terminate at different architectural targets. Software must not improvise MSI target addresses or assume that ordinary RAM writes can generate interrupts. The host's interrupt-remapping and controller capabilities determine which MSI writes are recognized, routed, or rejected. For compliant PCIe ordering, prior DMA writes and MSI signaling have relevant ordering guarantees; those guarantees do not replace correct CPU-side synchronization or ownership rules.

PCI MSI Versus PCI MSI-X

PCI MSI and MSI-X both use message-signaled notification. Conventional MSI supports a constrained, power-of-two configuration of vectors, with an architectural maximum of 32 in the Linux PCI driver documentation. MSI-X supplies a per-vector configuration table and supports up to 2,048 entries in the PCI specification model, subject to the device's advertised table size and system allocation. An MSI-X table entry records a message address, message data, and vector-control information; its Pending Bit Array (PBA) records masked pending states as specified by the capability. The table and PBA are typically mapped through a device BAR, not copied as application data into arbitrary host RAM.

MSI-X facilitates separate completion streams for receive, transmit, storage queue pairs, and administrative events; however, a device may expose fewer vectors than desired, and an operating system may allocate fewer than the hardware maximum. The driver must handle successful partial allocations where permitted and must not equate a table index, a Linux IRQ number, and the CPU's local vector number. Those belong to different namespaces. Likewise, MSI-X's ability to target different CPUs does not imply guaranteed load balancing: actual placement depends on the interrupt domain, affinity policy, and online processing elements. Linux's pci_alloc_irq_vectors() interface is the preferred general allocation route described in current kernel documentation.

MSI-X Vector Table, Masks, and Pending Bit Array

The MSI-X table is host-programmable device configuration holding one message address and data payload per vector, together with a mask bit. A function-wide mask can additionally suppress transmission of multiple MSI-X notifications. The Pending Bit Array represents interrupts that become pending under the relevant masking semantics. On unmasking, a device must follow PCI-defined behavior for a pending event. Software should not assume a masked notification vanishes, nor that the hardware records an unbounded counter of every event behind one pending bit.

Per-vector control enables queue shutdown, affinity changes, and controlled reconfiguration, but programming the table is not safe at an arbitrary moment when a device can generate an interrupt. Drivers must obey the PCI configuration and ordering requirements around masking and updates; pending work should be serviced using the device's actual queue state. A PBA bit indicates an interrupt condition for the vector rather than the count or contents of associated DMA completions. This distinction becomes critical when masking during polling, suspending the device, or handing a queue to a different CPU. A silent PBA does not prove a queue is empty if generation is disabled or a status path is broken.

Interrupt Routing, Vector Identity, and Translation Domains

Interrupt routing maps a device-origin event to a CPU-visible interrupt identifier. Routing can incorporate a PCI root complex, interrupt controller, message translator, host bridge, processor local interrupt unit, hypervisor, or I/O interrupt-remapping block. These elements may rewrite or validate addresses and identifiers. A practical diagram should label both the device-relative vector and the host-selected destination, because those values frequently differ and can change after driver reinitialization or CPU hotplug.

The term interrupt domain describes an operating system or platform abstraction used to allocate and map interrupt identities. A domain may be hierarchical: a PCI MSI domain, an IOMMU remapping domain, and a CPU interrupt-controller domain can each participate. Neither the PCIe address of an MSI message nor the OS-visible IRQ number should be assumed to identify a physical CPU directly. Secure systems program routing through trusted platform facilities and restrict untrusted devices from writing arbitrary interrupt-controller locations. Exact details differ for x86 interrupt remapping, Arm GIC ITS translations, and RISC-V MSI controllers.

x86 Local APIC and I/O APIC Context

In common x86 systems, local APIC facilities participate in delivering interrupts to processors, while I/O APIC facilities historically distribute external pin-based interrupts. MSI and MSI-X messages can target the interrupt delivery system using configured address/data encodings, subject to platform translation and remapping. An operating system allocates vector numbers according to processor and interrupt-domain rules. An APIC vector is not a PCI MSI-X table index, and neither is automatically the same as a user-visible IRQ counter label.

Real x86 platforms can include interrupt-remapping hardware, virtual APIC facilities, and firmware tables that alter the path. Some vector numbers are reserved for exceptions or platform functions; a driver cannot simply choose any 8-bit number because the hardware word is wide enough. The relationship between I/O APIC pins, local CPU vectors, remapped MSI writes, and CPU core affinity should be documented per host. For high-level Bus Systems study, the important design principle is that message destination and event identity are configured through a trusted routing plane, not dictated unilaterally by a peripheral.

Arm Generic Interrupt Controller: SPIs, PPIs, SGIs, and LPIs

The Arm Generic Interrupt Controller (GIC) architecture distinguishes several interrupt classes. Shared Peripheral Interrupts (SPIs) normally represent sources that can be targeted to processing elements; Private Peripheral Interrupts (PPIs) are associated with particular processing elements; Software-Generated Interrupts (SGIs) support software-directed signaling. Locality-specific Peripheral Interrupts (LPIs) are associated with message-based facilities introduced in GICv3, where implemented. The capabilities and routing of each class depend on the GIC architecture version and implementation.

An Arm system may receive a peripheral line at a GIC distributor or consume an MSI through a message translation facility. The CPU interface and redistributors control presentation and local handling. GIC priority, pending, active, and enable rules are architectural subjects with more detail than the generic PCIe model. LPIs are not simply another name for SPI lines, and an LPI's table-based enable/pending organization differs from the older interrupt classes. A system diagram should therefore show where the message is translated, how the destination processing element is chosen, and which state is owned by the controller versus the peripheral.

Arm GIC Interrupt Translation Service and LPI Delivery

Where implemented, the Interrupt Translation Service (ITS) accepts an event associated with a device and translates it into an LPI targeted to a processing element through GIC-maintained configuration. Its translation tables associate device and event identities with a selected interrupt and collection/target configuration. This allows many message-producing devices to share a structured interrupt routing infrastructure instead of requiring one physical line per event. The Arm architecture permits optional features and different generations, so a host description must not imply that every GICv3 system necessarily has an ITS.

In a typical architectural trace, software allocates the LPI and programs the appropriate ITS and redistributor structures; a peripheral emits a message; the ITS resolves the configured translation; and the target redistributor and CPU interface make the interrupt eligible for software service. Routing is not equivalent to copying DMA payloads, and delivery success does not by itself prove that the software has processed the device queue. Arm's official GIC documentation should be used to verify exact identifiers, table formats, invalidation requirements, and virtualization behavior for a specific implementation.

RISC-V IMSIC and Advanced Interrupt Architecture

The RISC-V Advanced Interrupt Architecture (AIA) defines message-interrupt mechanisms including the Incoming MSI Controller (IMSIC). IMSIC interrupt files hold pending and enabled interrupt identities for a hart and, where supported, additional privilege or virtual-machine contexts. Software configures which interrupt identity a device can signal and which interrupt file is targeted; an MSI write to the designated memory-mapped address carries the notification identity. This is a different organization from a classic single shared external interrupt line.

The AIA also describes an Advanced Platform-Level Interrupt Controller (APLIC), which can handle wired sources and, in appropriate modes, deliver MSIs toward IMSICs. Controllers and capabilities are optional or implementation-dependent; a basic RISC-V system should not be assumed to include IMSIC hardware. In virtualized systems, guest interrupt files can support directing events to guest contexts under controlled configuration. The architectural lesson is consistent with PCIe and GIC systems: a notification must be authorized, routed to a legal destination, and translated into processor-visible interrupt state by the platform, while the actual data remains in device registers or memory buffers.

Interrupts on SoC Fabrics and Peripheral Bridges

A system-on-chip can contain dozens or hundreds of interrupt-generating blocks: UART controllers, SPI engines, timers, watchdogs, DMA engines, storage controllers, power monitors, and security units. A peripheral bus such as APB may expose each block's interrupt-status and enable registers, while separate signal lines or an MSI-capable subsystem carry notifications to the main controller. The presence of an AXI or APB data interface does not imply that an interrupt signal is carried on the same functional channel as register reads and writes.

SoC designs may insert an interrupt aggregator that combines numerous local sources into a smaller set of outputs. That saves wires but increases the need for reliable source demultiplexing. Clock and power domains introduce more complexity: a peripheral may generate an event while its main data clock is gated, requiring always-on latches or wakeup logic. The design must specify polarity, synchronization, reset state, pending retention, isolation, and when status becomes readable after a domain wakes. Interface specifications should record those dependencies rather than presenting every peripheral interrupt as an instantaneous wire directly into the CPU.

DMA Completion and Interrupt Ordering

A DMA-driven device often writes data into host memory, updates a completion descriptor, and signals an interrupt. Software must distinguish the ordered publication of a completion from the later consumption of that completion. PCIe MSI transaction ordering generally ensures that a properly ordered interrupt-generating message does not overtake prior device DMA writes on the relevant path; Linux documentation emphasizes this advantage relative to traditional interrupt lines. However, this hardware property is not a blanket guarantee for all bridges, relaxed-ordering configurations, noncoherent fabrics, or driver mistakes.

The correct service contract also includes the queue's ownership fields, memory barriers where required, coherency operations for noncoherent platforms, and a rule preventing descriptor reuse while hardware might still access it. An interrupt can be delayed or merged with later completions. A ring may contain several new entries when only one MSI arrives. For a line-based interrupt, drivers may need a device register read to ensure prior posted writes have reached the required visibility point before consuming status or data. Completion and synchronization must always follow the actual device and platform programming specifications.

Interrupts, Doorbells, and Completion Rings

A doorbell usually points in the opposite direction from an interrupt. The CPU writes a memory-mapped doorbell register to tell a device that new commands are available; the device later raises an interrupt to tell the CPU that one or more commands have completed. Both can use memory-write transactions, but doorbell writes and MSI notifications have distinct initiators, destinations, meanings, and visibility requirements.

The queue itself is the durable record of work. A typical design uses producer and consumer indices and phase or ownership bits to avoid mistaking wrapped entries for fresh work. The handler should read the queue using the required synchronization, process all available completed entries within its budget, update the consumer index, and rearm notifications if its strategy requires it. Some devices separate a completion queue from an event queue; others use a shared status register. An interrupt handler must not assume a one-to-one relationship between hardware messages and software work items because coalescing, rearming, and races can all change that mapping.

Multiple Vectors and Per-Queue Notification

A multi-queue storage or network device can assign one MSI-X vector per queue, or one vector per group of queues, so notifications can be directed near the CPUs processing the corresponding data. This improves concurrency by reducing shared-status polling and lock contention. It also permits finer-grained masking and moderation. The vector count is bounded by device capability, host vector resources, driver policy, and processor topology. Allocating one vector per queue is an optional strategy, not an architectural necessity.

More vectors create their own costs: interrupt-domain state, operating-system bookkeeping, affinity decisions, and reconfiguration during CPU hotplug or suspend. Too many independently firing queues may overload a core or cause excessive cache movement. Drivers should describe what happens when fewer vectors than queues are available, often grouping queue completion sources and using a per-vector service loop. Dedicated administrative and error vectors are common patterns but not required for every peripheral. A vector allocation scheme is successful when it aligns notifications with useful work distribution rather than merely maximizing the number of allocated numbers.

CPU Affinity, NUMA Placement, and Target Selection

Interrupt affinity chooses which CPUs are eligible to service a given vector. It can reduce cross-core cache transfers by directing a queue's completion interrupts to a CPU near its application or networking work. In non-uniform memory access (NUMA) systems, the CPU that handles an interrupt, the memory node containing DMA buffers, and the device's PCIe root-complex location can all affect observed latency and bandwidth. Affinity should be considered alongside DMA placement and thread scheduling, not in isolation.

A target may change when CPUs are offlined or when the OS rebalances interrupts. Linux provides generic IRQ affinity facilities, and managed affinity interrupts have special handling during CPU hotplug. A managed vector is not necessarily user-modifiable through the usual procfs mask files. Affinity also cannot fix an underlying bottleneck in the storage device, interconnect, or memory controller. A strong evaluation measures packets or completions per CPU, device queue occupancy, processor migration, remote-memory accesses, and latency percentiles before and after placement changes.

Interrupt Coalescing and Moderation

Interrupt coalescing combines several device events into fewer notifications. A completion queue might interrupt after a configurable event count or elapsed time, whichever occurs first. Moderation more broadly limits notification frequency or delays events under specified policies. These features lower per-event interrupt overhead when traffic is high, but they can add waiting time for a small, time-sensitive transaction. Device-specific timer units, reload semantics, and interactions with adaptive moderation must be consulted rather than guessed.

The latency trade-off is often counterintuitive. For a light workload, a timer-based moderation delay can dominate service time even though the device completed immediately. For a heavy workload, batching 32 completions into one interrupt may improve total CPU efficiency and relieve lock contention enough to reduce queueing. Drivers may change moderation adaptively based on traffic characteristics; the control loop must avoid oscillation and should preserve performance guarantees for latency-sensitive operations. The best setting depends on the arrival process, service budget, wakeup cost, and acceptable tail latency—not a universal target of interrupts per second.

Hybrid Interrupt-Driven and Polling Service

Hybrid service begins with a notification, then polls a work queue while it is productive to do so. Many network-stack designs use an interrupt to schedule packet processing and suppress additional notifications during the poll cycle. The poller drains a bounded budget, and the driver carefully rearms interrupts when it determines that the queue is idle or it has yielded. The essential race is between checking for empty work and enabling notifications: new work must not be stranded without either another poll or another interrupt.

A correct rearm sequence depends on the hardware contract and usually requires a post-rearm check or a status mechanism designed to close the gap. Polling cannot be treated as automatically safer than interrupt-driven service: a busy poller can starve another task, spin on stale shared-memory state, or consume excessive power. Conversely, interrupt-only schemes can collapse under high event frequency because the CPU spends much of its time entering and exiting handlers. The design objective is to minimize total service cost while retaining correct handling of low-rate arrivals and bursty traffic.

Hard IRQ Context, Deferred Work, and Threaded Handlers

Operating systems typically separate work that must run promptly in interrupt context from longer processing deferred to a softer or schedulable context. A minimal top-half handler can acknowledge or mask the source, record essential state, and schedule a bottom-half mechanism or a threaded handler. The exact rules depend on the OS: some operations are forbidden in hard-interrupt context because they can block, reschedule, or rely on sleeping locks. Heavy packet processing, filesystem operations, and long waits generally do not belong in the minimal urgent path.

On Linux, the generic IRQ subsystem supports threaded handlers and affinity mechanisms. The handler must identify whether a shared line is actually its device's event, and the driver must correctly synchronize teardown against both hard and threaded components. Separating contexts does not reduce the importance of memory visibility: device status, completion queues, and driver-owned structures still require the platform's locking and DMA synchronization rules. For the Bus Systems scope, software contexts are included because they determine how rapidly hardware notifications can be consumed and which end-to-end latency is actually observable.

Notification Latency, Service Latency, and Tail Delay

Notification latency can be measured from event assertion or MSI emission until the target CPU observes the interrupt. Service-entry latency extends through interrupt-controller and processor dispatch to the start of the handler. Completion-consumption latency includes memory visibility, queue scanning, deferred work, and driver completion processing. An application may experience still more delay before its waiting thread is awakened or scheduled. One single "interrupt latency" number without a precise start and endpoint is not comparable across hardware or operating systems.

A useful model writes application notification delay as the sum of device moderation, signaling and routing, controller and CPU acceptance, handler dispatch, software processing, and task scheduling, while recognizing that some stages overlap. Under contention, tail latency can grow because of interrupt-disabled regions, memory stalls, priority interactions, or CPU scheduling. Measure p50, p95, p99, and maximum observed delays against the relevant arrival distribution rather than reporting only a mean. High interrupt throughput does not guarantee low delay for an isolated event, and low average latency does not rule out rare missed deadlines.

Throughput Limits and Interrupt-Rate Budgets

If a device produces R completion events per second and each interrupt represents B events on average, the expected interrupt frequency in a simple steady-state model is roughly R/B, before administrative or error interrupts. The CPU cost associated with notification processing is approximately interrupt rate multiplied by the average CPU time spent per interrupt, although cache behavior, context scheduling, and variable handler length can make the linear estimate optimistic. A device with high data bandwidth may generate few interrupts if it batches large transfers; a low-bandwidth peripheral can generate many interrupts if it signals every byte.

An engineering budget should include minimum and maximum event rates, batching policies, handler CPU cycles, queue depth, and overflow behavior. It must also verify fairness across devices sharing a controller or CPU. Interrupt-rate counters cannot by themselves prove useful work: an interrupt storm may produce very large counts with no completed transfers. Conversely, a quiet interrupt counter is not proof that a device is idle if polling is enabled. Interpret IRQ counts alongside completion-ring movement, delivered bytes, error registers, and device state transitions.

Interrupt Storms, Repeated Assertion, and Rate Limiting

An interrupt storm is an excessive stream of notifications that consumes service capacity. A typical cause is a level-triggered source that remains asserted because software fails to clear the correct status bit or because the hardware condition persists. Other causes include a malfunctioning endpoint, incorrectly programmed moderation, repeated error interrupts, or a driver that rearms too aggressively without draining a queue. Simply increasing the CPU clock may hide symptoms while leaving the underlying correctness problem unchanged.

Diagnosis begins by locating the earliest layer at which activity becomes excessive: source status, MSI generation, controller pending state, IRQ counters, handler invocation, or retrigger after EOI. Rate limiting can protect overall system availability, but it can also suppress valid device notifications and prolong recovery if the queue has no independent polling fallback. An appropriate storm response may mask one vector, collect status safely, service or reset the device, and restore generation only after the cause is understood. Global interrupt disabling is usually too blunt to be an operational remedy.

Lost, Delayed, and Coalesced Notifications

A lost interrupt is a situation in which work requires service but no notification reaches the software path that is expected to discover it. A delayed interrupt eventually arrives but after an unacceptable interval. A coalesced notification intentionally represents multiple underlying events with one delivery. These outcomes can appear similar when the application observes a stalled queue, so troubleshooting must inspect hardware generation status, masking, pending bits, interrupt routing, and the queue's durable completion records.

Race conditions near an empty-queue check are common. For example, software drains the ring, sees it empty, and is about to re-enable interrupts. If new work arrives between the last check and rearm, the hardware must either retain pending status, generate a new interrupt on rearm, or be caught by a subsequent software check. Designs without one of those properties can strand work indefinitely. Conversely, counters can underreport underlying events when edges or pending bits merge. Reliable interconnect contracts express delivery as a wakeup hint paired with persistent work state rather than an exact event counter.

Spurious Interrupts and Defensive Service

A spurious interrupt is a delivered or observed notification for which the software finds no relevant pending device work, or an interrupt-controller-specific spurious identifier. It can arise during shared-line races, masking transitions, status-clearing windows, device resets, or platform quirks. One isolated event is not necessarily proof of a hardware fault. A robust handler checks its source, declines ownership when appropriate, and does not clear unrelated devices' status simply to quiet an IRQ count.

Repeated spurious notifications require investigation. Observe whether the controller reports a real vector, whether the device has a pending condition, and whether the hardware is generating MSI writes or continually asserting a line. On a shared IRQ, one device's status may have disappeared by the time another handler probes it. On an MSI-X queue, the driver may have drained work through a concurrent poller before the notification was serviced. A service path should tolerate such races without double-completing commands or treating an empty completion queue as a fatal protocol error.

Posted Writes, Memory Barriers, and Completion Visibility

Memory-mapped control writes may be posted: the CPU instruction retires before the write has reached the device. This is important when enabling interrupts, clearing status, configuring a queue, or ringing a doorbell. Platform-specific reads, barriers, or driver API primitives can be necessary to ensure ordering or completion before subsequent operations. It is incorrect to assume that a compiler barrier, CPU fence, posted MMIO read, and DMA synchronization primitive all provide identical guarantees on every bus.

PCIe MSI ordering provides a particularly useful case. Where the PCI transaction ordering rules apply, a device's MSI write does not overtake its prior DMA data writes; Linux documentation explains this advantage over legacy pin-based interrupts. That statement must not be extended to arbitrary relaxed ordering or different coherency domains. The handler also needs a safe strategy for publishing its own completion-index updates and rearming the device. Interrupt arrival is therefore one point in an ordered producer-consumer protocol, not a stand-alone proof that all relevant CPU cache lines and device registers have magically reached final state.

Virtual Machines and Virtual Interrupt Injection

Virtualization introduces another mapping layer between device events and a guest-visible interrupt. A hypervisor can emulate a legacy controller, provide virtual MSI domains, or use hardware-assisted interrupt remapping and posted delivery for assigned devices. A guest may receive a virtual vector unrelated to the physical host interrupt identifier. The hypervisor must manage delivery, masking, priority, and migration while ensuring that one guest cannot redirect another guest's notifications.

Device assignment makes interrupt routing especially sensitive. A physical MSI generated by an assigned endpoint may require IOMMU interrupt remapping or another trusted translation so the destination is limited to an authorized guest or vCPU. A virtual machine's migration or CPU hotplug can change its target without the physical device changing its event semantics. Lost or duplicated virtual interrupts can stall virtual storage and networking even when the physical completion queue contains valid entries. Architecture studies must separately account for device-to-host delivery, host-to-guest injection, guest handler execution, and the durable work state.

Interrupt Remapping and Device-Origin Trust

An MSI source can be untrusted due to faulty firmware, hostile device logic, or incorrect device assignment. If a platform accepted arbitrary message addresses and interrupt IDs from any peripheral, the peripheral might be able to direct unwanted notifications to privileged or unrelated execution contexts. Interrupt remapping and domain-based authorization restrict which device-origin messages may map to which CPU interrupt destinations. The exact enforcement point depends on the host architecture and its interrupt controller or IOMMU facilities.

Interrupt routing security complements, but does not replace, DMA isolation. Preventing an MSI from reaching an unauthorized vector does not prevent the same device from attempting unauthorized data-memory accesses. Likewise, an IOMMU data translation policy does not automatically validate every interrupt message in every architecture. Secure system design considers device identity, source requester IDs, allowed interrupt domains, virtual-machine ownership, rate abuse, reset behavior, and the lifecycle of programmed mappings. This article remains defensive and architectural: protection should be implemented through supported kernel and platform APIs, not by manually writing unverified interrupt-controller addresses.

Interrupts as a Denial-of-Service Surface

Even correctly routed notifications can impose substantial CPU work if a device or guest generates them at an excessive rate. This is a resource-exhaustion problem rather than a direct violation of interrupt-target isolation. Attackers or broken endpoints may create repeated error notifications, fill work queues, or force constant entry into expensive handlers. Multi-tenant hosts need policies that limit the impact of a noisy device on unrelated workloads while preserving essential security and fault-reporting events.

Mitigations include per-vector moderation, fault containment, queue budgets, suitable interrupt affinity, rate-aware hypervisor policies, and controlled device reset. Suppressing an error interrupt without logging or handling the underlying fault may reduce the observed rate while allowing data corruption or loss of service. Systems should record the source and severity of each interrupt class, maintain telemetry across suppression episodes, and define an escalation path when a device cannot be safely quiesced. The design goal is controlled service, not merely a low IRQ counter.

Interrupt-Driven Power Management and Wakeup Events

Interrupts can wake a CPU or SoC from idle, but wakeup requires a path that remains capable of detecting and retaining events while other clocks or power domains are disabled. A controller may need always-on logic, wake-enable bits, special routing, or firmware cooperation. A conventional peripheral interrupt that is valid while the SoC is fully powered is not necessarily a permitted wake signal during deep sleep. Power state transitions must describe which queues or events remain armed and whether delivery is retained across suspend.

Dynamic power management introduces races between stopping new work, masking interrupts, acknowledging pending events, and disabling device power. A reliable suspend sequence quiesces or drains work and preserves only the wake sources the platform is designed to support. On resume, firmware or the OS may restore MSI/MSI-X tables, controller routing, queue ownership, and device enable registers. It must then check for work that became pending during the transition. Power savings cannot be evaluated in isolation from wake latency, missed-event risk, and the time required to rebuild interrupted transactions after a low-power cycle.

Device Reset, Removal, and In-Flight Interrupts

Resetting an endpoint does not guarantee that the CPU has already finished every handler or deferred job associated with it. A removal or reset protocol must prevent new notifications, stop or contain DMA, wait for in-flight handlers where required, and invalidate software references to deallocated queues. Some operating-system APIs synchronize an IRQ handler separately from threaded work, and some devices can still have posted transactions in flight after a control register changes. The exact shutdown sequence depends on the device and kernel lifecycle model.

A common failure is freeing a completion ring immediately after masking a vector while a handler on another CPU still holds a pointer to that ring. Another is restoring interrupts before descriptors and target routing have been reinitialized. Robust teardown uses a well-defined state machine: reject new submissions, quiesce the device, disable event generation, synchronize software users, account for pending completions, and only then release data structures and interrupt resources. On reinitialization, the reverse ordering must ensure the handler and queues exist before the device can generate events.

Real-Time Service and Worst-Case Interrupt Delay

A real-time design needs an upper bound on the time between a hardware event and the relevant deadline. Bounding only the electrical or MSI transmission time is insufficient. The budget must include maximum interrupt-disabled intervals, higher-priority handlers, controller routing, processor interrupt entry, deferred service execution, memory contention, and operating-system scheduling when completion requires a task context. Interrupt moderation timers must be included when enabled.

High priority reduces only some contributors. If a handler waits on a non-preemptible lock, or a service thread runs at an unsuitable scheduling priority, a numerically high IRQ priority cannot guarantee the deadline. Conversely, using extremely high priorities for every device undermines predictability. Real-time systems sometimes dedicate a core and queue to a particular event class, reserve resources, or use bounded polling at known schedule points. Such strategies should be justified through worst-case execution analysis and device-specific timing guarantees, not solely average benchmark results.

System-Level Reliability, Faults, and Error Interrupts

Devices also interrupt for faults: parity or CRC errors, link failures, queue overruns, watchdog expirations, thermal warnings, controller timeouts, and internal fatal conditions. These interrupts may use the same notification mechanism as normal completions, but their service contract is different. A fault handler often records status, prevents further traffic, preserves diagnostic evidence, and initiates retry or recovery rather than completing ordinary work. Sending error notifications on a dedicated vector can help isolate diagnosis and prevent a flood of recoverable errors from masking command completions.

Interrupt reliability is not just successful electrical delivery. The system must tolerate a notification that arrives during reset, a controller that loses state during power collapse, and a device that reports status but cannot safely resume. Health monitoring may need independent polling to discover silent device failures even if interrupts are configured. When failures are persistent, the software should avoid infinite retry-and-interrupt loops. Reliable architecture separates fault detection, fault reporting, fail-safe containment, and confirmed recovery, then tests the interaction among these stages under load.

Hardware Verification and Protocol Assertions

Verification should cover both the source and the path: event generation, pending-state retention, masking, controller routing, interrupt acceptance, status clear, and rearm. For edge-triggered designs, tests include pulses near clock boundaries, repeated edges while pending, and masking transitions. For level-triggered designs, tests include status remaining asserted across EOI and deasserting only when the documented condition is cleared. MSI paths require tests for address/data programming, vector masks, pending events, ordering with DMA writes, resets, and changes in target CPU.

Useful assertions state properties such as: an enabled persistent event eventually becomes visible to the configured handler under fair service assumptions; a masked vector does not invoke a handler yet retains required pending state; and no completion is consumed before its ownership marker is visible. Some liveness properties require explicit assumptions about controller progress and software scheduling. Simulation should inject simultaneous events, malformed configurations, queue overflow, and hotplug. Hardware traces and software tests complement one another because a passing bus transaction trace may still conceal a handler race in completion-ring processing.

Diagnosing Interrupt Delivery Failures

An incident should be traced from the earliest unproven state. Verify that the device actually completed the operation, that a persistent status bit or completion record reflects the event, that its interrupt generation is enabled, that the intended MSI/MSI-X table or line mapping is correct, and that the controller records or forwards the request. Then verify CPU acceptance, driver handler registration, correct status identification, and queue consumption. Skipping directly to OS IRQ counters can miss a device that never emitted a signal or a vector masked within the endpoint.

Collect device register snapshots and errors before a reset erases them. Compare per-vector IRQ counters against queue producer indices, completion counts, DMA status, CPU affinity, and performance monitoring. A missing increment in a user-facing IRQ counter is not conclusive without knowing whether the driver polls instead of interrupting. A rising counter with no completed work suggests a different class of fault. Where a device uses MSI-X, inspect how many vectors were allocated versus requested and whether the test workload is mapped to the expected queue and CPU. Avoid relying on a single signal as a complete proof of delivery.

Interrupt Delivery Engineering Checklist

Before deploying an interrupt scheme, document the source event and where its durable status lives. Determine whether its signaling is edge-, level-, or message-based and which hardware component owns pending state. Confirm that the controller's identity mapping matches the operating-system IRQ and that routing and affinity are deliberate. Record what must be visible in memory before software can consume a completion, and which device operation clears or rearms the cause. Finally, define what happens under masked, saturated, reset, power-management, and fault conditions.

For performance, specify the expected event rate, batching policy, latency budget, handler cost, queue placement, and number of available vectors. For correctness, test simultaneous events, repeated interrupts, hidden status under masks, late DMA writes, rearm races, and slow handlers. For security, make interrupt-remapping and DMA isolation part of device ownership, particularly under virtualization or hotplug. A useful acceptance test is not simply "the handler was called" but "every completed work item is eventually processed exactly once under the system's intended recovery and retry semantics." The following constructed examples make these decisions measurable.

Worked Example 1 — Level-Triggered Interrupt Reassertion

Consider a fictional peripheral with an active-high interrupt line and a write-one-to-clear status bit DONE. The device finishes a transfer and sets DONE=1, causing the line to rise. The interrupt controller reports the input and the CPU enters its handler. Suppose software sends EOI immediately but neglects to clear the peripheral's DONE bit. The controller now considers the previous service finished, yet the line is still high; the controller can deliver another interrupt. The result is a storm even though only one transfer completed.

Step Peripheral status Input level Controller or software action
1 DONE=0 Low Device is idle
2 DONE=1 High Completion raises the request
3 DONE=1 High Handler enters and reads status
4 DONE=1 High Premature EOI permits renewed delivery
5 DONE=0 Low Correct status clear deasserts source
6 DONE=0 Low Controller EOI or deactivation completes service

The ordering of device clear and controller EOI is platform-specific; this sequence merely demonstrates the relationship between the two ownership domains. A correct implementation must also handle a second completion arriving while status is being cleared. That may require reading a durable completion queue, masking and rechecking, or another device-specified technique. The numerical count of EOIs never substitutes for a count of consumed work items.

Worked Example 2 — Edge Notification Versus Persistent Queue State

A fictional device finishes four commands in close succession. It writes completion entries numbered 101 through 104 into a ring. The interrupt output is edge-triggered; during the burst, the controller observes one edge and records one pending interrupt. The handler later drains all four entries. This is correct if the device's queue preserves the work and the notification contract allows merging. It would be incorrect to increment a completion counter once merely because the CPU received one interrupt.

Observable Count What the count means
Completed commands 4 Four operations finished
New ring entries 4 Four durable completion records
Interrupt edges recognized 1 One notification opportunity
Handler invocations 1 One software service period
Work items consumed 4 All completed commands reclaimed

Now consider a second edge arriving while delivery is masked. Whether it remains pending depends on the interrupt controller. A design that relies on four separate callback invocations can fail even when no data was lost. Treat the interrupt as a request to inspect a work source, and test that all four entries are consumed before the driver declares the queue empty.

Worked Example 3 — DMA Writeback Followed by PCIe MSI

A PCIe storage endpoint writes a 4 KiB data block to host memory, updates a completion descriptor, and emits an MSI write. Assume that the device's transactions obey the applicable PCI ordering rules, that the host mapping and caches follow their documented coherence model, and that no relaxed-ordering exception changes the relevant guarantee. The MSI will not pass the earlier qualifying DMA writes, so by the time the CPU handles the interrupt, the device's prior writes have achieved the ordering required by that interconnect contract. The handler must still interpret descriptor ownership correctly.

  1. Device fetches a queued storage command.
  2. Device performs a 4,096-byte DMA write to the mapped destination.
  3. Device writes a completion entry that publishes the operation's status.
  4. Device sends the configured MSI message.
  5. CPU receives the routed interrupt, accesses the completion queue, and consumes the entry using the platform's required memory-ordering and coherency primitives.

An important negative case is a device that sends an MSI before publishing its completion entry. The interconnect cannot repair an endpoint's incorrect logical sequencing. Likewise, a CPU cannot infer that all future DMA activity is stopped simply because a particular MSI was received. Ordering applies to specified prior transactions; liveness, exact-once completion, buffer lifetime, and reset quiescence remain separate design obligations.

Worked Example 4 — MSI-X Masking and Deferred Delivery

Suppose a network endpoint has MSI-X vector 5 associated with receive queue 2. Software masks the vector while it processes a large burst. The device places 12 new receive completions in the queue and records a pending interrupt state according to its MSI-X capability rules. The driver then drains the queue and prepares to unmask the vector. The PBA may indicate that vector 5 was requested while masked; it does not encode 12 separate queue entries. When software unmasks, the device and platform perform the prescribed pending-delivery behavior.

State Queue pending entries Vector mask Notification interpretation
Initial 0 Unmasked No pending work
Burst arrives 12 Masked Device retains queue data; interrupt state may be pending
Poller drains 10 2 Masked Two work items still exist
Poller drains remaining 2 0 Masked Queue becomes empty after proper publication
Software rearms 0 Unmasked Any pending notification must be tolerated, even if work has already been consumed

The correct handler must safely treat a late notification for an already-drained queue as benign, while continuing to detect fresh work arriving at the rearm boundary. No one should assume that a PBA bit is a monotonically increasing event counter.

Worked Example 5 — Interrupt-Rate and CPU-Service Budget

A fictional device completes 1,200,000 small requests each second. Without batching, one completion generates one interrupt. With an average of 24 completions per interrupt, the expected frequency becomes 1,200,000 ÷ 24 = 50,000 interrupts/s. Suppose the total CPU time directly attributable to each interrupt service is 4 microseconds under this workload. The modeled CPU-time demand is 50,000 × 4 µs = 200,000 µs/s = 0.2 CPU-second per wall-clock second, approximately 20% of one logical CPU's time. If batching were absent at the same per-interrupt cost, the estimate would be 1,200,000 × 4 µs = 4.8 CPU-seconds per second, requiring far more than one CPU's available capacity.

Policy Completions per interrupt IRQ/s Estimated CPU seconds/s
Every completion 1 1,200,000 4.80
Batch of 8 8 150,000 0.60
Batch of 24 24 50,000 0.20
Batch of 48 48 25,000 0.10

This simple model ignores variability in handler cost, queue-drain work, scheduling, lock contention, and changes in the arrival rate. Batching still requires the CPU to process 1.2 million completion entries. It reduces notification overhead, not the underlying device workload. An actual benchmark should report p99 event latency and total useful throughput alongside IRQ counts.

Worked Example 6 — Moderation Timer and Isolated-Event Latency

Assume a device is configured to delay signaling for up to 50 µs after the first completion in a batch, unless a count threshold is reached. A single transaction finishes when the device has no other work. With no additional arrivals, the interrupt might be delayed close to 50 µs under this hypothetical timer policy. If route and processor entry require 5 µs, and handler dispatch requires another 3 µs, the modeled notification-to-handler delay becomes 50 + 5 + 3 = 58 µs. Without moderation it would be about 5 + 3 = 8 µs, assuming all other conditions stay fixed.

Under burst load, count-based early notification can reduce the average wait while still coalescing many completions. Therefore the policy can lower CPU utilization but raise idle-to-first-response latency. For a storage queue with latency-sensitive synchronous requests, a 50 µs artificial wait could be unacceptable; for a bulk network transfer, it may be a favorable trade. Report timer semantics explicitly, since some devices measure intervals from the first event, others since the last notification, and adaptive devices may override the setting.

Worked Example 7 — Per-Queue MSI-X Affinity on Four CPUs

Consider a server with eight receive queues, eight available MSI-X vectors, and four CPUs used for network processing. A simple policy allocates one vector per queue and assigns two queue vectors to each CPU. This can reduce the number of CPUs competing for the same queue lock, and it makes the IRQ counts easier to attribute. But it does not imply that each CPU receives equal traffic: one queue could get ten times as many packets as another. The system should balance actual workload, queue hashes, application placement, and memory locality.

CPU Vectors Receive queues Monitoring objective
CPU 0 0, 1 RX 0, RX 1 Compare packet rate and IRQ cost
CPU 1 2, 3 RX 2, RX 3 Check local cache and queue backlog
CPU 2 4, 5 RX 4, RX 5 Detect asymmetric service times
CPU 3 6, 7 RX 6, RX 7 Monitor CPU migration and overload

If CPU 2 becomes unavailable, the OS may migrate or disable managed vectors depending on the affinity policy. A driver should not assume that the original four-way mapping persists forever. In a NUMA system, moving a queue's IRQ without moving the application thread or data buffers can increase remote accesses, even if the distribution of IRQ counts looks more balanced.

Worked Example 8 — Requested Versus Allocated MSI-X Vectors

A storage driver requests nine vectors: eight for I/O completion queues and one for administrative events. The device advertises at least nine vectors, but the host grants only three because of resource or policy limits. If the driver allows a minimum allocation of three, it can place the administrative stream on one vector and map eight I/O queues across two vectors, for instance queues 0–3 and queues 4–7. Each I/O handler must then check all queues assigned to its vector.

The crucial correctness property is complete work discovery, not one vector per queue. A driver that hard-codes queue_number == IRQ_number will lose work or service the wrong queue after allocation changes. Likewise, an operating-system IRQ number obtained from pci_irq_vector() is not the table-entry index itself. Queue-to-vector mapping belongs in maintained driver state and must survive reset and CPU reconfiguration. The three-vector organization is a constructed fallback, not a prescription for real storage hardware.

Worked Example 9 — The Empty-Ring Rearm Race

An interrupt-driven consumer drains a completion ring, then checks it empty and unmasks its vector. A device completion can arrive between the empty check and the unmask operation. In a poorly designed interrupt scheme, the device considers an event already notified while software assumes no event exists, leaving the completion stranded. A robust scheme either retains pending notification while masked, supplies a reliable new message on unmask, or requires software to recheck after rearming. Which rule applies is device- and protocol-specific.

Moment CPU action Device action Safe invariant
t0 Drain ring No new completion Ring empty is provisional
t1 Read producer index Produces one entry immediately afterward Durable queue now contains work
t2 Unmask/rearm Device retains or emits required notification Work cannot become permanently hidden
t3 Recheck or receive interrupt Completion still in ring Consumer observes and processes it

If no retained notification or post-rearm check exists, merely enabling interrupts later does not prove the completion will be found. This is a liveness error, even if the ring data itself is coherent and correct. Hardware validation should explicitly control the timing around t1 and t2 to exercise this race.

Worked Example 10 — Separating Device Clear from Controller EOI

A hypothetical controller reports that interrupt input 12 is active. Its source is a device with two sticky status bits: RX_READY and TX_DONE. The handler reads both, consumes incoming buffers, reclaims transmitted descriptors, clears the device status using the specified write-one-to-clear values, and then completes service at the controller. The source may immediately reassert if more receive data arrives while the handler is running.

The test should deliberately inject RX_READY a second time before the first clear. If a naive read-then-clear destroys the second event, the driver loses work. A durable receive queue can prevent that if the handler drains until an agreed idle condition and uses appropriate rearm semantics. End-of-interrupt at the controller may occur earlier or later depending on architecture and interrupt type. What matters is that controller active state and device cause state are reconciled under the implementation's rules, with no assumption that one register write clears both.

Worked Example 11 — End-to-End Interrupt Latency Budget

A fictional device event experiences 12 µs of moderation, 3 µs of interconnect and controller routing, 4 µs waiting for the CPU to accept the interrupt, 2 µs for handler entry, and 9 µs for queue processing. If these terms are sequential and do not overlap, the modeled time until the device completion is consumed is 12 + 3 + 4 + 2 + 9 = 30 µs. If an application thread then waits another 20 µs for scheduling, the end-user completion delay becomes 50 µs. A measurement that stops on entry to the IRQ handler would incorrectly report only the earlier stages as the whole application latency.

Component Assumed delay
Device coalescing delay 12 µs
Signal and controller route 3 µs
CPU acceptance wait 4 µs
Handler entry 2 µs
Completion processing 9 µs
Task scheduling after completion 20 µs
Total through application notification 50 µs

This additive model is a simplified upper-level teaching aid. Real systems may overlap stages and have widely varying tails. Therefore a performance report must identify its timestamp source, timebase synchronization, and boundary of observation. Values here describe no particular hardware.

Worked Example 12 — Interrupt Storm Diagnostic Timeline

A test device produces one queue completion but the host observes 40,000 IRQ deliveries in one second. Suppose the completion-ring producer index advanced only once and the relevant device status bit remained asserted throughout the measurement. The discrepancy suggests repeated delivery of an uncleared level or a retrigger condition, not 40,000 useful completions. The investigator first records the status, trigger configuration, and controller active/pending state, then checks whether the driver is clearing the proper field.

Next the investigator masks only the affected vector if the recovery policy permits it, confirms that the interrupt rate drops, drains the completion queue, and checks whether the device's status can be cleared safely. If software cannot deassert the source or the fault immediately returns, device reset may be required after protecting in-flight DMA buffers. A high IRQ count alone cannot identify a defective controller; the source's pending condition provides stronger causal evidence. A good post-recovery test verifies both that interrupts stop when idle and that a fresh valid completion still triggers service.

Worked Example 13 — Platform Message Routing Through an Interrupt Domain

Consider an abstract MSI-capable endpoint whose event identity is E=6 and whose PCI requester identity is represented in the host's device configuration. The OS allocates a host IRQ and asks the platform to associate the endpoint's interrupt with processing element 2. The resulting message address and data are written to the endpoint's supported configuration registers. The device later issues the MSI transaction, which traverses the root complex and any enabled remapping or translation component before reaching the selected controller destination.

The precise bit layout is intentionally omitted: it differs across x86, Arm ITS, and RISC-V IMSIC mechanisms. The engineering lesson is to separate source identity, programmed message, OS IRQ identity, and target CPU. Replacing a CPU or moving the interrupt to another virtual machine can change the translation while leaving the device's semantic event E unchanged. Software should request a mapping through supported APIs, not derive a destination from a guessed physical address or vector number.

Device status bit Peripheral register field reporting an event or condition requiring inspection.
Doorbell Register or memory-mapped location used by software to notify hardware of submitted work.
DMA Direct Memory Access, a transfer initiated by a DMA-capable hardware agent.
EOI End-of-interrupt signal that changes a controller's in-service state under its specified rules.
Edge-triggered Interrupt signaled by a transition rather than a continuously asserted level.
Error vector Interrupt identifier designated for fault-reporting events in an implementation.
Event Underlying hardware condition that may motivate a notification.
Event count Number of underlying operations or conditions, not necessarily number of interrupts.
Guest interrupt Virtual interrupt presented to a virtual machine by platform or hypervisor facilities.
GIC Arm Generic Interrupt Controller architecture.
Handler Software routine invoked for an interrupt identifier.
Hard IRQ Context in which prompt interrupt handling is performed under an OS's nonblocking constraints.
Host IRQ number Operating-system interrupt identifier, not necessarily a physical controller vector.
IMSIC Incoming MSI Controller in the RISC-V Advanced Interrupt Architecture.
Interrupt domain OS/platform mapping structure connecting source interrupts to controller identities.
Interrupt injection Presentation of a virtual interrupt to a guest processing context.
Interrupt line Hardware signal representing an interrupt request in a pin-based design.
Interrupt remapping Hardware-supported validation/translation of device-origin interrupt destinations.
Interrupt storm Excessive repeated notifications that consume service resources.
Interprocessor interrupt Interrupt directed by one processor or core to another.
IOMMU Input-output memory management unit that can translate and isolate device address accesses.
IRQ Conventional abbreviation for interrupt request or OS interrupt identifier.
ISR Interrupt service routine, the code invoked to service an interrupt.
ITS Interrupt Translation Service for supported Arm GIC LPI delivery.
LPI Locality-specific Peripheral Interrupt in Arm GIC architecture.
Level-triggered Interrupt signal held active while the source condition remains true.
Local APIC x86 interrupt controller facility associated with a CPU context.
Masking Suppressing interrupt delivery at an identified control layer while work may remain pending.
Message-signaled interrupt Interrupt conveyed by a specially directed write/message rather than an external pin alone.
MSI PCI message-signaled interrupt capability with constrained vector configuration.
MSI-X Extended PCI message-signaled interrupt capability using table-based per-vector configuration.
Moderation Policy limiting interrupt frequency or delaying notifications to reduce overhead.
NUMA Non-uniform memory access organization where placement changes access cost.
Pending Bit Array MSI-X-defined structure representing pending masked vector notifications.
Per-queue interrupt Notification stream allocated to a particular device queue or group of queues.
PPI Private Peripheral Interrupt in Arm GIC terminology.
Polling Software repeatedly inspects work state without depending entirely on interrupts.
Posted MMIO write Device-directed write that may be buffered before reaching its target.
Priority Controller or CPU policy determining which eligible interrupts are served first.
Rearming Restoring notification generation or delivery after a masked/polling service period.
Redistributor Arm GIC component managing interrupt state associated with a processing element.
Remapping domain Trusted mapping boundary restricting interrupt or I/O destinations.
Requester ID PCI identity used by the platform to identify certain device-origin transactions.
Ring buffer Circular queue used for submission or completion records.
SGI Software-Generated Interrupt in Arm GIC terminology.
Shared interrupt Interrupt signaling resource used by more than one cause or device.
SPI Shared Peripheral Interrupt in Arm GIC terminology.
Spurious interrupt Interrupt indication without a corresponding currently serviceable cause at the inspected layer.
Status acknowledgment Device-specific operation that clears or retires a source event indication.
Threaded handler Interrupt-associated work running in a schedulable thread under OS-defined rules.
Top half Minimal immediate interrupt handling before deferring longer work.
Vector table Structure mapping identifiers to CPU handlers or PCI MSI-X message configurations, depending on context.
Virtual interrupt Interrupt delivered to a virtual CPU rather than directly to host software.
Wakeup interrupt Event enabled to bring a CPU or domain out of a supported low-power state.
Write-one-to-clear Register behavior in which writing a one clears a designated status bit.
