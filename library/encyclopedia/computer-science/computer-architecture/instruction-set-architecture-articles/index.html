Collection Overview

Instruction Set Architecture (ISA) is a Level 4 unit in the Computer Architecture division of the Computer Science volume within the MGU Encyclopedia. This index extends the existing Instruction Set Architecture parent overview, which defines the ISA as the formal, programmer-visible interface for processor instructions, registers, addressing, data movement, and execution behavior.

The ISA occupies a deliberate architectural boundary. It specifies the operations and effects software can rely on; the microarchitecture chooses how those effects are produced internally. Two processors may differ in pipelines, execution units, instruction cache organization, power management, and branch prediction yet execute the same ISA-compatible machine program, subject to the program's required features and the surrounding operating environment.

Three often-confused interfaces must remain separate. The ISA defines machine instructions and their architectural effects. The application binary interface (ABI) adds conventions such as function calling, stack use, data layouts, and object-file and operating-system expectations. A microarchitecture is a hardware realization whose speed, energy, and speculative behavior are not generally fixed by the ISA. Software compatibility depends on more than sharing a processor-family label.

In MGU's six-level model, this instruction-set-architecture-articles/index.html is the Level 4 unit index. Its 20 linked entries are planned Level 5 unit subarticles. Any future Level 6 and deeper companion articles will be commissioned in the separate subarticle-production workflow. This index does not create those deeper files.

Editorial provenance: the ISA parent overview introduces core operations, registers, memory, the hardware/software boundary, and design trade-offs, but does not enumerate a prescribed child list. The 20 titles and slugs in this index are a proposed, topic-bounded production plan. Their links are intentionally active to future article destinations, not claims that those targets already exist.

Architectural Contract, State, and Encoding

The first five specialist articles define the visible machine model: which operations are encoded, which registers and values are exposed, and how instructions name their operands. They should teach careful reading of a particular ISA revision rather than treating generic assembly syntax as a universal specification.

1. The ISA Contract and Programmer-Visible Machine State

Specialist scope: The software-visible behavior a conforming processor promises independent of internal implementation. Define architectural state as registers, program counter, applicable flags or status, memory effects, traps, and the observable results of executing instructions. Explain how a program can rely on a specified sequence of state transitions without knowing the implementation pipeline or gate design. Address supported optional features, reserved behavior, undefined or implementation-defined cases, and the need to identify a concrete architectural revision.

Technical boundary: Do not treat performance, pipeline depth, cache arrangement, or branch-predictor design as inherent ISA promises. Some architectural state is visible only in a particular execution privilege or configuration. Distinguish an abstract machine contract from the assembly language syntax used to express it.

Expected Level 5 deliverable: A small architectural-state diagram, one instruction-state transition, and a conformance checklist.

2. Machine Instruction Formats and Opcode Encoding

Specialist scope: How machine instructions represent an operation and its operands in encoded bit fields. Explain opcodes, operand specifiers, register fields, immediate constants, instruction lengths, prefixes, compressed representations, and decoding constraints. Compare fixed-width and variable-width encoding without assuming that an entire architecture must use only one. Examine instruction-alignment requirements and the consequences of extending an encoding space as a platform evolves.

Technical boundary: Keep decoder circuitry, micro-op generation, and instruction-cache internals in Microarchitecture. Show schematic field examples as fictional encodings unless a specific published ISA manual is cited. Avoid equating code density with executable performance across all workloads.

Expected Level 5 deliverable: An annotated hypothetical instruction format and a bit-budget exercise for opcode and register fields.

3. ISA Register Models and Status Flags

Specialist scope: Registers, program counter, status fields, and how software observes machine state. Compare general-purpose, dedicated, floating-point, vector, and privileged registers. Distinguish caller-visible architectural registers from larger physical register files that a CPU may use internally. Explain status flags, condition codes, control/status registers, register-width conventions, and the importance of identifying architectural versus platform- or operating-system-defined state.

Technical boundary: Do not imply that every ISA has one unified flags register or the same count of general-purpose registers. Register renaming is an implementation technique, not a different architecture register numbering scheme. Keep register-save conventions for the separate ABI topic.

Expected Level 5 deliverable: A labeled register map with examples of instruction-visible state changes and reserved fields.

4. Instruction Operands and Addressing Modes

Specialist scope: How instructions identify registers, immediate values, and effective memory addresses. Develop immediate, register, base-plus-offset, indexed, PC-relative, and indirect addressing where supported. Trace effective-address formation, alignment, displacement scaling, and the distinction between address calculation and the subsequent load or store. Explain how operand count and addressing complexity influence encoding and compiler choices.

Technical boundary: Addressing modes vary by ISA and are not universal. Distinguish virtual or effective addresses from their eventual translation or physical location, and keep the memory-management implementation in its appropriate unit. Avoid mixing addressing-mode semantics with a specific assembler dialect.

Expected Level 5 deliverable: Worked register and memory-operand examples with an address calculation and comparison of encoding costs.

5. ISA Data Types, Widths, Alignment, and Endianness

Specialist scope: The defined representation and interpretation of instruction operands and stored values. Explain byte, halfword, word, wider integer, floating-point, and vector widths when present; signed versus unsigned operations; sign and zero extension; and alignment behavior. Separate register width from effective address width and storage transaction size. Develop endianness as a property of how multibyte values are laid out under the applicable execution environment.

Technical boundary: Do not declare that every member of an ISA family necessarily uses the same data layout or supports all optional types. On some architectures alignment errors, emulation, and performance vary by instruction and platform. General data-encoding theory belongs to Data Representation.

Expected Level 5 deliverable: A hexadecimal memory-layout example and a table of width, extension, and alignment rules.

Instructions, Control Flow, and System Semantics

These five articles study what architectural instructions do to registers, memory, control flow, and protected execution state. Each article should distinguish a software-visible semantic guarantee from a processor implementation detail and identify where unsupported or optional features change the answer.

1. Integer Arithmetic and Logical Instructions

Specialist scope: Integer calculations, bitwise operations, shifts, comparisons, and architectural results. Cover addition, subtraction, bitwise Boolean operations, shifts, comparisons, bit-field operations, and arithmetic effects such as carry or overflow where specified. Explain signed and unsigned interpretations and how architectural semantics handle exceptional cases such as division by zero. Contrast instruction-visible results with implementation techniques such as combinational adders or iterative division.

Technical boundary: Do not assume saturating arithmetic or automatic overflow traps exist in every ISA. Flag updates, condition-code use, and availability of particular operations are architecture-specific. Gate-level circuitry belongs to Digital Logic, while mathematical Boolean identities belong to Computational Foundations.

Expected Level 5 deliverable: A sequence of short arithmetic traces showing operand interpretation, result, and applicable flags.

2. Load, Store, and Memory-Access Instructions

Specialist scope: Moving values between registers and memory under the architecture rules. Describe load/store designs, possible memory-operand arithmetic designs, access sizes, alignment, sign extension, and architectural effects of reads or writes. Introduce memory-mapped device access only to distinguish it from ordinary cached memory behavior. Show how address formation, page or protection faults, and instruction retirement affect the software-observed result.

Technical boundary: Do not assume an ISA maps all memory requests to a particular bus transaction, cache policy, or number of electrical cycles. Virtual-memory translation and coherence mechanisms belong to their dedicated units; the ISA unit specifies observable effects and constraints.

Expected Level 5 deliverable: A step-by-step trace of loading, modifying, and storing a value under specified address assumptions.

3. Branches, Calls, Returns, and Control Flow

Specialist scope: Program-counter changes, conditional branches, subroutine calls, and returns. Study instruction sequencing, unconditional and conditional branches, relative displacement, call return-address creation, and return mechanisms. Explain how branch conditions depend on flags or register comparison as defined by the ISA. Distinguish architecturally visible control transfers from branch prediction, speculation, and internal pipeline flushing.

Technical boundary: Calling conventions decide which registers carry function arguments or must be preserved; the ISA usually defines available instructions but not a whole application ABI. Treat exceptions and traps separately from ordinary subroutine calls. Do not equate every return with a dedicated hardware stack mechanism.

Expected Level 5 deliverable: A labeled control-flow trace including a conditional branch and a function call/return.

4. Atomic Instructions and Memory Ordering Models

Specialist scope: Shared-memory instructions and visibility guarantees supporting concurrent programs. Explain atomic read-modify-write, compare-and-swap or load-reserved/store-conditional where provided, fences, and the memory-ordering rules observed by software. Distinguish atomicity, ordering, visibility, cache coherence, and progress guarantees; none is automatically equivalent to the others. Describe how high-level language atomics must map onto ISA rules.

Technical boundary: Memory models differ between architectures, and some operations require privilege or feature support. Do not generalize a single instruction sequence across x86, Arm, and RISC-V or suggest that hardware atomics automatically solve higher-level race conditions. The implementation of coherence protocols belongs to Microarchitecture and Memory Hierarchy.

Expected Level 5 deliverable: A producer-consumer ordering example, a two-core litmus test, and a mapping from language-level operation to required ISA guarantees.

5. Exceptions, Traps, Privilege, and System Instructions

Specialist scope: Architectural entry points for faults, protected operations, and execution-state transitions. Explain synchronous exceptions, interrupt entry, trap return, privilege levels or modes, architected status, and system-control instructions at the ISA interface. Distinguish an instruction causing a trap from an operating-system service contract. Illustrate how architectural state is saved or made available to a handler under a defined model.

Technical boundary: System-call numbers and user-space argument conventions typically belong to an operating-system ABI, not the hardware ISA. Precise privilege structure depends on the specified ISA extension or profile. Avoid confusing the ISA-defined trap mechanism with the underlying interrupt controller or specific operating-system policy.

Expected Level 5 deliverable: An exception-state transition diagram and a classification table of instruction fault, interrupt, and software trap.

ISA Design Families and Specialized Extensions

These five articles compare ISA-design approaches and representative families without collapsing product generations, architectural profiles, instruction encodings, or optional extensions. Named ISA examples are intended as teaching case studies; versioned architectural manuals control technical detail.

1. RISC, CISC, and Load–Store Design Trade-offs

Specialist scope: Design philosophies concerning instruction complexity, operands, decoding, and software work. Develop the historical distinction among reduced and complex instruction sets, register-based and memory-operand designs, and decoding regularity. Compare instruction count, encoding density, compiler opportunities, and implementation freedom. Explain why contemporary processors complicate simple RISC-versus-CISC labels and why no category alone determines performance or energy use.

Technical boundary: Do not claim all RISC instructions are fixed-width or that every CISC instruction translates to one internal operation. The ISA classifies observable instructions; translating them to internal micro-operations is an implementation decision. Use workloads and actual processor specifications for comparative performance claims.

Expected Level 5 deliverable: A side-by-side architectural comparison and an example where instruction count differs but outcome is identical.

2. x86-64 ISA: Registers, Encoding, and Compatibility

Specialist scope: The software-visible structure and extension history of a major variable-length ISA family. Introduce general-purpose register evolution, x86-64 execution modes, instruction prefixes and encodings, memory-operand forms, status flags, and extension discovery. Explain the reasons that compatibility modes and optional instruction features complicate binary-portability assumptions within the nominal family.

Technical boundary: Use Intel and AMD architectural manuals as authoritative details rather than inferring behavior from generic x86 assembly. Keep speculative execution, cache behavior, and vendor-specific processor performance for Microarchitecture. Do not imply every x86-64 processor implements every vector or security extension.

Expected Level 5 deliverable: A compact field-and-register overview with a compatibility and feature-detection worksheet.

3. Arm A64 ISA and Architectural Profiles

Specialist scope: A64 programming model, instruction forms, and the role of architecture profiles. Explain AArch64 state and the A64 instruction set, register naming conventions, control-flow mechanisms, memory operations, exception levels, and optional architectural features with properly identified scope. Situate A-profile in relation to other Arm architectural profiles without assuming the same instruction set or memory model across every Arm device.

Technical boundary: Do not confuse Arm ISA revisions, execution states, CPU product names, or platform-specific calling conventions. Some optional features have profile and revision prerequisites. Use the current Arm architecture reference manual to verify instruction details; cache microarchitecture belongs to a neighboring unit.

Expected Level 5 deliverable: An A64 instruction-category map plus a chart distinguishing architecture profile, execution state, and device implementation.

4. RISC-V Base ISAs, Extensions, and Profiles

Specialist scope: Modular standard instruction sets and how named extensions define compatibility. Present base integer ISAs, XLEN, instruction encodings, extension naming, privilege-specification boundaries, and how profiles constrain supported feature combinations. Explain that unprivileged base behavior and optional features must be identified explicitly, and that the architecture does not mandate one pipeline or memory-controller design.

Technical boundary: Avoid implying all RISC-V processors support floating-point, vectors, atomics, or compressed encodings. Do not collapse RV32 and RV64 into a universal strict-superset claim. Cite ratified versions or profiles when making detailed interoperability assertions; implementation and SoC buses remain separate topics.

Expected Level 5 deliverable: An example ISA-string interpretation and a compatibility matrix separating mandatory and optional functions.

5. Floating-Point, SIMD, and Vector ISA Extensions

Specialist scope: Specialized instructions that broaden numerical and data-parallel operations. Explain floating-point operations and rounding-mode behavior, scalar versus packed SIMD, lane width, vector length abstractions, masking, and architectural exception or status rules. Contrast fixed-width vectors and scalable or vector-length-agnostic models without assuming one universal mapping from source expressions to hardware lanes.

Technical boundary: General floating-point numerical-analysis errors belong to Data Representation or Scientific Computing. Vector throughput, physical lane count, and execution units belong to Microarchitecture. Availability, rounding behavior, and save/restore requirements depend on a specific feature set and execution environment.

Expected Level 5 deliverable: A scalar-versus-vector dataflow exercise and a matrix listing architectural contracts versus implementation-dependent throughput.

Software Compatibility, Validation, and Evaluation

These five articles address the ecosystem consequences of an ISA: binary compatibility, toolchain targeting, architectural conformance, alternative execution methods, and defensible evaluation. Their purpose is to prevent statements about one instruction set from being mistaken for universal platform, operating-system, or performance guarantees.

1. Application Binary Interfaces and Calling Conventions

Specialist scope: How an ISA becomes a usable binary target through platform and toolchain conventions. Describe calling conventions, argument passing, callee-saved registers, stack alignment, function return values, object-file relocation, runtime linkage, and the distinction between ISA validity and ABI compatibility. Explain why two systems sharing an ISA may still require different binaries because of operating systems, libraries, object formats, or platform conventions.

Technical boundary: An ABI is not identical to the ISA; its ownership may involve compiler, OS, and platform specifications. Do not assign one universal calling convention to an entire ISA family. Keep compiler optimization and linker implementation details in their respective Programming and Development units.

Expected Level 5 deliverable: An annotated function-call ABI example and a compatibility decision checklist covering ISA, ABI, OS, and libraries.

2. ISA Evolution, Feature Detection, and Binary Compatibility

Specialist scope: Managing revisions and optional extensions without invalidating existing software. Explain backwards-compatible expansion, feature negotiation, minimum target baselines, software dispatch, compiler architecture flags, and constrained environments. Distinguish binary compatibility, source compatibility, and semantic compatibility. Explore changes that cannot be assumed safe when privileged features, exception behavior, or optional instruction groups differ.

Technical boundary: Do not infer that a marketing family name guarantees execution of every extension. Treat emulation and translation separately from native support. Deployment should document both compile-time target requirements and runtime feature discovery when relevant.

Expected Level 5 deliverable: A sample software deployment compatibility matrix and a feature-gating workflow.

3. ISA Semantics, Conformance Testing, and Formal Verification

Specialist scope: Checking that an implementation behaves as the published architecture requires. Define tests for instruction semantics, special operands, exception behavior, privilege boundaries, memory ordering, and optional features. Discuss architecture test suites, reference interpreters, executable semantics, differential testing, and formal properties. Explain that validation must identify the specification revision and tested configuration.

Technical boundary: Passing a particular test suite does not imply proof of all ISA behaviors, absence of hardware vulnerabilities, or high performance. Do not treat compiler self-tests as a substitute for architecture conformance. Microarchitectural timing and side-channel assurance require different evidence.

Expected Level 5 deliverable: A requirements-to-test matrix with representative instruction cases, negative cases, and documented coverage limits.

4. Binary Translation, Emulation, and Virtualized Execution

Specialist scope: How software or hardware may execute machine code across implementation boundaries. Differentiate interpretation, dynamic binary translation, full-system emulation, architectural simulation, and hardware-assisted virtualization. Discuss instruction emulation, trap handling, guest-visible state, system-call compatibility, and the difference between native instruction support and a software-mediated equivalent. Explain correctness and performance trade-offs of cross-ISA execution.

Technical boundary: A virtual machine is not necessarily a cross-ISA emulator. Host/guest ABI, device models, privilege modes, and supported extensions matter. Leave broad hypervisor administration, virtual infrastructure, and runtime environments to neighboring software units.

Expected Level 5 deliverable: A deployment matrix matching native execution, same-ISA virtualization, and cross-ISA translation to compatibility requirements.

5. ISA Design Evaluation: Code Density, Energy, and Workloads

Specialist scope: Evaluating architectural choices through measurable requirements instead of labels. Develop metrics such as encoded code size, binary distribution size, dynamic instruction count, cycles or time per workload, compiler support, decoder cost, energy per completed task, and long-term toolchain compatibility. Explain how ISA, compiler, microarchitecture, process technology, and workload interact so causal conclusions are properly bounded.

Technical boundary: An ISA alone does not determine performance per watt or silicon area. Benchmarks must specify tested hardware, compiler versions and flags, inputs, feature configurations, measurement conditions, and uncertainty. Avoid claiming that RISC or CISC guarantees a particular speed or power advantage.

Expected Level 5 deliverable: A transparent multi-criteria evaluation worksheet showing assumptions, metrics, comparators, and evidence needed.

Illustrative ISA Scenarios

Example 1 — Reading a fictional instruction encoding

Suppose a fictional 16-bit instruction assigns 4 bits to an opcode, 4 bits to a destination register, 4 bits to a source register, and 4 bits to an immediate value. The fields total 16 bits, permit at most 16 opcode patterns in that simplified format, and have 16 register identifiers in each four-bit operand field. That arithmetic alone does not establish that all 16 opcode patterns are legal, how immediates are extended, or which operations exist. A real ISA specification must give each field its semantics and document reserved encodings. Read Machine Instruction Formats and Opcode Encoding, ISA Register Models and Status Flags, and Instruction Operands and Addressing Modes together.

Example 2 — Calculating a base-plus-offset address

A hypothetical load instruction computes an address from a base register containing hexadecimal 0x1000 and a byte displacement of 0x18; the effective address is 0x1018. If the instruction reads a four-byte object, the system must also define the access width, alignment expectations, virtual-memory meaning, and possible fault behavior. Endianness determines the reconstructed multibyte value, not the sum used to locate the first addressed byte. Compare Instruction Operands and Addressing Modes, ISA Data Types, Widths, Alignment, and Endianness, and Load, Store, and Memory-Access Instructions. This is a neutral arithmetic example, not an encoding from a named architecture.

Example 3 — Two processors, one software-visible program

Two imaginary processors implement the same required ISA and extensions. One uses a short in-order pipeline and the other uses aggressive out-of-order execution. Provided the system environment satisfies the program's ABI and other assumptions, both can produce the same architecturally required program results while differing greatly in throughput, latency, and power consumption. An application timing benchmark is therefore not an ISA-conformance test. This distinction is central to The ISA Contract and Programmer-Visible Machine State, ISA Semantics, Conformance Testing, and Formal Verification, and ISA Design Evaluation: Code Density, Energy, and Workloads.

Example 4 — A binary uses an optional extension absent on another device

A compiler targets a vector instruction extension present on a development processor. The compiled binary is then placed on a compatible base-ISA device that does not implement that extension. Executing the unsupported instruction can produce an illegal-instruction exception rather than silently producing a slower vector operation. Suitable responses include choosing a common compilation baseline, dispatching to a feature-appropriate implementation, or using documented emulation where available. Read ISA Evolution, Feature Detection, and Binary Compatibility, Floating-Point, SIMD, and Vector ISA Extensions, and RISC-V Base ISAs, Extensions, and Profiles. Exact behavior depends on the particular ISA and execution environment.

Example 5 — A lock hand-off needs ordering, not just arithmetic

A producer writes a payload and then marks a flag indicating readiness. A consumer watches the flag before reading the payload. On a weakly ordered system, merely making the flag update atomic may not guarantee the payload is visible in the intended order. Software must use suitable release/acquire semantics or architecture-defined ordering mechanisms through its language runtime and compiler. The necessary instruction sequence depends on the platform and must not be guessed. Pair Atomic Instructions and Memory Ordering Models with ISA Semantics, Conformance Testing, and Formal Verification and the neighboring Memory Hierarchy overview.

Example 6 — Matching machine code is insufficient for cross-platform delivery

Two operating systems can run processors implementing the same ISA, but a compiled program may still use a calling convention, executable object format, shared libraries, or system-call interface not available on the second system. In that case, the ISA match does not establish platform-level binary compatibility. A deployment plan must identify ISA and required extensions, ABI, object format, operating system, and library dependencies. Consult Application Binary Interfaces and Calling Conventions, ISA Evolution, Feature Detection, and Binary Compatibility, and Binary Translation, Emulation, and Virtualized Execution.

Example 7 — A virtual machine is not automatically a different-ISA emulator

An application that runs inside a same-ISA virtual machine may execute most user-mode instructions directly on a compatible host while privileged operations are mediated. Running a binary built for a genuinely different ISA instead requires an appropriate translator, interpreter, or emulator, plus enough environment compatibility for the binary to function. The performance and security implications differ. Binary Translation, Emulation, and Virtualized Execution owns the comparison; Exceptions, Traps, Privilege, and System Instructions supplies the architectural privilege vocabulary.

All seven scenarios are constructed teaching examples. They do not describe a particular MGU computing platform, represent benchmark results, or claim that any named processor is conformant or certified.

Suggested Study Pathways

New learners: start with the existing Instruction Set Architecture parent overview, then The ISA Contract and Programmer-Visible Machine State, Machine Instruction Formats and Opcode Encoding, ISA Register Models and Status Flags, Instruction Operands and Addressing Modes, and ISA Data Types, Widths, Alignment, and Endianness. The goal is to read a machine-instruction reference precisely, not simply memorize mnemonics.

Assembly and low-level programming: move to Integer Arithmetic and Logical Instructions, Load, Store, and Memory-Access Instructions, Branches, Calls, Returns, and Control Flow, and Application Binary Interfaces and Calling Conventions. Compare a short function's instruction effects with the calling convention that makes it usable from other compiled code.

Compiler, toolchain, and platform engineers: study Machine Instruction Formats and Opcode Encoding, Instruction Operands and Addressing Modes, ISA Evolution, Feature Detection, and Binary Compatibility, Application Binary Interfaces and Calling Conventions, and Binary Translation, Emulation, and Virtualized Execution. Keep the instruction semantics, ABI commitments, and runtime assumptions distinct during deployment.

Hardware architects and verification engineers: combine The ISA Contract and Programmer-Visible Machine State, Atomic Instructions and Memory Ordering Models, Exceptions, Traps, Privilege, and System Instructions, and ISA Semantics, Conformance Testing, and Formal Verification. Link the architectural specification to testable behavior, then read the neighboring Microarchitecture unit to understand implementation possibilities.

Students comparing instruction-set families: read RISC, CISC, and Load–Store Design Trade-offs, x86-64 ISA: Registers, Encoding, and Compatibility, Arm A64 ISA and Architectural Profiles, and RISC-V Base ISAs, Extensions, and Profiles. Compare named versions and extension sets using manuals, not marketing labels; finish with ISA Design Evaluation: Code Density, Energy, and Workloads.

Concurrent, numerical, and accelerated-computing developers: pair Atomic Instructions and Memory Ordering Models with Floating-Point, SIMD, and Vector ISA Extensions, then identify which features are actually available via ISA Evolution, Feature Detection, and Binary Compatibility. Compiler lowering and numerical correctness may require neighboring specialist material rather than an assumption that vector instructions guarantee a faster or identical result.

Security and systems-software readers: use Exceptions, Traps, Privilege, and System Instructions, ISA Semantics, Conformance Testing, and Formal Verification, and Binary Translation, Emulation, and Virtualized Execution to distinguish architecturally defined privilege, a compliant implementation, and a virtualized environment. The existence of a privilege mode or extension alone does not certify platform security.

Recommended sequence: architectural contract and representation → core instruction effects → selected ISA families and extensions → ABI and compatibility → verification and measured evaluation. This preserves prerequisite order while allowing applied readers to enter at their relevant topic.

Reference Standards and Interpretation

Future Level 5 authors should use versioned specifications rather than relying on informal summaries when describing encodings, exceptions, optional extensions, or memory ordering. The following organizations publish authoritative architecture documentation for the representative families covered here:

  • RISC-V International — Ratified Specifications Library. Identify the relevant unprivileged and privileged specification revisions, ratified extensions, and any profile under discussion.
  • Intel — Intel 64 and IA-32 Architectures Software Developer's Manuals. Consult the relevant instruction-set reference and systems-programming volumes for explicitly named architectural features.
  • Arm — Architecture Reference Manual for A-profile. Use the relevant edition and architecture features when discussing A64 instruction behavior, execution state, and privileged structures.

Interpretation rule: this index is a scholarly production directory, not a substitute for an ISA reference manual. Features change over time; optional instructions and architecture profiles must be identified by their supporting specification. Version-agnostic educational examples on this page avoid claiming exact behavior for an unidentified processor.
