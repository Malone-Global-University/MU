Processor, Memory, Storage, and I/O Roles

The complementary responsibilities of computation, working state, persistent information, and external communication—and the requests and transfers that unite them.

1. Scope and the four cooperating roles

A functioning computer is a coordinated system rather than a processor standing alone. The processor interprets and executes instructions; main memory holds the working instructions and data that processors can address; persistent storage preserves selected information across normal loss of power; and input/output mechanisms exchange information with users, sensors, networks, and attached devices. These are logical roles, not a mandatory list of separate chips. A microcontroller can integrate processor, SRAM, nonvolatile flash, and I/O controllers on one die. A server can distribute the same functions across CPUs, memory modules, accelerators, network cards, and storage enclosures.

The principal architectural question is who supplies, transforms, retains, and delivers information, followed by where requests travel and who owns each operation. The four roles are distinguishable even when a product collapses them physically. For example, an NVMe controller is itself a specialized processor with local memory, yet it serves the host system primarily as an I/O and persistent-storage subsystem. An integrated GPU may be both a compute engine and a participant in shared memory. Architectural analysis therefore labels roles at the chosen system boundary rather than assuming that a part has a unique role at every scale.

This article introduces subsystem cooperation and observable operations. It does not attempt a component catalog or detailed exposition of cache replacement, flash wear leveling, or operating-system device-driver programming; those subjects belong to neighboring articles.

2. System boundary, ownership, and paths

Choose a system boundary before drawing a block diagram. A laptop boundary may include its integrated SSD and display, while an application-server boundary may treat a storage array as an external endpoint reached through a network. Ownership identifies which actor initiates or authorizes a request, which resources it may address, and which subsystem reports completion. Processor instructions can launch activity that continues independently through a DMA-capable device, but software still prepares the operation, grants permitted access, and interprets its result.

The control path identifies commands, status, and event notification. The data path identifies payload movement: a cache-line fill, a storage block, a packet, or a display frame. Both can share the same physical fabric or use independent resources. A completion interrupt is a control event, not proof that an entire data payload rode the interrupt path. Conversely, large bulk transfers can be completed without an interrupt for every item through polling or batched event signaling.

3. Processor responsibilities

A general-purpose processor maintains architectural registers, instruction sequencing state, privilege state, and the ability to load, transform, and store data as defined by its instruction set. It executes operating-system and application software, issues memory operations, performs address calculations, and programs device controllers through permitted register interfaces. These are capabilities of the processor’s architectural interface; pipelines, speculative execution, cache organizations, and execution-port counts are microarchitectural implementation choices.

The processor does not ordinarily fetch a filesystem record directly from flash cells as though the storage medium were a register. It requests I/O through system software and a controller, then operates on data after that data becomes accessible through the memory system. Storage and I/O controllers may perform substantial processing themselves; this does not eliminate the host processor’s responsibility for scheduling, permissions, and application semantics.

CPU cores do not all provide the same instruction throughput, memory bandwidth, or interrupt latency. A core can stall on a long-latency load despite an otherwise fast arithmetic pipeline. A workload can saturate the memory controller or storage link long before it saturates its arithmetic units. These distinctions are fundamental to whole-system performance analysis.

4. Memory as the active working state

Main memory provides addressable working storage for code, stacks, heaps, buffers, kernel data, and device-related structures. DRAM commonly serves this role in general-purpose systems; SRAM and on-chip memory may serve it in embedded devices. Memory is neither synonymous with a CPU cache nor with persistent storage. Caches replicate or stage selected information near consumers, and virtual memory supplies the process-visible addressing abstraction that the operating system and hardware translate into physical locations.

Main memory generally loses its contents when ordinary power is removed; persistence should not be assumed merely because information was written to RAM. Memory accesses have a particular address space, translation path, access permission, ordering relation, and latency. A CPU load may hit in L1 cache, miss through successive cache levels, and eventually request data from a memory controller. The application still sees one architecturally defined load, not a new instruction for every internal movement.

Devices may read or write memory through DMA when the platform and operating system establish the appropriate mapping. This shared access creates synchronization requirements: CPU caches, interconnect ordering, device buffers, and the operating-system DMA API determine when each participant may safely consume the data.

5. Persistent storage and durable information

Persistent storage holds information intended to survive normal shutdown and restart: operating-system images, programs, databases, logs, and user files. SSDs and HDDs are familiar physical implementations, but this architectural role can be served by other nonvolatile technologies and remote storage services. Persistence is a guarantee that must be defined at an interface, not a synonym for a write instruction leaving a CPU.

The storage stack typically translates application operations into filesystem, block, or device-level requests. A write may pass through application buffers, an operating-system page cache, block queues, a controller, and device caches before data reaches durable media. A completed call, a controller completion, and a confirmed durable write can have different meanings; software must use the platform’s documented synchronization or flush semantics when durability matters.

Persistent storage is normally accessed by commands or transfers rather than arbitrary byte-addressed CPU loads. Some nonvolatile memory technologies can be mapped more directly, but that design changes access and persistence rules and should not be inferred from the word “storage.”

6. Input/output as the external exchange boundary

I/O is the mechanism by which the system observes, controls, or communicates beyond its own executing instructions. Input examples include keyboard events, camera frames, sensors, network packets, and storage reads. Output examples include displayed pixels, network transmissions, actuator commands, and storage writes. Many devices are bidirectional and cannot be classified meaningfully as input-only or output-only.

A device controller provides a usable interface between system software and the physical device: command queues, configuration registers, DMA engines, status codes, interrupts, and protocol translation. The processor generally does not generate every electrical transition on a modern network link or flash memory bus. It sends commands and interprets completion while specialized controllers manage device-specific protocol details.

Some I/O is memory-mapped, meaning the CPU reaches controller registers through its normal address-access instructions with special memory attributes. This does not make device registers ordinary RAM: reads and writes may have side effects, widths can be restricted, and posted writes or ordering constraints can change when effects become observable.

7. Logical roles versus physical placement

The classic diagram showing CPU, main memory, storage, and devices as separate boxes is a learning aid. A modern system-on-chip can put CPUs, accelerators, caches, memory controllers, video engines, and peripherals in a single package or die. A server may employ discrete DIMMs, plug-in GPUs, remote storage, and network adapters. Both systems realize the same broad responsibilities, but the number of crossings, the available bandwidth, and trust boundaries differ.

Physical proximity alone does not establish logical uniformity. An integrated GPU can share system DRAM with CPU cores while using separate page tables, caches, and command queues. Chiplet-based packages may have substantial on-package bandwidth yet still require explicit coherent or noncoherent interfaces. Likewise a network-attached disk can supply the persistent-storage role even though its hardware lies outside the host computer.

8. The system-level request lifecycle

A useful universal sketch is request → permission and address interpretation → transport → target work → completion → consumption. The initiator may be software running on a CPU or a previously configured device engine. Permission checks can occur at the CPU’s memory-management unit, at an IOMMU, in a bridge or fabric, and inside the target. The target may perform a register action, move bytes, transform a block, or report an error.

Not all requests have explicit replies. Memory writes can be buffered; a posted I/O write can be accepted upstream before a final target action; a storage controller can acknowledge command submission long before media operations complete. The word “completed” must therefore identify which boundary has observed what event. Incorrectly treating queue submission as durable storage completion can produce lost updates, and treating interrupt receipt as automatic cache coherency can produce stale data.

9. Instruction fetch and working data

Instruction fetch and data access are different *purposes* of reading memory, not universally distinct physical memory devices. A stored-program computer represents both program instructions and operands in an addressable memory model. Harvard-style and modified-Harvard systems can provide separate instruction and data paths or cache organizations, sometimes converging at shared backing memory.

Code loading illustrates the cooperation: persistent storage supplies the executable image; system software maps its segments and establishes permissions; working memory or mapped pages provide instruction bytes to the processor; the CPU decodes and executes instructions. Program execution therefore depends on storage only when loading or paging requires it, not on a storage transaction for every instruction issued.

10. Cache hierarchy as a hidden but material intermediary

Processor caches commonly retain recently used data and instructions near execution units. They reduce average memory access latency and external traffic, but application-visible correctness still depends on the system’s memory model, access attributes, and coherence mechanisms. A cache hit is a memory access serviced internally; a cache miss may require a fabric transaction and eventually main-memory work.

A graphics controller and CPU can share memory without sharing identical cache behavior. A DMA buffer may be cache-coherent, or software may need explicit cache maintenance and ownership handoffs. “Shared memory” does not by itself imply coherent caches, atomic visibility, or a defined ordering guarantee. For design decisions, the question is whether a particular endpoint participates in the relevant coherency domain.

11. Memory controllers and access scheduling

A memory controller translates transactions arriving from CPU cores and other agents into commands appropriate for attached memory devices. It schedules accesses subject to timing rules, manages ranks and channels, and may perform error-detection or correction functions. For a processor core, the controller is downstream infrastructure rather than an instruction-decoding engine.

Two CPU sockets or accelerator devices can contend for the same controller even when each has a high-bandwidth local connection. Nonuniform memory access (NUMA) makes the location of memory allocations important: an access to remote memory can traverse additional links and experience different latency. More channels can increase bandwidth capacity but cannot eliminate dependencies in a serial instruction stream or remove queueing under contention.

12. The I/O controller and its register interface

The host discovers a device and learns which command interface, address regions, and interrupt facilities it supports. MMIO registers often contain command doors, queue pointers, status, or error reports. The device may present a logical command model rather than exposing the underlying media or sensor protocol. For a storage controller, command queues and data buffers allow substantial work to proceed with little instruction-by-instruction intervention by the host.

Register semantics are device-specific. A write-one-to-clear status bit is not ordinary RAM, and a “ready” flag might be updated asynchronously. Drivers must apply the required access widths, synchronization operations, and error handling. An architectural diagram that labels a block “I/O” must therefore leave room for the controller, transport fabric, physical device, and software layers.

13. Programmed I/O, DMA, and autonomous transfer

With programmed I/O, software explicitly reads or writes device-accessible registers or data windows as part of a transfer. With direct memory access (DMA), a controller or capable endpoint initiates memory transactions after software supplies suitable buffers and permissions. DMA does not imply a free transfer: memory bandwidth, cache effects, address translation, bus arbitration, and completion handling still consume resources.

A common DMA sequence is buffer allocation, mapping into the device address space, descriptor creation, queue publication, device execution, completion observation, and unmapping or reuse. The IOMMU can translate and restrict device-visible addresses, which need not equal CPU virtual or physical addresses. Coherent and streaming DMA interfaces impose distinct ownership and synchronization requirements. For example, the Linux DMA API documents different mapping and synchronization expectations; its exact calls are platform and driver-context dependent.

14. Event notification, interrupts, and polling

Controllers report completion and exceptional conditions through status registers, interrupts, or shared completion queues. A traditional interrupt line signals an event; message-signaled interrupts use a transaction-based mechanism. Neither is the path through which a disk’s entire data block moves. The processor or operating system uses the notification to examine the relevant queue or device state.

Polling avoids an interrupt-delivery event for each completion but spends CPU time checking for work; interrupt moderation batches notifications and may reduce overhead at the cost of additional waiting. High-throughput network and storage stacks frequently use mixtures of polling, batching, and interrupt-driven wakeups. The correct policy depends on event rate, response-time targets, available CPU resources, and power budget.

15. Storage read: from device to working memory

For a representative SSD read, an application requests a file range. Software identifies the corresponding storage blocks and submits an I/O command. The controller reads the relevant data from its media and transfers it to the mapped host buffer using the system’s storage and memory paths. On completion, the controller records status; the host then makes the buffer available to its consumer under the applicable synchronization rules.

That flow includes at least three distinct activities: a control request describing what to read, a bulk-data transfer delivering bytes, and a completion notification reporting status. The actual physical sequence can be pipelined and overlapped. A successful queue entry does not mean data already exists in the destination buffer; a DMA completion must be interpreted according to the controller’s specified ordering and the host’s memory-coherency model.

16. Storage write: from working memory to durable media

The reverse path begins with modified data in software-visible memory. The host prepares a command, grants the controller read access to the transfer buffer, and submits work. The device consumes the payload and eventually reports its command result. Yet the words “write complete” may concern controller acceptance, device cache, or nonvolatile media depending on the protocol, configuration, and flush commands.

Durable storage design separates visibility to the storage stack from survival after power loss. Filesystems and databases can employ journaling, write-ahead logging, barriers, and flush requests to enforce recovery requirements. An interconnect may deliver a buffer perfectly and still not guarantee the application’s desired durable state. Storage correctness therefore crosses architectural and software boundaries.

17. Network receive and network transmit flows

A received Ethernet frame illustrates a device-to-memory path. The network adapter detects a frame, validates or processes its link framing, places payload data into host buffers through DMA, publishes completion metadata, and notifies the host. The operating system and application examine protocol headers and consume the data. Transmit reverses the principal payload direction: software prepares buffers and descriptors, the adapter reads them, and the interface sends frames onto the network.

Network stacks may also use hardware offloads, queue pairs, checksums, segmentation assistance, or packet classification. Those functions belong to a controller or accelerator but do not eliminate system-level software authority. They demonstrate why the I/O role is best understood as a service boundary, not as a simple electrically attached peripheral with one status bit.

18. Display and interactive input flows

A display pipeline may compose a framebuffer produced by CPU or GPU work, access it through memory, encode the output signal, and drive a connected screen. Rendering a frame and scanning it out are distinct operations; they can overlap and can have separate timing budgets. In systems with a discrete GPU, command submission and memory movement may traverse an expansion interconnect before scanout occurs.

Keyboard and sensor input typically begin with events generated asynchronously relative to the CPU’s instruction stream. A controller buffers or encodes events, the platform reports them, and software decides how to act. The I/O role here is primarily low-bandwidth control and responsiveness, unlike bulk storage or high-speed networking. A good architectural diagram therefore distinguishes payload volume, event frequency, and latency requirements.

19. Address spaces and ownership boundaries

Software virtual addresses, CPU physical addresses, memory-mapped peripheral regions, and device-visible DMA addresses are related but not identical. Address translation and protection can occur at multiple points. A virtual address used by an application is not automatically a legal physical destination for a device. A PCIe base address register describes a host-visible region, not a license for the endpoint to access all system memory.

Isolation boundaries are part of the system’s functioning, not a security feature appended after integration. CPU memory protection constrains processes, IOMMU mappings constrain devices, and platform firmware establishes some initial resource assignments. Security reviews should identify the owner of each buffer, whether devices can perform peer-to-peer transfers, when a mapping is revoked, and what happens to outstanding work during reset.

20. Coherence, ordering, and visibility

Coherence concerns consistent observation of values for locations shared by participating caches or agents; ordering concerns which operations may become visible before others; completion concerns the protocol event indicating progress at a specified boundary. These are not equivalent guarantees. A coherent DMA buffer can still require memory barriers before device descriptors or ownership flags are safely published. A posted write may require a documented readback or other synchronization before software assumes that a device has observed it.

In a typical descriptor flow, software writes payload metadata, uses the required ordering primitive, then signals the device through a doorbell. The device produces results and completion status; software acquires the appropriate visibility before reading them. Omitting the ordering operation can allow a device to observe the doorbell before the completed descriptor state, even where data is stored in coherent memory. Such results are system-specific and must follow the platform’s actual memory model.

21. Latency, bandwidth, and throughput are different budgets

Latency is the delay experienced by a request or operation, while bandwidth expresses the capacity to move information per unit time. Throughput is the rate actually achieved by completed work. A high-bandwidth memory channel may still have substantial individual access latency, and a low-latency MMIO register may not be suitable for bulk transfers. A storage device’s advertised sequential bandwidth does not describe random small-I/O latency.

The complete path determines effective performance: application scheduling, CPU instruction work, translations, queues, fabrics, controllers, and physical devices all contribute. The slowest sustained stage usually limits end-to-end throughput for a pipeline of large transfers; for small dependent operations, fixed latency and software overhead may dominate. Performance claims must identify direction, operation size, concurrency, and measurement boundary.

22. Queue depth and concurrent requests

Queues allow many outstanding operations to overlap. A device with a single serial dependency cannot necessarily exploit a deep queue, while independent I/O requests can hide controller and media latency if adequate resources exist. Little’s law offers a useful steady-state relation: average in-flight work equals throughput multiplied by average time in the system, when measured over compatible scopes and under stable conditions.

More queue depth is not always beneficial. It can raise waiting time, create contention, increase tail latency, and intensify unfairness between requesters. A balanced design measures delivered bandwidth alongside latency distributions, queue occupancy, CPU utilization, and device errors. A single headline throughput number cannot explain a whole computing system.

23. Reliability and error propagation

Error detection exists at multiple layers. Memory can use ECC, links may use CRC and replay, storage devices can report command errors, and network protocols can detect corrupted frames. Detection does not automatically guarantee correction; recovery can require retry, buffer repair, device reset, alternative paths, or application-level reconstruction. A bad block and a failed PCIe link are different incidents with different responsible components.

An engineering fault trace asks which boundary first observed the failure, what work may already have occurred, and whether retry is safe. Reissuing a pure read is often different from repeating a device command with side effects. Software must not silently assume idempotence across storage operations, MMIO control writes, or distributed services. Logs and device status need timestamps and correlation identifiers where possible.

24. Power, sleep states, and resource availability

A laptop may park CPU cores, power down links, spin down or idle storage, and suspend peripheral controllers. A battery-powered sensor might spend most of its time in sleep and briefly wake to sample data, perform computation, and transmit a packet. These choices modify response time, bandwidth availability, and energy per task without changing the fundamental four-part functional model.

Wakeup introduces coordination requirements: a sleeping device may lose volatile queue state, a memory controller may have to restore operational timing, and software must sequence register access after power and clocks are ready. Low-power system design therefore needs explicit state-transition and wakeup contracts in addition to normal steady-state dataflow diagrams.

25. Embedded systems and microcontrollers

In a microcontroller, flash may hold program code, SRAM supplies working data, a processor executes instructions, and mapped timers, ADCs, UARTs, and GPIO controllers provide external interaction. The distinction between storage and memory can blur physically: flash may be directly addressable for instruction fetch and may also preserve application configuration. But its write latency, endurance, and erase requirements remain unlike ordinary SRAM access.

DMA is common even in small systems. For example, a peripheral may transfer an ADC sample sequence into SRAM while a core sleeps or performs another task. Interrupt or polling then signals buffer readiness. The design problem is the same as in a large server: control ownership, address permissions, transfer size, completion, and timing constraints—not simply the count of chips on the circuit board.

26. Servers, accelerators, and heterogeneous systems

Servers often expose multiple processors, many memory channels, high-speed network interfaces, and storage controllers. Accelerators such as GPUs or AI engines can run substantial kernels independently and access local or shared memory. At the system boundary they are both compute participants and devices with command submission, memory mapping, and completion procedures.

The architectural questions include data placement, transfer overhead, coherent versus noncoherent sharing, memory-capacity limits, and system-wide energy use. An accelerator’s peak arithmetic rate is not a guarantee of application speedup when the application repeatedly transfers buffers or waits for serialized host work. Similarly, a multi-socket server’s aggregate memory bandwidth may hide significant local-versus-remote memory differences.

27. Virtual machines and logical devices

A virtual machine can see virtual CPUs, guest memory, virtual disks, and virtual network interfaces. The host maps those logical roles onto real processors, RAM, storage volumes, and network ports. The four-part architecture remains useful even though each component exists at a different abstraction level. Some virtual devices are emulated in software; others expose hardware functions with controlled direct assignment.

Virtualization introduces further translation, scheduling, and isolation boundaries. Guest physical memory is not necessarily host physical memory. A virtual disk write might ultimately reach a file, block device, network storage system, or replicated storage service. End-to-end troubleshooting must cross those layers instead of attributing every delay to the visible guest “disk.”

28. Comparing platform organizations

A low-power embedded board prioritizes deterministic response and energy use; a desktop workstation often prioritizes interactive latency and accelerator capacity; a database server may prioritize memory footprint, storage IOPS, fault recovery, and predictable tail latency. These are not different definitions of processor, memory, storage, and I/O, but different allocations of architectural resources and different interfaces among them.

The architecture selected should match workload shape. Streaming video favors sustained data movement and buffering. A transactional database needs fine-grained synchronization, durable commit, and many concurrent small I/O operations. A control loop values bounded response time to sensor input. The same component may be “fast” under one workload and a bottleneck under another.

29. A responsibility matrix for system design

A matrix makes ownership explicit: the CPU executes instructions and configures work; memory supplies working storage and data buffers; persistent storage handles nonvolatile retention; and I/O controllers exchange commands or payloads with external endpoints. The processor and operating system jointly decide which process or driver may request a transfer, but the device controller determines protocol-specific execution and reports its status.

Avoid vague assignments such as “the bus saves the file” or “the interrupt copies the data.” The interconnect transports transactions; the storage device and software stack implement retention semantics; the interrupt signals that software should inspect some state. A diagram becomes operationally useful when every arrow names its payload, initiator, destination, and completion condition.

30. Design review questions

For every important system flow, ask: Who initiates it? What address space and permissions apply? What information moves, and through which fabric? Does CPU software copy bytes or does a controller perform DMA? What exactly counts as success? Are payload and notification ordered? Can another requester contend for the resource? Where can a failure be detected, and who recovers?

For timing-critical work, add an explicit latency budget by stage and a sustained throughput budget for shared resources. For security-sensitive work, record who owns every DMA buffer and what boundaries prevent a faulty endpoint from reading adjacent memory. For persistent data, record which event establishes durability. These questions turn a high-level four-box diagram into a testable system architecture.

31. Architectural misconceptions to avoid

A CPU does not store files by itself; it runs software that organizes storage commands. RAM is not a synonym for permanent storage, and a large RAM capacity is not a storage-capacity claim. DMA does not bypass all security or all software: it is an authorized mode of data movement, typically coordinated by a driver. Interrupts are not bulk-data channels: they notify. MMIO is not ordinary cached memory: register side effects and memory attributes matter.

A memory-coherent fabric does not abolish memory-order requirements, a faster link does not always reduce end-to-end latency, and a completed device command does not universally mean durable persistence. Finally, an integrated SoC still contains distinct logical roles even when the processor, memory controller, accelerator, and I/O blocks share one silicon die. Each misconception confuses a responsibility, implementation choice, or contract boundary.

32. Method for tracing a real system

Begin with a user-visible operation such as opening a document, recording a sensor sample, or sending a packet. Identify the application operation, operating-system boundary, responsible controller, data buffer, physical transport, and target endpoint. Then draw a second path for completion and errors. Annotate every transfer with its addressing and coherence requirements, and distinguish theoretical link capacity from observed service time.

Next, gather evidence: processor utilization and stall counters, memory bandwidth, queue depth, storage completion latency, device error records, and network counters as appropriate. Reconcile timestamps and avoid attributing coincident events to a causal fault without tracing the actual path. Changes to one subsystem should be tested across the entire operation, because moving a bottleneck does not necessarily improve application response time.

Worked Architectural Scenarios

The following are constructed educational examples. Numerical assumptions are hypothetical, with calculations rounded to sensible precision.

Example 1 — Opening a document

A 16 MiB file resides on an SSD. The application requests the file; the operating system finds its blocks; the storage controller transfers data to RAM; the processor parses its structure; the display subsystem renders it. A hypothetical sustained transfer rate of 800 MB/s gives 16 × 1,048,576 / 800,000,000 ≈ 21 ms of ideal bulk transfer time, excluding command latency, filesystem work, decompression, CPU parsing, and rendering. The ideal calculation cannot predict total file-open latency.

Example 2 — DMA buffer permission

A network adapter receives an 8 KiB packet into an approved device-visible buffer. The operating system establishes a DMA mapping, the device transfers the payload, and a completion entry identifies the result. A CPU virtual pointer alone is not a device address; the IOMMU may translate the device-visible address. The host must not consume the buffer until the applicable completion and synchronization rules are satisfied.

Example 3 — Coherent memory still needs ordering

Software writes a descriptor containing a payload address and length, then rings an MMIO doorbell. The design requires the descriptor to become available before the device observes the doorbell. On systems allowing relevant reordering, a device-specific memory barrier or publication primitive must precede signaling. Cache coherence alone does not establish this ordering.

Example 4 — Small I/O versus sequential I/O

Suppose an SSD can complete 100,000 independent 4 KiB requests per second in a controlled hypothetical workload. Payload throughput is 409,600,000 bytes/s, or about 410 MB/s. A sustained 2 GB/s sequential claim pertains to a different request mix. The device can show both results without contradiction because command overhead, concurrency, and media behavior differ.

Example 5 — Latency and concurrency

A fictional device averages 200 microseconds end-to-end per operation and sustains 50,000 operations per second. Little’s law gives 50,000 × 0.0002 = 10 average in-flight operations. This is a steady-state relationship, not an instruction to set queue depth exactly 10; latency variability and saturation change the optimum.

Example 6 — Memory bandwidth bottleneck

A CPU and an accelerator share an upstream 24 GB/s path. If both request sustained 16 GB/s simultaneously, their total offered load is 32 GB/s, greater than the path capacity. The workload cannot deliver both requested rates at once; arbitration, buffering, and application behavior determine the allocation and latency.

Example 7 — A storage command is not durable by default

A database writes a log record. The host submits a write; the device reports a command completion. If the implementation can complete writes into a volatile cache, application durability may require an additional documented flush or other ordering contract. A design review must identify the exact completion event that implies survival after power loss.

Example 8 — Microcontroller sensor sampling

A timer triggers 1,000 sensor conversions each second. Each 2-byte sample is transferred by peripheral DMA into a circular 2 KiB SRAM buffer. The raw sample data rate is 2,000 bytes/s; the buffer holds 1,024 samples, or about 1.024 seconds of data before overwrite if nothing drains it. The processor still must manage ownership and prevent unread samples from being overwritten.

Example 9 — Display scanout

A fictional display uses 1920 × 1080 pixels at 60 frames/s with 4 bytes per pixel. Uncompressed pixel read demand is 1920 × 1080 × 60 × 4 = 497,664,000 bytes/s, or about 498 MB/s. This is a simplified framebuffer-read estimate; it excludes compression, display timing overhead, composition, and any additional accesses made during rendering.

Example 10 — Remote storage placement

A virtual machine issues a read to its virtual disk. The host might back that device with a local file, an NVMe namespace, or network storage. The guest’s block command crosses virtual-device emulation, host scheduling, and possibly network transport before the payload returns. Recording only “disk latency” in the guest hides the distinct services and error boundaries.

Example 11 — Device reset and stale mappings

A device fails mid-transfer. The host records which descriptors were outstanding, stops new submissions, follows platform reset and quiescence rules, and reestablishes mappings and queue state if safe. It must not assume that a partial side-effecting write can be blindly repeated. The correct recovery policy is protocol- and device-dependent.

Example 12 — The busy CPU is not always the bottleneck

An application uses one CPU thread to prepare commands and waits for an SSD. CPU utilization may be low even while response time is high. Conversely, driver interrupt handling can saturate a core even when the physical link has unused bandwidth. A system-level diagnosis measures both controller service and software event-processing overhead.
