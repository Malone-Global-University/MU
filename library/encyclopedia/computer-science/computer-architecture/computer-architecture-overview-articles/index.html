Collection Overview

The Computer Architecture Overview unit is in the Computer Architecture division of the Computer Science volume of the MGU Encyclopedia. Its parent, Computer Architecture Overview, introduces the organization of processors, memory, storage and input/output; the execution of instructions; movement of data; competing design priorities; and the difference between architecture and microarchitecture. This unit develops the connections among those subjects without treating the parent page as a detailed technical specification.

Computer architecture is best studied at more than one level. An instruction-set interface defines capabilities visible to a software environment; a microarchitecture chooses how a processor realizes those capabilities; platform architecture coordinates processing, memory, I/O and supporting services. These meanings overlap, but they are not synonyms. A useful explanation must always specify which system boundary, workload and degree of observability are under examination. That discipline prevents the mistake of describing an ISA, a circuit block and a complete server as though they were interchangeable kinds of architecture.

This directory is the Level 4 unit index in the MGU hierarchy. Its linked pages are proposed Level 5 unit subarticles. Narrower companion articles may be commissioned from those Level 5 pages as needed, but this package creates none of them. The unit is intentionally integrative: it teaches readers how to combine decisions drawn from sibling units such as Instruction Set Architecture, Microarchitecture, Memory Hierarchy, Bus Systems, Pipeline Processing, and Parallel Architecture.

Editorial status: the published parent summary does not enumerate a fixed child-article list. Accordingly, the 20 titles and filenames below are a new, proposed editorial structure. Each destination is an active, extensionless public hyperlink for the future child page; none is claimed to be live or complete. This distinction makes the directory a production seed rather than an inventory of published specialist content.

Architectural Scope and System Organization

These five topics establish what computer architecture describes, where its boundaries lie, and how system functions connect. They are integrative guides to design choices, not replacements for the separate Computer Architecture, hardware-component, or formal-computation reference articles.

1. Architectural Abstractions and System Boundaries

Editorial focus: What belongs to architectural specification, platform organization, implementation, and physical integration. Develop a layered account of architecture, distinguishing the observable computing-system contract from choices of chip organization, board wiring, firmware, operating systems, and deployment. Explain how a single architectural term can refer to an ISA, memory organization, machine family, or whole platform, and require authors to state their abstraction level. Introduce examples where two implementations preserve software compatibility yet differ in cache size, out-of-order execution, interconnects, or power constraints. A useful result is a reproducible system boundary and a diagram of responsibilities, not an inventory of processor brands.

2. Processor, Memory, Storage, and I/O Roles

Editorial focus: Responsibilities and interactions of the principal computing subsystems. Explain why computation requires a coordinated relationship among processing engines, instruction and data memory, persistent storage, and external interfaces. Trace ordinary requests as architectural flows: input reaches working memory, software causes processor activity, results are retained or delivered elsewhere. Separate a subsystem’s logical responsibility from its physical location, since contemporary systems can combine multiple functions on a chip or distribute them across devices. Distinguish main-memory access from long-term storage and bulk data transfer from event notification. The subject is subsystem cooperation, not a full treatment of CPU internals, storage media, or driver software.

3. Stored-Program Organization and Machine State

Editorial focus: Stored instructions, persistent machine state, and the meaning of program execution. Explain how instructions and working data can be represented in addressable storage and operated on by a processor, while recognizing that a practical system also relies on registers, program counters, device state, and memory translation. Compare the classical stored-program concept with systems that have distinct instruction and data paths or specialized execution facilities. Trace a small program from an initial machine state to a later state without assuming that each instruction is one physical clock cycle. Keep the conceptual stored-program principle separate from historical claims that all modern machines employ an identical von Neumann implementation.

4. System-Level Datapaths, Control, and Communication

Editorial focus: How control decisions and information paths coordinate end-to-end work. Identify the difference between moving an operand, selecting an operation, issuing a request, and obtaining completion. Show how control and data pathways link the CPU, memory subsystem, accelerators and I/O, and how queues, permissions, synchronization and buffering affect the whole system. Use a schematic example to show a request flowing through multiple components without claiming a single universal bus or control unit. The emphasis is an architecture-wide dataflow view; detailed ALU wiring, pipeline forwarding circuits, PCIe packets, and network-on-chip arbitration belong to other specialist units.

5. Architectural Styles and Computing Application Domains

Editorial focus: System organizations chosen for general-purpose, embedded, mobile, and specialized needs. Compare broad architectural styles such as general-purpose server systems, small embedded controllers, mobile systems, data-intensive accelerators, and tightly constrained real-time devices. State the assumptions about programmability, latency, throughput, energy, cost, storage, peripherals and fault tolerance that shape each design. Explain why the best architecture depends on the workload and operating environment rather than on a universal metric of speed. Introduce the possibility of mixed systems—for example, a CPU plus accelerators and isolated controllers—without turning the article into a vendor product catalog or confusing deployment location with a distinct machine model.

Instruction Execution and Software Interfaces

These five topics trace the machine-visible contract and the system consequences of executing instructions. Each treats the interface among programmer-visible behavior, privilege, memory and I/O while reserving instruction encodings and processor implementation details for their dedicated units.

1. Instruction Set Interfaces and Programmer-Visible State

Editorial focus: The architectural contract seen by compiled code, machine tools, and system software. Survey registers, instruction effects, addressability, calling-convention dependencies, and architecturally defined state as interfaces between software and hardware. Contrast the software-visible ISA with physical execution machinery; the same ISA may be implemented by processors with markedly different microarchitectures. Discuss why backward compatibility, privilege levels and specified exceptions matter to applications and operating systems. Leave detailed instruction encodings, addressing-mode tables and ISA evolution to the dedicated Instruction Set Architecture unit. Focus here on which capabilities architecture must expose and which details are intentionally hidden from a programmer.

2. Instruction Lifecycles and Control Transfer

Editorial focus: Fetch, decode, execution, retirement, branches, and architectural progress. Introduce the logical sequence by which a stored instruction becomes a change in machine state, then distinguish it from overlapped, speculative or reordered hardware activity. Examine control transfers, procedure calls, interrupts and the difference between a completed instruction and a fully visible system effect. A worked instruction trace should include program-counter changes, operand availability and state updates without implying that every implementation uses identical pipeline stages. Advanced hazards, branch-prediction structures and reorder buffers remain in the Pipeline Processing and Microarchitecture units; this article owns the system-level explanation of the software-to-execution bridge.

3. Address Spaces and Architectural Memory Access

Editorial focus: Addressable locations, access attributes, translation, and memory-visible behavior. Explain what it means for an instruction or device to refer to an address and why virtual, physical and device-specific address spaces are not interchangeable. Examine address width, alignment, endianness, permissions, mappings and the relationship between memory access and I/O access. Use examples where identical numerical addresses can denote distinct locations in different address spaces. Distinguish architectural guarantees of memory access from implementation mechanisms such as TLB design, page-table formats, cache replacement and bus decoding. Readers should emerge able to ask who owns an address, which translation applies, and when a result becomes visible.

4. Exceptions, Interrupts, and Privilege Transitions

Editorial focus: Mechanisms that transfer control across events and protection levels. Describe synchronous exceptions, asynchronous interrupts, system calls, privilege transitions and the architectural state required for safe resumption. Compare a deliberate operating-system service request with a faulting memory access or a device-generated event. Discuss save/restore responsibilities, nesting, fault containment and the separation between architectural semantics and device routing details. Avoid equating an exception with a hardware failure or claiming all interrupt implementations have the same priority model. The goal is to connect instruction execution to operating-system protection and device behavior without replacing the individual operating-systems or interconnect articles.

5. Device Access and System-Level I/O Coordination

Editorial focus: How software-directed machines coordinate peripheral work and completion. Compare polling, interrupt-driven I/O, memory-mapped registers, direct memory access, buffered transfer and queued completion as architectural choices. Trace the lifecycle of a request from application or operating-system intention through a controller to a completed result. Explain the performance and safety consequences of address translation, concurrency, ownership changes and device permissions, keeping a clear distinction between I/O orchestration and the physical bus protocol. The neighboring Bus Systems and Device and I/O Management units provide specific hardware transactions and operating-system driver responsibilities, respectively.

Memory, Parallelism, and Specialized Systems

These five topics compare system organizations that govern movement, locality, concurrent execution and specialization. They emphasize workload and system-level interactions; the companion divisions on Memory Hierarchy, Parallel Architecture, and Bus Systems own their underlying mechanisms.

1. Memory-System Organization and Data Locality

Editorial focus: Hierarchy, locality, bandwidth, and latency as system-level design constraints. Show how registers, caches, main memory, persistent storage, and managed working sets interact with a program’s access patterns. Define temporal and spatial locality, working-set size, miss costs and bandwidth pressure as architectural concerns while acknowledging that caches and memory modules have distinct implementations. Compare sequential data access with irregular pointer chasing and explain why an increase in arithmetic throughput may not accelerate a memory-bound workload. Avoid detailed cache-coherence protocols, replacement algorithms or DRAM circuit design; those belong in Memory Hierarchy, Parallel Architecture and Hardware Systems. This unit’s task is connecting memory organization to workload outcomes.

2. Architectural Data Movement and Interconnect Topology

Editorial focus: System-level placement and transfer choices among components. Examine where data must move among CPUs, local memories, accelerators and peripherals, and how topology and transfer ownership constrain performance. Introduce shared paths, point-to-point links, chip-local fabrics, host-device transfers and nonuniform access without treating all of these as electrically equivalent buses. Explain that computing near data, batching transactions, and reducing copies may matter more than increasing peak arithmetic throughput. The dedicated Bus Systems unit owns address/control protocols, arbitration, and electrical or link-level details; this article owns the architectural question of whether a data-movement path is needed at all.

3. Multicore Organization and Shared-Memory Systems

Editorial focus: Machine-level consequences of several execution engines sharing resources. Explain the difference between multiple cores, multiple hardware threads, and multiple processors, and identify shared caches, memory controllers, I/O interfaces and power budgets as common bottlenecks. Survey concurrency, synchronization, memory visibility, workload partitioning and scalability at a system level. Use a simple speedup illustration to show why an eight-core machine does not automatically complete any workload eight times faster. Detailed coherence-protocol states, interconnect arbitration, instruction scheduling and parallel-programming APIs are neighboring specialties; this article establishes the questions a designer must answer when arranging several execution engines in one system.

4. Heterogeneous Processors and Domain-Specific Accelerators

Editorial focus: Coordination of CPUs with GPUs, NPUs, DSPs, and other specialized engines. Compare flexibility, parallel throughput, memory access, software tooling, data transfer and energy cost when choosing general-purpose or specialized compute engines. Distinguish a device’s peak arithmetic rating from end-to-end application speed, which includes movement, scheduling, preprocessing and result handling. Examine representative cases such as image inference, signal processing and database acceleration without presenting all accelerators as interchangeable. Explain host-device execution roles and the cost of moving workloads between compute domains. The article stays at system-integration level; GPU microarchitecture, neural-network algorithms and physical accelerator circuits remain separate subjects.

5. Embedded, Mobile, and Real-Time Architecture Requirements

Editorial focus: Architectural choices under timing, energy, size and environmental constraints. Analyze how real-time deadlines, deterministic response, finite memory, sensor interfaces, sleep states, physical size and service life can dominate design decisions in an embedded or mobile system. Contrast worst-case response requirements with average throughput and distinguish a hard deadline from a desirable low-latency goal. Present a controller-plus-application-processor architecture as one possible response to competing workloads. Avoid treating all embedded systems as resource-poor or all mobile devices as hard-real-time. Readers should learn to state environmental assumptions, fault consequences and power availability before choosing the processor, memory, isolation and I/O arrangement.

Architectural Evaluation, Trade-offs, and Assurance

These five topics make design decisions measurable and defensible. They distinguish modeling assumptions from benchmarks, specified capabilities from implementation, and architectural security or reliability objectives from evidence that any particular product meets them.

1. Architectural Performance Models and Bottleneck Diagnosis

Editorial focus: Quantitative models for compute, memory and communication limits. Develop the distinction among latency, throughput, utilization, service time, speedup and energy per unit of work. Introduce Amdahl’s law, workload fractions, memory bandwidth and arithmetic intensity as models whose results depend on assumptions. Work through examples in which optimizing one stage has a limited effect because another resource dominates. Show how a model guides an experiment rather than substitutes for it, including the need to measure input size, warm-up, contention and tail latencies. Detailed compiler optimization and processor counters belong to adjacent topics; this article owns architecture-wide hypothesis formation and bottleneck reasoning.

2. Power, Energy, Thermal, and Physical Cost Trade-offs

Editorial focus: Competing objectives in efficiency, cooling, area, cost and sustained performance. Compare instantaneous power, energy per task, thermal design, performance per watt, chip area and total platform cost rather than collapsing them into a single efficiency score. Explain how frequency, parallelism, memory traffic, leakage and cooling limits influence sustained output. Distinguish peak short-duration performance from continuous operation at thermal equilibrium. Include operating-environment differences: a battery-operated sensor, a handheld device and a rack server optimize for different constraints. Exact voltage-frequency curves, cooling hardware and power electronics belong to hardware units; this article develops the architectural trade space and the measurements needed to compare candidates fairly.

3. Reliability, Availability, and Fault-Tolerant Architecture

Editorial focus: System behavior during hardware errors, component failure and recovery. Define reliability, availability and serviceability as different objectives, then examine redundancy, error detection, isolation, recoverable state and graceful degradation. Contrast a detected memory error with a recoverable system response and distinguish fail-stop behavior from silent data corruption. Explain how fault domains, checkpointing and serviceability choices influence architecture without assuming that a redundant part eliminates all common-mode failures. Use mission-critical and ordinary consumer applications to show how acceptable risk changes the design. Error-correcting memory implementations, storage resilience and distributed replication have their own specialist articles; this topic supplies system-level assurance criteria.

4. Hardware Isolation and Architectural Security Boundaries

Editorial focus: Privilege, isolation and trust at processor, memory and peripheral boundaries. Examine how privilege levels, memory access control, device permissions, execution-state separation, trusted boot foundations and isolation domains shape a system’s security posture. Distinguish an architecture that provides a mechanism from evidence that firmware and software configure it correctly. Explain why DMA, shared caches and speculative behavior create system-level questions beyond conventional access checks, without treating every shared resource as automatically exploitable. Compare isolation objectives for multi-user servers, embedded devices and accelerator hosts. Detailed side-channel exploitation, cryptographic protocols and operating-system policy remain in neighboring Security Systems units; this subject owns the boundaries architecture makes possible.

5. Benchmarking, Design Space Exploration, and Architecture Selection

Editorial focus: Repeatable evaluation and decision records for architectural alternatives. Present a defensible selection process: specify workload, constraints, baseline, candidate architectures, representative inputs and acceptance criteria; then collect measurements under controlled conditions. Distinguish microbenchmarks from applications, arithmetic peak rates from achieved throughput, and an average result from latency distributions. Encourage sensitivity analysis to input sizes, energy budgets, concurrency and memory placement, plus checks for measurement bias and vendor-specific optimizations. The final deliverable should be a traceable decision record with alternatives and limitations, not a claim that one architecture is universally superior. It supplies a cross-unit framework for selecting design trade-offs.

Different architectural choices act at different levels and can coexist in a single machine. The following comparison is a set of decision lenses, not mutually exclusive commercial machine categories. In each case, architectural value depends on the workload and system boundary. A high-level specification alone cannot establish achieved timing, efficiency, or fault resistance.

Scope warning: “von Neumann” and “Harvard” describe distinctions about instruction and data paths; “RISC” and “CISC” describe broad instruction-set design traditions; “multicore” describes multiple execution engines; and “GPU acceleration” describes a specialization strategy. These concepts refer to different dimensions and should not be placed in one exclusive classification without qualifying the comparison. Hardware with the same ISA can have different physical organizations and different observed performance.

Illustrative Architecture Scenarios

Example 1 — Two processors execute the same software but perform differently

Two fictional processors support the same instruction-set interface and run an identical compiled workload. Processor A has greater arithmetic throughput; processor B has a more effective memory subsystem for this task. Suppose the program repeatedly traverses an irregular structure whose data largely misses the fastest caches. The limiting factor may be memory access latency or available bandwidth, so the observed winner cannot be inferred from the arithmetic rating alone. An investigation records input size, memory working set, locality, concurrency and clock or power conditions, then compares repeatable runtimes and relevant counters. Start with Instruction Set Interfaces and Programmer-Visible State, Memory-System Organization and Data Locality, Architectural Performance Models and Bottleneck Diagnosis and Benchmarking, Design Space Exploration, and Architecture Selection. This case demonstrates that software compatibility does not imply equal microarchitecture or equal application performance.

Example 2 — Adding cores to a partially serial workload

Consider a constructed computation whose execution time is 20% inherently serial and 80% ideally parallelizable, with parallel overhead omitted. Under Amdahl’s model, the ideal speedup using eight parallel workers is 1 ÷ (0.20 + 0.80 ÷ 8) ≈ 3.33×, not 8×. The model does not forecast real performance: contention, synchronization, uneven tasks, cache misses, scheduling and memory bandwidth may reduce measured speedup. The architect must first establish the workload fractions and whether scaling input size changes the assumptions. Compare Multicore Organization and Shared-Memory Systems, Architectural Performance Models and Bottleneck Diagnosis, and Benchmarking, Design Space Exploration, and Architecture Selection; use the sibling Parallel Architecture unit for specialized implementation methods.

Example 3 — An embedded vision system with an accelerator

A fictional camera device must analyze video locally under a fixed energy and thermal budget. A CPU-only design is simple to program but might miss the throughput goal; an accelerator could perform selected inference operations efficiently but would also require data transfers, scheduling, compatible software and memory allocations. A sensible architecture study measures frame latency from sensor capture to decision output, not just accelerator arithmetic speed. It also checks how the system behaves under thermal limits, software update failures, unexpected input sizes and device loss. Pair Architectural Styles and Computing Application Domains, Heterogeneous Processors and Domain-Specific Accelerators, Embedded, Mobile, and Real-Time Architecture Requirements, and Power, Energy, Thermal, and Physical Cost Trade-offs. The lesson is to optimize the end-to-end task subject to sustained operating constraints, not a single subsystem’s advertised peak.

Example 4 — A shared device creates a protection and recovery boundary

A multi-user system permits a peripheral to transfer data directly to memory. The design decision spans software permissions, memory translation, hardware-enforced access restrictions, completion notification and error recovery. A functioning DMA path is not evidence that every memory access is authorized, and a configured privilege boundary does not itself prove resistance to all attacks. The architecture team should state which component may access each address range, how configuration is verified, how faults are reported, and how the system recovers without exposing other users’ state. Begin with Exceptions, Interrupts, and Privilege Transitions, Device Access and System-Level I/O Coordination, Reliability, Availability, and Fault-Tolerant Architecture, and Hardware Isolation and Architectural Security Boundaries; read Bus Systems for the interconnect mechanics and Device and I/O Management for OS responsibilities.

All four scenarios are teaching constructions, not descriptions of deployed MGU equipment or measured product performance. Numerical assumptions, operating environments, fault models and excluded overheads are stated to prevent an illustrative calculation from being mistaken for a benchmark or engineering guarantee.

Architectural Decision and Investigation Framework

A reliable architecture comparison begins with a workload and acceptance criteria, not a favored component. Before selecting a machine organization, ask which interfaces must remain stable, which resources will dominate, and how evidence will be collected. Use the following questions to navigate to the appropriate planned specialist article and to neighboring completed references when greater implementation detail is required.

Recommended decision record: define the workload and input distribution; identify the target system boundary; write down compatibility, safety and performance requirements; list architectural options; predict the limiting resources; instrument a representative prototype; record energy, latency and throughput separately; document uncertainty and failure behavior; and explain which constraints drove the final choice. If a result depends on a specific benchmark version, device generation, input shape, or runtime configuration, record that dependence explicitly.

Suggested Study Pathways

Beginning students and independent readers: first read the Computer Architecture Overview, then Architectural Abstractions and System Boundaries, Processor, Memory, Storage, and I/O Roles, Stored-Program Organization and Machine State and Architectural Styles and Computing Application Domains. Follow with Von Neumann Architecture and Harvard Architecture to contrast historical organization principles. The outcome is a clear account of what a system architecture explains, which terms describe compatibility or organization, and why categories overlap.

Students of low-level programming and operating systems: follow Instruction Set Interfaces and Programmer-Visible State, Instruction Lifecycles and Control Transfer, Address Spaces and Architectural Memory Access, Exceptions, Interrupts, and Privilege Transitions and Device Access and System-Level I/O Coordination. Draw an execution trace involving a memory access and an I/O event, then identify which behavior is promised architecturally and which choice is left to the implementation. Continue into Instruction Set Architecture, Microarchitecture and System Calls when the investigation demands technical depth.

Hardware engineers and platform designers: read System-Level Datapaths, Control, and Communication, Memory-System Organization and Data Locality, Architectural Data Movement and Interconnect Topology, Multicore Organization and Shared-Memory Systems and Heterogeneous Processors and Domain-Specific Accelerators together. Compare the location of data, concurrency, interconnect topology, memory access and host–accelerator scheduling before selecting chips or board layouts. Continue into Bus Systems, Memory Hierarchy and Parallel Architecture for protocol, locality and parallel organization details.

Embedded, mobile and energy-constrained design teams: combine Embedded, Mobile, and Real-Time Architecture Requirements, Power, Energy, Thermal, and Physical Cost Trade-offs, Reliability, Availability, and Fault-Tolerant Architecture and Hardware Isolation and Architectural Security Boundaries. Define sustained throughput, deadline, environment, power and acceptable failure mode before comparing processors and accelerators. Use Power and Thermal Systems and Embedded Computing as adjacent sources, avoiding the assumption that lowest peak power always produces lowest energy per completed task.

Research, procurement and performance evaluation teams: use Architectural Performance Models and Bottleneck Diagnosis and Benchmarking, Design Space Exploration, and Architecture Selection to build an evidence plan, then return to Memory-System Organization and Data Locality, Multicore Organization and Shared-Memory Systems and Heterogeneous Processors and Domain-Specific Accelerators for hypothesis-driven tests. Require representative workloads, explicit units, controlled comparisons, measured tail latency where relevant, and a distinction between theoretical peak and sustained application results. A defensible procurement conclusion states what was measured, under which constraints, and what uncertainty or future scaling may change the ranking.
