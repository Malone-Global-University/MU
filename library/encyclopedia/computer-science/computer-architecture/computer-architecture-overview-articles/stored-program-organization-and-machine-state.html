1. Purpose, scope, and the stored-program idea

A stored-program computer represents executable instructions in an addressable form so that a processing mechanism can obtain an instruction, interpret its prescribed operation, and advance the computation. Program instructions and ordinary data may be kept in a common memory system, as in the familiar classical model, but the foundational idea is broader than a single wiring diagram. Modern machines have instruction caches, split first-level paths, firmware storage, translation hardware, and specialized accelerators. They can still support stored software whose behavior is defined by an instruction set.

The central question in this article is not how many transistors execute an instruction. It is what state a program begins with, what operation an instruction requests, and what observable state follows. A program becomes an ordered—or, with concurrency, appropriately constrained—series of state transformations. This approach explains execution consistently across simple microcontrollers, deeply pipelined CPUs, emulators, and virtual machines. It also prevents two common errors: assuming instructions execute in exactly one physical clock cycle and assuming every device has one undifferentiated memory.

2. Stored program versus fixed-function hardware

A fixed-function circuit realizes a designated behavior through connections and control logic. A stored-program processor selects among many behaviors according to encoded instructions. Those instructions can be changed without redesigning the processor’s entire logic, provided the new sequence uses operations the implementation supports. Stored-program control therefore separates a general execution mechanism from much of the algorithm represented in memory.

The boundary is not absolute. Firmware can configure fixed-function accelerators, graphics processors execute their own kernels, and microcode can help implement machine instructions. A system may contain both programmable and nonprogrammable subsystems. The architectural distinction concerns the interface being programmed, rather than whether any bit of state exists inside a device. A processor loading instructions from nonvolatile flash can be a stored-program system even if instruction fetch and ordinary data access use physically separate paths.

3. Instruction storage and addressable representation

A program is stored as an encoding of instructions—not as English commands. An instruction may contain an operation code and fields identifying registers, immediates, memory operations, or control-transfer targets. A binary encoding is meaningful only together with the instruction set architecture (ISA) and the execution environment’s rules. The same bytes may be instruction data for one ISA, invalid encodings for another, or noninstruction information when treated as ordinary data.

Instruction fetch operates through an address or equivalent control mechanism. The fetched bytes may come from a nearby instruction cache instead of a DRAM chip on every step. That optimization does not change the architectural meaning of the instruction. Actual instruction lengths, alignment rules, decode behavior, and valid execution modes depend on the architecture; a teaching diagram that assumes four-byte instructions is appropriate for a defined subset, not a universal property of CPUs.

4. Instruction length, alignment, and illegal encodings

Stored instructions are not universally fixed at the same length. Standard RV32I integer instruction encodings are 32 bits wide, but RISC-V configurations with compressed instructions can include 16-bit instructions. x86 instruction encodings have variable lengths. Instruction alignment requirements and legal encodings differ by execution mode, feature set, and architecture profile; a hypothetical table of consecutive four-byte instructions must identify the exact assumptions that make its PC arithmetic valid.

When the fetched bits do not describe a legal instruction under the current architecture and extensions, the machine may take an illegal-instruction trap rather than executing an arbitrary fallback operation. Similarly, a branch to an improperly aligned address can lead to defined fault behavior. A correct simulator should decode the intended instruction format and apply the corresponding legality rules before predicting any register or memory effects.

5. A precise definition of machine state

A useful abstract machine state may be written as S = (PC, R, M, P, C, D, ...): current program counter or instruction location (PC), architectural registers (R), accessible memory contents (M), privilege and protection state (P), control/status state (C), and any architecturally relevant device state (D). The ellipsis matters because different machines expose floating-point, vector, debug, translation, or system state. A specification determines which parts are visible and how they evolve.

A state component need not be equally observable to every program. An application cannot ordinarily read privileged control registers at will. An operating system can manage page tables and exception state that application code cannot. A debugger may inspect additional registers under authorization. The phrase persistent machine state here means the values that endure from one instruction transition to the next, not necessarily values that survive loss of electrical power. Registers and RAM are usually volatile, while storage durability is a distinct contract.

6. Architectural state and microarchitectural state

Architectural state is the state whose behavior is specified at the machine interface: committed register results, relevant memory effects, program control, and architecturally defined status. Microarchitectural state includes many implementation details used to realize that interface: pipeline latches, reorder-buffer entries, cache replacement metadata, branch-predictor tables, and physical register mappings. Two processors may expose nearly identical architectural state while implementing it with very different structures.

This distinction is especially important for modern out-of-order machines. An instruction can execute speculatively and modify temporary internal data without its result being committed to the architectural state. A mispredicted branch can cause those speculative results to be discarded. However, discarding architectural effects does not necessarily undo every cache or predictor effect; security analyses consider that separate issue. The program’s abstract execution is not a literal photograph of every transistor transition.

7. Instruction-set contract and execution environment

The ISA states how recognized instructions affect registers, addresses, control flow, exceptions, and other specified machine behavior. An execution environment additionally determines initial program state, supported memory regions, traps, services, and interfaces through which software runs. In RISC-V terminology, the execution environment interface (EEI) makes this distinction explicit. The operating system, firmware, runtime, and virtualization layer may all participate in supplying that environment.

A binary is not guaranteed to execute merely because two chips have the same nominal word width. Instruction encodings, required extensions, privilege model, endianness where relevant, calling conventions, operating-system services, and executable format matter. A correct system description therefore separates the instruction-level meaning of a sequence from the broader conditions under which that sequence can be loaded and run.

8. Program counter and the next instruction location

A program counter (PC), instruction pointer, or equivalent architected notion identifies the instruction being executed or the next instruction location under the ISA’s rules. Straight-line execution usually advances through adjacent instruction addresses, but branches, calls, returns, traps, and other transfers may choose different destinations. On a simple RV32I teaching machine with standard 32-bit instructions, ordinary sequential advancement is PC + 4 bytes.

A real processor may fetch ahead, predict a branch destination, and maintain several speculative fetch addresses. Those addresses are not all the same thing as the architectural instruction location at a defined point in program execution. For example, x86-64 uses RIP with variable-length instructions; the next sequential address cannot be computed by blindly adding four. An accurate trace starts with a named ISA and makes its instruction-length assumptions explicit.

9. General-purpose, special-purpose, and status registers

Registers provide small, quickly accessible pieces of architecturally defined state. Typical general-purpose registers hold values or addresses. Special-purpose registers can track instruction location, stack position, exception causes, translation configuration, or privilege. Some ISAs also define condition flags, floating-point status, SIMD/vector state, or control/status registers. Register names and side effects are specified by the architecture rather than inherited from a universal abstract CPU.

The base RISC-V RV32I model has 32 integer registers of 32 bits, with x0 hardwired to zero, and a program counter. Other architectures organize their programmer-visible state differently. Physical register renaming does not create additional architectural integer register names: it is an internal technique for maintaining multiple in-flight versions. When tracing software behavior, record architectural values unless studying the microarchitecture itself.

10. Condition flags, comparisons, and machine-dependent status

Some instruction sets provide condition-code registers containing status bits that arithmetic instructions may set and later branches may inspect. Other instruction sets use explicit integer-register comparisons in branch instructions. Neither arrangement is inherently required by the stored-program principle. A faithful machine-state trace must record flags only when the selected ISA defines them as architectural effects.

For example, a RISC-V beq operation compares two registers and chooses a target without consulting an x86-style EFLAGS register. On x86, arithmetic and comparison instructions may produce condition flags used by subsequent conditional branches. Mixing these two models leads to false dependencies and wrong branch results. In a cross-ISA comparison, name the source of each branch predicate, its update rules, and whether any flags are preserved across intervening operations.

11. Memory as an address-to-value relation

An abstract memory can be modeled as a mapping from addresses to values, usually bytes. An instruction reading address A receives a value subject to the machine’s protection, translation, alignment, and ordering rules. A store modifies the designated memory location or locations if the operation completes successfully. In a single-thread instructional trace, this can be represented as M[A] before and after the store. Real systems may have caches, buffers, and coherent copies between the instruction and physical memory chips.

Memory does not necessarily form one homogeneous region. Normal RAM, read-only firmware, reserved space, memory-mapped device registers, and inaccessible addresses may all occupy different portions of an address map. Some accesses cause exceptions or device side effects. A memory-model diagram should mark what kind of region is being referenced and who may access it, rather than assume that every numerical address selects ordinary writable RAM.

12. Pointers, objects, and memory representation

A program may treat a register value as a pointer to an object, but the hardware instruction typically sees an address expression and an access width. Object type, lifetime, and bounds are often enforced primarily by language rules, compiler transformations, runtime checks, or memory-protection systems rather than by every general-purpose load and store. A 32-bit value like 0x2000 has no inherent “pointer” property until interpreted under a program and addressing context.

This distinction matters during debugging and security review. A pointer can reference an unmapped page, an object that has been freed, or an MMIO register with side effects. Its numeric address alone does not establish permission, ownership, or type correctness. The architectural trace records the attempted memory operation and its permitted effects, while source-level diagnostics can supply additional object-level meaning.

13. Data values, widths, and interpretation

A bit pattern has no single meaning in isolation. The same 32-bit contents might represent an unsigned integer, a signed two’s-complement integer, a floating-point encoding, a pointer, or a sequence of characters. The instruction applied to the bits determines the architectural interpretation. For a 32-bit integer register, arithmetic may wrap according to ISA-defined rules; floating-point instructions instead follow their own format and rounding semantics.

Address width, register width, data-element size, and instruction-encoding length are separate properties. Calling a processor “64-bit” does not prove that every physical address has 64 meaningful bits, every instruction is eight bytes long, or every storage command transfers eight bytes. In machine-state tracing, specify value widths and any sign extension, zero extension, or truncation that affects a transition.

14. The instruction as a state transition

Formally, the step relation can be presented as S —instruction→ S′: given a valid instruction and its operands in the current state, the machine performs the specified effects and moves to a new state. A register arithmetic instruction might update one register and PC while leaving all other architectural registers unchanged. A load may update a register after reading memory. A store may update memory without changing a general-purpose destination register.

This is a semantic model, not a guarantee about physical timing. An instruction may take multiple cycles, generate memory operations, occupy several execution units, or require a trap. Concurrent systems may admit more than one valid ordering of externally visible memory operations. The state-transition model is therefore useful because it names what must be correct without committing to one internal circuit schedule.

15. Fetch, decode, execute, and architectural completion

The familiar fetch–decode–execute sequence is an introductory decomposition: obtain an instruction representation; determine its operation and operands; carry out its specified work. A fuller view adds operand access, memory interaction, result writeback, exception handling, and architecturally valid completion. The logical stages are not mandated physical pipeline stages. A deeply pipelined CPU can fetch several instructions while previous ones remain unresolved.

For an in-order interpreter, a compact trace might show one completed instruction per row. An out-of-order hardware CPU can issue younger independent instructions earlier, then retire results in an order that preserves its architectural contract. A memory-mapped write may require special ordering even after a related register operation finishes. Educational traces should say whether a row represents architectural completion, issue, execute, or a clock tick; confusing these levels produces inaccurate performance claims.

16. Arithmetic operations and destination registers

Suppose a hypothetical register instruction computes R3 ← R1 + R2. The operation reads current source register values, applies ISA-defined arithmetic, and produces a destination value. A trace can be checked by listing inputs, output, and unaffected state. On an actual RV32I machine, add x3,x1,x2 performs 32-bit integer addition with the prescribed modulo-2³² result. Whether the core uses one ALU, several ALUs, or a microcoded path is outside that instruction’s architectural meaning.

More complex instructions may set condition flags, read or write multiple registers, perform atomics, or modify floating-point status. Some instructions have no general-purpose destination. Correct tracing never assumes every operation writes a register, and it does not invent side effects missing from the ISA. The system-level role is to understand the specified transformation before studying any implementation-specific timing.

17. Signedness, overflow, and arithmetic state changes

Adding two register bit patterns can yield the same low-order result whether interpreted as signed or unsigned integers, while comparisons, division, and overflow handling can depend on interpretation. The machine instruction specifies what happens. In 32-bit modular arithmetic, 0xFFFFFFFF + 1 produces a low 32-bit sum of zero; another instruction set or operation may update condition flags or trap under particular conditions.

This illustrates why source-language arithmetic, ISA arithmetic, and hardware arithmetic cannot be collapsed into one vague category. High-level languages can impose undefined or checked-overflow behavior, whereas a specific machine instruction can prescribe a defined wraparound result. A worked trace should state operand width, instruction mnemonic, and the values written to registers or status. It should not infer a processor fault merely because a mathematical sum exceeds the signed range.

18. Loads and stores as explicit memory interactions

In a load/store architecture such as RV32I, arithmetic operates on registers, while explicit load and store instructions move values between registers and memory. lw x5,0(x4) reads a 32-bit word from the effective address in x4; sw x3,0(x4) writes the 32-bit value from x3 to the designated memory location. These descriptions assume aligned, permitted normal-memory accesses in the teaching example.

Loads can return values through caches or forwarding from an earlier store; stores may pass through buffers before becoming visible to other agents. The architectural rules still govern correctness. On systems where some operations can name memory operands directly, instruction behavior can encompass several internal memory actions. The abstraction “registers plus memory” is useful across architectures, but specific instruction formats and implicit memory operations vary.

19. Effective addresses, alignment, and access permissions

The address in a memory instruction often derives from one or more registers plus an immediate displacement. Alignment restrictions depend on access size, ISA, and environment. A four-byte load from address 0x2000 is naturally aligned to four bytes; a load from 0x2001 is not. Some environments permit certain unaligned operations, others trap, and some may emulate them with additional work. A trace should never silently assume a universal response to misalignment.

Even an aligned address can fail if it is unmapped, read-only, outside privilege permissions, or identifies a device register with different rules. Address translation may access page tables behind the scenes. The architectural outcome can be a completed load or store, or an exception, without requiring the programmer to see each page-table read as an explicit software instruction.

20. Sequential execution and control-flow changes

Straight-line code commonly moves the instruction location forward after each operation. Conditional branches select a different next instruction when a predicate is satisfied; unconditional jumps always select their target under the applicable rules. Calls and returns combine control transfer with a convention for remembering where to resume. A branch decision can depend on register comparison or condition flags depending on the ISA.

When evaluating a branch, first identify the state at the branch, then calculate its target using the architecture’s specified base address and displacement rule. Do not assume that every ISA interprets a branch offset relative to the same point. A branch predictor can speculatively fetch one path, but an eventual wrong prediction does not change which path the committed machine state must follow.

21. Subroutines, stack state, and calling conventions

A subroutine call is a structured control-flow change. Its return location might reside in a link register, on a stack, or elsewhere according to the machine and calling convention. A stack pointer is state used by software conventions and often by exception-handling code. Functions may preserve some registers and freely modify others, while local values and return metadata occupy designated storage.

These conventions are typically established by the application binary interface (ABI), not solely by the instruction encoding. Two binaries can use the same ISA but be incompatible if they disagree about calling conventions, object formats, runtime services, or stack organization. A machine-state analysis should distinguish hardware-required state changes, such as a specified jump-and-link operation, from software conventions governing which registers the caller expects to be preserved.

22. Code layout, data layout, and the executable image

A compiled program is usually packaged into sections or segments representing code, initialized data, zero-initialized data, metadata, and other information. A loader arranges these into an executable address space and initializes entry-point state. The details depend on executable format and platform. Program text is not automatically the same thing as the raw source-code characters written by a programmer; it is a machine-readable representation produced by the toolchain.

A linker can resolve references and perform relocations, while a loader may apply address-space layout choices and map shared libraries. The entry point tells the environment where execution begins, but the environment also has to establish stacks, arguments, memory mappings, and required runtime state. These are essential steps in practical stored-program operation and are separate from the elementary CPU fetch diagram.

23. Reset, firmware, and the first executable instruction

A processor does not begin its lifetime with a fully populated operating-system address space. Following reset or power-on, it enters an architecture- and platform-defined reset state and begins execution at an implementation-defined or specified reset vector or entry mechanism. Firmware may initialize clocks, memory controllers, trust settings, and devices before loading later software. The boot chain can include several programs, each transferring control to the next.

This makes initial state a first-class architectural question. A diagram that starts at “PC = first application instruction” omits how that state was established. An embedded microcontroller may execute directly from flash, whereas a server may traverse firmware and bootloader stages before an operating system runs. Neither pathway changes the principle that machine execution is governed by successive state transitions.

24. Virtual addresses and physical realization

An application often supplies a virtual address to a load or store. Address-translation machinery and operating-system page tables determine which permitted physical location it refers to. Translation can allow several processes to use similar virtual addresses while mapping them to different physical pages. Page faults may transfer control to a supervisor, which can supply a mapping, reject access, or take another platform-defined action.

For a correct trace, distinguish virtual address, translated physical address, and any device-visible I/O virtual address used by DMA hardware. A mapping’s existence does not imply the same permissions for reads, writes, and instruction fetch. Translation caches such as TLBs accelerate lookups but are generally not separate architecturally addressable memories that application code must read manually for every load.

25. Privilege levels and protected machine state

Modern architectures divide authority into execution levels or modes. Less-privileged code can request services through a controlled transition rather than directly modifying all registers and device mappings. Privileged state can include translation roots, trap vectors, interrupt controls, and protection configuration. A trap or system call transfers execution to an authorized handler under the architectural rules.

The same source-level arithmetic may run in different privilege modes, while an instruction that modifies page-table configuration may be valid only in privileged contexts. RISC-V has machine, supervisor, and user privilege concepts with implementation-dependent support and extensions; Arm and x86 organize corresponding protections differently. A machine-state record should note privilege and memory-access authority whenever those features can affect whether an instruction is permitted.

26. Traps and exceptions as state changes

An exception is a reported condition associated with executing an instruction, such as an illegal operation or certain address-access failures. Interrupts typically reflect external or asynchronous event notification, although their presentation and timing are architecture-specific. Taking a trap usually saves sufficient execution context, records the cause, and redirects control to a designated handler. That saved state permits an appropriate return or recovery action, subject to the event and environment.

For example, a RISC-V machine-mode trap can use mepc for the saved program-counter value and mcause for event information. That is a defined privileged interface, not evidence that all processors use those register names. A correct trace of a fault cannot simply advance the PC past an unsuccessful instruction and pretend the operation completed. It must follow the relevant exception and restart semantics.

27. Interrupt entry, return, and continuation

An interrupt can cause the processor to suspend ordinary instruction flow and run a handler. Software and hardware cooperate to preserve state needed for later continuation, handle the event, and restore an authorized execution context. Architectural details vary: some state is saved automatically, while other registers are saved by handler code or the operating system. Interrupts can be masked or prioritized and may be routed among cores.

An interrupt does not necessarily arrive after every instruction at a fixed deterministic instant. Delivery rules, interruptibility windows, priority, and pipeline state affect when software observes it. The conceptual trace should include a clean boundary between the interrupted architectural state and the handler’s state, without assuming the handler is an ordinary branch inside the same privilege context.

28. Operating-system context switches

A multitasking operating system can suspend one task and resume another by managing a saved execution context. The context commonly includes general-purpose registers, program location, stack state, and selected control state. Floating-point or vector state may be handled under architecture-specific policies. The operating system also associates the task with its virtual memory, credentials, and scheduling information.

Not every bit of internal processor state is saved. Branch predictor entries and caches may be reused or managed through isolation techniques without being part of a task’s logical register image. A resumed task must see the architectural values it was promised, not the exact predictor or cache contents present when it stopped. This is why instruction-set compatibility and context-switch correctness can survive major changes in physical core design.

29. One logical machine versus multiple concurrent agents

A sequential teaching machine has one evolving instruction stream, but multicore systems contain multiple execution agents with their own program counters and register states. They can share memory, communicate through queues, and receive interrupts independently. The global system state therefore combines multiple local states with shared resources and synchronization relationships; it is not generally a single globally agreed instruction-by-instruction timeline.

For shared-memory software, some results depend on atomics, fences, and the ISA’s memory model. Cache coherence helps agents see controlled versions of memory locations; it does not by itself dictate every permissible order of different memory operations. A useful system trace names which core performed each operation and distinguishes program order, visibility order, and explicit synchronization. The present article introduces that boundary rather than reproducing the dedicated Parallel Architecture treatment.

30. Memory consistency and the order of observation

The instruction order written by one programmer is not automatically the order in which every other core or device observes memory effects. An ISA's memory consistency model constrains permitted outcomes of concurrent accesses. An ordinary single-core trace with no interacting devices is useful for learning state transitions, but it is insufficient to reason about a lock-free queue or producer-consumer handoff between cores.

For example, producer code can place data in a buffer and then publish a ready flag. A consumer must not infer the buffer is ready using an unsynchronized flag access when the language and hardware permit reordering. Appropriate atomics or barriers establish the required publication relationship. This ordering layer is architecturally important yet different from the stored-program representation of the individual instructions.

31. Caches and the distinction between logical and physical storage

A load reads an architecturally defined memory value, even though the microarchitecture may satisfy it from an L1 cache, a shared cache, a store buffer, or main memory. Caches exploit locality and reduce average access cost; they do not cause the ISA to expose a new user-visible register for each cache line. Similarly, instruction fetch from an instruction cache still performs instruction fetch rather than a new category of program execution.

This abstraction has limits. Programs running concurrently must follow the memory model; instruction modification can require instruction-cache synchronization; and hardware fault behavior can depend on cache and memory reliability. But the teaching model should not multiply architectural machine states merely because a line has several physical copies. The relevant question is which value the ISA and memory system guarantee the instruction may observe.

32. Instruction fetch versus data access

The classic von Neumann picture often uses one common store for instructions and data. Yet modern designs commonly distinguish instruction fetch from data loads and stores in their first-level caches and pipelines. Fetch may be subject to execute permission, branch prediction, and instruction-specific caching, while loads and stores follow data-access permissions and memory ordering. Both can ultimately reach a shared memory system.

The logical separation matters when analyzing contention and security. A modified-Harvard CPU may have independent L1 instruction and data caches while retaining an ordinary unified process address space. A strict Harvard microcontroller may use distinct program and data address spaces and specialized operations to read stored program constants. Neither case requires abandoning the broader principle that instructions reside in storage and direct computation.

33. Harvard and modified-Harvard variants

In a strict Harvard organization, instruction and data memories or interfaces are distinct in a way that may permit simultaneous operations and different widths or technologies. The implementation may not allow an ordinary data load to read program memory. Modified-Harvard designs can separate cache paths near the core while unifying them at later levels. Some systems expose multiple address spaces in the ISA, while others make the distinction only in hardware.

A comparison should specify the layer being discussed: architectural address spaces, on-chip cache paths, external memory interfaces, or physical devices. Saying simply “Harvard is faster” or “von Neumann is slower” ignores workload, topology, cache locality, width, and timing. The stored-program model does not impose one specific arrangement on every contemporary computer.

34. Self-modifying code and instruction visibility

Since instruction encodings can be represented in storage, software may sometimes generate or modify code bytes. But writing new bytes does not universally guarantee that future instruction fetches immediately use them. Instruction and data caches, pipeline prefetch, coherence rules, memory permissions, and cross-core synchronization determine when the new instruction stream becomes visible. Many systems intentionally restrict write and execute permissions to reduce exploitation risk.

RISC-V defines instruction-fetch synchronization mechanisms such as FENCE.I in the applicable extension, and other architectures provide their own cache-maintenance and synchronization procedures. On multicore systems, coordinating other execution agents can require additional steps. The architectural lesson is that the ability to store an instruction as data does not remove the distinction between data writes and instruction-fetch visibility.

35. Microcode and the difference between two stored programs

Some processors use microcode or microprogrammed control to implement selected machine instructions or exceptional cases. This is not the same program as the application instruction stream. An application sees the published ISA, while microcode operates as an implementation technique below that interface. It may be stored in internal ROM or controlled storage and may coexist with hardwired fast paths.

The existence of microcode does not mean every machine instruction decodes into one fixed number of internal operations, or that every processor can accept user-written microcode. A designer can build an equivalent architectural behavior with hardwired logic, microcoded sequences, or hybrids. Two levels of programmability can coexist without merging their machine states or privilege boundaries.

36. Pipelines, speculative execution, and retirement

Physical instruction execution is frequently overlapped. One instruction may be decoding while another uses an arithmetic unit and an older one awaits a memory response. A superscalar core can accept multiple operations per cycle; an out-of-order core can execute a younger ready operation before an older blocked load. The number of architecturally completed instructions therefore cannot be equated to the number of clock cycles, and PC advancement does not reflect every speculative fetch.

In precise-retirement designs, speculative work is committed only when allowed by the architectural ordering and exception rules. A misprediction or fault can squash work and redirect fetch. This protects the observable machine-state contract while allowing internal concurrency. Specialized articles on pipeline processing and microarchitecture analyze the mechanisms; this article uses them to explain why the abstract stored-program trace and the hardware timeline are different descriptions of the same supported software behavior.

37. Device registers and side effects

A device can be controlled through memory-mapped input/output or another architected interface. A store to a control register may start a transfer or acknowledge an event, rather than simply placing a value into an ordinary RAM cell. A read might consume an input datum or clear a status flag. Device state is part of the whole system state, but its permissible transitions are usually defined by a device specification rather than the processor ISA alone.

For example, writing a network device doorbell may announce a descriptor ring that software has prepared in memory. The device can then fetch those descriptors using DMA. The processor instruction that writes the doorbell is only one step in an asynchronous operation whose subsequent effects depend on separate bus, DMA, and ordering contracts. A trace that treats the doorbell as an inert variable assignment can be profoundly wrong.

38. State outside CPU registers: timers and autonomous devices

Whole-system execution can evolve even when the main CPU is not retiring application instructions. Timers increment or fire, network controllers receive packets, storage devices complete commands, and DMA engines move data. These activities can change device and memory state and create pending interrupt conditions. Modeling only the CPU PC and general registers is therefore sufficient for some instruction exercises but incomplete for asynchronous system behavior.

A system-level model can include a set of events in addition to instruction steps. Each event has an initiator, its own legal state transitions, and an ordering relationship to other events. The method helps explain why an interrupt can become pending while software runs and why a device may finish a transfer between two software observations. Avoid inventing a precise order where the platform leaves timing nondeterministic.

39. Volatile working state versus durable storage

Registers, cache contents, and ordinary DRAM typically do not survive normal power loss. A program can store a variable in RAM, but that change is not the same as writing a durable file. SSDs, flash, and other nonvolatile devices preserve selected information under their own persistence guarantees. The term stored-program describes how executable instructions are represented and obtained, not a guarantee that the entire machine state is permanently stored.

Crash recovery may use persistent logs, checkpoints, nonvolatile storage barriers, or replicated state. Those are additional software and storage contracts. A powered-down application generally restarts from loaded code and restored data, not from the exact RAM and register state it possessed at the instant power failed. Some specialized systems use retention or nonvolatile memory techniques, but those require explicit specifications.

40. Accelerators and multiple stored-program domains

An accelerator such as a GPU or DSP may execute a distinct program or command stream while the host processor coordinates work. The accelerator may have its own instruction memory, registers, execution context, and access rules. A host application can submit commands, arrange buffers, and wait for completion, but the host PC does not simply advance through every accelerator instruction as though they ran on the same core.

When describing the combined system state, separate each execution agent's local state from shared buffers and synchronization objects. Some accelerator tasks are programmable kernels; others are fixed-function operations configured through registers. The stored-program principle therefore applies at particular execution boundaries and should not be stretched to assert that every active engine runs one universal ISA.

41. Virtual machines and emulated architectural state

A virtual machine monitor can provide a guest with a set of virtual CPUs and memory mappings. Guest software executes according to a presented architecture, while hardware virtualization and host software manage or emulate privileged events. Guest program counters and registers are meaningful architectural states even when the underlying physical scheduling is interrupted or redirected by a hypervisor.

An instruction-set emulator can instead interpret or translate guest instructions on a processor with a different ISA. It must reproduce the guest's required observable behavior, not its original number of hardware pipeline stages. This is a strong demonstration of the distinction between the stored instruction program and the mechanism realizing its semantics. Peripheral and timing behavior can remain platform-dependent and must be modeled separately where software relies on it.

42. Reliability, faults, and recoverable transitions

A state-transition trace is valid only if its assumptions about instruction execution and memory hold. Hardware errors can produce a detected memory fault, bus error, machine check, or other platform-defined event. An ECC correction may be invisible to ordinary code; an uncorrectable error may terminate a task or compromise further execution. Recovery requires knowing what effects already became visible and which state remains trustworthy.

Architectural exception mechanisms organize many recoverable software-detected failures. They do not promise that every physical fault is recoverable or that all device effects can be rolled back. A storage operation started before a crash might still have external side effects. A fault-aware machine model therefore records error status and completion boundaries rather than treating all unsuccessful operations as no-ops.

43. Performance costs without changing program meaning

Two processors executing the same ISA program can require very different elapsed times. Clock frequency, instruction throughput, cache misses, branch behavior, translation costs, and device latency all matter. An instruction-count trace alone is insufficient for a timing estimate: execution time ≈ instruction count × average cycles per retired instruction ÷ cycles per second only when units and measurement conditions are well-defined. Average CPI may vary with workload and effective frequency.

A five-instruction loop that fits entirely in cache might run quickly, while another small program suffers memory stalls or page faults. A faster frequency does not guarantee a faster application if CPI rises or external I/O dominates. The stored-program model establishes program behavior; performance models establish the cost of realizing that behavior on a particular machine.

44. Security: execution permissions and trust boundaries

Treating instructions as stored bits creates an important security question: who is allowed to supply or modify bytes that will be executed? Modern systems often distinguish read, write, and execute permissions. A writable data buffer need not be executable, and a program-code mapping need not be writable. Privilege levels, secure boot, signed code policies, and memory protection can constrain where executable state originates.

These mechanisms are not identical. A memory page permission restricts an access; verified boot can establish trust in early software; control-flow integrity limits certain kinds of transfers; and isolation prevents one principal from rewriting another's program. Speculative side channels can still matter even when architectural permissions work as designed. The architectural boundary is the authorized evolution of executable code and protected state.

45. Debugging a machine-state transition

A debugger can single-step instructions, inspect architectural registers, examine permitted memory, and follow control flow. A useful debugging record names the current PC, decoded instruction, operand values, resulting register or memory changes, and any exception or device event. Breakpoints and instrumentation may perturb timing, so a debug trace is evidence of architectural behavior under those conditions rather than a perfect measurement of uninstrumented execution.

To find an incorrect result, compare the trace with the ISA's instruction semantics. If the expected destination register remains unchanged, check source values, instruction encoding, privilege, branch path, and exception status before blaming ALU hardware. If a memory read differs, inspect address calculation, translation, byte ordering, and concurrent writes. These steps establish whether the error is in the program, platform configuration, or implementation.

46. Formal reasoning and executable specifications

Instruction-level specifications can be written as state-transition rules. A formal model can enumerate valid next states, express invariants, and compare an implementation against architecturally allowed behaviors. A simple sequential machine might have one next state per ordinary instruction, while concurrent memory models admit sets of legal executions. The formal approach is particularly useful for distinguishing guaranteed behavior from unspecified implementation choices.

Reference emulators, architectural simulators, and ISA test suites provide complementary evidence. A simulator can reproduce functional outputs without simulating every transistor or cycle. A cycle-accurate microarchitectural model answers a different question about timing and resource use. Tests should say which contract they intend to validate—functional semantics, instruction-set conformance, memory ordering, exception precision, or device completion.

47. What a trace can prove—and what it cannot

A trace built from a specified initial state and ISA semantics can prove that a particular sequence of architectural state changes is valid under its stated assumptions. It can demonstrate an arithmetic result, branch decision, memory update, or exception-handling path. It cannot, by itself, prove the processor’s energy consumption, cycle count, cache hit rate, DRAM wiring, or behavior under unmodeled concurrent inputs.

This limitation is productive. It separates functional correctness from implementation performance and from whole-system reliability. When testing a machine, begin with architectural conformance; then use performance counters and controlled benchmarks to analyze timing; then use fault injection and protocol verification to examine recovery. A stored-program explanation becomes more rigorous when it states exactly which level of behavior its trace represents.

48. Historical context and attribution limits

Stored-program computing emerged through overlapping theoretical proposals and engineering projects. The term von Neumann architecture is commonly associated with a classical stored-program organization, but the historical development involved many contributors and several machine designs. A modern architecture comparison should not flatten this history into a claim that one person invented every component of the stored-program computer.

Nor should the term be treated as a single mandatory machine specification. Modern computing combines instruction/data caches, out-of-order execution, multiple cores, dedicated DMA engines, and complex operating-system services. The stored-program principle remains fundamental precisely because it captures a durable abstraction while allowing these varied implementations.

49. Design and investigation checklist

Before claiming a system follows a particular stored-program model, identify: the ISA and privilege mode; how instructions are encoded and fetched; the initial PC; the architecturally relevant registers; memory addressing and permissions; the branch and trap rules; the role of caches and translation; and any devices with observable side effects. Mark which claims come from an ISA specification, a platform manual, or an implementation description.

For a worked program, state the initial values, show each completed instruction, update every changed state field, and explain the branch target. If the program interacts with another core or device, add ordering and synchronization assumptions. If asked for performance, record measured or assumed cycles separately. If asked about persistence, identify the storage contract rather than inferring it from an ordinary RAM store.

50. Common misconceptions and corrections

“One instruction equals one cycle” is false as a general rule: instruction semantics and physical timing are distinct. “The PC always moves forward by four” holds only for certain instruction sequences and encodings. “Code and data must share one wire” is not entailed by stored-program computing. “Writing code bytes changes the next instruction immediately” can fail when instruction-fetch synchronization is required. “All state is persistent” confuses a value surviving from one program step to the next with power-loss durability.

Additional misconceptions include treating caches as separate programmer-visible registers, assuming every virtual address identifies the same physical memory for every process, ignoring traps that prevent ordinary completion, and treating external device commands like inert RAM stores. The corrective method is consistent: specify the architectural contract, declare the relevant system boundary, and distinguish ordinary state transitions from implementation details.

51. Synthesis: one program, many implementations

The enduring insight of stored-program architecture is that a sequence of encoded instructions can determine computation without fixing every detail of a physical machine. The instruction set describes permitted state transitions; the execution environment supplies initial conditions and services; memory and devices provide addresses and side effects; privileged software coordinates protection and continuation. Each layer adds rules rather than replacing the others.

This gives a disciplined approach to architecture: model the observable state first, trace the legal transitions, and then analyze the pipelines, caches, fabrics, accelerators, and power management that implement them. The result is a faithful system-level explanation that applies to simple educational machines and modern platforms without confusing conceptual principles with a single historical hardware layout.

Worked Examples and Boundary Tests

The following examples are constructed teaching scenarios. They do not claim to measure any particular commercial processor or live MGU machine. Assume specified ISA semantics and memory attributes wherever a precise result is shown.

Example 1 — Instruction bytes are not source text

A source statement total = a + b is compiled into one or more machine instructions according to the selected ISA, compiler, optimization, and calling convention. An RV32I arithmetic instruction might use add x3,x1,x2, whose encoding is a 32-bit value. Its physical byte order in memory is determined by applicable instruction-encoding conventions. If the same four bytes are loaded as ordinary data, they are still bit patterns; only an instruction-fetch and decode context makes them a candidate instruction. A change in the compiler or target ISA can alter the bytes while preserving the source-level mathematical result.

Example 2 — Two states, one arithmetic step

Start with x1=9, x2=4, and x3=0. Executing sub x3,x1,x2 on an RV32I-style educational machine yields x3=5. If the instruction lies at 0x1400 and has the standard 4-byte length, its sequential successor is 0x1404. The state comparison records the changed register and PC; other architectural registers and ordinary memory remain unchanged. The trace is an architectural result, not a claim that the subtraction consumed exactly one clock cycle.

Example 3 — A short stored-program execution trace

Assume a simple RV32I environment with aligned, writable RAM at address 0x2000, no exceptions, x4 initially containing 0x2000, all other listed registers initially zero, and standard 32-bit instructions at 0x1000 onward. The program creates values 5 and 7, adds them, stores 12, reads it back, and takes a conditional branch. The instruction at 0x1018 does not execute; the branch reaches 0x101C, where x6 becomes 2. The accompanying trace table lists the state after each architecturally completed instruction.

Example 4 — A branch displacement is not universal

With a standard four-byte instruction at 0x1014, the illustrative RISC-V beq x5,x3,8 targets 0x101C when the comparison is true. An incorrect method that first advances the PC to 0x1018 and then adds 8 would report 0x1020. Other architectures use different branch bases and encodings, so the correct formula must come from the ISA. A hardware predictor may speculate on the wrong path, but the architectural transition still resolves to the branch-defined target.

Example 5 — Effective-address calculation

Suppose x4=0x2000 and an instruction accesses 12(x4) for four bytes. The effective address is 0x200C, which is divisible by four. If the mapped location contains the little-endian bytes 78 56 34 12 and the selected load interprets them as a 32-bit word, the numeric value is 0x12345678. This calculation assumes a little-endian data memory and a permitted aligned access. Changing the address, byte order, access size, or page permissions changes the interpretation or the result.

Example 6 — A prohibited memory write

A program attempts a store to a mapped page that permits reads and instruction fetches but disallows writes. The instruction can be perfectly well encoded and its effective address can be aligned; the write still must not silently succeed. The system instead follows its specified protection-fault behavior, transferring execution to a handler or terminating the task. For a trace, record the fault and the resulting control state. Do not put the intended new bytes into memory as though the store had committed.

Example 7 — Program loading is not program execution

A loader maps an executable segment and prepares an initial stack, but these actions are performed by privileged software and platform mechanisms before the application begins its entry-point instructions. Consider an application whose entry point is virtual address 0x400000: setting its initial PC to that address is a prerequisite for its first instruction, not the outcome of executing that instruction. The loader may also initialize zero-filled memory and library mappings. The loaded image and the live machine state are related but distinct objects.

Example 8 — A trap changes where execution continues

A RISC-V hart executes an instruction that triggers a trap under its current environment. Depending on the configured trap delegation and handler, privileged state records the saved instruction location and cause, and control transfers to the appropriate trap-vector address. A handler may fix a mapping and return to retry an instruction, or may report failure. The precise saved PC and return path depend on trap kind and architectural rules. The important trace change is not only a new PC but a new privilege and exception context.

Example 9 — Context switching between two tasks

Task A is paused with a logical PC of 0x2000 and general registers holding its work. Task B is resumed with a different PC and register image, even though both tasks may run on the same physical core. The operating system saves and restores architecturally required context and selects the appropriate address-space configuration. The core does not need to copy the entire instruction cache or branch-predictor history into each task's saved register frame for ordinary semantic correctness. The two tasks can share CPU time without sharing their logical register values.

Example 10 — Unified memory with split first-level caches

A processor fetches instruction bytes through an L1 instruction cache and loads data through an L1 data cache. Both may ultimately refer to the same external DRAM, and an operating system may present one virtual address space. This is often described as modified-Harvard near the core, even though application programs can follow a stored-program model. If a runtime writes executable bytes, it may need an architecture-specific instruction-cache synchronization procedure. Neither cache layout nor the required maintenance operation can be inferred solely from the phrase “stored-program CPU.”

Example 11 — The mistaken one-instruction-one-cycle claim

An instructional loop consists of 2,000,000 retired instructions. Under an assumed average CPI of 1.8 and an effective clock frequency of 3,000,000,000 cycles per second, compute estimated CPU time as 2,000,000 × 1.8 / 3,000,000,000 = 0.0012 s, or 1.2 ms. This is a workload-level estimate, not a universal CPU rate. It does not include unrelated I/O waiting and should not be derived from the small seven-instruction trace without a justified CPI measurement.

Example 12 — A two-core communication mistake

Core A writes a payload and publishes a flag, while Core B waits for the flag before reading the payload. If the code lacks the required synchronization, an implementation may allow an observation that surprises a programmer who imagined a single universal instruction order. To reason correctly, specify the language-level atomics and the hardware memory model, then show the release/acquire or equivalent ordering relation. Multiple core PCs and registers mean the system no longer has one simple linear stream of architectural instructions.

Example 13 — A memory-mapped device command

A driver prepares a DMA descriptor in ordinary memory, then writes a memory-mapped register to notify a device. That register write may have external effects: the device reads descriptors and begins transferring data. A separate completion queue or interrupt may report finishing. The driver needs the applicable memory-ordering and ownership protocol, so an abstract state trace must include device-side state transitions. Treating the doorbell as an inert RAM location would omit the action that matters.

Example 14 — Stored instructions are not necessarily durable state

A program stores the integer 42 into ordinary DRAM and then the computer loses power. The value was part of machine state while powered, but there is generally no guarantee it will reappear in RAM after restart. In contrast, a completed persistent-storage operation subject to the device and software durability contract may retain selected bytes. The stored-program concept does not make every register or RAM store nonvolatile; the storage layer defines which information can survive power loss.

Example 15 — Binary compatibility without hardware identity

Two processors both implement the same required ISA subset and support the same execution environment. They can execute a given compatible binary while differing in clock frequency, cache hierarchy, pipeline depth, memory controller, and physical register organization. If the program relies on unspecified timing or a missing optional extension, however, it may not behave as intended. Compatibility is therefore a claim about defined architectural and environment features, not proof of equal performance or identical silicon.

Example 16 — Testing a branch recovery event

An out-of-order processor predicts a branch incorrectly and begins executing a younger path. Hardware may transiently access caches and write speculative physical registers, then squash the wrong-path instructions. The correctness check is that the retired architectural register, memory, and control state match the specified taken or not-taken path, with precise exceptions as required. A separate security test considers whether transient microarchitectural effects remain observable. Functional rollback and elimination of every timing side effect are not interchangeable claims.
