Collection Overview

The Parallel Architecture unit belongs to the Computer Architecture division of the Computer Science volume of the MGU Encyclopedia. It extends the existing Parallel Architecture overview, which introduces forms of simultaneous execution, multicore processors, vector and GPU approaches, software parallelism, distributed systems, and practical scaling limits.

Parallel architecture asks how multiple execution resources can be organized, connected, supplied with data, coordinated and evaluated. Parallel work may exist inside a core, across cores, among accelerators, between memory domains, or among networked machines. Systems often combine several forms at once: a multicore CPU can issue vector instructions while a GPU executes a separate kernel and multiple compute nodes exchange results. Hardware capacity does not by itself establish the amount of speedup an application can achieve.

Parallelism is not synonymous with concurrency, throughput, or faster single-task response. Two tasks can be concurrent without running at the same instant; greater capacity may increase throughput while leaving one request's critical path unchanged. Likewise, many cores can be slowed by data dependencies, memory bandwidth, communication, synchronization, poor locality or unbalanced work. This unit connects machine organization to those limiting factors rather than presenting a single processor family as universally optimal.

Within the MGU taxonomy, this page is a Level 4 unit index. Linked pages are planned Level 5 unit subarticles; narrower companion articles may be commissioned beneath individual Level 5 subjects when needed. The four subject groups are editorial headings inside one directory, not additional physical hierarchy levels. Parent summaries and Level 5 children are produced in other threads.

Editorial provenance: the existing Parallel Architecture overview does not enumerate a prescribed child list. Parallelism Models and Processor Organization

The first five articles establish the architectural vocabulary needed to describe parallel resources without conflating instruction overlap, processor multiplicity, vector lanes, hardware threads or overall system capacity. Each should include explicit assumptions and a nonexample so its classification cannot be mistaken for a promise of performance.

1. Levels of Parallelism and Granularity

Research and instructional scope: Define the unit of work and degree of independence at each level: overlapping instructions, vector lanes, simultaneous threads, concurrent tasks, processor cores and cooperating nodes. Show that parallelism can be nested and that not every concurrent process runs simultaneously. Compare fine-grained and coarse-grained tasks, work decomposition, startup cost, and dependence constraints. Introduce hardware capacity versus exploitable application parallelism and distinguish latency reduction from throughput increase.

Editorial boundary: Do not restate the internal fetch, issue and retirement machinery covered by Microarchitecture. This child owns the organization and identification of architectural parallelism rather than an operating-system threading tutorial.

Expected specialist treatment: Annotate one image-processing workload with instruction, vector, core and system parallelism, plus one sequential dependency.

2. Flynn Taxonomy, SIMD, MIMD, and Classification Limits

Research and instructional scope: Explain SISD, SIMD, MISD and MIMD as conceptual classes, with careful treatment of rare and disputed practical MISD examples. Relate vector engines, independent processor cores and hybrid systems to these labels. Distinguish taxonomic stream count from shared-memory topology, instruction-set extension, physical processor count and programming model. Discuss why a modern GPU or CPU may contain structures describable at multiple levels instead of fitting one exclusive category.

Editorial boundary: The taxonomy is an interpretive model, not a vendor certification or proof that one architecture is faster. Binary instruction formats remain the ISA unit; GPU hardware internals and workloads can be linked to their separate established units.

Expected specialist treatment: Classify five conceptual processors and explain an ambiguous heterogeneous CPU–GPU system.

3. Multicore and Manycore Processor Organization

Research and instructional scope: Describe cores, clusters, chiplets, shared last-level caches, memory controllers and system-on-chip fabrics. Distinguish core count from hardware-thread count and logical-processor exposure. Discuss performance and energy trade-offs when choosing a small number of powerful cores versus many simpler throughput-oriented cores. Include practical consequences of shared cache, memory-bandwidth, coherence and thermal budgets without inventing a universal cutoff between multicore and manycore.

Editorial boundary: Per-core pipeline design belongs to Microarchitecture. Physical package assembly belongs to CPU and hardware units. Here the specialist emphasis is the topology of multiple processing elements and shared architectural constraints.

Expected specialist treatment: Compare a four-core latency-oriented layout with a manycore throughput layout using a stated task mix.

4. Symmetric and Asymmetric Multiprocessing

Research and instructional scope: Define symmetric multiprocessing in terms of peer processors sharing an operating environment, while recognizing that shared-memory hardware can contain nonuniform resource distances. Contrast asymmetric designs with specialized or explicitly designated processing roles. Explain heterogeneous-performance clusters, processor affinity, capability discovery and compatibility questions. Avoid equating asymmetry with a particular vendor product or asserting that heterogeneous cores necessarily run disjoint instruction sets.

Editorial boundary: Operating-system scheduling policy belongs to Processes and Threads. This article focuses on architectural processor roles, accessibility, shared services and the implications of differing execution resources.

Expected specialist treatment: Map a hypothetical mixed-performance processor and evaluate two workload-placement policies.

5. Vector and SIMD Parallel Execution Architecture

Research and instructional scope: Study vector-length concepts, fixed and scalable vector designs, lane utilization, masks, reductions, gather/scatter access, and memory-alignment effects. Distinguish a vector instruction model from a specific implementation of physical execution lanes and from independently scheduled MIMD cores. Explain why conditional divergence, strided access and arithmetic intensity can reduce effective throughput; treat vector width as a capacity constraint rather than an unconditional speedup multiplier.

Editorial boundary: Detailed opcode encoding stays in Instruction Set Architecture. GPU warp scheduling belongs to the GPU-oriented child below. Keep this subject on how data-parallel machines are organized and supplied with operands.

Expected specialist treatment: Estimate active-lane utilization for masked data and compare contiguous with strided memory access.

Execution Engines and System Topologies

The second group compares execution engines and system arrangements. The reader should be able to draw the processors, data stores, communication paths and shared resources before predicting performance. Hardware generation and capability matter; no one GPU, CPU or cluster represents all implementations.

1. GPU SIMT, Warps, and Throughput Architecture

Research and instructional scope: Explain how SIMT-style hardware groups logical threads for issue and execution, how divergence may serialize paths, and why occupancy is influenced by registers, shared memory, active groups and architectural limits. Distinguish execution groups from general-purpose CPU hardware threads and from the SIMD classification. Discuss coalesced memory access, host–device transfer costs and when GPUs are a poor fit for short, dependent or control-heavy tasks.

Editorial boundary: Do not claim identical warp size, branch reconvergence behavior or cache layout across GPU vendors or generations. Graphics Processing Unit owns the broader hardware overview; this child specializes in parallel execution organization.

Expected specialist treatment: Trace two divergent execution groups and a transfer-bound compute kernel using a version-agnostic example.

2. Hardware Threading and Core Resource Sharing

Research and instructional scope: Differentiate coarse-grained and fine-grained multithreading, simultaneous multithreading, and multiple independent cores. Explain why exposing two logical threads does not double arithmetic units or cache capacity. Discuss latency hiding, fairness, sibling-thread interference, cache and execution-port contention, and consequences for security boundaries. Separate the conceptual mechanism from the precise scheduling rules of a named implementation.

Editorial boundary: Microarchitecture treats dispatch queues and issue-port mechanisms inside one core. This child owns the system-level classification and resource-sharing implications of hardware thread contexts.

Expected specialist treatment: A two-thread timeline comparing stall hiding with shared-resource contention and no-load baseline.

3. Heterogeneous CPU, GPU, and Accelerator Systems

Research and instructional scope: Describe general-purpose CPU cores, throughput GPUs and domain-specific accelerators as cooperating architectural resources. Compare host-controlled dispatch, device-resident execution, address-space relationships, coherent versus noncoherent transfers, synchronization and workload partitioning. Assess the cost of moving data against the compute benefit of an accelerator. Include integrated and discrete devices, while explicitly avoiding a claim that every accelerator is independently programmable.

Editorial boundary: Machine learning hardware detail belongs to specialized-system units; bus protocols belong to Bus Systems. This subject owns whole-system composition and division of parallel work across heterogeneous engines.

Expected specialist treatment: A staged image-analysis pipeline with CPU control, GPU work, transfer overhead and synchronization points.

4. On-Chip Parallel Topologies and Interconnect Design

Research and instructional scope: Compare topological choices by diameter, bandwidth, bisection capacity, routing, hop count, congestion, area and power. Explain why the interconnect becomes a scaling constraint as core counts and cache agents grow. Include memory-controller placement, locality, traffic isolation and contention. Discuss failure domains and link redundancy only as architecture-level concerns, not as guaranteed features of every system-on-chip.

Editorial boundary: Bus Systems owns the detailed interconnect transaction protocols; this child evaluates their use and placement as resources in a multicore architecture. Avoid treating a two-dimensional mesh as universal in manycore processors.

Expected specialist treatment: Compare ring and mesh arrangements for a hypothetical 16-tile chip under local and all-to-all traffic.

5. Cluster and Multiprocessor System Organization

Research and instructional scope: Define a compute node, socket, rack, cluster and common architectural boundaries. Describe network interfaces, distributed memory, local and remote failure domains, storage paths and the effects of network latency on tightly coupled parallel execution. Contrast a large shared-memory server with many nodes connected by a high-speed network. Explain why node count alone does not determine scientific throughput or application response time.

Editorial boundary: Distributed Computing owns distributed algorithms, service semantics and message-passing programming. High-Performance Computing owns applied facility operations and workload-specific tuning. Here focus on architectural topology and resource placement.

Expected specialist treatment: Map a 64-node teaching cluster and estimate a simple communication-vs-compute threshold.

Parallel Memory and Coordination

The third group addresses the principal tension in scalable execution: independent work needs timely access to shared or exchanged information. The subjects distinguish shared address spaces, locality, explicit transfer, synchronization and collective communication while preserving the fact that those properties interact.

1. Shared-Memory Parallel Systems and Coherence

Research and instructional scope: Distinguish a shared address space from uniform latency and from fully coherent caches. Explain coherence at a conceptual level, the difference between invalidation and update protocols, and why a coherent system still needs defined synchronization and ordering rules. Introduce false sharing, contended cache lines, cacheline granularity and bandwidth pressure. Show where software-visible memory ordering and architectural hardware mechanisms meet.

Editorial boundary: Memory Hierarchy owns detailed cache layout and general locality; the Memory-Hierarchy and Bus Systems units retain coherence protocol depth. This child owns multicore sharing patterns and their architectural implications.

Expected specialist treatment: Trace two cores updating nearby counters with and without shared cacheline contention.

2. NUMA Topology and Memory Placement

Research and instructional scope: Explain nonuniform memory access as differences in access characteristics across memory domains. Contrast local and remote memory paths, coherence domains, page placement, memory-controller balance, and cross-socket traffic. Introduce first-touch placement as one possible policy, without treating it as universal. Describe how thread location and memory allocation can interact, and why reported NUMA node boundaries depend on firmware and operating-system topology descriptions.

Editorial boundary: Operating-system policy and allocator APIs belong to Software Systems. This article is about the architectural reasons locality matters and how hardware topology influences placement decisions.

Expected specialist treatment: A two-socket example comparing local/remote access time and aggregate memory-bandwidth demands.

3. Distributed-Memory Machines and Message Transfer

Research and instructional scope: Contrast local load/store operations with remote transfers through network hardware and protocol stacks. Describe message startup latency, per-byte transfer costs, collective coordination, interface offload and the effect of topology on application scalability. Note that some distributed systems offer remote direct memory access, shared-memory emulation or hybrid address spaces; labels do not define every access mechanism. Compare a tightly coupled cluster with a cache-coherent multicore node.

Editorial boundary: The MPI programming model, distributed consistency algorithms and failure-handling frameworks are sibling software topics. The Level 5 child concerns architectural communication capabilities and their limits.

Expected specialist treatment: Estimate when sending a halo boundary outweighs a numerical simulation step for two subdomain sizes.

4. Parallel Synchronization, Atomics, and Barriers

Research and instructional scope: Explain atomic read-modify-write operations, compare-and-swap, memory fences, barriers, locks as consumers of hardware primitives, and hardware-supported collective coordination. Distinguish data-race avoidance from cache coherence, and separate a synchronization barrier among threads from an instruction or compiler memory barrier. Introduce waiting, serialization, contention and progress guarantees without claiming all primitives are lock-free or equally scalable.

Editorial boundary: Binary Logic and State Machines own underlying formal reasoning; software concurrency owns specific lock implementations. This child owns the architectural contract and cost of synchronization across processors.

Expected specialist treatment: Model a contended atomic counter versus partitioned counters, including a correctness check.

5. Parallel Communication Topology and Collective Costs

Research and instructional scope: Explain why collectives depend on payload size, topology, routing, network injection rate and competing traffic. Differentiate point-to-point transfer cost from coordinated exchange across many processors. Introduce latency/bandwidth communication models as approximations; avoid asserting a universal collective algorithm or fixed performance formula. Address placement, congestion and link imbalance in processors, GPUs and clusters.

Editorial boundary: Collective algorithm implementation and MPI library tuning belong to distributed-software and HPC units. Here focus on architectural capabilities that shape the cost of communication patterns.

Expected specialist treatment: Compare idealized tree broadcast with a serialized chain for eight participants and explicit assumptions.

Scaling, Evaluation, and Resilience

The final group builds an evidence-based method for assessing parallel designs. It emphasizes workload assumptions, theoretical bounds, measured bottlenecks, energy use and architectural assurance. A persuasive architectural conclusion states which resources were available, what workload was attempted and where the limiting dependency occurred.

1. Amdahl’s Law, Gustafson’s Law, and Speedup Limits

Research and instructional scope: Derive Amdahl’s idealized speedup using the fraction treated as serial and the parallel fraction distributed across processors. Explain the assumed fixed workload and contrast scaled-workload reasoning often associated with Gustafson. Discuss parallel overhead, communication and nonuniform task duration as reasons actual scaling deviates. Clearly differentiate ideal upper bounds, measured speedup, throughput changes and weak versus strong scaling.

Editorial boundary: Algorithm Analysis owns general computational complexity and performance proof methods. This child treats parallel architecture resource scaling and the interpretation of architectural speedup claims.

Expected specialist treatment: Compute ideal speedup for a 10% serial fraction on 8 and 32 processors, then compare an overhead case.

2. Work, Span, Task Graphs, and Load Balancing

Research and instructional scope: Define total work, critical-path length (span), parallelism ratio and task dependencies as architectural planning measures. Examine static versus dynamic assignment, work stealing as a scheduling concept, grain size, imbalance, locality and synchronization overhead. Distinguish a theoretical parallelism bound from an achievable hardware schedule. Show why adding processors cannot shorten an unbroken dependency chain.

Editorial boundary: Detailed parallel algorithms and language runtimes belong to programming divisions. The unit focuses on the architecture-aware limits imposed by core count, memory proximity and communication costs.

Expected specialist treatment: A small DAG with work/span arithmetic and two schedules exposing critical path and idle processors.

3. Roofline Analysis, Memory Bandwidth, and Parallel Bottlenecks

Research and instructional scope: Explain the conceptual roofline relationship between peak compute throughput, sustainable memory bandwidth and arithmetic intensity. Show how cache effects, data reuse, vectorization, occupancy, synchronization and network transport complicate a simple two-ceiling chart. Contrast advertised hardware peaks with appropriately measured sustainable values. Emphasize units, workload precision and data movement assumptions in any performance assessment.

Editorial boundary: Memory Hierarchy owns storage technologies; Microarchitecture owns core execution counters. Here the roofline model relates full parallel platforms to workload demand without claiming one line predicts every observed latency.

Expected specialist treatment: Estimate attainable FLOP/s at two arithmetic intensities for a stated fictional compute and bandwidth budget.

4. Energy, Power, and Thermal Efficiency of Parallel Systems

Research and instructional scope: Describe why parallel hardware changes both instantaneous power and time-to-completion. Compare many simple processing units with fewer wide cores under a stated workload. Include dynamic and idle power, clock limits, thermal throttling, memory and interconnect energy, and the different goals of lowest energy, shortest latency and highest throughput. Explain why efficiency depends on utilization, manufacturing process, cooling and workload distribution.

Editorial boundary: Power and Thermal Systems owns detailed electrical and cooling engineering. This article owns architectural trade-offs when increasing parallel hardware resources under fixed envelopes.

Expected specialist treatment: Compare two fictional node designs for jobs-per-joule and deadline satisfaction at two utilization levels.

5. Parallel-System Reliability, Testing, and Validation

Research and instructional scope: Develop an architecture-level checklist for parallel execution correctness, synchronization assumptions, memory ordering, data corruption risks, performance nondeterminism and hardware faults. Distinguish deterministic outputs from repeatable timing, and transient failures from systematic parallel-program races. Describe redundancy, error correction, checkpointing and re-execution as selected reliability mechanisms, not universal guarantees. Include stress-test coverage across core counts, memory placements and workload mixes.

Editorial boundary: Application test suites, distributed transaction semantics and security threat modeling belong to their respective units. This article documents architectural assurance and the limits of empirical validation in concurrent hardware.

Expected specialist treatment: A validation matrix for a multicore-to-multinode design covering correctness, scalability, isolation and faults.

Parallel Architecture Comparison

Parallel architectures are best compared along independent axes: execution model, number and granularity of processors, memory organization, communication topology, programmability, and resource limits. A system may be simultaneously multicore, heterogeneous, NUMA and vector-capable. These categories are not alternatives on one linear scale.

Interpretive distinctions: SIMD describes a form of instruction and data organization; SIMT is a hardware/programming execution model for grouped threads; multicore identifies multiple processing cores; NUMA identifies nonuniform access locality; and a cluster describes systems linked at a larger communication boundary. One application can exploit all five. Peak arithmetic throughput, thread count and memory capacity should not be read as equivalent measurements.

Illustrative Parallel-System Scenarios

Each scenario is a constructed teaching example, not a performance measurement of an identified product or an account of MGU infrastructure. Its value is the decision logic: define execution units and dependencies, locate memory and communication costs, and state what evidence would support a recommendation.

1. Scenario 1 — Ideal speedup and its serial fraction

A hypothetical job spends 10% of its single-core execution in serial work and 90% in perfectly divisible parallel work. Under Amdahl’s idealized assumptions, an eight-processor speedup is 1/(0.10 + 0.90/8), approximately 4.71×; with 32 processors, it is 1/(0.10 + 0.90/32), approximately 7.80×. Neither value includes communication, contention or energy penalties and neither predicts a specific machine. The key conclusion is that a small serial fraction imposes a strong limit on fixed-size-workload scaling.

Relevant specialist reading: Amdahl’s Law, Gustafson’s Law, and Speedup Limits, Work, Span, Task Graphs, and Load Balancing.

2. Scenario 2 — Shared counter scalability

Eight worker threads increment a single shared counter. Even if arithmetic is tiny, the update requires synchronization and can force repeated movement or ownership transfer of a shared cache line. Splitting the updates into per-worker counters changes the access pattern and reduces the frequency of shared writes, although a correct final reduction remains necessary. The architecture question is not merely how many cores exist but how coherence and synchronization costs affect the useful work.

Relevant specialist reading: Shared-Memory Parallel Systems and Coherence, Parallel Synchronization, Atomics, and Barriers.

3. Scenario 3 — A two-socket memory placement error

A hypothetical two-socket system has two local memory domains. A parallel application starts threads on socket B but places most of its working data in socket A’s memory. Remote access may have different latency and bandwidth characteristics than local access. Changing placement can improve performance without modifying the algorithm or adding processors. The exact outcome depends on page policy, traffic direction, coherency, topology, and contention; no universal remote-access penalty is assumed.

Relevant specialist reading: NUMA Topology and Memory Placement, Shared-Memory Parallel Systems and Coherence.

4. Scenario 4 — GPU offload loses on a tiny job

A CPU can finish a small independent computation before the time needed to prepare and transfer data to a separate accelerator, launch a kernel and retrieve results. A much larger batch may reverse the comparison by amortizing fixed costs across more work. The correct evaluation separates end-to-end elapsed time, device compute time, transfer traffic, and potential concurrency between host and device.

Relevant specialist reading: Heterogeneous CPU, GPU, and Accelerator Systems, GPU SIMT, Warps, and Throughput Architecture.

5. Scenario 5 — Cluster size and halo exchange

An iterative numerical grid is divided among many nodes. Each node computes interior cells independently but exchanges boundary values at each step. Increasing node count reduces per-node arithmetic while changing boundary-to-volume ratio and raising the relative importance of message startup and network traffic. Strong scaling eventually weakens when communication and synchronization dominate. Different decompositions or larger total problems may produce different results.

Relevant specialist reading: Distributed-Memory Machines and Message Transfer, Parallel Communication Topology and Collective Costs.

6. Scenario 6 — Evaluating a hypothetical roofline ceiling

Assume an illustrative machine delivers 2 TFLOP/s of arithmetic and 100 GB/s of sustained memory bandwidth. A workload performing 5 floating-point operations per byte moved is limited by the simpler roofline bound to 500 GFLOP/s, below the arithmetic peak; at 40 operations per byte, the simple bound becomes 2 TFLOP/s. These are ceilings under stated units and assumptions, not measured application results. Cache reuse, nonuniform access, vector utilization and communication can lower the observed rate.

Relevant specialist reading: Roofline Analysis, Memory Bandwidth, and Parallel Bottlenecks, Vector and SIMD Parallel Execution Architecture.

7. Scenario 7 — More threads do not ensure resilience

An application runs across 128 nodes and completes faster under normal conditions than on one server. If the workload has no failure recovery mechanism, a single interrupted node might invalidate the entire run, depending on its coordination assumptions. Redundant execution or checkpoint-restart may change expected completion time but adds storage, computation and coordination overhead. Architectural evaluation should consider both performance when healthy and the reliability of completion.

Relevant specialist reading: Parallel-System Reliability, Testing, and Validation, Cluster and Multiprocessor System Organization.

Calculation discipline: use consistent units (operations, bytes, seconds and joules), clearly distinguish theoretical upper bounds from observations, and report whether a metric concerns single-job latency, system throughput or energy efficiency. Processor count without problem size and workload characteristics is not a sufficient performance claim.

Design and Investigation Framework

Parallel hardware should be selected and investigated through a sequence of explicit questions. “More cores” or “higher peak FLOP/s” is not a complete requirement. Start with the shape of the computation, then examine the resources that can execute it, the traffic it causes and the reliability assumptions it needs.

Practical decision sequence: (1) define workload and success metric; (2) quantify serial work, dependencies and grain size; (3) identify memory and communication requirements; (4) map the workload onto candidate processing engines and physical topologies; (5) estimate plausible ceilings and overhead; (6) measure a controlled baseline and candidate configuration; (7) examine memory placement, load imbalance, synchronization and energy; (8) validate correctness and isolation; (9) test reproducibility and failure behavior; and (10) record where the result would no longer generalize.

Evidence record: include hardware model and generation, core and thread count, accelerator and interconnect configuration, NUMA organization, memory capacity/bandwidth, compiler and library versions, dataset, problem size, scaling regime, measurement repetitions, power/thermal conditions and any important scheduling or affinity policy. For cloud or shared platforms, record placement and contention limits where observable. Claims comparing different systems must specify the metric and normalize assumptions before drawing a conclusion.

Suggested Study Pathways

The unit may be read systematically or used as a specialist reference. Choose a pathway according to the architectural decision being made, not solely according to hardware marketing labels. These links point to planned Level 5 articles; availability of the destinations is pending the separate subarticle production process.

Foundational computer architecture: Begin with Parallel Architecture overview, then Levels of Parallelism and Granularity, Flynn Taxonomy, SIMD, MIMD, and Classification Limits, Multicore and Manycore Processor Organization and Shared-Memory Parallel Systems and Coherence. Learn that parallelism categories overlap and that more hardware does not eliminate dependencies.

CPU and multicore platform designers: Follow Symmetric and Asymmetric Multiprocessing, Hardware Threading and Core Resource Sharing, On-Chip Parallel Topologies and Interconnect Design and NUMA Topology and Memory Placement. Then consult Microarchitecture for internal issue and retirement mechanisms.

GPU and accelerator systems: Study Vector and SIMD Parallel Execution Architecture, GPU SIMT, Warps, and Throughput Architecture, Heterogeneous CPU, GPU, and Accelerator Systems and Roofline Analysis, Memory Bandwidth, and Parallel Bottlenecks. Tie design choices to batch size, lane utilization, data placement and transfer overhead.

Shared-memory performance and synchronization: Read Shared-Memory Parallel Systems and Coherence, Parallel Synchronization, Atomics, and Barriers, NUMA Topology and Memory Placement and Work, Span, Task Graphs, and Load Balancing. Compare correctness, useful throughput and contention rather than treating one lock or placement policy as universally preferred.

Clusters and high-performance computing: Start with Cluster and Multiprocessor System Organization, then Distributed-Memory Machines and Message Transfer, Parallel Communication Topology and Collective Costs, and Amdahl’s Law, Gustafson’s Law, and Speedup Limits. Consult High-Performance Computing as a neighboring applied discipline.

Benchmarking and procurement: Use Amdahl’s Law, Gustafson’s Law, and Speedup Limits, Work, Span, Task Graphs, and Load Balancing, Roofline Analysis, Memory Bandwidth, and Parallel Bottlenecks and Energy, Power, and Thermal Efficiency of Parallel Systems. Define the service-level or research objective and include total cost and energy before comparing different resource counts.

Reliability, quality and architectural assurance: Combine Parallel-System Reliability, Testing, and Validation, Parallel Synchronization, Atomics, and Barriers, Shared-Memory Parallel Systems and Coherence and Cluster and Multiprocessor System Organization. Treat correctness, nondeterministic performance, transient errors and failures as distinct categories.

Learning checkpoint: a reader should be able to sketch an execution topology, identify memory and communication domains, state which work is independent, estimate a theoretical performance bound, and specify how to test that bound. A diagram of cores without the data path and synchronization requirements is not a complete architecture description.
