Scope, Purpose, and the Core–Cache Interface

A modern processor avoids waiting for every long-latency memory access by combining fast near-core cache hits, requests that can remain in flight, predictive requests issued ahead of demand, and instruction scheduling that overlaps independent work. These mechanisms target different parts of the same performance problem. A cache hit reduces the service time of a request; nonblocking operation admits other requests while a miss is unresolved; prefetching attempts to bring a line nearer before a demand access; and memory-level parallelism (MLP) describes the overlap among independent memory operations. None guarantees low application latency by itself.

This Level 5 MGU Encyclopedia article concentrates on the execution-facing cache access pathway: the interface between a load/store unit (LSU), near-core caches, outstanding-miss bookkeeping, prefetch engines, and the memory hierarchy below. It addresses the cache features that directly affect issue, replay, completion, retirement, and throughput. The companion Memory Hierarchy overview owns broad cache level organization, replacement algorithms, hierarchy capacity, and detailed coherence protocols. The present article is not a claim that all processors implement identical queues, counters, or cache organizations.

Three questions guide the entire treatment: How fast can an ordinary hit complete? How many misses can be outstanding concurrently? How often can data be brought close enough before it is demanded? The most effective design balances all three against available execution slots, cache capacity, bandwidth, power, area, and correctness requirements.

From a Load Instruction to Data Availability

Consider a load whose base register is ready. A scheduler may issue it to an address-generation unit; the resulting virtual address passes through translation and access checks, and the LSU determines whether the request can read from an older pending store. An ordinary cacheable load then approaches the L1 data cache, possibly in parallel with part of translation, depending on the physical organization. At the cache, tag lookup and data selection determine whether a usable copy is present and permitted.

On a hit, the requested bytes can return through the load-result network, and dependent micro-operations may become eligible for scheduling. On a miss, cache hardware either tracks a new outstanding request or combines this load with an existing request for the same line. The response later refills appropriate cache or buffer state and wakes waiting operations. A mispredicted path, a replay, a coherence invalidation, or a protection fault may modify this simple flow. Some designs allow load results to be forwarded before every bookkeeping action completes; the exact timing is implementation dependent.

The term load completion must therefore be kept separate from architectural retirement. An out-of-order load may finish long before older instructions commit, while a dependent chain cannot proceed until the relevant value is available. A speculative load that accesses a cache is also not proof that its result will retire. Cache Hits, Misses, and the Meaning of Latency

A cache hit means a request finds a suitable resident copy according to the cache’s lookup and coherence state; a miss means the cache cannot satisfy that request directly under the applicable rules. An L1 miss may hit in an intermediate cache; a last-level miss may require access to another chiplet, a remote socket, or DRAM. These outcomes often have different latencies, but an individual request can also be delayed by queueing, contention, translation work, writeback traffic, or a preexisting request to the same line.

Cache hit latency typically means time from a defined request acceptance point to availability of the requested data on a hit. It is not the same as hit throughput, which measures how frequently a cache can complete hits when many independent requests arrive. A cache might have several cycles of hit latency yet accept a new request each cycle if it is sufficiently pipelined. Conversely, a nominally low-latency cache may serialize accesses because of a bank conflict or insufficient ports.

When interpreting any published latency number, identify its clock domain, access type, cache state, address-translation assumptions, and whether the stated time includes request queueing. An average latency alone cannot explain all memory stalls because an out-of-order processor may overlap some of the delay with other independent instructions. Observed stall time is not simply a sum of all individual miss latencies.

L1 Cache Pipelines, Tag Checks, and Data Return

The L1 data-cache access path usually contains some combination of address indexing, tag comparison, state checking, data-array selection, ECC or parity checking, and result routing. A set-associative cache might read candidate ways and then select the matching way, or sequence portions of the lookup to save energy. Designs may use parallel or staged translation and indexing where aliasing constraints permit. A cache's hit critical path connects these circuit and control decisions to the consumer’s earliest possible use of the value.

Pipeline registers can divide a long cache-access path, increasing feasible clock frequency or request throughput at the cost of additional cycles of dependent-load latency. Additional data-array banks may support more concurrent accesses, but simultaneous requests to the same bank still may conflict. Wider cache lines do not imply that a complete line can be returned to an execution unit in one cycle: internal beats, read widths, alignment, and forwarding paths matter.

For a core with multiple load ports, a single L1 cache can still expose fewer effective resources than the port count suggests. Two loads may be accepted in one cycle under favorable bank or address patterns and serialized under others. Distinguish AGU capacity, LSU acceptance, tag bandwidth, data-array bandwidth, and fill bandwidth. A request can be blocked at any of these points even if the cache contains the data.

Cache Ports, Banking, and Structural Conflicts

A port is an independently usable access interface; a bank is a partition of storage whose resources can be scheduled separately. Increasing ports may require extra word lines, sense circuits, arbitration, area, and energy. Banking can provide much of the desired throughput with less physical complexity, but an address-to-bank mapping can concentrate traffic. Replication can assist read bandwidth for selected metadata or arrays, at the expense of keeping copies synchronized.

For example, a fictional two-bank L1 routes even-numbered line addresses to bank 0 and odd-numbered lines to bank 1. Independent accesses to two different banks may proceed simultaneously; two requests to bank 0 may require serialization if the bank accepts only one request per cycle. This is a bank conflict, not necessarily a cache miss. A performance event labeled “L1 bound” may include such near-core constraints rather than indicating misses that went to DRAM.

Writebacks, refills, snoops, and prefetch requests also require data or metadata paths. Some processors reserve resources or prioritize demands to prevent background operations from dominating demand latency. An architecture must specify whether accesses can be replayed safely after a temporary rejection and how age, fairness, and starvation are handled. These concerns connect physical cache organization to instruction scheduling and are separate from replacement policy.

Pipelined Versus Blocking Cache Behavior

In a blocking cache, a miss prevents admission or progress of some subsequent requests until the miss has been serviced. A very simple organization might stop all new cache accesses while fetching a missing line. A nonblocking or lockup-free cache allows at least some new requests to proceed while earlier misses remain outstanding. The term describes capabilities, not unlimited concurrency: new requests can still stall when bookkeeping entries, queue slots, downstream credits, coherence resources, or cache ports are exhausted.

A nonblocking cache may allow hits behind a miss (hit under miss), independent misses behind an older miss (miss under miss), or both. These are different service properties. Hit-under-miss can preserve throughput for data already resident, while miss-under-miss creates the opportunity to overlap independent long-latency fetches. The latter also requires the processor to discover and generate those independent requests before the first miss resolves.

Nonblocking behavior needs safe bookkeeping for all outstanding lines and all consumers waiting for each line. It also demands a completion path that tolerates responses returning in an order different from requests. A processor may preserve architecturally required program order through load/store queues, retirement logic, and ordering mechanisms without forcing the physical memory hierarchy to return every independent request in issue order.

Miss-Status Holding Registers and Outstanding-Miss State

A miss-status holding register (MSHR) is an entry, or conceptually equivalent state, that records an unresolved cache miss. Typical information includes a block address, request type, tracking or ownership information, status of the downstream transaction, and a collection of waiting consumers. Hardware families may use different names, split structures, or several layers of miss tracking. The architectural concept is more important than any particular implementation label.

When a load misses, the cache checks whether an appropriate miss to the same block is already outstanding. If so, a new waiting consumer may join the existing entry, subject to permissions, ordering and request-type constraints. Otherwise a new entry is allocated and a downstream request is issued when credits and bandwidth permit. On response, waiting consumers are woken, the line may be installed or forwarded, and bookkeeping is eventually reclaimed. Coherent caches also handle invalidations, transient states, and ownership changes that complicate this simplified description.

MSHR entries and waiter slots are distinct capacities. Having eight entries for distinct lines does not imply unlimited same-line request merging. An MSHR can be occupied even when no data has yet left a local queue. gem5’s classic cache documentation and its MSHR class explicitly model outstanding request entries and target requests, providing a concrete open reference for these principles.

Same-Line Miss Merging and Request Coalescing

Two loads may ask for different bytes of one line that is absent from L1. If the cache already has an outstanding line request, it can often merge the second demand into that request. The memory system fetches a cache-line granularity block rather than independently fetching that block twice. When data returns, each consumer receives the required bytes and any relevant ordering or exception bookkeeping is resolved. This is coalescing or secondary-miss handling; it is not the same as overlapping misses to two distinct lines.

For the purposes of counting memory-level parallelism, ten outstanding load instructions all waiting for the same 64-byte line need not represent ten independent downstream transactions. They may occupy a single outstanding-line entry with ten waiter records. Conversely, ten loads to ten different lines can require ten transactions, provided other hardware resources permit that many requests to be in flight. Uncacheable accesses and some atomic or exclusive operations may have different merging rules.

A useful diagnostic records both outstanding load instructions and outstanding distinct cache lines. Conflating them can produce wildly optimistic predictions about attainable bandwidth or the effect of increasing MSHR counts. Cache-line locality can reduce total traffic even though it simultaneously reduces the number of independent misses present.

MSHR Exhaustion, Backpressure, and Resource Reservation

Once every appropriate MSHR entry is in use, a request to a new missing block may stall even though the cache is called nonblocking. A request that hits an already-resident line might still proceed if the implementation supports hit-under-miss and the needed port remains free. A secondary miss targeting an existing entry might also proceed if sufficient waiter capacity exists. These distinctions matter for both benchmarks and hardware design: “MSHR full” does not always mean all cache activity stops.

Stalls can propagate backward into load-queue entries, scheduling queues, the reorder buffer, rename, and ultimately instruction fetch. New prefetches often receive lower priority than urgent demand requests, although a vendor may implement more complex priority classes. Some designs reserve capacity for coherence responses, page walks, or critical demands to avoid circular wait. Others throttle prefetch generation, prevent admission of selected speculative requests, or react to queue occupancy.

Queue capacity is not useful if the downstream fabric cannot accept the traffic. Similarly, adding more entries may fail to increase performance if a DRAM controller, shared interconnect, memory bank, or application dependency chain remains the bottleneck. A correct study of “more MSHRs” therefore measures whether additional distinct concurrent misses actually appear, whether they are served in parallel, and whether useful retirements increase.

Refill Buffers, Line-Fill Queues, and Completion Routing

Outstanding-miss bookkeeping may be separated from the physical buffering needed to receive a returned line. Processors can contain line-fill buffers, refill queues, writeback buffers, transient cache entries, and completion-routing structures that do not map one-to-one onto the abstract MSHR model. Some resources can track an outstanding request without storing the full cache line, while other buffers temporarily retain data before a cache-array write. Implementation-specific terminology should not be interchanged as though every processor used the same structures.

On response, an arriving block must reach the correct request context, be checked for integrity and relevant permissions, wake dependent loads if permitted, and make progress through any necessary cache or coherence state transitions. A refill path can become a throughput bottleneck even if many misses were successfully issued. For example, a narrow return interface may accept only part of a line per beat, forcing repeated use of the refill resource. The resulting pressure may delay other fills or foreground hits.

A particularly important optimization is critical-word-first delivery, when supported: the cache forwards the requested word or subblock as it becomes available rather than waiting for every byte of the line to be installed. This can shorten observed demand latency, but it does not remove the need to finish the entire coherent transaction and to maintain valid line state.

Load Queues, Reorder Windows, and Available Independent Work

An out-of-order core can overlap cache misses only if it discovers enough independent work before an older miss completes. The load queue tracks loads and enforces memory-order requirements; the reorder buffer limits the number of speculative instructions resident; the scheduler and physical registers hold independent instructions and their operands. If any structure fills, the front end may stop supplying new opportunities for memory overlap. More MSHRs alone cannot solve a lack of independent loads in the instruction window.

Consider a chain in which each load supplies the pointer for the next: p = *p repeated through a linked list. The next address is unknown until the preceding load returns, so a conventional core cannot naturally have many dependent pointer-chasing misses simultaneously outstanding. By contrast, a loop that computes eight addresses from independent array indices may expose multiple misses, provided the code and processor maintain the addresses and requests in flight. Software loop unrolling, vectorization, task parallelism, and memory access ordering can change how much MLP is visible.

Instruction-level parallelism (ILP) and memory-level parallelism are related but not synonyms. Independent arithmetic can occupy execution units while one miss waits; true MLP additionally requires multiple independent memory operations to overlap. A core can exhibit substantial ILP yet little MLP, or very high memory request concurrency with modest useful instruction retirement.

Demand Misses, Prefetch Requests, and Traffic Classes

A demand request arises because execution requires data for a particular instruction or operation. A prefetch request is generated before a corresponding demand is known to need immediate service. The prefetch is intended to reduce a future demand’s waiting time, not to change the program’s architecturally visible result. Coherence requests, writebacks, page-table walks, and device traffic are other consumers of shared memory-system capacity.

Not every prefetched line is ultimately used. A prefetched block can be evicted before use, arrive too late to prevent a stall, compete with another demand for an MSHR, or occupy space better used by ordinary program data. On the other hand, a successful early prefetch can convert a long demand miss into a near-core hit or into a demand that joins an already-progressing fill. Prefetch traffic may therefore increase raw bytes transferred while decreasing program stall time.

A robust accounting system distinguishes demand misses served by L2, demand misses served by DRAM, useful prefetch hits, prefetches that arrived late, and prefetches never used. The definitions depend on the hardware instrumentation. Treat general “cache miss count” as insufficient to determine whether the prefetch engine reduced or merely displaced misses.

Hardware Prefetching: Detection and Issuance

Hardware prefetchers observe some combination of recent misses, hits, instruction addresses, spatial patterns, or access deltas, then predict future line addresses. A mechanism may operate at L1, L2, or another level, and may be triggered by requests reaching that level rather than every instruction the core executes. The engine typically needs confidence logic, duplicate filtering, outstanding-request capacity, address translation or protection handling, scheduling priority, and a destination for each returning line.

Consider a sequence touching cache lines A, A+1, A+2, and so on. A stream predictor might request A+3 and A+4 before the processor demands them. A stride predictor can recognize that each access advances by a fixed number of lines, even when the stride is larger than one. Engines that identify such patterns differ in training requirements and susceptibility to false positives. They may also include explicit filters around page boundaries, permission contexts, or resource utilization.

Hardware prefetching is most effective when its pattern is sufficiently predictable and enough lead time is available. It is less reliable for random pointers, irregular graph traversal, or workloads whose next address depends on the just-fetched data. Application code may change prefetch behavior indirectly by changing iteration order, data layout, and demand miss frequency.

Next-Line, Stream, and Stride Prefetchers

A next-line prefetcher considers a line adjacent to a recently accessed line. A stream prefetcher recognizes repeated forward or backward movement through a region and continues requesting ahead. A stride prefetcher predicts a fixed distance between successive addresses, potentially using the instruction address to isolate multiple interleaved access streams. Prediction engines may operate on byte addresses or cache-line indices; whether a small byte stride repeatedly hits within one line matters to their training behavior.

Suppose a program accesses line numbers 100, 104, 108, 112. A stride engine that correctly learns +4 can request 116, 120, and perhaps farther lines, subject to its confidence and distance controls. A next-line scheme that blindly fetches 101 after 100 would not supply the next demanded line. In contrast, a sequential array scan touching 100, 101, 102, 103 is a natural fit for next-line or stream prediction.

No mechanism is universally superior. Several active streams may collide in a small predictor table; phase changes can make a formerly reliable stride inaccurate; and aggressive streams can overconsume bandwidth. The chosen prefetcher must be evaluated against the mix of applications, prefetch destination level, and traffic limits, not against an isolated synthetic stride pattern alone.

Correlating, Spatial, and Access-Pattern Predictors

More sophisticated hardware learns relationships that are not simple fixed strides. Correlation-based schemes record how prior misses or line accesses predict later ones; spatial-pattern schemes observe offsets or neighboring blocks within a region; delta-pattern schemes use sequences of differences between accesses. Some designs use signatures, history tables, or compact footprints to predict subsequent lines, at the cost of additional state and training latency.

These approaches can find regularity in mixed or repeating patterns, but greater predictor expressiveness can also raise energy, metadata storage, interference, and debugging complexity. A stream of misses caused by an alternating traversal, for example, may be learnable by a sequence predictor even when no single stride consistently describes it. A pointer chase whose next address is effectively random may remain unpredictable because observing previous addresses gives little information about the next one.

It is important to distinguish a prediction of a future cache-line address from a guarantee that the address is safe or useful to fetch. The memory system must still obey privilege, address-space identity, translation, coherence, and fault-suppression rules applicable to speculative prefetches. Detailed algorithm families belong to the prefetch-engine research literature; the microarchitectural question here is how predictive requests compete with real execution and whether they reduce critical-path stalls.

Prefetch Distance, Degree, and Timeliness

Prefetch distance describes how far ahead of current demand an engine requests a future line. Prefetch degree describes how many predicted lines it initiates per trigger or how aggressively it sustains a stream, depending on the scheme. Increasing either can improve timeliness for a regular stream, but only until queue capacity, bandwidth, cache retention, or prediction accuracy constrains the benefit.

If a regular stream consumes one distinct line every 20 cycles and the round-trip latency from the prefetch destination is 100 cycles, the idealized lead distance needed to hide that service time is approximately five lines under stationary, contention-free assumptions. This is a timing heuristic, not a fixed prescription: the first few misses train the engine, queued requests may lengthen service time, and data may be evicted before use. Some processors also recognize page boundaries and limit prefetches until translation for the next region is known.

A late prefetch can still reduce residual delay if the request is partially complete when a demand arrives. An early but wasteful prefetch can hurt by evicting useful lines or consuming downstream queue slots. A useful tuning approach measures timeliness together with accuracy, cache pollution, and the change in retired work—not merely the number of prefetches issued.

Prefetch Accuracy, Coverage, and Usefulness

Evaluation metrics answer different questions. Accuracy often compares useful prefetched lines with total prefetched lines, while coverage often measures the fraction of baseline demand misses prevented by useful prefetches. Timeliness asks whether a prefetched line arrived before its demand. Because tool definitions differ, all numerators, denominators, and line-use rules must be stated before comparing measured values. Coverage against a no-prefetch baseline is not automatically computable from one run’s miss count.

A prefetch might be called useful if the core later uses the prefetched line before eviction. But “used” does not prove that it reduced execution time: the demand might not have been on the critical path. Conversely, a prefetch that arrives just after demand and merges into an outstanding miss may still shorten waiting time without registering as a classic prefetch hit. Performance benefit should be measured separately as elapsed time, cycle count, instructions per cycle, or another workload-appropriate objective.

Likewise, high prefetch accuracy is not enough. Fetching every line one cycle too late could yield an impressive usage fraction while doing little to reduce stall time. A low-accuracy engine can occasionally be valuable if its useful requests cover a small number of extremely costly critical-path misses, but that must be balanced against the traffic and displacement it introduces.

Prefetch Pattern Comparison and Selection

Predictors solve different pattern-recognition problems. A simple adjacent-line engine can be small and effective for contiguous data, while a more expressive engine is useful only if the application supplies a repeatable relationship the predictor can learn. Training overhead, state interference, and throttling are important even when an algorithm appears accurate in a short access trace.

Prefetch Pollution, Bandwidth Waste, and Throttling

A prefetched line consumes transfer and storage resources whether or not it later serves a demand. A speculative read that displaces a hot cache block can increase misses elsewhere: this is cache pollution. Prefetching also competes for MSHRs, fill buffers, cache ports, interconnect credits, memory-bank service, and memory-controller bandwidth. The negative effects can be concentrated in a different thread or core from the one receiving the apparent benefit.

Hardware may throttle prefetches when accuracy falls, queuing becomes excessive, demand latency grows, or particular resources approach exhaustion. Another policy may prioritize demand over prefetched fills, drop predicted requests under pressure, or limit the number of prefetches per stream. These policies are implementation choices: there is no universal “demand always wins” rule that covers every level, resource, and cycle. Prefetching may even be disabled for particular regions or access types.

For assessment, compare at least three conditions: prefetch disabled, baseline behavior, and a carefully limited aggressive setting if configurable. Measure demand-service latency, total bytes moved, miss traffic, CPU progress, and effects on co-running workloads. Any speedup must be evaluated against the energy and fairness consequences of additional memory traffic, particularly in bandwidth-constrained multicore systems.

Software Prefetch Instructions and Compiler Hints

Some instruction sets expose software prefetch operations or cache hints. These can let code request data ahead of a future load or communicate an expected locality property. The processor may interpret the hint according to its own implementation and may ignore it; it is generally not a portable guarantee that a particular cache line will be resident on a particular cycle. Permissions, exception behavior, and the precise semantics differ by instruction set and instruction form.

A compiler or programmer might schedule a prefetch several iterations before an expected use in a predictable loop. Too short a lead may make the request late; too long a lead can evict the line before use. Software prefetches also add instruction overhead and can duplicate useful hardware prefetching. In modern processors, improving data layout, locality, vectorization, or independent work often delivers more reliable gains than manually adding a large number of prefetch hints.

Prefetching linked structures is especially difficult because the target pointer may not be known until a prior load returns. Some software can issue a prefetch after extracting a pointer and then perform independent work while the request progresses. This overlaps part of the latency but does not magically break the address-dependency chain. Processor and compiler optimization guides should be consulted before claiming a particular hint bypasses translation, bypasses protection, or forces cache residency.

Translation, Prefetch Address Spaces, and Page Boundaries

Data prefetching interacts with virtual-memory translation. A prefetch engine that predicts using virtual addresses may need page translation or must avoid requesting an unmapped page; a mechanism operating on physical addresses must obey the address-space and memory-type rules of its source request. Some prefetchers limit prediction to a known page or region, while others use additional translation resources. The design must prevent inappropriate data exposure or architecturally visible exceptions from a mere hint.

Page crossing is important for regular streams. Sequential line addresses may be predictable, but the next virtual page might map to a nonadjacent physical frame, be absent, or have different permissions. Therefore extending a physical line sequence across a page boundary without suitable translation is not generally correct. Hardware policies differ significantly: a documented restriction for one processor family is not a universal cache-design rule.

A prefetch that competes with demand page walks can affect translation performance even if its data prediction was accurate. Similarly, a load may wait for the TLB while the relevant data is already resident in cache. Memory-Level Parallelism: Definition and Measurements

Memory-level parallelism denotes concurrent, independent memory operations whose service intervals overlap. A common operational metric is the number of outstanding cache misses or memory transactions averaged over time. The metric must specify where it is measured: L1 misses, last-level misses, DRAM requests, load instructions, or distinct line fetches can yield different answers. It must also specify whether prefetches, page walks, stores, and coherence traffic count.

MLP differs from the miss count. One thousand requests processed strictly one after another can have high total misses and an outstanding-miss average near one. A burst of eight independent misses issued together can have much larger instantaneous MLP even though only eight misses occur. The performance relevance depends on whether the memory subsystem can serve these requests concurrently and whether returning data is on the processor’s critical path.

An intuitive timeline plots each miss as an interval from request acceptance to response, with overlapping horizontal bars representing concurrency. Counting bars at each moment gives outstanding-request count; the time average estimates mean concurrency. Peak MLP and average MLP convey different information. Because a miss can wait inside several nested queues, a complete analysis identifies the measurement boundary rather than treating every queued load as a DRAM request.

Latency Hiding Versus Latency Reduction

Three complementary methods improve memory performance. First, a hit in a nearer cache reduces the time to obtain data. Second, prefetching can move part or all of the service interval earlier, before the load needs the data. Third, MLP can overlap multiple service intervals, so total completion time is smaller than the sum of their individual latencies. These mechanisms can coexist but have different resource demands and failure cases.

For two independent misses each requiring 100 cycles, strictly serial service could cost about 200 cycles from the first request to the second completion, ignoring fixed issue overhead. With adequate overlap and resources, both may complete in about 100 cycles after their simultaneous issue. This does not change either request’s own round-trip latency. A successful prefetch may instead make one of the two loads hit when executed, changing its perceived latency. A cache hit that still waits behind an occupied access port illustrates that logical residency and observed delay are also separate.

Workload speedup cannot be obtained by subtracting the full “saved” cycles for every miss. Overlap between misses, dependent execution, retirement constraints, and existing independent work can mean that only a fraction of each miss lies on the overall execution critical path. Sound performance analysis begins with a timeline or measured occupancy, not an additive sum of all cache events.

Concurrency, Bandwidth, and Little’s Law

A useful steady-state relationship is average outstanding requests ≈ request completion rate × average request latency, provided the measured quantities refer to the same flow and boundary. This is an application of Little’s law. If four distinct line requests per 100 cycles complete on average and their mean in-system time is 100 cycles, the corresponding mean outstanding count is approximately four. The result is an accounting identity under stable conditions, not proof that four requests can be served independently or that enlarging a queue creates demand.

For an illustrative fixed-size line of 64 bytes, a sustained completion rate of one line every 10 ns corresponds to 6.4 billion bytes/s of line transfers. If mean response time is 100 ns, maintaining that transfer rate requires approximately ten outstanding line requests on average in the same service system. If only four independent requests can be active, the maximum throughput permitted by this concurrency bound is approximately 4 × 64 bytes / 100 ns = 2.56 GB/s, assuming the example’s fixed latency and fully useful independent transfers.

Real bandwidth can be lower because requests transfer different byte counts, service times grow under load, and queue occupancy includes other traffic. A useful upper bound is the minimum of independent-request availability, concurrency-limited data rate, and sustainable downstream bandwidth. Theoretical peak bandwidth does not tell us how many useful bytes the application receives, and memory-level parallelism does not eliminate queueing caused by saturation.

Queue Depth, Arrival Rate, and Saturation

Increasing outstanding-request capacity can improve throughput until another bottleneck appears. At low request rates, available parallelism may not fill the cache’s MSHRs, and enlarging the table changes little. Near saturation, a larger table may let the core tolerate a burst of misses while downstream service continues. But excess admission can also lengthen queueing delay and intensify interference, making a larger outstanding count look impressive without improving useful work.

For example, a memory subsystem that completes at most one 64-byte line every 20 cycles has a hard illustrative service-rate ceiling of 3.2 bytes/cycle, irrespective of whether its upstream cache tracks eight, 16, or 32 distinct outstanding requests. If average latency is 160 cycles and eight requests are available, the rough concurrency bound gives 8 × 64 / 160 = 3.2 bytes/cycle. Doubling capacity to 16 does not double throughput when the lower-level service limit is already reached. Queueing could instead raise average latency.

When making design decisions, measure throughput versus occupancy and identify the knee where extra requests yield diminishing gains. Also track tail response times, fairness across sources, and energy cost. A high MSHR occupancy may signal healthy latency tolerance, saturation caused by congestion, or prefetches displacing demand requests. The number alone does not resolve which explanation is correct.

Dependent Pointer Chases and Limited Parallelism

A pointer-chasing traversal often defeats conventional MLP because the address of the next load is produced by the current load. A simple sequence node = node->next provides one unresolved dependency chain. Even a large reorder buffer cannot issue a later load whose address has not yet been computed. Reducing miss latency—through locality, caching, or more favorable placement—can therefore help this workload more than simply adding MSHR capacity.

There are several ways to increase overlap without pretending that the dependency disappears. Software can traverse several independent linked lists at once, use a batched work queue, switch between independent tasks, or rearrange data into compact arrays whose addresses can be calculated in advance. A CPU with simultaneous multithreading may encounter additional independent misses from another thread. Some research mechanisms perform runahead or specialized address prediction; their correctness and practicality depend on additional control and recovery machinery.

This distinction explains why two benchmarks with nearly identical cache-miss counts may respond very differently to a microarchitectural change. The pointer chase may be latency bound, while an independent streaming array workload can be bandwidth bound with substantial MLP. Selecting an optimization requires identifying whether the critical resource is time per dependent step, number of concurrent steps, or bytes deliverable per unit time.

Outstanding Loads, Stores, and Writeback Traffic

Although the clearest MLP examples involve loads, the memory subsystem also handles stores and writebacks. A store may be retired architecturally before its data reaches the final coherent visibility point, depending on the applicable memory model and implementation. Committed store buffers decouple retirement from lower-level service, while speculative store queues preserve program-order and address-dependence information. Stores may merge, generate ownership requests, or wait for a cache-line transfer before completion.

Evicting a dirty cache line can require a writeback that consumes queue capacity and bandwidth. A stream of read misses may therefore be slowed by unrelated dirty evictions. Likewise, coherence probes can force cache metadata and data movements that compete with the refill path. A prefetch that causes replacement may induce both an incoming fetch and an outgoing dirty writeback, raising traffic beyond the nominal prefetch request.

Do not infer memory-order correctness from when a cache line physically arrives. Architectural memory ordering concerns which loads and stores may become observable and what fences or atomics guarantee; this is separate from the timing of underlying reads, writes, and internal speculations. The companion '+link('load-store-queues-and-memory-disambiguation','Load-Store Queues and Memory Disambiguation')+' addresses forwarding, replay, and ordering in detail. The broader Memory Hierarchy unit addresses coherence states and replacement policies; this article concentrates on traffic competition and performance implications.

Coherence, Prefetching, and Shared Cache Interference

Multiple cores may share a last-level cache, memory controller, or interconnect. A line demanded by one core can be present in another core’s cache, requiring a coherence or cache-to-cache transfer rather than a direct DRAM read. Prefetches in a coherent system must interact with the cache-coherence protocol and observe the relevant access rules. A speculative prefetch does not justify violating another core’s ownership or exposing protected contents.

Resource sharing makes local prefetch success an incomplete system objective. One thread may see fewer demand misses while its aggressive prefetch stream evicts another thread’s useful lines or consumes memory bandwidth needed by a latency-sensitive service. Shared MSHRs, memory queues, and cache ways can also create interference. Some systems use quality-of-service policies, throttling, partitioning, or priority controls to manage these interactions.

In multicore evaluation, report both per-core improvements and aggregate behavior. Record slowdown or fairness for co-running workloads, not only total traffic. A single-thread test on an otherwise idle processor cannot establish how the same design behaves under multiple demanding applications. This distinction is especially important in servers, real-time systems, and heterogeneous processors whose resource consumers have unequal performance objectives.

Instruction Fetch, Data Caches, and Unified Resources

Although this article’s principal examples use demand loads, instruction fetching also relies on caches, outstanding requests, prefetching, and memory bandwidth. An instruction-cache miss may stall the front end before enough instructions enter the reorder buffer to expose data-side parallelism. Conversely, data-side misses may compete with instruction fills at a shared last-level cache or memory controller, even when L1 instruction and data caches are physically separate.

Instruction prefetching may use sequential or control-flow-aware predictors; it need not behave like a stride prefetcher for data loads. Branch predictions can redirect demand fetch and change which instruction lines are prefetched. Wrong-path fetches may occupy resources even when those instructions never retire. A design therefore has distinct critical paths for instruction supply and data availability, with possible shared-resource bottlenecks deeper in the hierarchy.

A performance study should ask whether the core is waiting for instructions to decode or data operands to execute. Both may appear as memory-system traffic, but the remedies differ. Instruction-side mechanisms are covered more fully in '+link('instruction-fetch-decode-and-micro-ops','Instruction Fetch, Decode, and Micro-Ops')+' and '+link('branch-prediction-and-fetch-redirection','Branch Prediction and Fetch Redirection')+'. Here the key conclusion is that demand and speculative traffic from different front- and back-end clients cannot be evaluated independently once they share lower-level resources.

Multiple Cache Levels and Nonuniform Miss Costs

An L1 miss does not imply a DRAM transaction. A hierarchy can service it from L2, a last-level cache, a peer cache, or another memory location. The processor often implements different outstanding-request limits at each level, with local line-fill buffers, intermediate-cache MSHRs, fabric credits, and memory-controller entries. Thus a single request can occupy several categories of resource at different times.

The latency a load experiences may depend on where the data is found, on whether the request is already represented by an earlier miss, and on how much contention exists. A hypothetical 5-cycle L1 hit, 15-cycle L2 fill, and 110-cycle DRAM service are useful as classroom categories but are not universal processor specifications. Changing the hit distribution can yield significant performance benefit without changing the clock frequency, while changing MLP can improve throughput without altering any intrinsic service latency.

Prefetch destination also matters. A prefetch delivered to L2 might let a later L1 miss finish relatively quickly but will not always become an L1 hit. Placing every prefetched line directly in L1 risks pollution; placing it too far away may leave demand latency. A balanced design selects prefetch level and priority alongside cache size, access frequency, and expected reuse, while preserving coherent behavior.

Prefetching and Stream Bandwidth Limits

Predictable sequential workloads can often overlap many line fetches, but they still need sufficient sustainable bandwidth. If a core consumes a 64-byte line every eight cycles, its idealized demanded data rate is eight bytes/cycle. At 3 GHz this corresponds to 24 GB/s of payload traffic from the relevant level, before any additional data, writebacks, or prefetch waste. If the shared path sustains less than this, no prefetch distance can maintain the target rate indefinitely.

Prefetchers can hide startup latency and maintain a full pipeline of requests. Once the memory system is saturated, prefetching may shift request timing while increasing total contention. The difference between latency bound and bandwidth bound is therefore essential. A demand stream that already saturates DRAM may not improve when prefetching becomes more aggressive; it may get worse if inaccurate requests use bandwidth otherwise available to valid demands.

Prefetch tuning must account for cache-line granularity. An application reading only four useful bytes from each 64-byte line uses at most 1/16 of the fetched bytes for that access, even if the prefetches are perfectly predicted. Reducing wasted spatial traffic or restructuring data may be more valuable than fetching the same oversized lines earlier. This is a general principle; actual cache-line and transfer sizes vary by processor and level.

Cache Access, MLP, and Core Frequency Trade-Offs

Fast cache hit access is physically difficult. Larger or more heavily ported arrays can increase wire length, circuit delay, and energy. Designers may pipeline an L1 cache more deeply to reach a target clock frequency, trading longer dependent-load latency against potential throughput. A wider core can generate more memory operations per cycle but may require more load queue entries, more cache banks or ports, more MSHRs, and broader result-routing paths.

An optimization that improves one metric can reduce another. Increasing frequency raises cycles per second but may also increase the number of cycles for a fixed nanosecond-scale DRAM service time. Enlarging the reorder buffer lets more requests overlap but consumes area, power, and complex control resources. Increasing prefetch degree may maintain useful concurrency at the expense of energy or fairness. Low-power cores often deliberately accept lower peak concurrency than a wide, high-performance core.

Whole-program throughput is the objective, not minimum load-hit latency in isolation. A design with a slightly longer hit latency might outperform one with a shorter hit if it supports more independent accesses, higher sustainable bandwidth, or a better clock rate. Conversely, pointer-heavy code may strongly prefer a short dependent-load path even when theoretical maximum bandwidth is lower.

Memory-Level Parallelism in Simultaneous Multithreading

Simultaneous multithreading (SMT) allows instructions from multiple hardware contexts to occupy a core’s pipeline. This can expose independent load misses even when each individual thread has a difficult dependency chain. If one context stalls on memory, another may use otherwise idle issue slots, functional units, and outstanding-request capacity. Whether the gain occurs depends on the cache and scheduler resource-sharing policy.

SMT does not multiply physical memory bandwidth or cache-port counts. Threads may compete for reorder-buffer capacity, load queue entries, physical registers, MSHRs, fill buffers, and lower-level queues. An extra thread can improve latency tolerance when resources are underutilized or degrade performance if a working set grows and cache contention dominates. Fairness and per-thread slowdown therefore matter alongside total throughput.

When measuring SMT, distinguish per-thread latency from aggregate instructions per second, and note whether retired IPC counts across one or several contexts. A workload may improve total throughput while extending each individual job’s completion time. The dedicated '+link('simultaneous-multithreading-and-core-resource-sharing','Simultaneous Multithreading and Core Resource Sharing')+' article owns thread-context management and resource allocation in greater detail.

Memory-Level Parallelism in In-Order and Out-of-Order Cores

Classic single-issue in-order cores often stall on a long demand miss because dependent progress and instruction ordering are tightly coupled. However, not all in-order designs are completely blocking: multiple outstanding loads, decoupled access engines, hardware threads, and prefetchers can provide some concurrency. Similarly, out-of-order cores offer opportunities for MLP but are not guaranteed to exploit them if dependencies, small windows, or physical queue limits intervene.

A wide out-of-order core with multiple AGUs can generate many independent load addresses and maintain them in the memory system. Its reorder buffer and load queue must remain large enough to tolerate the outstanding service time. Independent work following a cache miss can be executed while waiting, but instructions still retire according to the core’s rules. The resulting speedup can be large for mixed arithmetic and independent loads yet small for a tightly serialized pointer chain.

Compare cores by their observed useful concurrency, not just declared “out-of-order” status or issue width. Two processors can have equal decode and issue widths but very different MSHR counts, load queue sizes, cache ports, prefetchers, and latency distributions. The practical microarchitecture must be studied as a coordinated resource graph.

Memory-Access Replays and Miss-Hit Interactions

A load may need to be retried for reasons other than a simple cache miss. An address-bank conflict, an unavailable cache port, a line under a transient coherence transition, a blocked refill, a load/store ordering violation, or an unresolved translation can prevent immediate completion. Such mechanisms often produce replay or reissue activity. Replayed requests consume schedule and data-path bandwidth even if the final result is eventually a cache hit.

The microarchitecture must prevent a replay from incorrectly completing a younger instruction, violating ordering, or exposing a wrong-path result to architectural state. Some requests remain resident in an LSU queue until retry conditions clear; others are rescheduled through a more general issue mechanism. There is no universal rule that every L1 miss causes the same kind of replay. Refill and result-forwarding paths may allow some dependent operations to proceed without repeating the original tag lookup.

Profiling should distinguish miss latency from replay overhead. Increasing cache capacity can reduce misses yet leave structural replay unchanged; adding more ports can reduce conflict replays while not affecting DRAM latency. Understanding which mechanism is active prevents incorrectly attributing all memory-side stalls to insufficient cache size or prefetching.

Speculative Access, Fault Deferral, and Correctness

Out-of-order processors may issue loads and prefetches before it is known that their instructions will retire. Incorrectly predicted control flow can therefore generate cache activity that later becomes irrelevant to the architectural program. The machine must ensure that squashed instructions do not commit architectural register changes, memory stores, or unauthorized results. At the same time, caches, buffers, and predictors can retain transient effects of speculatively executed work.

Faults associated with speculative demand accesses must be handled precisely under the instruction set’s rules. Translation and protection checks are part of that path, and a later squashed load must not report an exception as if it had retired. Many prefetch hints have different exception behavior from normal loads; exact rules depend on ISA and instruction encoding. It would be incorrect to treat all speculative data movement as equivalent to a permitted architectural access.

This distinction also matters for security. Cache timing, prefetch patterns, and contention may reveal information about microarchitectural state without any incorrect architectural retirement. Defensive designs consider permission enforcement, shared-resource partitioning, speculative controls, and software isolation. Detailed attack classes and mitigation trade-offs belong in '+link('microarchitectural-side-channels-and-mitigations','Microarchitectural Side Channels and Mitigations')+'.

Power, Thermal Behavior, and Performance per Watt

Every additional cache access, prefetched line, or downstream request consumes dynamic energy. A prefetch that avoids a critical stall can nevertheless reduce performance per watt if it creates substantial unneeded traffic. Additional MSHRs, predictor tables, ports, and larger buffers increase hardware state and can add static and dynamic power. High outstanding traffic may also keep memory channels active and reduce opportunities for low-power states.

Thermal constraints add a further trade-off: increasing request concurrency or frequency can raise power until the platform lowers clock speed. A design’s apparent microbenchmark advantage at fixed frequency may disappear under sustained thermal limits. Conversely, an accurate prefetcher can reduce total execution time enough to offset its energy overhead, especially if completing the workload earlier lets components become idle.

Use energy per completed task or joules per useful byte where appropriate, not just prefetch accuracy or theoretical bandwidth. A balanced comparison should hold workload, software, operating conditions, and measurement boundaries consistent. Measurement Counters and Bottleneck Attribution

Performance-monitoring units and profilers can report events such as retired loads, cache accesses, cache misses, outstanding requests, cycles with a pending load, prefetch activity, and stalls attributed to a hierarchy level. These events are processor-specific and may involve sampling, multiplexing, skid, aggregation, or microarchitecture-dependent definitions. A tool’s event called “memory bound” is not itself a literal sum of DRAM access cycles. The denominator and aggregation window must be examined.

A defensible diagnosis begins with wall-clock performance and retired work; then it examines IPC or CPI, memory-bound categories, useful cache-hit rates, demand miss distribution by level, and average or peak outstanding requests where supported. Finally it tests hypotheses by changing access pattern, thread count, prefetch setting, or data placement. Intel VTune’s Memory Access and top-down analysis documentation distinguishes near-core L1-bound behavior from lower-level cache and DRAM delays, illustrating why one total cache-miss count is inadequate.

Do not infer a universal MSHR count from a counter unless the hardware documentation supports that interpretation. Some tools report inferred concurrency or aggregate events rather than actual register occupancy. Where appropriate, combine counters with architectural simulation, carefully controlled microbenchmarks, and source-level inspection to build a consistent performance explanation.

Experimental Controls and Simulation Methodology

Comparing cache and prefetch designs requires repeatable workloads and explicit baselines. State cache hierarchy parameters, clock assumptions, memory timings, line size, core issue and load capacities, queue entries, and whether the test includes warmup. Different simulator memory models or core models can produce qualitatively different results. gem5, for example, documents distinct memory-system models; a reported result should identify which model and configuration were used.

In a controlled experiment, run at least a baseline configuration and a changed configuration while keeping every other parameter constant. If evaluating MSHR count, ensure the workload can expose more independent misses; otherwise a zero benefit is expected and does not by itself invalidate the mechanism. If evaluating prefetchers, log useful, unused, late, and duplicate requests along with overall execution cycles and traffic volume. Include the effects of cache pollution and interference, where relevant.

Simulation results are sensitive to warmup, random seeds, instruction traces, operating-system activity, and memory scheduling. For publication, record parameters and observations rather than claiming that schematic exercises below model a commercial CPU. Hardware counters and simulation provide complementary evidence, but neither eliminates the need to state the precise architecture and benchmark conditions.

Worked Example 1: Two Independent Cache Misses

Assumptions. A fictional nonblocking cache can track two distinct missing lines; each downstream request completes exactly 100 cycles after acceptance; the lower system can process two requests concurrently. Two loads, L0 to line A and L1 to line B, are independent and already have valid addresses. Ignore a one-cycle difference in issue slots for this simplified calculation.

One unresolved miss allowedIssue AA returns; issue BB returns200 cycles
Two unresolved misses allowedIssue A and BA and B returnNo further request100 cycles

The second policy overlaps the two latency intervals; it does not make either individual request a 50-cycle memory access. The 100-cycle result is an optimistic idealization: requests might not issue on the same cycle, share a bank, suffer bandwidth contention, or return at different times. If both loads were to the same absent line A, they could instead merge into one downstream request, which would not constitute two distinct-line misses.

Interpretation. More miss capacity is useful only if the processor can generate independent requests and the lower memory system has spare service capacity. A dependent load whose address comes from A’s data cannot issue at cycle 0 merely because a free MSHR exists.

Worked Example 3: Concurrency-Limited Throughput

Assumptions. Each independent request transfers one 64-byte line. Average response time from request acceptance to completion is 120 ns under a stable scenario. The downstream memory path can sustain 12 GB/s of total line traffic if supplied with enough requests. Ignore writes and other clients.

With an average of six distinct requests outstanding, the concurrency-limited rate is 6 × 64 bytes ÷ 120 ns = 3.2 GB/s. With an average of twelve, the corresponding bound is 6.4 GB/s. To saturate the hypothetical 12 GB/s path at the same latency, the steady-state outstanding count would need to be about (12 × 10⁹ bytes/s × 120 × 10⁻⁹ s) ÷ 64 bytes = 22.5 requests, so approximately 23 on average in a suitably steady system.

Worked Example 4: Prefetch Accuracy, Coverage, and Traffic

Assumptions. A simulation compares identical workloads with and without prefetching. The baseline produces 1,000 demand misses at the chosen cache boundary. With prefetching enabled, 300 prefetched lines are later used by demand before eviction, 200 prefetched lines are never used, and 700 demand misses remain. Assume for this exercise that all 300 useful prefetches correspond to baseline misses eliminated, with no other changes to miss classification.

There were 500 issued prefetch lines. Prefetch accuracy under the stated definition is 300 / 500 = 60%. Demand-miss coverage relative to the baseline is (1,000 - 700) / 1,000 = 30%. The 200 unused lines account for 40% of issued prefetches. At 64 bytes per line, all prefetched lines represent 32,000 bytes of line traffic if each goes through the chosen transfer boundary; this is additional or shifted traffic, not necessarily 32,000 bytes of net extra DRAM reads.

Important qualification. These tidy numbers were constructed to make the definitions transparent. A late prefetch, an evicted prefetched line, an altered replacement decision, or a demand that merges into a prefetch request could make simple one-to-one accounting invalid. Even a measured 30% miss reduction does not establish 30% program speedup. The next step is to measure cycles and determine which avoided misses were on the critical path.

Worked Example 5: Choosing a Prefetch Lead Distance

Assumptions. A sequential stream advances one cache line every 15 cycles after startup; a prefetch request takes 90 cycles to deliver the line into the chosen cache level; request rate and latency remain stable; and there is enough cache capacity to retain arriving lines until demand. The access sequence is predictable without crossing a translation boundary.

An idealized prefetch should begin at least 90 / 15 = 6 line-consumption intervals before the anticipated demand. Six lines of lead would place delivery near demand arrival, leaving no tolerance for queueing variation or predictor-training delay. A somewhat larger lead could absorb modest delay, but increasing distance without bound risks wasted traffic or eviction before use.

These numbers measure the timing of requests, not cache occupancy or performance directly. A real prefetch engine may limit outstanding lines, refuse to cross page boundaries, or change its degree with confidence. The correct prefetch distance must be tested under workload-specific service-time and resource conditions.

Worked Example 6: Pointer Chain Versus Independent Arrays

Assumptions. Four distinct cache lines each require a 100-cycle miss service. The memory subsystem can process four requests concurrently. An instruction dependency is the only difference between the two artificial programs. Both programs need four lines exactly once.

Software implication. If an algorithm can be reorganized into batches of independent tasks, it may give the processor enough address information to overlap requests. This is not always possible; correctness, data layout, memory footprint, and locality may favor a sequential representation. A realistic assessment should weigh these costs rather than assuming that converting every linked structure to arrays is practical.

Assumptions. A small fictional L1 contains every line requested by four loads. It has two banks, each capable of one accepted load per cycle, and two issue opportunities per cycle. Worked Example 8: Diagnose a Misleading Memory-Bound Result

A fictional processor reports low IPC, frequent cycles with outstanding L1 misses, and substantial prefetch traffic. Its workload is a streaming scan across large records; only eight bytes from each 64-byte line are used. One might suspect an inadequate prefetcher because the program waits on data. However, high outstanding-request occupancy could instead indicate that the existing prefetcher already fills downstream queues while DRAM bandwidth is saturated.

A structured investigation would first compare prefetch-enabled and prefetch-disabled execution time, not just demand miss counts. Next it would measure useful bytes consumed versus line bytes transferred, the number of in-flight distinct lines, memory bandwidth, and whether late or unused prefetches are common. It would also examine memory placement, page translation, thread count, bank conflicts, and cache-line utilization. If 56 of every 64 bytes are unused, improving data density may reduce traffic far more than extending prefetch distance.

Now suppose the same report comes from a single linked-list traversal with only one distinct miss in flight. In that case, increased memory bandwidth is unlikely to help; the critical problem is serialized dependent misses. The same coarse label, “memory bound,” can arise from entirely different constraints. A proper diagnosis connects resource occupancy, dependency structure, and measured end-to-end performance.

Primary References and Further Reading

The sources below document specific cache, prefetch, and measurement models. They are references for the stated conceptual mechanisms, not evidence that every contemporary processor implements identical structures or follows the fictional timing values in the worked examples.

  1. gem5 Project, Classic Caches — Nonblocking classic cache model, MSHRs, write buffers, and prefetch support. The project documentation is a direct reference for miss-tracking semantics.
  2. gem5 Project, Memory System — Request flow, cache handling, and outstanding read requests through the simulated hierarchy.
  3. gem5 Doxygen, MSHR Class Reference — Programmatic representation of miss entries and multiple target requests.
  4. gem5 Doxygen, Stride Prefetcher Class Reference — Example of confidence-based stride detection in a configurable hardware prefetch model.
  5. gem5 Doxygen, Queued Prefetcher Class Reference — Prefetch queue and request-issuance abstractions, including related throttling and translation behavior.
  6. Intel VTune Profiler, Memory Access Analysis — Cache-level attribution, DRAM-bound conditions, and memory-performance investigation.
  7. Intel VTune Profiler, Top-Down Microarchitecture Analysis — A structured approach to separating memory and core resource limitations.
  8. Intel, 64 and IA-32 Architectures Optimization Reference Manual, Volume 1 — Processor-dependent optimization concepts; consult the specified revision for particular platform claims.
  9. AMD GPUOpen, Ryzen CPU Performance Guide — Practical discussion of locality, memory access, prefetch hints, and performance investigation.
  10. David Kroft, “Lockup-Free Instruction Fetch/Prefetch Cache Organization,” Proceedings of the 8th Annual International Symposium on Computer Architecture (1981) — Foundational nonblocking-cache design literature.
  11. John L. Hennessy and David A. Patterson, Computer Architecture: A Quantitative Approach, relevant modern edition — Quantitative cache performance, memory-system throughput, and instruction-window constraints.

These references have different purposes. Simulator documentation shows one explicit implementation; manufacturer guides describe particular hardware families and performance tools; textbooks and research describe transferable design principles. Never import a version-specific performance number without its hardware and measurement context.
