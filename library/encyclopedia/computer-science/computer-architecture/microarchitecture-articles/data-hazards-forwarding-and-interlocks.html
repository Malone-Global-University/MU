Definition and Architectural Context

A data hazard arises when an instruction's planned progress conflicts with the availability or ordering of a value that the instruction must read or write. In a pipelined processor, different instructions occupy different stages concurrently. A producer can be computing a result while a younger consumer is already being decoded, even though the consumer is not permitted to use an older or incorrect value. Correct control therefore depends on the difference between when an instruction needs a value and when the correct version becomes available.

Forwarding (also called bypassing) routes a produced result toward a dependent consumer without necessarily waiting for the ordinary architectural register-file write and a subsequent read. A pipeline interlock detects an unsafe timing relationship and prevents the consumer from advancing until execution can proceed correctly. These are complementary mechanisms: a forwardable arithmetic result need not force a stall, whereas a load whose memory result arrives too late can require an interlock even in a well-bypassed pipeline.

This treatment is a Level 5 Microarchitecture subarticle. It concentrates on the hardware paths, comparators, readiness information, control enables, and timed instruction traces that implement data-dependency handling. The nearby Pipeline Processing overview addresses pipeline hazards at a broader level; Register Renaming and Physical Register Mapping owns the detailed mechanism for eliminating false name dependencies.

All example schedules in this article explicitly describe a hypothetical conventional pipeline. They are not reverse-engineered descriptions of a particular processor, and actual designs may resolve operands at different stages, use variable-latency caches, forward from different points, or issue operations out of order.

Instruction Dependencies and Value Provenance

Programs specify computations whose inputs must correspond to the correct earlier assignments. Suppose instruction A computes x5 = x2 + x3, and instruction B then computes x8 = x5 + x4. B needs the version of x5 produced by A. The issue is not that the register happens to have a particular numerical name; it is that B's result is mathematically defined by A's result. A correct processor may overlap their execution or route the value through internal paths, but it cannot make B consume an earlier version of x5.

# RISC-V-like examples; all operations are register arithmetic.
A: add x5, x2, x3       # x5 := x2 + x3
B: sub x8, x5, x4       # B depends on A via x5
C: xor x9, x6, x7       # C is independent of A and B
D: add x5, x10, x11     # D writes x5 again, creating a newer version
E: or  x12, x5, x13     # E needs D's x5, not A's

A dependency graph has directed edges from each value-producing operation to the operations that consume its result. The edges impose a minimum permissible order for those reads and writes; a microarchitecture must choose a schedule and hardware routes that satisfy them. Independent C may execute alongside A or B in an organization capable of doing so, but executing E using A's x5 would be incorrect after D has created the later version.

Registers are only one form of producer–consumer relationship. A store may supply data later loaded from a matching address; an address-generation operation may depend on earlier integer arithmetic; condition flags, control registers, and vector state can carry dependencies as well. Correctness requires tracking the actual operands and architectural semantics of the instruction, including instructions with implied inputs or outputs.

RAW, WAR, and WAW: Three Different Relationships

The classic taxonomy names relationships between an older instruction and a younger one. It is important to distinguish a dependency in the instruction stream from a hazard event: the relationship exists regardless of the hardware, but a timing hazard arises only if the proposed overlap would violate that relationship.

RelationshipOlder / younger behaviorMeaningCommon treatment
RAW: read after writeOlder writes r; younger reads rTrue dataflow dependency: younger must receive older's intended resultForwarding, waiting, or issue scheduling when the value is ready
WAR: write after readOlder reads r; younger writes rAnti-dependency through reuse of a nameOrdered reads/writes or register renaming where needed
WAW: write after writeBoth write rOutput-name dependency: younger's result must be the final architectural valueOrdered commitment or physical register renaming and ordered retirement

In a textbook five-stage, in-order pipeline with reads in ID and writes in WB in program order, WAR and WAW normally do not create register hazards: an older instruction reads before younger writes, and older writes reach WB first. A separate dependence category does not imply that such a hazard can occur in every implementation. Longer or variable-latency units, early or late operand reads, and out-of-order execution can make WAR or WAW relevant if the machine lacks suitable protection.

RAW dependencies are true dependencies. Renaming can eliminate false dependencies due to name reuse, but it does not erase the need for B to receive A's computed data. Some special transformations can avoid or predict a computation, but normal register renaming alone cannot make a true producer–consumer edge disappear.

The Five-Stage Teaching Pipeline and Its Timing Assumptions

We use a simple, single-issue, five-stage IF–ID–EX–MEM–WB model: instruction fetch, decode/register read, arithmetic or address generation, data memory access, and register writeback. It has one edge-triggered clock, in-order progression, an integer ALU, and a data memory that completes a cache-hit load by the end of its MEM stage. Arithmetic results become available at the end of EX; consumers take their execute operands at their own EX stage through register or forwarding inputs. Each stage receives the prior stage's registered information at the appropriate clock boundary.

StagePrincipal workValues relevant to hazards
IFFetch instruction from current addressInstruction and PC carried forward
IDDecode sources/destination and read registersSource register indices; tentative operand values; hazard compare inputs
EXPerform ALU operation or load/store address calculationForwarding multiplexers choose producer values for ALU inputs
MEMAccess data memory for loads and storesALU result already available; load value ready only at end for a hit
WBWrite completed result to architectural registersRegister-file visibility subject to the stated read/write convention

This timing model permits an ALU result produced at the end of cycle n's EX stage to feed the next instruction's EX in cycle n+1 through an EX/MEM bypass. It does not permit a load value that appears only at the end of cycle n's MEM stage to be consumed at the beginning of that same cycle by the next instruction's EX. A conventional adjacent load-use pair consequently needs one bubble even with full EX-stage forwarding; a different clocking, a deeper pipeline, cache timing, or an earlier operand-consumption stage can change that count.

We assume that branch, exception, memory-alias, and structural constraints are absent unless a worked example states otherwise. Each schedule is a teaching device, not a blanket performance promise.

Why Register Reads Can Be Too Early

In the five-stage model, instruction B may read x5 during ID while the producer A is still in EX or MEM. The architectural register file can still contain an older x5 because A's WB event has not happened. That early read is not itself an architectural violation; it becomes dangerous only if the stale value is used as B's real operand. A forwarding multiplexer before the ALU can override a stale value captured in the ID/EX pipeline register with the correct newly produced value at the appropriate EX cycle.

This separation between the physical read time and the effective consumption time explains why many diagrams show data moving out of a register file before the actual dependency is resolved. The microarchitecture may carry both register tags and read-port outputs until EX. A comparator and control logic decide whether a later bypass should replace a stored operand. In a more dynamically scheduled design, operands may be held in an issue queue and obtained by tag-based wakeup or result broadcast rather than by a fixed five-stage bypass.

Register-file timing conventions also matter. Some teaching pipelines let a WB write and an ID read of the same architectural register occur in one clock by a defined write-first or half-cycle arrangement. Others require a same-cycle WB-to-ID bypass or an extra hold. Always specify the rule before counting stall cycles. No implementation may treat a register-file behavior as universal merely because it was assumed in an introductory example.

RAW Hazards Without a Bypass Network

Consider consecutive add and sub instructions where the second consumes the first's result. Without forwarding, the dependent instruction must not use its earlier register-file value. A hazard controller may hold the consumer in decode until the producer writes back and the correct value can be read. For the timing arrangement above, that requires an additional delay relative to a forwarding pipeline.

add x5, x2, x3   # producer
sub x8, x5, x4   # consumer

With no bypassing and same-cycle WB-to-ID visibility, the first instruction writes in cycle 5, so the consumer can complete its effective read in ID in cycle 5 and execute in cycle 6. This contrasts with an ideal independent pair executing in cycles 3 and 4. The consumer is not permitted to execute in cycle 4 using a stale value. If writes are not visible to an ID read in the same cycle, the read may need to wait until cycle 6 and the eventual execution schedule is later still.

Stalling does not mean repeatedly executing a held instruction. The control unit prevents it from crossing a stage boundary while allowing older work to drain downstream. An inserted bubble is an instruction slot with no useful side effects. The hardware must suppress writes or other actions for that bubble to prevent phantom operations.

Full forwarding makes the classic arithmetic adjacency far cheaper because the arithmetic result can travel from the producer's EX/MEM latch to the consumer's ALU input at the next EX interval. It does not accelerate the underlying computation; it removes a data-transport and visibility delay.

Forwarding Architecture: Sources, Destinations, and Multiplexers

A typical in-order datapath augments each ALU input with a multiplexer choosing among ordinary register values, an ALU result in a nearby pipeline register, and a result approaching writeback. The logic compares the consumer's source-register tags with valid older operations' destination tags. It then selects the youngest older matching producer that already has an appropriate ready value.

For a 32-bit datapath with two 32-bit ALU operands, forwarding adds input multiplexers and wires that may reach across physically separated pipeline regions. The select logic must distinguish whether a producer truly writes a register and whether the identified result is valid at the expected stage. An ALU calculation sitting in EX/MEM can be a forwarding source; a load's EX/MEM value is typically its address, not loaded data, so forwarding that value as the loaded destination would be a bug.

Forwarding also has timing costs: tag comparisons, validity qualification, priority encoding, a wider operand multiplexer, and longer wires can lengthen the critical path. Architects may insert staging, duplicate a local network, use limited clusters, or schedule workloads to reduce long bypasses. Hence bypassing is not a zero-cost solution to all dependencies. Its benefit must be evaluated against clock rate, dynamic power, and the latency of alternatives.

Readers seeking the physical porting and routing aspects should pair this chapter with Register Files and Operand Delivery. Here the essential question is which producer's result is logically correct at the required cycle.

Forwarding Comparators, Write Enables, and Destination Validity

A simple bypass selector recognizes a match between the younger instruction's source register and an older instruction's destination register only if that older instruction produces a usable register result. For a RISC-V-like core, integer register x0 is architecturally constant zero, so a purported write to x0 must not cause a nonzero bypass into a source reading x0. A RegWrite enable (or its equivalent) and a valid-operation bit are necessary qualifiers.

# Conceptual forwarding selector for the consumer in EX.
# A, B are source register tags; all stages carry validity.
if EX_MEM.valid and EX_MEM.writes_reg and EX_MEM.rd != 0
   and EX_MEM.result_ready and EX_MEM.rd == ID_EX.rs1:
    forward_A = EX_MEM.result
elif MEM_WB.valid and MEM_WB.writes_reg and MEM_WB.rd != 0
   and MEM_WB.rd == ID_EX.rs1:
    forward_A = MEM_WB.writeback_result
else:
    forward_A = ID_EX.read_value1

# Analogous logic applies to source operand rs2 when used.
# Earlier stage wins only when it is the relevant ready producer.

This is pedagogical pseudocode, not a complete RTL specification. Some instructions do not use a nominal register source; others write multiple destinations or conditionally suppress a destination. The actual decoder's uses_rs1 and uses_rs2 flags should prevent accidental matches on unused field bits. The younger operand must not be forwarded from an operation that is invalid, squashed, faulting, or otherwise ineligible.

Source and destination widths may differ. Floating-point, vector, predicate, and control-register dependencies require the proper namespace, lane masks, or other granular metadata. The principle remains the same: identify the correct older producer and confirm that its value is ready and visible under the machine's rules.

Priority Among Multiple Matching Producers

Register names can be reused by several adjacent instructions. Suppose A writes x5, then B writes x5 again, and C reads x5. C is defined to see B's result, not A's. In a five-stage in-order pipeline, B is usually closer to C than A is when C reaches EX. If both pipeline registers advertise a matching destination, the bypass from B's more recent ready result must take precedence.

A: add x5, x1, x2
B: sub x5, x3, x4
C: and x8, x5, x9   # must consume B, not A

At C's EX cycle, B may occupy MEM while A occupies WB. The EX/MEM selection is therefore higher priority than MEM/WB if the younger producer's actual result is valid and ready for forwarding. This condition matters in more elaborate designs: a late load is not a ready ALU producer just because its destination tag matches. The interlock must prevent C from using an older A value if B is the intended newest writer but has not completed yet.

This illustrates two separate requirements. Tag matching locates potential producers; program-order precedence and readiness identify the value that can legally satisfy a consumer. The correct hardware cannot be defined by equality comparators alone.

Load-Use Hazards and Why Forwarding Cannot Defeat Time

A load's EX stage normally computes an effective address. In the assumed five-stage model, the data itself arrives at the end of MEM on a cache hit. If the immediately following instruction needs the loaded destination at the beginning of its EX stage in that same cycle, no combinational forwarding wire can deliver information before it exists. The consumer must delay by at least one EX slot in this timing model.

lw  x5, 0(x2)       # data appears at end of MEM
add x7, x5, x6     # immediately uses the loaded data

An interlock detects the adjacency while the load is in ID/EX and the consumer in IF/ID. The controller holds the consumer's stage register and the fetch address, and injects a bubble in the next EX slot. The load continues into MEM, then its data is available for forwarding from the appropriate writeback-stage latch to the consumer's delayed EX. Under these explicitly stated assumptions, one bubble is sufficient on a cache hit.

Long-latency misses require waiting beyond one cycle. A different microarchitecture may do load data forwarding earlier or later, may resolve dependent operands in another stage, or may replay an instruction after a speculative early issue. The phrase load-use stall describes the dependency problem, not one universal numerical penalty.

Pipeline Interlocks: Hold, Bubble, and Advance

Interlocking is a coordinated control action, not simply a signal that disables the entire processor. On a classic load-use hazard, it is useful to distinguish three operations: hold the consumer in IF/ID; hold the PC or fetch progress so the next instruction is not lost; and inject a bubble into ID/EX so the consuming EX stage performs no architecturally effective operation in the following cycle. At the same time, older stages (EX/MEM and MEM/WB) remain able to advance and free the dependency.

Controlled objectTypical load-use actionReason
PC / fetch progressionHold current fetch position or suppress acceptDo not skip the instruction following the held consumer
IF/ID registerHold current consumerPresent the same instruction for reconsideration
ID/EX registerInsert invalid/bubble operationPrevent incorrect execution from using stale load data
EX/MEM and MEM/WBAdvance normally when downstream readyAllow producer to complete and yield its value

With a global ready/valid pipeline, the control may be phrased as backpressure and occupancy rather than explicit clock enables. More sophisticated designs may queue the younger operation and release it on a scoreboard-ready event. Whatever encoding is chosen, preservation of the consumer and exactly-once execution of every valid instruction are essential.

Stalls and flushes are different. A stall preserves an instruction for later execution; a flush invalidates work (for example after a wrong-path branch) so it will never commit. Confusing the two causes lost instructions, duplicated side effects, or use of invalid forwarding candidates.

Source-Use Timing: Loads, Stores, Branches, and Other Consumers

Not every source register is consumed in EX at the same point. A load consumes its base address for address generation; a store may consume a base address in EX and the store payload when its memory write is performed; a branch may compare operands in ID, EX, or a separate resolution stage. An interlock designed for one consumer stage can over-stall another or allow a stale value into an earlier comparator.

For example, a store following a load of the data to be stored might not need the same delay as an ALU dependent on that load if the implementation supports late forwarding into the store-data path during MEM. If the store's data is captured definitively in ID without late bypass, it may need a delay. Likewise, an ALU result forwarded into an EX-stage branch comparator can satisfy a nearby branch without a bubble in some designs, while a branch resolved in ID may require extra dependency handling because its operand is needed sooner.

Design a hazard unit from operand-use metadata rather than simply assuming that every instruction uses both source fields at the same time. Different pipeline stages, partial register writes, flags, predication, and memory-data routes make a generic register-equality rule incomplete. When comparing published diagrams, resolve stage timing before comparing reported stall counts.

Combinational Hazard Detection in a Small In-Order Core

A minimal interlock can use fields already present in the stage registers. In the teaching model, if the operation in ID/EX is a load with destination rd and the valid operation in IF/ID will read that register as a source, issue cannot proceed on the normal next-cycle schedule. A convenient conceptual predicate is:

load_use_hazard =
    ID_EX.valid && ID_EX.is_load && ID_EX.writes_reg
    && (ID_EX.rd != 0)
    && IF_ID.valid
    && (
        (IF_ID.uses_rs1 && IF_ID.rs1 == ID_EX.rd) ||
        (IF_ID.uses_rs2_in_EX && IF_ID.rs2 == ID_EX.rd)
       )

The uses_rs2_in_EX formulation deliberately calls out when the second source is required; real hazard logic may have additional conditions for a store's later data input, branch comparison, instruction-specific register subsets, and early bypass paths. A simpler teaching design might conservatively treat every used source alike, stalling even when late forwarding could avoid a bubble. Conservative interlocking may be correct yet slower.

Comparators should operate on register identifiers associated with valid instructions and a correct decode. Pipeline bubbles must carry invalid status or suppress write enables, otherwise they could be mistaken for producers. The result of this logic feeds the register enables and bubble controls described previously. With a variable-latency load, the readiness condition must track actual data availability; a fixed one-cycle delay is insufficient on a cache miss.

A good hardware review asks whether each case has both a correctness guarantee and a forward-progress guarantee. The first prevents a consumer from reading an unavailable value; the second ensures the consumer eventually advances when the producer's data becomes ready or an exception resolves the operation.

Scoreboards and Register-Readiness Tracking

A scoreboard generalizes hazard detection by remembering whether architectural or physical operands are available and what outstanding instructions may write them. Unlike a single local load-use comparator, a scoreboard can cover operations that stay busy across multiple cycles. Each destination may be associated with a pending-writer state, a readiness time, a functional unit, or a producer identifier. The issuing logic consults these records to decide whether it may launch the next instruction.

In an in-order scoreboard design, the scoreboard can block the issue of a younger consumer until an older producer's result is usable. This is especially relevant for multiplication, division, or cache operations that do not complete in a single EX interval. Some scoreboards also implement instructions with out-of-order execution while preserving constraints on operand reads and writebacks. The term scoreboarding is therefore not equivalent to either strict in-order or modern register renaming.

A Boolean busy[r] may suffice for a very simple machine with at most one outstanding writer per register. It becomes inadequate when multiple older writes to the same architectural name can be in flight; the hardware then needs producer identities, age, or a policy that prevents ambiguous overwrites. For every consumer, the logical dependency points to the nearest older writer whose result is relevant, not simply any busy writer with the same name.

A concrete, publicly documented example of scoreboarding in a model of an in-order CPU is the gem5 MinorCPU. Its modeling of timing, execute-stage scoreboarding, and forwarding illustrates how data dependencies constrain an in-order pipeline. An educational simulator is not evidence that all production CPUs implement exactly the same ready-bit structure.

Multicycle Functional Units and Result Availability

A single-cycle integer addition, a pipelined multiplier, and an iterative divider have different availability schedules. A pipelined multiplier might accept a new independent operation each cycle yet produce each result after several cycles. An iterative divider may take many cycles and accept another divide only when its internal unit is free. Forwarding must be referenced to result readiness, not merely to the position of the instruction among nearby issue slots.

For a concrete hypothetical example, assume mul x5,x2,x3 has a four-cycle issue-to-result latency, while a following add x8,x5,x4 needs x5 at execution start. Even with a forwarding network, the addition cannot consume the result until the multiplier has produced it. The core may hold the addition, place it in a waiting queue, or—in an out-of-order implementation—execute independent younger operations while it waits. The dependent latency is determined by the entire producer-to-consumer path, which includes scheduling, functional-unit time, and operand transfer.

Another dependency exists when an operation's destination is a shared special register, condition code, or accumulator that does not fit the simplest integer destination model. Microarchitectures need to model those implicit accesses too. Omitting an implicit source from hazard checks may silently corrupt results under rare instruction sequences.

Variable latency also interacts with cancellation. A squashed long-latency operation must not later broadcast a value that wakes dependents from the wrong execution path. Some operations are allowed to continue internally for implementation reasons, but their outputs must be validated against the correct speculative context before they influence architectural retirement.

WAR and WAW Hazards in More Flexible Execution Models

In a simple in-order pipeline, architectural reads and writes naturally retain the needed order, so WAR and WAW generally do not demand new hazard stalls. That changes when instructions can finish at different times or consume operands after younger instructions have executed. For example, if an older instruction still needs to read x5 but a younger one writes x5 first, the older instruction could see the wrong value: a WAR hazard. If an older long-latency operation writes x5 after a younger, faster operation has written the same name, the final state would be incorrect: a WAW hazard.

# Anti-dependency (WAR) illustration:
A: add x8, x5, x3      # A must read the old x5
B: sub x5, x1, x2      # B writes a new x5

# Output-name dependency (WAW) illustration:
C: mul x5, x1, x2      # older potentially slow writer
D: add x5, x3, x4      # younger potentially fast writer

One conservative defense is to constrain execution or writeback until reads and writes are safe. Another is to allocate different physical registers for the two successive architectural versions. With renaming, B's destination can receive a new physical register without destroying the value A must read; D's newer destination can be represented separately from C's older result. An ordered retirement mechanism then preserves the architectural outcome.

Renaming does not change the behavior of a program; it changes where intermediate versions live. The full data structures—rename maps, free lists, checkpoints, physical-register lifetime, and precise recovery—belong to Register Renaming and Physical Register Mapping and Out-of-Order Execution and Reorder Buffers.

Dependencies in Out-of-Order Scheduling

Out-of-order processors remove the constraint that every younger instruction must wait behind an older, unready instruction. They do not remove true data dependencies. A reservation station or issue queue associates each waiting operation with source values or producing tags. Once a tagged result becomes available, dependent operations may be marked ready. Arbitration selects ready operations subject to execution ports, scheduling priority, and other constraints.

Suppose instruction A is a cache-missing load, B consumes A, and C is a register-only integer addition unrelated to either. A strictly in-order issuer may be blocked by B and cannot issue C. An out-of-order scheduler may execute C before B while waiting for A. B remains constrained by its RAW edge. If the core performs speculative execution, it also needs a way to discard work from invalid paths or recover from incorrect assumptions. Out-of-order execution and in-order retirement can coexist.

Wakeup can occur through result broadcasts, tag matching, readiness-bit lookup, speculative prediction, or localized bypass structures. A practical processor may restrict the distance over which an operand is broadcast because a large all-to-all network is expensive. Wakeup and selection can become critical timing paths, creating reasons to partition queues or cluster execution units. The existence of a ready result therefore does not guarantee that its consumer executes in the next physical clock.

Memory dependencies require additional logic. A load and store with potentially equal addresses cannot be treated as merely independent because their architectural registers differ. This article limits itself to the register-dependency aspect; address aliasing and speculative load ordering are treated under the dedicated Load-Store Queues and Memory Disambiguation article.

Load and Store Operands: Address Versus Data Dependencies

Memory operations can have multiple distinct dependencies. The base address may come from an earlier arithmetic instruction, the data being stored may come from a different producer, and the operation may also depend on older memory accesses to overlapping addresses. These are not interchangeable. A store of an old value to the correct address and a store of the correct value to the wrong address are both erroneous, but they require different hazard checks and bypass routes.

A: add x10, x2, x3      # computes address base
B: lw  x5, 0(x4)        # computes store payload
C: sw  x5, 0(x10)       # address needs A; data needs B

For C, the base register x10 is needed when its effective address is formed. The data x5 may be needed later, depending on pipeline placement. A design with bypass-to-EX for addresses and bypass-to-MEM for store data can resolve the two dependencies through different physical routes. A design that requires all source values at decode has a different stall pattern.

Store-to-load forwarding is a separate mechanism from the register forwarding discussed here. It may return bytes from an older pending store to a younger load of the same location, usually under specific size, alignment, address-match, and ordering rules. Nothing about an EX/MEM-to-ALU bypass automatically supplies memory-data forwarding. Systems handling partial stores, atomics, and complex memory ordering need additional care beyond the classical RAW register comparator.

Multiple-Issue Pipelines and Same-Cycle Dependency Checks

When a decoder or issuer considers two or more instructions simultaneously, it must check dependencies within the proposed issue group in addition to comparisons against operations already in the pipeline. If the second instruction reads a destination generated by the first, a simple dual-issue organization ordinarily cannot execute both together when their required execution stages run in parallel and the first result appears only later.

I0: add x5, x1, x2       # older producer
I1: sub x8, x5, x3       # younger dependent consumer
I2: xor x9, x6, x7       # independent candidate

A two-wide strictly in-order issuer may issue I0 alone if I1 cannot pair; it may not simply skip I1 to launch I2. A more flexible issuer could pair I0 with I2 after suitable scheduling, while preserving I1's RAW dependency. An implementation with specialized intra-cycle cascading may support certain producer–consumer issue combinations, but that requires explicit datapath and timing support and should not be assumed from the word superscalar.

At width W, naive all-pairs dependency checks among candidates can grow rapidly, and hardware must also resolve branch, memory, execution-port, and destination-conflict constraints. The designer may use predefined instruction pairing rules, restricted lanes, or decentralized scheduling to control complexity. For general width concepts see In-Order, Superscalar, and Issue Width; this article owns the detailed data-dependency conditions behind such pairing.

Bypass Topology, Critical Paths, Power, and Physical Distance

A broad bypass network can require many high-fanout wires between execution pipes, register-file banks, and operand selectors. Each additional producer source demands more comparisons or tags, each consumer adds mux destinations, and wide vector or floating-point paths increase the number of carried bits. As execution units spread across a silicon floorplan, wire delay can dominate the logic delay. Forwarding that seems simple in a schematic may be physically costly at high clock rates.

Some cores therefore cluster functional units with local bypass networks, replicate results at selected points, or tolerate a transfer cycle between clusters. This may produce a nonuniform dependency latency: a dependent operation scheduled on a nearby execution port can run earlier than the same kind of operation on a remote cluster. The compiler, instruction scheduler, or hardware issue policy may attempt to keep dependent chains local.

Power considerations are as important as maximum throughput. Driving long wide buses on every clock consumes energy even when the core does no useful dependent work. Operand gating, segmented broadcasts, selective wakeups, and banked routing can reduce switching. But reducing the network can produce additional stalls for some workloads. Effective design weighs latency reduction against frequency, area, energy per instruction, and the distribution of real operand dependencies.

A practical review should ask how many producers can be forwarded simultaneously, how conflicts are prioritized, which instruction classes use the network, whether values cross clock or voltage domains, and whether writeback may proceed when the forwarding path is blocked.

Exceptions, Squashes, and Validity of Forwarded Results

Forwarding must never introduce an architecturally invalid result. A branch misprediction, exception, replay, or aborted speculation can make an operation's computed bits irrelevant. A value may have been physically calculated without being allowed to update the architectural state. Tag comparison alone cannot distinguish a correct producer from an operation that the core has already invalidated.

In a small in-order core, each stage commonly carries a valid bit and control fields indicating whether the operation writes a register. A flush clears the validity of younger wrong-path work. In a speculative processor, producer tags may also be associated with epochs or recovery contexts so that a result from an obsolete execution cannot awaken a new operation that happens to reuse an identifier. These are general design principles; the precise protocol varies greatly.

Stalling and flushing may arrive simultaneously. The control specification must establish priority: for instance, an instruction known to be on an invalid path should be discarded even if a generic dependency detector would otherwise hold it. Older precise exceptions and correct-path redirects determine which instructions remain legitimate. A forwarding network must not accidentally select data from squashed operations, and architectural register writes or device side effects must not escape from bubbles.

This subject touches the boundary with Speculative Execution, Checkpointing, and Recovery. Here the narrower requirement is that only a correctly ordered and eligible producer may supply each consumer's operand.

Compiler Scheduling and Insertion of Independent Work

Compilers can sometimes move independent instructions between a long-latency producer and its consumer. If a load in the teaching pipeline is followed immediately by a dependent addition, a single bubble is required. If a safe independent instruction is placed between them, the dependent addition's EX stage starts one cycle later and can receive the load value without a hardware-inserted bubble. This is a scheduling opportunity, not a change in program meaning.

# Before, immediate dependent use:
lw  x5, 0(x2)
add x7, x5, x6
xor x9, x10, x11

# After, only if the XOR is independent and reordering is legal:
lw  x5, 0(x2)
xor x9, x10, x11
add x7, x5, x6

Real instruction motion must preserve exceptions, visible memory ordering, register definitions, control-flow conditions, and any ISA-specific constraints. The independent operation cannot be moved if it alters an input, crosses an operation whose observable effect must remain ordered, or changes which exception appears. In some circumstances, compilers use loop unrolling, software pipelining, or register allocation to increase available independent work, but the additional instructions and code size can themselves change cache behavior.

Scheduling is not an alternative to correct interlocks. Software may not know all variable memory latencies, pipeline revisions, or execution paths; general-purpose processors must maintain architectural correctness for legal code even when the schedule is unfavorable. Some historical exposed-pipeline designs place greater responsibility on the compiler, but that is an explicit ISA and toolchain contract, not an excuse for omitting necessary hazard protection.

Worked Example I: An Adjacent ALU-to-ALU RAW Dependency

In the stated five-stage pipeline, consider two consecutive arithmetic instructions. The producer's ALU result is latched into EX/MEM at the end of cycle 3. The consumer reaches EX in cycle 4, when the result is accessible through a forwarding path. The consumer does not need to wait until the producer writes the register file in cycle 5.

A: add x5, x2, x3
B: sub x8, x5, x4
InstructionCycle 1Cycle 2Cycle 3Cycle 4Cycle 5Cycle 6
A: addIFIDEXMEMWB—
B: sub—IFIDEX + bypassMEMWB

Cycle 3 is the key checkpoint. B may have read an old x5 in ID, but it also carries the source tag x5. During cycle 4, forwarding controls match that source to A's ready destination and select the newer arithmetic result as B's EX operand. The operation now computes using the correct value. A's later WB still updates architectural state on the established path.

This is an example of zero additional stall cycles for an adjacent ALU RAW dependency given the defined forwarding and latch timing. It is not proof that all producer types, instruction widths, or CPU generations have zero dependency penalty. If the arithmetic path itself has extra latency or the forwarding destination lies beyond B's operand deadline, additional delay may remain.

Worked Example II: One Load-Use Bubble on a Cache Hit

Now replace A with a load. Its address is computed during cycle 3, but the loaded value arrives only at the end of cycle 4. B would normally start EX during cycle 4; this is too soon. The interlock retains B in decode through that cycle, inserts one bubble into EX, and permits B to execute in cycle 5 when the load result can be forwarded.

L: lw  x5, 0(x2)
U: add x7, x5, x6
InstructionC1C2C3C4C5C6C7
L: loadIFIDEXMEM: data ready at endWB——
U: add—IFID: hazard detectedID heldEX + forwardMEMWB
Bubble———EX———

The processor must hold the appropriate earlier-stage control state while L advances. U is not fetched twice, and the bubble is not an instruction that writes a destination. In cycle 5, the forwarded load result replaces any earlier stale read of x5. If the load misses in the cache, this fixed one-bubble schedule is no longer sufficient; the consumer must wait or be replayed until data is ready.

A frequent timing error is to draw L's MEM and U's EX in the same cycle and then claim forwarding can cross between them because both boxes appear next to each other. The direction and moment of data availability determine legality. End-of-cycle MEM output cannot ordinarily supply a beginning-of-cycle EX input in that same cycle without a specifically defined timing arrangement.

Worked Example III: Double Matching and the Newest Writer

Three adjacent instructions illustrate why bypass selection requires priority, not just a yes/no comparator. The first two both assign x5; the third consumes that register. At the consumer's EX interval, two older pipeline latches can contain matching rd tags.

A: add x5, x1, x2       # version 1
B: sub x5, x3, x4       # version 2 supersedes version 1
C: and x8, x5, x9       # consumes version 2
CycleABCCorrect result selection
3EXIDIFA produces version 1
4MEMEXIDB produces version 2
5WBMEMEXForward B's version 2

In cycle 5 the most recent older writer B wins. A's result is available but semantically obsolete for C. A naive forwarding network that chooses the oldest matching pipeline latch could compute an incorrect answer despite every ALU working properly. The selection policy must also exclude invalid or unready producers; if B were a late load, C would need to wait for B rather than substitute A's older value.

This example uses only architectural register names; in a renaming machine, the two values may reside in different physical registers and C's source mapping would identify B's version directly. The requirement that C receive the latest preceding architectural definition remains unchanged.

Worked Example IV: Filling a Load-Use Slot with Independent Work

Consider a load, a dependent addition, and an unrelated XOR. If the XOR is safe to move before the addition, a compiler may fill the delay between the load and the consumer with useful work. With the stated five-stage timing, the XOR executes in cycle 4 while the addition executes in cycle 5, and the load result is ready for forwarding to the addition.

OrderExecution after load EX in C3Consequence under teaching assumptions
Load → dependent ADD → independent XORC4 is an interlock bubble; ADD executes C5; XOR executes C6One explicit load-use stall
Load → independent XOR → dependent ADDXOR executes C4; ADD executes C5No inserted bubble; useful instruction occupies the gap

Both sequences allow the ADD to use the loaded value at C5, but only the reordered sequence performs additional useful work during C4. In a long loop this can improve sustained throughput. It does not make the load complete sooner: it hides part of the producer–consumer delay behind independent computation.

The reordering is legal only if the XOR does not change an input of the load or addition, cannot introduce an observably different exception or side effect, and respects the required memory and control ordering. Machine-specific instruction scheduling should also consider whether other bottlenecks—issue ports, cache pressure, or branches—offset the benefit.

Worked Example V: A Latency-Four Multiply and an Independent Instruction

Assume a hypothetical multiplication launches at the beginning of cycle 10 and its result can first be consumed at the beginning of cycle 14. A dependent addition cannot legally execute earlier than cycle 14, even if the multiply unit accepts a new independent multiplication each cycle. A separate independent XOR may execute during the waiting interval if the processor supports issuing it without violating program order or if the compiler schedules it ahead of the consumer.

Latency answers when the multiply's particular result becomes usable; initiation interval answers how often another multiply can begin. A multiply unit with latency four and initiation interval one may sustain one independent multiply per cycle, but a chain where each multiply uses the previous result may advance at a much lower rate. No amount of result-bus width can forward an operand before its arithmetic result exists.

For a strict in-order issuer, the dependent ADD at the head of the issue stream can block a younger XOR; moving the XOR before it may fill a slot. For an out-of-order scheduler, the independent XOR can be selected while the ADD waits. The mechanisms differ, but the underlying dataflow constraint is identical.

Worked Example VI: Translating Hazard Bubbles into IPC

Suppose a hypothetical single-issue five-stage processor retires 800 instructions. Ignoring hazards, branch penalties, and memory misses, assume one instruction enters each cycle, so the total time including pipeline fill and drain is 804 cycles in this simplified model. If 80 independent load-use events each insert one additional bubble without overlapping other penalties, the time becomes 884 cycles. The observed instruction throughput across this one interval is:

IPC = 800 retired instructions / 884 cycles ≈ 0.905. Equivalently, CPI = 884 / 800 = 1.105. At 2.0 GHz, the 884-cycle interval corresponds to 884 / (2.0 × 10^9) seconds = 442 ns, under the assumptions and ignoring any external measurement costs.

Now suppose useful scheduling removes 40 of the 80 bubbles while leaving every other property unchanged. The interval becomes 844 cycles; IPC ≈ 0.948, and CPI = 1.055. The cycle reduction is (884 − 844) / 884 ≈ 4.52%. These numerical values are teaching illustrations, not benchmarks of RISC-V, Arm, or x86 processors.

Two pitfalls matter. First, an IPC figure derived from a short sequence includes fill/drain overhead and need not equal steady-state IPC for a long workload. Second, penalties may overlap: a backend stall can coincide with an instruction-cache miss or branch recovery. A real performance model should avoid simply adding every counter as if all stall causes are independent. Retired instructions, elapsed cycles, and clearly defined event attribution provide the foundation for credible analysis.

These mechanisms are not mutually exclusive. A modern machine can use renaming to remove name hazards, an issue queue to wait for operands, a bypass to deliver ready results, and interlocks or replay for unavailable memory data. A small teaching core can use only explicit holds and a two-level ALU bypass. Selection should follow the desired performance, timing, power, and verification budget rather than a claim that one design is universally superior.

Design and Performance Investigation Framework

For a concrete processor or simulator, first reconstruct the operand path and its timing. Identify where instruction sources are named, where register values are obtained, where each operation class produces a result, and where a consumer actually requires it. Only then should the number of bubbles be inferred from a diagram.

Diagnostic questionEvidence to collectLikely area to examine
Does the consumer receive the wrong older value?Producer and source tags, stage valid bits, operand mux selectionMatch priority, invalid writes, missing bypass
Does an ALU chain stall unnecessarily?Result-ready cycle versus consumer EX cycleForwarding coverage or conservative interlock
Does a load chain hang on a cache miss?Miss response, scoreboard readiness, replay and hold signalsVariable-latency wakeup and progress protocol
Does widened issue fail to help?Issue slots, group RAW checks, ports, ready-queue occupancyWithin-group dependencies and head-of-line blocking
Is performance sensitive to register allocation?Renaming policy and WAR/WAW stalls, if anyName dependences rather than true RAW dataflow
Are results corrupted after a redirect?Validity, flush priorities, wrong-path producer tagsStale forwarding or scoreboard entries after squash

For a performance study, distinguish dependency stalls from resource stalls, cache misses, and control-flow recovery. An unavailable operand can manifest as an issue-queue occupancy problem, but the numerical throughput cost may depend on whether other operations ran during that interval. When a stall counter is processor-specific, consult the exact counter definition before translating it into lost cycles.

Verification Checklist and Directed Instruction Tests

Correctness requires more than checking one adjacent addition. A useful verification suite compares the processor's architectural results against a trusted sequential reference model and additionally inspects internal pipeline control where possible. The following cases target distinct failure modes.

Test sequenceExpected property
ALU producer followed by ALU consumerCorrect newest value; no unnecessary stall with the modeled ALU bypass
Load followed immediately by dependent ALUCorrect bubble count for documented memory timing; no stale operand
Two producers of the same register, then consumerNewest eligible preceding producer takes forwarding priority
Instructions writing x0 then reading x0Constant-zero semantics; no invented dependency or nonzero bypass
Instruction with encoded but unused source fieldUnused field does not trigger a false hazard
Store using independently produced address and dataEach operand is delivered at its actual use stage
Long multiply, divide, or cache missConsumer waits until the result is valid; no fixed-delay shortcut
Flush arriving during a data stallWrong-path consumer is discarded; no duplicate execution
Back-to-back same-destination writes with different latenciesArchitecturally correct final version and precise state

Assertions can formalize critical invariants: no valid consumer executes with a required unready source; no invalid operation writes the architectural register file; an interlocked instruction is eventually either issued or legitimately flushed; and a forwarded operand equals the most recent eligible older producer's value. Randomized sequences should complement directed tests by varying registers, instruction types, timing, branch redirects, and memory responses.

Finally, verify performance assumptions separately from correctness. A bypass control may produce correct results but add a cycle that the design did not intend; conversely, a missing stall may improve synthetic IPC while corrupting data. Both outcomes are failures, but they require different diagnostic evidence.

Common Misconceptions and Essential Distinctions

“A RAW dependency always forces a stall.” False. A correctly timed forwarding path can satisfy many arithmetic dependencies with no added bubble. “Forwarding means the register file was updated sooner.” False. Forwarding can supply a consumer independently of the normal architectural writeback time. “All loads cost one extra cycle.” False. The one-bubble example applies to an adjacent dependent load with defined memory timing; an independent successor needs no load-use bubble, while a miss may take many additional cycles.

“WAR and WAW are true data dependencies.” They are usually name-related anti/output dependencies, and renaming can remove them; RAW records genuine value provenance. “An in-order pipeline always suffers WAR and WAW hazards.” No. The standard ordered five-stage pipeline avoids register WAR/WAW hazards through its read/write timing and execution order. “If two pipeline registers match a source, either forwarded value works.” No. The consumer requires the newest relevant older definition that is actually ready.

“A stall and a flush do the same thing.” No. A stalled instruction is preserved for later; flushed work is discarded. “Superscalar issue can always skip a dependent instruction.” Not with strict in-order issue. “A scoreboard is just a forwarding mux.” No. A scoreboard tracks outstanding dependency/readiness state, while a forwarding mux selects the actual operand data source.

“A store has one generic operand timing requirement.” Not necessarily. Address and data may be consumed at different stages. “One cycle in a textbook table is a universal hardware guarantee.” No. Clocking, forwarding distance, cache design, and functional-unit latency must be stated. Correct hazard analysis starts from the actual machine rather than the visual proximity of pipeline boxes.

Specialist Glossary

Anti-dependency
A WAR relation where a younger write must not destroy a value before an older instruction reads it.
Architectural register
Programmer-visible register named by the instruction-set architecture, potentially mapped onto a separate physical register.
Backpressure
Flow-control mechanism preventing a stage from accepting additional work when its downstream capacity or required operand is unavailable.
Bubble
Invalid or deliberately empty pipeline slot inserted so other instructions can preserve their required timing or ordering.
Bypassing
Direct operand delivery from a result-producing stage to a consumer, without necessarily waiting for an ordinary register read after writeback.
Clock boundary
Timing boundary at which pipeline state is transferred or latched under the specified clocking model.
Consumer
Instruction that requires a value produced or defined by an earlier operation.
Critical path
Longest relevant combinational delay constraining a pipeline stage's clock period.
Data hazard
Timing or ordering conflict in a proposed schedule involving the values that instructions read or write.
Dependency chain
Sequence of producer–consumer edges that constrains how soon later work can become ready.
Destination tag
Identifier used to associate a producer's result with the logical or physical register it defines.
EX/MEM register
Teaching-pipeline register carrying state from the execution stage into the memory stage.
Forwarding mux
Selector choosing between an ordinary operand and one or more eligible bypass sources.
Forwarding priority
Rule selecting the newest relevant older ready producer when several destinations match one consumer source.
Head-of-line blocking
Delay of otherwise eligible younger work behind a stalled older instruction in a constrained issue organization.
ID/EX register
Teaching-pipeline register carrying decoded operation state and operands toward execution.
Initiation interval
Minimum spacing between launches of successive independent operations on a functional unit.
Instruction-level parallelism
Opportunity to execute multiple instructions concurrently without violating dependencies.
Interlock
Hardware control that holds or delays an operation until conditions for safe execution are satisfied.
Issue queue
Buffer retaining instructions or micro-operations until operands and execution resources permit launch.
Load-use delay
Scheduling delay when a dependent operation requires loaded data later than the pipeline can ordinarily provide it.
MEM/WB register
Teaching-pipeline register carrying completed memory or arithmetic result state toward writeback.
Memory dependency
Ordering relationship among accesses that can refer to the same memory location, distinct from register-name dependency.
Operand readiness
Condition that the correct producer's input data is available in time for the consumer's execution.
Output dependency
WAW relationship in which two operations define the same architectural destination.
Physical register
Internal register storage allocated to a particular value version within a renaming processor.
Pipeline flush
Invalidation or removal of instructions that must not continue, often following a control redirect or exception.
Producer
Instruction or operation defining a value needed by one or more consumers.
RAW dependency
Read-after-write relationship requiring a younger read to obtain the result of an older writer.
Readiness scoreboard
Hardware state recording which operands or outstanding producers are ready for issue or execution.
Register renaming
Mapping architectural register names to physical value versions to remove many WAR and WAW name conflicts.
Replay
Reexecution of an operation whose earlier speculative attempt did not yield an acceptable committed result.
Reservation station
Structure holding operations and their source values or tags for readiness tracking and dynamic issue.
Retirement
Architecturally ordered acceptance of completed instruction effects in designs supporting speculative or out-of-order execution.
Scoreboarding
Tracking resource and operand availability to prevent unsafe or unavailable instruction execution.
Source-use stage
Pipeline point where an instruction actually needs the correct source value.
Squash
Discarding an invalid speculative or wrong-path operation so it cannot affect architectural state.
Stall
Delay of stage advancement or issue while an operation's prerequisites are unresolved.
True dependency
Producer–consumer relationship representing required dataflow rather than reuse of a register name.
Valid bit
Pipeline-state flag distinguishing a real operation from an empty, squashed, or otherwise invalid entry.
WAR dependency
Write-after-read relation where a younger writer must not overtake an older operand read.
WAW dependency
Write-after-write relation where the newest program-ordered definition must be the visible final value.
Writeback
Stage or event delivering the completed result to architectural or appropriate internal register state.

The term forwarding can also describe store-to-load forwarding in a memory subsystem. This glossary's primary usage refers to register-operand bypassing; the mechanisms differ in source, matching conditions, and timing.
