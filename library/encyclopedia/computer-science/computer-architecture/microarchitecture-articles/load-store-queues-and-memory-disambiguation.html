Scope, Definition, and Architectural Context

A load–store unit (LSU) is the processor subsystem that coordinates memory-access instructions: calculating or receiving addresses, managing outstanding loads and pending stores, resolving ordering dependencies, interacting with the data cache and translation hardware, and reporting completion to the rest of the core. Many out-of-order processors use a load queue (LQ) and store queue (SQ), collectively called a load–store queue (LSQ). Their purpose is not merely to hold data. They preserve enough program-order and address information to decide whether a younger memory operation may proceed without violating the instruction set architecture (ISA).

Memory disambiguation asks whether memory operations whose addresses may not yet be known can be proved independent or must be treated as potentially dependent. For registers, renaming gives a direct mapping between producers and consumers. Memory references are harder: two instructions that name different base registers may nevertheless refer to identical or overlapping bytes. A pointer calculation, virtual-to-physical translation, or an older instruction's delayed operand can postpone the moment when overlap becomes known.

The Fundamental Memory-Dependence Problem

Consider a program containing an older store S: STORE [A] ← 9 and a younger load L: R ← LOAD [B]. If A and B refer to disjoint byte ranges, the operations might overlap internally, subject to architectural ordering and implementation resources. If they overlap, the load may have to observe the older store's relevant bytes. The hard case is that A is not yet computed when B becomes ready. A fast processor wants to issue L now; a conservative processor may instead wait until the potential alias is resolved.

A memory read-after-write (RAW) dependence is a true data dependency when a younger load needs bytes produced by an older store. It differs from an ordinary register RAW dependence because the relationship becomes evident only after address calculation and often translation. The relevant test is overlapping address ranges, not equality of instruction mnemonics or base-register names. A 1-byte store at 0x1003 and an 8-byte load at 0x1000 overlap even though their starting addresses differ.

There are two broad options. Conservative scheduling holds the load until sufficient information is available. Speculative disambiguation issues the load under a prediction of independence and validates that choice when earlier stores become known. Neither option changes the programmer-visible memory semantics. The choice affects the amount of useful work done early, the frequency of expensive replays, and the complexity of the hardware that detects mistakes.

Memory-Operation Timeline and Basic Vocabulary

A memory instruction passes through several logical milestones. For a load: dispatch or queue allocation, operand readiness, effective-address generation, translation and permission checks, dependency lookup, data access or forwarding, writeback, and eventual retirement. For a store: queue allocation, address preparation, data preparation, eligibility to retire, retirement or commit, and subsequent communication of the write to the memory hierarchy. A design can overlap, combine, or subdivide these milestones; no universal stage count exists.

Issue means a ready operation is selected for a functional pipeline. Execution/completion means the operation has produced or accepted the relevant data and status. Retirement means its architectural place has been committed. Visibility means another observer is permitted to observe the memory effect under the applicable consistency and coherence rules. A store can retire while still buffered and not yet globally visible. A younger load may also obtain data from an older locally buffered store before that value has reached the cache.

Load Queue: Tracking Outstanding Reads

An LQ entry generally identifies the load's position in the instruction stream and tracks enough information to manage execution and validation. Depending on the design, fields can include a reorder-buffer identifier, sequence number, destination or completion status, effective and translated address, access size, byte mask, speculative-execution flags, dependency tracking, and whether the load obtained data from memory or from a forwarded store. Some processors use several separate structures rather than a single monolithic load queue.

Many implementations allocate an LQ slot before the load issues, so that the load retains its place among older and younger memory operations. A successful cache hit does not always mean its ordering obligations have ended: an unresolved older store might later reveal that the load executed too early. A load may therefore be complete as a data producer but still speculative as a memory-order decision. Retirement or a defined validation point determines when its entry can be safely reclaimed.

An LQ may also support checks between loads, for example when the memory model and coherence protocol require observation of same-address reads in a particular order. Such checks are separate from store-to-load forwarding. BOOM and XiangShan expose different mechanisms for these responsibilities, illustrating that the term “load queue” describes a family of control responsibilities rather than one universal circuit.

Store Queue: Addresses, Data, and Program Order

The store queue holds information about in-flight stores so later loads can determine whether they depend on those writes. An entry may contain age or sequence, store address, valid-byte mask, write data, and several independent state bits—such as whether address and data are ready, whether translation or exception checks have succeeded, whether the store has retired, and whether it has been issued to the cache-facing interface.

Address readiness and data readiness are distinct. A store can know where it will write before it knows what it will write, or vice versa. Some pipelines execute separate address-generation and store-data operations; others keep the instruction together when both operands are ready. The scheduling choice is an optimization. The correctness requirement is that a younger load overlapping the store cannot consume an obsolete value merely because one part of the older store remains unresolved.

Store entries also provide the order among multiple stores to the same location. The younger load generally needs the bytes supplied by the youngest relevant older store, or a composition of several older stores when the architecture and forwarding design permit. It must not accidentally forward data from a younger store that occurs after the load in program order. Queue indexing, age comparison, and branch recovery rules make this distinction reliable even when execution order differs from program order.

Speculative Store Queue Versus Committed Store Buffer

The expressions store queue and store buffer are often used loosely, but their separation is essential to reason about recoverability. A speculative SQ stores information about operations that may be squashed after a branch misprediction or exception. A committed store buffer, where present, accepts stores that have passed the architectural commit point but have not yet drained through the cache hierarchy or reached the relevant visibility point. Some implementations combine storage, with committed status determining whether an entry may be drained; others use physically separate stages.

An uncommitted store normally cannot create an irrevocable externally visible write: otherwise a wrong-path instruction could change memory or device state. After commitment, the store's visibility is governed by the ISA memory model, the cache-coherence protocol, and any ordering instructions. Retirement alone does not prove that every other processor can already read the new value. Forwarding can allow the same core to read its own buffered write in the meantime.

This distinction becomes especially important for memory-mapped device registers. A speculative store to a device might have irreversible side effects that no branch recovery mechanism can undo. Implementations therefore impose separate ordering and non-speculation constraints for non-idempotent or strongly ordered device memory rather than treating it like ordinary cacheable RAM.

Program Order, Execution Order, and Memory Order

An out-of-order core tracks at least three different orders: program order, the sequence prescribed by the thread's instructions; internal execution order, the times instructions issue and produce results; and an architecturally permitted memory order, the order and values visible under the ISA's consistency contract. A machine may allow a younger independent load to execute before an older store's cache access while still enforcing a valid memory model.

For example, an older store to X can remain buffered while a younger load from unrelated Y issues. On a weakly ordered ISA, this can be permitted without a fence; under a stronger model the hardware may still allow internal overlap while constraining what can be observed. The specific outcome depends on the ISA and memory type. It is incorrect to infer the full memory model from the apparent order in a cycle-level timing diagram.

Cache coherence and memory consistency answer different questions. Coherence helps coordinate writes and reads for particular cache lines or locations across agents. Consistency specifies the allowed orderings and observed values across memory operations. The LSQ is part of an implementation that must satisfy both relevant constraints; it does not, by itself, define either architecture-wide contract.

Effective Addresses, Byte Ranges, and Translation

An address-generation unit (AGU) commonly computes an effective or virtual address from a base, displacement, and sometimes scaled index. The LSU then collaborates with the data TLB and page-walk hardware to obtain the physical address and access attributes required for the final transaction. Access size and byte enable information determine which memory bytes are touched. These steps may run in parallel with cache lookup or forwarding preparation, but their completion and correctness remain implementation-dependent.

Comparing addresses can be deceptively complicated. Two virtual addresses can refer to the same physical bytes through different mappings; conversely, identically numbered virtual addresses in different address spaces may not refer to the same physical storage. A design that checks speculative aliasing with partial or virtual tags must have a correctness mechanism for translation, aliases, and physical-address validation. Large caches and LSQs commonly use staged comparison or filtering to manage timing cost.

Misaligned and page-crossing operations can span two access units, cache lines, or translation pages. Their byte sets must be accounted for even if the core internally splits them into multiple micro-operations. Whether an ISA permits, faults, or gives special atomicity to a particular misaligned access is a separate architectural question. The neighboring Address Generation, TLBs, and Page Walks article covers translation mechanisms in depth.

Age Ordering: Identifying the Relevant Older Stores

A load can depend only on stores that precede it in the same thread's relevant program order. When the LSU compares addresses, it must first filter candidates by age: the matching store must be older than the load. Then it must determine which older store or combination of older stores supplies the requested bytes. Using an older but superseded store would be a data-correctness failure; using a younger store would violate instruction order.

Circular queues add a subtle engineering issue. Physical array indices wrap around, so the numerical comparison store_index < load_index does not always identify which entry is older. Implementations rely on head/tail state, allocation epochs, sequence tags, or queue-specific age comparison. Branch recovery must also preserve which entries remain valid after younger entries are canceled.

For example, if program order is S1 [X]←4, S2 [Y]←7, S3 [X]←9, L [X], then L needs the value of S3 if all accesses are the same complete word and no intervening event changes semantics. S1 matches the address but is no longer the newest older writer. A parallel comparator can find multiple candidate hits; priority resolution must respect age rather than physical slot position.

Address Comparisons and CAM-Like Search

A simple LSU may compare a ready load address against several older store addresses in parallel. The hardware behaves like a content-addressable search: candidate tags and byte masks are examined and matching entries are reported. Real implementations may use segmented comparisons, partial tags, banks, pipelined searches, store-set filters, or other optimized structures rather than a literal fully associative CAM on every path.

The comparator must distinguish no overlap, definite overlap with available forwarding data, overlap with unavailable data, and unknown older-store address. “Unknown” is not the same as “does not overlap.” A memory-dependence predictor may choose to let a load run past the unknown case, but correctness then depends on detecting and repairing any harmful misprediction.

Comparator cost grows with queue capacity, number of load ports, address width, and byte-mask logic. A two-load-port design may require more search bandwidth than a one-load-port design, even if both issue the same number of ALU instructions per cycle. Designers therefore trade off associativity, latency, banking, predictor quality, power, and the probability of a late replay.

Store-to-Load Forwarding: The Central Data Path

Store-to-load forwarding permits a load to receive required bytes directly from an older store held locally in the SQ or a committed store buffer. Instead of waiting for the store to reach the data cache and then fetching those bytes, the load can use the pending write as its source. Forwarding is both an optimization and, in many cases, part of how a core preserves read-your-own-write semantics efficiently.

A typical decision requires that the store be older than the load, their addressed byte ranges overlap appropriately, the store data be valid, and no younger intervening older store override the forwarded bytes. The load also needs to pass—or defer correctly—its translation, permission, exception, and memory-type checks. Forwarding is not simply comparing two starting addresses and copying the older store's full word.

Different processor families have different forwarding restrictions. Some can merge bytes from multiple stores or combine forwarded bytes with cache data; others require a complete match or replay partial-overlap cases. An ISA usually specifies the value the load must eventually observe, not which microarchitectural forwarding configuration must implement that result.

Byte Masks, Width Mismatches, and Partial Overlap

Memory-access sizes are central to correct forwarding. Suppose a four-byte store writes bytes 0x1000–0x1003, and a younger eight-byte load reads 0x1000–0x1007. The store covers only the low half of the load. The remaining bytes may come from another older store or the cache, but a processor cannot assume a single four-byte forwarding source supplies all eight bytes.

A byte-enable or coverage mask marks the lanes each store changes. When several older writes contribute, the value for each requested byte should come from the appropriate latest writer, while the parts not covered by buffered writes may come from the memory system. Hardware choices include byte-wise merge, forward only on full coverage, and stall/replay until a supported combination is available. The correct choice is determined by the design, not by one universal rule about “partial forwarding penalties.”

Forwarding Priority Across Multiple Storage Levels

A core may source a load from several places: the speculative SQ, a committed store buffer, a write-combining structure, and the L1 data cache or lower memory hierarchy. These are not interchangeable sources. If the same byte appears in several, the LSU must choose the version justified by program order and architectural visibility, typically giving eligible newer local writes priority over older cache contents.

The design can perform a lookup sequentially or in parallel with the cache. Parallel checking reduces latency when no store conflict exists but can require canceling a tentative cache response when a matching store is found. A merged-source load is particularly demanding because every lane must come from the correct version and any exception or access-attribute restriction must still be respected.

XiangShan's published design documentation, for example, describes forwarding sources that include a store queue and a separate store buffer before falling back to cache data. BOOM describes killing a tentative memory request when an older matching store is found, then forwarding when data is available. These are useful documented design examples, not assertions that all processors have the same hierarchy or selection timing.

Unknown Older Store Address: Wait or Speculate?

An older store may not yet have a known address because its base register is waiting on an ALU result or cache-dependent pointer chain. A younger load might already have an address and could make progress if it does not alias. Stalling every younger load until every older store address resolves would be safe in many conventional cases but could sharply reduce memory-level parallelism.

Speculation allows the younger load to access memory under an independence prediction. The machine records enough information to revisit the choice when the older store address becomes known. If the address ranges do not overlap, the early load was useful. If they overlap and the data the load consumed was incorrect under the relevant ordering rules, a memory-order violation must be reported and the dependent architectural computation repaired.

Not every matching address automatically indicates a violation: a load might have been held, forwarded from the correct older store, or otherwise executed under a valid ordering. The detector must consider load age, the source and timing of its data, any intervening writes, and the target memory model. Conservative issue policies may reduce wrong-speculation cost at the expense of withholding useful loads.

Memory-Dependence Predictors and Store Sets

A memory-dependence predictor (MDP) estimates whether a load is likely to conflict with older stores whose addresses are not yet resolved. Rather than choosing “all loads wait” or “all loads speculate,” a predictor can learn that particular instruction sites frequently alias and hold those loads until the likely producer store is ready. Its state is a performance heuristic, not an architectural guarantee.

One established family is store-set prediction, associated with the research of George Chrysos and Joel Emer. The predictor groups loads and stores observed to have dependencies, enabling a load to wait for a relevant predicted store. A store-set ID table and last-fetched-store tracking are one possible implementation. The gem5 out-of-order model includes store-set-related data structures, providing a documented simulator example. Other approaches employ PC-indexed confidence, distance history, correlation, or conservative fallback.

A false positive—predicting dependence where no bytes overlap—causes unnecessary waiting. A false negative—predicting independence where an older store does matter—may cause an expensive replay. Predictor size, aliasing between unrelated instruction PCs, training policy, and context effects all influence performance. No predictor may exempt the correctness hardware from validating memory ordering before architecturally accepting the load.

Load Sleep, Wakeup, and Retry Policies

If an LSU finds a matching older store with an address but no data, it may put the load to sleep until the store's payload arrives. If the needed translation is missing, cache resources are full, or the memory interface returns backpressure, the load may similarly wait or enter a retry queue. A wakeup policy should reflect the actual blocking event, not simply rerun every stalled load every cycle.

Common implementation strategies include explicit notification when store data becomes valid, periodic retry, queue scans, issue-queue reinsertion, and dedicated load replay structures. Each balances control complexity against latency and energy. A machine that delays waking a load until the next polling interval spends cycles even though the producer is ready; a machine that wakes too aggressively may perform repeated comparisons with no prospect of success.

Reexecution for a resource reason—such as an unavailable cache miss-status holding register—is not necessarily a memory-order violation. The same word “replay” covers several mechanisms with very different corrective scope. The LSQ must report enough reason and age information to choose between a local retry, rescheduling a single load, selective reexecution of dependents, and full younger-instruction recovery.

Detecting a Store–Load Ordering Violation

A common violation case begins when a younger load executes before an older store's address is known. Later, the store address becomes available and overlaps the load's bytes. The LSU must determine whether the younger load consumed a value it should not have consumed. This requires checking a record of younger executed loads and the source of their values, often using LQ address tags and state bits.

A store-address search of younger loads can identify suspect overlaps. Some cores perform checks when the store address is generated; others have additional validation at store commit or a separate queue stage. Detection must respect program order and avoid flagging harmless address matches. If a newer eligible store already supplied the correct bytes to the load, an earlier matching store need not imply incorrect data.

The correction mechanism then invalidates the relevant load and any results that depend on its wrong value. Recovery may restart at the load or at an implementation-defined older boundary and can involve reclaiming physical registers, restoring rename maps, canceling outstanding cache transactions, and reissuing instructions. It is important to say which design is being described: BOOM documentation illustrates pipeline flushing for certain violations; other processors may employ narrower replay policies.

Replaying Loads Without Confusing Control-Flow Squashes

A memory-order replay and a branch misprediction squash both undo speculative work, but their causes differ. A branch squash removes instructions from a path that should not have executed. A memory-order replay can arise on an otherwise correct control-flow path: the load was on the right path but observed the wrong memory version because dependence information arrived late.

The hardware may choose to reissue only the load and its data-dependent consumers, flush all younger instructions from the load onward, or use a broader checkpoint rollback. Those strategies differ in state recovery, energy, and recovery latency. A narrower replay needs reliable dependency tracking and must also handle control decisions or stores that consumed the wrong load value. Replaying only the load while retaining a younger miscomputed branch or store could preserve a corrupted architectural outcome.

Correctness test: after all replay and retirement complete, the architectural register and memory state must match an execution permitted by the ISA's memory model, with exceptions precisely attributed. The instruction stream's internal number of executions is not itself visible software behavior, though retry counts and timing may be measurable through performance counters.

The Role of Reorder Buffers and Precise Retirement

The reorder buffer (ROB), or an equivalent ordered retirement mechanism, ensures that completed instructions enter the architectural stream in a controlled manner. A load can execute and supply values to younger speculative consumers before it retires. If an older store later invalidates that read, the ROB and rename/recovery machinery must keep the erroneous load and dependent younger work from becoming architecturally final.

Stores often mark themselves complete once their address/data and required checks are ready, but their actual write may be delayed until after retirement. This arrangement helps maintain precise exceptions and prevents wrong-path stores from escaping. Store retirement and cache writeback are separate, so the ROB can advance while a committed-store buffer continues to drain, subject to ordering and capacity limits.

The LSQ and ROB are coupled resources. A decode or dispatch stage may be unable to admit another memory instruction when the LQ or SQ is full, even if ROB slots and arithmetic execution units remain free. Conversely, a full ROB or failed branch checkpoint allocation can stall the front end before the LSQ reaches capacity. Performance analysis should identify which queue or ordering rule is actually binding.

Load–Load Ordering and Coherence Observations

Stores are not the only source of ordering constraints. Certain ISA memory models require same-address read-to-read relationships that prevent two loads in one thread from observing values in an impermissible order. External coherence traffic can make an internal load reordering observable. Some LSUs therefore track load–load address relationships or record coherence probes that could invalidate earlier optimistic assumptions.

The RISC-V RVWMO specification imposes preserved-program-order constraints for relevant overlapping operations and defines the legal load values. BOOM's documentation discusses detecting same-address load reordering when coherence probes expose a potentially invalid observation. XiangShan describes separate detection responsibilities for read-after-read (RAR) and read-after-write (RAW) memory access violations. The precise trigger conditions are specific to the ISA and design, not a blanket statement that all loads always execute in program order.

This is a reason to distinguish the CPU's local issue queue from the wider cache-coherence system. The LSQ may remember read addresses and validation state precisely because the cache can receive events from outside the core. A transient cache hit value and a finally legal architectural load value are related but not guaranteed to be identical until relevant ordering obligations are satisfied.

Fences, Atomics, and Other Ordering Boundaries

Fences and ordering-qualified atomic operations constrain the relationships among reads and writes as specified by the ISA. Their effects may require the LSU to block younger accesses, wait for older operations to reach particular milestones, or otherwise enforce visibility relationships. The exact rule is not “all fences always drain every store to main memory.” Some barriers constrain only designated directions, address classes, or observers.

Read-modify-write atomics, load-reserved/store-conditional sequences, and acquire/release operations impose additional semantics. A processor can realize these through LSQ arbitration, cache-coherence ownership, reservation tracking, or other mechanisms. Atomicity and ordering are related but distinct: an operation can be indivisible without having the strongest possible ordering effect, depending on the ISA encoding and memory type.

For RISC-V, the formal RVWMO model and FENCE instruction establish explicit rules; other ISAs have different contracts. The LSU must also respect page or physical-memory attributes that alter cacheability and permitted speculation. This article addresses the microarchitectural control boundary, while the Instruction Set Architecture unit owns the full programmer-visible memory-model specification.

Memory-Mapped I/O and Non-Idempotent Accesses

Ordinary cacheable memory may tolerate speculative reads, buffering, and repeated attempts when the ISA permits. Memory-mapped input/output (MMIO) can be fundamentally different. Reading a device register might clear a status bit, consume a queue entry, or trigger another side effect. Writing a control register might start an operation that cannot be canceled merely by restoring a rename map.

The LSU therefore needs the memory region's attributes, ordering requirements, and permitted access behavior before it treats a transaction as a normal speculative cache request. Implementations may hold certain MMIO operations until they reach the head of the ROB and prior instructions satisfy required ordering checks. XiangShan describes strongly ordered MMIO accesses separately from some non-cacheable but idempotent accesses that can be scheduled more freely. “Uncached,” “device,” and “strongly ordered” are not automatic synonyms across processor families.

An engineering analysis must state the platform memory type rather than assume all physical addresses behave alike. Forwarding rules, byte-lane merging, error reporting, and the legality of repeating a request can all differ at an MMIO boundary. Detailed device-register semantics belong with bus and device-management topics; the LSQ's responsibility is to preserve the specified boundaries.

Exceptions, Page Faults, and Deferred Architectural Effects

A load can encounter a page fault, permission failure, alignment fault, or other architecturally defined exception. The core may discover the problem while the instruction remains speculative or before older operations have retired. To preserve precise exceptions, it ordinarily records the fault information and reports the exception only when the instruction reaches the appropriate architectural boundary. A wrong-path load's fault may be discarded rather than delivered to software.

Likewise, a store's address or data may be available before the processor establishes that the write is permitted. The LSU cannot let an uncommitted store visibly modify memory and later attempt to “unwrite” an unauthorized access. Permission, translation, and memory-type checks are coordinated with the ROB and store-buffer rules before the physical side effect is allowed.

A load that is internally replayed for an alias or resource reason must not raise a duplicate architectural exception simply because it entered the execution pipeline multiple times. Conversely, an actual fault on the correct path must not be concealed by a replay mechanism. These cases show why LSQ state includes more than a numerical address and data word.

Translation Misses, Cache Misses, and Resource Replays

A load waiting for a TLB refill is not the same as a load waiting for a store value. An L1 cache miss is different again: the load may have no conflicting store but must wait for the memory hierarchy. A cache miss-status holding register (MSHR) can track an outstanding miss; if all relevant MSHRs are occupied, an additional load may be stalled or replayed even when the memory addresses are independent.

A correct diagnostic distinguishes address-not-ready, translation-not-ready, data-cache miss, store-conflict, bank conflict, resource exhaustion, and memory-order violation. Different implementations merge these cases or expose different counters. XiangShan's load replay documentation explicitly lists several distinct retry causes, demonstrating why a single reported “load replay” number may not imply speculation errors.

Some load pipelines announce a predicted short-latency result to dependent schedulers before cache confirmation. If the cache later misses or an alias blocks forwarding, this early wakeup may itself require cancelation or rescheduling. The operation's dependence tracking must extend to its consumers, not just its LQ slot.

Queue Capacity, Circular Allocation, and Backpressure

Load and store queues are finite. Dispatch may allocate entries in program order, then release them when the associated architectural and memory-order obligations are satisfied. Occupancy varies with workload: a series of cache-missing loads can keep LQ entries live for many cycles, while many stores may accumulate in the SQ or committed buffer waiting for the cache interface.

A full queue sends backpressure to earlier pipeline stages. This can reduce overall retirement throughput even if the ALUs are idle and the instruction window has room. Capacity planning must consider both peak memory instruction mix and residence time. As a rough throughput relation, if a stream needs two LQ entries per cycle and an entry remains allocated for 20 cycles on average, sustaining the stream without other limitations requires about 40 simultaneously occupied entries. This is an application of the occupancy relation, average occupancy = arrival rate × average residency; it is a sizing guide rather than a guaranteed design minimum.

Circular queues also need correct reclamation during squashes. If a wrong-path load is canceled, its entry must eventually become reusable without clearing entries held by older valid operations. If a committed store remains to drain, it must not be discarded when a younger branch is squashed. These lifetime differences explain why a physically unified structure may still need separate logical allocation and release rules.

Load and Store Execution Ports, Banking, and Power

The number of memory operations a core can start per cycle depends on more than the width of its instruction issue machinery. A design may have one or multiple load AGUs, store-address pipelines, store-data paths, cache read ports, and search ports for its forwarding structures. Two loads may be ready but contend for a single L1 bank; two address comparisons may require a multiported or banked SQ lookup.

Increasing LSU width can raise peak memory throughput but also increases comparator, mux, bypass, and wiring cost. A fully associative search among many stores needs to combine multiple candidate matches and age information quickly enough to fit the target clock. Partial address filtering or multiple pipeline stages can ease critical paths while increasing latency or the need for replay.

Energy matters. Searching all store entries for every load can consume power even when almost no accesses conflict. Designs may gate entries by age, exploit predicted dependence, partition queues, or stage the search. Such optimizations must remain functionally transparent: they may delay a load or cause replay, but they may not silently select the wrong address or wrong writer.

Speculative Execution Security and the Limits of Rollback

A speculative load may alter microarchitectural state, such as cache contents, replacement metadata, or resource contention, before it is eventually squashed. Restoring precise architectural registers does not necessarily erase these transient effects. Memory-dependence speculation and forwarding decisions are therefore relevant to transient-execution side channels, even though their primary design purpose is performance.

A widely discussed class of mechanisms is speculative store bypass: if a load is allowed to run before an older potentially aliasing store has resolved, it might transiently consume an older value before a violation is detected. Architectural rollback can prevent that incorrect value from being committed, but timing effects from dependent speculative work may still matter in a security analysis. This observation is conceptual; hardware implementations, mitigations, and exposure differ by platform.

Defensive approaches can include limiting specific speculative bypass paths, serializing sensitive operations, applying manufacturer-recommended controls, and reducing unintended information flow through caches or predictors. Trade-offs are workload-sensitive: delaying all loads after older stores can be very expensive. The dedicated Microarchitectural Side Channels and Mitigations article addresses threat models and mitigations more comprehensively.

Worked Example I — A Matching Store Forwards a Word

Consider a constructed machine with 32-bit, naturally aligned, little-endian scalar accesses. Initial memory at address 0x2000 contains the word 0x11111111. Four instructions occur in the following program order. Suppose the store's address and data have become available, but the store has not yet drained to the data cache.

Sequence Instruction Queue observation Event
1 S0: STORE32 [0x2000] ← 0xAABBCCDD Older SQ entry, address/data ready Local write remains buffered
2 I1: ADD r5, r6, r7 Nonmemory instruction May execute independently
3 L2: r8 ← LOAD32 [0x2000] Younger LQ entry Compares against older stores
4 I3: ADD r9, r8, 1 Consumer of load result Waits for valid r8 value

The LSU finds S0 as an eligible older overlapping store and forwards 0xAABBCCDD to L2 (assuming the implementation supports this straightforward full-word case and all required checks pass). I3 can subsequently use the forwarded result. It would be incorrect for L2 to return 0x11111111 merely because the cache still holds the old word.

This is store-to-load forwarding within the same thread/core. It does not mean another processor has already observed the buffered store. Nor does the example specify exact cycles: forwarding and wakeup latencies vary by core design.

Worked Example II — Two Older Stores and the Youngest Writer

Let memory location X initially hold 5, and consider S0: STORE [X]←10, S1: STORE [Y]←70, S2: STORE [X]←20, L3: LOAD [X], in that program order. Assume all accesses are complete, equal-width scalar words, the stores are valid, and Y is disjoint from X.

The comparison for L3 finds S0 and S2 as address matches, while S1 does not match. The correct locally forwarded value is 20 from S2, not 10 from S0. This remains true if the younger store S2 happened to issue its data-generation operation after S0: the queue resolves program-age priority, not “first data arrived.” If S2's address were known but its data were not ready, the load might have to wait; forwarding the overwritten value 10 would be wrong.

A variation with byte-sized stores is more complex. Suppose S0 writes 0xAA to X+0, S1 writes 0xBB to X+1, and L2 reads a two-byte value starting at X. If the hardware can merge both store bytes and the access rules allow it, a little-endian load obtains 0xBBAA. A design without supported multi-source forwarding may instead stall or replay. In either case the architectural result must be equivalent, not necessarily the execution timing.

Worked Example III — A Load Passes an Unknown Store Address

This constructed timeline models speculative memory disambiguation. Program order is S0: STORE [rA]←99, followed by L1: rB←LOAD [0x3000], then I2: rC←rB+1. The older store's base register rA is produced by a long-latency operation. Memory at 0x3000 initially contains 7. The core predicts that S0 and L1 do not overlap.

Relative event Older store S0 Younger load L1 Consequence
A Waiting for base address Address 0x3000 ready Independence prediction permits issue
B Still unresolved Reads 7 from cache I2 may speculatively compute 8
C Resolves rA = 0x3000 LQ entry still tracked Store and load overlap
D Address-comparison validation Previous load value invalid Ordering violation detected
E Eligible to supply value 99 Load and dependent work replay or recover L1 must ultimately obtain 99

A valid recovery may squash the load and younger work, then replay L1 with forwarding after S0 has correct data. I2 then computes 100, not 8. The timeline uses relative events, not measured cycles, because validation and recovery stages differ among implementations.

If rA had resolved to 0x4000 instead, there would have been no byte overlap and the early load of 7 could remain valid, subject to other ordering requirements. That useful no-alias case is the principal performance justification for memory-dependence speculation.

Worked Example IV — A Partial-Width Forwarding Decision

Assume little-endian memory bytes at 0x4000 through 0x4007 initially are 10 20 30 40 50 60 70 80 (hexadecimal). An older store writes two bytes at 0x4002, with byte values AA BB in increasing-address order. A younger LOAD64 [0x4000] then requests all eight bytes. The correct value, if no other writes intervene, is assembled from bytes 10 20 AA BB 50 60 70 80, producing the 64-bit numeric value 0x80706050BBAA2010 in this little-endian example.

The store covers only bytes at offsets 2 and 3. A hardware implementation capable of mixing forwarded bytes and cache data can construct the result. Another may block this load, or perform a narrower sequence of internal accesses, until it can obtain an architecturally correct result. Simply forwarding the two-byte payload as if it were the entire 64-bit value would be erroneous.

This scenario illustrates why forwarding design depends on byte masks, alignment, memory translation, and a precedence rule among overlapping stores. It does not establish that every real processor supports partial-forwarding merges at equal speed, nor that all misaligned load types are universally supported.

Worked Example V — Queue Pressure and Sustainable Issue Rate

A simplified core allocates one load-queue slot for every dispatched scalar load. Its LQ capacity is 32 entries. A workload attempts to dispatch two loads per cycle, and each load occupies an entry for an average of 24 cycles while waiting for its required completion/retirement conditions. Ignoring burstiness and other bottlenecks, an average sustainable arrival rate of 2 loads per cycle would require about 2 × 24 = 48 occupied slots—more than this queue can provide.

Using the occupancy relationship, the queue-only upper estimate under those assumptions is 32 / 24 ≈ 1.33 loads per cycle. This is not a measured processor throughput, nor a universal performance bound when occupancy distributions, release rules, and burst conditions differ. It demonstrates why dispatch width can exceed sustainable throughput in memory-heavy workloads.

If another workload reduces average LQ residency from 24 to 12 cycles while retaining the same 32-entry capacity, the occupancy-based estimate rises to 32 / 12 ≈ 2.67 loads per cycle; at that point the assumed two-load issue width may become the binding limit instead. Memory latency, ROB retirement, queue allocation rules, cache ports, and outstanding-miss capacity can still impose additional constraints.

Worked Example VI — Predicted Dependencies and Replay Cost

Suppose a hypothetical program executes 100 million retired instructions with 20 million loads. A policy allows memory-dependence speculation on 75% of those loads, and the observed harmful misspeculation rate among the speculated loads is 0.4%. Then the example predicts 20,000,000 × 0.75 × 0.004 = 60,000 harmful mispredicted loads.

If every such event causes an incremental average recovery cost of 18 cycles, and no costs overlap, the simple penalty estimate is 60,000 × 18 = 1,080,000 cycles, or 0.0108 additional cycles per retired instruction. This number is not a measured CPI; it deliberately excludes other stalls and effects. The 18-cycle cost is an illustrative assumption, not an architectural constant.

A predictor that reduces those events by 50% saves about 540,000 cycles under the same assumptions, but if it also adds waiting time to millions of loads through false-positive predictions, it may still reduce performance. Therefore the useful optimization target is total elapsed cycles, not simply minimizing the counter for load-order violations.

Worked Example VII — Distinguishing Replay Causes

An engineering performance log reports that 8% of issued loads are reattempted. Without further classification, this does not support a conclusion that “the memory predictor is wrong 8% of the time.” Consider a fictional distribution of 1,000 total retry events: 350 due to cache-bank conflicts, 250 due to unavailable miss-tracking resources, 200 due to pending store data, 150 due to translation delays, and only 50 due to confirmed memory-order violations.

Retry category Example count Correct first diagnostic question
L1 bank conflict 350 Are multiple loads concentrated on one bank?
Outstanding-miss resource shortage 250 Are miss-tracking entries saturated?
Store data not ready 200 Which older store blocks forwarding?
TLB or translation delay 150 Are misses or walks dominating translation?
Confirmed ordering violation 50 Which predicted-independent load was actually dependent?
Total 1,000 Separate capacity, latency, and correctness recovery

Only 5% of these retry events concern harmful ordering speculation in this constructed classification. The example is not a statement about any real processor's counters. It shows the need to understand event definitions, whether repeats are counted, whether classes overlap, and which denominator the tooling uses.

Comparative Design Patterns and Trade-offs

No single LSQ organization is best for all processors. A compact in-order core might rely on straightforward interlocks and a small write buffer; a wide out-of-order CPU may use speculative loads, associative store searches, dependence predictors, and substantial queue storage; a system-on-chip controller may emphasize deterministic ordering and low energy over peak speculative throughput.

Design strategy Benefit Main cost or constraint Typical design objective
Conservative load scheduling Simple ordering validation Delays independent younger loads Simplicity or determinism
Speculative load issue More overlap before stores resolve Replay machinery and security review High average throughput
Complete-width store forwarding Short local read-after-write path Search and mux latency Fast dependent loads
Byte-lane merge forwarding Handles more overlap patterns More complicated data assembly Broader forwarding coverage
Store-set dependence prediction Holds likely conflicting loads Training and false positives Reduce costly replays
Large LQ/SQ More in-flight memory work Area, wiring, port and power expense Wide, memory-intensive cores
Banked/pipelined search Scalable timing and energy Search latency or conflicts High-frequency multiport LSUs
Separate committed store buffer Decouples retire from cache drain Capacity and ordering bookkeeping Sustain stores and precise state

These are design patterns, not a ranking of specific commercial processors. A workload with frequent producer–consumer store/load pairs may value forwarding latency; a workload with irregular cache misses may be limited by MSHRs and LQ residency instead. Correct performance assessment requires measurements that distinguish these cases.

Engineering Verification: Required Invariants

Functional verification of an LSU is demanding because the conditions for correctness are relational: instructions have age, addresses can overlap in complicated ways, stores become ready at different times, and multiple recovery events may occur in the same cycle. Tests should verify both positive behavior (the right load value and allowed ordering) and negative behavior (no wrong-path store escapes, no younger store forwards backward in time).

A useful invariant set includes: every forwarded byte comes from the correct eligible older writer; any speculative load that consumed a disallowed value is prevented from retiring until repaired; a store is not externally committed before architecture permits it; queue age remains valid across wraparound; replays cannot create duplicate externally visible writes; and exceptions remain precise. Formal or simulation environments can additionally check that completed executions satisfy the ISA's memory-order axioms.

Verification must exercise race-like combinations: branch recovery during a TLB miss; a store address becoming ready while a matching load is at writeback; simultaneous cache-probe and load-validation events; mixed-width overlaps; multiple aliases after translation; and queue-full conditions during a flush. These combinations are far more revealing than testing an isolated LOAD or STORE in an otherwise empty pipeline.

Measurement Framework and Performance Counters

An LSQ performance study should begin with a precise workload, clock and ISA configuration, memory type, and the counters exposed by the actual processor or simulator. Relevant quantities include retired loads/stores, dispatch stalls due to LQ/SQ fullness, average and peak queue occupancy, cache-hit/miss distributions, load-to-use latency, successful store forwarding, failed forwarding, store-data wait cycles, TLB misses, resource retries, dependence-prediction false positives, confirmed ordering violations, and recovery cost.

Counters are not automatically additive. A load may first miss a cache, later retry because a resource was unavailable, and then complete after forwarding. Implementations may count micro-operations rather than architectural instructions; a wide or split vector access may occupy multiple internal entries. An analyst should document what a counter represents before calculating “percentage of loads affected.”

For reproducible comparisons, record the denominator and conditions: violation events / eligible speculative loads differs from violation events / retired instructions. IPC changes can reflect clock frequency, memory working set, thread count, prefetching, thermal behavior, or compiler differences. A strong finding links a specific LSU bottleneck to a causal experiment—such as varying queue capacity or predictor policy in a simulator—rather than attributing every memory stall to the LSQ.

Practical Investigation and Design Review Workflow

A disciplined review begins by identifying the visible symptom: low retired IPC, excessive load latency, repeated pipeline flushes, store-buffer stalls, or unexpected memory values. Then classify the memory traffic by access size, address overlap, locality, translation behavior, and read/write ratio. Distinguish true dependencies from speculative assumptions before evaluating predictive policy.

Next identify the resource boundary. Is the dispatch stage blocked because the LQ is full? Are cache read ports or banks saturated? Is an older store's data unavailable? Are full-width loads often crossing narrow buffered writes? Is a memory-dependence predictor generating excessive false-positive waits? These are different optimization targets and should not be conflated.

Finally, validate the proposed change against architectural behavior. A faster forwarding mux that selects the wrong older store is not an optimization. Removing a conservative interlock is valid only if late-conflict detection and replay cover all cases it previously protected. For scholarly comparison, specify which processor or simulator version is under discussion and avoid transferring cycle counts or queue parameters across unrelated core designs.

Common Misconceptions and Corrections

“A store writes memory when the store instruction executes.” Not necessarily. It may calculate its address and data, retire later, then wait in a committed buffer before reaching the memory hierarchy. The milestones should be named separately.

“A load that returned from the L1 cache must already be architecturally safe.” Not necessarily. An older unresolved store may later reveal an alias, requiring replay. Fault and memory-order validation can extend beyond data arrival.

“Store forwarding always works if two instructions name the same address.” Not necessarily. Byte masks, sizes, alignment, missing store data, memory type, and processor-specific forwarding restrictions can block it.

“A matching older store always means speculation failed.” Not necessarily. The load may have waited, forwarded the right data, or otherwise observed a value permitted by the memory model. A detector must examine the actual data source and ordering.

“Queue size alone determines maximum memory throughput.” Incorrect. Issue width, cache ports, MSHRs, latency, dependency patterns, store drain, retirement width, and translation can be tighter constraints.

“Replay and squash are the same event.” They overlap conceptually, but a local retry for a bank conflict can be much narrower than rollback after a memory-order violation or branch misprediction.

“Coherence, consistency, and LSQ ordering are interchangeable.” Incorrect. They describe related but differently scoped requirements. A correct core implements the relevant architectural model and coherence integration through a collection of mechanisms.
