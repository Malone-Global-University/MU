Collection Overview

Databases is a Level 4 unit in the Data Systems division. It develops the established Databases overview into a group of narrower Level 5 specialist articles. The unit has an independent scope and should not be merged into an adjacent discipline solely because the implementation technologies overlap.

The five existing specialist article files in this index are database-indexing, database-transactions, distributed-databases, relational-database-model, and structured-query-language. They are moved from the Data Systems root without renaming their basenames. Proposed child links point to canonical extensionless URLs and are editorial assignments, not claims of live publication.

Worked Scenarios

Design a system with explicit responsibilities

Begin with an institutional dataset containing operational records, access rules and a requirement for accurate recovery. Identify which functions belong to Databases, which belong to Data Engineering, and which require governance and security controls outside this unit. Record the exact data objects being managed, the unit's service guarantees, and the measurable failure cases.

Investigate a production failure

Suppose a search result, report or file appears incomplete after a system change. Trace the authoritative source through the layers described by this unit; compare the expected object state with the stored state, relevant metadata, and observable logs. Avoid assuming a data-loss incident is a hardware failure when the underlying cause may be indexing, query semantics, access control or delayed updates.

Design and Investigation Framework

  1. Define the authoritative data object and owner.
  2. Specify access, concurrency, persistence and consistency requirements.
  3. Compare the relevant architectures by representative workload.
  4. Choose a design and capture the reasons and alternatives.
  5. Test migration, rollback, security and recovery procedures.
  6. Evaluate performance, operational cost and failure modes with evidence.
