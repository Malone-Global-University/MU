Definition, Purpose, and Disciplinary Scope

Legacy single-byte character encodings are historically important arrangements in which one byte represents one code position in a finite character repertoire. A byte has 256 possible values, 00 through FF; an individual mapping assigns characters, control functions, or undefined positions to some or all of them. These encodings allowed many computers and documents to represent language-specific text before Unicode became the common interchange model. Their simplicity was local: two systems could each use one byte per character yet disagree fundamentally about what a given byte meant.

A code page is a named mapping or family of mappings used by an operating system, program, device, or data-exchange agreement. In everyday Windows and DOS terminology it often identifies a numbered encoding, such as code page 437 (CP437) or Windows-1252 (CP1252). In other settings, a mapping is identified by a standards name such as ISO-8859-1, by a family name such as KOI8-R, or by a product designation such as Macintosh Roman. The word code page does not imply global uniqueness, identical implementations, or a universal eight-bit alphabet. It is a necessary part of the text-decoding contract, not a property that can be reliably read from most isolated bytes.

This is the third Level 5 specialist article of the MGU Character Encoding unit. It follows Character Repertoires, Code Points, and Byte Encodings and ASCII Character Codes and Control Characters. Its subject is the design, provenance, operation, incompatibility, and preservation of historical one-byte mappings. The next article, ISO-8859 and Windows-1252 Compatibility, will analyze that particular standards pair in greater detail. Unicode forms and modern transcoding algorithms have dedicated sibling treatments.

The central operational rule is simple: bytes are evidence; an encoding name supplies an interpretation. A document that renders plausibly under one mapping may still be wrong, especially for names, punctuation, monetary amounts, archival quotations, and legal records.

Learning Objectives and Investigative Questions

After studying the article, the reader should be able to distinguish a byte value from its interpreted character; explain why one-byte encodings normally cover only a limited collection of scripts; identify differences among DOS, Windows, Macintosh, ISO, and KOI8 traditions; interpret a byte under two explicit mappings; differentiate undefined-byte failure from legitimate control-code interpretation; recognize the limits of automatic detection; reconstruct provenance; and conduct a reversible Unicode migration with documented validation.

A responsible investigator asks five questions before decoding: Which exact bytes were captured? Which encoding did the producer actually use? What did the surrounding application, locale, or protocol promise? Can the proposed mapping explain a sufficient sample without unexplained errors? Can the recovered text be shown to preserve meaningful data? A useful decoding workflow answers them in that order rather than beginning with a font selection or an editor's appearance.

Eight Bits and the 256-Position Model

An unsigned eight-bit value can represent 256 numeric positions, from decimal 0 to 255. A classic single-byte encoding uses exactly one byte for each encoded position and therefore cannot identify more than 256 distinct positions at one time. In practice the total repertoire of printable characters is smaller: positions may be reserved for controls, unsupported assignments, or purposes specific to the target platform. One byte per encoded character position is not the same as one byte per user-perceived grapheme, one byte per word, or a guarantee that an entire language can be represented.

Under a traditional ASCII-compatible mapping, values 00–7F correspond to the familiar ASCII positions and values 80–FF are available for additional mappings and control functions. But even that layout is a convention, not a universal rule. IBM EBCDIC code pages provide an important example of historically significant one-byte mappings not laid out like ASCII. Similarly, the term “extended ASCII” is misleading when it leaves the particular extension unidentified: 0x80 does not have one standard character meaning across all extended sets.

A character repertoire is a set of supported textual elements, while a code-page table is a representation of those elements by numeric positions. In contemporary terms, a decoder maps bytes to Unicode characters (usually Unicode scalar values or sequences as implemented by the decoder). A code page may have historically been defined independently of Unicode; any modern Unicode mapping is a formalized bridge, not proof that the original application internally used Unicode.

Character Repertoire, Mapping Table, and Encoded Text

Three layers are easily confused. The repertoire asks whether an encoding includes a symbol at all; the mapping asks which byte encodes it; and the text file supplies a sequence of such bytes arranged according to some higher-level convention. Consider the word Café. A Western European code page might store it as 43 61 66 E9; UTF-8 stores the same four Unicode characters as 43 61 66 C3 A9. The two files differ in length and the last character's representation. Neither a file extension nor the number of bytes establishes which encoding a producer selected.

Now consider the byte E9 alone. In Windows-1252 and ISO-8859-1, it corresponds to é (U+00E9). In IBM CP437, the same byte corresponds to Θ (U+0398); in Windows-1251, it corresponds to Cyrillic й (U+0439). This is not a corruption of the bytes. It is a mismatch between their original meaning and the mapping chosen for display.

Historical Drivers of Localized Character Systems

Character encodings developed in a world of limited memory, narrow communications channels, printer-specific glyph sets, fragmented product ecosystems, and region-specific language requirements. A computer sold for Western European business correspondence did not necessarily need the same additional letters as one sold for Russian administration or Greek publishing. Keeping one byte per stored position often fitted established software and storage assumptions, and reusing the ASCII region reduced barriers to interchange with existing American-origin software.

By the 1980s and 1990s, machines could exchange disks and documents across increasingly varied environments. This exposed the cost of local encoding choices. A spreadsheet exported from a DOS application might be opened in Windows, a Macintosh file could be sent through a mail system, or a Central European document could pass through a Western European default. Characters above ASCII might change meaning without any explicit processing error. A file could remain syntactically valid as a sequence of bytes while its words or numbers were no longer faithfully represented.

No single transition date marks the disappearance of code pages. Mainframe applications, specialized instruments, historic datasets, packaged software, printer protocols, legacy databases, backups, and long-lived documents can still depend on them. Technical standards aim to make newer exchange less ambiguous; they cannot retroactively change the original meaning of archived octets.

ASCII Compatibility: Common, but Not Universal

Many well-known encodings preserve the ASCII 00–7F assignments: Windows-1252, ISO-8859-1, CP437 for most relevant character positions, and numerous others. This is useful because plain ASCII words may look correct even when the chosen eight-bit encoding is wrong. It is also deceptive: a 10,000-byte document can appear mostly sensible while a handful of names, quotation marks, and currency signs are corrupted.

The high half of an ASCII-compatible code page is not an undifferentiated extension with one canonical alphabet. Values in 80–FF can contain accented Latin letters, non-Latin scripts, box-drawing glyphs, punctuation, symbols, and control positions in entirely different arrangements. Some mappings intentionally keep unassigned positions. Others correspond to fonts and terminal display traditions that are not represented accurately by modern assumptions about text appearance.

EBCDIC families are a major exception to ASCII compatibility and are addressed separately in EBCDIC and Historical Text Interchange. This article emphasizes the broadly encountered one-byte code-page model, without suggesting that every historic one-byte encoding begins with ASCII.

DOS OEM Code Pages and Display-Device Traditions

IBM PC-compatible DOS systems used numbered OEM code pages, with CP437 among the best-known examples. The high half of CP437 includes line-drawing characters, mathematical symbols, Greek letters, and accented letters. Those assignments were especially useful for text-mode screens, menus, and box borders. CP850 subsequently served many Western European DOS environments with different assignments for some high bytes. Other OEM pages served Cyrillic, Greek, and additional language requirements.

The division into OEM and Windows “ANSI” pages is a Windows historical naming convention, not a claim that a single ANSI-standard global encoding exists. Distinct input/output contexts could therefore disagree on high-byte characters within the same computer. A byte used to draw a DOS border could become a punctuation mark or a different letter after an application changed its current code-page setting.

For example, E9 maps to Greek capital theta Θ in CP437 but Ú in CP850. Both are valid byte mappings. A fixed-width box drawn under one code page may become visually disrupted under another. When migrating a text-mode application, one should preserve the original screen or printer context as well as its byte data, because glyph appearance, display attributes, and line-drawing conventions may have conveyed information beyond ordinary letters.

Windows Code Pages and the “ANSI” Misnomer

Classic Windows software often stored text in “ANSI” code pages, especially Windows-1252 for many Western European configurations and Windows-1251 for Cyrillic environments. The term ANSI in Windows API names such as ...A generally means a code-page-based interface, not that the bytes satisfy a single American National Standards Institute character standard. The relevant mapping depends on the API and configuration; for example, a Windows system's active ANSI code page is not identical by definition to the console's OEM code page.

A document saved in Windows-1252 can include left and right curly quotation marks at 93 and 94, an en dash at 96, an em dash at 97, and the euro sign at 80. An old import pipeline expecting ISO-8859-1 may interpret these as C1 control positions. A pipeline expecting CP437 may show entirely different glyphs. Naming Windows-1252, rather than “ANSI text,” makes the intended byte interpretation reproducible.

Code-page settings can vary across installations and historical periods. Therefore the ambient system locale should not be used as a replacement for file provenance. Modern programming APIs can often request a specific encoding explicitly. Their default encodings and replacement behaviors differ across versions, so the conversion plan should specify the decoder, code page, and error policy rather than assuming identical defaults on every host.

ISO/IEC 8859 and Region-Focused Repertoires

The ISO/IEC 8859 standards comprise multiple separately defined eight-bit character sets with coverage targeted at different writing systems and regional needs. ISO-8859-1, often called Latin-1, is a familiar Western European example; other numbered parts serve different language groups. Each part needs to be named individually. The string “ISO-8859” by itself does not identify the correct byte-to-character table.

An important nuance is that some byte values correspond to control positions rather than printable letters. In ISO-8859-1, the 32 positions from 80 through 9F correspond to Unicode U+0080–U+009F controls in a direct mapping. A system that treats some of these positions as punctuation may be following a different decoding convention—not reproducing strict ISO-8859-1 mapping. There is also a difference between a standard's historical mapping and how modern web browsers interpret legacy labels, discussed later.

ISO standards offered important consistency within specified environments, but they could not make 256 positions cover every writing system simultaneously. A manuscript containing several scripts required a different representation strategy, such as multiple character sets with switching rules or later Unicode encoding. Dedicated coverage of the ISO-8859-1 versus Windows-1252 issue follows in the next subarticle.

Macintosh Roman and Product-Specific Mappings

Classic Macintosh computers commonly used Macintosh Roman, a distinct one-byte mapping designed for their software environment. Its high positions differ from both the DOS OEM family and Windows-1252. For instance, byte 80 maps to Ä in the mac_roman mapping, whereas Windows-1252 uses it for € and CP437 uses it for Ç.

The significance is broader than these illustrative characters. Older word-processing and publishing environments may have associated codes with typographical behavior, fonts, and application conventions that do not survive a naive byte import. When text originated in such a system, recorded application version, exporting program, disk image, or document format can provide stronger evidence than modern visual inspection.

Several older encodings were extended or adapted by vendors. A filename's *.txt extension, the presence of English headings, or the user's later use of a PC does not establish that its original encoding was Windows-1252. Provenance should follow the data's creation and transfer history.

Cyrillic, Greek, and Other Script-Oriented Pages

One-byte systems served many scripts through regional mappings. Russian-language archives may include Windows-1251, KOI8-R, and CP866, each of which gives different meanings to numerous upper-byte values. Greek-language documents can likewise appear in different historic code pages. Some writing systems required more than 256 coded elements, and others needed script behavior not expressible merely by choosing a single byte for each visual unit.

The byte C0 illustrates the danger. Windows-1252 interprets it as Latin À, Windows-1251 as Cyrillic А, and CP437 as the box-drawing character └. An automated migration that accepts any “plausible alphabetic result” can silently substitute one character for another, including homoglyphs that look similar in some fonts yet have different code points.

Scripts with shaping, joining, bidirectional directionality, or combining marks require further text-processing rules even after bytes are correctly decoded. These rules are not determined by a code-page label alone. An encoded character is not automatically an accurately rendered piece of typography.

Why “Extended ASCII” Is Not a Precise Identifier

The phrase extended ASCII is widely used for “an eight-bit byte encoding whose lower half resembles ASCII.” It is not sufficient technical metadata. If two applications both describe their files as extended ASCII, one may expect CP437 while the other expects Windows-1252; a third may mean ISO-8859-1. The expression does not tell an implementer how to interpret 80, 93, C0, or E9.

This terminological looseness leads to two different errors. First, a system may display the wrong characters while continuing normally because all bytes have assigned meanings in the chosen alternative mapping. Second, a decoder can encounter undefined bytes and silently insert replacement symbols. In neither case is the underlying byte stream evidence of one universal “ASCII extension.”

Documentation should state a specific encoding identifier plus any relevant interpretation environment. Examples include “IBM code page 437 for the exported DOS screen data,” “Windows-1251 for the 1996 Cyrillic records,” or “ISO-8859-1 in the archived protocol's original definition.” Avoid inventing a code-page identifier merely because a sample appears to contain familiar accented letters.

The Same Byte Under Two Explicit Mappings: Worked Investigation

Take the hypothetical single byte 93. It is one octet, or binary 10010011; the bytes alone do not carry the description “left quotation mark.” Decode that byte under the explicitly named Windows-1252 mapping: the result is U+201C LEFT DOUBLE QUOTATION MARK (“). Decode it under IBM CP437: the result is U+00F4 LATIN SMALL LETTER O WITH CIRCUMFLEX (ô). Under strict ISO-8859-1, the result is U+0093, a C1 control position. These are three interpretations of the exact same stored byte, not three alternative byte spellings of the same character.

Now inspect 93 43 61 66 E9 94. Under Windows-1252 the sequence represents “Café”; under CP437 it begins with ô, the last E9 becomes Θ, and byte 94 maps to ö. A quick viewer might display plausible but nonsensical characters because every byte has some meaning. In an archive with multilingual content, that anomaly is a clue, not a mathematical proof of the intended code page.

Hypothesis Byte 93 Byte E9 Evidence assessment
Windows-1252 “ é Plausible for curly quoted Western European prose
CP437 ô Θ Possible on a DOS system, but unlikely for the same quotation context
ISO-8859-1 (strict mapping) U+0093 control é May be valid bytes but not the apparent intended punctuation

The correct decision depends on the producer's contract and the rest of the collection. It is especially important to distinguish a probable reading from a verified transcription.

Defined Positions, Undefined Bytes, and Fallback Policies

Not every one-byte mapping defines a printable character at every one of the 256 positions. In CP1252, for example, several high positions—including 81, 8D, 8F, 90, and 9D—are unassigned in common strict mapping implementations. Python's cp1252 decoder raises UnicodeDecodeError on byte 8D under the default errors='strict' policy. Choosing errors='replace' instead produces U+FFFD REPLACEMENT CHARACTER, marking the lost position but not reconstructing the original character.

A distinction is essential: a byte can be valid and mapped to a control code, as ISO-8859-1 93 is, without being a printable punctuation mark or a decoding error. Conversely, an implementation can map undefined positions with a vendor-specific fallback, private-use character, or best-fit substitution. Two converters bearing apparently similar names need not enforce identical fallback behavior, so reproducibility requires the implementation and its options to be captured.

Handling choice Result Appropriate use
Strict failure Stops and identifies an invalid or unmapped position Migration validation, lossless archival workflow
Replacement character Inserts U+FFFD or another placeholder Diagnostic preview with explicit loss indication
Ignore Silently drops positions Usually unsuitable for evidence preservation
Custom escape notation Preserves bytes as printable annotations such as \\x8D Investigation and exception logging, not plain-text equivalence
Surrogate or private mapping strategy Can preserve otherwise unmapped byte identity in a constrained pipeline Specialized reversible workflows, with explicit handling contract

Replacement is not repair. Once ambiguous input has been overwritten by replacement characters, recovery may require the unchanged original bytes or a reliable earlier copy.

Replacement Characters, Question Marks, and Unrepresentable Output

There are two directions of failure: decoding unknown or unmapped input bytes, and encoding Unicode characters into a smaller legacy repertoire. If text contains a character absent from the chosen code page, an encoder may fail, replace it with ?, approximate it with an unrelated but visually similar character, or use a custom escape convention. These behaviors are separate from the mapping table. A code page does not automatically support any Unicode scalar value just because it decodes every possible byte.

For example, Unicode 漢 cannot be encoded in Windows-1252. Python's strict encode('cp1252') raises UnicodeEncodeError; errors='replace' substitutes a question mark. The resulting 3F byte is no longer sufficient to reconstruct the original character. Similarly, a typographic glyph may have no byte assignment even though a font is capable of drawing it. Fonts and encodings have distinct responsibilities.

Application documentation must state whether replacements were permitted. In records involving people's names, citations, street addresses, amounts, and legal commitments, fallback can alter meaning or cause collisions. Prefer exact loss reporting with a transaction-like review rather than silently accepting degraded data.

One-Byte Encodings Do Not Solve All Writing-System Requirements

Even if an encoding reserves its entire 256-position space for graphic characters, it cannot cover all Unicode-assigned characters. Many languages and writing systems contain more distinct symbols than a small regional code page can represent; combining behavior, punctuation, and mixed-script text further complicate the issue. Some historical systems handled broader repertoires with multibyte encodings, shift sequences, or stateful interpretation. Those techniques are not single-byte encodings merely because individual component bytes are eight bits wide.

Conversely, a single user-visible symbol need not map to one code point even in Unicode. A combining mark plus a base letter can produce one grapheme; text shaping can select context-sensitive glyphs. A legacy mapping may encode a particular precomposed character in one byte but lack the corresponding decomposition sequence. Therefore character count, byte length, and perceived text length are different measurements and must not be conflated.

Internationalization problems also include collation, normalization, search behavior, and directionality. Converting bytes into Unicode correctly is necessary for many modern workflows, but it is not equivalent to fully localizing an application.

Code Pages in Files, Databases, Terminals, and Interfaces

A file's encoding is usually external metadata or an agreed convention, not an in-band marker attached to each byte. Some file formats explicitly declare encoding; others rely on a surrounding protocol, database column definition, document header, operating-system default, import option, or human knowledge of the source application. Plain .txt and .csv files often lack decisive embedded evidence. Row delimiters, quoting rules, and field-level encodings may introduce additional interpretation layers.

A database column described historically as VARCHAR may have depended on a named collation or code page rather than a generic Unicode encoding. A terminal program may display CP437-like bytes, but redirection through a shell or process boundary may convert text to a different encoding. A CSV export could use a code page chosen by application configuration rather than by the directory where the file was later copied.

For each dataset, record the producer, original system, export software/version, source encoding, transfer steps, file-level and field-level declarations, and validation sample. A code page that was appropriate for one field might not describe an entire binary container. Binary formats can mix ASCII identifiers, integer fields, and legacy text fields in the same file; the format specification controls which positions should be decoded as text.

The Windows “System Locale,” OEM Page, and Console Page

Windows has historically exposed multiple code-page concepts, including a Windows ANSI code page, an OEM code page, and console input/output code-page settings. They may differ, and changing one display setting does not rewrite the stored bytes of an existing file. Thus a procedure such as switching the console code page until a text file “looks right” can supply a useful hypothesis, but it does not establish the file's original encoding.

In Windows PowerShell 5.1, file reading/writing commands can have encoding defaults that differ from those in modern PowerShell. The console's display configuration, PowerShell's pipeline encoding, and an explicitly requested .NET encoder are not identical concepts. For byte-preserving investigation, use [System.IO.File]::ReadAllBytes() on a copied file, log the resulting hexadecimal sequence, and decode it with an explicit [System.Text.Encoding]::GetEncoding(...) instance.

Modern .NET runtimes may require registering the code-pages provider for some old encodings, whereas Windows PowerShell 5.1 typically uses .NET Framework, which supports many historical code pages on Windows. Avoid exporting an assumed default from one software release to another. The goal is an explicit, portable conversion specification rather than reliance on whichever locale happens to be active.

Web Encoding Labels Versus Strict Archive Interpretation

The WHATWG Encoding Standard defines interoperability behavior for modern web-platform text decoding. It intentionally maps several historical labels to particular web-compatible decoders. For example, a browser-like TextDecoder('iso-8859-1') resolves to the Windows-1252 decoder under that standard, so byte 80 yields the euro sign €—not U+0080 as a strict ISO-8859-1 byte mapping would do. The label ascii in that same web-specific API also resolves to Windows-1252. These rules preserve real-world browser interoperability; they do not redefine the original ASCII standard or authorize a historian to silently reinterpret a supposedly ISO-8859-1 archival record.

Python's standard 'latin-1' / 'iso-8859-1' codec, by contrast, maps byte 80 directly to U+0080. This is a useful example of why specifying a label without an interpretation platform can leave a reproducibility gap.

// Browser TextDecoder follows the WHATWG Encoding Standard.
const sample = new Uint8Array([0x80]);
console.log(new TextDecoder('iso-8859-1').decode(sample)); // €
console.log(new TextDecoder('windows-1252').decode(sample)); // €
// This is web compatibility behavior, not strict ISO-8859-1 decoding.

Never apply web-compatible label alias rules automatically to a legacy database field or an offline forensic export unless that environment actually specified those rules.

Detecting Encoding Is an Inference Problem

Most single-byte text sequences have no uniquely identifying signature. The same bytes often decode to some string under many candidate mappings. Without a producer's declaration or stronger contextual evidence, a detection tool can only rank hypotheses by language models, typical punctuation, frequency distributions, script patterns, or expected byte assignments. The return value “Windows-1252, 97% confidence” does not establish historical truth unless the tool's statistical calibration and dataset context justify such a probability claim.

A short sample such as 41 42 43 is especially uninformative: many ASCII-compatible pages represent it as ABC. More bytes can provide greater clues, but mixed-language archives, abbreviations, corrupted records, machine-generated identifiers, and rare personal names can frustrate automated detection. Several pages can also be present within one export if application settings changed over time.

A disciplined workflow treats detection as triage: generate candidate mappings, preview them side by side, compare with known text and metadata, inspect inconsistent rows, and retain uncertainty when unresolved. The next specialist article on Encoding Detection, Metadata, and Mojibake develops these techniques further.

Mojibake, False Confidence, and Accidental Re-Encoding

Mojibake is visibly garbled text produced by interpreting bytes under the wrong character encoding or by processing already corrupted text through further conversions. A frequent example occurs when the UTF-8 bytes for é, C3 A9, are decoded as Windows-1252, yielding Ã©. Another occurs when Windows-1252 93 is treated as CP437, yielding ô instead of a left quotation mark. Both are mapping errors, but their repair paths may differ.

One failed conversion can be compounded by another: if a mistaken interpretation is saved again as UTF-8, the new bytes represent the mistaken characters rather than the original intended ones. Subsequent automated “fixes” are risky because multiple conversion paths may yield plausible results. In some cases recovery is mathematically impossible without the original octets, particularly after ignored input, replacement characters, or lossy best-fit transformations.

Corrective processing should reconstruct a documented sequence of decoding and encoding operations. Test the proposed reversal on representative text, compare against known ground truth, and avoid bulk modification until ambiguous cases have been enumerated.

A Byte-Exact Comparison: Two Ways to Store “Café”

The Unicode text Café contains the four code points U+0043, U+0061, U+0066, and U+00E9 when the final letter uses its precomposed form. Under Windows-1252 or ISO-8859-1, it can be serialized as 43 61 66 E9, four bytes. Under UTF-8, it is 43 61 66 C3 A9, five bytes. If the latter bytes are decoded as Windows-1252, the visible text becomes CafÃ©.

Café ISO-8859-1 43 61 66 E9 4

The last two rows demonstrate a critical distinction: byte equality can coexist with textual inequality under different decoders. If a system receives only 43 61 66 C3 A9, it must know or infer whether UTF-8 Café or Windows-1252 CafÃ© was intended. No algorithm can generally resolve this ambiguity from the byte values alone.

Python Demonstration I: Explicit Mappings and Strict Errors

The following script uses only Python's standard library. It prints exact representations of bytes under four named code pages; then it contrasts strict failure, diagnostic replacement, and successful encoding. Run it on a test machine; the exercise does not modify user files.

raw = bytes.fromhex('93 43 61 66 E9 94')
for encoding in ('cp1252', 'cp437', 'latin-1', 'cp1251'):
    decoded = raw.decode(encoding)
    print(f'{encoding:7s}: {decoded!r}')

print('CP1252 0x80:', bytes([0x80]).decode('cp1252'))
print('CP437  0x80:', bytes([0x80]).decode('cp437'))

try:
    bytes([0x8D]).decode('cp1252', errors='strict')
except UnicodeDecodeError as exc:
    print('Strict failure:', exc.encoding, exc.start, exc.end)

print('Diagnostic replacement:', repr(bytes([0x8D]).decode('cp1252', errors='replace')))

try:
    '漢'.encode('cp1252', errors='strict')
except UnicodeEncodeError:
    print('Unrepresentable character rejected')

assert 'Café'.encode('cp1252') == bytes.fromhex('43 61 66 E9')
assert 'Café'.encode('utf-8') == bytes.fromhex('43 61 66 C3 A9')

The repr output makes nonprinting control positions visible as escape sequences instead of silently rendering them. The Unicode string is still interpreted text; preserve raw separately if later investigation requires byte-level evidence. Error recovery should make the bad position visible in a log, not silently turn it into a new archival fact.

Python Demonstration II: Preserve, Convert, and Verify

An accountable migration produces a new Unicode-encoded file while leaving the original unchanged. The script below assumes the source is already documented as CP1252. That assumption must be supplied by evidence, not inferred from this example. The code reads all source bytes, decodes strictly, encodes the interpreted text into UTF-8, then checks two independent invariants: UTF-8 content agrees with the Unicode text and re-encoding back to CP1252 reproduces the original bytes.

from hashlib import sha256
from pathlib import Path

source = Path('legacy-original.dat')
destination = Path('converted-utf8.txt')

if destination.exists():
    raise FileExistsError('Choose a new output path; do not overwrite a prior conversion')

raw = source.read_bytes()
text = raw.decode('cp1252', errors='strict')
utf8 = text.encode('utf-8', errors='strict')

if text.encode('cp1252', errors='strict') != raw:
    raise ValueError('Source byte round trip failed')

if utf8.decode('utf-8', errors='strict') != text:
    raise ValueError('UTF-8 round trip failed')

destination.write_bytes(utf8)
print('Original SHA-256:', sha256(raw).hexdigest())
print('New UTF-8 SHA-256:', sha256(utf8).hexdigest())
print('Original/new sizes:', len(raw), len(utf8))

A successful round trip is necessary for this chosen mapping to preserve bytes but is not proof it was historically correct. A mistaken, fully defined code page may also round-trip. External source evidence and semantic validation are still required. The script does not preserve file metadata, permissions, ownership, or every record-format convention; production migrations require those controls separately.

Windows PowerShell 5.1: Explicit .NET Code-Page Decoding

Windows PowerShell 5.1 uses the .NET Framework character-encoding APIs. Request the code page explicitly and use exception fallbacks to reject unrepresentable or undefined positions rather than silently substituting text. This example operates on an in-memory array, so it does not overwrite files.

# Windows PowerShell 5.1 (.NET Framework): read-only byte interpretation.
[byte[]]$raw = @(0x93, 0x43, 0x61, 0x66, 0xE9, 0x94)

$cp1252 = [System.Text.Encoding]::GetEncoding(
    1252,
    [System.Text.EncoderFallback]::ExceptionFallback,
    [System.Text.DecoderFallback]::ExceptionFallback
)

$cp437 = [System.Text.Encoding]::GetEncoding(
    437,
    [System.Text.EncoderFallback]::ExceptionFallback,
    [System.Text.DecoderFallback]::ExceptionFallback
)

$read1252 = $cp1252.GetString($raw)
$read437 = $cp437.GetString($raw)

'CP1252 text: ' + $read1252
'CP437 text: ' + $read437
'Original hex: ' + (($raw | ForEach-Object { $_.ToString('X2') }) -join ' ')

# Compare byte sequences rather than relying only on display appearance.
[byte[]]$roundTrip = $cp1252.GetBytes($read1252)
# Compare the arrays with PowerShell 5.1-compatible explicit indexing.
if ($raw.Length -ne $roundTrip.Length) { throw 'Length mismatch' }
for ($i = 0; $i -lt $raw.Length; $i++) {
    if ($raw[$i] -ne $roundTrip[$i]) {
        throw ('Mismatch at byte offset ' + $i)
    }
}
'Round-trip bytes match'

This explicit loop avoids reliance on PowerShell generic-method invocation.

For real files, [System.IO.File]::ReadAllBytes('C:\path\legacy-file.dat') captures bytes before any text decoder is invoked. Do not rely on the shell's currently selected display code page to identify the historical source mapping.

Reversible Conversion Is More Than a Byte Round Trip

For a particular decoder, one can define a byte round trip: decode raw bytes under a specific mapping and encode the resulting text under the same mapping, obtaining the original octets. This is a strong check of a conversion implementation, but it is not equivalent to semantic correctness. Because two different mappings can both cover the same byte positions, both may round-trip while yielding different strings.

The reverse text round trip asks whether every Unicode character can be encoded into a legacy mapping and decoded back without change. This is typically not true for an arbitrary multilingual string. Newer Unicode characters, emoji, ideographs, or punctuation may be absent. A robust system must either prohibit them for a documented reason, choose a Unicode-capable output encoding, or use an explicit, reversible external escape mechanism.

Archive migrations may have additional needs: preserve line endings, original text byte ranges in binary records, field lengths, filename byte sequences, and original code-page metadata. A byte-preserving wrapper can retain an exact source copy even if the newly normalized Unicode version has different byte length or code-point arrangement.

Why Legacy Character Counts and Field Widths Matter

Many historic formats allocate fixed numbers of bytes rather than arbitrary Unicode characters. An eight-byte name field can hold up to eight one-byte encoded positions if the characters are representable, but the UTF-8 equivalent may occupy more than eight bytes. A naïve migration that retains the old byte-width constraint without revisiting the field definition can truncate a character sequence, split a multibyte code unit, or corrupt a neighboring record.

Take the text Café: under CP1252 it is four bytes and under UTF-8 five. A record format allowing exactly four bytes for a display name cannot store the latter version without a layout change or alternative storage rule. The new schema may need a larger field, explicit byte length, versioned record size, or a separate indexed text representation. This is a binary layout and schema problem caused by a character-encoding transition, not a defect in Unicode.

Field padding and terminators need separate interpretation. If a legacy export pads fixed fields with 20 spaces or 00 NUL bytes, a migration must decide whether those bytes represent content or framing. Preserve the raw record in a forensic archive before trimming or normalizing fields.

Filename, Search, Sorting, and Identity Risks

Encoded bytes are often used as identifiers, filenames, index keys, or database values. A code-page error can turn two intended names into one normalized string, or turn one name into several inconsistent records. Case folding and collation are not given by the code page alone; a byte-wise sort is not necessarily a linguistically meaningful sort. After converting a dataset to Unicode, the application's search and equality semantics may change even if the displayed glyphs appear stable.

A classic risk occurs when a migration guesses an encoding from a short name and converts it incorrectly. The resulting Unicode string may be valid and printable, so neither a standard UTF-8 validator nor a database uniqueness constraint can recognize the historic identity loss. Responsible migrations therefore include representative name checks, duplicate-collision reports, reversible identifiers where possible, and explicit policy for uncertain characters.

For search engines and archives, keep raw source identifiers and decoded display strings separately when preserving provenance matters. A corrected display name should not erase the bytes or exact labeling used in the original record.

Mixed Encodings and Field-Level Contracts

A single container can combine multiple text representations. For example, a binary file might begin with an ASCII signature, continue with numeric length fields, and then contain legacy text payloads whose encoding differs by a language identifier. A database export might include Windows-1252 data in one column and UTF-8 fields added by a later system. The presence of one valid UTF-8 segment does not imply that all bytes in a file should be decoded as UTF-8.

Similarly, an application may have converted only some fields during a prior import. The surviving file can contain already misdecoded Unicode text rather than genuinely legacy raw bytes. Treating the entire file as one code page at that stage can worsen damage. Split investigation by format structure, field lineage, source-system version, and relevant segment boundaries.

When a data contract permits multiple encodings, include an explicit encoding field or external registry where feasible, and reject unsupported values. A permissive fallback to a guessed page should be documented as a temporary interpretive action, not an unnoticed permanent transformation.

Operational Migration Workflow: Inventory to Acceptance

A controlled conversion is a staged data project. First, inventory sources, origins, dates, known tools, embedded declarations, locale settings, and earlier conversion history. Second, preserve originals and calculate independent hashes. Third, classify candidate code pages by evidence and sample different scripts, punctuation, and rare bytes. Fourth, decode strictly where possible, record exceptions, and validate names and record counts against trusted references.

Fifth, design the target UTF-8 or other Unicode-based format with appropriate field widths, line-ending policy, and record boundaries. Sixth, export to a new destination, logging byte counts, Unicode error positions, and semantic exceptions. Seventh, run both technical checks and human review over representative records. Eighth, publish a migration manifest stating assumptions, software versions, source hashes, target hashes, exceptions, and rollback instructions.

Phase Control Evidence retained
Inventory Source-system and encoding provenance Manifest, export settings, version history
Preservation Immutable source copy SHA-256 hash, path, acquisition record
Identification Candidate code pages plus controls Sample bytes, code-page mapping, known text
Decode Explicit strict or documented error policy Error positions and decisions
Transform Target layout and Unicode encoding Versioned schema, transformation specification
Verify Byte tests plus semantic samples Reports, reviewer decisions, exception list
Deploy Staged cutover and rollback New artifacts, hashes, recovery procedure

This is the opposite of selecting “Save As UTF-8” on the only copy of an unknown text file. Export success is not proof that textual identity survived.

Diagnostic Decision Framework

When a document displays incorrectly, distinguish three possibilities. (A) Wrong decoding: the original bytes are intact but a program selected a different page. Test alternate decoders without rewriting the original. (B) Lossy past conversion: the bytes now encode replacement marks or substituted characters; look for earlier backups and a documented conversion trail. (C) Corrupt or mixed source: a damaged region or multiple field encodings require record-level investigation. The visible symptoms can overlap, so do not jump to a universal “change to CP1252” fix.

A practical field diagnosis should record: source hash and byte count; displayed symptom; suspected encoding and competing hypotheses; the distinguishing test bytes; expected language and known names; invalid positions under each candidate; outcome of round-trip tests; and whether human confirmation exists. The final decision may legitimately remain “unknown legacy mapping, original bytes preserved.”

Integrity, Security, and Evidence Preservation

A wrong encoding can be more than a cosmetic problem. Applications may make authorization, lookup, logging, filtering, or record-matching decisions using decoded strings. If one component decodes a byte sequence differently from another, they may disagree on a username, path, delimiter, or field value. Allowing silent best-fit conversions can create ambiguous identities, while ignoring invalid bytes can remove audit evidence.

Safer designs define a single encoding contract at each boundary, use strict decoding or explicit error collection, normalize text only when the domain requires it, and make security decisions on a consistent representation. Do not assume that an ASCII-looking header proves the rest of a payload is ASCII or UTF-8. A displayed ? or U+FFFD should be treated as a warning about a data-conversion decision, not as a trusted substitute for a source character.

For forensic or scholarly work, distinguish integrity of bytes, correctness of decoded interpretation, and integrity of attributed meaning. A SHA-256 checksum can establish that the same bytes are present in two places; it cannot tell which regional mapping was intended, and it cannot certify the fidelity of a lossy interpretation. Preserve enough context for another researcher to reproduce and challenge the decoding choice.

Performance and Storage Implications

One-byte encodings can be compact for the small repertoire they were designed to serve. A CP1252 sequence representing Café occupies four bytes while UTF-8 occupies five for the precomposed version. But an arbitrary comparison of bytes per character can be misleading: Unicode can represent a far larger repertoire without switching between incompatible regional pages, and compression, record layout, indexing, and software behavior often dominate total storage cost.

Under a legacy encoding, the most serious performance expense can be operational friction—manual diagnosis, repeated imports, incompatible clients, exceptions, and data cleansing. A modern migration may increase raw text bytes yet decrease system-wide complexity and error rates. Engineers should measure actual workloads and preserve semantics, rather than treating one byte per character as an inherently superior system architecture.

Reproducible Test Cases and Acceptance Criteria

For a migration project, establish a fixed dataset with known byte sequences and expected Unicode strings. Include ordinary ASCII, accented letters, punctuation in the 80–9F region, regional-script text, an undefined byte, and at least one string that cannot be re-encoded under the chosen legacy mapping. Also include blank fields, control bytes, and sample file boundaries if the format uses fixed records or line terminators.
