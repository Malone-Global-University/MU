1. Scope and Central Principle

Text encoding preserves a logical sequence of Unicode characters; it does not itself specify the sequence in which every visible mark will appear across a display line. Bidirectional text combines scripts ordinarily read left-to-right (LTR), such as English and Latin text, with scripts ordinarily read right-to-left (RTL), such as Arabic and Hebrew. The Unicode Bidirectional Algorithm (UBA, Unicode Standard Annex #9) determines a visual ordering for characters under a paragraph direction and their directional properties. Line breaking is a different process: Unicode Standard Annex #14 determines permitted and mandatory break positions, while a layout system decides which opportunities to use given line width, typography, and other constraints.

A common implementation failure is to regard RTL text as Latin text with its character order reversed. This damages spelling, combining marks, punctuation, and numbers. The governing model is: store and transmit the logical order; supply appropriate paragraph and field direction; apply the bidirectional algorithm for display; select line breaks; then shape and render glyphs with suitable script and font support. Real renderers can interleave parts of this pipeline, but its conceptual distinctions are essential.

This article is a Level 5 specialist study within the MGU Encyclopedia's Character Encoding unit. Its emphasis is the information encoded in text and the properties needed to interpret it—not the design of a complete text layout engine, a guide to every writing system, or an instruction to treat RTL text as suspect. Technical baseline: Unicode 18.0, UAX #9, UAX #14, and UAX #29, with W3C internationalization guidance for HTML.

2. Learning Outcomes and Essential Questions

After reading, the learner should be able to trace a mixed-script string in logical order; explain the roles of paragraph direction, strong/weak/neutral bidi types, embedding levels, and isolation; explain why digits and punctuation may behave unexpectedly around RTL runs; identify appropriate HTML dir, bdi, and bdo uses; distinguish code-point sequence from glyph shaping; and describe line-break opportunities, grapheme boundaries, and discretionary hyphenation.

The main operational questions are: Who controls the surrounding paragraph? Is the inserted content direction known? Can an arbitrary name or title affect punctuation outside its own boundaries? Does the layout engine implement Unicode bidirectional and line-break algorithms? Are invisible formatting characters permitted in identifiers or logs? Are language-specific shaping and line-break policies supported? These questions require explicit answers wherever internationalized text crosses a display or data boundary.

A Unicode code point may occupy more than one UTF-8 byte or UTF-16 code unit; a grapheme may contain several code points; and a shaped glyph can represent a combination of characters. None of these counts is necessarily a displayed line-column count.

4. Logical Order Versus Visual Order

Consider the logical string Order 42: طلب 123; paid. The Latin prefix, colon, Arabic word, digits, semicolon, and Latin suffix occur in that order in the stored string. A Unicode-aware renderer does not rewrite the source string to make the Arabic word legible. It resolves directional runs and displays them according to an embedding context. Copying or serializing the original should preserve the same logical Unicode sequence, though a user's visual selection may be complex.

An English paragraph containing Arabic may display the Arabic letters right-to-left while the digits 123 remain in their expected numerical sequence. Colons and semicolons are neutral in many contexts; their display positions can depend on adjacent strong text and resolved embedding levels. A screenshot alone is insufficient to recover a byte-exact source sequence: inspect code points when debugging.

Do not publish an unqualified visual transcription such as “the characters appear in reverse order.” Actual display depends on paragraph direction, isolate boundaries, fonts, width, and bidi implementation. The reference example is reproducible as a logical string, not a guaranteed visual screenshot in every terminal.

6. The Paragraph Base Direction

The UBA resolves each paragraph against a base embedding level, conventionally even for LTR and odd for RTL. An application can establish that direction from document context or by an explicit rule. In HTML, author-controlled content should generally declare its intended direction using dir="ltr" or dir="rtl"; dir="auto" is helpful for self-contained content whose direction is not known in advance.

The same mixed sentence may have different placements of neutral punctuation in an LTR versus RTL paragraph without changing its logical code points. This is normal. A known English invoice page should not change its entire paragraph direction simply because the customer's name happens to start with Arabic. Conversely, an Arabic user-interface page should generally have its structural direction specified rather than depend on a fragile heuristic.

The Unicode first-strong method examines strong directional characters, subject to algorithmic exclusions and contextual rules. It is not a language detector. Numbers and punctuation often do not determine direction; a title that begins with 2026 - may require examination of later text or explicit contextual metadata.

7. An Accessible Mental Model of the UBA

A useful high-level model begins by identifying paragraph boundaries and a base direction; processes explicit embeddings and isolating controls; assigns and resolves directional properties; treats eligible bracket pairs and neutral sequences according to their contexts; assigns implicit embedding levels; and reorders display runs in a final stage. The actual UAX #9 rules have a precise order and many edge cases. A hand-written heuristic such as reversing every RTL substring is not a conformant replacement.

The algorithm resolves display order. It does not translate words, choose fonts, join Arabic letters, determine which grapheme clusters a cursor should select, or calculate every line break. In a real UI, those later operations interact with bidirectional run division and line formation; implementation must respect the relevant standard version and layout context.

For advanced readers, UAX #9 names explicit-processing rules in the X series, weak and neutral resolution in W and N, implicit levels in I, and final-line reordering and cleanup in L. These names describe an algorithm, not annotations editors should insert into ordinary user text.

8. Embedding Levels and Directional Runs

An embedding level describes the directional nesting that helps the algorithm order characters for display. At a simple level, even-numbered levels are associated with LTR behavior and odd-numbered levels with RTL behavior. A mixed paragraph is partitioned into directional runs whose display positions are resolved using these levels; individual letters within each run are not arbitrarily reversed.

Punctuation and weak characters can acquire levels affected by their neighbors. A Latin product code embedded in Arabic text is often a coherent LTR run. A date, currency symbol, and parentheses can create more complicated boundaries, particularly at line ends. This is why localization testing should use representative full sentences rather than a single isolated Arabic word.

An implementation may expose resolved levels for debugging, but code-point storage and UI selection APIs should not be casually substituted for one another. The apparent left/right navigation of a cursor may use visual movement rules while string offsets remain logical.

9. Numbers in RTL Contexts

Numbers deserve special attention because they can be displayed in their usual digit order within an RTL sentence. ASCII digits belong to the European-number category (EN); many Arabic-Indic digits belong to the Arabic-number category (AN). Their interaction with Arabic letters, signs, decimal marks, dates, and surrounding Latin text is governed by UBA rules and the formatting environment.

For instance, الطلب 123 contains Arabic letters followed logically by ASCII digits. The digits are not to be stored as 321 merely because the phrase is Arabic. Likewise, 2026/11/23 is a logically ordered date string whose separators and placement within a paragraph need consideration, not hand reversal. If an application treats a telephone number, account number, or software version as a distinct LTR identifier, mark that field as a coherent directional segment, especially when displayed inside an RTL sentence.

Data-integrity rule: never modify numeric source order to “fix” a rendering issue. Use direction metadata, isolation, and competent text rendering.

10. Punctuation, Paired Brackets, and Context

Commas, colons, parentheses, quotation marks, slashes, and separator symbols often have weak or neutral bidi properties. When embedded RTL and LTR phrases meet, punctuation can appear to attach to the wrong segment. This is particularly noticeable in labels such as Name: ..., filenames next to a parenthesized count, and an Arabic address followed by a comma and postal code.

Paired brackets are not merely isolated neutral signs: UAX #9 includes bracket-pair resolution that considers matching brackets and surrounding strong types. Mirroring of selected characters can also occur according to resolved direction; Unicode's Bidi_Mirrored property does not mean code points in the source were exchanged. The rendered shape of an opening or closing bracket is a display concern distinct from byte and code-point identity.

A safe solution is to bound the unknown-direction part of the message rather than insert a handful of invisible direction marks until one screenshot looks right. Test the same label in both LTR and RTL contexts and at different line widths.

11. Directional Isolates: LRI, RLI, FSI, and PDI

Unicode isolate controls were introduced to keep directional behavior in an inserted phrase from inappropriately influencing the surrounding text. They are preferable to the older directional embedding controls for most newly constructed plain-text interchange situations that genuinely require embedded bidi controls.

Control Code point Meaning Paired with
LRI U+2066 Left-to-right isolate PDI
RLI U+2067 Right-to-left isolate PDI
FSI U+2068 First-strong isolate: direction inferred from its content PDI
PDI U+2069 Pop directional isolate: close the corresponding isolate Opening isolate

A typical logical stream is prefix + FSI + unknown-title + PDI + suffix. The title may contain Arabic, Hebrew, Latin, digits, or nested isolates, while the surrounding paragraph retains a more stable interpretation. Keep starts and ends balanced in generated data. In complex systems, direction metadata attached to structured fields may be preferable to embedding invisible characters in stored values.

The first-strong isolate infers direction from relevant strong characters within its scope. If the field's intended direction is known, an explicitly chosen LRI or RLI can be more predictable than inference. Unknown display direction should not be mistaken for permission to alter or discard source characters.

12. Direction Marks, Embeddings, and Overrides

Besides isolates, Unicode defines U+200E LEFT-TO-RIGHT MARK (LRM), U+200F RIGHT-TO-LEFT MARK (RLM), and U+061C ARABIC LETTER MARK (ALM). These marks can supply directional context in plain text. Older formatting controls include U+202A LRE, U+202B RLE, U+202D LRO, U+202E RLO, and U+202C PDF. Overrides can deliberately force displayed directional behavior unrelated to ordinary character properties.

Mechanism Appropriate role Caution
dir metadata or element Direction of an HTML paragraph/field Prefer meaningful structural markup
LRI/RLI/FSI plus PDI Isolate direction in plain-text fields where metadata is unavailable Keep boundaries paired and visible in diagnostic views
LRM/RLM/ALM Narrow punctuation/context adjustment in specialized interchange Hard to inspect; not a default fix for every field
LRE/RLE and PDF Legacy embedding behavior Usually less robust than isolation
LRO/RLO Explicit override with specialized use cases Dangerous in code review and identifiers; avoid in ordinary data

A character's existence in Unicode does not mean an application should accept it in every identifier. Conversely, the fact that controls can be abused does not justify prohibiting ordinary Arabic or Hebrew content.

13. HTML Direction Metadata: Practical Defaults

HTML provides semantic direction metadata rather than requiring authors to insert invisible control characters into each string. Choose a stable direction for known documents and sections, use a direction-isolating wrapper for dynamically inserted unknown-direction data, and avoid confusing CSS visual alignment with text direction.

<!-- The document's primary language and base direction are explicit. -->
<html lang="en" dir="ltr">
  <body>
    <p>Customer: <bdi dir="auto">العميل 123</bdi>; status: active.</p>
    <p lang="ar" dir="rtl">الطلب رقم <bdi dir="ltr">INV-2048</bdi></p>
    <p>Book title: <span dir="auto">עברית ואנגלית</span></p>
  </body>
</html>

<bdi> isolates the directional behavior of its contents; dir="auto" can infer a sensible base direction. A span with dir="auto" can also serve when an existing wrapper is needed. Set lang independently to convey the text's language; language and direction are related but not equivalent. The dir attribute does not translate the text or define its font.

Caution: An HTML document can include rendered samples of bidi text, but its source view, DOM string, and visual presentation are different inspection surfaces. Debug both the logical text and the browser output.

14. The Distinction Between BDI and BDO

<bdi> stands for bidirectional isolation and is designed to keep an inserted string from changing the interpretation of surrounding text. <bdo> stands for bidirectional override, and forces its descendants into a specified rendering direction. They are not interchangeable.

For ordinary names, search hits, message subjects, and user-provided titles, use semantic direction or isolation (bdi or an appropriate dir). Reserve <bdo dir="rtl"> or <bdo dir="ltr"> for situations where an explicit override is genuinely the intended content behavior, such as a controlled demonstration. Applying an override to Arabic prose merely to make it look RTL can defeat the normal algorithm.

CSS properties such as direction, unicode-bidi, text-align, and writing-mode solve different problems. text-align:right does not mean an element's text has an RTL base direction; vertical writing mode does not imply bidi RTL; and forcing a visual reversal is not an encoding transformation.

15. Worked Mixed-Script Label: Logical Data Contract

Consider an English-language service dashboard with a dynamic request label. The input text is the Arabic phrase طلب 123 (“request 123”), and the complete logical record is:

Ticket: [dynamic label]; status: open
Dynamic label (logical sequence): طلب 123

The dynamic label contains Arabic letters, a space, and ASCII digits. Its first strong directional character is Arabic; the ASCII digits remain a number. An HTML bdi wrapper isolates the phrase from Ticket: and ; status: open:

<p dir="ltr">Ticket: <bdi dir="auto">طلب 123</bdi>; status: open</p>

The semicolon is outside the isolated phrase. That boundary is deliberate: it belongs to the English sentence and should not be directionally absorbed into the inserted title. The example specifies source and structure; visual glyph positions may vary with font and layout width. This is the unit's required first-strong-isolate teaching scenario.

16. Worked Label: Explicit Plain-Text Isolates

When no markup or direction-metadata channel exists, a format may expressly permit paired isolation controls. A plain-text representation can use U+2068 and U+2069 around the unknown title:

Logical notation (control names, not embedded controls):
"Ticket: " + FSI + "طلب 123" + PDI + "; status: open"

The actual control characters can be described in escaped form as \u2068 and \u2069. These characters are not visible letters, but they are part of the string; a byte-for-byte signature or literal comparison sees them. A protocol must define whether they belong in the underlying value or only in its presentation layer. If a data system stores the title independently, it is generally cleaner to keep the original title unmodified and add isolation when displaying it.

For known Arabic content, RLI ... PDI can express explicit RTL isolation. For unknown content, FSI is a practical choice, but the proper field-level treatment depends on the application's direction metadata, parser, and display requirements.

17. Unicode Script Is Not a Complete Text Direction Policy

Unicode assigns a Script property used to characterize writing-system membership. Latin, Arabic, Hebrew, Devanagari, Han, and other scripts have different writing practices, but a script property does not entirely determine a paragraph's base direction or the resulting glyph layout. Characters such as digits, punctuation, inherited combining marks, and common symbols may not have the same script property as their neighbors.

A sentence can contain Latin and Arabic without changing the overall language of the UI, and a display line can contain several script runs with different fonts. Encoding says which Unicode characters are present; bidi ordering says how directionality is resolved; shaping decides forms and placement. Software must not detect “Arabic script” and then blindly reverse all bytes, code points, or grapheme clusters.

Script_Extensions can describe additional script associations for some shared characters. Applications doing security analysis or font selection may need a more nuanced model than a single per-character script label.

18. Arabic Joining and Script-Specific Shaping

Many Arabic letters change visual shape according to their joining context. A letter might take isolated, initial, medial, or final shaping forms when connected to neighbors under applicable shaping rules. Diacritics may attach to bases, and text engines may select ligatures or adjust marks. These are glyph-shaping operations, not a reason to rewrite the original stored letters as a reversed sequence.

The word سلام is logically stored in its linguistic character order. A competent font and shaping engine may display joining forms, but a code-point dump should still recover the original sequence. The presence of Arabic joining behavior does not imply every Arabic-script character joins in every position. Hebrew generally does not have the same joining system; Devanagari and other Brahmic scripts use their own shaping arrangements.

For archival data, keep the original logical text; do not replace modern encoded letters with presentation-form code points solely to imitate a screenshot. If specialized historic data uses presentation forms, document that fact and plan a deliberate migration rather than silently normalizing evidence.

19. Combining Marks, Grapheme Clusters, and Cursor Behavior

Direction and shaping interact with extended grapheme clusters, which commonly represent a user-perceived text element containing one or more code points. Arabic vowel signs, Hebrew vowel marks, and combining accents may accompany base letters. Cursor movement, deletion, selection, and truncation should be grapheme-aware where the UI promises character-level operations.

The UBA's treatment of nonspacing marks does not define the complete grapheme-cluster boundary algorithm; that is a separate topic covered by UAX #29. Truncating a string after an arbitrary UTF-8 byte, UTF-16 code unit, or even code point may split a meaningful text element. Breaking a paired isolate at a truncation boundary can also alter the display behavior of the surrounding paragraph.

A robust editor preserves the logical string, permits understandable visual navigation, and exposes enough direction and formatting information for users to review text safely. Direction-sensitive cursor behavior should be tested with real Arabic, Hebrew, mixed Latin identifiers, combining marks, and multiline input.

20. What Unicode Line Breaking Actually Specifies

The Unicode Line Breaking Algorithm (UAX #14) classifies potential positions between characters as mandatory breaks, allowed break opportunities, or prohibited break positions. It supplies a default framework for wrapping text in many scripts and allows specified tailoring in appropriate contexts. It does not decide the final positions of soft wraps because line width, glyph metrics, justification, hyphenation policy, typography, and user preferences are external inputs.

A text engine may receive a line-break opportunity after a space but choose not to use it if the remaining text fits. Conversely, a narrow container may force it to select an earlier allowed point. The logical text normally remains unchanged by a soft wrap; copying it from a page should not necessarily introduce a newline at the displayed wrap position.

UAX #14 line opportunities are not identical to word boundaries or grapheme boundaries. Some scripts permit breaks without spaces between words, and multilingual word-segmentation algorithms may need language-tailored behavior. A line-breaking implementation cannot safely replace UAX #29 grapheme segmentation or use a raw ASCII-space split as a universal rule.

22. Hard Line Breaks and Soft Wrap Opportunities

A hard line break represents a mandatory boundary in the relevant text processing context; a soft wrap is a display choice made at an allowed break opportunity. CR (U+000D) and LF (U+000A) require special treatment, including their common CRLF pair. A renderer should not accidentally turn one CRLF sequence into two visible lines simply because it processed the bytes separately without context.

The text Alpha Beta Gamma may display on one line at wide width and on three lines in a narrow container, despite identical Unicode characters. A document containing an actual newline between Beta and Gamma has a different logical structure. This distinction matters in source code, logs, legal records, address entry, screen-reader experiences, and copy-and-paste behavior.

Text wrapping also interacts with bidi reordering: UAX #9 includes line-level operations after levels are resolved. A renderer must not treat a line's visual sequence as the stored logical sequence when wrapping or editing.

23. Nonbreaking Spaces, Word Joiners, and Zero-Width Spaces

Ordinary spaces often provide soft-wrap opportunities, but not all whitespace-like code points behave alike. U+00A0 NO-BREAK SPACE commonly prevents a separation between related tokens. U+2060 WORD JOINER inhibits a break without inserting a visible space. U+200B ZERO WIDTH SPACE can signal a possible break opportunity without the appearance of an ordinary space.

These mechanisms can help with units, names, and scripts with complex word boundaries, but careless insertion can damage text search, copy/paste, and editorial evidence. A zero-width space is not a universal substitute for a line-break algorithm, and a nonbreaking space should not be used to protect entire paragraphs from wrapping. Document any intentional use in structured data contracts.

The soft hyphen U+00AD is another specialized discretionary behavior. Its display and break-handling depend on text-engine policies; do not assume it behaves like an ordinary visible hyphen or an unconditional hard break. Unicode 18.0 specifically updated its line-break property, reinforcing why implementation versions matter.

24. Hyphenation, Language, and Line-Break Tailoring

Hyphenation chooses potential division points within words and may require language-specific dictionaries or morphological rules. Unicode line breaking can express where a discretionary break may occur, but it is not a comprehensive dictionary-based hyphenation service. French, English, German, Arabic, Thai, Japanese, and other languages differ in preferred line composition and punctuation treatment.

East Asian line-breaking conventions can restrict certain punctuation from appearing at line edges; languages that typically omit spaces between words may require linguistic analysis for good breaking quality. UAX #14 defines a general default with permitted tailoring, subject to conformance requirements. Specify which locale and tailoring rules a product uses rather than claiming one ASCII-oriented wrapping function works everywhere.

A machine-translated sentence does not automatically inherit the correct line-breaking policy from the surrounding English document. Language tags and appropriate layout support matter alongside the character sequence.

25. Script Direction Is Not Vertical Writing Mode

The notions LTR/RTL, horizontal/vertical, and line progression describe different axes of layout. A right-to-left Arabic paragraph is typically horizontally arranged with a right-side starting point; a vertical CJK layout may stack lines in a different direction without implying that the underlying characters have RTL bidi classes. A writing-mode property therefore cannot stand in for Unicode bidirectional ordering.

Encoding remains agnostic to these choices: the same logical text can be displayed in several writing modes. Layout engines need appropriate orientation, typography, punctuation, and shaping support, but the bytes are not re-encoded merely because the page is vertical or mirrored for the user's language.

26. URLs, Email Addresses, and Technical Identifiers

Email addresses, URLs, invoice numbers, file paths, and code identifiers often contain characters intended to remain in a stable logical order even when surrounded by RTL prose. A UI should treat them as distinct fields, provide suitable directional isolation, and preserve unambiguous copy/paste behavior. Their displayed order should never be used as a source for validation or cryptographic signatures.

For example, INV-2048 embedded inside an Arabic label should be an isolated LTR field when that represents the design intent. A URL's syntactic separators (/, ?, #, :) may appear unexpectedly if it is rendered in an unrelated paragraph direction without isolation. Apply contextual direction metadata rather than introducing an actual reversed URL into the database.

Applications should not infer that every sequence of Latin letters is a URL or a trusted identifier; identify fields structurally when possible. This is especially important for long security tokens or account identifiers where a single visually misplaced character could mislead a user.

27. Python: Inspect Logical Code Points and Bidi Classes

Python's unicodedata library can inspect character names and Bidi_Class values. It is useful for diagnosis, but it is not a full Unicode Bidirectional Algorithm implementation and will not tell you the exact rendered glyph positions of a complete mixed paragraph. The following code prints the Unicode sequence in storage order and makes control characters explicit without introducing actual invisible controls into logs.

import unicodedata as ud

label = "طلب 123"
message = "Ticket: " + "\u2068" + label + "\u2069" + "; status: open"
assert message.startswith("Ticket: \u2068")
assert message.endswith("\u2069; status: open")

for index, ch in enumerate(message):
    code_point = f"U+{ord(ch):04X}"
    name = ud.name(ch, "<unnamed>")
    direction = ud.bidirectional(ch) or "<none>"
    if ch in "\u2066\u2067\u2068\u2069":
        assert direction in {"LRI", "RLI", "FSI", "PDI"}
    print(f"{index:02d} {code_point:8} {direction:4} {name}")

print("storage_round_trip:", message.encode("utf-8").decode("utf-8") == message)

A runtime's unicodedata tables may implement an earlier Unicode edition than the reference baseline for this article. The display algorithm and its implementation data must be tested separately if normative conformance matters. The crucial outcome is that the logical string remains unchanged by a display decision, and the isolate controls are visible in diagnostic output by code point.

28. Python: Safe Audit Rendering of Invisible Format Controls

In source files, logs, customer-service records, or archival repositories, control characters can change how a string appears without changing its meaning to a parser. A useful diagnostic formatter renders selected directional controls as visible labels, preserving the original value in a separate field. Do not indiscriminately erase these characters from user content; record them and apply context-sensitive validation policies.

import unicodedata

VISIBLE = {
    "\u061c": "<ALM>", "\u200e": "<LRM>", "\u200f": "<RLM>",
    "\u202a": "<LRE>", "\u202b": "<RLE>", "\u202c": "<PDF>",
    "\u202d": "<LRO>", "\u202e": "<RLO>",
    "\u2066": "<LRI>", "\u2067": "<RLI>",
    "\u2068": "<FSI>", "\u2069": "<PDI>",
}

def show_controls(value: str) -> str:
    return "".join(VISIBLE.get(ch, ch) for ch in value)

raw = "Ticket: " + "\u2068" + "طلب 123" + "\u2069" + "; status: open"
inspectable = show_controls(raw)
assert inspectable == "Ticket: <FSI>طلب 123<PDI>; status: open"
print(inspectable)
print("Unicode database:", unicodedata.unidata_version)
print("original UTF-8 bytes:", raw.encode("utf-8").hex(" "))

The inspector does not perform bidi reordering and is not a substitute for a forensic hex dump. For systems accepting arbitrary user text, audit views may additionally escape newline, tab, nonprinting controls, and exceptionally long strings. Keep raw and sanitized diagnostic copies separate so investigators can reconstruct what was actually received.

29. JavaScript: Isolating User-Provided Labels in the DOM

Web applications frequently insert names, search results, or product descriptions with unknown direction into a fixed-direction page. The safest general pattern is to use the browser's text APIs and semantic isolation instead of concatenating untrusted strings into raw HTML. The next function builds a row containing a label, a dynamic value, and a trailing status.

function makeTicketRow(ticketName, statusText) {
  const row = document.createElement("p");
  row.dir = "ltr";                    // Known English page context.
  row.append(document.createTextNode("Ticket: "));

  const value = document.createElement("bdi");
  value.dir = "auto";                 // Unknown inserted text direction.
  value.textContent = ticketName;     // No untrusted HTML interpretation.
  row.append(value);

  row.append(document.createTextNode("; status: " + statusText));
  return row;
}

document.body.append(makeTicketRow("طلب 123", "open"));

bdi helps keep the title's directional influence local. textContent prevents embedded markup from being executed as HTML. Those protections are distinct: bidi isolation does not sanitize malicious HTML, and HTML escaping does not by itself guarantee correct bidi display. A complete application still needs content rules, authentication, a safe rendering strategy, and regression tests with both RTL and LTR content.

When the direction of a field is known from trusted metadata, a correctly chosen explicit direction can be preferable to a heuristic. Avoid using CSS-only overrides to hide errors introduced by improper field boundaries.

30. JavaScript: Code Points, Code Units, and Display Limits

JavaScript strings are indexed in UTF-16 code units; the spread operator iterates code points, while visible grapheme clusters may contain several code points. None of those APIs computes the UBA or picks visual line breaks. The following example reports the distinct counts and shows that the logical text survives an ordinary iteration.

const example = "A😀 طلب";
const codePoints = Array.from(example);
const codeUnits = example.length;
const utf8Bytes = new TextEncoder().encode(example).length;

console.log({ codeUnits, codePoints: codePoints.length, utf8Bytes });
if (codeUnits <= codePoints.length) {
  throw new Error("The supplementary character should use two UTF-16 units");
}
if (codePoints.join("") !== example) throw new Error("Logical sequence changed");

// Intl.Segmenter counts grapheme clusters, not bidi runs or line breaks.
if (typeof Intl.Segmenter === "function") {
  const segmenter = new Intl.Segmenter("en", { granularity: "grapheme" });
  console.log("graphemes", [...segmenter.segment(example)].length);
}

Intl.Segmenter can supply grapheme segmentation where supported, but line breaking and bidi resolution require other APIs or text engines. Do not mistake the order of Array.from(example) for an already resolved visual sequence. Unicode data versions and ICU availability vary across browsers and JavaScript runtimes.

31. Windows PowerShell 5.1: Inspect a Mixed-Script String

Windows PowerShell 5.1 runs on .NET Framework and uses UTF-16 strings. The following routine reports each UTF-16 code unit and escapes the two isolate controls used in a sample. It does not claim to implement the Unicode Bidirectional Algorithm. The code units of supplementary characters can form surrogate pairs, so advanced code-point iteration must treat them as a pair rather than as two independent Unicode scalar values.

# PowerShell 5.1: construct the source without embedding invisible controls
$start = [char]0x2068  # FSI
$end   = [char]0x2069  # PDI
$label = 'طلب 123'
$text  = 'Ticket: ' + $start + $label + $end + '; status: open'

for ($i = 0; $i -lt $text.Length; $i++) {
    $u = [int][char]$text[$i]
    $tag = switch ($u) {
        0x2068 { '<FSI>'; break }
        0x2069 { '<PDI>'; break }
        default { $text[$i].ToString() }
    }
    '{0:D2}  U+{1:X4}  {2}' -f $i, $u, $tag
}

$bytes = [System.Text.Encoding]::UTF8.GetBytes($text)
Write-Output ('UTF-8 byte count: ' + $bytes.Length)
Write-Output ('Control pairs present: ' +
    ($text.Contains([string]$start) -and $text.Contains([string]$end)))

Because console output and fonts vary, a terminal may not display mixed bidi strings as a standards-conformant browser does. Compare the encoded code-unit values to avoid drawing conclusions from the appearance of a particular console host. This example is intended for Windows PowerShell 5.1; it is not a test of the host renderer.

32. Directional Text Across Records, APIs, and Logs

A durable data model should store a text field and any applicable direction or language metadata separately whenever feasible. Typical fields might include value, language_tag, display_direction, and source_encoding. A language tag alone may be insufficient: names, quotes, and technical identifiers may have a different direction from the application's main language.

In APIs and databases, document whether direction controls are permitted in source strings; if so, define validation and escaping behavior and do not normalize or strip characters without an explicit contract. Two strings with identical visible glyphs may differ by invisible controls, and a byte-for-byte hash will detect that difference. A search index may choose its own comparison policy, but a litigation record or audit log should preserve the submitted original.

Log systems often concatenate independently controlled fields into one line. This is an especially important site for isolation and diagnostic rendering: a malicious or merely unusual title can make an adjacent timestamp or category appear associated with the wrong event. Store structured fields separately, escape controls in reviewer-facing output, and support retrieval of the original unmodified bytes where evidence requirements justify it.

33. Unicode Bidirectional Text and Security Boundaries

The ability to change visual ordering without changing logical source order creates security risks in code review, filenames, displayed identifiers, terminal output, and logs. A known class of source-code deception uses bidi control characters to make displayed comments or tokens appear in a different relationship from the parser's interpretation. Such controls are not the only possible source of display confusion, and the presence of Arabic or Hebrew text is not evidence of abuse.

Defensive controls should be context-specific: show the names of bidi formatting characters in source-code review tools; constrain or lint them in programming-language identifiers or security-sensitive fields under a documented policy; keep logs structured; and use isolation for legitimate foreign-language text in the user interface. Review Unicode Technical Standard #55 and the relevant source-language or repository guidance rather than inventing a universal rule that bans RTL scripts.

The fundamental threat is disagreement between human review and machine interpretation. Mitigations must make the logical sequence observable while preserving linguistic accessibility. Do not depend on an apparently neat screenshot as proof that the source contained no direction controls.

34. Visual Spoofing, Confusables, and False Positives

Bidi controls are one component of a broader Unicode security problem. Confusable characters across scripts, lookalike punctuation, zero-width controls, case folding, and normalization can all contribute to misleading labels. These issues require different defenses: Unicode case folding cannot prevent bidi reordering, and bidi isolation cannot eliminate confusable identifiers.

A practical product separates ordinary display content from identifiers with strong requirements. User names and messages should generally support international scripts. A machine resource identifier may require a stricter allowed-character profile and transparent error messages. An audit UI should reveal directional formatting in a non-destructive way while retaining the source for evidence.

Flagging all text with Arabic characters as malicious would generate enormous false positives and undermine legitimate use. Instead, focus on suspicious control usage for the particular context, hidden changes in logical ordering, and discrepancies between displayed and parsed values.

35. Line Wrapping, Reordering, and Editing Operations

The interaction of line breaking and bidi ordering is one reason ad hoc string manipulation fails. A long mixed paragraph may wrap into several visual lines while its logical string remains one paragraph. Bidi resolution has line-level steps, including treatment of whitespace and trailing controls. The positions of some neutral characters can therefore differ from what a simplistic one-line demonstration suggests.

Text editing should support intuitive visual cursor motion, logical selection of stored substrings, appropriate grapheme boundaries, and safe copy/paste. The text copied from a browser should represent logical content, not a handcrafted visual reverse. Where users inspect a code sample or legally important identifier, provide a secondary, explicit representation of its code points or hex bytes.

Avoid truncating before applying isolation. If a UI is forced to shorten a long name, do so on a meaningful grapheme boundary and ensure that any presentation-layer isolate structure remains properly paired. Truncation rules must not leave one part of the adjacent sentence under the wrong directional scope.

36. Worked Investigation: Invoice Label in Two Contexts

A team maintains an English billing dashboard and an Arabic mobile application. The stored record contains title = "طلب 123", invoice_id = "INV-2048", and status = "open". The data layer has no reason to reverse the Arabic title or the identifier; the two UIs use different presentation metadata.

37. Testing Strategy for Internationalized Text Systems

A serious Unicode-aware test suite separates encoding, algorithmic, layout, and product-level requirements. At the encoding layer, verify byte decoding and source round trips. At the bidi layer, use version-matched Unicode BidiTest.txt and BidiCharacterTest.txt data when testing a bidi engine. At the line-breaking layer, use the corresponding version of LineBreakTest.txt. These tests are more authoritative than ad hoc screenshots.

38. Implementation Checklist for Teams

First, identify the authoritative logical text source and whether it is decoded strictly. Second, establish paragraph direction by trusted structure rather than visual guesswork when possible. Third, isolate inserted foreign-language or unknown-direction fields. Fourth, use a compliant text engine that implements bidi ordering, line-break classes, and relevant script shaping; avoid hand reversal. Fifth, distinguish source storage from presentation controls so copy/paste and search remain predictable.

Sixth, version Unicode and locale-related data in reproducible builds. Seventh, apply a documented field-level policy for invisible formatting controls, with more restrictive rules only where appropriate (for example, source-code identifiers). Eighth, expose inspectable diagnostics for audits and incident response. Ninth, test both LTR and RTL interfaces with mixed numbers and punctuation. Tenth, retest after upgrades to fonts, browsers, Unicode data, or layout libraries, because behavior can change even if bytes remain constant.

These activities serve both user experience and operational assurance: a readable invoice, correct Arabic customer name, reliable financial reference, and auditable source record depend on preserving the distinction between data and layout.

40. Answer Guidance and Expected Reasoning

Questions 1–3 should identify stored character order, directional runs, and the unchanged sequence of numerical digits. Questions 4–6 should identify Arabic and Hebrew strong types, European or Arabic number types, punctuation as neutral in many settings, and the role of paragraph-level direction. Questions 7–9 should explain that isolates constrain the influence of inserted text, while display direction, language, alignment, and writing mode encode different decisions.

Questions 10–13 should distinguish glyph joining from bidi ordering and from segmentation or line-break rules, and should compare characters that introduce, inhibit, or condition line breaks. Questions 14–17 should preserve the original machine identifier, record Unicode-version and layout assumptions, and use explicit control inspection in logs. Questions 18–20 should formulate proportionate security controls, identify version-matched conformance test data, and avoid confusing visual rendering with byte-level evidence.

The governing answer in most exercises is not “reverse the string”; it is “preserve the logical string, provide trustworthy direction metadata or isolation, and render through an appropriate Unicode-aware system.”

44. Synthesis: A Stable Contract for Multilingual Text

The central engineering contract is never confuse bytes, logical Unicode characters, resolved visual order, word or grapheme boundaries, and line-break decisions. Text storage does not dictate every glyph, and an apparently reasonable screenshot does not prove that the original data is correct. Mixed English–Arabic labels become manageable when source fields are preserved, paragraph direction is explicit, dynamic content is isolated, and display is delegated to a conforming engine.

For an institution maintaining searchable archives, technical documentation, databases, and multilingual instruction, the same rule improves usability, interoperability, and accountability: preserve the original; attach trustworthy metadata; choose algorithms by role; and make invisible controls visible to diagnostic tools when appropriate. The result is more reliable text handling without sacrificing support for legitimate right-to-left writing systems.
