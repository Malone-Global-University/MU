Definition, Purpose, and Scope

A byte-order mark (BOM) is an initial encoding signature formed by serializing the Unicode character U+FEFF at the beginning of a byte stream. In UTF-16 and UTF-32, that signature can identify the byte order used to serialize multibyte code units; in UTF-8, which has no alternative endian byte order, the same character's three-byte sequence can serve only as an optional encoding signature. The phrase byte-order mark therefore names a historical and technical convention rather than a requirement that every text file begin with a marker. An interchange design can use an explicit encoding label, a specified byte order, a BOM, or a combination permitted by its governing format. These mechanisms are related, but are not interchangeable.

The central engineering question is not merely whether a file begins with EF BB BF or FF FE. It is what authority defines the stream's encoding, what the first bytes mean under that authority, and how the receiver handles disagreement. An initial signature is an observable byte pattern. It does not authenticate the file, prove that subsequent bytes are well formed, or override every protocol-specific rule. Correct processing keeps the Unicode scalar value, its UTF code units, the serialized byte order, and the higher-level data format distinct.

This specialist article belongs to the MGU Encyclopedia's Character Encoding unit. It focuses on U+FEFF, UTF-8/UTF-16/UTF-32 signatures, generic and explicitly endian-labeled Unicode encoding schemes, detection precedence, incremental input, interoperability, and safe inspection of real files. The neighboring UTF-8, UTF-16, and UTF-32 articles explain the individual encoding forms more fully. The neighboring Binary Data article on endianness explains ordering for nontext numeric records.

Learning Objectives and Diagnostic Questions

After reading, students should be able to distinguish a BOM from a byte-order convention; decode the five common Unicode signatures; calculate the byte representation of U+FEFF and ordinary characters; explain why UTF-8 needs no byte-order negotiation; choose between an encoding declaration and signature according to an interchange contract; inspect a file without changing it; and design a decoder that recognizes a signature only where the protocol permits one. Readers should also be able to identify when a BOM becomes visible text, when an explicit endian declaration conflicts with an apparent signature, and why a valid signature is not evidence of valid payload data.

Before proceeding, try four diagnostic questions. If 41 00 represents the letter A in one UTF-16 byte order, what does 00 41 represent? Why does EF BB BF not imply a big- or little-endian choice? Why must a parser check four-byte UTF-32 signatures before interpreting the shorter FF FE UTF-16LE prefix? And what happens if a data-processing pipeline adds a BOM to every record rather than only at the start of a stream? Each question has a distinct answer at the boundary between bytes and characters.

Historical Origin and Unicode Standardization

The byte-order problem became prominent when multibyte character values were stored or transmitted between systems with different byte-order conventions. A sixteen-bit value such as 0x0041 can be written as 00 41 (most-significant byte first) or 41 00 (least-significant byte first). A receiver that knows only that it is looking at sixteen-bit units but not how the bytes were ordered may produce the wrong numerical values. U+FEFF provided a reversible indicator: its byte-swapped 16-bit pattern is 0xFFFE, a designated noncharacter, making the orientation conspicuous when read incorrectly.

Historically U+FEFF also carried a zero-width no-break-space function. Its preferred modern use is as an initial signature; U+2060 WORD JOINER is the recommended way to request the word-joining effect in text. The historic name ZERO WIDTH NO-BREAK SPACE remains associated with U+FEFF in character data, but does not make an embedded U+FEFF an encoding signature. The position, decoding scheme, and governing format determine the distinction.

The Unicode Standard makes the encoding-form/encoding-scheme distinction explicit. UTF-16 and UTF-32 encoding forms work in 16-bit and 32-bit code units; their schemes determine serialization into bytes. UTF-8 is already a byte-oriented encoding form and encoding scheme. The Unicode Standard does not require a BOM for conformant Unicode text; byte-order and signature requirements arise from the selected scheme and higher-level protocols. See Unicode Standard 18.0, Chapter 3 and Chapter 23, §23.8.

Code Points, Code Units, Serialized Bytes, and Glyphs

A code point is a numerical position in the Unicode codespace. A Unicode scalar value is a code point other than a surrogate value in U+D800–U+DFFF. A code unit is the basic element of an encoding form: eight bits for UTF-8, sixteen for UTF-16, thirty-two for UTF-32. A serialized byte stream is a sequence produced from those code units according to an encoding scheme. A glyph is a visual shape rendered by a font and shaping system, which is not the same thing as a code point or a byte string.

For the capital Latin letter A, Unicode uses U+0041. UTF-8 serializes it as 41; UTF-16BE as 00 41; UTF-16LE as 41 00; UTF-32BE as 00 00 00 41; and UTF-32LE as 41 00 00 00. The letter and its code point stay constant. Only the encoding form and byte serialization change. A BOM is not a replacement for this mapping; it can supply an initial clue as to which serialization was used.

Big-Endian and Little-Endian Byte Order

Big-endian serialization places the most significant byte of a multibyte code unit first. Little-endian serialization places its least significant byte first. The words describe byte ordering within the unit, not the direction of reading, the byte values themselves, or the sequence of Unicode scalar values in text. When a UTF-16 supplementary character uses a high surrogate followed by a low surrogate, that code-unit sequence stays in the same order under both endian conventions; only the two bytes within each code unit are reversed.

For example, U+1F600 GRINNING FACE is represented by UTF-16 code units D83D DE00. UTF-16BE writes D8 3D DE 00; UTF-16LE writes 3D D8 00 DE. It is wrong to reverse all four bytes or swap the high and low surrogates. The same distinction applies when a binary record contains numeric length fields followed by UTF-16 text: the record's numeric-field endianness and the text field's encoding scheme may be independent contracts, even when a format designer chooses to align them.

Modern computers often store native integers in little-endian order, but a program must not rely on the host CPU to infer the encoding of an external file. A correctly designed interoperable format specifies byte order, uses an unambiguous signature where allowed, or carries a higher-level declaration. Native platform defaults are implementation details, not reliable archival metadata.

What U+FEFF Means at the Beginning of a Stream

When a decoder is using a generic Unicode scheme that recognizes an initial signature, a leading encoding of U+FEFF may be interpreted as a BOM and removed from the decoded text. Its job is to orient the receiver or identify UTF-8. After that decision, ordinary text begins. But U+FEFF can also be an actual encoded character, especially in an explicitly endian-labeled scheme or later inside a stream. The Unicode Standard's distinctions are precise: under UTF-16LE or UTF-16BE as explicitly named schemes, any initial bytes encoding U+FEFF represent the character U+FEFF in text, not an orientation signature; generic UTF-16 may use the signature to determine orientation. The analogous distinction applies to UTF-32LE/BE versus generic UTF-32.

This distinction is often obscured by software API names. An application may label an output file “UTF-16LE with BOM” when what it means operationally is “little-endian UTF-16 bytes preceded by the signature consumed by an auto-detecting UTF-16 reader.” That can work within the application, but the formal protocol must define whether the leading marker is out-of-band signature or content. A robust program avoids inferring the policy solely from the API's informal naming.

If the first actual text scalar is intentionally U+FEFF and the protocol uses initial BOM recognition, the producer may need a second U+FEFF: the first supplies the signature and the second is content. In ordinary modern text, U+2060 is normally preferable for intentional word-joining. Do not silently remove embedded U+FEFF characters from records, signed documents, identifiers, or archival text; that is a data mutation.

The Five Common Unicode Signature Byte Sequences

Encoding scheme or signature Initial hex bytes Meaning and length
UTF-8 signature EF BB BF Three bytes; encoding identification only, no endian choice
UTF-16 big-endian FE FF Two bytes; next sixteen-bit units are big-endian
UTF-16 little-endian FF FE Two bytes; next sixteen-bit units are little-endian
UTF-32 big-endian 00 00 FE FF Four bytes; next thirty-two-bit units are big-endian
UTF-32 little-endian FF FE 00 00 Four bytes; next thirty-two-bit units are little-endian

All five patterns encode the same Unicode character U+FEFF, using the corresponding encoding form and byte serialization. They are not five distinct Unicode characters. For example, 0xFEFF is represented as FE FF in UTF-16BE and FF FE in UTF-16LE. UTF-32BE pads its 32-bit value with two leading zero bytes, while UTF-32LE puts the less-significant bytes first. UTF-8 encodes U+FEFF as EF BB BF using its ordinary variable-width algorithm.

A signature table is a starting point for inspection, not a complete file-format detector. A file can begin with those byte patterns accidentally, include an ordinary U+FEFF code point at its start, or have a binary container that explicitly excludes BOM recognition. The format contract governs the meaning.

Why UTF-8 Has No Byte-Order Problem

UTF-8 is a sequence of one-byte code units; every unit is already a byte. Multibyte UTF-8 characters use a specified sequence of individual lead and continuation bytes, not a sixteen- or thirty-two-bit code unit that can be serialized in two orientations. Consequently, there is no UTF-8BE or UTF-8LE encoding scheme. EF BB BF at the beginning of UTF-8 data is an optional signature, not a byte-order setting.

The Unicode Standard allows a UTF-8 signature but does not require it; a format or protocol may forbid or discourage it. RFC 3629 discusses the signature and interchange consequences. A producer cannot assume that every UTF-8 consumer will discard those three bytes. A byte-oriented tool may treat them as data: a first header name might become \ufeffid, a script interpreter may reject an apparent extra prefix, or a binary-field parser may misread the first three bytes. A consuming application should establish its UTF-8 BOM policy rather than assume that “valid UTF-8” entails “BOM accepted everywhere.”

The recommendation is protocol first. For a new API, JSON body, application configuration, or source file, follow the format's explicit encoding rules. If the format specifies UTF-8 without a signature, do not add one. If a legacy file workflow benefits from a UTF-8 signature and its consumers support it, the signature can be a deliberate compatibility choice. “Always add a BOM” and “always strip a BOM” are both poor universal rules.

UTF-16: Code-Unit Order and Orientation Detection

UTF-16 uses 16-bit code units. For a text stream labeled merely UTF-16, the initial two bytes may carry a BOM that chooses endian orientation. When no BOM or higher-level protocol specifies the orientation, the Unicode Standard defines big-endian as the default for the UTF-16 encoding scheme. An application-specific format may instead require little-endian, but that requirement must be stated separately; it does not change the Unicode scheme's default rule.

Suppose the text is Aé. Its UTF-16 code units are 0041 00E9. With a generic UTF-16 BOM in big-endian order the serialized bytes are FE FF 00 41 00 E9. With a generic UTF-16 BOM in little-endian order they are FF FE 41 00 E9 00. Without a signature, 00 41 00 E9 is unambiguously UTF-16BE only once the format or Unicode default is known. 41 00 E9 00 may be expected from a Windows-origin file that explicitly chooses UTF-16LE, but a standards-aware decoder should not guess little-endian from the operating system alone.

A swapped BOM interpreted in the wrong orientation becomes U+FFFE, a Unicode noncharacter. This is a useful symptom of byte-order confusion, but it is not a substitute for the file's declared scheme. Other code units may decode into well-formed but incorrect characters, so relying only on a validity error would miss some mistakes.

UTF-32: Four-Byte Orientation and Validation

UTF-32 uses a 32-bit code unit numerically equal to the scalar value it represents. UTF-32BE serializes each unit most-significant byte first and UTF-32LE least-significant byte first. Generic UTF-32 may use an initial BOM to orient decoding. Without either a signature or a higher-level declaration, the Unicode Standard uses big-endian for the UTF-32 encoding scheme.

For the text A😀, the code units are 00000041 0001F600. UTF-32BE with a BOM is 00 00 FE FF 00 00 00 41 00 01 F6 00; UTF-32LE with a BOM is FF FE 00 00 41 00 00 00 00 F6 01 00. A UTF-32 decoder must also reject scalar values above U+10FFFF and surrogate code points in U+D800–U+DFFF, even when the byte order was determined correctly. A correct four-byte alignment and a correct signature do not prove that all following units are legal Unicode scalar values.

Because FF FE 00 00 starts with the two-byte UTF-16LE BOM FF FE, a detector that checks two-byte signatures first may misclassify a UTF-32LE file as UTF-16LE. Test all relevant signatures with longest match first and obey the supported-format contract. Conversely, treating a four-byte prefix as sufficient proof of UTF-32LE in an arbitrary binary file is also unwarranted; a metadata record could begin with those bytes for unrelated reasons.

Encoding Form versus Encoding Scheme

The Unicode Standard uses encoding form for the mapping from scalar values to code units and encoding scheme for serialization of code units into bytes. UTF-16 the encoding form uses units 0x0041 and 0xD83D,0xDE00, independent of byte orientation. UTF-16BE and UTF-16LE encoding schemes fix that orientation in their names. Generic UTF-16, with its BOM/default behavior, is a separate specified encoding scheme.

UTF-16 generic scheme 16 bits Determined by BOM, higher protocol, or BE default Initial signature can determine order
UTF-16BE / UTF-16LE 16 bits Yes, explicitly Initial U+FEFF bytes are encoded character content under the named scheme
UTF-32 generic scheme 32 bits Determined by BOM, higher protocol, or BE default Initial signature can determine order
UTF-32BE / UTF-32LE 32 bits Yes, explicitly Initial U+FEFF bytes are encoded character content under the named scheme

This is a standards-level distinction. Some decoders deliberately offer a convenience option to remove an initial signature even when the application supplied an explicit endian label. That is a documented application policy, not evidence that the base encoding scheme changed. Where fidelity is important, configure the decoder to match the selected file or protocol grammar.

Surrogate Pairs Are Not Reordered by Endianness

A common implementation error is treating endian conversion as a reversal of an entire encoded character. Take U+1F600 GRINNING FACE. Its UTF-16 code units, in Unicode-defined logical order, are high surrogate D83D followed by low surrogate DE00. UTF-16BE writes D8 3D DE 00; UTF-16LE writes 3D D8 00 DE. Reversing all four bytes gives 00 DE 3D D8, which is not correct UTF-16LE serialization of the same two code units.

When parsing UTF-16, read two bytes per code unit using the selected byte order. Then validate the UTF-16 grammar: a high surrogate must be followed by a low surrogate, and a low surrogate must not appear alone. This validation occurs after byte-order interpretation. The same principle applies to UTF-32: read four-byte units using the declared order, then reject invalid scalar values. Byte-order selection and encoding validity are logically separate checks.

The Noncharacter U+FFFE and Why It Matters

U+FFFE is a designated Unicode noncharacter. It is a valid Unicode scalar value but a permanently reserved noncharacter, not an ordinary assigned text character; its special numerical value is highly useful for recognizing an incorrectly byte-swapped initial U+FEFF. The byte sequence FE FF means an initial U+FEFF signature under the generic UTF-16 scheme when decoded as big-endian. If a reader incorrectly decodes those bytes as little-endian, it obtains FFFE. The reverse holds for FF FE decoded as big-endian. Under an explicitly named UTF-16BE or UTF-16LE scheme, however, these bytes follow that scheme's normal content semantics rather than generic BOM detection.

Do not generalize from this special case to assert that all noncharacters make an entire text stream invalid. The Unicode Standard distinguishes noncharacters from surrogate code points, and noncharacters are valid scalar values even though their use is reserved for internal purposes. Applications and protocols may impose narrower policies. The key point here is that U+FFFE was deliberately useful as a signature mismatch indicator, while neither U+FFFE nor a successful U+FEFF check replaces full content validation.

Byte Order Marks Versus Other File Signatures

A file may start with a magic number or binary header that is unrelated to Unicode. PNG, ZIP, gzip, executable formats, and application containers use identifying structures with their own parsing grammar. A BOM is an encoding signature within a text-encoding interpretation; it is not a generic magic-number language for every file. A binary container may contain UTF-8 fields, UTF-16 strings, or UCS labels at fixed offsets without permitting any BOM at the container's beginning. Conversely, a plain-text document can legitimately start with a BOM even though its filename extension says nothing about encoding.

A parser should determine container format first, when the context supplies one, and then apply the container's designated encoding to the relevant field. Do not remove EF BB BF from the first bytes of an arbitrary PNG, ZIP, or data record. In a mixed binary/text record, the length prefix, version number, and signature each have a separate responsibility. If the container's grammar defines text as an octet slice, a BOM inside that slice may or may not be legal according to the field's specified text encoding.

How Declarations, Signatures, and Defaults Interact

A robust system defines an authority order. A protocol or file-format specification may require a particular encoding and forbid BOMs; in that case, a conflicting marker indicates malformed input or a disagreement to report, not permission to rewrite the contract. For generic UTF-16/32 text without a higher-level specification, an allowed initial BOM can set the endian orientation; absent that, the Unicode scheme has a big-endian default. A browser's HTML decoding algorithm has its own precedence rules and cannot be generalized to every file type.

HTML, Web Content, and Browser BOM Recognition

In HTML, a leading UTF-8 BOM can be used by the encoding-sniffing algorithm to recognize UTF-8. Modern HTML processing gives this initial signature higher precedence than competing encoding declarations in that decoding pathway. This is a web-specific rule. It does not mean the BOM is a sensible default for every HTML file or that a general-purpose CSV parser must behave like a web browser. The W3C Internationalization guidance explains the practical consequences of UTF-8 BOMs in HTML, including surprising mismatches with labels and declarations.

For MGU encyclopedia HTML files, a visible <meta charset="UTF-8"> declaration is part of the established page shell. That declaration identifies the intended encoding of the HTML source, independently of whether the on-disk UTF-8 file has a BOM. A clean UTF-8 file without a BOM is suitable when the site's hosting and build system reliably preserve UTF-8; inserting a BOM should be a deliberate deployment choice if any tooling has a known compatibility need. Do not treat source-level metadata as proof that the actual file bytes match the declaration: the publication pipeline must preserve the intended encoding.

See W3C Internationalization: Declaring Character Encodings in HTML and The Byte-Order Mark in HTML.

CSV, Command-Line Tools, and Spreadsheet Interoperability

CSV is a family of practices rather than a universal BOM policy. Some spreadsheet import paths have historically recognized a UTF-8 BOM as a useful signal; other text tools treat its leading bytes as data. If a CSV header begins with EF BB BF and a simple UTF-8 decoder retains U+FEFF, the first field name may be \ufeffaccount_id instead of account_id. These strings are visually similar yet have different code-point sequences and may fail exact-name matching. The same problem can occur in shell scripts, configuration files, and legacy data importers.

A safe CSV import workflow specifies the expected encoding, tests whether a BOM is permitted, removes a recognized initial encoding signature only when authorized, and preserves raw bytes for auditability. It does not remove U+FEFF from every cell or strip arbitrary leading characters. If the file is a legal record, document the original byte hash, declared encoding, signature treatment, and output transformation.

JSON, XML, and Other Format-Specific Policies

General Unicode permission to use a BOM does not supersede more restrictive application formats. RFC 8259 specifies that JSON text exchanged between systems not part of a closed ecosystem must be UTF-8; networked generators MUST NOT add a BOM, while parsers MAY ignore a BOM rather than reject the text. Thus a receiver's tolerance does not grant producers permission to emit one in interoperable JSON. XML defines its own encoding-detection and declaration conventions: BOM handling depends on document encoding and the XML processor's rules, not on arbitrary stripping at any byte position.

A robust application must distinguish wire-format conformance from decoder convenience. A programming library may accept a UTF-8 BOM even where a protocol disallows producing it. When publishing APIs or archiving records, cite the specific protocol and configure readers and writers accordingly. For JSON, see RFC 8259, §8.1; for XML, consult the relevant version of the W3C XML specification.

Detecting Signatures Without Overreading the Input

A decoder may receive data a few bytes at a time: one byte from a socket, two from a buffered file, and more from subsequent reads. It must not finalize a BOM decision prematurely when the prefix might still grow into a longer supported signature. For instance, FF FE might be a complete UTF-16LE signature, but the full four-byte prefix FF FE 00 00 matches UTF-32LE. If UTF-32LE is supported and the context allows generic detection, wait until enough input is available to distinguish the possibilities, or use declared metadata to choose immediately.

The maximum signature length in the common table is four bytes. A detector can retain up to four leading bytes while it checks supported encodings, but it also needs an end-of-stream rule: a two-byte UTF-16 BOM followed by end of file is a valid empty UTF-16 text payload, whereas a partial UTF-32 marker may be malformed. More importantly, even a definitive signature requires subsequent length divisibility and encoding-form validation. Keep the signature-detection state separate from payload streaming and cap the input size according to application policy.

Signature Detection Algorithm and Precedence

For unlabelled generic Unicode text in a format that explicitly allows signature-based detection, a practical detection order is: test 00 00 FE FF for UTF-32BE; FF FE 00 00 for UTF-32LE; EF BB BF for UTF-8; FE FF for UTF-16BE; and FF FE for UTF-16LE. After selecting an allowed signature, remove only its initial bytes, decode using the selected byte order and validate all subsequent input. If no signature is present, do not invent one: use the required encoding from the enclosing protocol or the permitted scheme's default. If neither is known, report uncertainty or use an explicitly documented heuristic policy.

An implementation may not support UTF-32; its algorithm should exclude unsupported schemes rather than falsely advertising complete detection. If a file has two signatures at its start, such as EF BB BF EF BB BF, a signature-aware UTF-8 decoder may remove the first and deliver a leading U+FEFF character from the second. A second deletion would be a separate normalization decision, not ordinary signature detection. The detector should also reject or report a signature that conflicts with an authoritative encoding declaration instead of silently “fixing” it unless the applicable format explicitly defines precedence otherwise.

Python Example: Inspect and Decode Common Signatures

The following self-contained example demonstrates exact signatures, deterministic longest-first matching, and strict decoding. It is a teaching detector for unlabelled Unicode streams, not a replacement for protocol-specific parsing. In particular, it does not assume that signature-like bytes in an arbitrary binary container authorize text decoding.

BOMS = (
    (b"\x00\x00\xfe\xff", "utf-32-be", "UTF-32BE"),
    (b"\xff\xfe\x00\x00", "utf-32-le", "UTF-32LE"),
    (b"\xef\xbb\xbf", "utf-8", "UTF-8"),
    (b"\xfe\xff", "utf-16-be", "UTF-16BE"),
    (b"\xff\xfe", "utf-16-le", "UTF-16LE"),
)

def decode_signed_unicode(data: bytes):
    for signature, codec, label in BOMS:
        if data.startswith(signature):
            text = data[len(signature):].decode(codec, errors="strict")
            return label, text
    raise ValueError("No recognized initial Unicode signature; supply a declared encoding")

for codec, label in [("utf-8-sig", "UTF-8"), ("utf-16", "UTF-16"), ("utf-32", "UTF-32")]:
    payload = "Aé".encode(codec)
    detected, result = decode_signed_unicode(payload)
    assert result == "Aé", (codec, result)
    print(label, payload.hex(" "), "=>", detected, repr(result))

assert decode_signed_unicode(bytes.fromhex("ff fe 00 00 41 00 00 00")) == ("UTF-32LE", "A")
try:
    decode_signed_unicode(b"\xff\xfe\x41")
except UnicodeDecodeError:
    print("Truncated UTF-16 code unit: rejected")
else:
    raise AssertionError("An incomplete code unit must fail")

Use a fully qualified format contract for production. With explicit UTF-16LE bytes, decoding through utf-16-le retains a leading U+FEFF as a character, while Python's BOM-aware utf-16 codec consumes the signature and selects byte order. The difference is intentional and demonstrates why an API parameter is part of the interpretive contract.

This second example prints the exact five signatures from the comparison table and verifies the decoded text using BOM-aware or explicit endian codecs. It also confirms that a UTF-8 BOM does not alter text-byte order: the UTF-8 payload after the signature is unchanged.

text = "Aé"
examples = {
    "UTF-8 with BOM": (b"\xef\xbb\xbf" + text.encode("utf-8"), "utf-8-sig"),
    "UTF-16BE": (b"\xfe\xff" + text.encode("utf-16-be"), "utf-16"),
    "UTF-16LE": (b"\xff\xfe" + text.encode("utf-16-le"), "utf-16"),
    "UTF-32BE": (b"\x00\x00\xfe\xff" + text.encode("utf-32-be"), "utf-32"),
    "UTF-32LE": (b"\xff\xfe\x00\x00" + text.encode("utf-32-le"), "utf-32"),
}
for label, (raw, codec) in examples.items():
    assert raw.decode(codec) == text
    print(f"{label:13} {raw.hex(' ')}")

assert examples["UTF-32LE"][0].startswith(bytes.fromhex("ff fe 00 00"))
assert examples["UTF-16LE"][0].startswith(bytes.fromhex("ff fe"))
assert examples["UTF-32LE"][0][:4] != examples["UTF-16LE"][0][:4]

Python Example: U+FEFF as Content Versus Signature

The following comparison shows that a BOM-consuming generic reader and an explicitly endian-labeled reader can produce different textual results from the same raw bytes. It also demonstrates the critical distinction between removing a single initial signature and deleting all U+FEFF characters throughout a file.

raw = bytes.fromhex("ff fe 41 00")  # UTF-16LE BOM, then letter A
with_signature = raw.decode("utf-16")
with_explicit_le = raw.decode("utf-16-le")
assert with_signature == "A"
assert with_explicit_le == "\ufeffA"
print("Generic UTF-16:", repr(with_signature))
print("Explicit UTF-16LE:", repr(with_explicit_le))

# Two leading U+FEFF encodings: generic decoder removes the first only.
doubled = bytes.fromhex("ff fe ff fe 41 00")
assert doubled.decode("utf-16") == "\ufeffA"
print("Two markers:", repr(doubled.decode("utf-16")))

A byte-order marker recognized at position zero is out-of-band for that decoding pathway. U+FEFF at any later text position is a character. Whether that character is semantically appropriate is a distinct question from whether it should be removed during decoding.

Windows PowerShell 5.1: Read-Only Signature Inspection

On Windows PowerShell 5.1, Get-Content is not a dependable binary inspection primitive because it normally presents text after decoding. Use System.IO.File.ReadAllBytes for a read-only view of the actual file prefix and apply the encoding policy explicitly. The following example prints at most four leading bytes and reports known signatures without rewriting any file.

$path = 'C:\MGU\example-unicode-text.bin'
[byte[]]$data = [System.IO.File]::ReadAllBytes($path)
$prefix = ($data | Select-Object -First 4 | ForEach-Object { '{0:X2}' -f $_ }) -join ' '
Write-Host "Leading bytes: $prefix"

$patterns = @(
    @{ Name = 'UTF-32BE'; Bytes = [byte[]](0x00,0x00,0xFE,0xFF) },
    @{ Name = 'UTF-32LE'; Bytes = [byte[]](0xFF,0xFE,0x00,0x00) },
    @{ Name = 'UTF-8';    Bytes = [byte[]](0xEF,0xBB,0xBF) },
    @{ Name = 'UTF-16BE'; Bytes = [byte[]](0xFE,0xFF) },
    @{ Name = 'UTF-16LE'; Bytes = [byte[]](0xFF,0xFE) }
)

$match = $null
foreach ($p in $patterns) {
    if ($data.Length -lt $p.Bytes.Length) { continue }
    $equal = $true
    for ($i = 0; $i -lt $p.Bytes.Length; $i++) {
        if ($data[$i] -ne $p.Bytes[$i]) { $equal = $false; break }
    }
    if ($equal) { $match = $p.Name; break }
}
if ($null -eq $match) { Write-Host 'No recognized signature' }
else { Write-Host "Detected initial signature: $match" }

For a controlled UTF-16LE input format with no signature, construct a System.Text.UnicodeEncoding($false,$false,$true) object for strict little-endian decoding and pass the complete, length-checked byte slice to GetString. In .NET Framework, encoding objects and error fallbacks may have behavior that differs from a shell's default text decoding; explicit construction is safer than relying on Get-Content defaults or the machine's active ANSI code page.

Windows PowerShell 5.1: Encoding and BOM Creation

The following demonstration constructs the bytes directly rather than relying on ambiguous console or Out-File defaults. The file is created in a controlled temporary path and the BOM is inspected rather than inferred from an editor. Use this only where your chosen format permits a UTF-8 signature.

$text = 'A' + [char]0x00E9
$utf8 = New-Object System.Text.UTF8Encoding($true, $true)
[byte[]]$signature = $utf8.GetPreamble()
[byte[]]$payload = $utf8.GetBytes($text)
[byte[]]$data = New-Object byte[] ($signature.Length + $payload.Length)
[Array]::Copy($signature, 0, $data, 0, $signature.Length)
[Array]::Copy($payload, 0, $data, $signature.Length, $payload.Length)
$path = Join-Path $env:TEMP 'mgu-utf8-bom-demo.txt'
[System.IO.File]::WriteAllBytes($path, $data)
Write-Host ([System.BitConverter]::ToString([System.IO.File]::ReadAllBytes($path)))
# Expected: EF-BB-BF-41-C3-A9

Windows PowerShell 5.1's encoding defaults are not the same as PowerShell 7's. Out-File, redirection, Set-Content, and .NET file-writing APIs can use different defaults, especially around UTF-16LE and UTF-8 signatures. In portable workflows, write through explicitly constructed encoding objects or exact bytes, and confirm the resulting file prefix with a byte-level inspection tool.

JavaScript: Browser TextDecoder and BOM Behavior

The browser TextDecoder API has byte-order-mark behavior controlled by its encoding label and the ignoreBOM option; this API-specific behavior is distinct from the Unicode scheme's formal nomenclature. With ignoreBOM: false (the default), a BOM is generally consumed for supported Unicode decoding. With ignoreBOM: true, the resulting U+FEFF can remain in the returned text where applicable. The option's name is easy to misread: ignoring the BOM means not treating it specially as a removable signature, not automatically deleting it. See the WHATWG Encoding Standard.

const bytes = Uint8Array.from([0xEF, 0xBB, 0xBF, 0x41]);
const normal = new TextDecoder("utf-8").decode(bytes);
const preserved = new TextDecoder("utf-8", {ignoreBOM: true}).decode(bytes);
console.assert(normal === "A", "Default decoder should consume leading signature");
console.assert(preserved === "\uFEFFA", "ignoreBOM should preserve leading character");
console.log(JSON.stringify({normal, preservedCodePoints:
  Array.from(preserved).map(ch => ch.codePointAt(0).toString(16))}));

Browser and Node.js versions may vary in the breadth of accepted encoding labels, especially for UTF-32, which is not part of the WHATWG Encoding Standard's ordinary web TextDecoder label set. Do not assume that an API providing UTF-8 and UTF-16LE can decode UTF-32BE by name. For binary pipelines, choose the matching library and verify its BOM and error-handling contract.

A Byte-Exact Teaching Format: MUTF

Consider a fictional teaching container called MUTF, created solely for this article. It is not a registered file format. The container has an eight-byte header followed by a Unicode text payload. The fixed header is independent of text-endian rules: bytes 0–3 are ASCII MUTF, byte 4 is version 01, byte 5 is an encoding identifier (01 UTF-8; 02 UTF-16BE; 03 UTF-16LE; 04 UTF-32BE; 05 UTF-32LE), and bytes 6–7 are an unsigned big-endian length of the payload in bytes. The payload contains no BOM, because the header already declares an explicit encoding. This demonstrates a sound alternative to ambiguous auto-detection.

Byte offset Width Field Rule
0–3 4 bytes Magic MUTF ASCII 4D 55 54 46
4 1 byte Version 01
5 1 byte Encoding identifier 01–05, as specified above
6–7 2 bytes Payload length Unsigned 16-bit, big-endian
8 onward Declared length Encoded text bytes No in-band BOM; decode according to identifier

For the text Aé, encoded in UTF-16LE, the entire record is 4D 55 54 46 01 03 00 04 41 00 E9 00 (twelve bytes). The header declares the encoding and the four-byte payload length, so an initial U+FEFF sequence inside the payload—if deliberately included—would be text content. A safe parser rejects unexpected encoding identifiers, mismatched payload length, malformed text, and trailing bytes unless a surrounding protocol explicitly defines concatenated records.

Python Example: Strict MUTF Record Parsing

This executable example implements the teaching record, verifies exact length, uses strict text decoding, and prohibits a signature in the payload as an application-level rule. The format's encoding identifier is authoritative: do not guess a different encoding when decoding fails. This is a pedagogical specification, not a network standard.

CODECS = {
    1: "utf-8", 2: "utf-16-be", 3: "utf-16-le",
    4: "utf-32-be", 5: "utf-32-le",
}

def encode_mutf(text: str, code: int) -> bytes:
    if code not in CODECS:
        raise ValueError("Unsupported encoding identifier")
    payload = text.encode(CODECS[code], errors="strict")
    if len(payload) > 65535:
        raise ValueError("Payload exceeds 16-bit length")
    return b"MUTF" + bytes([1, code]) + len(payload).to_bytes(2,"big") + payload

def decode_mutf(raw: bytes) -> str:
    if len(raw) < 8 or raw[:4] != b"MUTF" or raw[4] != 1:
        raise ValueError("Invalid MUTF header")
    code = raw[5]
    if code not in CODECS:
        raise ValueError("Unsupported encoding identifier")
    size = int.from_bytes(raw[6:8], "big")
    if size != len(raw) - 8:
        raise ValueError("Payload size mismatch")
    payload = raw[8:]
    codec = CODECS[code]
    signatures = {
        1: b"\xef\xbb\xbf", 2: b"\xfe\xff", 3: b"\xff\xfe",
        4: b"\x00\x00\xfe\xff", 5: b"\xff\xfe\x00\x00",
    }
    if payload.startswith(signatures[code]):
        raise ValueError("MUTF forbids a redundant payload signature")
    return payload.decode(codec, errors="strict")

record = encode_mutf("Aé", 3)
assert record.hex(" ") == "4d 55 54 46 01 03 00 04 41 00 e9 00"
assert decode_mutf(record) == "Aé"
for altered in (record[:-1], record + b"\x00", record[:5] + b"\x09" + record[6:]):
    try:
        decode_mutf(altered)
    except ValueError:
        pass
    else:
        raise AssertionError("Invalid record accepted")
print(record.hex(" "), "=>", decode_mutf(record))

The explicit format header makes signature detection unnecessary. It also illustrates two separate byte orders: the binary length is always big-endian, while the text payload may be UTF-16LE. There is no contradiction because the two fields have independent format contracts.

Streaming and Chunk Boundaries

A streaming decoder must treat a byte chunk as an arbitrary transport unit, not as a Unicode character boundary. A BOM may be split as EF in one read and BB BF in another, or a UTF-16LE signature may be split into FF and FE. UTF-8 multibyte sequences and UTF-16 code units may likewise cross chunk boundaries. The detector must buffer just enough prefix bytes to settle the allowed signature decision, then pass subsequent bytes to an incremental decoder that preserves partial-code-unit state.

A stateful implementation has at least three phases: undecided signature, chosen decoder, and finished. In the first phase it buffers bytes until the declaration or signature can be resolved. In the second it processes bytes incrementally without ever re-running BOM detection at ordinary chunk boundaries. On finishing, it calls the decoder's finalization operation to reject truncated code units or incomplete UTF-8 sequences. Without this finalization step, a truncated file may be accepted silently because the decoder kept unfinished bytes in its buffer.

Concatenation, Appended Files, and Embedded BOMs

Concatenating two text files that each have a BOM can create a stream with an interior U+FEFF at the join. The first signature may be consumed by a BOM-aware reader, but the later bytes decode as a character. This can affect search, CSV field matching, XML text, or any program that assumes there is no hidden format character inside the document. It does not automatically mean the data should be silently cleaned; the original files and concatenation contract should be examined.

For log files, streamed records, and archives, it is usually better to specify the encoding once at the file or container boundary and to avoid per-record BOM prefixes. If records are independently decodable text objects, the framing specification must say whether each record starts a new text stream, in which case a signature might be interpreted at each record boundary. The distinction must be explicit and reflected in tests. An outer file-level BOM never authorizes stripping the same bytes at arbitrary later positions.

The Difference Between Content Validity and Signature Validity

A matching BOM tells the parser only that the prefix is consistent with an encoding signature. It does not guarantee that the remaining payload has a length divisible by two or four, contains correct UTF-16 surrogate pairs, stays within the Unicode scalar range, or conforms to an application schema. For UTF-8, EF BB BF C0 AF begins with a valid UTF-8 signature but is followed by an invalid overlong sequence. For UTF-16LE, FF FE 3D D8 consists of a valid signature and a dangling high surrogate; strict decoding must reject it.

The reverse is also true: a file without any BOM can still be valid UTF-8, UTF-16BE, UTF-16LE, UTF-32BE, or UTF-32LE when the encoding is known from metadata. BOM absence is not Unicode invalidity. Parser validation and transport-level integrity controls are separate concerns. A file checksum may detect accidental byte corruption, but it does not tell the parser whether the byte stream is a conformant Unicode encoding scheme or whether the format allows a BOM.

Security and Trust Boundaries

BOM handling is a boundary between byte-level input and text-level processing, making it relevant to security even though a BOM is not a cryptographic feature. If one system treats an initial U+FEFF as a signature and another treats it as an ordinary character, they may normalize filenames, identifiers, headers, or access-control strings differently. Such inconsistencies can produce validation bypasses, duplicate keys, misrouted records, or signature-check failures. The vulnerability comes from inconsistent interpretation, not from the inherent maliciousness of U+FEFF.

Define and enforce a single policy at the trusted ingestion boundary. Preserve exact original bytes when auditability matters; reject unexpected signatures in formats that forbid them; use strict decoders for external data; apply any character normalization only after successful decoding and according to a documented rule; and test equivalence between authorization, storage, and display systems. The text signature is not evidence of origin, integrity, or authorization; authenticated channels, digital signatures, and independent checksums serve those separate purposes.

Internationalization, Accessibility, and Invisible Characters

A BOM normally has no visible glyph, so its mishandling can be difficult to diagnose in a visual editor. A string that begins with U+FEFF may look identical to one without it while behaving differently during search, copying, filtering, or text-to-speech preprocessing. Screen readers and accessibility technologies rely on the text and application semantics delivered after decoding. A wrongly decoded file can produce unreadable characters, omitted headings, or broken search targets despite superficially intact page structure.

Use inspection interfaces that can reveal code-point sequences and raw byte prefixes. When U+FEFF is intended as content, document why; for a word-joining effect in modern Unicode text, choose U+2060 WORD JOINER where appropriate. Do not use BOMs as an invisible styling or directionality mechanism. Bidirectional text display is governed by Unicode's bidi algorithm and separate formatting controls, not by byte order or the presence of a BOM.

Performance, Storage Overhead, and Operational Tradeoffs

The signature overhead is three bytes for UTF-8, two for UTF-16, and four for UTF-32. In a large text file this is negligible; in millions of tiny independently framed records it can become a measurable fraction of storage or network traffic. But performance is rarely the primary reason to choose an encoding signature. Compatibility with the receiving ecosystem, format conformance, and operational clarity matter more.

For a two-character Aé payload, a UTF-8 signature doubles the size from three to six bytes. For a one-megabyte payload, the same three bytes add approximately 0.0003% overhead. A schema that identifies encoding once in a file header may avoid repeating signatures on each record, while a self-describing plain-text file may intentionally include a signature for compatibility. Optimize after recording the workload and the consumer requirements; do not conflate BOM overhead with UTF-8/UTF-16/UTF-32 code-unit width.

Decision Framework for New Systems

When designing a new data system, first ask what external standard or interchange partner governs the format. If it specifies UTF-8 with no BOM, use that. If it explicitly declares UTF-16LE, write the indicated byte order and follow its rule for initial U+FEFF. If you control a simple private binary format, consider a stable format header with version, encoding identifier, byte count, and unambiguous parsing rather than heuristic text discovery. If the exchange is unlabelled Unicode text, determine whether BOMs are acceptable and which generic decoding scheme applies.

Next, define failure behavior. Will the reader reject mismatched declarations, invalid sequences, truncated units, and unknown encodings? Will it retain an unexpected initial U+FEFF as text, report a diagnostics warning, or reject the file? Finally, write tests across platforms and decoding libraries. Interoperability is proven through explicit conformance and byte-exact cases, not by the fact that one editor displays the text correctly.

Review Questions with Answer Guidance

What exactly does a BOM identify? It is an initial encoding of U+FEFF. For generic UTF-16 or UTF-32, it can identify the byte serialization orientation; for UTF-8 it can only identify the UTF-8 signature, because UTF-8 has no endian alternatives. Its role is controlled by context.

Is a BOM required for valid UTF-8? No. UTF-8 is self-sufficient as a byte-sequence encoding; protocol rules determine whether the optional signature is accepted, discouraged, or prohibited.

What is the Unicode default when UTF-16 or UTF-32 lacks a signature? For the generic Unicode UTF-16 and UTF-32 schemes, big-endian is the default in the absence of a BOM and a higher-level specification. A separately named UTF-16LE or UTF-32LE scheme already fixes little-endian by definition.

Why check UTF-32 signatures before UTF-16? UTF-32LE begins with FF FE, the complete UTF-16LE BOM. The full four-byte pattern FF FE 00 00 is more specific, so shorter matching first can misclassify a UTF-32 stream.

Does detecting a signature prove that the file is otherwise valid? No. Payload validity, file-format framing, declared metadata, and integrity controls must be checked separately.

What happens to a BOM in the middle of text? The bytes ordinarily decode to U+FEFF as character content. It is not another stream-opening signature unless an enclosing format defines a new independently decoded text stream at that boundary.
