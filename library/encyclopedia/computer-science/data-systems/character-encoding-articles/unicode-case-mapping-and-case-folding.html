1. Scope and Central Principle

A character's written form does not, by itself, determine how a computer should capitalize, compare, sort, or search it. Unicode case mapping specifies relationships among uppercase, lowercase, and titlecase representations for characters that have them. Case folding supplies a related, intentionally different transformation for case-insensitive matching. These operations sit above the encoding layer: the same Unicode string can be encoded using UTF-8, UTF-16, or UTF-32, and its casing behavior concerns its characters and their properties rather than any one byte layout.

This article develops the case model from the Unicode Character Database through concrete operations and deployment policy. It distinguishes simple and full mappings; default and language-sensitive behavior; Greek final sigma, Turkic dotted I, German sharp S, and scripts without case; interactions with normalization; and production uses in search, identifiers, databases, and archives. Its subject is neither a universal guide to linguistic capitalization nor an instruction to remove case distinctions from every data field. A person's name, an edition of a historical document, a password, and a search query can require fundamentally different treatment.

The governing technical basis is Unicode 18.0, particularly the default case algorithms in Chapter 3, the implementation discussion in Section 5.18, and the Unicode Character Database (UCD). Individual runtimes may implement older Unicode versions, so the article explicitly separates the standard's algorithm from the version supported by a particular library.

2. Learning Objectives and Operating Questions

After studying this entry, a reader should be able to identify the difference between a code point, cased character, case mapping, case folding, and locale-aware collation; explain why one input character may map to several output characters; identify situations that require Turkish- or Lithuanian-specific handling; make a defensible policy choice for an identifier or search index; and validate the choice against adversarial and multilingual test cases.

A useful decision sequence is: What does the application want to accomplish? Is it changing the text shown to a person, deriving a comparison key, or sorting a list? Which language and locale apply? Must changes be reversible? Which normalization policy is used? Does the runtime's Unicode version match the data or index version? Every one of these questions affects correctness.

3. Vocabulary: What Each Layer Means

Concept Meaning Not the same as

Code point Numeric identifier such as U+0041 A byte, UTF-16 code unit, or display cell
General category UCD classification such as uppercase letter (Lu) or lowercase letter (Ll) A complete definition of whether a character is cased
Cased property Unicode-derived property used by default casing algorithms Whether a glyph visibly resembles a capital letter
Simple mapping One-code-point mapping (or identity) A complete string mapping in every language
Full mapping String mapping that may expand to multiple code points A display-only rendering rule
Case fold Matching-oriented transformation that suppresses defined case distinctions An ordinary lowercase conversion
Collation Locale-dependent comparison and ordering behavior Code-point equality or case folding alone

Unicode character data describes properties. An application builds an operation from those properties, its language context, and its product requirements. Confusing the layers leads to incorrect equality tests and surprising text transformations.

4. The Unicode Case Data Model

The Unicode Character Database provides simple uppercase, lowercase, and titlecase mappings in UnicodeData.txt. SpecialCasing.txt supplies full mappings and rules that require string context or a language condition. CaseFolding.txt supplies the standard case-folding mappings. The definitions of derived properties, including Cased, Case_Ignorable, and changes under specific casing operations, are documented with UCD property data.

A program that merely checks for the Lu category will not implement all case-sensitive rules. A word may contain a letter with a different letter category, combining marks that do not break the relevant casing context, and characters with case mappings not captured by a superficial ASCII-only approach. The Unicode algorithms define how to incorporate these properties correctly. For production libraries, use a maintained Unicode implementation instead of writing a partial table from examples.

5. Uppercase, Lowercase, Titlecase, and Case Folding

These operations share Unicode data but serve different purposes. Uppercasing and lowercasing normally support display transformations, documents, user-facing labels, and text editing. Titlecasing may be applied to word beginnings, subject to complicated rules and locale conventions. Default case folding produces comparison-oriented text that is not necessarily appropriate for display.

Operation Typical question Example outcome Principal caution
Uppercase How should this string appear in capitals? straße → STRASSE in a common default full mapping Can expand one character into two
Lowercase How should it appear in lower case? ΟΣ → ος in Unicode-aware context Can depend on surrounding characters
Titlecase How should word-initial cased letters be represented? hello world → Hello World in a simple English example Real title conventions are language and style dependent
Default case fold Should two values match when case is ignored? Straße and STRASSE → the same folded key Folded output is not a display form
Locale-aware search comparison Are the values equivalent under local search rules? Turkish I and ı may be compared as case variants Requires a declared language and comparison sensitivity

No single operation answers all these questions at once. For example, data-entry normalization of account identifiers and user-facing title capitalization should not silently share the same algorithm.

6. Simple Versus Full Case Mappings

A simple mapping maps one code point to a single code point (or leaves it unchanged). A full mapping may replace one input code point with several code points. This distinction is not an optimization detail: it determines output lengths, the validity of character-by-character algorithms, and whether a fixed-size buffer is adequate.

Input Operation Typical Unicode result Why it matters
a U+0061 Uppercase A U+0041 One-to-one mapping
ß U+00DF Full uppercase SS U+0053 U+0053 One-to-many expansion
İ U+0130 Default full lowercase i U+0069 plus U+0307 Dot-preserving expansion
Σ U+03A3 Contextual lowercase σ or ς Surrounding text affects result
ﬃ U+FB03 Default full case fold ffi Compatibility ligature has a fold mapping

A transformation that assumes the number of code points or bytes never increases is unsafe. Even if the input uses a fixed-width encoding, a casing operation can change its serialized size after re-encoding.

7. String Context Changes Lowercasing

Unicode casing is not always independent for each character. The Greek capital sigma Σ is an important example: default Unicode lowercasing uses the ordinary small sigma σ in many positions but uses final sigma ς when the Final_Sigma context condition applies. That condition depends on neighboring cased and case-ignorable characters, not merely on whether the next byte happens to be a space.

Consider the ordinary uppercase Greek word ΟΣ. Under a Unicode-aware default lowercase operation it becomes ος: the last sigma becomes final sigma. The word ΣΟΣ becomes σος: the initial sigma is nonfinal, the last sigma is final. Case folding, by contrast, maps both σ and ς to the same matching form σ. Implementations should not attempt to reproduce this rule by converting a single code point and then simply checking for a trailing space.

8. Case-Ignorable Characters and Word Boundaries

A combining mark can occur between letters without necessarily ending the context relevant to a casing rule. Similarly, not every punctuation mark behaves identically for the final-sigma condition. Unicode's algorithm relies on character properties designed specifically for casing behavior; it is not identical to word segmentation or visual cursor movement.

This matters for Greek archival text, linguistic material, and text with diacritics. The safest general design is to transform the whole string with a conforming library, and to retain original text for round trips and source fidelity. When streaming, a converter may need to delay a decision until enough following context has arrived.

9. Turkish and Azerbaijani Dotted and Dotless I

The four characters I, i, İ, and ı cannot be handled as if English were the universal language. In Turkish and Azerbaijani, uppercase I pairs with lowercase dotless ı, while lowercase i pairs with uppercase dotted İ. Default Unicode casing is intentionally distinct from this language-tailored behavior.

Input Default lowercase or uppercase Turkish-aware mapping in corresponding direction
I U+0049 Lowercase i U+0069 Lowercase ı U+0131
İ U+0130 Lowercase i + U+0307 Lowercase i U+0069
i U+0069 Uppercase I U+0049 Uppercase İ U+0130
ı U+0131 Uppercase I U+0049 Uppercase I U+0049

For a Turkish person-name directory, locale-aware behavior can be essential. For a locale-independent protocol identifier, an explicitly specified invariant matching rule may be more appropriate. Never choose a transformation solely from the host operating system's current language setting if durable values have to compare consistently across servers and years.

10. Lithuanian Accents and the Dot Above

Lithuanian introduces further language-sensitive behavior involving the dot over lowercase i and j in certain accented forms. Depending on the surrounding combining marks, preserving or removing a dot above can be needed to maintain correct written forms. The Unicode SpecialCasing.txt file contains conditional rules for these cases, alongside the Turkic special casing rules.

This illustrates a broad lesson: a single letter's rendered appearance is not always sufficient to reconstruct the correct mapping. Some operations depend on decomposed combining sequences. A robust internationalization layer should identify the language, normalize according to the adopted processing policy when appropriate, and use a library that implements the relevant rules.

11. German Sharp S, Capital Sharp S, and Expansion

German uses ß (U+00DF), and Unicode also encodes ẞ (U+1E9E). In many default full uppercase operations, ß expands to SS, while full default case folding maps ß to ss. This is a classic demonstration that uppercase and lowercasing are not generally reversible and that a case-insensitive key may have a different code-point count from the original.

An application must not infer from the existence of a capital sharp S that every German editorial convention requires it, nor should it assume ß and ss are interchangeable in every linguistic context. A search system may intentionally treat them as case-equivalent under default folding; legal records and proper names should retain exactly what was supplied.

12. Greek Small Sigma and Caseless Matching

Unicode default case folding unifies ordinary small sigma σ (U+03C3) and final small sigma ς (U+03C2) into σ. Thus Σ, σ, and ς can have the same default folded value even though Greek presentation requires particular word-position choices. This is a reason to retain both original display text and a separately computed comparison key.

A search interface that displays the folded key may incorrectly replace a word-final letter with a nonfinal form. The fold is useful for matching, but its output should not be treated as a faithful copy of the submitted document.

13. Cherokee and Case-Folding Stability

Cherokee illustrates that a Unicode fold is not universally a lowercase transformation. Unicode's case-folding stability policy, together with later additions to the Cherokee repertoire, means the default folded form for Cherokee case pairs may be their uppercase form. Developers who define folding as lower() or lowerInvariant() will fail such cases.

The practical lesson is to follow the normative case-folding data, not an intuition that a case-insensitive key ought to contain only visually lowercase letters. Use a Unicode-aware implementation that knows the version of its data; do not substitute ASCII case conversion or a language-blind one-character mapping.

14. Scripts With No Conventional Uppercase–Lowercase Distinction

Most scripts do not use a capital-versus-small-letter distinction like Latin or Greek. For many Han characters, Arabic letters, and most symbols, default case operations leave the code points unchanged. That does not mean Unicode text comparison is simple for those scripts: normalization, collation, script variation, punctuation, compatibility characters, and language rules may still matter.

Text processing must keep the question narrow. Case folding removes case distinctions as Unicode defines them; it does not transliterate scripts, remove diacritics, resolve visually confusable characters, segment words, or produce a universal human-language equivalence relation.

15. Characters Versus Code Units and Bytes

A Unicode scalar value is not a UTF-8 byte and not necessarily a single UTF-16 code unit. Casing operations consume a string and may change the number of Unicode code points. Consequently the output may differ in UTF-8 byte length and UTF-16 code-unit length from the input. The examples below illustrate that byte accounting belongs after transformation, not before it.

Text Code points UTF-8 bytes UTF-16 code units Note
ß 1 2 1 U+00DF
SS 2 2 2 Full uppercase expansion
İ 1 2 1 U+0130
i + U+0307 2 3 2 Default full lowercase expansion
😀 1 4 2 Casing normally leaves it unchanged

These counts describe specific strings, not a promise that all Unicode casing fits the input's memory allocation. Any fixed-width storage, byte protocol, or database column limit should be verified against transformed output and the actual encoding used for serialization.

16. Titlecase Is Not Simply Uppercase on the First Byte

Unicode provides titlecase mappings distinct from general uppercase mappings. A titlecase character category (Lt) and titlecase transformation rules are relevant to digraphs, word initials, and some scripts. However, publishing conventions for book titles, surnames, prefixes, particles, and acronyms require additional linguistic and editorial decisions. A generic title() function may produce a technically valid Unicode transformation that is still stylistically unsuitable.

For example, a programming function cannot reliably decide whether iPhone, McDonald, de la Cruz, a scientific symbol, or a publication title should be altered merely by finding word boundaries. User-facing names and titles should normally preserve the source spelling. Treat automatic titlecasing as a suggestion or a clearly scoped transformation, not a universal sanitization step.

17. Case Folding: The Matching-Oriented Operation

Default case folding is intended to remove case distinctions according to Unicode's defined mapping data. Unlike lowercasing for presentation, it deliberately does not implement the contextual display rules for Greek final sigma, and its standard default form is not language-tailored. Its output is a useful intermediate key when a product explicitly defines invariant caseless matching.

CaseFolding.txt contains several statuses: common mappings (C), full mappings (F), simple mappings (S), and specially tailored Turkic mappings (T). Full folding can expand one input code point into a string. A runtime that exposes only simple folding cannot be presumed equivalent to a runtime that applies full folding.

Input Default lowercasing Full default case folding
Straße straße strasse
STRASSE strasse strasse
ΟΣ ος οσ
ς ς σ
İ i plus combining dot i plus combining dot
I i i

These results illustrate why a single call to lowercase is not a reliable substitute for case folding.

18. What Case Folding Does Not Guarantee

Case folding is not a universal “same meaning” or “same name” test. It does not guarantee that strings which sound alike, look alike, or are treated as equivalent in one language will fold to identical sequences. Conversely, two distinct source strings may fold to an identical result. Therefore folding is many-to-one, not reversible, and must not be used as the only stored representation of an authoritative name or document.

Case folding also does not define a sorting order. Sorting requires collation, which depends on locale, sensitivity, and versioned comparison data. An invariant fold can be one input to indexing but is not a replacement for locale-sensitive search or display ordering.

19. Default Folding Versus Turkic Folding

Unicode documents special Turkic mappings for case folding. This matters because a Turkish-aware caseless relation should not silently inherit the English-oriented dotted-I relationship. The default mapping of I folds to i; the Turkic-specific form can instead map I to ı. For İ, the Turkic special mapping can fold to plain i, unlike the default full fold that preserves the combining dot.

A database with users from multiple locales needs a policy: it may store language-tagged comparison keys, use locale-aware collation in a query, or specify one invariant identifier policy with known limitations. None of these choices is automatically correct for all human names. Document the decision alongside stored values and index metadata.

20. Normalization and Casing Are Different Operations

Unicode normalization (NFC, NFD, NFKC, NFKD) describes canonical or compatibility equivalence. Case mapping describes upper/lower/title relationships; case folding removes default case distinctions. The two can interact. Two canonically equivalent strings may have different raw code-point sequences but should be compared in a way that respects their equivalence if the application's contract calls for canonical caseless matching.

Pipeline Purpose Important limitation
Byte equality Exact preservation and digital signatures No Unicode equivalence implied
NFC then binary equality Normalize canonically equivalent sequences Still case-sensitive
Full default case fold then binary equality Apply a case-insensitive key May retain normalization differences
Canonical caseless matching Integrate canonical normalization with case folding Must follow the defined Unicode algorithm
Unicode NFKC_Casefold Identifier-oriented compatibility-plus-case processing Not merely an arbitrary sequence of NFKC and casefold() calls
Locale-aware collation Human-language comparison or sorting Results depend on locale, options, and data version

Do not claim that NFKC(casefold(x)), casefold(NFKC(x)), and the specified toNFKC_Casefold algorithm are universally interchangeable. The Unicode standard defines its own identifier-oriented mapping, including treatment of certain default-ignorable code points. Use an implementation of the named algorithm when the protocol requires it.

21. Canonical Caseless Matching

For canonical caseless matching, Unicode defines an algorithm involving canonical decomposition and full default case folding; its representative form can be written as NFD(toCasefold(NFD(X))). This is more specific than “just call lowercase.” It accommodates canonical equivalence and folding behavior such as special treatment required by the Unicode case algorithms.

Applications should take the standard's definition, version, and test data as the contract rather than assuming a convenient composed one-liner is a full conformance implementation. For a simpler, explicitly local comparison policy, the code examples below illustrate normalized full folding; they are not assertions of conformance with every Unicode identifier or caseless-matching profile.

22. Compatibility Caseless Matching and Identifiers

Compatibility characters—such as certain ligatures, width variants, and presentation forms—raise separate questions. The Unicode NFKC_Casefold operation is particularly relevant to identifier processing under a protocol with a specified repertoire, allowed-character policy, and normalization profile. It is not a license to equate all visibly similar glyphs or to strip distinctions from archived documents.

Before using compatibility-based comparison, decide whether compatibility distinctions are meaningful in the domain. In scholarly editions, compatibility normalization can erase intended textual evidence; in a restricted machine identifier, a documented NFKC-based profile can be desirable. Persist the original alongside any derived comparison representation unless a protocol explicitly requires a canonical stored form.

23. Worked Comparison: Four Strings, Four Policies

Consider the inputs Straße, STRASSE, ΟΣ, and ος. Byte equality treats each as its own exact sequence. Default lowercasing changes case but does not necessarily unify the German pair, since straße and strasse differ. Full case folding can unify the German pair; for Greek, case folding maps word-final sigma into the common nonfinal folded form.

Pair Raw code-point equality After simple presentation lowercase After full default fold
Straße / STRASSE No No Yes
ΟΣ / ος No Yes Yes
σ / ς No No Yes
A / a No Yes Yes

The table answers only the stated transformation questions. It does not determine whether such pairs should be treated as identical identities, names, legal entities, or dictionary headwords.

24. A Search Index Needs Both Original and Comparison Fields

An archival-search system may store an original source string and a derived search key. For example, a title field might preserve Straße, while an invariant folded field contains strasse. The query undergoes the same normalization-and-folding policy as the indexed key; the display result still uses the original string.

A robust implementation stores the source, policy identifier, Unicode and collation versions, derived key, and language tag where relevant. Rebuild or version the derived index when changing the case mapping rules; do not silently reinterpret old keys. If the application must support user-specific languages, use documented locale-sensitive search behavior instead of pretending one invariant key serves every locale.

25. Python: Full Default Folding and Exact Diagnostics

Python's str.casefold() is intended for aggressive, default Unicode-style case-insensitive matching; lower() is a different operation. Python also exposes Unicode normalization through unicodedata. The runtime's unicodedata.unidata_version should be recorded when test results or indexes need reproducibility.

import unicodedata as ud

samples = ["Straße", "STRASSE", "ΟΣ", "ος", "İ", "I", "ı", "ﬃ"]
for original in samples:
    folded = original.casefold()
    print(f"{original!r:12} lower={original.lower()!r:10} fold={folded!r}")

assert "Straße".casefold() == "STRASSE".casefold()
assert "ΟΣ".casefold() == "ος".casefold()
assert "σ".casefold() == "ς".casefold()
assert "Straße".lower() != "STRASSE".lower()
assert "İ".casefold() == "i\u0307"
print("Unicode data version:", ud.unidata_version)

This demonstration is about observable runtime behavior. The actual Unicode version printed by a particular Python interpreter can differ from Unicode 18.0; its output must not be described as a Unicode 18.0 conformance test unless the runtime supplies matching data.

26. Python: Documented Comparison Keys

The following function is an illustrative NFC plus full default case-fold key, not a replacement for a formally specified Unicode identifier profile. It preserves the original data separately and makes its policy explicit. The test also shows why normalization changes equality for canonically equivalent strings.

import unicodedata as ud

POLICY = "NFC-THEN-FULL-CASEFOLD-THEN-NFC/v1"

def search_key(text: str) -> str:
    if not isinstance(text, str):
        raise TypeError("Expected Unicode text")
    return ud.normalize("NFC", ud.normalize("NFC", text).casefold())

records = ["Café", "Cafe\u0301", "Straße", "STRASSE"]
for original in records:
    print({"display": original, "key": search_key(original), "policy": POLICY})

assert search_key("Café") == search_key("Cafe\u0301")
assert search_key("Straße") == search_key("STRASSE")
assert "Café" != "Cafe\u0301"

If the contract instead requires canonical caseless matching as formally defined by Unicode, use its specified algorithm and conformance data. Likewise, use locale-tailored comparison for Turkish or other language-sensitive requirements.

27. JavaScript: Locale-Sensitive Casing Is Not Full Case Folding

JavaScript supports toUpperCase(), toLowerCase(), and locale-aware casing methods; it does not expose a built-in Unicode full default case-fold method with the same contract as Python str.casefold(). A toLowerCase() comparison is therefore not a standards-equivalent replacement for full folding. For language-sensitive user search and sorting, Intl.Collator supplies a distinct, locale-aware comparison interface.

const words = ["Straße", "STRASSE", "ΟΣ", "ος", "İ", "I"];
for (const value of words) {
  console.log(JSON.stringify(value), "lower:", value.toLowerCase());
}
console.log("Turkish I:", "I".toLocaleLowerCase("tr"));
console.log("Default I:", "I".toLowerCase());
console.log("Turkish dotted i:", "i".toLocaleUpperCase("tr"));

console.assert("I".toLocaleLowerCase("tr") === "ı");
console.assert("i".toLocaleUpperCase("tr") === "İ");
console.assert("Straße".toLowerCase() !== "STRASSE".toLowerCase());

The tested locale examples illustrate how a runtime implements locale casing. They do not imply that every JavaScript engine supports the same full Unicode version or uses identical locale-data revisions.

28. JavaScript: A Comparison API for Search

For a UI that is searching human-language strings, use a locale-aware comparison policy instead of manufacturing an ad hoc global lowercase key. Intl.Collator has usage: "search" and sensitivity options; sensitivity: "accent" ignores case distinctions while retaining certain accent distinctions under the chosen locale's collation rules.

const tr = new Intl.Collator("tr", { usage: "search", sensitivity: "accent" });
const en = new Intl.Collator("en", { usage: "search", sensitivity: "accent" });
console.log("Turkish I/ı:", tr.compare("I", "ı"));
console.log("English I/ı:", en.compare("I", "ı"));
console.log("Turkish i/İ:", tr.compare("i", "İ"));
console.log("English cafe/café:", en.compare("cafe", "café"));

console.assert(tr.compare("I", "ı") === 0);
console.assert(tr.compare("i", "İ") === 0);

The exact collation relationships depend on locale, comparison strength, runtime, and underlying ICU/CLDR data. Collation equality must not be conflated with character-for-character identity.

29. Windows PowerShell 5.1 and .NET Boundaries

Windows PowerShell 5.1 uses the Windows/.NET Framework text stack rather than Python's Unicode casing APIs. For culturally tailored display conversion, code can request a specific CultureInfo. For case-insensitive comparisons, use a deliberate .NET comparison method with its own documented semantics. Neither ToLowerInvariant() nor a culture-aware ToLower() should be described as a complete Unicode case-fold algorithm.

$culture = [System.Globalization.CultureInfo]::GetCultureInfo('tr-TR')
$example = 'I'
Write-Output ('Original: ' + $example)
Write-Output ('Invariant lower: ' + $example.ToLowerInvariant())
Write-Output ('Turkish lower: ' + $example.ToLower($culture))

# Never rely on a text conversion to define a cryptographic identity.
$source = 'Straße'
Write-Output ('Source preserved: ' + $source)
Write-Output ('Invariant lowercase only: ' + $source.ToLowerInvariant())

Test the exact Windows/.NET release and culture-data behavior before deploying multilingual identity matching. This code is illustrative and is not presented as an execution-tested PowerShell conformance suite.

30. String Lengths, Allocations, and Buffer Safety

An application that modifies text must account for one-to-many expansions and differences between code points, UTF-16 code units, grapheme clusters, and UTF-8 bytes. The expansion ß → SS increases the number of Unicode scalar values without increasing the number of UTF-8 bytes in that particular example. The lowercase expansion İ → i plus combining dot increases its UTF-8 byte count. Other examples may change both counts differently.

Never allocate a destination buffer based on “one output code point per input character.” Prefer library calls that return the required output length or grow managed buffers safely. Apply byte limits after the chosen encoding step, and report overflow or truncation explicitly rather than silently discarding trailing combining characters.

31. Case Mapping and Stream Processing

Some casing rules use following context. A stream processor that lowercases partial chunks independently can produce results different from transforming the entire string. Greek final sigma is one reason a transformation may need lookahead or deferred output. This differs from UTF-8 decoding, which has its own partial-byte handling, and from Unicode normalization, which may also need boundary-aware processing.

Stage May need context? Failure when chunks are processed blindly
UTF-8 decode Yes, partial code-point bytes Malformed replacement or dropped bytes
Unicode normalization Yes, combining sequences Changed canonical ordering or composition
Lowercase mapping Yes, case and language context Wrong sigma or dotted-I behavior
Default case folding Defined per mapping, can expand Incorrect use of simple rather than full folding
Grapheme segmentation Yes, extended clusters Split a user-perceived character

Use streaming-capable implementations or buffer sufficient context; do not invent a fixed per-code-point transformation when the required operation is context-sensitive.

32. Case Mapping, Collation, and Sort Order

Sorting names is not the same as folding them. A folded key often supports exact matching under a chosen policy but may destroy distinctions used by the sorting conventions of a language. Unicode collation (UTS #10) and implementations such as ICU expose language-tailored sort and search behavior, levels of comparison sensitivity, and versioned collating data.

For a multilingual catalog, store original names for display, normalized index keys for exact operations where justified, and locale-aware collation keys for sorting if needed. Avoid assuming UTF-8 byte order, Unicode scalar order, or Python default string order equals human dictionary order. It often does not.

33. Database Equality, Uniqueness, and Index Stability

A database can have binary collations, case-insensitive collations, accent-insensitive collations, or combinations depending on its engine and configuration. The word case-insensitive alone is not a portable contract: database engines can use different Unicode and locale tables, may treat expansions differently, and may change behavior after upgrades.

Requirement Appropriate design question Mistake to avoid
Exact source integrity Must stored bytes be preserved exactly? Replacing source with folded value
Search within one language Which locale and sensitivity? Assuming English default casing
Case-insensitive unique key What formal equivalence and version? Relying on unspecified server collation
Cross-system synchronization Do both systems compute the same keys? Assuming .NET lower equals Python fold
Long-term archive Can historic key derivation be reproduced? Overwriting keys without migration

A uniqueness policy should be explicit about canonical normalization, full versus simple fold, and locale handling. For critical identifiers, consider a restricted character repertoire and a published normalization profile rather than unconstrained human-text equality.

34. Search, Tokenization, and Retrieval

Search pipelines combine tokenization, normalization, case handling, stemming, and ranking. Case folding may improve retrieval coverage; it may also collapse meaningful distinctions. It should be an intentional index configuration, with the original field retained. Case-insensitive matching is not equivalent to stop-word removal, accent folding, transliteration, or semantic similarity.

For example, a search for STRASSE might match a document displaying Straße under an invariant full fold. A multilingual archive might additionally need locale-specific analyzers for Turkish. The quality of a text-retrieval pipeline must be evaluated with representative language test sets, not just ASCII example queries.

35. Identifiers, Handles, and Security-Sensitive Strings

Never normalize or case-fold passwords as a universal rule: password verification must use the exact input transformation defined by the authentication system, and unexpected preprocessing can change the accepted secret. Similarly, a username, resource path, account handle, or authorization principal should follow a deliberate protocol-defined comparison and repertoire restriction.

A folded identifier can collide with another distinct source string. If the system disallows such collisions, it must enforce its uniqueness rule consistently and explain the policy at enrollment. If visually confusing but case-distinct strings are a concern, additional checks may be needed under the Unicode security and identifier specifications. Case folding alone does not solve confusable characters or mixed-script spoofing.

36. Case Folding Is Not Confusable Detection

Unicode security work differentiates case mapping from detection of confusables, mixed scripts, and other display-level issues. Latin a and Cyrillic а look alike in many fonts but are different code points and are not made identical by ordinary case folding. Compatibility forms can introduce other apparent similarities that do not imply a secure equivalence relation.

A high-integrity system should validate permitted scripts or profiles, normalize and compare under its specified policy, flag or review confusable identifiers where appropriate, and display the true source identifier in a way users can inspect. For legal and institutional records, preserving original text and an audit trail is essential.

37. A Production Case-Policy Contract

Specify a case-handling contract in writing before creating durable keys. At minimum define: input repertoire, language/locale, normalization, case transformation, Unicode/ICU/CLDR version, comparison mode, collision rule, original-data retention, migration plan, and test corpus. Give the policy a stable identifier so downstream services know which transformation produced a key.

A practical design is to keep display_value untouched and derive comparison_key under a named policy. In a regulated archive, the original may need to remain byte-for-byte intact, while the key can be rebuilt as standards evolve. Where locale rules differ, a single global comparison key may be inappropriate; use locale-specific indexes or an explicitly invariant protocol restriction instead.

38. Migration When Mapping Data Changes

Unicode's case-folding stability guarantees are substantial but do not eliminate the need to version a deployed stack and its implementation behavior. Application upgrades can also change normalization libraries, collation data, locale versions, programming languages, and database indexing rules. A migration should inventory affected fields, compute candidate keys with the new policy, detect newly colliding records, and resolve conflicts before enforcing uniqueness.

Do not rewrite original names to fit the new key. Stage the new derived field beside the old, measure queries and key collisions, run application-specific regression tests, and switch consumers together. Keep rollback information and document exactly which Unicode or runtime version supplied each behavior.

39. Test Cases That Actually Catch Errors

The minimum test set should cover ASCII, one-to-many expansions, locale tailoring, context-dependent casing, normalization, supplementary characters, noncased scripts, and untrusted strings. Test both resulting text and lengths in code points, UTF-8 bytes, and UTF-16 code units if these quantities matter to the application.

40. Performance, Caching, and Observability

Case mapping itself is often inexpensive compared with network or database operations, but full transformations can allocate new strings, expand sequences, and interact with expensive collation. Cache transformed keys only when the input, policy, locale, and version are known. In distributed systems, ensure all participating services compute matching keys; otherwise data routed through different nodes may violate uniqueness or produce inconsistent search results.

Log policy identifiers and failure categories rather than indiscriminately recording sensitive source strings. Measure collisions, fallback behavior, failed transformations, indexing lag, and disagreement between services. A reproducible test corpus is a more valuable assurance asset than an undocumented claim that the system is “Unicode-aware.”

41. Practical Investigation: Four Distinct Workflows

Workflow A—Display. Preserve a person's supplied name. When a user explicitly requests uppercasing, use a locale-appropriate string operation and review culturally significant spellings.

Workflow B—Document search. Keep source text, derive an index key using a specified normalization and fold policy, and test multilingual relevance. Display the original source, not the folded key.

Workflow C—Machine identifier. Define a character profile and a stable, documented equivalence algorithm, enforce collisions at creation, and treat later profile changes as migrations.

Workflow D—Legal or archival record. Preserve exact source text and, where required, exact original bytes. Derive searchable fields separately. Never alter the evidentiary record merely to make comparisons more convenient.

These workflows illustrate that the correct answer to “Should we case-fold?” depends on the object being processed and the promises the system must keep.

47. Editorial Scope and Closing Principle

This is Character Encoding specialist article 13 of 20, studying mapping of Unicode case and the distinct transformation used for caseless matching. It builds on the existing Unicode normalization specialist and supports later units on collation and text-input security. The intended physical file is data-systems/character-encoding-articles/unicode-case-mapping-and-case-folding.html; its public canonical URL omits .html.

The editorial rule is simple but consequential: preserve source text, define a comparison policy, and choose the operation for the job. Uppercase and lowercase transformations serve readable text; case folding serves an expressly defined equality relation; collation serves language-aware ordering. Treating them as interchangeable leads to incorrect names, broken search indexes, lost evidence, and inconsistent identities. A disciplined implementation retains originals, uses versioned Unicode algorithms, and tests beyond ASCII.
