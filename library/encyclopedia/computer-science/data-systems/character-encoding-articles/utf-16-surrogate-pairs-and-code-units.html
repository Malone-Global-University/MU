Definition, Purpose, and Scope

UTF-16 (Unicode Transformation Format—16-bit) is a Unicode encoding form that represents each Unicode scalar value using either one 16-bit code unit or a pair of 16-bit code units called a surrogate pair. Its defining boundary is not the number of bytes in a file but the relationship between code points and code units: scalar values in the Basic Multilingual Plane (BMP), other than the excluded surrogate range, use one unit, whereas scalar values from U+10000 through U+10FFFF use two. The encoding form itself operates on 16-bit values; the related UTF-16BE and UTF-16LE encoding schemes specify how those values become bytes.

A correct implementation must never count every 16-bit code unit as a separate Unicode character. Nor may it treat an isolated high or low surrogate as an independent Unicode scalar value. These distinctions matter in string length, indexing, cursor motion, database fields, APIs, network messages, sorting, text editing, validation, and file preservation. A technically valid pair of surrogate code units encodes exactly one supplementary scalar value, but a user-perceived character can comprise several scalar values even after the UTF-16 code units have been decoded.

This is the eighth Level 5 specialist article under the MGU Encyclopedia's Character Encoding unit. It extends the preceding articles on Unicode code points and UTF-8 validity, while avoiding redundant treatment of the entire Unicode codespace, comprehensive grapheme-segmentation algorithms, or detailed UTF-32 architecture. Its governing reference is the Unicode Standard, Version 18.0, particularly Chapters 2, 3, and 5; implementation examples also draw on the ECMAScript and .NET documentation. The encoding rules are standards-defined; programming language APIs can expose different error policies and string abstractions.

Learning Objectives and Principal Questions

After studying this entry, readers should be able to convert a scalar value above U+FFFF into a surrogate pair and reverse the process; identify the ranges of leading and trailing surrogates; distinguish code units, scalar values, bytes, and grapheme clusters; recognize an ill-formed sequence; compute UTF-16LE and UTF-16BE byte streams; interpret byte-order marks; and predict what happens when a string is indexed or sliced through a pair.

The practical objectives are to write bounded decoders and validators, preserve the difference between strict and replacement decoding, use Python, JavaScript, and Windows PowerShell 5.1 APIs knowingly, and design cross-system interfaces that specify both byte order and behavior on malformed data. This article answers four operational questions: Which 16-bit patterns represent a scalar? Which patterns are malformed? How does a program count or edit supplementary text? What contract is necessary to preserve text as it crosses byte-oriented boundaries?

Readers should also be able to recognize misleading claims: UTF-16 is not universally fixed-width per Unicode scalar, an unpaired surrogate is not a valid scalar value, a byte-order mark is not an automatic substitute for metadata in every protocol, and validation of an encoding form does not decide whether a string is visually safe or linguistically meaningful.

Historical Development: From Sixteen-Bit Codes to Variable-Length UTF-16

Early Unicode and ISO/IEC 10646 implementations often treated a character as a 16-bit value. A space of 65,536 positions appeared sufficient for many widely used writing systems, and operating systems and programming environments developed interfaces around 16-bit text elements. The eventual need for more code points required a way to preserve much of that infrastructure while representing characters outside the BMP. Surrogate pairs supply that extension without reassigning the existing non-surrogate BMP positions.

The reserved interval U+D800–U+DFFF was set aside for the encoding mechanism. It is not a normal set of independent letters, symbols, or control characters. Its values are organized as 1,024 leading surrogates and 1,024 trailing surrogates. Their combinations represent 1,048,576 supplementary scalar values, exactly the range from U+10000 to U+10FFFF. The fact that a code-unit sequence can represent more than 65,536 scalar values does not make all single 16-bit values valid scalar values.

Legacy descriptions of UCS-2 should not be treated as interchangeable with UTF-16. UCS-2 uses a single 16-bit value per BMP code point and has no surrogate-pair representation for supplementary code points. Modern software may still use a 16-bit storage unit or describe an API as “Unicode,” but one must establish whether the API actually recognizes pairs, permits isolated surrogates, or merely stores 16-bit numbers.

Four Different Units of Text Measurement

A byte is eight bits. A UTF-16 code unit is sixteen bits and ordinarily occupies two bytes when serialized. A Unicode scalar value is a code point outside the surrogate interval. An extended grapheme cluster is a unit of user-perceived text identified approximately by Unicode text-segmentation rules. These units are not interchangeable.

Unit What it measures Example for A😀é
Bytes in UTF-16LE without BOM Serialized octets 8 bytes
UTF-16 code units Sixteen-bit units 4 units (0041 D83D DE00 00E9)
Unicode scalar values Decoded scalar values 3 (U+0041, U+1F600, U+00E9)
Extended grapheme clusters User-oriented text units Typically 3
Display width in cells or pixels Renderer-specific output Not fixed by UTF-16

A string such as e followed by U+0301 COMBINING ACUTE ACCENT contains two scalars and two UTF-16 code units but normally one extended grapheme cluster. Conversely, an isolated surrogate stored in a JavaScript string is a 16-bit code unit without being a valid Unicode scalar. In all cases, the correct length depends on which layer the application intends to count.

Code-Unit Ranges and Their Meanings

UTF-16 separates ordinary single-unit scalar encodings from reserved surrogate values. The basic classification is stable across Unicode versions.

Range of 16-bit values Classification As a standalone UTF-16 unit
0000–D7FF Direct BMP scalar encoding Well formed
D800–DBFF High / leading surrogate Requires an immediately following low surrogate
DC00–DFFF Low / trailing surrogate Invalid without an immediately preceding high surrogate
E000–FFFF Direct BMP scalar encoding Well formed

There are 55,296 code-unit values from 0000 to D7FF, 1,024 high surrogates, 1,024 low surrogates, and 8,192 values from E000 to FFFF. Therefore 63,488 single-unit values represent BMP scalar values, and the other 2,048 values are reserved for pairing. The noncharacter values U+FFFE and U+FFFF are still scalar values and can be encoded as one code unit; they have special Unicode properties and application implications but are not surrogate code points.

Basic Multilingual Plane and Supplementary Planes

The BMP is Plane 0, with positions from U+0000 to U+FFFF. Unicode's remaining planes run from Plane 1 through Plane 16, terminating at U+10FFFF. Every scalar from the supplementary planes uses two UTF-16 code units, whether or not its code point is currently assigned to a graphical character. UTF-16 does not make supplementary characters invalid or optional merely because they need a pair.

Scalar interval UTF-16 units Representative example
U+0000–U+D7FF 1 U+0041 LATIN CAPITAL LETTER A → 0041
U+D800–U+DFFF Not scalar values No legal standalone encoding
U+E000–U+FFFF 1 U+20AC EURO SIGN → 20AC
U+10000–U+10FFFF 2 U+1F600 GRINNING FACE → D83D DE00

Supplementary means outside Plane 0, not specifically “emoji.” It includes historical scripts, musical symbols, mathematical symbols, and many other coded subjects. It is equally mistaken to assume that every emoji is supplementary: some symbols with emoji presentation originate in the BMP, and some displayed emoji sequences combine multiple scalar values and control characters.

High Surrogates, Low Surrogates, and Ordering

The high surrogate (also called leading surrogate) occupies D800–DBFF; the low surrogate (trailing surrogate) occupies DC00–DFFF. A well-formed supplementary encoding must have a high surrogate followed immediately by a low surrogate. Reversing them is invalid. There is no rule allowing intervening ASCII, whitespace, a second high surrogate, or a missing low surrogate.

An isolated D83D is not a valid Unicode scalar. A two-unit sequence DE00 D83D is not a valid way to encode U+1F600, because the order is wrong. A three-unit sequence D83D 0041 DE00 is malformed even though the first and last units could each participate in a legitimate pair with a different adjacent partner. Validation is inherently sequential.

The name “surrogate pair” describes two code units that jointly encode one scalar. It should not be confused with two Unicode scalar values, two graphemes, a glyph ligature, or a pair of bytes. One surrogate pair consumes four serialized bytes; the pair is a single scalar in Unicode interpretation.

Exact Forward Encoding Formula

For a supplementary scalar U in U+10000–U+10FFFF, UTF-16 computes a 20-bit offset X = U - 0x10000. This offset lies between 0x00000 and 0xFFFFF inclusive. The upper ten bits of X select the high surrogate, and the lower ten bits select the low surrogate:

X = U - 0x10000
high = 0xD800 + (X >> 10)
low  = 0xDC00 + (X & 0x3FF)

Bit shifting is equivalent to division by 1,024 with integer truncation, while masking by 0x3FF extracts the remainder modulo 1,024. A safe encoder checks 0x10000 <= U <= 0x10FFFF before applying these formulas. Values below U+10000 use the direct one-unit mapping, provided they are not surrogates. Values above U+10FFFF are outside the Unicode codespace and must not be encoded into UTF-16.

The result is unique. Two well-formed surrogate pairs cannot encode the same supplementary scalar, and a supplementary scalar cannot be encoded as one 16-bit unit. This is part of the determinism that allows an implementation to decode UTF-16 reliably from a known code-unit boundary.

Worked Encoding: U+1F600 GRINNING FACE

The scalar U+1F600 provides a frequently encountered, easily checked example. Start with U = 0x1F600, then subtract 0x10000: X = 0xF600. Divide that offset into high and low ten-bit portions: 0xF600 >> 10 = 0x3D and 0xF600 & 0x3FF = 0x200. Adding the surrogate bases produces 0xD83D and 0xDE00.

Input scalar:      U+1F600
Subtract 0x10000: 0x0F600
Upper ten bits:   0x03D  -> high surrogate D800 + 003D = D83D
Lower ten bits:   0x200  -> low surrogate  DC00 + 0200 = DE00
UTF-16 units:     D83D DE00
UTF-16BE bytes:   D8 3D DE 00
UTF-16LE bytes:   3D D8 00 DE

Both byte streams represent the same code-unit sequence. Without a declared byte order, however, four bytes cannot always be interpreted correctly. In particular, D83D is a 16-bit code unit, not the byte sequence D8 3D in every environment. Confusing logical code units with serialized bytes is a recurring source of damaged text and failed interoperability.

Boundary Calculations: First and Last Supplementary Scalars

At the first supplementary scalar U+10000, the offset is zero and the pair is D800 DC00. At the maximum scalar U+10FFFF, the offset is FFFFF, and the pair becomes DBFF DFFF. These are important test vectors because they cover the exact legal edges of the surrogate-pair space.

Scalar High surrogate Low surrogate UTF-16LE bytes
U+10000 D800 DC00 00 D8 00 DC
U+10001 D800 DC01 00 D8 01 DC
U+1F600 D83D DE00 3D D8 00 DE
U+10FFFF DBFF DFFF FF DB FF DF

The entire surrogate-pair grid has 1024 × 1024 = 1,048,576 valid combinations. The uppermost values of the high-surrogate range do not mean private-use or invalid scalar values by themselves; the complete pair determines the represented supplementary code point. The older classification of private-use high surrogates concerns the paired supplementary private-use planes, not permission to encode unpaired surrogates.

Reverse Decoding Formula

A decoder takes a valid high unit H and its immediately following low unit L and reconstructs the scalar:

U = 0x10000 + ((H - 0xD800) << 10) + (L - 0xDC00)

For H = D83D and L = DE00, the high contribution is 0x3D << 10 = 0xF400, the low contribution is 0x200, and adding the baseline 0x10000 yields 0x1F600. Decoding must first confirm the high and low ranges. Applying the arithmetic to arbitrary 16-bit numbers can yield plausible-looking values while concealing a malformed input sequence.

When a unit is neither a surrogate nor outside the sixteen-bit range, it decodes directly to the correspondingly numbered scalar. When a high surrogate is encountered, the decoder must examine the next unit before consuming a complete scalar. When a low surrogate appears without a preceding high surrogate, the sequence is malformed and the caller's error policy determines the outcome.

Well-Formed UTF-16 Code-Unit Sequences

A well-formed UTF-16 code-unit sequence is composed exclusively of legal one-unit BMP scalar encodings and legal adjacent high–low surrogate pairs. No leading surrogate may remain without its trailing partner, and no trailing surrogate may occur on its own. Empty sequences are well formed. A string's well-formedness is a property of its entire sequence and cannot be established merely by verifying that every member is a sixteen-bit integer.

An informal grammar makes the rule visible:

BMP_SCALAR  := 0000..D7FF | E000..FFFF
PAIR        := HIGH LOW
HIGH        := D800..DBFF
LOW         := DC00..DFFF
WELL_FORMED := (BMP_SCALAR | PAIR)*

Because a high surrogate always demands its immediate low partner, a streaming decoder can maintain a state such as “waiting for low surrogate.” At the end of a completed input, that pending state is an error. At the end of an arbitrary network chunk, it can be a normal incomplete state awaiting subsequent input; only a final flush should decide that no partner will arrive.

Malformed Sequences and Error Categories

Different malformed patterns require careful classification. A solitary low surrogate, an unpaired high surrogate at end of input, a high surrogate followed by a BMP value, and a high surrogate followed by another high surrogate are all ill-formed. Text APIs that store raw 16-bit units can nevertheless contain such sequences; their existence in memory does not make them legal UTF-16 encodings of Unicode scalar values.

Code units (hex) Status Interpretation
0041 Valid U+0041
D83D DE00 Valid U+1F600
D83D Invalid when input is final Unpaired high surrogate
DE00 Invalid Stray low surrogate
DE00 D83D Invalid Surrogates in reverse order
D83D 0041 Invalid High not followed by low
D83D D83D DE00 Invalid overall First high surrogate has no low partner
D800 DC00 Valid First supplementary scalar U+10000

One danger is treating a replacement character as proof the original text was valid. A permissive decoder may output U+FFFD for malformed input; a strict decoder should report failure and, where practical, its offset. Both are meaningful interfaces, but they satisfy different requirements.

Error Policies: Strict Failure, Replacement, and Preservation

Strict decoding rejects malformed sequences. Use it when validating documents, database identifiers, security-sensitive input, signed records, irreversible transformations, or any system that requires byte-accurate evidence. Replacement decoding substitutes U+FFFD or another documented fallback and permits display or continued processing; once replacement occurs, the original raw units cannot generally be reconstructed from the resulting string alone. Evidence preservation retains the original bytes or code units separately and records how the conversion interpreted them.

A strict policy does not require treating every unassigned Unicode code point or every Unicode noncharacter as malformed. Encoding well-formedness concerns the surrogate structure and valid scalar range; character assignment and application suitability are distinct policies. Likewise, code-point normalization and grapheme segmentation do not repair an ill-formed pair by magic. They operate at different conceptual stages.

For production ingestion, record the declared encoding, decoder, fallback setting, byte order, source identity, and any error offsets. If a malformed input is expected from a legacy system, document the recovery policy and provide a reversible original-data path rather than overwriting source evidence with guessed replacements.

UTF-16 Encoding Form Versus Byte Serialization

At the level of UTF-16 encoding form, values such as 0041 D83D DE00 are 16-bit code units, not yet bytes. To store or transmit them, a UTF-16 encoding scheme serializes each code unit as two bytes. The big-endian variant writes the most significant byte first; the little-endian variant writes the least significant byte first. Thus 0041 becomes 00 41 in UTF-16BE and 41 00 in UTF-16LE.

UTF-16 units UTF-16BE without BOM UTF-16LE without BOM
0041 00 41 41 00
20AC 20 AC AC 20
D83D DE00 D8 3D DE 00 3D D8 00 DE
0041 D83D DE00 00E9 00 41 D8 3D DE 00 00 E9 41 00 3D D8 00 DE E9 00

For each variant, the high surrogate remains logically first and the low surrogate logically second. Byte order reverses the two bytes within each 16-bit code unit; it does not reverse the order of the code units in the string. Reversing the entire four-byte sequence of a surrogate pair would change the code-unit ordering and corrupt the text.

Byte-Order Marks and U+FEFF

The character U+FEFF ZERO WIDTH NO-BREAK SPACE, used at the start of a serialized stream as a byte-order mark (BOM), helps identify UTF-16 byte order. A UTF-16BE BOM is FE FF; a UTF-16LE BOM is FF FE. The signature's function depends on its position and the protocol that carries the data. A BOM is not an intrinsic part of every UTF-16 string and should not be casually inserted into application values.

Leading bytes Typical interpretation
FE FF 00 41 BOM for UTF-16BE, then A
FF FE 41 00 BOM for UTF-16LE, then A
00 41 A if externally declared UTF-16BE
41 00 A if externally declared UTF-16LE

A BOM can establish byte order for generic UTF-16 data; an explicitly labeled UTF-16LE or UTF-16BE stream already has a byte-order contract, and protocols may specify whether a BOM is permitted, required, or stripped. If a byte-order signature appears in the wrong position, some systems treat U+FEFF as ordinary content. Do not silently strip arbitrary later occurrences, and do not infer byte order from the prevalence of zero bytes unless operating in a clearly documented recovery workflow.

Endianness, Byte Swapping, and Record Headers

An integer encoded in a two-byte field and a UTF-16 code unit both occupy sixteen bits, but their byte order must be defined by their respective data-format contracts. A record may specify its length field in network byte order and its text payload in UTF-16LE; there is no rule forcing every multibyte field to share the same endianness. A parser that sees FF FE at the beginning of a payload must decide whether those bytes are a UTF-16 signature or two ordinary bytes in a different field.

When porting a binary file between little-endian and big-endian systems, one can convert UTF-16LE to UTF-16BE by swapping each code unit's two bytes, provided the input is aligned to 16-bit boundaries and all structural boundaries are known. Blindly reversing the whole buffer, or byte-swapping arbitrary nontext metadata together with a string, is unsafe. It can reorder records, change length prefixes, or destroy fields not encoded as text.

Treat the byte order as metadata in a documented schema. Confirm how length fields are counted: in bytes, code units, scalar values, or a fixed-width field. A text length of four UTF-16 units means eight bytes before any BOM, padding, or framing, whereas four characters may occupy more or fewer units depending on the chosen definition of character.

Code Units, In-Memory Strings, and Platform Interfaces

Many Windows and .NET APIs expose a sequence of 16-bit character values. JavaScript strings are specified in terms of UTF-16 code-unit sequences; Java char values are 16-bit UTF-16 code units as well. These platforms can therefore represent a supplementary scalar as two elements at the code-unit level. The underlying implementation may optimize storage internally, but the public API's indexing and length semantics remain the relevant contract for application code.

Python's str ordinarily presents Unicode code points as abstract sequence elements, so a normal len('😀') is one, whereas a JavaScript string's .length for the same value is two. Python str can nevertheless hold an isolated surrogate if constructed artificially, and some operations on that string will fail during strict encoding. A JavaScript string can hold an isolated high or low surrogate; a method operating on code points may not prevent that storage condition from occurring in the first place.

The term character in a library API may refer to a code unit, scalar value, or user-visible grapheme. Developers must inspect each API's documented contract. Counting by code units can be appropriate for indexing a UTF-16 buffer; counting by grapheme clusters is often more appropriate for cursor movement and display-oriented editing. The same code should not assume one count serves both purposes.

The A😀é Byte and Unit Walkthrough

Consider the string A😀é, represented as three Unicode scalars: U+0041, U+1F600, and U+00E9. Its UTF-16 code units are 0041 D83D DE00 00E9. As a BOM-free UTF-16LE byte stream the content is 41 00 3D D8 00 DE E9 00; with a UTF-16LE BOM, the stream is FF FE 41 00 3D D8 00 DE E9 00.

Scalar values: U+0041    U+1F600        U+00E9
Code units:    0041      D83D DE00      00E9
UTF-16LE:      41 00     3D D8 00 DE    E9 00
Unit count:    1         2              1
Byte count:    2         4              2
Totals:        3 scalar values, 4 code units, 8 bytes without BOM

A system that allocates three two-byte slots because it counted three scalars would under-allocate by two bytes in this example. Another system that truncates the first two code units would retain 0041 D83D, leaving a high surrogate with no matching low partner. An accurate record specification uses a precise size unit and validates well-formedness before storing or displaying the resulting text.

Indexing, Slicing, and the Risk of Splitting a Pair

Because JavaScript indexes strings by UTF-16 code units, s[1] for s = 'A😀é' obtains the high-surrogate unit as a one-unit string; s[2] obtains the low-surrogate unit. Neither by itself represents the smiling face scalar. Similarly, slicing the string between the units can create two ill-formed UTF-16 sequences, even though the original string was well formed.

Code-point iteration, such as JavaScript for...of or Array.from on a well-formed string, advances through surrogate pairs together. It does not automatically segment extended grapheme clusters. An emoji modifier sequence or a family emoji joined by U+200D ZERO WIDTH JOINER can contain multiple scalars even though a user sees a single pictographic cluster.

Applications should not blindly truncate by code-unit count, especially near supplementary characters. Truncation policies must state whether the purpose is limiting storage bytes, Unicode scalars, extended grapheme clusters, or displayed width. If the purpose is storage, ensure adequate capacity and reject malformed results; if the purpose is UI presentation, use Unicode grapheme segmentation and platform text-layout facilities.

JavaScript Example: Code Units, Code Points, and Pair Validation

The following example is intended for a current JavaScript environment and demonstrates the difference between .length, .charCodeAt, .codePointAt, and for...of. It explicitly shows an isolated surrogate and avoids treating string slicing as scalar-safe.

const text = "A\u{1F600}\u00E9";
console.log(text.length);                      // 4 UTF-16 code units
console.log(text.charCodeAt(1).toString(16));   // d83d
console.log(text.charCodeAt(2).toString(16));   // de00
console.log(text.codePointAt(1).toString(16));  // 1f600
console.log([...text].length);                 // 3 code-point iterations
console.log([...text].map(c => c.codePointAt(0).toString(16)));

const broken = text.slice(0, 2);               // A plus isolated high surrogate
console.log(broken.length);                    // 2
console.log(broken.charCodeAt(1).toString(16)); // d83d
if (typeof broken.isWellFormed === "function") {
  console.log(broken.isWellFormed());           // false
  console.log(broken.toWellFormed());           // A + U+FFFD
}

The newer String.prototype.isWellFormed() and toWellFormed() methods are available only in supporting JavaScript runtimes; the feature check is intentional. toWellFormed() can replace lone surrogates with U+FFFD, but it does not recreate the missing low unit or recover the original scalar. A strict validation path should report or reject the malformed string before a lossy repair if exact preservation matters.

Java and .NET Code-Unit Caveats

In Java, String.length() counts UTF-16 code units, while codePointCount(0, str.length()) counts Unicode code points under the Java string abstraction. charAt retrieves one UTF-16 code unit; codePointAt can combine a high–low pair when a valid pair starts at the selected index. A char value is not, by itself, evidence of an independent Unicode scalar. Java's Character.isSurrogate tests a code-unit classification, not the well-formedness of an entire string.

In .NET, System.String.Length similarly represents a count of UTF-16 char elements. A supplementary scalar occupies two char values. The .NET System.Text.Rune abstraction in later .NET generations models scalar values rather than individual UTF-16 units, but Windows PowerShell 5.1 on .NET Framework does not provide the same modern API surface. Code targeting PowerShell 5.1 must use older string and encoding classes carefully, especially around decoder fallbacks.

Both Java and .NET may preserve isolated surrogate code units in strings because their string storage abstractions are not necessarily restricted to well-formed UTF-16. A call to a strict text encoder or validator is therefore the appropriate boundary before serializing such text as interoperable Unicode. These properties are API behavior, not evidence that Unicode permits lone surrogates as characters.

Python Example: Encoding, Decoding, and Round Trips

Python's str indexes Unicode code points for ordinary scalar text and encodes into UTF-16LE or UTF-16BE bytes on request. The following example is executable in Python 3 and shows exact expected byte sequences without relying on the host machine's byte order.

s = "A\U0001F600\u00E9"
be = s.encode("utf-16-be")
le = s.encode("utf-16-le")

assert len(s) == 3
assert be.hex(" ") == "00 41 d8 3d de 00 00 e9"
assert le.hex(" ") == "41 00 3d d8 00 de e9 00"
assert len(le) == 8
assert le.decode("utf-16-le", errors="strict") == s
assert be.decode("utf-16-be", errors="strict") == s

print("scalar count:", len(s))
print("utf-16le bytes:", le.hex(" "))
print("utf-16 code units:", len(le) // 2)

Using "utf-16" instead of an explicit endian encoding typically introduces a BOM when producing a byte stream and interprets BOM conventions during decoding. Such behavior is useful for files but should not be mistaken for the absence of an encoding contract. For a protocol that already specifies little-endian bytes and omits signatures, use the explicit utf-16-le codec rather than assuming a global default.

Python Example: Arithmetic Encoder and Strict Unit Decoder

An explicit small validator makes the surrogate rules testable without requiring a complete text-processing framework. The following functions accept integer scalar values or code units, validate their ranges, and fail on malformed inputs. They operate on code units, not on serialized byte arrays.

def to_utf16_units(cp):
    if not isinstance(cp, int) or cp < 0 or cp > 0x10FFFF:
        raise ValueError("code point outside Unicode range")
    if 0xD800 <= cp <= 0xDFFF:
        raise ValueError("surrogate is not a Unicode scalar")
    if cp < 0x10000:
        return [cp]
    x = cp - 0x10000
    return [0xD800 + (x >> 10), 0xDC00 + (x & 0x3FF)]


def decode_utf16_units(units):
    result = []
    i = 0
    while i < len(units):
        u = units[i]
        if not isinstance(u, int) or not 0 <= u <= 0xFFFF:
            raise ValueError("invalid 16-bit unit at index %d" % i)
        if 0xD800 <= u <= 0xDBFF:
            if i + 1 >= len(units):
                raise ValueError("unpaired high surrogate at index %d" % i)
            low = units[i + 1]
            if not isinstance(low, int) or not 0xDC00 <= low <= 0xDFFF:
                raise ValueError("high surrogate missing low partner at index %d" % i)
            cp = 0x10000 + ((u - 0xD800) << 10) + (low - 0xDC00)
            result.append(cp)
            i += 2
        elif 0xDC00 <= u <= 0xDFFF:
            raise ValueError("isolated low surrogate at index %d" % i)
        else:
            result.append(u)
            i += 1
    return result

assert to_utf16_units(0x1F600) == [0xD83D, 0xDE00]
assert to_utf16_units(0x10000) == [0xD800, 0xDC00]
assert to_utf16_units(0x10FFFF) == [0xDBFF, 0xDFFF]
assert decode_utf16_units([0x0041, 0xD83D, 0xDE00]) == [0x41, 0x1F600]
for invalid in ([0xD83D], [0xDE00], [0xD83D, 0x0041]):
    try:
        decode_utf16_units(invalid)
        raise AssertionError("malformed input was accepted")
    except ValueError:
        pass
print("UTF-16 unit tests passed")

These functions illustrate the grammar but are not replacements for fully audited libraries. They do not implement Unicode normalization, grapheme boundaries, language identification, terminal rendering, or application-specific restrictions. A real parser should also bound collection size, avoid untrusted allocation requests, and verify framing before decoding the contained units.

Windows PowerShell 5.1 Example: Strict UTF-16LE Decoding

Windows PowerShell 5.1 uses .NET Framework types. System.Text.UnicodeEncoding permits an explicit endianness and exception-on-invalid-bytes configuration. This example constructs a UTF-16LE byte array for A😀 and then tests rejection of an isolated high surrogate. It does not modify files and is intended to run in a standard Windows PowerShell console.

# Windows PowerShell 5.1, strict UTF-16 little-endian decoder.
$utf16LE = [System.Text.UnicodeEncoding]::new($false, $false, $true)
[byte[]]$valid = @(0x41, 0x00, 0x3D, 0xD8, 0x00, 0xDE)
$text = $utf16LE.GetString($valid)
Write-Host ("Decoded text: {0}" -f $text)
Write-Host (".NET char count: {0}" -f $text.Length) # 3 units: A plus pair

[byte[]]$truncated = @(0x41, 0x00, 0x3D, 0xD8)
try {
    $null = $utf16LE.GetString($truncated)
    throw "Unexpectedly accepted incomplete surrogate pair"
} catch [System.Text.DecoderFallbackException] {
    Write-Host "Rejected malformed UTF-16LE as expected"
}

The constructor's first Boolean selects big endian when true; the second indicates whether the encoder should emit a BOM preamble; the third requests exceptions for malformed sequences. This example specifically decodes known UTF-16LE bytes. A generic UTF-16 file with an optional BOM needs a separate byte-order detection policy. The PowerShell code is provided for instructional use and should be verified in the target Windows PowerShell 5.1 environment before deployment.

Streaming and Truncated Input

The boundary between input chunks is not a code-point boundary. A byte stream can end a read after the first byte of a code unit, after a high surrogate but before its low partner, or after part of a BOM. A correct streaming decoder must buffer enough incomplete state across reads and distinguish temporarily incomplete input from final truncated input. If the encoding is known to be UTF-16LE, a sequence of three bytes cannot be decoded into complete code units without waiting for another byte or reporting final truncation.

For a simple UTF-16LE payload representing 😀, a transport may supply 3D, then D8 00, then DE. The fully assembled sequence 3D D8 00 DE decodes correctly. If a decoder tries to interpret every read independently, the first read has an incomplete 16-bit unit, the second produces mismatched boundaries, and the last cannot be correctly interpreted alone.

Incremental decoders should expose an end-of-input signal or final flush, apply an explicit fallback policy, and keep byte offsets when diagnosing errors. In message-framed protocols, read the declared payload length exactly and validate the resulting UTF-16 structure before accepting the message as a string. Never treat receiving a short network read as evidence of a completed text record.

Streaming Example: Incremental Decoder Across Split Bytes

Python's incremental codecs provide a concise demonstration that arbitrary byte splits need not damage a valid UTF-16 stream. The final call declares that no additional input remains; this is the correct point at which an incomplete trailing code unit or surrogate should trigger an error.

import codecs
payload = "😀".encode("utf-16-le")  # 3d d8 00 de
parts = [payload[:1], payload[1:3], payload[3:]]
decoder = codecs.getincrementaldecoder("utf-16-le")("strict")
text = "".join(decoder.decode(part, final=False) for part in parts)
text += decoder.decode(b"", final=True)
assert text == "😀"

broken = codecs.getincrementaldecoder("utf-16-le")("strict")
try:
    broken.decode(payload[:2], final=True)  # Complete high unit, no low unit
    raise AssertionError("truncated surrogate accepted")
except UnicodeDecodeError:
    pass
print("incremental UTF-16 tests passed")

A decoder may choose to buffer the high surrogate until the following unit arrives. Another implementation may represent incomplete state differently. Those details are API-specific; the required invariant is that the completed byte stream decodes to the same scalar sequence regardless of read fragmentation.

Unicode Scalar Validity Versus Character Assignment

The validity rule for surrogate pairs is independent of the status of the resulting scalar in Unicode's character database. A well-formed pair can encode a code point that is unassigned in the current Unicode version. It can also encode supplementary private-use code points under an application-defined convention or a noncharacter reserved for internal use. These cases do not make the pair structurally malformed.

Conversely, D800 cannot be legitimized as an independent character merely by labeling it “private use.” The surrogate range is excluded from Unicode scalar values. A system may store such a unit for forensic preservation or legacy compatibility, but that is a distinct raw-code-unit representation—not a well-formed UTF-16 encoding of a scalar.

Text interchange services should separate their concerns: first check byte order and encoding well-formedness, then apply any application policy about allowed code points, formatting characters, controls, private-use values, or identifiers. Conflating these checks creates false rejections of valid data and false acceptance of malformed data.

Combining Marks, Grapheme Clusters, and Emoji Sequences

A surrogate pair is a mechanical encoding device, not a grapheme boundary. The family emoji sequences often displayed as one pictograph can include multiple emoji scalars joined by U+200D; some individual emoji scalars need surrogate pairs and some do not. Skin-tone modifiers, variation selectors, regional indicator pairs, and combining marks further complicate the relationship between stored units and user-visible symbols.

Consider e plus U+0301 COMBINING ACUTE ACCENT: this normally displays as one accented grapheme yet consumes two BMP scalar values and two UTF-16 code units. A single supplementary scalar consumes two units but usually one grapheme when displayed alone. A multi-scalar emoji sequence may consume far more code units despite being perceived as one grapheme. Therefore a UI character counter using UTF-16 .length is not equivalent to a user-perceived-character counter.

This distinction affects cursor movement, deletion, selection, truncation, highlighting, and password or username policies. If the interface must avoid splitting visible text elements, use Unicode grapheme-cluster segmentation rather than guessing from surrogate pairs alone. Grapheme segmentation itself is defined by rules that evolve with Unicode versions; it is not provided automatically by UTF-16.

Normalization, Case Mapping, and Collation Boundaries

UTF-16 encoding does not normalize text. The composed scalar U+00E9 encodes as one 00E9 unit; the decomposed sequence U+0065 U+0301 encodes as 0065 0301. Both are well formed and may display similarly, but they have different code-unit counts and binary representations. NFC and NFD normalization may help applications choose a canonical representation for certain operations, but normalization must be performed as a separate Unicode text transformation.

Case folding, locale-aware comparison, and collation likewise operate at a higher semantic level than UTF-16. A case-insensitive comparison cannot be implemented by lowercasing each 16-bit code unit independently and expecting all languages to behave correctly. Some mappings can expand or depend on context, and supplementary scalars cannot even be treated independently if an algorithm splits their surrogate pairs.

For databases and search indexes, store a clear distinction between original text, normalized search keys, collation rules, and raw-byte evidence. Comparing UTF-16 code units lexicographically is not the same as comparing Unicode scalar values in every case, and neither is necessarily the locale-aware order expected by users.

Interoperability: JSON, HTML, XML, and Web Services

In JSON source text, a supplementary scalar may appear as an actual Unicode character in a UTF-8 encoded JSON document or as a pair of \u escapes, such as "\uD83D\uDE00" for U+1F600. In the latter spelling, the two escape sequences describe one supplementary scalar when interpreted together. A lone surrogate escape such as "\uD83D" is syntactically possible under the JSON grammar discussed in RFC 8259 but does not correspond to a Unicode scalar; the RFC notes unpredictable interoperability when such bit sequences occur.

JavaScript strings often use UTF-16 code units internally, while contemporary web interchange generally uses UTF-8 bytes. Never assume that the memory representation of a JavaScript string determines the encoding of an HTTP message, JSON file, or browser DOM serialization. Encoding labels, content types, BOM conventions, and producer/consumer contracts matter at each boundary. An HTML document declaring UTF-8 remains UTF-8 even if its DOM is exposed through a UTF-16-oriented string API.

XML processors and databases can have additional constraints on which scalar values may appear, separate from UTF-16 well-formedness. A valid UTF-16 pair is not automatically a legal identifier, XML character in every XML version, or allowed application field. Validation should be layered: encoding integrity first, then syntax, then domain rules.

UTF-8, UTF-16, UTF-32, and Nonstandard Surrogate Encodings

A valid Unicode scalar may be represented as UTF-8 bytes, UTF-16 code units, or UTF-32 code units without changing its identity. U+1F600 is F0 9F 98 80 in UTF-8, D83D DE00 in UTF-16, and 0001F600 in UTF-32. All three represent the same scalar, and none specifies how that character should be rendered. The encodings are different serializations of the same Unicode text content.

Text UTF-8 bytes UTF-16 code units UTF-32 units
A 41 0041 00000041
€ E2 82 AC 20AC 000020AC
😀 F0 9F 98 80 D83D DE00 0001F600

CESU-8 and WTF-8 appear in certain compatibility or internal-storage discussions, but they are not substitutes for conforming UTF-8 interchange. CESU-8 represents UTF-16 code units separately in UTF-8-like sequences, so supplementary characters may produce six bytes where standard UTF-8 uses four. WTF-8 can preserve isolated surrogate code units in special circumstances. These formats require explicit contracts; labeling their data simply “UTF-8” invites interpretation and security errors.

Security: Surrogate Splitting and Cross-Layer Validation

One common security failure occurs when a service measures or validates a UTF-16 code-unit sequence and a different component later normalizes, converts, or interprets it under a separate policy. If a component truncates at a code-unit boundary through a surrogate pair, the result may be ill formed; another component might replace the broken unit, reject it, or encode it using a nonstandard preservation mode. That disagreement can change identifiers, signatures, audit logs, filenames, or filtering outcomes.

Do not treat the mere presence of a surrogate pair as a threat: valid pairs are routine Unicode. The risk lies in inconsistent handling of malformed input, lengths, normalization, and cross-language conversion. A parser should validate UTF-16 before assuming it has a Unicode scalar sequence, and all components of a security-sensitive protocol should agree on canonicalization and fallback behavior. Replacing an invalid surrogate with U+FFFD may be appropriate for a display path but unacceptable for a signature-verification or exact-match identifier path.

In systems where string content is used as a path, database key, authorization token, or signed value, validation must also consider control characters, separators, confusables, normalization policy, and application syntax. UTF-16 well-formedness is a necessary encoding-level check, not a complete input-security policy.

Secure Parser and Storage Design Checklist

A UTF-16 consumer should know which unit its length prefix counts, which byte order the payload uses, whether a BOM is permitted, and how malformed sequences are reported. Validate declared lengths before allocation, check for odd byte counts when receiving explicit UTF-16LE/BE payloads, and reject or handle final unpaired surrogates according to the stated contract. Preserve original bytes before any lossy recovery when evidence or data lineage matters.

Control Reason
Explicit UTF-16LE or UTF-16BE contract Avoid ambiguous byte order
Length unit documented Prevent byte/code-unit confusion
Maximum input size enforced Bound memory and processing costs
Strict validation at trust boundary Prevent malformed data entering downstream Unicode stages
Consistent normalization policy Prevent divergent identifiers or comparisons
Original bytes retained for repair Support auditability and reprocessing
Round-trip and boundary testing Detect surrogates lost or split by conversions

When a protocol uses generic UTF-16 and allows a BOM, define fallback behavior if no BOM is present. If a protocol explicitly mandates UTF-16LE without BOM, enforce that contract rather than inferring an alternative encoding from statistics. Debugging heuristics are useful for recovery, but they are not a replacement for a standardized format.

Operational Case Study: A Cross-Language Record Boundary

A JavaScript producer computes a text field length as message.length, then writes a two-byte little-endian length prefix followed by UTF-16LE bytes. Its message is A😀é. The reported length is 4, which is the correct number of UTF-16 code units. The payload occupies 8 bytes, so a Python consumer must not interpret 4 as a byte count; it must read 4 × 2 = 8 payload bytes before decoding.

The emitted payload, excluding the two-byte prefix, is 41 00 3D D8 00 DE E9 00. If the prefix is 04 00, the full message is 04 00 41 00 3D D8 00 DE E9 00. Reading four payload bytes would end after 41 00 3D D8, leaving a dangling high surrogate; accepting the next byte as a new record's prefix would corrupt the message stream. The issue is not a defect in UTF-16 but an undocumented length unit at the protocol boundary.

The repair is to specify the schema precisely: “unsigned 16-bit little-endian count of UTF-16 code units, followed by exactly twice that many bytes encoded as UTF-16LE, strict malformed-sequence rejection, maximum 32,768 code units.” With those terms both languages can implement the same contract. More generally, explicit byte lengths are often simpler for a byte-oriented transport, but either choice can work if it is unambiguous and bounded.

Operational Case Study: Legacy String with an Isolated Surrogate

A legacy program stores the code-unit sequence 0041 D83D 0042. It can be displayed or processed by some 16-bit-string APIs even though it is not well-formed UTF-16. If a later component attempts strict UTF-16LE encoding to a file, it should reject the isolated high surrogate. If it uses replacement behavior, the resulting scalar sequence may be A�B; that is not the same data as the original three units, and it cannot reveal which exact surrogate had been present.

For an archival workflow, keep the original code-unit sequence or raw bytes as a preservation artifact, record the source system and its encoding contract, and produce a separate normalized or repaired text field if needed for search and display. For a normal API that promises Unicode scalar text, reject the malformed string at the boundary. The choice must be policy-driven rather than accidental default behavior.

A particularly dangerous option is allowing one subsystem to preserve lone surrogates through an ad hoc encoding while another assumes the stream contains conforming UTF-8 or UTF-16. Such disagreement undermines predictable validation and interoperability even when both subsystems display plausible text.

Performance, Storage Footprint, and Access Patterns

UTF-16 uses two bytes for a BMP scalar and four for a supplementary scalar when serialized without overhead. UTF-8 uses one byte for ASCII, two or three for many non-ASCII BMP scalars, and four for supplementary scalars. Therefore UTF-16 can be more compact than UTF-8 for some collections with large proportions of frequently used non-ASCII BMP characters, while UTF-8 is typically more compact for predominantly ASCII text. Neither encoding is universally smallest, and application metadata, compression, and storage representation can outweigh raw text byte counts.

Indexing by code unit is efficient in an API that exposes code-unit offsets, but a constant-time code-unit lookup does not imply constant-time lookup of the nth Unicode scalar or nth grapheme cluster. Supplementary pairs and grapheme segmentation require iteration or auxiliary indexing. Converting a large corpus to and from UTF-16 can also add memory traffic and temporary buffers, especially if a system receives UTF-8 over the network but operates internally using 16-bit string interfaces.

Performance engineering should measure actual texts, APIs, and workloads. A high-throughput decoder must still reject malformed final input correctly and avoid splitting surrogate pairs. SIMD, table-driven validation, and streaming optimizations may improve speed, but none changes the underlying Unicode grammar.

Review Questions with Answer Guidance

Why does UTF-16 have both one-unit and two-unit scalar encodings? The BMP nonsurrogate scalars fit directly in a sixteen-bit unit. Supplementary scalars use a reserved high–low surrogate pair to represent the additional code-point range without reassigning the BMP's ordinary codes.

What exact calculation produces D83D DE00? Subtract 0x10000 from 0x1F600; split the remainder 0xF600 into its upper and lower ten-bit parts; add 0xD800 and 0xDC00 respectively. Reverse decoding adds 0x10000 to the recombined twenty-bit quantity.

Can an unpaired surrogate be stored in a JavaScript or .NET string? Yes, some string abstractions permit raw code units that are ill formed as UTF-16 sequences. Storage is not the same as Unicode scalar validity, and strict serialization may reject such a string.

Is a BOM required for every UTF-16 string? No. Byte order must be established through a BOM or an external encoding contract as defined by the applicable format or protocol. Internal code-unit sequences do not need a byte-order mark.

Does String.length count characters? In JavaScript it counts UTF-16 code units. That differs from scalar-value count for supplementary characters and differs still more from grapheme-cluster count for combined visible characters.

Why is strict failure different from replacement? Strict failure preserves the distinction between valid and malformed input. Replacement can produce displayable Unicode text at the cost of losing information about the original malformed units, unless the raw input was separately retained.
