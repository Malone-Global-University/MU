Collection Overview

The Data Catalogs and Metadata Management unit belongs to the Data Systems division of the Computer Science volume within the MGU Encyclopedia. It extends the established Data Catalogs and Metadata Management parent article, which addresses asset identity, governed metadata, stewardship, lineage, provenance, W3C DCAT 3, controlled access, metadata quality, operations and security.

A catalog is not merely a searchable list of table names. It is an evidence-bearing representation of data assets and the relationships, meanings, controls and lifecycle states that make those assets usable and accountable. Source systems remain authoritative for the actual data and enforce their own access policies; the catalog assembles identifiers, observations, annotations and approved descriptions. Catalog accuracy depends on both technical collection and responsible people. A recent scan can document schema shape, but cannot independently approve a business metric, verify legal use rights or establish that every upstream dependency was observed.

This page is the Level 4 unit index. Its twenty linked child subjects are intended Level 5 unit subarticles, with narrower Level 6 or deeper companions available for later focused development. Index subject groups organize reading and commissioning; they are not new taxonomy levels or article folders. Subarticle production belongs to a separate workflow.

Source fidelity: unlike some earlier units, the existing parent explicitly lists all 20 child titles and destination slugs. This directory preserves them, in the parent's order, without substitutions or expansions. The descriptions, comparative tools and learning routes in this index are editorial elaborations of those established subjects. Links are intentionally active for planned destinations; an active link is not proof that the linked article has been published.

Catalog Foundations, Asset Identity, and Stewardship

These five foundation articles define what a catalog is allowed to say about an asset, how that claim is represented, where observations come from and who may approve meaning. The central distinction is between durable, system-derived identifiers and business descriptions requiring accountable stewardship. A technically complete catalog without human agreement on meaning is still incomplete as an institutional reference.

1. Data Asset Identity and Namespaces

Primary scope: Durable identifiers, namespace boundaries, aliases and source-system names for cataloged assets. Explain the difference between a persistent internal asset ID, a qualified name supplied by a source system, and a changeable human-facing label. Construct asset keys from platform, environment, project, database, schema and object when appropriate, while documenting how renames, moves and resource replacement are handled. Compare stable IDs, canonical URLs, qualified database names and aliases as distinct reference mechanisms; none is universally immutable. Include collision prevention, tenant separation, stale alias management, identity resolution after connector changes and historical references required for lineage. Address asset identity for tables, streams, APIs, files, dashboards and externally registered resources, making clear that naming a thing does not authorize access to it.

Editorial boundary: The Binary Data and File Systems units own bytes and file paths; this article owns catalog identity and entity-resolution semantics, not the implementation of an entire database namespace.

Expected specialist treatment: Build an asset identity record that survives a display-name change, a source-table rename and an authorized move to another environment without accidentally joining two unrelated assets.

2. Metadata Schema Design

Primary scope: Catalog record fields, controlled types, validation rules, extensions and schema migrations. Develop a practical asset-record schema containing a durable key, source locator, type, owner, classification, lifecycle state, timestamps and evidence-backed relationships. Distinguish mandatory from optional metadata and validate identifiers, enumerations and references without overconstraining domain-specific descriptions. Show how to extend records for schemas, glossary terms, data products and lineage while maintaining backward compatibility. Explore null versus missing fields, unknown rather than falsely asserted values, schema-version tags, validation failures, human-edited annotations and machine-harvested attributes. Discuss schema evolution for the metadata system itself separately from changes to the schema of an underlying dataset.

Editorial boundary: Data Modeling owns general conceptual and relational modeling; this article addresses catalog metadata contracts, validation and migration rather than modeling a business database in full.

Expected specialist treatment: Present a small typed catalog schema and evaluate three records: valid, missing an approved owner, and containing an unknown classification value.

3. Metadata Discovery Connectors

Primary scope: Authorized harvesting of catalog metadata from databases, APIs, warehouses, streams and files. Trace the flow from configured source inventory through discovery, schema extraction, identity mapping, normalization, deduplication and indexed catalog publication. Compare polling, scheduled scans, events and push-based ingestion with explicit attention to scan coverage and potential drift. Explain connector scope, least-privilege credentials, rate limits, backoff, pagination, incremental scans, error isolation and source-system change detection. Distinguish metadata collection from copying underlying records; sensitive samples should not be gathered merely because a connector can read them. Address deleted or temporarily unreachable assets and distinguish successful connection from complete inventory coverage. Describe how each ingested field records provenance, last observed time and who may override it.

Editorial boundary: Data Engineering owns pipeline transformation and orchestration broadly; this child specializes in catalog discovery and ingestion provenance.

Expected specialist treatment: Sketch a connector run that finds three source objects, handles one renamed object and records a failed scan without deleting valid historical metadata.

4. Metadata Stewardship and Ownership

Primary scope: Institutional responsibility for catalog metadata, approval, review and dispute resolution. Differentiate technical custodians, business owners, subject-matter stewards and data consumers. Specify who can approve business definitions, classify assets, curate descriptions, resolve duplicate entries and retire outdated datasets. Examine stewardship assignment, escalation paths, delegated authority, staff turnover, conflicting claims and mechanisms for recording review evidence. Explain how automated discovery and human annotation cooperate: a scan may establish column names but not the approved meaning of an institutional metric. Include review cadences adapted to risk, coverage metrics and auditable workflows without assuming that listing a name makes ownership effective. Show how to prevent orphaned datasets and stale responsibility assignments.

Editorial boundary: Enterprise Data Governance owns institution-wide policy and accountability; this specialist treats how those responsibilities are represented and actioned inside catalog records.

Expected specialist treatment: Provide an ownership and approval matrix for a dataset whose schema changes automatically while its business definition requires a reviewed sign-off.

5. Business Glossary Management

Primary scope: Approved business definitions, synonyms, controlled vocabularies and links to technical assets. Explain why a business glossary provides reviewed meaning rather than merely serving as a keyword list. Model terms, labels, synonyms, definitions, units, valid populations, approval authorities and links to physical datasets or fields. Resolve homonyms used by different departments without silently merging incompatible meanings. Discuss versioned terminology, deprecated synonyms, localization, unit changes and semantic disagreement. Show that a term such as active student may depend on an approved measurement window and operational rule, not simply an automatically detected column name. Connect glossary terms to lineage and quality checks while retaining provenance of both automated suggestions and human decisions.

Editorial boundary: Data Modeling owns logical entity schemas, while Data Catalogs owns governed descriptions and semantic linkage; the glossary does not replace an executable metric definition or policy rule.

Expected specialist treatment: Create two conflicting definitions of “active learner,” resolve them through an owner-approved glossary term and specify which dashboards must display the effective definition.

Metadata Quality, Lineage, and Provenance

These articles ask whether catalog claims are complete and supported, how assets depend on each other, and what evidence establishes their history. Dataset lineage, field-level derivation, run telemetry and broader provenance are related but nonidentical subjects. Each child must identify observation scope, the authority of claims, temporal context and gaps that cannot be inferred from missing events.

1. Metadata Quality Measurement

Primary scope: Coverage, accuracy, validity, uniqueness, consistency and field-specific review freshness. Develop independent measures for metadata coverage, field validity, confirmed ownership, stale technical observations and correctness against authoritative sources. Explain why completeness alone cannot certify accuracy and why reviewed assets are not necessarily the full denominator of an inventory. Establish required fields by asset class and risk; distinguish system-observed fields from approved annotations. Show numerator, denominator, sampling approach, exceptions, owner and remediation target for each metric. Explore how coverage changes when a connector discovers previously unknown assets, and why that can lower the ratio while improving the inventory. Include dashboards, evidence requirements and prioritization by consequence rather than superficial record-count targets.

Editorial boundary: Data Quality Integration and broader Data Quality units concern values inside datasets; this article assesses the quality of descriptions and relationships in the catalog itself.

Expected specialist treatment: Calculate 230 assets with both required fields among 250 in scope (92%), compare individual owner/classification coverage, and explain how denominator changes alter the report.

2. Data Lineage Modeling

Primary scope: Dataset and operation graphs, dependency edges, evidence strength and change impact. Model nodes representing source datasets, derived datasets and transformation jobs, with directed relationships identified by type, effective time and evidence. Distinguish observed execution lineage, static code analysis and manually approved mapping. Explain how multiple upstream sources, fan-out, cycles caused by periodic or recursive processing, and external dependencies are represented without misleading claims of certainty. Show upstream and downstream traversal, deduplicated reachability, impact analysis after a schema change and the difference between an observed edge and a complete graph. Include modeling for versioned assets, lineage gaps and unknown intermediates. A diagram must document its scope, freshness and provenance rather than merely display attractive arrows.

Editorial boundary: Data Transformation owns how individual data pipelines change values; Metadata Graph Architecture owns general graph storage choices. This article owns the semantic meaning and evidence of lineage edges.

Expected specialist treatment: Draw a five-node directed lineage graph and compute downstream distinct-asset reachability, distinguishing the number of paths from the number of affected assets.

3. Column-Level Data Lineage

Primary scope: Field derivations, expression semantics, aggregation dependencies and uncertainty. Extend dataset-level lineage to specific columns and calculations. Compare direct passthrough, rename, join, arithmetic derivation, aggregation, conditional logic and masking as different dependency patterns. Show how SQL parsing, pipeline instrumentation and steward-reviewed definitions can contribute evidence while remaining incomplete for dynamic SQL, opaque UDFs and external transformations. Preserve the distinction between syntactic dependence and semantic correctness; a parser identifying source columns cannot guarantee that a metric matches a business glossary. Describe lineage when fields are reordered, renamed, dropped or created and how changes propagate to downstream dashboards. Address field-level confidentiality so lineage views do not reveal restricted schema details to unauthorized users.

Editorial boundary: Database Query languages own SQL syntax and execution; this child owns catalog-side representation and assessment of field dependencies and their evidence.

Expected specialist treatment: Trace a computed net_revenue field from sales_amount and returns_amount, then explain downstream impact when one input unit or null policy changes.

4. OpenLineage Integration

Primary scope: Exchange of run, job and dataset lineage events, including facets and execution context. Introduce the OpenLineage event model through jobs, runs, input and output datasets and metadata facets. Explain the distinction between a recurring logical job and a particular execution, and between a dataset-level declaration and the partitions actually accessed during a run. Trace event emission, transport, ingestion, idempotency, deduplication and reconciliation when observations arrive late or out of order. Show why a successful lifecycle event reports an execution status but does not certify accuracy of its data product. Discuss ownership of identifiers, namespace consistency across integrations, partial runs and varying connector coverage. Keep examples version-aware and avoid asserting that every engine emits all possible facets.

Editorial boundary: Data Lineage Modeling supplies the generalized graph; this article specializes in interoperable execution event contracts and operational ingestion, not job orchestration itself.

Expected specialist treatment: Model two runs of one job with different input partitions and show how duplicate or missing events affect what the catalog may safely claim.

5. Provenance with W3C PROV

Primary scope: Entity, activity, agent and derivation relationships for accountable data provenance. Explain W3C PROV concepts using entities, activities and agents and relations such as generation, usage, attribution and derivation. Distinguish provenance from execution-only lineage: a published research dataset, a citation, an approved document and a transformation run may all have relevant provenance. Show how accountable agents and versions can be associated with activities without treating an unverified provenance claim as proof. Consider primary and derived sources, revision history, provenance bundles, identity conflicts and interoperability when one system describes a dataset more coarsely than another. Stress the need to retain evidence, timestamps where meaningful, authority and correction procedures. Keep PROV general enough to apply beyond a single analytics platform.

Editorial boundary: OpenLineage Integration treats job/run telemetry; PROV provides a broader provenance vocabulary and is not a guarantee that every recorded relationship is independently verified.

Expected specialist treatment: Diagram an entity generated by a transformation activity that used a source dataset and was associated with an accountable organization, separating asserted from verified evidence.

Interoperability, Discovery, and Governed Access

These articles focus on exchange, search, graph-based relationships and governed discovery. Public metadata exchange does not entail public data access; useful ranking is not a substitute for approved meaning; classifications do not enforce their own controls. A catalog must remain intelligible across platforms without becoming an uncontrolled directory of sensitive infrastructure.

1. DCAT 3 Catalog Interoperability

Primary scope: W3C DCAT 3 catalog, dataset, distribution and data-service descriptions for exchange. Establish the role of W3C Data Catalog Vocabulary Version 3 in exchanging approved descriptions between catalogs. Model a conceptual dataset separately from its CSV distribution, API distribution and associated data service; show why one downloadable format does not define the whole dataset. Explain identifiers, themes, license metadata, access conditions, provenance and multilingual metadata where relevant. Consider mapping proprietary fields into a shared vocabulary, unmapped properties, dataset series and version relationships, and validation of exchanged records. Distinguish publishing catalog metadata from granting access to private data; an institution may export a minimal public record while retaining restricted metadata internally. Note that DCAT does not standardize the complete behavior of every catalog product.

Editorial boundary: Metadata Schema Design owns internal record requirements; this child owns standards-based outward interoperability and mapping semantics rather than general data publication policy.

Expected specialist treatment: Represent one approved dataset and two distributions, then identify which fields can be published publicly and which require internal-only protection.

2. Metadata Graph Architecture

Primary scope: Storage and traversal of asset, owner, glossary, lineage and policy relationships. Design a conceptual metadata graph in which assets connect to technical schemas, owners, glossary terms, contracts, classifications, lineage edges and quality observations. Compare relational tables, document records, graph-oriented stores and hybrid search indexes as implementation choices with different traversal and update characteristics. Explain stable IDs, typed edges, schema migrations, provenance tags, deduplicated traversal and access-control filtering. Distinguish an internal graph used by the catalog from a published lineage diagram and specify how graph inconsistencies are detected. Explore bounded breadth-first reachability, cycle handling, edge evidence and incremental updates, while noting that a graph database is not a prerequisite for a useful metadata catalog.

Editorial boundary: Data Lineage Modeling defines dependency semantics; Database Indexing and Graph Theory define more general techniques. This child addresses catalog-specific relationship storage and query behavior.

Expected specialist treatment: Compare a relational edge table with a property-graph sketch for a small catalog and show how a downstream impact query avoids duplicates and unauthorized asset leakage.

3. Catalog Search and Discovery

Primary scope: Metadata indexing, relevant ranking, faceted navigation and trustworthy result previews. Analyze what it means to find an appropriate data asset using technical names, business synonyms, domains, approved definitions, ownership and quality indicators. Compare lexical lookup, filters and faceted search with semantic or embedding-based discovery, taking care not to mistake similarity for accuracy. Distinguish catalog search indexing from database indexes on the underlying stored rows. Define relevance signals such as verified ownership, last-reviewed time, availability, popularity and contractual fit, and explain what each can and cannot prove. Address synonyms, misspellings, multi-language discovery, access-filtered results and sensitive metadata in snippets. A search result should expose provenance and caveats while preserving the separation between discovery and authorization.

Editorial boundary: Information Retrieval owns general search algorithms; this article applies them to metadata assets, catalog relevance, trust signals and discovery permissions.

Expected specialist treatment: Develop a ranking rubric for three similarly named datasets, one stale, one approved and one inaccessible, explaining why popularity alone should not determine the first result.

4. Data Classification in Catalogs

Primary scope: Asset and column sensitivity labels with evidence, review responsibilities and safe exposure. Describe institutional classification taxonomies such as public, internal, confidential and restricted, emphasizing that the actual categories and obligations must come from adopted policy. Explain how automated detectors and human reviewers assign labels, record evidence and handle uncertainty or false positives. Support asset-level labels, selected field-level annotations and inheritance while distinguishing classification from enforcement. Explore classification changes, owner challenges, exceptions, materialized previews, metadata itself as a sensitive resource and restrictions on revealing file names or columns. Discuss how catalogs connect to privacy and governance functions without claiming that a label alone encrypts, masks or restricts data.

Editorial boundary: Privacy Engineering defines personal-data minimization and security controls; this child owns metadata classification records and their review workflows, not enforcement of every underlying system.

Expected specialist treatment: Classify an illustrative enrollment table and its sensitive contact fields, then document different safe preview content for anonymous and authorized viewers.

5. Data Access Request Workflows

Primary scope: Catalog-mediated access requests, approvals, audit trails and enforcement boundaries. Follow a request from data discovery through stated purpose, policy evaluation, business or security approval, technical provisioning, periodic review and revocation. Distinguish approvals documented in a catalog from access actually enforced by an identity provider, database or storage platform. Show how classification, ownership, contractual restrictions and least privilege inform decisions; discuss separation of duties, expiration, emergency access and denial evidence. Avoid suggesting that a catalog link grants permission. Explore inaccessible assets in search results, request status, approval delegation and evidence of successful revocation. Include privacy minimization and governance escalation for sensitive requests while keeping enforcement mechanisms in neighboring security articles.

Editorial boundary: Identity and Access Management owns authentication and authorization enforcement; this child treats the catalog workflow, lifecycle and evidence that connect users to those systems.

Expected specialist treatment: Build a request-state diagram including proposed, submitted, approved, provisioned, expired and revoked, with a separate check confirming the actual system permission.

Contracts, Lifecycle, and Catalog Assurance

These articles govern change over time: promises between data producers and consumers, versions of descriptions, controlled retirement, observation freshness, and protection of the catalog itself. They distinguish a changed record from a reviewed decision and a successful scan from an accurate source. The unit must support historical interpretation and operational recovery, not simply current search results.

1. Data Contracts and Catalog Integration

Primary scope: Registration of schema, semantic, freshness and ownership expectations in the catalog. Describe a data contract as a declared agreement about a data interface and the expectations placed on producers and consumers. Distinguish machine-checkable schema and freshness constraints from human-approved meaning, use rights and service commitments. Map contract identifiers, owners, versions, enforcement evidence and violations to cataloged datasets and downstream dependencies. Explain breaking versus compatible changes and the workflow for alerting affected consumers before rollout. Discuss contract tests, backfill expectations, transfer of ownership and what the catalog must record when the active contract is unknown. Avoid assuming every dataset has one stable producer or that a catalog entry is proof of contract compliance.

Editorial boundary: Data Engineering owns pipeline implementation; this child owns the catalog registration, discoverability and governance of contracts at source–consumer boundaries.

Expected specialist treatment: Draft a one-page contract for a daily export with column requirements, a freshness objective, an approving owner and clear evidence for pass/fail.

2. Metadata Versioning and History

Primary scope: Time-aware metadata revisions, semantic changes, audit trails and effective dates. Separate dataset versions, technical schema versions, glossary-definition versions, catalog-record revisions and software releases. Explain why a report produced under a historical business definition must not be silently reinterpreted after a later edit. Define effective and recorded times where useful, editor attribution, rationale, approval, rollback and compatible versus breaking changes. Describe copy-on-write history, change events and retention policies without claiming one storage scheme fits every environment. Show how renames interact with persistent asset IDs and how downstream lineage or contracts can reference a specific historical meaning. Include correction of mistaken entries with append-only audit evidence when required by policy.

Editorial boundary: Database Transactions owns general update atomicity; this child owns semantic and historical traceability of catalog records and their dependent interpretations.

Expected specialist treatment: Compare a cosmetic glossary edit with a unit-of-measure change and record which historical dashboards and contracts need an explicit version boundary.

3. Data Asset Deprecation and Retirement

Primary scope: Lifecycle transitions, replacement mappings, dependency review and controlled withdrawal. Define lifecycle states for draft, active, deprecated, retired and archived assets and distinguish notice from actual decommissioning. Trace the need for stable replacement identifiers, approved sunset dates, notification of consumers, lineage impact analysis and security review before access or connectors are removed. Explain how the catalog preserves references to retired assets so historical analyses and audit trails remain intelligible, without falsely presenting a retired object as currently available. Address deleted sources, temporary connector failures, contract implications and workflows for restoring metadata without reopening prohibited access. Require evidence of completion beyond a changed status flag.

Editorial boundary: Software release management owns application deployment; this child treats the cataloged lifecycle and migration evidence for data resources.

Expected specialist treatment: Prepare a retirement checklist for a superseded reporting dataset including replacement mapping, affected consumers, approvals, archival records and a verified cutover.

4. Catalog Monitoring and Freshness

Primary scope: Coverage, scan timeliness, ingestion failure reporting and metadata service objectives. Distinguish source last changed, connector last attempted, connector last succeeded, catalog indexed, business description last approved and lineage event received. Define distinct freshness objectives based on risk and field function; a schema scan may be hourly while a legal definition receives periodic review. Model scheduled, event-driven and hybrid collection, retry limits, connector outages, alert routing and coverage erosion. Explain why a six-hour polling cycle cannot establish five-minute freshness for source changes unless another observation mechanism exists. Compare alerting thresholds, quality dashboards and runbooks for remediation. Include false alarms, time-zone boundaries and an unambiguous denominator for coverage metrics.

Editorial boundary: Data Engineering owns broad pipeline observability; this child owns operational trust in catalog metadata and discovery freshness.

Expected specialist treatment: Calculate compliance from 170 successfully scanned assets among 200 requiring a 24-hour observation window (85%) and design alerts for failed scans versus overdue stewardship review.

5. Metadata Catalog Security

Primary scope: Trust boundaries, least-privileged connectors, secure rendering and recovery of catalog metadata. Threat-model the catalog as a map of assets and an integration hub for source systems. Examine read and edit authorization, sensitive asset names, credential hygiene, least-privilege harvesting, separation of duties, audit logs, change approval and backup of curated annotations. Emphasize that ingested descriptions and connector payloads are untrusted; render them safely, validate links and prevent embedded instructions or markup from assuming privileged authority. Discuss defense against metadata exfiltration through search snippets, over-broad service accounts and adversarial imported descriptions, including AI-assisted discovery. Distinguish confidentiality, integrity and availability objectives, with tested restoration of machine-harvested and human-reviewed state.

Editorial boundary: Application Security and Identity and Access Management own general platform defenses; this child applies those controls to catalog-specific attack surfaces and metadata integrity.

Expected specialist treatment: Create a defensive review checklist for a connector that imports malicious HTML in a description, including escaping, access checks, quarantining and audited administrative correction.

Critical distinction: observing, describing, interpreting and authorizing data are different actions. Discovery connectors observe sources; human stewards approve intended meanings; lineage reports documented dependencies; classification registers handling rules; an external access-control system ultimately enforces access. A catalog may coordinate these activities while not replacing the underlying authority for any of them.

Illustrative Metadata and Catalog Scenarios

The following scenarios illustrate typical architectural and governance decisions. They are constructed teaching cases, not MGU production incident records or assertions about a particular deployed catalog. Each scenario asks which evidence is available and which specialist topic can resolve the uncertainty.

Scenario A — One dataset is renamed but should remain the same asset

A university catalog records an internal asset ID asset-0142, a source locator prod.analytics.enrollment and the display label “Enrollment Records.” The source table is renamed, while the actual logical dataset continues under a mapped identifier. A steward reviews the rename and updates the locator and alias record without assigning asset-0142 to a new dataset. That is different from deleting the old table and creating an unrelated table under the same name, which would require an identity decision. Data Asset Identity and Namespaces explains namespace qualification; Metadata Versioning and History records the effective change. A canonical URL can help people find the resource but should not be treated as a permanent identity merely because its text looks stable.

Scenario B — Metadata completeness increases while recorded coverage falls

An inventory has 250 in-scope assets; 230 have both an approved owner and a classification, yielding 230 ÷ 250 = 92% combined coverage. A new connector discovers 50 previously missing assets, none of which has these approved fields. The revised ratio is 230 ÷ 300 ≈ 76.7%. The lower percentage does not necessarily indicate that the catalog became less useful; the denominator became more honest. Metadata Quality Measurement must distinguish coverage, source accuracy and freshness. Metadata Discovery Connectors should document the added connector scope, and Metadata Stewardship and Ownership should assign review work rather than hide the new omissions.

Scenario C — A lineage graph yields more paths than affected assets

Consider a source table S feeding two intermediate tables A and B. Both feed an approved report R, and B also feeds dashboard D. The unique downstream assets reachable from S are A, B, R and D: four distinct assets, even though R has two directed upstream paths from S. Counting paths is not the same as counting affected assets. For change impact analysis, deduplicate by stable IDs and label each edge as observed, parsed or curated. Data Lineage Modeling owns the dependency claim; Metadata Graph Architecture owns efficient and access-filtered traversal; Column-Level Data Lineage narrows any claim about which specific report fields depend on the changed source.

Scenario D — One recurring job has two different execution histories

A daily publishing job runs on Monday with one date partition and on Tuesday with a different partition. Its logical job identity remains stable while each run has its own execution context and reported input/output facets. If an event is duplicated, ingestion should avoid inventing another execution; if an event is missing, the catalog should not silently fill in a fabricated run. A successful event also does not prove that the business metric is correct. OpenLineage Integration explains event exchange, Data Lineage Modeling captures the generalized dependency graph, and Metadata Quality Measurement evaluates the limits of observation coverage.

Scenario E — An institution publishes descriptions, not private student records

An internal dataset has a CSV distribution for authorized staff and an API distribution for governed applications. A public catalog entry can identify the dataset conceptually, document an approved description and declare access conditions without publishing private endpoints, samples or restricted technical details. The dataset is not the same entity as either distribution. DCAT 3 Catalog Interoperability develops the exchanged vocabulary, while Data Classification in Catalogs and Metadata Catalog Security define what metadata may safely be disclosed. Standardizing a description does not remove the institution’s access obligations.

Scenario F — A catalog approval does not actually grant database access

A researcher requests a restricted enrollment dataset. The catalog records the purpose, the responsible owner’s approval and a proposed expiration date. Access is effective only after an authorized source platform or identity system provisions the permission. The workflow should record that separate evidence and later verify revocation. If the approval expires while a database role remains active, the catalog is no longer a reliable representation of access. Data Access Request Workflows coordinates states and evidence, Data Classification in Catalogs records the handling label and Metadata Catalog Security protects the request and audit history. The IAM system remains the enforcement authority.

Scenario G — A published metric changes meaning without changing its column name

An institutional report initially defines “active learner” as a person who accessed the learning platform during the past 30 days. A revised policy counts only qualifying course engagement in the same window. The column name remains active_learners, but historical comparisons can no longer assume a stable definition. The glossary needs an effective date and approved definition version; contracts and downstream reports need notices or version pins. Business Glossary Management owns approved meaning, Metadata Versioning and History preserves historical context and Data Contracts and Catalog Integration records producer–consumer expectations.

Scenario H — Catalog freshness is not the same as source freshness

For 200 assets whose technical metadata must be observed within 24 hours, 170 have a successful scan within that window. The compliance rate is 170 ÷ 200 = 85%; it is not proof that the data in those assets are current. A connector scheduled once every six hours also cannot truthfully promise five-minute detection of source changes without a faster event path. Separate connector last-attempt time, last-success time, source observation time and steward-review time. Catalog Monitoring and Freshness establishes the objective, Metadata Quality Measurement specifies the denominator and Metadata Discovery Connectors identifies the collection mechanism.

Scenario I — An imported metadata description contains hostile markup

A connector imports a free-text dataset description containing embedded HTML or instructions addressed to an AI assistant. This content is untrusted source data, even if its surrounding metadata was harvested through an authorized connector. The catalog interface must escape or safely sanitize rendered output, avoid executing the description, apply authorization to search results, and preserve an audit trail if a steward corrects the record. Metadata Catalog Security defines the trust boundary, Metadata Discovery Connectors handles safe ingestion and Catalog Search and Discovery limits what preview text may be exposed. Neither a successful scan nor an authoritative-looking string makes the payload a command.

Methodological rule: when reporting a metric, state the denominator and observation window; when showing a relationship, state its evidence; when approving access, verify enforcement; when changing business meaning, preserve effective history. These requirements prevent catalog interfaces from making claims stronger than the data behind them.

Catalog Design and Investigation Framework

Use the framework before selecting a catalog product, commissioning a connector or treating catalog output as reliable evidence. A useful design review specifies the asset population, trust boundaries, source authority, human decision rights, observation frequency and recovery procedure. Technologies can be mixed; the questions establish which information must be reliable.
