Definition, Scope, and Governing Principle

A data asset identity is a catalog's claim that its metadata record refers to one particular resource across observations, integrations, and historical changes. A namespace defines the scope within which a name or source identifier is intended to be unique. These are separate ideas. A warehouse table called enrollment is not globally distinguishable unless the naming context supplies an appropriate account, environment, database, and schema; yet even a fully qualified table name may change when the table is renamed. A durable catalog identity must manage both facts rather than assume that a familiar string is a permanent identity.

This MGU Encyclopedia Level 5 article explains durable internal asset IDs, source-system identifiers, qualified locators, namespaces, canonical references, aliases, and evidence-based identity reconciliation. The parent Data Catalogs and Metadata Management overview establishes the broader function of catalogs; the unit directory lists twenty specialist treatments. Its neighbors develop Metadata Schema Design, Metadata Discovery Connectors, and Metadata Versioning and History.

Governing rule: assign an authoritative internal identity independently of a human-readable name or physical address; maintain source locators, external identifiers, and aliases as governed evidence; and decide whether an apparent change represents continuity, replacement, duplication, or uncertainty before rewriting references. A catalog cannot guarantee that two resources are the same merely because their names match, nor can it conclude they differ merely because their names do not.

Learning Objectives and Operational Questions

After studying this article, readers should be able to distinguish persistent catalog IDs from platform-qualified names; construct properly scoped source locators for common asset types; explain when tenant, platform instance, environment, and resource generation are needed to prevent collisions; maintain historical aliases without redirecting users to unrelated resources; and describe an auditable decision process for renames, relocations, deletion, and recreation. Readers should also recognize vendor-specific identity models without treating their serialized identifiers as interchangeable standards.

A catalog engineer should ask: What precise resource does this record denote? Who minted the identifier? Under which namespace is it unique? Can the source reuse a name or native ID? Does the source publish an immutable object ID or a change event? Is a rename distinguishable from drop-and-create? Which references must continue resolving after a move? Which aliases have expired? What evidence justified a merge? Is this a description link or an authorization decision? How will reconciliation behave if a connector stops scanning an asset?

Asset Identity Versus Asset Description

An asset identity answers which entity? Description answers what does the entity mean? These are connected, but neither substitutes for the other. A university may describe a table as Student Enrollment Records for readers, while its database object is physically named enrl_fact_v2. The institution may revise the description, change custodians, and reorganize its program vocabulary without changing the resource's identity. Conversely, two departments may publish assets with exactly the same display label but entirely different records and governance requirements.

A catalog should allow display titles and descriptions to be amended without issuing new entity IDs. It should also allow a resource to become inaccessible, unpublished, or retired while retaining a resolvable historical identity for audit and lineage. In this usage, durable means stable under the catalog's documented continuity policy, not that a physical object exists forever or that every rename must automatically preserve identity.

The phrase logical asset also needs precision. Some organizations catalog a product-like dataset that remains conceptually continuous across migrations from one warehouse to another; others catalog each concrete physical table as a distinct asset and join successive versions through an explicit replaces relationship. Either design can be coherent. A catalog must declare which level it identifies and must not quietly swap the meaning of an ID from a physical table to an abstract data product.

The Four Reference Layers

A practical catalog separates at least four reference mechanisms. First, the internal asset ID is minted by the catalog and normally remains unchanged for the lifetime of that catalog entity. Second, the source-native identifier is provided by a platform, where available; its guarantees depend on the platform and resource lifecycle. Third, the qualified locator says where a source resource can currently be found. Fourth, the display label or alias helps a person find or recognize it. A public catalog URL may form a fifth layer: a navigational link into an entity page, not automatically the entity's source identifier.

Asset IDs may be UUIDs, ULIDs, generated database keys, or other globally or namespace-unique tokens. The representation matters less than a consistent minting authority, uniqueness guarantee, immutability rule, and reconciliation policy. A URL can be intentionally designed to contain the durable ID, but merely being a URL does not make it immutable.

Namespaces: The Boundary of Uniqueness

A namespace is a naming context that determines where a particular identifier is meaningful. An SQL table name might be unique only within a schema; a schema name may be unique within a database; and the database name may be unique only within a particular warehouse account or server. A bucket name, file path, API route, stream name, or dashboard identifier has its own system-specific scope. A namespace registry should capture these boundaries explicitly rather than guess from dotted names.

A namespace can be hierarchical: institution → tenant → environment → platform instance → database → schema → table. It may instead be based on an opaque provider-assigned account ID and object ID, without a user-visible hierarchy. There is no universal list of mandatory components. Use the smallest set that actually prevents collisions in that source, plus any disambiguating generation or type fields required by its lifecycle. Context that can change, such as ownership team or business domain, usually belongs in metadata rather than the primary identity.

For example, analytics.enrollment in development and production need not denote the same object, and analytics.enrollment in two different warehouse accounts certainly cannot be merged without evidence. Similarly, the string customers may denote a table, a Kafka topic, an API resource, and a dashboard. The resource type is not cosmetic if a source can reuse a textual name across types.

The Anatomy of a Qualified Source Locator

A qualified source locator is an explicit description of the resource's present position within the origin's naming rules. It is suitable for discovery and source navigation, but should not automatically be used as the immutable identity. A relational table locator might contain {provider, account_id, environment, database, schema, table}. A file object might require {storage_service, account, bucket, object_key, version_id}. An API might require an API identifier, service deployment, operation or route, and a version boundary. A dashboard often depends on workspace and dashboard IDs rather than its title.

Asset type Typical locator context Change requiring identity review
SQL table Account/instance, catalog or database, schema, object Rename, schema transfer, drop-and-create
Warehouse view Warehouse/account, database, schema, view View redefinition or recreation
Message stream Cluster/account, namespace, topic/stream Cluster migration or topic recreation
Object-storage file Provider/account, bucket/container, key, optional version Rename-like copy, overwrite, new version
API resource Service identity, deployment, API version, operation Route refactor or service replacement
Dashboard BI tenant/workspace, platform dashboard ID Move, clone, reimport with new ID
External data product Issuer namespace and issued dataset ID Issuer migration or catalog federation

The dot character is not a universal delimiter. SQL identifiers may contain dots or quoted spaces; object paths can contain punctuation; API routes can contain dynamic parameters; and vendors vary in case sensitivity. Prefer typed components in structured fields, with a separate official string renderer, rather than reconstructing names by splitting a flattened value on punctuation. A source URL or JDBC connection string can contain credentials or volatile hosts and should not be copied wholesale into a public identifier.

Tenant, Account, Region, and Environment Isolation

Multi-tenant catalogs need both a globally unique catalog ID and rigorous partitioning of source claims. A source-native table_id=99 issued by account A is not the same as table_id=99 issued by account B. Even within one organization, two independently administered production accounts may reuse identical database, schema, and table names. Preserve an authoritative source-instance key and tenant scope in the mapping used to resolve external identities.

An environment string such as PROD or DEV helps distinguish deployments but is insufficient by itself; many organizations have multiple production tenants. Region matters when the platform's naming or object ID scope is regional; it should not be added mechanically when the upstream identity is already globally unique. Likewise, a hostname may change while the server instance persists, and an ephemeral cloud hostname can be especially poor material for identity.

Never infer that two assets are equal because their names match after case folding or Unicode normalization. Case sensitivity is platform-specific; two distinct quoted SQL identifiers can differ only in case, while another source may fold names by design. Adopt per-connector comparison rules grounded in the source specification, and record the original spelling alongside any normalized lookup representation.

Internal Catalog IDs and Minting Authority

Every catalog entity should have a single recognized minting authority. A catalog database might generate an opaque UUID on first accepted registration, then use that ID in ownership records, glossary assignments, classification results, lineage edges, saved searches, and lifecycle events. A public API may expose a stable URI incorporating the ID, while retaining a display name that can change independently. Reusing an ID for a new resource after retirement must be prohibited.

The ID's lifecycle also matters. Suppose an ingestion connector reports a previously unknown table. The identity service should first look up a trusted native identifier in a registered namespace, then a verified alias or migration mapping, and only then mint a new internal ID. If the connector lacks reliable evidence, it should create a provisional candidate or queue a steward review rather than merge on title similarity alone. An ID without provenance is not evidence that an entity match is correct.

Opaque IDs reduce accidental semantic coupling. An identifier of the form finance.prod.payment_summary looks useful but embeds assumptions that can become obsolete. If it must change to reflect a rename, all downstream references may break; if it does not change, readers may mistake its now-obsolete segments for facts. Prefer a non-semantic canonical ID plus a mutable qualified locator.

Source-Native IDs: Strong Evidence, Not Universal Truth

Many systems expose object IDs, GUIDs, resource ARNs, UUIDs, or other native identifiers. Such IDs can be excellent evidence of continuity through a rename, but their scopes and reuse policies vary. A database's internal object number may persist through an ALTER ... RENAME yet change after a drop-and-create. Another platform might preserve an external identifier during export/import, while a clone operation creates a new identifier with identical content. Connector documentation must state the exact native field and what its lifecycle guarantees.

Record the issuer, issuing namespace, observed value, observation time, and identifier semantics. If an ID is only unique within an account or source deployment, retain those qualifiers. If the upstream service reuses IDs or rotates them, document its generation or epoch. A native ID observed once should not forever overrule contradictory evidence about object replacement. Reconciliation should be able to mark evidence as disputed and preserve both the prior and proposed mappings for audit.

A native ID may also be absent. Text files in a directory and externally described datasets sometimes offer only paths, names, or publisher assertions. In those cases, confidence should be lower: provide policy rules for detecting likely continuity, keep historical observations, and do not manufacture an “immutable source ID” by simply hashing a changeable path.

Canonical URLs, IRIs, URNs, and Catalog Routes

A catalog canonical URL tells a browser or client where the record is published. A persistent identifier denotes the entity under an issuer's identity policy. A W3C-style IRI may play both roles when deliberately governed, and a DataHub URN may provide an application-specific identity mechanism, but neither interpretation can be inferred from syntax alone. Redirects support navigation; they do not prove that the endpoint still represents the same asset.

In federated discovery, W3C DCAT 3 distinguishes dataset resources, distributions, and identifier properties, including dcterms:identifier and adms:identifier. A dataset's metadata can include several externally issued identifiers without treating them as interchangeable. Organizations should define when catalog IRIs remain stable across updates and when a version, distribution, or new dataset resource requires a distinct identifier.

An implementation can publish https://catalog.example.edu/assets/asset-0142 as a stable landing page and redirect a former human-readable route such as /datasets/enrollment-2024 to that page when the historical alias is unambiguous. If a path is later reused for a new asset, the old route requires a collision-aware policy—not a blind permanent redirect.

A University Catalog: Baseline Identity Record

Consider an imaginary university that registers a production enrollment table. The catalog assigns asset-0142. The source exposes a native object identifier 88301 scoped to registered instance wh-prod-01. Its current locator is prod.analytics.enrollment, and its display label is Enrollment Records. These are illustrative identifiers, not a live university inventory or a vendor-specific API schema.

The record intentionally separates the authoritative catalog key from locator and display label. The field identity_policy documents the university's chosen assertion of continuity for this source; a production policy should additionally record generation/recreation events and the evidence available from the connector. The illustrative prod.analytics.enrollment shorthand omits the database name and therefore must never be confused with the complete structured locator above.

A Rename: Continuity Without Reassignment

Suppose the DBA renames academic.analytics.enrollment to academic.analytics.student_enrollment, and the source reports that object ID 88301 remains attached to the table. Under the adopted source policy, the catalog keeps asset-0142, updates its current locator, and adds a historical locator entry with a validity interval. Lineage records that point to asset-0142 remain associated with the original entity. Its human-facing label can remain Enrollment Records if that still fits business meaning.

Before After Catalog action
Internal ID asset-0142 asset-0142 Preserve
Source-native ID 88301 88301 Verify scope and continuity
Physical table enrollment student_enrollment Update current locator
Display name Enrollment Records Enrollment Records No forced change
Old qualified locator Historical alias Retain dates and evidence

The rename must not be inferred solely from timestamps or similar column definitions. Two tables can have identical schemas; a batch migration can create a replacement while deleting the prior table. Event records, source-native IDs, steward-approved migration manifests, or other verifiable evidence should determine whether the catalog preserves identity. If evidence is incomplete, the safe state is unresolved, not a fabricated rename event.

Drop-and-Create Under the Same Name

Now suppose the original table is dropped and an unrelated replacement is created under the old name academic.analytics.enrollment. Its new source-native ID is 99107. The old name being available again does not authorize the catalog to assign asset-0142 to the replacement. That would silently transfer the old table's lineage, owner assertions, quality results, and governance history to a different resource. The correct default for a physical-asset catalog is to mint a new asset ID and connect the records with explicit, evidence-backed relationships if appropriate.

This is the classic name-reuse collision. A simple key-value registry from qualified_name to asset_id will misresolve historical references if the name is recycled. Resolve historical aliases by effective time, source generation, and asset state; refuse an ambiguous lookup when context is missing. Never rewrite old lineage to point at the new entity solely because a string has become current again.

Some products may model a continuing logical data product above both physical tables. In that case, the product retains its own catalog ID while the constituent physical table IDs differ. State this as an explicit hierarchy, not as an excuse to merge the underlying assets.

Moving an Asset Between Schemas, Accounts, or Environments

A move may mean different things: a supported in-place schema transfer, a rename that changes a fully qualified path, a cross-region physical copy, a rebuilt replacement, or an organizational reclassification. Identity treatment must follow the actual change mechanism and catalog granularity. If the source offers a reliable native ID preserved by an in-place transfer, a single physical-asset record may retain continuity. If moving across accounts creates a distinct object ID, the physical asset normally changes even if a business-level dataset remains logically continuous.

The unit index asks for a record that can survive an authorized move to another environment. An implementation can satisfy that requirement by defining an explicit logical asset (for example, product-027) that is linked to environment-specific physical resources, or by applying a documented relocation policy with signed migration evidence. The operation should never erase the original environment and assume the new resource is literally the same underlying physical object.

When a source locator changes, preserve prior locators with valid_from/valid_to and observed_at fields. Distinguish effective time in the source from observation time at the catalog. A connector running one day late might learn about a move after downstream jobs have already recorded events under the new location.

Aliases as Governed Historical References

An alias is an alternative reference that may resolve to an asset under specific conditions. Aliases include former source names, published catalog slugs, business nicknames, prior workspace paths, and identifiers from predecessor systems. They must carry their issuer, namespace, reference type, target, effective interval, verification status, and evidence. Without those attributes, an alias table becomes a permanent source of false matches.

Aliases are not necessarily unique for all time. One name may refer to one table in 2025 and another in 2026. Lookup requests therefore need time context or should return a set of candidates plus a collision warning. Alias records also need revocation, correction, and retirement; otherwise a stale alias can lead an administrator or analyst to an unrelated successor.

Alias state Meaning Expected resolver behavior
Current and unique Alternative accepted name for active asset Resolve with provenance
Former, historically unique Previously valid name with ended interval Resolve for historical query; warn for current navigation
Superseded Replaced by verified reference Show successor relationship, not silent identity merge
Ambiguous Several possible targets Return candidates or request context
Revoked Incorrect, compromised, or misissued alias Do not use for automatic resolution
Unverified Similarity match without authoritative evidence Keep as candidate only

Namespace Registry and Ownership of the Naming Contract

An organization should maintain a namespace registry that defines the source instances from which identities originate. Each registration needs a durable namespace key, authority or owner, source platform, tenancy boundary, allowed resource types, native-ID scope, comparison and escaping rules, connector coverage, and a documented identity lifecycle. A connection name typed by an analyst is insufficient: two connectors may point to the same origin, or one connector name may be repurposed to a different source during deployment.

Use a stable source instance ID for the external authority, and keep connector configuration IDs separately. Replacing one ingestion agent with another should not create an entire duplicate catalog if both connect to the same source. Conversely, cloning a production database into testing must not cause its test tables to overwrite production assets simply because identical native names were replicated. The registry needs a deliberate account/environment mapping, not an accidental mapping inherited from a deployment file.

A namespace contract might specify that database and schema identifiers are compared exactly as returned by a particular engine; that field names can be quoted; that a source object ID is unique only within an account and resource generation; and that old aliases are retired when names are reused. Changes to this contract deserve the same scrutiny as changes to a data contract because they can invalidate entity matching at scale.

Canonicalization Without Inventing Collisions

A catalog frequently needs to compare locator strings, but canonicalization is not synonymization. Trimming characters, lowercasing names, removing punctuation, URL-decoding twice, or replacing Unicode lookalikes can collapse two distinct source resources into a single key. The comparison policy must be derived from the upstream system. For example, a case-insensitive source may treat Sales and sales as the same name; a case-sensitive source may not. Use the connector's verified semantics to normalize, and preserve exact source values as observed.

Preferred representation is a typed tuple: (tenant_id, source_instance_id, asset_kind, source_native_id, generation) when a strong native identifier exists. If only a locator is available, represent its components as an ordered, typed data structure rather than an ambiguous dotted string. Serialize with a deterministic encoding for storage or lookups; do not treat a cryptographic hash of the tuple as proof of physical continuity if the tuple is itself changeable.

Transformation Potential benefit Identity risk
Lowercase all database names Simplifies lookups on some platforms Merges names on case-sensitive sources
Drop account/instance component Shorter keys Cross-tenant collision
Strip schema name Easier display Same table name in multiple schemas
Normalize Unicode universally Avoids cosmetic variation May collapse distinct source keys
Hash current locator Convenient fixed-size lookup key Hash changes on move; no continuity evidence
Encode typed components losslessly Reproducible lookup representation Safe only if source semantics and scopes are correct

Platform Identity Models: OpenMetadata, DataHub, and OpenLineage

Several major systems demonstrate why identity should be described in terms of specific contracts, not the vague phrase “the metadata identifier.” OpenMetadata models many relational resources using a fully qualified name (FQN) constructed from source-service and containment names, such as service.database.schema.table, and also exposes entity IDs. A table's FQN and entity ID are different fields with different operational uses; the exact behavior of a rename depends on its implementation and supported API version. Consult the OpenMetadata table entity specification rather than assuming all connectors treat renames identically.

DataHub uses URNs to identify metadata entities, including datasets whose identifiers incorporate data platform, platform-specific name, and environment/origin. A platform-instance configuration can be important where several source instances publish the same names. DataHub's platform instance documentation addresses collision risks arising from source-instance scoping. Do not assume that copying a URN between installations guarantees that both installations mean the same underlying resource.

OpenLineage identifies a dataset by the pair (namespace, name), with platform-oriented naming conventions. Its dataset identity is designed for interoperable lineage events; it does not automatically become an institution's permanent internal catalog ID. The OpenLineage object model and naming conventions should guide specific integrations. Version and connector support matter because producers may emit inconsistent names.

System Illustrative identity mechanism Design consideration
OpenMetadata Entity ID and FQN Physical naming hierarchy can evolve
DataHub Dataset URN, platform/instance/origin context Missing instance scope may collide
OpenLineage Dataset (namespace, name) Different emitters must agree on naming
W3C DCAT 3 Dataset IRI and stated identifier properties Publisher's persistence and version policy governs
Institutional catalog Opaque internal ID with external mappings Reconciliation policy determines continuity

Identity Across Catalog Federation

Federation connects metadata from multiple institutions, platforms, or catalogs without transferring control of the original resource. When importing assets, do not rewrite all upstream IDs as if the local system minted them. Retain issuer-qualified external identifiers with observed timestamps, source URLs, and trust decisions. The local catalog can still assign its own canonical ID, but must distinguish sameAs-style identity assertions, related datasets, replicas, distributions, and merely similar descriptions.

Two catalogs might describe the same published dataset using different landing pages; this is a reconciliation candidate, not a guaranteed merge. Conversely, one DOI or stable publisher ID may be referenced by several distinct distributions: CSV, Parquet, or a maintained API. DCAT explicitly models datasets and distributions as different resources, and a single distribution change should not automatically imply a new dataset identity. Likewise, a new dataset edition may be an explicit version rather than a silent update to the prior edition.

Cross-catalog identity requires evidence levels. A publisher-controlled assertion is typically stronger than matching titles or descriptions. If two providers disagree on identity, preserve the disagreement in the metadata rather than forcing a graph merge that cannot later be explained.

The Identity Resolution Decision Tree

An ingestion or integration pipeline needs a deterministic decision process with an explicit unresolved outcome. Suggested order: (1) authenticate and register the source namespace; (2) parse its resource type and source-native identity according to the connector contract; (3) look for an existing scoped native-ID mapping and validate generation/continuity; (4) examine trustworthy rename or migration evidence; (5) consult qualified historical aliases with times; (6) flag conflicting matches; (7) mint a new catalog identity only when no existing identity is justified; and (8) record the evidence and decision.

Observation Possible result Required safeguard
Same native ID, same authorized source, unchanged generation Continue existing asset Confirm source ID is stable across relevant lifecycle
Same native ID, new qualified name, verified rename Update locator Record old locator and event
Same qualified name, different native ID New asset or explicit replacement Do not inherit old lineage automatically
Different source instance, same name Separate asset Preserve tenant/account scope
Connector changed, origin unchanged Continue asset Verify stable source-instance mapping
Asset absent from one scan Unknown/stale state Distinguish incomplete scan from deletion
Conflicting identities after import Review-required No automatic merge or silent overwrite

In a production system, confidence may be formalized as verified, asserted, inferred, unresolved, and rejected. If an inferred match can change security-sensitive metadata or lineage, require additional evidence or human approval. Reconciliation is a governance operation, not just a string-matching function.

Worked Python Model: Scoped Identity Keys

The following Python 3 example keeps a trusted native identity separate from a mutable source locator. The lookup_key is a lookup encoding, not a universal opaque ID and not a proof that the source will never reuse the supplied native ID. A real connector must supply and validate the native-ID scope and generation semantics before creating keys.

from dataclasses import dataclass
import json

@dataclass(frozen=True)
class SourceIdentity:
    tenant: str
    instance: str
    kind: str
    native_id: str
    generation: str

    def lookup_key(self) -> str:
        fields = [self.tenant, self.instance, self.kind,
                  self.native_id, self.generation]
        if any(not value for value in fields):
            raise ValueError("identity fields must be nonempty")
        return json.dumps(fields, ensure_ascii=False, separators=(",", ":"))

a = SourceIdentity("university", "wh-prod-01", "table", "88301", "g1")
b = SourceIdentity("university", "wh-test-01", "table", "88301", "g1")
assert a.lookup_key() != b.lookup_key()
assert a.lookup_key() == a.lookup_key()
print(a.lookup_key())

The JSON array avoids the ambiguity of concatenating components with punctuation such as : or .. The generation field is a modeled lifecycle discriminator, not an assertion that every warehouse exposes a generation number. When the source lacks it, the connector must adopt another documented continuity policy; inventing the value g1 does not solve object reuse.

Worked Python Model: Rename, Replacement, and Alias History

This small demonstration models the distinction between a confirmed rename and name reuse. It deliberately uses fixed test IDs so the results are reproducible. The rename method requires the caller to present continuity evidence; the example does not pretend that a simple string comparison supplies that evidence.

from dataclasses import dataclass, field

@dataclass
class Asset:
    asset_id: str
    native_id: str
    locator: str
    aliases: list[str] = field(default_factory=list)

    def rename(self, new_locator: str, *, verified: bool):
        if not verified:
            raise ValueError("rename requires source-backed evidence")
        if new_locator != self.locator:
            self.aliases.append(self.locator)
            self.locator = new_locator

old = Asset("asset-0142", "88301", "academic.analytics.enrollment")
old.rename("academic.analytics.student_enrollment", verified=True)
replacement = Asset("asset-0288", "99107", "academic.analytics.enrollment")

assert old.asset_id == "asset-0142"
assert old.locator == "academic.analytics.student_enrollment"
assert "academic.analytics.enrollment" in old.aliases
assert replacement.asset_id != old.asset_id
assert replacement.locator in old.aliases  # historical name collision
print("name reused; physical asset identities remain distinct")

This is a teaching model: a production alias store needs namespace, effective dates, evidence, conflict handling, and access controls. Most importantly, the fact that the replacement's current locator matches the old alias is not grounds to reassign the old ID or create an unconditional redirect.

Historical Alias Resolution with Time Context

Suppose an audit asks what academic.analytics.enrollment meant on March 1, 2026, while a current dashboard asks which asset occupies that name today. These are distinct queries. A history-aware resolver can represent each claim as (namespace, alias_value, valid_from, valid_to, target_asset_id, evidence_id). For a query with a date, return only entries valid at that time. Without a date, return a current entry if exactly one is authoritative and clearly distinguish old matches as historical.

Half-open intervals are useful: [valid_from, valid_to) means the start date is included and the end date excluded. Date precision and time zone must be documented; ambiguous timestamp comparisons can create artificial overlap or a gap at migration. An alias issued by one system must not automatically be interpreted in another source namespace, and a revoked alias should not be used for normal resolution even if its old interval matched historically—except in privileged audit contexts that explicitly need to see revoked claims.

A key control is a database constraint or application check preventing overlapping active alias claims for different assets in the same scope, unless the namespace's semantics genuinely permit such ambiguity. Historical claims may overlap because of inconsistent evidence; record and surface this anomaly instead of silently choosing the newest row.

Source Changes, Reconciliation Events, and Idempotency

Connectors often report the same observation repeatedly. An ingestion endpoint should be idempotent: receiving the same source record and event identifier twice should not mint two assets or duplicate a rename history. Model a source observation ID or deduplication key separately from the catalog asset ID. Event ordering also matters. A delayed rename event should not reverse a more recent source locator simply because it arrives later in wall-clock time.

Store observed_at, upstream effective_at where trustworthy, connector run ID, authoritative source namespace, and the fields actually observed. Reconciliation may use monotonic event sequences or version counters when supplied by the source. If ordering is uncertain, mark the record as needing review rather than applying the latest-arriving locator unconditionally. Exact-once event delivery is not guaranteed by all integrations; correctness depends on replay safety and historical traceability.

The relationship between identity and freshness should remain explicit. A connector that last saw a table 48 hours ago has stale observational evidence, not proof the table has ceased to exist. That topic is developed further in Catalog Monitoring and Freshness.

Temporary Unavailability, Deletion, and Tombstones

An asset may disappear from a scan because of a permission change, network outage, selective connector scope, pagination failure, or an actual deletion. These causes imply different catalog responses. A robust system records the observation as missing from covered scan, not observed, unreachable, or confirmed deleted according to evidence. Do not equate a skipped asset with a deleted asset and then reuse its ID on the next ingestion cycle.

A tombstone is a retained identity record for a confirmed retired or deleted entity. It can preserve the historical catalog ID, former locators, relevant lineage, and reason for retirement without exposing restricted source data. Tombstones prevent dangling references from being redirected to new resources occupying an old name. They also support audit and reproducibility when a research report cites a dataset that is no longer available.

Retention duration must follow organizational policies, lawful deletion requirements, confidentiality rules, and source contractual conditions. Retaining an ID and minimal history does not always justify retaining sensitive descriptions, row-level samples, or credentials. Tombstone access should respect the same governance principles as live catalog assets.

Duplicates, Replicas, Clones, and Versions

Two physical resources can hold identical data without being one asset. A read replica, an independently refreshed warehouse copy, a development clone, and a distribution in a different file format may be distinct physical entities. Catalog relationships can say replica_of, derived_from, same_logical_product, distribution_of, or replaces, but such relationships should not be flattened into identity equivalence without policy support.

Similarly, a dataset revision and an individual object-storage version may deserve distinct identities if downstream reproducibility requires citation of exact bytes. A logical dataset ID may remain constant while its published versions have different version IDs. The decision depends on the level of abstraction the catalog is intended to capture; the key is consistency. A lineage graph should not treat one physical table's historical version as the present-day table unless the event explicitly denotes that version.

An asset that moves from one system to another can be represented by a stable logical dataset node linked to old and new physical nodes, allowing analysts to trace continuity without claiming a warehouse copy is the original physical resource.

Identity for Tables and Database Objects

Relational databases offer rich naming contexts but also differing object-ID behavior. A robust catalog distinguishes servers/accounts, databases, schemas, object kinds, and source-native object IDs when supplied. Views and materialized views may have independent identities from their backing tables. A column locator requires additional context: table identity plus column ID or exact column path, depending on source support. Field renames can be especially difficult when the source does not issue stable field identifiers.

Quoting and case behavior are not universal. The catalog should preserve source-returned identifiers exactly and use the database platform's documented comparison semantics for lookup. Do not casually split "finance.q4"."gross.total" on dots as if it were a four-part hierarchy. For SQL systems offering stable object IDs, verify what happens across schema transfer, rename, backup/restore, and drop-and-create; those operations may have different guarantees.

A cross-database view can depend on multiple sources. Its own identity is separate from the identities of the underlying tables. Mapping their relationships belongs to Data Lineage Modeling, while this article establishes the stable endpoints that make those edges meaningful.

Identity for Streams, APIs, and Event Resources

A stream name may only be unique in a cluster or tenant. The same topic name can exist in two clusters, and a topic deleted and recreated under the same name may represent a new resource with a different retention history and schema-contract context. Include cluster/namespace and provider-generated resource IDs when supported, and model partitions or versions separately if the catalog requires that level of detail. Producer and consumer jobs must use compatible source identity mappings if lineage is to converge.

An API route such as /students/{id} is not globally identifying: deployment, API version, service issuer, and operation identity can matter. The service may redesign its routing without altering the logical data service, or expose the same route for staging and production. Keep human-readable routes as locators and register durable operation IDs where available. For public APIs, published OpenAPI operationId values are useful only within the documented API scope; they are not inherently globally unique or immutable.

Streaming identities often interact with schema registries and data contracts, but a schema ID, topic ID, and business product ID are distinct. Treating them as one identifier produces brittle lineage and mistaken access-control inheritance.

Identity for Files, Object Stores, and Data Products

File paths are frequently mutable or reused. A move from reports/2025/ to archive/2025/ might be a filesystem rename, an object-store copy-and-delete, or a new export generated from the same query. These are not equivalent events. Object storage may provide version IDs, etags, generation IDs, or provider-specific object identifiers, but their meanings differ. A content hash identifies content under a chosen algorithm; it does not by itself identify ownership, source history, or logical asset continuity.

A catalog describing a CSV distribution should distinguish it from the dataset it represents. The dataset may survive changes from CSV to Parquet, while each published file or distribution has its own identity and access path. DCAT offers a useful vocabulary for dataset/distribution modeling, while an institutional product registry can define business-level asset IDs for governed data products.

File-oriented catalogs should avoid treating absolute Windows or POSIX paths as universal identifiers. Paths can be remounted, renamed, symlinked, case-folded, or mapped differently for different users. The File Systems unit covers path mechanics; this article addresses their interpretation as catalog locators.

Identity for Dashboards, Metrics, and Registered External Resources

A dashboard commonly has an ID issued by its BI platform and workspace. Its visible title may change, and a copy into a different workspace may receive a new platform ID. If the institution wants a stable report product identity across those deployments, model it as a higher-level governed asset linked to workspace-specific dashboards. Do not assume a dashboard URL alone is immutable: dashboards can be republished or access-scoped, and URLs may incorporate workspace routes rather than a globally stable asset key.

Metrics need extra care because two assets with the name Retention Rate may calculate different populations or time windows. A metrics catalog can issue a durable definition ID and version its calculation, while separating the identity of the metric definition from physical columns that store computed values. Display-name equality does not establish semantic equivalence.

Externally registered resources may use DOI, publisher dataset identifier, IRI, or another issuer-controlled reference. Record both issuer and claim; support multiple identifiers without forcing equivalence. These are especially useful in cross-institutional research catalogs where an internally generated ID must coexist with a published citation identifier.

Relational Registry Design and Uniqueness Constraints

A catalog backing store should enforce key invariants rather than rely entirely on an ingestion script. The following SQLite schema is an illustrative identity registry, not a complete production metadata model. Its native mapping key includes tenant, source instance, asset type, native ID and modeled generation. It intentionally keeps current locators and historical aliases in separate tables; a source name that is reused should not overwrite an earlier entity's ID.

PRAGMA foreign_keys = ON;
CREATE TABLE asset (
    asset_id TEXT PRIMARY KEY,
    kind TEXT NOT NULL,
    lifecycle TEXT NOT NULL CHECK (lifecycle IN ('active','retired'))
);
CREATE TABLE native_mapping (
    tenant TEXT NOT NULL,
    instance TEXT NOT NULL,
    kind TEXT NOT NULL,
    native_id TEXT NOT NULL,
    generation TEXT NOT NULL,
    asset_id TEXT NOT NULL REFERENCES asset(asset_id),
    PRIMARY KEY (tenant, instance, kind, native_id, generation)
);
CREATE TABLE alias_history (
    tenant TEXT NOT NULL,
    instance TEXT NOT NULL,
    alias_value TEXT NOT NULL,
    valid_from TEXT NOT NULL,
    valid_to TEXT,
    asset_id TEXT NOT NULL REFERENCES asset(asset_id),
    evidence_id TEXT NOT NULL,
    CHECK (valid_to IS NULL OR valid_to > valid_from)
);
CREATE INDEX alias_lookup ON alias_history
    (tenant, instance, alias_value, valid_from, valid_to);

This schema does not yet prevent overlapping time intervals, demonstrate temporal timezone discipline, handle concurrent registration transactions, or authorize cross-tenant access. Those checks require application logic, more sophisticated database constraints, or transaction-level locking. A production identity service should also enforce that mapping rows cannot be transferred to a different asset_id without an approved correction workflow, and should preserve the correction audit trail.

Executable SQLite Case Study: Rename and Name Reuse

The next self-contained Python 3 example exercises the SQL model in memory. It demonstrates that the old asset remains asset-0142, a replacement receives asset-0288, and the same textual source name can appear in different periods without causing an identity merge. The test is local and uses only the Python standard library.

import sqlite3

connection = sqlite3.connect(":memory:")
connection.execute("PRAGMA foreign_keys = ON")
connection.executescript("""
CREATE TABLE asset (id TEXT PRIMARY KEY, native_id TEXT NOT NULL);
CREATE TABLE alias (name TEXT NOT NULL, start TEXT NOT NULL,
                    end TEXT, asset_id TEXT NOT NULL REFERENCES asset(id));
""")
connection.executemany("INSERT INTO asset VALUES (?,?)", [
    ("asset-0142", "88301"), ("asset-0288", "99107")])
connection.executemany("INSERT INTO alias VALUES (?,?,?,?)", [
    ("enrollment", "2025-01-01", "2026-05-01", "asset-0142"),
    ("student_enrollment", "2026-05-01", None, "asset-0142"),
    ("enrollment", "2026-09-01", None, "asset-0288")])

def resolve(name, date):
    rows = connection.execute("""
        SELECT asset_id FROM alias WHERE name = ? AND start <= ?
          AND (end IS NULL OR ? < end)
    """, (name, date, date)).fetchall()
    return [row[0] for row in rows]

assert resolve("enrollment", "2026-03-01") == ["asset-0142"]
assert resolve("enrollment", "2026-07-01") == []
assert resolve("enrollment", "2026-11-01") == ["asset-0288"]
assert resolve("student_enrollment", "2026-11-01") == ["asset-0142"]
print("historical and current identities remain separate")
connection.close()

For real event timestamps, use a consistent timestamp format or native temporal type and define effective-time precision explicitly. The script uses date strings only because the fictional migration events occur on distinct days; it is not a recommendation to use naïve dates for high-frequency catalog changes.

Windows PowerShell 5.1: Inspecting a Catalog Identity File

Windows PowerShell 5.1 can inspect a portable JSON identity manifest using ConvertFrom-Json. The demonstration below keeps the internal ID and current locator as separate properties and checks for a stale alias collision. It assumes the script's text is saved correctly as a PowerShell file in the relevant environment; non-ASCII script encoding behavior is version-sensitive in Windows PowerShell 5.1.

# Compatible with Windows PowerShell 5.1; demonstrative only.
$json = @'
{
  "asset_id": "asset-0142",
  "source_instance_id": "wh-prod-01",
  "source_native_id": "88301",
  "current_locator": "academic.analytics.student_enrollment",
  "former_locators": ["academic.analytics.enrollment"]
}
'@
$asset = $json | ConvertFrom-Json
if ([string]::IsNullOrWhiteSpace($asset.asset_id)) {
    throw 'Catalog asset ID is missing.'
}
Write-Output ("ID: " + $asset.asset_id)
Write-Output ("Current: " + $asset.current_locator)
foreach ($name in $asset.former_locators) {
    Write-Output ("Historical alias (not automatically current): " + $name)
}

This script is not an entity resolver and does not grant access to a database. An operational PowerShell workflow should retrieve manifests from an authenticated catalog API, validate signatures or trusted transport where appropriate, and avoid printing credentials or sensitive metadata. Do not use the presence of a catalog entry to conclude the current operator can query the source.

Identity and Lineage Graph Integrity

Lineage edges need durable endpoints. A relationship asset-0142 → asset-0205 should not silently change meaning because a former name becomes current for a different table. Graph nodes should normally reference internal asset IDs, while external lineage systems' namespace/name pairs are resolved through a mapping layer. The mapping itself needs validity intervals, source provenance, and reconciliation status. A wrong mapping can make a lineage graph look internally connected while attributing influence to the wrong dataset.

When importing OpenLineage events, an institution should agree on naming policy for the same source across Spark, Airflow, dbt, or other emitters. Distinct namespace strings might describe one resource; identical strings might be reused across clusters if emitters are misconfigured. A reconciliation gateway can retain raw observed keys alongside the resolved internal asset ID and its evidence. Avoid rewriting original events without preserving their source form.

This article establishes the identity contract for graph endpoints. Data Lineage Modeling, OpenLineage Integration, and Provenance with W3C PROV cover lineage semantics and evidence in greater depth.

Identity Is Not Authorization or Data Entitlement

A catalog may list an asset so employees can discover that it exists without permitting them to read its underlying data. A stable asset ID, source locator, dashboard link, or valid alias is not a bearer token, entitlement, or authorization decision. Authentication identifies the requesting principal; authorization determines whether that principal may view metadata, request access, or retrieve source data. The source system's current access controls remain authoritative unless a formally integrated policy system says otherwise.

This separation becomes important after renames. An old alias that resolves to a new asset must not implicitly transfer approvals granted for the prior asset; access decisions should be scoped to authorized resource identities and evaluated under current policy. A catalog may also suppress search results, descriptions, or paths that themselves reveal sensitive information. Publishing the existence and physical locator of a protected dataset can create a disclosure even without showing any rows.

A public catalog landing URL should not contain service credentials or signed object-store links with long-lived secrets. Detailed access-request approvals and access logging belong primarily to Data Access Request Workflows and Metadata Catalog Security.

Operational Quality Metrics for Identity Resolution

A catalog can measure whether identity resolution is reliable without claiming that a high record count proves coverage. Track the percentage of active assets with validated source-instance mapping; native-ID coverage by connector; conflicting current locator claims; suspected duplicate clusters; unresolved rename candidates; orphaned lineage endpoints; stale aliases; and time from observed change to approved identity update. Report denominators and collection scope, since a connector inventory that omits entire systems may look perfect by narrow internal metrics.

Metric Illustrative definition What it cannot establish alone
Source mapping coverage Verified mapped assets / assets in scanned scope Completeness beyond scanned scope
Alias conflict rate Conflicting active alias groups / tested alias groups All past historical collisions
Duplicate candidate count Unresolved possible-duplicate pairs Confirmed duplicates
Rename resolution latency Decision time − first reliable observation Whether the decision was correct
Orphaned lineage edges Edges with unresolved endpoint IDs / total inspected edges Accuracy of resolved edges
Native-ID availability Assets with usable scoped native ID / covered assets Stability of vendor-issued IDs

Quality reviews should sample identity decisions against direct source evidence and check whether an incident could have cross-linked two tenants or misrouted permissions. Counts are diagnostic aids, not substitutes for a documented continuity policy or independent verification.

Review Workflow for an Identity Dispute

When records conflict, preserve the source observations and open a review item rather than silently changing a primary key. A useful review contains both candidate catalog IDs, complete namespaces, native identifiers, source generation facts, earliest and latest observation times, current and former locators, and associated lineage or access-policy risks. The reviewer should be able to distinguish two kinds of request: merge these duplicates versus declare these related but distinct assets.

A responsible resolution process identifies a decision owner, obtains sufficient upstream evidence, records the decision and its rationale, applies changes transactionally, and publishes any required mapping updates. If a merge is approved, preserve a redirect or equivalence record from the retired duplicate without discarding its original history. If a mistaken merge must be reversed, recovery should be supported through an append-only decision log and original source claims.

A steward's approval is an accountable governance statement, but it should not substitute for physical evidence when that evidence is available. The goal is a traceable, reversible decision rather than an appearance of perfect automated certainty.

Migration Playbook: From Name-Based to Durable Asset IDs

Organizations often start with catalog rows keyed by database.schema.table and then discover that renames break links. A safe migration begins by inventorying current names and the original systems that produced them. Register source instances, native-ID scopes, and comparison rules before minting replacement IDs. Next, assign durable catalog IDs, build a source-mapping crosswalk, and record all existing lineage, glossary, access-request, and dashboard references that currently use name strings.

Introduce a read-only reconciliation period where both old names and new IDs can be resolved, but flag conflicts rather than rewriting them automatically. Validate a representative set of rename, replacement, cross-account, cloned-resource, and same-name-different-type cases. Then change downstream contracts to use durable IDs; preserve historical aliases with validity periods. Monitor duplicate creation, ambiguous aliases, failed mappings, and lineage breakage during the rollout. Finally, deprecate name-only lookups where they could cause unsafe cross-resource resolutions.

Rollback planning is mandatory: store the old-to-new crosswalk, preserve original raw source identifiers, and make transformations repeatable. A migration that changes every lineage edge while discarding the original endpoints cannot be audited effectively if its assumptions later prove false.

Practical Exercises and Study Questions

  1. Namespace collision: Two independent production warehouse accounts each contain academic.analytics.enrollment. Write the fields needed to distinguish them without relying on a display title.
  2. Rename continuity: A table changes from enrollment to student_enrollment, and the documented source object ID stays the same. Describe the internal ID, locator, and alias updates.
  3. Name reuse: A table is dropped; a new table appears at the old path with a new native ID. Explain why the new table should not inherit the former physical asset's ID.
  4. Connector replacement: A new ingestion connector scans the same production source. Explain how a source-instance registry avoids duplicating all records.
  5. Environment move: A dataset is copied from production to staging. Compare modeling it as one logical product with two physical assets against retaining one physical identity.
  6. Temporal lookup: An old alias was valid January through April, but a successor used the same name from September onward. Determine what to return for a query dated in June.
  7. External catalog: A publisher supplies a DOI, two distribution URLs, and a title. Identify which resources or references can change independently.
  8. Access control: A user knows the catalog ID and qualified source path of a restricted table. Explain why that knowledge does not constitute access authorization.
  9. Code exercise: Extend the SQLite example to reject overlapping current alias intervals and record the evidence for each accepted rename.
  10. Evidence review: A name-based catalog claims two tables are identical because their schemas match. Identify at least three stronger sources of identity evidence.

Answer framework: distinguish the level being identified; establish the qualified source scope; inspect native identifiers and event evidence; choose continuity, replacement, relationship, or unresolved status; preserve history; and enforce access independently. In Exercise 6, a query for June returns no valid alias under the stated intervals, not either asset by guesswork. Exercises 3 and 5 require explicit differentiation between physical continuity and logical product succession.

Glossary of Key Terms

Alias: Alternative reference to an asset, ideally scoped, time-bound, and evidence-backed. Asset identity: Governed assertion that catalog references denote a particular resource. Asset locator: Current information needed to find or address a resource in its source. Catalog ID: Internal identifier minted under the catalog's namespace authority. Collision: Situation where distinct resources resolve to the same key or alias. Continuity: Evidence-backed determination that a resource remains the same asset across a change. Distribution: Concrete accessible form or representation of a dataset, distinct from the dataset concept in DCAT modeling.

Effective time: Time a claim was true in the upstream domain. Entity resolution: Process of mapping observations and external references to governed catalog identities. Fully qualified name (FQN): Source- or platform-defined name including sufficient parent contexts to identify an entity within its naming rules. Generation: Lifecycle discriminator used where an identifier or path may be recycled. Issuer: Authority assigning an identifier. Lineage endpoint: Data asset node referenced by a lineage relationship. Logical asset: Governed conceptual dataset or product that may have multiple physical realizations.

Namespace: Naming context defining a scope of uniqueness. Native ID: Identifier supplied by the source platform. Opaque identifier: Identifier intentionally lacking encoded business or locator semantics. Physical asset: Concrete resource such as a particular database table or object-store file. Provenance: Evidence about the source and history of a claim. Qualified locator: Locator including the relevant platform and containment context. Reconciliation: Process of aligning observations with existing records while managing uncertainty. Replacement: Distinct successor resource linked to a predecessor without pretending they are identical. Tombstone: Retained record identifying an asset that has been retired or deleted. URN: Uniform Resource Name, with semantics governed by its namespace and issuing system. Validity interval: Period during which an alias or locator claim applied.
