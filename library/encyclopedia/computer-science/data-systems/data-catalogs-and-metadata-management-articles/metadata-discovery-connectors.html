Definition, Scope, and Governing Principle

A metadata discovery connector is a governed adapter that observes the structure and descriptive attributes of a registered information source and supplies those observations to a data catalog. It may enumerate database schemas and tables, retrieve API resource definitions, inspect message-topic configurations, list authorized files and object-store prefixes, or consume published metadata events. Its primary output is evidence about data assets, not a replicated copy of the underlying business records. The connector must be accountable for where it looked, what it was authorized to inspect, which observations it actually obtained, and what it could not establish.

Discovery differs from data ingestion. An analytics pipeline moves data for processing; a catalog connector normally gathers descriptors—names, source identifiers, column names and types, creation timestamps, source labels, data-set relationships, or available schema versions. Some products can also profile columns, inspect samples, or read query logs, but those are additional permissions and workflows, not automatic entitlements of metadata discovery. Even table names and comments may disclose sensitive information; metadata itself requires access control.

This specialist article follows the Data Catalogs and Metadata Management unit and its specialist directory. It extends Data Asset Identity and Namespaces and Metadata Schema Design. Broader workflow transformation and scheduling belong to Data Engineering; this article addresses the narrower contract of discovering and publishing trustworthy catalog metadata.

Governing principle: a connector's successful network request is not evidence of a complete inventory, a missing asset is not automatically deleted, and a machine-observed attribute must not silently replace a steward-approved statement.

Learning Outcomes and Review Questions

After completing this treatment, a reader should be able to design a source-registration record, choose discovery mechanisms by platform, configure least-privilege collection, traverse paginated inventories, retain progress checkpoints safely, distinguish complete and partial scans, reconcile durable identities across renames, and attach provenance to every imported claim. The reader should also be able to diagnose rate limiting, identify deleted versus unreachable objects, establish connector health, and construct a defensible publication gate for search indexing.

The controlling questions are operational rather than merely syntactic: What is the authorized source boundary? What qualifies as an asset in that boundary? Is the identifier durable across a rename? Are metadata results exhaustive or filtered? What happens if only page two of five fails? Does the connector know which fields a person curated? Can a privileged connector expose sensitive comments or sample rows? What evidence permits an asset to be marked missing or retired? A reliable design answers these questions before turning on destructive reconciliation.

Discovery as a Chain of Evidence

A typical process runs from source registration to collection, reconciliation, and catalog publication. Each stage changes the interpretation of evidence. The initial registration says the institution intended to inspect an approved source. The connection handshake shows the endpoint was reachable with certain credentials. Enumeration produces a list of objects visible to that principal. Schema extraction provides attributes of enumerated objects. Identity mapping asks whether each object corresponds to an existing catalog identity. Validation and normalization transform source-specific results into a typed record. Publication makes approved observations searchable.

A gap at any stage constrains the conclusion: if a connector authenticated but could not enumerate a schema, its status is not "inventory complete." If enumeration succeeded but a downstream search index failed, the catalog's stored metadata may be correct while discovery through search remains stale. Store distinct results for connection, enumeration, extraction, reconciliation, storage, and publication. Do not collapse every condition into one green or red job status.

Stage Evidence produced Failure that must remain visible
Register Approved source instance and allowed scope Unregistered tenant or environment
Connect Authentication and endpoint reachability Denial, expiry, TLS or routing failure
Enumerate Object list, cursor and scope coverage Page omitted, filter misapplied
Extract Typed attributes and source timestamps Unsupported type, forbidden field
Reconcile Matched native ID and catalog ID Collision or uncertain rename
Validate Contract acceptance and quarantine errors Invalid field or unknown vocabulary
Publish Catalog commit and index receipt Indexing lag, partial commit

Inventory Coverage Is Not Connection Health

Suppose a service account can list tables in the public schema but cannot see objects in the registrar's restricted schema. A connector might report an HTTP 200 response or a successful SQL query while observing only a fraction of the institutional estate. That observation is not necessarily a software failure: its permissions may be intentionally scoped. But the catalog must not equate the visible set with all source assets. Represent planned coverage, accessible coverage, enumerated coverage, and successfully extracted coverage separately.

Coverage needs a denominator. For a known three-schema scope, a run covering two of three schemas may report 2/3 registered schemas examined even if the unknown count of tables prevents a sound asset-level completeness percentage. For a page-based API, the denominator might be all pages indicated by the API, or it may be unknowable until traversal finishes. Use "unknown" rather than inventing 100%. Instrument source-side inventory estimates where available and record ACL exclusions explicitly. A catalog completeness metric must carry its own coverage assumptions.

Reference Architecture and Trust Boundaries

A production topology separates source connectors from catalog state, identity reconciliation, governance overlays, and search indexing. Connectors run with narrowly scoped source credentials and publish signed or authenticated envelopes to a trusted ingestion service. The ingestion service validates connector identity, timestamp, schema version, source instance, and allowed fields. It resolves assets using a durable identity registry, then appends field observations and run evidence. The catalog stores historical snapshots and human annotations independently, while an indexing process builds user-facing search documents from publishable claims.

A useful boundary is a staging area between extraction and publication. Stage raw metadata envelopes with short retention and sensitive-field redaction, not unlimited copies of data rows. Validation failures go to an access-controlled quarantine for repair. A publish transaction should either apply an internally consistent group of observations or record precisely which objects committed. Search is an eventually updated view rather than the primary evidence store; rebuilding it should not require source re-harvesting.

Source Registration Before Connector Execution

An organization cannot govern a connector whose target is only an opaque URL. A source registry should identify the legal or operating owner of the endpoint, the technical instance, environment, tenant or account, permitted namespaces, asset classes, authentication method, collection mode, and retention policy. It should separately record whether sampling, profiling, SQL text, user attribution, and lineage extraction have been approved. The distinction prevents a harmless-sounding "metadata" task from becoming unreviewed collection of operational details.

For example, register university-prod-postgres-01 as a stable source instance, allow registrar_public and finance_reporting, and explicitly deny hr_sensitive. Record the authorized principal, credential secret reference, approval date, connector release, and incident contact. Filter both client-side and source-side, but enforce security on the source itself; a filter inside the connector is not a substitute for database privileges. A new schema appearing outside the approved scope is a review event, not implicit permission to harvest it.

Registration control Approved example Consequence of omission
Source instance university-prod-postgres-01 Cross-environment name collisions
Allowed schemas Two named namespaces Unbounded collection or misleading coverage
Asset classes Tables and views Unsupported object types treated as failures
Excluded activities No row sampling or query text Unexpected data access and disclosure
Credential reference Vault-managed read-only principal Irreproducible, insecure authentication
Deletion posture Review-only until verified Accidental loss of catalog history

A Minimal Source-Connector Configuration Contract

The configuration should be declarative, version-controlled without storing plaintext secrets, and interpretable by both the scheduler and catalog control plane. It should say not only where to connect but how exhaustive the run is expected to be. The following is an illustrative policy document, not a vendor-specific production recipe:

connector_id: registrar-discovery-v1
source_instance: university-prod-postgres-01
source_kind: postgres
allowed_namespaces: [registrar_public, finance_reporting]
asset_kinds: [table, view]
discovery_mode: scheduled_full
minimum_success_scope: all_allowed_namespaces
credential_secret_ref: vault://catalog/registrar-readonly
collect_column_names: true
collect_data_samples: false
collect_query_text: false
run_timeout_seconds: 900
page_size_hint: 100
failure_policy: retain_last_verified_snapshot
missing_asset_policy: review_only

minimum_success_scope is a local governance rule: the connector must enumerate every approved namespace before it may label a run exhaustive. The page_size_hint is subject to the server's actual API contract. missing_asset_policy explicitly prohibits immediate deletion based on one scan. Operational implementations must validate the configuration and redact secret paths from low-trust logs when necessary.

Connector Families and Source-Specific Capabilities

A connector should adapt to a source's native inventory surface rather than force all systems into a SQL-table abstraction. Relational databases expose system catalogs and information-schema views; warehouses may provide extensive information schemas and service-specific governance APIs; object stores list keys and metadata but do not intrinsically know a file's business schema; streaming platforms expose topics, partitions and sometimes schema-registry subjects; REST APIs may expose resource registries or OpenAPI descriptions; business-intelligence systems expose datasets, semantic models and dashboards.

Source class Preferred discovery surface Typical metadata Principal limitation
Relational database information_schema, system catalog Tables, views, columns, constraints Visibility limited by role and engine
Cloud warehouse Information schema and governance API Schemas, relations, tags, locations API cost and privilege variation
Object store Authorized list/head APIs and manifests Objects, prefixes, format indicators Object layout does not prove business semantics
Stream broker Admin/metadata APIs and schema registry Topics, partitions, registered schemas Topic identity and subject names may differ
REST/SaaS Paginated resource list or export Entities, attributes, API descriptors Pagination and permission filters
BI/analytics Vendor inventory and lineage API Reports, measures, models, workspaces Personal/private assets may be hidden
File share Directory listing and read-only file metadata Paths, sizes, times, optional schemas Rename/move identity often weak

These surfaces can complement one another. Source-native tags may be harvested automatically, while approved business meanings require stewardship. An API description can document a schema but cannot prove that a deployed endpoint obeys it.

Relational Database Discovery

Database connectors often start with authorized catalogs or schemas, then enumerate tables and views and retrieve column types, nullability, constraints, object comments, and native object identifiers where exposed. In PostgreSQL, information_schema is relatively portable but can omit engine-specific metadata; PostgreSQL's pg_catalog carries additional internal details. Visibility depends on engine, version and permissions. Some systems expose stable internal relation identifiers for some operations, but those identifiers have lifecycle and scope limitations; never assume a portable native_id is permanent across restoration, recreation, or environment migration.

Separate extraction of schema structure from extraction of row content. Querying information_schema.columns can establish that a column called student_id exists; reading SELECT * FROM students is a materially different access and confidentiality decision. Capture source type declarations without claiming that an engine-specific type maps perfectly to the catalog's generic type vocabulary. Preserve the original type string and the normalization rule applied.

Warehouse and Lakehouse Discovery

Warehouse platforms commonly supply database, schema, table, view, column, masking-policy, and tagging metadata through metadata views or platform APIs. Some observability data is delayed or billed separately. A connector for such a platform should document eventual consistency, refresh interval, quota and role restrictions. A generic table inventory may be available while lineage, usage, sharing relationships, or policy metadata require specialized interfaces.

For lakehouses, distinguish the physical storage path, table or catalog identifier, table-format metadata, and compute engine's namespace. One table can have multiple ways to access or refer to it. Prefer a governed platform identity when available and require evidence before aliasing endpoints. A connector may discover an Iceberg or Delta table through a catalog API without recursively reading every underlying data file. That approach reduces cost and exposure while preserving correct source semantics.

API and SaaS Inventory Discovery

REST and SaaS connectors often read resource lists under an integration-specific permission scope, traverse pagination cursors, and obtain a compact metadata representation for each resource. They must handle absent objects, renamed labels, filtered resource types and rate-limit responses without confusing a transient problem with a deletion. API-specific object IDs are generally more useful than display names, but their lifetime and tenant scope must be documented. Two tenants may legitimately contain the same resource ID string.

Discoverability depends on the endpoint's contract. An API that returns only resources created by the integration identity is not a complete organizational export. For event-based APIs, webhooks may arrive late or out of order, may be redelivered, and may not include all prior objects. Maintain an initial authorized baseline, deduplicate events by stable event identifiers when available, and periodically reconcile against a listing endpoint. Always verify webhook signatures or equivalent authentication before treating an event as trusted metadata.

Streams, Topics, and Schema Registries

Message systems expose different categories of metadata: topic existence, partition count, retention settings, consumer-group details, and optionally schemas registered in a separate service. A topic name is not automatically a schema subject. The connector may need separate permissions to enumerate topics and inspect schema-registry subjects. Do not infer payload semantics from a topic's name alone; attach schema declarations and versions as source-backed observations with explicit limitations.

Stream-event metadata may tell the catalog that an asset was used in a job, but not that a separate daily source inventory is complete. A lineage event can be received while the source inventory connector is offline. Keep an event's dataset namespace, job/run identity and timestamp, as represented by the OpenLineage specification, distinct from a catalog-issued asset identifier. Reconciliation should connect them only when authoritative matching evidence exists.

Files, Object Stores, and Format Introspection

File and object-store connectors typically list authorized keys or directory entries, then collect metadata such as path, object version, last-modified time, size, storage class, and possibly declared content type. Inspecting file headers to infer a schema changes the connector's access profile and may trigger downloads. An object named enrollments.parquet is not proof of schema consistency, and a collection of similarly prefixed files is not necessarily one dataset. Define dataset grouping using approved layout conventions, manifests, or table catalogs.

Use server-side listing filters, request limits and version-aware identifiers when supported. Handle case sensitivity, normalization, percent encoding, and path separators according to each store's exact rules. A rename of an ordinary file often appears as a delete-plus-create because the store has no durable file ID visible to the connector. Do not claim stable asset identity merely because two files share size or a similar name; require explicit lineage, immutable version identity, or steward confirmation.

Metadata Versus Profiling, Sampling, and Row Replication

Metadata enumeration, data profiling, record sampling and data extraction are four different permission categories. A metadata-only connector may list columns and types without seeing a single row. A profiler may read aggregated distributions, minimums, null rates or row counts; even aggregates can leak sensitive facts. A sampler reads specific records and may copy restricted personal or confidential fields. A replica reads large portions of the dataset and has a different operational and legal purpose altogether.

Require separate approvals and explicit false defaults for optional content extraction. Never turn on profiling simply because the product advertises it as a connector feature. For catalog search, column names and owner-approved descriptions are often sufficient. When examples must be shown, prefer synthetic samples or preapproved masked records. A connector that can read source records but is configured not to do so should still be constrained by the source role wherever possible, because configuration controls can fail.

Credential Scope and Least Privilege

Assign a service identity to the registered connector, and grant only the metadata-listing capabilities actually needed for its source and scope. Prefer credential delegation, short-lived tokens, workload identities, narrowly scoped API keys, and provider-managed secrets when supported. Avoid user passwords, shared administrative accounts, and tokens with broad write privileges. Where an engine requires broad metadata permissions, perform a risk review and compensate with network controls and server-side audit logs.

Permissions should be explicit enough to produce meaningful access-denied reporting. An HTTP 403 on one workspace means that workspace was not inspected, not that it contains no assets. A database metadata role that sees only one schema must disclose its scope. Plan credential rotation, emergency revocation, access review, and secret masking before deployment. Audit connector operations but do not log complete authentication headers, connection strings containing passwords, or database query results.

Tenant, Environment, and Network Isolation

A catalog serving several institutions or environments must prevent cross-tenant identity collisions and evidence leakage. A source locator should contain an authorized platform instance and namespace boundaries, not an untrusted display name alone. Credential references must resolve within the correct tenant, and the ingestion endpoint must verify that a connector is permitted to publish observations for that source instance. This protects against a misconfigured integration accidentally attaching one tenant's metadata to another's catalog.

Connector networking also presents risk. Restrict egress to approved endpoints and ports, verify TLS certificates, avoid accepting arbitrary user-provided URLs that could trigger server-side request forgery, and validate redirects. Use private endpoints or network segmentation where appropriate. The catalog search tier should enforce visibility independently of what the internal connector can observe; extracting a restricted object for governance does not grant every employee the right to read its name, description or schema.

Run Identity, Time, and Reproducibility

Every execution needs a unique run identifier, registered source instance, connector version, configuration fingerprint, scan start/end times, invocation mode, credential identity reference, and status. Separate observed_at (when a source fact was observed), ingested_at (when the platform accepted it), and indexed_at (when it became searchable). These clocks answer different questions and may diverge under retry, network partition or search-index backlog. Record times in an unambiguous representation such as RFC 3339 UTC timestamps.

A snapshot is not necessarily instantaneous. A full scan taking two hours observes different assets at different moments; unless the source supports transactionally consistent enumeration, do not claim its results reflect one atomic source state. For replay or investigation, retain the connector release, normalization rules, cursor/checkpoint metadata, error summary, and the evidence keys of accepted observations. Redact sensitive values while retaining enough information to reproduce collection decisions.

Enumeration, Filtering, and Exclusion Lists

Enumeration identifies what a principal can see under the authorized source scope. Begin at a known container or listing root, apply approved include/exclude patterns, traverse children, and record complete coverage only for scopes whose traversal finished successfully. A filter may intentionally omit system tables, temporary objects, personal workspaces, or restricted namespaces. That does not make those objects nonexistent; it changes the stated inventory universe.

Review filter changes as configuration changes with consequences for stale-asset detection. If the policy newly excludes scratch.*, those objects should not automatically be treated as deleted source assets. Prefer recording out_of_scope_due_to_policy or unobserved_after_scope_change. Keep the exact effective filter configuration and version with each run. When a source can return an inventory count, reconcile it against connector counts while acknowledging that permission and snapshot timing may make totals differ.

Pagination and Complete Traversal

A list endpoint may return only one page of objects. The connector must follow the server's continuation contract until an authoritative termination condition is reached, or mark the run incomplete. Never assume that receiving 100 objects means the entire inventory contains 100 objects. Cursor tokens are opaque; do not derive the next cursor by incrementing a number unless the API contract specifies that method. Guard against repeated cursors, duplicate objects, empty pages with nonempty continuations, and per-page errors.

The safe pattern is to collect a page, validate its items, persist a page checkpoint, and continue until no further continuation is supplied. If page three fails, retain successfully read observations but do not mark the listing complete, and do not mark unseen historical objects missing. A retry may resume only if the provider guarantees the cursor's validity and consistency, or it must restart from a safe checkpoint. For APIs that change while being listed, snapshot tokens or a server-supported stable listing mode are preferable when available.

Pagination result What is established Catalog action
All pages and scopes completed Full traversal under effective policy Permit evidence-based reconciliation
Intermediate page times out Only preceding pages observed Record incomplete; block missing inference
Cursor repeats Pagination integrity uncertain Fail or quarantine run; inspect connector
One object invalid Scope may be complete; item extraction failed Retain valid objects; quarantine item
Credentials lose schema visibility Effective accessible scope narrowed Flag coverage change, not source deletion

Polling, Scheduled Scans, Push Events, and Hybrid Collection

Periodic scans are straightforward to audit and can find changes missed by event subscribers, but they impose listing load and discover change only after the next run. Events and push publication can give lower latency, yet they demand event authentication, duplicate handling, out-of-order processing, and a bootstrap inventory. Incremental API polling uses modification timestamps, change tokens or cursors and may be efficient when the source supports a reliable change feed. A hybrid system combines an initial full scan, incremental observation, and periodic reconciliation.

Mode Primary advantage Principal gap Appropriate compensating control
Scheduled full scan Enumerates intended scope Expensive and potentially stale Coverage measurement, modest cadence
Incremental polling Lower routine load Missed changes if watermark semantics are weak Overlap window and occasional full scan
Push webhook Low latency Drops, duplicates, out-of-order delivery Durable inbox and periodic reconciliation
Source-native change stream Detailed ordered change within scope Retention and permission constraints Checkpoint recovery and source snapshot
Manual import Useful for isolated systems Hard to keep fresh Named owner, expiry and review workflow

Use scans to establish inventory coverage, events to improve freshness, and reconciliations to detect drift. Neither mode is inherently trustworthy without evidence and operational checks.

Rate Limits, Backoff, and Request Budgets

Connector traffic must not harm the business system being cataloged. Apply bounded concurrency, per-source budgets, request timeouts, and backoff on temporary failures. HTTP 429 typically warrants respecting Retry-After when supplied. Retry only operations that are safe to repeat; collection GET requests are usually idempotent, but some export or job-start endpoints are not. Add randomized jitter to avoid synchronized retry storms. Repeated authentication failures, invalid schema responses or permission denials usually require intervention rather than unlimited retries.

For a warehouse, estimate API calls and monetary cost; for a database, monitor metadata-query latency and server load. A large estate may need shard-by-namespace scheduling, priority tiers, or a delegated metadata export rather than real-time queries to every source. Always keep a run-level deadline: slow scanning that never finishes is not a successful refresh. Record throttling as an operational condition, including whether it prevented complete coverage.

Incremental Scans and Checkpoint Safety

An incremental connector might request assets changed after watermark T, replay messages from offset N, or use a provider's opaque sync token. A checkpoint represents successfully and durably processed source progress, not merely the last item the connector read. Advancing it before catalog acceptance risks permanent omission after a crash. Advancing it after the source token expires may also be invalid. Persist source progress transactionally where feasible, and design at-least-once processing with idempotent observation IDs when atomic cross-system transactions are unavailable.

A time-based watermark needs an overlap window to tolerate timestamp precision, clock skew and late publication. Deduplicate repeated observations rather than treating overlap as new assets. If the provider's change stream excludes deletes or renames, schedule a full reconciliation. For each scan, record mode, baseline snapshot, cursor validity and coverage. An incremental run is not a basis for claiming that all older assets still exist; it reports only the change surface documented by the source.

Schema Extraction, Data-Type Mapping, and Confidence

After enumeration, the connector reads each object's supported descriptive attributes. For tabular objects, this may include column order, nullability, engine type, constraints, primary keys and view definitions where authorized. Preserve a source-native type alongside any normalized catalog type. For example, a PostgreSQL NUMERIC(10,2) may normalize to a decimal family, but dropping precision would destroy useful evidence. Similarly, an API schema's format: date-time is a declared contract, not proof that every production value conforms.

Record whether an attribute was observed, declared by documentation, inferred, or manually asserted. These evidence types do not carry identical confidence. For an object store, a connector may infer a CSV header from a file; such inference should be marked tentative and separately approved when expensive or confidential content access is involved. Preserve extractor version and its mapping rules so future consumers can understand why a column appeared as a given catalog type.

Durable Identity, Native IDs, and Renames

A source object can move or be renamed without becoming a new conceptual asset. Conversely, a new object may reuse an old name. Reconcile primarily with a source-native identifier whose durability is documented, scoped to the registered instance, with the catalog's immutable asset ID stored separately. Native IDs may be recreated or recycled by some platforms; therefore, do not assume absolute permanence. Record a verification rule and evidence for continuity. A name match is a locator match, not by itself proof of asset identity.

Consider asset-0142, a registrar table initially named registrar_public.student_enrollment. A later complete scan observes the same documented native object ID under registrar_public.enrollment_current; it is reasonable under the connector's identity contract to preserve asset-0142 and record the old name as an alias. If a new table is later created with the original name but a new native ID, give it a new catalog identity. Never merge it into asset-0142 because its qualified name matches the historical alias. If the native ID is missing or its lifecycle is uncertain, route the rename hypothesis to review instead of making an irreversible merge.

Normalization and Canonical Catalog Records

Normalization converts platform-specific observations into a catalog contract while preserving the source facts. Examples include mapping a vendor's table-kind enumeration into table or view, parsing timestamps into UTC, structuring database paths, and representing column types in a common vocabulary. Maintain original values and rule versions so the translation can be audited. A normalized asset_type is a catalog interpretation, not a reason to discard the source's precise object kind.

Avoid normalization that mutates identity accidentally. Case-folding object names is unsafe when the source distinguishes cases; trimming punctuation or replacing underscores can cause collisions. Different storage systems have different path semantics. Normalize for search display separately from identity lookup. A staging validator should reject unregistered instances, invalid field types, ambiguous IDs, and unrecognized classifications according to the relevant metadata contract; it should not invent missing owners or classification approvals.

Deduplication, Idempotency, and Replayed Evidence

A connector may see the same object twice in overlapping pages, repeated webhook deliveries, or an incremental replay. Deduplicate observations by an idempotency key that includes the source instance, native object identity, observation version or stable event ID, and operation semantics. This is distinct from deduplicating assets across independent systems. Two source instances may legitimately contain tables with the same name. Two names within one instance may be aliases, different objects, or a materialized copy; their relationship requires evidence.

A robust ingestion endpoint can accept the same envelope more than once without multiplying catalog records, changing an approved owner, or producing duplicate lineage edges. Store last-seen timestamps carefully: replaying an old event must not make its claim look newer than a subsequent observation. Where events can arrive out of order, compare source revisions or sequence positions if the platform exposes them; otherwise keep conflicting observations and flag their order as uncertain.

Field-Level Provenance and Observation History

An asset record aggregates claims that may come from different systems at different times. Do not represent all claims as if the latest connector run authored them. A column name may have been extracted directly from an information-schema view, while a business description was approved manually and a sensitivity label originated from a security-policy service. Each published field should retain a source, observed timestamp, ingestion timestamp, evidence reference, and the governing rule used to select a current value. For high-stakes fields, record the responsible authority and review status.

A common claim envelope is {asset_id, field, value, origin, observed_at, evidence_id, rule_version, status}. Field-level provenance supports explanations such as "column list last verified yesterday; business owner last approved six months ago; classification policy evaluated last week." It also permits a targeted refresh without rewriting unrelated annotations. Evidence IDs must point to authorized records; they should not expose credentials or confidential raw responses in public search interfaces.

Field Likely origin Preservation and override rule
Native object ID Source inventory API Connector-authoritative within documented scope
Column definition Information schema or API Refresh on verified schema change
Display title Source or steward Preserve approved human title unless policy says otherwise
Owner Stewardship workflow Connector cannot silently assert approval
Classification Approved security authority Retain decision and evidence history
Last observed Individual extraction run Update only after an actual observation
Lineage edge Job event, parser or reviewed claim Store evidence type and confidence separately

Human Annotation and Source-of-Truth Precedence

Catalog metadata may be augmented by technical operators, data stewards, information-security teams and business domain owners. Define field-specific precedence, not one universal rule that "newest value wins." If a source column disappears after a verified schema change, the machine may update the observed schema automatically. If a service account changes its display label, it should not automatically become the approved business owner. If a connector identifies a source tag indicating sensitive data, the catalog may raise a review or protective default without overriding an authorized classification decision behind the scenes.

Some source systems actually are the authority for certain business attributes; a human-maintained data product API may publish approved definitions. The distinction is not human versus machine but validated authority per field. Preserve both the latest source observation and the chosen catalog presentation value, together with the selection reason. Where the sources disagree, publish an uncertainty or review state appropriate to confidentiality rather than fabricated certainty.

Partial Runs, Failed Scans, and Quarantine

A connector can fail at many boundaries: authentication, scope traversal, a single object, metadata extraction, normalization, publication or indexing. Classify failures as transient, persistent, source-specific, or systemic. A malformed object should not necessarily prevent the connector from recording other observations, but a missing pagination page must prevent a full-coverage assertion. Keep a separate failed-object count and a record of which namespaces and pages were skipped. A queue for retry or quarantine must be access controlled because raw metadata can disclose sensitive schema details.

Fail safe on disappearance: if a scan aborts after listing one of three objects, the two unobserved objects are not evidence of deletion. A safe publication rule may accept partial non-destructive attribute updates while blocking absence-based reconciliation; the educational simulator below takes the simpler conservative approach and does not commit a failed run at all. For every run, distinguish complete, partial, and failed and keep prior valid evidence. It is important not to imply that a successful retry erases the forensic history of the failure.

Missing, Deleted, Inaccessible, and Out-of-Scope Assets

These states are not interchangeable. An asset might be missing from a complete authorized inventory, confirmed deleted by a native event or administrative record, inaccessible because permissions changed, out of scope because a filter changed, or simply not observed because a scan failed. A catalog can model them separately and choose different downstream consequences. A missing-in-snapshot observation may justify an investigation but not necessarily a public retirement, particularly where connector permissions are variable.

For eventual deletion, consider requiring repeated complete scans, a provider-backed deletion event, or source-owner approval before applying a tombstone. Deletion policy is local governance, not a guarantee that every platform uses the same rule. Preserve a soft-deleted asset's historical identity and lineage when retention requirements permit. DataHub documents stateful ingestion with stale-metadata handling and a safety threshold; this illustrates why absence-based removal must be tied to controlled run state and failure safeguards, not a naive set difference after any successful API request (DataHub stateful ingestion).

Drift Detection and Reconciliation Windows

Metadata drift occurs when the catalog's last accepted description no longer reflects a source's state or the authority's current interpretation. Drift may involve a new column, renamed table, altered type, revoked permission, changed owner, or a lost webhook. Compare source snapshots only when their coverage is compatible. If a source registration changes from scanning three namespaces to one, comparing asset counts without acknowledging the new scope is misleading. Record the baseline, config fingerprint, field-level differences, and whether the change is authorized.

A reconciliation window gives event-driven systems a periodic chance to discover missed changes. A configurable policy might scan critical assets hourly, reconcile full inventories nightly and review high-risk classification changes promptly; these are illustrative frequencies, not universal standards. Choose cadence based on change rate, source API limits, risk, and user needs. Drift findings should identify whether the system observed a real mutation or merely changed how it collects or interprets metadata.

Coverage, Freshness, Accuracy, and Completeness Metrics

Connector health dashboards should separate transport success from metadata value. Useful metrics include registered sources with recent completed scans, allowed namespaces fully traversed, assets observed with fresh evidence, extraction failures by type, unresolved duplicate candidates, source objects rejected by contract validation, and time between source observation and catalog publication. Freshness can be measured from field-level observations; a top-level run timestamp alone cannot establish that every field was inspected in that run.

Indicator Definition Caution
Connection success Successful authorized handshake Says nothing about inventory coverage
Scope completion Allowed scopes traversed / scopes scheduled Unknown object count may remain
Asset extraction success Objects with accepted extraction / enumerated objects Denominator excludes unseen scopes
Publication lag Indexed time minus accepted time Does not measure source age
Claim freshness Now minus last verified observation time Field-specific, not record-wide
Uncertain identities Assets awaiting reconciliation review Do not count as safe merges
Suspected missing Absent in a comparable complete snapshot Not equivalent to confirmed deletion
Connector exception rate Errors classified by operation and source Low errors can coexist with bad filters

Publishing dashboards should show source and time windows, not only aggregate percentages. An institution can achieve 99% of observed assets with fresh metadata while leaving an entirely inaccessible department out of the calculation. Material exclusions must be visible to governance reviewers.

Security, Metadata Leakage, and Auditability

Metadata itself can expose strategic or personal information: confidential table names, named patient attributes, query text, analyst usernames, storage locations, password-vault references, or a classification indicating a sensitive program. Different catalog audiences should see different portions of an asset description, and search indexes must apply consistent access controls. Protect raw ingestion logs, lineage events, error traces and archived source responses as carefully as the metadata store itself. Where a public directory must display an asset's existence, that visibility is a policy choice rather than a technical necessity.

Use authenticated ingestion endpoints, source-specific authorization, short secret retention, audit trails for connector configuration changes, and least-privilege review. Review plugin or connector updates for changed permissions. Do not allow a source comment that contains HTML, Markdown, embedded links or instructions to execute code in the catalog interface; treat source-provided content as untrusted input and sanitize during rendering. A catalog may ingest untrusted labels for search, but must not treat them as administrative instructions.

Worked Scenario: Three University Source Objects

Consider a registered registrar source instance university-prod-postgres-01 and an authorized scope registrar_public. A first complete run finds three objects: enrollment_current (native-201, catalog asset-0142), course_sections (native-202, asset-0143), and term_reference (native-203, asset-0144). These identifiers are fictional and deliberately simplified. The initial names and relationships are observed, not governance approvals. A separate stewardship process supplies business owners and classification decisions before any public index claims those attributes.

A second complete run finds the same three native identities, but the object with native-201 has changed its qualified name from registrar_public.enrollment_current to registrar_public.current_enrollment. Its catalog identity remains asset-0142, and the old path is added to historical aliases. A third scheduled scan successfully reads the first page but fails on the second; the connector records failed, preserves the last complete snapshot, and does not infer that native-202 or native-203 was deleted. If a later successful full scan does not find native-202, the result is an absence observation requiring the configured deletion policy, not an automatic irreversible removal.

Event Native objects seen Decision Historical evidence retained
Run 1: complete 201, 202, 203 Create three catalog assets Initial names and schema claims
Run 2: complete 201, 202, 203 Rename observation for 201; preserve ID Original alias and new locator
Run 3: failed Only first page Do not reconcile absence Run error and last complete inventory
Run 4: complete, optional 201, 203 Flag 202 as suspected missing Catalog identity and prior observations

A real source must define whether its native ID survives the particular rename operation and whether its listing is complete. The case assumes the connector has verified both properties. Without them, the rename is only a candidate relationship and should be reviewed.

Python: Executable, Failure-Safe Snapshot Reconciliation

The following standard-library Python demonstration models a trusted list-page adapter, a tiny catalog registry and a conservative commit policy. It intentionally uses an in-memory source rather than live credentials. It stages all pages before applying any results; a second-page exception leaves the previous accepted catalog snapshot unchanged. Stable native IDs are scoped to the source instance. On complete scans, an object absent from the current inventory becomes suspected_missing but is not deleted.

from copy import deepcopy
from datetime import datetime, timezone

SOURCE = "university-prod-postgres-01"

def now_utc():
    return datetime.now(timezone.utc).isoformat()

class Catalog:
    def __init__(self):
        self.assets = {}           # (source, native_id) -> catalog record
        self.history = []
        self.next_id = 142

    def scan(self, run_id, pages):
        staged = {}
        try:
            # Each page is a list of dicts; an exception simulates an API failure.
            for page in pages:
                if isinstance(page, Exception):
                    raise page
                for item in page:
                    native_id = str(item["native_id"])
                    key = (SOURCE, native_id)
                    if key in staged:
                        raise ValueError("duplicate native ID in this scan")
                    staged[key] = item["qualified_name"]
            # No changes above this line touched committed catalog state.
        except (OSError, ValueError, KeyError) as exc:
            self.history.append({"run": run_id, "status": "failed",
                                 "error": type(exc).__name__})
            return "failed"

        updated = deepcopy(self.assets)
        observed_at = now_utc()
        for key, name in staged.items():
            if key not in updated:
                asset_id = f"asset-{self.next_id:04d}"
                self.next_id += 1
                updated[key] = {"asset_id": asset_id, "name": name,
                                "aliases": [], "status": "observed",
                                "last_observed": observed_at}
            else:
                asset = updated[key]
                if asset["name"] != name:
                    if asset["name"] not in asset["aliases"]:
                        asset["aliases"].append(asset["name"])
                    asset["name"] = name
                asset["status"] = "observed"
                asset["last_observed"] = observed_at
        for key in updated.keys() - staged.keys():
            updated[key]["status"] = "suspected_missing"
        self.assets = updated
        self.history.append({"run": run_id, "status": "complete",
                             "observed": len(staged)})
        return "complete"

catalog = Catalog()
first = [
    {"native_id": "201", "qualified_name": "registrar_public.enrollment_current"},
    {"native_id": "202", "qualified_name": "registrar_public.course_sections"},
    {"native_id": "203", "qualified_name": "registrar_public.term_reference"},
]
assert catalog.scan("r1", [first[:2], first[2:]]) == "complete"
identity = catalog.assets[(SOURCE, "201")]["asset_id"]
renamed = [dict(x) for x in first]
renamed[0]["qualified_name"] = "registrar_public.current_enrollment"
assert catalog.scan("r2", [renamed[:2], renamed[2:]]) == "complete"
assert catalog.assets[(SOURCE, "201")]["asset_id"] == identity
assert "registrar_public.enrollment_current" in \
       catalog.assets[(SOURCE, "201")]["aliases"]
before_failure = deepcopy(catalog.assets)
assert catalog.scan("r3", [renamed[:1], OSError("page 2 timed out")]) == "failed"
assert catalog.assets == before_failure
assert len(catalog.assets) == 3
assert catalog.history[-1]["status"] == "failed"
print(identity, len(catalog.assets), catalog.history[-1]["status"])

This teaching model is not a production connector: it does not authenticate endpoints, validate external schemas, persist transactions, simulate actual concurrent source mutations, or implement an approved deletion workflow. Its source-native IDs and complete-list guarantee are assumptions stated by the example. A real implementation must commit the accepted snapshot and run checkpoint transactionally, implement retry budgets, validate observed scopes, and ensure that multiple workers do not race to create identities.

Interpreting the Python Demonstration

The successful first scan creates three catalog records, one per stable native identity. The second scan changes only the observed locator for native-201; the catalog ID stays constant and its previous name becomes a historical alias. The failed scan appends a run-history entry but does not modify catalog records. These assertions enforce the article's key invariant: absence-based interpretation requires a verified complete scan. An application can adopt more permissive partial-update rules, but it must never let partial coverage authorize deletion inference.

Notice also what the demonstration does not do. The use of deepcopy gives atomicity only in this small single-process memory model; a production catalog needs a database transaction or equivalent consistency mechanism. The function accepts data structures that are already authenticated and scoped; therefore, a live connector must perform independent security checks. It does not check row-level values or infer business ownership. Those omissions are intentional expressions of the discovery boundary, not recommended shortcuts for production systems.

SQL: Narrow, Read-Only Schema Discovery

For PostgreSQL, an approved principal with appropriate metadata visibility may inspect authorized column definitions through a portable information-schema view. This query is illustrative and should run only against a database the operator is authorized to inspect; exact visibility and available fields vary by server configuration. It reads metadata, not student records:

SELECT table_schema, table_name, ordinal_position,
       column_name, data_type, is_nullable
FROM information_schema.columns
WHERE table_schema IN ('registrar_public', 'finance_reporting')
ORDER BY table_schema, table_name, ordinal_position;

The connector should preserve the original schema and column identifiers, record the role's permitted scopes, and treat an empty response as zero visible columns under this role, not proof that the institutional database contains no objects. This query alone does not enumerate empty-column relations, establish object-native identity, identify deleted objects, or prove a complete table list. Use a separate authorized relation inventory and source-specific identity method for those purposes. PostgreSQL's information-schema documentation describes its visibility model and portability limits.

PowerShell 5.1: Inspecting a Paginated Metadata Export

On Windows, the following PowerShell 5.1 example demonstrates conservative traversal of a fictional read-only catalog endpoint. It assumes that the endpoint returns { "items": [...], "next": "..." } and that the caller has obtained an authorized access token. It is not a ready-made DataHub or OpenMetadata API client; adapt field names and authentication to the actual provider's contract. The example uses a typed response collection and refuses to claim a completed inventory after any request failure.

# Windows PowerShell 5.1; replace with your approved HTTPS endpoint.
$uri = 'https://metadata.example.invalid/api/v1/assets'
$headers = @{ Authorization = 'Bearer <AUTHORIZED_TOKEN>' }
$collected = New-Object 'System.Collections.Generic.List[object]'
$visited = New-Object 'System.Collections.Generic.HashSet[string]'
$complete = $false
try {
    while ($null -ne $uri -and $uri.Length -gt 0) {
        if (-not $visited.Add($uri)) { throw 'Repeated pagination URL' }
        $result = Invoke-RestMethod -Uri $uri -Headers $headers `
            -Method Get -TimeoutSec 30 -ErrorAction Stop
        foreach ($item in @($result.items)) { $collected.Add($item) }
        if ([string]::IsNullOrWhiteSpace([string]$result.next)) {
            $uri = $null
        } else {
            # Real systems should also constrain each next URL to the trusted host.
            $uri = [string]$result.next
        }
    }
    $complete = $true
} catch {
    Write-Warning ("Metadata scan incomplete: " + $_.Exception.Message)
}
[pscustomobject]@{
    Complete = $complete
    ItemsObserved = $collected.Count
    CanInferDeletion = $complete
}

Do not follow server-provided continuation URLs blindly in a real connector; validate origin, TLS, expected path and redirect policy before transmitting credentials. The placeholder token and .invalid host are deliberately nonfunctional. Error handling in production should classify response status, respect Retry-After, bound retries and redact secrets. An item count from this example is not necessarily unique or within the authorized scope until validation occurs. The key output is the explicit Complete flag.

Publication, Search Indexing, and Rebuildability

The catalog evidence store and the search index serve different purposes. The former maintains identity, provenance, history and governance decisions; the latter supports query, faceting, filtering and discovery. A connector should write accepted metadata to the governed store, then the publication system projects approved fields into a search document. If indexing lags, mark search freshness accordingly; do not silently rerun a source connector to repair an index-only problem.

Search projection must respect field sensitivity, tenant boundaries and approved descriptions. It may index historical aliases to support renamed-object lookup, but search results should clearly identify the current canonical asset. A rebuilt index must not inadvertently expose previously suppressed fields or treat a retired name as a live new object. Prefer replayable catalog change events or rebuilds from the accepted metadata store rather than using ad hoc scraping of rendered pages.

Monitoring, Alerting, and Service Objectives

Run monitoring should answer whether the connector could reach its source, which approved scopes were traversed, how many objects were extracted, how many identities were uncertain, and how quickly accepted observations reached the catalog. Alert on repeated authentication failures, unexpected drops in object count, sustained indexing lag, missing required namespaces, schema parsing errors, and connector-version changes that suddenly alter the inventory. Compare metrics only with like-for-like configurations and source scope.

Example service objectives could require 99% of scheduled critical-source scans to complete within a defined window and 95% of eligible observed asset descriptors to be indexed within an hour. These are illustrative policy targets, not universal benchmarks. A reliable dashboard includes the denominator and excludes neither restricted sources nor failed scans without disclosure. An alert should link to the run ID, errors, effective configuration and remediation owner rather than showing only "metadata ingest failed."

Connector Test Matrix and Acceptance Criteria

Integration testing needs more than a successful credential check. Test empty inventories, multiple pages, repeated cursors, duplicate objects, permission gaps, rate limits, malformed schema descriptors, source renames, source-name reuse, and an interrupted run immediately before checkpoint persistence. Exercise replay and idempotency after process restarts. Include connector upgrades and source API version changes, because a new vendor release may alter response shape or required permissions even while authentication continues to work.

Acceptance should be tied to observable assertions, not screenshots of a product reporting "success." Negative cases are especially valuable because most catalog damage occurs when a system misreads weak evidence as authoritative absence or identity equivalence.

Troubleshooting by Failure Layer

When a catalog appears incomplete, begin with the registered scope and run evidence rather than immediately rescheduling ingestion. Verify that the source instance, tenant and service role match the intended target. Compare the approved namespace list with the namespaces actually enumerated. Inspect pagination termination, filters, skipped asset types, quarantine counts, source API errors and last successful checkpoint. Then compare accepted catalog observations with search-index acknowledgments. Each layer can independently explain missing search results.

For apparent duplicates, inspect catalog IDs, native identities, tenant scope, source names and alias history; do not automatically merge by normalized display title. For apparent deletions, ask whether the last scan was complete under comparable scope and whether the source reports an authoritative deletion event. For stale descriptions, determine whether the connector ever reads that field or whether human stewardship controls it. Troubleshooting succeeds when it identifies the evidence boundary responsible for the inconsistency.

Governance and Operational Responsibilities

Ownership of the connector itself is different from ownership of the assets it describes. A platform team may maintain the connector code and source permissions; the source owner authorizes access; a catalog administrator manages ingestion contracts and indexes; security approves sensitive collection; business stewards approve definitions and ownership claims. Record these roles so failures reach the right people. A connector incident involving credentials should not be assigned to a glossary editor, and a disputed business definition should not be settled by redeploying a crawler.

The forthcoming Metadata Stewardship and Ownership article treats approval workflows in depth. Here the key interoperability contract is clear: connectors contribute machine-observed evidence, and governance determines which claims can be published as institutionally authoritative. Apply change control to source scopes, software versions, deletion policy and field-authority rules; retain audit history when personnel or permissions change.

Implementation Checklist for an Institutional Catalog

Before deployment, document approved sources, asset kinds and collection permissions. Establish stable instance identifiers, native identity rules, expected coverage, and an explicit list of forbidden data collection. Configure credential rotation, network allowlists, connector-release pinning, retries and rate budgets. Ensure every run emits status, effective scope, observed object count, extraction failures, checkpoints and timestamps. Require a typed metadata contract, field-level origin, and a quarantine channel for unsupported claims.

Before enabling production publication, test a three-asset full scan, an evidenced rename, a reused source name, an interrupted scan and a failed search-index update. Demonstrate that incomplete runs do not delete catalog history and that a connector cannot overwrite human-approved ownership and classification. Verify that catalog users see only authorized metadata, that old names resolve to the correct current identity, and that the index can be rebuilt without re-accessing source records. Establish an operational owner and review cadence for every configured connector.

Practical Exercises and Assessment Questions

  1. Source registry: Design a connector entry for a data warehouse with three schemas, one deliberately excluded. Identify which credential and coverage fields are required to prevent a misleading "100%" result.
  2. Coverage: An API reports next_cursor after 50 objects, but the second request times out. State what facts are known, what is unknown, and whether the catalog may mark the remaining assets missing.
  3. Identity: A table is renamed and retains a documented native ID. Construct the alias and provenance update. Explain what changes if the source ID is not stable across renames.
  4. Permissions: A connector role can inspect 200 tables but only 150 have column visibility. Create separate counts for enumeration coverage and extraction success. Why would one percentage conceal the issue?
  5. Field authority: A database comment conflicts with the steward-approved business description. Show how to store both observations without silently overwriting the approved claim.
  6. Safety: Modify the Python demonstration to flag suspected missing assets only after two comparable complete scans. Include a test where a failed scan occurs between those two scans; decide whether it resets or interrupts your evidence window.
  7. Events: Outline a full-snapshot-plus-webhook design that survives out-of-order events and a lost webhook. Identify the deduplication and reconciliation keys.
  8. Privacy: A connector product offers automatic row sampling. Draft the separate approval and access controls required before using it on student records.
  9. API limits: Calculate a request budget for 120 pages with a limit of 30 requests per minute, then explain why throttle headers and retry penalties make a simple minimum-time calculation an optimistic lower bound.
  10. Audit: Produce a one-page run report with statuses for connection, enumeration, extraction, reconciliation, storage, and indexing. Include the evidence a reviewer needs to distinguish failed ingestion from search-index lag.

These exercises should be answered with explicit assumptions. A policy that is safe for a read-only catalog may not satisfy regulatory retention rules, source-system constraints, or organizational privacy requirements without further review.
