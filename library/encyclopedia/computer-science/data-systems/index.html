Division Overview

The Data Systems division is Level 3 of the Computer Science volume of the MGU Encyclopedia. It covers how information is represented, preserved, structured, transformed, queried, secured, discovered, and analyzed. This is a directory of specialist Level 4 units, not a replacement for their individual overview articles or Level 5 specialist entries.

A file system, transactional database, analytical lakehouse, search engine, and data-science workflow all work with stored information, yet they make different promises. A file system names and stores files; a database manages records and updates; a warehouse organizes analytical records; a retrieval engine ranks documents against an information need; and data science evaluates evidence and models. Placing these subjects in separate units prevents one subject's subarticles from silently becoming peer-level summaries.

Taxonomy reconciliation: this edition recognizes 14 units: the 11 supplied established unit subjects plus Databases, Data Warehousing, and File Systems as legitimate broad parent subjects. Six narrower overview pages are assigned to existing Level 4 units as their Level 5 children. Directory links become live when the corresponding delivered files are installed.

Data-System Functions Compared

Different systems frequently appear in one solution. Their roles should not be collapsed into a single category just because they use the same physical infrastructure.

Worked Data-System Scenarios

Scenario 1: A university's digital encyclopedia

The original articles are files in managed storage. A catalog identifies title, authorship, revision, subject, and reuse permissions. A search engine extracts text, creates an inverted index, ranks candidate articles, and enforces publication access rules. A relational database may record editors and approvals; a warehouse may report article use and coverage by discipline. None of these functions is interchangeable. A stale search hit is an index-freshness issue, whereas an unauthorized edit is a workflow or security issue.

Scenario 2: Financial transactions and institutional reporting

A transactional database records a payment and its ledger entries with carefully defined atomicity and isolation. Data engineering transfers authorized copies into an analytical environment, preserving provenance and checking totals. The warehouse organizes historical measures and dimensions so finance staff can compare periods. A dashboard uses queries against the warehouse rather than improvising financial state from raw application logs. Encryption and restricted access protect sensitive fields at every stage.

Scenario 3: A large collection of images and research documents

Object storage preserves the original objects while metadata describes format, subject, rights, location and retention. Binary encoding and compression affect how images are stored; character encoding affects descriptive text. A lakehouse can support broad analytical access, while Information Retrieval handles keyword and semantic search. Model development belongs to Data Science and does not eliminate the need for provenance, evaluation and human verification of scholarly material.

Selection and Architecture Framework

  1. Specify the data object: determine whether the primary entity is a byte sequence, file, database record, analytical table, indexed document, or statistical sample.
  2. State the guarantee: identify durability, transactional consistency, access control, provenance, search relevance, or measurement validity as distinct requirements.
  3. Classify workload shape: compare concurrent point updates, long scans, document queries, media exchange, archival retention, and iterative modeling.
  4. Choose ownership boundaries: maintain one authoritative source for each record and define when, where, and why copies or materialized views exist.
  5. Plan transformation and metadata: record schema, meaning, lineage, privacy class, retention and error-handling rules before joining systems.
  6. Validate with evidence: use representative transactions, retrieval judgments, integrity tests and recovery exercises instead of extrapolating from isolated demonstrations.
  7. Design for change: schema revisions, format versions, index rebuilds, permission changes, and technology migrations require controlled lifecycle procedures.

Suggested Study Pathways

Foundational path

Begin with Binary Data → Character Encoding → Data Storage Methods → File Systems. This establishes what bytes mean, how readable symbols are represented, and how persistent objects are organized.

Database and application path

Continue Data Modeling → Databases → database indexing, transactions, SQL, and distribution → Data Engineering. This connects logical schemas with safe updates and operational integration.

Analytics and discovery path

Continue Data Engineering → Data Warehousing → Data Lakes and Lakehouse Architecture → Data Catalogs and Metadata Management → Information Retrieval → Data Science. Separate the retrieval of potentially useful evidence from inference about what that evidence demonstrates.

Protection and efficiency path

Use Data Compression and Data Encryption alongside every pathway. Compression reduces representation cost; encryption protects confidentiality. They solve different problems and neither substitutes for integrity validation, access management or backup.
