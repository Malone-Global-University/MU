Definition and Scope

Endianness and Byte Order is a Level 5 specialist article in the Binary Data unit of the MGU Encyclopedia’s Data Systems division. It explains how multi-byte values are arranged within stored and exchanged byte sequences, and how decoders must reconstruct those values from the corresponding format rules.

The article emphasizes external representation and interoperability: a byte stream is not an unambiguous integer without a declared field width, encoding, and order. The article belongs in the Binary Data specialist directory. Processor implementation capabilities, bus signaling and the entire theory of numeric encodings remain in their respective Computer Science units.

Why Byte Order Matters

A byte is an eight-bit quantity in the modern binary formats discussed here. An individual byte has no internal byte order: there is only one byte. Endianness, or byte order, becomes relevant when two or more bytes jointly represent a value such as a 16-bit integer, 32-bit identifier, floating-point field, or fixed-width code unit. The format must state which byte contributes the most significant portion of that value and which contributes the least significant portion.

This is an interpretive convention, not a property that can always be determined from the visible bytes. The sequence 01 00, read as a 16-bit unsigned little-endian integer, denotes 1; read as a 16-bit unsigned big-endian integer, it denotes 256. Both interpretations are internally consistent. The contract between writer and reader, rather than the machine reading the bytes, decides which interpretation is correct.

For reliable interchange, record at least field width, signedness or numerical representation, byte order, and offset. A format may also specify scaling, units, valid ranges, and version. A parser that knows only that a field is “binary” lacks enough information to reconstruct its intended value.

Endianness is principally about multi-byte field layout in this article. The question of how a bus transfers bits, a CPU implements loads, or a serial link encodes signals belongs to its own architectural or networking subject. A file format can prescribe the same byte sequence on machines that implement very different processor architectures.

Big-Endian and Little-Endian Conventions

Consider the 32-bit integer whose familiar hexadecimal value is 0x12345678. Its four constituent byte values are 0x12, 0x34, 0x56, and 0x78. The positions in the mathematical value are fixed: 0x12 contributes to the most significant eight bits, whereas 0x78 contributes to the least significant eight bits.

In big-endian form, the most significant byte appears at the lowest byte offset in the field. In little-endian form, the least significant byte appears at the lowest offset. “Lowest offset” means the beginning of the designated field when displaying bytes from left to right in increasing file-offset or memory-address order; it does not mean leftmost on a particular screen under every display convention.

Increasing byte offset Offset 0 Offset 1 Offset 2 Offset 3 Decoded 32-bit value
Big-endian representation 12 34 56 78 0x12345678
Little-endian representation 78 56 34 12 0x12345678

Both sequences encode the same intended number under their respective conventions. Merely displaying a hexadecimal number such as 0x12345678 does not reveal how its bytes appear in storage; it is conventional mathematical notation, not a dump of memory.

Big-endian is sometimes summarized as “most significant first” and little-endian as “least significant first.” These are useful mnemonics only when the unit being reordered is explicitly the byte of a multibyte value. The bit positions within each byte are not reversed by switching between little-endian and big-endian encoding.

Deriving a Value from Bytes

For a four-byte unsigned integer in big-endian order, let b0, b1, b2, and b3 be the bytes encountered in increasing offset order, each an integer between 0 and 255. The decoded value is:

big-endian: b0 × 2^24 + b1 × 2^16 + b2 × 2^8 + b3.

For the same four encountered bytes in little-endian order, the formula is:

little-endian: b0 + b1 × 2^8 + b2 × 2^16 + b3 × 2^24.

Take the raw stream 12 34 56 78. As big-endian, it becomes 0x12345678, or 305,419,896. As little-endian, it becomes 0x78563412, or 2,018,915,346. The algorithm must use the exact byte sequence it received. The important reversal is of the byte weights, not of the order in which bytes are printed for inspection.

For a 16-bit field, the analogous formulas are 256 × b0 + b1 (big-endian) and b0 + 256 × b1 (little-endian). A simple calculation is valuable in forensic analysis because it is independent of any convenience API. It also exposes why reading the first byte as a complete number or swapping bytes unconditionally is incorrect.

Raw bytes at increasing offsets Interpretation Unsigned value
00 01 16-bit big-endian 1
00 01 16-bit little-endian 256
01 00 16-bit big-endian 256
01 00 16-bit little-endian 1
12 34 56 78 32-bit big-endian 0x12345678
12 34 56 78 32-bit little-endian 0x78563412

An endian error can be invisible when a field consists of repeated bytes: 00 00, FF FF, and 12 12 are numerically unchanged when their two bytes are reversed. Tests based solely on such symmetric patterns cannot establish that a decoder is correct.

Fields, Offsets, and Mixed-Width Records

A binary record is usually a sequence of fields with explicitly defined offsets and widths. Byte order should be applied to each multibyte numeric field individually, not indiscriminately to the entire record. Suppose an eight-byte record is defined as a one-byte version, one-byte status, two-byte count (big-endian), and four-byte sequence number (little-endian). Its physical layout may be:

Offset Bytes Field Rule Meaning
0 02 Version 8-bit unsigned Version 2
1 80 Status Bit flags High status bit set
2–3 01 02 Count 16-bit big-endian unsigned 258
4–7 78 56 34 12 Sequence number 32-bit little-endian unsigned 0x12345678

There is no contradiction in a format that chooses different byte orders for different fields, although such a design requires unusually clear documentation. A parser should maintain a cursor, check that enough bytes remain, then decode each field with its own signedness, width and order. It must not reverse the complete eight-byte record, because doing so would relocate the version and status fields as well as the numeric payloads.

Offsets and alignment are separate issues. If a memory structure inserts two padding bytes between fields, those padding bytes are not automatically part of an adjacent integer and should not be endian-swapped with it. A portable file format should define byte offsets independently of a compiler's native in-memory structure layout; otherwise implementation-specific padding can make a file unreadable elsewhere.

Endianness Versus Bit Order

Byte order describes the ordering of complete bytes that jointly encode a multibyte value. Bit order, bit numbering, and physical transmission order are related but distinct concepts. A diagram may number the most significant bit as zero, or it may number the least significant bit as zero. A serial interface may send bits within an octet in a defined temporal order. None of those choices, by itself, establishes whether a multibyte integer is big-endian or little-endian.

For example, 0x96 is one byte with binary digits 10010110. In a 16-bit little-endian field 96 34, the first byte 0x96 still has exactly those eight bits. The 16-bit integer is 0x3496, not the result of reversing the eight individual bits in each byte. Reversing the bit sequence 10010110 yields 01101001 (0x69), a completely different transformation called bit reversal.

Network specifications may separately define (1) how octets are arranged into multibyte fields, (2) how diagrams label bits, and (3) how a link transmits or serializes them. The Internet Protocol's original specification discusses octet transmission order and bit labeling; physical-layer and link-layer standards can impose additional rules. A sound parser follows the protocol's field layout instead of reasoning from cable-level signaling or informal claims that a network is always “MSB first.”

Machine-Native Order and Portable Storage

A processor generally has a native byte-order convention for representing particular multibyte scalar values in addressable memory. Many widely used platforms use little-endian layouts, while some architectures and operating modes support big-endian or configurable order. A language runtime may hide this distinction when software works only with abstract numeric values, but the distinction reappears when converting integers to external byte sequences.

A local integer variable with the mathematical value 0x12345678 may reside in memory as 78 56 34 12 on a little-endian implementation. Writing those four raw in-memory bytes into a portable file without documenting the chosen order means the writer has silently committed the file to a machine-dependent convention. Another program may interpret them differently even if it uses the same integer width.

Prefer an explicit wire or disk order in all persistent or networked formats. A reader should decode that order into its local numeric representation, work with the value normally, and encode the agreed order when writing. Once numeric values have been decoded, most application logic does not need to concern itself with endianness. Repeated byte swapping throughout an application is usually evidence that the serialization boundary has not been clearly defined.

The term network byte order conventionally refers to big-endian order for multioctet integer fields in established Internet protocols such as IPv4. It is not a guarantee that every field in every network protocol, payload, file format, or application message uses big-endian encoding. Every format remains governed by its own specification.

Byte Order in Real File Formats

A well-designed file format resolves byte-order ambiguity either by fixing an order throughout its defined multibyte numeric fields or by marking the order in a header. The PNG image format is a prominent fixed-order example: the PNG specification requires multibyte integers in network (big-endian) byte order. A decoder must follow that rule even when executing on a little-endian machine; it should not infer PNG field order from its own hardware.

TIFF is an example of an indicated-order format. The header begins with 49 49 (ASCII II) for little-endian or 4D 4D (ASCII MM) for big-endian. In classic TIFF, the following 16-bit identifier for decimal 42 therefore appears as 2A 00 after II, or as 00 2A after MM. Thus the first four header bytes are:

Format Initial bytes Interpreted header
Classic TIFF, little-endian 49 49 2A 00 II plus value 42
Classic TIFF, big-endian 4D 4D 00 2A MM plus value 42

A reader can recognize which of the two alternatives it has encountered, then use that choice for the TIFF numeric fields to which the specification applies. This does not mean an arbitrary four-byte header containing II or MM is necessarily a valid TIFF file: a parser must still check the rest of the header and format constraints.

Different fields in other binary formats may be fixed-width, variable-length, text-encoded, bit-packed, or endian-independent. The existence of a file extension does not eliminate the need to consult its specification. The word “binary” does not imply one global endianness rule.

Signed Numbers and Floating-Point Fields

Signedness determines what numeric value a fixed-width bit pattern denotes; byte order determines how those bits are assembled from individual bytes. Apply both rules in the appropriate order. For example, the two-byte stream FF FE denotes unsigned 0xFFFE when decoded as big-endian: 65,534. Interpreting that 16-bit pattern as two's-complement signed yields −2. In little-endian order, the same two raw bytes denote 0xFEFF, or 65,279 unsigned, and −257 as signed 16-bit two's complement.

That example demonstrates why a parser must not conflate “signed big-endian” with a particular byte-swapping operation. The field definition first identifies which bits form the complete integer and how to read its signed interpretation; conversions to application values follow those rules. Sign extension and truncation have their own requirements, treated separately in the companion article on signed and unsigned binary interpretations.

Floating-point formats also require explicit byte order when represented as multiple bytes, but the encoded bit pattern must additionally follow an agreed floating-point representation, such as IEEE 754 binary32. The common binary32 representation of 1.0 has bit pattern 0x3F800000. That pattern appears as 3F 80 00 00 in big-endian byte order and 00 00 80 3F in little-endian byte order. Interpreting the bytes as a 32-bit integer rather than as a binary32 float would still yield an incorrect physical measurement. IEEE 754 representation and byte order are independent elements of the contract.

Text Encoding, Unicode, and Byte Order Marks

Ordinary ASCII characters and UTF-8 code units are single-byte units; there is no big-endian or little-endian choice for ordering the individual bits within an individual byte. UTF-8 stores a sequence of bytes according to character-encoding rules, and that sequence should not be reversed merely because the machine uses a different native byte order. In contrast, UTF-16 and UTF-32 use multibyte code units whose byte representation can require a defined endian order.

Unicode text streams may use a byte order mark (BOM) to signal certain encoding decisions. In UTF-16, the bytes FE FF indicate a big-endian BOM and FF FE a little-endian BOM. The UTF-8 BOM, when present, is the sequence EF BB BF; it can identify UTF-8 but does not choose a UTF-8 endian variant. Not every text file includes a BOM, and many applications use other metadata or conventions to determine encoding.

The raw stream 41 00 42 00 could represent AB as UTF-16 little-endian (0x0041, 0x0042), but it could also be interpreted as two different 16-bit big-endian code units if declared that way. It is not valid to inspect the stream, assume it is English text, and then declare its endianness without reference to the file's encoding. Character encoding, numeric field byte order, and textual language are separate layers of meaning.

Do not add, delete, or reverse a UTF-16 BOM as a substitute for properly decoding and re-encoding a file. A BOM is not a general-purpose integer-endianness marker and must not be inserted into unrelated binary records.

Byte Order in Python: Explicit Decoding

Python's built-in integer-to-bytes interface provides a concise, portable demonstration. Both int.from_bytes and int.to_bytes require a named order when the example is intended to document a format. The same two bytes can be decoded in different ways without modifying their contents:

raw = bytes.fromhex('12 34 56 78')

big_value = int.from_bytes(raw, byteorder='big', signed=False)
little_value = int.from_bytes(raw, byteorder='little', signed=False)

assert big_value == 0x12345678
assert little_value == 0x78563412

expected = 0x12345678
assert expected.to_bytes(4, 'big') == bytes.fromhex('12 34 56 78')
assert expected.to_bytes(4, 'little') == bytes.fromhex('78 56 34 12')

Python's struct module can also make width and order explicit. The prefix > specifies big-endian standard-format fields; < specifies little-endian standard-format fields; ! specifies network byte order. The format code I means a four-byte unsigned integer under these standard-size conventions. The following assertions illustrate field-by-field decoding:

import struct

payload = bytes.fromhex('02 80 01 02 78 56 34 12')
version, status = payload[0], payload[1]
count = struct.unpack_from('>H', payload, 2)[0]
sequence = struct.unpack_from('<I', payload, 4)[0]

assert (version, status, count, sequence) == (2, 128, 258, 0x12345678)

Use an explicit format and bounds checking in production. struct raises an exception if there are insufficient bytes for a requested fixed-width read, but an application must still validate values, lengths and semantic constraints. Native-mode struct formats may use machine-specific alignment and field sizes, so they are not the default choice for portable disk records.

Byte Order in Windows PowerShell 5.1

PowerShell users can decode a byte sequence without relying on any machine-dependent binary casts. The following arithmetic is deliberately explicit so that a reader can see the mapping from byte positions to numerical weights:

[byte[]]$data = 0x12, 0x34, 0x56, 0x78

[uint64]$big = (([uint64]$data[0] -shl 24) -bor ([uint64]$data[1] -shl 16) -bor ([uint64]$data[2] -shl 8) -bor [uint64]$data[3])
[uint64]$little = (([uint64]$data[3] -shl 24) -bor ([uint64]$data[2] -shl 16) -bor ([uint64]$data[1] -shl 8) -bor [uint64]$data[0])

'{0:X8}' -f $big       # 12345678
'{0:X8}' -f $little    # 78563412

For a portable tool that reads a file from disk, first verify the buffer length and the record version; then extract each field into a byte array and decode it according to its documented order. .NET's System.BitConverter interprets numbers using the host's byte ordering, exposed through [BitConverter]::IsLittleEndian. When its behavior is relevant, a program may branch on that property or use explicit byte shifts. Neither strategy should turn a machine's native order into an undocumented file-format requirement.

The educational purpose of the example is not to recommend manual shifts for all software. It is to establish the invariant: the same raw bytes and the same declared byte-order rule must yield the same value on every correctly implemented reader.

Detecting Incorrect Byte Order

Wrong-endian decoding often produces an integer that is syntactically valid but semantically absurd. A 32-bit field containing the big-endian bytes 00 01 00 00 represents 65,536. If read as little-endian, it becomes 256. A reader checking only whether the value fits in 32 bits will accept both; a stronger validator may use a known version, measured range, expected magic number, or independently known record length to detect a mismatch.

Magic numbers can sometimes identify a format, but must be understood as byte sequences rather than host-ordered integers. In TIFF, the II and MM identifiers explicitly declare the byte order. Other formats may fix the order by specification and provide a fixed signature, making the order discoverable from external knowledge. Guessing an order from whichever interpretation looks plausible is unreliable when both produce permissible values.

Symptom Possible cause Diagnostic action
Count appears 256 instead of 1 Two-byte field decoded in opposite order Inspect raw 01 00 and the field's endian rule
Length field is implausibly large Wrong byte order, offset or field width Cross-check record length and header specification
Integer identifiers change across implementations Native-endian write or read Compare serialized bytes across platforms
Text contains unexpected characters Encoding mismatch, not necessarily integer endianness Confirm UTF encoding, BOM and character rules
One field is correct, another is wrong Record contains fields with distinct rules or offsets Decode the fields independently
A test passes for 00 00 and FF FF Symmetric bytes mask byte swaps Test asymmetric patterns such as 12 34

A productive debugging record preserves the original bytes, their byte offsets, the intended field sizes, and both candidate decodings when diagnosing a suspected mismatch. Re-encoding a corrupted interpretation into another format may erase the evidence needed to identify the original error.

Security and Reliability Implications

Endianness defects are not merely presentation mistakes. An incorrectly decoded length can cause under-allocation, oversize allocation, truncated reads, or incorrectly bounded loops if the program relies on it without validation. A wrong offset can direct a parser into the middle of a payload rather than a valid table. A wrong timestamp, sequence identifier, or checksum field can produce inconsistent records, failed comparisons, and lost synchronization.

A parser for untrusted binary data should reject a length field that extends past the remaining buffer regardless of whether its numerical value fits the declared width. It should verify offset <= buffer_size and length <= buffer_size - offset after checking that offset is in range, rather than calculating offset + length in an integer type that could overflow. The correct byte order is a necessary condition for safe parsing, not a substitute for validation.

Compatibility failures are also common when a program uses raw memory copies of native structures. Differences in byte order, padding, integer sizes and alignment may all affect the output. Portable serialization is a deliberate mapping from typed fields to bytes, and portable deserialization is the inverse mapping under the same versioned specification. Tests should include a reference byte stream that is checked independently of the implementation's round-trip behavior: a writer and reader sharing the same bug can otherwise pass a self-test.

Worked Scenario: A Sensor Record

Suppose a sensor file defines a six-byte record consisting of a two-byte signed temperature value stored in tenths of a degree Celsius, followed by a four-byte unsigned sample counter. Both fields are declared big-endian. The six bytes are:

FF 9C 00 00 01 00

  1. Split the fields by width. Temperature is FF 9C; count is 00 00 01 00.
  2. Assemble each field in big-endian order. The 16-bit temperature pattern is 0xFF9C (65,436 unsigned). The count is 0x00000100 (256 unsigned).
  3. Apply signedness to the temperature. Because its highest bit is one, two's-complement decoding gives 65,436 − 65,536 = −100.
  4. Apply measurement scaling. −100 tenths of a degree is −10.0 °C.
  5. Check constraints. Confirm that the reading is within the sensor's specified operational range and that the counter meets the record's validity rules.

If the same temperature bytes were interpreted as little-endian, the bit pattern would become 0x9CFF and the signed value would be −25,345, or −2,534.5 °C under the same scaling—a plausible machine integer but an unreasonable result for many ordinary sensor installations. The four-byte counter would be interpreted as 65,536 rather than 256. The example illustrates the power of cross-checking decoded values against a field contract and independent domain limits.

A reader should not automatically flip endianness whenever a temperature looks implausible. It should report a malformed or inconsistent record, preserve the raw evidence, and require a defined version or format rule for recovery. Ad hoc guessing can conceal genuine data corruption.

Implementation and Review Framework

When designing or reviewing a binary format, apply the following sequence:

  1. Identify each field: record version, offset, width in bytes, and exact intended data type.
  2. Specify its ordering: a fixed big-endian or little-endian rule, an explicit per-file marker, or a documented alternative for that particular field.
  3. Separate layers of interpretation: byte order first assembles a bit pattern; signedness or float representation assigns a value; scaling and units assign application meaning.
  4. Define validation: minimum buffer sizes, maximum lengths, legal ranges, supported versions, and response to malformed inputs.
  5. Prepare reference vectors: include one-byte values, asymmetric two-, four-, and eight-byte patterns, zero, all-one patterns, negative values, and width boundaries.
  6. Test across implementations: verify that independent readers consume the same known-good bytes; do not rely only on one implementation's writer–reader round trip.
  7. Document portability: do not depend on a runtime's native byte order, default structure packing, or unstated interpretation of text.

A complete format specification ought to say what the bytes mean rather than merely state that they were “generated on a little-endian PC.” Properly defined external representations remain stable when compilers, processors, languages and operating systems change.

Study Questions and Worked Answers

Question 1. A 32-bit value is 0x12345678. What bytes are stored at increasing offsets under each conventional byte order? Big-endian: 12 34 56 78. Little-endian: 78 56 34 12. The integer value remains the same under the corresponding decoder.

Question 2. The raw two-byte stream is 34 12. What is its unsigned interpretation? Big-endian: 0x3412 = 13,330. Little-endian: 0x1234 = 4,660.

Question 3. Does converting a 16-bit integer from little-endian to big-endian reverse the individual bits of each byte? No. It changes which complete byte is placed first. For the intended value 0x1234, the byte pairs are 34 12 and 12 34; each byte retains its original internal bit pattern.

Question 4. Why is a 1-byte status code not “little-endian”? Because endianness refers to relative positions among multiple bytes of one field. The bits in an individual status byte may have separately documented meanings, but there is no within-field byte order to select.

Question 5. Is the TIFF byte order indicated by its II or MM header, or by the local processor? The file header. A compliant decoder follows the file's declaration, even when it differs from the processor's native order.

Question 6. Can a correctly decoded big-endian length field be accepted without any other check? No. A valid integer representation can still specify an out-of-range length, an unsupported record version, or an offset beyond the available buffer. Correct endianness and safe validation are independent requirements.

Question 7. The bytes FF FE denote −2 in which common interpretation? A signed 16-bit two's-complement big-endian field. Read as little-endian signed 16-bit two's complement, the same two bytes denote −257.

Question 8. How can a test distinguish whether a decoder respects byte order? Use an asymmetric reference vector, such as 12 34 for a two-byte field, and assert both the specified output and the exact bytes produced when encoding. Patterns such as 00 00 or FF FF are insufficient on their own.
