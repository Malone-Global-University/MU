Definition and Scope

Signed and Unsigned Binary Interpretations is a Level 5 specialist article within the Binary Data unit of the MGU Computer Science Encyclopedia. It explains how fixed-width bit patterns are assigned integer meanings and why signedness must be specified by a type, file format, protocol, or other authoritative contract. The topic belongs in the Binary Data specialist directory; it is not a separate Data Systems division overview.

The article focuses on unsigned positional values, conventional two's-complement signed integers, arithmetic range boundaries, reinterpretation and conversion, sign extension, and safe parsing. It distinguishes these questions from byte ordering, floating-point representation, text encoding, and general bit-field design, which retain their own specialist treatments.

What Signedness Describes

A binary bit pattern is a sequence of zeros and ones. Signedness is a rule for interpreting that pattern as an integer value: an unsigned n-bit integer represents a nonnegative value from 0 through 2ⁿ − 1, whereas a conventional signed two's-complement n-bit integer represents values from −2ⁿ⁻¹ through 2ⁿ⁻¹ − 1. Neither the bytes nor their order automatically declare which interpretation a reader should apply. A declaration, instruction, schema, file-format field, or application contract supplies that meaning.

For example, the eight bits 11111111 represent the unsigned integer 255 or the signed two's-complement integer −1. Both interpretations are internally consistent. Describing a stored byte as “negative” without specifying its signed interpretation is therefore incomplete. The ability to distinguish bit pattern, representation rule, and mathematical value is foundational to binary-file inspection, programming, networking, and database interchange.

Signedness is not a property of all binary fields. Eight bits can also denote a character-code unit, flags, a color component, an instruction, or part of a floating-point value. Even among integer encodings, two's complement is not the only possible signed rule. This article concentrates on fixed-width integers and does not replace the separate treatments of bit fields, byte order, text encodings, or floating-point formats.

Unsigned Positional Values and Integer Ranges

In unsigned base-two notation, each bit position has a positive place value. Numbering positions from the least significant bit at position zero, an n-bit pattern b[n−1] ... b[1] b[0] has unsigned value Σ b[i] × 2ⁱ. A set bit contributes its corresponding power of two; a clear bit contributes zero. The highest eight-bit place value is 128, followed by 64, 32, 16, 8, 4, 2, and 1.

Thus 10110100 has unsigned value 128 + 32 + 16 + 4 = 180. It fits inside an eight-bit unsigned field because the possible range is 0–255. Sixteen unsigned bits support 0–65,535; 32 unsigned bits support 0–4,294,967,295. These bounds follow from the width, not from a processor model, operating system, or preferred display notation.

Width Unsigned range Signed two's-complement range
4 bits 0 to 15 −8 to 7
8 bits 0 to 255 −128 to 127
16 bits 0 to 65,535 −32,768 to 32,767
32 bits 0 to 4,294,967,295 −2,147,483,648 to 2,147,483,647
64 bits 0 to 18,446,744,073,709,551,615 −9,223,372,036,854,775,808 to 9,223,372,036,854,775,807

A schema that allows a count to be unsigned is saying more than “it is usually positive.” It defines an exact set of representable values and often determines how comparisons, range checks, conversions, and serialization should behave. Negative counts may be invalid by design, but an unsigned type alone does not guarantee that untrusted input is sensible or within an application's permitted limits.

Two's-Complement Interpretation

Two's complement is the dominant representation for fixed-width signed integers in general-purpose computing. For an n-bit pattern, interpret the lower n−1 bits with their ordinary positive weights but assign the most significant bit a weight of −2ⁿ⁻¹. The signed value is therefore −b[n−1] × 2ⁿ⁻¹ + Σ (b[i] × 2ⁱ) for positions 0 through n−2.

For an eight-bit pattern, 01111111 is +127 because the high bit is zero and all seven lower bits are set. The pattern 10000000 is −128 because the high bit contributes −128 and the other bits contribute nothing. The pattern 11111111 is −128 + 64 + 32 + 16 + 8 + 4 + 2 + 1 = −1. The pattern 10110100, interpreted as signed, is −128 + 32 + 16 + 4 = −76. This is exactly 180 − 256, because the unsigned form exceeds the largest signed eight-bit value.

An equivalent decoding rule is especially convenient: first compute the unsigned value U. If the high bit is zero, the signed value is U. If the high bit is one, the signed value is U − 2ⁿ. In eight bits, U = 180 becomes 180 − 256 = −76; in sixteen bits, U = 65,535 becomes −1. This rule applies only when the specified integer representation is two's complement.

Unlike sign-magnitude or one's-complement systems, two's complement has a single representation of zero. Its negative range contains one more value than its positive range, which matters for absolute values and negation. An eight-bit signed integer can hold −128 but cannot hold +128, so attempting to negate −128 within the same signed eight-bit range requires special handling.

A Byte Interpreted Two Ways

The following table shows that the underlying bits never change when the interpretation changes. Hexadecimal is only a compact spelling of the pattern; it does not confer signedness.

Eight-bit pattern Hexadecimal Unsigned integer Signed two's-complement integer
00000000 0x00 0 0
00000001 0x01 1 1
01111111 0x7F 127 127
10000000 0x80 128 −128
10110100 0xB4 180 −76
11111110 0xFE 254 −2
11111111 0xFF 255 −1

Consider a stored temperature sample with byte 0xFE. A format specifying signed eight-bit two's-complement degrees assigns it the value −2. A different format specifying an unsigned eight-bit sensor counter assigns it the value 254. A reader who guesses from the byte alone can turn an ordinary negative temperature into an implausibly high count, or vice versa.

The governing contract must also state any scaling or offset. If a signed raw sample −2 is measured in tenths of a degree, the interpreted measurement is −0.2 degrees; if it is in whole degrees, the measurement is −2 degrees. Signedness controls integer meaning, not measurement units or sensor calibration.

Encoding a Negative Integer in a Fixed Width

To encode a representable negative integer −k in n-bit two's complement, compute 2ⁿ − k and write that nonnegative result as an n-bit pattern. For −37 in eight bits, calculate 256 − 37 = 219. Decimal 219 is binary 11011011, or hexadecimal 0xDB. Reading the same bits as an eight-bit signed integer gives 219 − 256 = −37.

A familiar hand method begins with the positive magnitude 37 (00100101), inverts all eight bits (11011010), then adds one (11011011). This invert-and-add-one method produces the same pattern as the modular calculation. Both require a declared width and a negative value within the signed representable range. The algorithm is a convenient encoding procedure, not a separate physical transformation applied whenever an integer is read.

An exact example shows why the width must be explicit. The sixteen-bit encoding of −37 is 11111111 11011011 (0xFFDB), not merely the eight-bit bytes placed next to unspecified zeros. Likewise, −1 is 11111111 in eight bits and 11111111 11111111 in sixteen bits. A stream that drops its field width loses essential information.

For zero, inversion and addition are unnecessary: the all-zero pattern encodes zero. For the minimum eight-bit signed value −128, the pattern is 10000000; its two's-complement negation within eight bits yields the same pattern, because +128 cannot be represented. Programs must not treat this exceptional case as a valid positive absolute value.

Other Signed Integer Encodings

Two's complement is common, but a binary reader must not silently apply it to every negative number. Historical machines and specialized formats have used other signed encodings. Sign-magnitude uses a dedicated sign bit and unsigned magnitude; one's complement uses the bitwise complement of the positive representation to encode a negative value. Both have distinct positive-zero and negative-zero bit patterns. A biased or offset-binary code stores a value after adding a fixed bias; it may be preferred when comparisons or hardware conventions require that ordering.

For example, under an eight-bit sign-magnitude convention, 10000001 means −1, whereas the same bits mean −127 under two's complement. Under eight-bit one's complement, 11111110 means −1, but under two's complement it means −2. These are not interchangeable. A format that uses a zigzag mapping for variable-length integer codes is different again: it maps signed values to unsigned codes before applying a separate variable-length encoding.

Representation Eight-bit 10000001 Eight-bit 11111110 Zero forms
Unsigned 129 254 One
Two's complement −127 −2 One
Sign-magnitude −1 −126 Positive and negative zero
One's complement −126 −1 Positive and negative zero

The right question is not “Which method does the computer use?” but “Which representation does this specific field require?” A format specification or programming-language type is authoritative. Floating-point values have their own sign, exponent, and significand fields and must not be decoded as ordinary signed integers simply because they also occupy binary words.

Modulo Arithmetic, Wraparound, and Overflow

A fixed-width n-bit adder yields a low n-bit result whenever the full mathematical sum extends beyond n bits. In unsigned modulo-2ⁿ arithmetic, the numerical result is the mathematical sum reduced modulo 2ⁿ. For eight bits, 255 + 1 produces a low byte of 00000000, numerically zero, with a carry beyond the eighth bit. This is a well-defined unsigned wraparound when the language or format specifies modulo arithmetic.

The same low-bit result can be viewed as a two's-complement pattern, but that does not mean every programming language permits signed integer overflow. For eight-bit signed values, 127 + 1 lies outside the valid range −128 through 127. The low eight bits are 10000000, which would decode to −128, yet language and instruction rules decide whether an operation wraps, traps, raises an error, saturates, or has an undefined result. Java defines wrapping behavior for its standard integer operations; Rust provides checked, wrapping, saturating, and overflowing operations and has context-dependent overflow checks; C and C++ require particular care around signed overflow. A portable program must consult the language and operation rather than infer behavior from hardware alone.

The carry flag and signed-overflow flag answer different questions in processor arithmetic. Carry-out concerns unsigned addition at a particular width; signed overflow concerns whether two's-complement operands of the same sign produced a result with the opposite sign. These conditions need not coincide.

Eight-bit addition Low result Unsigned carry-out? Signed overflow? Why
0x7F + 0x01 0x80 No Yes Signed 127 + 1 is out of range
0xFF + 0x01 0x00 Yes No Signed −1 + 1 equals zero
0x80 + 0x80 0x00 Yes Yes Signed −128 + (−128) is out of range
0x01 + 0x01 0x02 No No Both interpretations remain in range

A carry or overflow condition should be interpreted at the specified operation width, not inferred from a later widening conversion or a decimal display of the result. More importantly, applications handling financial amounts, sizes, positions, and counts should ordinarily validate arithmetic before accepting a wrapped value.

Sign Extension, Zero Extension, and Narrowing

When an unsigned field is zero-extended, zeros are placed to the left until the destination width is reached. For example, unsigned eight-bit 0xF6 (246) becomes sixteen-bit 0x00F6 (still 246). When a two's-complement signed field is sign-extended, the original sign bit is replicated on the left: signed eight-bit 0xF6 (−10) becomes sixteen-bit 0xFFF6 (still −10). Widening preserves the numeric value only when the proper extension rule is used.

Original eight-bit pattern Interpretation Sixteen-bit extension Preserved value
01101001 (0x69) Signed or unsigned 0x0069 105
11110110 (0xF6) Unsigned 0x00F6 246
11110110 (0xF6) Signed two's complement 0xFFF6 −10
11111111 (0xFF) Signed two's complement 0xFFFF −1

Narrowing may discard high bits. If a 16-bit raw pattern 0x01FF is reduced to its lowest eight bits, the result is 0xFF. Interpreted as unsigned eight-bit, that is 255; interpreted as signed eight-bit, it is −1. The source integer 511 is not representable in either eight-bit form. A checked numeric conversion should reject it rather than silently rely on truncation. When the intent is explicitly low-bit extraction, document that the operation is truncation, not value-preserving conversion.

A critical distinction is between preserving a value and preserving a bit pattern. Sign extension preserves −10's value but adds one bits; zero extension preserves the original low bits yet changes the value if those bits were meant to be negative. Both can be correct for different data models. Format readers should make the desired property explicit.

Comparison, Division, and Right Shifts

Addition and subtraction often use identical low-bit operations for signed and unsigned inputs, but comparisons behave differently. With eight-bit patterns 0xFF and 0x01, an unsigned comparison finds 255 greater than 1. A signed two's-complement comparison finds −1 less than 1. Sorting a field under the wrong rule can alter record order, access thresholds, or the interpretation of maximum values.

Division also depends on interpretation. Eight-bit pattern 0xFE divided by 0x02 gives unsigned 254 ÷ 2 = 127, whereas signed values −2 ÷ 2 = −1. Integer division's rounding rule for negative, non-exact quotients is language-specific. For example, truncation toward zero and floor division disagree on −3 ÷ 2. A binary format cannot inherit a universal quotient rule merely from storing signed integers.

Right-shift operations illustrate the same problem. Logical right shift shifts in zeros at the high end. Arithmetic right shift replicates the sign bit in a two's-complement operand. Applied to eight-bit 11111110, a logical right shift by one produces 01111111 (127); an arithmetic right shift produces 11111111 (−1 under signed interpretation). Some languages distinguish the two operations explicitly, while others define a result based on type or runtime semantics. Never assume a signed-right-shift rule without checking the relevant language or processor contract.

Conversions Between Signed and Unsigned Types

Some conversions change only how a fixed-width bit pattern is interpreted; others convert a mathematical value and may reject, truncate, wrap, or otherwise transform it. They should not be conflated. In a defined eight-bit reinterpretation, raw 0xFF means unsigned 255 or signed −1. An attempt to convert a numeric 255 into an eight-bit signed type might instead be diagnosed as out of range by a checked API.

C and C++ have intricate integer-promotion and usual-arithmetic-conversion rules; mixing a negative signed value with an unsigned value can change the comparison's meaning. Java has signed primitive integer types and particular unsigned helper operations rather than a conventional unsigned int primitive. Rust uses distinct signed (i8, i16, and so on) and unsigned (u8, u16, and so on) types with explicit checked conversion APIs. These differences are relevant when writing portable parsers or moving data through several languages.

A robust API should specify whether a conversion is checked (reject out-of-range values), saturating (clamp to an endpoint), wrapping (apply modular reduction), or a bit reinterpretation (keep the bits, reinterpret the type). No one of these is a universal default. Use an explicit name or test case for conversions whose meaning is otherwise ambiguous.

For a platform-neutral example of signed decoding, consider this Python function, which accepts a nonnegative raw bit pattern and a declared width. Its arithmetic defines two's-complement interpretation independently of Python's arbitrary-precision integer storage:

def decode_twos_complement(raw: int, width: int) -> int:
    if width < 1 or not 0 <= raw < (1 << width):
        raise ValueError("raw value outside declared width")
    sign_bit = 1 << (width - 1)
    return raw - (1 << width) if raw & sign_bit else raw

assert decode_twos_complement(0xFF, 8) == -1
assert decode_twos_complement(0xB4, 8) == -76
assert decode_twos_complement(0xFF, 16) == 255

The final assertion deliberately demonstrates that width matters: 255 has its sign bit set in eight bits but not in sixteen. This function is an instructional decoding model, not a replacement for production-quality input, size, memory, and schema validation.

Signedness in Binary Files and Protocols

A binary file or wire protocol often carries fixed-width fields in a particular order. The reader needs to know the width, signedness, representation, byte order for multibyte values, and valid range. For a one-byte field, endianness does not affect the result; for multibyte fields it affects which bytes form the integer, but it does not decide whether the resulting value is signed. Those are independent aspects of the contract.

Suppose two bytes are FF FE. If a format specifies a big-endian, signed, sixteen-bit, two's-complement integer, the assembled bit pattern is 0xFFFE, which decodes to −2. If it specifies a big-endian unsigned integer, the same assembled pattern is 65,534. If it instead specifies little-endian, those bytes form 0xFEFF: −257 in signed two's complement or 65,279 unsigned. The reader must resolve byte order before applying the sign rule. Endianness is treated in detail in the next Binary Data specialist article.

Well-designed formats name each field's interpretation rather than relying on an implementation language's native defaults. An integer count stored unsigned in a protocol may still require a smaller application maximum. A timestamp may be signed so that times before an epoch are representable. A sentinel such as −1 must be documented explicitly and must not be mistaken for the largest unsigned value after reinterpreting raw bytes.

Common Failure Modes and Security Implications

Unexpected signed–unsigned conversions can become reliability or security defects when data is used as a length, offset, allocation size, array index, or authorization threshold. A negative value converted to an unsigned size of equal width can become a very large positive value. If a parser trusts that result, it might attempt an excessive allocation, mishandle a bounds check, or compute an offset incorrectly. The correct response is to validate the original value against the application's accepted range before changing its interpretation.

A second failure mode is misclassifying a high-bit pattern as corruption. Raw 0x80 is the valid minimum signed eight-bit value −128, while also being unsigned 128. A format specifying a signed sensor sample should not reject 0x80 just because its most significant bit is set. Conversely, a database adapter should not interpret an unsigned status byte as a signed quantity simply because the host language's byte type is signed.

A third failure mode is using arithmetic overflow as though it were a safe range check. An expression such as offset + length <= capacity may be unsafe if the addition itself can wrap. A safer design first checks that offset is within capacity and then ensures length does not exceed capacity − offset, under a type and arithmetic rule where the subtraction is valid. In security-sensitive parsers, avoid mixing types or evaluating a condition before checking input domains.

A fourth failure mode is missing format versioning. The first version of a field may use signed eight-bit readings; a later version may expand to sixteen bits or change from a sentinel value to an explicit missing-data flag. Without a version tag or migration contract, older readers can silently reinterpret bytes. Boundary tests and format documentation should accompany every such change.

Practical Validation and Boundary Tests

Test signed and unsigned interpretations using values chosen to expose their differences, not only ordinary positive values. For an eight-bit field, exercise 0, 1, 127, 128, 254, and 255 in raw form, then compare the unsigned and signed interpretations. Test that a reader correctly handles −128 and rejects +128 as an eight-bit signed mathematical input. Test that an unsigned input rejects −1 unless a particular protocol deliberately defines a modular conversion.

For arithmetic, include transitions at 127 + 1, 255 + 1, −128 − 1, and −1 + 1, while asserting the behavior specified by the chosen language or operation. For extension, compare raw 0x80 when it is zero-extended to 0x0080 against sign-extension to 0xFF80. For mixed comparisons, explicitly test one negative value against a positive unsigned value.

A short investigation checklist helps keep representation and value separate:

  1. Record the raw bit sequence and its exact width.
  2. Identify the field specification or variable type that gives it meaning.
  3. Determine the integer encoding: unsigned, two's complement, sign-magnitude, biased, or another declared rule.
  4. Assemble multibyte values in their specified byte order, where applicable.
  5. Decode the value, then enforce the application's valid range and units.
  6. Inspect conversions, arithmetic, comparisons, shifts, and narrowing for sign or range changes.
  7. Preserve representative boundary cases in automated tests.

The underlying lesson is methodological: never infer a mathematical value solely from the appearance of its bits. Width, signedness, encoding, and context must travel together for binary data to be interpreted accurately and safely.

Study Questions and Worked Answers

Question 1. What are the signed and unsigned eight-bit interpretations of 10010110? As unsigned, the bits total 128 + 16 + 4 + 2 = 150. As eight-bit two's complement, subtract 256 to obtain −106.

Question 2. Encode −18 in eight-bit two's complement. Compute 256 − 18 = 238, which is 11101110 (0xEE). Decode it by subtracting 256 from 238 to recover −18.

Question 3. A reader obtains the sixteen-bit raw pattern 0x00FF. What is its signed value? It is 255, because bit 15 is zero. Reinterpreting only its low eight bits as a signed eight-bit quantity would instead yield −1. Width changes the interpretation.

Question 4. Does a processor's low eight-bit result 0x80 prove that the arithmetic operation overflowed? No. A low result alone does not reveal operand widths, the interpreted signedness, or the original operands. For example, unsigned 127 + 1 is a valid 128, whereas signed eight-bit 127 + 1 is out of range.

Question 5. Why is 0xFF a poor undocumented missing-value marker? Depending on its contract it may be 255, −1, an all-flags-set status, or an ordinary byte in a larger payload. A missing-value convention requires an explicit type, width, reserved value, and validation rule.
