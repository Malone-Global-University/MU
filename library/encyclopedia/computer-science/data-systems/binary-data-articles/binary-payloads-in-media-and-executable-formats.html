Definition, Purpose, and Place in the Encyclopedia

Binary payloads in media and executable formats are byte sequences that a file-format contract identifies as image samples, compressed audio or video units, machine instructions, constants, resources, or other specialized content. Such bytes rarely stand alone. A file normally supplies enough surrounding structure to establish what kind of payload it contains, where the payload begins and ends, and which interpretation rules a compatible reader should apply. Headers, chunks, box trees, tables, offsets, flags, and metadata turn an otherwise ambiguous collection of bytes into a usable format.

The central claim is deliberately narrow: a signature identifies a candidate container; structural fields locate candidate payloads; a declared format and its decoder or loader assign meaning. A reader cannot infer “this is a photograph” or “these are executable instructions” merely from a run of high-entropy bytes. Compressed pictures, encrypted documents, media frames, and program code can all look irregular in a hex viewer. Their roles emerge from format contracts and trusted analysis of the surrounding structures—not from the appearance of the bytes alone.

This Level 5 article belongs to the Binary Data overview and the Binary Data specialist directory. It complements Binary File Headers and Magic Numbers, Binary Serialization and Schema Contracts, and Typed Binary Views and Contextual Meaning. Rather than teaching a complete image codec, audio codec, instruction set, or operating-system loader, it compares how these disciplines package, identify, locate, and interpret payload bytes.

Learning Outcomes and Governing Questions

After studying this article, a reader should be able to annotate a binary container as a sequence or tree of structured regions; distinguish descriptive metadata from media data or executable contents; interpret offsets and lengths without assuming they are native-memory pointers; and explain why successful file identification is weaker than format validation or trust. The reader should be able to compare a fictional bitmap, an audio file, and an executable image by their signatures, size fields, metadata, and opaque payload regions.

The governing questions are: Where is the boundary? A parser must know exactly which byte range belongs to a field or a payload. What makes it meaningful? A decoder, codec, or instruction-set and loader contract must explain how those bytes are consumed. What can change without changing the apparent content? Metadata order, compression settings, container layout, and executable loading addresses may vary. What does successful inspection prove? Usually that selected structural checks passed, not that a picture is safe, a media stream is decodable, or a program is trustworthy.

The recurring discipline is to record a claim at the correct level: observed bytes, parsed structural fields, interpreted payload, or validated behavior. Confusing these levels leads to brittle readers and overconfident investigation reports.

The Common Container–Payload Model

A container is a higher-level representation that organizes one or more payloads. In simple formats the container may be a fixed header followed by a single contiguous payload. In extensible formats it may contain multiple typed chunks, nested boxes, variable-size tables, or regions whose offsets are found through separate indexes. The same conceptual split applies to images, audio, video, executable programs, archives, and database pages, but it does not imply that all those formats have identical semantics or validation requirements.

Structural element Typical role Example Reader's question
Signature or magic Suggests a format family PNG eight-byte signature, ELF 7F 45 4C 46 Are these the expected initial bytes?
Global header Declares version, class, type, geometry, or layout Image width and height, executable machine class Can the declared variant be supported?
Chunk or box descriptor Delimits a typed region PNG IHDR, RIFF data, MP4 mdat Does the declared region fit in the file?
Index or offset table Locates payload or related metadata ELF program headers, sample tables in timed media Are offsets relative to the correct base?
Payload Holds application-specific encoded content Filtered pixel samples, PCM audio, machine code Which decoder or loader interprets it?
Integrity or authenticity data Supports particular validation goals PNG CRC, application code signature What exact bytes and claim are covered?

Container and payload are relative terms. A compressed video sample is the payload of an mdat media-data box, but that sample has internal codec syntax of its own. A PE executable's resource section can contain an icon with a separate image structure. A RIFF container can have nested list chunks. A file that looks flat at one level can contain several more structural layers when interpreted under the relevant standard.

Byte Offsets, Lengths, and Scope

An offset identifies a position relative to a designated base, often the start of the file, start of a chunk's content, or start of another region. A length states how much data belongs to a region, but format rules determine whether the length includes a descriptor, type code, padding, or checksum. A reader must not assume all formats count the same units. PNG chunk lengths describe chunk data bytes and exclude the length field, type, and CRC. In a conventional RIFF chunk, the size field describes the data, while an odd-sized chunk's data may be followed by an alignment pad. An ISO base media box usually declares its own total size, including its initial box header, subject to special-size forms.

Suppose a parser encounters an offset 0x200 and length 0x80. It cannot safely compute “payload ends at 0x280” until it knows the offset's base, the integer widths, and whether the calculated region stays within the enclosing allocation. For an untrusted unsigned value, robust bounds checking uses the pattern start <= file_length and size <= file_length - start, after separately rejecting any invalid base arithmetic. This subtraction-based comparison avoids relying on an addition that may overflow a fixed-width integer.

A second subtlety is address space. A file offset means a byte position within stored content. A virtual address or relative virtual address (RVA) in an executable represents a location or displacement in a loaded memory image. They are not interchangeable. Alignment, zero-filled memory, or section placement can make a file offset and its corresponding in-memory address very different. This article marks that distinction whenever executable formats enter the analysis.

Representation Layers: Raw Samples, Encoded Samples, and Packaging

For media, the word image can refer to pixels in memory, a compressed image codestream, or a file containing that codestream and its metadata. For audio, it can mean numerical samples, a compressed sequence of audio frames, or a container holding tracks and timestamps. For executables, it can mean instruction bytes on disk, relocatable code sections, or an installed process image with memory mappings, relocations, and loaded libraries. These are different layers, each described by a different contract.

Domain Logical content Common encoded payload Surrounding structure Consumer
Raster image Spatial arrangement of color samples Filtered/deflated PNG image data; JPEG compressed scan Dimensions, color information, chunk or marker structure Image decoder
Waveform audio Samples ordered by time and channel PCM sample bytes or compressed audio frames Sample-rate and channel metadata, chunk boundaries Audio decoder and renderer
Timed audiovisual media Multiple synchronized tracks Encoded audio and video samples Track metadata, sample tables, timing, box hierarchy Demultiplexer then codecs
Executable image Program instructions and linked data Machine-code and constant regions Architecture and loading metadata, sections or segments Linker/loader and CPU

The outer file does not always contain a literal “list of pixels” or “list of audio samples.” A compressed encoder changes representation; a decoder must recover the intended image or audio according to codec rules. Similarly, a program's instructions may be translated, relocated, demand-paged, or accompanied by non-code data before execution. Understanding these transformations prevents the mistake of treating a media or executable file as one uninterpreted stream of raw samples or opcodes.

Fictional Format A: The SIMG Bitmap Container

Define an illustrative, nonstandard bitmap format named SIMG for teaching. It represents a two-pixel image with 24-bit RGB samples. The first four bytes are ASCII SIMG; the next byte is version 01; the next byte is channel count 03; bytes 6–7 hold image width as an unsigned 16-bit big-endian integer; bytes 8–9 hold height in the same form; bytes 10–13 hold the payload length as an unsigned 32-bit big-endian integer. The payload begins at byte offset 14 and stores uncompressed R, G, B triples in row-major order.

Offset Width Hex bytes Declared meaning
0 4 53 49 4D 47 Invented SIMG signature
4 1 01 Version 1
5 1 03 Three channels per pixel
6 2 00 02 Width = 2 pixels
8 2 00 01 Height = 1 pixel
10 4 00 00 00 06 Payload = 6 bytes
14 6 FF 00 00 00 00 FF Red pixel, then blue pixel

The six payload bytes are not self-describing. The header declares enough for this simple example to map them to two pixels. It also allows a minimal length check: expected payload bytes equal width × height × channels, or 2 × 1 × 3 = 6. A production specification would additionally define permitted dimensions, maximum allocations, color-space rules, row stride, optional metadata, byte order, and extensibility. No real application should infer that SIMG is a registered file format.

Worked Comparison: Container Bytes Versus Decoded Pixels

The SIMG file occupies 20 bytes in this example: 14 bytes of header and 6 bytes of pixel data. A program may decode it into a pixel array or a graphics surface with a different stride, channel order, or alignment. For instance, an in-memory graphics API might use four bytes per pixel with an alpha channel or place rows at padded boundaries. Thus an image with two pixels and six encoded bytes can occupy eight or more bytes in a particular in-memory representation.

This is not corruption; it is a difference in representation. An application should compare decoded pixel values when asking whether two image files display the same image. It should compare bytes when asking whether two files are exact copies. Two files can render the same pixels yet differ in metadata, compression settings, byte order, or encoded structure. Conversely, two files can share a header signature but encode incompatible or corrupted image content.

The example also illustrates a capacity hazard: a malicious header could advertise dimensions so large that their product overflows or demands enormous memory. Validation must enforce separate width and height limits, multiply using an adequately wide integer, and bound the resulting allocation before decoding. The declared payload length is a field to validate—not evidence that the corresponding bytes really exist or are safe to process.

PNG as a Real Chunk-Based Image Format

Portable Network Graphics (PNG) provides a useful contrast to the fictional fixed header. A PNG datastream starts with the eight-byte signature 89 50 4E 47 0D 0A 1A 0A; it then contains typed chunks. A chunk is represented as a four-byte big-endian data length, a four-byte ASCII type code, that many data bytes, and a four-byte CRC covering the type code and data. The signature itself is not part of an ordinary chunk. A conforming PNG has IHDR first, one or more IDAT chunks, and a terminating IEND chunk, with other allowed chunks depending on image properties.

The IHDR chunk carries dimensions and representation parameters, including bit depth, color type, compression method, filter method, and interlace method. The IDAT data carries pieces of the compressed datastream; image reconstruction requires decompression and the prescribed processing of scanline filters. An IDAT payload is therefore not a direct raster of RGB triples that a generic hex viewer can read. Ancillary chunks can carry additional information, but readers must respect PNG's critical/ancillary handling rules rather than silently assuming every unknown chunk is expendable.

Element Illustrative hex or name Observation
File signature 89 50 4E 47 0D 0A 1A 0A Recognizable PNG identifier
First chunk length 00 00 00 0D IHDR data is 13 bytes
First chunk type 49 48 44 52 = IHDR Must be first PNG chunk
Image data One or more IDAT chunks Contains parts of compressed image datastream
Terminal chunk IEND Marks end of PNG datastream

These details follow the W3C PNG specification. A matching signature is insufficient validation: a robust decoder must check chunk structure, bounds, required ordering, CRC behavior appropriate to its policy, and supported image parameters. A CRC detects certain accidental corruption; it is not a cryptographic authentication mechanism and does not establish provenance or benign content.

JPEG and the Difference Between Markers and Raw Image Data

JPEG is not one simple flat “header plus pixels” layout. The common JPEG interchange codestream uses markers such as start-of-image FF D8, start-of-frame definitions, quantization and entropy-coding tables, start-of-scan markers, and end-of-image FF D9. Application-specific metadata can also be carried in marker segments, for example EXIF or other application information in recognized conventions. Entropy-coded scan data requires JPEG-specific decoding; it is not a planar array of pixel samples simply because it appears between markers.

The marker structure raises an important lesson about self-delimiting syntax. Some marker-associated segments contain declared lengths; encoded scan content uses special rules governing markers and byte stuffing. A general-purpose parser that scans for a simple byte sequence without understanding those rules can misidentify boundaries. JPEG decoding itself may yield different in-memory component layouts and colorspace conversions depending on the decoder and requested output representation.

Compared with PNG, JPEG often emphasizes lossy compression under common image profiles, whereas PNG is normally used for lossless image representation. That difference describes the coding relationship between an original image and its reconstruction, not whether the files are “binary.” Both are binary formats. Neither can be judged valid or safe solely by its extension or by observing a familiar signature at its start.

Fictional Format B: The SAUD Audio Container

Define a second fictional educational format, SAUD, carrying uncompressed signed 16-bit mono PCM samples. Its four-byte signature is ASCII SAUD. Byte 4 declares version 01; byte 5 declares channel count 01; bytes 6–9 declare an unsigned 32-bit big-endian sample rate; bytes 10–11 declare bits per sample; and bytes 12–15 declare an unsigned 32-bit big-endian payload size. From byte 16 onward, sample payload consists of signed 16-bit little-endian integers, an explicitly declared choice independent of the header's byte order.

Offset Width Hex bytes Interpretation
0 4 53 41 55 44 Fictional SAUD signature
4 1 01 Version 1
5 1 01 One channel
6 4 00 00 1F 40 8,000 samples/second
10 2 00 10 16 bits per sample
12 4 00 00 00 08 Eight payload bytes
16 8 00 00 FF 7F 00 80 01 00 Four signed 16-bit little-endian sample values

The decoded sample values are 0, 32767, -32768, and 1. That is four sample frames in mono, not eight. At 8,000 sample frames per second, their nominal duration is 4 / 8000 = 0.0005 second. The example's header occupies 16 bytes; its payload occupies 8; the entire illustrative file occupies 24 bytes. These are not standard audio-file bytes and should not be fed to a WAVE decoder as if SAUD were WAVE.

This tiny example separates three independent questions: which bytes are the PCM payload, how each signed value is represented, and how sample rate and channels supply a time axis. A parser that gets the payload bytes right but ignores the channel count can still produce the wrong playback interpretation. A parser that guesses integer byte order from the host CPU can produce wildly incorrect sample magnitudes.

RIFF/WAVE as a Real Audio Container

WAVE commonly uses the Resource Interchange File Format (RIFF), a chunked architecture. A conventional little-endian RIFF WAVE file starts with ASCII RIFF, a four-byte little-endian RIFF size, and ASCII WAVE, then contains subchunks such as fmt and data. The four-character fmt identifier has a trailing ASCII space. The fmt chunk provides coding parameters, for example format type, channel count, sample rate, and other relevant layout data; the data chunk holds sample data under that description. Other chunks can occur, and a reader must not assume that audio data always begins at offset 44.

For simple uncompressed PCM, a frame contains one sample value for each channel at one time position. The block alignment for conventional interleaved PCM can be computed from the channel count and bytes per sample, subject to the exact format variant. With 16-bit stereo PCM, one sample frame typically occupies four bytes: two bytes for the first channel and two for the second. sample_rate × block_align gives nominal byte rate for this representation. Compressed WAVE variants require the rules of the declared codec and cannot always be evaluated by a naive PCM formula.

WAVE component Usual meaning Pitfall
RIFF Little-endian RIFF container identifier in conventional WAVE Do not assume every RIFF-derived variant is identical
RIFF size Size of following RIFF data Not automatically equal to physical file length minus 8 in malformed files
WAVE Identifies WAVE form type RIFF is a family, not a synonym for WAVE
fmt Describes sample encoding Contents vary with audio format and extensions
data Carries actual coded audio data May not be the first subchunk after fmt
Padding byte Aligns odd-sized subchunk content Not part of that chunk's declared data length

Microsoft's RIFF description and RIFF file-I/O documentation provide the underlying convention. Large-file extensions and additional metadata standards exist; do not treat the simple RIFF layout as a universal limit on all professional audio systems.

Audio Payload Interpretation: Sample Rate, Channels, and Endianness

A byte sequence that makes a plausible waveform in one format may yield noise or invalid output under another. An 8-byte array can hold four 16-bit mono samples, two 16-bit stereo frames, or eight 8-bit mono samples, before considering compression. A sample rate determines temporal spacing, not the numerical meaning of the samples. Audio channel assignment determines which positions represent left, right, center, and other channels. Sample type determines signedness and scaling: integer PCM and floating-point samples do not share the same numerical interpretation.

A WAVE file with a fmt descriptor should drive decoding. Do not infer bit depth from file size alone or assume that every 16-bit-looking byte pair is a sample. Metadata, alternate chunks, or compressed data may occupy some or most of the file. The same caution applies to video where the elementary coded frame data is generally separate from the track timing tables that make playback coherent.

An audio file can be byte-correct yet produce undesired sound because the player uses the wrong format metadata; conversely, different compressed files can reconstruct subjectively or mathematically equivalent audio while having entirely different bytes. Fidelity, lossless reversibility, and byte identity are separate criteria. A diagnostic workflow should first check declared format and boundaries, then decode according to the correct specification, then compare audio samples if a content-level comparison is desired.

Timed Media: From Audio and Video Samples to Tracks

A multimedia container can hold several time-dependent streams, such as video, one or more audio languages, captions, and metadata. Those streams may use entirely different codecs and timing units. The container therefore needs more than an image width and a payload count: it may need track identifiers, decoder configuration, sample locations, synchronization information, time scales, and mappings from decode order to presentation order. A single output picture may depend on earlier reference pictures in a compressed video stream.

A useful conceptual pipeline is container reader → track demultiplexer → elementary stream decoder → synchronized playback. The demultiplexer locates the encoded audio or video samples and associates timestamps and parameters with them. The codec understands syntax inside each sample and reconstructs audio or picture data. A renderer then presents decoded content under timing and output-device constraints. Parsing a container does not, by itself, decode a codec; knowing a codec name does not, by itself, find sample bytes inside a container.

Some containers are designed for streaming, random access, editing, or interoperability under different constraints. An index that enables seeking may reside far from the media bytes. A file can be structurally parseable without containing a supported codec. Conversely, a decoder might support a codec but not recognize a particular wrapping format. Tools should report these as separate support capabilities.

ISO Base Media File Format: Boxes, moov, and mdat

The ISO Base Media File Format (ISOBMFF) underlies families such as MP4 and other related formats. Its core structural concept is the box: a region with a size and a four-character type, with rules for extended sizes and special cases. Boxes can nest. An ftyp box, where used, identifies file-type/compatibility information; a moov box contains presentation and track metadata; mdat carries media sample data. It would be inaccurate to say every file has a fixed order of these boxes or that mdat alone tells a parser the timing and coding meaning of every byte in it.

In many presentations, metadata tables relate sample sizes, time stamps, and locations to bytes in media-data regions. Thus reading a moov structure may identify a video sample's location inside an mdat without that sample having a separate visible VIDEO label directly before it. The same file may contain audio and video interleaved in a way that benefits playback. Moving or changing metadata without updating offset references can render a file unusable even though the encoded media samples are still present.

ISOBMFF concept Function What it does not guarantee
Box size and type Identify and bound a typed region Semantic validity of child data
ftyp State brand/compatibility information That every advertised codec is supported
moov Describe presentation and tracks That all referenced samples exist and are decodable
mdat Store sample data Meaningful playback without metadata and decoders
Sample tables / indexes Relate timing and byte locations Safe offsets unless checked against file bounds

See ISO/IEC 14496-12:2026 and the Library of Congress format description. An engineer should consult the exact brand and media-profile specifications for format-specific behavior rather than extrapolate every rule from this simplified box model.

Executable Files Are Structured Images, Not Just Opcode Streams

An executable file or loadable program image contains enough information for operating-system and runtime mechanisms to interpret a program's code and data. A compiled instruction stream alone does not normally describe the target CPU, entry point, initialized data, memory permissions, location of imports or dynamic dependencies, and placement rules. Executable file formats therefore act as contracts between build tools, linkers, loaders, operating systems, and sometimes debuggers.

An executable can carry machine instructions, initialized variables, read-only literals, relocations, imported-symbol information, exception handling tables, dynamic-link metadata, resources, and optional debug information. Some content belongs in memory at execution time; other content is needed only to establish the image or support development and diagnostics. A loader generally reasons about loadable regions and mappings, not simply “read every byte into memory and jump to the beginning.” Some regions are zero-initialized in memory without equivalent stored bytes for their full in-memory extent.

Importantly, file structure is not authority to execute. An analyst can safely examine selected bytes without running a program, and a cautious reader should prefer this non-executing mode for files from unknown sources. Whether a file can execute also depends on architecture, runtime, permissions, signatures or policy checks, dependencies, and platform support. The presence of an ELF or PE signature is not a statement of trust.

Fictional Format C: The SXEC Executable Teaching Image

Define a fictional executable-like representation, SXEC, to illustrate file-to-memory mapping without teaching an instruction set. Its 24-byte header consists of a four-byte SXEC signature; a one-byte version; a one-byte architecture identifier; a two-byte big-endian region count; a four-byte big-endian table offset; a four-byte big-endian entry-point relative virtual address (RVA); and eight reserved zero bytes. Following this header is a table of fixed-width region descriptors. Each descriptor includes a file offset, file byte size, memory RVA, memory size, and permission flags. The model is not recognized by real operating-system loaders, and its example “code” is merely opaque bytes.

Header offset Bytes Interpretation
0–3 53 58 45 43 Invented SXEC signature
4 01 Example version 1
5 01 Fictional machine identifier
6–7 00 02 Two regions
8–11 00 00 00 18 Region table begins at file offset 24
12–15 00 00 10 00 Entry RVA 0x1000
16–23 eight 00 bytes Reserved

The descriptors are conceptual: one region maps a few opaque instruction-like bytes at RVA 0x1000 with read/execute permission; another maps literal data at RVA 0x2000 with read-only permission. The table is file metadata, not a third runnable instruction region. In a real executable the loader must also enforce allowed segment placement, architecture rules, relocation policies, page permissions, and many other conditions. This fictional layout merely demonstrates that code bytes cannot be interpreted meaningfully without an architecture and location contract.

The decisive point is offsets are not addresses. If a descriptor says “file offset 80, memory RVA 0x1000,” the first byte of that region is stored at file byte 80 but becomes associated with a different coordinate in a loaded memory image. A program counter operates on the mapped runtime address, not on the file's byte offset. The example avoids presenting invented opcodes as valid machine code, so readers do not accidentally treat a mock teaching format as an executable recipe.

ELF: Identification, Program Headers, and Sections

The Executable and Linkable Format (ELF) is widely used in Unix-like environments. ELF files begin with an identification sequence whose first four bytes are 7F 45 4C 46 (0x7F followed by ELF). Identification fields specify, among other things, the 32-bit or 64-bit class and data encoding convention. The main ELF header supplies structural coordinates such as the offsets of the program header table and section header table, as applicable to the particular ELF object type.

These tables serve different audiences. Program headers describe segments and related properties important for loading an executable or shared object; section headers describe an organization useful for linking, relocation, and inspection. Sections need not correspond one-for-one to loadable segments. Some ELF images can be loaded without relying on a complete section-header table; a tool should not demand that every loadable executable has a rich .text/.data section inventory just because common developer-built files usually do.

ELF structure Typical content Interpretation rule
e_ident Magic, class, endianness, version identifiers Verify class/data conventions before reading fields
ELF header Object type, machine, entry, table coordinates Interpret according to class and data encoding
Program headers Loadable regions and other segments Relevant to how a loader constructs memory image
Section headers Named logical sections and attributes Useful to tooling; not identical to load mapping
Section or segment bytes Code, data, symbols, relocations, strings Interpretation depends on declared section/segment type

The System V ABI ELF specification and the Linux elf(5) manual page explain these structures. Do not assume ELF always means little-endian or 64-bit, and do not read a machine-dependent field with the host architecture's defaults. Validate offsets and record sizes before dereferencing a table. A matching four-byte magic is one preliminary observation, not sufficient ELF validation.

PE/COFF: Windows Executables and Their Layered Header

Portable Executable (PE), related to COFF conventions, underlies many Windows executable and DLL images. A common PE image begins with a DOS-compatible MZ signature; its DOS header contains a field conventionally named e_lfanew at file offset 0x3C. The field gives the file offset of the PE header, where the four-byte PE\0\0 signature appears. A COFF file header follows, along with the PE optional header for an image and a section table. The term optional header is historical terminology: for a PE executable image it carries essential loader information.

Section records describe properties such as virtual size, RVA, raw data size, file pointer to raw data, and characteristics. A section may have a larger memory extent than its stored contents because some runtime bytes are zero-initialized. Import metadata can describe linked DLL functions; resources may include images or localized strings; relocation data can assist loading at an alternate base. A file's physical order and its in-memory mapping need not be the same.

PE element What a reader observes Correct interpretation
MZ at file start DOS-compatible initial signature Does not alone prove valid PE
e_lfanew File offset to subsequent PE header Must fit within file and be checked before use
PE\0\0 PE signature Validate when reached, not by a blind fixed offset guess
COFF header Machine, sections, flags Helps identify image class and scope
Optional header Magic and memory-image fields PE32 and PE32+ variants differ
Section table Raw-file coordinates and memory RVAs File offset and memory coordinate are different

Microsoft's PE format specification is the authoritative starting point for these details. A PE image may contain many other structures; this cross-format article highlights how the container locates possible code and data, rather than attempting to teach full Windows loading, import resolution, or code-signing policy.

Why File Offsets Are Not Runtime Addresses

Imagine a hypothetical PE section with a raw data pointer of 0x400, an RVA of 0x1000, and a raw file size of 0x200. A byte at file offset 0x410 is 16 bytes into that region. Its corresponding RVA, under this simple mapping, is 0x1010. A loaded virtual address adds the image load base to that RVA, subject to platform and loader behavior. The stored byte does not literally “live at address 0x410” when the program runs.

Quantity Example Coordinate system
File offset 0x410 Bytes from start of file
Section raw start 0x400 File offset from a section header
Offset inside section 0x10 0x410 - 0x400
Section RVA 0x1000 Relative to loaded image base
Computed RVA 0x1010 0x1000 + 0x10

That is a teaching calculation, not a general RVA converter for all PE inputs. Section sizes, alignment, headers, overlaps, and malformed mappings complicate real files. A safe implementation checks whether an RVA is actually inside the correct mapped region and whether the represented bytes exist. In ELF, a segment likewise has both file-related and virtual-memory-related coordinates. Treat them as separate fields even if an illustrative executable happens to place them at conveniently related numbers.

This distinction matters in software analysis, crash reporting, patch application, debugging, and security. Someone who confuses file and memory offsets can read the wrong bytes, misreport a code location, or write a corrupt output file. In trusted tooling, always state which coordinate space a number belongs to.

Sections, Segments, Code, Data, and Resources

File formats have multiple ways to organize content. An ELF section describes a logical part of an object, while an ELF segment groups material for the program loader. PE uses sections for loading-oriented storage/mapping descriptions. These similarly named objects are not interchangeable across specifications. A section or segment may contain instructions, constants, writable data, or structures consumed by a runtime system rather than directly executed.

An executable's text-like region often contains machine instructions; a read-only region may hold literal strings or tables; a writable data region may contain initialized variables. Relocations may specify where values must be adjusted; a dynamic import directory or symbol table may guide linking or diagnostics. A zero-fill region reserves in-memory storage that is not backed by equal-length initialized file bytes. Therefore even an executable that advertises a single entry point is not accurately modeled as one contiguous byte stream of opcodes.

Executable resources illustrate nested containers. A program can embed icon images, dialog templates, version information, or other data. An image inside a resource is a payload nested within an executable container. The executable loader need not treat those image bytes as instructions; separate resource APIs and image decoders handle them. Being embedded inside an executable does not magically convert an image into machine code.

Architecture, Instruction Sets, and Decoder Contracts

Machine-code bytes receive meaning through an instruction set architecture (ISA) and execution context. A sequence accepted as one machine's instruction encoding may be invalid or mean something different on another architecture. An ELF or PE header can identify the intended machine class, but that declaration must be interpreted alongside the platform's supported ABI, modes, and loader requirements. Byte ordering rules for multi-byte structural fields do not themselves describe every instruction encoding detail.

Disassemblers depend on a valid starting location and instruction interpretation mode. In variable-length instruction sets, a byte sequence can yield different apparent instructions when decoding begins at a different offset. A data region might accidentally resemble plausible opcodes. For that reason a naive “scan for instructions” pass can misclassify literal values, compressed resources, or encrypted data. The container's metadata is a starting point, not infallible evidence about every byte's role.

The deeper subjects belong to Instruction Set Architecture and machine-code encoding and disassembly, rather than to this structural comparison. The generalizable binary-data lesson is that payload bytes are interpreted under a typed contract. There is no interpretation-free reading of a “code section” any more than there is a context-free reading of a compressed IDAT stream as a picture.

Three Fictional Files Compared Side by Side

The fictional SIMG, SAUD, and SXEC teaching formats offer a controlled comparison because each declares exactly which bytes are metadata and which are payload. They have distinct purposes and intentionally incompatible contracts. SIMG follows a 14-byte header with RGB pixel bytes. SAUD follows a 16-byte header with little-endian signed PCM sample bytes. SXEC uses a header and a region table to locate code-like and data-like regions at file coordinates while describing their intended memory positions.

A Unified Binary Inspection Procedure

When examining a media or executable file of unknown provenance, begin with the bytes rather than the filename. Record total file length, a bounded initial hex sample, and the visible signature. Form a tentative format hypothesis. Then consult the exact specification for the declared version and variant. Read only a minimal validated header, checking each field's width, byte order, and base. Establish the extents of each chunk, box, or table entry using safe arithmetic and the outer file's known size.

Next classify regions as metadata, index, encoded payload, unused padding, or unknown—not as “junk” merely because their bytes do not display as text. Follow offsets and nested structures while applying recursion, count, and size limits. For media, distinguish container-level success from codec-level success. For executables, distinguish a recognizable program image from whether its machine type, memory-mapping requirements, or import dependencies can be fulfilled. Prefer static inspection when the source is untrusted.

Stage Evidence to collect Stop condition
Inventory File length, acquisition source, optional whole-file digest Empty or inaccessible file
Candidate identity Initial bytes, relevant signatures Signature absent or inconsistent with hypothesis
Header interpretation Width, version, endianness, variant Unsupported or contradictory field values
Region boundaries Offsets, lengths, parent-child containment Overflow, overlap forbidden by format, out-of-bounds
Payload classification Codec, instruction architecture, resource type Unsupported or conflicting declared interpretation
Specialized validation Decoder/loader compatibility; integrity checks Truncation, invalid structure, unsupported feature
Reporting Observed facts, assumptions, limitations Never promote a guess into certainty

These steps are observational. They do not require launching a file, invoking a script embedded in it, or extracting and executing any component. A good investigation preserves original bytes and performs analysis on controlled copies.

Worked Real-Format Exercise: A PNG's First Chunk

Take a PNG whose first 16 bytes begin 89 50 4E 47 0D 0A 1A 0A 00 00 00 0D 49 48 44 52. The first eight are the signature. Bytes 8–11 are a 32-bit big-endian chunk-data length of 13; bytes 12–15 spell IHDR. The reader can now compute the first chunk's total size as 4 length + 4 type + 13 data + 4 CRC = 25 bytes, so this chunk occupies file offsets 8–32 inclusive. The next chunk, if any, would begin at offset 33. This calculation does not yet know the image width or height; those are encoded within the 13-byte IHDR data.

Byte offset range Width Interpretation
0–7 8 PNG signature
8–11 4 Big-endian chunk data length = 13
12–15 4 Chunk type IHDR
16–28 13 IHDR data: dimensions and format parameters
29–32 4 CRC covering IHDR type and data
33 onward variable Subsequent chunks subject to PNG rules

An investigator must not claim the file is a valid PNG solely because these 16 bytes match. The remaining bytes might be missing, the CRC might be incorrect, the dimensions might be invalid, or required IDAT and IEND chunks might be absent. This is a boundary exercise, showing how fixed-width structural fields permit disciplined advancement through a binary stream.

Worked Real-Format Exercise: A Simple WAVE File

A common simple PCM WAVE representation has the outer four-character RIFF marker, a RIFF-size field, WAVE form type, a fmt chunk, and a data chunk. Many educational examples place these structures in an immediately sequential 44-byte header followed by audio samples, but that 44-byte pattern is a common case, not an unconditional WAVE specification. Additional LIST, JUNK, fact, extended-format, or other chunks can shift the data payload's offset. A parser must walk chunks under RIFF size and alignment rules instead of hard-coding sample offset 44.

For a simple mono PCM file with a sample rate of 8,000 Hz and 16-bit samples, the payload of four samples is eight bytes and represents 0.5 milliseconds. Assuming the common 16-byte PCM fmt chunk, the outer RIFF structure can occupy 52 bytes: 12 bytes of container header + 24 bytes for fmt chunk (8 header + 16 data) + 8 bytes of data header + 8 sample bytes. In such a minimal example, the RIFF size field is 44, because it excludes the leading 8 bytes of the RIFF chunk header.

The arithmetic is precise only under the stated simplified conditions. Some legitimate WAVE files contain more metadata, extended headers, or different encoding representations. Accordingly, tools should derive sample duration from validated format parameters and the decoded stream semantics, not simply divide total physical file length by a guessed byte rate.

Worked Executable Exercise: PE Header Location

Consider a file beginning with 4D 5A (MZ) and containing a four-byte little-endian value at file offsets 0x3C through 0x3F. If that value is 0x00000080, a tentative PE parser should seek to offset 0x80 and check for 50 45 00 00 (PE\0\0), after establishing that the file is long enough to hold the header and required following fields. A field's claim that its next structure begins at 0x80 does not authorize a read if the file ends at 0x40.

This exercise illustrates a pointer-like file offset, not a pointer to live memory. A byte dump can show the MZ header, the offset field, and the PE signature without executing or loading the image. From there a specialized PE reader can validate machine type, optional-header variant, section-table extent, and region coordinates. A file claiming to be PE may still be malformed, for an unsupported architecture, or malicious; none of those conclusions is settled by the PE\0\0 bytes themselves.

The same reasoning applies across formats: an advertised offset should be treated as an untrusted number until checked against a known base, accessible extent, integer width, and format-specific interpretation. A single trusted abstraction for safe region slicing makes the difference between a maintainable format parser and a collection of dangerous ad hoc indexing expressions.

Python Demonstration: Constructing and Inspecting Tiny Media Containers

The following self-contained Python example uses only the standard library. It constructs an actual one-pixel PNG with correct chunk CRCs and a conventional four-sample PCM WAVE in memory, then verifies the primary structural regions. The resulting media files are tiny teaching artifacts; the code does not download, inspect, or execute any unknown file. The PNG pixel is opaque red in an 8-bit truecolor image. The WAVE values match the four samples from the fictional SAUD example, but their wrapper is now a real WAVE file.

from io import BytesIO
import struct
import wave
import zlib

PNG_SIG = bytes.fromhex("89 50 4E 47 0D 0A 1A 0A")

def png_chunk(name, data):
    assert len(name) == 4
    return (struct.pack(">I", len(data)) + name + data
            + struct.pack(">I", zlib.crc32(name + data) & 0xFFFFFFFF))

# IHDR = width, height, bit depth, color type, compression, filter, interlace.
ihdr = struct.pack(">IIBBBBB", 1, 1, 8, 2, 0, 0, 0)
# One scanline: filter method 0, then one RGB red pixel.
scanline = bytes.fromhex("00 FF 00 00")
png_bytes = (PNG_SIG + png_chunk(b"IHDR", ihdr)
             + png_chunk(b"IDAT", zlib.compress(scanline))
             + png_chunk(b"IEND", b""))

assert png_bytes[:8] == PNG_SIG
position = 8
names = []
while position < len(png_bytes):
    assert len(png_bytes) - position >= 12
    size = struct.unpack_from(">I", png_bytes, position)[0]
    assert size <= len(png_bytes) - position - 12
    typ = png_bytes[position + 4:position + 8]
    value = png_bytes[position + 8:position + 8 + size]
    crc = struct.unpack_from(">I", png_bytes, position + 8 + size)[0]
    assert crc == zlib.crc32(typ + value) & 0xFFFFFFFF
    names.append(typ)
    position += size + 12
assert names == [b"IHDR", b"IDAT", b"IEND"]
assert position == len(png_bytes)

samples = (0, 32767, -32768, 1)
stream = BytesIO()
with wave.open(stream, "wb") as audio:
    audio.setnchannels(1)
    audio.setsampwidth(2)
    audio.setframerate(8000)
    audio.writeframes(struct.pack("<hhhh", *samples))
wave_bytes = stream.getvalue()
assert wave_bytes[0:4] == b"RIFF"
assert wave_bytes[8:12] == b"WAVE"
assert struct.unpack_from("<I", wave_bytes, 4)[0] == len(wave_bytes) - 8
with wave.open(BytesIO(wave_bytes), "rb") as reader:
    assert reader.getparams().nchannels == 1
    assert reader.getframerate() == 8000
    assert reader.getnframes() == 4
    assert struct.unpack("<hhhh", reader.readframes(4)) == samples

print("PNG:", len(png_bytes), "bytes; chunk sequence:", names)
print("WAVE:", len(wave_bytes), "bytes; samples:", samples)

The example demonstrates a principled separation of duties. PNG's chunk parser checks byte-level structure and CRCs but does not attempt to be a complete PNG decoder. Python's wave module interprets the audio container and reports sample frames; struct.unpack interprets the selected PCM bytes. The two constructed outputs illustrate why one payload can be identifiable, bounded, and decodable only when the correct surrounding contract is applied. For real untrusted input, use mature libraries with relevant size/resource controls instead of extending this minimal classroom parser by trial and error.

Python Demonstration: Safe Signature Probes Without Executing Files

A separate safe structural exercise recognizes only candidate executable signatures. It uses fabricated byte arrays that are intentionally not valid runnable ELF or PE programs. A probe that observes MZ and a reachable PE\0\0 marker may report “PE-like structure found”; it must not report “valid and safe Windows executable.” Likewise, 7F 45 4C 46 establishes the expected leading bytes of an ELF candidate but does not establish a complete ELF header or loadable program.

import struct

# Offsets in this function are always FILE offsets.
def bounded_slice(blob, start, count):
    if start < 0 or count < 0 or start > len(blob):
        raise ValueError("invalid region")
    if count > len(blob) - start:
        raise ValueError("region beyond file")
    return blob[start:start + count]

# Fabricated teaching data: not a runnable PE executable.
pe_like = bytearray(160)
pe_like[0:2] = b"MZ"
struct.pack_into("<I", pe_like, 0x3C, 0x80)
pe_like[0x80:0x84] = b"PE\x00\x00"

assert bounded_slice(pe_like, 0, 2) == b"MZ"
header_offset = struct.unpack("<I", bounded_slice(pe_like, 0x3C, 4))[0]
assert header_offset == 0x80
assert bounded_slice(pe_like, header_offset, 4) == b"PE\x00\x00"

# Fabricated teaching data: not a runnable ELF executable.
elf_like = b"\x7fELF" + b"\x02\x01" + bytes(58)
assert bounded_slice(elf_like, 0, 4) == b"\x7fELF"
assert bounded_slice(elf_like, 4, 1) == b"\x02"  # 64-bit class flag.
assert bounded_slice(elf_like, 5, 1) == b"\x01"  # Little-endian flag.

try:
    bounded_slice(pe_like, len(pe_like) - 2, 8)
except ValueError:
    print("Correctly rejected out-of-bounds region")
else:
    raise AssertionError("Bounds check failed")

print("Candidate PE signature at file offset", header_offset)
print("Candidate ELF magic, class, and data encoding observed")

The exercise's bounded_slice function makes every read conditional on the available bytes. Length checks are necessary but not sufficient: a complete PE/ELF parser must also validate compatible header sizes, table counts, flags, alignment, machine types, and mutually dependent structures. This demonstration intentionally stops before interpreting or invoking executable contents.

Windows PowerShell 5.1: Bounded Hex Inspection

Windows PowerShell 5.1 can read a bounded prefix as raw bytes without launching the file. The script below requires an existing file path and reads at most 128 bytes. It does not use Invoke-Expression, launch the inspected file, or trust its filename extension. The observed bytes can be compared to expected format signatures from a published specification.

$path = "C:\Path\To\Sample.bin"  # Replace with an existing file to inspect.
if (-not (Test-Path -LiteralPath $path -PathType Leaf)) {
    throw "No such file: $path"
}
$stream = [System.IO.File]::OpenRead($path)
try {
    $buffer = New-Object byte[] 128
    $count = $stream.Read($buffer, 0, $buffer.Length)
    $prefix = New-Object byte[] $count
    if ($count -gt 0) {
        [Array]::Copy($buffer, 0, $prefix, 0, $count)
    }
    $hex = ($prefix | ForEach-Object { $_.ToString('X2') }) -join ' '
    Write-Host ("Read {0} bytes" -f $count)
    Write-Host $hex
} finally {
    $stream.Dispose()
}

PowerShell's formatted hex output is an observation, not a declaration that the input is safe. If only the first 128 bytes are read, a program may have a larger header, a later signature, or important nested metadata that has not been inspected. Conversely, an attacker can arrange plausible initial bytes that lead to malformed downstream structures. Report exactly how much was examined and which assumptions remain unverified.

A second practical check is to inspect the whole-file size with (Get-Item -LiteralPath $path).Length and compare it to any declared offsets before reading more. Do not allocate a buffer equal to an untrusted advertised size. Prefer bounded streaming and a format-aware reader when inspecting large or deeply nested files.

Compression, Encryption, and the Appearance of Randomness

An encoded payload may be compressed, encrypted, both, or neither. A PNG IDAT datastream commonly contains compressed image information; a JPEG scan contains compressed image syntax; MP4 mdat may carry samples produced by a compressed codec; an executable section may contain machine code interspersed with data and possibly compressed resources. The byte distribution within any of these regions is not a reliable universal identifier. An encrypted region may look random, but so may sufficiently compressed media or data. Statistical tests do not replace explicit format interpretation.

Compression moves work into an algorithm-dependent reconstruction stage. An image decoder often needs metadata before it knows how to interpret compressed bytes. Encryption adds a key and cryptographic state requirement, and an authenticated scheme can provide integrity and authenticity properties under its threat model. A CRC is not a cryptographic substitute for a message authentication code or a digital signature. Byte similarity, checksum matching, and verified origin make different claims.

Nested encodings compound resource risks: a small compressed payload may expand to an enormous image or archive. A maliciously declared dimension, frame count, or chunk size may amplify allocation requirements before decoding even begins. Sensible limits apply to dimensions, output size, sample counts, recursion depth, nesting, and computational time. If specialized codec support is absent, the container can still be documented as partly recognized without pretending to validate the undecoded payload.

Metadata, Compatibility, and Format Variants

Metadata can describe content, but its presence and ordering vary widely. A PNG may carry color-profile, textual, or other ancillary information. A WAVE file may include additional RIFF chunks. An MP4-compatible file may carry multiple tracks and alternative codec configuration details. An executable may carry resources, imports, relocation data, and digital-signature-related structures. Some metadata affects interpretation; some is advisory; some is deliberately ignored by particular implementations.

Compatibility is not the same as magic-byte matching. A reader that handles basic PNG images might not handle every supported color or extension combination. An audio player may parse WAVE but not decode a particular compressed WAVE payload. An MP4 demultiplexer may locate tracks but lack a required codec. A PE parsing tool may identify section tables but not emulate or execute the target architecture. The correct diagnostic question is which layer and variant is supported?

Formats also evolve. A new version may add optional chunks, longer length fields, brand identifiers, or alternative encoding methods. Good readers reject impossible values and handle recognized extension rules precisely. They do not blindly treat unknown critical structures as harmless, nor do they assume every unknown ancillary or optional structure warrants total failure. The appropriate policy depends on the actual specification. This is why documenting a format's exact version and supported feature set is a substantive interoperability requirement.

Trust Boundaries and Security Implications

A file extension is a naming convention. A MIME/content-type declaration may help a recipient choose a parser but is not proof of file integrity. A magic number is a small byte-pattern observation. Even a file with internally consistent lengths and checksums may contain maliciously chosen content, exploit a decoder defect, or execute harmful logic when loaded under an appropriate environment. Security decisions must consider the provenance, validation, interpretation, and permitted actions of each file.

Threat or failure Why a signature check fails More appropriate control
Oversized image dimensions Header can declare enormous values Pixel/byte budgets and checked arithmetic
Deeply nested boxes Valid-looking descriptors can recurse excessively Nesting and work limits; parser isolation
Forged chunk lengths Signature does not constrain later fields Parent-bounded region parsing and semantic validation
Ambiguous multi-format file Two parsers may interpret the same bytes differently Strict format policy and consistent parser selection
Unsupported codec Container may parse while payload is undecodable Separate codec capability negotiation
Untrusted executable PE/ELF magic says nothing about author or effects Origin verification, permission policy, sandboxing
Corrupted payload Metadata can remain intact while data changes Appropriate integrity checks and error handling

Some files deliberately exploit format confusion: content may satisfy the preliminary recognition rules of more than one file type, or be interpreted differently by distinct readers. Such files are sometimes called polyglots. The defensive implication is not that all multi-format content is necessarily malicious, but that content-type validation should be enforced consistently through upload processing, storage, preview, and consumption. Renaming a dangerous file as an image does not neutralize it; accepting the extension alone is insufficient.

Why Code Signing Is Different From File Checksums

Many formats use CRCs or other integrity fields to detect accidental damage. PNG chunk CRCs help detect bit errors in a chunk's type and data. That is a different goal from verifying that a software publisher signed particular executable content. A code signature uses cryptographic mechanisms and a trust policy that depend on which bytes are covered, which identity or key is trusted, certificate handling where applicable, and verification results. A signature can establish an origin-related assertion under a defined policy without proving that the software is defect-free or harmless.

A whole-file hash is another different measurement. If two files have the same collision-resistant digest under an appropriate comparison process, it provides strong evidence of byte identity in that context. The digest alone does not explain what the bytes mean or whether the file is supported. A PNG can change an ancillary metadata chunk and yield a different file hash while displaying the same pixels. An executable can differ in metadata or layout while performing similar operations. Meaning, identity, integrity, and trust are not interchangeable properties.

For reliable cataloging, record both the structural representation and the validation claim. “PNG signature present,” “PNG chunks and CRCs structurally valid,” “image decoded,” and “file received from a verified distributor” communicate distinct findings. This layered reporting is useful for digital archives, security triage, media pipelines, and reproducible software builds.

Common Misconceptions and Corrective Explanations

“The file extension tells me the format.” Extensions are user-visible names and can be wrong or deliberately misleading. Investigate bytes and format contracts. “A matching magic number means it is valid.” Signatures identify candidates, not complete structures. “The payload starts immediately after the first header.” In chunked or indexed formats, payload location can depend on a table or nested region. “All media data is raw pixels or samples.” Many formats carry compressed and codec-dependent data instead.

“Every WAVE has exactly a 44-byte header.” That describes a common simple PCM layout, not an unconditional standard. “All MP4 files store video frames in simple consecutive order.” Timed media relies on track metadata and may separate decode and presentation concerns. “An ELF section header is what the loader always uses.” ELF program headers primarily describe loadable segments, and section metadata plays different roles. “A file offset is a memory address.” Executable formats distinguish raw stored coordinates from runtime memory coordinates.

“If the CRC matches, the file came from a trusted author.” CRCs are not cryptographic origin proofs. “If a program has a readable PE or ELF header, it is safe to run.” Recognizable structure provides no safety guarantee. “A high-entropy payload must be encrypted.” Compressed media can also be difficult to interpret visually. “Two renderings that look alike are the same bytes.” Metadata and encoding can differ even when decoded content matches.

Selection and Design Framework for Binary Containers

When designing a binary container, first decide whether its consumers need random access, streaming, extensibility, tight encoding, low decoding latency, or strong compatibility guarantees. A fixed header followed by payload supports simple readers but can become awkward when several independently optional elements must be added. A typed chunk format can be extensible and easy to scan but requires explicit handling of unknown types. A nested box hierarchy can support multiple media tracks or related objects but increases parser complexity and validation burden.

Choose a single explicit byte order per field group or make any variation unambiguous. Define whether length fields include their own headers and padding. Specify maximum values rather than merely choosing large integer widths. State whether unknown fields are critical or optional, what order is allowed, whether duplicate chunks are valid, and how to recover from truncation. For executable-like formats, distinguish stored file positions, mapping addresses, and permissions; do not equate a generic data record with an executable loader contract.

Design need Favor Trade-off to document
Simple fixed-layout sensor capture Fixed known header and bounded payload Version evolution and optional fields
Extensible image metadata Typed chunk organization Unknown chunk and ordering rules
Timed multimodal playback Track-based indexed container Timestamp and sample-location complexity
Portable binary interchange Explicit serialization contract Encoding overhead and schema lifecycle
Loadable program image Architecture-aware mapping metadata Loader security, relocations, dependencies

An operational format specification should include byte tables, concrete samples, negative tests, supported variant rules, and reference implementations. It should also separate container validation from whatever specialized decoder or loader ultimately processes the payload.
