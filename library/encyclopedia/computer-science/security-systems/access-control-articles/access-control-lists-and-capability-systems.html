Article overview

Access-control lists and capability systems encode the rights of security principals to operate on protected objects. ACLs associate grants with resources; capability mechanisms convey authority through protected references. This article traces the access-control matrix connecting both representations; studies POSIX ACL masks and inheritance, Windows DACLs, real object-capability enforcement, delegation, attenuation, bearer links, seL4, CHERI, and revocation; and shows how to choose, operate, audit, and test authorization designs through institutional cases.

1. Definition, scope, and central distinction

An access-control list (ACL) records which principals may exercise particular operations on a protected resource. A capability system instead makes possession of an unforgeable reference to a resource, together with specified rights, the basis for exercising authority. Both are means of representing and enforcing authorization, and both can implement the least-privilege principle. They differ most visibly in the direction from which authority is enumerated: an object-oriented ACL asks who can access this object; a subject-oriented capability inventory asks which objects this subject can access. Real implementations often blend aspects of both, and neither representation eliminates the need for authentication at its own trust boundaries, secure enforcement, auditing, or revocation planning.

The distinction matters when architects need to protect files, databases, records, microservices, operating-system objects, hardware memory, delegated document shares, and temporarily shared cloud objects. An organization may manage ACL entries at its file server yet hand authorized processes already-open file handles. A web platform may evaluate an object permissions list while issuing short-lived signed download links. These layers are not contradictory: the authorization question can be answered at one boundary and subsequently represented by a constrained handle at another.

This article explains the access-control matrix underlying both ideas; describes POSIX and Windows ACL semantics; distinguishes genuine object capabilities from bearer credentials, Linux process capabilities, and ordinary RBAC permissions; and develops governance, testing, and deployment methods. References to particular platforms describe representative behavior and should be checked against supported versions before operational changes.

2. Historical foundations: subjects, objects, and the matrix

A foundational abstraction represents authorization as an access-control matrix. Rows represent subjects—users, services, processes, or protection domains. Columns represent objects—files, records, services, memory regions, or devices. The entry at their intersection contains operations such as read, modify, execute, append, delegate, or administer. The matrix is often sparse: most subjects have rights over only a small portion of the total object inventory.

A full matrix is generally impractical to store explicitly for a large system. One representation groups entries by column, placing an ACL with each object. Another groups entries by row, placing an inventory of capabilities or tickets with each subject. An ACL does not necessarily store literal user names; it may refer to stable identifiers, groups, or service identities. A capability does not need to be a human-readable ticket; it may be a kernel-protected handle, tagged hardware pointer, or a restricted object reference protected by a trusted runtime.

This distinction has appeared in computer-security research since early multiuser operating systems and access-control theory. Modern cloud applications obscure it with group memberships, resource policies, URL tokens, and delegated permissions, but the underlying questions remain: where does authority reside, who may mutate it, and what does the trusted enforcement mechanism actually check?

3. Worked access-control matrix

Suppose a university maintains course:CS410, gradebook:CS410, and invoice:U184. A faculty instructor may read and edit the gradebook but may only read the course outline; a student may read the outline but not the gradebook; a finance operator may read and approve the invoice subject to workflow conditions. The matrix describes the desired result without committing to a technology.

Subject Course outline Gradebook Invoice
Instructor Read, update Read, enter grades None
Student Read None None
Finance operator Read None Read, approve when separate approval controls pass
Background archive job Read Read for archival task Read for archival task

The object ACL for the gradebook could list instructor: {read, enter-grades} and archive-job: {read}. A capability inventory for the instructor might contain constrained references to the outline and gradebook only. For either design, the finance operator's invoice authority must still be checked against the transaction's approval workflow. An object permission is not a substitute for separation of duties, record-state validation, or a time-sensitive business rule.

The matrix is valuable during architecture reviews because it separates intended access from how it is expressed in a directory, access token, policy language, or application database. Teams should record negative cases as explicitly as positive cases: the student must not gain gradebook access by changing a URL, and the archive job must not edit the values it reads.

4. Anatomy of an access-control list

An ACL is a collection of access-control entries (ACEs) or equivalent permission records associated with an object. A typical entry links a principal to a permission set and, on some platforms, specifies whether the rights are allowed or denied. Additional metadata can indicate inheritance, auditing, scope, or object-specific conditions. ACLs can be stored in file-system metadata, directory services, application databases, storage platforms, or management-plane policy documents.

A conceptual entry might be represented as resource=report:391; principal=group:research-editors; allow={read,update}; scope=record. This string is instructional rather than a universal ACL format. The important fields are a canonical object identifier, a stable subject or group identity, a precisely defined operation set, and rules describing how the entry applies. An entry described only as “full access” is often insufficient for a security review because platforms vary in what they include under that heading.

ACLs can express direct grants to individuals or indirect grants through groups. They may also be combined with a base owner/group/other permission scheme. A secure system needs to distinguish the configured grant from the effective grant, which may be constrained by group membership, token state, mask entries, parent-folder permissions, share permissions, mandatory security labels, or tenant-wide policy.

5. Principal resolution and identity lifecycle

An ACL entry usually refers to a principal identifier, not to a label shown in a graphical interface. A principal can be a user, group, application identity, workload account, or security context. Windows commonly uses security identifiers (SIDs), while POSIX ACL entries can refer to numeric user and group identifiers. Application platforms may use immutable account IDs and group IDs instead of display names. The mapping between identity and permission must be treated as a security dependency.

If staff member sara is renamed, an ACL tied to a stable identifier can remain valid. If a principal is deleted and its identifier is later recycled, careless lifecycle design can accidentally transfer old authority. Deactivated identities, orphaned group entries, expired vendor accounts, and retained service credentials can leave apparent permissions that are either ineffective or dangerously accessible through a restored identity. An access review must therefore join permissions with reliable identity-lifecycle data.

Groups reduce administrative repetition, but nested groups can obscure why someone has access. A reviewer should be able to reconstruct the path from user membership to the resource grant, including dynamic group membership and privileged groups. Identity provisioning should not silently grant application ownership or ACL-editing rights. The administrator who assigns access and the resource owner who approves it may need different responsibilities.

6. ACL evaluation is platform-specific

There is no single universal ACL evaluation algorithm. A security reference monitor evaluates a request using the operating system's or application's rules: matching principals, requested operations, enabled group memberships, applicable ACEs, inherited entries, and sometimes additional policy layers. The system should return an explicit outcome—allow or deny—plus an understandable reason suitable for privileged diagnostics. Applications must not infer that a missing record automatically permits access.

For a simple allow-only list, the model can be: deny unless an applicable entry grants the requested operation. More sophisticated implementations support explicit deny entries, order-sensitive processing, or masks that cap effective rights. Others combine ACL grants with a mandatory policy such that an ACL alone cannot authorize the operation. In Windows, the order and type of ACEs matter; on POSIX-style ACLs, the mask can reduce the effective permissions of named users, named groups, and the owning-group entry.

A secure design documents evaluation order rather than borrowing rules from another system. The phrase “deny overrides allow” is a useful policy intention but not a sufficient algorithmic specification for every engine or platform. Authorization code must examine the actual requested rights, canonical target, applicable entries, and system-level constraints.

7. Allow, deny, and exception precedence

Explicit deny entries are most useful when exceptions must be removed from an otherwise broad access path, but they can create confusing interactions. A file may allow a general staff group while denying one user; a policy engine may accumulate permissions from several groups; a directory may inherit parent restrictions. An auditor cannot determine effective access by reading a single line and ignoring other rules.

In Windows discretionary ACLs, canonical ordering normally places explicitly specified deny ACEs before explicit allow ACEs, followed by inherited entries in an established order. Access evaluation examines the requested access and ACE sequence. Reordering entries arbitrarily can change the result. A null DACL is also distinct from an empty DACL: according to Microsoft, a null DACL permits broad access, while an empty DACL grants none. These are platform-specific facts, not design recommendations to create null ACLs.

Whenever policy needs exceptions, prefer narrow scoping over complex deny overlays. For example, rather than granting an entire division edit access and denying twenty special cases, a smaller approved editor group may be easier to verify. Record why an exception exists, its owner, expiry or review condition, and the tests demonstrating that the exception does not block legitimate work or permit privilege expansion.

8. Object ownership and ACL administration

ACLs commonly associate administrative power with an object owner, system administrator, or delegated permission manager. This administrative authority is different from the ability to read or write the underlying content. Someone may manage access without needing to inspect sensitive documents; conversely, someone may read a file without permission to grant it to others. A robust permission vocabulary makes these actions separate.

Owner discretionary authority offers collaboration flexibility but also creates governance risk. If every document creator can invite unrestricted external users, enterprise data-classification rules may be bypassed. A mandatory organizational policy may therefore set a ceiling on owner-controlled shares, prohibit cross-tenant grants, or require approval before granting an external identity. ACL governance cannot be delegated solely to whoever happened to create the object.

Ownership transfer requires a defined process during employee departures, project handoffs, and account closure. Policy should address ownerless resources, abandoned shared folders, service-owned files, and privilege inheritance when an object moves between projects. Audit records should distinguish the person approving the change from the system or service performing it.

9. Traditional Unix permissions as a compact access list

Traditional Unix file mode bits describe permissions for the file's owner, owning group, and all other users. Read, write, and execute have different interpretations for regular files and directories. For a regular file, r normally permits reading content, w permits modifying content where the relevant file and other constraints allow it, and x permits executing it under the applicable system rules. For a directory, r permits listing names, w participates in creating and removing directory entries, and x means search/traversal permission.

A listing such as -rw-r----- describes owner read/write, group read, and other no access. The notation is compact, but it does not mean the owner can never be constrained by ACLs, mounted file-system behavior, privileged processes, or a mandatory policy. Directory operations often depend on the directory's permissions even when the file's own mode appears restrictive or permissive.

-rw-r-----  1 registrar records  5840 report.txt
# owner: read, write
# owning group: read
# others: none

Treat shell examples in this article as representative illustrations, not commands to execute on production data without checking filesystem support, identity mapping, backups, and organizational change control.

10. POSIX-style extended ACL entries

Linux systems commonly expose POSIX-style extended ACLs through getfacl and setfacl, where supported by the filesystem and mount configuration. These entries supplement owner, owning-group, and other permission categories with named users and groups. The ACL access-check algorithm has a defined order: owner identity is evaluated first, named user entries are considered next, then relevant group entries subject to the mask, and finally the other category where applicable. This is not the same as Windows ordered allow/deny ACE processing.

A representative ACL might look like this:

# file: /srv/research/summary.txt
# owner: archive
# group: reviewers
user::rw-
user:analyst:r--
group::r--
group:editors:rw-
mask::r--
other::---

The named editors entry appears to request read/write, but the mask reduces its effective permission to read only. The named analyst entry is also limited by the mask; here that limitation does not change its requested read-only access. The file owner entry and other entry are not constrained by that mask in the same way. The permission set should be inspected using getfacl, which can display effective rights, rather than inferred from an editor group's line alone.

11. The POSIX ACL mask and effective rights

The ACL mask is a frequent source of access-control errors. It defines the maximum effective permissions for the owning group, named user entries, and named group entries in the POSIX ACL model. If an administrator grants a named group rwx but the mask permits only r-x, that group does not obtain write access through that entry. Conversely, some ACL-editing tools recalculate the mask when entries change, potentially changing effective permissions beyond the line being edited.

An investigator should inspect the complete ACL before and after modifying entries. An application deployment script that sets one named-user permission can alter the mask, resulting in unexpected read or write behavior for other users. chmod can also interact with ACL representation and effective group-class permissions. Test with a nonprivileged identity representative of the intended user rather than concluding that root or an administrative shell's access proves the policy.

The practical workflow is: capture the original ACL, specify the intended effective permission, apply a minimal change, inspect getfacl output, test both allowed and forbidden operations, and record the result. Whenever failure would expose confidential data or halt critical operations, perform the change through a reviewed maintenance procedure.

12. Default ACLs and inheritance in directories

For POSIX-style ACLs, a default ACL on a directory influences the ACL initially assigned to new files and subdirectories created within it. It is distinct from the current directory's access ACL. A default ACL does not retroactively rewrite every existing child; it shapes creation behavior. The resulting permissions are affected by the creating process's requested mode and filesystem rules, so inheritance should be tested rather than assumed.

Consider a department folder intended to make newly created reports readable by an audit group. A default named-group entry can help establish consistent creation-time access. But if the folder was populated before the default ACL was added, those earlier files may remain unshared. If the application creates temporary files elsewhere and moves them into place, the resulting ACL behavior may differ from an ordinary create-in-place workflow.

Directory ACL changes should be tested with representative file-creation methods, including ordinary applications, batch imports, archival tools, and cross-filesystem moves. Administrators should document whether copying, replacing, and renaming content preserves or recomputes permissions. Encryption, tenant policy, and data classification may still impose independent restrictions on the contents.

13. Windows security descriptors and DACLs

Windows securable objects can carry a security descriptor containing an owner SID, group information, a discretionary access-control list (DACL), and possibly a system access-control list (SACL) used for auditing and other security functions. A DACL contains ACEs that permit or deny requested operations to trustees represented by SIDs. The requested rights are compared with the caller's effective security token and the object-specific rules.

Different Windows object types define generic and specific rights differently. File-system permissions, registry permissions, Active Directory object permissions, processes, services, and other securable objects should not be reduced to one interchangeable read/write scheme. An access-check result can also be affected by privilege use, restricted tokens, integrity policy, or other mechanism; DACL membership alone is not a complete effective-access report.

A security descriptor is not merely an ACL string: owner information, inherited ACEs, protected inheritance status, and audit requirements matter. For regulated workflows, document who is permitted to modify the DACL, who may take ownership, and whether rights are enforced by the kernel, a directory service, or an application-specific reference monitor.

14. Windows ACE ordering, inheritance, and effective access

In Windows, ACE ordering matters because the access-check procedure can satisfy or reject requested access as it traverses entries. Microsoft documents a preferred canonical order separating explicit entries from inherited entries, with deny and allow categories in a defined sequence. Administrators should normally use supported security APIs or management tools that preserve proper ordering, rather than manually assembling an arbitrary ACE list.

Inherited ACEs allow a parent directory or object container to propagate authorization to descendants. Inheritance reduces routine administration, but it can unintentionally expose sensitive documents placed within a broadly shared path. A confidential payroll folder, for example, may require explicit review of inherited entries, not just the additional payroll-team ACE shown in a user interface.

A careful effective-access review starts with the caller's relevant token SIDs and privileges, the exact target object, all applicable DACL entries, and any supplemental restrictions. Group membership changes can require a new logon or token refresh for some scenarios. Administrators should test the intended access using a representative account and distinguish file permissions from additional network-share restrictions.

15. Windows shares, NTFS permissions, and multiple controls

A Windows file shared over a network can be governed by more than one permission layer. Share permissions can restrict access through the network share while NTFS permissions restrict underlying filesystem operations. A successful check at the share layer does not override a filesystem denial. The effective ability to read or modify a file through that particular access path must satisfy the relevant layers.

An example is a shared Faculty directory where the share allows the institution's teaching staff to access the share, but NTFS permissions grant gradebook modification only to the instructors of each course. A staff member who can browse the share must not thereby gain access to every gradebook. A different file access route may involve different share controls but still be constrained by underlying filesystem and other policies.

Avoid using “Everyone Full Control” as an unexplained production default, even when another layer is expected to carry the real restriction. If a broad share permission is part of an approved design, record the dependency, test it, and ensure the ACL layer providing the effective restriction cannot be unintentionally bypassed. For sensitive resources, include privileged process access, backups, and administrative restoration paths in the analysis.

16. ACL administration, APIs, and delegated changes

ACL creation and modification are themselves protected operations. Services may expose APIs for grant, revoke, list-access, and evaluate-access; operating systems offer administrative tools and programmatic security APIs; SaaS platforms present sharing dialogs. In all cases, the system must authorize the change to authorization policy separately from the action being granted. A user who may edit a report should not automatically be able to grant ownership to an external party.

Use a clear change contract: canonical resource ID, requesting administrator, current version, proposed grant or removal, approval context, and reason. Version checks or transaction boundaries prevent one administrator from silently overwriting another's authorization change. If group membership is expanded, compute the indirect population that gains access, not merely the one new line added to the ACL.

In highly distributed systems, ACL edits may be replicated or cached. The management interface should distinguish “change accepted” from “all enforcement points now reflect the change.” For sensitive removals, provide an operational verification method and a defined response if propagation exceeds the expected window.

17. ACLs in applications, object stores, and APIs

Application-level ACLs frequently control records, dashboards, repositories, projects, documents, or message threads. Typical schemas associate resource_id, principal_id, permission, and optional scope or conditions. The application must resolve the canonical target resource using trusted database state, not merely authorize the identifier supplied in a URL. Both list queries and individual record reads require enforcement: filtering a page of results is not enough if an export endpoint bypasses the filter.

Cloud platforms may expose several distinct resource authorization mechanisms—identity policies, resource-based policies, ACL-like grants, bucket configuration, access points, or signed access tokens. Their precedence is platform-specific. It is inaccurate to say that a cloud storage ACL always operates like a Windows DACL or that every cloud feature labeled “ACL” is the recommended governance mechanism. Consult current provider documentation and prefer the least complex supported permission model that satisfies the requirements.

Application APIs should log policy changes and, where appropriate, security-relevant denials. They should not return confidential resource existence or permission details to unauthorized callers. Review aliases, symlinks, shared links, background jobs, precomputed reports, and bulk endpoints as alternate routes to the same protected information.

18. Access checks, object references, and confused identity

A common application failure occurs when a server checks whether the caller is authenticated but not whether that caller can use the specific object. For example, an authenticated resident may change /statements/101 to /statements/102 and obtain another household's record if the service authorizes only endpoint access. The correct behavior is an operation-level authorization check against the canonical statement and the authenticated tenant or household context.

ACL evaluation belongs at a trusted enforcement point. The service should look up the object's tenant, classification, owner, and current permission state from authoritative sources. A client-submitted claim such as isOwner=true cannot replace that check. An ACL API that lets users guess another resource's identifier and add themselves as editor is itself a policy-enforcement failure.

Treat the combination of subject + operation + canonical object + applicable policy version as the basic decision contract. If a capability is used instead, the trusted system must establish that it legitimately designates the object and grants only the requested operation. Both mechanisms require complete mediation at meaningful resource boundaries.

19. Capability security: authority through possession

A capability is an unforgeable reference that both designates a resource and embodies authority to perform specified operations on it. The holder can invoke permitted operations without relying on a separate global name-to-permission lookup for every action in the same way an ACL architecture might. This creates a natural link between possession, delegation, and least authority: if a component never receives a capability to modify the payroll database, it should have no direct route to that modification through the capability mechanism.

Unforgeability is essential. Knowing a resource's integer address, name, or URI must not be sufficient to construct a valid capability in a true capability system. Enforcement can be supplied by a kernel-managed capability table, a protected language runtime, or hardware tags and bounds. Merely passing a mutable Python dictionary labeled capability does not make its entries secure if untrusted code can invent or alter it.

Capabilities can support fine-grained authority transfer between components, but their security properties depend on the entire platform. An application that also permits broad ambient filesystem or network access can bypass capability restrictions by using those other channels. Evaluate the complete authority environment rather than assuming one protected handle makes every process least-privileged.

20. Unforgeable references, handles, and authority integrity

The reference component of a capability must identify the actual protected object; the rights component specifies what operations are authorized. In kernel capability systems, these facts may be stored in protected kernel structures and named through a handle or capability-space slot. In a language-based object-capability environment, the runtime can prevent programs from constructing arbitrary object references or accessing the underlying object except through exposed methods.

A capability's authenticity is different from secrecy. Some capability implementations rely on unguessable secrets and therefore require confidentiality as well as integrity; others rely on kernel tables or tagged memory, so an attacker cannot manufacture authority simply by guessing a numeric handle. A handle value is meaningful only inside the trusted context that resolves it. A value such as file descriptor 5 in one process generally does not grant access to the same resource in an unrelated process.

When documenting capabilities, distinguish the token form from the security guarantees: object binding, allowed operations, transferability, derivation constraints, lifetime, and revocation behavior. A system's use of the word “capability” is not evidence that it meets all of these properties.

21. Possession, confinement, and the authority graph

In capability-based design, authority flows through capability distribution. A service initially receives a small set of references, uses those references to access resources, and may pass restricted references to collaborators. The resulting authority graph describes which components can reach which resources directly or through delegated interfaces. It differs from a ReBAC graph because its edges represent operational authority or capability-bearing references rather than merely social or organizational relationships to be evaluated by a policy service.

Designers should answer what a newly created process receives at startup. If it inherits a broad filesystem root, privileged device handle, administrator service client, and a shared secret store, its effective powers are far greater than the one file it was supposed to parse. A true least-authority design gives it only the designated input and output handles and the minimal communication channel necessary to report completion.

Confinement also concerns the ability to export capabilities. An otherwise restricted component that can freely send powerful capabilities to untrusted peers can undermine organizational intent. An authority-flow review traces creation, derivation, transfer, storage, and retirement of references, plus any alternate channel through which a process might recover ambient authority.

22. Attenuation: deriving a narrower capability

Attenuation means producing a capability with no more authority than its source and often less: read-only rather than read/write, one object instead of a collection, short expiry instead of indefinite life, or permission to invoke one method rather than every method. Proper capability systems support authority reduction without allowing the recipient to reconstruct the original stronger capability.

For example, a data-processing service may hold a read/write reference to a project document. To generate a preview, it passes a derived read-only reference to a renderer. The renderer should not be able to modify the original even if compromised. In a hardware capability design such as CHERI, derivation rules and tagged capability metadata can constrain bounds and permissions; in a trusted object system, a wrapper can expose only selected methods while keeping the underlying reference inaccessible.

Attenuation must be analyzed against transitive powers. A supposedly read-only capability is still dangerous if its read method returns secrets or an internal token that grants stronger authority. Likewise, a wrapper that exposes executeArbitraryQuery may allow updates even if its public method name is read. The security guarantee is about actual effects, not branding or method names.

23. Delegation, transfer, and transitive authority

Capabilities are useful when one component must safely delegate part of its authority to another. In a conceptual workflow, a trusted records service creates a capability for report:391 with {read, export-redacted}; a report generator receives it; the generator can complete its work but cannot edit source values or approve their release. This is a controlled transfer of authority rather than a global grant to the generator's service identity.

Delegation raises questions. Can the recipient pass the capability to a third party? Can it derive broader capabilities? Can the original issuer enumerate current holders? Can the rights survive service restart, machine migration, or credential renewal? What happens if the delegated component becomes compromised? These answers depend on system design, not a universal property of all capability implementations.

At design time, identify delegation provenance and transitive closure: if Service A can delegate to B and B can delegate to C, can C exercise the same operation, and is that allowed? Authority may be restrained using indirection, non-transferable references enforced by a trusted mechanism, attenuation, compartmentalization, and policy checkpoints. An audit trail should describe both issuer and current holder where meaningful and technically possible.

24. Capabilities, bearer tokens, and signed links

A bearer credential allows anyone who possesses it to exercise the rights accepted by its verifier. This resembles a capability, but a signed URL or OAuth access token is not automatically a full object-capability system: it may identify a principal rather than an object, be broad in scope, depend on a separate access check, and support distinct sharing and revocation semantics. Precision matters because a “secret URL” can be copied, logged, leaked through browser histories, or sent to the wrong recipient.

An Amazon S3 presigned URL provides a useful capability-like example: AWS documents these URLs as bearer tokens permitting specified object operations within configured constraints. Its effective validity depends on expiration, credential lifetime, and applicable policies. It is not sufficient to treat the embedded expiration as a guarantee that a compromised link cannot be rendered unusable sooner or that it cannot remain usable until that expiration in every configuration.

Good controls include short validity, minimal permitted operation, server-side control of object and content type, avoidance of referrer or analytics leakage, careful log redaction, and an incident response mechanism for invalidating compromised credentials or policy permissions. Do not place long-lived privileged tokens into public pages or source code.

25. File descriptors as restricted object handles

An operating-system file descriptor illustrates handle-based authority, though it should not be equated with a complete object-capability discipline. When a process successfully opens a file, the kernel returns a descriptor representing an open file description and associated access mode. Subsequent reads or writes normally use that existing handle rather than repeating an ordinary pathname ACL check on every byte. A descriptor can also be inherited across process creation or transmitted using supported interprocess mechanisms.

This has a critical security consequence: changing a file's ACL or mode after a file has been opened generally does not automatically revoke a preexisting open descriptor's ability to perform authorized operations. The exact behavior of handles and revocation depends on the system, object type, operation, and any additional controls, but access-revocation plans cannot simply assume that editing a permission list closes already-open access.

A constrained helper design can open a designated input file, pass only a read-only descriptor to a sandboxed processor, and remove the helper's ambient access to unrelated paths. The processor still needs containment against other authority channels. Conversely, a writable descriptor passed accidentally to an untrusted subprocess can grant modification authority that no later check of the subprocess's username will make obvious.

26. Kernel-enforced capabilities: seL4 illustration

The seL4 microkernel uses capabilities as a core protection mechanism for kernel-object authority. Its documentation describes capabilities as unforgeable permissions to access objects and explains a capability-space structure (CSpace) in which capability slots are managed. A process can hold a capability to a specific object with defined rights and may derive or transfer references subject to kernel rules.

This system illustrates properties that an application-level “permission object” may not have: the kernel controls capability representation and access checks, and derivation can be constrained. seL4 provides methods for capability management and for revoking derived capabilities through its capability derivation structures. These specific semantics should not be assumed for all capability systems. CSpace naming and capability-slot arrangements are implementation details whose exact interface depends on the seL4 API and system configuration.

In a high-assurance embedded system, a component should receive only the endpoint, memory, and device authority it requires. The architecture must also account for bootstrap authority, creation of new objects, and who is trusted to distribute initial capabilities. The kernel's capability model does not itself certify that application code chose safe delegation policies.

27. Hardware-backed capabilities and CHERI

CHERI—Capability Hardware Enhanced RISC Instructions—extends instruction-set architecture concepts with capability metadata that can constrain memory references, including bounds and permissions. Protected tags and derivation rules help prevent ordinary untrusted code from manufacturing valid capability authority from arbitrary integer addresses. This makes CHERI relevant to spatial memory safety and software compartmentalization as well as to capability-based protection models.

CHERI hardware capabilities are not the same as conventional Unix file descriptor integers, Linux's named process capabilities, or application API tokens. The type of authority and how it is enforced differ. CHERI implementations and software environments may support hybrid or more pervasive capability modes; one should not imply that all software compiled for a CHERI system automatically gains full system-wide object-capability isolation.

Attenuation can reduce pointer bounds and permissions but does not automatically solve stale-reference revocation or temporal memory safety after an object is freed. The Cambridge CHERI FAQ and programming material explicitly distinguish capability integrity and bounds from wider runtime and object-lifetime assurances. Architects must keep hardware guarantees and software operational controls separate.

28. ACL revocation: removal and propagation

To revoke an ACL grant, an authorized administrator removes or narrows the applicable entry, group membership, or parent permission and confirms that the target enforcement point now denies the operation. This action may be simple in a centrally managed object permissions system, yet effective access can persist through another group, inherited grant, cached decision, active session, alternate credential, or preexisting handle. Removing one entry does not prove that the subject has lost every route to the object.

Distinguish control-plane revocation from data-plane effect. The ACL service may acknowledge the removal, but application nodes and replication replicas can still use cached old permissions until they refresh or expire. Strong revocation requirements justify shorter cache lifetimes, invalidation events, active-session termination, and read-after-write verification at protected operations. An effective-access checker should be able to explain remaining grants after the intended one is removed.

A practical revocation record contains: resource, principal, prior permissions, change initiator, approval, change time, effective policy version, observed enforcement state, and any surviving tokens or handles. For sensitive departures or suspected credential compromise, broad access-path investigation is more reliable than checking whether a single user has disappeared from one list.

29. Capability revocation: the hard problem

Capabilities are straightforward to pass and attenuate, but revocation may be more difficult when references have been widely distributed. A capability holder may pass a derived capability to another component, which passes another to a third component. If the issuer has no registry, revocation tree, trusted proxy, or indirection point, it may be unable to find or invalidate every surviving copy. This is not an argument against capability systems; it is a design requirement that should be evaluated before broad deployment.

Common strategies include an indirection object that checks a revocation state, a lease with bounded lifetime, a revocation tree that can delete derivations, versioned or generation-tagged handles, kernel-mediated disposal, and an application-specific invalidation channel. Each design has trade-offs in latency, availability, storage, auditability, and the maximum exposure window. Short expiration does not prevent misuse during the validity period.

The correct revocation question is: what is the maximum time and maximum scope during which a formerly authorized component can still perform the operation? Answer separately for access to future objects, existing open handles, exported data copies, tokens already issued, offline clients, and ongoing transactions. Authority may be revoked, but information already read cannot be retrieved from the reader's memory through access control alone.

Revocation mechanism Typical design Residual concern
Edit object ACL Remove grant or membership Old token, cached allow, open handle
Revoke signed sharing credential Invalidate verifier permission or signing credential Scope may affect other issued links

30. The confused deputy and ambient authority

A confused deputy is a component with legitimate authority that is induced to exercise that authority on behalf of an unauthorized requester. Imagine a document-conversion service that can read every tenant's storage namespace. It receives a path in a conversion request and opens that path using its broad service identity. If the caller can name another tenant's document, the service may disclose data even though the caller never possessed direct storage access.

A capability-oriented alternative has the requester supply a restricted, issuer-validated reference to the exact input document; the conversion service receives no ambient authority to browse unrelated objects. The service still must verify the capability's origin, operation scope, expiry, and binding to the intended task. A signed reference whose issuer can be tricked into authorizing arbitrary paths recreates the same problem.

Ambient authority is authority available from the execution environment without being passed explicitly for the particular operation—for example, a powerful process identity, broad filesystem access, unrestricted network credentials, or global secrets. Object-capability systems seek to reduce dependence on such background powers. ACL systems can also mitigate confused-deputy risks by requiring the deputy to evaluate the caller's object-level rights before using its own privilege. The critical protection is correct authority attribution and enforcement at the actual effect.

31. Hybrid designs and authorization handoffs

Many secure systems combine ACL checks and capability-style handles. A trusted storage service evaluates an authenticated user's ACL-based right to open a document, then returns a handle limited to reading that document for the duration of a job. The handle may be bound to one process or session, and its lifetime can be limited independently of the user's long-term group membership. This combines centralized administration with operationally narrow authority conveyance.

A handoff must be explicit: who performs the original check, what exactly does the resulting handle permit, and which policy changes can invalidate it? If a web server uses a shared superuser credential to mint unlimited download links, the architecture may bypass intended tenant controls at issuance. The link generator must authorize both the object selection and the permission it is about to delegate. Creating a powerful token is itself a privileged operation.

Versioned handles, scoped OAuth-style credentials, signed upload or download requests, kernel file handles, and brokered object references can all provide different forms of constrained access. They should not be described as equivalent just because each is transferable. A hybrid design should document the exact enforcement mechanism and the path used for emergency revocation.

32. Caching, consistency, and time-of-check/time-of-use

Every authorization architecture must deal with the passage of time. An ACL may be updated between the initial check and the protected write. A capability may remain valid after an organizational membership changes. A temporary share may be consumed just before expiration or while an object's owner is being changed. These are time-of-check/time-of-use issues and policy consistency questions, not merely database performance problems.

For sensitive mutations, use an authorization check tied to the canonical object and relevant record state close to the transaction that performs the effect. If resource ownership or classification can change concurrently, incorporate the necessary version, transaction, or locking conditions. When authorization results are cached, include the right dimensions in the cache key: principal, action, object, tenant, and any policy or context fields that affect the result. A cache entry keyed only by URL or role is commonly inadequate.

The design should specify the consistency model: immediate local enforcement, bounded-delay propagation, or another documented guarantee. Google Zanzibar's research highlights the importance of causal relationships between object-content changes and access-control changes in distributed systems. Do not claim that a generic cache or token store provides Zanzibar's consistency guarantees without a deliberately engineered mechanism.

33. Tenant boundaries and cross-organization grants

A tenant boundary ensures that one customer or organizational unit cannot read, alter, or delegate authority over another's resources without a specific authorized collaboration mechanism. ACLs can represent tenant-owned objects and their approved member groups; capabilities can convey narrow access to an object after the trusted issuer verifies that the intended recipient may use it. Neither model automatically prevents cross-tenant leaks if object IDs are resolved ambiguously or the enforcement service trusts requester-supplied tenant fields.

A multi-tenant service should derive tenant identity from trusted session or workload context, resolve resource ownership server-side, and check cross-tenant grants against an explicit approved-sharing policy. Consider the edge case of a property manager employed by two companies: it may legitimately operate under separate organizations, but the active tenant context must be unambiguous for each action. A grant created in Company A should not become a Company B permission because the same email address appears in both accounts.

Record who issued an external grant, to which stable identity, for which resource, with which operations and expiry. Test resource enumeration, bulk exports, search indexes, background processing, caching, and share-link endpoints. Verify that a delegated handle cannot be reused to reach a sibling object merely by changing a path parameter.

34. Observability, audit evidence, and forensic reconstruction

Authorization observability should answer what access existed, how it arose, and what occurred. For ACLs, useful evidence includes the resource policy version, direct and inherited ACEs, effective group membership, decision time, and the change history of grants and removals. For capabilities, useful evidence includes issuance, delegation, attenuation, use, expiration, and revocation events to the extent the architecture supports those observations. A bare capability may not intrinsically record an issuer or chain of custody; that metadata may require a separate trusted service.

Log sensitive permission changes and high-risk operations without disclosing tokens or protected payloads. Signed URLs, bearer credentials, and capability values should be treated as secrets where their possession conveys access; an access log that records the entire URL can unintentionally become a credential repository. Privileged diagnostics can store stable token fingerprints or grant identifiers while redacting usable credentials. Distinguish authentication failures, authorization denials, policy evaluation errors, and resource-not-found conditions internally.

An investigation workflow should reconstruct the principal's authority at the time of the event, not only its current access. Include policy versions, identity membership snapshots, handle or token lifetime, source workload, and tenant context. Keep retention and access to audit trails proportionate to security needs, applicable law, and institutional privacy rules.

35. Threat model and failure-mode inventory

Both models can fail through mistakes outside their core abstraction. ACL failures include stale groups, inherited broad permissions, inconsistent allow/deny interpretation, unsafe administrative rights, missing per-object checks, and divergent control-plane replicas. Capability failures include exposure of bearer handles, excessive initial rights, uncontrolled transfer, missing revocation paths, and confusion between a secure reference and an ordinary guessable identifier. A hybrid system may inherit both sets of risks if its boundaries are poorly documented.

Security reviews should evaluate legitimate operations, malicious requests, administrative errors, outages, and recovery. A mechanism that is secure only when every dependency is healthy may need a safe failure behavior that does not create a default-open path.

37. Selection framework: choosing the appropriate authority representation

Choose an ACL-centered representation when the institution's principal business requirement is centrally administering who can access a particular object, such as a shared folder, a record collection, or a document collaboration workspace. Favor explicit object ownership, stable identities, manageable groups, change control, effective-permission reporting, and a reliable deprovisioning path. The ACL itself should not become an unbounded pile of individualized exceptions.

Choose capability-oriented mechanisms when a component can receive only the resources required for a particular operation, especially in sandboxing, microkernels, interprocess communication, isolated processing pipelines, and narrowly delegated workflows. An issuer or broker must securely create and deliver references; derived permissions must not amplify authority; and the system needs a realistic revocation strategy. Capabilities are particularly valuable when a user-controlled component should not have ambient authority to browse the overall resource namespace.

A hybrid is often appropriate for enterprise services: object-level ACL or relationship policy at authorization time, followed by narrowly scoped, short-lived operational handles. Select based on the trust boundaries, cost of audit/revocation, required cross-service interoperability, institutional governance, and the actual behavior of supported software rather than on terminology alone.

38. Worked scenario I — university research collaboration

A research center shares draft manuscripts, field notes, and restricted participant data. The university wants faculty collaborators to edit manuscripts, graduate assistants to review selected notes, and an external statistician to analyze one deidentified dataset. The ACL-centered design stores effective grants on research objects, using stable user and group IDs. A faculty group receives manuscript-edit rights; a narrower data-governance group controls restricted data; the external collaborator receives only dataset read rights after approval.

For data processing, a controlled service can issue a short-lived read-only object reference to the deidentified export. The statistician's sandbox receives this reference without permission to browse institutional storage. The authorization issuer records which object and permitted operation were approved. If collaboration ends, the data owner removes ACL grants and invalidates remaining share references according to the system's supported revocation mechanism.

Verification tests include: the student assistant cannot open raw participant records; the external statistician cannot modify the export or enumerate unrelated files; a transferred reference cannot access a different dataset; and membership removal produces denial at the target enforcement points within the documented window. The design also checks whether copied files or previously downloaded datasets remain outside the reach of ordinary permission revocation.

39. Worked scenario II — multitenant property management

A property platform serves unrelated landlords, management companies, tenants, and vendors. A manager should read leases for the properties assigned to their company; a resident should see only their lease and statements; a maintenance contractor should receive a time-bound work order and necessary site details. The resource model binds every lease, statement, and work order to a canonical property and tenant organization, with separate privileges for viewing, changing, exporting, and sharing.

An ACL or ReBAC-style policy service can decide whether a manager may open a work order. The platform may then deliver a limited capability-like token to a mobile contractor, granting access only to work-order:W398 and its approved attachments until the task ends. That token cannot serve as evidence of permission to view other residents' documents. The token issuer itself must validate the property-company relationship and current contractor assignment.

Negative tests simulate moving the contractor to a different property, guessing another work-order ID, forwarding a link, changing the parent company, and using a token after revocation. Governance records the grant owner, work order, permitted operations, maximum lifetime, and resulting audit trail. Sensitive resident details should be minimized, since an authorized task does not imply authority to see every field.

40. Worked scenario III — payroll and approvals

A finance department needs payroll preparers to modify draft payroll batches while reviewers may approve a batch they did not prepare. An ACL can grant read/write permissions to payroll-preparers and read/approve permissions to payroll-approvers on the relevant application objects. However, separation of duties requires business logic beyond a static object grant: one individual must not both submit and approve the same batch, even if that individual belongs to both roles.

The approval action therefore checks the actor, the recorded preparer, current batch state, allowed accounting period, tenant, and any mandatory dual-approval threshold. A download service may receive a read-only handle to a finalized payment report, but it must not gain permission to edit payroll configuration or approve disbursement. Audit evidence should record which policy authorized each stage and which record version was approved.

Test concurrent approvals, batch ownership changes, role withdrawal after login, administrative override, failed authorization service, and export after a batch is canceled. The design teaches a central lesson: neither ACL membership nor capability possession alone expresses every stateful business constraint without accompanying policy logic.

41. Worked scenario IV — isolated document conversion

A campus publishing service accepts uploaded PDFs and converts them into accessible document previews. Conversion libraries process complex, potentially hostile input, so they should not run with unrestricted access to university storage, network shares, credentials, or internal services. The trusted front-end first verifies that the requester's identity may process the chosen document and that the content type and task are allowed.

The service starts a restricted conversion worker, passes a read-only input handle and a write-only output handle for a designated temporary result, and avoids exposing a reusable directory traversal capability or broad service account. The worker cannot access other student files merely by constructing a path. Its filesystem, network, process, and system-call environment are restricted using supported sandbox controls.

Tests attempt to open unrelated paths, write back to the input, transfer an output handle beyond the job, access the internet, or use malicious embedded content to invoke privileged APIs. Where the platform cannot provide strong capability-like isolation, the team documents compensating controls and does not claim a full object-capability security boundary. Successful conversion is evaluated alongside isolation and cleanup.

42. Worked scenario V — leaked share and urgent revocation

An administrator discovers that a vendor's temporary download link was pasted into an external ticketing conversation. The link may be a bearer token usable without further login; merely deleting it from the ticket may not invalidate cached copies. Incident triage identifies the object, token issuer, allowed operation, actual expiration, access log records, and whether the vendor also holds independent ACL access.

The responder disables the compromised sharing path through the supported service mechanism, which may require policy denial, rotating or invalidating signing credentials, removing underlying access grants, or otherwise retiring the link. The team verifies that a request using the formerly valid link now fails. If a session or handle may remain alive, the response includes termination or isolation actions within supported platform capabilities. Logs are examined without exposing the token again.

Post-incident controls include shorter link lifetime, issuer-scoped credentials, restricted object operations, sensitive-URL redaction, safer collaboration channels, and a procedure to inventory active shares. This scenario highlights how a capability-like share can be highly usable yet require more deliberate revocation design than an administrator expects.

43. Authorization test matrix and negative testing

Authorization testing must verify both legitimate work and attempted boundary crossings. The test plan should combine principal, resource, operation, grant path, and policy state. A test harness should avoid privileged bypass accounts when verifying ordinary permissions. Each result should record expected outcome, actual outcome, relevant policy version, and whether the operation affected protected data.

Automate stable tests in continuous integration where practical, and include manual investigations for identity groups, inheritance, token disclosure, and unexpected behavior across integrated services. Do not treat a correct user-interface warning as proof of backend enforcement.

44. Implementation roadmap and division of responsibilities

Phase 1 — inventory and model. Identify protected resource classes, owners, principals, operations, existing ACL stores, signed link issuers, privileged broker services, and any capability-bearing handles. Draw the access-control matrix and mark trust boundaries. Distinguish business approval constraints from simple object permissions. Create an initial sample of effective-access traces for sensitive resources.

Phase 2 — define authority contracts. Establish a canonical resource ID scheme, principal lifecycle, permission vocabulary, and clear grant/deny semantics. Specify whether rights may be inherited, how delegated references are attenuated, when they expire, and what guarantees revocation provides. Assign ownership of policy issuance and security testing. Define a safe default response to missing identities, unknown objects, and dependency failures.

Phase 3 — deploy a limited implementation. Introduce the chosen enforcement at a small set of resources, preserve necessary user workflows, and test negative cases. Monitor discrepancies between expected and actual access. If a new capability issuer is added, perform threat modeling around signing keys, handle transport, log leakage, transfer, and invalidation.

Phase 4 — operate and certify. Establish recurring effective-access reviews, stale grants cleanup, exception approvals, drift detection, incident revocation drills, and periodic measurement of denied unauthorized attempts. Re-evaluate architectures as storage services, operating systems, group directories, and cloud APIs change. Security architecture, identity governance, application owners, and incident response should have explicit responsibilities rather than assuming the ACL editor alone owns the risk.

45. Operational indicators and evidence packages

Metrics should reflect actual authority and revocation quality rather than merely counting ACL entries. Useful measures include: proportion of sensitive objects with named owners; proportion of grants with justified permission sets; time to remove access after departure; observed stale-grant rate; active temporary shares beyond intended lifetime; percentage of authorization checks covered by negative tests; permission-change rollback rate; and median time to verify a critical revocation. Do not publish one “security score” without explaining scope and limitations.

A reviewable evidence package for a sample protected object includes: canonical object ID; classification and tenant; owner; explicit and inherited grants; identity and group membership paths; any issued capability-like references; current policy versions; relevant change approvals; verified access-test outcomes; and outstanding exceptions. The goal is reproducibility: another authorized reviewer should be able to explain why a specific user or service can perform a particular operation.

For an incident, record both authority configured now and authority available when the event occurred. A current ACL screenshot cannot establish past access if groups, inheritance, or token issuance have since changed. Preserve time-stamped policy changes and capability issuance data in a controlled and privacy-aware manner.

46. Implementation and governance checklist

  • Define every resource class and operation using stable identifiers.
  • Record each resource's owner, tenant, classification, and approval authority.
  • Inventory ACLs, group memberships, inherited grants, share policies, and capability issuers.
  • Document the real platform-specific ACL evaluation and deny/allow precedence.
  • Separate content modification rights from permission administration rights.
  • Verify POSIX ACL masks and Windows DACL inheritance where applicable.
  • Enforce object authorization at backend operations, not only UI or navigation.
  • Constrain each capability or delegated handle to the minimal object and operation scope.
  • Protect capability authenticity, bearer secrecy where required, and secure transport.
  • Prevent derivation from creating greater authority than the source.
  • Specify what happens to open handles and issued tokens after permission changes.
  • Test time-of-check/time-of-use and concurrent policy updates.
  • Prove tenant separation in list, export, search, background, and direct-object operations.
  • Redact usable bearer credentials from logs and analytics.
  • Maintain a rapid operational procedure for compromised links or handles.
  • Reconcile identity departure, group changes, ownership transfer, and orphaned grants.
  • Run positive and negative tests with representative nonprivileged accounts.
  • Audit sensitive grants, privilege administration, and delegated authority issuance.
  • Preserve policy versions and revocation evidence for incident reconstruction.
  • Review exception lifetimes, operational metrics, and outstanding risk ownership.

48. Study questions and applied exercises

  1. Construct a four-subject, five-object access-control matrix for a university department. Identify where ACL and capability representations would store its entries.
  2. Explain why looking only at a POSIX named group entry may misstate effective write permissions. Describe how to verify the result without using a privileged account.
  3. Distinguish Windows null and empty DACLs. Why is confusing them dangerous?
  4. A file's ACL is changed from read/write to no access while an application still holds an open descriptor. What additional questions must a revocation plan answer?
  5. Design a capability issuance procedure for a one-time document conversion job. Identify issuer, recipient, object, rights, lifetime, and revocation route.
  6. Distinguish a true kernel-protected capability from an application dictionary containing a file path and can_edit=true.
  7. Explain the confused-deputy failure when a privileged thumbnail generator trusts a customer-supplied path.
  8. Identify two risks from forwarding a signed download URL through email, analytics, or chat.
  9. Write negative tests for cross-tenant object retrieval, inherited folder permissions, and stale authorization caches.
  10. Explain why a hardware-bounded CHERI pointer is not the same as a Linux process's named capabilities or a cloud IAM role.
  11. Describe the difference between changing an authorization policy and verifying that a running service is no longer able to exercise old authority.
  12. Propose an evidence package sufficient to reconstruct why a vendor accessed a confidential report two weeks before their account was disabled.

Applied exercise A — Permission trace. For a sample directory, list the owner's rights, named user/grant entries, relevant mask, group memberships, directory traversal rights, and effective operations. Explain every difference between displayed grants and effective access.

Applied exercise B — Authority graph. Draw a document processing chain with a broker, conversion worker, archive service, and log collector. Mark the capability or credential each component possesses and identify the most dangerous unintended delegation edge.

Applied exercise C — Revocation rehearsal. Define a simulated compromised share token, revoke its authority using the supported platform mechanism, and measure the maximum time before negative tests consistently deny the operation. Avoid exposing usable credentials in evidence logs.
