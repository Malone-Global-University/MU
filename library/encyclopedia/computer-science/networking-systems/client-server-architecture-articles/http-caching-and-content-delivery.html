Scope, Purpose, and Responsible Boundaries

HTTP caching allows a recipient or intermediary to store an HTTP response and reuse it for a later request when the applicable protocol rules permit reuse. Content delivery places selected representations close to their consumers through edge networks, regional caches, and origin services. Used together, they can reduce latency, origin processing, network transfer, and the effects of ordinary demand spikes. They also create a subtle correctness obligation: a reused response must be appropriate for this request, this user, this moment, and this security context.

This Level 5 specialist article extends Client–Server Architecture in the Client–Server Architecture Unit. It follows Server Load Balancing, which selects a backend for work; caching may avoid contacting that backend at all. The present article interprets the core HTTP semantics of RFC 9111 together with RFC 9110, the extensions that permit qualified stale reuse, and the operational requirements of content-delivery networks (CDNs).

A cache is not an authority for a bank balance, enrollment entitlement, exam grade, access decision, or revocation unless a system has explicitly modeled the acceptable staleness and verification mechanism. A cache hit does not establish that the answer is correct. Conversely, a policy of bypassing every cache can cause needless origin saturation, unpredictable latency, and high operating expense. The design objective is useful reuse under controlled freshness, identity, and failure boundaries—not the maximum possible hit-rate percentage.

The Client–Cache–Origin Request Path

A user agent requests an HTTPS resource identified by a scheme, authority, and target path. Depending on the deployment, it may find a reusable representation in its own HTTP cache, a service-worker-managed application cache, a corporate proxy, a CDN edge point of presence (PoP), a regional shield, or an application-side reverse proxy. Only when no suitable stored response exists—or when validation is required—does some layer need to contact the next hop toward the origin server. Every hop has a distinct policy and trust boundary, and a browser may also use non-HTTP storage mechanisms that follow different rules.

Browser or API client
   | (browser cache hit? no network request)
   v
CDN edge / point of presence  -----> cached response, if eligible
   | (edge miss or revalidation)
   v
Regional shield / reverse proxy ----> cached response, if eligible
   | (miss or required validation)
   v
Application origin / static storage
   |            |
   |            +--> database, asset build, or object store
   +--> response + metadata (Cache-Control, ETag, Vary, ...)

Trace both the forward request path and the response metadata returned on the reverse path. For the same request, the browser may be a hit while a CDN has no entry, the CDN may revalidate with a 304 Not Modified, or a regional cache may serve stale content during an origin interruption. An accurate incident report identifies the serving layer, the policy in effect, the cache key, the observed age, and whether origin processing occurred. Without those observations, a fast response can be mistakenly attributed to a healthy application that the request never touched.

Private, Shared, and Application-Managed Caches

A private HTTP cache is dedicated to one user agent or user context, such as a browser's ordinary HTTP cache. A shared HTTP cache serves more than one user and often operates at a reverse proxy, enterprise proxy, or CDN. HTTP private means that shared caching is prohibited for the indicated response (subject to field-name-qualified semantics); it does not encrypt the response, prevent screenshots, or erase an already delivered page from browser history. no-store instructs compliant HTTP caches not to store response information, but other storage paths and application behavior still require separate controls.

A service worker can intercept fetches and manage a Cache Storage API store under its own application logic. The application must deliberately implement suitable privacy, invalidation, lifecycle, and access policies; ordinary HTTP Cache-Control rules are not, by themselves, a complete description of custom service-worker caching behavior. An application memory cache, database query cache, or distributed key-value store is another independent system. Such caches may hold model objects rather than HTTP representations and require explicit invalidation, tenancy partitioning, and authorization checks.

Avoid the blanket statement that "the CDN caches all static files". CDNs differ by default cacheability rules, TTL overrides, supported methods, cookie handling, response-status handling, and customer-defined edge logic. Operators should document what each layer stores, whether cache configuration overrides origin response metadata, and which layer is authoritative when policies conflict. These differences matter as much for security investigations as for performance tuning.

Request Methods and Response Cacheability

The most common cached exchange is a successful GET returning a complete representation. HEAD responses also participate in cache semantics; a HEAD response can update metadata for a stored GET response when the standard's conditions are met. Other methods are not universally cacheable merely because an application emits Cache-Control. For example, POST caching requires explicit freshness and a usable content-location model, and general-purpose cache support is limited. An unsafe method can invalidate stored responses for a target URI when a successful response is received under the protocol rules.

Cacheability depends on a combination of method, status, headers, authorization context, representation metadata, and the cache's implementation policy. HTTP has provisions for some redirects, client-error responses, and partial responses. Common status codes such as 200, 203, 204, 206, 300, 301, 308, 404, 405, 410, 414, and 501 have specific cacheability semantics; this is not a promise that a particular CDN will store them by default. An unexpectedly cached 404 can delay visibility of a newly uploaded resource. The correct remedy is an intentional freshness policy, not the assumption that error responses never enter caches.

Never cache a state-changing operation's side effect. Storing a representation for a later GET is a different act from deciding whether it is safe to repeat a POST, PATCH, or payment request. Cache storage, retry semantics, idempotency, and application transactions have distinct correctness models. Separate those responsibilities in API design and in incident reviews.

Cache-Control: Core Response Directives

Cache-Control carries the primary cache instructions. The following table summarizes common response directives, not every protocol extension. Always interpret them under RFC 9111 rather than as independent switches; for example, no-cache does not mean "do not store"—it requires successful validation before reuse. By contrast, no-store prohibits storage by compliant HTTP caches. must-revalidate restricts stale reuse once the response ceases to be fresh, including during an origin outage. The public and s-maxage directives affect some restrictions on shared reuse, so they must not be applied casually to user-specific data.

Response directive Operational meaning Typical design decision
max-age=N Freshness lifetime in seconds Short-lived public resources or versioned assets
s-maxage=N Shared-cache freshness lifetime; also enforces revalidation restrictions after expiry Independent edge lifetime for an intentionally shared response
public Explicitly permits storage by shared caches where conditions otherwise restrict it Public representations, not private dashboards
private Prevents shared-cache storage of the full response Signed-in or user-specific browser responses
no-cache Storage may occur, but reuse requires successful validation HTML documents that must check for updates
no-store Instructs HTTP caches not to store request/response content Sensitive records, tokens, private account results
must-revalidate Forbids reuse once stale without successful validation Strict freshness or policy-controlled responses
proxy-revalidate Like must-revalidate for shared caches only Shared intermediary policy
immutable Signals that a fresh response will not change for its lifetime Content-hashed assets
stale-while-revalidate=N Allows bounded stale reuse while validation proceeds, when applicable Low-risk public content where latency matters
stale-if-error=N Allows bounded stale reuse on qualifying errors, when applicable Continuity of noncritical public content

The request may also contain directives such as no-cache, max-age, max-stale, min-fresh, or only-if-cached. A browser reload request can therefore change whether a response is reused even when the server emits exactly the same response directives. A CDN-specific override may change the observed behavior further; record policy at both origin and edge rather than inferring the active rule solely from one Cache-Control header.

Freshness Lifetime, Current Age, and the Decision to Reuse

A cached response is fresh when its estimated current age is less than its freshness lifetime. The protocol derives age from a combination of Date, Age, request/response transit times, and resident time. Simplifying examples can use a well-synchronized origin Date and a trusted Age header, but production caches must follow the full RFC 9111 current-age algorithm, including handling of apparent age and upstream delays. A response with Cache-Control: max-age=300 does not necessarily remain fresh for five minutes after it reaches the browser; it may already have spent two minutes inside another shared cache.

Consider a public catalog response served from a shared cache with Age: 180 and a five-minute freshness lifetime. Ignoring small transit delays for illustration, the response has about 120 seconds of freshness remaining. If it is later encountered with Age: 330, it is stale. The cache must validate it or follow an applicable stale-reuse permission; it cannot silently reset the clock simply because another edge node forwarded it. HTTP caches may calculate age even when the Age field is absent, so a missing field does not prove the response is newly generated.

For an explicit shared lifetime, s-maxage takes priority in a shared cache; otherwise max-age or Expires can determine freshness, with heuristic rules reserved for eligible responses lacking explicit expiration. A useful design worksheet states the maximum tolerated staleness in business terms first, then chooses lifetimes and validation rules that comply with it. The number of seconds is a consequence of the requirement rather than a convention copied from a competitor's site.

Heuristic Freshness and Negative Caching

When an explicitly cacheable or heuristically cacheable response lacks defined freshness, an HTTP cache may assign a heuristic expiration using available metadata such as Last-Modified. RFC 9111 constrains where heuristic freshness is permitted, but does not impose a universal percentage or one standard expiration interval. Implementations and intermediaries may employ different policies. Operators should therefore avoid leaving the effective lifetime of business-critical pages to accidental heuristics.

Negative caching stores responses indicating absence or failure, such as a 404 Not Found, when cache rules and configuration permit it. This can protect the origin from repeated requests for non-existent assets but also creates a failure mode during publication: a user requests a not-yet-uploaded file; an edge caches the 404; the author uploads the file; users continue seeing the cached absence until expiration, invalidation, or permitted revalidation. Redirects can behave similarly: a cached permanent redirect may persist after an intended route change.

For publishing workflows, define conservative policies for 404 and 301/308 responses, test canonical route changes, and record edge-specific error TTL overrides. Do not assume that every edge respects the same error-status cache duration. When a missing page is unexpectedly sticky, examine the response that originally produced the failure, not only the newly published 200 response.

ETag, Last-Modified, and Conditional Requests

A validator lets a cache ask whether its stored representation is still valid without always retrieving the full body. An ETag is a server-generated entity tag representing a selected resource version, while Last-Modified records an origin timestamp. A request carrying If-None-Match can lead to a 304 Not Modified when the selected representation still matches. In eligible cases, If-Modified-Since provides time-based conditional validation. An ETag is not inherently a cryptographic hash or a proof of integrity; its meaning is defined by the origin.

GET /assets/course-outline.css HTTP/1.1
Host: example.edu
If-None-Match: "rev-84"

HTTP/1.1 304 Not Modified
Date: Mon, 23 Nov 2026 17:00:00 GMT
ETag: "rev-84"
Cache-Control: public, max-age=300

The 304 has no response body for the requested representation. A compliant cache updates permitted stored metadata and reuses the stored entity when the conditions are satisfied. If the origin instead returns a new 200 with a new ETag and content, the cache replaces the representation as its policy allows. If-None-Match takes precedence over If-Modified-Since where both are supplied for validation under HTTP semantics. A cache that receives a 304 cannot infer that every stored variant or every user-scoped response is validated; the validator must correspond to the selected representation.

For APIs that mutate resources, other conditional headers such as If-Match support lost-update prevention. That is an application concurrency mechanism, distinct from the revalidation path used to save transfer bandwidth. A strong validator can be appropriate for byte-specific decisions, whereas a weak ETag permits semantic equivalence for cache validation but is not suitable for all range or mutation conditions.

A Stored Response: Miss, Hit, Revalidate, Replace

The simplest lifecycle begins with a miss: the cache has no reusable representation for the request key and forwards the request to the next hop. If the origin's response is storable, the intermediary may save it and return it to the client. Subsequent matching requests can be hits while the response is fresh. After expiration, a cache might issue a conditional request, receive 304, update stored metadata, and continue to reuse the body; or it might obtain a replacement 200. If the response is not storable or does not match the request, the cache must fetch a permitted response instead.

First request       : miss -> origin 200 -> store (when eligible)
Second fresh request: hit  -> stored response; origin not contacted
Expired response    : revalidate with validator -> 304 -> reuse
Updated resource    : revalidate -> origin 200 -> replace stored body
Disallowed response : bypass or non-storage according to policy

Not every vendor's dashboard reports the same states. One product may call a validated delivery a hit; another may distinguish a revalidated hit from an ordinary hit. Some systems collapse concurrent misses into one origin fetch and label waiting requests as hits or coordinated fetches. Define the numerical metric carefully. A headline hit rate without origin bytes, shield participation, and revalidation rate may overstate performance savings or hide an unsafe cache policy.

Vary and Representation Negotiation

An origin can return different representations for requests sharing the same URL. The Vary response header specifies which request header fields influenced representation selection. A cache must compare the nominated field values against those of the original request before reusing a stored response without validation, subject to the standard's matching rules. A common example is Vary: Accept-Encoding, which separates compressed and uncompressed variants when a cache's key and normalization account for them correctly. Vary: Accept-Language can distinguish language preferences, but high-cardinality preferences may create many variants.

Vary is not a substitute for authorization. A response derived from a particular signed-in user's profile must not become a generally shareable object because an engineer put Vary: Cookie or Vary: Authorization on it. The policy must first establish whether shared caching is permissible, then establish an appropriate, complete variant identity. Vary: * prevents ordinary matching of a stored response for reuse; it is not a way to express every possible personalization feature. CDN custom cache keys may treat or override Vary in product-specific ways, so platform configuration must be tested.

Design intentionally low-cardinality variants. Instead of varying on an entire User-Agent string, consider explicitly generated image formats, viewport classes, or application device modes when these truly affect response bytes. Varying unnecessarily on cookies, languages, and headers can turn a cache into a near-always-miss datastore while increasing memory use and operational confusion.

Cache Keys: URLs, Queries, Headers, and Cookies

A cache key identifies the stored response candidate for a new request. The primary HTTP identity normally includes the target URI and an allowed method; intermediary-specific configuration may extend it with chosen query parameters, header fields, cookies, device signals, or normalized routing rules. An under-inclusive key can confuse distinct users, languages, or resource variants, creating incorrect or unsafe reuse. An over-inclusive key creates unnecessary misses and makes eviction unpredictable. The correct key is the narrowest one that still captures every input that legitimately changes the representation.

Suppose a catalog endpoint /course/42?format=compact and /course/42?format=detailed returns different bytes. Ignoring format in the key would be incorrect unless the origin ignores that parameter too. Conversely, /news?utm_campaign=fall and /news?utm_campaign=spring may deliberately share the same representation; dropping a tracking parameter might improve reuse if routing, authorization, and origin behavior are proven identical. Sorting or removing query fields must use a canonicalization algorithm consistent with the origin: an attacker should not be able to exploit a mismatch between what the cache keys and what the application reads.

AWS CloudFront documents separate cache policies and origin request policies: a header can be forwarded to the origin without necessarily affecting the cache key, and selected key dimensions are also forwarded. This distinction is powerful but risky. If the origin changes the response according to a forwarded header excluded from the key, one consumer's response may be stored under a key shared by another. Review each forwarded input as either representation-defining or safely irrelevant; do not base the decision solely on bandwidth optimization.

Compression, Content-Encoding, and Cache Variants

Text assets such as HTML, CSS, JavaScript, JSON, and SVG often benefit from content coding such as gzip or Brotli. A server can negotiate content coding using Accept-Encoding, with the selected coding indicated by Content-Encoding. A cache must keep representations and validators consistent with the coding and may store multiple coded variants or apply a normalized on-the-fly compression strategy according to its implementation. Reusing a compressed representation for a client that cannot decode it is a correctness failure, not merely a performance loss.

Compression changes byte-level representation properties. Strong ETags for different coded variants generally need to reflect those different representation bytes, while weak validators may intentionally represent semantically equivalent versions under appropriate conditions. Range requests must operate on the selected representation and its byte positions; transparent transformations require particular care. Avoid asserting that a generic CDN always compresses all resources. Binary image, audio, and video formats may already be compressed, and blind recompression can waste CPU or even enlarge transfers.

Review content coding alongside TLS and secret-bearing responses. Compression of attacker-controlled data adjacent to secrets can create side-channel risks in particular threat models. The solution depends on the data flow and attacker's observation capabilities; turning off all public compression is not a universal security requirement. Separate public, cacheable asset compression from compression policies for sensitive dynamically assembled responses.

Authorization, Cookies, and Shared-Cache Eligibility

The presence of an Authorization request header ordinarily restricts shared-cache reuse under RFC 9111 unless the response carries an explicit directive that permits it, such as qualifying public, s-maxage, or must-revalidate semantics. This is a standards rule, not a license to mark every authenticated endpoint public. A response containing student grades, account settings, access tokens, addresses, or personal messages should normally use private, no-store or another explicitly justified restrictive policy. Even a cache that is technically permitted to store a response may expose information if the key fails to distinguish users or the application emits public directives in error.

Cookie presence alone is not a universal protocol-level "never cache" rule. Many CDNs implement their own cookie-oriented default behaviors, so an untested configuration can either cache too little or accidentally cache a personalized response. The application must declare whether each route is public, user-specific, tenant-specific, or sensitive, then verify that the cache and origin enforce compatible rules. Session cookies, access tokens, and authorization decisions must not be treated as incidental metadata that can be stripped to raise hit rates.

A strong baseline is to avoid shared caching of authenticated representations unless there is a clear, audited model for public output. A legitimately public file downloaded by an authenticated browser may be shareable; a user's billing detail must not be. Document invalidation and revocation behavior when cached data relates to permissions. A resource that was public yesterday might become restricted today, and a long cache lifetime can preserve exposure after the source policy changes.

Sensitive Responses and Non-HTTP Storage Limits

For sensitive pages, Cache-Control: no-store is an important instruction to compliant HTTP caches, but it is not a universal data deletion mechanism. A user may already have downloaded, screenshotted, printed, exported, or otherwise retained information. Browser back-forward caches, history, service-worker code, IndexedDB, application memory, and operating-system storage have separate lifecycles. The system must prevent sensitive responses from being inappropriately stored in additional layers, and it must not promise remote deletion merely by changing response headers.

Treat personal data and multi-tenant records as a classification problem before a TTL problem. Classify routes such as public static, public semi-dynamic, authenticated individual, tenant-scoped, operational secret, and legally restricted. Determine whether caching is permitted at any shared layer, what consent or legal rules apply, the maximum acceptable age, and the steps required upon logout, role change, or revocation. Cache keys incorporating user identifiers may be permissible for specialized private systems but are not a replacement for access control; every retrieval path still needs to enforce the authorization model.

Security reviews should inspect not just the normal 200 response but also redirects to login, error pages, password-reset endpoints, download endpoints, document-preview renderers, and content-negotiated variants. Sensitive information can escape through headers, redirects, mixed public/private fragments, or a cache rule that treats a URL file extension as more authoritative than the response's actual semantics.

Stale-While-Revalidate and Stale-If-Error

Stale-while-revalidate and stale-if-error are optional extensions standardized by RFC 5861. They allow a cache to reuse a response after ordinary freshness has expired under defined conditions. With stale-while-revalidate=N, a cache may return an eligible stale response during a bounded window while validation proceeds, often making the user experience faster. With stale-if-error=N, a cache may reuse a stale representation during qualifying upstream failures for no longer than the permitted stale window. These allowances are not guarantees that every intermediary implements the behavior, and they do not override security or revalidation restrictions that must be honored under the active rule set.

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Cache-Control: public, max-age=120, stale-while-revalidate=30, stale-if-error=300
ETag: "public-article-v17"

This illustrative public-document policy allows two minutes of ordinary freshness, then a limited window for permitted stale reuse while validation happens and a longer qualifying stale-on-error window. It is inappropriate for an exam answer key published at a precise time, a credential revocation, a medical emergency instruction, or an account balance. A stale response should be recognizable through diagnostic metadata where supported; user interfaces may need an explicit as-of timestamp for information whose age affects decisions.

A useful rule is to make staleness a conscious product promise. For an evergreen public reference article, a few minutes of stale-on-error may be acceptable; for a changing service-status bulletin, the cost of publishing a superseded warning may exceed any performance benefit. Test disconnected origins, errors, revalidation races, multi-tier caches, and explicit must-revalidate or s-maxage policies before approving stale-serving behavior.

Immutable and Content-Addressed Static Assets

A hashed filename such as /assets/site.8f2e1a.css can serve as a content-addressed deployment identity: changing the content yields a different name, so the old URL never needs to return different bytes. Such assets can safely use long freshness periods and immutable when deployment and retention processes guarantee the identity-to-bytes relationship. RFC 8246 describes immutable as a signal that the representation will not change while it is fresh; it is not an instruction that a browser can ignore expiration forever.

GET /assets/site.8f2e1a.css HTTP/1.1
Host: example.edu

HTTP/1.1 200 OK
Content-Type: text/css
Cache-Control: public, max-age=31536000, immutable
ETag: "sha256-example-build-id"

The HTML entry document usually should not receive the same year-long immutable policy because it is the pointer that selects the current hashed files. A safer deploy strategy is: publish new assets under new names; verify their availability at every required origin; publish HTML that references those names; retain old assets through the maximum expected client lifetime; then remove expired versions through an explicit retention policy. Reusing a hashed filename for different bytes breaks the model and can leave clients with mismatched JavaScript and CSS for long periods.

An actual cryptographic content address must be derived and verified correctly. An ETag that merely looks like a hash is not evidence of content integrity. Use signed release manifests, subresource integrity where appropriate, and deployment-level provenance for stronger claims. Cache freshness is about reuse eligibility; supply-chain integrity is a separate property.

HTML, JSON APIs, and Dynamic Public Pages

For ordinary HTML, short freshness or explicit validation often gives a good compromise between responsiveness and timely updates. Cache-Control: no-cache can permit local storage while requiring successful validation before reuse, which often saves bytes when a 304 is available. A carefully classified public catalog or announcement API may be appropriate for shared caching, especially when its response is identical across users and clearly time-bounded. In contrast, GET /api/me is user-specific even if its HTTP method is cache-friendly, and an HTTP method alone never determines whether shared storage is safe.

GraphQL or REST applications should identify the representation-defining parameters: path, query, locale, authorization context, API version, feature flags, and tenant ownership. A uniform request structure can mask wildly different freshness needs. A public list of historic course titles might be shareable for minutes; a live registration seat count may require seconds or explicit validation; a student's private transcript should not enter a shared cache at all. The application can also split static public components from sensitive user-specific components so that the page benefits from caching without storing private output at the edge.

A content management system should publish a per-route cache contract with asset class, canonical key inputs, allowed stores, freshness lifetime, validator strategy, purge trigger, and error fallback. Treat cache policy as version-controlled application behavior rather than an undocumented set of CDN dashboard checkboxes. That makes incidents reproducible and lets testing verify semantic behavior before deployment.

CDN Points of Presence, Origin Shields, and Fill Paths

A content delivery network operates geographically and topologically distributed points of presence that can serve static or eligible dynamic content nearer to requesting clients. A CDN edge is often both a network entry point and an HTTP intermediary; it may terminate TLS, apply routing or security policy, cache a response, transform permitted representations, or forward requests to an origin. Distance alone does not determine latency: peering, congestion, cache hit status, TLS connection reuse, and edge-to-origin routing all matter. The nearest geographic location is not always the fastest network path.

A regional shield or additional caching tier can consolidate cache misses from many edge nodes. Without a shield, a newly popular object might be fetched by dozens of PoPs; with shielding, repeated misses can converge on an intermediate cache. That reduces origin load but adds another policy layer and makes the total freshness path more complex. Origin shielding does not solve stampedes if the shield itself fails to coordinate concurrent fills, nor does it make an incorrect cache key safe.

CDN architecture should document points of presence, TLS identity, origin reachability, authentication to origins, cacheability defaults, route match rules, origin failover, logging, purge authority, and incident control. When selecting a platform, compare verified capabilities such as cache-key customization, regional shield support, purging behavior, response-header handling, log export, compliance locations, and control-plane resilience. Vendor feature labels should not replace representative tests against the current deployed configuration.

Origin Load, Request Collapsing, and Stampede Control

A cache stampede occurs when many concurrent requests for the same expired or missing object reach an origin before a new cached response becomes available. A cache with a 99% hit rate in normal operation can still overwhelm its origin during a coordinated invalidation or flash crowd. Request collapsing or single-flight fill allows one upstream request to populate the object while additional identical requests wait or receive a permitted stale response. Implementation details vary, and not every intermediary provides identical behavior for non-cacheable responses or different variants.

Coordinate protection at several layers: bounded concurrency toward the origin, request collapsing for a key, limited stale-while-revalidate for suitable public content, jittered refreshes, capacity budgeting, and a fallback strategy for origin failures. Avoid prewarming every popular object simultaneously across every PoP. A purge that invalidates thousands of objects can temporarily increase origin traffic, so purge execution needs rate limits, staged scope, and observability.

For dynamic cache fills, distinguish origin computation time from transfer time. Caching a slow database-backed representation might eliminate repeated computation and be valuable even if its payload is small; caching a large, cheap static image primarily saves bandwidth. Measure origin requests per second, cache-miss concurrency, fill bytes, database load, and tail latency. A "hit rate improved" claim is incomplete if the few remaining misses became expensive enough to overload the origin.

Error Responses, Redirects, and Recovery Constraints

An intermediary may encounter origin timeouts, connection refusals, 500 responses, deliberate maintenance pages, and application redirects. The distinction between caching a normal response and caching an error response matters. A stored 404 can be valid when a resource is genuinely absent; a platform-configured error TTL can also make it persist longer than intended. CDN products may have special default or override policies for 403, 404, 500, and other statuses, and some can replace origin errors with custom pages. Verify these behaviors instead of applying one broad "cache all" rule.

A redirect may be cached under HTTP rules; therefore, a change from an old URL to a new one can remain visible to users after a website deployment. A permanent redirect status does not necessarily mean "can never be changed" in every cache, but it often creates persistent client behavior. Test extensions, trailing slashes, query redirects, and canonical host migrations with an explicit redirect policy. For sensitive resources, a redirect to a login page must not be served to another user merely because the URL or status looks shared.

Under an origin outage, a qualified stale response may be safer than an empty page for noncritical public material; for transaction results and safety-critical guidance it may be actively harmful. Error fallback is a business decision tied to information age and user impact. If no permissible stored response exists, correctly return an error rather than inventing a success or replaying an unauthorized response.

Range Requests, Partial Content, and Large Objects

Video, archives, large documents, and resumable downloads may use HTTP Range requests and 206 Partial Content responses. An intermediary can store and combine partial responses only under the conditions specified in HTTP caching and representation semantics. Correct assembly depends on matching strong validators, byte ranges, and representation coding. A 206 that belongs to an older file version cannot be mixed with a range from a different version to reconstruct a document.

The If-Range header permits a client to request a range conditionally, falling back to the complete representation when the validator does not match under HTTP rules. Other headers such as Content-Range and Accept-Ranges describe the representation's partial-delivery capabilities. The exact decisions are more nuanced than "the CDN caches chunks"; some providers cache a full object on the first range request, some cache spans, and some require explicit settings for large-object support.

For large PDFs, training videos, and software releases, test edge behavior with a cold cache and repeated partial requests. Monitor how much the CDN fetches from the origin versus how many bytes the client actually consumes. A user seeking the final minute of a video should not cause repeated full-object origin retrievals unless that cost is explicitly accepted. Ensure access-controlled downloads use signed URL or token models with properly modeled expiration and caching boundaries.

Invalidation, Expiration, Revalidation, and Purge

Expiration allows an object to become stale at the end of its freshness lifetime. Revalidation contacts the next hop to confirm whether a stored representation remains usable. Invalidation marks or removes a stored representation so a subsequent request cannot reuse it normally. Purge is a provider-specific administrative mechanism that may invalidate objects by URL, prefix, tag, key, or surrogate grouping. Different platforms support different purge granularity and propagation behavior; a completed purge command does not necessarily guarantee instant eviction from every end user's private browser cache.

Three common deployment patterns solve different problems. Content-addressed filenames make old and new assets coexist, often avoiding large purges. Short-lived HTML ensures that pointer documents can update through expiration or validation. Targeted CDN purge handles urgent corrections to public documents, but it requires authority, observability, and an origin that is ready to serve the new representation. If an edge purges before the new origin file is available, the purge may simply populate a new cached 404.

A robust publication workflow stages the object, checks its hash and correct content type, validates responses from the origin path, publishes new references, then uses limited purge only where required. Log who initiated a purge, why it was necessary, how many keys were affected, and whether rollback is possible. Purge credentials are privileged production controls; protect them like deployment credentials rather than embedding them in public scripts.

Invalidation After Writes and Eventual Consistency

When content changes after a CMS edit, a registration transaction, or an inventory update, the cache needs a clear invalidation owner. A publish event might request a purge, while a database transaction changes authoritative state. These operations often are not atomic across systems. A job may commit the origin update but fail to purge a cache, or purge may arrive before a replicated origin can return the new version. Retrying blindly can create races or excessive invalidation traffic. The operational design must specify ordering, retries, deduplication, and reconciliation.

Eventual consistency is not a catch-all excuse for serving any old response. Each application should define a staleness budget. A public library article might tolerate minutes; an updated staff access revocation may require immediate checks against authoritative controls. For write-heavy systems, prefer read-your-writes guarantees where users need to see their own committed change, or bypass cache for those read paths. A global edge cache may be inappropriate when the product promise requires immediate read-after-write consistency for every user.

A practical safeguard is an append-only change ledger containing object identity, intended version, origin confirmation, purge submission, acknowledgement, and later spot checks. For high-priority corrections, use short TTLs, explicit no-store, or a controlled versioned URL rather than assuming a globally distributed purge will finish synchronously. Document what happens if the invalidation service itself becomes unavailable.

Web Cache Poisoning and Request Ambiguity

Web cache poisoning occurs when an attacker manipulates a response that a shared cache later serves to other users. A typical root cause is a mismatch between the inputs that the origin uses to generate a response and the inputs included in the cache key. For example, if an origin trusts an unvalidated forwarding header to construct an absolute link but the CDN ignores that header in its key, one maliciously shaped request might influence a representation stored for ordinary users. Header normalization, route transformations, and differently interpreted duplicate fields can create similar inconsistencies.

Defenses require agreement among cache, proxy, and application about canonical URLs, trusted headers, request-target parsing, query strings, and content variations. Accept forwarded client-host and scheme metadata only from configured proxy hops; reject ambiguous or malformed inputs rather than trying to guess the user's intent. Include every representation-defining field in the cache key or ensure it cannot influence a publicly cached response. Avoid generic "ignore all query strings" policies on APIs where query parameters affect results.

Testing should use a non-production environment and verify that variations in headers, query order, casing, cookies, and encoded path delimiters cannot cause a response for one semantic request to be retrieved under another. WAF controls and CDN cache-poisoning protections are useful layers, not substitutes for correct cache-key contracts and origin input validation. Retain request and response evidence without exposing secrets in logs.

Web Cache Deception and Sensitive Routes

Web cache deception exploits a disagreement about whether a URL refers to public static material or private dynamic material. A hypothetical application might render a signed-in account page at a path that appears to end in .css; an edge configured to cache everything with a .css suffix could store that private page as though it were a stylesheet. The dangerous condition is the combination of permissive edge caching, origin route interpretation, and user-specific content. Actual attack mechanics depend on routing and cache rules, but the design defect is general.

Do not grant cacheability solely from a filename extension or path regex when the origin can route that path to dynamic sensitive content. Use origin-declared content type and cache directives, plus explicit allowlists of public routes; evaluate how path normalization differs between proxy and application. Security review should cover redirects, encodings, suffixes, and rewrites. Test the negative case: send authenticated requests to suspicious or unusually encoded public-looking paths and confirm that private response content is neither stored nor replayed to an unauthenticated user.

Cloudflare, for example, documents cache-deception defenses, including mismatch checks between expected cacheable content and actual origin response characteristics. These are product-specific mechanisms, not guarantees that every possible mismatch is impossible. Application ownership of confidential output and a restrictive default for authenticated routes remain the primary controls.

Signed URLs, Access-Controlled Media, and Token Lifetimes

An organization may distribute paid course videos, unpublished manuscripts, or licensed assets through a CDN using signed URLs, signed cookies, or an edge authorization service. A signed token proves that a request carries an authorized capability under the configured verification rules; it does not automatically ensure that cached bytes can be reused across all callers. Determine whether authorization is verified on every request before cache retrieval, whether the token's identity belongs in the cache key, how expiration and revocation work, and what content remains public after a token expires.

Avoid using a shared cached response to bypass an access decision that the application assumes will run at the origin. A CDN configured to verify a signature at the edge may legitimately serve cached bytes without contacting the origin; a CDN that does not perform authorization must not be treated as such a gate. For high-value content, combine short-lived capabilities with secure origin access, logging, watermarking or DRM where appropriate, and explicit revocation expectations. No HTTP cache can claw back a legitimately downloaded copy from a user's device.

An important cost trade-off is that putting unique one-time tokens in the cache key can destroy reuse, while stripping them without independent authorization can disclose content. The architecture should separate authorization metadata from content identity only after proving that the edge enforces access policy independently of the origin. Audit with a valid token, an expired token, another user's token, and a request lacking a token.

Content Integrity, CSP, and Browser Security Boundaries

A CDN can preserve origin availability and reduce transfer time, but its caching layer becomes part of the software supply path. Protect origin access with TLS and appropriate authentication, maintain deployment provenance for static assets, and verify that the CDN does not unintentionally cache mixed-content or credential-bearing responses. Subresource Integrity (SRI) can help browsers verify specific external scripts or stylesheets when correctly configured. Content Security Policy (CSP) controls permitted resource and execution sources. Neither SRI nor CSP replaces HTTP cache privacy and key correctness.

The cached response's content type and security headers matter. A JSON response delivered with an unexpected type or an HTML page rendered as downloadable content can behave differently across clients, and incorrect content sniffing can amplify risk. Set correct Content-Type, consider X-Content-Type-Options: nosniff where appropriate, and preserve intended CORS and content-policy headers. A cache must not reuse a response with access-control headers whose meaning differs by caller when the key or Vary semantics do not preserve that distinction.

Separate the protection of bytes in transit from protection of bytes at rest. HTTPS protects communication to a properly authenticated endpoint, but a shared cache may store decrypted content internally. Review the provider's data-retention, geographic processing, access controls, tenant isolation, and incident response. Do not assume that serving through HTTPS makes a cached personalized response safe for global reuse.

Geography, Data Residency, and Compliance

Distributed edge delivery can replicate cached representations across regions or store them in locations different from the origin's country. That can be beneficial for public reference material but may raise contractual or regulatory issues for private student, patient, customer, and employee information. CDN "region controls" differ in scope: some restrict caching locations, others restrict where TLS terminates, request logs are processed, cryptographic keys are held, or data can be routed. A geographic label in a dashboard is not sufficient evidence of compliance.

Create a data-flow inventory for each response class: what fields it contains, which edges may see the plaintext, which providers act as processors, what metadata is logged, how long it remains stored, and what deletion or investigation mechanisms are available. The performance team should not decide residency solely based on observed latency. Work with counsel or compliance officers on applicable requirements; software design must implement decisions rather than infer legal permissions.

For a public academic encyclopedia, global caching of published articles and static assets is usually easier to justify than global caching of protected records. Keep the public and private paths architecturally distinct to avoid using one permissive caching policy for both. Where necessary, use a non-caching regional path for restricted transactions and a distributed edge path for explicitly public material.

Performance Metrics and Real User Experience

The most common cache KPI is hit ratio: responses satisfied by cache relative to eligible requests. Other important measures include byte hit ratio, origin offload, revalidation rate, cache fill latency, edge-to-origin transfer bytes, and user-visible response-time percentiles. Each answers a different question. A site can have a very high request hit ratio while frequently fetching a few multi-gigabyte assets, producing a low byte hit ratio. Conversely, caching very large static files may save substantial bandwidth but have little effect on the small dynamic requests that dominate user interaction latency.

Measure time to first byte (TTFB), page-navigation performance, and application interaction metrics together with origin timings. A browser cache hit may avoid any network request; a CDN cache hit still requires network travel and typically TLS connection use; a revalidated response may need an origin round trip but transfer almost no body bytes. Compare cold versus warm clients, high-latency regions, mobile networks, and different content types. Do not infer user experience exclusively from synthetic tests launched inside the CDN's own region.

Performance tuning should be reversible. Change one dimension, such as the public asset TTL, query-key policy, or image-coding variant, then compare a control and treatment over a representative traffic window. Report changes in origin CPU, egress, edge hit rate, p95/p99 latency, error rate, and publication-correction latency. A faster site that occasionally serves another user's information is a failed design, regardless of benchmark improvement.

CDN Economics and Capacity Planning

A simplified monthly transfer estimate is requests × average response bytes. If a public article gets 1,000,000 requests and averages 150 KiB transferred without caching, the nominal downstream payload is about 143 GiB, excluding protocol overhead and compression variations. An 85% byte hit ratio may reduce origin transfer for that class substantially; it does not eliminate edge-to-client delivery, and provider billing may count requests, data transfer, advanced security rules, purges, origin-shield traffic, logging, or regional premiums separately. Always evaluate the actual billing dimensions.

Caches have operational costs: storage, cold misses, invalidation, security assurance, key fragmentation, instrumentation, and incident response. A short TTL may increase origin work; a long TTL may reduce origin work but make correction slow. The optimum policy depends on business value, content change rate, allowed staleness, and regional demand patterns. A static logo used on every page deserves a different policy from a rarely accessed administrative export.

Capacity planning should include the miss storm after a regional outage or mass purge. Estimate how much request volume an origin would see if edge cache hit rate suddenly dropped from 95% to 40%, rather than budgeting only for the ordinary five percent of misses. If a public page sees 20,000 requests per second, the origin might receive 1,000 misses/s at 95% offload but 12,000 misses/s at 40%, before considering collapsed forwarding or shields. Test throttling and graceful origin protection at those stress points.

Cache-Status, Age, Logs, and Traces

The standard Age header reports the estimated age when an intermediary uses a stored response. RFC 9211 defines the Cache-Status structured response field so compliant caches can report information such as cache identity, hit state, TTL, forwarding reasons, and whether a request was collapsed. An illustrative value is Cache-Status: ExampleCache; hit; ttl=120. Some CDNs expose nonstandard fields such as X-Cache or vendor-specific cache-status names. Do not treat the existence or exact spelling of one provider header as a universal guarantee.

HTTP/1.1 200 OK
Cache-Control: public, max-age=300
Age: 180
Cache-Status: ExampleCache; hit; ttl=120
ETag: "catalog-v12"

These fields are diagnostic evidence, not a complete event log or proof of application consistency. An upstream cache can set its own metadata, a downstream cache can modify it under protocol rules, and proxies may remove or replace informational fields. Record a trace identifier across ingress and origin so operators can distinguish a cache hit from a request that actually reached application code. Be careful not to log session tokens or sensitive query strings merely to improve cache debugging.

Build dashboards for hits, misses, bypasses, revalidations, storage errors, negative caching, hit and byte-hit ratios, origin RPS, shield RPS, purge propagation, and stale deliveries. Segment by route class, geography, content type, and edge location. An overall average can hide a severe leak or high-miss hotspot affecting just one sensitive endpoint.

Operational Runbook: Stale Page or Unexpected Cache Miss

When a user reports an old page, first obtain the exact public URL, query parameters, affected user context, approximate time, expected version, and actual observed content. Reproduce with both an ordinary request and a controlled revalidation request. Inspect Date, Age, Cache-Control, ETag, Last-Modified, Vary, Cache-Status, redirects, content type, and vendor-specific indicators. Determine whether the old bytes came from the browser, service worker, CDN, regional shield, proxy, or origin itself. A response that is old at the origin will not be corrected by endlessly purging edge caches.

For excessive misses, compare two otherwise identical requests and note whether the key differs due to cookies, query fields, language, compression, or cache rules. Check whether the response is disallowed for storage, has an extremely short TTL, carries Set-Cookie, is larger than the provider's object limit, or is transformed in a way that prevents reuse. These are platform-dependent possibilities, not universal prohibitions. Measure origin traffic and byte movement before changing the key so the team can detect a security or correctness regression.

A controlled incident change should identify the owner, test against a staging route, bound the purge scope, and confirm both corrected bytes and correct access policy. Save a small evidence bundle: URL, request variants, status and headers, response checksum for public bytes, timestamps, service logs, and edge configuration revision. Close the incident only when the reported user path behaves correctly and monitoring shows no unintended increase in origin load.

Windows PowerShell and curl.exe Diagnostic Examples

Windows 11 commonly supplies curl.exe. In PowerShell, use the explicit executable name when you want curl's command-line flags rather than the shell's own web-request command. The examples below use documentation-only URLs; replace them with a domain you administer. They observe responses and do not mutate cache settings. For a standard read, inspect only headers; note that a HEAD request may follow a different edge code path from the GET request you're investigating, so run both when results differ.

# Inspect a public resource's response headers, including redirects.
curl.exe -sS -I -L 'https://example.edu/assets/site.css'

# Compare ordinary requests to a request asking for revalidation.
curl.exe -sS -D - -o NUL 'https://example.edu/articles/guide'
curl.exe -sS -D - -o NUL -H 'Cache-Control: no-cache' 'https://example.edu/articles/guide'

# Ask a known ETag endpoint to validate a representation.
curl.exe -sS -D - -o NUL -H 'If-None-Match: "rev-84"' 'https://example.edu/articles/guide'

A conditional request with a fabricated ETag does not guarantee a 304. Servers can ignore conditions in certain circumstances or return 200 when the selected representation differs; authentication and redirect behavior can also change the result. -o NUL is the Windows convention for discarding a response body; it should not be copied uncritically to Unix shells where /dev/null is customary. Record the actual status and headers instead of asserting that a cache is broken because one demonstration command did not return a hit.

PowerShell's Invoke-WebRequest can also expose headers in its response object, but syntax and default behaviors differ between Windows PowerShell 5.1 and PowerShell 7. For repeatable testing, document the shell version, client tool, redirects, request headers, and whether the browser has a service worker. A CDN cache decision may differ between the browser and curl because their request headers and cookies are not identical.

CDN and Reverse Proxy Implementation Families

Major CDN platforms and reverse-proxy servers share HTTP concepts but do not expose identical controls. Cloudflare documents custom cache keys, purge mechanisms, cache deception defenses, and rules that can alter default storage decisions. Amazon CloudFront separates cache-policy dimensions from additional headers and cookies forwarded to origins; its behavior depends on distribution, cache policy, origin-request policy, and edge configuration. Fastly and other programmable edges have distinct metadata, shielding, and surrogate invalidation controls. NGINX and Varnish can implement reverse-proxy caches controlled by local configuration and custom logic. Treat the names as implementation families, not as evidence that every feature is included by default.

An enterprise selection test should ask which layer is authoritative for public versus private classification; how custom keys are built; whether Vary, compression, error statuses, and Authorization are handled as expected; whether stale directives are honored; how purge propagates; whether logs can be exported securely; and what origin failover does during a miss. A vendor feature such as "cache everything" is unsuitable until its interactions with login routes, query parameters, and security headers are known.

Never copy a provider-specific configuration snippet into production without checking its documentation for the deployed date and product tier. Caching features evolve, and a directive used in one service can have different defaults in another. Build small integration tests using at least one public static object, one changing public HTML page, one public API, and one authenticated private endpoint before migrating a site's full workload.

Architecture Selection and Review Framework

A practical review starts with the meaning of the representation. Is it globally public? Does it change with identity, tenant, locale, feature flag, query, or permission? What is the cost of returning yesterday's value, and how will the organization discover that it did? Only then select private versus shared caching, an explicit TTL, validators, a cache key, and a purge or versioning strategy. The final design should be demonstrable with representative HTTP requests rather than expressed solely in a diagram.

  1. Classify response data and identify authoritative ownership. Separate public bytes from user-specific bytes.
  2. Define staleness tolerances for ordinary changes, urgent corrections, and security revocations.
  3. Specify cache locations (browser, intermediary, regional shield, application) and whether they may store each class.
  4. Define key and variant rules for URL, query, encoding, language, cookies, headers, and identity inputs.
  5. Choose freshness and validation rules, including explicit policies for errors and redirects.
  6. Document invalidation and release workflow: content addressing, origin readiness, purge authority, and rollback.
  7. Test hostile and unusual inputs, particularly login transitions, query normalization, path suffixes, and auth headers.
  8. Instrument hit/miss evidence and origin pressure before and after enabling caching.
  9. Exercise failure cases: origin timeout, stale permission, missed purge, shield outage, and cache bypass.
  10. Require accountable approval for public caching of anything that may contain personal or licensed information.

The resulting design can be expressed as a compact "cache contract" attached to each route or route family. A contract that cannot be tested is an operational assumption; treat it as unresolved rather than quietly promoting it to a production guarantee.

Worked Scenario 1 — A New MGU Public Article Is Published

The editorial team uploads a new encyclopedia page while a visitor previously requested the URL and received 404 Not Found. The edge cached that negative response for a configured period. The article now exists at the origin, yet some readers still see the old 404. The right diagnostic order is: confirm the exact canonical and physical path; confirm a fresh origin 200 with correct content type; inspect edge Age, error caching policy, and redirects; perform a narrow invalidation if allowed; then retest from the affected region. This shows why an origin upload and a public cache purge are different events. A live link is not evidence that its target is published correctly.

Worked Scenario 2 — An Immutable Stylesheet Is Updated Safely

The design team needs a CSS update. Replacing bytes at /assets/style.css with a long cached lifetime would leave many users on the old version. Instead, build a new hashed asset /assets/style.a92d4.css, publish it first, verify it at the origin, update the HTML document to reference it, and retain the prior asset while old HTML may still be used. The asset can carry long-lived immutable freshness; the HTML pointer gets short freshness or validation. Rollback can restore an earlier HTML pointer without requiring the old asset to have been deleted. This is a release engineering solution, not a cache-clearing trick.

Worked Scenario 3 — A Private Student Dashboard Reaches a Shared Cache

A CDN route uses an overly broad rule that treats every GET response as public. A student loads /api/me, then another user requests the same path. If the private response has been stored under a key that does not distinguish identity, the second user may receive the first user's data. The remediation is to block unsafe shared storage, notify security stakeholders, identify exposed requests, and correct origin directives and edge policy. Adding an Authorization-shaped query value as a quick cache-key patch does not replace authorization architecture. The test plan must verify private behavior under distinct identities and unauthenticated access.

Worked Scenario 4 — A Public Catalog Has Two Language Variants

An academic catalog returns English to one visitor and Spanish to another according to language negotiation, but the CDN key ignores that request input. If the origin varies the actual bytes, a cache might return the wrong translation. Define an explicit language selection mechanism, such as a stable path segment or controlled query field, or use Vary: Accept-Language with a platform-verified variant policy. Avoid varying on arbitrary long language strings if a small supported locale list meets requirements. Recheck ETags and content coding for each representation. Correctness requires the cache identity to follow the representation identity.

Worked Scenario 5 — An Origin Outage Tests Stale-On-Error

A public reference article is usually updated weekly. During a 15-minute origin outage, the CDN has a recently expired validated copy and a documented stale-if-error allowance sufficient for the outage. Serving the previously public article may be preferable to returning an error, provided the permission is valid under the active cache rules. For a time-sensitive safety alert posted after the cached version, the same fallback is inappropriate. The architect classifies these routes separately, observes stale deliveries, and restores ordinary validation when the origin returns. The design promise is bounded stale reuse, not indefinite offline correctness.

Worked Scenario 6 — A CDN Purge Causes an Origin Stampede

An administrator purges 20,000 asset URLs in one action immediately before a large enrollment announcement. Edge nodes simultaneously miss, and each PoP tries to fetch popular assets from a small origin. Origin latency spikes and some users see errors despite healthy CDN networking. The team responds by restoring controlled fills, limiting origin concurrency, using a regional shield or request collapse where available, and avoiding unnecessarily broad invalidations. Future deployments rely on hashed assets with staged publication, leaving targeted purge for genuinely mutable public documents. The metric is origin load during the miss storm, not only hit rate after it subsides.

Worked Scenario 7 — An API Key Ignores a Significant Query Field

A public course search endpoint returns different lists for ?campus=east and ?campus=west. A custom CDN key excludes the campus parameter while the origin uses it in database selection. Users receive valid JSON for the wrong campus. Confirm that the key contains every representation-defining query input and that ignored tracking fields genuinely have no effect on server logic. Add tests for different query order, encoded values, duplicate parameters, and normalization. The incident illustrates an under-inclusive cache key; shorter TTLs reduce exposure duration but do not fix the underlying correctness error.

Worked Scenario 8 — A Large Video Download Uses Byte Ranges

A learner pauses an instructional video and resumes near its end. The browser requests a byte range and receives 206 Partial Content; the edge may serve or fetch a corresponding representation range. The operator checks strong validators, Content-Range, selected content encoding, range support, origin egress, and whether the CDN fetches a whole object for every partial request. If the video is licensed, edge authorization must still apply when the bytes are served from cache. A range response assembled from two file versions would be invalid even if every individual chunk was delivered successfully.

Worked Scenario 9 — A Browser Appears to Ignore a CDN Purge

The publisher purges a public HTML page from the CDN, confirms an edge miss, and sees the correct new origin bytes. One user's browser still displays the old page. The likely causes now include the browser's private HTTP cache, a service worker cache, an open page retaining old application state, or a different canonical URL. A second global CDN purge is unlikely to change a response that no longer uses the CDN. The team reproduces with a new browser profile, examines the network panel and service worker lifecycle, checks redirect variants, and uses targeted client instructions only after identifying the actual stale layer.

Worked Scenario 10 — Two CDNs Disagree About Caching a Cookie Response

A public article includes a nonessential analytics cookie, and its response carries Set-Cookie. One CDN refuses to cache by default; another can cache under a configured rule. The team does not conclude that Set-Cookie is universally prohibited by HTTP caching. Instead it classifies whether the article bytes are truly public, decides if that cookie should be emitted on the article at all, reads each provider's current behavior, and tests two users with different cookies. Where possible, separate public cacheable content from personalized tracking and set privacy-safe defaults. The result is a defensible cross-provider policy rather than folklore.

Worked Scenario 11 — A Cache Hit Metric Conceals an Expensive Miss Class

Analytics reports 97% request hits. The remaining three percent are large generated reports and long-running search requests that cannot safely be shared. They dominate origin CPU, p99 latency, and cost. Simply raising TTL for those reports could leak private data. The organization instead improves query efficiency, admission control, result generation, and user-private caching where permitted. Dashboards separate public hit ratio, byte hit ratio, origin work by route, and private traffic. The lesson is to optimize business outcomes and safety rather than a headline cache-hit percentage.

Worked Scenario 12 — An Urgent Access-Policy Change Meets Cached Content

A document previously published publicly is reclassified as restricted. A long-lived public cached copy may remain available after the origin changes permissions. The response cannot be treated as revoked merely because the database row now says private. The organization removes exposure at all controlled shared layers, uses any available invalidation or access-gateway controls, evaluates contractual incident obligations, and acknowledges that already downloaded copies cannot be recalled. Future architecture separates permanently public assets from resources whose access policy may change and avoids year-long immutable caching for revocable content. Access policy must be designed as part of the cache lifecycle.

Applied Study and Configuration Exercises

  1. Build a representation matrix: Identify five sample endpoints (public article, hashed asset, public catalog, private profile, restricted download). For each, define cache locations, key dimensions, permitted lifetime, and purge triggers. Explain which routes must not use shared caching.
  2. Trace a validation cycle: Using a test server under your control, save ETag, issue a conditional request, and document whether the result is a matching 304 or a replacement 200. Measure bytes transferred and correct cache age.
  3. Exercise variant mismatches: Test a public language-negotiated resource for two locales and two Accept-Encoding values. Verify that the cache never serves the wrong representation.
  4. Model an editorial publish race: Produce a controlled 404, then publish an object and measure the delay until readers receive the new 200. Compare short negative caching with explicit targeted purge.
  5. Run a privacy negative test: Use two test users and one anonymous client against a staging profile endpoint. Verify that one user's response is never shared with another or a signed-out client, regardless of apparent hit-rate improvements.
  6. Estimate origin overload: For 10,000 requests/s and an ordinary 95% hit rate, compute expected origin misses; repeat at 50% hit rate and identify protection mechanisms.
  7. Plan an immutable-asset deployment: Stage a new hashed JavaScript bundle, update HTML, retain the old bundle, and design rollback criteria when older clients hold a previous entry document.
  8. Test outage policy: For three content classes, decide whether stale-if-error is permitted, how long it may last, and what monitoring or user-facing age display is necessary.
  9. Investigate a suspicious custom key: Determine whether forwarding a header to an origin while excluding it from the key can change the response and create a poisoning risk.
  10. Write a purge runbook: Describe the preconditions, exact key scope, approval process, verification steps, and fallback if the purge service is unavailable.

Specialist Glossary

The definitions below summarize protocol and operational terminology. Refer to standards for exact normative conditions and vendor documents for configured platform behavior.

Age header
HTTP metadata indicating the estimated time since a response was generated or validated, as interpreted by caches.
Application cache
Application-managed storage of computed data or representations, distinct from normative HTTP cache behavior.
Authorization boundary
Point at which a request is checked against the policy governing protected content.
Back-forward cache
Browser optimization that may preserve page state and has behavior distinct from ordinary HTTP caching.
Browser cache
Private cache in a user agent that stores reusable HTTP responses.
Byte hit ratio
Share of delivered bytes served from cached content rather than retrieved from the origin.
Cache busting
Technique for creating a distinct cache identity when content changes, often through content-versioned URLs.
Cache contract
Explicit route policy for storage, key selection, freshness, validation, and invalidation.
Cache deception
Attack arising when private dynamic content is mistaken for cacheable public content.
Cache fill
Retrieval and possible storage of a response after a cache miss.
Cache hit
Request satisfied with a stored response under permitted cache reuse rules.
Cache key
Identifier selecting candidate stored representations, including relevant method, URI, and configured variants.
Cache miss
Request for which a suitable reusable stored response is unavailable.
Cache poisoning
Attack that causes a maliciously influenced response to be stored and reused by others.
Cache stampede
Concurrent requests that overwhelm an origin when an object expires, is purged, or has not been stored.
Cache Storage API
Browser API used by service workers and applications for application-controlled request/response storage.
Cache-Control
HTTP field carrying caching directives for requests and responses.
Cache-Status
Standardized HTTP field for reporting intermediary cache decisions under RFC 9211.
Canonicalization
Conversion of varied request forms into an agreed identity according to specified rules.
CDN
Content delivery network; infrastructure that delivers eligible content from geographically distributed locations.
Client
Application or user agent initiating an HTTP request.
Collapsed forwarding
Coordination that serves multiple same-key misses through fewer origin fetches.
Conditional request
Request with a precondition such as If-None-Match used to validate state or control an operation.
Content-addressed asset
Asset identified by a filename or key that changes when its content changes.
Content-Encoding
HTTP field describing representation coding such as gzip or Brotli.
Content-Range
HTTP field describing which bytes a partial response represents.
Current age
RFC-calculated estimate of a stored response’s age at a given point in time.
Date header
HTTP field stating a message’s originating date/time used in cache age calculations.
Edge authorization
Access decision executed at a CDN or gateway before serving a protected representation.
Edge cache
Cache operating at a CDN or distributed network edge location.
Entity tag
Validator supplied by an origin in the ETag field.
ETag
HTTP header containing an entity tag, often used for conditional validation.
Expiration
Transition from fresh to stale when a permitted freshness lifetime ends.
Freshness lifetime
Duration a stored response may normally be reused without validation.
Geographic PoP
Point of presence in a distributed delivery network.
HEAD
HTTP request method that retrieves response metadata without transmitting the representation body.
Heuristic freshness
Freshness interval estimated by a cache when permitted and no explicit lifetime is specified.
Hit ratio
Share of eligible requests satisfied using a cached response under a defined measurement scheme.
HTTP cache
Storage mechanism that reuses HTTP responses according to applicable HTTP cache rules.
HTTP validator
Metadata used to determine whether a stored representation is still current.
If-Modified-Since
Conditional request field comparing a resource modification timestamp.
If-None-Match
Conditional request field used to compare entity tags for validation.
If-Range
Conditional request field controlling whether a range request may use the selected representation.
Immutable directive
Cache-Control extension signaling a fresh representation is not expected to change.
Invalidation
Action that prevents ordinary reuse of an existing stored representation.
Last-Modified
HTTP field indicating the resource’s modification time at the origin.
Max-age
Response or request directive relating to freshness duration.
Multi-tier cache
Arrangement with more than one cache hop, such as edge and regional shield.
Negative caching
Storage of qualifying responses indicating absence or failure, such as selected 404 responses.
No-cache directive
Instruction requiring successful validation before stored response reuse.
No-store directive
Instruction prohibiting storage by compliant HTTP caches.
Origin server
Authoritative source for a resource in HTTP architecture.
Origin shield
Intermediate cache tier consolidating requests from other edge caches.
Personalized representation
Response whose content depends on a particular user, identity, or entitlement.
Private directive
Cache-Control response restriction preventing shared storage under normal semantics.
Public directive
Directive explicitly permitting shared caching when relevant caching requirements are met.
Purge
Operational cache invalidation or removal using a provider or proxy control mechanism.
Query normalization
Rules for ordering, retaining, and canonicalizing query parameters in request identities.
Range request
Request for part of a selected representation, usually expressed using the Range field.
Revalidation
Contact with the next hop to confirm whether a stored representation remains valid.
Reverse proxy
Intermediary receiving requests on behalf of one or more origin services.
S-maxage
Shared-cache freshness directive with revalidation restrictions after staleness.
Service worker
Browser-executed worker capable of intercepting requests and managing independent caches.
Signed URL
Request URL carrying a verifiable capability subject to signature and expiration rules.
SRI
Subresource Integrity, a browser mechanism for verifying selected fetched assets against integrity metadata.
Stale
State of a stored response whose age exceeds its freshness lifetime.
Stale-if-error
Extension permitting bounded stale reuse during qualifying failures.
Stale-while-revalidate
Extension permitting bounded stale reuse while validation proceeds.
Strong validator
Validator appropriate for exact representation matching under HTTP semantics.
Surrogate key
Provider-defined grouping or tag used to invalidate multiple cached objects.
TLS
Transport Layer Security, used to protect authenticated network communication.
TTL
Time to live, often used informally for a freshness or platform cache retention interval.
Vary
HTTP field identifying request-header dimensions used when selecting reusable stored representations.
Weak validator
Entity tag with weaker equivalence semantics, marked by the W/ prefix.
