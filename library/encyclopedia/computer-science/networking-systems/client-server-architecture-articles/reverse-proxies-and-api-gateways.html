Purpose and Scope

Reverse proxies and API gateways are intermediaries on the request path between a client and one or more services. They provide a deliberately managed public or internal entry point, accept traffic on behalf of upstream applications, and decide what to forward, transform, reject, buffer, cache, log, or route. A reverse proxy is not an alternative to an application server: it mediates communication with servers that still own the resources and business operations. An API gateway commonly uses reverse-proxy functionality while providing API-oriented capabilities such as route and contract governance, client identification, quotas, versioned interfaces, service aggregation, and policy enforcement.

This Level 5 article belongs to the Client–Server Architecture Unit of the MGU Computer Science Encyclopedia. Its parent Client–Server Architecture explains the broader client/server exchange. Previous specialists cover DNS and Service Endpoints, HTTP Versions and Transport, TLS and Secure Client Connections, and Two-Tier and Three-Tier Systems. The present treatment focuses specifically on the intermediary's responsibilities, trust boundaries, routing design, and observable failure behavior; server fleet balancing and general HTTP caching are covered in separate Unit articles.

The architectural question is not simply whether a proxy is installed. It is which intermediary is authoritative for each policy, which identities it can reliably establish, and what guarantees remain the responsibility of the upstream service. Correct answers require distinguishing the client-facing connection from the proxy-to-upstream connection, defining requests that may be retried, and ensuring that no security assumption depends on untrusted headers.

Terminology and the HTTP Intermediary Model

In HTTP terminology, a forward proxy is selected or configured by the client to make requests toward outside origins; a gateway or reverse proxy appears to the client to be the origin-facing endpoint but passes all or part of the request to other servers. A load balancer chooses among eligible destinations, often with health and policy inputs. A web application firewall (WAF) screens traffic using configured rules. An API gateway may combine reverse proxying, balancing, protocol translation, authentication, and API management. These categories overlap in deployed products, but they describe different responsibilities.

A single product may fulfill several roles, or a chain may contain a CDN, WAF, external reverse proxy, internal gateway, and application sidecar. The client can still perceive one HTTPS site. The number of proxies or services does not, by itself, establish the number of business-logic tiers. Distinguish the physical route from policy ownership: the first lists hops, the second states which component is permitted and obligated to make a decision.

HTTP standards call an intermediary a gateway when it acts as an origin server for incoming connections and translates or forwards requests to other servers. Product usage of the term “API gateway” is broader, often adding commercial and operational features. Do not infer standardized authentication semantics merely from the gateway label.

Anatomy of the Proxied Request Path

Consider a campus application at https://portal.example.org/api/enrollments. Public DNS directs the client's connection toward an edge entry point. The edge terminates the first TLS session, decides whether the requested host and path belong to an approved route, applies admission controls, and opens or reuses a separate connection to an application service. The application authenticates and authorizes the enrollment request, consults its database, and returns an HTTP response. The proxy then relays that response and may add security or observability headers under an explicit policy.

Each connection has an independent remote peer, IP address, TLS negotiation, timeout policy, and possible failure. The upstream server typically observes the proxy's network address, not automatically the original client's address. Forwarded metadata must be explicitly introduced and validated. An apparent “one request” in the browser can involve several connections, authorization decisions, cache checks, retries, and redirects; tracing should preserve their relationship without pretending they are one unbroken end-to-end connection.

Forward Proxy, Reverse Proxy, Gateway, and Service Mesh

A corporate forward proxy sits on the client side of the trust relationship and is commonly configured to govern outbound requests, enforce egress policy, or log destinations. A reverse proxy is deployed by or for the service operator and governs inbound requests to the operator's applications. A transparent interception device is different again because it may be placed on the path without explicit client proxy configuration. The same general HTTP forwarding rules can be relevant, but who controls the intermediary changes the security model.

At the edge, an API gateway usually publishes approved APIs and manages callers. At the service-to-service layer, a service-mesh proxy may provide identity, mutual TLS, traffic splitting, retries, and telemetry for workloads that are already inside the platform. Mesh and gateway are complementary patterns; neither means that applications no longer need to validate authorization, input, transaction conditions, or business invariants.

When an architect proposes another proxy, ask which distinct policy it owns. Adding two products that both rewrite paths, authenticate callers, or retry requests without a documented precedence can produce contradictory behavior. Minimize duplicated transformations and make every trust boundary observable.

Host, Path, Method, and Header Routing

Most HTTP gateways select a route using one or more of the request's authority/host, path, and method; sophisticated systems may also match headers, query parameters, protocol metadata, or authenticated identity. Define a deterministic precedence and reject ambiguous or unmatched requests intentionally. For example, portal.example.org/api/catalog/* can map to one backend and portal.example.org/api/enrollments/* to another. A separate host such as admin.example.org can require a stronger access path and authentication policy.

Route matching is not identical to application authorization. A request can match the enrollment route and still be forbidden from modifying the selected enrollment. Route matches must also be resilient to alternate encodings, dot segments, repeated slashes, case changes where relevant, and percent-encoded delimiters. Document whether matching occurs before or after normalization and whether the backend performs additional transformations. If gateway and backend disagree, a request rejected by one path can be accepted by another unexpectedly.

Method constraints are useful for minimizing exposure, but should respect protocol semantics: a GET should not have unintended state-changing side effects, and an apparently idempotent request should not be assumed harmless without examining the application's contract. Avoid reliance on undocumented route evaluation order when deploying configuration changes.

Upstream Discovery, Endpoints, and Health

The gateway must know where healthy upstream instances are located. Discovery may use static host and port configuration, DNS, a platform service registry, orchestrator endpoints, or control-plane configuration. This introduces a dynamic operational dependency: if an instance drains, changes its address, fails a readiness check, or loses a network route, the intermediary's destination set must converge appropriately. A stale destination can fail even while the public DNS and front-end TLS remain healthy.

Readiness checks should reflect whether the service can accept new work; liveness checks ask whether recovery or restart is needed. The two questions are not interchangeable. A shallow TCP check can succeed while the application cannot access a required datastore; conversely, an overly strict check that fails whenever a noncritical dependency is slow can remove every instance simultaneously. Combine signals carefully and retain a manual or controlled recovery route.

DNS lookup caching and re-resolution behavior vary among products. Verify whether the proxy resolves a hostname at startup, periodically, on connection, or under a configured service-discovery policy. The DNS TTL by itself does not guarantee the proxy will honor endpoint changes immediately. For finer health selection, see the Unit article on Server Load Balancing.

URI Rewriting, Host Preservation, and Canonical URLs

Reverse proxies can map a public URI to a different upstream path or hostname. For example, an external /api/v1/catalog/books route might become /books on a catalog service. Rewriting reduces internal naming exposure and permits legacy migrations, but introduces a contract: redirects, cookies, link generation, WebSocket endpoints, and relative paths must still make sense to the client. A backend unaware of the external path prefix may emit a redirect pointing to an inaccessible internal path.

Preserve the requested public scheme, authority, and intended path semantics across the trusted proxy boundary. If the frontend accepts HTTPS but talks HTTP to an internal application, the application must not infer its public scheme from the private transport alone. Otherwise it may generate insecure redirects, wrong absolute URLs, or incorrectly scoped cookies. Restrict the authority value that the application may use for externally generated links; accepting any attacker-provided Host risks host-header injection and poisoned password-reset links.

For MGU's own website publication conventions, distinguish the physical .html file from its extensionless public canonical URL. A reverse proxy or hosting rewrite must be consistent with canonical declarations and redirects; it cannot by itself make an absent target file exist. Avoid redirect loops when both edge and application try to force HTTPS or trailing-slash policy.

HTTP Message Semantics at an Intermediary

An intermediary must preserve the HTTP method, selected target resource semantics, conditional request fields, representation metadata, and status meaning unless it is deliberately implementing a documented translation. HTTP/1.1 connection-specific fields are not general end-to-end metadata. The Connection field and the field names it nominates identify hop-by-hop information that must not be blindly passed onward. Intermediaries may terminate one protocol version and originate another, for example HTTP/3 on the client side and HTTP/2 or HTTP/1.1 upstream.

Translation requires attention to request framing, streaming, trailers, content encoding, and the mapping between authority and URI components. Invalid or ambiguous message framing is a security issue, not merely an interoperability inconvenience. Gateway and backend parsers must agree on message boundaries so a malformed request cannot be interpreted as two different streams by the two systems.

Proxy-generated responses should carry meaningful status codes. A 502 Bad Gateway often means a gateway received an invalid response or encountered an upstream protocol problem, whereas 504 Gateway Timeout indicates that the gateway did not receive a timely response from an upstream server; 503 Service Unavailable may reflect overload or deliberate maintenance. Exact error mapping is implementation-dependent, and an upstream may also return these codes directly. Log the source of the status rather than assuming the browser-visible code uniquely identifies the failing component.

Forwarded, X-Forwarded-For, and Trusted Proxy Hops

After a reverse proxy accepts a client connection, the backend usually sees the proxy's source address. Operators often attach Forwarded (RFC 7239), X-Forwarded-For, X-Forwarded-Proto, and host-related fields to record the original request context. The standardized Forwarded header and commonly deployed X-Forwarded-* conventions are not interchangeable in every implementation; their parsing, IPv6 notation, multiple-hop behavior, and acceptance policies must be explicit.

Never assume an arbitrary incoming forwarded header is truthful. A malicious client can send its own X-Forwarded-For value unless the first trusted edge strips or overwrites it under a known policy. Configure which peers are trusted to supply forwarding metadata, how many hops may be interpreted, and which CIDR ranges or mutually authenticated workloads are authorized. At the last hop, determine the client identity using the full trusted chain rather than blindly taking the leftmost textual address.

Origin-IP information is useful for abuse telemetry, regional policy, and support investigations, but it is not a complete human identity or substitute for a session. Reverse proxies may hide or replace IP addresses for privacy; mobile networks, NAT, and shared networks also make IP-to-person attribution unreliable. Document how the scheme, host, external path, and original IP are computed and passed to authorization, redirects, and audit logs.

TLS Termination, Re-Encryption, and Workload Identity

The public gateway often terminates TLS using a certificate for the external hostname. At that point it can inspect and route HTTP messages, but the original TLS session ends. The upstream connection is a separate channel. If upstream confidentiality and peer authentication are required, create a new validated TLS connection—potentially mutual TLS (mTLS)—to the backend. Termination on the edge does not imply that internal communications are encrypted, nor does a private subnet alone replace encryption and identity.

Validate both sides of the trust boundary. The client should validate the gateway's certificate and expected hostname. The gateway should validate any upstream certificate or workload identity according to a configured trust policy, rather than merely enabling encryption without identity verification. Certificates and keys require expiry monitoring, rotation, emergency revocation and ownership. When a CDN or WAF precedes a gateway, identify which layer terminates which TLS segment and who may decrypt request bodies.

ALPN can negotiate HTTP/1.1, HTTP/2, or HTTP/3 as supported at each connection. The gateway may speak HTTP/3 to browsers but use HTTP/2 to upstream services. A protocol version accepted externally does not prove the upstream uses the same transport. See TLS and Secure Client Connections and HTTP Versions and Transport for the cryptographic and transport foundations.

Authentication at the Gateway

A gateway can reject unauthenticated callers before they consume backend resources. Common arrangements include validating a short-lived signed access token against configured keys and issuer/audience restrictions, integrating with an OpenID Connect identity provider, requiring mTLS client certificates, or consulting an external authorization service. Token validation must check more than the signature: expiration, issuer, audience, algorithm policy, key freshness, and relevant authorization context may matter. Never treat an opaque string that merely resembles a token as proof of identity.

The application must understand the outcome and the trust path. A gateway may pass a validated principal identifier using a carefully controlled internal header, a signed assertion, or service credentials. Unless the backend is inaccessible except through the trusted gateway, a caller may bypass the gateway and forge that metadata. Even when the gateway is the only ingress, explicit backend authorization remains essential for object-level permission and domain-specific operations.

API keys can identify a subscribing application and associate requests with usage policy; they are not automatically proof of a human user's identity and should not be the sole mechanism for authorizing sensitive data access. Rotate credentials, redact secrets from logs, and treat credential exposure through URLs and analytics as a deployment risk.

Gateway Policy Versus Resource Authorization

Authorization can occur at multiple scopes. The edge can require a valid token and an appropriate coarse scope for the route. The backend then decides whether that subject may read, update, or delete the particular record. For example, a token authorized for enrollments:read may be adequate to enter a read endpoint, but it should not grant visibility into every student's enrollments. The service must evaluate the relevant student, campus, tenancy, or delegated role against the requested object.

Some architectures centralize fine-grained decisions in a policy decision point, but the application still must provide trustworthy object attributes, enforce the decision, and prevent time-of-check/time-of-use inconsistencies. A gateway cannot reliably decide object access when it lacks domain state or when a request's object identifier is hidden inside an application-specific payload. Likewise, filtering a route by URL path will not protect alternate routes to the same record.

Record policy precedence: which control rejects a caller when credentials are valid but missing scopes; how the service verifies a gateway assertion; how internal jobs invoke the API without a browser; how token revocation propagates; and whether error responses disclose resource existence. The OWASP API Security Top 10 highlights broken object-level authorization precisely because generic gateway protections are insufficient.

CORS, Browser Cookies, and CSRF at the Edge

Cross-Origin Resource Sharing (CORS) is a browser mechanism that controls which origins can read qualifying cross-origin responses. A gateway can implement CORS preflight responses and add allowed-origin fields, but its configuration must agree with the application's credential and endpoint semantics. An overly broad origin reflection or use of wildcard policy with credentials can break the intended boundary. CORS is not an authorization system for nonbrowser clients, which can make network requests without enforcing browser CORS checks.

Cookie-based browser authentication requires attention to Secure, HttpOnly, SameSite, cookie domain/path, and session rotation. An edge that changes the public host or path may require deliberate cookie rewrites; rewriting indiscriminately can accidentally expand a cookie's scope. Protect state-changing actions against cross-site request forgery using appropriate origin validation and anti-CSRF controls rather than relying exclusively on CORS.

Separate browser-only restrictions from service-to-service permissions. For example, a CLI client can call an API without an Origin field. Requiring an Origin field as a general authentication criterion will reject legitimate machine clients while providing little protection against attackers who can forge headers outside browsers.

Rate Limiting, Quotas, and Identity Keys

Rate limiting limits the pace at which requests are admitted; quotas track consumption over a longer interval; concurrency limits bound simultaneous work. A policy may distinguish anonymous IP-based requests, authenticated consumer IDs, tenant accounts, endpoint classes, and costly operations. Choose a reliable identity key and resist header spoofing. For public requests, per-IP limits alone can penalize users behind shared NAT while attackers rotate source addresses; authenticated consumer controls may be more meaningful, but anonymous abuse still requires an edge defense.

Common mechanisms include token buckets, leaky buckets, fixed windows, sliding windows, and bounded in-flight request counts. Distributed gateways often require a shared or coordinated state store to apply limits across replicas. An approximate or best-effort implementation should not be advertised as a hard financial or safety guarantee. Return a meaningful response such as 429 Too Many Requests where applicable, and give retry guidance without telling all clients to resume simultaneously.

Rate policy should account for the cost of the operation: a small metadata read differs from a heavy search export. The backend needs its own CPU, memory, query, and transaction protections in case traffic bypasses the gateway or a seemingly inexpensive request triggers expensive work. Budgets, authentication, and economic quotas are separate from denial-of-service resilience.

WAF Filtering, Payload Validation, and Body Limits

A web application firewall or gateway inspection layer can block known malicious patterns, enforce request size limits, require approved content types, and reject malformed headers before they reach application code. These checks can reduce exposure, especially for public APIs, but cannot prove that a request is safe or authorized. Rule sets can produce false positives and false negatives; policy owners must review blocked samples, understand bypass routes, and maintain an emergency procedure for bad deployments.

Request body inspection requires buffering or streaming decisions. Buffering a large upload may consume memory or disk before the service sees the first byte; streaming reduces buffering pressure but can constrain full-payload validation. Apply maximum headers, body bytes, decompressed bytes, nesting depth, upload duration, and request rate according to the endpoint's real needs. Compression bombs and unexpectedly complex JSON structures can produce disproportionate upstream work.

Where the gateway validates a schema, the backend should still validate domain constraints. A syntactically valid JSON object can request an unauthorized transfer, an invalid enrollment, or an unsafe file path. Canonicalize content before applying path or authorization rules and audit the frontend–backend normalization agreement.

Request Smuggling, Header Ambiguity, and Normalization

Request smuggling occurs when different HTTP recipients disagree on where one request ends and another begins. A frontend proxy and backend parser might differ in their treatment of message length, conflicting transfer metadata, or malformed framing. A maliciously crafted byte sequence can then be interpreted differently on the two sides of the connection and interfere with another client's request. HTTP/1.1 message framing requirements were tightened to reduce this class of vulnerability, but heterogeneous deployments still require review.

Do not accept conflicting or malformed framing and hope the next hop will interpret it safely. Normalize or reject ambiguous messages at the first trust boundary; keep proxy software and backends patched; test HTTP/1.1-to-HTTP/2 transitions and downgrade paths; and ensure intermediaries properly remove hop-by-hop fields. In security testing, use an authorized staging environment and non-disruptive test cases, because request desynchronization may affect unrelated users.

Path traversal and authorization bypasses can also arise from disagreements over encoded separators, Unicode normalization, multiple decoding passes, and routing precedence. Edge denial rules based on a raw string may be bypassed if the backend normalizes it differently. Establish one canonical interpretation of public paths and validate all downstream mappings.

Response Headers and Information Disclosure

At the edge, operators often configure Strict-Transport-Security, content type and cache controls, request IDs, and security headers appropriate to the site. The correct set depends on the application: an HTML browser response may need different policy from a JSON API or downloadable file. A proxy that blindly overwrites all Content-Security-Policy or Cache-Control fields can weaken a carefully designed application response.

Strip unnecessary internal topology information from outward-facing responses, such as detailed stack traces, private upstream hostnames, and accidental debug headers. Be cautious with the opposite extreme: removing all metadata can impede legitimate client troubleshooting and caches. Error responses should be stable and privacy-conscious, and APIs may use RFC 9457 problem details to communicate machine-readable error semantics without exposing implementation internals.

Preserve end-to-end representation metadata correctly when compression, transcoding, or caching occurs. A component that changes body bytes must account for content encoding, content length, ETags, range requests, and any signatures over the representation. Prefer avoiding unnecessary body transformations.

Buffering, Streaming, and Backpressure

Proxy buffering can protect an upstream service from slow clients and improve throughput when the intermediary has sufficient capacity. Request buffering may allow a complete body to be checked or stored before forwarding; response buffering can free a backend connection earlier if the proxy can transmit the response later to the client. These gains are not universal. Long-lived streaming responses, server-sent events, large downloads, and interactive APIs may require buffering to be disabled or tuned so events can reach the client promptly.

Backpressure is the mechanism that keeps slow downstream consumers from causing unlimited memory growth. A proxy handling a large upload should enforce body and time limits and apply flow control rather than accumulating unbounded pending data. Similarly, a backend producing data faster than the client consumes it must be slowed, buffered within a bound, or terminated by policy.

Timeouts require separate definitions for connection establishment, upstream response headers, total request lifetime, idle stream periods, body reads, and downstream writes. A generous streaming idle timeout may be appropriate for event streams, while a normal CRUD request should have a finite end-to-end deadline. Label each configured timeout by the phase it controls.

WebSockets, Server-Sent Events, gRPC, and Protocol Upgrades

Not every client–server exchange is an independent short HTTP request. WebSockets use an initial handshake and then a bidirectional message channel; server-sent events (SSE) keep an HTTP response open and stream events; gRPC commonly uses HTTP/2 framing and streaming. A gateway must explicitly support the chosen transport and avoid policies that break long-lived connections, such as short idle timeouts, unsuitable buffering, or inappropriate connection header rewriting.

For WebSocket traffic, validate the opening handshake and any application origin or authentication rules, but remember that the open channel may carry many messages requiring continued authorization and resource limits. For SSE, flush events without unexpected buffering; support cancellation and reconnect semantics. For gRPC, account for HTTP/2 requirements, trailers, status semantics, message limits, and deadline propagation. A proxy that can serve ordinary JSON APIs is not necessarily configured correctly for streaming gRPC.

Connection draining becomes especially important during deployment: abruptly terminating long-lived streams can disconnect thousands of consumers at once. Establish reconnection and resubscription contracts, including message replay and deduplication where needed. Protocol translation from an external browser API to an internal gRPC service must define error and metadata mapping explicitly.

Upstream Load Balancing and Draining

Many reverse proxies distribute incoming connections or requests among application instances using a balancing algorithm. Algorithms include round-robin and least-connections variations, with optional weights, locality, consistent hashing, or request-affinity policies. Algorithm selection should reflect the workload: long-lived requests complicate naive connection counts; sticky sessions may hide missing shared-state architecture; and health checks must accurately identify eligibility.

Graceful draining marks an instance as ineligible for new traffic while allowing existing requests or streams a controlled interval to complete. It must coordinate with the application, which may need to finish active transactions, refuse new work, and flush telemetry before shutdown. An orchestrator that removes a pod from discovery and a proxy that keeps cached endpoints for too long can produce avoidable connection failures during deployment.

Watch for unequal request costs and concentration effects. Ten requests to run expensive reports can consume more capacity than a thousand simple status reads. Proxies and services should expose per-route latency, in-flight requests, backend saturation, and queue depth rather than relying only on aggregate requests per second. See Server Load Balancing for detailed distribution mechanisms.

Retries, Timeouts, and Ambiguous Completion

A gateway can retry an upstream request after a connection error or timeout. This can improve availability for certain safe or idempotent operations, but it can also duplicate work, amplify load, and create uncertainty. A timeout does not prove the upstream failed to commit. A payment, enrollment, or order might succeed just before the connection drops; blindly repeating the request can cause a second side effect if the operation is not protected by a stable idempotency contract.

Design each route with a bounded retry budget, per-attempt timeout, overall request deadline, and explicit method or operation eligibility. Propagate the original deadline downstream; do not allow repeated attempts to exceed the user's permitted time or multiply total load uncontrollably. For non-idempotent write operations, require appropriate idempotency keys or application-level deduplication before enabling retries; even idempotent methods can have nontrivial backend side effects if implemented incorrectly.

Distinguish an upstream connection failure before any bytes are sent from a read timeout after the request may have reached the server. Do not assume the proxy can always determine which stage occurred. Clients, gateways, and backends should cooperate on status inquiry and reconciliation for uncertain outcomes.

Circuit Breaking, Admission Control, and Overload

Circuit breakers stop or limit calls to an upstream dependency that is persistently failing or saturated. They are useful when repeated attempts would waste resources or lengthen a cascading failure. An open circuit may return a controlled failure, use a safe cached response where the contract permits it, or divert eligible work to a genuinely healthy alternative. The decision must account for operation semantics; rerouting a state-changing request to an inconsistent replica can be worse than a visible temporary failure.

Combine circuit breaking with admission control, bounded queues, concurrency limits, and downstream cancellation. A proxy should be willing to reject work early rather than hold indefinitely many requests and overload the application. Monitor circuit state changes, error bursts, healthy-host counts, pending queues, shed traffic, and recovery success; a circuit breaker that remains open after recovery is another outage.

Distinguish an actual circuit breaker from a simple health check. A health check decides whether an endpoint appears eligible; a circuit breaker can protect a dependency based on observed errors, concurrent requests, or other dynamic signals. Both need hysteresis to avoid oscillation.

Edge Caching and Personalization Boundaries

Some reverse proxies and API gateways cache responses to reduce backend work and improve latency. Cacheability is defined by HTTP method, status, freshness directives, validators, request selection fields, and application-specific contracts. A cache must not accidentally serve one user's confidential response to another. In particular, shared caches must respect the conditions governing responses to requests containing Authorization; personalized data generally needs explicit private or nonstorage policy.

Cache keys must include every input that affects response selection, including relevant Vary fields, accepted encoding, host, path, and possibly approved query parameters. Overly broad keys cause cross-tenant or cross-language leaks; overly narrow keys decrease cache effectiveness and waste storage. A cached 404 or redirect may remain visible after a deployment if its freshness policy is not considered. Cache invalidation and stale-if-error behavior must be designed with data sensitivity and acceptable staleness in mind.

A gateway should not unilaterally cache a write response or convert an authenticated dynamic endpoint to public caching merely because the response was 200 OK. Application owners should declare the semantic contract, then the intermediary can execute an approved caching strategy. See HTTP Caching and Content Delivery for validators, surrogate caches, and CDN behavior.

API Products, Versioning, and Developer Contracts

An API gateway platform may publish APIs as managed products: the operator defines a route group, accepted consumers, credentials, usage plans, versions, documentation, and service-level expectations. This is an operational interface for API governance rather than an automatic guarantee that the underlying application contracts are stable. The service provider still owns resource meanings, validation, error models, backward compatibility, and deprecation timelines.

Version control can be implemented in paths, hostnames, headers, media types, or contract documents. Gateways can route /v1/ and /v2/ to different backends or adapt selected fields as part of a transition. Such transformations should be limited and tested: a gateway cannot infer how to preserve business meaning if the data model or authorization policy changes. Prefer clear consumer migration and documented sunset decisions to indefinite accumulation of hidden compatibility rewrites.

Change management should include a source-controlled API contract, review ownership, automated compatibility checks, client communication, release rollback, observability by version, and a retirement policy. Gateway configuration alone is not sufficient for a safe breaking change.

Backend-for-Frontend and API Aggregation

A backend-for-frontend (BFF) is a server-side interface tailored to a particular user experience, such as an administrative web portal or mobile app. A gateway may route to a BFF, or a gateway product may implement limited aggregation. A BFF typically owns application-specific orchestration and data shaping that would be inappropriate in a generic routing layer. This boundary is a design choice rather than an absolute product rule.

For a course dashboard, one client-visible request might combine catalog metadata, enrollment eligibility, and user notifications. Aggregating can reduce network round trips but introduces partial failures and fan-out. The orchestrator must define which subcalls are essential, which outputs may be stale, how identities propagate, and what to do when one backend is unavailable. A gateway that blindly invokes many dependencies can turn a small public request into excessive internal traffic.

Keep domain transactions within authoritative services. Combining three read responses is different from simultaneously changing three databases. If an aggregated write workflow spans services, it needs a documented coordinator, idempotency, durable state transitions, and reconciliation; no proxy setting can supply atomicity across independent systems.

Multitenancy, Consumer Isolation, and Quota Design

Public APIs often serve multiple institutions, departments, or business customers. The gateway can map authenticated consumer IDs to routing, quotas, billing labels, and access policies. However, the backend must enforce the actual tenant boundary for every object and query. A gateway route such as /tenants/alpha/records does not guarantee that the caller belongs to tenant alpha; URL text is untrusted until checked against verified identity and allowed relationships.

Quota fairness depends on correctly aggregating traffic across gateway replicas and deciding whether limits apply per account, key, principal, or endpoint. A tenant with many API keys should not trivially escape an account-level quota if the product contract is account-based. Conversely, grouping every user behind one IP address can impose arbitrary shared limits. Use accurate identity attribution and observability to explain policy outcomes to consumers.

Never let an untrusted tenant label directly select internal cluster destinations, credentials, or storage namespaces without validation. Tenant-specific routing can create server-side request forgery, lateral movement, or data exposure if configuration allows arbitrary user-supplied hostnames. Build an allowlisted service map and restrict egress to approved upstream networks.

Access Logs, Metrics, and Distributed Tracing

The intermediary is often the earliest reliable measurement point for incoming traffic. Useful fields include timestamp, route identity, client-facing scheme and protocol, downstream status, gateway-generated error reason, upstream cluster, upstream response status, connection establishment time, upstream latency, total request duration, bytes transferred, policy rejection reason, and a correlation identifier. Logging must avoid raw credentials, session cookies, unnecessary payload data, and unbounded personally identifiable information.

A single total latency does not identify where time was spent. Separate queue time, TLS negotiation or connection establishment, policy processing, upstream wait, body streaming, and client write time when the product exposes them. A 499-style vendor-specific client-closed code, for example, must not be mistaken for an IETF-standard HTTP status. Document which metrics are generated by which component and the denominator used for error rates.

Distributed tracing connects gateway spans to service spans through an approved propagation standard such as W3C Trace Context. Bound untrusted baggage and sampling inputs, and prevent a caller from forcing unrestricted debug retention. Cross-check trace IDs with access logs and service deployment versions. Capture enough detail to distinguish a gateway rejection from an upstream service failure without leaking request secrets.

Service-Level Objectives and Error Attribution

A gateway can provide a clear definition of externally observed availability, latency, and request success. But an edge-only metric may count a cached success even when the origin is down, or count legitimate 401 responses as “failures” if poorly defined. Establish which methods, paths, users, statuses, and maintenance windows belong in an indicator. Use separate indicators for admission-policy rejections, successful authorized business operations, and actual service unavailability.

For latency, prefer percentiles over only mean response time, and measure at least one client-visible boundary. Trace a slow request across the ingress and application spans before changing timeout settings. A proxy can mask backend latency by retrying, which may improve isolated user outcomes but obscure an escalating dependency outage. Monitor attempts per successful request and retry amplification explicitly.

Set objectives for the system, not just the gateway: a perfectly healthy reverse proxy returning 503 to every request is not a healthy application. Error budgets and escalation paths should identify who owns route configuration, TLS certificates, gateway compute, identity infrastructure, backend capacity, and persistent data.

High Availability and Gateway Failure Domains

Placing all traffic behind one reverse proxy creates an intentional chokepoint and a potential single point of failure. Redundancy may require multiple gateway instances, separate failure zones, resilient configuration distribution, health-aware network routing, and recovery of certificates, policies, and secrets. A second gateway with the same broken configuration is not independent redundancy. Shared control-plane dependencies, certificate issuers, DNS, logging exporters, and rate-limit stores can create common-mode failures.

Consider how clients reach healthy gateways after a zone failure, how long existing connections remain bound to dead nodes, and which components can continue operating without management APIs. Some gateways can forward requests during a control-plane outage using the last accepted configuration; others have different dependency behavior. Test the exact product rather than assuming a specific fail-open or fail-closed mode.

A health-aware gateway deployment should survive at least the failure modes required by its service objectives: instance loss, dependency timeout, certificate renewal interruption, configuration rollback, and an exhausted upstream pool. Document recovery-time and recovery-point objectives separately; an ingress gateway commonly stores little durable business state, but its configuration and audit evidence are operationally critical.

Configuration as Code and Change Governance

Proxy configuration controls public routing and sometimes authorization. Treat it like application code: review changes, validate syntax, test the resulting effective configuration, limit administrative access, and deploy with a rollback plan. Separate infrastructure changes from policy decisions so operators can identify whether an incident was caused by a new route, certificate, rate threshold, upstream target, or authentication requirement.

A source-controlled route inventory should name each external host and path, owning service, accepted methods, identity requirement, body limit, timeout, retry eligibility, caching policy, upstream trust, and incident contact. Enforce least privilege in the gateway control plane; a team that owns one API should not automatically be able to redirect other tenants' traffic or read their TLS secrets.

Support progressive rollout of route changes where possible. Before a cutover, validate that public endpoints and upstream services are reachable, policy precedence is correct, browser redirects retain the public scheme, and audit logs capture the new version. On rollback, remove obsolete routes cleanly; temporary exemptions tend to become permanent undocumented attack paths.

Deployment Options: NGINX, Envoy, Managed Gateways, and Kubernetes

NGINX-style reverse proxies are commonly used for virtual hosts, TLS termination, response buffering, and upstream routing; their exact features depend on product edition and configuration. Envoy provides a programmable proxy architecture, rich HTTP routing, health and telemetry mechanisms, and trust configuration for forwarding metadata. Cloud-managed gateways can reduce infrastructure operations and integrate service discovery, API consumers, authentication and quotas, but have provider-specific limits, pricing, and semantics.

In Kubernetes, the Gateway API expresses Gateway listeners, route attachment and HTTPRoute rules with separation of infrastructure and application configuration responsibilities. Controller capabilities and support for particular filters, protocol translations, and backend TLS policies must be checked individually. An Ingress controller may remain appropriate in many clusters; a migration to Gateway API should be justified by a concrete capability or governance need.

Selection criteria include operational skill, required protocol support, egress and ingress trust model, expected traffic, observability, developer onboarding, portability, change-management maturity, and total cost. Do not choose solely on headline throughput benchmarks from an environment unlike the intended workload.

Capacity, Cost, and Resource Budgets

Gateway costs include compute, memory for buffers, TLS operations, egress and inter-zone transfer, log volumes, tracing, rate-limit storage, licensing, managed service request charges, and operator time. A seemingly small gateway cost can be dominated by per-request observability or network transfer at scale. Conversely, introducing a gateway can save backend capacity through effective caching, early rejection, and connection reuse.

Estimate workload using requests per second, average and peak body sizes, concurrent streams, TLS handshakes, upstream connections, policy evaluation time, and latency distributions. Suppose an enrollment API receives a peak of 500 requests per second and each gateway request produces three internal service calls; that can create 1,500 service calls per second before retries or cache hits are considered. This is a planning example, not a measured forecast. Model downstream fan-out explicitly.

For rate-limit stores or external authorization systems, measure their availability and latency contribution as first-class dependencies. A design that adds a remote policy check to every request may impair availability unless policy caching, bounded timeouts, and safe failure rules are deliberate. Test whether buffer memory grows with slow clients and whether downstream connection pools saturate under workload spikes.

Trust Boundary and Threat-Model Checklist

Review the complete ingress path rather than only the public proxy: DNS resolution; public TLS identity; WAF and edge; gateway; internal routing; service identity; application-level authorization; data access; and outbound dependencies. Consider spoofed forwarded headers, exposed admin interfaces, stolen client credentials, bypass routes, request smuggling, host-header injection, SSRF through dynamic upstream selection, unbounded uploads, cache poisoning, tenant isolation failures, and logs that expose tokens.

For each threat ask: What is the attacker-controlled input? Which component has authority to validate it? Which independent control prevents bypass? What evidence would reveal the attempt? How can operators contain and recover from a compromise? A high-level diagram is insufficient if it does not identify the originating trust level of a header or assertion.

Keep testable negative cases: direct access to a private backend must fail; a forged principal header must not grant access; a valid token for one student must not read another student's enrollment; malformed framing must not cross the boundary ambiguously; a gateway outage must return a controlled error; and a configuration rollback must restore the previous authorized route set.

Operational Runbook: Diagnose the Correct Layer

Start with the symptom and request path. Is the client unable to resolve the hostname, unable to establish TLS, receiving a gateway-generated rejection, getting a gateway timeout, or reaching an application that returns a legitimate error? Confirm the public host and protocol first, then a unique request identifier and timestamp. Use controlled tests against the edge and, from an authorized network location, the upstream service. Avoid bypassing a proxy with production credentials from an untrusted machine.

Inspect routing tables, route priority, certificate expiry, DNS-to-edge mapping, health counts, upstream DNS or registry entries, upstream TLS verification, and per-route limits. Compare logs at the gateway and service using a correlation ID. If the gateway emits a 504 but the backend later commits the operation, resolve the business state before asking the user to retry. A failed health check might be a symptom of an overloaded database rather than a network problem.

Escalate with an evidence bundle: UTC time window, redacted request ID, public method and path template, observed status, gateway policy decision, upstream status or connection error, deployment/configuration revision, affected regions, and whether the incident is reproducible. Do not include raw passwords, bearer tokens, session cookies, or sensitive request bodies.

Windows PowerShell: Read-Only Investigation

The commands below are observation-oriented examples for Windows 11 PowerShell. Replace the reserved illustration hostname with an endpoint you operate or are authorized to test. They do not change gateway configuration or bypass TLS verification; some commands depend on the installed PowerShell version and operating-system capabilities.

# Confirm name resolution and the public TCP endpoint:
Resolve-DnsName portal.example.org
Test-NetConnection portal.example.org -Port 443

# Inspect status and response headers without changing the service:
try {
  $response = Invoke-WebRequest -Uri 'https://portal.example.org/' -Method Get -ErrorAction Stop
  $response.StatusCode
  $response.Headers
} catch {
  $_.Exception.Message
  if ($_.Exception.Response) { $_.Exception.Response.StatusCode }
}

Interpretation: successful DNS resolution does not prove that the destination application is healthy. A successful TCP connection does not prove that certificate validation or HTTP authorization succeeds. An HTTP 401 may be an intentional identity challenge, not a network failure. For PowerShell scripting, use a bounded set of observations and capture returned errors rather than retrying a sensitive write operation automatically.

Architecture Decision Framework

Before selecting a gateway, document the workload and the expected policy boundaries. First identify the callers: browser users, mobile apps, internal services, or third-party partners. Then list the services that must be reached, their public URI contracts, accepted methods, identity models, and response classifications. Explicitly distinguish the requirements that can be enforced at the edge from those requiring business data at the service. A route list without ownership is not an architecture decision.

Next compare candidate deployments using measurable criteria: protocol requirements, number of independently evolving APIs, expected peak concurrency, TLS and upstream trust, service discovery, availability targets, policy change ownership, deployment maturity, and portability. Include the gateway's failure modes, cost, log sensitivity, and support burden. Run a production-like traffic test through the complete chain, not a proxy-only synthetic benchmark.

Finally write a brief decision record: selected approach, rejected alternatives, assumptions, risk ownership, verification results, rollback triggers, and the date of reevaluation. A single reverse proxy with a small set of routes may be the correct choice for an internal service. A shared API gateway may be justified for many partner consumers with independent credentials and published contracts. A service mesh may be justified by east–west identity and observability requirements without forcing every internal request through a public gateway.

Worked Scenario 1 — Campus Portal with Two Application APIs

Initial situation: MGU operates a course catalog API and an enrollment API under a single public hostname. The browser requests https://portal.example.org/api/catalog/courses and /api/enrollments. The two services run on different private networks and are deployed on independent schedules. Publishing their internal hostnames to browsers would couple clients to internal topology.

Architecture: A reverse proxy accepts HTTPS for the public host, applies deterministic path-based route matching, and forwards to service-specific upstream pools. The enrollment route requires an identity check and a stricter request-body and rate policy. Both services validate their own input, and the enrollment service enforces student-level access. Route configuration is versioned together with an endpoint inventory, and the proxy includes a trusted request ID in downstream logs.

Failure exercise: Simulate the catalog service becoming unavailable while enrollment remains healthy. The gateway must return an appropriate error for affected catalog requests without hiding errors or rerouting them to enrollment. Review the monitoring data by route and check that the public certificate and unrelated API remain functional. This demonstrates fault isolation by route, not guaranteed independence: a shared proxy failure still affects both APIs.

Worked Scenario 2 — A Forged Forwarded Client Address

Initial situation: An application uses the first address in the X-Forwarded-For string as the “real” client for abuse blocking. An external caller sends a crafted header with a preferred address. The edge appends an actual observed address but leaves the untrusted first entry intact; the backend then accepts the spoofed value.

Diagnosis: The problem is a broken trust boundary, not a flaw in DNS or TCP. Any client can attach an HTTP header unless the first trusted hop removes or overwrites it. An upstream service may see multiple valid-looking addresses for multiple proxies, and there is no universal safe rule to trust the first one without knowing how the proxy chain is configured.

Correction: Identify the trusted ingress hop, overwrite or sanitize client-supplied forwarding metadata there, constrain trusted upstream peer addresses, and have the backend reconstruct the client address only from the declared hop policy. Test a forged header from outside and a legitimate multi-proxy request. Keep IP attribution out of privileged user authorization; use verified identity and tenant context instead.

Worked Scenario 3 — TLS Ends at the Edge

Initial situation: A service is published over HTTPS, and auditors assume traffic is encrypted all the way to its private application container. The reverse proxy, however, terminates public TLS and forwards ordinary HTTP over a shared internal network. The public browser lock icon is valid but says nothing about the internal hop.

Decision: Define the trust requirements for the second connection. If internal confidentiality and authentication are required, configure an upstream TLS session with certificate validation and, where appropriate, mutual TLS. Manage gateway trust roots, backend certificate identities, expiry monitoring, and rotation. Ensure the proxy's route selection uses the intended upstream identity rather than disabling certificate verification merely to make the handshake pass.

Verification: Confirm at the gateway and server that the negotiated upstream transport and expected peer identity are correct. Simulate a backend certificate mismatch and require a controlled failure rather than silent fallback. Record exactly where decrypted data can be seen and who can access those systems. Public HTTPS and internal HTTPS are separate security claims.

Worked Scenario 4 — Student Authorization Bypass Attempt

Initial situation: A gateway validates a signed token with a general enrollments:read scope. A student requests the enrollment record for a different student by changing the record ID in the URL. The gateway sees a valid token and a permitted route and would ordinarily forward the request.

Required design: The enrollment service checks the authenticated subject, permitted delegation, relevant campus policies, and the ownership of the requested record. A gateway rule requiring the general scope is useful for rejecting clearly ineligible callers, but the service alone has the authoritative relationship needed to decide this object-level access. If a policy service is used, it must receive trustworthy object attributes and return a decision that is actually enforced.

Testing: Create two authorized test users and objects in a staging environment. Verify that each user can access the permitted record but receives a safe denial for the other. Repeat across list, search, export, and bulk endpoints, because hiding one direct URL is not sufficient. This is a security invariant, not a gateway product feature.

Worked Scenario 5 — API Gateway Throttling Under Shared NAT

Initial situation: An educational portal limits requests solely by client IP. Hundreds of students connect through one campus Internet exit address; a burst of normal activity triggers 429 responses for many users, even though no individual exceeded an intended user quota. Conversely, an abusive caller can rotate IP addresses and evade the rule.

Redesign: Separate anonymous perimeter defenses from authenticated per-user and per-tenant usage policies. Apply a bounded endpoint-specific cost budget for expensive exports and concurrent requests. Configure shared limiter state when multiple gateway instances serve the same logical quota. Clearly define whether the quota is per principal, API key, institution, or account. Keep backend workload limits even after an edge admits a request.

Review: During a staged burst, report accepted and rejected requests by identity and route. Make sure a denied request does not execute the expensive operation upstream. Inspect fairness under shared NAT, recovery behavior after the window passes, and whether a limiter-store outage causes an explicitly chosen fail-open or fail-closed policy. Do not treat a best-effort quota as an absolute charge cap.

Worked Scenario 6 — A Gateway Retry Duplicates an Enrollment

Initial situation: A gateway forwards a POST /enrollments request. The service commits the enrollment but the response connection drops. The gateway retries automatically; the service treats the second request as new and creates a duplicate. From the student's perspective the first attempt appeared to fail.

Root cause: The gateway inferred unsuccessful business completion from a transport failure. It knew that the response was missing, not whether the transaction had committed. Merely shortening timeouts or using more backend instances cannot resolve the ambiguity.

Correction: Disable unsafe automatic retries or implement a durable idempotency key bound to the caller and operation payload, with a stable result lookup. The service checks the deduplication record and its own transactional invariants before accepting a new write. Propagate a deadline and return an inquiry path for uncertain outcomes. Test response loss after commit and ensure that repeated delivery produces one accepted enrollment, not one enrollment per attempt.

Worked Scenario 7 — A Streaming Event Feed Stops Updating

Initial situation: A dashboard uses server-sent events to display live operational updates. Direct testing against the service shows an event every few seconds, but users behind the reverse proxy see events in large bursts or not until the connection closes. A default response buffer and short proxy timeout are incompatible with the streaming workload.

Diagnosis: Trace the request from browser to proxy and backend. Inspect response buffering, content encoding, idle-time behavior, maximum concurrent streams, and whether keepalive traffic can satisfy the product's configured idle semantics. Distinguish buffering from service failure; if the backend emits on schedule but the proxy buffers, increasing backend CPU does not help.

Correction: Apply stream-appropriate buffering and timeout policy to the specific endpoint while preserving total resource bounds and authentication. Define reconnect and message replay behavior so a brief disconnect does not silently lose critical events. Test graceful drain during deployment and measure latency at the client, not just the upstream service.

Worked Scenario 8 — Versioned API Migration Without a Flag Day

Initial situation: A legacy student-record API uses /api/v1/; new clients require a different representation in /api/v2/. Requiring all consumers to upgrade at once would disrupt mobile apps and partner integrations on different release schedules.

Plan: Publish both contracts with explicit owners and compatible authorization rules. The gateway matches versioned public routes to separate upstream targets, allowing staged migration and per-version error and latency metrics. A small documented rewrite can assist with path compatibility, but changes in the meaning of enrollment state belong in application-level adapters or new service contracts rather than hidden proxy transformations.

Execution: Route a controlled portion of test traffic, verify both versions with contract tests, announce deprecation and migration dates, and log consumer adoption. Roll back the new route without breaking the old interface if health and correctness signals fail. Remove obsolete routes only after consumers are accounted for and policy owners approve retirement.

Worked Scenario 9 — Host-Header and Redirect Confusion

Initial situation: A public gateway terminates HTTPS and forwards to an HTTP application. The backend generates absolute password-reset URLs using whichever Host value arrives in the request. An attacker supplies an unexpected host, or a misconfigured proxy passes an unvalidated forwarding value, causing links to point to an attacker-controlled domain or an internal server name.

Correction: Define an allowlist of public hostnames at the gateway; reject unknown authority values. Configure canonical external origins at the application rather than accepting arbitrary user-supplied host text. Convey the external scheme only through the trusted forwarding interface, and configure cookies, redirects, and CSRF origin policies to agree with that authority.

Verification: Request the site through its intended host and several deliberately invalid hosts in a test environment. Check redirects, link-generation templates, cookie domain and path, and the security of the password-reset workflow. Confirm that HTTPS redirection does not loop and that internal upstream hostnames never appear in client-visible pages.

Worked Scenario 10 — Kubernetes Gateway API and Route Ownership

Initial situation: Several development teams share a Kubernetes platform. Infrastructure staff own public DNS, certificates, and the edge listener; application teams own service routes. Editing a single monolithic proxy file creates coordination bottlenecks and excessive permissions.

Model: Where supported, the Gateway API separates a Gateway listener from HTTPRoute objects that attach to it under declared restrictions. An application team can propose routing to its service without automatically controlling shared certificates or unrelated hostnames. Platform policy governs which namespaces, hosts, backends, and reference grants are permitted. The implementation's support for TLS, filters, timeouts, and cross-namespace references still needs verification.

Controls: Protect the configuration repository, approve route changes, verify that the effective controller accepts intended attachments, and check that a rejected route cannot silently expose a service. During an upgrade, compare actual Gateway API behavior to the tested controller version. A declarative manifest is a desired configuration, not evidence of correct data-plane enforcement until observed.

Worked Scenario 11 — Gateway 504 and Database Saturation

Initial situation: The public gateway frequently returns 504 for an enrollment search endpoint. Operators increase the gateway timeout, but user-visible latency worsens. Traces reveal that the application accepts requests and then waits on a saturated database connection pool. The gateway is reporting a downstream symptom, not originating the root resource bottleneck.

Diagnosis: Compare the gateway's upstream connection time, time to first response byte, service internal queue time, and database connection wait. Check retries, because repeating an already-slow search may double or triple the load. Separate an upstream timeout from an application that produces a 504 itself; the status code alone is not enough evidence.

Response: Bound queue depth, stop inappropriate retries, tune the expensive query or add capacity as justified, and set a realistic deadline budget. Include request cost in throttling rules. Verify that the system returns controlled overload responses rather than exhausting threads and connections. The long-term correction is measured end-to-end capacity management, not an indefinitely longer gateway timeout.

Worked Scenario 12 — Gateway Outage and Common-Mode Configuration

Initial situation: Two reverse proxy replicas serve the same public application. Both begin returning errors immediately after a configuration push that changes the upstream cluster name. Operators initially regard the two replicas as redundant, but the fault is common to both instances.

Diagnosis: Compare the effective configuration revision, accepted route set, upstream health and error reasons. A second replica protects against some host failures, but not shared configuration, certificate or control-plane mistakes. Determine whether the control plane can revert the change while keeping unaffected routes stable and whether the proxy can operate on the last known good configuration.

Remediation: Roll back the exact configuration revision, confirm healthy upstream endpoints and public requests, and stage future changes against representative route tests. Apply canary rollouts to the configuration plane where feasible, define automated rejection of invalid upstream references, and maintain an independent recovery channel. A useful incident review changes the release process and detection mechanisms, not merely the replica count.

Applied Design and Investigation Exercises

  1. Trust-chain reconstruction: Draw a client, CDN, WAF, gateway and backend. For every hop record the peer address, TLS identity, authority value and forwarding metadata. Identify which field is attacker-controlled at entry, and where it first becomes trustworthy.
  2. Route inventory: For a university portal, create a host/path/method table with backend owner, authorization rule, body limit, timeout, retry eligibility and expected log identifier. Justify why an unmatched route returns a controlled failure.
  3. Ambiguous write: Model a POST that commits at the server but loses its response. Specify an idempotency key, deduplication scope and status inquiry; demonstrate that a second submission does not create a duplicate.
  4. Failure attribution: Create a diagram with DNS failure, certificate mismatch, route miss, edge rejection, upstream timeout and application rejection. List the minimal observations that distinguish each.
  5. Streaming compatibility: Trace an SSE or gRPC stream through an edge gateway and upstream service. Assign idle timeout, total lifetime, buffering, backpressure and draining behavior to each hop.
  6. Tenant boundary: Design an API where the caller supplies a tenant identifier. Show where the identifier is parsed, bound to verified principal permissions and checked against each requested object.
  7. Capacity calculation: Assume 800 public requests per second, 20% requiring four internal calls and the remainder requiring one. Calculate baseline upstream calls per second, then estimate how a 10% retry fraction changes the demand; identify which operations must not be retried.
  8. Configuration migration: Write an architecture decision record contrasting a simple reverse proxy, a managed gateway, and a Kubernetes Gateway API controller for a three-service deployment. Include rollback and policy ownership.

These exercises are design and observation tasks; no live MGU production configuration is assumed. Results should identify assumptions and the evidence necessary to verify them in a controlled environment.

Specialist Glossary

Terms refer to their architecture-specific meanings in the context of proxies and API gateways; implementation details vary.

Admission control
A policy that accepts, queues or rejects incoming work according to capacity and priority.
ALPN
TLS extension for negotiating an application protocol such as HTTP/2 or HTTP/1.1.
API gateway
An intermediary that exposes and governs APIs, commonly adding routing, identity and consumer-management policy.
API key
A credential commonly used to identify an API consumer or usage plan, not necessarily a user identity.
Authorization
A decision about whether an identified principal may perform a particular action on a resource.
Backend
A service or server that receives requests forwarded from a proxy or gateway.
Backend-for-frontend (BFF)
An API tailored to the needs and workflow of a particular client experience.
Backpressure
Propagation of downstream capacity limits to an upstream producer or requester.
Body buffering
Holding request or response bytes at the intermediary before forwarding them.
Canary release
A controlled rollout that initially exposes a small portion of requests to a new route or version.
Circuit breaker
A protection that limits attempts to a failing or overloaded dependency.
Client-facing connection
The network and transport session between the client and the intermediary.
Connection draining
Stopping new traffic to an instance while existing operations finish within a bounded period.
Connection pool
Reusable transport connections maintained to reduce setup cost and control concurrency.
Content Security Policy (CSP)
Browser-enforced content loading and execution restrictions supplied by an HTTP response header.
Control plane
Management system that distributes intended routes, policy and endpoint configuration.
Correlation ID
Identifier used to join logs or traces associated with a request.
CORS
Browser policy for exposing qualifying cross-origin responses to scripts.
CSRF
Attack that induces a browser to send an unwanted authenticated request.
Data plane
The forwarding path through which user requests are actually processed.
Deadline
An overall time bound by which an operation is expected to complete or be cancelled.
Destination pool
A set of eligible upstream endpoints for a route.
Drain timeout
The limit allowed for active requests or connections to finish during shutdown.
Edge
The service-entry boundary closest to outside clients under a deployment architecture.
Egress
Outbound traffic departing a workload or networking boundary.
End-to-end field
HTTP metadata whose meaning extends to recipients beyond a single connection hop.
Envoy
A proxy software project often used for programmable HTTP routing and service-mesh data planes.
Fail closed
A failure policy that rejects work when required authorization or protection cannot operate.
Fail open
A failure policy that continues selected work without a failed control, only when explicitly acceptable.
Forward proxy
An intermediary selected by a client to connect toward destination origins.
Forwarded header
RFC 7239 HTTP field for recording information about request processing through proxies.
Gateway API
Kubernetes resource model for defining gateways, listeners and routes.
Graceful shutdown
A shutdown process that rejects new work while allowing current requests to finish safely.
Health probe
Observation used to determine whether a service endpoint appears eligible or needs repair.
Host-header injection
Use of untrusted HTTP authority metadata to influence links, routing or other behavior.
HTTP 429
Too Many Requests response used to signal rate or admission limits.
HTTP 502
Bad Gateway response indicating a gateway or intermediary received an invalid upstream response or encountered a related failure.
HTTP 503
Service Unavailable response, often used during overload or maintenance.
HTTP 504
Gateway Timeout response indicating an intermediary did not receive a timely response from upstream.
HTTPRoute
Kubernetes Gateway API resource that describes rules connecting HTTP requests to backends.
Idempotency key
Caller-provided operation identity supporting safe deduplication of repeated requests.
Ingress
Incoming traffic entering an application or network boundary.
Issuer
Authority identified by a token as responsible for its issuance.
JWT
JSON Web Token, a structured token format that requires correct validation policy.
Least privilege
Confining a principal or component to the minimum capabilities it needs.
mTLS
Mutual TLS authentication of both connection peers through a defined certificate trust policy.
OpenAPI
Machine-readable description format for HTTP API operations and schemas.
Origin
HTTP authority and scheme context defining the logical server endpoint.
Origin header
HTTP request field indicating the request origin in some browser contexts.
Origin server
Server authoritative for handling requests to a particular resource or representing that server.
Path normalization
Consistent interpretation of encoded path segments and separators before routing and authorization.
Policy decision point
Component that evaluates an authorization policy and returns a decision.
Policy enforcement point
Component that applies a policy decision to an attempted operation.
PROXY protocol
Connection-level metadata format supported by some proxies for transmitting client connection details.
Quota
Consumption budget applied over a specified period or accounting interval.
Rate limit
Control that bounds accepted request frequency or equivalent workload pace.
Readiness probe
Check intended to establish that a service can receive new workload.
Request smuggling
Security issue caused by disagreement over HTTP message boundaries across recipients.
Retry amplification
Increased total work caused by repeated attempts under failures or delays.
Reverse proxy
Intermediary appearing as an origin-facing service and forwarding received requests to upstream servers.
Route
Configured rule selecting processing policy and possible upstream destination.
Route precedence
Order or priority with which potentially overlapping route rules are evaluated.
Schema validation
Checking payload shape and types against a declared interface structure.
Security assertion
A statement about identity or permissions whose provenance and integrity must be verified.
Server-sent events (SSE)
HTTP response streaming model for server-to-client event delivery.
Service discovery
Mechanism for finding eligible runtime service endpoints.
Service mesh
Workload-to-workload networking architecture often using proxies and a management plane.
SSRF

Tenant
Organizational customer or isolation domain sharing infrastructure with others.
TLS termination
Completion of a TLS session at an intermediary or service endpoint.

Metadata propagated across service boundaries to correlate spans in a distributed request.
Trusted proxy
Intermediary authenticated or allowlisted to supply forwarding metadata under an explicit policy.
Upstream connection
Independent connection opened or reused from the gateway to the backend service.
Virtual host
Routing configuration selecting a site or service by requested authority or host.
WAF
Web application firewall, an HTTP traffic inspection component applying configured protective rules.
WebSocket
Bidirectional message transport established after an HTTP handshake or protocol mapping.
X-Forwarded-For
Widely deployed, nonstandardized client-chain address header whose trust interpretation requires configuration.
X-Forwarded-Proto
Common forwarded metadata indicating the external request protocol under a trusted proxy convention.
Zero trust
Access model requiring explicit evaluation of identities and permissions rather than automatic trust by network location.
