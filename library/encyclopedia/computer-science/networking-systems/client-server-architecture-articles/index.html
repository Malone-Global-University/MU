Collection Overview

The Client-Server Architecture unit belongs to the Networking Systems division of the Computer Science volume of the MGU Encyclopedia. It extends the existing Client-Server Architecture overview, which establishes the client and server roles, HTTP and secure transport, application and data tiers, scaling, reliability, security, and worked university-system cases.

In client-server computing, a client asks another process to perform a defined service or return information. The server controls the requested capability and its associated authority; the same program can also become a client to other services. Production systems may interpose DNS, proxies, gateways, caches, load balancers, and databases between a visible user interface and an authoritative record. This directory studies these responsibilities as a coherent architecture—not simply as a collection of protocols or product names.

Foundations and Protocol Exchanges

These five articles establish the identity of an endpoint, the mechanics of an exchange, the role of names and transports, and the protective boundary of a secure channel. They progress from an application-level model to the underlying delivery mechanisms without treating every network detail as application architecture.

1. Client and Server Roles

Logical client and server roles, resource ownership, initiating requests, and responsibility allocation. Explain that a client or server is a role in a particular exchange, not necessarily a hardware class or an organizational boundary. Follow a browser, application service, identity provider, and database through chained requests in which one process may alternate roles. Define authoritative state, service ownership, client-side convenience checks, and server-side enforcement; distinguish logical architecture from physical deployment. Close with a responsibility matrix for validation, authentication, authorization, presentation, and record persistence.

2. HTTP Request and Response Lifecycle

Request construction, routing, interpretation, response formation, and ambiguous outcomes. Trace one request from a user action through connection reuse, HTTP method and target, request fields, proxy routing, application validation, storage access, and response rendering. Explain the semantics of safe and idempotent methods and distinguish a timeout from proof that a server-side operation failed. Include an annotated exchange with status codes, headers, a controlled failure, and a client-side retry decision. Keep detailed HTTP version framing in its separate transport article.

3. DNS and Service Endpoints

Name resolution, host authority, schemes, ports, addresses, and endpoint selection. Describe how a human-readable host is resolved, why the DNS result may designate an edge service or gateway rather than the final application, and how scheme, host, port, and path identify different aspects of a web target. Distinguish network reachability from service identity and from application authorization. Cover development loopback endpoints, stable production names, DNS caching, service discovery, and the operational risks of hard-coded addresses or incorrect environment configuration.

4. HTTP Versions and Transport

HTTP/1.1, HTTP/2, HTTP/3, TCP, UDP, and QUIC transport relationships. Compare the shared HTTP semantics with version-specific transport and message framing. Explain HTTP/1.1 connection reuse, HTTP/2 multiplexed streams, and HTTP/3 over QUIC, including why QUIC uses UDP without surrendering reliable stream delivery. Show how connection setup, head-of-line blocking, packet loss, and multiplexing affect workloads; explain why an HTTP version upgrade cannot fix slow application queries or oversized responses. Preserve the distinction between protocol features and deployment-dependent performance claims.

5. TLS and Secure Client Connections

Confidentiality, endpoint authentication, certificates, and protected channel boundaries. Introduce TLS handshakes, certificate-path and hostname validation, integrity protection, and the trust relationships involved in HTTPS. Distinguish encrypted transport from identity-aware access control for application records. Study the security implications of TLS termination at a reverse proxy, protected internal hops, client credential storage, and certificate lifecycle operations. Include defensive troubleshooting for validation failures; do not teach bypassing certificate checks as a permanent operational remedy.

Application Tiers, Routing, and Delivery

These four topics explain how a seemingly simple client-server relationship becomes a multi-component production path. They focus on deployment boundaries, traffic mediation, scaling, and caching while preserving the distinction between an application’s authoritative state and infrastructure used to deliver it.

1. Two-Tier and Three-Tier Systems

Separation of presentation, business logic, data storage, and deployment tiers. Define tiers as logical responsibilities and compare direct client-to-data designs with an application-mediated design. Use a course-enrollment service to distinguish presentation state, transaction rules, and persistence, then examine what changes when several application instances share a database. Discuss deployment independence, connection pooling, access restrictions, change management, and the tradeoff between simplicity and extra network hops. Avoid equating the number of tiers with the number of physical servers.

2. Reverse Proxies and API Gateways

Inbound request mediation, routing policy, gateway services, and proxy trust. Explain how a reverse proxy receives external requests and forwards them to selected upstream applications. Differentiate common proxy responsibilities—TLS termination, routing, request normalization, payload limits, and observability—from API-management policy such as quotas and interface-version routing. Examine forwarded-header provenance, authenticated identity assertions, timeouts, upstream health, and failure domains. Include an annotated flow showing that a proxy can enforce additional protections without replacing application-level authorization.

3. Server Load Balancing

Traffic distribution, health checks, shared bottlenecks, capacity, and failover. Compare round-robin, least-connections, weighted, and health-aware selection at a conceptual level. Explain readiness versus liveness checks, stateless application replicas, sticky-session tradeoffs, load balancing at different protocol layers, and the effect of losing an instance. Work a capacity example with normal operating headroom and one-instance failure. Emphasize that multiple application servers do not remove a shared database, identity provider, or network dependency bottleneck.

4. HTTP Caching and Content Delivery

Client, proxy, server, and CDN caching with freshness and privacy controls. Explain what can be cached at the browser, reverse proxy, application, and content delivery network layers. Cover Cache-Control, validation with ETags, cache keys, content variants, stale data, invalidation, and the difference between public immutable assets and private personalized records. Use a university course catalog to show a safe caching opportunity, then contrast it with sensitive enrollment state. Make clear that an HTTP GET response is not automatically suitable for shared caching.

State, Identity, and Interface Contracts

These three articles address how clients remain recognizable across exchanges, how rights are enforced, and how service interfaces stay compatible as software evolves. Their shared theme is the difference between a convenient client-side representation and a binding, server-enforced contract.

1. Session and State Management

Cookies, sessions, tokens, shared server state, and lifecycle management. Distinguish HTTP statelessness from application state, and explain the roles of session identifiers, cookies, access tokens, and durable account records. Trace an authenticated browser visit across multiple application instances, showing why local-only session memory can complicate scaling. Discuss credential expiration, revocation, Secure and HttpOnly cookies, SameSite configuration, shared-state stores, logout, and consistent user experience during intermittent connectivity. Avoid depicting cookies and tokens as interchangeable security guarantees.

2. Client-Server Authentication and Authorization

Identity verification, resource-level permission checks, and least-privilege boundaries. Develop separate models for proving identity and determining whether a given operation on a given resource is allowed. Trace a student requesting a transcript and a student requesting another person’s transcript; explain why login alone does not grant object-level access. Cover service-to-service identity, trusted proxy assertions, protected routes, least privilege, and authorization decisions based on authoritative server state. Include an access-check matrix and a defensive review of common object-identifier mistakes.

3. API Contracts and Service Versioning

Schemas, response semantics, backward compatibility, and coordinated interface change. Define a client-server contract across resource names or RPC methods, request validation, field meanings, error responses, and version expectations. Explain how browser caches, mobile installations, and partner clients may use different versions simultaneously. Compare additive and breaking changes, contract testing, capability negotiation, deprecation windows, and schema-compatible updates. Distinguish version labels from genuine compatibility policy, and connect interface decisions to safe rollout and service ownership.

Reliability, Operations, and Deployment

These three articles build operational reasoning: define failure semantics, measure real user-visible performance, and diagnose an implementation across local and production environments. They treat deployment and incident response as part of architecture rather than an afterthought.

1. Client-Server Reliability Patterns

Timeouts, bounded retries, idempotency, circuit breakers, and overload protection. Build an explicit failure model for disconnected clients, partial network loss, slow dependencies, and server-side completion after client timeout. Explain deadlines, exponential backoff with jitter, retry budgets, idempotency keys, circuit breakers, bulkheads, and load shedding. Use an enrollment submission to show why an ambiguous outcome must be reconciled instead of blindly resubmitted. Discuss queue-backed work and safe degraded modes while avoiding claims that any one pattern guarantees exactly-once execution.

2. Client-Server Performance and Observability

Latency budgets, throughput, queueing, metrics, tracing, and investigation of bottlenecks. Define elapsed request time, sustained throughput, concurrency, saturation, error rate, and tail percentiles. Introduce Little’s Law with its steady-state assumptions and construct an end-to-end latency budget spanning client, network, proxy, application, and database. Explain how logs, metrics, and distributed traces complement one another and where their evidence can mislead. Present a disciplined way to find bottlenecks without confusing average response time with p95 or p99 latency or recording sensitive payloads indiscriminately.

3. Client-Server Deployment and Troubleshooting

Local development, production topology, environment configuration, and fault isolation. Contrast a loopback-only learning server with an Internet-facing production deployment using DNS, TLS, proxies, application replicas, and private data stores. Explain configuration management, secret handling, deployment rollouts, health checks, dependency maps, and basic incident triage. Trace a failed course-catalog request through browser inspection, name resolution, network reachability, proxy response, application logs, and database dependencies. Distinguish a diagnostic symptom from a confirmed root cause and explain safe recovery principles.

Worked Architectural Scenarios

Scenario 1 — A public course catalog under heavy demand

Suppose a campus portal receives a surge of public catalog reads at registration time. The requested course descriptions change infrequently, so suitable public responses and immutable page assets can be cached by browsers or a CDN. A reverse proxy routes cache misses to application instances, which consult an authoritative catalog store. The engineering review must establish which responses contain personalized data before enabling shared caching, how updates invalidate cached descriptions, and whether the database can sustain cache-miss traffic. Read HTTP Caching and Content Delivery, Reverse Proxies and API Gateways, and Server Load Balancing together.

Scenario 2 — One seat remains in a required course

Two authenticated students submit enrollment requests close together. Each browser may optimistically show an available seat, but that observation cannot enforce capacity. The application must authenticate the caller, authorize the operation, and coordinate a transaction against authoritative enrollment data. If one client times out after the server commits a successful enrollment, retrying without reconciliation could create a duplicate side effect. Compare Client-Server Authentication and Authorization, Session and State Management, and Client-Server Reliability Patterns.

Scenario 3 — One application instance fails during a traffic surge

Imagine three instances that can each serve 80 requests per second for a representative test workload. Their combined nominal capacity is 240 requests per second, ignoring load imbalance and shared bottlenecks. Losing one reduces the nominal total to 160 requests per second, so a service expecting 200 requests per second may become overloaded even with a functioning load balancer. Real capacity also depends on response-time targets, database limits, and safety headroom. Study Server Load Balancing, Client-Server Performance and Observability, and Client-Server Reliability Patterns.

Scenario 4 — The browser reports a failed request, but the server looks healthy

A student reports that a course-catalog page intermittently stalls. The investigator separates browser rendering problems from DNS failures, TLS validation, proxy timeouts, application errors, and downstream database delays. A successful port connection does not establish successful application processing; a server average latency does not reveal all slow-tail requests. Relevant evidence may include a browser network timeline, gateway status, request identifiers, application logs, and traces. Follow DNS and Service Endpoints, TLS and Secure Client Connections, Client-Server Performance and Observability, and Client-Server Deployment and Troubleshooting.

All four scenarios are constructed educational illustrations, not claims about MGU production systems or observed institutional incidents.

Operational principle: specify the authoritative owner of each resource, the identity and privileges of each caller, the meaning of each operation, the behavior of the network under failure, and the evidence needed to verify the design. Record workload assumptions before asserting capacity or availability.

Suggested Study Pathways

Foundations for new readers: Begin with the parent overview and then build a request from endpoint identity through network exchange and secure transport. Read Client and Server Roles, DNS and Service Endpoints, HTTP Request and Response Lifecycle, HTTP Versions and Transport, TLS and Secure Client Connections.

Web and API developers: Concentrate on layered application responsibilities, client state, authorization, and the compatibility promise of a published service interface. Read Two-Tier and Three-Tier Systems, Session and State Management, Client-Server Authentication and Authorization, API Contracts and Service Versioning.

Platform and cloud engineers: Follow the entry path through proxies, replicas, caches, and service failure; compare architecture choices against actual traffic and operational maturity. Read Reverse Proxies and API Gateways, Server Load Balancing, HTTP Caching and Content Delivery, Client-Server Reliability Patterns.

Security and privacy readers: Trace separate security boundaries—channel integrity, caller identity, access rights, and response storage—rather than assuming HTTPS protects every application action. Read TLS and Secure Client Connections, Reverse Proxies and API Gateways, Client-Server Authentication and Authorization, Session and State Management, HTTP Caching and Content Delivery.

Operations and incident response: Learn to distinguish failed requests from ambiguous completion and to isolate latency or availability problems with evidence from each system layer. Read Client-Server Reliability Patterns, Client-Server Performance and Observability, Client-Server Deployment and Troubleshooting, Server Load Balancing.
