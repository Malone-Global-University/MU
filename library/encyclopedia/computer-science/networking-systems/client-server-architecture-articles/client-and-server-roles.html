Roles Belong to Interactions

A client invokes an operation offered through an interface. A server implements or mediates that operation and communicates its outcome according to the interface contract. The useful unit of analysis is a particular exchange between participants. A browser is the client when it asks a catalog service for an item. The catalog service is the client when it asks a database for the corresponding record.

A host provides a place to run software. A process executes software, and an instance is a running copy of a workload. A service is a capability exposed through a defined interface. Several instances may provide one service, a single process may offer several interfaces, and participants on the same host can still use a client-server interface. Network addresses, names, and ports help locate endpoints. The interface describes what operations those endpoints accept and what the outcomes mean.

When analyzing a system, name both participants, the operation, and the relevant protocol. “The catalog API is an HTTP server for product reads” is more specific than “the API is a server.” “The catalog API is a database client for product lookup” identifies another responsibility of the same workload.

Client-side validation improves responsiveness. Server-side validation enforces the policy for every caller. For example, a registration screen can disable submission for an invalid date, while the registration service checks eligibility and enforces uniqueness when it accepts a write. Two clients can both display an available slot before either submits. The system that owns the booking invariant must decide which submission commits.

Roles Across Layers and Connections

Application roles describe the exchange understood by the application protocol. Transport state describes how bytes or messages move. For a conventional HTTP connection over TCP, the client commonly initiates the connection and the server accepts it. Once the connection is established, TCP carries bytes in both directions. The application protocol supplies the meaning of those bytes, including which message is a request and which is a response.

A connection can carry several application exchanges over its lifetime. HTTP/2, for example, permits concurrent exchanges on separate streams within one connection. A connection count can therefore differ sharply from a request count. When measuring load, choose the unit that represents the resource you are sizing, such as concurrent streams, queued requests, or active database transactions.

Message direction alone is insufficient to classify roles. A subscription server can send updates after a client subscribes. A caller that exposes a callback endpoint takes the server role when another participant invokes that endpoint. In a peer-to-peer design, a peer can request a data block in one exchange and supply a block in another. Describe each exchange according to the protocol it actually uses.

Intermediaries and Delegated Work

A reverse proxy that terminates an inbound HTTP exchange and forwards a request acts as an HTTP server to the inbound client and as an HTTP client to the upstream service. Those two exchanges can have different connections, time budgets, and authentication requirements. A cache may answer an eligible request without contacting the origin. A transport-level relay can forward traffic without taking the same application responsibilities as an HTTP proxy.

A forwarded request also raises an identity question. The immediate calling process and the user on whose behalf it acts can have different identities. An API should apply a defined policy for accepting delegated identity and authorize the requested operation at the appropriate boundary. Recording the immediate caller and the authorized user context helps explain decisions and trace failures across hops.

An Analytical Model for Role Assignment

Describe an exchange with five fields: initiating participant, receiving participant, protocol, requested operation, and observation boundary. The same two services can reverse roles on separate exchanges. A warehouse service can accept a stock query from an order service and later initiate a callback to report that promised stock is available. The two exchanges have independent credentials, deadlines, response semantics, and failure records.

Assign roles at the smallest boundary that preserves the question you want to answer. For user experience, a browser and a public endpoint may suffice. To explain an intermittent timeout, draw every terminating intermediary and dependency that can queue, reject, or acknowledge the operation. Include where work crosses from one administrative domain into another.

Interface Contracts and Endpoint Identity

An endpoint describes where a participant sends an exchange. The interface contract describes the operations offered there and how callers interpret their outcomes. A hostname may resolve to multiple addresses, and a single address can serve multiple authorities. Routing by authority and application path can lead to different handlers through the same gateway.

Separate the public service identifier from a particular replica and from the identity authenticated on a connection. A connection to a gateway proves the identity established for that hop under its authentication configuration. Any claim about the origin service or end user needs a chain of trust appropriate to the deployment. Record which component checks each identity and what context it passes onward.

Client Responsibilities Across Different Applications

A browser coordinates navigation, renders representations, and applies user-agent policies. A command-line client may expose exit status and machine-readable output for automation. A batch worker optimizes throughput and tracks checkpoints. A mobile client can persist drafts and synchronize them after connectivity returns. All these clients invoke interfaces, but their local state and recovery obligations differ.

For an offline-capable application, distinguish draft state, pending submission, acknowledged submission, and reconciled authoritative state. Showing a pending operation as confirmed can cause users to act on information the service has never accepted. An explicit pending state lets the client preserve useful local work while accurately representing uncertainty.

Server Responsibilities and Invariants

A server publishes operations, parses requests, validates input, applies authorization, coordinates dependencies, and produces defined outcomes. Business invariants belong at the boundary that can enforce them across all competing requests. For a booking service, an availability check can help shape the response, while a transaction or constraint at the authoritative write boundary prevents two claims on the same resource.

A service can delegate persistence or computation and still own the outcome it promises. If the public response says that the reservation is confirmed, the server needs evidence of the required commit. If the service promises queued processing, its contract should identify what acceptance means, how results become observable, and how long status remains available.

Frontends, Gateways, and Backends

Frontend and backend describe placement in a system design. Client and server describe participation at an interface. A server-side rendering process is a server to a browser and a client to a content API. A gateway can apply routing and admission controls while leaving application-specific checks to the service with access to the relevant policy and resources.

Map identity and request context across each terminating hop. A gateway may have authenticated a device, while the underlying service needs a verified user identity and operation-level permission. Record the credentials expected on each hop and the source of any delegated claims. This makes the policy testable even as more calling applications are introduced.

Connections, Requests, and Streams

A socket, connection, stream, and request describe different kinds of state. A connection can carry multiple sequential requests or support concurrent streams, depending on the protocol. A connection may also survive a failed request. Count the objects associated with the resource under investigation, such as TCP connections for socket pressure and active application requests for handler saturation.

Server-sent events deliver data through a continuing HTTP response. A WebSocket session can support bidirectional application messages after establishment. For either design, define who may initiate business operations, how messages correlate with results, and what reconnection means for outstanding work. Connection establishment alone cannot express those application policies.

Acceptance, Completion, and Visibility

An operation can pass through transport delivery, parsing, admission, execution, commit, response delivery, and client observation. Each boundary exposes different evidence. TCP acknowledgment concerns receipt of bytes by a peer's TCP implementation. A successful HTTP response communicates an outcome defined by the HTTP method, status, and application contract.

An HTTP 202 response indicates acceptance for processing while completion remains pending. Applications commonly expose a job identifier and a status resource to make eventual outcomes visible. Even a confirmed write can take time to appear through read replicas or cached views. A contract should identify the view against which a write is confirmed and any guarantees for subsequent reads.

Replicas, Sessions, and Shared State

Multiple service instances can share a service identity. If one instance stores an interaction's session only in local memory, a follow-up request routed elsewhere can lose that session. Sticky routing can reduce that risk during routine operation, but restart and failover still need defined behavior. Shared session storage shifts the dependency to a separate service. Self-contained credentials have their own expiry, revocation, and key-management trade-offs.

Decide which state must survive replacement of any individual instance. Distinguish durable business records from transient connection state, recomputable caches, and resumable user context. Then decide which timestamp, sequence, or version token can establish whether two observations concern the same state.

Timeouts, Retries, and Cancellation

A timeout is a local observation. The remote side might have rejected the request, queued it, completed it, or lost the response. Retry only according to the operation's contract. Method idempotence concerns the intended effect of repeated identical requests. A service that supports retrying writes may define an application-specific deduplication identifier with bounded scope and retention.

Cancellation requests can release resources when work is interruptible. Once a write has committed, undoing its effect requires a separate operation with its own authorization and business rules. Propagate remaining time budgets where supported and avoid letting independent retry loops amplify a slowdown across successive service boundaries.

Capacity, Queues, and Backpressure

Servers typically have limits at connection admission, request queues, handler pools, and dependency pools. Clients can contribute by bounding concurrent requests and pacing retries. Dropping excess work early can protect already-admitted operations when queues approach their latency budgets. The caller needs enough information to distinguish a temporary admission failure from a permanent input error.

Measure queue time and execution time independently. A fast handler can sit behind a long queue, and a low average can mask bursts. Throughput should capture successful useful operations. A service seeing many duplicate attempts may report high request throughput while completing relatively few distinct operations.

Correlation and Observability

A trace identifier correlates activity across hops, while a span identifier identifies a specific step. An operation identifier or idempotency key can retain meaning across separate attempts when the application contract says so. These identifiers answer different questions. Two attempts can have different trace and connection identifiers while referring to a single intended write.

When diagnosing an incident, identify the observation boundary first. Compare caller-side latency, gateway admission, origin execution, and dependency state. Use correlated records to reconstruct ordering when clocks differ. Avoid inferring global order solely from timestamps captured on separate machines.

Verification and Contract Testing

Build a role matrix for each operation and include callers, interfaces, identity checks, state owners, and promised outcomes. Test each client against supported representations and errors. Exercise duplicate attempts, stale reads, connection loss, failover, partial responses, slow dependencies, and deployment skew between client and server versions.

For a deduplicated write, verify that two simultaneous requests for the same scoped identifier cannot commit twice, that repeated identifiers with incompatible inputs receive the documented outcome, and that recovery after restart preserves the promised guarantee. For a read cache, verify how freshness, authority, and any user-specific representation affect cache reuse.

Worked Example 1 — Reserving a Library Book

A library portal exposes an operation for reserving an available copy. The browser sends the member's request to a gateway. The gateway forwards it to the reservation service. The service commits the result through a database transaction and returns a reservation identifier.

Role assignments for the reservation operation
ExchangeClientServerResponsibility at this boundary
Portal requestBrowserGatewaySubmit the request and return the public response.
Reservation operationGatewayReservation serviceForward the request with authorized context and apply reservation rules.
Transactional writeReservation serviceDatabasePersist the result and enforce the data constraints that prevent double booking.

If the database commits and the reply is lost, the browser experiences a timeout while the reservation may already exist. A design can allow the browser to repeat the same operation using a request identifier. The reservation service can associate that identifier with the committed result and return the same reservation identifier on repetition. Recording the identifier and result atomically with the reservation avoids a gap in which the write succeeds but a retry appears new. The contract also needs to define identifier scope, handling for a different payload under the same identifier, and the retention window.

Suppose the portal gives the gateway two seconds to respond. If one downstream call consumes 1.5 seconds, a new two-second downstream timeout can overrun the original budget. Propagate the remaining budget where supported. Treat client cancellation as a request to stop work where possible, while separately handling operations that have already committed.

Worked Example 2 — A proxy serves a fresh cached response

A browser requests a public representation with a fresh cached copy on the edge. The edge returns the stored representation and the origin receives no corresponding request.

Role analysis. The edge serves this exchange. It takes an upstream client role when it fetches or revalidates a representation.

Verification. Compare edge cache records and origin request counts for the same observation interval. A gap between them can reflect legitimate cache hits.

Worked Example 3 — A callback reverses the roles

A scheduling service accepts a job from a reporting service and stores a callback URL supplied through an approved configuration. When work completes it calls the reporting service.

Role analysis. The scheduling service first serves the submission and later becomes the client for delivery. The reporting service has to serve and acknowledge the callback independently.

Verification. Track job completion and callback delivery separately. A completed job can have a failed callback, which requires its own retry and deduplication behavior.

Worked Example 4 — An asynchronous submission returns HTTP 202

A caller submits a report. The public service responds with a job identifier after admitting the work. A later status query reports that execution failed.

Role analysis. The submission, status query, and worker execution are distinct interactions. Successful admission and eventual execution have separate outcomes.

Verification. Verify the contract for status polling and use the job identifier to join the two results.

Worked Example 5 — A timed-out write is repeated

A call commits an inventory adjustment, but its response is lost. The caller retries with the same operation identifier under a documented retry contract.

Role analysis. The server returns the recorded adjustment result. The client can reconcile its pending state with that authoritative outcome.

Verification. Compare write records across both attempts. The expected result is one adjustment and a stable result identifier.

Worked Example 6 — A session disappears after failover

Instance A creates a session in local memory. A subsequent request reaches instance B after instance A exits.

Role analysis. The service still has reachable replicas, but the new instance lacks the session state required to continue the user interaction.

Verification. Test forced instance replacement with a live test session. Inspect session persistence and the documented reauthentication or recovery path.

Worked Example 7 — A request budget is consumed by a dependency

A client allows 900 ms. The gateway consumes 100 ms before forwarding, and the service uses another 500 ms before a dependency call starts.

Role analysis. At most 300 ms remains, including return-path and response work. Each hop manages a portion of the same end-to-end budget.

Verification. Compare correlated timings and configure the downstream call to fit the remaining time. Handle late completion independently of the caller deadline.

Worked Example 8 — A connection count hides handler pressure

Forty clients each hold one HTTP/2 connection and each starts ten concurrent exchanges.

Role analysis. The connection count is 40, while up to 400 exchanges can be outstanding in this simplified example if limits admit them.

Verification. Inspect concurrent streams and admitted requests alongside the number of sockets. Instrument any dependency pool that handles the admitted work.

Worked Example 9 — A replicated read trails a confirmed write

A service acknowledges a write committed to its authoritative database. A subsequent query goes to a replica that has not caught up.

Role analysis. The write and read have different observation points. The read contract determines whether older state is permitted.

Verification. Compare observed record versions. If the application promises read-your-writes, route or coordinate reads to satisfy that promise.

Worked Example 10 — Retries multiply across hops

A client allows up to three attempts against a gateway. The gateway permits up to two origin attempts per client attempt.

Role analysis. The origin could see up to six attempts for one user operation under these simplified limits. A slow dependency can make retries add to existing queue pressure.

Verification. Correlate user operations with attempts. Place retry responsibilities where the operation contract and remaining time budget can be evaluated.

Worked Example 11 — A cached login state goes stale

A mobile client shows a previously cached account view. The server declines a new write because the credentials have expired.

Role analysis. The client owns the local representation, and the service decides access to the protected operation at the time of the request.

Verification. Allow reauthentication and reconcile pending work after the server accepts it. Check the authoritative result before showing it as completed.

Mapping a Service Boundary

  1. Choose one operation and list the initiating participant and the endpoint that accepts it.
  2. Record the interface, expected outcomes, and the owner of each state change.
  3. Repeat the mapping for every dependency contacted while carrying out the operation.
  4. Identify where authentication is established, where authorization is enforced, and how delegated identity is represented.
  5. Trace one successful exchange and one ambiguous outcome, such as a timeout after a write. Define what the caller can verify and what it can safely retry.
  6. Record measurements at each boundary so user-visible latency can be compared with queue time, processing time, and dependency latency.

A boundary map can also distinguish availability from correctness. A gateway may accept connections while its upstream service is unavailable. A successful transport exchange can carry an application rejection. Inspect the returned outcome and the relevant service records before inferring where the operation failed.

Review Questions

Which role does an API process play when it receives a browser request and queries a database?

It serves the browser-facing request and acts as a client for the database exchange. Each role has its own interface and failure conditions.

Why must a shared booking rule be checked where authoritative state changes?

Different clients can see the same earlier state. The authoritative write boundary can enforce the booking rule across concurrent submissions.

What does a client timeout establish about a remote write?

It establishes that the caller did not obtain the expected result within its deadline. A status lookup or a documented deduplication mechanism can help determine whether the write committed.

Specialist Glossary

Admission
Acceptance of work into a processing boundary under its resource and policy limits.
Authority
The entity or identifier responsible for a named resource or protocol namespace, as defined by the context.
Backpressure
Feedback that prompts a producer to adjust its sending rate or outstanding work.
Callback
A separate invocation directed to an endpoint supplied or selected for later notification.
Client
The initiator of an operation in a specified exchange.
Commit
The point at which a state change becomes established under the relevant storage or transaction guarantees.
Connection
A protocol association that can carry exchanges or streams.
Deadline
The time limit for the caller to obtain or await an outcome.
Delegation
Authority for one participant to act with a defined scope on behalf of another.
Endpoint
A destination or exposed interface used to send an exchange to a participant.
Idempotence
The property that repeating an operation has the same intended effect as applying it once, under its contract.
Intermediary
A participant between caller and origin that forwards, serves, or otherwise handles an exchange.
Origin server
The endpoint responsible for the target resource in HTTP terminology.
Replica
An instance or copy that participates in serving a workload or storing its data.
Request correlation
Identification of records or messages that concern the same exchange or operation.
Service
A capability exposed through an interface.
Server
A participant that handles operations offered at a specified interface.
State owner
The component or coordinated boundary that enforces authoritative state transitions.
Stream
A sequence of data or messages with identity and ordering rules defined by its protocol.
Timeout
A local outcome indicating expiration of a waiting period.
