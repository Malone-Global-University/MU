Definition and Scope

A binary file header is the opening region, or a format-defined region near the opening, of a byte sequence that supplies information required to interpret the rest of the file. A magic number or file signature is a recognizable sequence of bytes used by a format to signal its identity or family. Although the phrase magic number is historical, a signature need not be numeric: the four ASCII characters RIFF, the nontextual eight-byte PNG signature, and the sixteen-byte SQLite signature are all recognizable byte sequences. A header may also specify a format revision, byte order, total length, record counts, internal offsets, dimensions, or options governing subsequent parsing.

The distinction is fundamental: recognition is not validation. Finding the expected bytes near the beginning establishes a candidate format. It does not prove that subsequent lengths are consistent, chunks are in the required order, data is intact, a checksum is correct, or the file is safe to process. A filename extension is even weaker evidence because it is external metadata that can be changed without modifying the file. An effective reader combines signature recognition with format-specific validation and clearly bounded decoding.

Why Headers Exist

Computers store and exchange bytes; bytes alone cannot tell a reader whether a payload holds compressed pixels, a database page, an executable image, or sensor measurements. A header provides a contract for interpretation. The contract may be defined by a published standard, a vendor specification, an application, or an agreement among producers and consumers. Its role is to establish the layout before a parser performs operations whose meaning depends on that layout.

Headers reduce ambiguity in three complementary ways. Identification indicates which format family might apply. Structural description gives the layout: field widths, offsets, lengths, counts, flags, and expected sections. Compatibility signaling allows a reader to decide whether it understands the version and mandatory features. Some formats supply very little information in their headers and require extensive conventions outside the file; others carry rich descriptors or directories. Neither approach exempts the reader from validating the rest of the object.

Consider a sensor archive with several hundred records. If the first bytes describe version, width, sample type, and byte order, independent software can decode the archive without knowledge of its original programming language or machine architecture. Conversely, if the file contains a raw memory image of a compiler-specific structure, a recognizable initial marker may not make the layout portable. Reliable interchange requires a byte-level specification, not merely a signature.

Identification Versus Interpretation Versus Trust

A useful three-stage model separates candidate detection, format validation, and authorization to act. Detection answers “does this file begin like a recognized format?” Validation asks “does the complete relevant structure satisfy the format's rules and the application's resource limits?” Authorization asks “may this particular validated object be opened, displayed, executed, imported, or used as evidence in this context?” These are separate decisions.

For example, a file with bytes 89 50 4E 47 0D 0A 1A 0A is plausibly a PNG datastream. A PNG reader must still verify that the next chunk is IHDR, parse the required fields, enforce legal values, process chunk boundaries and integrity checks, and reach the valid conclusion of the datastream. Even a fully valid image may be untrusted user input that must be handled by a constrained decoder. A successful magic-number match grants no immunity from malformed data or malicious content.

Decision Evidence it uses What it establishes What it does not establish
Extension check .png, .db, .gz, .exe A name-based hint Actual format or correctness
Signature match Defined bytes at a specified location Candidate format family Complete validity
Header parse Version, flags, lengths, offsets Initial structural consistency Validity of all payload data
Full format validation Required sections, limits, checks, relationships Compliance with tested rules Authenticity or suitability for execution
Cryptographic verification Trusted key, signature or MAC, signed scope Integrity/authenticity within its trust model Safety of the program or semantic quality of content

A checksum helps detect many accidental changes; it is not a substitute for a cryptographic signature or message authentication code. Similarly, antivirus classification, MIME type, and an operating system's file association are additional layers of evidence, not alternate definitions of the binary format.

Magic Bytes as Exact Sequences

A magic sequence is best documented as bytes in hexadecimal at an exact offset, not as a vague human-readable string. If the specification states 4D 47 55 31, the reader should compare four bytes in that order. It should not decode arbitrary bytes using an unspecified text encoding and compare the resulting characters. ASCII-derived signatures are common because they are easy to recognize in a hex dump, but other formats use deliberately nontextual values.

The term number should not induce an endianness conversion. A four-byte signature such as 4D 47 55 31 is a sequence, not necessarily a 32-bit integer. Comparing it as an integer can produce different values on big-endian and little-endian machines if the programmer relies on native memory interpretation. Comparing it as four bytes avoids that mistake. By contrast, a four-byte payload length immediately after the signature is a numeric field and requires an explicit byte-order rule.

Not every format begins at offset zero, and not every recognizable marker uniquely identifies a single variant. Some formats embed a signature after a bootstrap structure; some use a common container header followed by a format-specific subtype. File identification should therefore specify where to look, how long to inspect, and what additional evidence is required.

Common Header Fields and Their Semantics

A file format can define fields in any order, but recurring header components include a signature, revision or compatibility value, header length, payload length, flags, record count, type code, section directory, and optional integrity information. These should be expressed as a field map rather than inferred from a program's in-memory structure.

Field Typical purpose Essential design question
Magic/signature Distinguish a format family Exact bytes, width and location?
Major/minor version Control compatibility rules Which versions and features are supported?
Header length Identify where the payload starts Does the length fit in the file and meet a minimum?
Payload length Bound subsequent reads Does the declared extent fit within remaining bytes?
Count Describe number of records Can count × record size overflow?
Offset Locate a table or section Is the offset relative to file, header or parent chunk?
Flags Select optional interpretations Are reserved and incompatible bits rejected?
Format/type code Describe payload encoding Is the code legal for the declared version?
Checksum or digest Detect particular classes of corruption Which bytes are covered and which algorithm applies?

A reader should not treat every field as authoritative simply because it appears in a header. Header values are themselves input and require type, range, ordering, and cross-field checks. Versioning rules may change the meaning of a field; optional sections may change the true header length; an offset may be relative rather than absolute. These are matters for the format specification, not guesses by a generic parser.

A Byte-Exact Fictional File Format

To make the principles concrete, define a deliberately simple fictional MGU1 measurement file. It is not an existing industry standard. Its fixed header is 16 bytes, followed by an opaque payload of exactly the length specified in the header. All multibyte numeric fields are unsigned big-endian integers. The header contains a four-byte signature, one version byte, one flags byte, a two-byte header length, a four-byte payload length, and a four-byte record count.

Byte offsets Width Field Encoding Requirement
0–3 4 bytes Signature 4D 47 55 31 (MGU1) Exact sequence
4 1 byte Major version uint8 Must equal 01 in this edition
5 1 byte Flags uint8 Must equal 00; other bits reserved
6–7 2 bytes Header length uint16, big-endian Must equal 0010 hex (16 decimal)
8–11 4 bytes Payload length uint32, big-endian Must fit available bytes and policy
12–15 4 bytes Record count uint32, big-endian Domain rule defined by payload schema
16… Variable Payload Opaque bytes Exactly the declared payload length

The format here intentionally says only how to frame the opaque payload; it does not claim that the record count can be verified without a record schema. A separate specification might declare fixed-size records, variable-length entries, compression, or data types. The format's version-1 flags remain zero so no reader must guess the meaning of unknown options. Future expansion would require an explicit revised contract.

Worked Hex Dump: Recognize and Frame a File

Suppose a twelve-byte payload represents three illustrative four-byte records, and the entire file is twenty-eight bytes. The header and payload might begin as follows; offsets are hexadecimal byte positions.

Offset   Bytes                                                 Meaning
000000   4D 47 55 31  01 00  00 10  00 00 00 0C  00 00 00 03  16-byte header
000010   10 20 30 40  11 21 31 41  12 22 32 42              12-byte payload

Read the fields in sequence: 4D 47 55 31 identifies the fictional MGU1 format; 01 declares major version 1; 00 leaves flags clear; 00 10 represents decimal 16; 00 00 00 0C represents decimal 12; and 00 00 00 03 represents decimal 3. The payload begins at offset 16 and spans bytes 16 through 27 inclusive. The file is exactly 16 + 12 = 28 bytes. Nothing in the header alone tells us the semantic meaning of 10 20 30 40 unless the payload schema specifies it.

If the file instead contains only ten payload bytes, the signature and every field of the fixed header still look well formed, but the file is truncated. If the header declares a payload of billions of bytes and the physical file is tiny, the parser must reject the file before allocation. If it declares a version not understood by the reader, a policy of “try anyway” is unsafe unless the specification explicitly defines backward-compatible parsing rules.

Boundaries: Header Length, Payload Length, and Total File Size

A byte parser must distinguish available size from declared size. Available size is the number of bytes actually present in the bounded input; declared size comes from the file and is potentially false or malicious. In the fictional format, the reader begins by requiring at least sixteen available bytes before accessing the fixed header. It then validates the signature, version, flags, and header-length field. Only then should it treat the remaining declared length as a candidate payload extent.

For a file with N available bytes, fixed header H = 16, and payload length L, the essential length check is L ≤ N − H, provided N ≥ H. The subtraction-based form avoids an overflow hazard inherent in blindly computing H + L using narrow fixed-width integers. If the format requires exact file consumption, also require L = N − H. Some formats deliberately allow trailers, concatenated members, or external padding; their specifications define the correct policy.

A header can include multiple sections with lengths and offsets. Each section must be validated individually and sometimes collectively: range overlap may be illegal, table order may be constrained, and one count may be required to equal another. A single “file length is large enough” check is insufficient if an internal offset points into the middle of another record or the section directory points outside the file.

Offsets, Tables, and Relative Addressing

Complex formats use tables rather than sequential layouts. A header may point to a section directory; each directory entry may identify a type, file offset, stored length, decompressed length, and flags. This permits readers to skip unneeded sections and locate content without scanning every preceding byte. It also creates more opportunities for malformed or ambiguous offsets.

An offset has meaning only with a declared origin: file start, payload start, chunk start, or another absolute/relative base. A file-relative offset of 64 designates byte 64 from the start; a chunk-relative offset of 64 designates byte 64 from that chunk's defined base. Readers must not mix the two. An offset into the header may or may not be legal depending on the format, and identical offsets for two sections can signal shared data, aliasing, or corruption.

For every table reference, independently verify the table's own position, the width of each entry, the count, the multiplication entry_count × entry_size, and the location of every referred-to section. On finite-width integers, compute these relationships without overflow, preferably using a wider checked arithmetic type or subtraction-based bounds logic. Document whether overlapping ranges are allowed and whether multiple sections may refer to the same payload bytes.

Version Fields and Feature Negotiation

Version fields are conventions, not universal guarantees. Some formats use a major/minor version; others use feature flags, identifying subtype fields, or a combination. A parser needs a compatibility policy: which old versions it accepts, whether unknown optional features can be skipped, and which unknown critical features require rejection. A version label alone says nothing about compatibility without a specification.

Designing a format to extend safely often requires a header-length field, explicit reserved bits, or typed length-delimited extensions. If a version-1 reader accepts later files with the same fixed header, the later specification must ensure that new mandatory information cannot be silently ignored. In the MGU1 example, major version 01 and zero flags are required, and 00 10 fixes the header length. A future MGU2 could choose a distinct signature or version value and define a new layout, but the version-1 parser should not speculate about its semantics.

Reserved fields are not invitations for arbitrary use. Writers should set them to specified values; readers should enforce the required rules or follow the standard's explicit ignore policy. Otherwise, incompatible producers may create equally plausible but semantically different files that cannot be reliably decoded by independent implementations.

Flags, Bitfields, and Optional Sections

A flags byte or word compresses several binary choices into one field. A format might use bit 0 to indicate compression, bit 1 to indicate a checksum, and bit 2 to indicate an optional metadata block. Those meanings are only examples; real meaning comes from the specification. Masks describe which bits are allowed, while reserved-bit tests identify unsupported or malformed combinations.

Consider an eight-bit flags value of 0xA0 when only low three bits are defined. If reserved bits must be zero, the reader should reject it because 0xA0 & ~0x07 is nonzero within the eight-bit width. A reader should also validate whether combinations are legal. Compression and encryption might be individually supported but disallowed together for one version; a manifest section might be mandatory when a corresponding flag is set.

Optional fields change parsing offsets. A parser must not assume a fixed payload start if the header length depends on flags, optional metadata, or variable-length strings. A robust parser first validates the fixed preamble, then parses extensions under their declared bounds, and only then locates the payload. Misreading one optional field can shift every subsequent offset, yielding plausible but incorrect values.

Header Integrity: Checksums and Their Limits

Some headers store a checksum, cyclic redundancy check (CRC), digest, or a redundant copy of important metadata. These detect different kinds of corruption. A CRC is valuable for ordinary transmission or storage errors and can be computed efficiently; it is not a cryptographic authentication mechanism. An adversary who can change the data can generally recompute an ordinary checksum. A cryptographic signature or message authentication code requires a defined trust model and verification procedure.

The reader needs to know exactly which bytes are covered by an integrity field. In PNG, each chunk carries a CRC over the chunk type and chunk data, not over the four-byte chunk-length field. RFC 1952 defines a gzip trailer containing a CRC-32 of the uncompressed data plus its size modulo 2^32; gzip may also carry an optional header CRC field under a flag. These are different integrity scopes and must not be conflated. See the PNG specification and RFC 1952.

A good parser checks integrity in addition to structural bounds. But even a verified CRC does not establish that image dimensions are sensible, the decompressed size is acceptable, or a document's content is trustworthy. Integrity, structure, authenticity, and business meaning occupy distinct validation layers.

Case Study: PNG Signature and Chunk Structure

The PNG signature consists of eight bytes: 89 50 4E 47 0D 0A 1A 0A. The non-ASCII first byte, line endings, and other fixed values help detect some unintended conversions. In the PNG datastream format, the signature is followed immediately by an IHDR chunk. A chunk is framed by a four-byte big-endian data length, four-byte type, the declared number of data bytes, and a four-byte CRC. The IHDR chunk's data length is exactly thirteen bytes. A valid datastream contains required image-data structure and terminates with an IEND chunk.

PNG datastream opening (schematic)
89 50 4E 47 0D 0A 1A 0A   signature
00 00 00 0D               IHDR data length = 13
49 48 44 52               chunk type = "IHDR"
[13 bytes of IHDR data]    width, height, format parameters
[4 CRC bytes]              CRC over type + data, not length
[next chunks ...]

A parser that stops after checking eight magic bytes has not established PNG validity. It must ensure there are enough bytes for each length and CRC, that the IHDR fields are legal, that chunk-order and multiplicity rules are respected, that data does not exceed configured resource limits, and that the datastream ends correctly. The W3C PNG Third Edition is a normative source for these rules. This article does not attempt to reproduce every PNG chunk or decoder requirement.

Case Study: Gzip Preamble and Optional Fields

The gzip format described by RFC 1952 begins each member with a fixed part of the header: identification bytes 1F 8B, a compression-method byte (08 means DEFLATE), a flags byte, a four-byte modification time, a hint byte, and an operating-system byte. The fixed part is ten bytes, but optional fields may follow. A reader must inspect the flags before deciding where the compressed data begins.

Position  Field                         Bytes/meaning
0–1       Identification                1F 8B
2         Compression method            08 for DEFLATE
3         Flags                         optional-field indicators
4–7       Modification time             uint32 little-endian
8         Extra flags                   method-dependent hint
9         Operating system              format-defined code
10…       Optional header fields        present according to flags

An FEXTRA field includes a length and data; FNAME and FCOMMENT are NUL-terminated if present; FHCRC introduces an optional two-byte CRC16 derived from the header. Reserved flag bits must be zero. The gzip member also contains compressed data and an eight-byte trailer. Multiple gzip members may be concatenated. Consequently, a parser that treats all gzip files as one ten-byte header plus a single compressed stream may accept or misread invalid input. Consult RFC 1952 for the exact format and field semantics.

Case Study: SQLite Database Header

The SQLite version-3 database file has a sixteen-byte opening signature: the ASCII text SQLite format 3 followed by a zero byte. The complete database file header occupies 100 bytes at the start of page 1. Further fields encode page size, format-version markers, in-header statistics, text-encoding designation, and other database metadata. In this case, the initial signature is a strong identification cue, but correctly interpreting the database requires page structures and consistency rules far beyond the initial sixteen bytes.

53 51 4C 69 74 65 20 66 6F 72 6D 61 74 20 33 00
 S  Q  L  i  t  e     f  o  r  m  a  t     3  NUL

A file that begins with the signature but lacks 100 bytes cannot satisfy the ordinary file-header requirements for a valid SQLite database. Conversely, copying 100 apparently plausible bytes into a file does not make the b-tree pages consistent. SQLite's official Database File Format documents the fields and their validity conditions. The subject of database page structure belongs primarily to the Databases unit.

Case Study: Executable Formats and Offset Signatures

Executable formats demonstrate why a magic value may be only the first step of a multi-location header lookup. ELF begins with the four-byte identification sequence 7F 45 4C 46 (0x7F and ASCII ELF), followed by an identification array describing class, data encoding, and other properties. Windows Portable Executable (PE) files ordinarily begin with a DOS-compatible MZ header; a field conventionally named e_lfanew points to the later PE 00 00 signature. The parser must therefore validate an offset before reading another identifying marker.

A careless PE recognizer that accepts any MZ prefix or blindly follows an unbounded e_lfanew value risks misclassification and out-of-range access. A correct reader validates all necessary bounds and PE/COFF structural fields using the official Microsoft PE format specification. ELF readers must similarly honor the declared class, endianness, and header-table constraints under the System V generic ABI.

Identification is not permission to execute a file. Opening or disassembling bytes for inspection is distinct from invoking an operating-system loader. Filename, magic bytes, and executable-file validity do not alone establish publisher authenticity or safety.

Case Study: RIFF Containers and Form Types

The Resource Interchange File Format (RIFF) illustrates family signatures rather than a single content identity. Common RIFF files start with four bytes spelling RIFF, then a four-byte little-endian size field, then a four-byte form type, such as WAVE for waveform audio or AVI for an AVI-form video container. RIFF identifies a container family; the form type identifies a particular kind of RIFF data. The four spaces/characters and their exact offsets matter because header fields are byte sequences, not a human-friendly title.

It follows that a detector cannot reliably label a file “WAV audio” merely because its first four bytes read RIFF. It must inspect the form type and confirm the expected chunk layout. RIFF variants and extended-size conventions have their own rules; some RIFF-derived formats use large-size mechanisms rather than fitting every file into the original 32-bit size model. Readers should follow the specific subtype specification rather than applying a universal “first eight bytes determine everything” heuristic.

This case also shows why byte order must be declared per format: the RIFF size uses little-endian interpretation, whereas PNG chunk lengths are big-endian. The presence of alphabetic ASCII identifiers in both formats does not imply that their subsequent integers use the same ordering.

Case Study: ZIP, JPEG, and Detection Ambiguity

Not all common formats support a single unconditional starts-with test. ZIP archives commonly contain a local-file header signature 50 4B 03 04 (PK plus marker bytes), but robust archive discovery must account for the archive's directory structures and permitted surrounding material. A ZIP file may be empty or structured differently from a simple first-local-header example, and ZIP-based container formats may hold entirely different application content (for example, office documents). A reader needs ZIP format rules and container-level identity checks.

JPEG images commonly begin with the two-byte start-of-image marker FF D8, followed by other JPEG markers. Some files have application-specific APP marker segments such as JFIF or Exif, while others differ; a valid JPEG must not be defined by the presence of one optional APP marker alone. Similarly, the PDF format's %PDF- header is a useful clue but does not by itself demonstrate a parseable cross-reference structure, valid objects, or a consistent document. These examples emphasize that file detection operates at the precision allowed by the format, not at the convenience of a fixed list of extensions.

For security-sensitive uses, use a parser that understands the complete container, not just a signature table. Archive extraction in particular requires separate path, size, nesting, and decompression policies after basic format identification.

Headerless Formats and Embedded Payloads

Some binary structures do not have a distinctive magic sequence at all. A headerless raw audio stream, memory dump, fixed-width numeric table, or image buffer may require external metadata to decode. In such cases, the format contract may be supplied by a filename convention, MIME declaration, command-line argument, dataset manifest, database schema, or surrounding network protocol. It is a design mistake to invent a purported intrinsic signature from arbitrary initial sample bytes.

Another challenge is embedded data. A PNG file may be carried inside an archive, a network packet, or a larger resource container. A recognizer must know the beginning of the bounded substream and should not assume that offset zero in the containing object is offset zero in the embedded format. A signature appearing somewhere in a long file is not sufficient evidence that the file's outermost format is the inner format. Likewise, random data may contain short magic patterns by coincidence, particularly when scanning large quantities of bytes.

A responsible analysis should distinguish “a matching signature at a documented offset,” “a likely embedded object,” and “a fully validated standalone file.” These conclusions have different confidence levels and consequences.

Why Extensions and MIME Types Can Disagree

A filename extension is a label supplied through the filesystem naming environment; a MIME or media type is a label used in protocol and application contexts; a magic sequence is part of the byte content. They are not interchangeable. A user can rename picture.png to invoice.txt without changing the PNG signature, and a web server can supply the wrong media type for an otherwise ordinary file. Some containers deliberately share suffixes or signatures across variants, while some file associations use operating-system policy rather than any structural test.

Applications must decide which evidence governs each action. An upload pipeline might compare extension, declared media type, detected format, full decoder result, and permitted application policy. Conflicts should be handled deliberately rather than resolved by blind trust in one field. Detecting true format is also not necessarily sufficient to accept content; a service that accepts images may forbid extremely large dimensions, nested containers, executable resources, or unsupported animation features even in technically valid formats.

Where the service relies on content security, it should verify the format with the component that will actually process it rather than trust a shallow detector whose interpretation diverges from the downstream parser.

Parsing Steps for a Bounded Reader

A generic safe workflow begins with the fact that a file header is untrusted input. Parsing should use a known-size byte buffer or bounded stream, explicit field readers, checked arithmetic, and a state machine derived from the format's normative sequence. A useful design order is:

  1. Open the file as bytes without executing or rendering it.
  2. Determine available input length or establish streaming resource limits.
  3. Verify enough bytes exist for the smallest fixed preamble.
  4. Compare signature bytes at the location defined by the specification.
  5. Read version, flag, size, and offset fields using declared widths and byte order.
  6. Reject unsupported versions, illegal flags, impossible lengths, and out-of-range offsets.
  7. Parse optional extensions and section directories under their own bounds.
  8. Apply structural, checksum, and format-specific semantic rules.
  9. Decode payload data only within approved size, time, recursion, and memory limits.
  10. Report precise errors and keep raw evidence available where investigation requires it.

This order prevents the common mistake of allocating memory based on a claimed payload size before verifying that the claim is plausible and permitted. It also helps produce reliable error messages: unknown signature, unsupported version, truncated header, length exceeds available bytes, and checksum mismatch are different failures with different remediation paths.

Python Example: Validate the Fictional MGU1 Header

The following Python code parses the fictional format defined above, not a production protocol. It uses Python's struct facility and explicit size checks. A hard payload-size limit illustrates application policy, while an exact-consumption check enforces the simplified format's no-trailing-bytes rule.

from pathlib import Path
import struct

MAX_PAYLOAD = 16 * 1024 * 1024
HEADER_SIZE = 16


def parse_mgu1(data: bytes):
    if len(data) < HEADER_SIZE:
        raise ValueError("truncated fixed header")

    magic, version, flags, header_size, payload_size, records = \
        struct.unpack_from(">4sBBHII", data, 0)

    if magic != b"MGU1":
        raise ValueError("unexpected signature")
    if version != 1:
        raise ValueError("unsupported version")
    if flags != 0 or header_size != HEADER_SIZE:
        raise ValueError("invalid version-1 header")
    if payload_size > MAX_PAYLOAD:
        raise ValueError("payload exceeds application limit")
    if payload_size != len(data) - HEADER_SIZE:
        raise ValueError("truncated or trailing payload bytes")

    payload = memoryview(data)[HEADER_SIZE:]
    return {"version": version, "records": records,
            "payload_size": payload_size, "payload": payload}


sample = bytes.fromhex(
    "4D475531 0100 0010 0000000C 00000003 "
    "10203040 11213141 12223242"
)
parsed = parse_mgu1(sample)
assert parsed["payload_size"] == 12
assert parsed["records"] == 3
assert len(parsed["payload"]) == 12

The >4sBBHII format means big-endian, four literal signature bytes, two single-byte unsigned fields, one 16-bit unsigned field, and two 32-bit unsigned fields. The record count is returned but not interpreted: the example has not defined a record schema, so claiming the three records are valid would go beyond the information supplied by the header. Production code would also define file-opening policy, error reporting, and resource quotas for the containing application.

Windows PowerShell 5.1: Inspect and Parse Header Bytes

Windows PowerShell 5.1 can inspect a binary file without assuming text encoding. ReadAllBytes loads the entire file into memory and is appropriate for small, trusted-size demonstration files; for large or untrusted files, use a bounded FileStream read instead. The code below prints the first sixteen bytes when available and parses the fictional big-endian length fields by shifting individual bytes. It does not execute the file.

$path = "C:\Path\To\sample.mgu1"
$bytes = [System.IO.File]::ReadAllBytes($path)

if ($bytes.Length -lt 16) {
    throw "Truncated MGU1 header"
}

$signature = [byte[]](0x4D, 0x47, 0x55, 0x31)
for ($i = 0; $i -lt 4; $i++) {
    if ($bytes[$i] -ne $signature[$i]) {
        throw "Incorrect signature"
    }
}

$version = [int]$bytes[4]
$flags = [int]$bytes[5]
$headerLength = ([int]$bytes[6] -shl 8) -bor [int]$bytes[7]
$payloadLength = [uint64](
    ([uint64]$bytes[8] -shl 24) -bor
    ([uint64]$bytes[9] -shl 16) -bor
    ([uint64]$bytes[10] -shl 8) -bor
    [uint64]$bytes[11]
)

if ($version -ne 1 -or $flags -ne 0 -or $headerLength -ne 16) {
    throw "Unsupported or invalid MGU1 header"
}
if ($payloadLength -ne [uint64]($bytes.Length - 16)) {
    throw "Payload length mismatch"
}

"Header: " + [BitConverter]::ToString($bytes, 0, 16)
"Version: $version; Payload bytes: $payloadLength"

This demonstrates exact signature comparison and explicit field layout. The original file's record-count field at offsets 12–15 is not parsed here because no downstream use is required. Avoid relying on [BitConverter]::ToUInt32() without checking the desired endian behavior: it follows the platform's byte order, which is not the same thing as the file format's declared order.

Minimal Streaming Reader and Partial Reads

A file need not be loaded entirely to inspect its header. A streaming reader can read the fixed preamble, validate it, and then process bounded chunks. However, a stream read may return fewer bytes than requested without indicating end-of-file. Correct code accumulates bytes until the required count is received or EOF is reached, rather than assuming one Read call fills the buffer.


def read_exact(stream, count):
    if count < 0:
        raise ValueError("negative count")
    out = bytearray()
    while len(out) < count:
        part = stream.read(count - len(out))
        if not part:
            raise EOFError("truncated input")
        out.extend(part)
    return bytes(out)

#     ... validate header before streaming the bounded payload ...

Streaming introduces additional design questions: seeking may be unavailable, offsets may point backward, the file may change between reads, and an advertised payload may exceed time or space quotas. A parser should establish a consistent policy for cancellation, progressive verification, and trailing bytes. Most importantly, reading a valid fixed preamble does not authorize reading an unbounded amount of data based on the next untrusted length field.

Designing a Portable Header Contract

The simplest robust header is usually the one whose fields can be described without reference to a compiler or a specific processor. State every fixed byte's meaning; declare sizes in bytes, not machine words; declare numeric widths and endian rules; distinguish fixed header length from optional extensions; and define how a parser recognizes the end of each section. Provide a valid sample byte sequence and at least one invalid sample for each important rejection rule.

A portable specification also needs an extension policy. If future versions may add fields, either reserve well-defined space or use explicit versioned and length-delimited extensions. Clarify whether unknown extension types may be skipped or must cause rejection. Specify whether zero-length payloads are legal, whether trailing bytes are allowed, whether duplicate sections are legal, and whether size fields refer to compressed or uncompressed bytes. Ambiguity is not a flexibility feature when two independent implementations must interoperate.

The fictional MGU1 contract demonstrates this approach by fixing a sixteen-byte header and one big-endian payload length. It is intentionally restrictive. Relaxing it for optional sections or alternate record types would require new structural rules and tests, not merely adding a flag whose meaning exists only in a developer's source code comments.

Security Failures and Malformed-Header Patterns

Attacks against binary parsers often begin with structurally plausible headers. Oversized lengths can cause excessive allocation or overflow; negative values can arise when signed and unsigned fields are confused; enormous record counts can trigger long loops; offsets can point outside the file; multiple sections can overlap unexpectedly; recursive container entries can exhaust stack or CPU resources; and a decompression size can greatly exceed the compressed size advertised or actually stored.

Failure pattern Why a shallow header check misses it Defensive response
Correct magic, truncated payload Signature does not cover subsequent bytes Check every read against bounded input
Length arithmetic overflow Addition/multiplication wraps in a narrow type Use checked/wider arithmetic and subtraction-based bounds
Unsupported critical feature Version or flag information ignored Reject per compatibility rules
Conflicting offsets Each isolated range might be in bounds Validate collective overlap/ordering rules
Compression bomb Compressed file is small but decoded output is huge Cap output, CPU, recursion and nesting
Type confusion Bytes are parsed by an unintended decoder Confirm subtype and full grammar before dispatch
Time-of-check/time-of-use race File changes between inspection and consumption Operate on a stable handle or immutable snapshot

Shallow format sniffing is especially dangerous when one component checks the first bytes and another component actually processes the file under different rules. A consistent parser and shared policy reduce opportunities for that disagreement. The article Binary Input Validation and Safe Parsing develops those protections further.

False Positives, Polyglots, and Forensic Caution

Short magic patterns occasionally appear by chance, and deliberately crafted files may satisfy more than one recognizer. A polyglot file is constructed to be interpreted as more than one format by different consumers. This can occur through permitted trailing material, optional sections, offset rules, or differences between parsers. It is not proof that every format accepts arbitrary combined data; it is evidence that shallow recognizers can disagree about a file's identity.

Forensic analysis should record the exact observed bytes, offset, acquisition method, and tool behavior. “This file begins with a PNG signature” is stronger and more reproducible than “this is definitely a safe PNG image,” but weaker than “a specific conforming PNG decoder validated the complete bounded datastream under documented settings.” Investigators should separate raw-byte observations from inferred provenance, integrity, or intent.

Tools that use signatures to recover deleted or embedded data often called file carving face similar issues. A candidate start marker may identify an object, but determining its extent may require parsing chunk lengths, end markers, allocation boundaries, and container semantics. Naively cutting at the next magic sequence may truncate a valid object or split an embedded payload that happens to contain the same bytes.

Testing Strategies for Header Parsers

Testing a parser requires more than one successful sample and one bad signature. A strong suite starts with valid fixtures whose bytes can be reproduced independently and adds focused malformed cases. Each structural invariant should have a corresponding test that changes exactly one relevant field, so a failing test identifies a specific rule rather than some accidental downstream effect.

Suggested test categories include short inputs of every length below the fixed header, wrong signatures in each byte position, unsupported versions, reserved flags, zero or maximum lengths, declared lengths one byte too small or too large, integer overflow boundaries, duplicate/overlapping offsets, malformed optional sections, truncated trailers, checksum errors, and legal large-but-bounded files. For field directories, test counts that disagree with the available table extent. For streaming parsers, simulate partial reads and early EOF.

Fuzz testing explores unexpected byte combinations; differential testing compares independent readers against the same corpus; property-based testing checks invariants such as successful parse/serialize round trips where the format permits them. A complete test program includes performance and resource-limit behavior, not only acceptance and rejection. The parser should fail deterministically and without out-of-bounds access, unbounded allocation, or code execution.

Common Misconceptions

“A magic number proves the file type.” It identifies a candidate interpretation. The full format grammar and context determine validity and subtype.

“Every header begins at the first byte.” Many do, but some identification fields appear at specific later offsets or within an outer container. The PE signature is a familiar offset-based example.

“The filename extension and media type are authoritative.” Both can be wrong or misleading; neither substitutes for content-aware validation.

“A header length is the number of bytes currently present.” A length field is a claim inside the file and must be checked against actual available bytes and policy limits.

“CRC means the data is authentic.” CRCs primarily detect accidental corruption; authenticity requires appropriate cryptographic evidence and a trust model.

“The processor decides the byte order.” A portable binary format defines the byte order of its multibyte fields, independently of the reader's host machine.

“No magic bytes means no structure.” Headerless or externally described streams can still have precise schemas and framing rules.

Worked Exercises and Investigations

  1. A file begins 4D 47 55 31 01 00 00 10 00 00 00 0C 00 00 00 03 and contains 28 bytes total. Identify the signature, version, header size, payload size, record count, and first payload offset under the fictional MGU1 specification.
  2. The same header is followed by only 11 payload bytes. Identify the precise validation failure and explain why a valid signature does not excuse it.
  3. A file of length 24 declares a fixed header of 16 bytes and a payload length of 0xFFFFFFFF. Write a subtraction-based extent check and explain why a 32-bit 16 + length calculation is risky.
  4. Given the PNG opening 89 50 4E 47 0D 0A 1A 0A 00 00 00 0D 49 48 44 52, identify the signature, next chunk's data length, and chunk type. What information is still missing before the chunk can be validated?
  5. A gzip member starts 1F 8B 08 08 .... Explain why the optional filename flag affects where compressed data begins; do not guess the filename's length from the fixed header.
  6. A file is named budget.pdf but begins with the SQLite version-3 signature. State what can reasonably be inferred, and what further checks are required.
  7. An application accepts any file beginning RIFF as waveform audio. Explain the missing form-type and structure checks.
  8. A PE detector sees MZ and then seeks to an offset advertised by the file without checking the file length. Identify the bounds mistake.
  9. Propose four invalid fixtures for MGU1 that exercise separate rules, not four variants of an incorrect signature.
  10. A file passes a CRC check, but its dimensions imply a multi-gigabyte decoded image beyond policy. Should a service process it? Explain the difference between integrity and resource authorization.

These exercises require byte-level reasoning rather than merely naming a format. A careful answer specifies the byte offset, width, endianness, rule, and conclusion supported by the available evidence.

Answers and Reasoning for Selected Exercises

Exercise 1: Signature MGU1, version 1, header size 16, payload size 12, record count 3, first payload offset 16. File size 28 matches exactly. The record count is only a declaration until the record schema is examined.

Exercise 2: The available payload is 11 bytes but the header declares 12; the file is truncated by one byte. The signature remains correct but the size invariant fails.

Exercise 3: With N = 24 and H = 16, require L ≤ N − H = 8. 0xFFFFFFFF plainly fails. On a 32-bit unsigned accumulator, adding 16 can wrap and produce a misleading small value.

Exercise 4: The eight-byte PNG signature is followed by a big-endian length of 13 (00 00 00 0D) and IHDR (49 48 44 52). The 13 data bytes and four CRC bytes still need to be read and checked, along with further PNG rules.

Exercise 6: The name conflicts with the content's candidate format. Verify the full SQLite header and database structure; do not assume the object is a valid database or a valid PDF from the initial observation alone.

Exercise 7: RIFF indicates a container family. Check the form type such as WAVE, then validate subtype-specific chunks and bounds. The family signature cannot identify arbitrary content as audio.
