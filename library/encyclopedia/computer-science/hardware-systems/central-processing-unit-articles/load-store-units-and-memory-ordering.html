Scope and Central Question

The load/store unit (LSU) is the portion of a processor that turns load and store instructions into ordered, address-checked transactions with the memory system. Arithmetic pipelines mostly consume and produce register values; a memory pipeline must also determine which bytes a reference names, which older stores could supply those bytes, whether the access is permitted, and when its effects may be exposed to another observer. The central question is therefore more demanding than “how quickly can a cache return data?”: how can a processor execute memory requests aggressively while preserving the architectural memory semantics of the program?

This is Central Processing Unit specialist article 14 of 24, in the Hardware Systems division of the MGU Computer Science Encyclopedia. It covers address generation, load and store pipelines, load queues and store queues, store-to-load forwarding, memory-dependence prediction, ordering, replay, store commitment, fences and atomic instructions, and practical validation. The main comparison is between the operations a processor executes, the results it retires, and the stores that become observable. Those events need not occur at the same time.

The article uses an illustrative out-of-order core and limited software models to make the logic concrete. Actual CPUs differ in queue organization, cache policies, forwarding rules, fence implementation, and ISA guarantees. Nothing here should be read as the microarchitectural specification of every x86-64, AArch64, or RISC-V processor. RISC-V RVWMO, Arm memory ordering, and Intel's developer manuals are primary architectural references.

Learning Objectives and Prerequisites

After studying this article, readers should be able to trace a load or store through address generation, address translation, the LSU, and the memory hierarchy; explain how queues track instruction age and outstanding memory work; calculate load-data values reconstructed from a byte mask and one or more older stores; and distinguish a speculative execution dependency from a permanent architectural dependency. They should also interpret basic memory-ordering litmus tests, explain why coherence does not define all legal cross-address outcomes, choose the correct synchronization abstraction, and investigate load/store stalls using measured evidence.

Prerequisites include byte-addressed memory, virtual addresses, cache lines, pipeline stages, program order, instruction retirement, and a basic understanding of concurrency. For an introduction, first read CPU Pipelines and Hazards and Instruction Completion and Retirement. For caches, see CPU Cache Hierarchies and Locality. The Python examples describe deliberately simplified mechanisms, not complete runnable CPU simulators.

A Memory Instruction Is More Than an Address

Consider load r1, [r2 + 12]. The decoder recognizes an architectural instruction; the address-generation unit combines a base register with the signed immediate; address translation resolves the resulting virtual address; the LSU decides when it may issue; the cache or an older buffered store supplies the bytes; hardware extends or transforms those bytes as required; and the destination register eventually receives the result. A page fault, protection violation, alignment exception, or ordering conflict can interrupt or replay this sequence.

For store [r2 + 12], r3, there are at least two inputs: address and data. They can become ready in different cycles, and out-of-order cores often hold them separately until both are known. Even after a store is marked architecturally committed, it may reside in a store buffer before becoming visible to another core, subject to the memory model. Unlike an ordinary arithmetic instruction, a store could affect externally visible shared state; the processor must therefore regulate when that side effect is released.

Conceptual LSU Dataflow

An LSU typically interfaces with operand-read logic, an address-generation unit (AGU), translation structures, a data cache, a load queue, a store queue, and a retirement/commit mechanism. Some architectures use dedicated load and store AGUs; others share integer execution hardware or split address and data pipelines. The diagram is a logical map, not a transistor-level or cycle-accurate implementation.

The load response may come from an L1 data-cache hit, a store-forwarding path, a lower cache, DRAM, or a coherence response; the result can be forwarded to dependent instructions before those instructions retire. The store path must retain unresolved or uncommitted writes while protecting architectural correctness. Real implementations may allocate separate address/data queues, use a unified structure, or include additional miss-status handling registers and writeback buffers.

Instruction Age, Issue, Completion, Retirement, and Visibility

Program order is the order of architectural instructions in one thread. Issue order is the order in which micro-operations are selected for execution; completion means the particular operation produced its local result; retirement is the ordered point where the processor accepts its architectural effects; and visibility concerns when another observer can see a memory write. In an out-of-order design, a younger cache-hit load can complete before an older cache-miss load. Yet the younger instruction ordinarily cannot retire ahead of an older instruction that has not completed, if the implementation uses in-order retirement.

A store typically can compute its address and data early, wait in an ordered structure, retire when safe, then drain from a store buffer according to its memory model and coherence machinery. One must not treat a trace showing “store executed” as proof that all other cores already see the value. Conversely, a processor may provide the new value to its own younger load through forwarding while the store is not yet globally visible. This distinction underlies store-buffering litmus tests.

The Load Path: From Operands to Value

A common load sequence is: decode and allocate bookkeeping → wait for base/index operands → compute effective virtual address → translate and check access → identify older overlapping stores → access a forwarding path or the cache hierarchy → extract, sign/zero extend, and deliver the value → confirm ordering and retire at the correct point. Implementations can overlap several of these operations and may start cache indexing in parallel with translation where the geometry permits.

If the load misses in L1, the core may retain a miss-tracking entry while independent instructions continue. If it overlaps an older store whose address or data remains unknown, the core may wait or speculate according to its disambiguation policy. A load can also re-execute because of a coherence event, a detected ordering violation, a failed memory dependency prediction, or an exception. A ready value is not by itself proof that the load is architecturally safe to retire.

The Store Path: Address, Data, and Commitment

A store generally has to determine its address, identify the bytes to modify, and obtain the store data. On a little-endian system a four-byte store of 0x11223344 to address A places bytes 44 33 22 11 at A..A+3; byte order must be taken from the architecture and access width, not guessed from a diagram. An LSU can queue the address and payload separately until both are available, and it may format byte write masks before accessing cache or bus infrastructure.

Stores cannot simply update the architectural memory hierarchy as soon as they execute if they might later be discovered to be on a mispredicted path or behind a faulting older instruction. They can instead wait until retirement authorizes their effects. The design then arranges visibility, buffering, and ordering in accordance with its contract. Some writes—particularly memory-mapped I/O and strongly ordered device traffic—follow more restrictive rules than ordinary cacheable memory.

Address Generation Units

An AGU calculates effective addresses, commonly by adding a register base, optional index or scale, and displacement. It is a hardware datapath; it need not know whether a pointer refers to a stack, heap, or file mapping. Address generation may be scheduled separately from the load-data return or store-data preparation. Multiple AGUs can permit several memory addresses to be generated per cycle, though cache ports, translation resources, and queue capacities may constrain sustainable throughput.

A useful performance decomposition distinguishes address-generation throughput, load-data bandwidth, store-data bandwidth, and commit/drain capacity. A processor advertised as “two loads and one store per cycle” under a particular microbenchmark may achieve less on unaligned accesses, insufficiently translated addresses, cache misses, or read-modify-write sequences. The number of nominal ports does not establish application-level memory throughput without the instruction mix and operand availability.

Worked Example: Base-plus-Offset Addressing

For an illustrative 64-bit core, suppose a register contains 0x00001000 and the instruction encodes a signed immediate of -24. The computed effective address is 0x00000FE8. This example illustrates arithmetic only; whether the resulting access is legal depends on address translation, permissions, alignment, and memory attributes.

BASE = 0x1000
IMM = -24
MASK64 = (1 << 64) - 1
address = (BASE + IMM) & MASK64
assert address == 0xFE8
print(hex(address))  # 0xfe8

The arithmetic wraparound here models an unsigned 64-bit address calculation. The legality and interpretation of such wraparound are ISA-specific, so this small Python snippet is not a general model of pointer validity or canonical-address checks.

Address Translation, TLBs, and Permissions

Address translation is separate from the logical memory-ordering decision. A data TLB can translate a virtual address to a physical one; a miss may trigger a hardware page-table walk or an architecture-specific software-managed translation path. A translation failure can cause an architectural exception, and permission checks may depend on the operating mode and the type of access. Load and store operations can have different permission outcomes at the same virtual address.

An access that straddles pages may require translation of both pages; one part may be accessible while the other is not. The system must ensure that fault handling and visible side effects comply with the ISA, especially for a store split across boundaries. Page-table update rules and TLB synchronization belong more fully to Address Translation and Translation Lookaside Buffers. LSU designers must nevertheless coordinate translation status with replay, buffering, and precise exception reporting.

Alignment, Access Width, and Split Transactions

An aligned eight-byte load at an address divisible by eight is often simpler to service than an eight-byte load crossing a cache-line boundary. A misaligned access may be supported directly, handled in multiple internal requests, or raise an exception depending on the ISA, memory type, and platform. If a line boundary or page boundary is crossed, two cache lines or translations may participate; such an access can consume additional queue and cache-port resources.

Atomicity is a separate question. A machine may accept a misaligned access without guaranteeing that another observer perceives the operation as indivisible. Do not infer atomic behavior merely from the fact that the instruction executes successfully. On certain platforms, split access to device registers can be incorrect even if the same access pattern works on ordinary RAM. Alignment, access size, and the documented memory-region attributes must be checked together.

Byte Lanes and Write Masks

Stores often modify fewer bytes than a whole cache line. A byte write mask records which lanes should be replaced; a forwarding path can use similar masks to assemble a younger load's value. For example, a two-byte store to offsets 1 and 2 of a four-byte word changes those lanes but leaves offsets 0 and 3 unchanged. The byte lanes should be reasoned about in address order, and endianness applied only when converting the lane sequence to an integer.

def apply_store(old: bytes, offset: int, payload: bytes) -> bytes:
    assert 0 <= offset <= len(old) - len(payload)
    result = bytearray(old)
    result[offset:offset + len(payload)] = payload
    return bytes(result)

original = bytes.fromhex('aa bb cc dd')
assert apply_store(original, 1, bytes.fromhex('11 22')) == bytes.fromhex('aa 11 22 dd')
print(apply_store(original, 1, bytes.fromhex('11 22')).hex())

This deterministic byte-array example illustrates masking, not a performance model. Real stores can be merged, buffered, split, or forwarded through structures with different internal granularity.

Load Queues and Store Queues

An out-of-order core may allocate load queue (LQ) entries to track loads in flight and store queue (SQ) entries to track older stores whose addresses, data, or commitment status may not yet be resolved. These queues permit dependence checks, forwarding, exception tracking, replay detection, and retirement coordination. An LQ entry can record address, age, completion status, and information needed to check whether its earlier execution remained legal.

The SQ is often searched by younger loads for matching older writes. A load must not take data from a younger store, even if that store executed first physically. The relevant comparison is instruction age. Some designs divide store-address and store-data storage or maintain a store buffer for retired stores distinct from the speculative SQ. The exact naming and placement vary; BOOM documents a concrete load/store design and its store-dependence mask mechanism at BOOM LSU documentation.

Queue Capacity and Backpressure

Queues are finite. When no LQ or SQ slot is available, decode, rename, or dispatch may stall, even though arithmetic execution units are free. A load miss can occupy a queue entry long after its initial execution attempt, and a long-lived store awaiting address data or retirement may block younger memory operations. The queue-full condition becomes a front-end throughput limitation rather than a direct cache-hit-latency issue.

A first-order capacity estimate is occupancy ≈ arrival rate × mean residence time under steady-state assumptions (Little's law). If, hypothetically, a core accepts 1.5 memory operations per cycle and an entry stays resident for 20 cycles, average occupancy approaches 30 entries. This does not establish a queue's required size: latency variability, bursts, load/store proportions, allocation rules, and backpressure require headroom. A design with inadequate entries can lose throughput even at a high cache hit rate.

arrival_rate = 1.5  # illustrative memory operations per cycle
mean_residence = 20  # illustrative cycles
average_occupancy = arrival_rate * mean_residence
assert average_occupancy == 30.0
print('Approximate average occupancy:', average_occupancy)

Store-to-Load Forwarding

A younger load should see the value of the youngest older store that covers each required byte, provided the architectural model allows the access and the store payload is available. Store-to-load forwarding supplies that data from buffered store entries without requiring the store to become globally visible first. This can save a round trip through a cache, and it is necessary for single-thread consistency when a load immediately follows an older store to the same location.

Forwarding is not an unconditional cache-bypass guarantee. Exact-match and partial-overlap cases may require different hardware; some patterns stall until the store becomes drainable or are replayed. The cost depends on store width, load width, byte alignment, and available data. Most importantly, the forwarding choice must respect instruction age rather than the accidental order in which queue entries were examined.

Worked Example: Youngest Older Store Wins

Suppose an older store writes AA BB at addresses 0–1, a later but still older store writes 22 33 at addresses 1–2, and a still younger load reads addresses 0–2. Its result in address order is AA 22 33, because the second store supersedes the first at address 1. The example below walks stores newest to oldest to reconstruct each byte, then consults a backing memory image for uncovered bytes.

def forward_bytes(memory: bytes, stores, load_address: int, size: int, load_age: int):
    out = []
    older_stores = [s for s in stores if s['age'] < load_age]
    for addr in range(load_address, load_address + size):
        byte = memory[addr]
        for store in sorted(older_stores, key=lambda s: s['age'], reverse=True):
            delta = addr - store['address']
            if 0 <= delta < len(store['data']):
                byte = store['data'][delta]
                break
        out.append(byte)
    return bytes(out)

memory = bytes.fromhex('00 00 00 00')
stores = [
    {'age': 2, 'address': 0, 'data': bytes.fromhex('aa bb')},
    {'age': 5, 'address': 1, 'data': bytes.fromhex('22 33')},
]
assert forward_bytes(memory, stores, 0, 3, load_age=7) == bytes.fromhex('aa 22 33')
assert forward_bytes(memory, stores, 0, 3, load_age=4) == bytes.fromhex('aa bb 00')
print(forward_bytes(memory, stores, 0, 3, 7).hex())

The backing-memory fallback is valid only for this simplified single-thread snapshot, with no concurrent updates or unresolved store entries. A real load may need to stall rather than choose memory if an older store's address or data is unknown; the next sections explain why.

Partial-Overlap and Forwarding Restrictions

Consider a four-byte load overlapping only two bytes of an older store. A sufficiently flexible LSU can merge forwarded bytes with bytes obtained elsewhere; a narrower forwarding path may replay the load or wait for the store to enter the cache. This is a performance detail, not an excuse to return the wrong bytes. Designers must also account for multiple older stores, page splits, endianness, cache-line splits, atomic accesses, and the difference between natural-size and unusual access widths.

For performance diagnosis, a high proportion of store-forwarding stalls can indicate awkward structure layout, mixed-width field accesses, or a pattern of stores followed too closely by partially overlapping loads. It does not necessarily mean the program has a data race. Investigate whether data sizes, alignments, and dependencies produce forwarding restrictions on the specific processor; never generalize a forwarding penalty from one CPU generation to all others.

Memory Dependencies: RAW, WAR, and WAW

Read-after-write (RAW) memory dependence is a genuine flow dependence: a younger load to the same overlapping bytes must observe an appropriate earlier store, not an older stale value. Write-after-read (WAR) and write-after-write (WAW) constraints concern the observable ordering of accesses; processors can overlap implementation work provided the ISA-prescribed behavior is maintained. Register renaming removes certain register-name hazards, but it cannot rename arbitrary memory addresses because aliasing is determined dynamically.

Load/store dependence questions are hard because addresses can be computed late. Two instructions may use unrelated registers whose runtime addresses alias, and conversely two syntactically similar expressions may reference different objects. A legal microarchitectural schedule is determined by resolved addresses, access types, sizes, instruction age, and the memory model—not simply by what two assembly mnemonics look like.

Why Unknown Store Addresses Matter

Suppose a younger load is ready to read address A, but an older store has computed its data without yet computing its address. The older store might target A, in which case the load must not permanently use the pre-store value. One conservative core waits for all relevant older store addresses; a more aggressive core predicts independence and executes the load. Later resolution reveals whether that decision was correct.

A prediction error calls for replay or recovery, not acceptance of an architecturally incorrect value. For example, a core can invalidate the younger load result, cancel dependent speculative work, and re-execute once the store is known. How broadly the core squashes instructions depends on its recovery machinery. Speculation can increase throughput when independent operations are common, but the correctness requirement survives any prediction accuracy claim.

Store-Set and Dependence Prediction

A memory-dependence predictor attempts to infer whether a given load should wait for a particular older store. A store-set design associates program-counter histories with likely dependence relationships; other designs use different history tables or simpler conservative rules. Good prediction permits independent loads to proceed without waiting for unrelated store addresses while delaying loads likely to alias.

Prediction state is a performance hint, not architectural authority. A predictor can generate false positives, which reduce parallelism, and false negatives, which require correction. Its correctness depends on a separate mechanism that detects problematic memory ordering and enforces replay when needed. The predictor itself does not create an exception to the ISA memory model. The general mechanism is explained in research on dynamic memory disambiguation and is illustrated by the BOOM LSU's store masks and ordering checks.

An Illustrative Conservative Alias Test

If a load's byte interval overlaps the address interval of an older store, it may need to forward, stall, or be replayed depending on data readiness. A disjoint interval does not create same-location RAW dependence, though broader ordering rules may still constrain issue. The following interval check is deliberately independent of cache lines: sharing a cache line does not necessarily mean sharing accessed bytes.

def overlaps(addr_a, size_a, addr_b, size_b):
    assert size_a > 0 and size_b > 0
    return addr_a < addr_b + size_b and addr_b < addr_a + size_a

assert overlaps(0x1000, 8, 0x1006, 4)
assert not overlaps(0x1000, 4, 0x1004, 4)
assert overlaps(0x1000, 1, 0x1000, 1)
print('Overlap tests passed')

This function assumes finite, nonwrapping address ranges. A physical LSU must also handle translation, wraparound, memory type, faulting accesses, and the granularity at which its internal comparisons operate.

Speculative Loads, Validation, and Replay

An early load may be marked complete while the core still tracks it in the load queue to detect a younger/older ordering problem. If a store's address resolves to overlap a younger load that incorrectly observed an earlier value, the machine needs a replay procedure. Some processors also monitor coherence probes or related events to enforce required load ordering across cores. These cases are distinct even though both can lead to a re-execution.

Correct replay requires more than reissuing a load. Dependents that consumed the bad value must be invalidated or recomputed; speculative writes must not escape; branch outcomes based on the stale value must be corrected; and the retirement stream must remain consistent. The precise details vary. The central proof obligation is that the final retired behavior matches a legal architectural execution, despite temporary speculation or an initially wrong predictor guess.

Demonstration: An Aliasing Violation Detector

This toy checker flags only one situation: a younger load executed before an older store's address became known and the two byte intervals overlap. It does not by itself decide whether the broader ISA memory model allows other reorderings.

def needs_replay(older_store, younger_load):
    if not older_store['address_resolved_after_load']:
        return False
    if older_store['age'] >= younger_load['age']:
        return False
    return overlaps(older_store['address'], older_store['size'],
                    younger_load['address'], younger_load['size'])

store = {'age': 3, 'address': 100, 'size': 4, 'address_resolved_after_load': True}
load = {'age': 7, 'address': 102, 'size': 2}
assert needs_replay(store, load)
assert not needs_replay({**store, 'address': 200}, load)
print('Speculative overlap checks passed')

From Load Queue to Architectural Retirement

A loaded value can be forwarded to dependent operations as soon as the core deems it tentatively usable; the load itself must still carry sufficient metadata for a fault or replay, and its architectural retirement remains age constrained. The machine must avoid retiring a younger instruction whose correctness depends on an unresolved older fault. Once the instruction is committed, software-visible registers and exceptions must reflect the legal program sequence.

This is why a load's execution-complete bit and its retirement-eligible bit are different notions. A cache-hit load can execute quickly but wait behind a long-latency older instruction at the head of the reorder buffer. Conversely, slow memory may cause a front-end stall because queue entries remain allocated even while other execution pipes have capacity. These resource chains should be considered separately from “raw memory latency.”

Store Commitment and the Store Buffer

Stores on a wrong path must not corrupt architectural memory. In a common out-of-order design, a store first resides in a speculative queue, becomes non-speculative when its instruction retires, and subsequently drains through a committed-store buffer into the memory hierarchy. Some cores use a single structure with committed/uncommitted regions; others have physically separate queues. The abstraction is speculative computation first, authorized side effect later.

The store buffer can allow retirement to continue without waiting for external visibility of every individual store. This improves throughput but introduces memory-ordering subtleties. For ordinary coherent memory, other cores need not see all of the writer's buffered stores at the instant the writer retires them. Barriers, atomic release/acquire operations, and ordering policies impose the required constraints. A full store buffer can block retirement and create backpressure even when load processing is otherwise healthy.

A Timeline: Forwarded Data Versus Remote Visibility

Imagine core 0 executes store x = 1, then load x. The load can obtain 1 through store forwarding even if core 1 continues temporarily to see 0 in its coherent view, subject to the architecture's conditions. This is not a contradiction: forwarding is a same-core value-selection mechanism, while cross-core visibility is managed by cache coherence and ordering rules. Different cores' observations must still satisfy the ISA model.

If core 0 then performs a release operation and core 1 performs a corresponding acquire that reads from it, the synchronization contract can establish that earlier data writes are visible to the acquiring thread under the relevant language and ISA rules. The presence of a cache line in both cores is not, by itself, such a contract. Distinguish coherence, ordering, synchronization, and compiler transformations; each controls a different part of the system.

Memory Consistency Is an Architectural Contract

A memory consistency model defines which values and orders of memory accesses are permitted to be observed by interacting threads or agents. It does not require that every micro-operation execute literally in instruction order; instead, it constrains the observable results of those internal schedules. Different ISAs provide different guarantees, and software memory models impose an additional contract governing compiler transformations and data races.

Sequential consistency (SC) is a useful reference: all operations appear in some single total order that respects each thread's program order. Many practical systems permit more executions than SC while retaining particular same-address, dependency, or synchronization constraints. A processor that performs independent memory operations out of order can still meet its specification if the outcomes are legal. Therefore performance engineering and concurrency correctness require describing the particular ISA and the language-level synchronization, not a generic claim that “modern CPUs reorder memory.”

Sequential Consistency as a Baseline

Under SC, if thread 0 does x=1; r0=y and thread 1 does y=1; r1=x, with both variables initially zero, the outcome r0=0, r1=0 is impossible. For thread 0 to see y=0, its read would have to occur before thread 1's write to y; similarly, the other read would precede thread 0's write to x. Both threads also require their own store before their own load, producing an impossible ordering cycle.

A weaker model such as x86-64's ordinary write-back-memory behavior can permit both loads to obtain zero because each core's load can effectively bypass its own older buffered store to a different address. This is the classic store-buffering (SB) litmus test. The distinction is not evidence of a faulty CPU; it explains why a program demanding cross-thread ordering needs proper synchronization. The litmus is best studied on atomic variables or in an ISA-level model, not by racing non-atomic C++ variables.

Store-Buffering Litmus Test

Initial state Thread 0 Thread 1
x = 0, y = 0 store x = 1 store y = 1
r0 = load y r1 = load x

The key question is whether r0 = 0 and r1 = 0 can both occur. Under SC, no; under typical x86-64 TSO ordinary cacheable memory, yes. Under weaker hardware models, additional outcomes may be allowed for different litmus programs. The following simulator enumerates only one simplified mechanism: two FIFO store buffers, stores enqueued in program order, and loads able to read the most recent buffered same-address store from their own thread or else shared memory. It therefore demonstrates the SB outcome but does not attempt to capture every feature of real TSO or device memory.

from collections import deque

def sb_outcome():
    mem = {'x': 0, 'y': 0}
    buffers = [deque(), deque()]
    # Both stores are retired locally but have not drained to shared memory.
    buffers[0].append(('x', 1))
    buffers[1].append(('y', 1))
    r0 = mem['y']  # No same-address forwarding from core 0's x store.
    r1 = mem['x']  # No same-address forwarding from core 1's y store.
    # Buffers may later drain in FIFO order per core.
    for buf in buffers:
        while buf:
            key, value = buf.popleft()
            mem[key] = value
    return r0, r1, mem

r0, r1, memory_after = sb_outcome()
assert (r0, r1) == (0, 0)
assert memory_after == {'x': 1, 'y': 1}
print('SB outcome:', r0, r1)

x86-64 TSO in Context

For ordinary cacheable write-back memory, the x86-64 architectural model is commonly described by total store ordering (TSO). It preserves a relatively strong ordering: loads remain ordered with other loads, stores remain ordered with other stores, and a store is not ordinarily reordered with an older load. The important relaxation is that a younger load to another location may be observed before its own core's older store has become globally visible. Forwarding maintains the same-core store-to-load relationship when addresses match.

This simplified summary is insufficient for every instruction or memory type. Locked operations, fences, non-temporal stores, write-combining memory, I/O, and specialized operations have additional rules. Source code is also transformed by a compiler before it reaches hardware. Consult Intel's Software Developer's Manual for the formal guarantees relevant to a target CPU and memory type. Do not assume that x86 TSO means every thread observes every recent store immediately.

Armv8-A Memory Ordering

Armv8-A uses a weaker ordering architecture than x86-64 for ordinary independent memory accesses. Ordering can arise from dependencies, explicit barrier instructions, atomic operations, or load-acquire and store-release instructions, according to the architectural rules and shareability domain. A program that works incidentally on a stronger-ordered processor may therefore require synchronization that makes its intended ordering explicit when ported to Arm hardware.

Arm's DMB orders specified classes of memory accesses for specified observers; DSB also supplies completion constraints; ISB synchronizes instruction execution after relevant context changes. These barriers are not interchangeable, and an instruction-cache synchronization sequence is not a substitute for ordinary shared-memory acquire/release. Arm's architecture guides explain memory-ordering constraints and acquire/release instructions.

RISC-V RVWMO and Fences

The default RISC-V weak memory ordering model (RVWMO) preserves selected program-order relationships, including specified dependencies and ordering constraints, rather than requiring every independent access to retain its original relative position in a global order. RISC-V's FENCE instruction orders nominated predecessor and successor classes of memory operations. Atomic instructions may carry acquire (aq) and/or release (rl) ordering bits. The exact rules, including address, data, and control dependencies, are defined by the ratified specification rather than informal slogans.

A common mistake is to interpret aq as “block every earlier write” or rl as “force every later read to finish.” Acquire constrains certain later operations relative to the acquire; release constrains certain earlier operations relative to the release. Fences can provide broader orderings when needed. The official RVWMO explanatory material supplies the precise examples, and the unprivileged ISA specification defines the normative rules.

Cache Coherence Versus Memory Consistency

Cache coherence answers a per-location question: how do cores obtain a consistent treatment of writes to the same coherence location, with ownership and invalidation or update protocols enforcing the required rules? Memory consistency answers a broader question: what orderings across multiple locations may different observers see? A coherent system may still permit the store-buffering litmus result because per-location agreement does not guarantee global sequential consistency across different locations.

The LSU participates in both. It requests cache data, responds to relevant coherence events, tracks speculative loads, and ensures its committed behavior meets the memory model. The cache hierarchy and coherence fabric carry information among cores, while ordering logic and synchronization determine which execution sequences are legal. See CPU Cache Coherence and Atomic Operations for cache-line ownership, atomic read-modify-write, and coherence protocols.

Atomicity, Ordering, and Durability Are Different

An atomic memory operation is indivisible with respect to the specified observers and granularity; ordering constrains its relationship with other operations; durability concerns whether data survives power failure or other persistence events. A processor can execute an atomic store without making it ordered relative to every unrelated access, and it can order writes without guaranteeing they have reached nonvolatile storage. Calling all three properties “committed” conceals important engineering obligations.

Atomicity also depends on size and alignment guarantees. Hardware support for one natural-width atomic access does not imply atomicity for an arbitrarily large structure or a misaligned access crossing a cache line. Persistent-memory software may need cache-line flushes and persistence barriers beyond ordinary multicore fences. Those procedures are platform-specific and are not interchangeable with language-level synchronization for live threads.

Acquire, Release, and Happens-Before

The release–acquire pattern allows one thread to publish a data structure and another to observe it safely. For example, thread A initializes a payload and then performs a release store to a ready flag; thread B performs an acquire load of that same flag and, after reading the published value, accesses the payload. In a language such as C++, a successful acquire operation reading from the corresponding release sequence can establish a synchronizes-with relationship and thus a happens-before edge for the earlier writes.

This is a language-level contract carried through compiler lowering and hardware instructions. A plain Python variable, C++ volatile, or ordinary unsynchronized load of a flag does not automatically provide those guarantees. Properly structured atomics are preferable to manually scattering raw fences through application code. Separate the data accesses from the publication access and document which atomic read establishes the intended synchronization.

An Illustrative Message-Passing Pattern

The following snippet is conceptual C++11-style code; it is not meant to be executed as embedded Python. It emphasizes the synchronization edge rather than API setup or lifetime management.

// Shared initialization: payload = 0; ready = false.
int payload = 0;
std::atomic<bool> ready{false};

// Producer thread
payload = 42;
ready.store(true, std::memory_order_release);

// Consumer thread
if (ready.load(std::memory_order_acquire)) {
    assert(payload == 42);
}

Assumptions: one producer initializes the non-atomic payload, nobody concurrently modifies it afterward, and the consumer reads it only after the acquire load observes the publishing release. Those assumptions prevent a data race in this specific publication pattern. A different ownership or update pattern requires a different synchronization design. Compilers may implement the atomics differently on x86-64, Arm, and RISC-V while preserving the same language-level guarantee.

Why Fences Are Not a General Substitute for Atomics

A fence orders certain operations relative to others, but its effect is defined by the ISA or programming language and the surrounding accesses. A fence alone is not a magical lock, does not necessarily make a read-modify-write indivisible, and cannot repair an arbitrary data race in a high-level language. In C++, fence-based synchronization requires particular atomic operations and a defined relation between them; simply placing a fence before and after ordinary shared-variable access is insufficient.

Use mutexes when a critical section protects complex invariants, atomic operations when a defined synchronization or lock-free algorithm genuinely requires them, and barriers only with a documented contract. At the hardware level, distinguish ordering from completion: Arm's DMB, DSB, and ISB, for example, serve different purposes. Over-fencing can reduce concurrency and pipeline throughput without improving correctness beyond an already sufficient synchronization scheme.

Atomic Read-Modify-Write and LSU Coordination

An atomic operation such as fetch-and-add, compare-and-swap, or load-reserved/store-conditional combines a read with an update under architectural indivisibility rules. It may use special cache-coherence permissions, reservation tracking, a locked instruction, or other hardware support depending on the ISA and implementation. It also has ordering semantics that may be relaxed, acquire, release, or stronger. Those dimensions must be specified independently.

The LSU and coherence system must prevent another observer from seeing an invalid intermediate state for the defined atomic operation. This is more demanding than ordinary store-to-load forwarding within one core. An unsuccessful compare-and-swap or conditional store also has defined side effects and ordering requirements; the result cannot be reasoned about as a mere pair of ordinary independent load/store instructions. Implementations and API choices should be anchored in ISA and language documentation.

Memory-Mapped I/O and Device Memory

Memory-mapped I/O (MMIO) uses load/store-like instructions to interact with device registers, but the access may trigger physical actions such as acknowledging an interrupt or starting a DMA transfer. Such accesses can have side effects on reads, be sensitive to width and order, or require completion before proceeding. Ordinary assumptions about cacheability, speculative execution, and safe replay may not apply.

Device-memory ordering is governed by its specified attributes, platform bus rules, and driver interfaces. For example, many systems use operating-system-provided read/write functions that apply required ordering or byte-swapping; a hand-written C pointer dereference may not provide the necessary compiler or hardware semantics. Do not generalize a cacheable-RAM fence recipe to PCIe device registers or independently accessible DMA engines. Refer to the platform's driver and architecture manuals before writing low-level MMIO code.

DMA, I/O Coherence, and Ordering Domains

A direct-memory-access (DMA) engine reads or writes memory without issuing instructions on the CPU core. Whether CPU caches and the device are mutually coherent depends on the platform, device, connection, and memory attributes. Even on a coherent platform, a driver may have to use explicit memory barriers to order descriptor initialization before publishing a work-queue pointer or ringing a device doorbell.

Thus LSU ordering, cache coherence, IOMMU translation, and DMA synchronization are related but distinct. A device's ability to access a physical address does not prove that it has seen every buffered CPU write, and a completed device write does not automatically mean the operating system has performed any necessary cache maintenance on a noncoherent platform. Driver correctness requires documented ordering and ownership handoffs, not just plausible instruction ordering in C source.

Speculation, Side Effects, and Transient Information Leakage

Speculative loads can leave traces in caches, TLBs, predictors, or queues even when their instructions are later squashed and do not retire. That behavior creates a potential transient-execution side channel: architectural rollback of a wrong-path load is not necessarily erasure of its microarchitectural effects. The security problem differs from an ordinary architectural memory-ordering violation. One concerns information leaked through physical timing state; the other concerns which program-visible values are legal.

Mitigation choices depend on the threat model and platform: bounds-check hardening, speculative-execution barriers, safer data-access structure, microcode or firmware updates, isolation, and platform-specific kernel controls may each address different attack classes. Do not assume every memory fence is a complete security barrier. CPU Security Isolation and Speculative Side Channels owns the deeper mitigation and threat-model treatment.

Memory-Level Parallelism and Nonblocking Loads

A nonblocking memory subsystem can maintain several misses in flight, overlapping delays to the extent that cache and memory resources permit. Memory-level parallelism (MLP) is distinct from merely having multiple load issue ports. A pointer-chasing chain has a dependency from one address to the next, limiting overlap even when the LSU has dozens of load-queue entries; independent array streams may generate far more concurrent requests.

Effective overlap depends on queue size, available miss-status handling structures, TLB-walk concurrency, cache-bank contention, interconnect bandwidth, and DRAM behavior. Memory latency is not simply divided by the number of outstanding requests: serialized dependencies remain serialized, while throughput limits emerge when too much traffic is in flight. The best interpretation combines instruction dependencies, hardware counters, and measured application progress.

Worked Example: Dependent Versus Independent Loads

Suppose four loads each have a hypothetical 80-cycle response time. A pointer chain where each load's address is found in the previous load's result has a lower bound near 4 × 80 = 320 cycles on that serial dependency path, ignoring overhead. If four independent loads can issue together and the memory subsystem has sufficient capacity, the slowest response might be available after roughly 80 cycles instead. This is illustrative; real misses overlap partially, service times vary, and surrounding instructions consume resources.

latency = 80
n = 4
serial_critical_path = n * latency
parallel_idealized_path = latency
assert serial_critical_path == 320
assert parallel_idealized_path == 80
print('Serial:', serial_critical_path, 'Parallel lower bound:', parallel_idealized_path)

The CPU cache hierarchy article covers locality and cache levels; here the focus is on how the LSU tracks independent requests and enforces their dependencies while allowing such overlap.

Load and Store Bandwidth Limits

Maximum load/store instruction throughput depends on address-generation resources, data-cache ports, queue allocation, store-data bandwidth, alignment, forwarding penalties, and memory disambiguation. A benchmark that streams 32 bytes per cycle in a tight loop may measure a combination of load ports, cache bandwidth, vector-width restrictions, and compiler choices rather than a single LSU component.

A useful arithmetic ceiling is effective bytes/cycle ≤ min(address capacity, data-port capacity, cache/interconnect capacity) after units are normalized. A core with two eight-byte load paths offers an idealized 16 bytes per cycle at that interface, but this number does not guarantee 16 bytes/cycle from DRAM or when the code has serial dependencies. For stores, also consider how many committed bytes per cycle can drain from buffers; temporary burst throughput can exceed sustained downstream bandwidth.

Store-Buffer Coalescing and Write Combining

Adjacent or repeated stores may be merged into fewer downstream transactions if the ISA and memory type permit it. For example, successive byte stores to distinct offsets of a cache line can sometimes be combined before a line update. This reduces traffic, but software may observe effects differently when device-memory or non-temporal write-combining rules apply. Hardware combining must preserve any architecturally required ordering and indivisibility.

Store coalescing within a CPU store buffer and write-combining memory types are not synonyms. Coalescing is an implementation optimization; a write-combining memory attribute can explicitly relax visibility and completion expectations, making appropriate ordering operations important at hardware/driver boundaries. A correct performance experiment distinguishes regular cacheable writes, streaming stores, and MMIO writes rather than treating all memory traffic as equivalent.

False Sharing and Inter-Core Contention

False sharing occurs when distinct variables used by different cores occupy the same coherence line. The LSU may issue independent stores to separate bytes, yet the coherence system transfers ownership of the shared line between cores. The cost is a coherence and layout effect even though there is no same-address RAW dependence. For example, two threads updating separate counters placed in one line can experience high interconnect traffic despite being logically independent.

Padding or per-core sharding can reduce such contention; however, increasing layout size can harm cache residency, and sharding requires a correct aggregation strategy. Measure before and after under controlled affinity and workload conditions. This phenomenon belongs at the intersection of LSU traffic, cache-line granularity, coherence, and data layout—not as evidence that the source program contains a direct memory dependence between its counters.

Prefetching Interactions and Memory Order

Hardware or software prefetching requests cache lines in anticipation of future accesses. A prefetch hint ordinarily does not produce a language-level synchronization event, nor should it be treated as an architectural load of a value. It can nevertheless change cache occupancy, translation activity, bandwidth demand, and the timing of later accesses. Prefetch traffic and demand loads often share memory-system resources and can compete for limited miss-handling capacity.

A correct LSU must keep demand-load faults and architectural values consistent regardless of speculative or prefetch traffic. Some instructions specifically carry fault-suppression or hint semantics, but these are ISA-specific. Tuning prefetch distance requires balancing the lead time needed to hide latency against wasted bandwidth, eviction of useful lines, and extra pressure on downstream resources. It never replaces proper ordering operations in a concurrent program.

A Simple Queue-Pressure Model

This teaching model accepts one memory operation per cycle for three cycles and services one operation every two cycles. It illustrates how an initially empty finite queue accumulates work when arrivals temporarily outpace service; it does not model overlapping cache misses, ROB behavior, or real pipeline scheduling.

from collections import deque

def queue_trace(arrivals, service_every=2, capacity=4):
    queue = deque()
    occupancy = []
    for cycle, arrival in enumerate(arrivals):
        if arrival:
            if len(queue) == capacity:
                raise RuntimeError('Backpressure before admission')
            queue.append(cycle)
        if cycle % service_every == 1 and queue:
            queue.popleft()
        occupancy.append(len(queue))
    return occupancy

assert queue_trace([1, 1, 1, 0, 0, 0]) == [1, 1, 2, 1, 1, 0]
print(queue_trace([1, 1, 1, 0, 0, 0]))

A real performance model must separate LQ from SQ lifetime, track retire events and unresolved dependencies, represent cache misses and MSHRs, and account for bursty issue demand. This example is mainly a diagnostic prompt: what resource is full, and what event finally releases it?

Correctness Invariants for the LSU

Useful invariant statements include: a load's retired bytes must come from architecturally legal sources; an older store that aliases a younger load cannot be silently ignored; a wrong-path store must not produce forbidden architectural side effects; a faulting memory instruction must report the correct exception according to instruction age; committed stores must obey the ISA's visibility rules; and no queue entry or physical register can be reclaimed while a live instruction still depends on it.

These are specification-level obligations, not assertions that each processor must use the same queue structure. A core may implement them through conservative issue, aggressive speculation with replay, in-order memory execution, or different recovery paths. Verification should connect invariants to a reference architectural model and should stress boundary cases such as page splits, missing store data, simultaneous redirects, and multiple overlapping older writes.

Ordering and Value Selection Must Be Checked Separately

An implementation can choose the correct source value for a load and still violate a required ordering relation, or obey an issue-order restriction while returning the wrong bytes from a partial store. The two properties require independent checks. Value selection asks which writes are candidates and which bytes they supply; ordering legality asks whether the overall execution is admitted by the architectural memory model. Add fault and replay behavior as a third, orthogonal dimension.

For example, a store-forwarding function passing all byte-mask tests does not prove that two cores use release/acquire correctly. Conversely, running a set of classic memory litmus tests does not exhaust the bugs in split accesses, duplicate queue entries, or address-translation faults. A comprehensive CPU verification program includes directed microarchitectural tests and architecture-level memory-order tests, plus software-language concurrency tests when compiler behavior is involved.

Formal Verification and Litmus Testing

Litmus tests describe short concurrent programs whose possible outcomes reveal memory-model guarantees. Store buffering, message passing, load buffering, and independent reads of independent writes are common patterns. The expected set of permitted outcomes must come from the target ISA model, not from a guess based on source order. An implementation that produces a forbidden outcome violates the architecture; an allowed outcome is not necessarily evidence of a programming bug when the program is intentionally weakly synchronized.

Formal and simulation-based approaches can model loads, stores, fences, atomics, dependencies, reorder buffers, and forwarding. Differential testing compares the retired execution or event relations with a trusted reference. Random testing is useful but can miss rare interleavings; model checking or exhaustive bounded enumeration provides stronger coverage within its chosen state and instruction limits. Ensure the test suite includes required outcomes only as allowed sets, not as a guarantee that every allowed outcome occurs on every core.

Applied Scenario 1 — Partial Store Forwarding in a Packet Parser

A packet parser writes a two-byte header field into an in-memory record and immediately reads a four-byte word containing that field. A profiler shows unexplained load stalls despite the record remaining in L1. The relevant issue may be partial store-to-load forwarding: the read overlaps the earlier write but requests a larger byte range. A particular processor might merge bytes, stall until a store drains, or replay a load if its fast path requires a suitable size/alignment match.

The engineering review begins with correctness: determine the endianness and field layout, confirm the load reads the most recent appropriate bytes, and verify that unaligned reads are supported by the language and ISA. Only then test alternative layouts or access sizes. In C/C++, reinterpret-casting a structure into an incompatible integer type can introduce alignment and aliasing undefined behavior independent of the CPU's forwarding capability. Use defined loads, copies, or serialization functions and benchmark the optimized implementation. Diagnostic owner: LSU forwarding restrictions, not cache capacity alone.

Applied Scenario 2 — The Store Queue Becomes the Throughput Limit

A processor streams many small stores into a working set whose lines require frequent coherence ownership transfers. The arithmetic execution units show spare capacity, but retirement throughput collapses. A plausible chain is: store traffic waits for ownership or downstream bandwidth, committed stores drain slowly, store-buffer occupancy rises, and the backpressure eventually prevents newer store or ROB entries from making progress. This is distinct from a high load-miss rate, though the two may coexist.

A defensible diagnosis correlates store-buffer stalls with cache-line ownership events, line alignment, and remote-thread activity. Potential remedies include batching, per-thread output buffers, reduction of false sharing, and reducing total write traffic. A store fence inserted without a proven ordering need could worsen the bottleneck. The measurement should report throughput, queue-related stall signals if available, and the effect of a controlled single-thread versus multicore comparison. Diagnostic owner: store retirement/drain and coherence resources.

Applied Scenario 3 — An Older Store Address Is Not Ready

An out-of-order core has an older store whose address depends on a cache miss. A younger independent-looking load already knows its address and is ready to issue. If the core always waits, useful work may be unnecessarily serialized. If it predicts independence and executes, it may later discover that the store aliases the load. A correct design must detect the conflict and replay the load and any affected work without allowing an incorrect result to retire.

An engineering experiment should compare conservative waiting, prediction with replay, and a dependence predictor across traces with different true alias frequencies. Report both useful throughput and replay frequency. Even a highly accurate predictor cannot be the only correctness mechanism; test the rare misprediction path with directed random cases that force late store addresses. Diagnostic owner: memory disambiguation and recovery. The successful outcome is not “no speculation,” but speculation whose mistakes remain architecturally invisible.

Applied Scenario 4 — A Flag Publishes a Data Structure

A producer fills a descriptor and then sets ready; a consumer waits until ready is set before reading the descriptor. On a strong-ordering system, a casual implementation using ordinary shared variables may appear reliable in testing. The same source may fail under compiler optimization, on a different ISA, or under an unanticipated interleaving because the necessary happens-before relation was never established.

The correct design uses a well-defined synchronization API: initialize the descriptor, release-store the ready state, acquire-load the state in the consumer, then access the descriptor only after observing the publication. For more complicated ownership and repeated updates, use a mutex, versioned protocol, or another documented handoff. An acquire/release pair is not a universal solution if multiple writers race over the payload or the consumer accesses it before synchronization. Diagnostic owner: language-level concurrency contract and ISA memory-model lowering—not a presumed faulty cache.

Applied Scenario 5 — A Device Doorbell and Descriptor Ring

A driver prepares a descriptor in memory and then writes a device doorbell register to tell a DMA engine that the work is ready. If the device can observe the doorbell before it can observe the descriptor contents, it may process incomplete work. The appropriate remedy depends on DMA coherence, the platform bus, memory attributes, and the operating-system driver API. A CPU-to-CPU fence mnemonic cannot be assumed sufficient for every device and interconnect.

The engineering plan first establishes descriptor ownership, coherent versus noncoherent memory, required cache maintenance, and the specified ordering of descriptor writes relative to MMIO doorbell writes. It then uses supported platform primitives and verifies behavior with a device-appropriate test. The same review considers whether a status register read has side effects and whether writes can be combined. Diagnostic owner: boundary among LSU, cache maintenance, memory barriers, MMIO, and DMA—not ordinary application-level atomic flags alone.

Applied Scenario 6 — A Pointer-Chasing Graph Traversal

A graph traversal repeatedly loads the next node address from the current node. Even when the memory subsystem can serve many independent misses concurrently, this dependency chain limits exploitable memory-level parallelism. Increasing load queue capacity alone cannot overlap accesses whose addresses are unknown until their predecessors return. The performance bottleneck may be memory latency rather than raw bandwidth.

Potential changes include compacting nodes, improving adjacency locality, processing multiple independent traversal frontiers, precomputing an index, or restructuring the algorithm to expose parallel paths. Such changes may alter memory consumption, update cost, or traversal semantics and must be evaluated against the workload. A strong experiment separately measures pointer-chain latency, working-set size, aggregate memory bandwidth, and independent stream concurrency. Diagnostic owner: data dependence and MLP, with locality as an interacting but separate factor.

Ten-Gate LSU Design and Evaluation Framework

1. Architectural contract Which ISA, memory regions, and memory model apply? Document ordering, atomicity, and alignment guarantees.
2. Value formation Which bytes must each load return? Proven byte masks, endianness, and youngest-older-store selection.
3. Address resolution When are addresses translated and checked? AGU, TLB, permission, and split-access tests.

A design should pass correctness gates before being optimized for peak issue bandwidth. Claims such as “the LSU supports two loads per cycle” do not settle questions about load-to-use latency, replay rates, memory ordering, or the costs of synchronization. The artifact of a successful review is a coherent trace from ISA requirements to queue policy, verified exceptions, performance evidence, and known limitations.

Guided Exercise 1 — Trace a Load From Older Stores

An illustrative store queue contains three older stores: age 1 writes bytes 10 20 at addresses 0–1, age 3 writes 30 at address 1, and age 4 writes 40 50 at addresses 3–4. Memory originally contains 00 in every byte. A load at age 6 reads addresses 0–4. Determine the five bytes in ascending address order. Then explain why an otherwise identical store of age 7 is not eligible to forward to that load.

Check: The value is 10 30 00 40 50. The age 3 store supersedes the age 1 write at address 1; address 2 comes from memory; and the age 7 store is younger than the load in program order. If the address of an older store is unknown when the load issues, the processor may need to wait or speculate with validation rather than relying on an incomplete store list.

Guided Exercise 2 — Predict Queue Pressure

An LSU admits an average of two load instructions per cycle, while the average load-queue residence time is 18 cycles. Estimate average occupancy under stable conditions, then explain two reasons that a 36-entry queue would still be a risky configuration. What if latency occasionally rises to 100 cycles for bursts of misses?

Check: Little's law gives 2 × 18 = 36 average occupied entries. A queue with exactly that capacity has no statistical headroom, and bursty arrivals/long-tail miss latency can push occupancy above the average. Actual residence time includes recovery and retirement policy; rates can also change when queue-full backpressure throttles admission. A practical design measures occupancy distributions rather than using only the mean.

Guided Exercise 3 — Reason About Store Buffering

Two cores begin with x=y=0 and execute store x=1; load y and store y=1; load x. Explain why the both-zero result contradicts sequential consistency but can be legal under a store-buffered model. Then identify a correct way to implement an ordered producer-consumer protocol at the language level, rather than merely inserting an arbitrary delay or relying on one CPU's usual behavior.

Check: SC requires a single total order consistent with both thread orders, which makes the both-zero cycle impossible. Buffered stores can make each other core's newly written variable temporarily unavailable while its own load proceeds. For publication/consumption, use an atomic release store and acquire load linked through the publishing atomic, or use a mutex protecting the state. The precise protocol and memory orders depend on the data ownership pattern.

Guided Exercise 4 — Investigate a Forwarding Stall

A low-level routine performs two-byte stores followed immediately by partially overlapping eight-byte loads. A profiler attributes stalls to memory execution even though the data set fits into the L1 cache. Propose a controlled experiment that can distinguish a forwarding restriction from random cache misses, and identify two correctness hazards that could invalidate a naive code rewrite.

Check: Vary alignment and access width while holding algorithmic work and data footprint constant. Collect load-latency/forwarding-related events where supported and compare a nonoverlapping control pattern. Correctness hazards include C/C++ strict-aliasing or unaligned-access violations, and changes to byte order or value semantics. Any rewrite must produce the same architectural bytes under the same language rules.

Guided Exercise 5 — Review a DMA Descriptor Handoff

A driver writes a descriptor in coherent or noncoherent shared memory and then updates a device doorbell. List the facts needed before deciding whether a barrier is necessary and which one to use. Distinguish CPU-to-CPU publish/consume ordering from CPU-to-device ownership transfer.

Check: Identify the platform's DMA-coherence contract, mapping/cache attributes, descriptor ownership rules, required cache maintenance, MMIO accessors, interconnect ordering, and device specification. Use the operating-system/driver APIs that encode those guarantees. Acquire/release atomics for CPU threads are not automatically equivalent to a device doorbell ordering sequence, nor is an instruction synchronization barrier necessarily relevant to descriptor visibility.

Glossary

Term Meaning
Load/store unit (LSU) CPU execution subsystem that coordinates memory requests, buffering, dependence checks, and ordering.
Address-generation unit (AGU) Hardware that calculates effective addresses for loads and stores.
Program order The architectural sequence of instructions in one thread.
Issue Selection of a ready micro-operation for an execution resource.
Completion Production of a local execution result, not necessarily retirement or remote visibility.
Retirement Ordered acceptance of an instruction's architectural result.
Visibility The circumstances under which another agent can observe a memory write.
Load queue (LQ) Structure tracking outstanding loads and their ordering/replay information.
Store queue (SQ) Structure tracking older stores and address/data readiness.
Store buffer Storage that can retain committed stores awaiting downstream visibility.
Store-to-load forwarding Supplying a younger load from matching older buffered store bytes.
Byte mask Selection of byte lanes that an access modifies or supplies.
Memory disambiguation Determination or prediction of whether memory instructions reference overlapping locations.
Replay Re-execution or recovery after a speculative result is invalidated.
Memory dependence A data- or ordering-relevant relation among memory operations.
RAW dependence A younger read requiring a value written by an older write.
Memory model Architectural/language rules constraining legal memory-access observations.
Sequential consistency (SC) A single order of all operations preserving each thread's program order.
TSO Total-store-ordering style model, used to describe important x86-64 ordinary-memory guarantees.
RVWMO RISC-V weak memory ordering model for relevant memory accesses.
Acquire Synchronization ordering that constrains certain operations after an acquire.
Release Synchronization ordering that constrains certain operations before a release.
Fence Instruction or language construct enforcing specified ordering constraints.
Atomic read-modify-write Indivisible update, according to the specified architecture and granularity.
Cache coherence Per-location/line coordination of cache ownership and observed writes.
MMIO Access to device registers through memory-address-like operations.
DMA Device access to memory without ordinary CPU execution of each transfer.
MLP Memory-level parallelism: concurrent outstanding memory work.
False sharing Coherence traffic caused by independent variables sharing a cache line.
Store buffering litmus Two-thread test revealing whether stores can remain unseen while younger unrelated loads execute.
Precise exception Fault reporting with a coherent architectural state corresponding to an instruction boundary.
Nonblocking cache Cache supporting multiple outstanding misses or useful work during misses.
