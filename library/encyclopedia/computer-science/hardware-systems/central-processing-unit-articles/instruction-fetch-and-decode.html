Definition, Scope, and the CPU Front End

Instruction fetch obtains the encoded instructions that a processor may execute, while instruction decode identifies instruction boundaries, operations, operands, immediate values, and legality from their bit patterns. These operations form the front end of a processor. The front end delivers valid instruction records or internal operations to later stages; it does not itself guarantee that a fetched instruction will execute or retire. Branch prediction and speculation can cause a CPU to fetch instructions that will subsequently be discarded.

The central engineering question is how a core converts an instruction address and an executable byte stream into a timely, correctly identified operation under changing control flow, translation permissions, variable instruction lengths, cache misses, and implementation limits. A fetch interface must preserve instruction identity, the original program counter, encoded length, and any error status long enough for later precise handling. Decode must respect the instruction set and enabled features, rather than infer meaning from arbitrary bit layouts.

Its ownership is the front-end pathway: address selection, byte acquisition, instruction alignment, classification, operand identification, and dispatch interfaces. Detailed execution datapaths, control/exceptions, speculative retirement, cache design, and branch-predictor internals have separate articles.

The Front End as a Multi-Stage System

An illustrative front end includes a next-PC selector; instruction-address translation and an instruction cache or memory fetch interface; a fetch buffer; boundary/alignment logic; an ISA-aware decoder; and an output queue feeding rename, issue, or execution. The exact cut between stages varies. A small in-order core may combine fetch and decode in two stages; a high-throughput superscalar design may have several decode lanes, operation caches, and separate prediction structures.

One useful accounting identity is delivered operations = eligible fetched instruction bytes × valid boundary reconstruction × decoder availability, subject to control-flow correctness and downstream backpressure. This is a conceptual dependency, not a literal multiplication of measured rates. Fetching thirty-two bytes in one cycle does not mean eight four-byte instructions can be dispatched if only four decode slots exist, if a branch redirects mid-bundle, or if the byte stream contains a long instruction split across a boundary.

An architecturally visible instruction may expand into several implementation-private micro-operations, and multiple architectural instructions may be fused in a way not visible to software. Maintain separate counts for bytes fetched, instructions decoded, micro-operations generated, operations issued, and instructions retired. Those denominators answer different performance questions.

Architectural PC, Fetch PC, and Prediction Metadata

The architectural program counter describes the address of an instruction in the software-visible execution sequence according to the ISA. A speculative processor also maintains one or more fetch addresses that may run ahead of the committed instruction stream. A predicted taken branch can redirect fetching before the branch executes; a later correction cancels the wrong-path work. These are not independent architectural PC values created for the program.

Every fetched instruction record should retain its original instruction address and length or enough information to reconstruct them. A front end that passes only decoded operation names downstream loses the ability to report faulting addresses, compute PC-relative targets correctly, or replay an instruction after a recoverable event. The fetch unit may additionally attach prediction identifiers, branch-type hints, page/line origin, or exception tags, none of which necessarily appear in the architectural contract.

Fall-through address selection follows the actual encoded instruction length. In a fixed four-byte ISA, a sequential next address is often PC+4. In RISC-V configurations with 16-bit compressed instructions, fall-through may be PC+2; other encodings are possible under supported extensions. In x86-64, encoded instructions can have variable byte lengths, and the decoder must determine the next boundary before sequential progression can be finalized.

Executable Example: Predict, Redirect, and Cancel

def frontend_trace(program, start_pc, predicted_next, resolved_next):
    pc = start_pc
    fetched = []
    for _ in range(3):
        fetched.append(pc)
        pc = predicted_next.get(pc, pc + program[pc])
    # A resolved branch at 0x1004 invalidates its younger fetches.
    branch_pc = 0x1004
    kept = fetched[:fetched.index(branch_pc) + 1]
    redirected = resolved_next[branch_pc]
    return fetched, kept, redirected

sizes = {0x1000: 4, 0x1004: 4, 0x1020: 4}
all_fetches, retained, new_pc = frontend_trace(
    sizes, 0x1000, {0x1004: 0x1020}, {0x1004: 0x1008})
assert all_fetches == [0x1000, 0x1004, 0x1020]
assert retained == [0x1000, 0x1004]
assert new_pc == 0x1008
print('Canceled younger fetch from', hex(0x1020))

This model tracks addresses, not execution results. An implementation would also cancel queued decode records and manage outstanding fetch responses. It illustrates the correct relationship between a predicted next-fetch address and the address selected after branch resolution.

Instruction Fetch Bandwidth and Fetch Blocks

Front ends often request data in aligned chunks rather than individually reading each instruction from main memory. A fetch block may contain several encoded instructions, some partial instructions, and an early branch. A cache line may be much larger than a cycle’s fetch chunk; conversely, a single instruction may straddle two chunks. Fetch bandwidth is measured in bytes per time or in instructions delivered, and both metrics depend on instruction length and the availability of valid data.

The width of an instruction cache read, the granularity of an interconnect burst, and the number of instructions decoded in a cycle are different parameters. A wide cache can refill a fetch queue while a narrow decoder limits useful progress. A narrow cache or instruction boundary unit may prevent a wide decoder from ever reaching its advertised throughput. Physical alignment also matters because an arbitrary address may lie near the end of an aligned block.

A design must correctly handle instruction bytes crossing a fetch-block boundary and, where permitted, cache-line or page boundaries. The next required bytes must be assembled in order and tagged with the originating PC. Validity must be attached to the combined instruction, rather than assumed merely because its first byte was returned successfully.

Fetch Boundaries, Alignment, and Fragmented Instructions

An instruction boundary is the address at which an instruction begins. It is not necessarily a cache-line boundary, memory-word boundary, or virtual-memory page boundary. Fixed-length ISAs with alignment restrictions simplify boundary discovery, though fetch blocks can still end in the middle of the required fixed-width word. Mixed 16- and 32-bit instruction sets require a preliminary length decision from the encoded stream.

If a 32-bit instruction starts at offset 2 of a four-byte aligned fetch word, the first halfword is in that word and the second halfword is in the next word. An instruction-alignment buffer can retain the partial halfword while waiting for the rest. If the second half is inaccessible, the system must report the architecturally appropriate fetch-related failure rather than interpret a truncated instruction as valid.

The choice of endianness governs how bytes are represented in a multi-byte instruction encoding. It does not authorize simply reversing the entire instruction stream or skipping alignment checks. A robust decoder forms the instruction bits according to the ISA and memory model, then extracts fields at their defined positions.

Executable Example: Gather an Instruction Across Blocks

def gather(code_memory, pc, length, fetch_block_bytes=4):
    # Simplified: a byte-addressed immutable memory dictionary.
    collected = bytearray()
    while len(collected) < length:
        addr = pc + len(collected)
        block_start = (addr // fetch_block_bytes) * fetch_block_bytes
        offset = addr - block_start
        take = min(length - len(collected), fetch_block_bytes - offset)
        for byte_addr in range(addr, addr + take):
            if byte_addr not in code_memory:
                raise MemoryError(f'fetch missing byte at {byte_addr:#x}')
            collected.append(code_memory[byte_addr])
    return bytes(collected)

memory = {0x1002: 0x93, 0x1003: 0x00,
          0x1004: 0x10, 0x1005: 0x00}
assert gather(memory, 0x1002, 4) == bytes.fromhex('93001000')
try:
    gather({0x1002: 0x93, 0x1003: 0x00}, 0x1002, 4)
except MemoryError as error:
    print(error)
else:
    raise AssertionError('a partial instruction cannot succeed')

An actual memory system returns cache lines or bus responses with fault and access metadata, not a Python dictionary. This teaching example ensures a partial instruction cannot silently appear complete when the second fetch block is absent.

Virtual Addresses, Instruction Translation, and Execute Permission

On systems with virtual memory, the instruction fetch address typically must be translated to a physical location before or in parallel with accessing the instruction cache. An instruction translation lookaside buffer (iTLB) caches recent address translations; a miss may require a page-table walk. Each access is also subject to execute permissions and relevant protection controls. Some systems combine translation and cache lookup stages differently, but successful byte retrieval alone is not proof that the instruction was authorized for execution.

Execution permission is distinct from data-read permission in common protection schemes. An operating system may mark a page non-executable even if application code can read it as data; some architectures also have execute-only mappings. A processor must reject instruction fetch from a prohibited page according to its defined exception behavior. Translation caches also require coherent management across address-space changes, page-table updates, and privilege transitions.

When an instruction crosses a page boundary, both relevant parts of the instruction must be fetched under their applicable translation and access rules. A valid first half does not grant permission to fetch the second half from the next page. The effective fault presentation must follow the ISA and privileged architecture; a simplified teaching model should record which byte or portion failed without inventing vendor-specific trap fields.

Executable Example: Permission-Checked Cross-Page Fetch

PAGE = 16  # miniature teaching page, not real hardware page size
pages = {0: {'x': True}, 1: {'x': False}}
image = {14: 0x93, 15: 0x00, 16: 0x10, 17: 0x00}

def fetch_instruction(pc, size):
    output = []
    for addr in range(pc, pc + size):
        if not pages.get(addr // PAGE, {}).get('x', False):
            raise PermissionError(f'no execute permission at {addr}')
        output.append(image[addr])
    return bytes(output)

try:
    fetch_instruction(14, 4)
except PermissionError as exc:
    assert '16' in str(exc)
else:
    raise AssertionError('second-page permission must be checked')
pages[1]['x'] = True
assert fetch_instruction(14, 4) == bytes.fromhex('93001000')
print('Page permission checked for all instruction bytes')

The example intentionally does not simulate a TLB or real page-table format. It enforces the important invariant: every fetched byte must be covered by a permitted executable mapping. Real page sizes, privileges, executable-only behavior, and precise exception classification depend on the platform.

Instruction TLBs, Address-Space Context, and Stale Translations

An iTLB entry usually represents a translation associated with a virtual page and relevant address-space or privilege context. The metadata may include page size, permission and validity bits, global-mapping status, or equivalent implementation fields. Not all cores use the same tagging design. A stale entry can cause incorrect code lookup or permission behavior after a page-table change if the operating system does not perform the required translation synchronization.

There is a distinction between an instruction cache containing previously fetched bytes and an iTLB containing translations. The cache may physically index or tag its data, or use virtual bits under constraints; the TLB holds the address mapping. Invalidation of one structure does not automatically imply invalidation of every other front-end structure. Changes to executable mappings, kernel text, or just-in-time-generated code may demand several distinct synchronization steps.

When diagnosing an apparent fetch from the wrong process, examine the address-space identifier or context-switch discipline, translation shootdowns, privilege permissions, and any use of shared virtual mappings. Do not assume that flushing the instruction bytes alone repairs stale translation state. A page-table update becomes safe only when the architecture-specific ordering and invalidation contract is satisfied.

Instruction Cache, Misses, Refill, and Locality

An instruction cache keeps recently used instruction bytes near the core. Sequential code often benefits from spatial locality; repeated loops benefit from temporal locality. A small hot loop can achieve high instruction supply when its working set fits in the relevant cache and front-end buffers. Frequent calls into scattered code, branch-heavy traces, or a program with a large active code footprint can increase cache pressure and fetch stalls.

A cache hit does not mean decoding is instantaneous. The cache must return bytes, the boundary logic must identify complete instructions, and the decoder must produce a valid operation. Conversely, a cache miss may be partly hidden by prefetch and buffering, but misses that interrupt the critical fetch stream can starve downstream stages. This makes instruction-side cache-hit metrics useful yet insufficient by themselves to diagnose front-end performance.

Cache associativity, line size, physical placement, replacement policy, and prefetch design are implementation choices. This article treats them as front-end constraints; the CPU Cache Hierarchies and Locality specialist article owns their detailed hardware design.

Executable Example: An Instruction Cache Working-Set Toy

from collections import OrderedDict

def miss_count(fetch_pcs, line_size=16, capacity_lines=2):
    # Fully associative LRU teaching cache: line identity only.
    lines = OrderedDict()
    misses = 0
    for pc in fetch_pcs:
        line = pc // line_size
        if line not in lines:
            misses += 1
            if len(lines) == capacity_lines:
                lines.popitem(last=False)
        else:
            lines.pop(line)
        lines[line] = None
    return misses

loop_pcs = [0, 4, 8, 12] * 5
spread_pcs = [0, 16, 32, 0, 16, 32] * 3
assert miss_count(loop_pcs) == 1
assert miss_count(spread_pcs) == len(spread_pcs)
print('hot loop:', miss_count(loop_pcs), 'miss; spread:',
      miss_count(spread_pcs), 'misses')

No real cache model is this simple: a line may be prefetched, accesses can overlap, associativity is not necessarily fully associative, and virtual translation adds another dimension. Nevertheless, the example shows why the instruction footprint of a program affects effective front-end bandwidth.

Instruction Density and Effective Fetch Capacity

An instruction set with shorter average encodings can fit more instructions into an equal number of fetched bytes, though it does not follow that every instruction runs faster. Encoded density influences instruction-cache footprint, fetch traffic, and boundary complexity. A compressed instruction extension can reduce code size, but the decoder must discover whether each instruction is compressed and expand or directly interpret it as defined by the ISA.

Consider an eight-byte fetch group. It may contain two four-byte instructions, four two-byte instructions, or another legal mixture. In a mixed-width program, the front end must count completed instructions, not merely words or halfwords, and correctly carry partial encodings to the next group. A branch partway through a group can limit the number of useful instructions delivered on the predicted path.

Compression can change where an instruction falls relative to cache lines and pages. It may also change branch offsets and code layout. Results are workload-dependent: better code density can reduce instruction misses, yet additional decompression logic and changes in alignment can offset part of that benefit. Any performance claim should specify the implementation, instruction mix, and measurement conditions.

Executable Example: Byte Supply Versus Decode Width

def theoretical_delivery(fetch_bytes, mean_instruction_bytes,
                         decode_slots, output_capacity=None):
    if mean_instruction_bytes <= 0 or fetch_bytes <= 0 or decode_slots <= 0:
        raise ValueError('positive capacities required')
    by_bytes = fetch_bytes / mean_instruction_bytes
    caps = [by_bytes, float(decode_slots)]
    if output_capacity is not None:
        caps.append(float(output_capacity))
    return min(caps)

assert theoretical_delivery(16, 4, 4) == 4
assert theoretical_delivery(16, 2, 6) == 6
assert theoretical_delivery(8, 4, 6) == 2
assert theoretical_delivery(16, 4, 6, output_capacity=2) == 2
print('Supply and decode impose separate upper bounds')

The estimator uses an average encoding length and assumes a steady state; it is an upper-bound illustration rather than a measured IPC prediction. Real fetch/decode rates are further limited by alignment, branch redirects, queue occupancy, cache misses, instruction complexity, and back-end stalls.

Prefetch Buffers, Fetch Queues, and Backpressure

A prefetch buffer or fetch queue decouples an upstream cache or memory interface from downstream decode. If the cache delivers an instruction group while the decoder is temporarily busy, the bytes may remain queued rather than being discarded. During a brief fetch miss, the decoder can continue consuming previously buffered instructions. Queues therefore smooth intermittent supply and demand, although they cannot overcome a sustained imbalance.

Each queue entry requires clear validity and ordering rules. For variable-length instructions, the queue may store raw bytes and associated starting address or may store predecoded instruction boundaries. Additional tags can record predicted control-flow path, exception status, privilege context, or sequence identity. A redirect must invalidate entries younger than the redirecting instruction, even if they have already crossed a fetch-cache boundary.

Backpressure prevents overflow when downstream resources are full. If decode cannot accept another item, the fetch queue must retain it without duplication; if the fetch queue is full, upstream fetching must stall or use a defined buffering mechanism. Loss, reordering, replay without invalidation, and stale fault tags can cause correctness failures that ordinary arithmetic instruction tests do not expose.

Instruction Fetch Faults and Error Attribution

Fetch can fail because the next instruction address is misaligned under the active ISA, the address lacks a valid translation, execute permission is denied, a memory or bus access fails, or an error-detection mechanism rejects returned bits. These failures have distinct architectural classifications, and a processor may represent them internally with tags that accompany the affected instruction. Not every bus transaction problem must immediately stop the machine; the relevant issue is whether the failing instruction would become architecturally observable.

A wrong-path speculative fetch might encounter an inaccessible address and later be squashed because an older branch resolves differently. A correct processor must not expose that discarded path as if the application executed it. On the correct path, however, a fetch fault must be reported using the architecture-defined exception and PC rules. Later stages often carry the faulting PC and cause until the instruction reaches the appropriate precise reporting point.

An instruction that straddles a page boundary is particularly instructive. Fetching its first portion successfully does not justify manufacturing the remaining bits. If the second portion faults, the implementation must preserve enough information to report the event correctly and must not decode unrelated bytes as a replacement. Detailed trap encoding and privilege transition behavior belong in CPU Control Logic and Exception Handling.

RISC-V Instruction-Length Classification

The base RISC-V integer ISA uses 32-bit instructions. With a compressed instruction extension, the stream may contain 16-bit encodings as well as 32-bit encodings and aligned instruction addresses can be two-byte boundaries. The standard encoding convention uses the lowest two bits of the first 16-bit parcel to distinguish ordinary 16-bit encodings from 32-bit-or-longer instruction encodings. In the common RV32/64 I+C subset, a halfword whose low two bits are not 11 starts a 16-bit instruction; otherwise the next 16 bits must be considered for a 32-bit instruction candidate.

Important qualification: a decoder for a general RISC-V implementation must also understand defined longer-length encodings when supported, and reject reserved or unsupported patterns. The classifier below intentionally accepts only a teaching subset of 16- and 32-bit lengths; it is not a full RISC-V length decoder or an ISA conformance test. It must not claim that every pattern with the low two bits equal to 11 is necessarily a valid 32-bit instruction.

The instruction-start alignment parameter IALIGN is 32 bits for the base ISA and becomes 16 bits with compressed-capable configurations. A taken jump to a prohibited alignment can cause an instruction-address-misaligned exception; a branch that is not taken need not generate the same event solely because its unused target would have been misaligned.

Executable Example: RISC-V 16/32-Bit Length Teaching Model

def limited_riscv_length(first_halfword, compressed_enabled):
    if first_halfword & 0b11 != 0b11:
        if not compressed_enabled:
            raise ValueError('16-bit instruction unavailable without C')
        return 2
    # The lowest five bits 11111 indicate longer/reserved length forms;
    # this miniature model deliberately refuses them.
    if first_halfword & 0b11111 == 0b11111:
        raise ValueError('unsupported longer/reserved encoding')
    return 4

assert limited_riscv_length(0x0001, True) == 2
assert limited_riscv_length(0x0093, True) == 4
assert limited_riscv_length(0x0093, False) == 4
for sample in (0x0001, 0x001F):
    try:
        limited_riscv_length(sample, False)
    except ValueError:
        pass
    else:
        raise AssertionError('unsupported encoding was accepted')
print('Common C/32-bit lengths classified, unsupported forms rejected')

Instruction length and instruction legality are separate decisions: an encoding can have a recognizable length while representing a reserved or unsupported operation. Production implementations require the complete applicable ISA length and decode rules, including exact exception behavior.

def sequential_pcs(start, lengths):
    pc = start
    result = []
    for length in lengths:
        if length not in (2, 4):
            raise ValueError('toy model supports 2- or 4-byte instructions')
        if pc % 2:
            raise ValueError('misaligned instruction address')
        result.append((pc, length))
        pc += length
    return result, pc

A four-byte instruction may legally start at a two-byte boundary when IALIGN=16; it can then span aligned four-byte fetch chunks. Validity still depends on its actual encoded bits, platform feature support, and permitted executable memory.

x86-64 Instruction Boundaries and Prefix Processing

x86-64 encodings are variable-length and may include instruction prefixes, opcode bytes, an addressing-form byte (ModR/M), an optional scale-index-base (SIB) byte, displacement, and immediate fields. Their presence depends on the instruction and mode. Front-end boundary detection can be more involved than slicing the instruction stream into fixed four-byte words, particularly when one instruction ends near a cache-line boundary and another begins in the same group.

The architectural instruction-length limit in ordinary Intel 64 and IA-32 encodings is fifteen bytes. A robust decoder must enforce it and apply the documented prefix rules; extra prefixes are not simply ignored without consequences. A variable-length front end may use predecode metadata or specialized length decoders to identify instruction starts before full semantic decode. Implementation details differ substantially across processor generations.

Do not equate boundary detection with semantic validity. A sequence can have a discoverable length but contain an illegal opcode, an unsupported extension, or invalid prefix usage. Conversely, a byte pattern that resembles a simple opcode may be data or a field of another instruction if decoding begins at the wrong location. Correct disassembly requires known code boundaries and mode context, not a visual scan for mnemonic-looking bytes.

AArch64 Instruction Alignment and Fixed Fields

In AArch64 execution using the A64 instruction set, instructions are fixed-width 32-bit words with defined field positions and four-byte instruction alignment. This regularity simplifies instruction boundary detection and parallel field extraction. It does not remove the need for instruction translation, execute permission checks, correct endianness handling, code-memory synchronization, or branch redirection.

A64 decoders classify instructions from combinations of opcode fields rather than from one universal contiguous opcode field that identifies every instruction family. Register specifiers, immediates, condition encodings, and operation variants occupy different positions in different instruction classes. A decoder should therefore implement the proper class-specific encoding tables, not merely use the fact that all instructions are four bytes long.

An important taxonomy distinction is that “Arm” encompasses different ISA states and instruction encodings across products and historical generations. The current comparison is specifically about AArch64 A64, while older A32/T32 and some microcontroller configurations have different length and alignment rules. Broad statements about all Arm-family hardware must not silently substitute A64 behavior.

Opcode Classification, Operand Fields, and Decode Products

After boundaries are identified, semantic decoding determines what each legal instruction means. Typical outputs include an operation class, architectural source/destination register indices, immediate operands, memory access width, control-flow classification, instruction length, and extension or privilege constraints. Later pipeline stages may translate this into internal control signals or micro-operations; the exact representation is an implementation choice.

For example, a simple register-immediate addition decoder needs to identify its opcode, funct fields, source register, destination register, and a properly sign-extended immediate. It must also confirm that the encoding is legal in the configured ISA. A branch decoder needs its source indices and reconstructed signed PC-relative offset; other instructions need different format-specific assembly rules. Reusing one bit-extraction rule for all classes is a common source of incorrect decoders.

The decode record should preserve provenance: original PC, raw encoding, decoded length, valid/illegal status, and any fetch exception. If the front end speculates, a younger record also needs a way to be invalidated. These attributes make later fault reporting, instruction retirement, and verification possible without pretending the decoder is the whole processor.

RISC-V ADDI: Field Extraction and Sign Extension

RISC-V base integer ADDI is an I-type instruction. The low seven opcode bits identify the broad integer-immediate class; bits 14–12 provide the function field, bits 19–15 select the first source register, bits 11–7 select the destination, and bits 31–20 contain the signed 12-bit immediate. In RV32I and RV64I, the immediate is sign-extended to the machine width for the arithmetic operation.

For the encoding 0xFFF10093, the operation is ADDI x1, x2, -1. The source register number and destination number are architectural indices; they do not say where the operand is physically stored in a renamed implementation. The calculation may later be performed by an ALU, but this decoder’s responsibility is to produce a correct instruction description.

It is essential to validate both opcode and function class before calling an encoding ADDI. A general I-type opcode may identify other operations; the same immediate field positions do not make every instruction an add-immediate. The example below intentionally recognizes exactly one instruction family.

Executable Example: Decode a RISC-V ADDI Word

def signed(value, width):
    sign = 1 << (width - 1)
    return (value ^ sign) - sign

def decode_addi(word):
    opcode = word & 0x7F
    funct3 = (word >> 12) & 0x7
    if opcode != 0x13 or funct3 != 0:
        raise ValueError('not an ADDI encoding')
    return {'op': 'ADDI',

            'rs1': (word >> 15) & 31,

Branch Immediate Reconstruction: Noncontiguous Bits

RISC-V B-type branches encode their signed branch offset in scattered bit positions instead of one contiguous immediate field. The reconstructed byte offset takes imm[12] from bit 31; imm[10:5] from bits 30–25; imm[4:1] from bits 11–8; and imm[11] from bit 7. The low offset bit is zero. The sign bit must be extended before the offset is added to the address of the branch instruction itself.

This encoding illustrates why decoding cannot stop at identifying opcode and register indices. The correct branch-target formula requires assembling an offset from the defined fields, respecting sign, and using the original branch PC. Adding the offset to the already incremented fall-through PC would be incorrect for the RISC-V branch class. Prediction hardware may supply a target early, but the eventual architectural calculation must use the ISA rule.

The branch’s comparator semantics depend on funct3 and operand values. Decoder outputs typically classify whether the operation is BEQ, BNE, BLT, BGE, BLTU, or BGEU, while downstream execution decides whether the condition holds. In a given configuration, unsupported or reserved encodings must be rejected rather than being guessed into a nearby class.

Executable Example: Decode a RISC-V B-Type Offset

def sign_extend(value, width):
    return (value ^ (1 << (width - 1))) - (1 << (width - 1))

def branch_offset(inst):
    imm = (((inst >> 31) & 1) << 12)
    imm |= (((inst >> 7) & 1) << 11)
    imm |= (((inst >> 25) & 0x3F) << 5)
    imm |= (((inst >> 8) & 0xF) << 1)
    return sign_extend(imm, 13)

def beq_word(rs1, rs2, offset):
    assert offset % 2 == 0 and -(1 << 12) <= offset < (1 << 12)
    bits = offset & 0x1FFF
    return ((((bits >> 12) & 1) << 31) |
            (((bits >> 5) & 63) << 25) |
            ((rs2 & 31) << 20) | ((rs1 & 31) << 15) |
            (((bits >> 1) & 15) << 8) |
            (((bits >> 11) & 1) << 7) | 0x63)

for offset in (-4096, -18, -2, 0, 2, 18, 4094):
    word = beq_word(1, 2, offset)

    assert branch_offset(word) == offset

The helper assembles BEQ encodings for instructional testing and omits some real-world legality and alignment conditions. The signed 13-bit branch offset has a range of −4096 through +4094 in two-byte steps; available legal branch-target alignment also depends on the ISA configuration.

Decode Records and Register Dependency Metadata

A decoded instruction often becomes a structured internal record containing operation type, source register identifiers, destination register identifier, immediate value, memory attributes, and control-flow classification. The record is not necessarily an execution command ready to run immediately; it can be queued until data dependencies and resources are satisfied. The decision to create physical register mappings, to allocate reorder-buffer entries, or to issue work belongs to later stages in many cores.

An in-order implementation can read architectural registers during decode and forward operands to execution. A more complex implementation may decode register names first and later rename those names into physical dependencies. In either design, the decoder must not mislabel which source registers an instruction reads or which destination it writes. That error can create silent data corruption even if the ALU produces a mathematically correct result for the operands it receives.

Unneeded source fields should not be treated as real dependencies. For example, bits that occupy an rs2-like position in one format may be immediate bits in another. If a dependency checker blindly assumes every instruction reads two sources, it may introduce needless stalls or, worse, read the wrong physical value. Decode is therefore a central interface between the ISA encoding and the core’s dataflow machinery.

Executable Example: Minimal Decode Records

from dataclasses import dataclass

In this model, None denotes an absent destination or immediate. Real decoders additionally preserve legality, memory order, fault, prediction, privilege, and pipeline-control metadata. The key property is that the record corresponds to one specific encoded instruction at one specific PC.

Illegal Encodings, Unsupported Extensions, and Privilege

Not every possible instruction bit pattern is legal. ISA documents define reserved encodings, feature-dependent operation families, and privilege restrictions. The decoder must classify an instruction under the current execution mode and enabled ISA configuration. An instruction may decode to a known mnemonic in a reference manual yet still be unavailable on a processor lacking the relevant extension or illegal in the current privilege level.

The implementation may mark such a record as an illegal instruction or another architecturally defined exception and carry that status to the precise handling point. No operand operation should silently run under an approximate interpretation. Particularly dangerous is a decoder that matches only a broad opcode and ignores required function bits, accidentally accepting a reserved encoding as a supported operation.

The front end should separate three questions: (1) do the bytes constitute a complete instruction of recognized length; (2) is the encoding legal for the configured ISA and current execution context; and (3) are its attempted effects permitted when actually executed? Certain access checks may be performed later than initial byte decoding, and some system instructions have context-sensitive effects. The result must preserve the architecture’s defined observable behavior.

Branch Prediction and the Fetch Address Stream

Branch prediction attempts to keep the instruction supply moving before a conditional branch’s outcome is known. A direction predictor estimates taken versus not taken, while a branch-target buffer may remember target addresses; return prediction mechanisms can use a return-address stack or another model of call and return behavior. These structures help choose the next fetch address. They are not the ultimate authority on which instructions belong to the program’s committed path.

A prediction can be perfectly accurate for direction but still lead to incorrect fetching if its target is wrong, stale, or associated with the wrong control-flow instruction. Conversely, a correct target with a wrong direction prediction wastes fetch bandwidth. When a branch eventually resolves, its computed direction and target must be compared to the prediction. Any younger instructions on an incorrect path are invalidated, with a redirect to the correct address.

Branch predictors can be shared or partitioned among hardware threads, and their data structures can have aliasing: distinct branch PCs map to the same prediction entry. Aliasing is an implementation-performance issue and, in some settings, a security consideration. Detailed predictor organizations and recovery schemes belong to Branch Prediction and Speculative Execution.

Executable Example: A Two-Bit Saturating Direction Predictor

class TwoBitPredictor:
    def __init__(self):
        self.counters = {}
    def predict(self, pc):
        return self.counters.get(pc, 1) >= 2
    def observe(self, pc, taken):
        old = self.counters.get(pc, 1)
        self.counters[pc] = min(3, old + 1) if taken else max(0, old - 1)

model = TwoBitPredictor()
assert model.predict(0x1000) is False
for outcome in (True, True, True):
    model.observe(0x1000, outcome)
assert model.counters[0x1000] == 3
assert model.predict(0x1000) is True
model.observe(0x1000, False)
assert model.predict(0x1000) is True
model.observe(0x1000, False)
assert model.predict(0x1000) is False
print('Hysteresis avoids flipping on a single contrary outcome')

The model predicts direction only. It does not predict targets, handle speculative history, use global correlations, or model rollback. It demonstrates the idea of hysteresis: a strongly learned branch pattern may require multiple contrary observations before the direction estimate reverses.

Call, Return, and Indirect Branch Prediction

Direct unconditional branches often have targets derivable from their instruction encoding and PC. Conditional branches additionally need an outcome estimate. Indirect branches and returns can be harder because the target depends on register or stack state that is not necessarily available during fetch. A branch-target buffer or indirect-target predictor supplies a provisional destination before downstream execution validates it.

A return-address stack is a common performance mechanism that predicts where a function return will go by tracking call and return patterns. It approximates a software call stack but is not an architectural substitute for it: unusual control flow, exceptions, unbalanced returns, or context transitions can upset predictions. The processor must recover from a wrong prediction, rather than assume the predictor’s stack is always correct.

Indirect branches are important for virtual method dispatch, function pointers, switch tables, interpreters, and callbacks. Their target predictability is workload-dependent. An application’s branches should be profiled before attributing a throughput problem to instruction-cache misses or decoder width; frequent indirect mispredictions can cause front-end flushes even when every required instruction is already cached.

Instruction Redirects, Flushes, and Replay

The front end must respond not only to ordinary branches but also to exceptions, interrupts, serialization operations, address-translation changes, and selected pipeline recovery events. Some events redirect to an architecturally specified target; others require replay of an instruction or refetch from a known address. The implementation chooses queue flush, tag cancellation, checkpoint recovery, or other internal techniques to satisfy the defined architectural behavior.

Cancellation needs to reach every outstanding younger operation, including decode-buffer entries that have not been dispatched and fetch responses that arrive after the redirect. A common failure mode is allowing a late return from a discarded fetch request to enter a newly restarted queue as though it belongs to the correct path. Sequence identifiers or epochs can prevent that confusion: data returned under an old path tag is rejected after the redirect.

Replay is not equivalent to re-executing an instruction with architectural side effects twice. The recovery boundary must guarantee that repeated speculative work does not produce duplicate committed stores, duplicated exceptions, or externally visible device actions. Detailed rollback and retirement rules belong to neighboring CPU specialist articles; the front end’s responsibility is correct instruction identity and orderly re-supply.

Executable Example: Fetch Epochs Prevent Stale Responses

class FetchControl:
    def __init__(self):
        self.epoch = 0
        self.accepted = []
    def request(self, pc):
        return (self.epoch, pc)
    def redirect(self):
        self.epoch += 1
    def response(self, token, bytes_):
        issued_epoch, pc = token
        if issued_epoch != self.epoch:
            return False
        self.accepted.append((pc, bytes_))
        return True

f = FetchControl()
old = f.request(0x1000)
f.redirect()
new = f.request(0x2000)
assert not f.response(old, b'OLD')
assert f.response(new, b'NEW')
assert f.accepted == [(0x2000, b'NEW')]
print('Late old-path response rejected')

Epoch tagging is one possible design technique. Real hardware may need separate sequence numbers, reorder checkpoints, request IDs, and per-resource response handling; simply incrementing one counter does not implement all aspects of a CPU redirect.

Decoding Several Instructions per Cycle

A superscalar front end attempts to deliver multiple instructions per cycle. It needs sufficient fetch bytes, boundary information, parallel decoding resources, and downstream queue capacity. If instruction lengths vary, the core must find several instruction starts in the same fetch group, and each decoder may support only certain complexity classes. A “four-wide decoder” specification generally does not mean all possible groups of four instructions can be processed without constraints.

Parallel decoding must preserve the program order of the decoded instruction records even if later execution is out of order. Branches may terminate or redirect a group, and a partial instruction at the end of a fetch group may need more bytes before it can enter a decode lane. Some front ends partition decode lanes into simple and complex paths, use a micro-op cache, or limit how many complicated macroinstructions can be decoded in one cycle.

The appropriate performance metric is the sustained instruction or micro-operation delivery rate for a representative instruction mix, not a theoretical maximum observed only on an ideal stream. Internal micro-op counts can exceed architectural instruction counts. If comparing processors, explicitly state whether throughput refers to fetched bytes, decoded macroinstructions, micro-operations, dispatched operations, or retired instructions.

Decoder Width, Micro-Operation Generation, and Fusion

In some processors an architectural instruction translates into one internal micro-operation; in others it can produce several. Some front ends fuse certain instruction patterns into a combined internal unit of work under specific implementation rules. This complicates simple calculations that equate one decoder slot with one issued operation. For example, two adjacent architectural operations may be recognized as a useful pair without changing the architectural result that software observes.

Architectural instruction semantics remain defined by the ISA even when a particular microarchitecture performs early fusion or uses a special internal operation format. A debugger and disassembler should still report the original instruction sequence, not invent a replacement machine-code instruction simply because the hardware fused work internally. The trace must retain enough source mapping to report exceptions and precise retirement correctly.

Fusion and expansion are not guaranteed for all instruction arrangements or all microarchitectural generations. Code-layout, operand selection, branch type, and implementation heuristics may affect whether a pattern qualifies. An engineering performance review should consult the relevant processor documentation and measure actual event counts before claiming a given compiler pattern will always fuse.

Micro-Operation Caches and Alternate Supply Paths

Some high-performance processors cache already-decoded internal operations, reducing repeated work by the full instruction-length decoder on frequently executed code. Such an operation cache is distinct from an instruction cache of encoded bytes, although both exploit locality. Its presence can change the front-end bottleneck: a loop may run quickly from the decoded supply path but slow down when its operations do not fit or when a control-flow transition misses the operation cache.

A decoded-operation cache needs to respect program identity and instruction changes. It cannot return stale operations after executable code changes unless the ISA and system software have satisfied the appropriate synchronization requirements. Depending on the implementation, cache tags and invalidation rules may incorporate address translation, execution context, or other metadata. These are vendor-specific details, not universal CPU requirements.

A cache hit is not equivalent to an executable instruction being free of instruction-side stalls. A downstream queue can fill, an operation can be blocked by resource limits, or a branch can redirect the supply stream. Performance analysis should distinguish decoded-operation hits from retired instruction throughput and should preserve the architectural-to-internal-operation mapping.

Microcode and Complex Decode Paths

Some instruction-set implementations use microcode or sequenced internal operations for selected complex instructions, exceptional operations, or implementation management tasks. A decoder can identify an instruction whose execution requires a microcode assist or internal control sequence. In such designs, a single architectural instruction may temporarily consume special front-end or execution resources that reduce the throughput of nearby instructions.

The term microcode should not be used loosely for every internal operation. Many modern processors decode common instructions into micro-operations without using an accessible microcode program for every instruction. The exact interface between the decoder, microcode sequencer, and execution resources is architecture-specific and can vary across generations.

This article covers the handoff: decode identifies the operation class and any special sequencing requirement. The detailed internal translation, patching, and sequencing design belongs to Microcode and Internal Operation Translation. A front-end review should identify whether unusual latency is due to instruction supply, expansion, specialized sequencing, or back-end execution.

Fetch-to-Decode Latency Versus Steady-State Throughput

Latency describes how long an individual instruction takes to travel from selected fetch address to an available decoded record. Throughput describes how many instructions or internal operations can be delivered per unit time when the pipeline is full. A processor can have a deep front end with substantial latency yet high steady-state throughput; conversely, a short in-order pipeline may have low latency but limited decode width.

Misses and redirects make latency variable. An L1 instruction-cache hit may supply bytes rapidly; an iTLB miss can require a translation walk, and an I-cache miss can take much longer depending on the memory hierarchy. Predictions sometimes hide part of front-end latency, but a wrong prediction reveals recovery cost because the core must refill from a corrected address.

Instruction-level parallelism, back-end execution width, and retirement resources impose additional limits that a faster front end cannot overcome. An honest analysis isolates front-end stalls and measures them in the context of the workload. Confusing the maximum advertised decode width with actual instructions retired per cycle exaggerates potential performance gains.

Stall Attribution and Front-End Performance Counters

Processor performance counters may report instruction-cache misses, translation misses, branch mispredictions, decoded-operation cache events, stalled cycles, and delivered operations. Hardware event names and definitions vary, so counter values from different processor families should not be compared as though they were identical measurements. Aggregate “front-end bound” estimates often depend on derived formulas and sampling conventions.

A robust investigation correlates counter data with code layout, branch profiles, cache behavior, and actual workload outcomes. If the decoder is empty for many cycles, the cause could be a fetch miss, an instruction boundary problem, a target redirect, or upstream throttling. If decode frequently produces valid operations but the queue cannot accept them, the bottleneck is downstream backpressure rather than an inadequate instruction cache.

Use performance measurement to test a hypothesis, not to select a narrative after seeing one number. Ensure profiling runs have stable workload inputs, comparable processor frequencies, and enough observations to avoid mistaking startup transients for steady-state behavior. Cross-check that improvements in front-end supply translate into completed program work rather than merely higher speculative activity.

Multi-Core, Simultaneous Multithreading, and Instruction Supply

In a multicore processor, each core commonly has its own front-end machinery, although details of shared cache capacity, power budgets, and interconnect services vary. In simultaneous multithreading, multiple architectural thread contexts may compete for front-end cycles, buffers, prediction capacity, and downstream execution resources. A scheduler may prioritize ready threads or alternate which context supplies the next fetch address.

One thread stalled on an instruction-cache miss can sometimes leave fetch or decode capacity available for another thread. That benefit depends on which resources are shared and whether the stalled thread occupies critical queues. The interaction can also cause interference: two threads with large or conflicting code footprints may displace each other’s instruction cache lines or predictor entries.

Performance attribution should identify the thread and core context rather than treating all fetched bytes as belonging to one linear instruction stream. The architectural state of one thread must remain isolated even if the front end shares prediction tables or decode execution units. Detailed resource partitioning is treated in Simultaneous Multithreading and Hardware Contexts.

Self-Modifying Code and Instruction Visibility

A processor may have recently fetched or cached instructions from an address before software modifies the corresponding bytes. The architecture and execution environment define how a new instruction stream becomes visible after code writes. Data-cache coherence alone does not always establish the required ordering of instruction fetch with code stores; specialized instruction synchronization or cache maintenance may be necessary.

On RISC-V systems implementing the Zifencei extension, FENCE.I provides defined local synchronization between stores to instruction memory and subsequent instruction fetch on the same hart. System software must also address cross-hart synchronization through its appropriate mechanisms. On other ISAs, different instruction/data cache maintenance and synchronization requirements apply. The exact recipe must come from the platform documentation, not a generic assumption that executable bytes update instantaneously.

Just-in-time compilation, dynamic instrumentation, hot patching, and firmware update paths all require deliberate code-publication protocols. A system should prevent execution of incomplete instruction sequences and coordinate executable permissions, instruction visibility, and thread access. This article explains the fetch-side hazard; it does not replace the OS and security guidance for writable/executable mappings and safe code deployment.

Instruction-Side Consistency and Memory-Ordering Boundaries

Instruction bytes live in memory, but the ordering rules for ordinary data loads and stores do not necessarily settle when code changes must be observed as instructions. The distinction is fundamental in processors with separate instruction and data caches. Some architectures maintain additional coherence rules or synchronization operations; others require system software to perform explicit maintenance before executing newly generated code.

Translation changes are another separate issue. Changing page-table execute permission or remapping a virtual instruction page may require invalidating translation information, while changing instruction bytes may require instruction-side synchronization. Executing the correct updated code can therefore involve two conceptually different contracts: the address maps to the intended physical page with suitable execute rights, and the instruction fetch stream observes the intended contents.

A practical failure report should state whether the observed stale behavior came from an old translation, old instruction-cache bytes, stale decoded operations, or a race between writers and executing threads. The remedy differs by mechanism. Simply labeling the event “cache incoherence” conceals distinctions important for debugging and security.

Speculative Fetch, Permissions, and Security Boundaries

Speculative fetching may access instruction-side structures before a branch is resolved. The architectural result of a wrong-path fetch must not masquerade as a committed exception or executed instruction. Nevertheless, speculation can modify implementation-private structures such as prediction or cache state, and those changes can have timing consequences even when the speculative instruction never retires.

This distinction motivates protections against microarchitectural side channels. The precise risk depends on the processor, code, threat model, and mitigation configuration. A front-end security review should consider predictor state sharing, indirect-target influence, cross-context isolation, instruction-cache timing, and the possibility that software could infer information from contention. It should not claim that every speculative fetch reveals secret data or that a software-level permission rule automatically prevents every timing effect.

Instruction decode also forms an input-validation boundary: illegal encodings, malformed instruction sequences, and unsupported features must not trigger undefined behavior in the core’s control logic. Design verification should include adversarial instruction streams and privilege transitions. The specialist CPU Security Isolation and Speculative Side Channels covers the deeper mitigation landscape.

Front-End Power and Area Trade-Offs

A wider front end requires more fetch bandwidth, more boundary-finding capability, more decode lanes, and often more queue capacity. These structures consume silicon area and energy, while their benefit depends on whether the workload and downstream pipeline can use the additional supply. A core targeting low-power embedded applications may favor simpler in-order fetch/decode even if that reduces maximum throughput.

Prediction tables, instruction caches, and operation caches consume both static and dynamic power. A front end that aggressively fetches wrong-path instructions wastes energy as well as cycles. Techniques such as clock gating, selective prediction, throttling, and careful queue sizing can reduce unnecessary work, but they require correct control and verification under stalls or resets.

Architectural decisions should use realistic performance-per-watt and area budgets. The fastest front end in isolation may be an inefficient system choice if it starves execution, spends most cycles predicting low-value work, or exceeds thermal limits. Power comparisons should distinguish workloads and manufacturing contexts rather than asserting that one instruction encoding or cache structure is universally superior.

Front-End Correctness: Required Invariants

An effective verification plan starts with invariants independent of the implementation’s performance. Identity: each accepted decoded instruction corresponds to the intended bytes at a well-defined PC. Completeness: no incomplete or unsupported encoding is silently executed. Order: records delivered to the architectural instruction sequence preserve control-flow and sequential order, even when internal execution reorders later. Fault attribution: a fetch or decode fault remains attached to the correct instruction.

Other invariants cover cancellation (no wrong-path record can commit), flow control (a valid instruction is neither dropped nor duplicated under backpressure), permissions (all instruction bytes are accessed under applicable rules), and liveness (the front end eventually delivers instructions when the memory system responds and downstream resources accept them). Liveness needs fairness and environment assumptions; it cannot be established merely by checking one transition.

Assertions should distinguish response validity from semantic legality. A fetched word may have valid memory data yet encode an illegal instruction; a branch may be legally decoded but predicted incorrectly. These conditions require different expected responses. A strong test suite maintains a reference decoder and independent execution trace rather than only confirming that the DUT agrees with its own generated control signals.

The randomized check validates the address walk, not the legality of the encoded instructions. To test a real decoder, generate legal and illegal instruction byte streams from an independent ISA specification and compare the decoded fields and exception behavior.

Six Applied Scenarios: Evidence Before Explanation

The following scenarios combine a symptom, a technical distinction, and a testable verification route. They are constructed teaching cases, not reports of incidents at MGU or measurements from a particular CPU. They demonstrate why instruction fetch and decode should be treated as an integrated system that is nonetheless separable from the rest of the processor.

Each scenario asks what evidence would distinguish an instruction-supply problem from a downstream execution problem and what correctness requirement survives performance optimization. Engineers should collect a PC trace, source encoding or disassembly, translation and cache context, and pipeline-validity information appropriate to their implementation before deciding on a remedy.

Scenario 1 — A Compressed Instruction Straddles a Fetch Block

A compact RISC-V program has a 32-bit instruction beginning at address 0x1002. The first halfword comes from one aligned four-byte fetch word and the second from the next. A faulty predecoder assumes every 32-bit instruction is word-aligned and instead decodes the last halfword as a separate compressed instruction. The resulting program counter drifts, and the subsequent disassembly no longer matches the instruction sequence the compiler emitted.

The correction is to classify length from the first halfword under the active ISA configuration, retain the partial instruction, fetch the needed additional bytes, and combine the instruction before semantic decode. A directed test must cover both aligned and offset-two 32-bit instructions, plus a missing or inaccessible second fetch block. The test should compare original PCs, lengths, raw encodings, and decoded operation identities—not merely the total number of instruction words returned.

If the assembled instruction crosses a page boundary, permissions for the second page must also be respected. This is why an instruction-alignment buffer must be part of a correct fetch interface rather than an optional performance shortcut.

Scenario 2 — A Small Loop Is Slower Despite I-Cache Hits

A numerical loop fits entirely in the L1 instruction cache, and cache-miss counters are near zero, yet the core rarely reaches its expected instruction retirement rate. Measurements show frequent branches, occasional incorrect target predictions, and limited decoder delivery after redirects. The I-cache is supplying bytes quickly, but control-flow recovery prevents continuous decode and dispatch.

A useful experiment changes code layout or branch behavior while keeping arithmetic work comparable. Compare branch prediction statistics, delivered operations, queue-empty cycles, and retired instructions per cycle. If the predictor improves but the throughput does not, a different bottleneck—decode width, data dependencies, or execution ports—may dominate. If predictor changes improve delivered instruction supply and program time, the evidence supports a control-flow limitation.

This scenario illustrates the limit of using a single cache-hit metric as a proxy for front-end health. An instruction can be present in cache yet fetched at the wrong time or from a repeatedly discarded path.

Scenario 3 — A JIT Compiler Executes Yesterday’s Code

A just-in-time compiler writes a new instruction sequence into an allocated code region. One thread attempts to execute it immediately. The application occasionally appears to execute stale instructions even though a data read of the region shows the new bytes. The likely causes include missing instruction-cache synchronization, an unsafe publish protocol, or executing concurrently with a writer; the exact problem must be diagnosed under the platform’s architecture and OS contracts.

The implementation must ensure that the generated instruction sequence is complete, that the appropriate instruction-visibility operation has been performed, and that execution permissions and thread synchronization are correct. For RISC-V, the locally defined role of FENCE.I in Zifencei is relevant, while cross-hart synchronization requires additional coordination. Other ISAs prescribe different cache-maintenance and barrier sequences.

A successful test involves repeated code publication and execution under concurrency while checking the resulting behavior and required synchronizations. It is not sufficient to verify only that a memory debugger displays the new bytes.

Scenario 4 — A Wide Decoder Is Starved by a Narrow Fetch Path

A six-instruction-per-cycle decoder is connected to a front end that typically delivers only sixteen instruction bytes per cycle. The running program averages roughly four bytes per instruction. Under favorable alignment, the fetch side can supply only about four instructions per cycle even if the decoder has idle lanes. More complex instruction boundaries and taken branches can reduce that number further.

Increasing decode width alone would not solve the bottleneck. An engineer should assess whether wider byte delivery, improved instruction density, a decoded-operation supply path, or branch-target improvements would raise real throughput without excessive energy and area cost. The correct benchmark is completed program work under representative workloads, not an isolated decoder demonstration.

If the average instruction length falls to two bytes, the bottleneck can move from fetch bandwidth to decode width or downstream queues. The same hardware can therefore exhibit different front-end ceilings for different instruction mixes.

Scenario 5 — A Page Boundary Masks a Fetch Permission Error

A 32-bit instruction begins near the end of an executable page, but its final bytes are on a neighboring page without execute permission. An incomplete teaching emulator reads the first bytes and substitutes zero for the missing remainder, incorrectly reporting a legal operation or an illegal encoding rather than the correct instruction-fetch access failure.

The repair is to tie byte assembly to per-page translation and permission checks. A failure in the second page must be preserved with the instruction’s original starting PC and any architecture-specific fault metadata. The emulator must not silently fill absent bytes or continue decoding the next page as unrelated instructions.

The directed test should cover a valid/valid pair, valid/non-executable pair, valid/unmapped pair, and a fetch on a wrong speculative path that is ultimately canceled. This distinguishes access permission, instruction completeness, and precise exception behavior.

Scenario 6 — A Hot-Patch Redirect Accepts an Old Fetch Response

A running system installs a new branch target and redirects fetch, but an outstanding memory transaction for the former path returns after the redirect. Without a valid sequence tag, the late response enters the new queue and is decoded at an address associated with the wrong path. The problem appears intermittent because it depends on memory latency and timing.

A front end can attach a fetch epoch or comparable generation identifier to each request and response. A redirect invalidates queued younger work and causes responses from the old generation to be discarded. Tests deliberately vary response order and latency, including responses arriving on the same cycle as a redirect, and assert that the decoded instruction stream corresponds to a single legal path.

This protection should coexist with architectural instruction-memory synchronization. A correct epoch tag prevents wrong-path contamination, but it does not by itself guarantee that a newly patched code region is visible to instruction fetch. Separate consistency contracts must both be satisfied.

Study Pathway and Hands-On Laboratory

A productive study sequence begins with a binary instruction trace and progresses toward a coupled front-end model. First, hand-decode a small set of legal RISC-V ADDI and B-type examples; include negative immediates and edge offsets. Second, run the mixed-length PC walker with different 2- and 4-byte sequences, marking fetch-group boundaries. Third, add memory access permissions and deliberately split an instruction across a prohibited page boundary.

Next, add a finite-capacity fetch queue and an epoch-tagged branch redirect. Inject cache-latency delays and verify that instructions never duplicate or disappear under stalls. Finally, collect delivered-instruction counts and compare them against a theoretical fetch-byte/decode-width ceiling. Be explicit about why the actual rate is lower when branches, misses, or downstream stalls occur.

The goal is not to build a production superscalar core in one exercise. It is to establish correct instruction identity, legality, stateful flow control, and a defensible performance accounting model. Each increment should have independently testable invariants and repeatable inputs.

Review Questions and Worked Guidance

  1. What is the difference between a fetch PC and the architectural PC? The fetch PC may follow predictions and run ahead; the architectural instruction address identifies the program-visible instruction stream as defined by the ISA.
  2. Can a four-byte instruction begin at PC=0x1002? Yes in an ISA configuration allowing halfword alignment, such as RISC-V with a suitable compressed extension; not as a general rule for an IALIGN=32 configuration.
  3. Why is a second-page permission check necessary? All bytes of a spanning instruction must be fetched from authorized mapped memory; a valid first half does not authorize the second.
  4. How does instruction density affect fetch bandwidth? Shorter mean encodings can deliver more instruction boundaries per fetched byte, but correctness, decode capacity, branch behavior, and back-end throughput remain limiting.
  5. What does a branch predictor output? A provisional direction and/or target that selects future fetching; the actual branch semantics must eventually validate that prediction.
  6. What is the decoder’s response to an unsupported instruction? Identify the encoding as unavailable or illegal under the configured ISA rather than inventing a valid operation.
  7. Why can I-cache hit rate be high while IPC is low? Branch redirects, decode bottlenecks, alignment, queue pressure, and back-end stalls can prevent useful progress.
  8. Why is FENCE.I significant on RISC-V? Under Zifencei it defines local synchronization between prior code stores and subsequent instruction fetch on that hart; cross-hart coordination is separate.

Guided Exercise 1 — Build a Fetch-Boundary Model

Start with a byte-addressed instruction image of at least thirty-two bytes that contains both two-byte and four-byte RISC-V instructions under a constrained C-enabled teaching subset. Track PC, length, and the aligned four-byte fetch-block addresses needed for each instruction. Add an intentionally truncated final instruction and assert that the model rejects it instead of reading a default zero value.

Deliverable: a table containing instruction-start PC, length, fetched blocks, and decode/fetch status, plus tests for an instruction beginning at address 2 mod 4. Explain how your model would change if longer RISC-V encoding forms were supported. The primary evaluation criterion is correctness of boundaries and error reporting, not the number of instructions per second.

Guided Exercise 2 — Implement a Redirect-Safe Fetch Queue

Model a two-entry fetch queue with delayed memory responses. Attach a generation number to each request. On branch resolution, update the fetch address, increase the generation, and invalidate younger queued records. Send old responses after the redirect and confirm that none are admitted to the new queue. Repeat under a downstream decoder stall.

Deliverable: a timestamped trace of accepted, stalled, canceled, and rejected records. Prove that no accepted instruction appears twice and that a wrong-path item cannot reach the execution interface. Distinguish the path-generation tag from instruction-memory synchronization: an epoch prevents path confusion but does not determine when newly written code becomes visible.

Guided Exercise 3 — Explain a Measured Front-End Bottleneck

Assume a front end can supply 16 instruction bytes per cycle, classify four instruction boundaries, decode six instructions, and deliver at most four decoded records to a downstream queue. Evaluate ideal ceilings for an average instruction length of four bytes and then two bytes. Next, introduce a branch redirect every twelve useful instructions with a three-cycle supply interruption and derive an approximate effective throughput under your explicit pipeline assumptions.

Deliverable: a table of limiting stage, theoretical ceiling, redirect-loss assumption, and calculated delivered instruction rate. Recompute after widening fetch to 24 bytes and describe when the improvement would matter. An answer should identify why such an analytical model cannot replace event-counter data on a particular processor.
