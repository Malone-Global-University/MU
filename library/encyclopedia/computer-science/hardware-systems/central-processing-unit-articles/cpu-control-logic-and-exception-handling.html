Definition, Ownership, and Scope

CPU control logic interprets decoded work, coordinates processor state changes, selects the next instruction address, and reacts to exceptional events. Control is not one physical box: an implementation may distribute it among a decoder, issue logic, pipeline-valid gates, finite-state sequencers, control/status registers, branch-resolution circuitry, interrupt arbitration, and completion or retirement hardware. These pieces together ensure that legal instructions make the promised architectural state transition and that exceptional events divert execution safely.

An exception commonly arises synchronously from executing or attempting to execute an instruction: an illegal opcode, instruction-access fault, privilege violation, memory fault, breakpoint, or deliberate environment call. An interrupt is generally a request from a timer, device, interprocessor signal, or other source that need not correspond to the current instruction. RISC-V calls the transfer to a handler for either class a trap. Architectures vary in terminology and in which conditions are restartable, maskable, deferred, or fatal.

Learning Objectives and Key Questions

A reader should be able to identify the source of a control decision, distinguish faults from interrupts, explain which state is saved on a trap, and trace how a processor cancels younger work while preserving earlier results. They should also be able to separate the ISA contract from implementation-specific priorities and software policy.

The Hardware Control Path: From Decode to Trap Entry

A useful mental model has three interacting paths. The ordinary instruction-control path selects operands, function units, register destinations, and memory commands. The control-flow path decides sequential fetch versus branch, jump, or replay. The exception-control path takes error and interrupt reports, determines an eligible cause, prevents forbidden state updates, captures trap information, redirects fetch, and coordinates architectural state restoration.

The same physical multiplexers may serve ordinary branches and trap-vector redirects, but the authorization conditions differ. A branch is part of instruction semantics; a trap can change privilege mode, update cause/status registers, suppress side effects, and transfer control to an architecturally designated handler. An exception reported by a load may be discovered many cycles after decode, while the controller must still attribute it to the load rather than to whatever younger instruction is currently at the front of the machine.

The event logic often interacts with cache/TLB protection checks, error-correcting code reports, memory ordering, debug, and retirement. The key design objective is not just “jump to a handler”; it is to construct a well-defined machine state from which authorized software can diagnose, recover, retry, terminate, or report failure.

Combinational Decode Versus Sequential Control

An instruction decoder can generate control bits as combinational functions of opcode fields and privilege state: ALU selection, operand-source choice, memory-read/write intent, and register-write intent. This resembles a truth table mapping an instruction class to controls. However, multicycle operations and error recovery need state: the machine must remember whether a load is outstanding, whether a divider is busy, whether a flush is in progress, and whether it has entered a handler.

A finite-state controller may move through RESET, FETCH, DECODE, EXECUTE, WAIT, WRITEBACK, and TRAP_ENTRY states. It can hold the same decoded instruction stable across several cycles, assert a request only when a bus is ready, and withhold completion until an acknowledgment arrives. A deeply pipelined core instead combines per-instruction valid bits, queues, hazard checks, exception metadata and retirement arbitration, preserving the same general architectural responsibilities with more decentralized hardware.

The important distinction is that control state is not identical to architectural state. A pipeline occupancy bit or waiting-for-memory flag can change every cycle without changing a program register. Conversely, a committed register write changes architecturally visible state and must follow the ISA-defined ordering and privilege conditions.

Teaching Model: A Decoder Producing Control Decisions

from dataclasses import dataclass

@dataclass(frozen=True)
class Control:
    alu: str
    mem: str = 'none'
    reg_write: bool = False
    next_pc: str = 'sequential'

CONTROL = {
    'ADD': Control('add', reg_write=True),
    'AND': Control('and', reg_write=True),
    'LOAD': Control('add', mem='read', reg_write=True),
    'STORE': Control('add', mem='write'),
    'BEQ': Control('eq', next_pc='conditional'),
    'ECALL': Control('none', next_pc='exception'),
}

def decode(opcode):
    if opcode not in CONTROL:
        raise ValueError('illegal instruction')
    return CONTROL[opcode]

assert decode('LOAD').mem == 'read'
assert decode('STORE').reg_write is False
assert decode('ECALL').next_pc == 'exception'
print('Decoder control decisions passed')

This is a compact instruction-class teaching table, not an encoding decoder. Actual decode logic also checks bit fields, implemented extensions, current privilege, instruction legality and operand sizes. An illegal encoding is a synchronous exception in an architecture that defines that behavior; it must not silently become a no-op just because no matching row is found.

Finite-State Sequencing and Handshake Control

A multicycle load provides a useful example of control state. After address generation, the load-store unit issues a request and waits for its response. The controller must not claim completion before data is valid, and it must not reissue the same request merely because the target stalls. If a bus fault arrives with the response, the instruction needs an exception record instead of a destination-register write. If an older branch invalidates the load as speculative work, the core may need to suppress the result or avoid making an irrevocable external effect.

Handshake interfaces typically use valid/ready or request/grant conventions. Their exact timing depends on the bus protocol. A simple controller can assert a stable request until acceptance; a pipelined design may allow many transactions outstanding, match responses with transaction tags and route each error back to its originating instruction. Neither model makes a system correct unless write side effects, retries and cancellation obey the memory system contract.

Control invariants include: a transaction is accepted at most once for a given request handshake; a register write occurs only for a valid, authorized instruction; a response is associated with the correct originating operation; and a faulted instruction does not commit a forbidden destination change.

Teaching Model: Multicycle Load Controller

def load_controller(responses):
    state, issued, result = 'ISSUE', 0, None
    for ready, fault, data in responses:
        if state == 'ISSUE':
            if ready:
                issued += 1
                state = 'WAIT'
        elif state == 'WAIT':
            if fault:
                state = 'TRAP'
            elif data is not None:
                result, state = data, 'DONE'
        if state in ('TRAP', 'DONE'):
            break
    return state, issued, result

assert load_controller([(False,False,None),(True,False,None),
                        (False,False,42)]) == ('DONE',1,42)
assert load_controller([(True,False,None),(False,True,None)]) == ('TRAP',1,None)
print('Load sequencing and fault suppression passed')

The model deliberately splits request acceptance and response completion into separate observations. Some buses can return data in the same cycle as acceptance, and real designs must support their interface specification. The code illustrates suppression of a register result on a response fault; it does not model memory ordering, bus side effects, or speculative cancellation.

Exception, Interrupt, Trap and Abort: Terminology

These words are frequently mixed across ISA manuals, operating systems and developer discussions. Here, a synchronous exception means an event causally associated with a particular instruction or attempted instruction; an asynchronous interrupt is an externally or independently signaled request that the processor elects to service at a permitted point. A trap is a transfer of control into an exception or interrupt handler under an ISA-defined rule. An abort often describes a condition that cannot be repaired by simply retrying, although formal classifications differ across processors.

RISC-V explicitly uses trap as the umbrella term for an exception or an interrupt. x86 uses the terms fault, trap, and abort as classes of exceptions with different saved-instruction-pointer and restart semantics. Arm uses its own exception-level, vector and asynchronous exception categories. No single named processor’s terminology should silently be projected onto the others.

Faults are not necessarily programmer errors. A page fault may be expected and recoverable under virtual memory; a deliberate environment-call instruction intentionally enters privileged code; a physical memory integrity error may require containment or shutdown. The control mechanism reports and transfers; software and platform policy decide the appropriate response.

Synchronous Exceptions and Instruction Attribution

Synchronous events include decoding an unsupported instruction, violating an instruction-access permission, using a forbidden privileged instruction, triggering a breakpoint, and generating a data-access or address-translation fault. The event is tied to an instruction address and often a specific accessed address or additional fault information. This provenance enables software to distinguish whether it should emulate an instruction, map a missing page, signal a process, or treat the fault as unrecoverable.

The detection point is not necessarily the architectural reporting point. Illegal-instruction detection often occurs during decode; a load fault may be detected during a cache/TLB walk or on a delayed memory response; some arithmetic operations detect their conditions during execute. A processor capable of out-of-order execution can have faults from several instructions “in flight,” yet it should present the oldest relevant fault at the required retirement boundary and cancel younger state updates.

A synchronous exception need not be maskable via the ordinary interrupt enable bits. For example, illegal-instruction and access-fault exceptions in common RISC-V implementations remain active even when regular maskable interrupts are disabled. Whether an event can be delegated to a lower privileged handler is a separate question from whether it can be disabled.

Asynchronous Interrupts and Admission Windows

An interrupt may originate from a periodic timer, peripheral completion, interprocessor request, or platform interrupt controller. The source asserts a pending condition; interrupt eligibility depends on per-source enable, global enable, current privilege and delegation or routing settings. The CPU normally services an eligible interrupt at an instruction boundary defined by the architecture rather than during an uncontrolled half-written result.

Pending does not necessarily mean immediately serviced. A higher-priority exception may be taken first; interrupts may be disabled in a critical section; a core may be unable to admit an interrupt until an architecturally uninterruptible operation or finite internal sequence reaches an acceptable boundary. Platform controllers and ISA extensions may alter the available priority policy. Source acknowledgment and deassertion are commonly the responsibility of the handler and interrupt-controller integration, not of the CPU datapath alone.

“Interrupt latency” includes detection/synchronization, selection, completion of older work, redirect and pipeline refill, handler prologue, and potentially cache/TLB service. It is not simply one fixed number of clock cycles for all programs or cores.

Reset, Nonmaskable Interrupts and Debug Entry

Reset establishes a documented initial hardware state and starting control flow; it is usually neither an ordinary software exception nor a recoverable interrupt. An NMI is intended for high-urgency situations and is not governed by the ordinary interrupt mask mechanism, but its nesting, exact vector, record and recoverability are implementation- or extension-specific. Debug entry may suspend ordinary execution and preserve separate debug state instead of entering the normal operating-system handler.

Control units must define priority for simultaneous reset, debug request, NMI, synchronous fault and ordinary pending interrupt. A design might make reset unconditional, debug special, and maskable interrupts eligible only after older instructions commit; the actual order comes from the selected ISA and implementation specification, not from a universal list. A reliability-critical design also needs a defined response if an exception occurs while its trap entry is already underway.

The open-source Ibex core is a useful concrete case: its controller coordinates boot, branch redirects, interrupts and debug, and its exception documentation distinguishes normal maskable interrupts from an external NMI and internal error indications. These details describe Ibex and its supported privilege modes, not every RISC-V processor.

Event Provenance, Tags and Exception Metadata

Hardware needs to preserve enough information to identify the instruction that generated an exception. In a simple in-order core this can be its PC, instruction word and a fault-valid bit associated with the pipeline stage. In a machine with several outstanding memory operations, the load-store queue or reorder buffer may attach an exception tag, cause, fault address, and completion status to a particular instruction. That metadata must survive scheduling changes until a legal reporting boundary.

A typical event record may contain valid, cause, fault_pc, fault_address, instruction_id, and optional auxiliary status. Some fields are architecture-defined control/status registers; others are transient microarchitectural tags. They should not be confused: the existence of a fault address in an internal queue does not imply the architecture exposes it in a particular CSR on every event.

On squashing speculative work, a controller should discard or invalidate its exception metadata along with the instruction. Conversely, an older fault cannot be lost because a younger branch misprediction or new fetch event arrives. Event provenance is a correctness property, not just a debugging convenience.

Priority Is Conditional and Architecture-Specific

At least three priorities must be distinguished. Within one instruction, more than one synchronous error condition may be possible and the ISA specifies which cause is reported. Across instructions, precise state usually requires honoring program-order commitment so an older fault takes precedence over a younger one. Among interrupt sources, the privileged architecture, interrupt controller and implementation jointly define eligibility and priority. A single global integer “priority of every possible event” is often an inaccurate model.

For example, an instruction fetch can encounter address translation and access-check conditions along the way; the reported cause depends on architecture-specific priority rules and what checks are reached. An illegal instruction might also have would-be operand addresses, but speculative address computation must not create an externally visible younger fault. Interrupt-controller arbitration can change which pending interrupt is chosen without changing the older synchronous-exception rule.

Practical verification should vary pending masks, privilege modes, outstanding instruction ages, and fault combinations. A simplistic model that always services the highest interrupt number first, or always makes a timer interrupt override a synchronous fault, is not a sound generic CPU model.

Instruction Fetch Exceptions and Redirection

Instruction-side translation, execute permission and physical access can each prevent fetching a legal instruction. The fetch pipeline may discover a fault for a predicted path that is later discarded; that speculative fault must not necessarily become an architectural exception if its instruction is never reached in the committed program path. A real exception is attributed to the architecturally relevant instruction and routed through the selected trap mechanism.

Once a trap is selected, the controller redirects the fetch PC to the appropriate vector, invalidates wrong-path instruction buffers, and associates the new stream with a new privilege context. If a branch predictor or prefetch mechanism has outstanding work, the processor must distinguish data returned for the old path from data for the handler path. The exact flush granularity and whether speculative cache effects are also undone depend on microarchitecture; architectural flushing does not imply that every microarchitectural trace vanishes.

Trap-vector alignment and permissions matter. If a handler address is invalid, or instruction fetch from the handler itself faults, recovery can escalate to special fault handling or a fatal condition. This is a separate design and software-integration problem from selecting the original exception cause.

Illegal Instructions, CSR Privilege and Software Calls

An instruction can be illegal because its encoding is not defined, an optional extension is absent, a required privilege is not available, or some restricted control/status operation is prohibited. Control must reject it without allowing its nominal writes to leak into architectural state. Some systems intentionally handle absent instructions through emulation, but that policy belongs to the privileged software environment and depends on whether an appropriate handler exists.

An environment call—ECALL in RISC-V, SVC in AArch64, or other architected system-call mechanisms—is a deliberately generated synchronous exception, not merely an ordinary function call. Hardware changes the exception context; the handler interprets service numbers and arguments according to an operating-system-defined ABI. The CPU does not inherently know that an integer means “open file” or “schedule a task.”

Breakpoints may be explicit trap instructions or debug-triggered events. Their routing and saved state differ by architecture and debug configuration. The distinction matters in a debugger: stopping before an instruction, executing a breakpoint instruction, and triggering a hardware watchpoint are related but not interchangeable operations.

Memory Faults, Alignment and Protection

A load or store can encounter an unmapped virtual address, a forbidden access permission, an address alignment rule, a physical memory access error, or a bus/device fault. These mechanisms are distinct. A page fault often relates to page-table translation and permissions; an access fault may relate to physical access/protection or memory-system constraints. Some processors support misaligned memory operations directly, some handle them in multiple micro-operations, and others raise a synchronous condition.

For stores the timing problem is especially important. Once a write reaches a device with irreversible effects, “undoing” it may be impossible. Many designs therefore hold stores until the required instruction-order safety point, or otherwise provide implementation-specific guarantees. A fault detected after partial externally visible effects can demand special handling and may not have the same simple restart semantics as a fault caught before memory modification.

Page-table walks can themselves require memory accesses and generate translation-related failures. A TLB hit is not evidence that a program has blanket permission; the active translation context, privilege and access type are part of the checks. The handler may repair mapping and retry, terminate a process, or report a machine-level failure. CPU hardware supplies the evidence and enforcement mechanism; software chooses policy.

Arithmetic Exceptions and Status Are ISA-Dependent

An integer divide-by-zero instruction is not automatically a processor trap. For example, the RISC-V integer M extension defines architectural quotient and remainder values for division by zero, whereas x86 integer divide instructions can raise a divide-error exception. Likewise, integer overflow may wrap by ISA definition or update condition flags without trapping. A high-level language runtime may raise an exception after detecting an overflow even if the underlying machine arithmetic did not trap.

Floating-point exceptional conditions are also easy to mislabel. IEEE-style operations can generate accrued invalid-operation, divide-by-zero, overflow, underflow or inexact status, but the standard RISC-V floating-point extensions do not provide traps for these status conditions. Other ISAs may support masked or unmasked FP exceptions with different delivery rules. The ALU/FPU specialist article owns the arithmetic calculations and status formation; this article owns the control paths when an event is actually an architecturally reportable trap.

An engineer should consult both the instruction semantics and privileged architecture before deciding whether a result is committed, whether a flag is set, and whether exception-control logic must enter a handler. The words “arithmetic exception” in application code do not prove that the processor took an architectural exception.

Recoverable Faults Versus Machine-Check Conditions

Recoverability depends on provenance, the architectural contract and the system response. A demand-paged load can often be restarted after its mapping is installed. An ECC-detected correctable error may be corrected transparently, reported through telemetry, or delivered through a deferred notification. An uncorrectable cache or memory error, control corruption, or failure while entering a handler may require stopping a process, isolating a core, resetting a subsystem, or halting the machine.

A machine-check or reliability event is not guaranteed to be a precise, synchronous instruction fault. Some errors are detected after data has moved across a system boundary; some are recorded after the affected operation; and some have insufficient provenance for safe restart. A system that claims universal precise recovery for every hardware error would be overstating what most architectures guarantee.

Trap priority, error-containment domain, recovery register formats, logging interfaces, firmware involvement, and machine-check architecture vary widely. The hardware should avoid silently continuing with corrupted state where integrity cannot be established. Such mechanisms are developed more fully in the CPU Reliability, Error Detection, and Recovery specialist article.

A Compact RISC-V Trap Record

RISC-V’s machine-level trap architecture is a useful concrete example. When a trap is taken into M-mode, the hardware records the interrupted or faulting instruction address in mepc, a cause in mcause, and, for selected events, supplementary information in mtval. It also records and modifies privilege/interrupt-enable state in mstatus and directs execution using mtvec. These are machine control and status registers (CSRs), not ordinary integer registers.

Not every cause supplies the same mtval data: it may hold a faulting address, relevant instruction bits, or zero, according to cause and implementation rules. The high interrupt-indicator bit in mcause differentiates interrupt causes from synchronous exception causes. Standard cause numbers represent classes such as illegal instruction, instruction access fault, load access fault, or machine external interrupt; extensions may add causes.

The processor does not automatically save every general-purpose register to a software stack on normal trap entry. The trap handler prologue must preserve whatever general-purpose, floating-point, vector or other software-visible state is needed by its calling convention and execution path. Trap-state CSRs and software-saved register context are therefore different layers of the recovery protocol.

Trap Entry: Ordered Hardware Actions

Consider a machine-level synchronous exception for an instruction whose PC is 0x120. A simplified architectural transition is: select the valid exception in program order; write mepc = 0x120; put its cause into mcause; populate mtval as defined for that event; copy mstatus.MIE to mstatus.MPIE; clear MIE; save prior privilege in MPP; enter M-mode; and redirect the PC to the trap handler selected by mtvec. Architectural instructions younger than the trapping instruction must not commit forbidden effects.

The hardware does not promise that these actions happen as separate visible clock cycles in that textual order. They describe the atomic architectural state that software observes on entry. Detailed control machines may perform redirect and CSR updates through different internal pipelines. The source of mepc differs for a synchronous exception versus an interrupt: an interrupt typically records the address at which execution should resume; it need not name an instruction that actually caused the interrupt.

If software intends to skip a deliberate ECALL instruction after handling it, the handler must set an appropriate continuation PC before returning. It must know whether the trapped instruction was 2 or 4 bytes where compressed encodings are supported; unconditionally adding four to every fault PC is incorrect. Restarting a faulting load often means retaining the original fault PC instead.

Teaching Model: Trap Entry and MRET State Restoration

from dataclasses import dataclass

@dataclass
class PrivState:
    pc: int = 0x120
    privilege: str = 'U'
    mie: bool = True
    mpie: bool = False
    mpp: str = 'U'
    mepc: int = 0
    mcause: int = 0
    mtval: int = 0

def trap_to_machine(state, cause, tval=0, vector=0x800):
    state.mepc = state.pc
    state.mcause = cause
    state.mtval = tval
    state.mpie = state.mie
    state.mie = False
    state.mpp = state.privilege
    state.privilege = 'M'
    state.pc = vector

def mret(state):
    state.pc = state.mepc
    state.privilege = state.mpp
    state.mie = state.mpie
    state.mpie = True
    state.mpp = 'U'   # Teaching platform implements U and M

s = PrivState()
trap_to_machine(s, cause=2, tval=0xFFFFFFFF)
assert (s.mepc, s.privilege, s.mie, s.mpp) == (0x120,'M',False,'U')
assert (s.mcause, s.mtval, s.pc) == (2,0xFFFFFFFF,0x800)
mret(s)
assert (s.pc, s.privilege, s.mie, s.mpie) == (0x120,'U',True,True)
print('M-level trap-entry and MRET teaching model passed')

This demonstration represents selected standard state transitions and intentionally fixes a two-level U/M teaching machine. It omits privilege-sensitive routing, delegation, fields such as MPRV, and optional extensions. In a real MRET, state restoration follows the supported RISC-V privileged specification, including additional status effects; writing these fields as ordinary software assignments is merely a teaching device.

Trap Vectors: Direct and Vectored Modes

In RISC-V mtvec has a BASE and MODE component. Direct mode sends both synchronous exceptions and interrupts to the BASE address, where software examines mcause. In standard vectored mode, asynchronous interrupts dispatch to BASE + 4 × interrupt_cause_code, while synchronous exceptions still enter at the BASE. Supported modes and alignment restrictions are architecture-defined. Firmware or an OS must install valid handler code and configure the vector before enabling events that require it.

The offset convention does not imply that every handler needs just four bytes. The target slot may contain a short branch to a larger routine. Nor does an interrupt vector replace source acknowledgment: handler code may still have to identify and clear a peripheral or platform interrupt-controller condition. On some implementations there are implementation-specific NMI or fast-interrupt vectors outside the baseline general rule.

A design review should check vector alignment, writable CSR limitations, executable permissions, escalation on handler fetch faults, and the behavior when an unsupported MODE value is requested. Incorrect vector assumptions can create a chain of traps with no valid recovery path.

    if mode == 'direct':
        return base
    if mode == 'vectored':
        return base + 4 * cause_code if interrupt else base
    raise ValueError('unsupported mtvec mode')

Pending Interrupts, Enables and Privilege Routing

For ordinary RISC-V machine-level interrupts, eligibility depends on pending and per-source enable bits, privilege routing, and global-enable rules. In M-mode, mstatus.MIE is relevant for M-level interrupt delivery; if execution is at lower privilege, the machine-level gating rules differ. mip represents pending indications and mie enable controls, but some bits may be read-only, supplied by external controllers, or affected by extensions and delegation.

Supervisor-level routing introduces mideleg, sie, sip, and S-mode status where supported. A delegated interrupt is not merely the same M-mode interrupt at a lower numerical priority. It has a different target privilege, mask context, and possibly a different handler vector. Hardware also must avoid delivering a supervisor-directed interrupt when the target privilege is not eligible under its rules.

Platform controllers such as PLIC or the Advanced Interrupt Architecture can identify and prioritize external sources; they should not be conflated with the per-hart privileged CSRs. A core-level model must say whether it assumes the platform has already selected an interrupt identity, rather than pretending that all possible devices directly occupy mie bits.

Interrupt Arbitration and Multiple Pending Sources

If several interrupts are enabled and pending simultaneously, the system has to select one to deliver or expose to software. For standard RISC-V machine interrupts, the privileged architecture defines baseline priority relationships; extensions and platform facilities can supply additional source-specific priority controls. A core should not infer order merely from bit positions unless its implementation specification explicitly says so.

An interrupt request can remain asserted after the CPU vectors to its handler. If the handler fails to clear the peripheral condition or acknowledge the interrupt controller, the same source can retrigger immediately on return. Conversely, edge-triggered information can be lost if crossing and latching are designed incorrectly. Correct integration requires specified level/edge behavior, synchronization to the CPU clock domain, pending persistence, acknowledgment and completion sequencing.

Fairness is not automatic. A constant stream of high-priority events can starve low-priority work; systems may use coalescing, rate limiting or software dispatch. Those are system-level policies layered over the CPU’s eligibility and exception-entry mechanism.

Exception Delegation and Supervisor Traps

Many general-purpose operating systems need exceptions from applications to enter supervisor code without requiring every event to be handled first by the machine firmware. Where implemented, RISC-V exception and interrupt delegation registers allow selected causes to be handled at S-mode under the defined rules. A delegated trap uses the supervisor trap CSRs and handler vector instead of overwriting machine trap records, subject to the architecture’s routing constraints.

Not all exceptions can be delegated in every configuration, and machine-level events cannot be redirected down into less privileged code merely because a bit was set. The available delegation masks are governed by implemented privilege levels and standardized capabilities. An instruction fault in S-mode may have different routing from the same kind of fault in U-mode, and virtualization adds virtual-supervisor/guest-specific trap state where the H extension is supported.

Hardware controls the privilege transition and records why it occurred; the operating system owns page-table updates, system-call dispatch, signal delivery and other policies. Failing to separate these layers leads to diagrams that falsely claim that a CPU controller “allocates memory” or “opens a file” during trap entry.

Privilege Checks and Unauthorized Control Transfers

Privilege checks protect control/status registers, instruction classes, address-translation configuration and memory-mapped regions. A processor should verify the access rights for the current execution mode and report a defined exception for a prohibited operation. An ordinary program instruction cannot simply jump into kernel privilege by setting a branch target; privilege elevation is mediated by architected exception/trap mechanisms and privileged return rules.

The handler entry must establish the proper target mode before fetching privileged instructions. Similarly, a trap return needs to restore a valid prior mode rather than taking arbitrary application bits as trusted privilege commands. System software may deliberately configure delegations, permissions and interrupt masks, but these configurations themselves require authorized access. A control block that suppresses memory protection checks only on the normal path but not on a replay or debug path would create a security boundary failure.

Defense-in-depth testing includes illegal CSR accesses, attempted privileged instructions in U-mode, unexpected trap returns, virtual-memory permission failures, and simultaneous debug/exception events. The exact expected cause comes from the ISA and implementation configuration; tests should not invent generic trap numbers.

Returning From a Trap and Instruction Restart

A trap-return instruction restores machine state according to the privileged ISA and transfers execution to the saved continuation PC. In RISC-V, MRET uses machine trap state, restores relevant interrupt-enable and privilege fields, and jumps to mepc; SRET is the corresponding supervisor mechanism when supported. The handler is responsible for preserving software registers and updating the saved PC when continuing after a deliberately trapped instruction or a nonretriable event.

Restart is not always the right policy. A page fault repaired by installing a mapping often retries the same load, so retaining its fault PC makes sense. A successful environment call generally must advance beyond the ECALL instruction, but the handler must respect instruction length and ABI policy. A fatal hardware fault may never return. For a breakpoint, behavior depends on debug and exception semantics, and the debugger may adjust the continuation address explicitly.

If a retried instruction issues an external side effect twice, correctness can be lost. Architects try to make precise restart contracts enforceable; software must still treat memory-mapped device and partially complete operations carefully. “Resume from the PC” is not equivalent to a universal promise that every operation is safe to replay.

Nested Traps and Safe Handler Prologues

Ordinary RISC-V M-level trap entry saves one level of interrupt-enable history in MPIE and the prior mode in MPP. It does not automatically push a complete per-nesting trap frame on a stack. A new event taken before the handler preserves mepc, mcause and required status may overwrite records needed to return from the earlier trap. Consequently, a safe handler begins with a carefully designed critical section in which its own trap context is preserved before permitting optional nested interrupts.

After saving state, software may selectively re-enable interrupts, change the per-source enables, and service higher-priority work. Such nesting increases latency variability, stack consumption, reentrancy requirements, and risk of double faults. A new synchronous exception inside the handler can be particularly dangerous if it faults on the same invalid memory or privilege configuration needed for recovery.

Ibex documentation explicitly warns about preserving machine trap CSRs before enabling nested interrupts and describes particular NMI/double-fault behavior. These are concrete implementation facts, not a basis for claiming that every RISC-V core has the same NMI mechanism or an unlimited nesting capability.

Precise Exceptions: The Architectural Contract

A precise exception presents architectural state as though instructions before a well-defined boundary have completed and later instructions have not modified the visible state. For a fault on instruction I, the processor ordinarily makes earlier instructions visible according to the ISA and memory consistency contract, reports the faulting instruction and cause, and prevents younger instructions from committing architectural effects. A synchronous exception therefore appears at a stable program-order point even if fault detection occurred earlier or later inside the machine.

Precision is a visibility property, not necessarily proof that no younger execution happened physically. Speculative branches, cache probes, and integer arithmetic may have run; their results can be marked invalid and their architectural writes suppressed. Internal resource use and some microarchitectural side effects can remain and must not be described as fully rolled back. This distinction also explains why speculative side-channel behavior is a separate security topic.

Not every system error is precise. Some external faults, deferred memory errors or asynchronous machine checks cannot be attributed to one fully restartable instruction. A design must document where its guarantees end; falsely promising precise restart for an imprecise event can cause silent state corruption.

In-Order Pipeline Precise Fault Handling

In a small in-order core, the controller can track exception metadata in successive pipeline registers and ensure that an older instruction has priority over younger work. When the selected fault becomes eligible for architectural reporting, the core blocks its writeback and memory side effects, invalidates later pipeline stages, redirects fetch and writes trap state. If earlier memory operations have not finished, the controller must coordinate their completion or provide an architecture-compliant ordering mechanism.

The pipeline stage detecting an exception may differ by source. Illegal encoding often appears in decode, arithmetic legality in execute, and bus access failure after a memory operation has waited several cycles. A design that simply vectors on the earliest signal in time can report a younger load fault before an older instruction’s exception. Correctness requires instruction age or a suitable pipeline-order invariant, not just combinational OR-ing of all exception wires.

Pipelined teaching diagrams should distinguish kill from stall. A stall retains the instruction for later progress, while a kill invalidates it and prevents future architectural side effects. A trap generally requires a controlled kill of younger instructions; a recoverable resource conflict may require only a stall.

Out-of-Order Execution, Reorder Buffers and Retirement

An out-of-order processor may execute an instruction as soon as operands and resources are available, regardless of its program-order position. It therefore needs a mechanism such as a reorder buffer (ROB), retirement queue, or equivalent commit structure to reestablish architectural order. An instruction can finish calculating a result and still be unable to retire because an older instruction is not ready. A fault may be recorded with the completed instruction and delivered only when it becomes the oldest retirement-eligible operation.

This mechanism lets an earlier division, translation walk or cache miss defer architectural progress while younger independent operations execute transiently. If an older instruction faults, the machine squashes younger work, restores the proper speculative/renamed state and directs the exception to a handler. If a younger instruction faults but an older one later redirects the branch path, that younger fault may simply be discarded as wrong-path work.

The ROB itself is a microarchitectural implementation, not a programmer-visible ISA requirement. Different processor designs can meet a precise exception contract through other commit or checkpoint techniques. The neighboring Instruction Completion and Retirement and Register Renaming specialist articles provide the deeper mechanics.

Fault Ordering, Wrong-Path Work and Misprediction

Branch prediction allows a processor to fetch and execute instructions before it knows whether that control-flow path is correct. Suppose a predicted taken branch leads to a load from an invalid page, but the branch later resolves not taken. The load’s fault report should be tied to speculative work and suppressed when the mispredicted path is canceled. Otherwise an application could receive exceptions for instructions it never architecturally executed.

If the branch resolves correctly and the load reaches the commit boundary, the page fault may need to be delivered. This difference means that an exception candidate must carry its instruction identity and validity status; it cannot be represented solely by a global “page_fault_now” line. When several outstanding memory requests exist, response tags and cancellation rules become central.

Prediction recovery is a control redirect, but it is not itself an architected trap. It does not normally write exception cause registers or enter privileged software. The overlap in redirect wiring should not cause the documentation to conflate branch repair, fetch replay, interrupt admission and fault entry.

Memory Side Effects and Precise Store Semantics

Stores demand special caution because writing to physical memory or a device can have externally visible consequences. A processor may calculate an address and data early while deferring store commitment through a store buffer until it is safe. If the store later faults, implementation and ISA guarantees determine what may already have happened. A well-designed retirement protocol avoids allowing a younger store to perform irreversible actions ahead of an older fault.

Under a memory consistency model, visibility to other cores is not identical to the local register-retirement event. Store buffers, fences, cache coherence and memory-mapped devices impose additional timing and ordering constraints. An engineer cannot prove exception correctness merely by showing that the integer register file is unchanged; memory effects and device operations also matter.

For a device write, retrying an instruction after a bus timeout can be hazardous if the device already acted on the first transfer. Systems use idempotent protocols, completion tags, transactional mechanisms or explicit unrecoverable-error policies as appropriate. CPU hardware cannot universally guarantee exactly-once behavior for arbitrary external devices.

Pipeline Flushes, Cancellation and Replay

After selecting a trap, the controller must invalidate younger instructions and redirect future fetch. “Flush” can mean clearing valid bits, killing speculative queues, discarding prefetched instructions, draining or canceling memory work, restoring renaming checkpoints, or updating predictor-related state. Different implementations distribute these actions across several cycles; a single flush signal in a teaching diagram is a shorthand rather than a complete mechanism.

Replay is used when an instruction must be retried after a temporary condition, such as a recoverable hazard or resource conflict. Replay can occur without a privileged trap. Restart following a true architectural fault is different: the handler may modify mappings, state or the PC and execute a trap-return instruction. The design needs clear rules for whether an instruction is replayable, its side effects are suppressed, and its fault metadata is retained or regenerated.

Key control assertions include: a killed instruction never writes a destination register; a killed speculative store never reaches a forbidden externally visible commit point; any recorded fault maintains the correct original instruction identity; and a redirected fetch stream cannot be confused with an older pending request.

Interrupt Admission and Commit Boundaries

In precise machines, asynchronous interrupts are generally sampled or admitted at an architectural instruction boundary. An interrupt must not arbitrarily split an instruction’s visible effects, such as updating one register and forgetting a required paired state update. A complex or multicycle instruction may have defined interruptibility/restart rules that differ from a simple one-cycle integer operation; the hardware and ISA jointly establish where interruption can occur.

For an in-order machine, the controller may wait for an instruction to finish before servicing a pending timer event. In an out-of-order machine, the retirement mechanism can establish the continuation address and mark the exact boundary at which the event is taken. Interrupt latency therefore reflects both interrupt arbitration and the ability of the execution pipeline to reach a permitted boundary, not solely a hardware interrupt pin.

Even when an interrupt is deferred, it should not silently disappear. Pending-state latching and source acknowledgment rules must ensure that a sustained request remains observable. A system may intentionally coalesce or throttle events, but that is explicit platform policy and cannot be assumed to follow automatically from CPU control logic.

Interrupt and Exception Latency Metrics

Control design is constrained by latency and throughput. Detection latency measures how long after an event becomes observable the CPU recognizes it. Admission latency includes masking and the time until a permitted boundary. Vector latency includes trap-state capture and fetch redirection. Handler-first-instruction latency adds pipeline refill and memory behavior. Finally, service latency includes the handler code and device response. These are separate metrics; one aggregate number can obscure the real bottleneck.

Stall cycles, pending older cache misses, long uninterruptible operations, deep speculation, cache warming, power states and memory translation can make worst-case latency significantly greater than the best case. Real-time systems should establish bound assumptions, not infer worst-case behavior from an average benchmark. Interrupt storms can consume substantial time even if each individual vector entry is fast.

Performance measurements should include hot and cold handler paths, interrupt masking windows, nested events, cache/TLB misses, repeated faults, and the cost of restoring context. For systems that make certification claims, worst-case execution timing requires hardware-specific evidence and a defined workload/platform configuration.

Handler Software Interface and Context Preservation

Hardware saves the event records specified by its ISA, then privileged code performs the remainder of the handler protocol. The handler typically establishes a safe stack, preserves registers it will modify, retrieves cause and fault details, and dispatches according to the cause. For a normal interrupt it may interact with an interrupt controller and a device to acknowledge completion; for a page fault it may consult a mapping database; for an environment call it may execute a service governed by the OS ABI.

A handler must know which registers are considered scratch, which are reserved for the calling convention, and which extended contexts—FP, vector, debug or performance-monitor state—need preservation. Lazy saving may be a valid optimization where the OS and architecture support it, but it introduces its own first-use traps and reentrancy rules. An interrupt controller cannot automatically save every task’s high-level runtime state; software remains accountable for the process context.

Careful design isolates privileged entry from untrusted user pointers and unverified memory. It should avoid reading faulting user data before ensuring a safe execution context, and should not presume that the current user stack is suitable for kernel exception handling.

Privilege Isolation, Trap Entry and Security

Trap entry is a security-sensitive transition from potentially untrusted code to more privileged instructions. Hardware must enforce privilege rules for vector configuration, trap return, memory protection, CSR access, instruction legality and address translation. Software must validate any user-controlled values before acting on them. A wrong saved PC, stale privilege field, or stale translation context can redirect execution into unintended address spaces.

Fault metadata can reveal addresses or execution details. The architecture controls which registers are visible at which privilege level, but the operating system still needs policies for exposing diagnostic information to processes. Some microarchitectural events may be observable through timing even when the architectural exception path was correct; control correctness alone does not eliminate transient-execution side channels.

Trap handling also creates opportunities for denial of service through repeated invalid instructions, excessive system calls, interrupt storms or deliberate page faults. Proper boundaries, rate control, process isolation and error policy are necessary in the surrounding system. The CPU’s primary obligation is to produce enforceable, architecturally correct transitions rather than to decide social or administrative policies itself.

Virtualization and Multi-Level Trap Routing

A virtual machine introduces another layer of event control. The guest operating system may expect to receive its own exceptions and interrupts, while the hypervisor needs to intercept sensitive operations, protect host resources, and route virtualized events. RISC-V’s hypervisor extension, Arm virtualization extensions and x86 virtualization mechanisms provide different models for trap delegation, control/status state, virtual interrupts and returns.

Some guest operations execute directly; others trap to a hypervisor or are emulated. A page fault may originate in guest virtual address translation or in the host’s second-stage mapping, and the handler needs to know which stage caused it. Hypervisor hardware can provide additional cause and fault-address registers or exit-qualification fields; these are not interchangeable with ordinary M-level mepc/mcause explanations.

Correct routing requires that a guest cannot forge host privilege, bypass host memory protection, or access another guest’s interrupt/controller state. Real-world virtualization design should be grounded in the selected architecture’s virtualization manual rather than an assumed universal trap vector format.

Debug Mode, Breakpoints and Exception Conflicts

Debug requests, hardware breakpoints and watchpoints can arrive concurrently with ordinary exceptions or interrupts. Implementations may give debug entry special priority, preserve a debug program counter and cause, halt the pipeline, or enter a separate privilege context. The same processor may also execute an architected breakpoint instruction whose semantics differ from entering an external debugger.

A debugger stepping through a load fault, interrupt handler or system call needs to distinguish whether the core stopped before an instruction, after committing it, or at a trap boundary. When a faulting instruction is replayed after handler return, the debugger must not accidentally interpret the repeated execution as two successful commits. Some debug-trigger configurations suppress ordinary trap delivery in particular contexts; the exact rules must be read from the processor’s debug specification.

Hardware debug facilities are powerful and must be access-controlled in deployed products. Debug unlocking, trace exposure, breakpoint configuration and secure-debug policy are platform matters. Ordinary application code should not be able to bypass production privilege protection merely by requesting debug entry.

Designing a Reference Exception-Selection Model

A useful golden model should track an instruction stream, each instruction’s program-order identity, execution completion, exception candidate, and permitted architectural effects. The model should also represent privileged state, relevant interrupt pending/enables, trap vector configuration and a minimal handler. A check compares the implementation’s retired instruction stream and trap records against the reference rather than only comparing the PC each cycle.

Directed sequences should deliberately place an illegal instruction before a younger speculative load fault; put a valid instruction before a page fault; raise a timer interrupt while a long division is pending; and trigger a fault around a branch-misprediction flush. Each case must state what is allowed to commit and where execution may legally resume. A pure numerical unit test cannot expose a pipeline that accidentally writes a younger result after an older fault.

When formal verification is feasible, safety properties can be written as assertions: every committed instruction was valid and authorized; each trap record corresponds to an eligible event; no killed instruction commits; and the selected trap PC equals the correct boundary. Liveness properties about eventually servicing enabled interrupts require assumptions about masks, fairness, resource availability and platform signals.

Implementation Hazards and Common Misconceptions

  • “Exceptions and interrupts are the same.” Both can cause traps; their sources, timing and saved-PC semantics differ.
  • “Every arithmetic error traps.” Arithmetic result and status behavior is ISA-dependent; many conditions only set flags or return specified values.
  • “The earliest asserted fault signal wins.” Precise handling depends on instruction age and the architecture’s fault-priority rules.
  • “The CPU saves all registers automatically.” Ordinary trap entry saves a defined subset of control state; software normally preserves the remaining context.
  • “Vectored mode sends every exception to a distinct address.” Standard RISC-V vectored mtvec offsets apply to interrupts, not ordinary synchronous exceptions.
  • “Disabling MIE blocks all errors.” Ordinary interrupt masking does not disable all synchronous exceptions, NMIs or reset.
  • “A speculative page fault must reach software.” Wrong-path faults are normally suppressed before architectural delivery.
  • “A flush undoes every physical effect.” Architectural cancellation does not guarantee removal of all caches, timing or externally visible effects.
  • “A handler always resumes at PC+4.” Correct continuation depends on cause, instruction length, restart policy and ISA.
  • “One priority table applies to all processors.” ISA revisions, implemented extensions and platform controllers can change priority and routing.
  • “A short average interrupt latency proves real-time suitability.” Worst-case latency requires platform-specific constraints and evidence.

Applied Scenario 1: User Program Executes an Illegal Instruction

Situation. An unprivileged process reaches a 32-bit instruction word that is not defined by the implemented ISA or is restricted at its current privilege. The decoder discovers a synchronous illegal-instruction condition. The controller must prevent that instruction’s destination register or memory intent from taking effect, preserve the faulting PC, and present the architecturally correct trap cause to the designated privileged handler.

Correct flow. A simple processor can hold the fault with the instruction while earlier work completes, then select the exception and redirect fetch. A superscalar processor may detect the invalid encoding early but defer its delivery until it reaches the retirement head. The handler might determine that the instruction is unsupported, emulate it under an approved policy, or report the failure to the task. The CPU does not make that administrative choice.

Review evidence. Inject several illegal encodings, including one on a predicted wrong path. Confirm that a real-path illegal instruction records the proper PC and cause, while a wrong-path illegal instruction leaves no architectural trap when canceled. Check that privileged registers, user memory and younger register destinations remain unchanged. Finally, test the handler’s continuation policy rather than assuming that incrementing the fault PC is always valid.

Applied Scenario 2: Demand-Paged Load and Precise Retry

Situation. A program attempts to load a value through a mapped virtual address whose page is not resident or whose translation has not yet been installed. A translation walk identifies a page fault, and the load’s completion path produces fault metadata instead of a valid destination result. Younger arithmetic may have executed speculatively; a younger store may have an allocated queue entry.

Correct flow. The processor allows older instructions to reach their required architectural boundary, suppresses the faulting load’s writeback, prevents younger instructions from committing, records the load’s fault PC and relevant address information, and enters the authorized handler. Software checks whether the access is valid under its memory policy. If it installs a mapping and the instruction is restartable, trap return points to the original load so the load executes again with a valid translation.

Review evidence. Assert that the load destination is not overwritten with stale data and that the younger store does not cause an unwanted device/memory effect. Test a truly forbidden access as well as an ordinary missing page; the OS may respond differently. Examine how a TLB refill, page-table update and eventual return affect both data access and instruction ordering. This scenario connects exception-control hardware to, but does not duplicate, the separate virtual-memory and operating-system topics.

Applied Scenario 3: Timer Interrupt During a Long Operation

Situation. A timer requests service while the processor executes a long-latency integer division and several younger independent instructions are ready. The interrupt is pending, but trap entry must observe privilege routing and enable conditions. A microcontroller with a single iterative divider may have to reach a safe instruction boundary; a larger core may allow other instructions to finish execution but preserve an ordered retirement point.

Correct flow. At an eligible interruption boundary, the machine saves the continuation PC and trap status and transfers to the timer handler. The handler preserves its software context, acknowledges the timer as required, performs minimal time-critical work, and returns or schedules another task. The saved continuation address for an interrupt is not necessarily the PC of the division operation merely because division was active when the timer signal arrived.

Review evidence. Measure response with the divider idle and busy, interrupts enabled and disabled, and handler data in and out of cache. Confirm the timer cannot cause a partially updated architectural result and does not starve indefinitely under allowed assumptions. Document whether the implementation can interrupt or restart long internal sequences; do not infer that ability from a generic pipeline diagram.

Applied Scenario 4: Two Pending Interrupt Sources

Situation. A network receive condition and a timer signal become pending at nearly the same moment. The platform interrupt controller presents eligible sources; the processor applies the ISA-defined privilege, routing and mask rules. The selected interrupt enters an appropriate vector, and the second remains pending according to the platform’s persistence and acknowledgment design.

Correct flow. The handler examines the selected cause, performs the corresponding service and acknowledges the source without prematurely clearing unrelated pending information. If a high-priority source remains asserted continuously, system policy must address starvation, service batching and response fairness. If the handler enables nesting, it first preserves trap and general-purpose state so a subsequent interrupt does not destroy its return address.

Review evidence. Exercise all enable combinations, nested-event windows, and level/edge-trigger configurations of the actual platform. Confirm that only authorized sources reach S- or M-mode handlers and that the correct pending source remains serviceable after the first return. Avoid hardcoding an assumed numerical priority order in tests unless the implementation’s interrupt architecture actually specifies it.

Applied Scenario 5: Speculative Fault Before Branch Resolution

Situation. A branch is predicted taken, and the predicted target contains a load to a prohibited address. The processor begins translation and recognizes a possible page fault. A few cycles later, branch execution shows that the prediction was wrong. The load belongs to an instruction stream that should not have been architecturally executed.

Correct flow. The branch-recovery mechanism squashes the load and its exception metadata, redirects fetch along the correct path, and ensures the load neither retires nor invokes the page-fault handler. If a similar load occurs on the actual committed path, its exception can be delivered normally. This behavior is fundamental to precise instruction semantics even when the implementation still incurred cache, TLB or timing effects from the speculative access.

Review evidence. Vary the relative timing of branch resolution and fault detection; verify the instruction-age tags and valid bits; compare the retired instruction trace with a sequential reference model. Also confirm that a different, older real-path exception is not lost during recovery. The scenario shows why “fault signal observed” and “architectural trap taken” are distinct engineering events.

Applied Scenario 6: Fault Inside a Privileged Handler

Situation. A processor takes an ordinary load access fault and enters a privileged handler. Before the handler saves its trap records, the handler attempts to read an invalid stack location and faults again. A second exception now risks overwriting the original saved PC, cause and privilege status, leaving no reliable return context. Ordinary interrupt masking cannot prevent a synchronous memory fault caused by the handler itself.

Correct flow. A robust system sets up a safe entry environment, provides a trustworthy trap stack or scratch register convention, avoids unvalidated memory access before critical state preservation, and defines double-fault escalation. The exact behavior can involve a special trap mechanism, separate emergency context, NMI/RNMI features or fatal reset, depending on the architecture and implementation. It should not rely on the fiction that nested fault recovery is automatically available.

Review evidence. Fault-inject into handler prologues, test missing stack mappings and invalid vectors, and verify whether the platform detects double faults or preserves sufficient state to diagnose them. Review the selected RISC-V privilege revision and actual silicon documentation, because extensions and core-specific mechanisms significantly affect what can be recovered.

Guided Exercises and Design Investigations

  1. Control signal derivation: Given ADD, LOAD, STORE, BEQ and ECALL, complete a table for ALU select, register write, memory access, branch redirect and exception entry. Explain why an illegal opcode must not issue a store.
  2. Trap record trace: Starting in U-mode with pc=0x120, MIE enabled and mtvec.BASE=0x800, model a machine-mode illegal-instruction trap. Show mepc, mcause, MPP, MPIE, MIE and the new PC.
  3. Vector comparison: Determine entry addresses for a synchronous illegal instruction (code 2) and a timer interrupt (code 7) when mtvec uses direct and vectored modes with BASE 0x800. Explain the different offsets.
  4. Precise fault: A program-order sequence ADD, LOAD, STORE has executed, but LOAD reports a data fault. Identify the permitted architectural register and memory effects and justify the required squashes.
  5. Wrong-path detection: A speculative instruction faults after a branch was predicted incorrectly. Write an invariant that prevents its exception from reaching software.
  6. Handler continuation: Compare the appropriate saved-PC policy after a demand page fault, an environment call and an unrecoverable hardware integrity error.
  7. Nested event: Construct an event trace where a second trap arrives before the first trap frame is preserved. Identify which fields can be lost and how a safer prologue reduces risk.
  8. Interrupt latency: Separate synchronization, pending arbitration, boundary delay, vector redirect, handler prologue and actual service. Discuss which portions can be measured and which need explicit worst-case assumptions.
  9. Formal check: State safety assertions for unauthorized CSR writes, a killed instruction’s register write enable, and correct trap-record provenance.
  10. Taxonomy review: Distinguish hardware mechanism from OS policy in a page fault, system call, machine-check log and timer preemption.

Review Questions and Answers

QuestionConcise answer
Does every interrupt correspond to a faulting instruction?No. Interrupts are normally asynchronous requests admitted at a permitted boundary.
Why does a speculative fault not always reach software?Wrong-path or killed instructions cannot create committed architectural exceptions.
What is a precise exception?An event presented at a defined instruction-order boundary with earlier state preserved and forbidden later effects suppressed.
What distinguishes mtvec vectored mode?The standard interrupt target adds 4 × cause code to BASE; synchronous exceptions use BASE.
What state does hardware generally save?ISA-defined trap PC, cause and selected privilege/status; software saves the remaining execution context.
Why must a handler preserve trap state before enabling nesting?Another event can overwrite one-level trap records and destroy the return context.
Why can a page fault be retried but a device timeout may not be safe to retry?Page translation can often be repaired without an external effect; a device may have already performed an irreversible action.
Does a flush erase all speculative side effects?It prevents invalid architectural commitment, not necessarily all internal cache or timing effects.
Is an integer divide-by-zero necessarily a synchronous trap?No; the ISA specifies whether it traps or returns a conventional result.
Who decides whether a faulty user program is terminated?Privileged system software or platform policy, based on information enforced and reported by hardware.
