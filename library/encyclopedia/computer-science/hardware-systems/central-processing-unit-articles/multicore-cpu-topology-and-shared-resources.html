Scope and Central Question

A multicore CPU places more than one execution core within a processor product, but the word multicore alone tells an engineer remarkably little about cost or performance. Two cores can execute instructions independently while sharing an L3 cache, memory controller, fabric link, power budget, or physical package. Two hardware threads may instead share the same core. And two cores visible to an operating system may belong to different silicon dies or NUMA locality domains even when the product is marketed as a single socket. The central engineering question is therefore which resources are private, which are shared, where are they located, and what does a workload do to them?

This specialist treatment owns the concrete organization of processor packages, dies, chiplets, core clusters, shared last-level caches, interconnect paths, and proximity to memory and I/O. It explains how that organization changes contention, isolation, parallel scalability, and placement decisions. It does not duplicate the detailed cache algorithms in CPU Cache Hierarchies and Locality, coherence-state protocols in CPU Cache Coherence and Atomic Operations, or multiple-thread operation inside one core in Simultaneous Multithreading and Hardware Contexts.

A useful multicore design review must make a resource map before interpreting a benchmark: independent arithmetic capability is not the same as independent bandwidth, cache capacity, or power supply. Moreover, neither core count nor package count guarantees uniform performance. This distinction governs the examples, diagrams, formulas, and selection framework below.

Learning Objectives and Prerequisites

After reading, the learner should be able to identify sockets, packages, dies, chiplets, cores, and logical processors without treating them as synonyms; interpret private versus shared cache diagrams; explain ring, mesh, and fabric trade-offs without assuming a vendor's unreported topology; calculate basic limits from Amdahl's law and bandwidth constraints; reason about NUMA memory placement and CPU affinity; and design a fair topology-sensitive performance experiment. The reader should also be able to distinguish a schedulable CPU identifier from a physical core, reason about a cross-core cache-line transfer, and recognize when an apparent performance regression is caused by resource contention rather than a slow instruction.

Recommended preparation includes processor datapaths, cache locality, load/store operation, and virtual-memory translation. The Central Processing Unit overview supplies the broad background; the CPU specialist directory gives the full 24-article sequence. Examples here are deliberately illustrative, not claims that a particular commercially available processor uses the diagram's exact cache sizes or interconnect distances.

Defining the Levels of Processor Organization

A hardware thread or logical processor is a separately scheduled architectural execution context; core denotes a processing engine with substantial instruction-execution resources; die denotes a continuous piece of silicon; compute chiplet denotes a die or package element containing CPU cores; package denotes the assembled processor product; and a socket is the motherboard interface accommodating a package. Depending on product family, an entire CPU can use one die, many dies, or a heterogeneous mix of computing and I/O dies. An OS may also expose virtual CPUs that are scheduled onto physical hardware by a hypervisor, adding another layer of mapping.

Term Practical meaning Common reporting mistake
Logical CPU / processing unit (PU) Context available to the operating-system scheduler Equating two SMT siblings with two independent physical cores
Physical core Execution machinery for one or more hardware contexts Assuming all cores have identical capacity
Core cluster / complex Group of cores with a defined sharing or proximity relationship Assuming any cluster boundary is a NUMA boundary
Die / chiplet Silicon component containing some portion of the product Assuming one CPU package implies one die
Package / socket Processor assembly and its board installation point Treating package number as proof of memory-access uniformity
NUMA memory node OS-visible memory locality domain and policy target Assuming there must be one NUMA node per socket

Terminology is implementation-specific. For instance, a “core complex” in a manufacturer's documentation is a concrete sharing boundary for that product generation, not a universal building block of every processor. Numbering also requires care: Linux core_id can repeat across packages; a unique physical-core key generally needs package, die where meaningful, and core identity in the appropriate scope.

An Illustrative Package and Core-Cluster Diagram

The conceptual diagram below deliberately depicts two compute clusters sharing access to an I/O and memory subsystem. Each cluster contains two cores, each core has a private L1, and each cluster has an L3 cache. A pair of memory controllers is reached through a package fabric. The labels convey relationships, not physical routing, cache inclusivity, or bandwidth specifications of any actual CPU model.

Reading the diagram: accesses from a core to its private cache typically traverse a shorter and less-contended path than accesses to memory reached across shared controllers. A pair of cores in the same cache cluster may enjoy high shared-data locality while also displacing one another's working set. Cores in different clusters can be physically present within one package yet encounter additional fabric traffic for data exchange. The exact latencies depend on implementation, clock domains, power state, cache policy, and measured workload.

OS-Visible Topology Is a Projection of Physical Hardware

Operating systems learn topology from architecture-specific discovery, firmware tables, and processor interfaces, then publish a usable view to software. That view may be filtered by CPU hot-plug status, container CPU sets, affinity restrictions, hypervisor exposure, firmware configuration, and the platform's ability to represent all hierarchy levels. A topology API is authoritative about the view it returns, not proof of every internal silicon detail.

On Linux, lscpu -e and /sys/devices/system/cpu/cpu*/topology/ can expose package, die, core, and sibling relationships; lscpu -C can summarize caches. On Windows, GetLogicalProcessorInformationEx exposes processor-core, package, die, cache, NUMA, and processor-group relationships. Tools such as hwloc or Microsoft Sysinternals Coreinfo can help visualize the map. Do not infer a unique physical core from an OS logical-processor number alone; do not assume an index remains stable after hot-plug, BIOS changes, or virtual-machine migration.

Worked Example: Count Cores Versus Logical Processors

Imagine a package with four performance cores that expose two hardware contexts each and four efficiency cores with one context each. Its physical-core count is eight, while its logical-CPU count is twelve. It would be incorrect to infer twelve independent full-performance execution engines. At the same time, eight physical cores do not guarantee eight equal-capacity engines; microarchitecture, clocks, shared resources, and power management can differ among the core classes.

p_cores, p_threads = 4, 2
e_cores, e_threads = 4, 1
physical = p_cores + e_cores
logical = p_cores * p_threads + e_cores * e_threads
assert (physical, logical) == (8, 12)
print(f"physical cores={physical}, logical processors={logical}")

For scheduling, the distinction determines whether a new runnable thread may use idle execution machinery or must compete with a sibling already using the same core. The response is workload-dependent: SMT may hide pipeline stalls effectively in one code mix, but provide less benefit when siblings saturate the same execution ports or cache bandwidth.

Single-Die CPUs and Multi-Die Packages

A monolithic die integrates cores and infrastructure on one silicon piece. Its advantages can include simpler internal paths and uniform manufacturability of some components; its costs can include yield, die-size, power-delivery, and product-scaling constraints. A chiplet design partitions the system into dies joined by package-level interconnects. Partitioning can improve manufacturing flexibility, reuse across product families, and the separation of compute logic from I/O or analog functions. These are design opportunities, not automatic benefits for every workload.

A compute die may contain multiple cores and local caches while an I/O die contains memory controllers, peripheral interfaces, and package fabric endpoints. Alternatively, memory and I/O controls may be distributed. Cross-die communication introduces latency and energy costs and can create fabric bottlenecks. The performance result depends on cache hierarchy, shared data placement, inter-die bandwidth, and software locality rather than simply on chiplet count.

Core Complexes and Cluster Boundaries

Core cluster is a broad organizational term: the cluster may share L2, L3, an instruction cache, a front-end, an interconnect segment, or a power domain. Some designs place one cache slice per cluster; others implement distributed last-level cache slices or centralized banks. A shared cache is a capacity and communication resource, not a promise that cache access costs are identical from every core.

If a program passes cache lines frequently among two producer-consumer threads, keeping them near a shared cache and coherence neighborhood may reduce some transfers. But if the threads constantly stream unrelated large arrays, placing them in separate clusters can reduce cache contention. No single rule—“always pack together” or “always spread apart”—is correct for both workloads. The topology matters in combination with the access pattern.

Private Execution Resources and Shared Infrastructure

A typical physical core has substantial private resources: program counter(s), instruction execution engines, at least some registers and buffers, and usually L1 instruction/data caches. Resources outside the core may include last-level cache capacity, memory controllers, on-package interconnect routers, I/O translation facilities, and the package's power/thermal budget. Some resources that appear private at the architectural level are shared internally when SMT is enabled, and some caches are partitioned by design.

Resource Common sharing pattern Principal concern
Integer/FP execution units Mostly core-local; may be shared by SMT contexts Pipeline-port contention
L1 data/instruction cache Commonly core-local, shared by SMT siblings Local capacity and access conflict
L2 cache Private per core or shared within a small core group Working-set interference
Last-level cache Shared across a cluster, die, or broader domain Capacity, bandwidth, cross-core latency
Memory controller Shared by cores attached to its memory domain Aggregate DRAM-channel bandwidth
Fabric routers and links Shared by many cores and agents Hop count, queueing, congestion
Power and thermal headroom Shared at several hierarchy levels Frequency reductions under load

A hierarchy should be described as a graph with ownership and bandwidth, not merely as a drawing of nested boxes. The physically nearest resource may also be occupied or busy; queueing delay can dominate its nominal access latency under load.

Cache Sharing as a Topological Relationship

Cache structure is central to multicore placement. The CPU's L1 caches usually serve one physical core, while higher levels may span several cores. Shared cache can improve data reuse and reduce expensive external transfers when threads cooperate. The same sharing can lower effective cache capacity per thread or introduce contention when their footprints conflict. A large aggregate cache size may be divided into slices or clusters that do not have equal access latencies.

Consider two workers using 8 MiB each. If they share a 12 MiB usable cache and their access patterns do not reuse the same data, their combined 16 MiB working set exceeds that cache's capacity. The resulting misses depend on replacement policy, address mapping, and access order; the shortfall alone does not quantify a miss rate. If the workers instead reuse 4 MiB of overlapping read-only data, the shared cache could reduce duplication and improve performance. The cache's topological sharing scope must therefore be paired with a working-set analysis.

Worked Example: Cache-Domain Membership

The following toy map uses four logical processors and two shared L3 domains. It asks which pairs can share a last-level cache; it does not infer memory latency, interconnect bandwidth, or cache coherence protocol. Such grouping can be read from the operating system or a portable topology library, then checked against the target machine.

cache_domain = {0: 'L3-A', 1: 'L3-A', 2: 'L3-B', 3: 'L3-B'}
def shares_llc(a, b):
    return cache_domain[a] == cache_domain[b]
assert shares_llc(0, 1)
assert not shares_llc(0, 2)
print([(0, i, shares_llc(0, i)) for i in range(1, 4)])

The reverse of this question—“which threads should share an LLC?”—cannot be answered from topology alone. It requires data-sharing frequency, reuse distance, cache-bandwidth demand, interference measurements, and the application's synchronization model.

Distributed Last-Level Caches and Home Agents

Some multicore systems distribute LLC slices, coherence directories, or address home agents across an interconnect. An address-mapping function determines which slice or agent owns a line's directory/home information; the querying core may be near or far from it. This complicates a simplistic hierarchy where every core is exactly one fixed latency away from one global L3. A local hit, a remote-slice hit, and a memory access can have different paths even when all use the same logical last-level cache level.

The mapping, slice count, and replacement design are vendor- and generation-specific. Software generally should not hardcode assumptions about undocumented hash functions. Performance engineers instead use cache-domain discovery, hardware performance counters where supported, and controlled experiments to identify the cost of sharing or placement. Coherence state machines are treated separately in the dedicated CPU coherence article.

Ring, Mesh, Crossbar, and Fabric Interconnects

A ring connects agents around a logical loop and can be efficient for a moderate number of endpoints, but total link traffic and traversal distances rise as the design scales. A mesh introduces more routing choices and can distribute traffic over many paths, at the cost of routing complexity and potentially variable hop count. A crossbar can offer flexible simultaneous paths but grows in hardware cost with port count. Fabric is a general term for an interconnect whose physical and logical structure may involve switches, links, bridges, or multiple protocol layers.

A CPU with chiplets may use one interconnect within compute dies and a different package fabric between dies. A ring versus mesh comparison without router capacity, operating frequency, address mapping, and contention is incomplete. Designers balance latency, bisection bandwidth, area, power, clock-domain crossings, service quality, resilience, and manufacturing constraints. Readers seeking signaling and protocol details should consult Computer Architecture's Bus Systems unit rather than treating this article as a bus electrical specification.

Hop Count Is Not the Whole Latency

A useful teaching model is total access time = fixed endpoint cost + router/link costs + queueing + service. The smallest-hop route can become slow when queues are saturated; a somewhat longer route can win if its effective capacity is higher and the fabric supports that alternative. Memory traffic may traverse cache lookup and coherence management before reaching a controller, so the count of physical fabric links alone is not an end-to-end memory-latency model.

def toy_path_latency(base_ns, hops, per_hop_ns, queue_ns, service_ns):
    return base_ns + hops * per_hop_ns + queue_ns + service_ns
near_busy = toy_path_latency(5, 1, 2, 30, 8)
far_clear = toy_path_latency(5, 4, 2, 2, 8)
assert near_busy == 45 and far_clear == 23
print(f"near/busy={near_busy} ns, far/uncongested={far_clear} ns")

These are constructed illustrative parameters, not silicon measurements. Real fabrics may not dynamically choose a different route for a request and do not necessarily have constant per-hop delay. The lesson is that contention and placement must be observed, not inferred mechanically from a diagram.

Memory Controllers and Channel Topology

Physical memory bandwidth is delivered through memory controllers and channels. Multiple cores can issue memory requests independently but still compete for the same controller queues, DRAM channels, memory banks, and write/read scheduling capacity. A core's local L1 bandwidth might be large while package-level sustained DRAM bandwidth is much smaller. Once the memory subsystem saturates, additional cores may increase requests and power without increasing useful completed bytes.

Memory-channel count, data rate, transfer efficiency, read/write mix, and workload locality shape the bound. Controller placement also matters: some packages make one set of cores physically closer to a controller or group memory with a NUMA locality domain. Channel bandwidth is separate from capacity, and dual-channel versus single-channel labels do not by themselves identify the number of memory controllers or NUMA nodes.

Worked Example: Aggregate Bandwidth Bound

Suppose six identical workers each demand 12 GB/s from DRAM while the platform sustains 48 GB/s for the tested access mix. Aggregate demand is 72 GB/s; under a deliberately simplified fair-share model, only two-thirds of demand can be supplied. That does not mean every worker always receives exactly 8 GB/s: real memory scheduling, traffic distribution, and priority may be unequal.

worker_count = 6
worker_demand_gbs = 12.0
sustainable_gbs = 48.0
demand = worker_count * worker_demand_gbs
fraction = min(1.0, sustainable_gbs / demand)
assert demand == 72 and round(fraction, 6) == round(2/3, 6)
print(f"aggregate demand={demand:.0f} GB/s, attainable fraction≈{fraction:.1%}")

When a kernel is bandwidth-bound, the next optimization may be data reuse, compressed representations, fewer memory passes, or changes to placement rather than increasing its worker count. The bound should be estimated from measured sustained bandwidth under an equivalent access pattern, not from only the product's headline transfer rate.

NUMA: Memory Locality Within and Across Packages

Non-uniform memory access (NUMA) means different CPU-to-memory paths can have different latency or bandwidth characteristics. A NUMA node is an operating-system locality and allocation domain; it can correspond to one socket, part of a socket, or a platform configuration spanning components. NUMA is a relation between memory and initiators, not a proof that physically separate DRAM is absent or inaccessible. Many systems retain a shared physical address space while access costs vary.

A page can be “remote” to a running CPU when its memory resides in another locality domain. The application may still function correctly, but pointer-chasing latency, fabric traffic, and controller congestion can increase. Some platforms permit firmware-configured modes that change visible node granularity without changing the number of processor packages. On such systems, “one NUMA node per socket” is a particularly unreliable shortcut.

Illustrative NUMA Topology Matrix

The table represents invented measured-like relative access costs for a two-node model. It illustrates asymmetry without claiming a universal factor. Nodes can also differ in CPU count, memory capacity, and available bandwidth; the topology need not be symmetric.

Requesting CPU node Memory node 0 Memory node 1
Node 0 90 ns 155 ns
Node 1 150 ns 95 ns

Latency depends on operation, cache misses, contention, and clock conditions. This toy matrix cannot predict application performance by itself: a cache-friendly program may rarely reach DRAM, while an application that touches unpredictable dependent pointers can be much more sensitive. Topology distance and performance should be measured for the same hardware and operating conditions, not borrowed from a similarly branded processor.

Worked Example: Weighted Local and Remote Access

Assume a memory-intensive task performs 80% local and 20% remote uncached DRAM reads, at constructed costs of 90 ns and 155 ns. A simple weighted-average service-latency illustration yields 103 ns. This is not a real execution-time prediction because it ignores overlapping misses, cache hits, prefetching, queueing, and bandwidth.

local_fraction = 0.80
local_ns, remote_ns = 90.0, 155.0
weighted_ns = local_fraction * local_ns + (1-local_fraction) * remote_ns
assert weighted_ns == 103.0
print(f"illustrative mean DRAM service latency={weighted_ns:.1f} ns")

Moving allocations local might lower memory access cost, but an indiscriminate binding policy can create imbalance or put memory pressure on one node. Interleaving can spread bandwidth demand, while local allocation often favors latency-sensitive work. The preferable policy depends on bandwidth and capacity, not merely the shortest access time.

First Touch, Binding, Preferred, and Interleaved Allocation

On many Linux configurations, anonymous pages are physically allocated on first touch according to the effective memory policy and available nodes. Consequently, having one thread allocate and initialize all data before starting workers can concentrate pages on that first thread's node. A parallel initialization phase that follows future worker ownership can often improve locality. Caveats include inherited memory policy, cpusets, transparent huge pages, page migration, and differences in file-backed mappings.

Bind restricts allocation to specified nodes subject to policy and failure behavior; preferred expresses a preference with fallback according to operating-system semantics; interleave distributes pages across allowed nodes; local chooses a node near the allocating CPU when possible. These policies have distinct behavior on allocation, migration, and exhaustion. The Linux kernel's NUMA memory-policy documentation is the normative starting point for Linux-specific modes, not a generic guarantee across operating systems.

CPU Affinity and Memory Affinity Are Different Controls

Pinning execution to CPUs does not automatically move an application's already-allocated pages. Likewise, binding memory to a NUMA node does not force its worker threads to remain there. Good placement strategies coordinate both sides and account for migration, load balancing, time-varying workload demand, and other tenants. On Linux, CPU sets and memory policy expose different controls; Windows provides separate scheduling and NUMA-related APIs.

Hard pinning can benefit predictable, high-intensity workloads that demand cache or memory locality. It can harm throughput when cores would otherwise be idle, when task demand changes quickly, or when CPU capacity is asymmetric. A scheduler that is NUMA-aware may already make useful placement decisions. Before forcing affinity, record the baseline, measure migrations and access locality, and test against load variations rather than treating affinity as a universal optimization.

Worked Example: A Placement-Cost Heuristic

This model assigns four memory-heavy tasks to two nodes based on a simplified per-task remote-access penalty and node capacity. It demonstrates a choice procedure, not a complete scheduler: it omits migration overhead, cache traffic, task dependencies, and concurrent memory bandwidth.

nodes = {'N0': {'slots': 2}, 'N1': {'slots': 2}}
tasks = [('A', 'N0'), ('B', 'N0'), ('C', 'N1'), ('D', 'N1')]
assignment = {}
for task, home in tasks:
    eligible = [n for n, d in nodes.items() if d['slots'] > 0]
    chosen = min(eligible, key=lambda n: (n != home, n))
    assignment[task] = chosen
    nodes[chosen]['slots'] -= 1
assert assignment == {'A':'N0', 'B':'N0', 'C':'N1', 'D':'N1'}
print(assignment)

A production allocator should treat topology as one input to a measured cost model, with fairness, capacity, memory pressure, and priority constraints. A choice that minimizes estimated per-request latency can reduce whole-system throughput if it packs too much activity onto one cache or controller.

Multicore Coherence Traffic as a Shared-Resource Demand

When separate cores read and write the same cache line, coherence transactions maintain the architecture's rules for the line's visibility and ownership. Even if all required data eventually comes from caches, the transfers consume fabric links, tag lookups, directory resources, and sometimes time waiting for another core. A program with a shared counter can therefore scale poorly because cores repeatedly take turns owning the cache line, not because any individual integer-add instruction is particularly expensive.

This is a topology question insofar as the ownership handoff travels among cores, clusters, or dies. The actual MOESI/MESI variants, serialization points, atomic instructions, and memory-consistency contracts belong to the separate coherence and LSU articles. Do not conflate coherence (which value each agent may observe under the protocol) with the performance cost of moving the line through the package.

False Sharing Across Physical Cores

False sharing occurs when threads update different variables that occupy the same coherence granule, typically a cache line. The variables are logically independent, but ownership traffic follows the line rather than the variable. The cost often rises with the distance, update frequency, and number of competing cores. Padding or aligning independent counters can reduce line ping-pong; whether padding helps depends on object layout, allocator behavior, and cache-line sizes on the target processor.

A common mistake is to add threads to a per-thread counter array without recognizing that adjacent counters share a line. Another is to presume “make every value 64-byte aligned” is universally appropriate; padding can waste memory, harm cache capacity, and complicate ABI layouts. First verify the line-sharing hypothesis with a focused experiment and the platform's documented coherence granularity.

A Toy Line-Sharing Detector

The demonstration groups byte addresses into 64-byte lines. It identifies potential line sharing; it cannot prove that two threads actually write concurrently or that the platform's line size is 64 bytes. Replace the assumed granularity with measured or documented hardware information when applying the method.

line_bytes = 64
addresses = {'worker0': 0x1000, 'worker1': 0x1008, 'worker2': 0x1080}
line = {k: addr // line_bytes for k, addr in addresses.items()}
assert line['worker0'] == line['worker1']
assert line['worker2'] != line['worker0']
print(line)

A more realistic investigation measures speed under separate-core versus same-core placement, changes padding while holding algorithm and data volume constant, and checks whether memory traffic and cache transfers change. The result should be replicated under controlled frequency, thermal, and background-load conditions.

Core-to-Core Communication Patterns

Communication between cores can be read-mostly, producer-consumer, multiple-reader/single-writer, many-to-many, or update-intensive. Each pattern interacts differently with shared caches and fabric placement. Producer-consumer data exchange may benefit from nearby cores, especially when messages fit in shared cache. Independent streaming workers may benefit from spreading across cache or memory-controller domains. A shared work queue can introduce contention around its metadata despite the useful work being parallel.

Communication includes more than data payloads: synchronization variables, allocation metadata, page-table changes, interrupt delivery, and I/O completion notifications can all move through shared infrastructure. Evaluate total line movement and contention rather than only bytes in an application's logical messages.

Cross-Core Interrupts and TLB Shootdowns

Some operating-system operations require other CPUs to invalidate stale translation entries or acknowledge coordination requests. A mapping change affecting many active cores can trigger inter-processor signaling and wait for remote handling. The cost may grow with the number of affected processors and their topology, although implementations may batch invalidations, use address-space tagging, or choose different strategies. The earlier TLB article explains the detailed invalidation correctness protocol.

Such coordination can limit scalability of tasks that frequently change memory mappings, allocate and free large numbers of virtual-memory regions, or manage many virtual machines. A topology-aware analysis distinguishes expensive remote communication from page-table work performed locally. It also separates shootdown frequency from shootdown duration; optimizing one metric does not necessarily optimize the other.

I/O Locality and Device Affinity

PCIe roots, storage adapters, and network interfaces have physical attachment points within a server's package-and-I/O topology. A network-processing thread may gain locality when placed near the NUMA node that serves its NIC and DMA buffers. Conversely, separating packet-processing workers can sometimes improve overall capacity if the nearby cores are already saturated. The device's DMA behavior and cache coherence must be established rather than assumed.

For an I/O workload, topology discovery should link CPU groups, memory locality, IRQ affinity, driver queues, and device path. NUMA node labels exposed by the operating system may be missing, synthetic, or not granular enough to describe every hop. A practical tuning report includes baseline queue depth, interrupt rates, bytes processed, tail latency, and any change in CPU/fabric utilization.

Heterogeneous Cores and Asymmetric Capacity

Modern CPU packages sometimes mix performance-oriented and efficiency-oriented cores. The hardware presents different instructions-per-cycle characteristics, cache arrangements, vector support, clocks, and power behaviors depending on family and operating mode. A scheduler must distribute latency-critical tasks, background work, and parallel bulk work according to these capacities and the current system state. A runnable thread is not necessarily equally fast on every logical CPU.

Intel documents performance-hybrid cores and Thread Director as hardware guidance consumed by supported OS scheduling. Linux documents capacity-aware and energy-aware scheduling for architectures where capacity models are available. The fact that a system exposes unequal core types does not imply that all schedulers, virtual machines, or applications have an equally precise map. Feature detection and runtime measurements remain necessary.

Scheduling Domains and Load Balancing

Schedulers often represent CPU groups at increasingly broad topology levels. A local balancing decision may preserve cache affinity while an all-system decision can move a task to an idle distant processor at the cost of cache warmth and potential NUMA remoteness. Linux scheduling domains provide a concrete example of such hierarchical policy; Windows has its own scheduler and processor-group relationships.

A balanced runnable-thread count is not the same as balanced performance. One core running a memory-stalled task, another running an AVX-heavy compute task, and a third running interrupt handlers do not consume equal shared resources. For heterogeneous systems, a suitable policy may use effective capacity rather than equally dividing threads. Affinity should be evaluated alongside each worker's observed progress and scheduling delays.

Windows Processor Groups and Large Systems

Windows exposes processor groups for systems whose logical-processor counts exceed a group's capacity, and APIs describe per-group relationships. Windows 11 and Windows Server 2022 changed defaults so processes and their threads may span all groups by default, subject to compatibility and API constraints. Developers should use GetLogicalProcessorInformationEx and relevant group-aware affinity interfaces rather than assume all CPUs fit in one 64-bit mask. Group organization is an OS enumeration and scheduling mechanism, not a direct silicon boundary.

Windows documentation provides RelationProcessorCore, RelationCache, RelationProcessorPackage, RelationProcessorDie, and NUMA node relationships. A group mask alone is insufficient to classify physical core, chiplet, or memory distance. In addition, virtual machines may expose groups and topology chosen for compatibility or licensing, not a perfect reproduction of the host's package layout.

Linux CPU Topology, CPU Sets, and hwloc

Linux exposes online and possible CPU maps and topology attributes such as physical_package_id, core_id, and core_cpus_list/older sibling aliases. Cache-sharing descriptions may also be available under cache shared_cpu_list. numactl --hardware, lscpu, and hwloc can help correlate the processor map with memory nodes and caches. A process's effective CPU set can be smaller than the host-wide list, particularly within a container or job scheduler.

hwloc models packages, dies, cores, processing units, caches, memory nodes, and I/O relationships. Its documentation cautions that memory nodes and the primary CPU topology tree do not always nest in the simplistic “one NUMA node inside one socket” manner. Use the library's topology and distance information where possible rather than only a single string label from /proc/cpuinfo.

Worked Example: Identify Unique Core Keys

In this fictional inventory, the operating system exposes two packages with two physical cores each and two SMT logical processors per core. The logical IDs are not contiguous by physical core. Counting unique (package, core) tuples correctly gives four cores, whereas counting logical IDs gives eight. In systems exposing die identifiers and where core_id is scoped differently, include the proper extra disambiguating fields.

cpus = [
    (0,0,0), (4,0,0), (1,0,1), (5,0,1),
    (2,1,0), (6,1,0), (3,1,1), (7,1,1),
]
logical = len(cpus)
physical = len({(package, core) for _,package,core in cpus})
assert logical == 8 and physical == 4
print(f"logical={logical}, physical={physical}")

For a real machine, do not sort numeric CPU IDs and assume adjacent IDs are SMT siblings or cache neighbors. Discover the explicit sibling and shared-cache relationships. Virtualization, offline processors, firmware behavior, and different enumeration choices all defeat the adjacency shortcut.

Hybrid and Chiplet Systems Complicate Simple Affinity Rules

An algorithm that assigns threads in ascending logical-CPU order may pile the first threads onto the same core, a particular cluster, or an efficiency-core group, depending on OS enumeration. A chiplet-aware allocator may instead wish to keep a cooperating group within one LLC domain, while a streaming allocator may spread across controllers. Hybrid core types add capacity asymmetry and possibly different instruction acceleration capabilities.

An adaptable allocation policy should map candidate CPUs to physical cores, SMT siblings, cache domains, memory nodes, and usable core classes before deciding placement. The application can then encode workload-sensitive goals, such as minimizing producer-consumer latency, maximizing independent bandwidth, avoiding pathological cache interference, or conserving energy. Test the results rather than assuming that a tidy affinity chart guarantees a faster workload.

Parallel Scaling: The Amdahl Boundary

Amdahl's law expresses the limitation imposed by serial work. If the serial fraction is s and the parallel part scales ideally across p equal workers, the ideal speedup is 1 / (s + (1-s)/p). This is an upper-bound model under fixed problem size, not a promise that increasing core count yields the result. Memory contention, synchronization, scheduling, migration, load imbalance, nonuniform capacities, and power constraints can all reduce observed speedup.

For a job whose serial fraction is 0.15, eight ideal equal cores give speedup 1/(0.15 + 0.85/8) ≈ 3.90, not eight. The example says nothing about what happens if the parallel part is bandwidth-limited. Amdahl's law identifies a structural ceiling from serialization; hardware topology adds additional ceilings.

Worked Example: Amdahl Versus Actual Scaling

def amdahl_speedup(serial_fraction, cores):
    if not (0 <= serial_fraction <= 1 and cores >= 1):
        raise ValueError('invalid inputs')
    return 1 / (serial_fraction + (1-serial_fraction)/cores)
assert round(amdahl_speedup(.15, 8), 3) == 3.902
assert amdahl_speedup(.15, 1) == 1
print(f"ideal 8-core speedup={amdahl_speedup(.15,8):.2f}x")

A useful experiment computes speedup from measured elapsed time at 1, 2, 4, and 8 physical cores with consistent data sets and power policy. Repeat using SMT siblings to expose resource-sharing effects, and compare local versus cross-cluster placement. Record differences in topology and parallel efficiency rather than folding all configurations into one “threads” axis.

Work, Span, and Synchronization Structure

Amdahl's simplified serial fraction is not the only way to reason about scaling. Work is the total computation performed and span is the length of the longest dependency chain. In an ideal parallel scheduler, execution time cannot be better than either total work divided by available effective processing capacity or the span. Real systems also pay for scheduling, queue management, locks, barriers, cache-line movement, and other overhead.

For tasks involving fine-grained dependencies, the span can dominate long before package bandwidth saturates. Conversely, a highly parallel memory scan may have short dependency chains but saturate shared memory channels. The appropriate optimization depends on whether the application's limiting factor is computation, dependency, memory, communication, or external I/O.

Shared-Resource Bottlenecks and the Roofline View

A useful high-level bound compares arithmetic throughput and memory bandwidth: attainable operations per second are limited by peak compute capability and by arithmetic intensity × sustained memory bandwidth. The arithmetic intensity counts useful operations per byte moved at the chosen memory level. Moving the same data repeatedly from DRAM can make a many-core computation bandwidth-bound even when every core has idle arithmetic units.

peak_gflops = 800.0
sustained_gbs = 100.0
intensity_flop_per_byte = 2.0
bound = min(peak_gflops, sustained_gbs * intensity_flop_per_byte)
assert bound == 200.0
print(f"illustrative bound={bound:.0f} GFLOP/s")

This equation is an idealized upper bound and assumes consistent units, equivalent memory traffic accounting, and a measured bandwidth appropriate to the operation. Memory-level choice changes the bound: an algorithm may be limited by LLC bandwidth instead of DRAM bandwidth. Roofline analysis is a complement to, not a replacement for, CPU topology discovery.

Contention Can Hide Behind High Core Utilization

A system can report near-100% busy logical processors while useful completed operations plateau. The cores may be stalled on memory, waiting at barriers, spinning on locks, or losing performance to cache evictions. Scheduler activity and frequency throttling can also raise apparent utilization without improving service throughput. High aggregate usage does not, by itself, show that execution units are fully productive.

During diagnosis, measure completed requests or units of work, not only CPU time. Compare instructions per cycle, stalled cycles, LLC hit/miss patterns, memory bandwidth, remote memory events, synchronization wait time, and topology placement as supported by the platform's tools. Beware that hardware performance counters vary by CPU generation and often cannot be compared one-for-one across different core classes.

Latency, Throughput, and Tail Behavior

Latency measures time to finish a request; throughput measures completed requests per time; and tail latency characterizes the slowest fraction of requests. Spreading tasks can improve aggregate throughput while making one request slower due to synchronization or remote access. Packing tasks near an LLC can lower typical inter-thread communication delay while increasing queueing and tail variability if all requests compete for the same core group.

An evaluation should therefore state the business or technical objective explicitly. For an interactive service, p99 latency and deadline compliance may matter more than peak aggregate jobs per second. For an offline rendering farm, steady-state throughput and energy per result may dominate. Same-core, same-cluster, same-package, and cross-package placement should be tested under comparable concurrency.

Frequency and Thermal Coupling Across Cores

Per-core performance changes under package-level power and thermal constraints. As additional cores become active, some CPUs reduce sustained frequency, change voltage/frequency operating points, or shift activity among power domains. Thus a two-thread speedup is not necessarily two times single-thread speed even if the work is perfectly independent. Peak boost clocks are not equal to guaranteed all-core sustained operating frequencies.

Thermal throttling, fan behavior, voltage guardrails, and workload-specific instruction mix can interact with topology. Hardware designers may concentrate high-power cores or spread them physically to manage hotspots; package policy may be more relevant than the number of shared cache levels. For deeper electrical and thermal mechanisms, consult the dedicated Power and Thermal Systems division and CPU power/thermal specialist articles.

Virtual CPUs, Hypervisors, and Topology Exposure

A VM's virtual processor topology may be chosen for management, compatibility, or licensing. It can expose apparent sockets and cores that differ from the host silicon. The hypervisor may schedule multiple vCPUs onto the same physical core at different times or map them across NUMA nodes; memory backing can also move or be allocated remotely. Consequently, a guest's logical topology is not automatically a complete performance description of its host.

Virtualization tuning should check vCPU-to-host mapping, CPU overcommit, steal or ready time, host and guest NUMA configuration, memory allocation, noisy neighbors, and migration practices. Explicit virtual NUMA can help large guest workloads when mapped consistently to host memory locality, but an inaccurate virtual topology can mislead application-level placement. Always document which layer a measurement observes.

Security and Side Effects of Shared Resources

Sharing caches, fabric links, memory controllers, or SMT resources can create timing interference. In some threat models, shared microarchitectural state can contribute to side-channel information leakage or denial-of-service contention. Isolation decisions depend on tenant trust, architecture-specific mitigations, cache partitioning features where available, process placement, hypervisor policy, and workload behavior. A cache-sharing map is therefore relevant to security review but does not prove that a specific attack is feasible.

Avoid conflating performance interference with a security vulnerability: a reduction in throughput from co-located tasks is a service-quality symptom, while an exploitable timing channel requires a particular threat model and information path. Detailed speculative and cache side channels belong to the separate CPU Security article; the purpose here is to include sharing domains in the platform isolation assessment.

Reliability, Error Domains, and Failure Containment

Multiple cores can share uncore infrastructure and therefore share exposure to some faults. An error in one cache slice, memory controller, fabric link, or power domain may affect more than one core. Conversely, redundant paths, ECC-protected structures, error reporting, and recovery strategies can contain or mitigate some failures. The scope varies by product and platform configuration and cannot be determined by socket count alone.

Operational diagnostics should distinguish corrected memory/cache errors, uncorrectable machine-check events, fabric timeouts, scheduler stalls, and ordinary application exceptions. Error locality can inform isolation and maintenance decisions, but a fault counter's name does not necessarily identify the defective physical component. Consult the product's RAS documentation before assigning blame to a package or chiplet.

Processor Topology Versus the Bus-System Taxonomy

The processor topology question asks which cores and resources exist, how they share capacity, and how placement affects performance. A bus or interconnect question asks how transactions are carried, arbitrated, ordered, encoded, and electrically signaled. Those questions intersect but are not identical. This article discusses ring/mesh/fabric shapes and communication costs only to explain multicore behavior; it does not restate PCIe framing or on-die protocol specifications.

The MGU taxonomy also separates physical CPU cache organization from abstract memory-hierarchy principles, and hardware coherence from programming-language synchronization. This separation keeps a reader's causal diagnosis precise: “remote cache access” is not interchangeable with “remote NUMA DRAM,” and neither is interchangeable with “the compiler reordered a memory operation.”

Measuring a Machine Before Optimizing It

A repeatable investigation begins with hardware identification and the OS-visible topology actually granted to the process. Record model, microcode/firmware revision when available, package count, die and core count, SMT status, shared-cache groups, NUMA nodes, memory configuration, and CPU affinity restrictions. Next record CPU frequency policy, thermal conditions, virtualization, and competing workloads. Otherwise two test runs can differ even though the application binary and nominal thread count did not change.

Start by creating a resource-sharing hypothesis rather than tuning everything at once. “Workers interfere in L3” predicts a different set of observations from “all workers saturate DRAM” or “tasks are waiting on one shared lock.” Each can produce a flat throughput curve, but the interventions differ. A good performance note states the hypothesis, the change, the expected counter movement, the observed work-rate change, and any confounding limits.

Practical Topology Discovery on Windows

On Windows, GetLogicalProcessorInformationEx is the structured API for cores, caches, packages, dies, and NUMA relationships. Microsoft Coreinfo is a convenient external inspection tool; its output should be interpreted with regard to its tool version and the OS's processor-group reporting. A simple PowerShell snapshot provides useful preliminary context without providing the full core-to-cache relationship graph:

Get-CimInstance Win32_Processor |
    Select-Object DeviceID, Name, NumberOfCores, NumberOfLogicalProcessors
Get-CimInstance Win32_PhysicalMemory |
    Select-Object BankLabel, Capacity, Speed

The CIM report may provide socket-level counts and module inventory but not enough detail to distinguish all shared caches, core types, or per-node memory affinity. Hardware topology utilities and documented OS APIs are needed for those questions. On a VM, counts may represent the guest configuration rather than the host's physical topology. Also distinguish operating-system logical processor count from available processing capacity under a job or process affinity mask.

Practical Topology Discovery on Linux

A Linux investigation can begin with lscpu -e=CPU,ONLINE,SOCKET,DIE,CORE,NODE where supported, lscpu -C, numactl --hardware, and lstopo if the relevant tools are installed. Linux sysfs under /sys/devices/system/cpu/cpu*/topology/ and /sys/devices/system/cpu/cpu*/cache/ can expose sibling lists and cache-sharing CPU masks. A tool must gracefully handle missing attributes, permission restrictions, containers, offline CPUs, and kernels with differing field support.

lscpu -e=CPU,ONLINE,SOCKET,DIE,CORE,NODE
lscpu -C
numactl --hardware
# If hwloc is installed:
lstopo --of console

Interpret NUMA node(s): 1 cautiously. It may be the actual exposure of the firmware and OS, or it may be a guest/container view. Absence of visible NUMA division is not proof that every underlying memory path has identical latency. Conversely, the presence of multiple nodes is not by itself evidence that remote pages are causing a performance regression.

Benchmark Design: Separate Independent Variables

A useful topology study varies one dimension at a time: (1) one versus multiple physical cores; (2) SMT sibling use; (3) core placement within and across shared-cache clusters; (4) CPU placement local versus remote to allocated memory; and (5) increasing memory bandwidth demand. Keep problem size, algorithm, input distribution, and compiler settings fixed within each experiment. Warm-up and repeated steady-state observations are usually necessary because boost frequencies, caches, page allocation, and runtime optimizers change over time.

Measure both whole-program results and resource-level indicators. Run multiple trials, show the dispersion (not only the best run), note whether threads migrate, and compare tail latency under representative load. An abnormal improvement after manual pinning could reflect lower migration, better NUMA locality, less cache contention, less OS noise, or simple measurement variance. A credible conclusion narrows the cause with controlled evidence.

Performance-Counter Interpretation Limits

Hardware counters can quantify cycles, instructions, LLC events, remote-memory events, memory-controller traffic, or interconnect activity when the architecture supports those metrics. Their meanings differ: “L3 miss” on one product may not correspond directly to a named counter on another, and counters may be sampled, multiplexed, or filtered. Caches and interconnects also evolve across CPU generations. Treat named event groups as platform documentation questions rather than universal units.

Counting miss events without normalizing by work can be misleading. A run that performs twice as much work can incur more cache misses while improving work rate. Better comparisons include misses per thousand retired instructions where appropriate, bytes transferred per completed transaction, cycles per request, sustained bandwidth, and wall-clock time. Normalize carefully and disclose when metrics are unavailable or incomparable.

Worked Example: Parallel Efficiency

Parallel efficiency is measured speedup divided by the number of equal-capacity workers used for the comparison. If eight physical cores reduce job time from 80 to 20 seconds, speedup is 4× and efficiency is 50%. This scalar metric becomes misleading when mixing cores of unequal capacity or logical SMT contexts; for heterogeneous machines, report the actual configuration and consider effective-capacity weighting.

baseline_seconds = 80.0
parallel_seconds = 20.0
physical_cores = 8
speedup = baseline_seconds / parallel_seconds
efficiency = speedup / physical_cores
assert speedup == 4 and efficiency == 0.5
print(f"speedup={speedup:.1f}x, equal-core efficiency={efficiency:.0%}")

An efficiency drop with more cores does not identify the cause. It might be algorithmic serialization, insufficient tasks, scheduling, last-level-cache contention, memory bandwidth, synchronization overhead, or reduced all-core frequency. Diagnosis requires testing a specific mechanism rather than applying “use fewer threads” as a permanent substitute for understanding it.

Locality Versus Load Balance: A Decision Table

Workload characteristic Initial placement hypothesis Main failure mode to test
Producer and consumer exchange small mutable messages Place near a shared-cache/coherence neighborhood Core capacity saturation or excessive wakeups
Independent memory streams Spread across distinct memory-controller domains Remote-memory placement or unequal bandwidth
Large read-only common lookup table Consider shared-cache locality Cache capacity eviction or bandwidth contention
Independent latency-sensitive services Separate from high-interference neighbors Reduced locality or unused system capacity
Large NUMA-sensitive graph traversal Couple thread placement with page ownership Pointer-chasing to remote pages
Heterogeneous CPU package Match critical tasks to effective core capacity Energy, thermal, or fairness regression
Packet-processing worker groups Align CPU, buffer memory, and device queue locality NIC/IRQ hotspot and software-queue contention

The table describes hypotheses, not universal prescriptions. The selection can change with data size, cache policy, processor generation, application phase, and competing load. Measure the location and demand of the bottleneck before setting persistent affinities.

Common Interpretation Errors

Error 1: “The machine has 64 CPUs, therefore 64 full-performance physical cores.” The count may refer to logical processors, hardware threads, or guest vCPUs. Error 2: “Same socket means equal memory latency.” A socket can contain multiple dies and NUMA domains. Error 3: “The largest LLC always delivers best throughput.” Cache contention and access distance also matter. Error 4: “More runnable threads equals more parallel speedup.” Shared bandwidth, serial work, and scheduler overhead cap throughput.

Error 5: “NUMA pinning always improves performance.” Poor binding can exhaust local memory or reduce load balance. Error 6: “High CPU utilization proves compute saturation.” Stalls or busy-wait synchronization may dominate. Error 7: “Two threads writing separate variables cannot contend.” They may share a coherence line. Error 8: “The same topology names mean the same physical design on every product.” Operating systems and vendors expose abstractions whose precision and meaning differ. Each error is corrected by a resource map plus measured workload behavior.

Applied Scenario 1 — A Shared Cache Helps an Analytics Pipeline

An analytics service has two worker threads that repeatedly access a large shared, mostly read-only dimension table while processing separate batches. The team initially spreads workers across different LLC clusters to avoid interference. Performance declines compared with pairing them within a shared-cache domain. The hypothesis is that sharing avoids duplicate cache footprints and expensive inter-cluster transfers for popular table entries. The team measures table reuse, cache misses, latency, and throughput under both placements while holding input distribution and the number of physical cores constant.

The decision is not to declare same-cluster placement universally superior. As the table grows beyond the cache or the number of workers increases, capacity pressure may outweigh reuse. The operational rule is to choose a placement policy tied to the actual working-set shape and revisit it after model or data growth. Related studies include cache locality, memory-bandwidth measurements, and safe affinity changes.

Applied Scenario 2 — A Memory Scan Stops Scaling at Eight Cores

A scientific array-processing job scales nearly linearly from one to four physical cores but adds little throughput from eight to sixteen. CPU utilization remains high. The likely candidate bottlenecks include sustained DRAM bandwidth, page placement, memory-channel configuration, all-core frequency, and synchronization. The team performs a read/write bandwidth test with the same access pattern and sees the channel throughput plateau as the core count rises, while available compute execution capability still exists.

The response is to reduce transferred bytes, fuse passes, improve cache reuse, or adjust data partitioning. Spreading threads without matching page placement might worsen the problem. The team documents throughput at each core count, per-node memory traffic, remote access fraction, and energy per processed element. It avoids claiming that the platform's entire memory system is universally saturated from one single benchmark.

Applied Scenario 3 — A Two-Socket Database Has Remote Page Traffic

A database uses two processor packages but its workers initialize a large in-memory index from one startup thread. Later, queries on the other package repeatedly traverse pages allocated near the first. Queries are functionally correct, yet p99 latency rises when worker placement shifts. The team verifies page placement, CPU migrations, and local versus remote memory access before making changes.

A controlled remediation partitions the index by ownership, parallelizes page initialization, and balances read-only replicated structures against memory-capacity cost. The team may test interleaving for a shared scan-heavy structure while preserving local allocation for pointer-chasing indexes. The outcome should be judged on queries per second, p95/p99 latency, memory footprint, and cross-socket traffic, not on average DRAM latency alone.

Applied Scenario 4 — A Chiplet Boundary Changes Queue Handoff Cost

A work-stealing runtime passes small task descriptors among worker threads. A benchmark shows higher handoff latency between two workers assigned to separate compute chiplets than between workers within one cache cluster. The team checks whether the difference persists after controlling CPU frequency, task size, and background load. It also measures overall completed tasks to avoid optimizing latency at the expense of throughput.

A topology-aware queue policy may give workers local tasks first and steal remotely when needed, limiting unnecessary cross-chiplet movement while preserving load balance. If one chiplet goes idle while another is overloaded, a strict locality-only policy can be worse. The refined design permits remote steals when the expected benefit exceeds migration and coherence costs. The article on shared resources owns the placement cost; the queue algorithm belongs in software and parallel-programming materials.

Applied Scenario 5 — A Virtual Machine's vCPU Count Misleads Operators

A cloud VM advertises 24 virtual CPUs. Operators assume it has 24 dedicated physical cores and tune a worker pool to 24. During peak hours the service shows uneven latency and steal/ready time. Investigation reveals host overcommit and an exposed virtual topology that does not fully match the actual physical core and NUMA relationships. Increasing the pool size cannot remove a host scheduling bottleneck.

The remediation is to coordinate virtual topology, reservation or placement policy, vNUMA and memory allocation, and the service's true concurrency requirements with the provider. Application-level tests remain essential because a guest OS cannot necessarily observe all host-level shared resources. Record guest-visible topology and host-level facts separately; do not present a guest socket number as a physical host-socket measurement.

Applied Scenario 6 — A Hybrid Laptop Prioritizes Interactive Work

A hybrid-core laptop runs a latency-sensitive user interface beside background indexing and media transcoding. A naive application pins all work to a fixed group of logical processor IDs, inadvertently creating congestion on the same performance-core cluster. The OS's scheduler and hardware capacity hints could have kept urgent work responsive while letting low-priority tasks use other available resources.

The team replaces brittle numeric-ID affinity rules with clear task priorities and a measured policy for exceptional cases. It checks sustained behavior on battery and external power, thermal state, deadline misses, and work completed per joule. Explicit pinning is retained only where tests demonstrate an advantage. This case illustrates that correct topology awareness sometimes means not overriding a capable scheduler.

Ten-Gate Multicore Engineering Framework

Gate Question Evidence for a decision
1. Confirm workload Is the goal throughput, latency, predictable deadlines, or energy? Work-rate and latency baseline
2. Discover visible topology Which logical CPUs map to cores, dies, packages, caches, and nodes? OS topology and affinity report
3. Establish physical limits Which caches, controllers, fabric links, and power domains are shared? Vendor specifications and measured resource scope
4. Classify access pattern Is traffic compute-bound, cache-resident, streaming, or remote-memory-heavy? Working-set and memory/CPU counters
5. Determine communication How often do workers exchange data or synchronize? Message/lock rates, sharing observations
6. Identify NUMA ownership Where are pages allocated relative to their users? Memory locality and migration measures
7. Control scheduler effects Can migration, SMT, or core asymmetry explain a result? Affinity, active capacity, and scheduling trace
8. Calculate bounds What limits follow from serialization and shared bandwidth? Amdahl and measured-bandwidth estimates
9. Run controlled experiments Does changing one topology variable improve user-valued outcomes? Repeatable A/B trials with variability
10. Deploy and reassess Will the configuration remain effective under changed load and hardware? Rollback path, monitoring, re-benchmark schedule

Use gates in order, but revisit them as new observations invalidate earlier hypotheses. A topology optimization that improves synthetic throughput but worsens user-facing p99 latency or operational reliability should not be accepted without an explicit trade-off decision.

Guided Exercise 1 — Draw a Processor Resource Map

Given a fictional two-package system, each package containing two compute chiplets, each chiplet containing four cores, draw the package/chiplet/core hierarchy and propose a location for two last-level-cache sharing domains per package. Count 16 physical cores for the complete machine. Next hypothesize the logical-processor count if every core exposes two hardware contexts: 32. State clearly that the example does not specify whether SMT contexts share all pipelines, which memory controllers serve each chiplet, or how many NUMA nodes firmware exposes.

Check: the number of compute chiplets is four total, not eight; core count is four chiplets × four cores = sixteen. Do not deduce NUMA count merely from chiplet count.

Guided Exercise 2 — Compare Two Thread Placements

Two threads repeatedly hand off a 64-byte message. Placement A keeps both on separate physical cores sharing a nearby LLC domain; placement B moves them to different dies. Design an experiment that uses the same thread count and work, controls CPU frequency, and records handoff latency and completed messages per second. Identify at least two competing explanations if placement A is faster (coherence path length and cache reuse), and at least two possible confounders (different core capacity and background activity).

Check: any result must be presented as platform-specific. A thread on a sibling SMT context is not necessarily equivalent to a second physical core, and prefetcher or cache policy changes can alter the result.

Guided Exercise 3 — Analyze a NUMA Allocation Mistake

A thread on node 0 initializes a 2 GiB array. Later, twelve workers on node 1 perform dependent random reads of that array. Describe why first-touch allocation may make accesses remote, why a memory-binding change may not relocate already allocated pages, and how you would verify and repair locality. Compare parallel initialization with explicit migration and note the potential cost of duplicating the array.

Check: identify thread placement, page placement, and measurement as three separate questions. Do not prescribe global interleaving without examining latency and capacity.

Guided Exercise 4 — Find the Saturation Point

A streaming kernel achieves 8, 16, 27, 36, 40, and 41 GB/s with 1, 2, 4, 8, 12, and 16 physical cores. Plot bandwidth versus core count and identify the likely saturation region. Estimate marginal throughput beyond eight cores. Then list tests that would separate memory bandwidth saturation from cache thrashing or reduced all-core frequency.

Check: throughput increases by only about 5 GB/s from eight to sixteen cores, but the numbers alone cannot prove why. Compare physical DRAM traffic, cache events, core clocks, and changes to working-set size.

Guided Exercise 5 — Design a Hybrid-Core Policy

A service uses one high-priority event loop, four CPU-intensive batch workers, and intermittent background scanning. Explain how a policy could prioritize the event loop on suitable high-capacity cores without hardcoding numeric CPU IDs. Include conditions for allowing the batch workers to use the rest of the package and for reversing a manual affinity rule if deadlines or energy worsen.

Check: the answer distinguishes priority and capacity from fixed core identity. A good policy has measurement and rollback, and it does not assume that all SMT siblings or efficiency cores provide the same benefit.

This article's specialist responsibility is physical multicore topology and shared-resource consequences: core/cluster/package/chiplet relationships; cache and memory locality; uncore contention; scheduling and affinity consequences; and performance diagnosis across the topology.
