1. Definition, Scope, and Governing Question

Keyboard access is the ability to discover, reach, operate, and leave an interface using a keyboard interface rather than a pointing device. Focus management is the control of where keyboard interaction is directed as a person moves through ordinary document content, composite controls, dialogs, and dynamically changing workflows. These are closely related, but they are not synonyms. A page can contain dozens of focusable elements and still be unusable because focus travels in a confusing order, disappears visually, lands behind an overlay, or returns to the wrong place after an action.

The governing question is: Can a person complete the entire workflow without a pointing device and without losing their place? A defensible answer must be based on completing real tasks, including entering a page, moving among controls, acting on the intended target, responding to errors, reaching newly presented material, backing out, and recovering from interruption. Counting tabindex attributes or running an automated rule checker cannot answer that question alone.

Keyboard interfaces matter for many users: people who cannot use a mouse, people navigating with an alternative keyboard, switch or keyboard-emulating assistive device, people with temporary injuries, screen-reader users who depend on keys, and proficient keyboard users seeking efficient navigation. Device details belong in Motor Accessibility and Alternative Input; this article owns the interaction contract exposed to those input methods.

The article examines desktop and browser-based web interfaces as its primary examples, with principles that extend to native applications. It does not replace Semantic HTML and the Accessibility Tree, Accessible Names, Roles, States, and Properties, or the later specialist guide to complete ARIA widgets. Meaning, identification, and operability must work together; no one dimension certifies the other two.

2. Who Uses Keyboard Interfaces and What Counts as Success?

A keyboard is an interaction abstraction, not merely a full-size physical device. A mouth stick, alternative key layout, switch control that issues keystrokes, or certain voice-command systems may rely on the same keyboard-operable interface. Operating-system accessibility settings may modify how repeated keys, key combinations, or key duration behave. An implementation that requires rapid double-key presses or a narrowly timed sequence can therefore fail even when individual keys work.

Success should be evaluated across four capabilities: reachability (every necessary function can be approached), operability (the expected keys perform the action), orientation (the user can tell where focus is and what happened), and escape/recovery (the user can leave a region, undo errors, or continue after a state change). A focus ring is necessary to many journeys, but it will not rescue a control with no keyboard activation. Conversely, a key handler does not provide an accessible experience if nothing indicates its active target.

Keyboard access need not make a keyboard mimic a mouse event by event. For example, a path-dependent freehand drawing function has a narrowly framed exception under WCAG 2.1.1; a product should nevertheless identify the user's actual objective and consider keyboard-operable routes to equivalent results, such as setting coordinates or choosing an existing shape. Evaluation should not use the technical exception to excuse an otherwise unnecessary drag-only account setup or image upload.

Distinguish task-critical controls from decorative or informational items. Static headings normally belong to document reading rather than sequential Tab order. A keyboard user must be able to read them through browser or assistive-technology navigation, but making every paragraph tabbable would increase effort without making the content easier to use.

3. Four Different Meanings of Focus

The word focus can refer to several different systems. DOM focus identifies the element currently receiving keyboard events, typically observable through document.activeElement. Sequential navigation focus is the browser's movement among eligible focusable areas when the user presses Tab or Shift+Tab. Assistive-technology reading or virtual-cursor position can move through headings, paragraphs, and controls without changing DOM focus. Active descendant is a semantic reference, such as aria-activedescendant, representing the item active within a composite control while DOM focus remains on a containing element.

These are not interchangeable. A screen reader may announce an item in a document's reading mode that is not the active DOM element. A listbox can indicate an active option through aria-activedescendant while the textbox or listbox container still receives physical key events. A text caret inside an editable field also has its own location within the focused element.

Concept What moves? Common observation Frequent design mistake
DOM focus The browser's focused target document.activeElement in developer tools Deleting the focused node without a fallback
Tab sequence Browser-managed move among focusable targets Tab and Shift+Tab Inserting decorative elements as stops
Virtual cursor Assistive-technology reading position Screen-reader reading/navigation commands Assuming reading position always equals DOM focus

Every focus-management design should state which focus model it changes, what user action initiates the change, and how the user can continue. A component that silently moves DOM focus after a routine status update may contradict the user's screen-reader reading context or keyboard task plan.

4. Keyboard Events and the Contract of Standard Keys

Tab generally moves forward among sequentially focusable controls; Shift+Tab moves backward. Enter activates native links and buttons; Space activates buttons and often toggles native checkboxes. Arrow keys move through controls according to the control type: text caret in text fields, selection in native lists, and active items in properly designed composites. Escape commonly dismisses transient dialogs, menus, and certain popups. Home and End may jump to endpoints within controls where that convention is documented.

These behaviors are browser and platform conventions, not an invitation to intercept every key. A page-wide keydown handler that uses Space for an application shortcut can unintentionally prevent document scrolling or checkbox activation. An author who prevents Tab's default action without implementing a sound alternative may strand the user. When a standard native control already implements the desired operation, preserve it instead of reproducing its keyboard contract in JavaScript.

Test with the actual keys, not only a script that dispatches synthetic click events. Native buttons are normally activated by the browser; custom button-like containers require a deliberately implemented and tested input contract. Additional hardware devices, operating systems, and browser shortcuts complicate the picture, so product-defined shortcuts should be modest and discoverable.

5. Sequential Navigation: The Browser's Tab Order

For ordinary web pages, sequential focus follows the HTML focus navigation rules, influenced by focusability, tabindex, shadow trees, embedded browsing contexts, and the document structure. In uncomplicated markup, eligible interactive elements usually follow source order. This is a productive default: users can predict that the next control relates to the next meaningful step.

A sensible sequence for a registration form might be account email → password → reveal password → terms checkbox → submit → help link. The exact order must match the task and its presented relationships. Focus should not jump to a footer newsletter field after the first input merely because a framework rendered the field outside the apparent visual group. When tabs are used to enter a page, the browser might first visit the site's navigation and skip link; that can be entirely appropriate. A keyboard study must evaluate the whole path rather than isolating the component in a test harness.

A common conceptual error is to require every document element to have a Tab stop. Headings, paragraphs, table cells, and images normally do not need one merely to be readable. Keyboard-operated browser scrolling and screen-reader navigation provide other mechanisms. Excessive stops create a keyboard equivalent of a maze and can obscure the controls that actually perform work.

The evaluation test is not 'does Tab touch everything?' but 'does the user encounter a logical, understandable, operable sequence of meaningful controls?' WCAG 2.4.3 addresses focus order where sequence affects meaning or operation; it does not mandate one universal visual-scanning path for every layout.

6. `tabindex`: Zero, Minus One, and Why Positive Values Are Usually Wrong

The tabindex attribute changes focus participation. tabindex="0" places a normally non-tabbable element in the sequential focus sequence at its relevant position. tabindex="-1" normally removes an element from sequential Tab navigation while permitting focus by script, though platform and element behavior may have nuances. A positive tabindex is a strong warning sign: positive values create priority ordering that can detach keyboard navigation from the visual and source sequence. W3C authoring guidance discourages their use in routine application architecture.

<!-- Native controls already participate in normal navigation. -->
<label for="query">Search topics</label>
<input id="query" name="query" type="search">
<button type="submit">Search</button>

<!-- A heading can receive programmatic focus after a route change. -->
<h2 id="results-title" tabindex="-1">Search results</h2>

<!-- Avoid artificial priority: <a href="..." tabindex="12"> ... -->

tabindex="-1" is not a universal way to hide something from keyboard users: descendants may still be tabbable, and some elements can be focused through other mechanisms. When a whole region must be inactive, consider the browser's inert behavior, proper conditional rendering, or removal from the active document flow, depending on the interface. Likewise, aria-hidden="true" alone does not make focusable descendants noninteractive; applying it to a still-focusable subtree can yield a particularly confusing experience.

For composite widgets, it is reasonable to manage a single tabindex="0" entry and several -1 descendants, provided the arrow-key model is complete. That specialized pattern is different from scattering 0 across ordinary static content.

7. DOM Order, CSS Order, and Visual Expectations

Modern layouts can present a different visual sequence from source order. CSS Grid placement, flexbox order, absolute positioning, and responsive rearrangement can move elements onscreen without corresponding changes to DOM focus order. A card visually on the right may receive focus before a card on the left, or a bottom-sticky purchase control may be encountered before prerequisites that appear above it.

The correct repair is normally to establish a logical source and task structure first, then design presentation around it. Avoid using positive tabindex as a patch: it tends to break when content is inserted or the viewport changes. When the same DOM must support desktop and mobile layouts, test at narrow widths, high zoom, localized text lengths, and both text directions where relevant.

Worked inspection method: draw the sequence of visible task steps, then navigate Tab/Shift+Tab with a visible focus indicator. Write down the element reached at each step. Compare the results to screen-reader reading order and the intended task. Where differences occur, ask whether an action is presented at the wrong point, not just whether the CSS appears tidy. A good responsive arrangement minimizes contradictions among visual order, DOM reading order, and keyboard operation.

An author can deliberately use a focus sequence that is not visually top-to-bottom if the task remains coherent and meaning is preserved. The design question is predictability, not rigid compliance with a screenshot's spatial geometry.

8. Native Links, Buttons, and Form Controls Before Custom Handlers

For navigation, use an anchor with an href; for an action, use a button. Native elements include default roles, browser focus handling, activation behavior, and integration with assistive technologies. A pointer handler attached to a div is not an accessible button merely because it looks like one, and role="button" changes semantics without providing the full keyboard behavior of a native button.

<!-- Navigation and action are different contracts. -->
<a href="/library/encyclopedia/computer-science/">Computer Science index</a>
<button type="button" id="show-help">Show help</button>

<!-- Avoid using a styled generic container as the primary control. -->
<!-- <div onclick="showHelp()">Show help</div> -->

Native checkboxes, radio groups, select controls, text inputs, and details/disclosure elements also provide established keyboard behavior. Custom versions may be justified when essential product needs cannot be met with suitable native mechanisms, but they carry requirements for naming, selection, focus, key operation, and testing. disabled controls ordinarily leave the Tab sequence and cannot be activated, so the user's route to resolving an unavailable action must remain discoverable in nearby explanatory content.

When a control contains nested interactive descendants—such as a whole clickable card with internal buttons—users may encounter conflicting tab stops and event behavior. Prefer a clear link for the item and separate action buttons, with no interactive element nested inside another interactive element. This reduces both pointer and keyboard ambiguity.

9. Visible Focus: The Interface Must Reveal the Current Target

A keyboard user needs a visually detectable indication of the currently focused control. Removing outlines globally with outline: none or outline: 0 without an effective replacement makes a page disorienting, especially when many controls share similar styling. Focus is not the same as hover, selection, checked state, or an error indication. A selected tab can have a filled background while its current focus needs a separate visual signal.

/* A robust starting point: retain native outlines, enhance keyboard focus. */
:where(a, button, input, select, textarea, summary):focus-visible {
  outline: 3px solid currentColor;
  outline-offset: 3px;
}
/* Example only; verify contrast, clipping, zoom, and forced colors. */

:focus-visible is useful because browsers can choose when a focus indicator should appear based on input modality and the element. It should not become an excuse to hide focus from users whose technology or interaction mode differs from an assumed keyboard/mouse split. Ordinary text inputs can receive visible focus after a pointer click; behavior depends on browser heuristics. Test the actual implemented style, including high-contrast/forced-colors mode and components drawn on unusual backgrounds.

An outline around a control may be clipped by overflow: hidden, covered by a sticky element, or rendered outside an iframe viewport. Focus styling must be verified in context. A high-visibility design often uses a substantial outline with sufficient separation from the control edge, and does not rely on color change alone when other visual cues would help.

WCAG 2.2 contains distinct success criteria relevant to keyboard function and focus. Their levels and specific requirements differ; they must not be collapsed into a generic 'keyboard AA' label. WCAG 2.2 also addresses On Focus (3.2.1, A), Content on Hover or Focus (1.4.13, AA), and error identification, instructions, and status updates where relevant. An interface can satisfy a narrow rule while still creating slow or frustrating task pathways. Conversely, a positive usability study does not independently establish conformance with every applicable criterion. Both kinds of evidence matter.

The keyboard test plan should record criterion relevance, device and browser combinations, workflow observations, failures, and retest evidence. Where an organization claims WCAG conformance, it must follow the standard's actual conformance requirements rather than infer a page-wide result from an isolated example.

11. Focus Not Obscured: Sticky Headers, Overlays, and Scroll Positions

A fixed header can entirely cover a focused control after the browser scrolls it into view. Sticky cookie notices, chat widgets, bottom action bars, and cross-page navigation rails create similar risks. WCAG 2.4.11 (AA) addresses entire obscuration of focused components by author-created content in the relevant circumstances; 2.4.12 (AAA) strengthens that to any obscuration. Focus visibility and accessibility may still be poor well before the entire component disappears.

A targeted mitigation for predictable sticky headers may include CSS such as:

html { scroll-padding-top: 5rem; }
[id] { scroll-margin-top: 5rem; }

This example is not a universal conformance guarantee. scroll-padding and scroll-margin affect certain scrolling operations and may not solve every browser focus-scroll behavior, especially with nested scroll containers or overlays of variable height. Authors also need to inspect z-index layers, component placement, keyboard focus changes, and viewport size under zoom. A sticky footer can obscure controls at the bottom even if the header is accounted for.

Create a viewport test with narrow width, 200–400% zoom where applicable, a sticky header and a long form. Tab into each input while keeping hands off the mouse. Confirm that the focused input and focus indicator remain perceivable, with nearby label and validation context visible enough to continue the task. This exposes defects that a static contrast audit cannot find.

12. Focus-Induced Changes: Avoid Surprise Navigation and Context Switches

Receiving focus should not, by itself, unexpectedly submit a form, navigate away, change user context, or trigger a disruptive workflow. WCAG 3.2.1 addresses the on-focus principle. Opening help text on focus can be appropriate if the additional content is accessible and manageable; silently replacing the entire view when a field is tabbed into is usually not.

A common failure is a navigation menu that opens on focus and immediately sends the keyboard into a new region without any evident way back. Another occurs when an autocomplete selects the top suggestion merely because a user tabs into its input, before the person has typed anything. More subtle failures include reordering the whole page on focus so that the next Tab no longer follows the expected control.

Prefer explicit activation for significant changes: a button opens a dialog, a selected option followed by confirmation starts a transaction, and a link navigates. For purely contextual content on focus, ensure that it does not cover important controls, can be dismissed when needed, and remains accessible while the user interacts with it. Do not design with an assumption that every focus event came from a keyboard; focus may be established by assistive technology or script.

13. When Programmatic Focus Is Justified

The browser usually knows where focus belongs during ordinary navigation. Application code should move focus only when there is a meaningful change of interaction context that would otherwise leave the user without a sensible next step. Examples include opening a modal dialog, confirming a route transition in a single-page application, landing on an error summary after a failed submission, or moving to the next available item after the currently focused item is deleted.

The necessary design questions are: What event caused the change? What element should receive focus? Why is this element the most useful continuation point? What should happen if the target does not exist or is not ready? Where does focus go when the temporary context ends? For transient UI such as dialogs, plan the return destination before opening the interface. For permanent changes, such as removing a list item, choose a task-appropriate successor rather than returning blindly to an element that no longer exists.

function focusHeadingAfterViewChange() {
  const heading = document.querySelector('#view-title');
  if (!heading) return;
  // The heading has tabindex="-1" and is not an extra Tab stop.
  heading.focus();
}

focus() does not automatically announce everything useful to a screen reader. The focused element must have a sensible accessible name or text context, and the new content must be present in the DOM at the time focus is requested. Some UI frameworks defer rendering; a focus request performed before commitment may silently fail. The correct lifecycle and focus target should be part of the component contract.

Avoid habitual autofocus on every page load. Unexpected focus can interrupt screen-reader orientation and cause the viewport to jump past introductory material. A single focus shift may be useful after a specific user action, but repeated or unsolicited shifts can make the interface feel unstable.

14. Modal Dialogs: Enter, Operate, Exit, and Restore Focus

A modal dialog is a temporary interaction context that requires a response or dismissal before the user returns to the background application. The intended keyboard behavior is not an uncontrolled trap: focus is intentionally constrained within the active modal, and the user has an appropriate keyboard way to close or complete it. On closure, focus normally returns to the invoking control unless that control no longer exists or the task logically requires another destination. W3C's ARIA Authoring Practices explain exceptions to automatic return and the selection of suitable initial focus. See the official dialog pattern.

Using the native <dialog> element with showModal() is often preferable to recreating modality using arbitrary containers. Browser support includes putting the rest of the document in an inert state for that modal interaction, and native dialog behaviors. Authors still need to decide where initial focus belongs, label the dialog, provide an understandable dismissal mechanism, and verify focus return in their actual implementation.

<button id="open-preferences" type="button">Edit preferences</button>
<dialog id="preferences-dialog" aria-labelledby="preferences-heading">
  <h2 id="preferences-heading" tabindex="-1">Preferences</h2>
  <form method="dialog">
    <p>Review the options before saving.</p>
    <label><input type="checkbox" name="updates"> Send updates</label>
    <button value="cancel">Cancel</button>
    <button value="save">Save</button>
  </form>
</dialog>
<script>
const open = document.querySelector('#open-preferences');
const dialog = document.querySelector('#preferences-dialog');
open.addEventListener('click', () => {
  dialog.showModal();
  dialog.querySelector('#preferences-heading').focus();
});
dialog.addEventListener('close', () => {
  if (open.isConnected) open.focus();
});
</script>

This is a teaching example, not a full preferences workflow: handling persistent settings, validation, confirmation, and exceptions requires more code. The heading focus is appropriate for a dialog with introductory content but is not mandatory for all dialogs. For a short confirmation, initial focus may instead belong on a suitable action; for a destructive action, care may favor the least destructive option. The designer must decide based on expected user outcomes and official pattern guidance.

Do not add a custom Tab-cycling script to a native modal without clear need; it can conflict with the browser. Test nested layers, focus movement after disabling a control, Escape/cancel semantics, and the return destination after the invoking item has been removed.

15. Nonmodal Dialogs, Popovers, and Disclosures Need Different Rules

A nonmodal dialog permits interaction with other parts of the page while remaining open. It must provide a usable way to move between its contents and the rest of the interface. Constraining Tab indefinitely inside a nonmodal region contradicts the expected nonmodal behavior. A popover may be a simple list of choices, a transient informational panel, or a more complex interactive surface; its focus rules depend on its actual behavior, not the fact that it visually floats above content.

A disclosure reveals or hides content in the normal document flow. A native <details><summary>...</summary>...</details> structure provides a keyboard-operable disclosure with browser-managed semantics, although the author must still test styling and content. A custom disclosure button needs accurate expanded state and appropriately hidden content. In many ordinary disclosures, focus can remain on the activating button after expansion because the revealed content follows in the normal reading and Tab sequence.

<details>
  <summary>What payment methods are supported?</summary>
  <p>Card and bank-transfer options appear at checkout.</p>
</details>

A design that always moves focus into newly revealed content on every disclosure toggle can surprise users, especially if they were expanding several sections to scan headings. Move focus only when the task genuinely requires a new context. A tooltip-style hint should not become a concealed keyboard-only detour; content shown on focus also needs suitable dismissal and persistence behavior where WCAG 1.4.13 applies.

16. Composite Widgets: One Tab Stop, Then Internal Navigation

A composite widget is a coordinated control comprising multiple interactive items—for example, a tablist, tree, menu, listbox, toolbar, or interactive grid. Many standardized composite patterns use one sequential Tab stop and arrow-key navigation within the composite. Without this distinction, a grid with hundreds of cells might impose hundreds of Tab presses simply to reach the following page section.

The fundamental interaction cycle is: Tab enters the composite at a meaningful item; arrows navigate its internal choices; Enter/Space act where the pattern requires; Tab exits to the next element outside the composite. The exact keys depend on the widget type, orientation, selection policy, and the APG pattern. Do not apply arrow-key navigation to ordinary navigation links merely because they appear side by side in a toolbar-like visual layout. If the structure is simply five links, normal Tab behavior may be clearer.

Pattern Typical Tab contract Typical internal movement Activation or selection nuance
Ordinary links/buttons Each interactive item can be a stop Usually no author-defined arrow navigation Browser handles activation
Tabs A tab in the tablist is a stop Left/Right arrows for horizontal lists Automatic or manual activation policy
Menu One entry point under menu pattern Arrow navigation through items Enter/Space generally invokes
Listbox Listbox or active option represents entry Arrow navigation through options Selection may follow focus or require explicit action
Tree One item represents entry Vertical and hierarchical arrows Expand/collapse/selection are distinct
Data grid Controlled entry and cell navigation Arrows move among cells Editing mode may alter key use

The goal is not to memorize one master shortcut table. It is to apply established conventions consistently so users do not need to relearn basic operation for every application. The later Accessible Interactive Components and ARIA Patterns article develops the complete control-by-control interaction contracts.

17. Roving `tabindex`: Managing Focus Among Peer Items

In roving tabindex, one item in a composite receives tabindex="0" and peers receive -1. Arrow navigation updates which item is the sequential entry point and moves DOM focus to that item. A common invariant is exactly one active tab stop for the composite, except during transitional states intentionally managed by the component.

function moveRovingFocus(items, nextIndex) {
  const count = items.length;
  if (!count) return;
  const index = (nextIndex + count) % count;
  items.forEach((item, i) => {
    item.tabIndex = i === index ? 0 : -1;
  });
  items[index].focus();
}
// Call after a supported arrow-key action in a correctly modeled composite.

This code illustrates the focus mechanism only; a real widget must select eligible items, honor disabled-item rules for its pattern, respect right-to-left conventions where applicable, and synchronize selection or expansion state. In some patterns, disabled items remain arrow-focusable even though they cannot be activated. Their treatment cannot be determined by a blanket element.disabled ? skip : focus rule. Consult the relevant pattern's normative semantics and recommended interaction behavior.

Roving focus has practical advantages: DOM focus actually lands on the item, and browsers generally scroll the newly focused item into view. But it requires careful handling when the focused item is re-rendered or removed, and when React/Vue-style reconciliation re-creates DOM nodes. Store the logical active item in component state rather than assuming a particular node instance will survive every update.

18. `aria-activedescendant`: Active Item Without Moving DOM Focus

A second composite strategy leaves DOM focus on a container or textbox and sets aria-activedescendant to the ID of the logically active item. Assistive technologies can then announce the active item according to supported roles and relationship rules while the container continues receiving keyboard events. This is useful in patterns such as certain listboxes, grids, trees, and comboboxes.

<!-- Simplified concept: use only where the role permits this relationship. -->
<div role="listbox" tabindex="0" aria-label="Cities"
     aria-activedescendant="city-b">
  <div id="city-a" role="option" aria-selected="false">Austin</div>
  <div id="city-b" role="option" aria-selected="true">Boston</div>
  <div id="city-c" role="option" aria-selected="false">Chicago</div>
</div>

This snippet has no keyboard handler, so it is not a functional custom listbox. It illustrates the relationship between the focused composite and its active item. A production component must add the correct arrow and selection operations, name and state exposure, lifecycle handling, and live assistive-technology testing. The referenced ID must remain valid under the applicable ownership or controlled-element relationship, and the active item must be visibly identifiable.

Unlike DOM focus movement with roving tabindex, updating aria-activedescendant does not automatically guarantee the active child scrolls into view. Authors must manage scrolling and visibility if a long or virtualized list is involved. This distinction is critical: a screen reader might announce 'Boston' while a sighted keyboard user still sees 'Austin' above the scroll area unless the code keeps them synchronized.

19. Choosing Between Roving Focus and Active Descendants

The choice should follow a component's required behavior and its reference pattern, not team preference alone. Roving focus often simplifies scrolling and direct interaction with visible item elements. Active-descendant management can be advantageous where typing must remain in a textbox, or where a composite manages a large logical set with a stable container focus target. Both require careful semantic modeling and testing.

Semantic requirements Proper roles, states, handlers Supported role/relationship and valid IDs
Testing requirement Key operation, focus, scroll, AT Key operation, active announcement, scroll, AT

A team should not switch between strategies for the same widget type without a clear product reason, as users may notice inconsistent interaction. An implementation can pass a structural ARIA check yet fail because the active descendant ID refers to an item removed by filtering. Another can move focus visually but misannounce selection because aria-selected was not updated. Choose the strategy, then document invariants for every state transition.

20. Tabs: Automatic Activation Is Not Always Better

A tab interface presents alternative panels through a tablist. With automatic activation, arrow navigation both moves focus and changes the selected panel. With manual activation, arrow navigation moves focus among tab labels and the user presses Enter or Space to select a panel. W3C recommends automatic activation only when a panel can be displayed without noticeable latency; otherwise arrow exploration can trigger distracting or slow loads.

Consider a records dashboard with three tabs: Overview, Documents, and Audit History. If switching panels triggers expensive remote queries and destroys scroll position, forcing a load on every arrow press penalizes keyboard users. Manual activation lets the user move quickly to the target and explicitly commit the choice. Conversely, if all panels are already available, automatic activation may feel natural and efficient.

The tablist should convey selected state (aria-selected), panel relationships, and its keyboard contract. The panel must have an appropriate route into its contents; for example, when its first content is not otherwise focusable, tabindex="0" on the tabpanel can support onward navigation in some APG examples. Focus on a tab and selection of a tab are not necessarily identical, especially in manual mode.

This article establishes the focus principle rather than publishing a generic cut-and-paste widget. Complete tab patterns are treated by Accessible Interactive Components and ARIA Patterns. Refer to the W3C Tabs Pattern for the currently maintained interaction details.

21. Menus, Trees, and Interactive Grids: High Complexity Warrants Restraint

A website's ordinary navigation list is not automatically an ARIA menu; applying menu roles creates a more demanding keyboard contract than most simple link lists need. A menu is a composite application control with expected arrow-key behavior, entry and exit rules, and item semantics. A tree adds hierarchy, expansion, and selection; a grid adds cells, rows, and possible editing interactions. The more behavior an author adds, the greater the testing obligation.

For a tree, the common orientation is Up/Down across visible nodes, Right to expand or enter a child context, and Left to collapse or move toward a parent, with pattern-specific exceptions. A grid may use arrows to move among cells while Tab may advance beyond the widget; a cell that enters editing mode needs a way to restore grid-navigation mode. Text editing must not be broken by an overbroad key handler that steals arrow keys from the input caret.

The minimum architectural record for any such widget should contain: roles, label/description rules, focus strategy, entry stop, expected keys, selection policy, expanded/collapsed state, behavior when data changes, scrolling, disabled-item policy, and a screen-reader validation matrix. Without this record, accessible operation is often accidental and regressions are difficult to detect.

Where a native <select> or ordinary table with separate controls meets the task, prefer it. Complexity is not itself a measure of interface quality. A form with one select can serve more users than a bespoke searchable tree with twenty undocumented shortcuts.

22. Forms: Focus on Errors Without Disorienting Users

A failed submission should explain what needs correction and provide a reasonable path to the first actionable issue. An accessible error summary near the top can be programmatically focused after submission, with links to invalid fields. Alternatively, focusing the first invalid field may be suitable for a short form with a clear message. Neither should be an unconditional rule: the number and severity of errors, task context, and browser validation behavior matter.

<div id="form-errors" tabindex="-1" role="alert" hidden>
  <h2>Correct the following fields</h2>
  <ul><li><a href="#email">Enter a valid email address</a></li></ul>
</div>
<label for="email">Email address</label>
<input id="email" name="email" type="email" aria-describedby="email-help">
<p id="email-help">We will use this address for account messages.</p>

In this illustrative fragment, a script would show the summary, update invalid state and field-specific messages, then move focus appropriately after a failed submit. It also needs to handle the link's action and ensure errors are exposed programmatically. role="alert" may announce an update, but does not guarantee that focus moves; repeatedly re-rendering the entire alert can cause duplicate speech. A visible error message alone may not clearly identify the field or how to recover.

Avoid moving focus on each keystroke as a validator changes status. A person typing slowly may need the same input long enough to finish. Reserve a substantial focus change for clear task boundaries such as Submit, Next, or explicit navigation. The specialist Accessible Forms, Errors, and Recovery article provides the broader validation and error-recovery framework.

23. Dynamic Content: Addition, Removal, and Focus Continuity

Modern interfaces update lists, panels, and controls without reloading the page. If the currently focused node is deleted, the browser may move focus to the body or another unhelpful place. The user then has to rediscover where they were. This frequently happens after removing an item from a cart, deleting a notification, closing a selected tab, or submitting a row-level action.

The repair is task-dependent. After deleting the third of five notifications, focus may move to the next remaining notification action; if the last notification is deleted, to the previous action or the now-empty list heading. After adding an item, focus may remain on Add if the user is likely to add more, accompanied by an accessible status announcement. After invoking Edit, focus can move into an opened editor because the interaction context changed.

UI transition Risk Reasonable focus continuation
Remove one row Focused delete control disappears Next row action, otherwise previous or list heading
Open an inline editor New controls are undiscoverable First relevant editor field or named editor heading
Save a form Focus lost when button is replaced Confirmation heading or original action, depending on flow
Add an item to a collection Focus jumps away from repeated task Keep focus on Add; announce result
Close a transient popup Background context unclear Usually restore its invoking control
Change a filter Results update away from focus Keep focus on filter; announce result count or provide route

Track logical item identity, not only array index, because list filtering, sorting, and deletion can change positions. Before changing DOM structure, choose a fallback candidate, then apply focus after the new target exists. Prevent unnecessary changes of focus merely to announce a result; status updates and focus movement solve different problems.

24. Single-Page Applications and Client-Side Route Transitions

In traditional document navigation, the browser performs a page transition and establishes a recognizable new document context. In a client-rendered application, changing a route may replace the main view without giving keyboard or screen-reader users an equivalent indication. Focus can remain on the navigation link from the old view, now removed, or somewhere in persistent application chrome. An updated URL alone does not guarantee orientation.

A practical route-change policy is to update the document title, render the new main heading, and move focus to that heading (tabindex="-1") or another well-justified target after the navigation is committed. The transition should also support back/forward history and avoid stealing focus during incidental background data refreshes. If the route is simply a small state change inside a stable context, a status announcement may suffice instead of a forced heading jump.

<main id="route-content">
  <h1 id="route-heading" tabindex="-1">Account overview</h1>
  <!-- Route-specific content -->
</main>
<script>
function announceRouteReady(title) {
  document.title = `${title} | Example Service`;
  const h1 = document.querySelector('#route-heading');
  if (h1) h1.focus(); // Call after the new view has rendered.
}
</script>

This is an integration contract, not a complete routing implementation. Component frameworks differ in render timing, built-in focus restoration, title handling, and scroll restoration. The team should test hard reloads, internal link transitions, browser Back, redirects, and authentication interruptions. The intended pattern must be consistent enough that a keyboard user can predict how to orient in the new view.

25. Virtualized Lists, Infinite Scrolling, and Focus Ownership

Virtualization renders only some items in a large collection. It can improve performance, but focused nodes can disappear when the rendered window changes. Infinite scrolling can repeatedly insert content before the next expected Tab stop, preventing users from reaching information or footer controls. A virtualized listbox using aria-activedescendant may reference an item whose element no longer exists in the DOM.

Design options include a stable keyboard-operable pagination method, a controlled 'Load more' action, or a virtualization strategy that maintains logical focus and scroll position across render windows. Provide a clear result count or location cue where practical. If new items are inserted after an explicit Load more action, consider whether focus should stay on the button, move to the first new item, or go to a new section heading. A choice that benefits one task may be disruptive for another.

Before accepting a virtualized widget, test the first and last item, a filtered empty result, rapid scrolling, row deletion, dynamic sorting, and screen-reader virtual navigation. The service must not turn Tab into an endless chase where new controls continually appear before the user can exit. Loading indicators should not steal focus on every update.

26. Keyboard Shortcuts and Timing-Sensitive Commands

Keyboard shortcuts can improve efficiency, especially in editors and professional tools, but compete with browser, operating-system, screen-reader, and international keyboard conventions. WCAG 2.1.4 addresses shortcuts using only letters, punctuation, numbers, or symbols: authors must meet one of the specified mechanisms for turning them off, remapping them with a non-printable modifier, or activating them only when the relevant component has focus. This rule is not a blanket prohibition of all single-character shortcuts; the conditions matter.

Shortcut designs should disclose available commands where users naturally look for them, provide a way to complete essential work without memorizing a shortcut, and avoid capturing keys while a user is typing in an input, textarea, or editable region. A global S = Save shortcut, for example, can corrupt the experience of someone entering an email address or writing a note. A save button and a properly scoped Ctrl+S or Cmd+S binding may be more reliable, subject to platform conflicts.

Avoid precise timing requirements such as 'press the next key within 250 milliseconds' unless genuinely necessary and explicitly supported. Alternate input tools can introduce delay, and users may pause between keys. Repeatability and forgiveness are better default goals than speed assumptions. Provide visible confirmation for important actions, and avoid destructive commands without an understandable recovery path.

The keyboard shortcut policy should be recorded at product level. If two independent components bind the same key, local scopes and focus ownership must decide which responds. Random event handlers added by separate teams are a common source of conflicts.

27. Embedded Content, Editors, and Keyboard Boundary Conditions

Embedded iframes, rich text editors, code editors, maps, media controls, and third-party widgets often establish their own keyboard contexts. A user may be able to Tab into an embedded experience but unable to Tab back out, or a shortcut used by the embedded tool may conflict with the host page. These cases are particularly important because the page owner may not control all of the embedded implementation.

The basic requirement is a reliable entry and exit path. Test ordinary Tab, Shift+Tab, Escape where applicable, the browser's documented mechanisms, and screen-reader mode changes. If leaving a component requires a nonstandard command, its instructions must be accessible before the user becomes stuck. Do not accept a vendor's general accessibility statement in place of directly testing the embedded workflow used in your product.

An interactive map may need an accessible list of locations or keyboard-operated zoom and movement controls; a media player needs named buttons that can be operated without pointer gestures. An advanced code editor may intercept Tab to indent code; provide an understandable way for users to leave editing mode, and make the shortcut discoverable. Accessible implementation depends on the tool and its input model, not on a one-size-fits-all script.

Where an external frame takes focus, the host application's focus indicators may disappear by design because the active target is inside the embedded document. That should not be confused with focus loss. The test must follow focus across document boundaries and determine whether a usable and visible target remains available.

28. No Keyboard Traps, and the Legitimate Boundaries of Modality

A keyboard trap occurs when a user can enter a region using the keyboard but cannot leave using a keyboard interface, except in narrowly defined situations with documented exit methods recognized by the relevant criterion. A deliberately modal dialog is a contrasting case: while open, keyboard focus is constrained to the dialog, but the user can dismiss it or complete the interaction using the keyboard and then return to the surrounding context.

This distinction matters because some teams treat any attempt to constrain focus as a WCAG failure, while others mistakenly call a true trap 'modal behavior.' Evaluate purpose and exit. Does the region have an intended transient context? Is there a keyboard-operable dismissal or completion path? Are controls to dismiss it reachable and perceivable? Does focus return predictably? Does the user need to follow a hidden or obscure command to escape?

Common traps arise from nested overlays with conflicting focus-lock scripts, iframes with inaccessible toolbars, legacy plugins, keyboard-event handlers that prevent Tab, and custom widgets that continually cycle focus even after the overlay closes. Reproduction should record the exact starting control, keys pressed, focused element, and whether an escape path works with no pointing device.

An emergency workaround such as refreshing the page is not an acceptable ordinary exit from an author-created interaction. It may discard unsaved information. Preventing such dead ends should be a release-blocking condition when the affected path is necessary for completing a user task.

29. Testing Matrix: Different Browsers, Input Methods, and States

Automated tests can detect certain structural problems, but they cannot independently prove a usable focus order, visible focus under overlays, correct return after deletion, or intuitive keyboard navigation. The minimum practical test includes manual keyboard traversal of representative complete tasks. Add screen-reader combinations to evaluate semantic exposure, remembering that virtual cursor movement and DOM focus are different systems.

Test dimension Minimum cases Evidence to record
Keyboard-only traversal Tab and Shift+Tab through primary task Ordered list of stops; unreachable or confusing controls
Key operation Enter, Space, arrows, Escape, Home/End as relevant Whether actions match documented or standard behavior
Visibility Default, zoomed, high contrast, sticky elements Focus marker and target remain visible
State transitions Open/close, submit/error, delete, filter, route Focus destination, user orientation, recovery
Browser differences Supported desktop browsers/platforms Unexpected focus or scroll variation
Assistive technology Representative screen reader with target browser Announcement of target, state, and changed context
Dynamic content Fast updates, no results, network errors Stable focus and useful status signals
Responsive layouts Narrow viewport and enlarged text Coherent focus sequence and no overlays hiding focus
Alternative input Keyboard-emulation path where supported Timing tolerance and ability to reach functions

Do not interpret a single screen-reader/browser combination as evidence for every assistive-technology environment. Nor should an evaluation claim that a keyboard user always experiences the same reading sequence as a screen-reader user. The team should explain coverage and known limitations in release notes or evaluation records where material.

For actionable defects, record setup → initial focus → keystrokes → expected behavior → observed behavior → environment → consequence → proposed repair. This allows a developer who was not present at the test to reproduce the failure. Prioritize defects by blocked task and severity, not only by how easy they are to fix.

30. Common Failure Modes and Root-Cause Analysis

Keyboard defects often appear as isolated visual glitches, but their causes sit in architecture and lifecycle decisions. The table below connects symptoms to repairs without assuming that a one-line CSS change resolves the entire experience.

Observed failure Likely root cause More durable corrective action
Focus appears to vanish after deleting a row Focused DOM element was removed Choose and focus a stable logical successor
Tab jumps around a responsive layout CSS order differs from source order Align source and task structure; test breakpoints
Modal opens with focus behind it Overlay lacks genuine modality/focus placement Adopt native modal or a tested dialog contract
Focus ring invisible Outline removed, weak styling, or clipping Restore and test a robust indicator in context
Arrow keys cannot reach list options Incomplete composite interaction model Apply APG pattern and focus strategy
Focus stays inside a closed popup Focus-lock cleanup or inert state failed Release modality and restore appropriate target
Keypress triggers unrelated command while typing Global shortcut intercepts printable keys Scope, remap, or disable shortcut
Search filtering resets focus to page start Re-render destroyed active control Preserve logical focus on filter; announce update
Focus under sticky navigation Scroll/overlay geometry ignores focused element Redesign overlay/scroll positioning and retest
Link works by mouse only Click-only generic element Use an anchor or button with native activation

A repair should be evaluated at three levels: the individual element (focus, semantics, activation), the interaction transition (before and after an action), and the complete workflow (can the user still accomplish the objective?). Fixing the outline does not address a broken submission path; moving focus into a dialog does not address the impossibility of closing it.

31. Implementation Patterns: Focus Styling, Route Landings, and Safe Recovery

A reusable design system can standardize most of the recurring focus obligations. Start with native controls, shared visible-focus tokens, well-defined dialog primitives, and a policy for programmatic focus. The following implementation fragments intentionally illustrate separate concerns rather than form one script to paste into production.

Pattern A — Focus styling that survives forced-colors evaluation

:where(a, button, input, select, textarea, summary):focus-visible {
  outline: 3px solid currentColor;
  outline-offset: 3px;
}
@media (forced-colors: active) {
  :where(a, button, input, select, textarea, summary):focus-visible {
    outline: 3px solid Highlight;
    outline-offset: 3px;
  }
}

The example depends on surrounding backgrounds and control styles. Inspect actual rendered contrast, outline clipping, disabled states, and any transformed containers. :focus-visible should complement rather than erase other necessary browser affordances.

Pattern B — Preserve focus after removing a list item

function removeRowAndRestoreFocus(button) {
  const row = button.closest('li');
  if (!row) return;
  const nextRow = row.nextElementSibling || row.previousElementSibling;
  const list = row.parentElement;
  row.remove();
  const successor = nextRow?.querySelector('button, a[href]');
  if (successor) {
    successor.focus();
  } else {
    const heading = document.querySelector('#collection-heading');
    if (heading) heading.focus(); // tabindex="-1" on heading
  }
  // Separately announce successful deletion through a status region.
}

This simplified example assumes a known list structure and does not perform confirmation, persistent deletion, asynchronous failure handling, or model-state reconciliation. A production UI should not irrevocably remove a record on click if undo or confirmation is required. It should also avoid using CSS alone to hide the row while leaving inaccessible focus targets.

Pattern C — Manage an inline disclosure without a focus jump

<button type="button" aria-expanded="false" aria-controls="shipping-help"
        id="shipping-toggle">Show shipping details</button>
<div id="shipping-help" hidden>
  <p>Delivery options appear after a destination is selected.</p>
</div>
<script>
const toggle = document.querySelector('#shipping-toggle');
const panel = document.querySelector('#shipping-help');
toggle.addEventListener('click', () => {
  const open = toggle.getAttribute('aria-expanded') !== 'true';
  toggle.setAttribute('aria-expanded', String(open));
  panel.hidden = !open;
  // Keep focus on the activating button.
});
</script>

This illustrates appropriate state synchronization: the disclosure remains focused, its expanded state changes, and content becomes available in reading/Tab order. Adding tabindex="0" to every paragraph in the panel would be counterproductive. The equivalent native <details> may be simpler for many uses.

Pattern D — Prevent keyboard handlers from stealing typing keys

function isEditingTarget(target) {
  return !!target.closest('input, textarea, select, [contenteditable="true"]');
}
document.addEventListener('keydown', (event) => {
  if (isEditingTarget(event.target)) return;
  // Scope any application shortcut to a known component and
  // implement the WCAG 2.1.4 shortcut safeguard appropriate to it.
});

The code intentionally defines no global shortcut. A real implementation must also consider nested content-editable regions, platform conventions, shadow DOM, and assistive-technology shortcuts. The safest shortcut is often the one you never need to intercept because the necessary action has a visible native control.

32. Eight Worked Cases: From Keyboard Failure to Usable Task Flow

The following are constructed instructional scenarios, not reports of specific live products. Each separates the user goal, failure mechanism, corrective choice, and evidence required for acceptance.

Case 1 — A student cannot reach an online examination's Submit button

An examination platform visually places Submit below the final question but uses a custom scrollable panel that intercepts Tab and continually cycles through the answer options. The student can select answers with a mouse but cannot leave the panel by keyboard. Adding aria-label to Submit will not fix an inaccessible path to it.

Repair: identify whether the panel is truly a composite; restore a normal Tab exit route and preserve native form controls wherever possible. Test from the exam title to the final submission confirmation, with no pointer. Acceptance evidence: a user can enter the question area, move through answers, reach Submit, review confirmation, and leave the flow without an undocumented shortcut.

Case 2 — A bank's security dialog opens behind the keyboard cursor

A user activates Verify Identity; a modal visually overlays the page, but DOM focus remains on the background action. Tab reaches account links hidden under the dimmed layer. This is a failure of modal interaction, not simply a missing focus outline.

Repair: use a correctly labeled native modal dialog where suitable, choose initial focus based on the verification task, make Cancel/close reachable, and restore focus to Verify Identity or a logical next step on closure. Acceptance evidence: Tab/Shift+Tab stay in the modal while open, the user can dismiss or finish it with keyboard, and background controls remain noninteractive until closure.

Case 3 — A research dashboard has an invisible focus indicator

Buttons respond to Enter and Space, but the design system globally removes outlines. Mouse users see a hover effect, while keyboard users cannot tell which similar chart filter is active. Adding a tooltip on hover does not fix the focus problem.

Repair: introduce a consistent :focus-visible treatment, test dark/light panels, high-contrast mode, and zoom, and distinguish keyboard focus from the filter's selected state. Acceptance evidence: every actionable filter has a clear focus indicator without covering chart labels or being clipped by card boundaries.

Case 4 — A support portal loses focus after a ticket is deleted

A support agent deletes a row in a queue. The row and its Delete button are removed, leaving DOM focus at the document body. The next Tab returns to the beginning of navigation instead of the next ticket. Repeating this operation at scale creates hundreds of unnecessary keystrokes.

Repair: preserve logical selection; after removal, focus the next available row's primary action, otherwise the previous row or list heading, and announce deletion success. Acceptance evidence: the agent can delete consecutive tickets without losing queue position, including the last-item and empty-list cases.

Case 5 — A university course site changes routes without orientation

A learner activates Module 3 in a single-page application. The content swaps, but focus remains on the old Module 3 link or disappears if the navigation component is recreated. The title and heading may remain stale. The learner has no clear indication that the main task changed.

Repair: after route completion, update the document title and focus a meaningful main heading, preserving back-navigation behavior. Acceptance evidence: the new module is identifiable without mouse input, and Back restores an understandable context without an unexpected infinite focus loop.

Case 6 — A data-entry tablist loads a remote panel on every arrow press

A six-tab finance interface automatically activates each tab on Right Arrow, causing multiple network requests and intermittent focus jumps. A user trying to reach the sixth tab accidentally triggers five expensive loads. The tablist may be semantically valid, yet interaction efficiency is poor.

Repair: use a manual-activation tab pattern when latency is noticeable, keeping arrow movement and selection distinct. Acceptance evidence: rapid arrow navigation does not launch needless loads; Enter or Space activates the selected destination; selected state and panel focus are communicated correctly.

Case 7 — A product filter's active option is scrolled out of view

A custom listbox uses aria-activedescendant and updates the active option after Down Arrow, but never scrolls its inner viewport. A screen reader may announce later options while a sighted keyboard user sees the top of the list. The interface now exposes two conflicting locations.

Repair: ensure the active option stays visually within the scroll area and maintain valid IDs, selected state, and keyboard behavior through filtering. Acceptance evidence: the active item, announced item, and visible item remain synchronized at the beginning, middle, and end of a long list.

Case 8 — A keyboard shortcut interrupts a medical intake form

A clinic intake system binds the unmodified letter S to Save while a patient is typing a surname into an input. The form saves prematurely and interrupts entry. The existence of an accessible Save button does not excuse the global conflict.

Repair: remove or remap the shortcut, or constrain it to the appropriate focused application control under WCAG 2.1.4's permitted options; preserve the visible Save action. Acceptance evidence: ordinary text can be entered without commands firing, all fields can be completed, and any retained shortcut is discoverable and does not collide with essential platform behavior.

33. Ten-Step Keyboard and Focus Evaluation Framework

Use the following as a repeatable task-based method, not a substitute for detailed WCAG evaluation or direct user research. Each gate should produce an observable artifact so that designers, engineers, and testers can agree on what success looks like.

Step Question Evidence or decision
1. Define task What does the user need to accomplish without a pointer? Written task and completion state
2. Map controls Which elements are truly interactive? Native-control inventory and role map
3. Specify tab path How does sequential navigation move through the task? Ordered traversal chart
4. Specify key behavior Which keys act at each component? Interaction contract referencing the right pattern
5. Confirm visible focus Can users see the active target at all relevant sizes? Focus-state visual inspection
6. Plan transitions Where does focus go after open, save, delete, and route changes? Before/after focus transition matrix
7. Define exit/recovery Can users close, leave, undo, and continue? Escape, cancellation, and error cases
8. Test environments What happens with zoom, browser differences, AT, and alternative input? Supported test matrix and findings
9. Remediate by consequence Which failures block or misdirect key user goals? Prioritized defect register
10. Retest lifecycle Do revisions preserve keyboard behavior? Regression tests and ownership records

A team can supplement this with a focus-flow diagram: draw each actionable state as a node, show Tab paths and action-triggered changes as distinct edges, and mark focus restoration after transient states. Even a simple diagram reveals missing exit edges and circular focus paths more clearly than long prose alone.

Release readiness should require successful full-task manual testing for high-impact journeys, not only automated rules. Accessibility and design-system owners should retain tests for recurring components, while application teams remain responsible for their real workflow integration.

34. Team Responsibilities, Design Systems, and Lifecycle Controls

Keyboard accessibility is a shared operational responsibility. Designers specify state, ordering, modality, visible focus, and error recovery; engineers implement the focus mechanism and its lifecycle; content and product teams maintain understandable actions and transitions; testers verify actual tasks; and affected users provide insight into efficiency, fatigue, and unexpected barriers. These responsibilities should be explicit rather than passed from team to team after launch.

A mature design system should supply a small number of well-tested interactive primitives—buttons, links, disclosures, dialogs, forms, tabs, and other justified composites—with documented keyboard expectations. Each primitive should include an API for focus return where appropriate, and each must be validated inside actual application transitions. Reusing a shared component does not guarantee that a route change, modal stack, or asynchronous filter will work in every product.

Require a keyboard contract in component review: default focus entry, key map, visible indicator, focused/selected/disabled distinctions, action result, dynamic state updates, and how the component yields focus when complete. Test plans should cover lifecycle actions such as delete and re-render, not only first paint. Platform-specific differences should be recorded, and divergence from expected conventions needs a reason and user evidence.

For remediation, avoid sweeping fixes such as adding tabindex="0" to every element or automatically focusing every newly displayed message. Correct the underlying task architecture. Recheck the affected workflow after localization, responsive redesign, component replacement, or framework upgrades because focus order and timing can change despite unchanged content.

36. Study Questions and Applied Exercises

Conceptual questions. (1) Why is a focusable button not necessarily keyboard-usable? (2) How does a screen reader's virtual cursor differ from DOM focus? (3) Why is a positive tabindex fragile under responsive layout changes? (4) When should opening an element shift focus, and when should focus remain on the trigger? (5) How does a modal focus constraint differ from an inaccessible keyboard trap? (6) What is the practical difference between a selected tab and a focused tab? (7) What additional work does an author using aria-activedescendant owe a sighted keyboard user? (8) Why cannot a successful automated scan establish complete task accessibility?

Exercise A — Trace a real task. Choose a multi-step form on a site you are authorized to examine. Without a mouse, record all Tab stops from entry to submission. Mark unexpected jumps, focus invisibility, and unnecessary stops. Then test Shift+Tab to assess reversal. Deliver a short path diagram and two prioritized improvements.

Exercise B — Reproduce a dialog cycle. Use a local test page with a modal <dialog> and a labeled opener. Confirm initial focus, Tab containment, Escape behavior, Save/Cancel completion, and focus return. Delete the opener while the dialog is open in a controlled test environment and document your chosen fallback destination.

Exercise C — Contrast two focus strategies. Create a small horizontal three-item composite. Implement roving tabindex, then model the same logical active item using a supported active-descendant strategy. Compare DOM focus, scrolling, active-state communication, and what happens if the active item is removed. Explain which strategy fits an editable combobox and why.

Exercise D — Audit sticky overlay behavior. Place a fixed header over a long set of controls, then test at narrow width and large zoom. Compare a simple scroll-padding-top mitigation with an adjusted overlay layout. Report whether any focused component remains entirely or partly obscured and which WCAG 2.2 criteria are applicable.

Exercise E — A focus recovery test. Build a four-item task list with a Delete button on each item. Delete the second item, then the last remaining item. Record the focus destination after each operation. Add asynchronous confirmation and a simulated network failure; decide when focus should remain and when a status message is preferable to a focus move.

Exercise F — Write an acceptance contract. Select one keyboard problem from the scenarios and prepare: governing user task, affected controls, expected keys, before/after focus targets, visible-focus specification, browser/AT test matrix, and objective release acceptance criteria. Include at least one case where the correct behavior is not to move focus.
