1. Definition, Scope, and Governing Question

An accessible interactive component is a discrete interface mechanism that can be discovered, understood, operated, and exited by people using different sensory, motor, and cognitive strategies. A component may be as simple as a disclosure button or as demanding as a spreadsheet-like grid. Its accessibility is not captured by visual similarity to a familiar product. It rests on whether its controls communicate what they are, what they do, their current conditions, and the commands available to operate them. Users must be able to complete the underlying task rather than merely reach a control.

WAI-ARIA—Accessible Rich Internet Applications—provides roles, states, and properties used by browser accessibility APIs to describe elements when native HTML alone cannot convey the intended semantics. The W3C ARIA Authoring Practices Guide (APG) describes common interaction patterns and illustrative implementations. An APG pattern is not a plug-and-play compliance certificate: examples have implementation choices and must be verified in the real browser, framework, content, and assistive-technology combinations in which they are deployed.

The governing question is: Which interaction pattern best represents the task, and what complete behavioral contract must the team implement before presenting that pattern as accessible? This article owns component-pattern selection, composition, keyboard contracts, state transitions, and concrete testing methods. The companion articles on Semantic HTML and the Accessibility Tree, Accessible Names, Roles, States, and Properties, and Keyboard Access and Focus Management examine those foundational mechanisms individually.

2. The Four-Part Component Contract

A working interactive control has four linked contracts: semantic, behavioral, perceptual, and lifecycle. The semantic contract is its exposed name, role, value, state, and relationships; the behavioral contract covers keyboard, pointer, and alternative-input actions; the perceptual contract makes state changes visible, nonvisually available, and understandable; the lifecycle contract governs opening, updates, errors, and teardown. All four matter. A dropdown with a perfect aria-expanded value but a keyboard trap is not accessible. A button that responds to Enter but has no accessible name is not accessible either.

Contract Design question Observable failure Acceptance evidence
Semantics What object and state does the browser expose? An icon appears as an unnamed button Inspect accessibility tree; verify name and role
Operation What keys and gestures activate or navigate? Tab reaches a tablist, but arrows do nothing Execute documented key matrix
Feedback How does the user know the result? “Saved” appears only as a color flash Verify visual text and assistive announcement as appropriate
Lifecycle Where does focus go when content opens or closes? Dialog closes and focus disappears Test open, cancel, confirm, and removal paths

The most useful review artifact is a state-transition specification: for each event, list the initial state, trigger, resulting DOM and ARIA state, focus destination, visible feedback, and error or cancellation path. This is more actionable than an undifferentiated demand for “ARIA support.”

3. Prefer Native HTML Before Inventing a Widget

Use <button> for actions, <a href> for navigation, <input> and <select> for common data entry, <fieldset> and <legend> for groups, and <details> with <summary> for an appropriate simple disclosure. Native controls already include established keyboard activation, focus behavior, accessibility mappings, and integration with browser and operating-system services. A styled <div role="button"> does not gain Space/Enter activation or focusability simply because its role is declared. When an author recreates a familiar browser control, the project inherits the burden of reproducing its entire interaction contract.

Native does not mean unstyled, visually plain, or sufficient under every circumstance. It means start with the platform contract and augment only what a genuine requirement demands. A <select> may be more robust than a custom listbox when choices are simple; a set of radio buttons may be easier than a bespoke searchable popup when there are only a few options. Conversely, an application with thousands of records and live suggestions may require a specialized combobox. That is a product decision with measurable accessibility costs.

<!-- Native control: focusable and keyboard-operable by default. -->
<button type="button" id="export-report">Export report</button>

<!-- Not equivalent: role alone does not add browser button behavior. -->
<div role="button">Export report</div>

The second example is intentionally incomplete and unsuitable. If a design system already produces a nonsemantic wrapper, correct its underlying element rather than layering ARIA attributes over structural debt. Consult the W3C APG introduction and APG keyboard guidance.

4. Normative Specifications, APG Guidance, and WCAG

Do not conflate three related authorities. HTML and WAI-ARIA specifications define semantics and technical requirements; WCAG defines outcome-oriented accessibility success criteria and conformance conditions; APG is informative design and implementation guidance for common widget patterns. Following an APG code sample is useful evidence of design intent, not automatic proof of WCAG conformance. An application can satisfy a particular keyboard pattern and still fail text contrast, resize, error identification, or accessible authentication requirements.

The published WAI-ARIA 1.2 Recommendation is an established normative reference. ARIA 1.3 material reviewed in 2026 remains a Working Draft and should not be described as a finalized Recommendation. Current APG pages change over time; development teams should record the reviewed date and pattern version, and recheck them during significant redesigns.

Resource Role in a project Typical evidence
HTML Living Standard Browser-native elements and behavior Correct markup, DOM events, native states
WAI-ARIA Recommendation Roles, states, attributes and structural rules Accessibility-tree mapping, authoring constraints
ARIA Authoring Practices Guide Common widget interaction conventions Pattern-specific keyboard and focus tests
WCAG 2.2 Testable outcomes and conformance criteria Criterion-linked evidence and exceptions
Representative user research Whether real people can use the task Observed strategies, failures, and recovery

For the unit-wide distinction between conformance claims and usability evidence, see Accessibility Standards and Conformance.

5. Select Patterns by Function, Not Appearance

A chevron, three-dot icon, or rectangular popup does not uniquely identify a component. A chevron might open an ordinary disclosure, expand a tree branch, trigger a menu, or reveal combobox suggestions. The correct pattern depends on what the opened material contains, whether it is a collection of commands or form choices, how selection is committed, and what keyboard conventions users should expect. Pattern selection therefore precedes CSS selection.

User goal Usually begin with Avoid assuming
Show or hide additional content <details> or disclosure button A menu is required because a chevron is shown
Choose one of several simple values Native <select> or radios Custom listbox is automatically superior
Perform an action from a command list Menu button, where menu semantics are warranted Site navigation requires role="menu"
Switch between related panels Tabs Tabs are equivalent to links to different pages
Edit spreadsheet-like cells Interactive grid Every HTML table should have role="grid"
Enter text with suggestions Native input/datalist where suitable, or combobox Suggestions alone are a fully accessible combobox
Temporarily require a decision Native <dialog> with showModal() when appropriate A CSS overlay is automatically modal

A decision record should capture task scale, expected input devices, native alternatives considered, screen-reader and speech-input implications, expected maintenance burden, and the fallback if scripting fails.

6. Disclosures: Expanding Ordinary Content

A disclosure reveals or hides content without changing the user's conceptual location. The trigger is a button whose visible label names the content and whose expanded state matches the displayed region. It should work with Enter and Space through native button behavior. A simple native <details>/<summary> can satisfy many disclosure tasks without additional scripting. Authors should not use a generic noninteractive heading as the only click target.

<details>
  <summary>Shipping restrictions</summary>
  <p>Some destinations require additional handling.</p>
</details>

When a bespoke design genuinely needs an independent button, maintain aria-expanded and panel visibility in lockstep. aria-controls can associate a button with the controlled element but does not itself cause the panel to appear or disappear. Avoid a state update that changes the icon while leaving the accessibility tree stale. Do not move focus into the expanded material simply because it became visible; users ordinarily continue reading or navigating from the disclosure.

<button type="button" id="more-btn" aria-expanded="false"
        aria-controls="more-panel">Show service details</button>
<div id="more-panel" hidden>
  <p>Applications are reviewed in the order received.</p>
</div>
<script>
const moreButton = document.querySelector('#more-btn');
const morePanel = document.querySelector('#more-panel');
moreButton.addEventListener('click', () => {
  const opening = morePanel.hidden;
  morePanel.hidden = !opening;
  moreButton.setAttribute('aria-expanded', String(opening));
  moreButton.textContent = opening ? 'Hide service details' : 'Show service details';
});
</script>

This is a bounded teaching example, not a complete reusable library. In a framework, state should be generated from one source of truth rather than independently changed by multiple handlers.

7. Accordions: Grouped Disclosures with Structure

An accordion is a set of disclosure headings, each controlling an associated panel. The APG pattern places the interactive button inside an appropriate heading element; this preserves document structure and exposes expansion state. Some accordions allow several panels open at once, while others require one open panel. That choice affects the interface's promise: a user should not lose material they are comparing merely because a designer arbitrarily enforced one-open-at-a-time behavior.

<section aria-labelledby="billing-heading">
  <h3 id="billing-heading">
    <button type="button" aria-expanded="false" aria-controls="billing-panel">
      Billing questions
    </button>
  </h3>
  <div id="billing-panel" hidden>
    <p>Use the invoice history to inspect prior charges.</p>
  </div>
</section>

The snippet shows required relationships, not working toggle behavior; it needs the same synchronized handler described in the previous section. Optional arrow-key shortcuts between accordion headers may be implemented consistently, but Enter and Space on the header button are core operations. Do not assign a region role to dozens of tiny panels indiscriminately: excessive landmarks can obscure rather than clarify navigation. A compact FAQ may be better as simple details elements than as an elaborate ARIA component.

8. Buttons, Toggle Buttons, and Command Feedback

A command button performs an action; a toggle button represents a persistent on/off condition such as “Mute audio.” Its label should normally remain stable while aria-pressed changes between true and false; renaming “Mute” to “Unmute” while also exposing aria-pressed can create confusing or duplicated state communication. A switch expresses an on/off setting, often better served by a native checkbox with appropriate styling, while a command button such as “Save” should generally not announce a pressed state.

<button type="button" id="mute" aria-pressed="false">Mute audio</button>
<script>
const mute = document.getElementById('mute');
mute.addEventListener('click', () => {
  const newValue = mute.getAttribute('aria-pressed') !== 'true';
  mute.setAttribute('aria-pressed', String(newValue));
  // Production code must also change the actual audio state here.
});
</script>

State cannot be ceremonial. The demonstration exposes the toggled condition, but unless the underlying audio operation succeeds, it misrepresents reality. In real applications, update the semantic state only when the operation succeeds or communicate a pending and then failed state. Button names should include their visible labels for speech-input compatibility; do not name a visible “Export” button “Generate spreadsheet artifact” solely for assistive technology.

9. Modal Dialogs: Containing a Temporary Decision

A modal dialog interrupts the current workflow and prevents interaction with content outside the dialog until it is dismissed or a decision is made. A genuinely modal implementation must establish an accessible name, a sensible initial focus target, a contained Tab sequence, a reliable dismissal mechanism (commonly Escape except when a product requirement justifies constraints), and an appropriate focus destination afterward. aria-modal="true" describes modality to assistive technologies; it does not by itself disable background controls or trap focus.

Where suitable, the native <dialog> element opened with showModal() supplies a top-layer modal context, background inertness, and browser focus behavior. The application must still provide a meaningful name, decide where initial focus belongs, supply a close affordance, handle task-specific results, and verify focus restoration. A dangerous confirmation may deliberately focus the least destructive action first. A large text-heavy dialog may be easier to read if initial focus is placed on a static heading with tabindex="-1" rather than on a button deep in the dialog.

<button type="button" id="open-settings">Open settings</button>
<dialog id="settings-dialog" aria-labelledby="settings-title">
  <h2 id="settings-title">Notification settings</h2>
  <p>Choose which updates to receive.</p>
  <form method="dialog">
    <button value="cancel">Close settings</button>
  </form>
</dialog>
<script>
const settingsDialog = document.getElementById('settings-dialog');
document.getElementById('open-settings').addEventListener('click', () => {
  settingsDialog.showModal();
});
</script>

For an application with complex validation or asynchronous confirmation, manage dialog closure explicitly rather than relying on the sample's simple method="dialog" close behavior. Test browser focus restoration when the launching element is removed or the route changes. See the W3C modal dialog pattern and native dialog WCAG technique.

10. Alert Dialogs, Confirmations, and Irreversible Actions

An alert dialog is appropriate for an urgent message requiring a response, not every piece of incidental status text. The APG differentiates it from an ordinary alert, which may notify without taking focus. Overusing alert dialogs for routine acknowledgements creates interruption costs, especially for users operating through sequential navigation or screen reading. Destructive actions should identify the affected resource and consequence, keep the least destructive path easy to reach, and clearly indicate whether cancellation preserves prior data.

A robust “Delete account” flow must separate the request to delete, the confirmation of scope, submission, possible server failure, and final outcome. If the server rejects deletion, do not close the dialog and announce success. If a dialog closes after success, focus normally returns to the invoking control, unless the surrounding interface has fundamentally changed; then choose a stable, meaningful destination such as the next remaining row or a status heading.

Accessibility cannot compensate for an unsafe decision process. The confirmation wording, reversibility, audit records, and authorization checks belong to product governance as well as the component specification. The alert-dialog role communicates urgency; it does not justify bypassing ordinary usability requirements.

11. Tabs: One Content Area, Multiple Related Panels

A tabs widget is a coordinated set of tab controls and corresponding panels. It should expose a tablist, tab roles, aria-selected state, and a relationship between each tab and its panel. Keyboard users generally use the arrow keys to move within the tablist rather than pressing Tab repeatedly through every tab. Tab moves from the active tab to the selected panel's next focusable content, with the tab panel itself focusable when needed for navigation.

Automatic activation updates the panel when a tab receives focus and is most appropriate when the change is effectively instantaneous. Manual activation requires Enter or Space to switch, which avoids costly network requests or focus delays. Switching tabs should not unexpectedly submit a form, route to an unrelated page, or discard unsaved inputs. The visible selected tab and aria-selected must correspond to the displayed panel.

<div role="tablist" aria-label="Report sections">
  <button type="button" role="tab" id="tab-summary"
          aria-controls="panel-summary" aria-selected="true" tabindex="0">Summary</button>
  <button type="button" role="tab" id="tab-details"
          aria-controls="panel-details" aria-selected="false" tabindex="-1">Details</button>
</div>
<section role="tabpanel" id="panel-summary" aria-labelledby="tab-summary" tabindex="0">
  <p>Current reporting period overview.</p>
</section>
<section role="tabpanel" id="panel-details" aria-labelledby="tab-details" tabindex="0" hidden>
  <p>Itemized reporting detail.</p>
</section>

The static snippet is not a functioning tabs widget: production code must implement arrow-key movement, appropriate wrapping, selection and panel toggling, and focus policy. It is intentionally separate from the richer working examples in the APG tabs pattern. See the next section of this article for the interaction differences between tabs and menus.

12. Menu Buttons: Commands in a Temporary Menu

A menu button opens a popup menu of commands or, in some contexts, links. The trigger remains a button; it reports expansion with aria-expanded and may identify the popup using aria-haspopup="menu". Once the menu is open, keyboard operation follows a menu pattern: arrows navigate items, Enter/Space activate appropriate items, Escape dismisses and normally returns to the trigger, and Tab behavior must follow the documented interaction design. A collection of ordinary links is not a menu merely because it appears as a dropdown.

Menu items are specialized roles such as menuitem, menuitemcheckbox, or menuitemradio. A visually disabled command requires a precise decision about whether it remains in arrow navigation and whether activation is suppressed; aria-disabled="true" does not itself block events. The menu should not open simply on pointer hover with no keyboard equivalent, and it should remain usable when a user moves between the trigger and popup at high zoom.

Appropriate examples include “More actions” on a document row, editor commands, or selected-object operations. In a simple site header with expandable category links, a disclosure navigation pattern often better preserves ordinary link behavior, familiar Tab navigation, and reading-mode expectations. The APG itself cautions that a full menubar is not required for most site navigation.

13. Site Navigation Is Not an Application Menubar

A horizontal row of links styled like a desktop application's File/Edit/View commands is often still site navigation, not a menubar. Giving it role="menubar" changes screen-reader expectations and generally introduces arrow-key traversal, specialized focus management, and menu-item semantics. If users expect to Tab through links, a poorly implemented menubar can make navigation slower and less predictable. The same applies to a mobile hamburger button: opening an ordinary list of navigation links need not invoke menu roles.

For a disclosure-based site menu, use a button to reveal a group of links inside a labeled <nav> or appropriate list structure. Keep links as links. Decide whether focus stays on the trigger or moves into the expanded group based on user expectation and the exact pattern, and make Escape behavior predictable where the expansion overlaps or obscures other material. The APG navigation menubar example explicitly discusses why disclosure navigation is often preferable.

Diagnostic test: ask what a user expects after opening the popup. If they want to browse pages or follow a familiar link, retain normal navigation semantics. If they want to execute editor commands with arrow-key movement, a menu pattern may be appropriate. Avoid decisions based solely on animation or icons.

14. Listboxes: Selecting Options from a Composite

A listbox contains options from which the user selects one or more values; it is not a list of actions. Its structure relies on listbox and option roles, an accessible name, and a clear distinction between the focused option and the selected option. The interaction may use roving DOM focus or aria-activedescendant; selection behavior depends on whether focus automatically selects an option or the user commits deliberately. In multiselect listboxes, additional documented conventions apply and should not be invented casually.

Where a native <select> meets the user need, prefer it. Native controls handle considerable cross-platform complexity, including touch input and system pickers. A custom listbox may be warranted for a genuinely rich experience, but each option must have a meaningful accessible name and the component must communicate the current selection. Developers should verify what happens when the option set is filtered, an item disappears, or a selected value is no longer valid.

A common defect is implementing visual highlight with CSS while leaving aria-selected unchanged, causing one option to appear chosen and another to be announced as chosen. Another is misusing aria-selected to mean merely hovered. A third is embedding an uncoordinated array of buttons or links inside each option, producing a control whose keyboard model cannot be explained consistently.

15. Comboboxes: Text Entry and Popup Coordination

A combobox is an input-oriented composite that can expose a popup listbox, tree, grid, or dialog. It may accept editable text, select from choices, or offer suggestions. The word “autocomplete” describes a user-visible behavior but does not fully determine the required ARIA pattern. The team must define whether the current text is the value, whether an option is merely suggested or committed, how Escape behaves, whether free-text values are permitted, and whether suggestions are fetched asynchronously.

The editable combobox usually keeps DOM focus on the input while arrow keys navigate suggestions, potentially indicated through aria-activedescendant pointing at the active option. aria-expanded describes popup visibility; aria-controls associates input and popup; aria-autocomplete may describe the applicable form of completion. The active option must exist and be owned in an appropriate relationship when referenced, even under virtualized rendering. Simply adding role="combobox" to a text field with an adjacent unordered list is not sufficient.

Performance is an accessibility feature. If every arrow press waits for a slow network response before the user can inspect an option, the interface becomes difficult to operate. Supply a stable selection model, handle empty and error results, preserve typed text during dismissal, and report loading or result-count changes without flooding live regions. See the APG combobox pattern.

16. Autocomplete, Search Suggestions, and Result Status

Autocomplete requires a decision about ownership of the suggestion list. A search field may show query completions, suggested documents, recent searches, or combinations. Those are different conceptual objects, even if they appear in the same popup. A list of links to documents might be easier to operate as a named results region with ordinary links than as an elaborate combobox; the correct choice depends on whether moving through options changes the input value or triggers immediate navigation.

For server-backed suggestions, debounce without imposing arbitrary keyboard latency, guard against stale responses arriving out of order, and communicate an actionable empty result. If a suggestion is chosen, distinguish the provisional suggestion, committed text, and any actual navigation. Do not announce every character as a new live-region message. A restrained role="status" such as “Five suggestions available” may be useful when the results arrive, but focus and option semantics should carry detailed navigation information.

Measure success with representative queries, including spelling variations, internationalized input, voice dictation, and results that wrap across narrow viewports. The accessible implementation must be resilient when no suggestion is selected: a user who types valid free text should not be forced to choose a synthetic option unless the task truly requires it.

17. Radio Groups, Checkboxes, and Switches

Radio buttons, checkboxes, and switches express choice state, not a generic pressed action. Use native <input type="radio"> and <input type="checkbox"> when possible, grouping related controls with <fieldset> and <legend>. A switch is semantically an on/off setting, for which a styled native checkbox is frequently an effective implementation. If the custom switch role is used, the team must supply correct keyboard activation, state, labeling, and the expected focus behavior.

<fieldset>
  <legend>Preferred notification channel</legend>
  <label><input type="radio" name="channel" value="email"> Email</label>
  <label><input type="radio" name="channel" value="sms"> Text message</label>
</fieldset>
<label>
  <input type="checkbox" name="reminders"> Enable appointment reminders
</label>

Avoid visually substituting a single toggle for a three-way choice or using aria-pressed where a true checked state is intended. Disabled and read-only semantics also need care; “gray” is a visual style, not an interoperable disabled state. If a setting is temporarily unavailable, explain why, preserve the user's previous choice when possible, and provide an alternative route.

18. Range Controls, Sliders, and Spinbuttons

A slider represents a numeric value within a defined range, often with arrow-key increments, Home/End bounds, and optional Page Up/Page Down increments. Native <input type="range"> supplies a strong starting point. A spinbutton provides numeric entry with increment/decrement interactions; a labeled <input type="number"> may be preferable for many forms. The user needs a meaningful name, bounds, current value, and understandable units. A slider that only says “50” without “50 percent volume” may technically expose a number but fail the task.

<label for="volume">Volume: <output id="volume-value">50%</output></label>
<input id="volume" type="range" min="0" max="100" value="50">
<script>
const volume = document.getElementById('volume');
const volumeValue = document.getElementById('volume-value');
volume.addEventListener('input', () => {
  volumeValue.textContent = `${volume.value}%`;
});
</script>

The exact meaning of arrow-key direction may vary with orientation and language direction; follow platform conventions and test rather than hardcode unexamined assumptions. Do not require minute pointer movements to adjust a value if a text entry or native stepper can accomplish the task. For financial or safety-sensitive quantities, provide an explicit textual value and consider a reversible entry route.

19. Treeviews: Hierarchical Navigation Within a Widget

A treeview presents expandable and selectable hierarchical items, often in a file browser, category selector, or application outline. It is not simply a nested list. A true tree widget requires conventions for Up/Down movement, Right/Left expansion and collapse in the appropriate writing direction, Home/End movement, selection behavior, and announcements of level and expanded state. The user must be able to distinguish a parent that can expand from a leaf item and know whether a focused item is also selected.

For a small nested set of informational links, plain lists with disclosure buttons are often more comprehensible than a full tree. A treeview is justified when users need to operate a single composite hierarchy with keyboard movement comparable to a file explorer. Selecting a tree node should not be confused with expanding it: some users need to inspect siblings without causing navigation or losing context.

Virtualized trees are especially fragile when focused nodes vanish from the DOM. Ensure the active item remains represented or focus is moved to a stable visible ancestor, and update level, position, and set-size information when the structure changes. Test a deep hierarchy, a collapsed branch with previously selected descendants, and a deleted item.

20. Grids and Treegrids: Interactive Tables with Editing Contracts

An HTML <table> supports reading tabular information. Assigning role="grid" means something more: users may navigate cells as a coordinated application widget, activate embedded controls, edit values, or select rows. The grid pattern often creates one Tab stop for the overall widget and uses arrow keys internally. That design can make a dense data editor efficient, but it also changes how screen readers navigate the content. A static report should not become a grid merely because it has many columns.

An interactive grid needs a deliberate cell-navigation mode, an editing mode, row/column labeling, a stable account of selected cells, and error recovery. Define what Enter, F2, Escape, Tab, and arrows do in each mode. If a cell contains a textbox, arrows may edit text rather than move between cells; the interface must provide a predictable way to enter and exit editing. A treegrid combines hierarchy with interactive rows and adds another layer of expansion and row semantics.

For very large datasets, distinguish hidden rows due to filtering from rows absent because of virtualization. A screen reader should not be told the view has ten rows when the logical result has ten thousand unless that limitation is clearly communicated. Examine APG grid and APG treegrid guidance before choosing this architecture.

21. Toolbars: Grouped Application Commands

A toolbar collects controls that serve an identifiable activity: for example, editing text, adjusting a chart, or reviewing an image. Its toolbar role and accessible label can help a user identify the group. For a sufficiently complex toolbar, a roving focus strategy can reduce dozens of sequential Tab stops to a single entry point and use arrow keys to move among controls. The APG toolbar guidance discusses groups of three or more controls and the interactions of buttons, toggle buttons, menus, and inputs within one container.

Toolbar composition presents a genuine design tension. Arrow keys may move between controls, but sliders, spinbuttons, and text inputs can themselves use arrow keys for value editing. A well-designed toolbar specifies when navigation changes focus and when a focused control consumes keys. A generic keydown handler on the parent that steals all arrow presses can make child controls unusable. Order commands in a way that remains logical when a user reaches the toolbar through the accessibility tree or by touch.

For simple groups of two buttons, ordinary buttons inside a labeled region may be enough. A toolbar should not be used only as a decorative border. When command availability changes, the user must be able to discover the state and understand what action, prerequisite, or selection would enable the command.

22. Tooltips, Help Text, and Popovers

A tooltip supplies brief supplemental information in response to focus or hover; it should not be the only way to discover essential instructions or a required form label. In an ARIA tooltip relationship, the trigger can reference the tooltip using aria-describedby. Tooltips should be dismissible where applicable, persist sufficiently for people to read and move the pointer, and not cover critical controls. A tooltip is not an interactive dialog. If users need to click a link, check an option, or enter text inside the popup, choose a different pattern.

<label for="account-id">Account identifier</label>
<input id="account-id" aria-describedby="account-id-help">
<p id="account-id-help">Enter the reference shown on your account statement.</p>

This persistent help text may be more usable than a hover-only tooltip: it works under magnification and touch input and can be discovered without guessing a hidden target. A help popover may be appropriate for longer explanations, but it must have a triggering control, an accessible name or description as appropriate, an explicit close path, and defined focus behavior. Browser support for new platform popover APIs should be tested rather than presumed to eliminate all accessibility obligations.

Remember the distinction between a tooltip (noninteractive explanation), a disclosure (content shown under user control), a menu (commands), and a dialog (a contained task). The CSS appearance of a floating panel does not decide its semantics.

23. Carousels, Rotators, and Automatic Movement

A carousel displays a sequence of slides or cards and may advance automatically. Its accessibility depends on more than whether next and previous buttons have names. The user must know which slide is current, whether motion is automatic, how to pause or stop it, what happens to focus when slides change, and whether hidden slide content remains unexpectedly exposed to assistive technologies. Automatic changes can disrupt reading and magnification, so products should have a defensible reason to animate content and a clear user override.

Use real buttons for next, previous, and pause controls. Provide an identifiable name for the carousel and individual slide position or label. Do not send every automatic slide change as an assertive announcement; it can interrupt reading. When a user deliberately requests a slide, concise feedback is more reasonable. Avoid placing keyboard focus into an offscreen slide or letting controls disappear while focused.

A carousel should also be assessed as a content decision. If users need to compare three application options, a static list may be easier to understand and more robust than a carousel. An accessible widget is not proof that the presentation format serves its purpose. The APG carousel pattern provides optional design approaches, but no specific interaction format should be copied uncritically.

24. Drag and Drop: Alternative Ways to Reorder or Move

Drag-and-drop interfaces are frequently inaccessible to people who cannot sustain a pointer gesture or who use keyboard and speech input. WCAG 2.2 Success Criterion 2.5.7, Dragging Movements, requires a single-pointer alternative for covered drag operations unless an applicable exception applies. This is not the same obligation as keyboard accessibility; a product must assess both separately. A keyboard-accessible drag workflow does not by itself establish that a single-pointer alternative exists.

For a sortable list, provide Move up and Move down buttons, a destination selector, or cut/paste-like controls. A user should be told the result of a move and be able to reverse it or correct an error. On a kanban board, options might include “Move to Review” or “Move before Card 4,” allowing a single tap without dragging. Avoid announcing every intermediate pixel position; announce the logical source, destination, and final order.

<li>
  <span>Review contract</span>
  <button type="button">Move up</button>
  <button type="button">Move down</button>
</li>

These controls are a structural illustration: they still require logic that updates the ordered data model, disables or handles boundary moves, announces meaningful results, and persists the order. A text field containing the item's numeric rank can be an additional route where precise reordering matters. Review WCAG 2.2 Dragging Movements when defining acceptance criteria.

25. Popup Layering, Portals, and Nested Overlays

Modern frameworks frequently render popups in a portal detached from their trigger's DOM subtree. That does not necessarily break accessibility, but it can complicate event handling, reading order, inertness, focus return, and relationship references. A popup that visually appears inside a form may be elsewhere in the DOM; an aria-controls association may identify it, but it does not automatically ensure the correct reading or focus behavior. Teams should inspect the actual accessibility tree rather than infer it from component file structure.

Nested overlays amplify risk. A combobox inside a modal dialog may open a popup that overlays the dialog; a help popover may open from inside a grid editor; a destructive confirmation may sit on top of another modal. Define the active interaction layer, dismiss order, stacking behavior, and focus destination for every layer. Escape should not unpredictably close the entire application when the user's intent is to dismiss only the innermost popup.

A useful invariant is: only the active modal layer should be operable and perceivable as interactive, while nonmodal layers must not block unrelated page tasks without clear justification. Avoid indiscriminate aria-hidden manipulation on ancestors that contain the focused node. Prefer platform modalities and carefully scoped event ownership.

26. Pointer, Touch, Keyboard, Speech, and Switch Input

A component must be evaluated across input methods, not just a desktop keyboard and mouse. Touch users need targets they can acquire without precise aiming; speech-input users benefit when visible control labels are present in accessible names; switch users need predictable focus sequences; keyboard users need activation without pointer positioning; and magnification users need controls that remain visible and reachable in narrow views. Gesture-only actions need alternatives, and hover-only interfaces need a non-hover route.

Input method Likely failure Better implementation principle
Keyboard Arrow or Tab commands conflict with widget behavior Follow a documented, predictable key model
Screen reader Custom visual choice has no selection state Expose role, name, focused option and committed value
Speech recognition Visible label absent from accessible name Include visible command words in the name
Touch Tiny control is next to a destructive command Adequate target size/spacing; confirm risky actions
Switch access Focus repeatedly enters dozens of child controls Logical grouping and efficient navigation
Screen magnification Popup opens beyond zoomed viewport Position and scroll to keep active target visible

WCAG 2.2 adds a Target Size (Minimum) criterion at Level AA with specific sizing, spacing, and exceptions; do not simplistically claim that every target must meet a single universal pixel dimension. Test actual interactions at zoom and with touch or simulated coarse-pointer conditions, especially for densely packed command bars.

27. Focus Management in Composite Widgets

Composite widgets solve a navigation problem by coordinating a set of controls under one predictable keyboard model. Two common approaches are roving tabindex, in which one child has tabindex="0" and others -1, and aria-activedescendant, in which DOM focus remains on a container or input while an attribute points to the visually active child. Both can be valid in appropriate patterns; they are not interchangeable copy-paste recipes.

With roving tabindex, key handling usually updates which item is tabbable and moves actual DOM focus. With aria-activedescendant, key handling updates the active descendant without moving DOM focus, and must manage the visual active state, accessibility relationship, and any scrolling explicitly. A screen reader may use different modes and announcements depending on the role and platform. The choice affects pointer interaction and the state of a component when its options change.

// Illustrative roving-tabindex idea for a known collection of buttons.
function focusChoice(items, nextIndex) {
  items.forEach((item, index) => {
    item.tabIndex = index === nextIndex ? 0 : -1;
  });
  items[nextIndex].focus();
}

This is a helper function, not a complete widget. A real implementation needs event handling, boundaries, direction conventions, disabled-item policy, and selected-state updates as appropriate. Do not implement roving focus on all page navigation links merely because it reduces Tab stops; it is useful in specific composite patterns with established keyboard expectations.

28. Disabled Items, Loading, and Asynchronous State

An unavailable command can be hidden, removed, natively disabled, or exposed with aria-disabled, depending on whether the user needs to discover it and whether its absence would cause confusion. Native disabled commonly removes a control from normal sequential focus; aria-disabled="true" communicates a state but does not prevent clicks or keyboard actions. If a disabled option remains focusable to explain why it is unavailable, the event handlers must refuse the action and provide an understandable reason.

Loading states require more than a spinner. Users should know whether the component is busy, whether input is accepted, and what happens when a request completes or fails. A listbox can temporarily announce a loading state without discarding the selection; a Save button can communicate pending work while avoiding accidental double submission; an infinite-scroll grid must update its logical position information without relocating focus. aria-busy and status regions can assist, but their effectiveness depends on placement and controlled announcement behavior.

If the user presses Escape while an asynchronous request is pending, define whether the request is canceled, the popup closes but the request may continue, or the result is ignored when it arrives. State races—such as an old query result replacing a newer set of options—are accessibility failures because they can change a target under the user's cursor or focus.

29. Virtualization, Hydration, and Dynamic Reconciliation

Performance techniques such as virtual scrolling and server-to-client hydration can break otherwise sound ARIA relationships. An aria-activedescendant reference may point to an option that has been unmounted. A visual row may preserve its text while its underlying DOM node is replaced, causing keyboard focus to disappear. A newly hydrated component may temporarily disagree with the server-rendered selected state or produce duplicate identifiers. These failures are often intermittent and therefore missed by quick visual inspection.

Set specific invariants: stable IDs for controlled relationships, no duplicate IDs after route changes, an accessible active descendant that exists while referenced, deterministic focus preservation during updates, and a coherent fallback when data disappears. When a focused result is removed, choose the next meaningful result or the surrounding search field and communicate the update. Avoid silently returning to the top of the page.

For large lists, include realistic tests that load more results, filter out the selected item, change sorting, and navigate back in browser history. Accessibility must survive data lifecycle events, not just the first render. More detail on accessible navigation and orientation is developed in Accessible Navigation and Information Architecture.

30. Internationalization and Writing-Direction Behavior

Component keyboard conventions are influenced by language and writing direction. Left and Right arrows can have different intuitive meanings in right-to-left layouts; menu placement, tree expansion, and carousel movement may need adjustments. Do not assume that simply setting dir="rtl" correctly rewrites every hardcoded key mapping and animation. At the same time, avoid changing platform conventions without evidence: the appropriate behavior depends on the widget, reading direction, and user expectations.

Text enlargement and translation can turn a compact tablist into multiple rows, truncate labels, or alter the relationship between a menu trigger and popup. Accessibility evaluation should cover long translated labels, mixed-direction input, accessible names that match visible translated text, and text that wraps when zoomed. A hidden icon-only control should not rely on a culturally specific symbol if the action is obscure.

A localized component contract needs an explicit test matrix for labels, number and date formats, direction of arrow-key movement, current-value speech, focus indicators, and error messages. This is an example of why design systems require internationalization as a first-order requirement, not an afterthought applied after the component code is frozen.

31. The Most Common ARIA Component Failure Modes

Recurring component defects follow a limited set of root causes: semantics added without corresponding behavior, multiple sources of state truth, incorrect pattern selection, inaccessible dismissal, loss of focus under dynamic updates, and inadequate testing outside the primary browser. They can be spotted by asking a small number of practical questions during code review.

Failure Root cause Remediation principle
role="button" on a nonfocusable element Assuming role provides behavior Use a native button
Tab moves through every tab in a tablist Missing composite key model Implement arrow movement and active Tab stop
Modal permits background Tab navigation Mistaking aria-modal for enforcement Use native modal behavior or implement containment
Listbox reads the wrong selected value Visual and semantic states diverge Derive both from one selection model
Menu closes when moving pointer to it Hover-only or brittle event ownership Stable trigger/popup lifecycle and keyboard support
Combobox announces stale suggestions Async race or stale ID references Cancel/ignore stale requests; stable active option
Grid arrow keys steal text editing No edit/navigation mode specification Separate modes and commands
Tooltip contains indispensable instructions Hidden help used as primary content Persistent instructions or accessible help control
Moving carousel steals focus Animation state treated as navigation Keep focus stable; provide motion controls
Dialog closes with no focus destination Removed invoker and missing return plan Restore to meaningful surviving context

A defect should be recorded against its violated contract, not only as “screen reader issue.” This helps engineering teams repair the underlying component for all users.

32. A Repeatable Component Evaluation Workflow

First establish the component's intended task and chosen pattern. Then check semantics by inspecting the accessibility tree, behavior by using only the keyboard, visual feedback by zooming and adjusting contrast, and lifecycle by forcing exceptions. Test opening and closing, cancellation, timeout, delayed data, empty data, invalid input, and repeated invocation. Include assistive technology combinations that are actually relevant to the deployment, rather than claiming universal compatibility after one screen reader.

A practical evaluation sequence is: (1) identify the expected pattern; (2) verify native alternatives; (3) inspect names/roles/states; (4) check focus entry; (5) exercise every documented key; (6) test pointer and touch; (7) verify announcements and visual cues; (8) force empty, loading, error, and disabled states; (9) test zoom, reflow, and text enlargement; (10) verify teardown and focus return; (11) compare with applicable WCAG criteria; (12) record limitations, reproduction steps, and evidence.

Automated tools can find missing accessible names or structural errors, but they cannot establish whether a menu's command model makes sense or whether a dialog returns users to a meaningful place. Likewise, passing a component demo does not prove an integrated application has preserved its behavior. Validate the real content and business workflow.

33. Pattern-Oriented Acceptance Criteria

Accessibility requirements become actionable when expressed as observable outcomes with explicit test conditions. Do not write only “supports WCAG 2.2 AA.” An acceptance rule for tabs might say: “With focus on an active tab, Right Arrow moves focus to the next tab; manual activation does not change the visible panel until Enter/Space; selected status and visible panel always agree.” A rule for a dialog might say: “Opening the dialog moves focus inside; background controls cannot be reached; closing restores focus to the invoking control unless it no longer exists, in which case focus moves to the corresponding stable context.”

Component Key acceptance criterion Negative or recovery test
Disclosure Enter/Space toggles visibility and aria-expanded Repeated rapid toggles do not desynchronize state
Tabs Arrows traverse tabs; selection and panel agree Slow-loading panel does not steal focus
Menu button Trigger opens; arrows move among commands; Escape dismisses A disabled command does not execute
Dialog Background is inoperable while modal; focus return defined Invoking row deleted before close
Combobox Typing, active option, and commitment are distinct Stale network response cannot replace a later query
Grid Navigation mode and editing mode have predictable keys Focus survives row sorting or record removal
Carousel User can pause automatic motion and find slide controls Slide change does not move focus unexpectedly
Reorder control Single-pointer and keyboard alternatives work Boundary move produces a clear result

Acceptance criteria should name test environments and evidence: recorded keyboard sequence, accessibility-tree screenshot, observed screen-reader output, or issue reproduction video where appropriate. They should also identify owners for unresolved browser/assistive-technology interoperability limitations.

34. Eight Worked Cases: From Widget Defect to Repair

The following scenarios are constructed instructional examples, not claims about actual incidents at MGU or named companies. Each applies the governing rule: determine the task, select the smallest sufficient pattern, verify operational behavior, and test lifecycle states.

Case 1 — A purchase-details accordion reports the wrong state. A product page uses a chevron that rotates when clicked, but aria-expanded stays false. A screen-reader user hears that the section is collapsed even while the content appears. Repair the state model so DOM visibility, icon, and aria-expanded derive from one boolean; test rapid toggling and collapsed content removal from the navigation sequence. The issue is state synchronization, not a missing landmark.

Case 2 — A settings dialog loses focus on Save. The user opens a dialog from a settings card, changes values, and presses Save. The card rerenders and removes the invoking button. When the dialog closes, focus falls to the document body. Define a stable return location such as the updated card heading or surviving edit button; manage success and error outcomes separately. The issue is dialog lifecycle and asynchronous state, not merely Escape handling.

Case 3 — Tabs load remote content on arrow focus. An analytics panel has five tabs. Each Right Arrow press fires a network request and freezes selection for two seconds. Switch to manual activation so arrows move among tabs without switching panels until the user presses Enter or Space. Ensure only the chosen result is displayed and older requests cannot overwrite it. The issue is activation policy and latency.

Case 4 — A site navigation dropdown uses role="menu" without arrows. A top-level “Departments” button opens a vertical list of page links, but the user cannot use Up/Down arrows and expects ordinary Tab navigation. Rather than recreating an application menubar, use a labeled navigation region with a disclosure button and ordinary links. The issue is pattern misclassification.

Case 5 — Search suggestions disappear while being explored. A user types a place name, presses Down Arrow to inspect options, and a delayed query response replaces the list. The aria-activedescendant now points to a removed option. Assign stable option IDs, ignore obsolete requests, maintain active-item visibility, and deliberately restore a valid focus target when results change. The issue is asynchronous composite integrity.

Case 6 — An editable grid captures arrow keys inside a text field. A budget grid uses a parent handler that moves between cells whenever an arrow is pressed, even when users are editing a number. Separate navigation and editing modes; when the text field has focus, let editing keys behave normally. Provide an explicit exit operation and test Undo or cancellation. The issue is conflicting keyboard contracts.

Case 7 — A carousel advertises an offer that changes before it can be read. A promotional carousel auto-advances every few seconds, has no pause control, and announces each slide at high priority. Add a persistent motion-control mechanism, reduce unsolicited announcements, keep focus stable, and consider a static list for important comparison content. The issue is time control and meaningful content access, not merely slide labeling.

Case 8 — A project board requires dragging cards. A team member using switch input cannot drag a card into a new column. Add an “Actions” menu or ordinary button to choose a destination and optional relative order; enable movement with a single pointer as well as keyboard input. Announce the final location and provide reversal. The issue is equivalent task operation, including the WCAG 2.2 dragging requirement, not only ARIA semantics.

35. Selecting and Governing Components in a Design System

An organization's design system should maintain a pattern inventory for each reusable component: intended use, known nonuses, HTML structure, role/state mapping, keyboard matrix, visual states, focus and dismissal policy, touch/speech behavior, responsive rules, test environments, and known limitations. Every new feature team should be able to find this record without reverse-engineering a demo. If an existing component cannot pass the contract, mark it restricted rather than silently permitting new deployments.

Pattern variants deserve separate documentation: an auto-activating tabset differs meaningfully from a manual tabset; a modal differs from a nonmodal dialog; a select-only combobox differs from an editable combobox; a single-select listbox differs from a multiselect one. Do not put incompatible variants behind a single undocumented prop that changes keyboard behavior at runtime.

Engineering ownership covers event handlers and state synchronization; design ownership covers discoverability, layout, and visible state; content ownership covers clear labels and messages; accessibility specialists validate standards application and user scenarios; quality teams preserve regression evidence. No single automated lint rule can own the entire accessibility outcome.

36. A Ten-Step Component-Selection and Implementation Framework

  1. Identify the user's task. Is this a command, selection, text entry, navigation, comparison, or temporary decision?
  2. Choose a native baseline. Compare buttons, links, input controls, details, and dialog with the proposed custom component.
  3. Name the intended pattern. Use one APG pattern only when it truly describes the desired behavior; document justified deviations.
  4. Specify states and transitions. Include open/closed, selected/unselected, disabled, pending, error, success, and cancellation.
  5. Define keyboard entry, movement, and exit. Record Tab, Shift+Tab, arrows, Enter, Space, Escape, and other applicable keys.
  6. Define focus policy. State initial focus, active descendant or roving focus, scroll behavior, and restoration after removal.
  7. Expose the semantic model. Ensure correct accessible name, role, state, value, and relationships, with native HTML where practical.
  8. Support additional input and presentation conditions. Test pointer, touch, speech input, zoom, text growth, reflow, and motion preferences.
  9. Test unusual lifecycle paths. Include empty results, delayed response, repeated activation, localization, deletion, and interrupted workflow.
  10. Ship with evidence and ownership. Record test results, limitations, monitoring triggers, and the team responsible for maintenance.

The framework deliberately starts with product purpose and ends with operational accountability. It prevents a component team from claiming accessibility because a role string is present while the real task remains impossible.

38. Study Questions and Applied Exercises

Conceptual questions. (1) Why is a styled dropdown not automatically a menu? (2) Which problems does native HTML solve before ARIA is added? (3) What is the difference between a focused tab and the selected tab in a manual-activation tabset? (4) Why can aria-modal="true" be inaccurate even when a popup looks modal? (5) What condition must hold when aria-activedescendant references an option? (6) Why does role="grid" create responsibilities that do not apply to an ordinary table? (7) What are the separate requirements for keyboard access and single-pointer alternatives to dragging? (8) How can a design system prevent regression when a component is reused?

Exercise A — Pattern triage. Take five existing product controls and write the task they serve, native alternative, intended APG pattern if any, expected Tab/arrow/Enter/Escape behavior, and expected focus position after closing. For every use of role="menu", defend why ordinary links or a disclosure are insufficient.

Exercise B — Dialog lifecycle. Implement a native <dialog> with a heading, Save and Cancel controls, a simulated network error, and a launching control that may disappear after success. Document focus entry and return for every result. Test only with a keyboard, then inspect the accessibility tree and repeat with one screen reader.

Exercise C — Composite state test. Construct a small manual-activation tabset with two panels. Write an acceptance matrix for all arrow, Enter, Space, Tab, Shift+Tab, and Escape behaviors that apply. Then deliberately introduce a mismatch between aria-selected and visible panel and explain how to detect it.

Exercise D — Reordering without dragging. Design an accessible three-column board with buttons or menus that move an item. Show how a user completes the same move with keyboard, speech input, and a single pointer without dragging. Capture the announcement after the move and the reversal path.

Exercise E — Async failure injection. Simulate a combobox search that responds to the first request after the second. Explain how to reject the stale response, keep the active option valid, preserve the typed string, and announce the final number of suggestions without repetitive chatter.

For grading, evaluate whether the student states observable behavior and evidence, not just whether they include role names in markup. A credible answer names failure paths, not merely ideal transitions.
