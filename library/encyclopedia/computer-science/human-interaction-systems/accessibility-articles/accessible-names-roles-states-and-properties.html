1. Definition, Scope, and Governing Question

An interface is accessible only when its important objects can be identified, distinguished, and understood by people who do not experience the visual or pointer-based presentation in the intended way. Accessible names tell users what an object is called; roles say what kind of object it is; states and properties expose its present condition and relationships; and accessible descriptions provide supplementary information. These signals are conveyed by browser or platform accessibility APIs to screen readers, speech-control tools, switch interfaces, and other assistive technologies. A name such as “Save draft,” the role button, and a disabled or busy state form a much more useful representation than an unnamed clickable rectangle.

The governing question for this specialist article is how an interface reliably conveys what a control is, what it is called, what it does, and what has changed. The answer combines native HTML, an accessible-name computation, appropriate WAI-ARIA (Accessible Rich Internet Applications) metadata, interaction logic, and testing. ARIA is a vocabulary for semantics, not a substitute for events, rendering, layout, or keyboard support. An object can be exposed as a button and yet fail to activate on Space; a control can have an intelligible name but remain outside the keyboard sequence; and a live region can report a change that never reaches the visual user. Each is a separate failure.

The parent article, Semantic HTML and the Accessibility Tree, owns structural HTML and the browser's translation of that structure into an accessibility tree. This article narrows the subject to the object's identity and communicated condition: accessible names, descriptions, roles, state attributes, relational properties, live announcements, and defects in that communication. Keyboard Access and Focus Management will own actual focus motion, keyboard commands, and focus restoration; Accessible Interactive Components and ARIA Patterns will own full widget behavior. These boundaries allow technical depth without duplicating a neighboring specialist article.

Working definition. A successful semantic contract gives an assistive-technology user enough accurate, current, programmatically available information to decide whether to inspect, operate, or ignore the element, and to understand the result of an operation. That is a stronger test than asking whether an aria-* attribute appears in source code.

2. Four Parts of the Accessible Object Contract

Most practical inspections begin with four questions. Name: is there a concise, recognizable label, preferably aligned with what is visible? Role: does the platform expose the element as the correct kind of object, such as button, checkbox, heading, dialog, or navigation region? State or value: can the user discover whether the object is expanded, checked, pressed, selected, required, invalid, busy, disabled, or currently set to some value? Description or relationship: is essential additional information, such as a format hint or error message, attached to the correct control?

The four parts interact. “Delivery options” might be the name of a section heading, an expandable button, or a radiogroup; their roles imply different behaviors. “Selected” makes sense for a tab or option in a selection set, whereas “pressed” generally describes a toggle button and “checked” identifies a checkbox or switch. A description such as “Use eight or more characters” adds useful instructions to a “Password” textbox without replacing its short name. A user who hears only “Button, collapsed” cannot know what will expand; a user who hears “Delivery options, button” cannot tell whether the panel is already open.

Semantic field Core question Typical exposed information Frequent defect
Name What is this object called? “Shipping address” Empty, vague, or mismatched label
Role What kind of object is this? Checkbox, button, tab, dialog Noninteractive role on a control
State or value What is its condition now? Checked, expanded, 40 percent Stale or contradictory state
Description What additional detail matters? “Required; use MM/DD/YYYY” Instruction separated from control
Relationship What is associated with what? Control labels panel; error describes field Broken ID reference or incorrect owner

A screen reader may announce these fields in a different order and may omit or add information according to user settings, verbosity, browser, and platform. The developer's obligation is to expose the right semantics, not to script one assumed spoken sentence. Automated accessibility-tree inspection shows what a browser publishes; actual assistive-technology use establishes whether those signals lead to a usable task.

3. Native Semantics Before Author-Defined ARIA

HTML elements already express many roles and states. <button> normally exposes a button role, responds to keyboard activation, participates in focus navigation, and represents disabled status when its disabled attribute is set. <input type="checkbox"> exposes checkbox semantics and a native checked state; <label> can give it a visible, clickable name. <select> communicates the nature of a selection control without a custom listbox implementation. This built-in behavior is not merely convenient: it reduces the number of independent properties an application team can get out of sync.

ARIA augments native behavior where a real semantic capability is absent. A button that controls a collapsible panel can use aria-expanded to communicate openness. A toggle button can use aria-pressed; HTML has no native pressed-state attribute for a push button. A dialog can use a name relationship. These are additive uses. Overriding a native button with role="heading", or declaring a div to be a button but providing no keyboard activation, creates a false model of the interface.

<!-- Prefer native naming and control behavior. -->
<label for="notifications">Send notifications</label>
<input id="notifications" type="checkbox" checked>

<!-- Add a state that HTML buttons do not express by themselves. -->
<button type="button" aria-expanded="false" aria-controls="details-panel">
  Account details
</button>
<div id="details-panel" hidden>...</div>

The second example is only the initial state of a working disclosure. Application code must toggle both the panel's actual visibility and the button's aria-expanded value. If one changes without the other, screen-reader users receive contradictory information. Because native attributes sometimes take precedence over conflicting ARIA declarations, authors must not deliberately maintain two competing sources of truth; the 2026 ARIA in HTML Recommendation documents permitted combinations and restrictions.

Design rule: use HTML to create the object; add ARIA only for semantics that HTML does not sufficiently expose; keep every attribute aligned with what the component actually does.

4. What Makes an Accessible Name Recognizable?

An accessible name is the short textual identity of an interface object. It is not necessarily visible text in the object's descendant nodes. A text-labeled button normally receives its name from its content; a form input may receive its name from an associated <label>; an image may receive a text alternative; and some elements may be named by reference to other nodes. What matters is that the browser computes an appropriate name under the element's role and the applicable algorithm.

Good names are specific, stable, and task-oriented. “Download annual report (PDF)” is more useful than “Download”; “Remove invoice 1042” is better than “Delete” among several repeated controls. Stability does not mean never changing a name: a “Mute audio” button can legitimately become “Unmute audio” after activation if it represents an action rather than a fixed toggle. The change should match the user's mental model and the component's state pattern. A button already labeled “Mute” and also marked aria-pressed="true" should not arbitrarily become “Unmute” while retaining the same toggle semantics; the label/state contract must be designed consistently.

A label is not sufficient simply because it exists. A button named “Click here” is programmatically named but context-poor. A “Search” button on a page containing three independent search areas may need a more specific name or a clear group/region context. A label that says “Billing postal code” while the adjacent visible text says “ZIP code” may impair speech-input discovery, especially when the visible phrase is not included within the accessible name.

Visual control Weak name Better name Reason
Icon-only close control “X” “Close filters” Indicates action and target
Download icon in repeated rows “Download” “Download February invoice” Distinguishes parallel actions
Search field in a navigation header “Input” “Search site” Identifies purpose
Password field “Minimum eight characters” “Password” plus a description Separates identity from instructions
Favorite toggle “Star icon” “Add to favorites” or named “Favorite” with pressed state Describes intended function

The accessible name should be concise enough to scan repeatedly. Put detailed caveats, validation rules, and examples in a separate accessible description, ideally also visible. Long names make navigation inefficient and can obscure the distinguishing words that matter most.

5. Accessible Name Computation: A Practical Mental Model

Browsers determine accessible names using the Accessible Name and Description Computation algorithm, together with HTML-specific mappings and the element's role. The following is a useful inspection heuristic, not a complete normative precedence algorithm: check first whether aria-labelledby references valid content; then whether an allowed aria-label supplies text; then whether applicable host-language labeling features such as <label>, alt, or legend contribute; then whether the role supports naming from contained text; finally inspect lower-priority fallback mechanisms. The actual algorithm has role-dependent and traversal-dependent rules, including important exceptions for hidden and referenced descendants.

The distinction between name from author, name from content, and naming prohibited is fundamental. An icon button can appropriately receive a name from author-supplied ARIA text. A standard button usually derives its name from its visible content without extra metadata. Conversely, the ARIA specification prohibits author naming on certain purely structural or generic roles; putting aria-label on arbitrary paragraphs or list items does not turn them into reliably named navigable objects. When in doubt, consult the role's Accessible Name characteristics and the ARIA-in-HTML restrictions.

An important implication is that aria-labelledby can override the name a user might expect from visible content. The mere presence of several naming methods does not guarantee a combined result: higher-precedence author naming can replace lower-precedence content. This is a frequent source of surprises in component libraries, particularly when an outer component injects a default aria-label over developer-provided button text.

The 1.2 Accessible Name and Description Computation is a Working Draft at the time of this article (November 2026), rather than a finalized Recommendation; the already established WAI-ARIA 1.2 Recommendation and HTML mapping standards remain important authority. Version labels matter when investigating nuanced edge cases. A current browser accessibility tree is evidence of its implementation, not proof that every implementation interprets a developing specification identically.

6. Visible Labels and Native Association

The most robust way to name a conventional form control is usually a visible label associated through HTML. An explicit <label for="..."> references a labelable control's unique ID; a control can also be wrapped within its label in appropriate circumstances. This relationship helps assistive-technology users recognize the input, enlarges the pointer target, and connects the visible words to the editable field. Merely placing a text node beside an input, or using a placeholder as its only label, does not create an equivalent robust association.

<label for="shipping-email">Email address</label>
<input id="shipping-email" name="email" type="email" autocomplete="email">

<!-- A placeholder is an example, not a substitute for a label. -->
<label for="reference-code">Reference code</label>
<input id="reference-code" name="reference" placeholder="For example, AB-1234">

The component should also communicate group context through the right structure. A set of native radio buttons that asks users to select a delivery method is better modeled using <fieldset> and <legend> than by duplicating the whole question in each option's label. The group legend can provide shared context while each option receives a concise name. Complex author-named custom groups require additional semantic care and should not be introduced solely for styling.

<fieldset>
  <legend>Preferred delivery method</legend>
  <label><input type="radio" name="delivery" value="email"> Email</label>
  <label><input type="radio" name="delivery" value="post"> Postal mail</label>
</fieldset>

A visible label must remain available as users zoom, reflow content, change themes, and correct errors. A design system that hides labels visually for aesthetic reasons may degrade voice control, cognitive clarity, and usability even if an aria-label keeps the name technically nonempty. The preferred sequence is to preserve visible words, pair them with native control semantics, and add supplemental information only where needed.

7. `aria-labelledby`: Names Derived from Other Content

aria-labelledby accepts a whitespace-separated list of element IDs and builds the accessible name from those referenced nodes. It is particularly useful when visible headings or labels already exist but cannot be associated with a control using a native HTML labeling feature. For a dialog, for example, a visible title can serve as its name. For multiple similar links, a combination of short local text and an adjacent article title can help distinguish actions.

<h2 id="review-title">Review your order</h2>
<div role="dialog" aria-modal="true" aria-labelledby="review-title">
  <p>Confirm the items and delivery address before payment.</p>
  <button type="button">Confirm order</button>
</div>

This fragment communicates a name, but it is not a complete modal dialog implementation. Focus placement, containment where applicable, closing behavior, outside-content inertness, and focus restoration still require deliberate handling; a native <dialog> may be preferable for such workflows. That distinction becomes crucial when teams mistake semantic attributes for behavior.

When multiple IDs are used, their referenced text is concatenated in the specified order. Each ID must resolve to the intended element within the relevant DOM tree, and the labels should remain stable across rendering changes. A reference to a missing node, a recycled list-item ID, or a duplicated ID can result in a wrong or absent name. Referenced hidden text is an important exception to ordinary accessibility-tree exclusion: the naming algorithm may draw from explicitly referenced hidden material. Do not generalize from this exception to assume that all hidden interface content is navigable or announced.

aria-labelledby is not a click association. If it names a custom control from a visible label, clicking that visible label does not automatically activate or focus the custom control as an HTML <label> often does for an associated native control. The implementation must separately satisfy the pointer and keyboard interaction model.

8. `aria-label`: Appropriate Uses and Overuse

aria-label directly supplies a string name to an element whose role permits author naming. It is valuable for controls with no usable visible text, such as a close icon whose graphical X would otherwise lack a meaningful name. It can also name a navigation region when the same page has multiple such regions, allowing users to choose among “Primary,” “Account,” and “Footer” navigation landmarks.

<button type="button" aria-label="Close notification">
  <svg aria-hidden="true" focusable="false" viewBox="0 0 16 16">
    <path d="M3 3l10 10M13 3L3 13"></path>
  </svg>
</button>

<nav aria-label="Account">
  <a href="/profile">Profile</a>
  <a href="/settings">Settings</a>
</nav>

A nav landmark's accessible label identifies the region while leaving its link content available; aria-label on an element that receives a name from descendant content can have very different consequences. In those cases, the author-supplied name may replace descendant text as the accessible name, obscuring detail that screen-reader users would otherwise encounter. Use this feature selectively, not as a universal “fix” for every element in an audit report.

Accessible labels are also content. They need translation, editorial ownership, localization, and change control. A textless icon may look identical across locales while the aria-label remains untranslated, resulting in a linguistically inconsistent accessible interface. An updated visible action can leave a stale hidden string. Prefer visible names when possible, and treat invisible labels as first-class UI copy with tests and review responsibilities.

9. Accessible Descriptions and Context Beyond the Name

Names identify; descriptions explain. The standard relationships are aria-describedby, which references supporting DOM content, and aria-description, which supplies a description string directly. The accessible-description computation gives referenced descriptions precedence when applicable. Prefer visible help text referenced with aria-describedby for task instructions, file restrictions, password rules, and explanatory caveats that users may need to reread. An accessible description should support the control, not carry the control's entire identity.

<label for="invoice-id">Invoice number</label>
<p id="invoice-help">Use the number shown at the top right of your invoice.</p>
<input id="invoice-id" aria-describedby="invoice-help">

A short description does not excuse hiding key instructions visually. Someone with memory or reading difficulties may benefit from the same hint as a screen-reader user. Conversely, describing a control with a large paragraph may create excessive verbosity on repeated focus. Consider nearby visible text, a small description, and links to longer help as distinct presentation levels.

For validation messages, a descriptive relationship can bring the current error into the field's context. Where supported and appropriate, aria-errormessage identifies an error element associated with an invalid control; aria-invalid="true" communicates the invalid state. That error relationship should not be treated as a complete error recovery system. Visual errors, summary navigation, focus decisions, and the opportunity to correct the value remain essential, and are the primary subject of Accessible Forms, Errors, and Recovery.

10. Distinguishing Name, Value, Instructions, and Error Messages

A common design defect is to pack every datum into one overloaded label: “Required invoice number, digits only, current input 1234, invalid, please fix.” The name may become long and unstable, while semantic properties that assistive technology expects in distinct channels remain unset. A better model separates the stable identity “Invoice number” from the current textbox value, the required state, a visible format hint, and any error. This makes each piece available through its intended API field and allows users to revisit only the information they need.

Information Better representation Why it matters
Field identity <label> or appropriate naming relationship Stable object recognition
Current text entry Native input value Exposes what the user entered
Required field Native required where applicable Supports validation and announced requirement
Expected format Visible helper text plus aria-describedby Separates instructions from the label
Invalid state Native validity plus aria-invalid as appropriate Exposes condition without renaming control
Specific correction Visible error connected to the field Provides an actionable repair step

In an editable control, the current value should not be duplicated in its accessible name unless the design has a compelling semantic reason. Otherwise a name generated from rapidly changing text may become noisy, and tools that rely on stable names may fail to locate the control. In a range widget the numeric value belongs in value semantics; in a checkbox the current checked state belongs in its state. The overarching principle is one meaning per channel, while ensuring the channels remain synchronized as the interface changes.

11. Roles: Meaning, Expectations, and Structural Ownership

A role represents the kind of accessible object: button, link, checkbox, textbox, heading, list, navigation, dialog, status, tab, tabpanel, grid, or other defined category. It influences how assistive technologies announce and organize the page. Roles also carry behavioral expectations. If a control is declared a checkbox, users reasonably expect checked state and a standard keyboard interaction. If an element is exposed as a dialog, users reasonably expect a coherent dialog workflow rather than ordinary content styled in a box.

Roles can be implicit in HTML or explicit through role="...". An explicit role is not an invitation to overwrite any element's semantics. Some combinations are redundant, inappropriate, or prohibited. The August 2026 W3C ARIA in HTML Recommendation is the correct starting point for what roles and attributes authors may put on given HTML elements. WAI-ARIA 1.2 defines the role taxonomy and characteristics; the HTML accessibility mappings and Core-AAM describe how user agents expose that information.

The following practical distinctions prevent conceptual drift:

  • A button performs an action; a link navigates to a destination. Using a button role on a navigation anchor usually obscures the expected behavior.
  • A tab is not an ordinary navigation link; it belongs to a tablist and controls presentation of a tabpanel according to a specific interaction pattern.
  • An alert conveys urgent, usually non-interactive notification; a dialog contains an interface region that requires interaction. Do not use them interchangeably.
  • A heading structures a document; a button activates an operation. A clickable heading can contain a properly nested button when appropriate, but a semantic heading role by itself does not create operability.
  • A listbox is an interactive selection widget; a native HTML list is document structure, not automatically an interactive picker.

A role declaration must match the actual user-facing contract. If users encounter a visually evident button, a semantic role of “generic” is insufficient. If the interface contains a real editable text field, a role that masks the field's editability is actively harmful.

12. Naming Restrictions and the “ARIA Everywhere” Anti-Pattern

Not every accessible object is supposed to have an author-supplied name. Some roles are structural or generic; their text is intended to be read in context rather than replaced by a synthetic label. WAI-ARIA explicitly identifies roles where naming from author is prohibited. Examples include certain roles associated with paragraphs, generic spans, code fragments, emphasis, and presentation. HTML elements mapped to those roles have corresponding restrictions unless an allowed role override changes the applicable rules.

<!-- Anti-pattern: attempted author naming on a generic paragraph. -->
<p aria-label="Important payment information">
  Your payment has not yet been submitted.
</p>

<!-- Prefer visible text plus appropriate document structure. -->
<h2>Payment status</h2>
<p>Your payment has not yet been submitted.</p>

The second version does not need a synthetic accessibility label for the paragraph: users can navigate to the heading and read the text. Adding names to every container often signals a misunderstanding of the accessibility tree. It may also suppress descendant information for certain roles and create duplicate, disorienting announcements. A conforming implementation should use named landmarks or groups only where their role permits a name and the name creates real navigational value.

Accessibility linting should therefore flag not only missing names but names on the wrong objects. A component library can enforce permitted naming patterns by role. For example, a labeled nav is useful when several navigation regions exist; a div without an appropriate role does not become meaningful solely because it has an aria-label. Avoid treating “more ARIA” as equivalent to “more accessibility.”

13. States and Properties: What Is Different and Why It Matters

WAI-ARIA distinguishes states, which often change as a user interacts, from properties, which describe characteristics or relationships that may be more persistent. The distinction is conceptually useful, but both kinds of ARIA metadata can change at runtime. An expanded state is directly associated with a disclosure's visibility; a description reference may be relatively stable until an error appears; a selected state may change among tabs or listbox options. Developers must know which element owns each attribute and which user action causes it to change.

Attribute or feature Principal meaning Common context Important caveat
aria-expanded Whether controlled content is expanded Disclosure, combobox, tree item Does not show or hide content
aria-pressed Toggle-button pressed condition Bold formatting, mute toggle Not the same as selection
aria-checked Checked condition Checkbox, switch, radio Native inputs should use native checked state
aria-selected Selection within a widget Tab, listbox option Selection is not always activation
aria-current Current item in a set Current page, step, date Different from a selected tab
aria-invalid Entered value has been found invalid Form input Must correspond to actual validation
aria-disabled Perceived disabled or unavailable status ARIA widgets, some other cases Does not block events or focus
aria-required Required state Custom input widgets Prefer native required on HTML inputs
aria-busy Element or region undergoing changes Updating result region Must return to false when ready
aria-haspopup Presence and kind of interactive popup Menu button, combobox Boolean true means menu, not generic “popover”

Several attributes accept special value vocabularies. aria-checked and aria-pressed can support mixed in the roles or patterns where it is meaningful; aria-expanded is Boolean; aria-current can communicate page, step, location, date, time, true, or false. Providing a permitted value is necessary but not sufficient. The visual presentation, accessible representation, focus behavior, and underlying application state must agree. Refer to each role's permitted attributes rather than setting all state attributes on all controls.

14. Disclosure Controls: Expansion State and Controlled Content

The disclosure pattern is an effective demonstration of ARIA's boundary. A native button activates a nearby region; its aria-expanded value identifies whether that region is open. The aria-controls relationship may refer to the controlled element, while HTML hidden (or another suitable visibility mechanism) determines whether users encounter the content. The interface should not display an open panel while announcing “collapsed,” nor should it announce “expanded” while the panel remains inaccessible.

<button id="shipping-toggle" type="button"
        aria-expanded="false" aria-controls="shipping-help">
  Shipping details
</button>
<div id="shipping-help" hidden>
  <p>Standard delivery normally takes several business days.</p>
</div>
<script>
  const toggle = document.getElementById('shipping-toggle');
  const panel = document.getElementById('shipping-help');
  toggle.addEventListener('click', () => {
    const opening = panel.hidden;
    panel.hidden = !opening;
    toggle.setAttribute('aria-expanded', String(opening));
  });
</script>

The example is a compact teaching implementation rather than a reusable component. It relies on a native button so Enter and Space work without custom key handlers. It has no external state manager and assumes neither a framework nor animation. A production component must also handle changes made through external actions, component unmounting, conditional rendering, delayed content, and any animation that temporarily separates what appears open from what remains available to the accessibility tree.

Do not interpret aria-controls as a command to navigate to the controlled panel; it is a machine-readable relationship, and assistive technologies differ in whether they expose useful shortcuts for it. “Controls” conveys an association, not the interaction mechanics. The next articles address focus and the complete behavior of accordions, tree widgets, and other compound patterns.

15. Pressed, Checked, Selected, and Current Are Not Synonyms

The most common avoidable state error is selecting a vocabulary because its English meaning sounds plausible, not because it matches a particular role. A toggle button can be marked pressed or not pressed; a checkbox is checked or unchecked; a tab is selected within a tablist; a navigation link may be current within a navigation set. These models affect the information users expect and sometimes the keyboard commands they apply.

<!-- Persistent toggle-button identity; the pressed state changes. -->
<button type="button" aria-pressed="true">Mute audio</button>

<!-- Native checkbox state; no duplicate aria-checked needed. -->
<label><input type="checkbox" checked> Email me a receipt</label>

<!-- Current navigation destination, not a tab selection. -->
<a href="/account" aria-current="page">Account overview</a>

A toggle button's fixed name typically describes the controlled feature and its pressed state tells whether that feature is active. An alternative action-label model (“Mute audio” becoming “Unmute audio”) may be usable, but mixing both models without thought leads to ambiguity. When creating a single-select listbox, ensure the selected option represents the product's intended selection semantics; when building a tablist, selected state usually identifies the tab associated with the displayed panel. A current-page link does not become selected merely because its destination matches the present URL.

aria-pressed="mixed" is appropriate only for a meaningful indeterminate toggle condition, such as a formatting selection spanning both bold and non-bold text. It is not a generic replacement for “unknown.” Native checkboxes support indeterminate state through the DOM indeterminate property, which is distinct from the HTML checked attribute. Their visual and semantic states need consistent management without redundant contradictory ARIA.

16. Disabled, Read-Only, Required, and Invalid Conditions

Disabled generally means an action or input is not presently available. A native disabled attribute on a supported HTML control suppresses ordinary interaction and typically removes that control from sequential keyboard focus. aria-disabled="true" communicates disabled status but does not disable click handlers, prevent submission, or manage focus. A custom widget using aria-disabled must enforce the restriction itself and communicate why the option is unavailable when helpful. Some composite patterns deliberately keep disabled options focusable so users can discover their existence; this must be a conscious interaction decision.

Read-only describes content that can be inspected but not changed; it is not the same as disabled. Required means a value must be supplied; it should be communicated both programmatically and in an understandable way, especially if the visual design uses only an asterisk. Invalid means a particular control's value has failed validation; it should not be set merely because the user has not yet started typing. Distinguish a general warning from a field-specific invalid state.

<label for="customer-id">Customer ID</label>
<input id="customer-id" value="AC-1042" readonly>

<label for="payment-code">Payment code (required)</label>
<input id="payment-code" required aria-invalid="true"
       aria-describedby="payment-error">
<p id="payment-error">Enter the six-digit code from your confirmation.</p>

In this snapshot, aria-invalid="true" should reflect a real validation outcome; a production application should set or clear it when validation changes. In dynamic forms, the error text must not persist after the user corrects the issue without a corresponding updated state. If using aria-errormessage, make the referenced error content available and align it with the invalid condition; support variation should be tested in the target browser and assistive-technology combinations. Native validation, live announcements, error summaries, and focus movement are separate considerations.

17. Values, Ranges, Metering, and Progress

Some objects communicate more than a Boolean state. A slider has a minimum, maximum, and current value; a progress indicator may represent completion percentage; a spinbutton has an editable numeric value; and a meter represents a measurement within a known range. Wherever native elements provide the needed semantics, they should be considered before custom ARIA widgets. HTML input type="range", progress, and meter expose useful properties and behavior, while a custom role="slider" requires keyboard interaction and state management not provided by ARIA alone.

<label for="font-size">Reading font size</label>
<input id="font-size" type="range" min="12" max="30" value="18">

<label for="upload-progress">Document upload progress</label>
<progress id="upload-progress" max="100" value="40">40%</progress>

For custom range widgets, aria-valuemin, aria-valuemax, aria-valuenow, and sometimes aria-valuetext may be needed according to the widget role. The current numeric value and its spoken meaning must agree: a slider storing values 0–3 but representing “Off, Low, Medium, High” may need a meaningful value text such as “Medium.” Do not apply these attributes to arbitrary elements that have no compatible range-widget role. A <progress> element without a value can represent indeterminate progress; it should not falsely claim a percentage when none can be calculated.

Loading status is distinct from completion percentage. A progressbar does not by itself tell users that an unrelated results list has been updated, and a live region that says “Working” does not expose the amount completed. The two may be complementary when the workflow genuinely supports both. For long-running operations, keep the user informed without producing excessive announcements on every small increment.

18. Relations: Labels, Descriptions, Controls, Owns, and Active Descendants

ARIA relationship properties connect objects that would otherwise appear separate in the accessibility model. aria-labelledby supplies name sources; aria-describedby supplies descriptive sources; aria-controls identifies content controlled by another element; aria-owns can influence an accessibility parent-child relationship; and aria-activedescendant indicates a logically active descendant while DOM focus remains on a controlling element. These relationships serve distinct purposes and should not be substituted for one another.

The safest relationships reflect real structure. If a popup is contained inside a suitable widget hierarchy, preserve natural DOM relationships whenever possible. Using aria-owns to rearrange accessibility ownership is a specialized technique with potential reading-order and compatibility side effects; it is not a repair for an arbitrary visual layout. aria-activedescendant requires the implementation to update the active option, scrolling and visual indication while maintaining the expected DOM focus behavior; assigning an ID alone does not make arrow navigation work.

<label for="country-search">Search countries</label>
<input id="country-search" type="text" role="combobox"
       aria-autocomplete="list" aria-expanded="true"
       aria-controls="country-options"
       aria-activedescendant="country-option-2">
<ul id="country-options" role="listbox">
  <li id="country-option-1" role="option">Canada</li>
  <li id="country-option-2" role="option" aria-selected="true">Mexico</li>
</ul>

This is a semantic schematic, not a complete combobox. It omits the event handling, popup visibility rules, option focus management, keyboard command processing, and selection behavior needed for a functioning widget. Without those pieces it should not be deployed as a production combobox. The example's real purpose is to show that aria-controls, aria-activedescendant, aria-selected, and aria-expanded carry different kinds of information, even when they participate in one interaction.

19. Popups, Dialogs, and Composite Widgets: Semantic Limits

For a menu button, aria-haspopup="menu" tells assistive technology that the control opens a menu. aria-haspopup="true" is equivalent to a menu popup, not an unrestricted declaration that something appears on screen. Other supported values include listbox, tree, grid, and dialog as appropriate. A regular tooltip, help bubble, or simple disclosure panel should not be labeled as an application menu merely because a panel becomes visible. aria-expanded exposes current openness where the widget model calls for it; aria-controls can identify the related popup.

<button type="button" aria-haspopup="menu"
        aria-expanded="false" aria-controls="account-menu">
  Account actions
</button>
<ul id="account-menu" role="menu" hidden>
  <li role="none"><button role="menuitem" type="button">Download statement</button></li>
</ul>

Again, this snippet illustrates labels and states; it is not a compliant menu widget by itself. In particular, a menu is a composite widget with specific arrow-key, focus, and dismissal expectations. In many ordinary application interfaces, a disclosure containing a list of normal links or buttons is more appropriate and simpler than a desktop-application-style menu. Choose a complex role only when the product truly intends to implement the complex behavior.

A modal dialog requires more than role="dialog" or aria-modal="true"; the app must actually constrain interaction appropriately, manage focus, and support exit. aria-modal is an assertion about modal behavior, not a mechanism that makes surrounding content inert. Browser-native dialogs can reduce the need to implement these mechanics manually, but must still be named and used correctly. Role metadata must be reviewed alongside a real keyboard and screen-reader task, not in isolation.

20. Live Regions and the Meaning of a Dynamic Update

A live region communicates changes that happen without the user's focus moving to the changed content. Examples include “Three results found,” “Draft saved,” or “Connection lost.” aria-live="polite" typically queues announcements at an appropriate moment; aria-live="assertive" requests more urgent interruption and should be reserved for genuinely time-sensitive information. The status role has an implicit polite live region, and alert has an implicit assertive live region. Overuse of assertive announcements can interrupt speech, disrupt concentration, and make an interface less usable than a quieter design.

<p id="save-status" role="status"></p>
<script>
  function reportSaved() {
    document.getElementById('save-status').textContent = 'Draft saved';
  }
</script>

In this teaching example, the status container already exists in the DOM and its text is updated after an event. That is a more dependable starting pattern than creating an entire prepopulated live region at the instant the announcement is needed, because support for first-time insertion and initial content can vary. role="status" generally does not move keyboard focus to the status; it reports information while users continue working. A critical error may warrant visible remediation and appropriate focus guidance rather than merely a louder announcement.

ARIA live attributes influence how updates are processed. aria-atomic can request that a region be announced as a whole rather than by changed fragments; aria-relevant can describe which additions, removals, or text changes matter; and aria-busy can indicate that an element is undergoing updates and should not be presented as complete. Implementations should avoid using these attributes speculatively—default behavior and actual browser/assistive-technology support should be tested for each interaction. Live announcements do not replace persistent visible feedback or clear error text.

21. Loading, Saving, Validation, and Other Async Status Patterns

Dynamic interfaces often have three distinct moments: an operation is requested, a result becomes available, and the interface offers the next appropriate action. Accessible status communication should follow that state transition. During a request, a visible progress indicator or “Saving…” message may set an accurate expectation. On completion, “Changes saved” should appear visibly and, if necessary, be announced politely. On failure, a specific message should identify what remains unsaved and what the user can do. A status that is cleared too quickly can prevent users from reviewing it.

<section id="results-region" aria-busy="false" aria-labelledby="results-title">
  <h2 id="results-title">Search results</h2>
  <ul id="results-list"><li>Example result</li></ul>
</section>
<p id="results-announcement" role="status"></p>

When a search runs, the application can mark the results region busy and then clear that state after replacing its items. It can update the nearby status with a concise completion message, such as “12 results.” This should be grounded in the actual result count and synchronized with the displayed items. Announcing each inserted list item individually would generally be unnecessarily noisy. Visual users and screen-reader users should receive materially equivalent information about waiting, failure, and completion.

Validation is especially sensitive. A routine hint need not be assertive; a server-side error should not quietly vanish. Adding a live region to every input and updating it on every keystroke can overwhelm the user. Prefer targeted messages at meaningful events such as submission or departure from a completed field, and ensure that a user who misses the announcement can still find the visible error through the field's description or error relation. Distinguish an announcement from actual correction support.

22. Hidden, Visually Hidden, and Removed Content

Accessible-name calculation creates edge cases around visibility. Content hidden with display: none, the hidden attribute, or visibility: hidden is generally absent from ordinary accessibility navigation. Yet text in an explicitly referenced hidden node can sometimes contribute to the accessible name or description under the algorithm's special traversal rules. Content visually concealed using a carefully implemented visually-hidden CSS technique can remain in the accessibility tree. These patterns should be chosen for an identifiable semantic purpose rather than used indiscriminately.

aria-hidden="true" removes an element and its descendants from the accessibility tree, subject to platform and implementation details. Applying it to a container that contains a keyboard-focusable control is usually a serious error: the user may reach an interactive object that is not meaningfully exposed to assistive technology. Likewise, putting essential instructions inside an inaccessible hidden subtree with no valid reference can eliminate information necessary to complete a task.

<!-- Decoration that need not be announced. -->
<button type="button">
  <svg aria-hidden="true" focusable="false" viewBox="0 0 16 16">
    <path d="M2 8h12"></path>
  </svg>
  Continue
</button>

An icon can be decorative when the adjacent button text already supplies the name; that does not make the whole button decorative. An icon-only control needs an independent accessible name on the interactive button. Hidden-label techniques should be evaluated with screen magnification, voice control, and cognitive usability in mind, not just screen readers. Accessible information should be available in the right modality for the task and should not contradict the visual interface.

23. Localization, Language, and Speech-Input Compatibility

Accessible names are UI copy and must enter the localization pipeline. Translators need context about whether a string names a button, a landmark, a status message, or an explanatory description. A string such as “Close” could be a verb on a button or an adjective elsewhere; without context, localization may produce an inaccurate name. Dynamically generated object names also need locale-sensitive formatting for dates, numbers, units, and currencies.

The Label in Name requirement in WCAG 2.2 is especially relevant to controls with visible text. When a visible control says “Continue,” speech-input users may issue the command “Click Continue”; a completely different accessible name can impair that workflow. The accessible name should include the visible text and, as a practical preference, often begin with it. Do not replace visible “Search catalogue” with an invisible label that bears no lexical resemblance to those words. Screen-reader clarity and speech-input discoverability should be designed together.

When a dynamic label changes language, ensure the surrounding page and embedded text have appropriate language metadata. A multilingual service may include proper names or mixed-language data that screen readers pronounce differently; per-element language spans can help where genuinely appropriate. Translation must also encompass announcements and error descriptions, not only menu buttons. A multilingual interface with English-only aria-label values is incomplete even if its visible controls have been translated.

24. Common ARIA Failure Modes and Their Root Causes

Many ARIA defects arise from state ownership rather than misunderstanding of attribute spelling. An application stores an “open” Boolean in one component, while another component computes aria-expanded from a stale property. An input's visible validation message changes but its aria-describedby continues referencing the old message. A repeated list generates duplicated IDs, so every “Remove” control is named for the first row. A tab visually becomes selected, but aria-selected remains true on two tabs. These are data-flow and lifecycle errors with accessibility symptoms.

Failure pattern Likely root cause Corrective direction
“Button” with no name Icon-only control lacks a label Give the permitted interactive element a meaningful name
Names do not match visible text Stale aria-label overrides content Prefer visible naming; align accessible and visible labels
Screen reader announces “collapsed” over open panel State and DOM visibility diverged Update actual visibility and ARIA from one state model
Two tabs reported selected Multiple independent selection flags Enforce one selection invariant
Critical content is never announced Event updates outside a stable live region Use persistent status region and test announcement timing
Every result row repeats the same name Duplicated IDs or wrong references Generate stable unique IDs; inspect computed names
“Disabled” item remains operable aria-disabled mistaken for behavior Enforce interaction restriction and communicate it
Dialog opens but focus stays behind it Semantic declaration mistaken for modal implementation Implement or use native modal behavior
Paragraph loses useful text Overuse of author naming Remove invalid or unnecessary ARIA

The underlying corrective method is not to add an attribute at random. Inspect the actual role, name, state, description, and relationships; reproduce the user action; identify the component state that is authoritative; and repair the connection between application behavior and accessible semantics. Regression tests should fail when the accessible state no longer matches the visible state. The next specialist article addresses the broader focus and keyboard aspects of many of these defects.

25. Inspecting the Accessible Object in Developer Tools

An accessibility audit should inspect computed accessibility data, not merely raw attributes. Open the browser's accessibility inspection panel, focus the target element, and record the computed role, name, description, state, value, and relevant relations. Then compare that record to the visible element and the user's task. A successful inspection does not stop when a computed name appears; it verifies that the name is correct and distinguishable, the role reflects the intended interaction, and the state changes immediately after the operation.

A useful investigation sequence is:

  1. Identify the visible control, its user-facing label, and its intended action.
  2. Inspect its DOM element and determine whether native HTML semantics are available.
  3. Inspect the computed accessibility-tree object, recording its role and name.
  4. Find the actual name source: native label, referenced content, element text, aria-label, or another mapping.
  5. Inspect the description and relationships, including the IDs they reference.
  6. Record the initial state, activate the control, then inspect the resulting state and visible content.
  7. Confirm any status message is exposed without an unexpected focus shift.
  8. Test the same workflow with keyboard navigation and at least one relevant screen-reader/browser combination.
  9. Verify an accessible label remains accurate after translation, re-render, validation, or repeated-row creation.
  10. Capture the environment, observed outcome, expected outcome, affected users, and reproducible steps in the defect report.

Automated rules can catch some empty names, invalid roles, duplicate IDs, and missing required ARIA attributes. They are less capable of judging whether “Open” is meaningfully specific, whether an accessible name matches visible text well enough for speech input, whether a state reflects the actual user interface, or whether a status update arrives at the right moment. These require task-based human review. A screen reader's particular phrase is not a universally reproducible output; capture browser, operating system, assistive technology, version, and configuration when reporting an observed announcement.

26. Testing Correctness Across State Transitions

Static page-load checks miss many failures. A component may have a correct name and role before interaction, then lose its name when the rendering framework replaces a node. A disclosure may begin collapsed and correct, but announce “expanded” while its lazy-loaded panel is still absent. A list of invoice rows may use stable IDs initially and generate collisions after sorting. Test transitions, not merely snapshots.

State transition What to observe Example of failure
Closed to open Panel visibility and aria-expanded agree State stays false after opening
Unchecked to checked Native or permitted checked value changes Visual tick updates, semantics do not
Valid to invalid Field error is visible and associated Red border only; no programmatic error
Pending to complete Busy status clears; outcome is announced if needed Infinite “busy” or no completion message
Single selection moves One selected item and corresponding panel Two tabs selected simultaneously
Modal opens and closes Dialog name, modal behavior, focus return Dialog named but background still operable
List reorders Accessible item names still point to correct records Row controls inherit stale ID references
Locale changes Visible and accessible labels update together Text translated but hidden labels remain English

When testing, classify the outcome precisely. Semantic correctness means the required role/name/state data is available and correct. Behavioral correctness means the user can actually operate the control under the expected inputs. Perceptual correctness means the visual or auditory feedback reflects the same condition. Task success means a person can complete the intended goal reliably and reasonably. A product should meet all four; a pass in one is not evidence of a pass in another.

A controlled test can deliberately introduce one defect to teach diagnosis: duplicate an ID, remove a <label for>, keep aria-expanded unchanged, or set aria-hidden on a parent of a focusable element. Inspect the result and repair it. Such exercises are safer in a local training environment than in a live service, and they develop the skill of explaining why a defect matters rather than memorizing the “correct” attribute name.

27. Choosing the Correct Semantic Mechanism

A practical selection framework begins with the user's question rather than with the complete ARIA attribute catalogue. If the user needs to know the identity of an ordinary form field, choose native labeling. If a region needs a name, decide whether an existing visible heading can be referenced. If a toggle has a Boolean feature state, decide whether it is natively a checkbox or a push-button toggle. If content expands, expose its openness and keep the actual region synchronized. If a background operation finishes, consider persistent visible feedback and a measured live announcement.

Interface need Preferred starting point Likely augmentation Do not confuse with
Name a text input <label for> aria-describedby for a hint Placeholder-only labeling
Name icon-only action Native <button> aria-label if permitted SVG title as only action name without testing
Identify a named region <section> with visible heading or <nav> aria-labelledby / aria-label as allowed Naming every generic container
Expose disclosure <button> plus real panel visibility aria-expanded, optional aria-controls A dialog or menu
Expose binary choice Native checkbox None ordinarily Toggle button pressed state
Expose tab selection Correct tablist/panel pattern aria-selected, ownership relations Current navigation page
Expose field failure Native validation and visible correction aria-invalid, description/error relation Mere color change
Expose save confirmation Visible status text role="status" Focus-stealing alert for routine success
Expose custom range Native range input if possible Range-valued ARIA for genuine custom role Static percentage text
Expose dialog Native <dialog> or complete dialog widget Suitable label and modal semantics A styled div with role alone

This table is intentionally a starting point, not a universal recipe. Role eligibility, required state values, widget composition, focus handling, and browser support still need verification against the applicable W3C specifications and product interaction requirements. A team should prefer the simplest semantically honest design and justify custom widgets by actual product need, not merely a visual style guide.

28. Eight Worked Cases: From Defect to Repair

Case 1 — Three unnamed magnifying-glass buttons

Situation. A research portal has a site-search button in the header, a collection-search button in the sidebar, and a search-within-results button in a floating toolbar. Each is drawn as a magnifying-glass SVG with no visible words. The accessibility tree exposes three buttons with empty or unhelpful names. Screen-reader users navigating a list of buttons cannot distinguish them.

Investigation. Inspect the computed names rather than assuming the SVG filename or icon title will be inherited as the button name. Ask whether each button could reasonably display a visible label. If the product must retain icon-only controls, label the appropriate native button with a concise action such as “Search site,” “Search collections,” or “Search results,” then verify translation and speech-input discoverability.

Result and boundary. A correct accessible name repairs identification, but it does not establish that the search panel can be opened or focused. The latter behavior belongs in keyboard and interactive-component review. Lesson: an image's meaning and a button's operational name are different design questions.

Case 2 — “Read more” links in a list of articles

Situation. A news index contains 20 repeated “Read more” links. Each is technically a link and has a nonempty accessible name, but a screen-reader user scanning links out of context encounters 20 indistinguishable entries.

Investigation. Prefer descriptive visible link text, such as “Read the coastal erosion report,” where the layout allows it. Alternatively, use a valid aria-labelledby relationship to combine “Read more” with a nearby article title, keeping visible wording in the accessible name. Avoid generating labels from positional data such as “Item 7” when the collection can reorder. Check IDs for uniqueness and ensure that all links point to their intended records.

Result and boundary. The links become distinguishable without inventing a custom role. Lesson: an accessible name must support the user's information-retrieval task, not merely satisfy an automated “has accessible name” rule.

Case 3 — Accordion visually open but announced collapsed

Situation. A college course FAQ uses a native button and panel. A framework component updates a CSS class when opened, but aria-expanded still reads false. The panel appears open to sighted users while a screen reader reports it as collapsed.

Investigation. Trace the state through the component's actual source of truth and locate every place openness is mutated. Derive the panel's visibility and aria-expanded from the same state, or use one deterministic update. Validate after mouse, Enter, and Space activation, after route changes, and after the component rerenders.

Result and boundary. Users receive a truthful expanded state. Further review is necessary for heading hierarchy, focus placement, and collapsed-content exclusion. Lesson: ARIA can become stale when it is treated as cosmetic annotation instead of part of the component's state contract.

Case 4 — A mute control that changes both name and state

Situation. A video player starts with a button named “Mute audio” and aria-pressed="false". When activated, the label becomes “Unmute audio” and pressed becomes true. Different users hear overlapping signals about action and condition; a spoken command may no longer match the control name they originally learned.

Investigation. Choose one model. A fixed-name toggle can remain “Mute audio” while updating aria-pressed between true and false, with a visual state affordance. Alternatively, a conventional action button may change between “Mute audio” and “Unmute audio” without using pressed-state semantics. Evaluate the model against the rest of the player's controls and the intended assistive-technology output.

Result and boundary. A coherent model avoids contradictory names and state indications. Lesson: accuracy depends on the combination of attributes and action semantics, not on the presence of any one “correct” field.

Case 5 — A validation error that exists only in red text

Situation. A tax application marks the taxpayer-identification field red after an invalid submission. A red sentence appears under the form, but it is not associated with the input. Keyboard and screen-reader users find no clear indication of which field failed or how to correct it.

Investigation. Give the field a stable visible name, mark invalid state when appropriate, provide a specific visible error next to the field, and reference that error using an appropriate description or error relationship. Consider a form-level error summary that links to the affected field. Avoid reading the whole error repeatedly on every keystroke; test when the message is announced and how users can revisit it.

Result and boundary. The field's name remains stable while its error is understandable and actionable. Lesson: visible color, invalid state, and correction instructions are separate information channels and all must be designed.

Case 6 — Autocomplete list with misplaced active-descendant references

Situation. A library catalogue offers a custom suggestion list. Typing causes suggestions to appear; arrow keys change a blue highlight, yet the screen reader keeps announcing the previous option. The UI stores a highlighted index but does not update aria-activedescendant when the list order changes.

Investigation. Check the focused combobox element, the referenced option ID, the option's actual role and text, and whether the option remains in the controlled listbox. Ensure stable IDs, update the active-descendant reference alongside the visual highlight, and implement the keyboard, scrolling, and selection behavior required by the full combobox pattern. Verify that “active” and “selected” reflect the product's actual interaction distinction.

Result and boundary. The semantic relation follows the visible active option. Lesson: relations are pointers into a changing object model; they are not keyboard implementations or substitutes for selection logic.

Case 7 — Save confirmation hidden behind a spinner

Situation. A budgeting application displays a spinner after a user edits a category. The spinner disappears when saving ends, but there is no persistent confirmation. Some users submit the same change repeatedly because they cannot tell whether it succeeded.

Investigation. Provide visible saving and outcome messages; maintain a stable status region so the final “Category saved” text can be conveyed nonintrusively. When relevant, mark the affected region busy only while the operation actually runs. Distinguish failed persistence from a temporary delay and give a retry route that preserves user input.

Result and boundary. Users can discover the result without losing focus. Lesson: a spinner's visual motion is neither a completion message nor an accessible announcement of the operation's result.

Case 8 — Translated buttons retain English invisible names

Situation. A multilingual medical booking form displays its controls in Spanish, including “Continuar,” but the button has an English aria-label="Next step". A user of speech input says the visible words and the command is not recognized reliably; a screen-reader user hears a language mismatch.

Investigation. Replace the unnecessary hidden name with the visible native button text wherever possible. If a programmatic label must exist, make its translation part of the localization bundle and ensure it includes the visible words in an appropriate order. Evaluate mixed-language proper names and the status announcements that follow the action.

Result and boundary. Accessible and visible labels stay consistent across locales. Lesson: localization, speech recognition, and nonvisual access depend on the same semantic naming discipline.

29. Design-System Contracts and Implementation Ownership

In a multi-team organization, semantic correctness must be built into shared components, not rediscovered at each page. A design-system button component should specify whether it receives visible text, an icon-only accessible label, disabled state, pressed state, or expansion state; it should reject contradictory combinations where feasible. A form-field component should require a name, allow linked help and errors, and expose validation state without replacing the name. A dialog component should demand a title or explicit accessible name and keep its modal behavior owned by one implementation.

Component Required contract State invariants to test Common ownership mistake
Icon button Accessible name, native activation Name remains accurate after render Design team supplies icon but no naming guidance
Disclosure Named button and controlled region Expanded equals actual visibility CSS and ARIA updated independently
Toggle Consistent action/state model Pressed or checked matches reality Name flips without state model review
Form field Label, value, instructions, errors Validity and messages agree Error text owned by unrelated component
Tab interface Tablist/tab/tabpanel roles and relations Single-selected invariant, correct panel Each tab owns independent selected Boolean
Async status Visible and programmatic outcome Busy clears, correct result announced Spinner removed without completion communication

The component API should name its responsibilities clearly. For example, an icon-button component might require accessibleLabel when no text child is supplied; a disclosure component might compute aria-expanded internally rather than accept an unrelated ARIA string that can drift from visibility. Automated tests can inspect DOM semantics and component state changes. Usability validation still requires real assistive technology and actual people with diverse needs where appropriate.

Ownership includes documentation. A designer decides what action the component represents and which label is meaningful; a developer implements native semantics, relations, and behavior; content teams maintain names and translations; quality specialists inspect actual assistive technology behavior; and product owners decide whether an ambiguous interaction needs redesign. Semantic accessibility is a cross-functional obligation with concrete implementation artifacts.

30. Ten-Step Naming, State, and Announcement Framework

  1. Describe the user's task. Identify the exact operation or information request rather than beginning with a component library label.
  2. Choose the native element. Use the built-in HTML control that best matches the task where one is suitable.
  3. Determine the accessible role. Confirm its implicit or permitted explicit role and the behavior users should expect.
  4. Choose the visible name. Write a short, meaningful label that distinguishes the control and agrees with its purpose.
  5. Compute the accessible name. Use native labeling first; add allowed aria-labelledby or aria-label only with a reason.
  6. Separate supplementary information. Put instructions and repair guidance in visible content with a suitable description or error association.
  7. Define the state model. Identify every state that changes, its source of truth, and the component that updates it.
  8. Associate related objects. Ensure IDs are unique and stable, and use aria-controls or other relationships only for true semantic associations.
  9. Plan dynamic communication. Choose visible status text and a suitable announcement mechanism without needless interruptions or focus theft.
  10. Verify the full transition. Inspect computed role/name/state before and after use, confirm actual behavior, and test with representative assistive technology.

Acceptance evidence should include the visible design, the DOM and computed accessibility object, interaction transition results, and observed assistive-technology behavior. The author should explicitly distinguish what was verified from what remains untested. A static inspection of a markup snippet can show that the author attempted to provide attributes; it cannot establish the accessibility of the running product across devices or user workflows.

32. Study Questions and Applied Exercises

Conceptual questions. (1) Why is an accurate accessible name not enough to make a control usable? (2) What distinguishes a role from a state? (3) When is aria-labelledby preferable to aria-label? (4) Why can adding an accessible label to a paragraph be inappropriate? (5) What is the difference between aria-pressed, aria-checked, aria-selected, and aria-current? (6) Why does aria-disabled not guarantee that an action is unavailable? (7) What makes a live-region announcement unnecessarily intrusive? (8) How can a computed-name inspection reveal a labeling bug that is invisible on screen?

Exercise A — Trace name sources. Build one native text input with a <label>, an icon-only button with aria-label, and a named dialog using aria-labelledby. Inspect their computed names in browser accessibility tools. Change the referenced IDs and document how missing or duplicate references alter the accessible result. Restore correct markup and explain why the original association was preferable.

Exercise B — Synchronize a disclosure. Implement a button that opens and closes a nearby information panel. Use a single Boolean state to manage both visibility and aria-expanded; optionally add aria-controls with the panel's ID. Test with Enter, Space, pointer input, and assistive-technology announcements. Explain why setting aria-expanded alone would not provide disclosure functionality.

Exercise C — Compare semantic choice models. Implement three simple controls: a native checkbox, a toggle button, and a current-page navigation link. For each, write down the intended user question, visible appearance, name, role, state, and input behavior. Make one deliberate mismatch, observe the inconsistency in accessibility inspection, and repair it.

Exercise D — Design status feedback. Create a form that simulates a delayed save. Show a visible “Saving…” message, then either “Draft saved” or a clear failure message. Provide appropriate accessible status communication without moving focus for routine success. Test whether a message appears on time, persists long enough to review, and is not announced repeatedly for one operation.

Exercise E — Review a local interface. Choose a public or training page with repeated interactive controls. Inventory the first ten visible controls and record each object's computed name, role, description, and state. Flag ambiguous labels, mismatches, invalid author naming, and broken ID references. Separate findings that can be determined by source inspection from those requiring a keyboard or screen-reader task. Provide concrete remediation steps rather than a scanner score alone.

Review standard. For each exercise, submit (a) the intended task, (b) source or DOM evidence, (c) computed accessibility semantics, (d) a short description of actual interaction, (e) what the evidence supports, and (f) one acknowledged limitation. This keeps the article's technical claims demonstrable without confusing a local training example with verified WCAG conformance.

  • Accessibility Testing and Assistive-Technology Compatibility — evidence collection, browser/AT testing matrices, repeatable reproduction, and compatibility limits.

The practical sequence for front-end developers is native semantic structure → accessible object naming and state → keyboard focus → navigation and widget behavior → real assistive-technology verification. Designers may begin with names and state diagrams; testers may begin with inspection and transition matrices. The specialist topics remain distinct even though professional workflows combine them.

34. Related Topics and Cross-Division Context

The Accessibility overview provides the broader account of equitable use of technology. The Human Interaction Systems division situates the present article beside Human-Computer Interaction, User Interface Design, User Experience Design, and Interaction Models. Those subjects examine human goals, interactions, and the design process; this article owns the precise accessible semantics used to communicate UI identity and changing condition.

The Programming and Development division addresses implementation techniques; the Software Systems division situates component design in software architecture and maintenance; and Computing Ethics examines the obligations of designers, vendors, and institutions toward users affected by inaccessible systems. Accessible names and roles are technical mechanisms supporting participation, not substitutes for inclusive research, accessibility conformance, or real-world usability.

35. Primary Specifications, Official Guidance, and Further References

The technical explanations in this article are grounded in the following standards and official educational guidance. A normative standard, an editorial working draft, and a non-normative teaching guide should not be represented as having identical publication status. The example code and eight teaching cases above are constructed illustrations; they do not describe an independently tested deployed product.

  1. W3C, Accessible Rich Internet Applications (WAI-ARIA) 1.2 — Recommendation defining roles, states, properties, role characteristics, and author requirements.
  2. W3C, ARIA in HTML — Recommendation dated 11 August 2026, defining permitted and prohibited use of ARIA roles and attributes in HTML.
  3. W3C, Accessible Name and Description Computation 1.2 — November 2026 Working Draft, with text-equivalent traversal and name/description computation details.
  4. W3C, Core Accessibility API Mappings 1.2 — developing specification describing exposure of ARIA semantics to platform accessibility APIs.
  5. W3C, HTML Accessibility API Mappings 1.0 — browser mapping of HTML features and associated accessibility properties.
  6. WHATWG, HTML Living Standard — native labels, controls, hidden and inert behavior, forms, and the meaning of HTML elements.
  7. W3C WAI, Authoring Practices: Providing Accessible Names and Descriptions — detailed design guidance and authoring examples; educational guidance, not a substitute for the normative name algorithm.
  8. W3C WAI, Authoring Practices: Disclosure Pattern — appropriate button and expansion semantics.
  9. W3C WAI, Authoring Practices: Button Pattern — push buttons, toggles, and menu buttons.
