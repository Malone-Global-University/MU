1. Definition, Scope, and Governing Question

Text resizing, zoom, and responsive reflow describe how a digital interface preserves access to content and functionality when readers enlarge text, magnify an entire page, narrow the effective viewport, or alter their preferred text presentation. They are related but distinct. Text resizing changes the scale at which characters are rendered; full-page zoom generally changes the apparent scale of text and other interface elements; responsive reflow changes the arrangement of content so that enlarged material remains usable within a reduced visible area. An interface can support one mechanism while failing another. A paragraph that doubles in size may remain legible even though its submit button disappears behind a fixed panel. A responsive page may look elegant on a smartphone while breaking when a desktop browser reaches 400% zoom.

The governing question is: Can a person enlarge and adapt a complete digital task without losing essential information, controls, orientation, or the ability to finish? The answer must be established through rendered behavior rather than through a design declaration. This article examines text enlargement, browser zoom, viewport geometry, flexible CSS layout, wrapping, embedded content, forms, overlays, test methods, and accountable implementation. It is Article 11 of 26 in the Accessibility specialist unit, in the Visual, Nonvisual, and Media Accessibility group.

The preceding article, Color Contrast and Visual Presentation, owns color differentiation and visual styling. Screen Readers and Nonvisual Navigation owns nonvisual reading and control. This article owns the scale-and-layout contract: whether the same essential task remains available as presentation changes. Responsive design is a method toward that contract, not a sufficient result by itself.

2. Who Needs Scaling and Why the Same User May Need Different Modes

People enlarge digital content for many reasons. A reader with low vision may need larger type and greater distance between elements; someone with reduced contrast sensitivity may enlarge text to help distinguish glyph shapes; a person with a motor disability may benefit when text controls grow together with interactive targets; and a reader with dyslexia, fatigue, or concentration difficulties may prefer spacious layouts. Temporary conditions also matter: glare outdoors, a cracked display, unfamiliar prescription lenses, a shared screen, or a presentation viewed from the back of a room can change which scale is usable.

No one scaling method suits every person or every task. Some readers prefer browser zoom because buttons and icons grow as well as text. Others prefer text-only enlargement because photographs and structural chrome should remain stable while the words grow. Some rely on operating-system text-size settings or browser minimum font sizes; others change magnification dynamically as they inspect a chart or complete a form. A screen magnifier may move a narrow viewing window across the page; that is a different interaction from responsive reflow, though good reflow can reduce unnecessary panning.

Accessibility is therefore not a single “large text mode.” Content authors should permit supported browser and platform adjustments, avoid assumptions about the user's chosen device or visual settings, and preserve functional equivalence across those adjustments. A user must not have to return to 100% zoom to locate a required field, see a warning, or access confirmation. The correct comparison is the task outcome, not whether a screenshot looks identical at two zoom levels.

3. Four Mechanisms That Must Not Be Conflated

A review begins by identifying what was actually changed. Different mechanisms affect CSS pixels, layout, scroll geometry, and the relationship between text and controls in different ways.

Mechanism What changes Typical risk What to observe
Browser full-page zoom Text, graphics and rendered interface scale; CSS viewport available to layout may shrink Navigation, columns, overlays or controls cease to fit Effective viewport, reflow, visible controls, focus and scroll paths
Browser text-only zoom or increased default text size Text grows more than surrounding layout Fixed-height containers clip labels; icons fail to align Wrapping, container growth, form fields, labels
Operating-system text scaling / accessibility text settings Device or app text may grow depending on platform and implementation Inconsistent scaling between app and controls Real platform settings and representative applications
Screen magnification / pinch magnification A portion of a rendered interface is enlarged for viewing Repeated panning and hidden context Reading and task navigation within the magnified view

Full-page zoom is not simply the CSS zoom property. Author-applied transform: scale() can make content look larger without causing normal document reflow, and may introduce clipping or overlaps. Similarly, narrow-device responsive behavior is not necessarily the same as desktop zoom behavior: viewport handling and browser chrome vary. An acceptance test must record the browser mechanism and viewport state instead of reporting only “zoom passed.”

4. WCAG 2.2 Requirements and the Correct Reading of Their Thresholds

The most directly relevant requirements are in the W3C Web Content Accessibility Guidelines (WCAG) 2.2. These are success criteria, not design recipes; meeting them requires checking the rendered interface and the applicable exceptions. The levels in the table are the WCAG 2.2 levels, not a claim that a particular regulation adopts that version.

WCAG criterion Level Governing requirement in practical terms Common failure
1.4.4 Resize Text AA Text other than captions and images of text can reach 200% without loss of content or functionality Enlarged input labels become clipped
1.4.10 Reflow AA Content reflows at the defined narrow CSS viewport dimensions without two-dimensional scrolling, apart from material requiring a two-dimensional layout Entire page becomes horizontally scrollable
1.4.12 Text Spacing AA User-applied spacing values must not cause loss of content or function Button text overlaps or vanishes
1.4.5 Images of Text AA Use actual text instead of images of text when the stated exceptions do not apply An essential image label cannot adapt like text
1.3.2 Meaningful Sequence A The programmatic reading sequence preserves meaning Visually moved steps are read out of order
2.4.11 Focus Not Obscured (Minimum) AA A focused component is not entirely hidden by author-created content Sticky header covers keyboard focus
2.5.8 Target Size (Minimum) AA Pointer targets meet the stated size or spacing alternatives, subject to exceptions Dense icon actions become unusable

The precise limits matter. Under 1.4.4, the normative threshold is up to 200% text resizing; this criterion does not state that every page must remain identically laid out. Under 1.4.10, the width is 320 CSS pixels for vertically scrolling content; 256 CSS pixels is the corresponding height for horizontally scrolling content (such as vertically written text). These are layout sizes, not physical pixel counts or a requirement that the author simulate every device. Under 1.4.12, the standard tests compatibility with user-applied spacing—not a mandate that every page default to those spacing values. W3C's Resize Text explanation, Reflow explanation, and Text Spacing explanation elaborate the distinctions.

5. Two-Hundred-Percent Text Resizing: What Counts as Preserved Functionality

At 200% enlargement, a person should be able to read the required text and continue the task. Labels, instructions, validation messages, button text, inline help, and text inside custom components all matter. “The article paragraphs grow” is insufficient if the navigation labels remain illegible or the form's last response option becomes unreachable. A user may also resize in increments between 100% and 200%; if an intermediate state clips content, it should not be treated as irrelevant merely because the endpoint looks correct.

A common defect appears in components that combine font-relative text with fixed-height boxes. At the default size, a two-line address might fit in a height: 3rem panel; after an author changes line-height or the browser enlarges text, it needs four lines. When overflow: hidden and a fixed height remain, the continuation is gone. Prefer content-driven height, appropriate minimum height, wrapping, and padding that grows with typography. Test the actual text-bearing controls, not only generic paragraphs.

Some complex interfaces legitimately show shortened values in narrow cells, provided users can discover the full text through an accessible mechanism; the Understanding Resize Text document discusses such cases. This does not license invisible essential instructions or hover-only disclosures. A readable truncation mechanism must be discoverable, operable in the relevant input modalities, and integrated with the interaction pattern. Text embedded in rasterized imagery is inherently less adaptable than live text and should not be used as a routine substitute for labels.

6. Browser Page Zoom: Why Scaling Changes the Available Layout

When a browser zooms a page, content typically occupies more physical screen space. On many desktop browsers, this also changes the available CSS viewport width against which responsive breakpoints are evaluated. The implication is profound: a wide desktop layout can transition into a narrow stacked layout even though the window itself has not been manually resized. An engineer who tests only 400-pixel mobile simulation but never zooms the real desktop may miss platform-specific menus, dialogs, and sticky elements that fail during this transition.

The often-used reference is a page opened with a 1280-CSS-pixel-wide viewport at 100% zoom and tested at 400% zoom. Under the simplified ratio, 1280 ÷ 4 = 320 CSS pixels. Browser frame, scrollbars, display settings, and zoom implementation may make the measured size differ slightly. The point is to inspect the effective rendered viewport and the complete interaction, not to use a screenshot comparison as a substitute for criterion-based testing.

The increase from 100% to 400% does not mean WCAG 1.4.4 requires 400% text enlargement. The two criteria are separate: the larger zoom setting is a practical method of testing the narrow reflow condition; text resizing has its own 200% threshold. If a responsive breakpoint changes CSS font sizes, check that users still have an effective route to the required enlargement rather than secretly shrinking text to defeat the zoom.

7. Reflow at 320 CSS Pixels: Reading Without Paired Scrolling

For ordinary vertically scrolling content, WCAG 1.4.10 expects readers to access information and functions at a width of 320 CSS pixels without needing to scroll horizontally and vertically together to follow ordinary lines or reach most controls. Reflow may stack a three-column site into a single column, move supplemental navigation into a menu, allow labels to sit above fields, and place action buttons vertically. The intended outcome is an intelligible reading path that mostly moves in one direction.

This is not a rule against all horizontal scrolling. For example, an actual data table whose meaning depends on comparing intersecting rows and columns may require two-dimensional layout, and a horizontally scrollable region for the table can be appropriate. The exception belongs to content that needs the two-dimensional spatial relationship, not to an entire page merely because it contains a table. Surrounding headings, explanatory paragraphs, controls, legends, and task navigation should still reflow. A fixed-width marketing card with text does not become an exception by naming it a “dashboard.”

A decisive test is to read a long paragraph from beginning to end and then complete a real action. If every line requires a rightward pan and a return pan to begin the next line, the layout has not provided the intended reading access. If all the text reflows but the final action button is rendered offscreen beyond an inaccessible overflow region, the task also fails. The normative exceptions and examples are explained by W3C Understanding Reflow.

8. The 256-CSS-Pixel Height for Horizontally Scrolling Content

WCAG 1.4.10 also addresses content designed primarily to scroll horizontally, such as some forms of vertical writing. For such material, the relevant dimension is 256 CSS pixels in height. The relationship is analogous to the 320-pixel width rule but oriented around the content's natural reading direction. It would be inaccurate to claim that all webpages must fit into a 256-pixel-high screen without vertical scrolling.

The criterion recognizes that some text directions and layouts are not best understood through a default horizontal-writing, vertical-scrolling assumption. An application for Japanese vertical typography, historical documents, or certain specialized reading experiences needs to inspect how columns of text advance and whether users must make repeated movements in both directions to read each sequence. Orientation, writing mode, input methods, and browser support can alter observed behavior.

Engineering teams should test the direction the content is actually designed to scroll, then preserve a coherent progression in that direction at the relevant narrow dimension. Do not rotate or transpose the entire site simply to satisfy a numerical checklist. Horizontal-writing websites normally use the 320-CSS-pixel-width test; the alternate height threshold is relevant when the content is designed for a horizontally advancing reading sequence.

9. The Two-Dimensional-Layout Exception and Its Boundaries

Some information loses essential meaning if every component is broken into a single linear column. Spatial maps, technical diagrams, videos, presentations, games, data tables, and interfaces whose tools must stay adjacent to the material being manipulated can present legitimate cases. Their spatial layout may be an essential part of their meaning or operation. This is an exception for a portion of content that requires it, not permission for unrelated menus, instructions, or page chrome to overflow.

Treat an exception as an evidence-backed classification. Ask: What relationship is lost if the material stacks? Can a smaller alternative preserve it? Can the surrounding interface reflow while this specific region scrolls independently? A table's header-to-cell comparisons might justify a horizontally scrollable table wrapper. The page title and export button do not thereby need a 900-pixel width. A map may require a two-dimensional view for navigation, but an address, route summary, location name, and alternative instructions can still be exposed in ordinary reflowing text.

A team should also consider alternative representations even where an exception technically applies. A tabular comparison can sometimes be expressed as labeled records or an accessible drill-down without losing important relationships. Exceptions are constraints to analyze, not default architectural choices. Record the reason, region boundaries, available alternative, and evaluation evidence so later redesigns do not copy the exemption indiscriminately.

10. Responsive Design Is a Behavioral Contract, Not a Device Category

Responsive design is commonly introduced through device widths: desktop, tablet, and mobile. Accessibility requires a broader formulation. The effective available area changes because of browser zoom, sidebars, reading panes, translated copy, user font settings, and device orientation. The same screen can cross several responsive thresholds during one task. A design must therefore be responsive to available space and content needs, not to guesses about a person using a certain device.

The best responsive architecture begins with semantic content order and layouts that can shrink, wrap, or stack without deleting required information. Use CSS intrinsic sizing, flexible tracks, wrapping controls, and breakpoint changes based on component stress rather than fashion-driven screen dimensions. At any breakpoint, the user should retain access to navigation, content, error feedback, relevant contextual help, and the primary actions. A menu can be collapsed, but it must remain discoverable and keyboard-operable.

Teams often ship a visually effective mobile page that simply hides the desktop table, filters, or “advanced options.” Such a page might look narrow enough while withholding functionality from users who reached the narrow layout by zooming on desktop. Check feature parity across responsive states. An essential function should not disappear because the design assumes that people on narrow viewports only want simplified tasks. Adaptive layouts can vary in presentation; they must not silently downgrade the user's rights or capabilities.

11. Viewport Metadata and User-Controlled Magnification

The common responsive viewport declaration is:

<meta name="viewport" content="width=device-width, initial-scale=1">

It helps mobile browsers render the page using the device's CSS viewport rather than a wider default layout viewport. However, viewport metadata can also be misused to limit magnification. Directives such as user-scalable=no or restrictive maximum scale values have historically interfered with some users' ability to zoom, though modern browsers may ignore these constraints in some circumstances. Do not depend on a browser override as the accessibility solution: omit author-imposed zoom restrictions and test the actual application on representative browsers. MDN's viewport documentation explicitly warns against disabling zoom.

Native mobile apps and embedded webviews may use additional accessibility scaling facilities. A webpage cannot guarantee the behavior of every host environment, but it can avoid obstructing standard magnification and can document relevant supported platforms. Page controls labeled A+ or “large text” can be useful in specific services, yet they should complement browser preferences rather than replace the user's existing controls. A user should not have to discover a custom magnification widget before reading the site's directions.

12. Measuring CSS Pixels, Device Pixels, Zoom and Effective Space

A CSS pixel is an abstract layout unit; a device pixel is a hardware display unit. Their relationship depends on display density, device-pixel ratio, and zoom behavior. A phone with a high-density display may have thousands of hardware pixels across its panel while exposing a much smaller CSS layout width. Evaluating reflow by counting device pixels produces misleading results.

For test documentation, record viewport dimensions in CSS pixels, browser and operating system, zoom method and level, text scaling preferences, and the content state. Browser developer tools can provide a viewport readout, but simulated mobile emulation does not reproduce every aspect of pinch zoom, browser toolbar behavior, or real screen readers. Similarly, window.innerWidth and document.documentElement.clientWidth can differ because of scrollbars or the visual viewport; use a repeatable measurement method and inspect what the user actually sees.

If the team writes that “400% passed at 1280,” clarify whether 1280 was the prezoom viewport width, a physical window size, or a monitor resolution. These are not interchangeable. A useful report might state: “Desktop browser page zoom at 400%; effective layout viewport about 320 CSS pixels wide; all article text reflows; data table uses an independent scroll region; primary actions remain visible and operable.” The observed functional result is more important than the label on a screenshot.

13. Font Units: Pixels, Root Em, Element Em, and Percentages

CSS offers several ways to size type. px expresses a CSS length, rem references the root element's computed font size, em uses an element-relative measure, and % can represent an inherited proportion. Relative units are useful because typographic dimensions can remain linked, but no unit automatically guarantees accessibility. Browsers can zoom text expressed in CSS pixels, while poorly designed rem layouts can still overflow when multiple nested components grow.

:root { font-size: 100%; }          /* preserve the user's default */
body  { font-size: 1rem; line-height: 1.55; }
h1    { font-size: 2rem; line-height: 1.2; }
button, input, select, textarea { font: inherit; }
.control { padding: 0.65em 1em; min-height: 2.75rem; }

The central design rule is to preserve relationships, not to ban pixels. Borders of one CSS pixel can be appropriate; a form containing a label in a pixel-locked box with clipping is not. Root font-size resets that force a 10-pixel baseline solely to simplify arithmetic can undermine user settings. font-size: 62.5% is likewise not automatically inaccessible, but it demands care because it changes the root scaling assumption and can make defaults unexpectedly small. Avoid using viewport width alone to scale text when it results in inadequate enlargement under zoom.

Choose type sizing by readability and test the rendered results. Use relative dimensions for components that must grow with labels; use flexible width so the additional characters have room; and ensure that line-height grows without creating overlap. The acceptance criterion is that a real person can enlarge text and complete the task—not that the stylesheet contains a particular collection of favored units.

14. Fluid Type and the Limits of `clamp()`

Responsive typography may use clamp(minimum, preferred, maximum) to scale between sizes. This can improve layout harmony across wide screens, but it introduces a subtle risk: a formula based strongly on viewport width may shrink the CSS font size as browser zoom reduces the effective viewport, partially canceling the user's requested enlargement. The WCAG 1.4.4 obligation to support effective enlargement does not disappear because the type scale is “fluid.”

/* Example: readable minimum, with only a modest viewport adjustment. */
.article-heading { font-size: clamp(1.7rem, 1.5rem + 1vw, 2.4rem); }
.article-body    { font-size: 1rem; }

The example is a design starting point, not a proof of compliance. If the root size is changed in a browser or application, rem contributions may change differently from the viewport contribution. Test at 100%, 200%, and 400% browser zoom; also test text-only enlargement where available. Inspect particularly the minimum clamp bound at narrow zoomed layouts. A fixed tiny minimum may keep a heading inside one line but defeat the intent of magnification.

Line length and hierarchy should remain comprehensible. It is acceptable for a heading that occupied one line to use three lines after enlargement. It is not acceptable for the heading to overlap its paragraph, be ellipsized without an accessible way to read the full label, or occupy a fixed region that blocks the main task. Prefer a good wrapping layout to artificially restricting the requested scale.

15. Fluid Containers and Intrinsic Sizing

Layout failures often begin with rigid containers. A text card that has width: 720px on a small viewport forces the page to overflow; a content region constrained by height: 300px may conceal expanded paragraphs. A more adaptable container uses a maximum width for comfortable reading and a width limited by the available space.

.article-shell {
  inline-size: min(100% - 2rem, 72rem);
  margin-inline: auto;
}
.reading-column { max-inline-size: 68ch; }
.card { min-inline-size: 0; height: auto; padding: 1rem; }

ch can be useful when targeting a readable approximate line length, though actual line width depends on the font and language. Do not impose a minimum width that prevents narrow rendering. When an element includes padding and borders, consistent box-sizing: border-box can simplify calculations. Yet even flexible containers fail if a child has a fixed minimum, a long unbreakable string, or positioned content extending beyond the parent.

Test the entire nesting chain: viewport → main region → grid track → card → label → input → feedback. A flexible card cannot shrink below a flex item’s automatic minimum content width unless that constraint is addressed. A single problematic child can induce page-level horizontal scrolling. Debugging therefore starts with the element responsible for overflow, not a global overflow-x: hidden that may conceal useful content while leaving the defect intact.

16. Flexbox, CSS Grid, and the Invisible Minimum-Width Trap

CSS Flexbox and Grid are excellent tools for reflow, but default intrinsic sizing can surprise experienced developers. Grid tracks declared as 1fr can still be constrained by their contents; flex items can resist shrinking to a width smaller than an unbroken string. Where appropriate, use minmax(0, 1fr) and min-width: 0 or logical equivalents to permit shrinkage. This allows the text's own wrapping behavior to determine height instead of forcing the page wide.

.page-grid { display: grid; grid-template-columns: minmax(0, 1fr) 18rem; gap: 1.25rem; }
.page-grid > * { min-width: 0; }
.actions { display: flex; flex-wrap: wrap; gap: 0.75rem; }
@media (max-width: 48rem) {
  .page-grid { grid-template-columns: minmax(0, 1fr); }
}

This layout is only a partial pattern. The sidebar must remain reachable when it stacks, the actions must preserve meaningful order, and controls must have accessible names and keyboard operation. A width breakpoint expressed in rem is not a conformance guarantee by itself. Test the assembled page with long translated labels, an open validation message, and zoomed browser chrome.

A common anti-pattern is solving a flex or grid overflow by applying overflow: hidden to the body. That suppresses a visible scrollbar but may hide the final characters, menu or buttons. The correct repair removes the offending width constraint or contains a legitimate exceptional region with its own usable scrolling controls.

17. Long Words, URLs, Filenames, and Unbreakable Data

A normal sentence wraps naturally at spaces. A long URL, product identifier, file path, hash, equation token, or text in a language with different breaking conventions may not. One line containing an unbroken value can expand the minimum width of its parent and break an otherwise careful responsive design. Use suitable wrapping behavior on prose and value containers, while preserving the information itself.

.article-copy, .message, .card {
  overflow-wrap: anywhere;
}
.filename, .external-url { overflow-wrap: anywhere; }

overflow-wrap: anywhere is often useful for long tokens, but not an instruction to split all information indiscriminately. For code or structured strings where exact alignment and copyability matter, an independent scrolling container may be more usable. Manual <wbr> opportunities can help with known patterns, but content pasted by users or generated dynamically still needs resilient styling. Hyphenation may improve reading in supported languages when the correct lang attribute is supplied; automatic hyphenation should be tested rather than assumed uniform across browsers.

Never truncate essential values merely to achieve screenshot symmetry. If a transaction ID, security warning, or contact number is cut off, the user may be unable to verify or correct the action. A carefully designed details control can reveal full information, but the control itself must remain reachable and usable at high zoom.

18. White Space, Code Samples, and Preformatted Text

Preformatted text and source code are a common legitimate source of horizontal scrolling, especially in technical encyclopedias. A <pre> block may intentionally preserve indentation and line breaks. Forcing every code line to wrap can make the code hard to read or copy correctly, while allowing an oversized <pre> to expand the page can force side-to-side navigation across all surrounding prose.

.code-example {
  max-inline-size: 100%;
  overflow-x: auto;
  padding: 1rem;
}
.code-example pre { margin: 0; }

A local scroll region confines the issue to the code example. If readers need to understand the code in a single direction, provide an explanatory prose summary, split a complex example into smaller steps, or offer meaningful line wrapping when preserving long line positions is unnecessary. Use semantic code text, not screenshots of code as the primary teaching medium. A “copy code” action can help only if it is keyboard-operable, discoverable, and communicates its result.

Page-level horizontal overflow caused by one preformatted example is a containment defect. Conversely, a localized scroller does not automatically satisfy all accessibility expectations: users must be able to access its content and know what to do when the right edge is not visible. Treat the scroll region's size, focus behavior, scrollbar visibility, and keyboard operation as part of the example's accessibility.

19. Responsive Images, Diagrams, and Embedded Media

Images may be visually enlarged along with text, but they should not dictate an arbitrarily wide page. Ordinary images can often shrink within the containing column while preserving aspect ratio. Video players and embedded frames need similar limits; their controls and captions must remain operable. Fixed width attributes are not inherently wrong if CSS permits responsive rendering, but unmanaged intrinsic dimensions can overflow.

img, video { max-inline-size: 100%; block-size: auto; }
.media-frame { inline-size: 100%; aspect-ratio: 16 / 9; }
.media-frame iframe { inline-size: 100%; block-size: 100%; border: 0; }

There is a difference between fitting the media element and preserving its meaning or operation. A large scientific diagram may need a zoomable region for reading tiny annotations. A video player may technically fit at 320 CSS pixels but have inaccessible controls or caption placement. An embedded third-party widget may enforce its own min-width. A map may require two-dimensional panning, yet route directions and location names should still be exposed outside its interactive canvas where relevant.

When a meaningful diagram cannot be reduced without sacrificing detail, describe its essential takeaway and provide an accessible alternative representation. Refer to Accessible Images, Charts, and Nontext Content for equivalent information, and Captions, Transcripts, and Audio Description for media alternatives. Those are separate obligations from responsive dimensions.

20. Data Tables: Preserve Comparisons Without Making the Page Overflow

Wide tables are among the clearest cases where preserving two-dimensional relationships can matter. Users may need to compare values across columns while keeping the corresponding row labels visible. A naïve approach transforms every table cell into a stacked card, but the meaning of a time series or matrix may be lost. Another naïve approach leaves the entire site at the table's intrinsic width, imposing two-dimensional panning on every paragraph before and after it.

<div class="table-region" role="region" aria-label="Quarterly results table" tabindex="0">
  <table>
    <caption>Quarterly results, by region</caption>
    <thead><tr><th scope="col">Region</th><th scope="col">Q1</th><th scope="col">Q2</th></tr></thead>
    <tbody><tr><th scope="row">North</th><td>14</td><td>17</td></tr></tbody>
  </table>
</div>

.table-region { max-inline-size: 100%; overflow-x: auto; }
.table-region table { border-collapse: collapse; }

role="region" and tabindex="0" can make an independently scrolling region easier to access in some browser and keyboard combinations; apply those attributes deliberately and test focus behavior rather than adding them to every table reflexively. Keep captions, scoped row/column headers, and a visible indication when data extends beyond the first viewport. For simple two-column key/value tables, labeled records may be a better narrow presentation—but check that the redesigned presentation retains data association.

21. Forms: Labels, Inputs, Error Text, and Vertical Growth

Forms are a high-risk site of reflow defects because they combine dense labels, multiple fields, validation messages, helper text, indicators and action controls. A form that appears attractive at 100% zoom may fail when the user increases text: the label wraps over the next control; the error icon is positioned over the last word; or the input is too short to display a typed value. Accessible forms must accommodate both static guidance and dynamic states.

A sound narrow-layout strategy uses visible labels above their fields, full-width controls limited to their container, flexible button rows, and error text that appears in normal document flow. Do not assume a two-column label/input arrangement can be maintained at every zoom level. Avoid fixed-heights for error panels and replace decorative placeholder-only labels with persistent names. If multiple fields are conditional, test expanded states when the longest guidance is visible.

.field { display: grid; gap: 0.35rem; min-inline-size: 0; }
.field input, .field select, .field textarea { inline-size: 100%; max-inline-size: 100%; box-sizing: border-box; font: inherit; }
.form-actions { display: flex; flex-wrap: wrap; gap: 0.75rem; }
@media (max-width: 35rem) { .form-actions > * { flex: 1 1 100%; } }

An application should preserve data and validation state as the viewport changes. Reflow must not reset a multi-step application, replace the form with a different unfinished mobile flow, or hide its summary when an error is detected. Accessible Forms, Errors, and Recovery addresses the full form semantics and recovery model.

22. Dialogs, Sticky Headers, Drawers, and Overlays

Overlays often become unusable before the main page does. A modal designed with height: 600px can exceed the visible height after zoom; its confirm button may fall below a clipped footer. A fixed-position banner may cover the first form control, while a sticky navigation bar can occupy nearly the entire narrow screen. The issue is not merely appearance: these elements may remove access to required actions.

Dialog bodies should have a sensible maximum size relative to the viewport and a deliberate internal scrolling strategy when their content cannot fit. Keep a clearly labeled close action reachable, contain keyboard focus appropriately for a modal, and restore focus when the dialog closes. Be cautious with overflow: hidden on modal bodies when combined with fixed footer actions; it can conceal validation text or the last input. A dialog's own scrolling region may be needed, but the whole workflow must remain understandable.

.dialog-panel {
  inline-size: min(40rem, calc(100% - 1.5rem));
  max-block-size: calc(100dvh - 1.5rem);
  overflow-y: auto;
}

100dvh reflects the dynamic viewport in browsers that support it; account for compatibility requirements and mobile safe areas in actual implementation. A sticky header should not obscure the focused element, particularly under WCAG 2.2 Focus Not Obscured (Minimum). Check the opening, editing, error, and closing states at zoom, rather than taking a screenshot only of the empty dialog.

23. Navigation, Menus, Search, and Discoverability at High Zoom

Navigation often changes form when space becomes scarce. Desktop horizontal links become a collapsed menu; a filter sidebar becomes a drawer; account actions move beneath a button. This is a legitimate reflow adaptation when the substitute interface preserves the same essential destinations and operations. The user must know where those options moved, be able to open and close the replacement, and keep a clear focus and reading order.

A collapsed menu can fail without any horizontal overflow: its trigger may have no accessible name; the menu may open offscreen; the focus indicator may be covered; or a link visible in desktop view may be omitted entirely. At high zoom, look for controls that have become icons without text, help content that is reachable only by hover, and navigation that requires a broad pointer movement. Preserve search and filtering access, not merely the principal page links.

A table-of-contents sidebar can reflow above the article, below the article, or into a disclosure region. Evaluate whether its placement supports orientation; putting twenty navigation links before the first paragraph may be cumbersome even if technically available. User needs, actual task length, and consistent keyboard access determine the better design. See Accessible Navigation and Information Architecture for navigation ownership, and Accessible Interactive Components and ARIA Patterns for the disclosure and menu interactions.

24. Focus Visibility, Scroll Position, and Dynamic Reflow

When the interface changes size, the current focus location may move, disappear, or become hidden behind a sticky element. Users who navigate by keyboard or a screen reader may be especially affected because the pointer does not visually identify their position. A responsive breakpoint should not recreate the entire DOM unnecessarily or silently replace the focused control with a different inaccessible element.

If a button opens a dialog, focus should move into the dialog as appropriate. If the user closes the dialog at 300% zoom, focus should return to a logical visible place. When a validation error is inserted above the submit button, users should be able to locate it without having to pan through a newly overflowing region. scroll-margin-block-start can help with sticky header offsets in some layouts, but it does not excuse an overlay covering the only available content area.

Care is needed when code calls scrollIntoView(), recalculates scroll position on resize, or animates transitions. A script that repeatedly forces the viewport to the top after zoom makes a page difficult to use even if its CSS reflows. Responsive design should preserve task state, reading continuity and focus identity. The deeper keyboard mechanics belong to Keyboard Access and Focus Management, while this article tests whether scaling disrupts them.

25. User-Selected Text Spacing and Paragraph Expansion

WCAG 1.4.12 Text Spacing addresses what happens when a user overrides four presentation properties at once: line height of at least 1.5 times font size, spacing after paragraphs of at least 2 times font size, letter spacing of at least 0.12 times font size, and word spacing of at least 0.16 times font size. The requirement is no loss of content or functionality under those overrides, with language/script qualifications where properties do not apply. It is not a directive to use those values as the site's default typography.

/* Temporary audit override for relevant text containers; not a default theme. */
body, body * { line-height: 1.5 !important; letter-spacing: 0.12em !important; word-spacing: 0.16em !important; }
p { margin-bottom: 2em !important; }

This code is an illustrative audit starting point, not a canonical test stylesheet: real audits need to scope paragraph spacing, inspect mixed writing systems, and avoid accidental side effects from overly broad selectors. A text-spacing test must compare relevant states before and after the override, checking clipping, controls, menus, headings, cards, and forms. It is not enough to verify that the stylesheet is syntactically accepted.

An icon-only button may not be affected like a text label, while a badge with a fixed height might suddenly crop its words. Headings arranged on narrow cards may wrap and overlap following content. Spacing failures commonly reveal hard-coded dimensions that also harm zoom and translation. Text spacing is therefore an independent test that strengthens—but does not replace—the reflow evaluation.

26. Meaningful Sequence When Columns Collapse

As layouts change, the visual reading order should remain consistent with the intended meaning and with the programmatic document sequence. CSS Grid ordering, flex order, and absolute positioning can create a polished desktop display while leaving screen-reader and keyboard reading order in a contradictory sequence. A responsive breakpoint may restore some elements to document flow, exposing logical mistakes that were hidden by a visual grid.

For example, a two-column checkout may show shipping details on the left and a payment summary on the right. At narrow zoom, the summary could move above or below the address fields. Either arrangement may be valid, but the narrative, labels, error messages, and confirmation must make sense in the resulting progression. A product gallery with a separate buy button must not be reordered in a way that makes a visually adjacent action unrelated to its semantic label.

Begin with the meaningful DOM sequence, then use CSS to enrich layout without changing the intended order for assistive technology and keyboard interaction. When a genuinely different process sequence is required, build and test the new sequence explicitly rather than relying only on CSS visual reordering. Reflow is a semantic continuity problem as well as a dimensional one; a page can be free of horizontal scrolling yet still confuse users through displaced explanations and focus order.

27. Operating-System Text Settings and Browser Preferences

On many platforms, users can alter system text sizes, display scaling, browser default fonts, minimum text sizes, or accessibility settings. These controls do not produce identical behavior across Windows, macOS, iOS, Android, and Linux environments, and web browsers may not apply every platform preference to every CSS property in the same way. Authors should not infer that a page supports these needs merely because it passes one desktop browser zoom test.

A sensible compatibility plan includes a small set of representative browser and platform configurations. For each, open the full workflow and inspect the actual rendered text and usable controls, not only the computed style. Test browser minimum font size when supported, mobile text enlargement, and settings that affect rendering or font substitution. Large text may expose previously hidden overflow even if page zoom has already been tested; fonts with different glyph metrics may also change wrapping without any change in nominal CSS size.

The operating system is responsible for the platform controls it exposes, but the application must avoid decisions that defeat those controls. Fixed pixel-height custom buttons, absolute-positioned labels, canvas-rendered interface text without adaptable alternatives, and unscalable webviews are common risks. Native platform accessibility implementation belongs to Native Applications and Operating-System Accessibility; this article examines the resulting layout obligations of web interfaces.

28. Orientation, Split Views, Small Windows, and Foldable Screens

A user's effective viewport may become narrow because a device rotates, a browser window is snapped beside another application, a split-view reading environment opens, or a foldable device changes posture. These are normal modes of use, not exceptional test conditions. Responsive interfaces should respond to the available space instead of requiring a particular screen shape. Do not infer that landscape orientation always means more usable width: browser bars, split panes, keyboards, and zoom settings can consume substantial space.

The key audit questions are whether the content remains available, controls can be reached, and text can still be enlarged. A horizontal layout can collapse gracefully under a tall narrow pane; a sidebar can become a disclosure; a multi-column comparison can use a region-specific scroll container. Conversely, a short landscape viewport may make a fixed-height dialog unusable even though its width is adequate. Test both dimensions and the open state of overlays, keyboards, and browser toolbars.

Avoid orientation locks unless there is a defensible essential exception in the applicable requirement. A form, course article, benefits application, or commerce page generally should not force the user to rotate a device simply because the design was built for a reference mockup. Keep controls operable on touch and keyboard, and account for dynamic viewport changes rather than assuming a permanently stable browser chrome.

29. Internationalization, Translation Expansion, and Writing Systems

Languages vary in word length, script characteristics, line-breaking rules, writing direction, and typographic conventions. A label that occupies eight characters in one language may require several times the space in another. A German compound word, long Finnish inflection, localized date, Arabic mixed-direction field, or vertical Japanese text can expose a layout assumption that English-only testing did not. Text expansion testing is therefore a useful proxy for resizing robustness—but it is not a substitute for actual scaling tests.

Authors should use accurate lang attributes, allow natural text wrapping, avoid fixed-height cards, and test with real translations rather than only synthetic repeated characters. For bidirectional interfaces, logical CSS properties such as margin-inline-start, padding-inline, inline-size, and block-size can reduce direction-specific mistakes. Yet logical properties alone do not establish correct reading order or localized design. Numbers, filenames, and mixed-direction identifiers require careful examination.

A multilingual article may need language-specific hyphenation and a different typographic rhythm. The text-spacing criterion has explicit qualifications for writing systems where certain spacing properties do not apply. Engineers should consult relevant language practice before declaring a reflow failure or claiming that an override is universally appropriate. The governing aim is that language expansion, user enlargement, and reflow do not produce new information barriers.

30. Third-Party Components, Widgets, and Embedded Services

Content can reflow perfectly until a payment widget, booking calendar, authentication prompt, advertisement, video player, live chat bubble, or external chart is embedded. Such components often bring their own minimum widths, fixed positioning, font rules, or JavaScript resize assumptions. A provider might permit a responsive iframe but render a fixed-width panel inside it, creating hidden text and inaccessible controls at high zoom.

Procurement and integration teams should test these dependencies inside the real host page, not only in a vendor demo. Record the provider version, wrapper dimensions, iframe behavior, keyboard access, zoom settings, and observed failure. Some integrations can be repaired by changing host-side CSS; others require vendor fixes or an accessible alternate workflow. Do not hide the failing iframe with overflow: hidden and record the result as complete: that may remove the very payment or confirmation function the user needs.

Where an external service is essential, contractual acceptance criteria should include reflow and text resizing at the applicable test conditions. An organization can outsource software construction but cannot assume its user-facing responsibilities disappear. The broader procurement and maintenance responsibilities belong in Accessibility Governance, Procurement, and Remediation.

31. Design-System Governance and Component Acceptance

A design system can make reflow behavior predictable by standardizing content-driven component sizing, spacing tokens, responsive grid patterns, button wrapping, dialog dimensions, and long-string handling. It can also spread one defective assumption across an entire institution. A text truncation rule in a shared badge or rigid height in a common modal may affect hundreds of screens and content types.

Treat each reusable component as a contract under stress conditions. Its specification should describe how it behaves with 200% text enlargement, a 320-CSS-pixel viewport, required text-spacing overrides, long names, right-to-left content, visible error messages, and high-zoom keyboard operation. Include interactive states—open, expanded, selected, invalid, loading, and disabled where applicable—rather than approving only a blank demo component. Library changes should be regression-tested in representative production workflows.

Documentation should identify where an exceptional two-dimensional layout is genuinely necessary and where ordinary content must reflow. Developers should not have to rediscover the table-scroll policy or dialog-height calculation in each project. A component acceptance record can specify sample content, environment, known limitations, and the version in which a defect was resolved. Shared patterns provide scale only when the same evidence-based rules govern their use throughout the application.

32. Automated Inspection Versus Human Evaluation

Automated accessibility scanners can detect some fixed dimensions, missing viewport metadata, or known markup problems, but they cannot reliably determine every reflow failure. A scanner does not know whether a horizontal scroll region is a legitimate data table exception, whether a confirmation button remains reachable, or whether a user has lost a meaningful comparison after a responsive transformation. Visual snapshots and DOM assertions can help, but they require human interpretation.

A serious review combines several methods: viewport and zoom experiments, text-only enlargement, user-style text-spacing overrides, keyboard task testing, content stress tests, cross-browser checks, and observation of affected users where appropriate. Automated screenshot differences can identify areas to inspect; they are not proof that every pixel change is bad. Some changes—extra line breaks, taller buttons, stacked sidebars—are signs of correct adaptation.

Failure reporting should be specific: identify the page and state, zoom mechanism, viewport, browser, exact lost content or function, reproduction steps, severity, and expected outcome. The defect may arise from a single child element, a global style, or a third-party iframe. In every case, establish what the user could not do, then repair the layout and retest the entire task. A “passed automated audit” badge never replaces this behavioral evidence.

34. Ten-Step Reflow and Text-Resizing Evaluation Framework

  1. Select a meaningful task. Identify the pages, controls, conditional states, content, and successful completion evidence; do not evaluate only a static landing page.
  2. Establish the baseline. Record browser, operating system, effective CSS viewport, default zoom, content language, and starting task state.
  3. Increase text to 200%. Use a supported mechanism and inspect intermediate increments for clipping, overlapping labels, and lost functionality.
  4. Increase page zoom. Observe responsive transitions toward the narrow viewport, noting effective CSS dimensions and control movements.
  5. Evaluate 320-pixel reflow. Read ordinary paragraphs and perform actions without page-level two-dimensional navigation, checking any documented exception separately.
  6. Apply text-spacing overrides. Check labels, headings, cards, buttons, errors, dynamic content, and the complete process under the four test settings.
  7. Stress content. Add long words, localized labels, user-entered values, expanded descriptions, and alternate media states.
  8. Exercise interaction. Use keyboard navigation, open dialogs, trigger errors, scroll nested regions, and verify visible focus and continuity.
  9. Trace the root cause and repair. Find rigid widths, intrinsic sizing constraints, overlays, unsuitable scroll wrappers, or third-party limitations; avoid hiding the symptom.
  10. Document and regress. Capture evidence of the repaired task, affected components, versions, remaining limits, and checks required at later releases.

The framework is intended to be repeated on representative workflows: reading, searching, completing a form, reviewing a comparison, making a decision, and confirming its outcome. An isolated layout pass at one viewport is not a reliable proxy for a full task's accessibility. Where failures interact, correct the shared component or layout architecture before patching dozens of downstream screens individually.

35. Eight Worked Cases: Diagnosis, Repair, and Verification

The following cases are constructed instructional scenarios, not claims about specific organizations or measured public incidents. Each demonstrates a different failure mode and the evidence needed to verify a repair.

Case 1 — A course article overflows at 400% zoom

A university article has paragraphs in a fixed min-width: 60rem content panel. At 100% zoom, the text appears comfortably centered. At an effective viewport of approximately 320 CSS pixels, each sentence requires repeated left-and-right panning. The failure is page-level width, not a problem with the user’s zoom choice. Repair by replacing the rigid minimum with flexible width, ensuring nested grid tracks can shrink, and letting paragraphs wrap naturally. Verification: read a complete chapter and follow its internal links at high zoom without horizontal panning for normal prose; confirm that long filenames are handled within their own elements.

Case 2 — A payment form clips enlarged field labels

A checkout puts labels and inputs in 50-pixel-high rows. At 200% text scaling, a translated “Billing address line two” label wraps onto three lines, covering the input below. The developer attempts to fix the screenshot by reducing label font size, which undermines enlargement. Instead, let rows grow with content, stack label above control, preserve the accessible field name, and show validation text in document flow. Verification: enter payment information, trigger and correct an error, then complete checkout with the enlarged labels visible throughout.

Case 3 — A sticky navigation bar hides keyboard focus

A news website collapses its sidebar at high zoom but retains a 140-pixel fixed header. When keyboard focus reaches a link near the top of a section, the header entirely obscures it. The text otherwise reflows, yet the task remains inaccessible. Repair by reducing sticky chrome when space is limited, adjusting scroll positioning, or allowing the header to leave the viewport. Verification: navigate by Tab and section links with the browser zoomed; each focused control remains at least partially visible and recognizable.

Case 4 — A data table forces the entire page to scroll horizontally

A financial report contains a twelve-column comparative table. The table's intrinsic width expands the parent document, so even surrounding headings and the explanatory prose need lateral scrolling. The table may reasonably retain its two-dimensional layout; the whole page may not. Place the table in a bounded, usable horizontal scrolling region with a caption and row/column associations, while normal prose reflows. Verification: read the explanation without panning; inspect all table cells through its local scroll controls; return to the next paragraph without losing position.

Case 5 — A modal dialog's action buttons fall offscreen

A government application opens a confirmation dialog with a fixed height: 700px. At high zoom, the dialog extends below the visible area, while document scrolling is disabled. The confirm and cancel actions cannot be reached. Repair the dialog's viewport-relative maximum height, internal scrolling and focus behavior, and ensure action placement remains reachable. Verification: review every confirmation detail, navigate to each control using keyboard, make a selection, and return to the originating task without needing to reset zoom.

Case 6 — A chart legend collapses into ambiguous icon fragments

An operations dashboard positions status labels with absolute offsets around a chart. After text spacing overrides, labels overlap and are truncated; color alone identifies series. A reasonable repair uses live labels in a flexible legend, allows wrapping, and adds an accessible structured representation of the chart's meaning. Verification: apply the text-spacing settings and compare chart labels, legend, and accessible data summary; confirm that no series identity depends solely on color or a cropped label.

Case 7 — A translated navigation menu loses destinations

An international service translates short English menu items into longer phrases. At a medium zoom breakpoint, the code hides items after the sixth link rather than moving them into a usable overflow menu. The last navigation destination becomes unavailable. Repair by wrapping controls or placing all destinations into a tested disclosure with a clear name and focus management. Verification: count equivalent destinations across locales and responsive states; navigate to the formerly hidden page by keyboard and touch.

Case 8 — A third-party authentication widget rejects narrow width

An organization integrates an authentication provider whose iframe assumes a 480-pixel minimum width. The host page reflows, but the sign-in button and recovery link disappear beyond the clipped frame. Repair requires a provider-supported responsive configuration or a viable alternative sign-in route, not merely cropping the iframe. Verification: authenticate, recover from an incorrect password, use the alternate recovery path, and complete the original task at the narrow viewport. Record the vendor version so a later update can be re-evaluated.

36. Implementation Pattern Library: Resilient Layout Without Concealment

Good zoom and reflow behavior is often produced by a small number of carefully applied layout techniques rather than by a massive collection of zoom-specific styles. The following bounded examples illustrate those techniques. They do not replace semantic HTML, working focus handling, browser evaluation, or product-specific accessibility requirements.

Pattern A — A flexible reading layout with a sidebar. The main region is allowed to shrink; the sidebar stacks when there is insufficient room. The DOM order must make sense when the tracks become one column.

.layout {
  display: grid;
  grid-template-columns: minmax(0, 1fr) minmax(12rem, 18rem);
  gap: 1.25rem;
}
.layout > * { min-inline-size: 0; }
@media (max-width: 45rem) {
  .layout { grid-template-columns: minmax(0, 1fr); }
}

Pattern B — A responsive group of cards. Tracks adapt without the author assuming exactly three devices. Note that a minmax() minimum still needs to be appropriate for a very narrow viewport; clamp the effective minimum if necessary.

.card-list {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(min(100%, 15rem), 1fr));
  gap: 1rem;
}
.card-list > * { min-inline-size: 0; block-size: auto; }

Pattern C — A resilient button row. Actions do not overlap when labels enlarge or translate. At narrow widths, controls receive a complete row so their names remain visible.

.actions { display: flex; flex-wrap: wrap; gap: .75rem; }
.actions button { font: inherit; max-inline-size: 100%; white-space: normal; }
@media (max-width: 30rem) { .actions > * { flex-basis: 100%; } }

Pattern D — A responsibly bounded exceptional scroll region. A large matrix stays in its own horizontal scroller while surrounding text remains within the page. Use a meaningful label and test keyboard access when the region needs focus.

.matrix-scroll { max-inline-size: 100%; overflow-x: auto; }
.matrix-scroll table { border-collapse: collapse; }
.page-content { min-inline-size: 0; }

Pattern E — A zoom-friendly long-value field. The value wraps instead of forcing a viewport-wide track. Preserve exact copyability for identifiers and consider a copy control when the value is operationally important.

.long-value {
  overflow-wrap: anywhere;
  max-inline-size: 100%;
  font-family: ui-monospace, monospace;
}

No pattern should be “validated” only through static code reading. A dialog, table, or card can use these rules and still fail when it contains nested fixed widths, translated labels, an iframe, or a script that repositions controls after every resize. Always test the actual assembled component states.

The repair column must be interpreted in context. For example, adding an independent horizontal scroller is appropriate for a matrix that needs spatial comparison, but not a universal fix for paragraphs. Using overflow-x: hidden as a blanket remedy can suppress visible evidence of the defect while removing access to clipped content. A correct remediation eliminates the user barrier, not just a scrollbar in a screenshot.

38. Acceptance Criteria, Evidence Records, and Release Gates

A reusable acceptance criterion describes an observable outcome, a representative environment, and the task state that must succeed. “Make the page responsive” is insufficiently specific; “At an effective viewport width of 320 CSS pixels, the enrollment form's instructions, fields, validation messages, and submission action remain available without page-level two-dimensional scrolling” can be verified. Likewise, “Text can reach 200% using a supported browser mechanism without clipping labels or preventing task completion” is a stronger requirement than “Support large fonts.”

For component acceptance, record the source commit or release version, relevant page route, interaction state, browser and OS, scaling mechanism, effective viewport, test steps, observed result, and defect reference where needed. A screenshot can be supporting evidence but must not be the only result for an interactive state. If a content region claims an exception, document exactly why its two-dimensional relationships are essential and how surrounding content remains accessible.

Define release gates for critical workflows such as authentication, payment, account recovery, application submission, educational assessment, and emergency information. A design-system update to modal behavior should trigger renewed tests in those flows. Accessibility conformance and actual user success are complementary forms of evidence: standards review establishes defined technical requirements, while user-centered evaluation reveals friction not always captured by individual criteria. Neither should be represented as an automatic guarantee of the other.

40. Study Questions and Applied Exercises

  1. Explain why a page can pass a narrow smartphone screenshot review but fail reflow when zoomed on a desktop browser. What additional environment details would you record?
  2. Distinguish the 200% text resizing threshold from the 320-CSS-pixel reflow condition. Why is the common “400% zoom” comparison useful but not identical to the resize-text requirement?
  3. A page uses overflow-x: hidden to remove a scrollbar. A confirmation button remains offscreen. Diagnose why the change is not an accessibility repair.
  4. Build a two-column form with labels and inputs, then test long localized labels and increased text spacing. Revise the layout so each field remains understandable and operable.
  5. Construct a page with a wide data table and long explanatory paragraphs. Constrain horizontal scrolling to the table while maintaining its meaningful row/column relationships.
  6. Compare text-only enlargement with full-page zoom in a supported browser. Record differences in label wrapping, icon scale, header height, and dialog controls.
  7. Apply the four WCAG 1.4.12 spacing overrides to a component library page. Identify every element that clips, overlaps, or hides content, and determine the shared root causes.
  8. Create a reproducible acceptance test for a large-screen checkout flow that must work when the browser's effective width reaches about 320 CSS pixels.
  9. Examine an embedded calendar or authentication iframe. Determine whether failure originates in the host's wrapper, the embedded document, or their interaction.
  10. Explain the accessibility consequences of reordering a checkout summary with CSS order while the DOM and focus sequence remain unchanged.
  11. Design a failure record for a high-zoom dialog with a hidden action button; include the user task, environment, observed result, severity, and repair evidence.
  12. Compare two repairs for long filenames: arbitrary wrapping and a locally scrollable code-style region. Which is more appropriate for a prose link, and which might be better for a space-sensitive terminal command?

Capstone assignment. Select a realistic article or service workflow with navigation, a form, a dialog, and a table or media component. Produce a short requirements register, test it under 200% text enlargement, a 320-CSS-pixel reflow state, and text-spacing overrides; identify any exception and document why it is legitimate. Deliver a revised design, test evidence, and a concise statement of remaining limitations. Do not claim a general WCAG conformance result from these limited tests alone.
