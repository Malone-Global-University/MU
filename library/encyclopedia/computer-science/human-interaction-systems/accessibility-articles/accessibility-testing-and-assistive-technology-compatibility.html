1. Definition, Scope, and Governing Question

Accessibility testing and assistive-technology compatibility is the disciplined investigation of whether people with varied sensory, motor, cognitive, and communication needs can perceive, understand, navigate, and complete the intended tasks of a digital product. A credible evaluation joins standards-based conformance tests, inspection of rendered interface structure, keyboard and alternative-input trials, assistive-technology interoperability checks, and observation of real task performance. It records both what was demonstrated and what remains untested.

The governing question is not “Did an accessibility scanner report zero issues?” It is “Can the product's essential content and interactions be used, through the access paths people rely on, and what reproducible evidence supports that conclusion?” A screen reader announcing a button is insufficient if activation never opens the corresponding view. Likewise, a component that works with the evaluator's screen reader may fail with a different browser or accessibility API. The evaluator must distinguish incorrect author code, platform support gaps, configuration errors, and unmet user needs.

This article owns the evaluation method and interoperability evidence, not the design of every individual component. It complements Accessibility Standards and Conformance, which interprets requirements, and the subsequent Accessibility Governance, Procurement, and Remediation, which assigns organizational ownership and release policy. Examples illustrate evaluation methods; they do not certify a live MGU page or any named product.

2. Four Levels of Accessibility Evidence

Testing produces different kinds of evidence, which must not be collapsed into a single score. Structural evidence concerns machine-readable semantics: heading hierarchy, accessible names, roles, states, relationships, and content order. Operational evidence concerns keyboard, pointer, voice, switch, and focus behavior throughout tasks. Interoperability evidence establishes how a defined browser, operating system, and assistive-technology combination interprets and operates the product. Experiential evidence concerns whether people using their own strategies can understand and finish the task without disproportionate effort or avoidable harm.

A structurally correct modal dialog might still trap focus after dismissal. A keyboard-completable checkout might announce shipping methods ambiguously in a screen reader. A screen-reader test might pass while voice-control software cannot identify unlabeled icon buttons. A standards conformance evaluation might identify no testable failure for a confusing information architecture that participants nevertheless struggle to use. Each result is useful, but each answers a different question.

Evidence layer Typical method What it supports What it cannot establish alone
Structure DOM and accessibility-tree inspection Roles, labels, relationships, exposure Successful operation
Operation Keyboard and alternative-input script Task action and recovery Every AT/browser pairing
Interoperability AT and browser matrix Behavior in named environments Unseen platform versions
Experience Moderated user tasks Usability and practical barriers Exhaustive WCAG conformance

A defensible acceptance decision identifies the necessary evidence at each layer, together with failures, exceptions, and a repeatable retest strategy. An aggregate "accessibility percentage" cannot represent these distinctions.

3. The Standards Baseline: Requirements Versus Techniques

For web content, WCAG 2.2 is a W3C Recommendation with testable success criteria organized under Perceivable, Operable, Understandable, and Robust. At a specified conformance level, an evaluator checks applicable success criteria and the five formal conformance requirements, including full pages, complete processes, accessibility-supported use of technologies, and non-interference. A report must state the exact guideline version and target level; "WCAG compliant" without scope and version is inadequately precise.

Understanding documents and Techniques are important explanations and examples, not additional mandatory success criteria. A successful technique can help substantiate a requirement, but authors may use other approaches that satisfy the same normative criterion. An ACT test rule is also not the success criterion itself. Conversely, the absence of a tool failure does not demonstrate that every criterion is satisfied. A useful test plan maps each requirement to methods capable of observing it, including manual judgment where necessary.

The evaluator should also distinguish a baseline requirement from broader inclusive-design objectives. Plain-language assistance, clear task orientation, efficient keyboard paths, and alternate representations may provide substantial benefit beyond a narrow checklist. Record their findings as usability or inclusive-design recommendations when they are not failures of a particular criterion; do not relabel them as mandatory WCAG defects. For digital documents and native applications, other standards, procurement frameworks, and informative mappings may be relevant; the web conformance model should not simply be declared applicable without considering product scope.

4. WCAG-EM 2.0: An Evaluation Method, Not a New Conformance Standard

On July 23, 2026, W3C published WCAG Evaluation Methodology 2.0 as a W3C Group Note. It provides a systematic method for evaluating digital products against WCAG 2. It is informative guidance; it does not replace the WCAG Recommendation or establish a separate conformance level. The five broad stages are: define the evaluation scope; explore the target product; select a representative sample set; evaluate that set; and report findings. Evaluators revisit earlier stages when exploration reveals new templates, technologies, workflows, or barriers.

Its 2026 revision is especially useful because a product is not always a set of static HTML pages. It may include stateful views, transactions, external identity steps, user-generated content, and responsive variants. Sampling and scope definitions must account for that diversity. The method also makes evaluators state an accessibility support baseline rather than assuming that a technology is interoperable merely because an API exists.

A key methodological detail is deliberate sampling. The 2.0 Group Note describes structured coverage plus a random sample set normally equal to 10% of the structured set, when additional distinct samples are available, and inclusion of complete processes. Do not present this as "test any ten pages" or a universal sample-size rule. The number and character of samples depend on product diversity and the methodology's detailed requirements. An evaluation that tests only a beautiful homepage while ignoring checkout, account recovery, or assessment submissions does not become representative through a standards citation.

5. Define the Product and Evaluation Boundary

Before opening a scanner, write a scope statement identifying the product name, release or commit, included environments, public versus authenticated areas, languages, desktop and mobile states, key services, embedded content, and known dependencies. Include concrete routes and workflows rather than relying only on organizational department names. A single university service might encompass the informational website, course catalog, learning platform, login provider, assignment editor, payment flow, PDF documents, and media player; leaving the transitions undefined conceals barriers at the boundaries.

Choose the conformance target with the relevant commissioner and state what is and is not covered. Define the technology and accessibility-support baseline: for example, a named browser version with NVDA on Windows, Safari with VoiceOver on macOS, and a supported mobile configuration. These are test environments, not promises that all other combinations fail. Document third-party widgets, federated authentication, and dependencies that fall within the user's process even when operated by another supplier. Ownership disputes should not erase the user's barrier from the result.

A concise scope record can be reviewed by product owners and testers:

Field Example of useful specificity
Product build 2026.11 release and repository commit
Included tasks Search course, enroll, pay, view receipt
Content variants English, Spanish, mobile layout, captions
Target WCAG 2.2 Level AA for specified web views
Environment baseline Named OS/browser/AT combinations and versions
Exclusions Explicitly listed with rationale and user impact
Evidence date Calendar date, reviewer and test environment

An exclusion is an evaluation boundary, not proof of accessibility or a waiver of applicable legal responsibility.

6. Discover Common Views, Essential Tasks, and Rare States

The discovery phase inventories templates, content types, role-specific views, dialogs, forms, search results, filters, media, documents, embedded third-party components, interactive diagrams, and error or empty states. Identify the work that makes the product useful. In a library catalog, an essential task may involve finding a title, filtering, opening a record, and requesting an item; inspecting the title page alone is inadequate. In a benefits portal, submission and correction must both be inspected.

Include exceptional states because accessibility failures often appear after the happy path: a missing field exposes a new message; a timed session expires; a form redirects to identity verification; a chart shows no data; a dialog closes while focus disappears; a voice-control user receives a different label after localization. Ask engineers for state inventories and test fixtures, then verify which states are actually reachable through the user interface. An inaccessible warning that never appears in a default scan can still block an essential process.

Discovery also reveals shared components. One faulty design-system combobox may appear in dozens of routes. Sample enough instances to evaluate common implementation and meaningful variations, but do not assume that fixing the component automatically corrects every integration. Context can change accessible names, error messaging, and keyboard expectations. Maintain links between a reusable component issue and affected product views so the engineering repair can be efficient without losing evidence of impacted tasks.

7. Representative Sampling and Complete Processes

Select samples deliberately across common layouts, roles, content types, interface technologies, critical transactions, responsive views, and sources of content. Include pages using shared templates as well as exceptional pages that introduce new semantics or interaction patterns. A representative inventory should include data tables, complex forms, overlays, navigation components, and media if they appear anywhere in the scope. Randomly selected additional samples provide a check against the evaluator's tendency to choose familiar or polished pages.

Under WCAG-EM 2.0, complete processes must be included when a selected sample is part of one. If a person begins enrollment in a course, proceeds through several forms, confirms payment, and retrieves a receipt, a representative conformance evaluation cannot test only the course-selection screen. The experience may fail on the final confirmation step even when preceding views are accessible. Track the full sequence, role, data fixture, and expected terminal state.

Selection concern Example Reason for inclusion
Common view Global site navigation Appears across many pages
Essential process Registration and confirmation Failure blocks primary service
Exceptional state Expired session Recovery often loses context
Technology variant Embedded interactive chart Different rendering and semantics
Random sample Unplanned article page Tests representativeness
Role variant Instructor grading page Unique permissions and controls

Report exactly what sampling establishes. It supports a structured judgment about the sampled product; it is not a mathematical guarantee that every uninspected permutation is defect-free.

8. Test States, Accounts, Data, and Reproducible Fixtures

A test plan needs reliable preconditions. Create controlled accounts representing relevant roles and permission levels, synthetic records that trigger validation, realistic long and multilingual labels, large datasets, and an environment where confirmations and failures can be reached safely. Never make a test depend on sending real money, disclosing private records, or altering live participant accounts. Store necessary credentials in approved secure systems, not screenshots or published defect reports.

Define state transitions explicitly. For a payment form, testers may need a complete route to invalid input, corrected input, review, confirmation, back navigation, and interruption recovery. For an accessible editor, create content that includes headings, lists, links, a data table, and a complex image. For live dashboards, provide a fixture that announces an update, stops updates, and reports a stale connection. Without fixtures, testers may report "not tested" because they could not reach the behavior; worse, they may falsely mark it as passed.

Write versioned scripts that identify input data by safe labels and describe expected outcomes without assuming a specific screen reader's exact wording. For instance, "the required state and field name are conveyed" is more durable than "NVDA says these exact eight words." Retain build numbers, viewports, OS versions, and relevant browser extensions in the test record. Reproducibility is essential when a failure appears only in a particular rendering engine or assistive-technology release.

9. Build a Test Environment Matrix

A useful interoperability matrix is risk-based and explicit. Identify what users actually rely upon, support policies for target operating systems and browsers, relevant assistive technologies, regional and language needs, and the application's deployment constraints. Include both browser + operating system + assistive technology and input method + device context, since a screen reader does not substitute for voice-control or switch testing. Record exact versions and the date rather than stating only "Windows" or "VoiceOver."

A baseline may include NVDA with Firefox and Chrome on Windows; JAWS with a supported Windows browser; VoiceOver with Safari on macOS and iOS; TalkBack with Chrome on Android; and separate magnification, keyboard, switch, and voice-control configurations. This is a sample, not a universal required list. Real service populations, institutional support commitments, and observed usage should drive actual selection. A low-volume configuration may nevertheless be critical if it is the only viable path for a group of users.

When a compatibility problem is reported, first reproduce it in the original combination, then compare a second one to distinguish implementation from platform effects. A second combination passing does not negate the first user's barrier. A workaround that changes markup specifically to satisfy one version must be checked for regressions in more modern platforms. Version drift makes the matrix a maintained evidence artifact, not a once-for-all certification.

10. Define Test Oracles and Result Categories

A test oracle states the outcome expected when a behavior is correct. For accessibility, good oracles combine semantic, operational, and user-centered observations. For a disclosure button, the oracle might require a meaningful accessible name, synchronized expanded state, keyboard activation, focus remaining on the trigger, and newly exposed content being reachable. A single property such as aria-expanded="true" cannot establish all of these conditions.

Distinguish pass, fail, not applicable, not tested, and inconclusive. A scanner returning no finding does not convert a manually evaluated criterion to pass. A third-party login that cannot be tested in staging is not automatically conforming; document it as untested, together with its user impact and follow-up owner. If a browser crashes or the test harness cannot reach a state, the appropriate result is inconclusive rather than a speculative failure or success.

For subjective judgments, predefine evidence: "instructions identify the required format and an error tells the user how to correct it" is more repeatable than "form is easy." When multiple evaluators disagree, preserve observations and discuss the relevant normative text, not just the tool's severity label. Reviewers can use a shared rubric, matched examples, and double-checking on a subset of cases to reduce inconsistency. The ability to reproduce a finding matters more than a universal-looking score.

11. Automated Static Checks: Fast, Useful, Incomplete

Automated checks detect many mechanically observable problems: some missing form labels, absent image alternatives, invalid ARIA attributes, duplicate IDs, and certain color-contrast combinations. They scale across large sites and can be integrated with editor tooling, build pipelines, and continuous integration. Their greatest value is catching repeated or newly introduced errors early, not replacing human evaluation.

Automated tools generally cannot determine whether an image alternative actually conveys the intended information, whether a dialog returns focus correctly in every route, whether a chart is understandable without vision, whether a voice-command user can find an actionable control, or whether a transaction offers meaningful error recovery. Even a rule that reports "pass" may mean only that the specific rule's conditions were satisfied. W3C's evaluation-tool selection guidance explicitly cautions that human judgment remains necessary and tool outcomes can mislead.

A sound automated workflow stores tool name and version, rule set, page or component, state, viewport, and violation details. It handles warnings separately from confirmed failures, minimizes duplicate findings, and retains enough context to reproduce the DOM state. Do not delete manual findings because a later scan reports clean. Conversely, confirm suspicious automated results before escalating them as real user barriers; overlay interference or hidden test fixtures can generate false positives. The tool is a screening instrument, not a certificate.

12. Dynamic Scanning and State-Coverage Gaps

A scanner sees the rendered state that exists when it runs. Single-page applications, modals, expandable groups, autocomplete lists, validation summaries, and asynchronous results may expose defects only after interaction. If the harness visits the initial route and immediately scans, it misses those conditions. A comprehensive test route explicitly opens each critical state, waits for the relevant content, and checks the resulting DOM while retaining an independent manual interaction test.

A practical sequence is: reset the fixture, navigate, confirm the intended view, open the component, trigger one valid and one invalid action, run an automated check for each materially different state, and capture the relevant accessible name, role, status, focus destination, and screenshot. Revisit after the fix to ensure the runtime behavior persists. A hidden panel can be semantically correct while closed and defective after opening; only stateful testing detects the latter.

// Illustrative browser-test pseudocode; adapt selectors and APIs to the actual tool.
await page.goto('/apply');
await page.getByRole('button', { name: 'Continue' }).click();
await expect(page.getByRole('alert')).toContainText('required');
await runAccessibilityRules(page); // Only checks the currently rendered state.

This example demonstrates a testing pattern, not a complete conformance test. The result needs follow-up for keyboard flow, announcement behavior, correctness of the message, and recoverability without losing entered data. The same principle applies to a search overlay, a live chart, or a mobile navigation drawer.

13. ACT Rules and Consistency Between Evaluation Tools

The Accessibility Conformance Testing (ACT) Rules Format 1.1 became a W3C Recommendation in February 2026. It defines a formal way to describe test rules so tools and methodologies can evaluate conditions consistently. ACT Rules can help align checks of the same condition across tools; the standard is a format for writing rules, not a statement that every accessibility requirement is machine-testable.

Individual ACT rules vary in status, applicability, and implementation coverage. The formally published W3C ACT Rules list and community-developed candidate rules should not be treated as identical governance categories. A single success criterion may need several rules and additional human judgment. A tool may implement a subset, adapt implementation details, or produce outcomes that require interpretation. Review the rule's applicability, expectations, assumptions, and mapping before trusting the result.

Claim heard in practice Correct evaluation interpretation
"This tool supports ACT" Ask which rules and which versions
"The rule passed" A particular condition passed in tested content
"No ACT failures" Uncovered or inapplicable criteria still need evaluation
"Two tools disagree" Inspect applicability, implementation, and tested state
"ACT is WCAG" ACT is test-rule infrastructure, not WCAG's normative requirements

Treat rules as traceable evidence. Link a reported result to its tested element, rule identifier, tested state, and applicable WCAG criterion where appropriate.

14. DOM and Accessibility-Tree Inspection

The DOM describes document structure and runtime changes, while the accessibility tree exposes the user-agent representation that assistive technologies consume through platform accessibility APIs. These structures overlap but are not identical. Elements may be omitted, flattened, renamed, reinterpreted, or combined. The evaluator should inspect the resulting name, role, state, value, relationships, and whether an element is actually reachable through the intended interaction.

Use browser accessibility inspection alongside, not instead of, an assistive technology. An inspector may show that a dialog has the role dialog and an accessible name; only operational testing can show whether focus enters it, background controls become unavailable as intended, Escape works when appropriate, and focus returns to a meaningful element. Likewise, a button may have the correct computed name while a voice-control user cannot target it because the visible label and accessible name do not align.

<button id="details-toggle" type="button"
        aria-expanded="false" aria-controls="details-panel">
  Show shipping details
</button>
<section id="details-panel" hidden>
  <h2>Shipping details</h2>
  <p>Rates appear here after the user opens the section.</p>
</section>

This markup is structural only: it needs event handling to update hidden and aria-expanded together. A test should verify the closed state, activation by keyboard and pointer, correct state change, reachable content, and reversible dismissal. Merely finding the right attributes in source code is not sufficient.

15. Keyboard-Only Evaluation

Keyboard testing begins with the keyboard alone, without a mouse or screen reader, because those other technologies may mask operational defects. Use Tab and Shift+Tab to traverse sequential focus, Enter and Space to activate controls as appropriate, arrow keys for applicable composite widgets, and Escape where a component's documented pattern supports it. Observe whether focus is visible, whether content is reachable without hidden traps, and whether the order follows the task's meaning.

Write a complete task, not a generic instruction to "tab through the page." For example, open the course selector, choose an option, enter required details, correct an error, move to the review screen, and return without data loss. Check both backward and forward navigation. For a drag-oriented reorder tool, verify the promised non-dragging mechanism. For an automatic carousel, verify pause and movement controls, not merely the fact that keyboard focus lands on a slide indicator.

Some interfaces use a single Tab stop for a composite widget and arrow keys internally; this is not necessarily a problem. A radio group, tablist, grid, or tree may have its own keyboard convention. Evaluate against appropriate ARIA Authoring Practices Guide patterns where applicable, while remembering the guide's examples are guidance requiring real interoperability testing. Record the exact sequence and its expected result. Keyboard success does not establish screen-reader, speech-input, or switch compatibility, but keyboard failure is a strong diagnostic signal.

16. Focus Order, Dialogs, and State Transitions

Focus management is a common source of defects in otherwise well-marked interfaces. When a dialog opens, keyboard focus should move to a meaningful destination inside it, with a focus strategy appropriate to its content and the dialog pattern. If the dialog is modal, interaction should not escape into background controls. When it closes, focus should return to the invoking control or another logical point when the invoking element no longer exists. Verify that the returned element is visible and actionable, not merely that document.activeElement is non-null.

For route changes in a single-page application, test the transition from a known control to a new view: What tells screen-reader users that navigation happened? Where does focus land? Does the new page title, heading, or status provide orientation? Does the browser Back action restore a reasonable location? A static audit of both route documents may miss a transition where focus remains on an element that is removed without announcing the new content.

Capture failures as step sequences such as "open filter dialog; choose criterion; submit; dialog closes; press Tab; no visible focus until the footer." The sequence makes the symptom and context explicit. It also allows a developer to compare the DOM, accessibility tree, scroll position, and event timing at the failure. Do not patch focus by inserting arbitrary positive tabindex values; first correct semantic structure and application state flow.

17. Names, Roles, States, and Relationships

For each interactive control, confirm that the accessible name identifies its function, the role matches the intended interaction, and state or value changes are exposed. Examples include checked for a checkbox, expanded for a disclosure, selected for a tab, and invalid for a field after validation. Relationships such as aria-describedby should point to relevant, available descriptions. Do not infer a correct announcement solely from markup: the browser and assistive technology must communicate the information in a usable way.

Inspect ordinary states and exceptional ones. A button whose visible label changes to "Stop recording" should not retain an accessible name of "Start recording." A progress control that moves from 20% to 60% should expose an intelligible new value. A table with complex headers must preserve meaningful relationships, not just style each cell with bold text. Dynamic lists may expose the correct count but omit important changes in item status.

Test using the native HTML control first as a comparison when investigating custom widgets. A customized checkbox built from div elements may demand code for click, Space, focus, semantics, and state synchronization, all of which come automatically with a well-used native checkbox. If a custom implementation is necessary, document the full interaction contract. A passed role check cannot compensate for a missing keyboard behavior or broken state model.

18. Visual Presentation and Color Testing

Visual accessibility assessment covers text contrast, nontext contrast, focus appearance, layout stability, resize behavior, clarity of labels, use of color, and spatial organization. A scanner may catch certain static color combinations, but an evaluator still needs to inspect focus and hover states, gradients, overlays, text drawn on images, disabled controls when relevant, forced-colors behavior, dark themes, and states changed by validation. The measurement must use actual foreground and background colors at the rendered element.

WCAG 2.2 distinguishes ordinary text contrast under 1.4.3, contrast of certain graphical and control information under 1.4.11, and separate focus-related criteria. Do not apply the 4.5:1 ordinary-text threshold indiscriminately to all interface graphics or conflate the target's size with its contrast. For complex charts, check whether meaning is conveyed by shape, label, pattern, or text as well as color. A graph may pass basic color contrast yet remain unusable if two categories are distinguished only by red and green.

Use screenshot comparisons at representative widths and zoom levels, and inspect actual content rather than only a design-system demo. Ask whether an error remains distinguishable if color differences disappear, whether the active focus ring stands out against adjacent colors, and whether zoom causes content to overlap. Visual methods support, but do not replace, nonvisual access evaluation. A strong result tests alternative representations and semantic meaning together.

19. Text Resizing, Zoom, Reflow, and Magnification

Test at browser zoom and text-only resizing separately because they can change layout through different mechanisms. WCAG 2.2's 1.4.4 Resize Text concerns resizing text without loss of content or functionality under its defined conditions; 1.4.10 Reflow concerns presentation at a constrained effective viewport with stated exceptions. Reflow tests commonly use a 320 CSS pixel wide viewport for vertically scrolling content and the equivalent threshold in the other dimension for horizontally scrolling content. Do not equate an emulator's physical pixels with CSS pixels or assume that a screenshot alone proves keyboard operation at the altered scale.

Walk essential tasks at enlarged settings: read instructions, locate help, enter data, open error details, follow breadcrumbs, and submit. Check for invisible scroll containers, horizontally clipped dialogs, overlapping sticky headers, controls that shrink out of view, and content that requires two-dimensional scrolling without a legitimate exception. Browser zoom also changes available viewport space; compare actual positions, not just computed font sizes.

Magnification users may navigate only a small visible region at once. Evaluate whether focus moves predictably, whether the active input stays in view, and whether a modal dialog opens outside the magnified region. On desktop, use an appropriate magnifier and confirm whether pointers, carets, and focus remain trackable. Record zoom level, window dimensions, OS scaling, and whether the tested issue appears at a smaller or larger scale. An interface can satisfy a static responsive screenshot while placing critical guidance far from the editing point, making the actual task exhausting.

20. Understanding, Predictability, and Cognitive Testing

Accessibility evaluation must also investigate understanding and memory burdens. Test whether labels, instructions, error messages, navigation sequences, and confirmation screens use consistent language; whether people know the current step; and whether information needed to complete a task remains available when needed. Some of these concerns map to WCAG 2.2 criteria, while broader recommendations derive from W3C's cognitive accessibility guidance. Record which findings concern conformance and which concern inclusive usability.

A useful protocol asks participants to complete a realistic action without being coached on the interface's intended vocabulary. Observe where they hesitate, repeat steps, lose context, or misunderstand consequences. For a multi-stage application, compare the cost of returning to an earlier answer, correcting contradictory data, interpreting validation, and understanding what "Submit" actually authorizes. Do not force all participants into a timed speed contest: measure success and barriers while respecting varied pace and fatigue.

Check the interface under translations and simplified reading modes when those are supported. A "Next" control that changes to "Confirm" without an explanation may appear predictable to its designer but surprise a user who is not ready to commit. Cognitive evidence can reveal an improvement opportunity that no machine rule will flag. Treat these observations as structured findings with task, context, and consequences rather than general accusations that a page is "confusing." Involve people with varied cognitive experiences without assuming that one participant represents a whole disability group.

21. Accessible Forms, Errors, and Recovery

Forms should be tested before and after validation, with both valid and invalid inputs. Confirm that each field has a meaningful label; required status is perceivable; grouped options are presented as a coherent question; instructions are findable at the moment of entry; and errors identify both the problem and an actionable route to correction. Screen-reader testing should confirm that error details are reachable and appropriately announced without interrupting user control. Keyboard testing should verify that focus can move to the error and return to the field without losing already entered information.

A sample script should include required-field omissions, a format error, a server-side error, cancellation, backward navigation, and a recovered submission. Avoid the shortcut of reading only the error summary's raw text. A summary that lists six errors but offers no usable way to reach the fields may still block progress. Similarly, a visual inline error may never reach a screen-reader user if it is not programmatically associated with the relevant field or otherwise communicated.

<label for="contact-email">Email address</label>
<input id="contact-email" type="email" required
       aria-invalid="true" aria-describedby="contact-error">
<p id="contact-error">Enter a valid address such as name@example.org.</p>

This illustrates an invalid state, not a ready-made universal form pattern. In a real implementation, set aria-invalid and error associations at the appropriate moment, maintain visual and programmatic messages, preserve values, and test actual submission behavior. Do not mark every field invalid on initial page load merely because the sample markup contains a static error example.

22. Media, Documents, Charts, and Complex Nontext Content

Different media require different evidence. For prerecorded video, inspect captions for accuracy, synchronization, speaker identification, and meaningful non-speech sound; inspect audio description for visual information not conveyed by the soundtrack; and verify that the media player itself is operable using relevant input methods. For live media, distinguish real-time caption performance from prerecorded editorial quality, and document whether corrections and recordings become available. A caption file merely being present is insufficient if the user cannot select it or if essential content has been omitted.

For tagged PDFs, EPUB, documents, and spreadsheets, test semantic structure, navigation order, reading order, tables, language, and the actual reading application. A document exported from a well-structured authoring file can lose tag relationships or navigation. Test the distributed artifact rather than only the authoring source. A chart should provide appropriate nonvisual meaning, which may combine a short summary and accessible data; a graphic can have nonempty alternative text while still omitting the decisive trend or value.

Maintain format-specific checklists as supplementary tools, but retain an integrated user-task model: can a student find the assignment section, use the document's contents list, interpret a chart, and answer a question? The PDF validator's output is one piece of evidence. Media and document testing connects directly to Accessible Documents and Electronic Publications and Captions, Transcripts, and Audio Description.

23. Language, Localization, Direction, and International Use

Language affects text-to-speech pronunciation, braille translation, input conventions, labels, and user comprehension. Record the principal document language and changes of language within content. Test mixed-language text, quotations, names, abbreviations, and technical terms with appropriate assistive-technology voices where feasible. A nonvisual user may still understand a sentence but hear a crucial date or name incorrectly if language metadata is missing. A string's mere presence in a translation file does not demonstrate accessible localization.

For right-to-left interfaces, evaluate logical reading order, directional icons, focus sequence, form grouping, and whether mirrored layout creates contradictions. Numbers, email addresses, and embedded Latin terms can introduce bidirectional text issues. Voice-control software may depend on language-specific command recognizers; verify commands and visible labels in the actual locale. Mobile virtual keyboards and input-method editors should also be tested when the service relies on their behavior.

Document the language of tested content and the AT configuration used. Do not report "screen readers work" based exclusively on English content if the product's supported users rely on Spanish, Arabic, Chinese, or another language. Where full testing coverage is not possible, communicate the gap transparently and prioritize languages by real service reach and impact, not by whether a team member happens to know the language. Avoid using unreviewed machine translation as a substitute for evaluating a high-stakes instruction or consent message.

24. Assistive-Technology Interoperability as a System Property

A web interface interacts with assistive technology through a chain: application markup and script → browser semantics and accessibility API exposure → operating-system bridge → assistive-technology interpretation → user action and feedback. A defect can originate at any point. Incorrect application semantics usually require an author fix; a browser mapping bug may require a platform fix or carefully assessed workaround; an AT configuration issue requires accurate reproduction before assigning blame.

Interoperability tests should observe outcomes rather than demand identical words from different screen readers. Two products may announce a control differently yet both convey name, role, state, and position sufficiently for the task. Conversely, a vendor support table that marks a particular ARIA behavior as supported does not prove an application's custom component works. The W3C ARIA-AT support tables explicitly warn against treating their results as a final verdict and recommend application testing in relevant combinations.

Use layered diagnosis. First inspect rendered semantics. Second operate with keyboard alone. Third test with the failing assistive technology and browser. Fourth compare another supported combination. Fifth isolate a minimal reproduction, preserving the meaningful state change. Finally distinguish a fragile workaround from a durable correction. The objective is user access across supported combinations without perpetually coding to a temporary platform bug. Record residual limitations and retest them after browser or assistive-technology updates.

25. Designing a Support and Test Matrix

The ideal matrix is not "every device ever manufactured"; it is a defensible combination of population needs, criticality, platform support commitments, and known failure risks. Set a primary matrix for release testing, a secondary matrix for periodic sampling or incident response, and an exploratory list for emerging technologies. Use observable task results rather than labels such as "fully supported" with no test date. Reevaluate when the product or platform changes materially.

26. NVDA: Windows Screen-Reader Testing

NVDA is commonly used to evaluate nonvisual web navigation on Windows. Build task scripts that include heading and landmark navigation, links, form controls, tables, dialogs, and status updates. Inspect both the browse/virtual reading context and direct interaction with controls. A page may read correctly from top to bottom while failing when the user jumps by heading or activates a dynamically inserted option. Avoid treating NVDA's exact speech as normative text; focus on whether the required information and control semantics are available.

Record the NVDA version, speech mode, browser, language, and relevant configuration changes. If possible, first reproduce a finding with default settings to avoid mistaking a custom verbosity preference for an application failure. Check the behavior after a page update, after an invalid form submission, and after a browser history action. When a tester uses the keyboard to access a control, confirm that virtual cursor position and actual focus are not moving independently in a way that hides the result.

Pair NVDA tests with DOM inspection and a second supported browser when results appear inconsistent. A live announcement may be silent because it was added after the content, because timing differs across engines, or because the message was never created in the expected accessible state. Determine what was exposed before concluding "NVDA is broken." NVDA evidence is valuable but does not cover voice control, touch screen readers, or every Windows user.

27. JAWS and Windows Compatibility Verification

JAWS testing can expose differences in navigation conventions, forms interaction, and interpretation of custom widgets. Run the same outcome-based task used with another screen reader, rather than assuming identical keystrokes or announcements. Test headings, region traversal, edit fields, required status, and transitions into complex controls. In a web application, verify whether the tester can enter a composite widget, change a value, and leave it without losing the current page context.

Track the JAWS version, browser, relevant verbosity settings, and whether the test environment includes enterprise policies or extensions that affect behavior. If a result differs from NVDA, compare accessible names and state mappings first. An alternate browser may help isolate a compatibility gap, but it does not remove the requirement to describe the failure in the originally supported environment. A defect may require a standards-conformant author correction, or it may reveal a platform support issue whose workaround needs careful cross-testing.

Avoid reporting a blanket JAWS compatibility verdict from a few examples. A successful heading-navigation test does not imply that announcements, rich text editors, or custom grids are usable. For high-stakes workflows, rehearse realistic error conditions and the full completion path. Where a component's ARIA design follows a published pattern, compare reported ARIA-AT support evidence with the actual implementation while recognizing the support tables are not application certification.

28. VoiceOver on macOS and Safari

VoiceOver on macOS uses platform conventions that differ from Windows screen readers, including navigation through rotor-like structures and groups that may require interaction. Test the supported operating-system and Safari combination explicitly; an application that passes one Windows screen reader cannot be presumed compatible. A semantic table might require different navigation gestures or commands; confirm that row and column meaning remains available, not that the interaction mimics Windows.

Inspect focus transitions after dynamic route changes and overlays. A custom tab interface may change the selected panel visually while VoiceOver continues announcing stale content. Reproduce with the actual macOS accessibility inspector when possible, and compare what the platform accessibility API exposes. Test keyboard-only access separately so a VoiceOver user's navigation technique does not mask a component that is itself inaccessible to other keyboard users.

Record changes caused by system settings such as increased contrast, reduced motion, full keyboard access, language, and voice. Do not conflate macOS VoiceOver with iOS VoiceOver: they share a product name and accessibility principles but differ in device input, application structure, and supported interaction patterns. Particularly for hybrid desktop applications, evaluate both the surrounding native controls and the embedded web content, including where focus crosses the boundary. A seamless task must remain seamless across that transition.

29. VoiceOver on iOS and Touch Exploration

On iPhone or iPad, VoiceOver users may explore by touch, swipe through items, use the rotor, and activate controls through screen-reader gestures rather than direct taps. Assess discoverability, order, naming, activation, and focus restoration with the reader actually enabled. A visually large touch target can be difficult to find if its accessibility frame is poorly aligned, and a visually hidden element can become a stray stop in the accessibility traversal. Test portrait and landscape where supported.

Check dialogs, bottom sheets, menus, notifications, and tab changes because focus and reading order can diverge from visual movement. A button that opens a filter sheet should give a meaningful entry point into the sheet; after it closes, the user should return to the original context. For a custom slider, verify that accessible adjustable actions work rather than assuming a swipe gesture used by sighted users remains available while VoiceOver is enabled.

Record device model, iOS version, Safari or app version, accessibility settings, language, and whether an external keyboard is attached. When a mobile web feature uses ARIA behavior found in desktop examples, test it in the real mobile browser and screen reader. W3C's ARIA APG cautions that mobile/touch compatibility is not guaranteed by its examples. The user experience, not the presence of a pattern name, determines interoperability.

30. TalkBack on Android and Touch-Screen Readers

Android testing commonly uses TalkBack with the deployed app or a mobile browser, but behavior depends on Android version, browser or framework, device manufacturer, and accessibility service. Test sequential traversal, touch exploration, element activation, form-entry transitions, navigation drawers, and content updates. A custom control may expose a label but omit the actionable role or state required for efficient navigation. Check whether grouped information is announced in a coherent sequence without requiring excessive repeated swipes.

For web content, investigate Android browser semantics and the mobile viewport. For native content, inspect the framework's semantic nodes, including Compose or View implementations where applicable. Do not assume that the same accessibility attributes or platform events are exposed by embedded WebViews and ordinary browsers. Validate user operations in realistic transitions, such as switching from a document viewer back to the application or opening a secure permission dialog.

As with iOS, test supported alternative input and responsive layout separately. A result that works under touch exploration may fail with an attached keyboard or a switch. Record the exact device and build in a defect report; vague statements such as "Android screen reader fails" prevent reproduction. When an issue appears after a system update, compare a previous supported version and a minimal test fixture before assigning a cause. The practical requirement remains that intended tasks be discoverable and operable.

31. Linux, AT-SPI, and Alternative Desktop Environments

Linux desktop accessibility often relies on AT-SPI and applications or toolkits that expose compatible accessibility information. Screen-reader and other assistive-technology availability varies across distributions and desktop environments. Testing must identify the supported Linux environment rather than assuming all distributions share a uniform accessibility experience. Record the window system, browser or toolkit, screen reader where relevant, and any accessibility bridge configuration.

Inspect programmatic names, roles, states, focus events, text-selection information, and dynamic content under the chosen toolkit. A native application may show a visually conventional menu while exposing little useful information to assistive technology if the widget does not implement the expected accessibility interface. Similarly, a web interface embedded in a native application may lose accessibility information at its host boundary even when the webpage works correctly in a standalone browser.

Linux testing is especially important for public-sector, education, research, and enterprise products with explicit cross-platform support. If Linux is not in the published support scope, avoid implying it has been verified; document limitations and user needs transparently. Do not infer from a browser engine's general standards implementation that an entire Linux distribution's AT bridge works. As with other environments, task-level compatibility is established only through reproducible evidence in the actual deployment conditions.

32. Speech Input, Dictation, and Voice Control

Voice-control testing asks whether someone can operate the interface by speaking commands or dictating text, not whether a microphone icon can be clicked. Identify a supported platform, then attempt to activate visible controls by the words displayed on screen, navigate common views, enter and edit text, correct recognition errors, and submit or cancel a workflow. A visible label that differs materially from the accessible name can impair voice targeting even if a screen reader receives a technically valid name. This is particularly important for icon-only controls.

Test ambiguous names and repeated controls. A page with six buttons all called "Edit" may require an additional disambiguation mechanism. A voice command that triggers a destructive action should support understandable confirmation and recovery. For long forms, verify that the user can move between fields, correct text, and activate help without switching to a precise pointer. Include a quiet environment and, where appropriate, background-noise conditions to understand recognition limits without blaming users for speech variation.

Distinguish voice recognition accuracy from the interface's ability to be controlled after a command is recognized. If the platform transcribes "Continue" correctly but the application exposes no target with that label, it is primarily an interface-targeting problem. If the target exists but the recognizer mishears a phrase, record that separately. Do not require users to disclose their voice characteristics or a medical diagnosis in defect reports. The test should protect privacy while documenting the resulting task barrier.

33. Magnification, High Contrast, and Visual Assistive Technology

Screen magnification changes the size and visible region of an interface, not only its appearance. With a supported magnifier, test focus tracking, keyboard-caret visibility, pointer tracking, error discovery, and the ability to keep instructions close to the current task. Where the OS supports contrast themes or color overrides, verify that controls remain perceivable and that status information does not depend on fixed background graphics. A page can preserve contrast at default zoom and fail under forced colors because custom outlines or icons disappear.

Test the point at which a user must scroll to maintain context. If an autocomplete list opens below a field that is no longer visible at high zoom, can the person identify the suggestions and return to editing? If a toast appears far from the active focus, is the message announced or otherwise accessible? If a dashboard requires scanning a large canvas, is a text or table alternative provided? These are meaningful user-level tests, not only pixel-level checks.

Document magnification settings, display scale, viewport dimensions, contrast modes, and whether hardware acceleration or browser options affect rendering. Use manual visual inspection together with task tests. Automated contrast checks may not understand images or OS override behavior, while user testing may reveal effort and disorientation that a screenshot comparison misses. The goal is stable task access across presentation preferences, not merely a larger screenshot.

34. Switch Control, Scanning, Alternative Keyboards, and Motor Access

Switch-access testing evaluates whether a user can reach and activate controls through sequential scanning or an adapted input mechanism. A keyboard path is a useful foundation but may not fully represent switch behavior, timing constraints, or assistive software's scanning model. Test navigation through menus, forms, dialogs, and primary actions with the configured scanning mechanism. Measure avoidable navigation burden as well as outright blockers: requiring dozens of scans to reach a repeatedly used action can undermine independent task completion.

Tasks requiring dragging, multipoint gestures, rapid sequences, or sustained pressure need accessible alternatives where applicable. Test an explicit move-up/move-down control, selection-and-confirmation interaction, or other non-dragging route rather than assuming a hardware adapter can simulate every pointer motion. Verify that errors and accidental selections are reversible. If automatic updates reorder controls during scanning, test whether the current selection remains stable and whether the user receives an intelligible notification.

Document device configuration, scanning speed, input method, and test conditions, while avoiding false assumptions about the participant's strength or dexterity. For a research session, offer breaks, preserve participant control over settings, and ask about their normal strategies rather than imposing a standardized speed. These tests often reveal design improvements valuable to keyboard, speech-input, and mobile users as well. They complement, but do not replace, Motor Accessibility and Alternative Input.

35. Refreshable Braille and Multimodal Output

Refreshable braille can expose different information and navigation affordances from speech output. If braille support is within the product's user needs or support claims, test meaningful text order, headings, control labels, table navigation, form status, and messages with a compatible screen-reader/braille configuration. A screen reader speaking the correct phrase does not automatically prove that braille users can inspect it conveniently or that the displayed text includes relevant punctuation, abbreviations, and symbols.

Complex numerical material, code, mathematical notation, and multilingual content are particularly important. An audio explanation that is intelligible in context may be awkward for precise data review, while a structured expression can support braille navigation and verification. For educational materials, examine whether a user can locate a particular cell or equation term repeatedly without restarting the entire document. Do not claim a universal braille grade or translation behavior without identifying the actual language and reader settings.

A practical approach is to test with an experienced braille user and their appropriate device where possible, while preserving a reproducible semantic inspection record. If real-device testing is not available, state the limitation clearly rather than marking braille support "passed" based on speech-only tests. Treat multimodal output as interoperable access to the same task and content, not as a requirement for identical interaction sequences across fundamentally different devices.

36. Equivalent Outcomes Across Input Modalities

An accessible product supports equivalent task outcomes, not necessarily identical gestures or keystrokes. A sighted pointer user may drag an item; a switch user may select and reposition it; a voice user may say a visible command; a screen-reader user may choose a move option from a labeled menu. These paths can differ while preserving the ability to complete the intended task safely and review the result.

Develop a task-equivalence matrix for high-value functions. Identify the goal, available modality, activation and feedback method, potential errors, confirmation, and recovery. For example, changing a delivery address must remain possible with keyboard, voice control, and an appropriate mobile screen-reader path; it should not rely exclusively on a map pin dragged by a mouse. Test not just a single action but the resulting state and confirmation.

37. Involving People with Disabilities in Evaluation

Evaluation benefits from participants with relevant lived experience using their own strategies and technology. These sessions are not substitutes for standards-based inspection: a small set of participants cannot exhaustively assess conformance, and an expert audit may miss barriers revealed by actual use. The methods are complementary. Invite participants to complete representative tasks, observe without leading, and ask what information or control they needed at each point. Their prior experience with the service, technology configuration, language, and domain knowledge all affect findings.

Recruit based on functional needs and task contexts rather than assuming diagnostic labels predict identical behavior. Arrange accessible consent, communication options, compensation, appropriate breaks, and control over whether recordings or screen contents are retained. Avoid requiring participants to expose real medical, financial, or identification data. When a task involves sensitive information, use realistic synthetic fixtures that preserve task complexity without revealing personal details.

Separate observed barrier from inferred cause. A participant might say a search result is impossible to find; an investigator could then inspect headings, announced result counts, focus location, and the filter state. Do not blame the participant for an unfamiliar command or assume every unfamiliar command indicates a defect. The analysis should explain whether the interface creates an unreasonable demand, whether a reliable alternative exists, and what implementation change would remove the barrier. Follow up with a correction test involving the same functional scenario when feasible.

38. Task Scripts, Observation, and Completion Measures

A useful task script describes a goal in ordinary language rather than prescribing the exact clicks the design team expects. For example: "Find the accessible version of the assigned reading and locate the table on page three." This allows participants to use natural search, heading navigation, keyboard traversal, or screen-reader strategies. Researchers may establish the starting conditions, but should avoid revealing which navigation link or control is considered the correct path.

Record completion, critical errors, assistance needed, alternative routes, reversals, unexpected data exposure, and the participant's explanation of barriers. Time-on-task may be useful, but interpretation must account for technology configuration, unfamiliarity, language, fatigue, and deliberate verification in high-stakes tasks. Speed is not an adequate substitute for accuracy or autonomy. A participant who takes time to review a transaction before submitting may be behaving more safely, not demonstrating poor usability.

When testing a remediation, use the same goal and comparable data, then inspect whether the reported barrier is resolved without introducing new ones. Keep observers' notes distinct from participant statements and technical test logs. A credible evidence record can include screen recordings if consented, anonymized event descriptions, AT configuration, and screenshots of test fixtures. Do not publish personally identifying user data in a general bug tracker. Link the task evidence to specific interface states and, where appropriate, WCAG success criteria.

39. The Reproducible Accessibility Defect Record

Every actionable defect should enable another person to reproduce the failure and understand its practical consequences. Include title, product build, page or view, affected user task, exact environment, preconditions, ordered actions, expected behavior, observed behavior, accessibility criterion or inclusive-design objective, evidence, impact, and retest outcome. Separate a symptom from a proposed implementation fix; the suggested fix might change after root-cause analysis.

Issue: Dialog focus lost after applying a filter
Build: 2026.11.23-a1 | Browser: [name/version]
OS + AT: [OS/version] + [assistive technology/version]
Precondition: Signed in; course catalog results visible
1. Open Filters with keyboard.
2. Select Evening and activate Apply.
3. Dialog closes. Press Tab once.
Expected: Focus returns to Filters or a logical result target.
Actual: No visible focus; AT remains on removed dialog content.
Impact: Keyboard/AT user loses their place in results.

Status: Open; owner and retest date to be assigned.

Do not omit affected task or user consequence simply because a lint tool already produced a selector. For issues that are intermittent, capture frequency, timing, network condition, and whether a delayed render was involved. Protect sensitive material in logs, especially authentication and user-generated content. An issue record can cite the relevant normative requirement, but it should not claim a legal violation merely because a tool assigned severity "critical." The goal is an efficient correction supported by verifiable evidence.

40. Root-Cause Investigation and Browser/AT Debugging

After reproducing a defect, isolate the failing layer. Check whether the element exists and has a meaningful native control type; whether scripts modify focus and state at the correct moment; whether the accessibility tree exposes expected semantics; whether the platform fires the intended accessibility event; and whether the assistive technology responds to that event. Try a minimal test case, not to dismiss the original issue, but to identify the smallest condition that triggers it.

For a missing announcement, compare a native button, a correctly implemented custom button, and the failing component in the same environment. If the native button works and the custom one does not, inspect role, accessible name, keyboard handling, and changing state. If identical code works in one browser but not another, examine mappings or event support. If neither works in the environment, inspect AT settings and known support limitations. Record every variant so that the engineering team does not chase speculative root causes.

A correction should favor standards-conformant patterns and simpler native controls over brittle browser detection. Be cautious with one-off timeouts that attempt to force a screen reader to announce content, because they can create double announcements or fail under slower devices. An effective retest verifies the original failing sequence, a related success path, at least one other supported combination, and any likely side effects on keyboard or pointer use. Root-cause knowledge should improve component libraries and test scripts, not remain locked in a one-time support ticket.

41. Severity, Priority, and Consequence of Failure

Severity should reflect what a barrier prevents, whom it affects, whether a reliable equivalent route exists, and the potential consequence of error. A mislabeled decorative icon may be low impact when all information is elsewhere; an unlabeled payment confirmation or unreachable medication alert may be critical. Frequency matters but does not outweigh serious exclusion: a barrier affecting fewer users can still prevent an essential service. Record how an evaluator assigned priority rather than relying only on a scanner's preset label.

Use separate dimensions where helpful: functional impact, scope and frequency, safety or rights consequences, available workaround, and confidence in evidence. A severity scale can guide triage, but it should never imply that a low-number issue is acceptable indefinitely. Review failures in complete processes with special care. A single inaccessible authentication step may make dozens of otherwise accessible pages irrelevant to an affected user.

42. Fixing Author Defects Without Coding to Temporary Platform Bugs

Prefer the simplest accessible implementation that meets the user's task. Replace a nonsemantic clickable container with a native button where appropriate; correct a label before adding a speech-only workaround; update control state at the same time the interface changes; and ensure newly displayed content remains reachable. These corrections reduce dependence on a particular screen-reader implementation and often help voice-input, keyboard, and touch users simultaneously.

If an assistive-technology or browser defect is confirmed, seek a workaround that works across supported combinations and will not become harmful when the underlying platform issue is fixed. W3C's ARIA-AT guidance warns against coding to the bugs without careful analysis. A workaround that announces a status twice might help one screen reader now but become disruptive after a future update. Record the environment, source of the issue, alternative routes, and retest trigger.

Evaluate every fix through its full interaction lifecycle: default, keyboard focus, activation, changed state, error, cancellation, and completion. For a reused component, run its tests in representative products because surrounding layout and event handling can alter behavior. A narrow pass in a component showcase is useful but does not guarantee end-to-end access. When a limitation cannot be corrected immediately, describe a genuine independent alternative and its constraints rather than silently changing the failure status to "resolved." 43. Accessibility Regression Testing and Continuous Integration

Accessibility needs regression coverage just as security, performance, and functionality do. Adopt layered tests: static analysis during development; component-level checks for semantics and keyboard contracts; stateful browser tests for dialogs, forms, and navigation; scheduled AT/browser evaluations for critical flows; and periodic user testing where meaningful. Add regression cases whenever a real defect is found so that the same failure does not return unnoticed.

A pipeline should report what it actually tests. A build may pass linting and automated accessibility rules while still requiring manual screen-reader and voice-control sign-off. Keep automated results machine-readable, preserve versions, identify affected components, and avoid alert fatigue from thousands of duplicate warnings. Gate high-confidence, newly introduced failures appropriately, and provide a documented review path for inconclusive cases. Do not count an unrun test as success because a test job was skipped.

steps:
  - name: Unit and semantic component tests
    run: npm run test:components
  - name: Stateful browser accessibility checks
    run: npm run test:accessibility
  - name: Publish evidence and untested-state report
    run: npm run report:accessibility
# Manual AT task runs remain a separate, explicitly tracked gate.

Reassess after browser, OS, assistive-technology, design-system, or content-platform updates. A clean pipeline cannot guarantee against changes in a third-party payment flow or a new language variant. Track those dependencies and schedule real task retesting when they change.

44. Dynamic Content, Live Regions, and Asynchronous States

Dynamic applications introduce timing and communication problems that static DOM checks routinely miss. Test what happens when an autocomplete suggestion list appears, a background calculation completes, a search returns results, a message arrives, or a transaction fails. Determine whether the resulting information is exposed in the accessibility tree, announced when appropriate, available for later review, and not lost due to unexpected focus movement. Excessive announcements can also block work; accessibility is not achieved by marking every update as urgent.

Build cases for loading, success, no results, validation error, network failure, and recovery. For an aria-live region, verify the region's purpose and update sequence in the actual platform environment. Do not assume that adding a live-region attribute to markup guarantees an announcement. Likewise, avoid moving focus to every new status message; focus should move when the interaction pattern and user task justify it, not as a universal substitute for status communication.

<p id="search-status" role="status" aria-live="polite"></p>
<!-- Application code updates the text after a search finishes. -->

A test should query whether users learn that the result count changed, can navigate the new results, and can recover if the search fails. Compare speech output, braille where relevant, and the visible status. Document timing-sensitive bugs with network throttling or controlled asynchronous fixtures so a developer can reproduce the event ordering.

45. Content Authoring Quality and Editorial Workflows

Accessibility can regress through content updates even when the application template remains unchanged. Editorial teams may publish a new image without meaningful alternative text, paste an inaccessible table, insert heading-like bold paragraphs, upload a scanned PDF, or add a video without captions. Test a representative workflow from author entry through preview, publication, and end-user consumption. A CMS checker should identify risks at authoring time, but it cannot determine the adequacy of every description or document export.

Develop editorial acceptance checks: correct headings and hierarchy, link purpose, meaningful chart data, accurate captions and transcripts, descriptive titles, accessible table headers, appropriate language metadata, and publication of accessible document editions. Retain a process for reviewing AI-generated alternatives against original content. Include error handling: can an editor discover why a required accessibility field fails, and can they repair it without losing their work? Authoring-tool accessibility is itself a separate question from accessibility of the published artifact.

Track defects back to their true source. A missing video caption may require a production workflow change, not a front-end code patch. An invalid heading sequence introduced by a shared rich-text widget may require both author education and a tool repair. Sampling should include recent content, unusual formats, and pages from different editors to reveal inconsistency. This extends accessibility quality beyond a one-time technical audit to content lifecycle monitoring, while leaving policy and organizational accountability to the governance unit.

46. Cross-Browser, Cross-Platform, and Version Drift

Assistive-technology compatibility is time-sensitive evidence. Browsers modify accessibility-tree mappings, mobile operating systems update gesture semantics, and screen readers change announcement behavior. An evaluation must record what was tested at the time and identify triggers for retesting. After a significant platform update, prioritize components with complex custom semantics, dynamic focus, dialog states, composite controls, and heavily used critical processes.

Do not interpret a single version difference as proof that one product is universally defective. Reproduce the issue, compare the tested application code, and determine whether a change in platform implementation exposes a previously hidden author problem. Maintain a known-issue register with affected versions, user consequences, workarounds, owner, and anticipated review date. A vendor support announcement may guide planning but is not a replacement for testing the actual product.

Use confidence language proportionate to evidence: "The enrollment task completed with NVDA version X and Firefox version Y on Windows build Z under the specified fixtures" is stronger than "supports all screen readers." When uncertainty is substantial, disclose it. A credible support statement helps users decide whether a service will work for them and helps product teams triage risk. For a public resource, make known limitations accessible in their own right, without requiring users to contact inaccessible help channels to learn the truth.

47. Metrics: Coverage, Outcomes, and Reporting Integrity

Metrics should illuminate progress without disguising untested areas. Useful measures include percentage of identified critical tasks covered by test scripts, number of environments actually exercised, verified blocking defects by workflow, time to verified remediation, recurrence of defects, and task completion under representative input methods. A scan's issue count can be useful for triage but cannot be treated as a comprehensive accessibility score. Counts may change because the tool's rule library or test scope changed, even when the product did not.

Distinguish coverage metrics from outcome metrics. Testing a button in six screen readers improves coverage; demonstrating that a person can complete a registration process provides outcome evidence. Neither metric alone is sufficient. A more comprehensive report states test dates, scope, assumptions, known exclusions, sampled tasks, results and unresolved impacts. It should allow a reader to determine which product parts have never been evaluated.

A possible executive summary is: "Nine of ten critical tasks were tested with the primary keyboard and screen-reader matrix; eight completed without blocking defects; one failed due to an inaccessible identity step; the remaining task is untested pending a secure fixture." This communicates more than an "accessibility score of 94." Do not allow dashboards to imply that a risk is eliminated because the metric cannot observe it. Include human-readable descriptions of severe barriers alongside charts and numerical trends.

48. Reporting Conformance Without Overclaiming

A conformance report should specify the standard and version, target level, evaluated product scope, methodology, testing dates, technologies relied upon, assistive-technology environment, representative samples, and results. Report failures and coverage limitations plainly. WCAG-EM 2.0 provides reporting guidance; meeting a few sample tests does not necessarily justify a sweeping conformance statement about an entire service. The W3C evaluation report template illustrates useful reporting fields.

The distinction between conformance evaluation and user testing remains important. A product may meet a formal set of testable criteria while some people still experience significant barriers; conversely, a positive participant session cannot establish that every applicable success criterion passes. Report each line of evidence on its own terms. State whether findings are full evaluations, scoped reviews, smoke tests, prototype inspections, or specific platform-compatibility demonstrations.

Do not imply certification by W3C or endorsement by an assistive-technology vendor unless such recognition has actually been issued through an appropriate process. Accessibility statements and procurement documents should not use a test-tool badge as proof of comprehensive conformance. If a serious defect remains, explain the affected function, an available accessible alternative if one truly exists, a feedback channel, and the status of correction. Conformance claims must remain accurate as the product changes; a prior report becomes stale when major content or behavior is modified.

49. Evaluation Boundaries and the Governance Handoff

This article provides a method to find, substantiate, reproduce, and retest barriers. It does not itself create an organization's procurement policy, assign budget, establish legal risk acceptance, or authorize long-term exceptions. Those duties belong in the separate Accessibility Governance, Procurement, and Remediation specialist article. The division is intentional: evaluators must be able to report an inconvenient failure without the reporting method being rewritten to match an organization's appetite for remediation.

When handing findings to governance, provide a stable defect inventory with user impacts, scope, technical evidence, reproduction steps, severity rationale, dependency information, and recommended verification. Include high-impact unsupported or untested flows; "not tested" should remain visible as a risk rather than being silently dropped. Where a vendor controls the failing step, identify contractual and technical dependencies without removing the user impact from the service record.

Evaluation should continue through correction, not end when defects are filed. A fix is not verified until the failing user task succeeds under the relevant test conditions and adjacent functionality remains intact. Governance then determines release criteria, staffing, training, procurement response, and periodic review. By keeping evidence, engineering decisions, and governance responsibilities distinct but linked, teams reduce both overclaiming and unproductive cycles of repeat audits.

50. Worked Scenario 1: Keyboard Navigation and Hidden Focus

A hypothetical university catalog has a prominent filter sidebar and a sticky header. Automated scanning reports no missing labels. With keyboard only, a tester opens the filter pane, chooses a category, and closes it. The next Tab action moves focus behind the sticky header, where the indicator is visually obscured. The student does not know which control is active and cannot reliably return to the result list.

Investigation: Record viewport width, zoom level, focus sequence, and actual active element; inspect CSS positioning and scroll behavior. Check WCAG 2.2's applicable focus visibility and non-obscuration requirements, while distinguishing a separate usability concern if the keyboard path is needlessly long. Repeat at normal zoom and 200% zoom. Verify a focus return target after the filter pane closes, and check whether the result count is exposed to screen-reader users.

Resolution evidence: The corrected flow should return focus to a logical visible control, avoid obscuring focus across target viewports, preserve the chosen filters, and make updated results discoverable. Re-run the same script in the primary keyboard environment and representative screen-reader combination; then inspect a different catalog page using the same component. A scanner's clean report remains supporting evidence only. The scenario demonstrates why structured keyboard and view-state tests are necessary even when the initial page is semantically well marked.

51. Worked Scenario 2: Modal Dialog and Screen-Reader Support Gap

A registration application opens a modal confirmation dialog. It has a visible title and a button labeled "Confirm registration." NVDA in one browser reads the title, but another screen-reader/browser pairing enters the dialog without identifying its purpose. After the dialog closes, keyboard focus is sometimes left on a removed node. A developer suggests adding repeated urgent live announcements to force attention.

Investigation: Confirm that dialog name and role are exposed in the accessibility tree, the modal state is correct, focus enters a suitable element, the background is not operable while modal, and Escape or Cancel follows the intended pattern. Compare supported browser/AT combinations and build a minimal reproduction. Consult relevant ARIA APG dialog guidance and available ARIA-AT support evidence without treating example behavior as proof for this application.

Resolution evidence: Fix lifecycle and focus behavior first, then choose a semantically reliable naming approach. Test both opening and closing from multiple invoking controls. A fallback announcement should not duplicate information for other readers or obscure the user's own speech output. Record whether a platform support gap remains after author code is corrected and link to any follow-up issue. The essential outcome is a user who can identify the decision, act deliberately, and continue without losing their place.

52. Worked Scenario 3: Checkout Validation and Recovery

A mock online store has a three-step checkout. The card-number field is required, and a payment attempt with an invalid number displays a red message near the field. The initial automated scan catches no failure because the error is absent until submission. A screen-reader user hears that payment was declined but cannot find which field needs correction; pressing Back clears the shipping address.

Investigation: Use synthetic payment data and inspect the entire process. Test label and error associations after submission, announced status, logical focus, available review screen, and preservation of previous steps. Compare keyboard, screen-reader, voice-input, and magnification paths. Identify whether the error arises in client validation, a remote payment widget, or the application's error mapping; do not expose a real payment credential during testing.

Resolution evidence: A successful retest conveys the relevant correction, permits return to the field, preserves authorized entries, allows review before resubmission, and provides a clear confirmation. The evaluator records any third-party dependency as part of the user journey. Even though one error may map to a particular WCAG success criterion, the process-level evidence is indispensable: a field can be correctly labeled while recovery remains practically inaccessible. The result should not be called conforming merely because the first two checkout screens pass.

53. Worked Scenario 4: Autocomplete, Live Updates, and Multiple Browsers

An admissions portal offers a searchable country field. Suggestions appear after three characters, and keyboard arrows visually highlight a result. In one browser, a screen reader announces the correct suggestion; in another, the text field updates but the active suggestion is not conveyed. A browser automation test reports that all options have role="option", giving the team false confidence.

Investigation: Document the combobox pattern, name, expanded state, relationships, active option, listbox exposure, keyboard behavior, and selection event. Reproduce with a slow network fixture and a complete option list. Determine whether the input maintains focus while the active descendant changes, or whether focus is incorrectly shifted into the popup. Test Escape, no-results state, and correction after choosing the wrong country.

Resolution evidence: The user can understand that suggestions exist, navigate choices, know the active selection, commit or cancel, and continue in supported AT/browser combinations. Record differing announcements only where they affect these outcomes. A fix that inserts a manual alert on every arrow press may create double speech and regression risk; use the intended accessible pattern first. The case demonstrates the gap between a DOM's static list of roles and a functional assistive-technology interaction contract.

54. Worked Scenario 5: Lecture Video and Accessible Media Player

A recorded university lecture includes speech, a rapidly changing diagram, and a demonstration in which the instructor points to unlabeled regions. Captions are available but omit some technical names. A descriptive transcript repeats spoken words without identifying the diagram transitions, and the player hides the caption-selection control from keyboard focus.

Investigation: Separate the content alternative problem from the media-player control problem. Review caption timing and accuracy against the recording, identify significant sound and speaker changes, and evaluate whether the visual description communicates information that speech omits. Test keyboard access to captions, transcript link, playback speed, and volume controls. Check operation with screen readers and magnification; do not mark a caption present as an equivalent of tested caption quality.

Resolution evidence: A revised transcript includes the missing visual explanation, captions identify meaningful technical content, and the published player exposes selectable captions and usable controls. Test the actual deployed media rather than only a corrected caption file in isolation. If producing audio description requires a separate version or pause structure, document how users can obtain it. The scenario illustrates that content accuracy, player interaction, and user navigation produce distinct kinds of evidence even within one lecture.

55. Worked Scenario 6: Interactive Map with a List Alternative

A regional service map lets users locate nearby assistance centers by clicking markers. The application also provides a searchable list, but selecting a list item highlights the corresponding marker without displaying address information to the screen reader. A switch user can reach the list but cannot activate the service detail because the button appears only on marker hover.

Investigation: Define the user goal as obtaining service details and contact information, not "clicking a pin." Test list search, filtering, result counts, keyboard and switch activation, focus movement, and whether details are available outside the map canvas. Assess the role and label of controls and the relationship between list selection and detail panel. Verify the flow at enlarged text settings and under screen-reader navigation.

Resolution evidence: Users can identify a relevant location and retrieve its name, address, hours, and contact route using their supported input method, regardless of the map visualization. A list that only changes the color of a pin is not equivalent. Re-test both map and list for state synchronization, ensuring that a pointer user still gets correct feedback. This case distinguishes a legitimate alternative representation from a token accessibility feature that fails at the final action.

56. Worked Scenario 7: Hybrid Native Application and Embedded Web Content

A desktop application uses native navigation controls around an embedded web editor. Keyboard users can enter the editor, but returning to the native toolbar requires a pointer click. A screen reader reports the editor's content but not the toolbar's changed document state. A developer tests the embedded page directly in a browser and reports that it works, overlooking the host application.

Investigation: Map the complete path from native frame to embedded page and back. Compare focus events, accessible names, role exposure, and document state under the actual desktop accessibility API. Test Save, Undo, document-title updates, and error recovery. Check whether the embedded engine exposes its accessibility tree through the host and whether the window's native toolbar correctly receives events.

Resolution evidence: A keyboard-only and AT user can enter, edit, save, and leave the editor without a pointer, and the new state is communicated. Browser-only testing remains a useful isolation method but does not certify the hybrid shell. The defect record must identify the native app build, embedded engine, operating system, and assistive technology. This case demonstrates that interoperability is an end-to-end property of the deployed product, not a transferable label attached to one component or framework.

57. Worked Scenario 8: Data Dashboard, Magnification, and Asynchronous Alerts

An operations dashboard updates its table every thirty seconds and displays red warning dots near delayed transactions. At 300% magnification, the update message is outside the visible region. When a new row arrives, focus moves unexpectedly to the first row and the user loses their current selection. A screen reader announces "updated" but not what changed; a keyboard user cannot pause updates.

Investigation: Reproduce with controlled data, high zoom, keyboard, and a screen reader. Determine whether updates are essential, whether the table preserves row identity and focus, whether status semantics identify the changed item, and whether a pause or manual refresh path is provided where applicable. Verify that color is not the sole way to identify a delay, and that the underlying values remain available as text.

Resolution evidence: Users can pause or manage updates where needed, understand changed transaction states, retain position in the table, review historical items, and operate at supported zoom levels. Capture the event order in test logs and verify behavior during both normal and failed network conditions. A static screenshot cannot show this failure, and a scanner may only see valid row semantics. The scenario reinforces the need to test time, state, focus, and alternative presentation together.

58. A Twelve-Stage Evaluation and Verification Framework

The following workflow unifies formal and practical accessibility assessment without pretending that a single technique proves everything. A project can adapt the order to its risk and development stage, but should preserve traceability between requirements, tasks, environments, observed failures, and verified correction.

Stage Activity Tangible evidence
1 Define product, version, scope, target Signed-off scope and exclusions
2 Identify essential tasks and audiences Task inventory and user contexts
3 Map templates, states, content and systems View/state/process inventory
4 Define support baseline Named browser, OS, AT, input matrix
5 Select structured, random and process samples Sample rationale and test fixtures
6 Execute static and stateful rule checks Tool logs with rule/version/state
7 Inspect semantics and keyboard behavior Role/name/focus/action observations
8 Exercise AT and alternative input Environment-specific task results
9 Conduct appropriate user task research Consented observations and outcomes
10 Document and prioritize defects Reproduction, impact, evidence, owners
11 Retest fixes and neighboring workflows Verified resolution and regressions
12 Report limitations and schedule rechecks Dated results, coverage and remaining risks

Decision rule: A test is not complete because the form or component looks finished. It is complete when the defined behavior can be reproduced, observed through relevant access methods, and documented with meaningful coverage limitations. When a product changes, evaluate whether the evidence still applies. When a serious failure remains, retain the failure in the report and route it to the governance process rather than adjusting the test to produce a desired score.

60. Applied Study and Assessment Exercises

  1. Write an evaluation scope for a five-step online enrollment process that includes an external authentication service, dynamic validation, and a downloadable receipt. Identify every transition that must be tested.
  2. Construct a sampling plan for a 200-page institution site with six templates, two role-specific portals, three languages, and a multimedia library. Explain how you would choose structured, random, and complete-process samples under WCAG-EM 2.0.
  3. An automated scanner returns zero issues on a dialog. Write a keyboard and screen-reader task script that could nevertheless identify focus, announcement, and dismissal defects.
  4. A button has the accessible name "Delete item" and visually reads "Remove." Explain how you would test speech-input activation and what correction you would consider.
  5. A form reports a successful submit but loses data after a network error. Write a defect record with preconditions, exact steps, expected/actual outcomes, and affected users.
  6. Compare the evidentiary value of a DOM inspection, an NVDA test, and a moderated task with an experienced screen-reader user. State what each cannot establish.
  7. Design a browser/AT matrix for a mobile and desktop educational service. Explain why platform versions and input methods matter.
  8. Investigate a live status message announced twice in one browser and not at all in another. Show how a minimal reproduction can distinguish application code from platform behavior.
  9. Plan a reflow and magnification assessment for a data-heavy dashboard with floating filters, sticky headers, and frequent alerts.
  10. Explain why an ACT rule result is neither a full WCAG conformance decision nor a proof of usability. Identify the proper report language for the finding.
  11. A vendor supplies a recent VPAT but the deployed checkout has changed. Define what evidence you would request and what user tasks you would retest before accepting a compatibility claim.
  12. Create a regression plan for a custom combobox shared across eight application areas. Include component tests, full user tasks, supported AT combinations, and retest triggers.
  13. Design an ethical participant-research session for voice-control and switch-access users. Include consent, compensation, fixtures, privacy, and observation limits.
  14. A screen reader completes a task, but a braille user cannot inspect the precise account value. Explain why speech-only evidence is insufficient and how to extend the test.
  15. Draft a one-paragraph executive accessibility status statement that identifies tested scope, blocking tasks, AT coverage, untested areas, and outstanding limitations without inventing a single numeric certification score.

Assessment standard: A substantive answer should identify the user goal, tested environment, expected observable behavior, sources of uncertainty, evidence produced, and how a correction would be verified. Simply recommending "run an accessibility tool" is insufficient.
