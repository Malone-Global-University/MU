Definition and Scope

A state-machine diagram is a visual account of the allowed states of a system and the transitions between them. A transition table represents the same behavioral contract in rows and columns. Neither is merely decoration. A diagram makes lifecycle structure, branches, loops, and exceptional paths recognizable; a table makes transition coverage, ambiguous guards, and omitted input cases easier to inspect. Together they can function as readable specifications, inputs to generated tests, and records of engineering decisions.

This specialist article develops a disciplined method for moving among a state vocabulary, a mathematical transition relation, a diagram, a transition table, traces, and executable code. It distinguishes finite automata, output-producing Mealy and Moore machines, and extended machines whose behavior depends on data variables. It also explains how these artifacts should be versioned and checked so that a visually attractive drawing does not disguise a defective specification.

The intended boundary is representation and consistency. Formal Transition Systems owns the underlying mathematical theory; Mealy and Moore Machines owns output semantics; Extended Finite-State Machines owns variable-bearing machines; and State-Based Software Testing develops model-derived test programs in detail. Our focus is how to describe, review, reconcile, and operationalize their behavior accurately.

Why Use Both Views?

A drawing can communicate in seconds that a request is submitted before it is approved, that cancellation can occur during review, and that an exception branch eventually returns to the main process. But drawings become crowded when there are many inputs or guards. A table can list every (state, event) combination and show exactly which are legal, refused, ignored, or deferred, yet it may obscure the broad lifecycle. The two formats answer different questions about the same model.

Suppose an access-request workflow has four states and four events. A reviewer can understand its general shape from a graph of six labeled arrows, then inspect a sixteen-cell state/event matrix to determine what happens when approve arrives in draft. Without that second step, an unstated transition can become an implicit programming-language default. Without the diagram, the table's many entries can hide an unintended cycle or unreachable branch.

Treat either representation as a projection of an authoritative model. Do not let independently edited diagrams, requirements prose, implementation switch statements, and spreadsheets silently diverge. The safest practice is to maintain a canonical transition inventory and generate or reconcile alternative views from it.

A State-Machine Specification Has Several Layers

A useful specification separates (1) alphabet or event vocabulary, (2) control states, (3) initial conditions, (4) transition conditions, (5) next-state effects, and (6) observation or output rules. Further layers may declare timers, variables, concurrent regions, error policies, and environmental assumptions. A box-and-arrow graphic without these definitions is usually an illustration rather than an executable contract.

For a deterministic input-driven machine, a simple transition function is δ: Q × Σ → Q. A richer representation might use rows (source, event, guard, action, target); its operational meaning depends on the order in which guards are evaluated, actions occur, and events are consumed. For a nondeterministic relation, several transitions may be enabled without any priority ordering. Never claim that a table is deterministic merely because it has been sorted alphabetically.

A diagram can omit some data for readability, provided its legend identifies where the complete conditions and effects live. A good technical document explains exactly what was omitted and does not imply that an abbreviated drawing is exhaustive.

Choosing the Level of Formality

Different projects need different levels of notation. A small DFA can be represented completely by labeled circles and arrows. A workflow with authorization and persistent records benefits from tabular guards and effects. Reactive controllers with nested states may require UML state-machine or SCXML conventions. At the far end, a verified protocol may use a mathematical transition relation and temporal properties as its primary specification.

Formal notation is not a measure of project prestige. It is a tool for closing ambiguities. A three-state controller may still require strict treatment if a wrong transition could permit an unsafe operation; a large exploratory user-interface prototype may require less ceremony initially. Choose the minimum notation that makes the important behavioral questions decidable and reviewable.

Notation Contract and Legend

Before drawing, define a notation contract: what a node represents, how initial and terminal states appear, what an arrow consumes, where guards are written, where actions are written, and whether missing arrows mean rejection, no change, or unspecified behavior. A widely used compact label is event [guard] / action, but that string is not universal across all tools or formalisms. State your chosen semantics rather than relying on a reader's familiarity with a particular diagramming package.

In this article, unless otherwise indicated, a row (q, e, g, a, q') means that event e is considered in state q; if g holds, action a is prescribed and the machine enters q'. A self-loop consumes its event and may still perform an action. An omitted guard is treated as true in examples. An omitted action means no modeled effect, not necessarily no physical activity outside the modeled system.

Node Conventions

A state node should have a stable identifier and a human-readable meaning. Prefer AwaitingReview over State3, and provide an identifier such as S2 only if external requirements, tools, or test cases refer to it. A state may represent a durable lifecycle position or an ephemeral controller mode; the distinction affects logging and persistence but not the basic ability to draw it.

A filled circle or arrow from an entry marker commonly identifies an initial pseudostate in UML-like notation. A target of this marker is not necessarily a real state that can be revisited. A bull's-eye final-state marker commonly denotes completion of a region, whereas a history marker, choice pseudostate, and fork/join have distinct semantics in richer notations. Do not treat every special circle as an interchangeable generic node.

For a DFA, accepting states may be shown with a double circle. This is language-acceptance notation and need not imply a workflow terminal state. Confusing “accepting” with “completed and no future transitions” changes the machine's meaning: an accepting DFA state can have outgoing transitions and later become nonaccepting.

Arrow Conventions

An arrow denotes a transition from source to target. Direction matters; a bidirectional relationship is two transitions unless the selected notation explicitly defines a reversible edge. Every transition should have a stable identifier if the specification will be tested, audited, or changed. Self-loops are first-class transitions, not merely annotations saying “stay where you are.”

For a deterministic machine, every state and input has exactly one successor when the transition function is total. For a partial state machine, some combinations can be intentionally undefined. A diagram's missing arrow is not enough to distinguish deliberate refusal from an accidental omission. Record the policy in a table or model metadata. For guarded transitions, two arrows with the same event may be legal if their guards are mutually exclusive; if guards overlap, specify priority or nondeterminism explicitly.

Initial States and Reset Behavior

An initial marker should identify one starting configuration for a deterministic single-region machine. When multiple starts are possible, state whether the model is nondeterministic, parameterized, or incomplete. “Start” is not the same as “reset”: a software process may restart with persisted state, and a physical controller may reset to a safe mode while retaining hardware faults.

A system with initial state Draft and event submit can be rendered as start → Draft → InReview, with submit on the second edge. If the start arrow is treated as an ordinary input-consuming transition, trace counts and acceptance calculations can be wrong. Keep initialization in a separate part of the model unless startup is deliberately represented as an event.

Terminal, Accepting, and Error States

A terminal workflow state has no further meaningful modeled work, although it may still support read operations or archival maintenance. An accepting automaton state is designated for a language-recognition test and may have many outgoing edges. An error state records a failure mode; it may be absorbing, recoverable, or able to escalate. Label these meanings independently.

In particular, a state called Rejected is not automatically terminal, and a state called Error is not automatically safe. A rejected application might be amended and resubmitted, while a fatal device fault might require manual intervention rather than a spontaneous transition to normal operation. The diagram should present the intended recovery route instead of leaving it to inference.

Example Domain: A Document Approval Workflow

Consider a constructed document-approval workflow with states Draft, Review, Approved, and Rejected. Inputs are submit, approve, reject, and revise. A valid submit moves a draft to review; approval or rejection is possible only during review; a rejected document may be revised into a draft. The Approved state is final for the modeled approval episode. This deliberately small example exposes most of the presentation issues without requiring a particular diagramming tool.

The following transition relation is partial: only authorized lifecycle events are included. Unsupported events are rejected by the API with no state change and an error response; that policy is separate from the listed lifecycle transitions. The word “rejected” is therefore used in two distinct senses: the lifecycle state Rejected and an API refusal of an invalid event. A production specification should avoid using the same term ambiguously in logs or user messages.

A Canonical Transition Inventory

The canonical inventory defines five transition identifiers. They are the authoritative edge set from which we will generate views and tests. approve and reject are intended to be authorized decisions; for now the table records their state eligibility, while authentication, identity, and authorization checks are explicit external requirements rather than assumed achievements of the diagram.

ID Source Event Guard Target Intended effect
T01 Draft submit Document complete Review Record submission
T02 Review approve Approver authorized Approved Record decision
T03 Review reject Approver authorized Rejected Record reason
T04 Rejected revise Editor authorized Draft Open a new revision
T05 Draft revise Editor authorized Draft Save draft changes

The guard column makes the limitation of a purely four-state diagram clear. Even in Review, an approval is not enabled unless the actor has the relevant authority. If the event vocabulary includes identities and the model carries an authorization context, the state space may be larger than the four visible lifecycle labels. This is a view, not a complete proof that all authorization rules are enforced.

Diagram of the Approval Workflow

The following is a compact diagram using labeled edges and an initial marker. It is intentionally an accessible SVG rather than a separate image asset. Its labels correspond to the five rows above, but the drawing abbreviates the guards and effects: the table remains authoritative for those details.

Read the arrows in this order: the initialization marker points to Draft; T01 submits to Review; T02 approves and T03 rejects; T04 permits revision from Rejected back to Draft; and T05 is a self-loop for draft editing. The diagram has no outgoing lifecycle edge from Approved, by explicit policy, but the application may still permit read-only inspection of an approved document.

The same partial relation can be displayed as a matrix. The cells below show guarded destination states; — means “not a lifecycle transition under this specification,” not an instruction to silently ignore a command. A system responding to disallowed commands should retain the current state and return an explicit error or rejection outcome outside this matrix.

A matrix can detect missing combinations mechanically. A sparse edge list can be easier to maintain if the event vocabulary is large. The formats need not compete: generate a matrix for review and preserve the edge list as the source of truth. State-by-event matrices are appropriate when the input alphabet is known and finite; they become unwieldy when events carry unconstrained data, in which case guarded event classes and separate variable definitions are preferable.

A Guard Is Not Merely an Arrow Label

A guard is a Boolean predicate that must be evaluated against defined data at a defined point in execution. amount <= limit is meaningless unless amount, limit, their types, source of truth, and evaluation instant are specified. In a diagram, an abbreviated guard such as [authorized] may be sufficient for readability; in the transition inventory, identify the governing requirement and any external dependency.

Two guards are overlapping when some input and data valuation makes both true. A deterministic machine that has two outgoing transitions on approve must show how one is selected. A pair [amount < 1000] and [amount >= 1000] partitions non-null numeric values but may leave missing, invalid, or nonnumeric values untreated. A complementary pair [authorized] and [not authorized] only covers cases if the predicate is total and does not fail on lookup or timeout.

Transition Actions and Their Visibility

Actions can update variables, append events, emit commands, or call external services. A transition table should distinguish the decision to issue an effect from the effect's successful completion. When a machine sends notify and then moves to Notified, that name may be false if the notification was merely queued. A more careful model uses NotificationQueued and accepts later delivered or failed observations.

Separate transition effects from entry/exit actions in statechart-style diagrams. An effect on an edge occurs when the transition fires; a state entry action occurs whenever that state is entered under the notation's precise execution rules. Translating one to the other is not generally behavior-preserving when a state can be reached from multiple edges or when internal transitions do not cause entry and exit.

The Event Consumption Contract

The example workflow processes one input event at a time, atomically from the viewpoint of the transition inventory. The implementation must decide whether events are queued, retried, coalesced, or processed concurrently. The diagram does not establish exactly-once delivery or transaction isolation, and it cannot prevent race conditions by itself. For instance, two reviewers may send conflicting decisions while the state is Review; the storage or serialization layer must ensure that only one eligible transition commits.

For educational diagrams it is reasonable to omit the infrastructure, but not to imply that event ordering is guaranteed merely because transitions are drawn one at a time. An explicit operating assumption—“process one accepted event against the current committed state”—keeps the model intelligible without pretending that the distributed implementation has been proven.

Executable Transition Table in Python

This example records the five lifecycle transitions in a machine-readable list. It demonstrates static checks for duplicate (source, event) pairs, unexpected states, and a declared initial state. Guards and effects remain documented labels here; it would be unsafe to silently pretend that a string such as Approver authorized is an evaluated security predicate. Executable authorization requires a separate trusted function and tests.

STATES = {"Draft", "Review", "Approved", "Rejected"}
EVENTS = {"submit", "approve", "reject", "revise"}
INITIAL = "Draft"
ROWS = [
    ("T01", "Draft", "submit", "Review"),
    ("T02", "Review", "approve", "Approved"),
    ("T03", "Review", "reject", "Rejected"),
    ("T04", "Rejected", "revise", "Draft"),
    ("T05", "Draft", "revise", "Draft"),
]
assert INITIAL in STATES
assert len({row[0] for row in ROWS}) == len(ROWS)
assert all(src in STATES and dst in STATES and ev in EVENTS
           for _, src, ev, dst in ROWS)
assert len({(src, ev) for _, src, ev, _ in ROWS}) == len(ROWS)
TRANSITIONS = {(src, ev): dst for _, src, ev, dst in ROWS}

def next_state(state, event):
    if state not in STATES or event not in EVENTS:
        raise ValueError("unknown state or event")
    if (state, event) not in TRANSITIONS:
        raise ValueError(f"disallowed lifecycle event: {state}/{event}")
    return TRANSITIONS[(state, event)]

assert next_state("Draft", "submit") == "Review"
assert next_state("Review", "approve") == "Approved"
print("five transition rows checked")

This skeleton is a state-eligibility checker, not a deployable approval service. It intentionally does not evaluate the documented guards, record durable transactions, or authenticate a caller. A later section adds guard functions and explains how static artifacts should declare the limits of their own executable models.

Generating a Matrix from the Same Data

Manual duplication creates drift. A simple generator can produce the state-by-event matrix directly from the canonical rows. The output uses — to denote absent lifecycle edges, so reviewers can see the exact policy for unsupported combinations. In a real publishing pipeline, the generator would emit validated HTML table cells and a structured test manifest using the same source model.

states = ("Draft", "Review", "Approved", "Rejected")
events = ("submit", "approve", "reject", "revise")
rows = {
    ("Draft", "submit"): "Review",
    ("Review", "approve"): "Approved",
    ("Review", "reject"): "Rejected",
    ("Rejected", "revise"): "Draft",
    ("Draft", "revise"): "Draft",
}
assert len(rows) == 5
matrix = [[rows.get((s, e), "—") for e in events] for s in states]
assert matrix[0] == ["Review", "—", "—", "Draft"]
assert matrix[2] == ["—", "—", "—", "—"]
for state, cells in zip(states, matrix):
    print(state, "/", " | ".join(cells))

A generated table is only as reliable as the canonical model. If a developer changes the intended workflow but does not update the source inventory, both the diagram and the table can agree with each other while disagreeing with requirements. Traceability to approved requirements is therefore a distinct review responsibility.

Generating a Diagram Specification

A text-based diagram format makes review, code history, and automation easier than an opaque screenshot. For example, Graphviz DOT represents a directed edge as source -> target; attributes can supply transition labels, shapes, or node styling. The following example generates syntactically coherent DOT source and uses a dedicated point node for the initial marker.

rows = [("T01", "Draft", "submit", "Review"),
        ("T02", "Review", "approve", "Approved"),
        ("T03", "Review", "reject", "Rejected"),
        ("T04", "Rejected", "revise", "Draft"),
        ("T05", "Draft", "revise", "Draft")]
lines = ['digraph Approval {', '  rankdir=LR;',
         '  node [shape=ellipse];', '  start [shape=point];',
         '  start -> Draft;']
for tid, src, ev, dst in rows:
    assert all(s.isidentifier() for s in (src, dst))
    assert ev.isidentifier() and tid.isidentifier()
    lines.append(f'  {src} -> {dst} [label="{tid}: {ev}"];')
lines.append('}')
dot = '\n'.join(lines)
assert dot.count(' -> ') == 6
assert dot.startswith('digraph Approval {')
print(dot)

The DOT listing is source for a graph renderer, not a claim that this HTML page loads Graphviz. Its labels contain no guard or effect fields, so it is a schematic representation. The authoritative transition inventory remains the place to verify authorization and side effects.

Mermaid Diagram Syntax as a Presentation Option

Mermaid offers a text syntax for many diagrams, including state diagrams. A short example is stateDiagram-v2 followed by [*] --> Draft, Draft --> Review: submit, and other labeled edges. Mermaid can be useful in Markdown-centered documentation systems where text is already version-controlled. Its source is not equivalent to a formal execution engine unless a separate interpreter is specified.

stateDiagram-v2
    [*] --> Draft
    Draft --> Review: T01 submit
    Review --> Approved: T02 approve
    Review --> Rejected: T03 reject
    Rejected --> Draft: T04 revise
    Draft --> Draft: T05 revise

The official Mermaid state-diagram reference describes current syntax and renderer conventions. Published diagrams should include a textual transition table for readers who cannot inspect the rendered graphic, and links to the corresponding guard and action definitions when necessary.

Formal Equivalence Between Table and Diagram

Let E_table be the set of directed, labeled transitions extracted from the canonical table, and E_diagram the same set extracted from the diagram source. Structural agreement means the normalized sets are equal, including sources, targets, event labels, and any recorded conditions or effects. Two drawings may look similar but differ materially if they have reversed one arrow, dropped a self-loop, or merged two guarded edges.

Normalization is required because a diagram may use aliases (Submitted versus Review) or aggregate several events into one label (approve | reject). Resolve every alias or aggregation unambiguously before comparison. Equal edge sets do not automatically mean equal behavior in statecharts where entry/exit actions, event queues, concurrency, or transition priorities alter the execution semantics. Structural equivalence is a necessary consistency check, not a universal semantic-equivalence theorem.

Executable Edge-Set Reconciliation

A lightweight consistency check can compare edge tuples from two independently prepared representations. For pedagogical simplicity, each edge is reduced to (source, event, target); a production checker would include guard identifiers, effects, initial-state metadata, and semantics version. The program reports missing and unexpected edges instead of merely returning a Boolean.

canonical = {
    ("Draft", "submit", "Review"),
    ("Review", "approve", "Approved"),
    ("Review", "reject", "Rejected"),
    ("Rejected", "revise", "Draft"),
    ("Draft", "revise", "Draft"),
}
diagram = set(canonical)
assert canonical == diagram
wrong = (diagram - {("Review", "reject", "Rejected")}) | {
    ("Review", "reject", "Approved")
}
missing = canonical - wrong
unexpected = wrong - canonical
assert missing == {("Review", "reject", "Rejected")}
assert unexpected == {("Review", "reject", "Approved")}
print("missing:", sorted(missing))
print("unexpected:", sorted(unexpected))

This check catches a class of editorial regression that ordinary HTML link validation cannot detect: a diagram may render perfectly yet encode the wrong destination for an event. Use the output in substantive technical review rather than treating visual inspection as sufficient.

Coverage, Completeness, and Totality

Coverage answers which state/event combinations are explicitly addressed. Totality means the transition function assigns an outcome to every permitted state/input pair, after accounting for declared data valuations. The two notions differ. A diagram with every state connected to every other state may still omit a relevant event, and a table with one row per state/event pair may still contain overlapping or unsatisfiable guards.

For the approval model, four states times four event types produce sixteen possible state/event combinations. The lifecycle inventory defines only five of them; the remaining eleven are deliberately disallowed. The API can nevertheless be total as an operation if every unsupported input yields a defined refusal outcome without committing a state change. It would be misleading to add eleven self-loops to the lifecycle diagram and call them approved business events: a refused command is a different observable outcome from a successfully consumed lifecycle event.

A coverage report should therefore distinguish enabled, guarded, refused, deferred, and unspecified. A blank cell should never secretly mean all five. Such distinctions are especially important in security-sensitive systems where the absence of a documented transition can conceal unauthorized state changes in the implementation.

A Coverage Matrix with Explicit Outcomes

The approval example can be refined by recording whether each event is a candidate lifecycle transition (L), a guarded candidate (G), or an explicit refusal (R). This is a design-time policy matrix; it does not decide the result of evaluating an individual guard. In our five transition rows, all five candidates are guarded, so the matrix's G cells still require runtime checks.

Current state submit approve reject revise Candidate transitions
Draft G R R G 2
Review R G G R 2
Approved R R R R 0
Rejected R R R G 1

A tabular review should confirm the meaning of the refused outcomes. Is there an audit record? Is a forbidden approval attempt a security signal? Does retrying the same invalid command cause repeated notifications? The state machine may remain unchanged while the service still performs an observable refusal action. Those responses belong in an API or error-outcome contract even when the lifecycle graph remains sparse.

Executable Coverage Audit

The next example prints all state/event pairs and checks that each is either a declared candidate or an explicit refusal. Coverage is reported as a count of classified combinations, not as test coverage of an implementation. The important distinction is that a fully classified policy matrix can still be incorrect relative to business requirements.

states = ("Draft", "Review", "Approved", "Rejected")
events = ("submit", "approve", "reject", "revise")
allowed = {
    ("Draft", "submit"), ("Draft", "revise"),
    ("Review", "approve"), ("Review", "reject"),
    ("Rejected", "revise"),
}
policy = {(state, event): ("GUARDED" if (state, event) in allowed
                           else "REFUSED")
          for state in states for event in events}
assert len(policy) == len(states) * len(events) == 16
assert sum(x == "GUARDED" for x in policy.values()) == 5
assert sum(x == "REFUSED" for x in policy.values()) == 11
assert policy[("Approved", "approve")] == "REFUSED"
print("classified combinations:", len(policy))

For more complex data-bearing models, enumerating all valuations may be infeasible. Tools may use satisfiability checking or symbolic reasoning to determine whether the union of guards covers the intended input domain. A matrix alone cannot substitute for those methods.

Detecting Overlapping Guards

Consider a transition table with two approve rows in Review: one guarded by amount <= 1000, another guarded by amount >= 1000. At exactly 1000, both guards hold. If one row approves automatically and the other requires escalation, the ambiguity is consequential. A visually compact diagram may show both arrows and still fail to reveal their overlap.

For numeric thresholds, test boundary values and specify inclusive versus exclusive comparison carefully. For Boolean guards, truth tables may suffice. For compound constraints, a satisfiability solver can search for a valuation that enables two candidate transitions. If the model intentionally uses priority—“first matching row wins”—document that operational rule. Otherwise, mutually exclusive guards are often easier to reason about than order-dependent behavior.

Executable Boundary-Overlap Check

This example proves only a finite-sample counterexample: it finds a value for which two guards overlap. It does not claim to prove general exclusivity for arbitrary Python predicates. The corrected guards amount < 1000 and amount >= 1000 are disjoint over the illustrated integer range and collectively cover that range.

def low(amount):
    return amount <= 1000

def high(amount):
    return amount >= 1000

overlaps = [x for x in range(995, 1006) if low(x) and high(x)]
assert overlaps == [1000]

def corrected_low(amount):
    return amount < 1000

def corrected_high(amount):
    return amount >= 1000

sample = range(995, 1006)
assert all(corrected_low(x) != corrected_high(x) for x in sample)
print("overlap counterexample:", overlaps)

Real data may include None, invalid numeric encodings, currency differences, and overflow. A boundary-focused diagram review should ask how those values are classified, not merely whether the nominal integer threshold looks consistent.

Detecting Unreachable States

A diagram may contain an elaborate branch that cannot be entered from any allowed initial configuration. Reachability can be checked by graph search on the declared transitions. This is not always proof of practical reachability: guards may block a path that is structurally possible, while data conditions may enable paths in the full model that are absent from a simplified diagram.

Use reachability analysis to identify probable omissions and dead documentation. A state called Escalated that is never a transition target may be a planned feature rather than implemented behavior. Such a state should not silently appear in user instructions as if it were reachable.

Executable Reachability from the Diagram

The sample uses breadth-first search on the structural edge set. The order of exploration does not affect the set of reachable state labels. The detached Archived state is flagged, while every state in the approval example is reachable from Draft by some sequence of declared events (ignoring guards).

from collections import deque
states = {"Draft", "Review", "Approved", "Rejected", "Archived"}
edges = [
    ("Draft", "Review"), ("Review", "Approved"),
    ("Review", "Rejected"), ("Rejected", "Draft"),
    ("Draft", "Draft"),
]
adj = {q: set() for q in states}
for src, dst in edges:
    adj[src].add(dst)
found, queue = {"Draft"}, deque(["Draft"])
while queue:
    for target in adj[queue.popleft()]:
        if target not in found:
            found.add(target)
            queue.append(target)
assert found == {"Draft", "Review", "Approved", "Rejected"}
assert states - found == {"Archived"}
print("unreachable:", sorted(states - found))

Reachability and deadlock analysis become substantially more demanding when transitions depend on variable valuations or synchronized components. See the dedicated Reachability and Deadlock Analysis unit.

Terminal States, Dead Ends, and Deadlock

A directed graph node with no outgoing edges is a structural sink. Whether it constitutes a deadlock depends on the specification. A completed approval episode may intentionally terminate in Approved; a machinery controller stuck in Running with no allowed fault response would be a serious defect. An operationally blocked component may also have outgoing arrows whose guards are all false. Conversely, an explicit self-loop can keep a machine transition-enabled while preventing meaningful progress.

The correct review question is not simply “Are there nodes with zero outgoing arrows?” It is “Does the modeled system reach a configuration in which required progress is impossible, and is that configuration an accepted final condition?” Make final-state conventions explicit so a completeness audit does not wrongly accuse intended terminal conditions of error.

Executable Structural-Sink Classification

Here the expected final state is exempted from the diagnostic that flags unexpected structural sinks. This analysis is intentionally weaker than semantic deadlock checking: it cannot evaluate guards, timers, or dependencies in another component.

states = {"Draft", "Review", "Approved", "Rejected", "Escalated"}
edges = {
    ("Draft", "Review"), ("Review", "Approved"),
    ("Review", "Rejected"), ("Rejected", "Draft"),
    ("Draft", "Draft"),
}
finals = {"Approved"}
outdegree = {q: 0 for q in states}
for source, target in edges:
    outdegree[source] += 1
sinks = {q for q, degree in outdegree.items() if degree == 0}
unexpected = sinks - finals
assert sinks == {"Approved", "Escalated"}
assert unexpected == {"Escalated"}
print("unexpected structural sinks:", sorted(unexpected))

Transition Identification and Requirement Traceability

Stable transition identifiers, such as T01 and T02, permit requirements, code changes, tests, logs, and diagrams to refer to the same behavior. A traceability record can connect T02 to “only an authorized approver may finalize a submitted document,” the implementation function that validates the role, and tests for authorized, unauthorized, and concurrent approval attempts. Identifiers should not change merely because a diagram layout changes.

Do not overload identifiers with presentation order. T02 should mean a particular transition definition; moving its arrow from left to right does not create a new behavior. If a transition's guard or effect changes materially, record the revision in version history so reviewers can distinguish a visual repositioning from a changed contract.

Representing Mealy Output Tables

A Mealy machine associates outputs with transitions. A table therefore needs both next state and output for each (state, input) pair. A diagram typically labels an edge input/output under the declared notation. The same destination can have different outputs depending on the source state and input. If a diagram prints only event labels, it has discarded part of the transducer's specification.

State Input Next state Output
Locked coin Unlocked unlock
Locked push Locked alarm
Unlocked coin Unlocked refund
Unlocked push Locked relock

An output label is not evidence of physical completion. The table says what the modeled component emits, not whether a downstream actuator or message recipient successfully acted. The companion Mealy and Moore Machines explains precise sequence-output alignment and conversion between models.

Representing Moore Output Tables

A Moore machine attaches each output to its current state. Its representation should include a state → output table alongside the state/input transition table. Putting a distinct action on every incoming edge would be a different presentation, and can become wrong if state entry behavior differs from transition effects.

State State output Input coin → next Input push → next
Locked gate_locked Unlocked Locked
Unlocked gate_open Unlocked Locked

The output here is a persistent logical status, not a pulse unlock command. Do not assume this two-state Moore machine reproduces the preceding Mealy transducer's four distinct event outputs. The state outputs and transition outputs encode different observation contracts; equivalence would require a declared observation convention and possibly state splitting.

Tables for Nondeterministic Automata

An NFA transition table maps (state, input) to a set of possible next states, not to one destination. An empty set means no transition for that pair; it is not an implicit self-loop. If ε-transitions exist, add a separate ε column or a separate transition list. A diagram with two arrows bearing the same input can represent genuine nondeterministic branching rather than a mistaken duplicate.

State a successors b successors ε successors
q0 {q0, q1} ∅ {q2}
q1 ∅ {q2} ∅
q2 ∅ {q2} ∅

Do not collapse the set notation when transcribing a diagram. The question is whether at least one permitted run accepts the word, not whether the illustrator happened to place one edge above another. The companion Nondeterministic Finite Automata covers state-set simulation and ε-closure.

Extended-State Tables and Variable Valuations

An extended finite-state machine has control states plus data variables. Rows may read (source, event, guard, update, destination) and need a precise rule for whether updates are atomic, which variables they may modify, and whether an exception aborts the transition. Two histories may share the visible control state but have different legal next events because their variable values differ.

For example, a workflow could remain in Review while variable approvals_received counts decisions. An arrow labeled approve [approvals_received = 1] / approvals_received := 2 does not communicate all possible outcomes for invalid or duplicate approvals. Supplement diagrams with variable domains, invariants, initialization, and a guard/action table; do not pretend every data valuation is an independent named control state unless that expansion is actually useful.

An Extended Approval Rule with Trusted Guards

The executable example below makes an explicit, modest distinction between role checking and record persistence. A trusted caller context is represented only by a Boolean argument for demonstration. The transition function is pure: it returns the next state and an outcome, and leaves database commits and external identity verification to the caller. A real implementation must not trust a role Boolean supplied by the client.

def decide(state, event, *, can_approve=False, complete=False):
    if state == "Draft" and event == "submit" and complete:
        return "Review", "submitted"
    if state == "Review" and event == "approve" and can_approve:
        return "Approved", "approved"
    if state == "Review" and event == "reject" and can_approve:
        return "Rejected", "rejected"
    if state == "Rejected" and event == "revise":
        return "Draft", "revision_opened"
    if state == "Draft" and event == "revise":
        return "Draft", "draft_saved"
    return state, "refused"

assert decide("Draft", "submit", complete=True) == ("Review", "submitted")
assert decide("Review", "approve") == ("Review", "refused")
assert decide("Review", "approve", can_approve=True) == ("Approved", "approved")
assert decide("Approved", "revise") == ("Approved", "refused")
print("guard and refusal branches checked")

The script deliberately makes no claims about idempotency, confidentiality, authentication, or concurrent transaction safety. The diagram and table specify eligible decisions; the surrounding architecture enforces trust, storage, and delivery properties.

Hierarchical States and Nested Diagrams

Large reactive systems often contain recurring patterns that are easier to display as composite states. A parent state such as Processing might contain Validating, Charging, and AwaitingReceipt. A transition out of the parent may be intended to apply from multiple child states, but its exact precedence and entry/exit behavior depend on the selected statechart semantics.

A hierarchical diagram should show which states belong to which region and should provide a clear expansion path. Collapsing a parent into one node is safe for a presentation only if the hidden distinctions are not relevant to the decision under review. The detailed semantics belong to Hierarchical Statecharts.

Orthogonal Regions and Concurrency

A statechart with orthogonal regions can have multiple active substates simultaneously. One region might track a connection (Online or Offline) while another tracks a task (Idle or Busy). A flat diagram that shows these as four independent boxes can wrongly suggest a machine occupies only one of them at once. The actual configuration may be a pair such as (Online, Busy).

If a statechart displays fork/join or parallel-region notation, explain event dispatch, synchronization, and completion behavior according to the chosen standard. A transition table covering the full Cartesian product of region states may explode in size, so structured region-level tables and cross-region invariants can be more intelligible than a single global matrix.

Choice, Junction, History, and Final Pseudostates

UML-style state machines use pseudostates to express control-flow structures that are not ordinary, stable states. A choice evaluates guards at a decision point; a junction connects transitions under the notation's execution rules; a history marker supports reentry into a previously active configuration; and final marks completion of a region. Their semantics should not be inferred from icon similarity or imported from unrelated flowchart notation.

These constructs are useful when they reduce duplication, but they also introduce execution rules that a plain edge-list table may not represent. If the correctness of a workflow depends on whether a guard is checked before or after an exit action, use the selected formalism's explicit semantics and state the assumption in a separate execution table. Do not flatten complex pseudostates into simple arrows without documenting the translation.

Events, Internal Transitions, and State Entry or Exit

In an event-driven statechart, an internal transition may react without exiting and reentering its state, while a self-transition may invoke exit and entry behavior. These are not generally identical when the state has entry/exit actions. A diagram showing an arrow that loops back into the same box does not convey this difference unless the notation states how internal transitions are represented.

A practical table should distinguish transition kind, exit actions, edge effects, entry actions, and any deferred events. An apparently harmless translation from an internal edit event to a self-loop may cause duplicated notifications, repeated allocation, or lost in-progress work. In a strict review, classify these as semantic changes, not formatting changes.

SCXML and Executable Statechart Semantics

The W3C SCXML 1.0 Recommendation specifies an event-based statechart language with an execution model for states, transitions, conditions, data, and event processing. Its XML structure can serve as a machine-readable representation when interoperability and runtime behavior matter. The Recommendation is a specific language with constraints and algorithms; it is not synonymous with any arbitrary state diagram drawn in a GUI.

For example, SCXML distinguishes a transition with a target, an optional event, and an optional cond; it also specifies configurations and microstep processing. A simple (source, event, target) table may be a useful overview, but it cannot claim SCXML equivalence unless hierarchy, priorities, eventless transitions, actions, and data semantics have been preserved. See SCXML Execution Semantics for a fuller treatment and the official W3C specification.

UML State-Machine Notation and Its Limits

The OMG UML 2.5.1 specification defines state-machine concepts and notation, including regions, pseudostates, transitions, events, and behaviors. Its diagrams are particularly useful where software or systems models share a consistent UML vocabulary. However, copying a familiar UML appearance does not automatically grant a custom tool the exact UML execution semantics.

A document should identify whether it is UML-conformant, UML-inspired, or simply an informal directed graph. This prevents false confidence when notation elements are mixed: a DFA double circle means acceptance, a UML final marker means region completion, and a generic workflow circle may mean neither. Consult the official OMG UML 2.5.1 specification when formal notation conformance is required.

A Comparison of Diagram and Table Families

Different forms are suitable for different questions. Use this comparison to select a representation by intended meaning instead of selecting whichever figure appears most familiar.

Representation Best use Primary information Common omission
DFA graph Recognition over a finite alphabet States, symbols, start, accepting states Missing transitions in a purportedly total DFA
NFA transition table Branching and epsilon moves Sets of successors Mistaking an empty set for a self-loop
Mealy table Input-sensitive responses (state,input) → (state,output) Output lost during diagram conversion
Moore table State-associated responses Next-state table plus state-output map Initial output and observation timing
Guarded workflow table Business lifecycle control Source, event, guard, effect, target Role/data assumptions treated as verified
UML statechart Nested reactive systems Regions, entry/exit, pseudostates Priority and run-to-completion semantics
SCXML document Portable executable statechart definition Event dispatch, configuration, actions Incorrect hand translation into a simple graph

The same project can use several forms without creating competing specifications. What matters is whether every form is tied to an explicit shared semantic model and whether simplifications are labeled.

Layout, Visual Hierarchy, and Readability

A diagram should make likely paths easy to follow. Place the initial state where a reader can find it, avoid unnecessary crossings, keep edge labels near their arrows, and use stable names. Group related states spatially when doing so reflects a real subsystem or hierarchy rather than an arbitrary visual cluster. If a diagram is too dense to read without zooming, split it into a high-level lifecycle and focused detailed diagrams with explicit cross-references.

Use color, if at all, as a redundant aid: a green state should not be the sole indication of a successful or accepting condition. The state label, legend, and table must carry the same meaning. Long edge labels are often a sign that guard/action definitions belong in a separate table keyed by transition ID. Diagram layout improves comprehension, but it must not silently change the model's semantics.

Accessibility and Alternate Representations

A technical state diagram should have a descriptive title, a concise explanation of its function, a programmatically available text alternative where supported, and a complete textual table or equivalent narrative for readers who cannot inspect the geometry. A graphic saying only “state diagram” in its alternative text fails to describe the actual process. Keyboard access and contrast requirements should be considered when diagrams are embedded in an interactive viewer.

For this HTML article, the SVG example includes a <title> and <desc>, and the five transitions are reproduced in a table. The textual representation also assists indexing, translation, review in plain-text diffs, and downstream tools that cannot parse arbitrary drawing programs. Do not mistake textual alternatives for expendable duplication; they are a second verification view.

Diagram Source Management and Version Control

Store diagram source alongside its rendered output. Text formats such as DOT and Mermaid make line-based diffs practical, but generated diagrams should include the model revision or commit reference used to build them. A bitmap exported from a modeling tool may be useful for presentations, yet by itself it lacks a reliable connection to machine-readable transition data.

A publication workflow can retain an authoritative model in structured JSON, YAML, XML, or code, then generate tables and diagrams. This reduces representational drift without eliminating editorial judgment. Code generation must be bounded: do not execute arbitrary user-supplied guard expressions during document rendering, and do not use unescaped labels as code or markup.

Safe Rendering of Untrusted Labels

Labels can contain quotes, angle brackets, line breaks, or user-supplied names. Rendering them into HTML or DOT without escaping can break a document or introduce a script-injection vulnerability in a browser pipeline. Treat arbitrary labels as data. Use a supported renderer's escaping mechanism for the target format rather than writing string concatenation around raw text.

from html import escape
label = '<img src=x onerror=alert(1)> & review'
cell = '<td>' + escape(label, quote=True) + '</td>'
assert '<img' not in cell
assert '&lt;img' in cell
assert '&amp; review' in cell
print(cell)

This code demonstrates HTML escaping only. DOT, XML, JSON, and Mermaid have their own quoting and parsing rules. Encoding valid text for one format does not make it safe for another, and avoiding script injection is only one aspect of a secure diagram-rendering service.

Documentation Versus Execution Authority

An authoritative table used to generate production behavior has a different risk profile from a diagram included in a training manual. If a table contains executable guards, it may be necessary to validate expression languages, enforce resource limits, and separate configuration authorship from production approval. A user should not be able to add a new approve edge simply by editing a wiki illustration.

Define which artifact can change system behavior, who can approve changes, and what checks must pass before activation. A reviewer should be able to tell whether a proposed modification alters only visual placement, adds a new transition, changes a guard, changes an effect, or changes the runtime interpretation. The higher the consequence of a transition, the less acceptable it is to make these categories indistinguishable.

Model-Based Testing from Transition Tables

Transition tables can support systematic testing by generating a test for every eligible transition and representative refusals for every prohibited state/event pair. That does not guarantee sequence coverage: a transition might only be reached after a particular chain of events or a special variable valuation. Tests also need to inspect outcomes, persisted effects, and enforcement of guarded transitions rather than merely comparing next-state labels.

A model-based testing strategy can use state coverage, transition coverage, transition-pair coverage, and guard boundary testing. Distinguish these from assertions about application code. A table-driven test passes only if it exercises the actual implementation through an appropriate interface and validates its observable results. For a broader treatment, see State-Based Software Testing.

Executable Transition-Walk Test

The following sequence covers all five defined lifecycle transitions in a constructed trace. It illustrates model transition coverage without implying that a production service was exercised. Self-loops and back-edges are included deliberately: ignoring them would overstate coverage while omitting meaningful behavior.

rows = {
    ("Draft", "submit"): ("T01", "Review"),
    ("Review", "approve"): ("T02", "Approved"),
    ("Review", "reject"): ("T03", "Rejected"),
    ("Rejected", "revise"): ("T04", "Draft"),
    ("Draft", "revise"): ("T05", "Draft"),
}
walks = [
    ["revise", "submit", "approve"],
    ["submit", "reject", "revise"],
]
covered = set()
for walk in walks:
    state = "Draft"
    for event in walk:
        tid, state = rows[(state, event)]
        covered.add(tid)
assert covered == {"T01", "T02", "T03", "T04", "T05"}
print("model transitions covered:", sorted(covered))

The example resets to Draft before each walk. That is a model-level fixture, not proof that a real workflow's persistent storage can be reset safely. Production test design needs controlled fixtures, authorization setup, and cleanup policies.

Trace Tables and Event Histories

A trace table records state-before, input, guard decision, action, and state-after for each step of a particular run. Unlike a transition table, which describes possibilities, a trace table describes one execution. This distinction is useful when debugging, demonstrating a specification, or auditing an incident.

Step State before Event Guard result State after Observable result
0 — Initialize — Draft Document opened
1 Draft submit Complete Review Submission recorded
2 Review reject Authorized Rejected Reason recorded
3 Rejected revise Authorized Draft New revision opened
4 Draft submit Complete Review Resubmitted
5 Review approve Authorized Approved Decision recorded

A trace is only evidence if it corresponds to actual committed behavior. Event logs may be delayed, duplicated, redacted, or re-ordered relative to their production times. If an institution uses traces for accountability, the logging architecture must capture identity, version, decision provenance, and transaction correlation independently of the diagram's aesthetics.

Sequence Constraints Beyond Edge Coverage

A transition table can express which individual steps are legal while leaving important sequence rules untested. An implementation might correctly reject approve in Draft yet allow repeated approval events to modify records after Approved. A diagram with a terminal state suggests the rule, but tests should verify it explicitly. Similarly, a model could permit resubmission only after revision without preserving the document's revision identifier.

Sequence constraints often require additional state, historical variables, or temporal properties. Do not force the entire history into one unreadable diagram; record the invariant in a separate requirements table, then link it to transition identifiers and tests. For example: “once Approved is committed, no later lifecycle event changes the state within this episode.”

Temporal and Safety Properties Alongside the Diagram

A model may need assertions that cannot be read from one arrow. Safety properties describe what must never happen, such as an approval without the required authority. Liveness properties express desired progress under stated assumptions, such as a submitted request eventually receiving a decision if a reviewer is available. A diagram indicates candidate transitions; it does not prove that the property holds under every possible execution.

Use a separate properties table with assumptions, interpretation, and verification method. For example, “the only transition to Approved is T02” is a structural property of our reduced model, while “every persisted approval is authorized” requires a trustworthy guard implementation, correct storage, and audit evidence. See Safety and Liveness Properties for the full theory.

A Property-to-Evidence Matrix

Property What the diagram or table can show What needs additional evidence
No direct draft approval No Draft → Approved edge Actual API refuses unauthorized direct updates
Only approved users decide T02 and T03 have guards Trusted role evaluation and race-safe commit
Terminal approval No outgoing lifecycle edge from Approved Storage prevents later lifecycle mutation
Revision route exists Rejected → Draft edge Revision identity and audit trail work
Every submitted request eventually resolves Available review outcomes Fairness assumptions, scheduling, timeouts
Diagram and table agree Equal normalized edge sets Semantics, execution engine, guard behavior

The last two columns prevent a recurring documentation error: presenting a drawing as if it were a security proof, a liveness proof, or an operational compliance certificate.

Change Impact and Versioned Transitions

Suppose a new requirement allows an approved document to be withdrawn. That is not a matter of drawing one extra arrow. The team must define the new event, authorization guard, resulting state, side effects, downstream notifications, and retention policy. The change may invalidate terminal-state assumptions, test fixtures, analytics dashboards, and user documentation.

For each modified transition, record the requirement, model revision, implementation owner, test IDs, and affected outputs. Regenerate both diagrams and tables from the revised inventory and compare their edge sets. Retain an approval history so reviewers can reconstruct what behavior was valid at the time an incident occurred.

Applied Scenario 1 — A Document Approval Service

A university uses a controlled workflow to approve curriculum changes. Administrators need an immediate lifecycle diagram, while engineering staff need exact tables for allowed commands and authorization checks. The diagram makes the rejected-to-revised loop visible; the table lists every relevant combination and flags unauthorized approval attempts. Every transition carries a stable identifier and a link to a requirement. Deployment checks compare the model with service-level tests and database permissions.

The key risk is treating the approve arrow as authorization. An arrow shows where an allowed approval leads, not who is allowed to approve. The guard must be evaluated against authenticated, authoritative identity data and committed atomically with the state change.

Applied Scenario 2 — A Network Protocol Handshake

A client protocol uses states Disconnected, Connecting, Connected, and Closing, with events such as connect, ack, timeout, and close. The diagram reveals a retry cycle and the path from Closing back to Disconnected; a table reveals whether repeated acknowledgments or a timeout after completion have defined behavior. A trace table helps reproduce an intermittent failure.

The representation must distinguish a command to send from an acknowledgment received. Network delivery may duplicate, delay, or reorder messages; a state diagram does not make those possibilities disappear. The protocol specification should explicitly document retry limits, message correlation, and behavior under duplicate events.

Applied Scenario 3 — An Industrial Controller

A controller moves among Idle, Starting, Running, and Fault. A visual diagram is useful for operators, but a transition matrix must address emergency stops, sensor faults, restart permission, and reset prerequisites. Entry and exit actions may matter more than the shape of the arrows, so UML or another precise statechart semantic model may be required.

The critical distinction is between logical control documentation and engineered safety assurance. A red Fault box is not a certified interlock. Physical safeguards, validated control logic, fault detection, and safe-state design require separate engineering evidence. The diagram supports that review; it cannot replace it.

Applied Scenario 4 — A Token Recognizer

A lexical analyzer recognizes a regular pattern over an alphabet. A DFA diagram with a double-circled accepting state is appropriate for showing how input symbols drive recognition. A dense alphabet may make a transition table more useful, especially when the implementation needs a total transition function or a defined sink state for every unrecognized symbol.

In this domain, acceptance is evaluated after the complete word or at a defined lexer boundary. A double circle does not imply that the lexer halts upon entering that state. Keeping language acceptance distinct from workflow completion prevents accidental truncation and incorrect tokenization.

Applied Scenario 5 — A User Interface with Nested Modes

An editing application has top-level modes Viewing and Editing; within Editing it tracks Clean, Dirty, and Saving. A single flat diagram can quickly become cluttered, while a hierarchical diagram groups the nested states. A table is still useful for dangerous events such as close, discard, save_failed, and permission_revoked.

The team must specify whether navigation away from editing triggers exit actions, whether a save completion event is ignored after a cancel, and whether an internal edit action should retrigger state entry. These are execution semantics, not cosmetic layout choices.

Applied Scenario 6 — A Security-Sensitive Account Lifecycle

An account-management system includes Pending, Active, Suspended, and Closed, with administrator and account-holder actions. The diagram helps stakeholders see restoration and closure routes. The table exposes whether a suspended account may still receive privilege changes, whether a closed account can be reopened, and which role checks apply to each transition.

No design should conclude that an action is secured solely because a diagram omits an edge. Review the actual API, storage procedures, authorization enforcement, and audit events. The transition model supplies a reviewable policy map, while the implementation must enforce that policy at every relevant entry point.

Ten-Gate Diagram and Table Review Framework

Gate Review question Expected evidence
1. Scope What behavior and boundaries are modeled? Named component, assumptions, version
2. Vocabulary Are states and events unambiguous? State definitions, event dictionary
3. Initialization What configuration exists before input? Explicit initial state or configuration
4. Transition rows Are sources, targets, guards, effects defined? Canonical inventory and identifiers
5. Missing cases What happens on unsupported combinations? Explicit totality/refusal policy
6. Guard logic Can transitions overlap or leave gaps? Boundary tests or formal guard checks
7. Observables Are commands, status, and side effects distinguished? Output vocabulary and timing assumptions
8. Consistency Do graphical and tabular views encode the same edges? Normalized reconciliation result
9. Behavioral evidence Are reachability, traces, and invariants checked? Model tests, properties, implementation evidence
10. Governance Can a model change be traced and approved? Revision records, responsible owner, test mapping

The gates should be applied proportionately. A classroom automaton may need a compact state table and two proof obligations; a safety-critical or security-sensitive system requires evidence beyond this document. The framework helps reviewers find omissions, not claim that any one diagram format is universally sufficient.

Common Misconceptions and Corrections

“Every arrow shown is automatically permitted.” False if the arrow has a guard, requires a role, or depends on unmodeled data. “Every missing arrow is a no-op.” False unless the policy explicitly defines it as such. “A self-loop does nothing.” False; it can consume an event and execute actions. “A terminal workflow state and an accepting DFA state are the same.” False; they represent different predicates. “One transition table proves deterministic behavior.” False if guards overlap or event processing is not specified.

“The diagram is correct because it renders.” Rendering validates only some syntax and layout properties. “The table is correct because every cell is filled.” A complete but wrong policy is still wrong. “The same edges mean identical behavior in every formalism.” Entry/exit actions, priorities, event queues, output timing, and hierarchy can change semantics. “A workflow arrow grants authorization.” It does not. “Changing a diagram is only editorial.” It may be a behavior change if the diagram is the normative specification or generates code.
