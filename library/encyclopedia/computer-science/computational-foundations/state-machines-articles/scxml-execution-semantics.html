Definition and Scope

SCXML (State Chart XML) is the World Wide Web Consortium's XML-based language for describing the control behavior of event-driven state machines. Its principal contribution is not that it draws statecharts in a different notation: it defines what an interpreter must do when a configuration receives an event, when a guarded or eventless transition becomes enabled, when states exit and enter, and when executable actions raise further events. The W3C SCXML 1.0 Recommendation was published on 1 September 2015; its errata should be consulted alongside the Recommendation. The dated Recommendation, rather than an earlier Working Draft, governs the semantics described here.

An SCXML machine may combine nested states, concurrent <parallel> regions, extended variables, entry and exit actions, shallow or deep history, final states, internal event generation, external event dispatch, and invoked services. The core subject of this article is execution semantics: the observable consequences and ordering rules that convert a document into a running machine. Syntax matters because the specification makes some differences operationally significant, including an omitted event versus event="*", a targetless transition versus one that explicitly re-enters its source, and a synchronous <raise> action versus an event transported using <send>.

This Level 5 specialist belongs to State Machines. Read Hierarchical Statecharts for modeling motivations, Extended Finite-State Machines for guards and variables, and State Machine Diagrams and Tables for documentation techniques. The present article supplies the specific W3C processing contract, not a generic description of all statechart runtimes.

Development, Standardization, and Conformance

SCXML grew out of work on event-driven dialog systems and the broader statechart tradition, including David Harel's hierarchical and orthogonal statechart concepts. Interchangeability of a drawing is insufficient for interoperable execution: two processors may agree on state names but disagree about which transition wins, when an action runs, or which event is consumed next. SCXML addresses this through normative definitions of legal configurations, enabled transitions, ordered effects, datamodel operations, and required processor behavior.

The Recommendation uses normative requirements and provides an informative interpreter algorithm in Appendix D. Calling Appendix D "informative" does not make the normative transition-selection and execution requirements optional; it means an implementation can use a different algorithm if its externally relevant behavior satisfies those requirements. Conversely, copying a few lines of pseudocode does not certify an interpreter. Profiles may support different datamodels, optional I/O processors, and documented platform extensions; interoperability assessment must state those supported capabilities explicitly.

Standards work also distinguishes SCXML document conformance from processor conformance. A document with well-formed XML is not necessarily valid SCXML. An engine that renders a statechart diagram is not necessarily an SCXML processor, and an engine that handles simple <state> transitions may still lack correct internal-queue ordering, parallel conflicts, <invoke>, or datamodel semantics. The official Recommendation, its errata, and corresponding conformance cases form the appropriate authority for implementation claims.

Learning Objectives and Analytical Questions

After studying this article, readers should be able to explain why SCXML has separate external and internal event queues, distinguish a microstep from a macrostep, identify the transition priority for a nested state, trace exit/action/entry ordering, and decide when a machine has reached a stable configuration. They should recognize when type="internal" changes the exit domain, when an automatically generated done.state.* event enters the internal queue, and why a <send> dispatch is not the same as confirmation of an external business effect.

The most useful practical question is: Given an initial configuration, datamodel valuation, and sequence of events, what precisely happens before the next external event may be examined? Answering it requires state hierarchy, XML document order, active regions, guards, the two queues, effects, and possibly invocation status. A flat transition table that omits these details cannot answer the question reliably.

Relationship to the State-Machine Taxonomy

A deterministic finite automaton recognizes words by advancing one state per input symbol. A Mealy or Moore machine associates outputs with transitions or states. An extended finite-state machine adds variables, predicates, and updates. A hierarchical statechart adds parent/child organization, shared behavior, and potentially concurrent regions. SCXML specifies a particular executable language and operational interpretation for such constructs. It therefore occupies a narrower editorial scope than formal transition systems or general statecharts, even while it uses their underlying ideas.

Do not project SCXML's exact document-order priority, event descriptors, <invoke> lifecycle, or done.state.* naming onto UML state machines, XState, hardware-description-language controllers, or arbitrary workflow software. Their semantics may share a family resemblance without matching SCXML. Conversely, SCXML is not a workflow engine, database transaction manager, or durable message broker by itself. Persistence, authentication, and external-effect guarantees depend on the surrounding implementation.

Core Terminology

Parallel state <parallel> with concurrent child regions Each region has an active descendant and may select nonconflicting transitions

Some terms have subtly different meanings in other formalisms. An SCXML <final> is a defined completion state, not merely a label meaning “finished” in a diagram. A transition is an XML element with a source state determined by where it is nested; its source is not an arbitrarily supplied from attribute.

State-Configuration Invariants

SCXML's legal configurations are constrained sets, not arbitrary collections of active IDs. Exactly one direct child of <scxml> is active. Every active atomic state carries its active <state> and <parallel> ancestors. A compound state has one active child, while an active parallel state includes all its child regions and appropriate descendants. These rules explain why simultaneous activity must be represented through <parallel> rather than by illegally activating two ordinary siblings.

A configuration such as {Workflow, Editing, Typing} can be valid when Workflow is a compound state and Editing contains Typing. {Workflow, Typing} without the active Editing ancestor is not a complete legal configuration. For a parallel state Operating with two regions Task and Network, the configuration may contain {Operating, Task, TaskBusy, Network, NetworkUp}. The process must enter an initial descendant of each parallel child. Keeping the complete configuration, rather than only the leaf IDs, is important when entry/exit handlers, history and ancestor-sourced transitions are evaluated.

The initial attribute and <initial> child provide default entry routes. A compound state's first child is the default when neither is given. Default entry descends until legal atomic configurations are formed. History targets can select remembered descendants; a first use of history follows its declared fallback transition. One should distinguish a target state name from the full configuration generated after ancestor and default-descendant completion.

The SCXML Document Skeleton

A basic SCXML document declares a standard namespace and a version. The following minimal example uses only core structural features; it is complete XML and illustrates initialization, named events, and a final top-level state.

<?xml version="1.0" encoding="UTF-8"?>
<scxml xmlns="http://www.w3.org/2005/07/scxml"
       version="1.0" initial="idle">
  <state id="idle">
    <transition event="begin" target="running"/>
  </state>
  <state id="running">
    <transition event="finish" target="completed"/>
  </state>
  <final id="completed"/>
</scxml>

At startup, idle is entered. The begin event enables the transition into running, and the later finish event reaches the top-level <final>, ending the SCXML session. A host must still specify how those external events arrive; XML itself supplies neither a transport nor a user interface. The namespace shown is the required SCXML namespace, even though the conventional W3C specification URL lives elsewhere.

Parsing and Structural Validation

Parsing XML verifies a representation, not execution correctness. A loader should distinguish XML well-formedness, SCXML structural validity, references to existing state IDs, legal state specifications, supported datamodel languages, and runtime expression errors. Attribute combinations such as event/eventexpr or initial plus a child <initial> have their own rules. Unique IDs and legal state ancestry are not optional authoring niceties.

The following standard-library example safely inspects structure only. It neither evaluates expressions nor executes statecharts. That explicit boundary is important when teaching the difference between XML syntax tooling and a conformant SCXML processor.

from xml.etree import ElementTree as ET
SCXML = "http://www.w3.org/2005/07/scxml"
doc = '''<scxml xmlns="http://www.w3.org/2005/07/scxml"
 version="1.0" initial="idle"><state id="idle">
 <transition event="begin" target="running"/></state>
 <state id="running"><transition event="finish" target="done"/>
 </state><final id="done"/></scxml>'''
root = ET.fromstring(doc)
assert root.tag == f"{{{SCXML}}}scxml"
states = [e.attrib["id"] for e in root.iter()
          if e.tag in {f"{{{SCXML}}}state", f"{{{SCXML}}}final"}]
assert states == ["idle", "running", "done"]
assert len(states) == len(set(states))
transitions = root.findall(f".//{{{SCXML}}}transition")
assert [t.get("event") for t in transitions] == ["begin", "finish"]
print("XML inspection passed; no SCXML execution was performed")

A Running Example: Request Review

We will model a request that begins in Draft, moves to Reviewing, and ends in either Approved or Rejected. A deliberately small version demonstrates event selection, while later extensions add nested review stages, an approval guard, completion, and notification. Suppose the application posts submit, approve, or reject events. The expected control behavior is: only a draft can be submitted; only a reviewing request can be approved or rejected; a terminal decision is not silently reversed by a stray event.

The model should not treat entry into Approved as proof that money has been disbursed, a database transaction has committed, or an approval email has been delivered. Such effects require external acknowledgments and their own explicit states. The SCXML control model can record decision intent and react to a later response, but the host services own external side effects and their durability.

Baseline Request-Review SCXML

This document uses event="submit", a guard on approve, and a datamodel value. The ECMAScript datamodel is named explicitly because the expressions are ECMAScript, not generic XML or Python. The outcome assignment and the target transition are part of the same SCXML microstep, but they do not constitute a database transaction.

<?xml version="1.0" encoding="UTF-8"?>
<scxml xmlns="http://www.w3.org/2005/07/scxml"
       version="1.0" datamodel="ecmascript" initial="draft">
  <datamodel>
    <data id="authorized" expr="false"/>
    <data id="outcome" expr="'pending'"/>
  </datamodel>
  <state id="draft">
    <transition event="submit" target="reviewing"/>
  </state>
  <state id="reviewing">
    <transition event="grant.authorization">
      <assign location="authorized" expr="true"/>
    </transition>
    <transition event="approve" cond="authorized" target="approved">
      <assign location="outcome" expr="'approved'"/>
    </transition>
    <transition event="reject" target="rejected">
      <assign location="outcome" expr="'rejected'"/>
    </transition>
  </state>
  <final id="approved"/>
  <final id="rejected"/>
</scxml>

grant.authorization is a teaching event, not an authentication protocol. In a real service, trust must come from a verified authorization decision, not an untrusted caller's ability to send that event. Notice also that <final> beneath the root ends processing. If later events must be handled (appeals, reversals, archival), the approved/rejected modes would instead need nonfinal states or an enclosing compound workflow.

Formal Operational Configuration

For analysis, represent an interpreter snapshot as C = (A, D, H, Qᵢ, Qₑ, I, R), where A is the active-state set, D is datamodel state, H holds saved histories, Qᵢ and Qₑ are internal and external event queues, I tracks invocations, and R records whether the session is running. This is a teaching abstraction, not a claim that the Recommendation mandates an implementation's internal data structures. The official requirements specify observable behavior; an implementation can store the same information differently.

A processing event binds the protected _event variable, giving guards and actions access to the current event's name, data, and selected metadata. During an eventless transition, _event need not denote a newly selected external event; a prior bound event may remain available. Therefore, eventless guards should not depend on the fiction that a fresh event has just arrived. The active configuration and datamodel together determine which transitions can fire.

External and Internal Event Queues

SCXML separates externally delivered events from events generated for processing within the same session. An action <raise event="x"/> places event x at the back of the internal queue; it does not recursively interrupt the action or immediately execute another transition. An external event is considered only when the processor has reached internal stability, with no eligible eventless transition and no unprocessed internal event that enables a transition.

The separation makes run-to-completion intelligible: if submit triggers state entry that raises validate.complete, the resulting internal transition can execute before an already queued external cancel is reconsidered. The exact processing order matters for acceptance tests, user-interface feedback, and security review. “Events are FIFO” is not a sufficient model: there is FIFO within queues, but eventless transitions have their own precedence, and the internal queue is processed before returning to the external queue.

Macrosteps and Microsteps

A microstep is execution of the selected, compatible set of transitions. It may exit states, perform transition content, enter new states, update the datamodel, and queue more events. A macrostep is the sequence of such microsteps that finishes when no eventless transition is enabled and the internal event queue has been exhausted. A macrostep may therefore involve more than one state transition after a single external input, and it may fail to terminate if an eventless transition or internally raised event repeats indefinitely.

The word atomic is sometimes used informally for run-to-completion. In SCXML, it does not promise ACID atomicity of external I/O, and it should not imply that all side effects can be rolled back if a later action fails. It primarily means the next ordinary external event is not selected while internal processing is unfinished. The host's thread model, callbacks, transport, and database commits still require independent design.

Eventless Transitions Take Priority

An SCXML transition lacking the event attribute is enabled by its guard (or by default when no guard is supplied). The processor examines enabled eventless transitions before removing the next internal event. Only if no eventless transition is available does it consider the queued internal events; only after internal stability does it select new external events. This rule makes eventless transitions useful for immediate routing after a datamodel update, but it also creates potential livelocks.

The distinction between event="*" and an absent event is essential. The former matches a named event, including names outside a narrow family, subject to transition priority; the latter requires no event at all. A wildcard handler cannot stand in for automatic entry routing, and an eventless transition cannot be expected to consume a message. Similarly, an eventless guard that is always true may repeatedly fire unless the state/variable update disables it.

A Pure Python Queue-Order Demonstration

This implementation is a small conceptual experiment, not a complete SCXML engine. It models one stable-state loop, a transition caused by an external event, a queued internal event, and an eventless follow-up. Its purpose is to make ordering testable without falsely equating the example to Appendix D's full parallel-selection algorithm.

from collections import deque
external = deque(["submit", "cancel"])
internal = deque()
state = "draft"
validated = False
trace = []
while external or internal or (state == "review" and validated):
    if state == "review" and validated:
        trace.append("eventless:review->approved")
        state = "approved"
        validated = False
        continue
    if internal:
        event = internal.popleft()
        trace.append("internal:" + event)
        if state == "review" and event == "validation.ok":
            validated = True
        continue
    event = external.popleft()
    trace.append("external:" + event)
    if state == "draft" and event == "submit":
        state = "review"
        internal.append("validation.ok")
assert trace == ["external:submit", "internal:validation.ok",
                 "eventless:review->approved", "external:cancel"]
assert state == "approved"
print(" | ".join(trace))

In a genuine SCXML interpreter, the eventless check is performed at each internal-stability point, and transition content is ordered with all exits and entries. This example isolates scheduling rather than pretending to implement state hierarchy, conflict filtering, expression evaluation, or <invoke>.

Event Names, Descriptors, and Prefix Matching

SCXML events have names such as payment.approved, payment.declined, or error.execution. A transition's event attribute may contain space-separated descriptors. Descriptor matching is case-sensitive and token-based: descriptor payment matches payment and payment.approved, but not payments.approved or paymentX. A descriptor ending in .* is an alternate spelling of the same token-prefix intent. A sole * matches any named event. This design supports broad error handlers such as event="error" and narrower application handlers without requiring a separate transition for every suffix.

Event-prefix matching does not itself choose the most specific string. SCXML's transition-selection algorithm considers active-state depth and transitions in XML document order. If one state declares two enabled transitions and the first has descriptor payment, that earlier transition may win over a later payment.approved transition, even for the approval event. To obtain the desired result, place guarded or specific transitions before their broad fallbacks, or organize them in deeper states where descendant priority is appropriate.

Executable Event-Descriptor Matcher

The following Python function demonstrates the token-prefix rule in isolation. It does not implement the complete permitted lexical space of SCXML event descriptors or error handling for malformed documents; it tests the conceptual matching cases used in this article.

def match_descriptor(descriptor, event):
    descriptor = descriptor.removesuffix(".*")
    if descriptor == "*":
        return True
    d, e = descriptor.split("."), event.split(".")
    return len(d) <= len(e) and d == e[:len(d)]

def match_any(descriptors, event):
    return any(match_descriptor(d, event)
               for d in descriptors.split())

assert match_any("payment error", "payment.approved")
assert match_any("error.*", "error.execution")
assert not match_any("payment", "payments.approved")
assert match_any("*", "any.named.event")
assert match_any("payment.approved", "payment.approved")
assert not match_any("payment.approved", "payment.declined")
print("Descriptor examples passed")

A production parser should validate descriptor syntax against SCXML's defined datatype rather than silently normalize unusual event names. Case conversion, trimming internal tokens, or using a generic substring check can alter application control flow and should be avoided.

Transition Sources and Ancestor Search

In SCXML, a transition is sourced from its enclosing <state> or <parallel> element. When an event is available, the interpreter searches for an enabled transition from each active atomic state. It inspects transitions on that atomic state in XML document order, then searches its ancestors from nearest to farthest. The first suitable transition within each source-state scan is collected; the candidate set is later filtered for conflicts across parallel regions. Eventless transitions use a parallel process without an event match.

This is often described as a preference for descendant transitions over ancestor defaults. The nuance is that selection occurs for each active atomic state when there are parallel regions. Two candidates can be locally optimal yet conflict globally if their exit sets overlap. Thus the phrase “take the deepest transition” is helpful for a single branch but insufficient as a general implementation algorithm.

Guards and Observable Data Snapshots

The cond attribute is evaluated according to the selected datamodel. When a transition candidate is evaluated, its guard must be true, or absent, for the transition to be enabled. The same event may enable different transitions under different variable valuations; data conditions are therefore part of the control state. cond is intended as a test, not an authorized channel for sending money, mutating databases, or publishing output.

One cannot assume every possible guard is evaluated once at a single global snapshot across a macrostep. After a microstep executes <assign> or other actions, the processor may examine guards again in the new configuration. The specification requires precise execution and transition order, while evaluation cost and expression-language behavior follow the chosen datamodel. For testing, capture the configuration and relevant variable values before each transition-selection pass, not only at the beginning of the external event.

Document Order and Transition Priority

Within a given source state, the first enabled transition in document order is selected. An author might write a broad fallback before a narrow condition and be surprised that the fallback always wins. To illustrate, consider a reviewing state with transitions event="result" and event="result.approved" in that order. When result.approved arrives, the first descriptor matches by prefix. The later transition is never selected by that state's initial scan.

This is an operational requirement, not merely a formatting convention. Reviewers should inspect source order and independently exercise overlapping descriptors or guards. If two rules genuinely must act together, placing them in one sequential state will not produce two transitions from that same local scan; an explicit combined action, an internal follow-up event, or properly designed parallel regions may be required.

An Executable Priority Counterexample

This small program demonstrates how document order defeats a naïve “most-specific descriptor first” expectation. It intentionally models one source state only.

def matches(pattern, event):
    return pattern == "*" or event == pattern or event.startswith(pattern + ".")

rules = [
    ("result", "generic-result"),
    ("result.approved", "approved-result"),
]
def choose(event):
    return next((action for pattern, action in rules
                 if matches(pattern, event)), None)

assert choose("result.approved") == "generic-result"
rules.reverse()
assert choose("result.approved") == "approved-result"
assert choose("result.rejected") == "generic-result"
print("Earlier enabled transition takes priority within its source")

This example does not supersede SCXML's ancestor priority or cross-parallel conflict rules. It isolates the effect of ordering two transition elements inside the same state.

Selecting a Compatible Transition Set

With no parallel states, an event normally yields at most one selected transition. With active <parallel> regions, the same event can enable one transition in each active branch. SCXML selects a compatible set; it does not blindly execute every locally matching rule. A candidate's exit set consists of the active states that taking that transition would leave. Two transitions conflict when their exit sets intersect in the current configuration.

For example, an event abort may enable a local Task.Running -> Task.Stopped transition while an ancestor declares Operating -> Failed, which exits the entire parallel system. Both cannot simply run and produce simultaneously active Stopped and Failed states. Priority prefers a transition whose source is a descendant of another candidate's source; otherwise document order breaks the tie among conflicting sources. Nonconflicting transitions in different regions can execute in one microstep.

Why Exit-Set Intersections Matter

Testing target names alone is not adequate conflict detection. A transition that moves between descendants of a single region may exit only that region's active subpath, while another that crosses the parallel boundary exits the common parallel ancestor and all active children. Their exit sets, rather than their immediate target IDs, express whether the outcomes can coexist. Targetless transitions have empty exit sets and, under the SCXML conflict definition, do not conflict with state-changing transitions on this basis.

The set of active states used in exit-set computation is the configuration at selection time. If a transition has no target, its content may still update data or raise events. It is therefore incorrect to describe a targetless transition as a no-op; it is simply a transition without structural entry or exit. Stateful side effects may produce later eventless transitions, changing the configuration in another microstep.

A Simplified Parallel Conflict Filter

The demonstration below makes two candidate exit sets explicit. It does not claim to reproduce the entire W3C conflict algorithm, especially ancestry-based priority; its narrow purpose is to show why disjoint transitions can coexist but overlapping ones cannot.

candidates = [
    ("Task:pause", {"Task.Running"}),
    ("Network:disconnect", {"Network.Online"}),
    ("Operating:abort", {"Task.Running", "Network.Online", "Operating"}),
]

def compatible(group):
    exited = set()
    for _, exit_set in group:
        if exited.intersection(exit_set):
            return False
        exited.update(exit_set)
    return True

assert compatible(candidates[:2])
assert not compatible([candidates[0], candidates[2]])
assert not compatible([candidates[1], candidates[2]])
print("Parallel local changes are compatible; ancestor exit conflicts")

A production interpreter must additionally calculate exit sets from effective targets and the transition domain, account for history expansion, and apply the prescribed descendant/document-order precedence. Use the W3C SCXML interpretation algorithm for that complete procedure.

The Microstep Execution Contract

After the optimal compatible transition set is chosen, SCXML executes it in three phases: exit the states that must be exited; execute the transitions' content; enter the states that must be entered. This phase separation is vital. A transition action cannot assume its new target's <onentry> handler has already run, and an exiting state's <onexit> handler executes before the transition's own actions. With parallel regions, multiple transitions can be selected, but their effects still follow the specified ordered execution rules rather than arbitrary thread interleaving.

Exit ordering is descendants before ancestors, using reverse document order as appropriate among states at comparable levels. Entry ordering is ancestors before descendants, using document order to resolve ties. Executable content within ordered elements follows its defined sequence. Implementations may optimize how they compute these sets, but a diagnostic trace must reflect these meaningful orders.

Entry and Exit Effects in a Complete XML Example

This example logs an entry/exit path. It is intended for a conforming SCXML processor supporting the ECMAScript datamodel and <log>; log transport and formatting depend on the host. The expected order after next is leave-left, cross, enter-right. The enclosing workspace state remains active and does not re-enter.

<scxml xmlns="http://www.w3.org/2005/07/scxml"
       version="1.0" datamodel="ecmascript" initial="workspace">
  <state id="workspace" initial="left">
    <state id="left">
      <onexit><log label="stage" expr="'leave-left'"/></onexit>
      <transition event="next" target="right">
        <log label="stage" expr="'cross'"/>
      </transition>
    </state>
    <state id="right">
      <onentry><log label="stage" expr="'enter-right'"/></onentry>
    </state>
  </state>
</scxml>

If a UI is refreshed on the cross action, it must not assume the target state's entry action has already finished. A cleaner integration typically publishes a stable-state snapshot or an externally observable confirmation at a deliberate boundary, not an accidental intermediate trace of the interpreter's internal phases.

An Executable Exit–Action–Entry Recorder

This Python example implements the ordering for one explicitly specified simple transition. It provides a regression-test pattern without claiming to cover all SCXML topology cases.

trace = []
def exit_state(name): trace.append("exit:" + name)
def run_action(name): trace.append("action:" + name)
def enter_state(name): trace.append("enter:" + name)

active = {"workspace", "left"}
for name in ["left"]:
    exit_state(name)
    active.remove(name)
run_action("cross")
for name in ["right"]:
    active.add(name)
    enter_state(name)
assert active == {"workspace", "right"}
assert trace == ["exit:left", "action:cross", "enter:right"]
print(" > ".join(trace))

For a deeper machine, exit every active descendant required by the exit set, and enter the required ancestors and descendants. For parallel machines, compute the full selected transition set before applying this ordered change. A program that selects and executes region A completely before examining region B can accidentally make the second guard depend on the first transition's side effects, yielding behavior inconsistent with the mandated transition-set selection.

Transition Domains and Least Common Compound Ancestors

For a state-changing transition, the transition domain identifies the boundary under which states are exited and entered. In the ordinary external case, it is determined using the least common compound ancestor of the source and effective targets (or the <scxml> wrapper when needed). The word compound matters: the least common node in a generic tree algorithm may not be the appropriate SCXML domain. The effective target expands history pseudo-states before the domain is resolved.

For an eligible internal transition from a compound state to its own descendant, the domain may be the source itself. That preserves the source while exiting and re-entering relevant descendants. For external transitions, the source can be exited and re-entered as dictated by the domain. The exact set must be calculated from the configuration and transition type; a superficial arrow between two state IDs does not describe sufficient behavior.

Internal Versus External Transition Types

The type attribute on <transition> defaults to external. The special type="internal" treatment applies when the source is a compound state and every effective target is a proper descendant of that source. In that case the source remains active, while descendants can be exited and entered. When those conditions do not hold, an internal transition's exit-set behavior falls back to the external case. This is not an unrestricted guarantee that “internal transitions never cause exits.”

Suppose Reviewing contains Waiting and Checking. A transition sourced on Reviewing, targeting Checking, and marked internal can move between those descendants without executing the Reviewing state's <onexit> or <onentry>. The same source/target with default external semantics can exit and re-enter Reviewing. That difference affects history capture, side effects, invocation cancellation, and data initialization assumptions; it should be an explicit design decision.

Targetless Transitions and Self-Transitions

A <transition event="heartbeat">...</transition> with no target executes its content without changing active states. It does not run entry or exit handlers merely because its source handled the event. A transition with target="sameState" is different: its exit and entry behavior follows SCXML's transition-domain rules, which may include reentering that state. Treating these as aliases is a common bug in table-driven implementations.

Targetless transitions are useful for counters, metrics, internal notifications, or acknowledgments that do not change the mode. Nevertheless, a targetless transition can still enqueue an event, update a guard variable, or invoke an extension action that affects external systems. Tests should assert both the unchanged active configuration and the expected effects, rather than treating unchanged state as proof that nothing happened.

Executable Targetless Versus Re-Entry Illustration

The distinction can be tested with a trivial model. We model the entry/exit callback counts instead of pretending to run a full SCXML interpreter.

class Mode:
    def __init__(self):
        self.active = "watching"
        self.entries = 1
        self.exits = 0
        self.pulses = 0
    def heartbeat(self):
        self.pulses += 1           # targetless content
    def restart(self):
        self.exits += 1            # source->source external
        self.entries += 1

m = Mode()
m.heartbeat()
assert (m.entries, m.exits, m.pulses) == (1, 0, 1)
m.restart()
assert (m.entries, m.exits, m.pulses) == (2, 1, 1)
print("Targetless action preserves state entry and exit counters")

In production, prefer a genuine SCXML conformance test for the exact nested topology being used, because a self-targeted transition's exit domain is sensitive to its source and ancestor relationships.

Completion and Final-State Events

When the processor enters a <final> inside a compound state, it generates a done.state.ID internal event where ID is the compound state's ID. A parallel state completes when all its child regions are in final states, at which point the appropriate done.state.* event is generated for the parallel parent. Entering a direct child <final> of <scxml> ends the session rather than merely generating an event for further processing by that same session.

Completion is therefore structural, not an inference from a business-status variable such as approved=true. A service might be approved in its data model while the workflow remains in a nonfinal AwaitingDispatch state. Conversely, a compound review can reach its <final> and produce a completion event while the enclosing application continues. Document the particular layer at which a final state has been reached.

Completion as an Internal Event: XML Example

Here, entering reviewDone completes the compound state review, producing the internal event done.state.review. The enclosing root state workspace can handle that completion event and transition to its own final child. This is distinct from ending the entire SCXML interpreter.

<scxml xmlns="http://www.w3.org/2005/07/scxml"
       version="1.0" initial="workspace">
  <state id="workspace" initial="review">
    <state id="review" initial="waiting">
      <state id="waiting">
        <transition event="approve" target="reviewDone"/>
      </state>
      <final id="reviewDone"/>
    </state>
    <transition event="done.state.review" target="workspaceDone"/>
    <final id="workspaceDone"/>
  </state>
</scxml>

The done.state.review event is placed in the internal queue and processed under run-to-completion semantics. On entering workspaceDone, the processor can also generate done.state.workspace, although this example defines no handler for it and has not entered a top-level final. If the intent is to terminate the session, a separate top-level <final> and transition should be supplied.

History, Default Entry, and Saved Configurations

A <history> child records prior descendant activity when its parent is exited. A shallow history records immediate active children; a deep history records active atomic descendants. If the parent has not been visited before, the history element's default <transition> provides the fallback. A history transition target is a specification of which configuration to restore, not an ordinary node that remains active as a leaf.

In parallel systems, restoring deep history may entail multiple atomic descendants—one in each region. An implementation must reintroduce necessary ancestors and any unfilled default regions to obtain a legal configuration. For systems with a changing schema or external resources, stored history alone cannot guarantee that resumed operations remain valid; the host must validate permissions, referenced objects, and invocation assumptions when restarting work.

A Complete History Declaration

The history pseudo-state lives inside the parent whose configuration is remembered. A transition targeting that history element requests restoration, not entry into a durable state named recent.

<scxml xmlns="http://www.w3.org/2005/07/scxml"
       version="1.0" initial="editor">
  <state id="editor" initial="typing">
    <history id="recent" type="deep">
      <transition target="typing"/>
    </history>
    <state id="typing">
      <transition event="preview" target="previewing"/>
    </state>
    <state id="previewing">
      <transition event="type" target="typing"/>
    </state>
    <transition event="pause" target="paused"/>
  </state>
  <state id="paused">
    <transition event="resume" target="recent"/>
  </state>
</scxml>

After preview then pause, resume returns to previewing using stored deep history. A fresh session beginning in editor starts at typing. The semantics of restarting an interpreter process and recovering a previous session snapshot are separate from SCXML's in-session history construct; durable recovery requires a persistence design.

Datamodel Choices and Expression Languages

SCXML defines abstract mechanisms for variables, guard expressions, assignments, parameters, and system data, but it does not require every implementation to support one universal language for those expressions. A document's datamodel attribute and the processor's supported datamodels determine valid syntax and evaluation behavior. The standard describes the ECMAScript and null datamodels and provides extensibility; a separate W3C specification addresses an XPath datamodel. A fragment containing cond="count > 0" must not automatically be assumed portable to a processor using a different expression language.

A processor must maintain protected system variables such as _event, _sessionid, _name, and _ioprocessors as applicable to the datamodel. Document authors should not attempt to overwrite them with ordinary <assign> statements. Application data should be declared with <data> entries and given names whose ownership and value types are clear. Failure to separate system and application variables produces brittle, processor-specific code.

Early Versus Late Data Binding

The SCXML root's binding attribute controls when declared data is initialized. With early binding, the interpreter initializes data declarations at session startup; with late binding, state-local data is initialized upon the state's first entry. This distinction is not the same as initializing data every time the state is entered. The W3C algorithm records whether a state's first entry has occurred so that an exit followed by re-entry does not blindly reset its values.

For example, an Editing state's local retryCount might be initialized before any active entry under early binding, or when Editing is first entered under late binding. A later transition that exits and re-enters Editing does not, merely because of late binding, reset the count to its original value. To reset the value deliberately, use explicit executable content. For predictable restart behavior, document whether the host creates a new SCXML session or restores a prior session snapshot.

Data Assignment and Guard Evaluation

<assign location="..." expr="..."/> updates a datamodel location as executable content. A guard cond="..." reads current values, and those values can change across successive microsteps within one macrostep. For clarity, model a business decision as two separate concerns: control eligibility (guard) and authorized business mutation (external system). An integer counter inside a statechart is not an authoritative financial ledger, nor does setting approved=true prove that a third-party authorization succeeded.

Side effects inside actions can introduce errors and trigger error.execution events. An implementation may also support scripts or custom executable-content elements. Those capabilities require careful consideration of input validation, sandboxing, logging, and failure handling. Test both the success path and expression failures; a misspelled variable name or invalid type is a runtime event source, not merely a cosmetic defect in a diagram.

Assignment and Automatic Routing Example

The following example demonstrates a deliberate post-update eventless route. The XML escapes the comparison operator for attribute validity and uses the ECMAScript datamodel explicitly. When increment is received twice, the second assignment makes count equal to two, enabling the eventless transition to finished before another external event can be selected.

<scxml xmlns="http://www.w3.org/2005/07/scxml"
       version="1.0" datamodel="ecmascript" initial="counting">
  <datamodel><data id="count" expr="0"/></datamodel>
  <state id="counting">
    <transition event="increment">
      <assign location="count" expr="count + 1"/>
    </transition>
    <transition cond="count &gt;= 2" target="finished"/>
  </state>
  <final id="finished"/>
</scxml>

The first increment is a targetless transition that changes only data; the eventless test then fails. On the second increment the data update succeeds and the eventless transition becomes eligible. A static event graph that shows only arrows between states would miss this important intermediate variable change and could incorrectly describe when finished becomes active.

A Small Python Model of Datamodel Updates

This independent, executable illustration verifies the intended state/data evolution. It is not a standard-complete evaluator for SCXML's ECMAScript datamodel.

state = "counting"
count = 0
trace = []
for event in ["increment", "increment", "increment"]:
    if state != "counting":
        trace.append((event, state, count, "ignored"))
        continue
    if event == "increment":
        count += 1
        trace.append((event, state, count, "assigned"))
    if state == "counting" and count >= 2:
        state = "finished"  # eventless follow-up
        trace.append(("eventless", state, count, "entered"))
assert trace == [
    ("increment", "counting", 1, "assigned"),
    ("increment", "counting", 2, "assigned"),
    ("eventless", "finished", 2, "entered"),
    ("increment", "finished", 2, "ignored")
]
print(trace)

For the real XML example, entering a top-level <final> halts processing; this illustration records the third event as “ignored” for teaching purposes rather than pretending the terminated interpreter still consumes messages. Assertions about actual post-termination dispatch require testing the host's event-transport lifecycle.

The Protected `_event` Structure

When the interpreter dequeues a named internal or external event, it binds _event to the event that is being processed. Required event fields include name, type, sendid, origin, origintype, invokeid, and data, with detailed representations depending on the datamodel. Guards can inspect _event.data, but should not assume the origin was authenticated solely because a field was populated. A host may attach transport-derived identity separately, and that identity must be validated in its trust context.

The _event binding remains associated with the current named event while its selected transitions and their exit/entry content execute. In a later eventless microstep, authors should avoid relying on unstated “new event” semantics: there was no fresh dequeue just because an eventless guard was examined. If a decision should be attributable to a specific triggering message, store its validated data explicitly and log the relevant event or request correlation ID.

Error Events and Exceptional Conditions

SCXML specifies error event families such as error.execution, error.communication, and error.platform. Once a processor has begun executing a well-formed document, runtime errors are signaled as internal events with names beginning error.. An event="error" transition can provide a broad fallback because SCXML's event-prefix matching accepts error.execution and related events. A more specific handler in a descendant state can take priority according to normal transition-selection rules.

Error events are events, not mandatory C-style exceptions that unwind every stack frame. A guard or action failure may generate an error that is processed after the current executable-content block has progressed according to the specified semantics. Applications must define how a failure affects queued work, outstanding messages, incomplete side effects, and visible status. Silence in a trace is not evidence that no failure occurred; instrument the processor's error channel and host transport separately.

`<raise>` Versus `<send>`

<raise event="..."/> adds a named event to the same session's internal queue, with no message body mechanism of its own. <send> can direct an event and associated data to an SCXML session or an external endpoint via an event I/O processor, and can request delayed delivery. The event's destination and configured processor determine whether it returns to the current session as internal traffic, appears in an external queue, or travels to another component.

Do not simplify the distinction to “raise is synchronous and send is asynchronous.” A <raise> statement runs during executable content, but the resulting event is queued and processed later, not recursively dispatched at the exact statement. A <send> statement's transport semantics and delivery guarantees depend on the event I/O processor; the absence of an error event does not establish successful business-level receipt. Describe the queue and delivery path explicitly.

Sending Internal Events Without Recursive Dispatch

The SCXML Event I/O Processor defines destinations including the current session. A standards-aware integration must choose the correct processor and destination; a symbolic self-target should not be conflated with calling a local handler on the same programming-language stack. Delayed messages add another scheduling layer. The example below concentrates on guaranteed <raise> ordering, without relying on optional transport integration.

<scxml xmlns="http://www.w3.org/2005/07/scxml"
       version="1.0" initial="first">
  <state id="first">
    <transition event="advance" target="second">
      <raise event="follow.up"/>
    </transition>
  </state>
  <state id="second">
    <onentry><log label="stage" expr="'entered second'"/></onentry>
    <transition event="follow.up" target="third"/>
  </state>
  <state id="third"/>
</scxml>

After advance, the processor completes the transition to second—including second's entry content—before handling follow.up in a subsequent microstep of the same macrostep. Another external event waiting in the queue cannot intervene between these internal operations. That conclusion follows from the scheduling rules, not from a special interpretation of the string follow.up.

Delayed Sends and Cancellation

A <send> action may specify a delay, and <cancel> can request cancellation of a delayed send using its identifier. Cancellation is best-effort and applies within the permitted session scope: a message already delivered or dispatched cannot be “unsent” merely by issuing <cancel>. When implementing timeouts, distinguish timer was scheduled, timer canceled before dispatch, and timeout event was already enqueued; these are not interchangeable facts.

A robust timeout design assigns a unique correlation ID to each outstanding request or operation, treats late replies idempotently, and guards against races between cancellation and delivery. The statechart can represent these races, but a distributed scheduler still governs actual delivery. Avoid relying on wall-clock precision that the event I/O processor or host has not promised.

Invocation Lifecycle and Stable-State Scheduling

<invoke> starts a supported external service or child process under the chosen invocation type. In SCXML, invocation handlers are started at a stable macrostep boundary for states entered and not exited during that macrostep. A state entered and left immediately by eventless or internal transitions need not launch an invocation that would become obsolete before any external event is processed. This ordering is intentionally different from treating <invoke> as a simple synchronous line inside <onentry>.

An invocation's completion can generate done.invoke.ID, and errors or child events may be routed back. When a parent state is exited, active invocations associated with it are canceled under the processor's lifecycle rules. That cancels the statechart's invocation relationship; it does not necessarily undo every external activity or compensate an irreversible business effect. Cancellation and compensation should be separate operational concepts.

`<finalize>` and `autoforward`

When an external event arrives from an invoked child, an associated <finalize> handler can preprocess the event and update data before the parent's transition guards are evaluated. With autoforward, the processor can forward external events to invoked processes according to its rules. These mechanisms alter observable event processing and should be described in diagrams and tests, especially when the parent has multiple concurrent invocations or event names overlap.

A common mistake is to treat <finalize> as the same thing as a transaction finally-block or a guarantee of cleanup after any failure. It is a particular event-preprocessing construct for invocation results. If an invoked service must be released, compensated, or deduplicated, the host integration must implement those obligations using its own lifecycle controls and appropriate SCXML actions.

A Conceptual Invocation Trace

Suppose Processing is entered during external event start, then an internal ready is raised, and ready moves the machine to Waiting. An invocation declared in Processing should not be started if Processing was entered and exited before the machine reached a stable boundary. In contrast, an invocation declared in Waiting may begin after internal processing stabilizes. This demonstrates why “on entry” and “at stable invocation time” are not synonyms.

entered = []
active = "idle"
entered.append("Processing")
active = "Processing"
# Follow-up event is handled in the same macrostep.
entered.append("Waiting")
active = "Waiting"
invocations_to_start = [s for s in entered if s == active]
assert invocations_to_start == ["Waiting"]
assert "Processing" not in invocations_to_start
print("Stable-state invocation scheduling:", invocations_to_start)

This code is a pedagogical lifecycle sketch: it checks the principle that transiently visited states are excluded, not the complete queue, service-type, or cancel-invoke algorithm. A conformant processor must also account for existing invocations, document order, and errors generated while invocation begins.

Parallel Regions and Multiple Enabled Transitions

An active <parallel> element includes all its child regions. Each region may select a transition for the same event. If their exit sets do not overlap, SCXML can execute them within the same microstep. A communication-state region could respond to network.down while an editing-state region independently records that the user requested a local draft save. This is a model of multiple active behaviors, not a claim that the actions run simultaneously on two CPU cores.

The selected transition set is processed with ordered exit, transition, and entry phases. A processor must resolve conflicts before taking the microstep. Consequently, the author should not rely on parallel transitions as a way to create unsequenced writes to the same variable; where actions can interact, the specified ordering and shared datamodel must be analyzed explicitly. Independent regions are valuable for separation of concerns, not a substitute for concurrency engineering.

A Parallel SCXML Configuration

The following structurally complete example has a parallel root child with two regions. An event reset may trigger local transitions in both regions. Each region preserves its own active substate while satisfying the overall legal-configuration requirements.

<scxml xmlns="http://www.w3.org/2005/07/scxml"
       version="1.0" initial="operating">
  <parallel id="operating">
    <state id="task" initial="taskIdle">
      <state id="taskIdle">
        <transition event="begin" target="taskBusy"/>
      </state>
      <state id="taskBusy">
        <transition event="reset" target="taskIdle"/>
      </state>
    </state>
    <state id="network" initial="online">
      <state id="online">
        <transition event="lost" target="offline"/>
      </state>
      <state id="offline">
        <transition event="reset" target="online"/>
      </state>
    </state>
  </parallel>
</scxml>

After begin and lost, the active leaves are taskBusy and offline. A single reset event enables both regional transitions because their exit sets are disjoint. The resulting leaves are taskIdle and online. An additional ancestor-sourced reset transition that exited operating would raise a conflict-selection question and would require applying the standard's priority rules before assuming either outcome.

Reachability Under Macrostep Closure

For verification, the externally observable state machine is often best represented at stable macrostep boundaries, after eventless and internal transitions have completed. Two different internal traces can lead to the same stable active configuration and datamodel valuation. Collapsing the internal transitions may simplify client-facing tests, but it can hide important effects, logs, generated events, and nontermination risks.

A useful two-level model therefore records both microstep traces and macrostep outcomes. Microstep records support conformance and diagnosis; macrostep snapshots support user-facing behavior and integration contracts. For automated checking, specify the exact equivalence criterion: matching only active leaf states is weaker than matching datamodel values, queued events, invoked-service status, and externally emitted commands.

A Bounded Macrostep Explorer

The following finite example computes the closure of two internal follow-up rules after a hypothetical external event. The bound prevents a test from hanging if a faulty rule repeatedly produces itself. It is a simplified verifier for the teaching machine, not a W3C SCXML interpreter.

from collections import deque

def settle(state, queue, limit=20):
    queue = deque(queue)
    trace = []
    for _ in range(limit):
        if state == "review" and not queue:
            state = "ready"      # eventless routing
            trace.append("eventless:ready")
            continue
        if not queue:
            return state, trace
        event = queue.popleft()
        trace.append("internal:" + event)
        if state == "checking" and event == "ok":
            state = "review"
    raise RuntimeError("internal work exceeded bound")

state, trace = settle("checking", ["ok"])
assert state == "ready"
assert trace == ["internal:ok", "eventless:ready"]
print(state, trace)

For genuine SCXML, the closure algorithm must check eventless transitions before dequeueing each next internal event and must also account for datamodel updates, parallel transition sets, completion events, and service invocations. A step bound is an engineering safety policy; it does not change what the unconstrained specification permits.

Nontermination, Livelock, and Starvation

A macrostep may contain infinitely many microsteps. An always-enabled eventless self-cycle or repeated internal event can prevent the next external message from being processed. The distinction between deadlock and livelock matters: a deadlocked machine has no useful enabled progress, while a livelocked machine may actively execute transitions forever without reaching stability. From the user's perspective both can resemble an unresponsive service, but their diagnostics differ.

Guard eventless transitions so each execution makes progress toward disabling the condition, entering a different state, or exhausting a finite resource. Implement watchdogs, bounds, and observability at the host level; design safe failure behavior when a bound is hit. Do not assert that the W3C Recommendation itself imposes an automatic finite-microstep limit—an engine's cutoff is an additional operational choice.

Persistence, Restart, and Versioned Sessions

SCXML history is an in-session behavioral mechanism, not a universal durable checkpoint. A recoverable application may need to save the active-state configuration, datamodel, event queues, pending sends, outstanding invocation IDs, relevant history values, and a versioned representation of the machine definition. Restoring only the top-level state name can lose an active parallel region or replay a completed action. A rebooted host must also decide what to do with messages received during downtime and external effects already committed before a crash.

One defensible implementation pattern treats external operations as idempotent commands with unique identifiers, while persisting enough state to recognize acknowledgments and duplicates. The specification's run-to-completion model helps define logical processing boundaries but does not automatically supply durable queuing, transactionality, or exactly-once business effects. When machine definitions change, migrations should map old state IDs, datamodel schemas, and pending timer meanings explicitly. Test restart during transitions, between internal and external messages, and while an invocation is active.

Event Correlation and Idempotency

Distributed services can deliver an acknowledgment after a timeout, duplicate a response after a retry, or process a command before the client receives confirmation. A statechart should correlate each reply to the operation that produced it, rather than treating every event with the right name as a valid current response. The SCXML _event metadata can carry messaging context, and application data can include validated correlation keys; neither substitutes for authorization or replay protection.

An idempotent workflow distinguishes command issued, command accepted, effect confirmed, and effect reconciled. The external service may commit its change even if the statechart session crashes. On recovery, query or reconcile authoritative records rather than unconditionally repeating an action. In diagnostic traces, log operation IDs, invocation IDs, source identifiers, and transition outcomes without exposing passwords or sensitive event payloads.

Security and Trust Boundaries

SCXML interpreters process untrusted input through event data, expression evaluation, external resource loading, XML parsing, scripts, and send/invoke integrations. A secure implementation must bound resource use, disable unsafe XML features where applicable, validate event origin and payload schemas, enforce authorization at actual side-effect boundaries, and constrain where documents can send messages or invoke services. A statechart's internal variable named isAdmin is not an authorization authority if an attacker can inject an event that sets it.

The ability to trigger error handlers, wildcard transitions, or internal loops can itself become an attack surface. Apply quotas to event queues and microsteps, protect logging pipelines, limit external destinations, and exercise malformed and adversarial inputs. Where a statechart controls physical equipment or financial transactions, fail-safe and compensation behavior belongs in the domain's responsible system as well as in the control model. Never treat a standards-conformant statechart as evidence that an entire application is secure.

Trace Logging and Observability

A useful interpreter trace records the external event chosen, the active configuration before selection, relevant datamodel fields, candidate transitions and their source states, the chosen compatible set, exit and entry sets, executed actions, newly raised internal events, resulting configuration, and final macrostep stability. Log timestamps can help diagnose delays, but logical sequence numbers are often more important: two effects in one microstep may occur close enough in time that wall-clock ordering is misleading.

For production observability, distinguish specification-level facts from host-level I/O facts. “<send> executed” means the interpreter attempted a send under its configured processor; it does not mean an external recipient completed the requested operation. Record a separate acknowledgment. Likewise, an onentry trace is not necessarily a user-visible committed state if another eventless or internal transition immediately exits that state before the macrostep ends.

A Deterministic Trace Comparison Harness

A test harness can compare an observed sequence of logical events with an expected sequence. The example below uses normalized records so that irrelevant runtime timestamps do not obscure behavioral differences. An actual conformant test suite would receive these events from the processor under test, not manufacture them in its own expected-value function.

expected = [
    ("external", "submit"),
    ("select", "draft->review"),
    ("exit", "draft"),
    ("action", "enqueue:validation.ok"),
    ("enter", "review"),
    ("internal", "validation.ok"),
    ("select", "review->approved"),
    ("exit", "review"),
    ("enter", "approved"),
]
observed = list(expected)  # substitute processor trace in a real test
assert observed == expected
mutated = list(expected)
mutated[4], mutated[5] = mutated[5], mutated[4]
assert mutated != expected
print("Ordering regression would detect swapped entry/internal steps")

This is an assertion-pattern illustration. It does not certify a real SCXML processor or prove that every record named here is present in a vendor's logging API. Such observability must be provided by instrumentation or a purpose-built conformance harness.

Conformance Testing Strategy

A meaningful SCXML conformance program begins with feature inventory. Record which datamodels and event I/O processors are supported, how errors are surfaced, and which optional extension elements are enabled. Separate structural validation tests from behavioral execution tests. Construct small documents with one purpose each: root initialization, nested ancestor transitions, overlapping event descriptors, true/false guard pairs, targetless transitions, internal versus external transition types, parallel conflicts, history, completion events, delayed sends, and invocation lifecycle.

For each behavioral case, specify an initial configuration and datamodel, external event sequence, expected selected transitions, expected active configurations, observable action order, and any allowed platform variation. Compare a real processor with the normative Recommendation, its errata, and the available W3C test materials. Passing the executable Python demonstrations in this article does not constitute SCXML conformance; those scripts are small independent teaching models.

Comparing SCXML with UML and Framework-Specific Machines

SCXML is a W3C XML language with specific event-queue ordering, document-order rules, and defined I/O constructs. UML state machines are a modeling facility within a broader object-oriented notation and have their own semantics for regions, completion, and transition kinds. Framework-specific libraries may offer a JSON definition, callback APIs, promises, or actor systems with related but distinct behavior. Treat differences as meaningful even when the drawn state diagrams look nearly identical.

A migration needs a semantic mapping, not merely automated rewriting of state labels. Check priority, guard evaluation, history, action order, external events, queued internal follow-ups, effect cancellation, and invocation lifetimes. When no exact mapping exists, add explicit intermediate states or actions, adjust tests, and document the divergence. A chart that draws correctly after conversion might still change its behavior under an overlapping event or an error.

Common Portability and Integration Pitfalls

An SCXML document can be syntactically valid yet unavailable on a given engine because it requests an unsupported datamodel, I/O processor, extension action, or invocation type. Library implementations can also differ in which optional services they expose and how they bind event data to the host language. A platform may wrap the interpreter in a multithreaded architecture without changing the logical run-to-completion contract; another may expose only a subset of SCXML capabilities.

Avoid making portability claims without an explicit profile: the exact engine and version, supported features, tested XML documents, expected host transports, and known gaps. Do not silently reinterpret SCXML's ECMAScript expressions as another language or replace <raise> with arbitrary direct callbacks. For regulated or safety-sensitive integration, record a reproducible conformance baseline and retest after runtime upgrades.

Worked Scenario 1 — An Approval Workflow with Internal Validation

A request arrives in Draft; the submit external event moves it to Checking. The entry action initiates a local validation computation and raises validation.passed, which enters the internal queue. The processor finishes the transition to Checking, then processes the internal event and moves into Reviewing. Only once internal work stabilizes may it examine the next external event, perhaps cancel. A test must verify that cancel cannot intervene between the submit transition's entry actions and the internal validation transition.

If validation is instead a remote service, the flow should not pretend the remote acknowledgment has arrived immediately through <raise>. The remote operation belongs to <invoke> or a suitable <send> integration with an explicit waiting state and correlation ID. Its eventual response is subject to the external communication mechanism. The architectural distinction is between local, internally generated follow-up and external, independently scheduled completion.

Worked Scenario 2 — A Two-Region Upload Manager

The manager maintains Transfer and Connectivity regions beneath a <parallel> parent. After a file is queued, Transfer advances from Idle to Uploading while Connectivity remains Online. A network.down event changes the network region to Offline and may also cause a compatible transfer-region transition to Paused. If both changes have disjoint exit sets, the interpreter executes them in one microstep. If a parent-sourced fatal transition exits the entire parallel state, conflict resolution matters.

Tests should assert the complete active configuration, not only the current transfer mode. An engineer must additionally model acknowledgment, retry policy, byte-range validation, and durable transfer state outside the abstract event-selection rules. SCXML can coordinate those responsibilities, but it does not provide a resumable file-transfer protocol or data integrity checking merely because a <parallel> element exists.

Worked Scenario 3 — A Customer-Support Conversation

A support assistant is in CollectingDetails, nested under OpenConversation. A customer.message event matches a child transition that updates a transcript view, while the parent has a broad customer fallback for unrecognized customer events. Source priority allows the child to handle the recognized message without firing the parent's catchall. If two transitions within the child match the same message, their document order decides which one is chosen.

If a completion event indicates the customer finished a form, an eventless transition may route to ReadyForAgent when the required fields are present. The system should record which events were processed before a stable response is sent. It should also use verified channel identity and authorization; prefix matching a string such as customer.admin is not evidence that the sender is an administrator.

Worked Scenario 4 — A Network Recovery Supervisor

The supervisor has modes Connected, Waiting, and Recovering, with delayed retries. When a disconnect occurs, it enters Waiting, schedules a retry message, and may cancel that message if reconnection succeeds first. An event arriving just as <cancel> executes may already be dispatched. Accordingly, a retry handler checks the current generation number and connection state before performing work, rather than trusting cancellation as guaranteed prevention.

A genuine implementation must define the delay's time source, retry budget, and response correlation. A nonterminating eventless retry loop would starve future external events and consume resources; a bounded waiting state is better. Record whether the processor or an external scheduler owns outstanding timers when a process restarts.

Worked Scenario 5 — A Payment Authorization Integration

A payment request enters AuthorizationPending and invokes a payment service. An event done.invoke.auth42 or a provider-specific result may indicate completion, and <finalize> may normalize the returned data before guards select a success or failure branch. Authorization, capture, settlement, and ledger posting are distinct business events. The statechart should not mark all four complete because a single invocation returned without an error.

A crash may occur after the provider authorizes a charge but before the local system logs the response. Reissuing without an idempotency key could create a duplicate operation. The safe design persists correlation, reconciles provider state, and reserves compensating actions for cases where an external side effect must be reversed. SCXML run-to-completion is not a distributed transaction; that is the governing lesson.

Worked Scenario 6 — An Interactive Learning Assessment

A quiz statechart models PresentQuestion, CheckingAnswer, Feedback, and Complete. The learner's submit.answer event leads to CheckingAnswer, where an internal event may indicate locally computed scoring. A completed quiz enters a nested <final> that raises done.state.quiz, allowing the enclosing lesson session to move to ReviewSummary without terminating the entire application.

The learning platform also requires accessibility, assessment validity, and secure records. A learner can navigate backward visually without undoing a completed official submission. A correct statechart distinguishes display state from authoritative academic record and tests that an unauthorized client event cannot overwrite the score. Implementation is successful when SCXML behavior, learner experience, and institutional data controls agree.

Ten-Gate SCXML Engineering Framework

Gate Decision question Evidence required
1. Choose semantics Is SCXML 1.0 actually the execution contract? Standard/version and supported runtime profile
2. Validate structure Are the active configurations and targets legal? Document validation and initialization tests
3. Define events Which events are internal, external, or platform-generated? Event catalog, routing, and trust classification
4. Audit transition priority Which rule wins under overlap? Nested-source and document-order counterexamples
5. Analyze data Which datamodel and binding policy apply? Typed variables, guard cases, initialization tests
6. Check microsteps Are exits, actions, and entries correctly ordered? Instrumented microstep traces
7. Check macrosteps Do eventless and internal transitions reach stability? Bounded exploration and nontermination tests
8. Govern effects How do send, invoke, cancel, and failures behave? I/O processor profile and acknowledgment handling
9. Verify recovery Can a session restart without duplicating business work? Checkpoint, idempotency, migration, and replay tests
10. Establish conformance Does the chosen engine behave as claimed? Repeatable processor test suite against W3C requirements

The framework should be applied before production deployment and again when adding parallel regions, changing event names, upgrading an engine, or introducing new I/O integrations. Each gate concerns a distinct failure mode; passing an XML parser check does not satisfy the other nine.

Common Misconceptions

“Every external event causes one transition.” An external event can cause zero transition executions if no rule is enabled, or several microsteps when internal and eventless follow-ups occur. “All matching parallel transitions run.” Only a compatible optimal set runs, following conflict resolution. “Internal transitions have no exit/entry effects.” That description is false outside the defined compound-source/proper-descendant special case. “A wildcard is eventless.” event="*" matches a named event; an omitted event is eventless. “Late binding resets data at every entry.” It initializes state-local data on first entry.

“A successful <send> equals successful delivery.” Dispatch and external business acknowledgment are separate. “Final ends every containing machine.” A nested final generates completion events; a top-level final ends the SCXML session. “Run-to-completion makes I/O atomic.” The rule orders interpreter work but does not confer transaction semantics on external services. “The example Python engines are conformant.” They deliberately implement only narrow behavioral ideas. “Valid XML means valid SCXML.” Structural constraints, supported datamodels, and execution obligations extend far beyond XML well-formedness.

Review Questions

  1. Distinguish the internal event queue from the external event queue. Why must a processor examine eventless transitions before dequeueing an internal event?
  2. Define a microstep and a macrostep, then give an example of one external event producing three microsteps.
  3. If a child and its parent have eligible transitions for the same event, which candidate receives priority in the ordinary single-branch case?
  4. How can XML document order affect a decision even if an event descriptor appears more specific than an earlier one?
  5. What makes two parallel-region transitions conflict? Why are targetless transitions special under this criterion?
  6. Give the required order of exit handlers, transition content, and entry handlers.
  7. Under what conditions does type="internal" preserve the compound source state?
  8. Why is entering a nested final state different from entering a top-level final state?
  9. Explain the operational difference between <raise>, <send>, <invoke>, and <finalize>.
  10. Why is a session-history state insufficient for crash-safe recovery of an external payment workflow?
  11. How do early and late datamodel binding differ, and what happens on re-entry after first initialization?
  12. What evidence would you request before accepting a product's claim of SCXML 1.0 conformance?

Guided Exercises

Exercise A — Priority and overlap: Write a two-state document where event="error" occurs before event="error.execution" within the same state. Predict which transition wins when error.execution arrives. Reverse the XML order and repeat. State the difference between the event descriptor and a guard.

Exercise B — Microstep sequence: Start in Draft; let submit enter Checking, whose <onentry> raises check.ok; let check.ok enter Ready; and let an eventless guard route Ready to Complete. Write an ordered trace of exits, transition actions, entries, internal enqueue/dequeue, and stable state. Explain whether a queued external cancel can be processed between these steps.

Exercise C — Parallel conflict: Draw a <parallel> with two regions, each reacting locally to reset. Add a parent-sourced transition that exits the parallel state. Identify candidate transitions, compute their exit sets, and apply the descendant/document-order rules. Test the result in an SCXML processor.

Exercise D — Recovery: Design a payment flow with an invoke result, a timeout, and a later reconciliation step. Identify statechart data that must be checkpointed and business records that must remain authoritative. Specify a crash-restart test that proves one provider response cannot cause a duplicate capture.

Exercise E — Processor verification: Select an engine and list its supported datamodel and I/O processors. Run the priority, history, completion, error, and invocation cases from the conformance matrix. Record the exact version, input file, observed trace, expected behavior, and any documented profile limitations; do not describe a case as “passed” without execution evidence.

Glossary

Term Definition
Active configuration Legal set of currently active states and their required ancestors
Atomic state State with no child states, including a <final> for algorithmic purposes
Compound state State with nested state children and one active child branch
<parallel> State whose child regions are simultaneously active
Eventless transition Transition without an event attribute, tested by guard availability
Event descriptor Token-prefix pattern used to match a named SCXML event
Optimal transition set Compatible high-priority enabled transitions selected for a microstep
Exit set Active states exited by a transition or compatible transition set
Transition domain Boundary used in determining exit/entry behavior of a transition
Microstep One execution of an optimal transition set with its ordered effects
Macrostep Internal processing sequence ending in a stable configuration
Run-to-completion Rule that another external event is not selected during unfinished internal processing
<raise> Executable action that enqueues an internal event in the current session
<send> Executable action for event delivery through an event I/O processor
<invoke> Construction starting an external service under a supported invocation type
<finalize> Preprocessing executable content for events returned from an invocation
<cancel> Best-effort cancellation of a delayed send created by the session
_event Protected datamodel variable describing the most recently dequeued event
done.state.* Platform-generated event indicating a compound or parallel completion
done.invoke.* Event signaling completion of a particular invocation
Shallow history Saved immediate active child configuration of a parent
Deep history Saved atomic descendant configuration of a parent
Early binding Data declarations initialized at session startup
Late binding State-local data initialized upon first entry of that state
Conformance test Executed case comparing processor behavior with a specified normative requirement

Suggested Study Pathway

Start with Formal Transition Systems to understand configurations and paths. Study Extended Finite-State Machines for datamodel guards, Hierarchical Statecharts for nesting and parallel regions, then this SCXML article for exact operational rules. Next examine Safety and Liveness Properties, State-Space Exploration and Model Checking, and State Machine Implementation Patterns.

For an implementation-oriented pathway, begin with the complete XML examples, then construct the test matrix as executable SCXML processor tests. Only after matching the relevant normative behavior should a project add external sends, invocations, durable checkpoints, and platform extensions. This sequence separates semantic correctness from system integration reliability, which is essential for trustworthy applications.
