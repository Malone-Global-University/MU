Definition and Scope

A formal transition system is a mathematical description of how a system can move between configurations. The model identifies possible states, designates starting states, and states which changes are permitted. In a labeled transition system (LTS), a transition also carries an action or event label such as submit, approve, timeout, or retry. The model can describe a small finite controller, a workflow with many records, a concurrent protocol, or an abstract representation of a program. Its purpose is to turn informal expectations into a precise set of possible behaviors that can be examined independently of any particular programming language or interface.

The essential question is not whether the system resembles a diagram. It is whether an observer can determine what the diagram means: which initial configurations are possible, what each edge permits, what a missing edge means, and what claims the model can justify. A picture with arrows but no declared semantics may conceal more uncertainty than it resolves. A well-specified relation can be represented by a diagram, mathematical formula, transition table, executable enumerator, or formal verification language without changing its intended meaning.

A transition system is a broader foundation than a deterministic finite automaton (DFA). A conventional complete DFA is a specialized recognizer with a finite state set, a total next-state function for each input symbol, and an acceptance criterion for finite strings. A general transition system need not be a string recognizer; it may be nondeterministic, partially specified, infinite-state, event-driven, or concerned with operational behavior rather than acceptance. Later State Machines specialist articles address each specialization in depth. This article establishes the shared semantics on which those treatments depend.

Why Formalization Matters

Informal process descriptions hide assumptions about ordering, concurrency, failures, and authority. Consider the statement: “A reviewer can approve a request after it has been submitted.” Does the request have to be in a pending state? Can two reviewers approve at once? Can a withdrawn request still be approved? Is approval allowed while a document is being revised? If no approval action is defined in a state, is the action forbidden or merely undocumented? Each interpretation corresponds to a different behavior set.

A transition model forces the author to answer these questions at the appropriate level of abstraction. It can make illegal transitions visibly absent, identify reachable failures, and support checks such as “a rejected request is never published.” It also exposes gaps in requirements: an undefined cancellation path is not automatically safe. The value lies in disciplined scope control. Model the variables relevant to the claim, state what the environment may do, and explicitly recognize what has been omitted.

The strongest results are conditional: under the specified state space, transition relation, initialization, and environment assumptions, a property holds or a counterexample exists. Formalization does not replace evidence about implementation correctness, hardware behavior, external policy, user conduct, or deployment conditions. It provides a rigorous contract against which such evidence can be collected.

A Mathematical Model

For this article, use the following labeled, proposition-observing transition system:

Formal notation: T = (S, Act, →, I, AP, L).

Here S is the set of states; Act is the set of action labels; → is a relation contained in S × Act × S; I ⊆ S is the set of initial states; AP is a set of atomic propositions expressing observable facts; and L : S → 2^AP assigns each state the propositions true there. A tuple (s, a, t) in the relation is written s —a→ t. The state-only labeling function L is optional in simpler LTS definitions; it is included here because it makes safety properties and model-checking examples explicit.

The model does not require S to be finite. A finite diagram is a useful teaching case, while a system state containing an unbounded queue or counter can produce infinitely many distinct configurations. Similarly, there may be one initial state, several initial states, or no initial states in some formalizations. This article assumes at least one initial state for operational examples, and it treats a model with I = ∅ as having no initialized executions.

Action names need not be exclusive. Two different successor states may be reached by the same label from one source. A label may represent a user event, internal computation, message arrival, or environment event. The transition relation says which moves the model permits, not how a CPU executes them or who is authorized to cause them. Those responsibilities must be supplied by a linked implementation and a meaningful trust model.

State Sets and the Abstraction Boundary

A state is a configuration sufficient to determine the modeled future possibilities together with the external actions or choices allowed by the model. It is not necessarily every bit of memory in a real machine. For an approval workflow, a useful state might contain the workflow phase, the requested operation, a version number, and an authorization flag. If the only property under study is whether an unapproved request can be released, a single control-state label may be enough. If the property concerns stale approvals after content revisions, a version identifier may become essential.

This is the critical abstraction decision. States that look identical under a too-coarse model may have different real behavior. For example, two pending requests with different approval permissions may not be safely merged if the model must establish authorization. Conversely, duplicating states for details that never affect any requested property creates complexity without adding analytic value. State selection should follow the claims to be proved.

A state can be represented as a symbol, tuple, immutable record, or valuation of variables. The mathematical object is the underlying configuration, not its display label. A human-friendly name like READY is not enough to guarantee that all relevant readiness conditions hold in the actual implementation.

Initial States and Environmental Assumptions

Initial states designate configurations where modeled executions may begin. A single start state suits a fresh workflow. Multiple initial states may represent permitted startup configurations, uncertainty about a recovered checkpoint, or nondeterministic initial allocation. A safety claim must account for every allowed initial state, not merely the one chosen by a convenient demonstration. Adding an initial state can reveal behaviors that a previous proof did not consider.

Environment choices often control which transitions are enabled. A user may submit a request, a network may deliver a message, or a scheduler may run a process. These are not intrinsically guaranteed. If the model assumes “the network eventually delivers every message,” label that assumption separately from the service's own transition rules. Otherwise, a liveness argument can accidentally embed the desired conclusion in the initial modeling choices.

Initialization must also distinguish configuration validation from runtime behavior. A state imported from storage may be structurally valid but violate an invariant that fresh installations satisfy. One effective review asks whether startup and recovery enter the same formal initial-state set and whether externally supplied state is validated before it is accepted as a legitimate starting configuration.

Action Labels and Transition Meaning

An action label communicates the event or step associated with an edge. A labeled transition is a triple (source, action, destination); it should not be mistaken for a function call or an event record by itself. An implementation may log an event before a transaction commits, after it commits, or more than once because of retries. The transition model must specify which observation the action label represents.

Labels can be externally visible (approve, publish) or internal (τ, commonly pronounced “tau”). Internal steps model computational progress that a chosen observer does not directly see. The abstraction can suppress such steps when comparing traces, but doing so may alter the interpretation of time, divergence, or fairness. A sequence of infinitely many internal transitions can prevent a visible action from occurring, even when ordinary visible traces look harmless.

An effective label vocabulary is concrete and consistent. If both approve and approval-recorded occur in a design, specify whether they are separate decisions or two names for one atomic event. If a transition changes several database records, the model must state whether that is one atomic logical step or a sequence whose intermediate states may be observed.

Transition Relations Rather Than Functions

A transition relation allows any number of successors, including zero, for a state and action. In a deterministic function-based model, the next state is uniquely determined for each supported state-input pair. In a relation-based model, the same source and action can lead to different destinations when the specification intentionally leaves a choice unresolved. Neither choice is intrinsically superior; it depends on the level and purpose of modeling.

The relation can express underspecification without assigning probabilities. If a remote request either succeeds or times out, the model may permit both outcomes. This does not mean that each has probability one-half. A stochastic model requires an additional quantitative interpretation. Likewise, the model's nondeterminism does not imply that an actual computer executes both branches at once; it means that the specification admits either possible successor.

A deterministic application may still be modeled relationally when external state has been hidden. The actual destination might depend on a timestamp or network condition excluded from the abstract state. Relational modeling represents uncertainty due to omitted detail, input choice, concurrency, or intentionally permitted behavior.

Total, Partial, and Input-Enabled Specifications

A transition relation is partial when some state-action pairs have no successor. Whether this is correct depends on the contract. An unavailable approve action in the draft state may mean approval is forbidden. In a separate input-enabled protocol model, every input may need a defined reaction, perhaps an explicit rejection or no-op. These are different commitments. A “missing edge” should never silently alternate between “illegal,” “impossible,” “ignored,” and “not yet designed.”

An unlabelled state is terminal with respect to the modeled relation when no outgoing transition exists. A state may have no outgoing visible transition but still have internal progress. A workflow's intentional completed state should not automatically be counted as a fault. In a nonterminating service, however, a reachable state with no enabled steps may be a deadlock. Some verification tools assume every state has a successor and add self-loops to terminal states; that convention makes infinite-path logics easier to interpret but changes the literal notion of deadlock.

Specification completeness is not the same as model completeness. A finite model can exhaustively enumerate all permitted transitions and still omit a real-world failure mode because its state or environment assumptions were wrong. Review the abstraction contract before interpreting a green result from an exhaustive search.

Runs, Paths, and Executions

A run, also called an execution or path in many texts, is a sequence of states connected by valid transitions. With labels shown, a finite run has the form s₀ —a₁→ s₁ —a₂→ ⋯ —aₙ→ sₙ, beginning at an initial state when it represents an initialized execution. An infinite run continues without a final state. A maximal run cannot be extended; in an ordinary transition-system interpretation it is either infinite or finite and ends at a state with no successor.

A finite prefix of an infinite run is still a valid finite path. This matters because safety failures are often demonstrated by finite prefixes, while progress obligations typically concern how paths continue. A diagram can contain an infinite self-loop even if the text description expected eventual completion. Whether that loop violates a requirement depends on the temporal property and the fairness assumptions, not merely on the visual presence of a cycle.

Carefully distinguish a state path from an action trace. State paths retain configurations and may distinguish behaviors that generate the same visible actions. Action traces project a run onto its labels and may discard internal transitions. Different abstraction choices can produce different trace languages from the same system.

Finite Traces, Infinite Traces, and Observations

A trace is an observation extracted from an execution. Under action-trace semantics, a path's visible labels form a word or an infinite sequence over an observation alphabet. Under state-proposition trace semantics, the system is observed through the sequence L(s₀), L(s₁), .... Neither is universally “the” trace. A verification claim should identify which projection it uses.

Suppose a workflow performs submit, an internal validation step, and approve. With internal actions hidden, its action trace may be submit, approve; with all labels included it includes the validation step. These traces are not interchangeable when the question concerns audit completeness or maximum delay between steps. A property such as “approval is followed by publication” is also sensitive to whether the observer sees post-approval retries and failure transitions.

Finite traces are suitable for reachability and many testing objectives; infinite traces are central to standard interpretations of linear temporal logic. Tools that evaluate temporal logic on finite logs usually employ explicit finite-trace semantics or endpoint conventions. Apply those conventions rather than importing the ordinary infinite-path meaning silently.

Reachability as the First Fundamental Query

A state t is reachable when there exists an initialized finite run ending at t. Formally, let Post(X) be the set of destinations of transitions with sources in X. The reachable set is the least set containing I and closed under Post:

Reachability fixed point: Reach(T) = μX . (I ∪ Post(X)), where μX denotes the least fixed point.

For a finite explicitly represented graph, breadth-first search (BFS) or depth-first search (DFS) computes this set. A state shown in a diagram can be syntactically present but unreachable. It should not be treated as a demonstrated runtime scenario from the specified initialization. Conversely, removing a state from an illustration does not establish that the implementation can never enter it.

Reachability is existential: there is some permitted sequence of actions that arrives at the target. It does not imply that the target is likely, inevitable, or reachable under a narrower operational environment. A correct explanation always accompanies a reachability claim with the start set, transition relation, and any restrictions on the allowed action schedules.

The Request-and-Approval Example

Consider a request that must be submitted, reviewed, and then either approved or rejected. Use the abstract states draft, pending, approved, rejected, published, and withdrawn. A legitimate initial state is draft. The intended transitions are draft —submit→ pending, draft —withdraw→ withdrawn, pending —approve→ approved, pending —reject→ rejected, pending —withdraw→ withdrawn, and approved —publish→ published.

This small graph captures the requirement that publication follows approval; it does not yet capture who may approve, document revisions, retries, or external publication failures. The abstract labels reflect logical changes, not network requests. approved —publish→ published assumes the publication event is modeled as a successful atomic state change. A realistic deployment would need separate attempted and completed publication states if failures are significant to the property.

Source state Action Destination state Permitted meaning
draft submit pending Enter review
draft withdraw withdrawn Cancel before review
pending approve approved Record approval
pending reject rejected Record rejection
pending withdraw withdrawn Cancel during review
approved publish published Complete publication

This is a constructed teaching model, not a claim about a particular institution's actual approval system.

Representing the Example in Python

A transition relation can be represented by a sequence of labeled triples. Use immutable state names and treat the relation as data rather than embedding all the rules in an arbitrary collection of conditional branches. This representation makes it straightforward to print permitted actions, explore alternative runs, and detect missing or unexpected edges.

STATES = {"draft", "pending", "approved", "rejected", "published", "withdrawn"}
INITIAL = {"draft"}
TRANSITIONS = {
    ("draft", "submit", "pending"),
    ("draft", "withdraw", "withdrawn"),
    ("pending", "approve", "approved"),
    ("pending", "reject", "rejected"),
    ("pending", "withdraw", "withdrawn"),
    ("approved", "publish", "published"),
}

def successors(state):
    return {(action, target) for source, action, target in TRANSITIONS
            if source == state}

assert INITIAL <= STATES
assert all(source in STATES and target in STATES
           for source, _, target in TRANSITIONS)
assert successors("pending") == {
    ("approve", "approved"),
    ("reject", "rejected"),
    ("withdraw", "withdrawn"),
}
assert not successors("published")

This example is deliberately a relational specification, not a web application. It does not check authentication, commit a database transaction, or send a publication job. Those behaviors require separate implementation logic constrained by the formal model. Because the graph is small, it is easy to inspect every permitted edge; that transparency is a useful starting point for more demanding models.

Executing a Labeled Action Trace

To evaluate a sequence of requested actions, maintain the set of possible current states. In a deterministic model this set often contains a single state, but the set-based interpretation works for a nondeterministic relation as well. At each step, collect all destinations reachable with the given action from any current state. If none exists, that action sequence is not an execution of the model.

EDGES = {
    ("draft", "submit", "pending"),
    ("pending", "approve", "approved"),
    ("pending", "reject", "rejected"),
    ("approved", "publish", "published"),
}

def follow(initial_states, actions):
    current = set(initial_states)
    for action in actions:
        current = {dest for src, label, dest in EDGES
                   if src in current and label == action}
        if not current:
            return set()
    return current

assert follow({"draft"}, ["submit", "approve", "publish"]) == {"published"}
assert follow({"draft"}, ["approve"]) == set()
assert follow({"draft"}, ["submit", "reject", "publish"]) == set()

A failed action trace means that the relation contains no path bearing that exact sequence of labels. It need not mean that an actual network call was rejected; the abstract system may not represent that network call at all. If invalid input is supposed to be acknowledged, model the rejection action and response explicitly.

The Meaning of Forbidden and Missing Edges

A diagram often invites the reader to conclude that every omitted arrow represents prohibited behavior. This conclusion is valid only under a closed-world interpretation in which the transition relation is intended to be complete. Under an open-world interpretation, missing arrows may indicate behavior not yet specified. Some formalisms use additional notation to distinguish required, permitted, or unknown transitions. It is dangerous to assume that the same unadorned diagram supports both interpretations.

For the request example, there is no rejected —publish→ published edge. In a complete specification, this means that publication directly after rejection is not allowed. In an incomplete design sketch, the absence is merely a question requiring resolution. In a deployed service, it is still necessary to test that the handler refuses such a request and that no alternate API bypasses the constraint.

Each specification should state whether transitions are exhaustive, what happens on invalid events, and whether exceptional transitions such as administrator override, rollback, and recovery are modeled. An editorial label such as “planned state” or “draft flow” cannot substitute for an explicit semantic statement.

Unreachable States and Redundant Diagram Nodes

A declared state may be unreachable from every initial state. For example, a diagram might contain suspended without an incoming path. Unreachability does not automatically make the state useless: the state may represent an intended future feature, a recovery-only entry point, or an unreachable error marker included to test a design claim. But it does mean that no run under the current initialization and transition relation enters that state.

The right response is to classify the discrepancy. If suspended is required by policy, the graph may be incomplete. If it is an artifact of a removed feature, the state may be removable. If it was intended as a failure state, its unreachability may be a desirable result—provided the reachability calculation genuinely covers all allowed transitions and initial configurations.

For a finite system with V states and E edges, a graph exploration typically takes O(V + E) time and O(V) additional space for the visited structure and work queue, assuming states and adjacency operations have bounded cost. The statement applies to the explicitly represented graph; generating successors from rich symbolic constraints can be much more expensive.

Breadth-First Reachability in Python

The following code explores every state reachable from a chosen initial set. It records predecessors so the model can explain how a target state was reached, rather than returning only a yes-or-no answer. For an unweighted finite state graph, BFS finds a path with the fewest transitions among those in the modeled graph.

from collections import deque

EDGES = {
    ("draft", "submit", "pending"),
    ("draft", "withdraw", "withdrawn"),
    ("pending", "approve", "approved"),
    ("pending", "reject", "rejected"),
    ("pending", "withdraw", "withdrawn"),
    ("approved", "publish", "published"),
}

def explore(initial_states, edges):
    adjacent = {}
    for source, action, target in edges:
        adjacent.setdefault(source, []).append((action, target))
    parent = {state: None for state in initial_states}
    queue = deque(initial_states)
    while queue:
        state = queue.popleft()
        for action, target in adjacent.get(state, ()):
            if target not in parent:
                parent[target] = (state, action)
                queue.append(target)
    return parent

parents = explore({"draft"}, EDGES)
assert set(parents) == {"draft", "pending", "approved", "rejected",
                        "withdrawn", "published"}
assert parents["published"] == ("approved", "publish")

For reproducible trace display, sort successors and initial states before traversal; sets alone do not promise a stable traversal order. Different shortest paths can exist, and BFS returns one according to enumeration order, not a uniquely privileged explanation.

Reconstructing a Counterexample Trace

A counterexample trace shows a finite execution that violates a proposed safety property. It should contain states and action labels, allowing an engineer to reproduce the logical failure and decide whether the edge or the property is wrong. The following example adds one forbidden transition and reconstructs a shortest path from draft to published through rejected.

from collections import deque

EDGES = [
    ("draft", "submit", "pending"),
    ("pending", "reject", "rejected"),
    ("rejected", "publish", "published"),  # Injected specification defect
]
queue = deque([("draft", [("start", "draft")])])
seen = {"draft"}
witness = None
while queue:
    current, path = queue.popleft()
    if current == "published":
        witness = path
        break
    for source, action, target in EDGES:
        if source == current and target not in seen:
            seen.add(target)
            queue.append((target, path + [(action, target)]))

assert witness == [
    ("start", "draft"),
    ("submit", "pending"),
    ("reject", "rejected"),
    ("publish", "published"),
]

In a realistic model, “approval occurred at some point in the past” may need to be represented as a historical flag or an explicit state component. Reaching published alone does not reveal whether approval was ever present unless the abstraction stores sufficient information to distinguish legal and illegal histories. A witness is only as informative as the state vocabulary supporting it.

Invariants and State Predicates

An invariant is a predicate intended to hold in every state reachable from the designated initial set. A simple example is “at most one owner holds the resource.” For a workflow with state variables published and approved_for_current_version, the invariant can be written published ⇒ approved_for_current_version. This is a stronger specification than merely asserting that the visible approved control state precedes published in one example.

There are two standard verification routes. One is to enumerate the reachable states and evaluate the predicate on each. The other is to establish that the predicate is inductive: it holds in every initial state and is preserved by every modeled transition from a state satisfying the predicate. An inductive invariant yields a proof for all reachable states, including those not yet enumerated, provided the proof obligations and transition semantics are sound.

An invariant may be true on all reachable states without being inductive over the entire abstract state universe. In that case, strengthen it with a supporting condition or reason about reachable-state restrictions. Failure of a candidate to be inductive does not, by itself, establish that the desired safety property is false.

An Inductive Proof Obligation

Let P(s) be a proposed invariant. Its basic induction conditions are ∀s ∈ I : P(s) and ∀s,t,a : (P(s) ∧ s —a→ t) ⇒ P(t). If both hold, then induction on the length of any finite initialized run proves P for every reachable state. This argument uses no probabilistic assumptions and does not rely on an arbitrary exploration cutoff.

For the abstract publication model, assume the boolean state tuple (phase, approved_current_version). The initialization sets the approval flag to false. An approve transition may set it true only in a valid review phase. A publish transition requires it true. If a revision invalidates approval, the revision transition must reset the flag. The proof then has meaningful content: every publish edge preserves the policy and every path to a published state enters with valid approval.

A claim that the system is “secure because publish checks the flag” is incomplete if other transitions can set phase = published without passing through that check. The inductive method examines the full relation and therefore helps reveal alternate paths into restricted states.

Invariant Checking with Explicit States

Finite exploration can evaluate invariants for each reachable state and produce a precise witness when one fails. In this compact model a state includes both a workflow phase and an approval flag. An invalid edge is deliberately introduced to illustrate how an omitted prerequisite becomes visible.

from collections import deque

initial = ("draft", False)
transitions = {
    (("draft", False), "submit", ("pending", False)),
    (("pending", False), "approve", ("approved", True)),
    (("approved", True), "publish", ("published", True)),
    (("pending", False), "bypass", ("published", False)),
}

def allowed(state):
    phase, approved = state
    return phase != "published" or approved

queue = deque([(initial, [initial])])
seen = {initial}
violation = None
while queue:
    state, path = queue.popleft()
    if not allowed(state):
        violation = path
        break
    for source, _, target in transitions:
        if source == state and target not in seen:
            seen.add(target)
            queue.append((target, path + [target]))

assert violation == [("draft", False), ("pending", False),
                     ("published", False)]

This result demonstrates the invariant check in the model. To interpret it as a deployed vulnerability requires confirming that the bypass transition corresponds to an executable operation. Conversely, removing it from the model would not prove that the implementation lacks such a bypass.

Safety Properties and Finite Bad Prefixes

A safety property asserts, roughly, that something bad never happens. In the standard infinite-trace setting, violation of a safety property can be witnessed by a finite bad prefix that cannot be extended into a satisfying execution. Examples include mutual exclusion, no publication without authorization, and absence of an invalid state. State invariants are an important but not exhaustive way to state safety requirements.

A finite trace that reaches a known forbidden state is a particularly direct counterexample. More intricate safety properties refer to sequences of states or actions, such as “a commit must not occur unless an earlier prepare has been acknowledged.” Such claims may be reduced to ordinary invariants by adding monitoring state that remembers the relevant history. That monitor is part of the formal construction; it is not automatically available in the implementation.

Safety analysis should not be confused with a security penetration test. It identifies bad behaviors admitted by the formal relation, often exhaustively for bounded models. The model may omit attackers, deployment permissions, faulty dependencies, or low-level races; coverage of those concerns must be documented separately.

Deadlocks, Terminal States, and Stuck Behavior

A state is a deadlock in a simple labeled transition system when no transition is enabled, but practical specifications distinguish expected termination from unintended inability to progress. A completed or cancelled workflow may legitimately terminate. A live service that cannot process any event after a network error may not. The formal graph alone does not know which interpretation applies; an explicit terminal-state policy is necessary.

A no-outgoing-edge check should therefore classify reachable dead ends into allowed terminal states, error states, and unexpected deadlocks. For instance, rejected and withdrawn may be intentional terminal outcomes in the teaching workflow. A pending request blocked by a missing retry or cancel edge may be an operational problem. In concurrent models, global deadlock can occur even when individual processes each have transitions available in isolation because synchronization preconditions cannot be met simultaneously.

Deadlock freedom also differs from progress. A machine with a self-loop always has an enabled edge yet may never complete useful work. Separate the questions “can the system move?” and “must the system eventually accomplish its obligation?”

Detecting Reachable Dead Ends

The next example identifies states reachable under an explicit graph and classifies states without successors. It reports a failure only when such a state is not in the declared set of acceptable terminal outcomes. This is better than assuming every state of out-degree zero is defective.

from collections import deque

edges = {
    "draft": [("submit", "pending")],
    "pending": [("approve", "approved"), ("reject", "rejected")],
    "approved": [("publish", "published")],
    "rejected": [],
    "published": [],
}
terminal_allowed = {"rejected", "published"}
seen, queue = {"draft"}, deque(["draft"])
while queue:
    current = queue.popleft()
    for _, target in edges.get(current, []):
        if target not in seen:
            seen.add(target)
            queue.append(target)
dead_ends = {state for state in seen if not edges.get(state, [])}
unexpected = dead_ends - terminal_allowed
assert dead_ends == {"published", "rejected"}
assert unexpected == set()

If a verification tool makes the relation total by attaching self-loops, this exact dead-end query must be adapted. Totalization can change interpretations of next-step and eventuality formulas, even when some basic reachability conclusions remain unchanged.

Nondeterminism and Branching Behavior

Suppose pending —review→ approved and pending —review→ rejected are both permitted. The transition relation intentionally does not specify which result occurs. A user running one demonstration may observe a single outcome, but the model represents both. Safety verification evaluates all permitted branches; reachability asks whether at least one branch reaches a target; inevitability asks whether all relevant continuation paths satisfy a future obligation.

An angelic interpretation asks whether some favorable choice exists. An adversarial or demonic interpretation requires a property to hold under all permitted choices. Formal verification of safety commonly takes the latter perspective: if a defect can occur under any admitted transition sequence, it matters. Production systems may constrain choices through scheduling or permissions; encode those constraints only when justified, and keep the assumptions visible.

Nondeterminism is not randomness. A probabilistic model attaches probability distributions or rates to choices; a nondeterministic relation simply lists possibilities. Treating all edges as equally likely because they share a source is an unjustified statistical assumption.

Stuttering and Internal Steps

A transition can change the modeled control state without changing the propositions an observer sees. Such a transition is often called a stuttering step with respect to those observations. For example, two internal scheduling states may both satisfy status = pending. They are different formal configurations but appear identical to a reader who observes only public workflow status. Stuttering is important when a specification permits implementation steps that should not count as business events.

Some temporal properties are insensitive to finite insertions or deletions of stuttering steps, while formulas involving a strict next-state operator can distinguish them. For instance, X ready is sensitive to one extra intervening step; the less position-specific statement “eventually ready” has a different interpretation. Infinite internal activity also requires care: a system may keep taking invisible steps forever and never perform a publicly visible action.

A trace-equivalence claim must therefore state whether internal labels are hidden, whether stuttering is ignored, and what observations remain visible. These choices affect whether a refactored implementation can be considered behavior-preserving under the chosen specification.

Liveness and Progress Obligations

A liveness property states that something good eventually happens, under a formal interpretation of paths. For a request system, one possible requirement is “every submitted request eventually receives a final outcome.” A system with an infinite pending —wait→ pending loop may satisfy many state invariants yet violate this progress requirement on a path that waits forever.

A common notation is G(pending → F terminal), where G means “globally, at every point” and F means “at some future point.” This is an informal presentation of a linear-time temporal formula, interpreted over infinite traces under chosen atomic propositions. A finite event log alone does not settle a general liveness claim: a pending request at the end of the log might complete later. For bounded real-world requirements, a deadline property is often more appropriate than an unbounded eventuality claim.

Liveness can require environment assumptions. If a remote reviewer is allowed never to respond, no application-only proof can guarantee review completion unless the process includes a timeout, escalation, or default resolution. The specification should make those paths explicit rather than assuming cooperative actors without saying so.

Fairness Is an Assumption, Not a Magic Fix

A path may indefinitely postpone an enabled transition because the model allows an adversarial schedule. Weak fairness, for a particular action or process, commonly requires that an action continuously enabled from some point onward is eventually taken. Strong fairness commonly requires eventual execution when an action is enabled infinitely often, even if it is repeatedly disabled between opportunities. Exact formulations vary by formalism and how actions are identified.

Adding fairness can rule out infinite paths that the raw relation otherwise permits. That may be appropriate for a scheduler designed to provide service, but it may be false for an unreliable network or a human approval queue. A proof obtained only after assuming fair delivery is not evidence that real networks cannot lose messages. State the fairness condition, the actors to which it applies, and the operational mechanism—if any—that makes it plausible.

Fairness should also not disguise deadlocks. If an action is not enabled at all, requiring the scheduler to run it does nothing. Progress analysis must inspect enabling conditions, availability of recovery actions, and whether the environment can permanently prevent the desired outcome.

Temporal Logic as a Property Language

Temporal logic describes properties of entire executions rather than isolated states. Linear Temporal Logic (LTL) evaluates a formula along a path using operators such as G (“always”), F (“eventually”), X (“next”), and U (“until”). Computation Tree Logic (CTL) distinguishes path quantifiers—A for all paths and E for at least one path—combined with temporal operators in its formal syntax. Both depend on a precise state space and transition semantics.

Examples include AG ¬unsafe for “unsafe never holds on any path” and EF completed for “a completed state is reachable along some path” in a conventional CTL reading. AG(started → AF completed) expresses a stronger branching-time progress requirement than EF completed. A model may easily reach completed along one path while allowing other paths to run forever without completion. That is why a single successful demonstration does not establish system-wide progress.

Formal notation should be introduced only when its semantic assumptions are understood. Deadlock treatment, infinite-path extension, fairness, hidden actions, and the meanings of atomic propositions influence the interpretation. For deeper syntax and proofs, consult the specialist articles on Temporal Logic for State Machines and Safety and Liveness Properties.

Model Checking and Explicit Exploration

Model checking determines whether a mathematically specified system satisfies a formal property, often by exploring a reachable state graph or a symbolic representation of it. On a finite model, an exhaustive procedure can be conclusive for the represented states and transitions. When a claim fails, a model checker may supply a counterexample execution. When it succeeds, the strength of the conclusion depends on faithful modeling, property specification, and assumptions.

Explicit-state exploration uses visited-state sets and successor enumeration. Symbolic model checking uses representations such as decision diagrams or satisfiability/constraint solvers to avoid constructing every state as an individual object. Bounded model checking searches for violations up to a selected depth and generally cannot prove unbounded safety from an absence of counterexamples without additional reasoning. Finite abstraction and inductive methods can strengthen the result.

The article's Python BFS examples are educational state-space exploration, not a replacement for a general-purpose model checker. They demonstrate the core idea: begin from I, apply the transition relation, maintain the reached set, evaluate predicates, and retain informative witnesses.

From a Workflow Table to a Verification Question

To verify a business rule, translate it into an explicit property rather than relying on appealing arrow placement. Consider the rule: “No request is released without approval for its current version.” A model with only states draft, approved, and published may appear to satisfy the rule. But when edits are permitted after approval, the model needs to remember the version that was approved, or it may miss the stale-approval case.

A more useful state can be a tuple (phase, content_version, approved_version), with approved_version = None before approval. The publish transition is enabled only if approved_version == content_version. An edit increases the content version and can preserve the earlier approved version as history, making the mismatch explicit. The property becomes a predicate about current data, not an informal observation that an approval event once happened.

A deliberate modeling question is whether version numbers can increase without bound. In a finite demonstration, bound the version range and document the bound. A bounded success result should not be advertised as an unbounded proof unless further mathematical reasoning establishes it.

State-Dependent Transition Guards

A guard is a condition controlling whether a transition may occur. In an extended state-machine model, an action can have a guard and an update. For example, publish is allowed only if phase == approved and approved_version == content_version. The transition then updates phase to published. This is one way to generate a transition relation over a state space of variable valuations.

If guards depend on time, permissions, inventory, or network acknowledgments, those inputs become part of the state, actions, or explicit environmental assumptions. Failing to model a dependency can accidentally grant a transition in situations where the implementation would reject it—or forbid a path that should be available. For formal work, every free variable in a guard must have a defined domain and interpretation.

Guards should also be separated from side effects. A guard checks whether an edge is enabled; the update describes the resulting abstract state. A real database transaction may abort or partially fail unless atomicity is guaranteed by the chosen platform. Model failure and rollback edges where these outcomes affect the property.

A Version-Aware Publication Model

The following compact generator represents a bounded version-aware workflow. It explores up to two content versions, with approval tied to a specific version. Its purpose is to test whether a transition graph permits publication of unapproved content; the bound is an explicit teaching constraint rather than a claim about real version counters.

from collections import deque

# State = (phase, current_version, approved_version)
start = ("draft", 0, None)

def next_states(state):
    phase, version, approved_version = state
    result = []
    if phase == "draft":
        result.append(("submit", ("pending", version, approved_version)))
    if phase == "pending":
        result.append(("approve", ("approved", version, version)))
    if phase in {"pending", "approved"} and version < 2:
        result.append(("edit", ("draft", version + 1, approved_version)))
    if phase == "approved" and approved_version == version:
        result.append(("publish", ("published", version, approved_version)))
    return result

seen, queue = {start}, deque([start])
while queue:
    current = queue.popleft()
    for _, target in next_states(current):
        if target not in seen:
            seen.add(target)
            queue.append(target)
assert any(s[0] == "published" for s in seen)
assert all(s[0] != "published" or s[1] == s[2] for s in seen)
assert ("draft", 1, 0) in seen  # Earlier approval becomes stale after editing

The property is established only for the reachable configurations in this bounded model. A richer specification may allow concurrent edits, administrators, asynchronous publication completion, or restoration from a checkpoint. Each additional capability should be introduced with a clearly described change to S and →.

State-Space Growth and the Product Problem

The number of global configurations can grow rapidly when a system has several independent components. If one component has m states and another has n, their naive Cartesian product has up to m × n joint states. For k identical components with n local states each, the raw product can have n^k combinations even before adding queues, counters, identities, or failure modes.

This is the state-explosion problem. Not every product state is reachable; constraints and synchronization may eliminate many combinations. Nevertheless, the size of the potential state space explains why exhaustive verification of a real distributed system can be difficult. Symbolic techniques, compositional reasoning, symmetry reduction, bounded domains, and partial-order reduction may help when their prerequisites hold.

It is important to distinguish the state count from the transition count, and both from the cost of deciding whether a transition is enabled. A graph with a thousand explicit states may be easy to search, whereas a system with a compact symbolic description can encode an enormous space of possible valuations.

Product and Interleaving Composition

Composition builds a global model from component models. Under simple asynchronous interleaving, a joint state is a tuple (s₁, s₂). A transition may update the first component while leaving the second unchanged, or vice versa. This represents one conceptual action at a time. It does not mean physical processors are serial; it is an abstraction intended to capture the observable outcomes of independently ordered atomic steps.

Under synchronous composition, components may be required to perform matching actions together. A send edge and a receive edge might synchronize on a common channel label. Under other semantics, sends enqueue messages and receives occur later. These choices generate different reachable behaviors. Synchronizing every action can eliminate valid interleavings; synchronizing none can admit impossible behaviors.

When combining components, specify shared variables, event matching, atomicity, and environmental assumptions. A state pair is not automatically reachable just because each local state is reachable independently. One component may constrain the other's progression, preventing the joint execution required to reach that pair.

Two-Component Interleaving Example

The example below composes two simple counters. The first component can increment from zero to two, the second from zero to one. Each step changes one component while preserving the other. All six joint states are reachable in this unconstrained toy model.

from collections import deque

start = (0, 0)

def successors(state):
    x, y = state
    if x < 2:
        yield "inc_x", (x + 1, y)
    if y < 1:
        yield "inc_y", (x, y + 1)

seen, queue = {start}, deque([start])
while queue:
    current = queue.popleft()
    for action, target in successors(current):
        if target not in seen:
            seen.add(target)
            queue.append(target)
assert seen == {(0, 0), (1, 0), (2, 0),
                (0, 1), (1, 1), (2, 1)}

This example has no synchronization or shared-resource constraints. If both counters used an exclusive lock, the global state would also need to represent lock ownership and the transitions that acquire or release it. Otherwise the model would be too weak to assess mutual exclusion.

Shared State and Concurrency Assumptions

A shared variable creates an interaction between components, even when their control states are individually simple. Suppose two processes each execute “read counter; increment local value; write counter.” If the model treats the entire operation as one atomic transition, it can obscure a lost-update problem. If it represents the read and write as separate steps, an interleaving can show how both processes read the same old value and overwrite one another.

A modeling decision about atomicity therefore changes the set of admitted behaviors. To verify the safety of a lock or transactional mechanism, specify which steps occur atomically and what ordering guarantees the execution environment actually provides. An overly strong atomic-step assumption can make a flawed program appear correct.

Concurrent modeling also needs a policy for simultaneous events. An interleaving model orders conceptual atomic steps; a synchronous model may allow a combined transition; a real-time model may associate timestamps. None is automatically the correct description of a concrete platform without an explicit correspondence argument.

Compositional Reasoning and Interfaces

A large transition system can sometimes be analyzed component by component. Each component is given an interface contract specifying assumptions about its environment and guarantees about its own behavior. The composition should establish that each component's required assumptions are supplied by its partners or by the environment. A local proof alone cannot establish a global property if the component's assumptions are not satisfied when deployed.

Consider an approval service and a publication service. The publisher might guarantee “never publish unless the approval token matches the content version,” assuming the token is authentic and the content hash is immutable during the transaction. The approval service may guarantee token issuance only after an authorized review. The overall property then depends on interface correctness, token validation, storage consistency, and the composition of those guarantees.

Compositional proof is especially useful when an implementation changes frequently. A component can be replaced without rederiving every global fact if the replacement is shown to preserve the required contract. That preservation claim must be justified at the level of observations and assumptions relevant to the system.

Observational Abstraction

Two concrete configurations may be mapped to one abstract state when the distinctions are irrelevant to the property being studied. An abstraction function α maps concrete states to abstract states. For example, detailed queue lengths might be grouped into empty, nonempty, and overflow. The abstract graph then describes transitions between these categories instead of tracking every exact count.

Abstraction is powerful but potentially misleading. If the abstract relation contains every behavior of the concrete system under the chosen correspondence—an overapproximation—then proving a universal safety property on the abstraction can justify the concrete property, provided the observation mapping and proof conditions hold. But an abstract counterexample may be spurious, representing a combination of steps no concrete execution can realize.

An underapproximation includes some real behaviors but not necessarily all. It is useful for discovering concrete counterexamples, but absence of a failure in the restricted model does not generally establish global safety. The direction of approximation is part of the evidence supporting a verification result.

Trace Equivalence and Bisimulation

Two systems are trace equivalent under a chosen observation model when they admit the same observable traces, often after hiding internal actions. This is a useful definition of behavioral similarity, but it can overlook branching distinctions. Two states may permit identical sets of complete visible traces while offering different intermediate choices; a user or environment that can interact after each step may distinguish them.

Bisimulation is a stronger stepwise correspondence: related states must be able to match one another's moves while remaining related, under the applicable strong or weak semantics. In strong bisimulation, visible and internal steps are generally matched directly according to the chosen labels. In weak bisimulation, sequences of internal moves may be abstracted in a more permissive matching relation. Both require formal definitions before invoking them as proof claims.

For engineering, the practical question is what must be preserved by a refactoring. Is it enough to preserve the observed sequence of success and failure events? Must the set of possible responses after every user action be preserved? Must timing, output count, or error identity be preserved? Select an equivalence that matches that contract rather than applying the word “equivalent” without qualification.

Refinement from Specification to Implementation

A high-level specification may permit several outcomes while the implementation selects one through deterministic logic. Such a selection can be a legitimate refinement if every implementation behavior maps to a behavior allowed by the abstract model and any additional obligations are met. Refinement need not mean that the two systems have identical internal states or one-to-one transitions.

A standard approach uses a relation between implementation states and specification states. A single abstract transition might correspond to several concrete internal steps, and some concrete steps may be treated as stuttering. The proof must account for visible observations and for any progress obligations that cannot be discharged by safety-style trace inclusion alone. An implementation that silently loops forever instead of returning a permitted result may satisfy a weak safety abstraction while violating the intended liveness requirement.

A refinement argument should document its mapping, simulation obligations, environment assumptions, and observable contract. A test suite that exercises a handful of paths is useful implementation evidence, but it does not establish complete refinement over a large or unbounded state space.

When a State Machine Is Not a DFA

A DFA recognizes a language of finite input strings; the standard complete form uses a deterministic total transition function and a set of accepting states. A general labeled transition system describes possible operational steps and need not have accepting states, a single input stream, or a total transition function. An application workflow with asynchronous callbacks, cancellation, and error recovery is therefore not automatically a DFA even if its diagram contains only a few circles and arrows.

An LTS may model DFA execution by taking DFA input symbols as action labels and identifying accepting states as an observation. But the reverse translation requires additional choices: what constitutes the input alphabet, whether every action is externally supplied, how terminal outcomes are interpreted, and how nondeterminism is resolved. The distinction preserves separate technical ownership between this article and the specialist Deterministic Finite Automata treatment.

The broadest mental model is that a DFA is a particular sort of labeled state machine specialized for language membership. A transition system is a general behavioral substrate from which recognizers, reactive controllers, protocols, and verification models can be built.

Labeled Transition Systems and Kripke Structures

A Kripke structure, in a common model-checking formulation, emphasizes states and a relation between them together with a labeling of states by atomic propositions. An LTS emphasizes actions labeling transitions. Both can support temporal reasoning, but they place observations in different locations. The extended tuple used in this article includes both action labels and state propositions, and is commonly called a transition system in model-checking literature.

To move between views, one may hide action labels when only state properties matter, or augment states so that action information becomes observable as a proposition. These transformations are not semantically neutral for every logic: an action-sensitive formula may not survive a projection that forgets the action, and next-step properties can be affected by inserted intermediary states.

The correct representation is driven by what is being checked. Authentication and access-control policies may be natural state predicates; message-delivery protocols may require action observations; timing properties may need explicit clocks. A model should expose only the observations necessary to express the intended requirements while preserving the behaviors relevant to those requirements.

Analysis of Cycles and Strongly Connected Components

Cycles in a transition graph describe repeated behavior. A strongly connected component (SCC) is a maximal set of states in which every state is reachable from every other within the component. SCC analysis can expose repeating phases and is important for many model-checking algorithms. A reachable nontrivial SCC or a reachable self-loop permits a cycle that can be repeated indefinitely in an unconstrained finite LTS.

Whether such a cycle violates progress depends on what the cycle contains, whether leaving it is required under fairness assumptions, and which properties are evaluated. A retry loop is not necessarily wrong; a retry loop with no limit, backoff, cancellation, or permanent-failure handling may nevertheless frustrate a business obligation. A cycle may also encode intended service continuity, such as accepting many independent requests.

An SCC is a graph-theoretic structure, not a probability statement. It does not tell an analyst how often a loop occurs in deployment or how long the system remains inside it. Those questions require workload, scheduler, or stochastic information not contained in the bare relation.

Building an SCC-Aware Cycle Check

An elementary recursive DFS can detect a directed cycle by distinguishing nodes currently on the exploration stack from those already completed. This example checks whether a reachable cycle exists; it does not make a liveness judgment. In production, use an explicit stack if the modeled graph can be deeply nested enough to exceed the runtime's recursion limit.

from collections import deque

edges = {
    "idle": ["pending"],
    "pending": ["waiting", "done"],
    "waiting": ["pending"],
    "done": [],
}

reachable, work = {"idle"}, deque(["idle"])
while work:
    current = work.popleft()
    for neighbor in edges.get(current, []):
        if neighbor not in reachable:
            reachable.add(neighbor)
            work.append(neighbor)

color = {state: 0 for state in reachable}  # 0 unseen, 1 active, 2 done

def has_cycle(state):
    color[state] = 1
    for neighbor in edges.get(state, []):
        if color[neighbor] == 1:
            return True
        if color[neighbor] == 0 and has_cycle(neighbor):
            return True
    color[state] = 2
    return False

assert any(color[s] == 0 and has_cycle(s) for s in reachable)

A cycle detector can answer a useful structural question but is not a temporal-logic model checker by itself. To prove progress, one must analyze which cycles are fair, which actions are required, and whether some reachable nonterminating execution remains.

Parameterized and Infinite-State Systems

A transition system can represent an unbounded number of clients, arbitrarily large messages, or integer counters. An infinite-state system is not directly exhausted by ordinary finite graph traversal. One response is to bound relevant domains and verify a finite instance; another is to use symbolic reasoning, inductive invariants, abstract interpretation, or parameterized verification techniques.

Bounding is legitimate if it is reported as such. “No bad state occurs for three users and a queue capacity of five” is a useful finite-instance result, but it is not a proof for any number of users. Some protocols exhibit cutoff results under additional hypotheses, allowing small-instance reasoning to generalize; such a cutoff must be established, not presumed.

A performance limit in the model checker is distinct from a genuine safety counterexample. Search that stops because memory is exhausted does not imply either that the property holds or that it fails. An honest report states the explored domain, algorithm, proof status, and remaining uncertainty.

Testing Derived from Transitions

The transition relation supplies a systematic source for tests. A test can cover a specific edge, a state, a transition pair, or an invalid action. State coverage does not guarantee transition coverage: a suite may visit both endpoints of an edge without ever executing that edge. Even transition coverage does not establish that every longer execution sequence has been tested.

A practical test plan begins with required edges and expected forbidden actions, then adds recovery paths, repeated events, unusual orderings, and boundary conditions. For a workflow, a pairwise sequence such as submit → withdraw should be tested separately from submit → approve. If an implementation exposes errors in addition to state changes, tests should verify those outputs as part of the contract.

Model-based tests must map model labels to real operations and model states to observable implementation configurations. If the test harness cannot distinguish approved from pending reliably, it may report a false pass. Instrumentation and trustworthy observations are part of the verification pipeline, not auxiliary conveniences.

Testing Forbidden Transitions

This minimal implementation checks the chosen transition relation before applying any action. A rejected action raises an error rather than silently changing state. That is one valid application policy; a different service could return a structured rejection event, and that policy would need its own explicit modeling.

class InvalidTransition(ValueError):
    pass

NEXT = {
    ("draft", "submit"): "pending",
    ("pending", "approve"): "approved",
    ("pending", "reject"): "rejected",
    ("approved", "publish"): "published",
}

def step(state, action):
    try:
        return NEXT[(state, action)]
    except KeyError as exc:
        raise InvalidTransition(f"{action} not permitted from {state}") from exc

assert step(step("draft", "submit"), "approve") == "approved"
try:
    step("rejected", "publish")
except InvalidTransition:
    pass
else:
    raise AssertionError("forbidden transition accepted")

In a real service, validate actor permissions and transaction versions as well as state-action legality. A transition table is not an authorization system unless its state and guards encode the necessary authority constraints and every relevant entry point enforces them.

Monitoring Implementation Traces

Operational trace collection can compare events observed in deployment with the action sequences admitted by the model. A monitor can start from the model's initial set, update the possible-state set for each received event, and flag an observation sequence with no remaining compatible path. This is runtime conformance monitoring, not necessarily a proof that all unseen behaviors are correct.

Real logs introduce difficult semantics. Events can be duplicated, delayed, reordered, or lost. A distributed transaction may emit a record of an attempted operation before the final commit. A monitor that assumes perfect log order may report violations that are only artifacts of observation, while a monitor that drops too many details can overlook meaningful faults. The trace projection and its reliability therefore require explicit engineering decisions.

A sound monitoring design documents correlation identifiers, version numbers, causality, clock conventions, and what happens when the event stream is incomplete. It should distinguish an unknown conclusion from a definite specification violation rather than forcing both into a binary pass/fail label.

Security Boundaries and Authorization

Formal transition systems can express security-sensitive behavior, but they do not automatically enforce it. To reason about unauthorized publication, a model needs information about actor roles, token validity, authentication state, or any other facts relevant to a policy. If those are omitted from the state and the allowed-action conditions, the model can prove only a weaker property, such as “the workflow control status was approved before publication.”

A common failure is a confused transition boundary: one API verifies an operation while another API, background worker, or recovery path changes the same protected state without equivalent checks. A complete security model includes every entry route capable of triggering the relevant transition. Security testing then attempts to exercise those routes using identities and inputs that should not be permitted.

Other important considerations include replayed events, stale state reads, audit-log tampering, and unauthorized rollback. These can be represented by explicit adversarial actions or environmental interference. The relevant State Machine Security unit develops these concerns further; the foundational point is that security properties must be stated over an adequately rich behavioral model.

Versioning, Recovery, and Persistent State

A service may resume execution from a persisted snapshot. That snapshot may be stale relative to external resources or contain transitions recorded only partially. Recovery therefore raises two different questions: whether the restored configuration belongs to the model's permitted initial/recovery set, and whether subsequent actions preserve required invariants. A successful normal startup does not answer either question.

Versioning helps define a correspondence between logged actions and state transitions. If a message is applied twice, the intended transition may be idempotent or may be invalid on the second application. If different nodes apply events in different orders, the final states may differ unless the protocol enforces a deterministic order or suitable commutativity properties. The transition model should specify these choices explicitly.

State-machine replication in distributed systems adds consensus, ordering, and fault assumptions to this basic picture. It is not equivalent to merely sharing one diagram among several services. That topic belongs in the specialist State Machines in Distributed Systems article.

Scenario 1 — Request Approval and Publication

An organization wants to prevent unreviewed content from being released. The model has workflow phases, a content version, and the approval version. The initial state is an unpublished draft. Actions are submission, revision, approval, rejection, and successful publication. The central safety invariant is that any published item is associated with an approval matching the content version that was published.

The engineering sequence begins by listing all operations that can change publication status. An explicit search then looks for a path from the draft initial state to a published configuration with a mismatched approval. Finding such a path yields a witness for policy review; not finding it in a bounded model only establishes the bounded result. The model cannot certify reviewer identity or database transaction atomicity unless those concerns are part of the chosen state and relation.

The primary benefit of the exercise is requirements precision. Instead of relying on a prose promise that “review always comes first,” the institution must decide what editing after approval means, whether direct publishing exists, and what observable event constitutes completed publication.

Scenario 2 — Network Connection Lifecycle

A network client may move through disconnected, connecting, established, retry_wait, and closed. A request to connect can lead to success or failure, and a timeout may trigger retry scheduling. A simple LTS can show whether it is possible to send data before establishment and whether every failure state has a defined recovery or terminal outcome.

A safety property might forbid send in all states except established. A progress property might require each started connection attempt eventually to either establish a session or fail definitively, but that property must account for lost packets and retry policies. An unbounded retry_wait cycle may be permitted unless the model includes a limit or fairness assumption.

The LTS describes logical possibilities. It is not yet a TCP specification: it omits sequence numbers, acknowledgments, congestion behavior, and real protocol requirements. Those features should be added only when relevant to the property under investigation.

Scenario 3 — Two Workers and a Shared Resource

Two workers need exclusive access to one resource. Each worker has local states idle, requesting, holding, and released. The global state includes both local control states and the lock owner. Under interleaving semantics, acquisition and release are atomic abstract steps, while work outside the critical section is independent.

The safety requirement is ¬(worker_A_holding ∧ worker_B_holding). A model that omits lock ownership may reach a configuration where both workers appear to hold the resource. That can be either a genuine design defect or a modeling omission; the remedy is to define the acquisition protocol precisely. Exhaustive exploration of a bounded two-worker model can identify violating schedules that manual sequential testing never exposes.

Progress questions are separate. A lock can guarantee mutual exclusion yet allow starvation if one worker never receives service. Fairness, queue discipline, and lock recovery determine whether a stronger progress claim is justified.

Scenario 4 — Recovery from a Failed Payment Step

A transaction process includes created, authorized, captured, settling, settled, reversed, and failed. The LTS clarifies which status changes are permitted after asynchronous processor notifications. A replayed notification may arrive after a refund and must not reactivate an irrevocably reversed operation without an explicit legal transition.

One safety property is that a settled transaction is never simultaneously classified as failed in the authoritative ledger. Another is that a reversal cannot be followed by an unexamined capture event. The correct state representation may require transaction identifiers, amounts, settlement revisions, and idempotency keys. A small phase-only graph is an orientation model, not proof of accounting correctness.

The scenario illustrates why transition systems are useful even when the final implementation is database-driven. They expose cross-service ordering rules and missing exception handling before those defects become production incidents.

Scenario 5 — Embedded Device and Maintenance Mode

An embedded controller supports off, initializing, operating, fault, and maintenance. It may not activate an actuator in maintenance mode. A formal model can examine whether startup tests, fault acknowledgments, or remote commands can accidentally bypass the maintenance interlock.

A simple LTS assumes every transition is a discrete action. If the requirement concerns a temperature threshold, deadline, or physical motion between steps, the plain graph may be too coarse. Timed automata or hybrid models may be needed. Formal abstraction should be selected according to physical risk and the observable properties, not because a finite diagram is convenient.

A successful safety analysis must be supplemented with hardware interlock evidence, sensor fault assumptions, watchdog design, and appropriate verification in the actual operating environment. The transition graph is one assurance layer rather than the entire safety case.

Scenario 6 — Account Login and Lockout

A login workflow has states such as unauthenticated, challenge_pending, authenticated, and locked. Actions include submitting credentials, issuing a challenge, completing a challenge, logging out, and reaching a retry limit. The LTS makes it possible to ask whether a user can reach authenticated without completing required checks or can continue trying credentials indefinitely after lockout.

A useful model includes an attempt counter and the authentication method used. If the count is abstracted to below_limit and at_limit, the transition relation must preserve the distinctions relevant to the property. Authentication state may also expire; a purely untimed graph cannot establish an expiration deadline without additional semantics.

The scenario clarifies the difference between a state transition and a security decision. The model's authenticate edge should encode the conditions that authorize the change, while production enforcement still depends on trusted implementations and consistent policy across interfaces.

Ten-Gate Transition-System Design Framework

Gate Question Required design artifact or evidence
1. Property What behavior or failure must be characterized? A clear safety, reachability, or progress question
2. State Which facts affect the answer? State variables, domains, and abstraction rationale
3. Initialization Where can an execution legitimately begin? Explicit initial-state set, including recovery
4. Actions Which events can trigger changes? Defined action alphabet and internal-step policy
5. Relation What does each transition permit? Guards, updates, and exhaustive-edge policy
6. Environment Which actors or external failures are modeled? Assumptions, nondeterminism, scheduling, and fairness
7. Observations What constitutes a visible trace? State labels, action projection, and event semantics
8. Analysis Which claims can be checked? Reachability, invariants, deadlock, and temporal properties
9. Fidelity How does the model relate to the implementation? Refinement mapping, test plan, monitored traces
10. Limits What remains outside the verification result? Bounds, omitted behaviors, tools, and residual risks

A credible modeling exercise completes these gates in an order driven by the question under investigation. Adding sophisticated formal logic before resolving basic state or transition ambiguity usually produces elaborate notation around an incomplete contract.

Common Modeling Mistakes

Treating a diagram as self-explanatory. Nodes and arrows do not define initialization, action semantics, error handling, or atomicity. Equating an absent edge with enforced denial. A closed-world specification is an assumption; the implementation must still honor it. Hiding security-critical state. A published status alone cannot prove that the current document version was authorized. Assuming nondeterminism means equal probability. A transition relation contains no implicit likelihoods.

Confusing reachability with inevitability. EF complete is not AF complete. Treating dead ends as universally wrong. Some terminal outcomes are legitimate. Ignoring partial or infinite runs. A service that remains enabled but never finishes can pass basic deadlock checks. Believing bounded exploration proves unbounded correctness. Bounds are a scope limitation unless supported by generalization arguments.

Collapsing multiple concrete actions into one unexamined atomic step. Races or partial failures may disappear from the model. Assuming logs faithfully reproduce transitions. Attempts, commits, replays, and observation delays need explicit treatment. Declaring a specification verified without naming its property. A correct model can satisfy the wrong requirement. These are failures of modeling discipline, not merely software defects.

Foundational path: begin with state sets, initialization, transitions, action traces, and reachability. Reconstruct a counterexample in the request workflow. Then study invariants, terminal-state classifications, and the distinction between safety and liveness. This progression makes later formal-language and model-checking material easier to interpret.

Automata path: move from this general relation-based foundation to Deterministic Finite Automata, Nondeterministic Finite Automata, and Regular Languages and Automata. Ask which additional structure turns a general behavioral relation into a string recognizer.

Verification path: after invariants and witness traces, continue to Reachability and Deadlock Analysis, Safety and Liveness Properties, and State-Space Exploration and Model Checking. Preserve property definitions, assumptions, and witnesses as the models become more complex.

Implementation path: connect specifications to State-Based Software Testing, State Machine Security, and State Machine Implementation Patterns. Focus on translating abstract actions into actual operations without losing invariants.

Summary of Essential Distinctions

The practical value of a formal transition system is its separation of possible configurations, permitted steps, initialized executions, observable traces, and properties to be checked. The same picture can support very different claims depending on whether actions are input-enabled, whether missing transitions are forbidden, whether termination is expected, and whether fairness or timing assumptions constrain continuations.

Reachability establishes the existence of a path; an invariant demands a fact in all reachable states; liveness concerns eventual progress across continuation paths. An explicit finite graph can be exhaustively searched, but a finite exploration cannot automatically justify an infinite-state claim. Composition, abstraction, and refinement allow models to scale and connect to implementation, provided their semantic obligations are declared and checked.

The foundational operating principle is to select the smallest precise model that still preserves the behavior relevant to the claim. A modest transition relation with an honest abstraction boundary is more useful than a sophisticated verification report whose initial conditions, external actors, or error transitions are unclear.

Sources and Further Reading

The following technical sources support the definitions and conceptual distinctions. Some references are formal treatments; others illustrate how transition-based specifications are applied to real systems. Links do not imply that a third-party source endorses this particular teaching example.

  • Christel Baier and Joost-Pieter Katoen, Principles of Model Checking, MIT Press, 2008, Chapter 2. Defines transition systems with state propositions and actions, as well as paths, traces, reachability, and model-checking fundamentals. Accessible text.
  • Edmund M. Clarke, Orna Grumberg, and Doron A. Peled, Model Checking, MIT Press, 1999. Foundational treatment of state-space exploration, temporal logic, and automated verification.
  • Leslie Lamport, Specifying Systems: The TLA+ Language and Tools for Hardware and Software Engineers, Addison-Wesley, 2002. Explains action-based specifications, stuttering, safety and liveness, and refinement. Author's book materials.
  • Leslie Lamport, The Temporal Logic of Actions, ACM Transactions on Programming Languages and Systems, 1994. Establishes a state-transition approach to temporal system specifications.
  • Leslie Lamport and Yuan Yu, Specifying and Verifying Systems with TLA+, Microsoft Research, 2002. Applied specification and verification of hardware protocols.
  • UPPAAL, Formal Semantics Documentation. Illustrates a timed transition-system formalization for extended timed automata.
  • UPPAAL, Tool Features. Documents state-space reachability, invariants, and diagnostic traces in a formal verification tool.
  • Gerard J. Holzmann, The SPIN Model Checker: Primer and Reference Manual, Addison-Wesley, 2003. Focuses on model checking concurrent systems and constructing counterexample executions.
  • Nancy A. Lynch, Distributed Algorithms, Morgan Kaufmann, 1996. Uses state-based models and rigorous reasoning about asynchronous and distributed computation.
  • Robin Milner, Communication and Concurrency, Prentice Hall, 1989. Develops labeled behavior, observational equivalence, and process-theoretic foundations.

When implementing a real system, consult the exact semantics of the selected notation and tool, particularly for fairness, deadlocks, state labeling, hidden actions, and infinite-path evaluation. Textbook notation and tool-specific conventions can differ without making either inherently incorrect.
