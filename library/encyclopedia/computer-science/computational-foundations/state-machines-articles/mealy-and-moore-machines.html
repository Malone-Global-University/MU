Definition and Scope

A Mealy machine and a Moore machine are deterministic finite-state transducers: they consume a sequence of inputs, change a finite internal state, and produce observable outputs. Unlike a deterministic finite automaton (DFA), whose central question is whether a complete input word is accepted, a transducer models the response emitted as the system runs. The distinction is fundamental for protocol controllers, embedded devices, interfaces, and event-processing software. A payment approval response, for example, is not merely an accepting state; it is an output whose value and timing must be specified.

In a Mealy machine, output depends on the present state and current input and is naturally attached to a transition. In a Moore machine, output depends on the present state alone and is naturally attached to a state. Both can express deterministic finite-state input/output behavior under appropriate conventions, but the concrete number of states, an initial output, the response boundary, and hardware timing can differ. This article develops the mathematical models, transition and output tables, exact translation methods, software implementations, tests, and design decisions that make this distinction useful.

The scope is deliberately narrower than the companion treatments of Deterministic Finite Automata, Formal Transition Systems, and Extended Finite-State Machines. We focus on finite-state, deterministic, total machines with one output symbol for each consumed input, while separately identifying the cases in which an application uses variable-length emissions, guards, timeouts, or side effects.

From Recognition to Transduction

A DFA tracks a state and, after reading an input, answers whether the resulting state is accepting. An output transducer instead exposes information during processing. Consider the sequence of badge-reader events valid, passage, invalid: a transducer might report unlock, relock, alarm as those events occur. The output sequence is part of the specification, not an incidental log. Two machines may end in the same state after a word while producing different intermediate responses; they are therefore not behaviorally equivalent as transducers.

This change in purpose changes the questions we ask. An engineer must define which inputs are possible, how unknown events are handled, which output is associated with reset, what happens on repeated inputs, and whether a response is produced synchronously with the event or becomes visible only after an update. For a Moore machine, there is also an output value at its initial state unless the external interface explicitly suppresses it. For a Mealy machine, the ordinary word-transducer convention emits one output per input symbol and no output before the first input.

A model that explicitly records outputs makes correctness claims testable: given the same initial state and the same input word, the specified output word must be reproduced. It also makes the boundary between a theoretical machine and a real controller visible. Real systems may have multiple clocks, nondeterministic external events, unbounded data, and asynchronous actions. Those aspects must be represented separately rather than silently attributed to a simple Mealy or Moore machine.

The Formal Mealy Machine

A standard Mealy machine is the tuple M = (Q, Σ, Γ, δ, λ, q₀), where Q is a finite nonempty set of states; Σ is a finite input alphabet; Γ is a finite output alphabet; δ: Q × Σ → Q is a total next-state function; λ: Q × Σ → Γ is an output function; and q₀ ∈ Q is the initial state. Totality means every state/input pair has exactly one successor and one output. Partial transition specifications are useful notations, but an implementation must state what happens outside the described cases.

For an input word a₁a₂…aₙ, define qᵢ = δ(qᵢ₋₁, aᵢ) and bᵢ = λ(qᵢ₋₁, aᵢ). The resulting output is b₁b₂…bₙ. Notice that bᵢ uses the source state qᵢ₋₁; the next state qᵢ is computed from that same source state and input. It is legal for an implementation to compute these in either order if it preserves the old-state value required by the mathematical definition.

For any input word of length n, a conventional Mealy transducer emits exactly n symbols. This immediately gives a useful test: a candidate implementation that accidentally adds a reset symbol, omits a response, or emits two responses for one input does not implement the stated model without an explicit interface adjustment. A separate start-up event can be modeled as an actual input, but doing so changes the declared input trace and should not be hidden inside the simulator.

The Formal Moore Machine

A standard Moore machine is the tuple N = (Q, Σ, Γ, δ, g, q₀). Its states, alphabet, transition function, and initial state play the same roles, but its output map is g: Q → Γ. Its visible output is determined solely by its current state. If q₀, q₁, …, qₙ are the states visited on a₁…aₙ, the complete Moore output sequence is g(q₀), g(q₁), …, g(qₙ).

This convention produces n+1 outputs for n inputs because the initial state already has an output. In software, the first value may be read during initialization; in a synchronous controller, it may be a value held at the output pins before the first active input sample. For comparisons with Mealy machines, it is common to discard this initial value and compare the n post-transition outputs g(q₁)…g(qₙ). That alignment is a declared observation rule, not an assertion that initial outputs do not exist.

A Moore machine can contain two distinct states with the same output; output values do not uniquely identify internal states. Conversely, a single Moore state cannot produce two different outputs at the same instant merely because different inputs arrive. To express an input-sensitive response through state outputs, an equivalent Moore realization may need distinct copies of a target state corresponding to different incoming output values.

Output Timing: A Necessary Convention

A theoretical machine maps an input word to an output word. A deployed controller also has an event schedule: inputs are sampled, state changes are applied, and outputs become visible at defined times. Confusion arises when a diagram's output labeling is mistaken for a complete timing specification. Mealy output can depend combinationally on the current input; Moore output follows current state. Yet either can be registered, buffered, or exposed as part of an atomic software step.

We therefore distinguish three concepts: logical symbol index (which input step owns a response), state-update boundary (whether the response is computed from the pre-update or post-update state), and physical observation time (when a consumer can read it). An aligned Moore conversion may produce g(qᵢ) after the ith transition, corresponding exactly to the Mealy output for that input; it does not necessarily introduce a whole extra logical symbol of latency. In some synchronous hardware realizations, a different allocation of registered logic can introduce additional cycle latency. That is an architectural choice that must be checked from the clocking diagram.

Reading State Diagrams

A Mealy diagram writes each edge label as input/output, such as coin/unlock; a Moore diagram writes a state's label as Locked/locked_indicator, and its edges carry the input that causes the transition. A self-loop still represents a consumed input and, for a Mealy machine, still produces an output. It is not shorthand for an event that never occurred. A diagram with no outgoing edge for an input either specifies a partial machine or leaves its failure behavior unspecified.

Labels also need a vocabulary contract. Does unlock denote a short pulse, a command posted to an actuator, or a persistent Boolean level? If the name identifies an event, two successive unlock outputs must remain distinguishable; if it identifies a level, consecutive identical values may mean a continuing state. A diagram does not settle this distinction on its own. Readers should write the output alphabet and the external interpretation next to the diagram rather than infer it from an informal drawing.

The companion State Machine Diagrams and Tables owns the general drawing conventions and diagram completeness tests. Here the emphasis is specifically on locating observable outputs correctly and converting between edge-output and state-output semantics.

A Two-State Turnstile Specification

Consider a constructed turnstile with states L (locked) and U (unlocked), and inputs coin and push. A coin in L unlocks the gate and moves to U; pushing in L produces an alarm and leaves it locked. A coin in U is returned; a push in U permits passage and returns it to L. These are illustrative logical outputs and do not claim to cover sensors, emergency egress, or physical safety. This design includes every state/input pair, so it is a total Mealy machine.

Current state Input Next state Mealy output Meaning
L coin U unlock Credential accepted
L push L alarm Unauthorized passage attempt
U coin U refund Repeated payment
U push L relock One authorized passage completed

This machine is intentionally small but already demonstrates why a Moore conversion can enlarge the state set. Incoming edges to U produce either unlock or refund; incoming edges to L produce either alarm or relock. A single Moore state for U or L cannot report both values. The conversion must distinguish the relevant incoming output history without changing which next inputs are possible.

Executable Mealy Turnstile

The first implementation uses dictionaries to make the formal transition and output functions visible. Each iteration retrieves both results from the current state, appends exactly one output, and only then updates the stored state. The assertion checks the entire trace, including the repeated-coin branch. For a production controller, invalid inputs and actuator errors would need a policy and an external safety layer; the example models only the declared alphabet.

STATES = {"L", "U"}
INPUTS = {"coin", "push"}
TABLE = {
    ("L", "coin"): ("U", "unlock"),
    ("L", "push"): ("L", "alarm"),
    ("U", "coin"): ("U", "refund"),
    ("U", "push"): ("L", "relock"),
}
assert set(TABLE) == {(q, a) for q in STATES for a in INPUTS}

def run_mealy(word, start="L"):
    state, outputs = start, []
    for symbol in word:
        if symbol not in INPUTS:
            raise ValueError(f"unknown symbol: {symbol!r}")
        successor, output = TABLE[(state, symbol)]
        outputs.append(output)
        state = successor
    return state, outputs

word = ["coin", "coin", "push", "push"]
final, output = run_mealy(word)
assert (final, output) == (
    "L", ["unlock", "refund", "relock", "alarm"]
)
assert len(output) == len(word)
print(final, output)

For the input coin, coin, push, push, the machine outputs unlock, refund, relock, alarm and returns to L. Crucially, the self-loop in U on coin emits refund; a simulator that skips outputs on self-loops would be incorrect. The example can be extended with a structured log of (state_before, input, output, state_after) records to produce a trace suitable for reviewing disputed events.

Transition Tables as Executable Contracts

A good transition table is more than a figure caption. It specifies the full input/state cross-product and can act as the source of truth for generated tests, code, or formal checks. A table should list the initial state, alphabet, output vocabulary, all transition rows, and the meaning of unexpected symbols. In languages with exhaustive pattern matching, every table row can become an explicit branch; in table-driven software, every pair should be checked before a release.

The table should not conflate output calculation with output delivery. unlock might mean “issue an unlock command” rather than “the physical latch is verified open.” If the actuator can reject a command, the subsequent acknowledgment is an independent input and may require additional states. Likewise a protocol controller that sends a response cannot assume the peer received it. The mathematical output symbol is an observable decision of the modeled component, not a guarantee about downstream effects.

A useful model-review exercise is to present each state with every input in the alphabet. Ask whether the next state and emitted value are unique and whether the output is safe for the stated conditions. For example, should repeated coin in U issue refund, a credit update, or no change? That choice is a requirements decision, not something derivable from the Mealy formalism itself.

Trace Semantics and the Extended Function

The single-step functions extend to input words. Let δ*(q, ε) = q and δ*(q, wa) = δ(δ*(q,w), a), where ε is the empty word. For the Mealy output function, let λ*(q, ε) = ε and λ*(q, wa) = λ*(q,w) · λ(δ*(q,w), a), where the dot concatenates a new output symbol. These recurrences specify exactly how a finite state produces an arbitrarily long output word.

For a Moore machine, the full output trace begins with g(q) and appends g(δ*(q, prefix)) after every input. Define the aligned, post-transition output γ*(q, a₁…aₙ) = g(q₁)…g(qₙ), omitting g(q₀). This explicit distinction matters when stating equivalence. One machine may agree with another on every nonempty aligned trace yet disagree on the value visible at reset. An auditor must choose which relation the product contract actually requires.

Extended trace definitions make inductive proofs straightforward. To prove that a conversion preserves outputs, establish that a converted state encodes sufficient information after a prefix and that one more symbol produces the correct next state and output. Because words are built by repeated extension, this local step plus the empty-word case yields a property for all finite input sequences.

Moore States and Persistent Outputs

A Moore machine is natural for state-exposure outputs such as READY, BUSY, or FAULT, where a state determines an indicator or stable operating mode. Imagine states Idle, Processing, and Done, with outputs idle, busy, and complete. An event causes a transition; the new state's indicator remains visible until the next transition. This is often easier to explain than an output attached to every triggering event. Still, the design must say whether a transition into Done triggers a one-time notification or simply makes the status value complete readable.

A one-time effect such as “send an email” is not automatically the same thing as a Moore output value. Reading a Moore state twice should not imply sending two emails. A practical event-driven implementation may calculate state-associated observable values separately from entry actions or transition side effects. The former fits the mathematical Moore definition directly; the latter requires explicit execution semantics that the foundational transducer model does not contain.

Outputs can also be vectors, not just single names. A Moore state might map to (LED_on, motor_enable, warning) where each component has a stable value. When modeling a real actuator, the safe reset state and the state mapping should be reviewed against independent interlocks; a state label alone is not sufficient assurance of safety.

Executable Moore Controller

This example is a small state-display controller. The initial output is read before any input; after each event, the state changes and its new associated output is appended. As written, a three-symbol input produces a four-symbol complete output trace. The test guards against the common error of evaluating g before updating the state and mistakenly treating that as the post-transition output.

NEXT = {
    ("OFF", "set"): "ON", ("OFF", "reset"): "OFF",
    ("ON", "set"): "ON", ("ON", "reset"): "OFF",
}
G = {"OFF": 0, "ON": 1}

def run_moore(word, start="OFF"):
    state = start
    full_output = [G[state]]           # initial output
    for a in word:
        if (state, a) not in NEXT:
            raise ValueError((state, a))
        state = NEXT[(state, a)]
        full_output.append(G[state])   # after transition
    return state, full_output

word = ["set", "set", "reset"]
state, full = run_moore(word)
assert state == "OFF"
assert full == [0, 1, 1, 0]
assert len(full) == len(word) + 1
print("initial plus post-step outputs:", full)

The second set symbol causes a self-loop while maintaining output 1; it is not omitted. The initial zero is a mathematically meaningful output, although an application interface could choose not to publish it. That choice must be made consistently when comparing a converted machine against a Mealy design.

Neither style is a general performance guarantee. Why Mealy and Moore Machines Are Interconvertible

For deterministic finite-state transducers with finite alphabets, both styles can describe the same per-input output relation when we adopt an appropriate initialization convention. A Moore-to-Mealy translation assigns each edge the output of its destination state. The Mealy output for the ith input then agrees with the Moore value after the ith transition. The Moore value before the first input is not represented by this Mealy word output unless one adds an initialization protocol.

For a Mealy-to-Moore translation, the destination state must encode not only the Mealy successor state but also the output just emitted on the incoming edge. That encoding is often written (q, b) for Mealy state q and last output b. A separate initial Moore state supplies a designated initialization value, or one otherwise establishes an initial-value convention. Without such care, a purported conversion may preserve future outputs but produce the wrong response for the first input or at reset.

The precise statement is therefore output equivalence under an observation convention. Equal strings at the same logical input steps do not by themselves prove identical timing at electrical pins, identical side-effect execution, or identical treatment of reset. Those require separate interface and implementation specifications.

Moore-to-Mealy Conversion Rule

Start with a Moore machine N = (Q, Σ, Γ, δ, g, q₀). Retain its state set, input alphabet, transition function, and initial state. Define the new Mealy output by the equation λ'(q, a) = g(δ(q, a)). In a diagram, copy the destination state's Moore output onto each incoming edge. After any input symbol, the Mealy output equals the Moore output of the newly reached state.

The conversion has the same number of states as the original machine before any optional minimization. It is important that the rule uses the destination state, not the source state. If we instead use g(q) we match the pre-transition Moore output, causing a one-input shift when compared against post-transition outputs. Both conventions can be modeled, but they are not the same claim and should never be interchanged silently.

The formula preserves output behavior for all input words by induction. For the empty word, both aligned output sequences are empty. Assume equality after a prefix that reaches state q. On the next symbol a, the Moore machine reaches δ(q,a) and emits its state's output, while the Mealy machine emits exactly g(δ(q,a)). Both advance to the same state. The result holds for the extended word.

Executable Moore-to-Mealy Conversion

The following construction converts the preceding OFF/ON Moore machine into a Mealy machine. Both functions run from the same initial state and consume the same input. The test compares the Mealy word with the Moore post-transition suffix, explicitly excluding the initial value. This is the correct alignment for the conversion formula.

STATES = {"OFF", "ON"}
ALPHABET = {"set", "reset"}
STEP = {
    ("OFF", "set"): "ON", ("OFF", "reset"): "OFF",
    ("ON", "set"): "ON", ("ON", "reset"): "OFF",
}
OUT = {"OFF": 0, "ON": 1}
MEALY = {
    (q, a): (STEP[q, a], OUT[STEP[q, a]])
    for q in STATES for a in ALPHABET
}

def trace(word):
    q, mealy, moore = "OFF", [], [OUT["OFF"]]
    for a in word:
        nxt, out = MEALY[q, a]
        q = nxt
        mealy.append(out)
        moore.append(OUT[q])
    return mealy, moore

for word in [[], ["set"], ["set", "reset"], ["reset", "set", "set"]]:
    x, y = trace(word)
    assert x == y[1:]
print("Moore outputs match Mealy after dropping initialization")

For the empty word, the Mealy sequence is empty and the Moore trace still contains 0; removing the first Moore element makes them equal. If a real device requires a reset-status response at startup, the converted Mealy interface must supply that information through a distinct initialization mechanism rather than pretending that the ordinary Mealy machine produced a zero-length-input symbol.

Mealy-to-Moore Conversion by State Splitting

Consider a Mealy state q reachable on incoming transitions whose outputs differ. A Moore state labeled only q could not expose all those incoming outputs, because g(q) is a single fixed value. We instead make a Moore state (q, b) for each output b that appears on an incoming transition to q. Its output is b. From (q, b) on input a, compute the original successor p = δ(q,a) and emitted output c = λ(q,a), then transition to (p,c). Notice that future behavior depends on q, not on the recorded b; the second component is solely the output label appropriate to the newly entered Moore state.

The usual presentation adds a fresh initial state START associated with an initialization symbol ⊥ that is not one of the original output symbols. From START, processing an input a follows the original initial state's step, entering (δ(q₀,a), λ(q₀,a)). For the original alphabet of inputs, the resulting Moore machine produces a sequence [⊥, b₁, …, bₙ]; after dropping the distinguished initial symbol, the outputs equal the Mealy word. An application can replace ⊥ with a defined reset signal, but that choice changes what observers see before processing starts.

Because the original machine is finite, there are finitely many such pairs: at most |Q|·|Γ| plus a start state before pruning unreachable states. This is an upper bound for a straightforward construction, not a requirement that the minimal Moore machine always has that many states. After conversion, standard state-equivalence methods may merge behaviorally indistinguishable states without affecting the declared output contract.

Executable Mealy-to-Moore Conversion

This program constructs a reachable Moore graph from the earlier turnstile table. It uses a special initial state with output None, treated as a sentinel outside the ordinary unlock/refund/relock/alarm output alphabet. The generated machine preserves the Mealy trace after that first symbol and therefore demonstrates the conversion precisely rather than relying on a diagram that may conceal initial-state assumptions.

from collections import deque

M = {
    ("L", "coin"): ("U", "unlock"),
    ("L", "push"): ("L", "alarm"),
    ("U", "coin"): ("U", "refund"),
    ("U", "push"): ("L", "relock"),
}
ALPHABET = ("coin", "push")
START = ("START",)

moore_next = {}
moore_out = {START: None}
queue = deque([START])
while queue:
    s = queue.popleft()
    original_q = "L" if s == START else s[0]
    for a in ALPHABET:
        q2, emitted = M[original_q, a]
        target = (q2, emitted)
        moore_next[s, a] = target
        if target not in moore_out:
            moore_out[target] = emitted
            queue.append(target)

def mealy_outputs(word):
    q, out = "L", []
    for a in word:
        q, x = M[q, a]
        out.append(x)
    return out

def converted_outputs(word):
    s, out = START, [moore_out[START]]
    for a in word:
        s = moore_next[s, a]
        out.append(moore_out[s])
    return out

for word in [(), ("coin",), ("push",),
             ("coin", "coin", "push", "push")]:
    assert converted_outputs(word)[1:] == mealy_outputs(word)
assert len(moore_out) <= len({"L", "U"}) * 4 + 1
print("reachable converted Moore states:", len(moore_out))

The converted states record a reachable original state and the output of the step that led there. An important implementation check is that the START state uses the original initial state L as its source; it must not interpret the sentinel as an ordinary Mealy state. Conversions that omit this special treatment frequently mishandle the very first symbol.

The two tracks agree on every post-input output. They are not literally identical as full-output traces because the Moore track has an initialization value. This distinction is exactly why a statement such as “the machines are equivalent” should specify an equivalence relation. It is also why tests should compare events at matched observation points, not merely compare the final state names.

Conversion Correctness Invariant

A useful invariant for the converted Moore machine is: after reading any nonempty input prefix w, its state is (δ*(q₀,w), last(λ*(q₀,w))). That is, the first component is the original Mealy state after w; the second is the last output produced by the original Mealy run. The Moore output is the second component. For the empty prefix, the converted machine remains in its specially defined START state, so the invariant has a separately handled base case.

The inductive step is direct. Suppose the converted state encodes (q,b), and the next input is a. The original Mealy machine produces (p,c) = (δ(q,a), λ(q,a)). The converted Moore transition goes to (p,c), whose output is c. Thus both the state projection and the newest output agree after the longer prefix. The argument explains why state splitting works and makes it easier to spot invalid optimizations: if a proposed merger loses the distinction between two different incoming outputs at the observation boundary, the invariant fails.

The same reasoning gives a criterion for a correct simulator: the observed sequence must be reproducible from the declared old state and input, and the next state must carry sufficient information for subsequent events. An implementation can use different internal names, but its external traces must preserve this invariant after the agreed initialization adjustment.

Equivalence as a Relation on Observable Traces

When comparing two Mealy machines, a natural equivalence relation requires them to produce the same output word for every input word from their respective initial states. State names and state counts need not agree. When comparing Moore machines, full-trace equivalence additionally requires agreement at initialization; alternatively an interface may define equality only on outputs observed after inputs. A comparison between a Mealy machine and a Moore machine must explicitly establish this alignment.

Formally, let obs(M,w) be the output word of a Mealy machine and let post(N,w) be the Moore machine's state outputs after each consumed symbol, without its initial output. Post-transition trace equivalence means obs(M,w) = post(N,w) for every w ∈ Σ*. If a system's external contract includes the Moore initial output, that signal must be compared separately. Two implementations that differ only before the first event can still be meaningfully different to users or upstream components; a device may be expected to announce READY immediately at boot.

For finite deterministic transducers, checking equivalence does not require trying all infinitely many words. A search over pairs of machine states can detect the shortest input word on which their output functions differ. If no reachable pair has a differing output for an input, the relation is preserved for every future input. This is the same product-state reasoning used in DFA equivalence, but outputs rather than accept/reject status drive the disagreement test.

Distinguishing Words and Product-Machine Search

Given two Mealy machines with the same input and output alphabets, begin at the pair of initial states (q₀, r₀). For each reachable pair and each input a, compare λ₁(q,a) against λ₂(r,a). If they differ, the path to that pair followed by a is a distinguishing input word. Otherwise add the pair of successor states (δ₁(q,a), δ₂(r,a)) to the search. Breadth-first search returns a shortest distinguishing word by number of input symbols, assuming all symbols have equal unit cost.

Because there are at most |Q₁|·|Q₂| pairs, a total deterministic finite comparison terminates. The naive table-based cost is O(|Q₁|·|Q₂|·|Σ|), excluding any expensive output comparison or data normalization. The result is a proof of equivalence under the chosen alphabet and initial conditions only if both machines are complete and the comparison uses the correct output alignment. A partial specification must first be completed consistently, or the test should report unspecified transitions rather than quietly treat them as valid.

A counterexample tells the designer which user-visible behavior changed during a refactor. It is generally more useful than a simple “not equivalent” Boolean, because it can be replayed in the original and revised implementations. The witness should include the input word and both output words, as well as the first mismatching step.

Executable Mealy Equivalence Checker

The following breadth-first search returns a shortest distinguishing input sequence between two deterministic Mealy tables, or None when their outputs agree on all possible input words. The deliberately altered turnstile model replaces the response refund with ignore; the shortest witness is two consecutive coin inputs, because the mismatch occurs only after entering U.

from collections import deque

GOOD = {
    ("L", "coin"): ("U", "unlock"),
    ("L", "push"): ("L", "alarm"),
    ("U", "coin"): ("U", "refund"),
    ("U", "push"): ("L", "relock"),
}
CHANGED = dict(GOOD)
CHANGED["U", "coin"] = ("U", "ignore")

def shortest_difference(left, right, alphabet, left_start, right_start):
    todo = deque([(left_start, right_start, ())])
    seen = {(left_start, right_start)}
    while todo:
        q, r, word = todo.popleft()
        for a in alphabet:
            q2, x = left[q, a]
            r2, y = right[r, a]
            if x != y:
                return word + (a,), (x, y)
            pair = (q2, r2)
            if pair not in seen:
                seen.add(pair)
                todo.append((q2, r2, word + (a,)))
    return None

assert shortest_difference(GOOD, GOOD, ("coin", "push"), "L", "L") is None
witness = shortest_difference(
    GOOD, CHANGED, ("coin", "push"), "L", "L"
)
assert witness == (("coin", "coin"), ("refund", "ignore"))
print("first differing input word:", witness)

A systematic acceptance test should run this equivalence check on a machine translated between Mealy and Moore styles, using the corresponding aligned outputs. It should also retain direct trace tests for initialization and for events near a reset or cancellation boundary—areas where the abstract equivalence relation intentionally excludes some deployment semantics.

State Equivalence and Minimization of Transducers

Two Mealy states p and q are behaviorally equivalent if every future input word produces the same future output word when started from either state. For a total deterministic machine, that is captured recursively by checking, for every input a, that their immediate outputs agree and their successors are also equivalent. This relation can be found by iterative partition refinement or by searching for distinguishing words. Merge only genuinely equivalent states, not states that merely happen to have identical labels on their outgoing edges for one input.

For Moore machines, state equivalence additionally requires their current outputs to be equal: g(p) = g(q). After that, the successors on every input must again be equivalent. This creates a natural initial partition by Moore output value. A conversion from Mealy to Moore may introduce several states sharing an underlying original state but displaying distinct outputs; those copies are not equivalent as full Moore states when their current outputs differ. Removing that distinction would change externally visible information.

State minimization is valuable but subordinate to the interface contract. When outputs represent actuator commands or security-relevant decisions, a refactor that preserves final state but changes a transient output can cause an operational incident. For detailed partition-refinement algorithms, see the specialist Automata Minimization article. Here the key is to minimize with respect to transducer outputs, not with respect to the DFA accept/reject criterion.

A Partition-Refinement Thought Experiment

Suppose a Moore machine has states A, B, C, and D with outputs 0, 0, 1, 1. A first partition is {A,B} and {C,D} because differing current outputs prohibit full-output equivalence. Now consider an input x. If A transitions to the 0 block and B transitions to the 1 block, then an observer sees different outputs after x, so A and B must be separated. Apply the same argument for each input and repeatedly refine the blocks until none split.

A Mealy machine instead begins by grouping states according to the vector of immediate outputs over all input symbols. States that respond identically to each single input may still be distinguishable by longer words if their successor states respond differently later. The iterative refinement then uses both current output vectors and successor partitions to find the final equivalence classes.

The point is not that one minimization algorithm is universally cheaper, but that the observable output definition shapes the state equivalence relation. A table entry describing next_state without output is insufficient to establish transducer equivalence. A review that performs only reachability analysis can remove unreachable states, yet still leave redundant reachable states; a review that only compares output values can merge states that lead to different future behavior.

Encoding Outputs as Symbols, Vectors, or Records

The formal alphabet Γ need not contain just one-bit values or English words. A symbol can be a tuple such as (status, error_code, authorization_flag), a fixed-size bit vector, or an enumerated message type. Mathematically, a tuple is still a single element of the output alphabet. This permits one output per input while representing multiple simultaneous outputs. If fields range over finite sets, the overall alphabet remains finite even when its number of possible combinations is large.

However, a continuously growing error message, arbitrary user string, or unbounded transaction balance cannot be modeled faithfully as a finite output alphabet without abstraction. A system that copies an arbitrary input payload to its output is not generally captured by a plain finite-output-symbol Mealy machine unless the alphabet itself is appropriately bounded or the model is extended. Similarly, a hardware bus may expose many bits at once, but a fixed-width word is finite for a fixed width.

Designers should distinguish no event, idle, and unknown. An output symbol NONE may intentionally signal that nothing happened on a particular input step; that is still one output symbol under the standard synchronous transducer convention. By contrast, an event stream that literally emits zero, one, or several messages for one input has variable-length output behavior and may be modeled with an extended transducer or with an output word rather than a single symbol.

Output Events Versus Output Levels

A Mealy output send_ack is naturally interpreted as an event or command issued for the current input, while a Moore output busy is naturally interpreted as a persistent level or observable property of the current state. These are design conventions, not mathematical restrictions. Either machine can represent finite status words or command codes if the event and observation rules are made explicit. What matters is whether consumers react to a value or to a change/occurrence.

For example, suppose a monitor repeatedly reports alarm on every unauthorized button press. If the application exposes a stream of alarm events, every repeated alarm occurrence counts. If instead it exposes the current alarm lamp state, repeated identical values may only describe the lamp's persistent condition. An adapter that changes a stream of events into a status value needs edge detection or an event counter if each occurrence is significant. Otherwise, successive identical outputs become indistinguishable to downstream consumers.

This distinction often explains why a superficially equivalent Moore implementation appears to “lose” alerts: it may have preserved a persistent state but discarded the event semantics. A correct design can expose a ALARM_ACTIVE status and separately publish an ALARM_TRIGGERED event. That is a composite interface; it should not be hidden behind one unexplained diagram label.

The Initial-Output Problem

Consider an equipment monitor whose Moore initial state is SAFE with output green. A converted Mealy machine emits no output before its first input under standard semantics. If the user interface requires an immediate green indicator when the monitor starts, output-equivalence after input steps is insufficient. The system needs an initialization response, a persistent state query, an explicit initialize input, or a separate level output channel.

The reverse problem arises when converting a Mealy machine to Moore. A constructed Moore START with a sentinel is mathematically convenient, but it may be inappropriate to display that sentinel to end users. A software API may suppress the first internal output and only publish post-event responses; hardware may initialize its output pins to a safe concrete value. These solutions implement distinct interface contracts even if they share the same input/output words after the first input.

The safest specification is a short initialization contract: initial internal state, initial observable outputs, whether the initialization action itself is logged, and whether the first external input can arrive before initialization completes. Reset behavior should be tested as part of this contract, not simply described as “set state to q₀.”

Reset, Reinitialization, and Power-Up Behavior

Reset is often treated as an implementation feature rather than an alphabet symbol. If it can occur at any time, however, it changes the state and possibly outputs. There are two valid modeling strategies: include reset explicitly as an input with defined behavior from every state, or place reset outside the machine with a separate transition that restores the initial configuration and publishes specified outputs. The choice affects equivalence checking because a comparison that ignores reset cannot certify reset-time responses.

A Moore output usually becomes whatever the reset state maps to after resetting, but the physical output may remain unstable while hardware resets or while software services restart. A Mealy controller can be given a reset event that emits reset_ack, but the ordinary definition does not generate such an output automatically. In safety-sensitive equipment, the reset-state output should be a safe level selected independently of whether the modeling style is Mealy or Moore.

If the device supports warm restart, persisted state recovery, or late initialization, a single fixed q₀ may not capture the startup possibilities. That calls for a richer initialization model or an environment assumption. A claim that two machines are equivalent “from the initial state” must not be generalized to all recovered states without an additional proof.

Clocked Hardware Interpretation

In a synchronous digital implementation, a state register stores the current state. Combinational next-state logic computes the state that will be loaded at the next active clock edge. A Moore output decoder uses the registered current state; a Mealy output decoder may use both the current state bits and current inputs. In logic equations, q_next = F(q, input), with either out = G(q) (Moore) or out = H(q,input) (Mealy).

The input-to-output combinational path in a Mealy realization can allow a response before the next state-register update, whereas a Moore realization commonly reflects a newly registered state following the next clock edge. This can make Mealy attractive for certain cycle-sensitive outputs. It does not follow that all Mealy implementations respond earlier: registering the Mealy output may delay it; retiming a Moore design or changing the interface pipeline may alter the comparison. The actual constraint is the clock-to-output and input-to-output timing budget.

Hardware state representations also influence circuit complexity. A machine with fewer symbolic states may not produce smaller or faster logic after binary or one-hot encoding, synthesis, and timing closure. State selection should therefore be based on observable behavior and verified implementation characteristics rather than assuming that the theoretically smaller machine is always superior.

Glitches, Synchronization, and Output Registration

A Mealy output that depends directly on input combinational logic may change when the input changes, even while the state register is unchanged. If the input contains an asynchronous pulse or electrical bounce, a transient output can occur unless the design synchronizes, qualifies, or registers the signal. A Moore output based only on stable registered state is generally less directly sensitive to instantaneous input changes, but it is not automatically glitch-free: a poorly designed combinational state decoder can still exhibit hazards while state bits switch.

Critical controls often register outputs or use carefully designed handshakes and interlocks. Registering a Mealy output can improve stability but affects when downstream logic sees the response. Synchronizers reduce metastability propagation risk for asynchronous digital signals; they do not replace domain-crossing protocols for multi-bit data, pulse capture, or coherent message transfer. External pushbuttons typically need debouncing in addition to clock-domain considerations.

In software, there is no literal hardware glitch from a transient Boolean gate value, but there are analogous race conditions: reading partially updated state, sending an event before a transaction commits, or publishing two conflicting responses from concurrent handlers. The design's event-processing semantics and atomicity must be specified independently of whether output is drawn on a state or edge.

Hardware Timing Example: A Pattern Detector

Suppose a serial detector should pulse high when the most recently received bits end with 101. One Mealy design can hold only the prefixes needed for the next comparison and assert its detect output on the transition that receives the final 1. A Moore design can enter a MATCH state and expose output 1 there. If the output must be read at a particular clock edge, the implementer must align the two traces to that edge and decide whether the Moore MATCH state persists for a cycle or is a registered representation of the completed input sample.

Repeated pattern occurrences add another requirement. For inputs 10101, there are two overlapping occurrences of 101; the prefix memory after one match matters to recognizing the next. A design that returns to an unconditional start state after detection may miss the overlap. This is a state-transition correctness issue common to both styles, not a reason to prefer one output convention.

The following output-level simulator reports detections in a consistent one-output-per-input stream. The code is a finite memory of recent input history; it is not a hardware gate-level model. The output remains synchronized with consumed symbols, allowing a later Mealy or Moore circuit implementation to be compared against the same reference trace.

Executable Overlapping-Pattern Detector

This Mealy-style detector remembers a bounded suffix of previous bits and tests each new sample. The pattern length is fixed, so the representation is finite; a production hardware design could compile the suffix behavior into a small state-transition table. The example verifies overlapping occurrences and that every input produces exactly one output bit.

PATTERN = "101"

def detect_101(bits):
    state = ""           # bounded suffix of previously read bits
    results = []
    for bit in bits:
        if bit not in "01":
            raise ValueError("expected a binary symbol")
        window = state + bit
        results.append(1 if window.endswith(PATTERN) else 0)
        # Keep only the longest relevant suffix for the next input.
        state = window[-(len(PATTERN) - 1):]
    return results

assert detect_101("101") == [0, 0, 1]
assert detect_101("10101") == [0, 0, 1, 0, 1]
assert detect_101("111") == [0, 0, 0]
assert detect_101("") == []
print(detect_101("10101"))

For this fixed length-three pattern, using the most recent two symbols as a state is valid although not necessarily minimal; several different suffixes can be merged in a minimized machine. More efficient realizations keep only those suffixes that are also prefixes of 101. The critical correctness condition is that two input prefixes may share a state only when every possible continuation generates the same future output trace.

A Protocol Acknowledgment Controller

Protocol responses illustrate a natural Mealy use case. An endpoint may be CLOSED or OPEN; on a valid open request in CLOSED, it moves to OPEN and emits ack; on another open in OPEN, it may emit already_open without changing state. A Moore model with only CLOSED and OPEN cannot encode the difference between ack and already_open as state-only outputs, because both requests end in OPEN. State splitting can fix the mathematical output mapping, but the extra internal states may add conceptual overhead.

At the implementation layer, an acknowledgment's delivery is separate from its generation. A network send may fail, the peer may retry, or two logically identical requests may carry different identifiers. Those requirements can demand request IDs, retransmission counters, or an unbounded message store beyond the plain finite transducer. Treat the finite model as the control skeleton and explicitly model any bounded or abstracted data.

A protocol can also define events that generate no response. Under the fixed one-symbol-per-input convention, represent this as a designated output SILENT. If the real system emits a sequence of packets of variable length, the observable model may need outputs that are words or lists rather than single symbols. A protocol review should state whether a SILENT symbol is externally visible or merely an internal placeholder.

Software Reducers and Pure Transition Functions

The safest way to implement a Mealy machine in event-driven software is often as a pure function step(state, event) -> (new_state, output). It takes a complete old state and one input event, returns an explicit next state and output, and performs no external side effects. The caller can then apply the update and publish the result according to a separate transaction policy. This separation makes tests deterministic and allows replay of recorded input sequences.

A Moore machine can be represented as step(state, event) -> new_state plus view(state) -> output. A user interface can call view whenever it needs the current status without accidentally triggering an action. If a system needs both event notifications and persistent status, it can implement both channels deliberately rather than forcing a choice of notation to carry unrelated semantics.

Pure reducers also expose the exact moment at which a bug could arise. Mutating the shared state before computing a Mealy output may cause λ(new_state,event) to be used where λ(old_state,event) was required. In a concurrent application, an actor mailbox or serialized event loop can guarantee one event is processed at a time; otherwise the caller needs locking or transactional state management.

Executable Pure Reducer with Replay

The following reducer returns an immutable pair representing the successor and output. The driver logs full traces and verifies that replaying the same word from the same initial state gives identical results. The function contains no I/O and does not rely on process-global mutable state, which makes it suitable as a reference oracle for a more complex service.

from dataclasses import dataclass

@dataclass(frozen=True)
class Result:
    next_state: str
    output: str

TRANSITIONS = {
    ("CLOSED", "open"): Result("OPEN", "ack"),
    ("CLOSED", "close"): Result("CLOSED", "already_closed"),
    ("OPEN", "open"): Result("OPEN", "already_open"),
    ("OPEN", "close"): Result("CLOSED", "ack"),
}

def step(state, event):
    try:
        return TRANSITIONS[state, event]
    except KeyError as error:
        raise ValueError("unspecified state/event") from error

def replay(events):
    state, log = "CLOSED", []
    for event in events:
        result = step(state, event)
        log.append((state, event, result.output, result.next_state))
        state = result.next_state
    return state, tuple(log)

word = ("open", "open", "close")
assert replay(word) == replay(word)
final, log = replay(word)
assert final == "CLOSED"
assert [row[2] for row in log] == ["ack", "already_open", "ack"]
print(log)

Logging both old and new state permits later comparison with a formal table. The replay guarantee holds only if the event sequence and initial state fully determine the modeled behavior. Real clocks, randomness, database reads, network failures, and authorization checks must either be inputs to the reducer or live in an explicitly separated outer layer.

Event Ordering and Atomicity

A transducer processes a sequence of inputs. If an application handles multiple events concurrently, it must establish which sequence the machine is actually following. Two simultaneous events can yield different traces when reordered: a coin then push can authorize passage, while push then coin first produces an alarm. A requirement to be correct under concurrency may therefore need serialization, an ordering policy, or a richer concurrent transition model.

The step (state,input) -> (next,output) should be observed atomically at the selected abstraction boundary. Publishing output before durably recording new state can leave clients believing that an operation completed when a subsequent crash rolled it back. Recording state before publishing output can require a retry mechanism to avoid lost notifications. Patterns such as a transactional outbox, durable queue, and idempotent command handling address delivery consistency, but they are not properties supplied automatically by either Mealy or Moore mathematics.

State machine transitions and external side effects are also not necessarily reversible. A payment command may be emitted and processed elsewhere even if a local handler fails. The formal model should distinguish a decision to send a command from acknowledgment that the command took effect, representing the acknowledgment as a later input where appropriate.

Invalid Inputs and Totality Policies

In a formal total machine, every state/input pair has a defined result. Real software receives malformed, unknown, out-of-order, or unauthorized events. It is unsafe to equate “not in the table” with “ignore,” because ignoring an input can still need an error response, audit entry, or alarm. One disciplined approach is to include an explicit INVALID input class with a total transition policy; another is to reject invalid representations before they enter the machine and document validation as a separate interface layer.

If validation collapses many raw inputs into one abstract symbol, the implementation must prove that those inputs genuinely have the same required observable behavior. For example, treating malformed credentials and expired credentials as equivalent might be acceptable for a generic public error message but insufficient for internal monitoring or rate limiting. Output secrecy, input validation, and authentication are responsibilities of the surrounding security design; the small finite-state model can only formalize the cases it includes.

A default self-loop is especially dangerous when it silently suppresses failure events. It might be correct for idle_tick but incorrect for emergency_stop. Requirements should identify whether a fault transitions to a safe state, emits a warning, or must be handled by a system independent of the FSM. Completeness is a property of a declared abstraction, not proof that every real-world input has been represented.

An Explicit Unknown-Event Policy

This example separates recognition of event names from the transducer's legitimate state/event table. Unknown event names produce an exception rather than a concealed no-op. If the product requires recovery from unknown events, a caller may translate the exception into a structured rejection with a persistent audit record. That rejection behavior can then be modeled as an explicit output if it belongs within the interface contract.

VALID_EVENTS = {"start", "finish", "cancel"}
TABLE = {
    ("IDLE", "start"): ("BUSY", "started"),
    ("IDLE", "finish"): ("IDLE", "invalid_finish"),
    ("IDLE", "cancel"): ("IDLE", "already_idle"),
    ("BUSY", "start"): ("BUSY", "already_busy"),
    ("BUSY", "finish"): ("IDLE", "completed"),
    ("BUSY", "cancel"): ("IDLE", "cancelled"),
}
assert set(TABLE) == {
    (state, event)
    for state in ("IDLE", "BUSY") for event in VALID_EVENTS
}

def safe_step(state, event):
    if event not in VALID_EVENTS:
        raise ValueError(f"unsupported event: {event}")
    return TABLE[state, event]

assert safe_step("BUSY", "cancel") == ("IDLE", "cancelled")
try:
    safe_step("BUSY", "power_failure")
except ValueError:
    pass
else:
    raise AssertionError("unknown event was silently accepted")
print("declared events total; undeclared events rejected")

The error path does not guarantee real fault tolerance. It merely avoids accidental ambiguity. For a controller facing potentially dangerous external events, the designer must determine whether power_failure is an environmental condition outside the machine, a specific input that leads to a safe state, or a signal handled by independent hardware.

Variable-Length Outputs and Generalized Transducers

The basic Mealy definition emits one symbol in Γ per consumed input. A more general sequential transducer may produce a finite word for each step: λ: Q × Σ → Γ*. That allows zero, one, or multiple output symbols per input, which is useful for serializers, packet assemblers, and event-routing systems. It is no longer the strict one-output-symbol Mealy convention used in the earlier equivalence proofs without revising how outputs are aligned.

Generalized outputs require an additional choice of observable granularity. A state transition might emit an entire packet whose bytes can be observed individually, or might atomically publish a message. A consumer observing bytes may see intermediate prefixes that a consumer observing complete packets does not. This distinction affects equivalence, safety properties, and error handling. A conversion that simply splits states by the last symbol is not enough to preserve arbitrary variable-length outputs under every observation convention.

If the system uses timers, data registers, guards, or nested state configurations, the formalism should be expanded deliberately. Extended Finite-State Machines addresses finite control paired with data variables; Hierarchical Statecharts addresses nested and concurrent state regions; and SCXML Execution Semantics concerns event processing and entry/exit behavior in a particular executable framework.

A Vending-Machine Case Study

A constructed vending controller offers another output-sensitive example. Let credit range over 0, 1, and 2, with an item price of two units. Inputs are insert and select. In a Mealy version, insert in credit state 1 moves to credit 2 with output ready, while select in credit state 2 produces dispense and resets credit to 0. A select in lower-credit states emits insufficient, leaving credit unchanged. The state set can remain small because each step's response is attached to the event.

A Moore interpretation could expose persistent credit-status outputs, such as zero, one, and ready, but it would need special treatment for the one-time dispense action. If dispense becomes a distinct state output, the state must have a defined exit rule so that the item is not dispensed repeatedly whenever code reads the state. In an event-driven implementation, a better separation might be a Mealy command stream for dispensing plus a Moore projection for credit display.

Credit state insert -> state/output select -> state/output
0 1 / accepted 0 / insufficient
1 2 / ready 1 / insufficient
2 2 / return_coin 0 / dispense

The machine abstracts away coin denomination, refunds after power failure, delivery confirmation, and inventory. These omissions are intentional boundaries for a teaching example, not indications that a real vending machine can be certified with six transition rows.

Executable Vending-Machine Controller

The code below implements the table directly and demonstrates that a select event produces either insufficient or dispense depending on the old credit state. It also checks how a repeated coin at full credit is handled. A production version should use a currency-safe representation, account for inventory and device responses, and preserve audit records for cash handling.

VEND = {
    (0, "insert"): (1, "accepted"),
    (0, "select"): (0, "insufficient"),
    (1, "insert"): (2, "ready"),
    (1, "select"): (1, "insufficient"),
    (2, "insert"): (2, "return_coin"),
    (2, "select"): (0, "dispense"),
}

def vend(events):
    credit, outputs = 0, []
    for event in events:
        credit, response = VEND[credit, event]
        outputs.append(response)
    return credit, outputs

assert vend(["select"]) == (0, ["insufficient"])
assert vend(["insert", "insert", "select"]) == (
    0, ["accepted", "ready", "dispense"]
)
assert vend(["insert", "insert", "insert"]) == (
    2, ["accepted", "ready", "return_coin"]
)
print(vend(["insert", "insert", "select"]))

This example also illustrates why final-state comparison alone is inadequate. Both select from credit 0 and select from credit 2 end in credit 0, but their outputs differ. An implementation that only tests the final credit balance could pass while failing to dispense an item or incorrectly dispensing one.

Separating Commands from Acknowledgments

An actuator command and its acknowledgment are two distinct external observations. In the turnstile, unlock is the controller's output; unlocked_sensor may arrive later as an input confirming that the gate is physically open. A reliable control protocol should not leap from “command issued” to “mechanism verified” without modeling the response path. Adding PENDING_UNLOCK and FAULT states may be necessary when actuation can fail or time out.

This is not strictly a Mealy-versus-Moore problem. Either formalism can include a bounded acknowledgment handshake. What changes is how outputs such as command_unlock, awaiting_confirmation, and fault_indication are represented. A Mealy machine may emit the command on a transition into a waiting state; a Moore machine may expose WAITING as a state status. A real controller may combine these concepts through separate output channels.

A timing guarantee such as “confirmation must arrive within two seconds” cannot be expressed precisely by a finite-state machine with no clocks unless time is abstracted into explicit finite events, such as timeout. For more rigorous real-time models see Timed Automata. In any architecture, the safety-critical physical interlock should not rely exclusively on a high-level software event representation.

Handshake Example with a Separate Status Channel

The following miniature design separates the Mealy response from a Moore-style status projection. The transition function may issue command_open when a request arrives, while the status opening remains visible until a separate acknowledgment event occurs. Both outputs are defined by a single state machine, but they represent different observable channels and should not be confused.

STEP = {
    ("CLOSED", "request"): ("OPENING", "command_open"),
    ("CLOSED", "opened"): ("CLOSED", "unexpected_ack"),
    ("CLOSED", "timeout"): ("CLOSED", "no_action"),
    ("OPENING", "request"): ("OPENING", "already_pending"),
    ("OPENING", "opened"): ("OPEN", "confirmed"),
    ("OPENING", "timeout"): ("FAULT", "raise_fault"),
    ("OPEN", "request"): ("OPEN", "already_open"),
    ("OPEN", "opened"): ("OPEN", "duplicate_ack"),
    ("OPEN", "timeout"): ("OPEN", "no_action"),
    ("FAULT", "request"): ("FAULT", "reject_fault"),
    ("FAULT", "opened"): ("FAULT", "reject_fault"),
    ("FAULT", "timeout"): ("FAULT", "reject_fault"),
}
STATUS = {
    "CLOSED": "closed", "OPENING": "opening",
    "OPEN": "open", "FAULT": "fault"
}

def run(events):
    state, records = "CLOSED", []
    for event in events:
        state, command = STEP[state, event]
        records.append((command, STATUS[state]))
    return state, records

state, records = run(["request", "opened"])
assert state == "OPEN"
assert records == [("command_open", "opening"), ("confirmed", "open")]
assert run(["request", "timeout"])[0] == "FAULT"
print(records)

This model is deliberately still finite and deterministic. It assumes the set of possible events is exactly request, opened, and timeout, and it does not attempt to represent simultaneous hardware faults. The status projection could be displayed continuously, while the command outputs should be processed exactly once for each input step according to the surrounding delivery contract.

Mealy and Moore Models in User Interfaces

User interfaces often mix state-associated display values and event-associated feedback. A login component might have state SIGNED_OUT, AUTHENTICATING, or SIGNED_IN, with a Moore-style display function selecting the current screen. Separately, a login attempt may produce a Mealy-style output such as show_validation_error or start_auth_request. The state does not need to be renamed for each transient error if the interface explicitly handles those event outputs.

An error banner can be modeled either as part of the persistent state or as an event followed by a display update. The choice depends on whether the message must survive redraws, navigation, retries, or reloads. Treating an important error as a mere transient command can make it disappear unexpectedly; treating every command as a permanent state can create unnecessary state proliferation. A useful design separates state, state-derived view, and effects and documents which channel each consumer uses.

UI state machines also require care around asynchronous responses. A late response to an earlier request can arrive after the user has canceled or initiated a newer request. The model must either carry request identities as state/data or abstract those responses into separately validated input classes. The pure finite-state form is only adequate when the relevant distinctions are genuinely finite and represented.

Monitoring and Alerting Systems

A machine that monitors equipment might expose a Moore-style state NORMAL, WARNING, or CRITICAL, from which dashboards compute persistent colors and labels. It may additionally emit Mealy-style alert events when a threshold crossing occurs. A status view and a notification stream answer different questions: what condition holds now? versus what event just happened? If a stream is reconstructed from status changes, repeated threshold violations without a change in status may be lost.

Thresholds should be understood as inputs to an abstraction layer. If a raw temperature ranges over many possible values, a classifier might map it into the finite alphabet below, inside, or above. The precision, hysteresis, sensor faults, and sampling schedule belong to the overall specification. A two-state warning machine that changes output on every boundary crossing may chatter if measurements oscillate around the threshold; hysteresis adds states or data to prevent unhelpful toggling.

The security and operational implications are substantial: failure to distinguish an alarm event from an ongoing alarm status can lead to missed pages or repeated paging. Specify event deduplication, acknowledgement, and silencing behavior explicitly rather than expecting the Mealy/Moore distinction to choose the policy automatically.

Finite-State Size and Engineering Complexity

The number of states is one useful measure of model complexity, but not the whole cost. A Mealy machine may use fewer states yet have more complex combinational output logic, larger edge tables, or harder timing constraints. A Moore machine may use more states but produce simpler output decoding and clearer persistent-state displays. In software, the number of distinct states may have less influence on runtime cost than transition-table representation, event validation, logging, and external I/O.

The straightforward Moore-to-Mealy conversion introduces no extra states. The straightforward Mealy-to-Moore conversion has an upper bound of one initial state plus |Q|·|Γ| output-labeled state pairs, although only reachable pairs are necessary. Some original output symbols may never occur on edges entering a given state, reducing the actual count. Equivalent pairs may later be minimized, provided current output values and future behavior are preserved.

Runtime simulation is linear in the number of consumed input symbols for constant-time dictionary or array lookups: O(n) time for n inputs. Storing the complete output word takes O(n) space; streaming outputs to a sink can use O(1) additional trace storage for a fixed-size state and output symbol. Conversion and equivalence-checking algorithms have costs in machine-state and alphabet sizes, not in the length of one example input word.

If the physical input event alphabet is enormous, it is often necessary to classify events into a smaller symbolic alphabet or use a guarded extended machine. The cost of that classifier is outside the finite transducer's lookup count. Complexity estimates should state whether they count output buffering, event logging, and the size of represented output symbols.

Testing an Output-Producing Machine

A credible test plan checks the specified output word, not only the final state. For each test sequence, log the initial state, inputs in order, output after each input, and final state. Mealy implementations should be tested against the source-state output rule; Moore implementations should be tested for their initial output and for the post-transition output of every input. Tests must cover self-loops, repeated events, reset boundaries, and every declared state/input pair.

Because the state and input alphabets are finite, engineers can generate all input words up to a chosen depth, cross-check alternative implementations, and search for counterexamples. Such bounded enumeration is a powerful regression test but is not a proof for words of arbitrary length. Equivalence-checking algorithms over the finite product state graph give a stronger result when the model assumptions hold. For software integrated with I/O, tests must separately verify exactly-once intent, message loss/retry semantics, and safe behavior on invalid inputs.

A good property-based test also checks structural invariants: each transition has a valid next state; output symbols belong to the output alphabet; the simulator emits one symbol per input under standard Mealy semantics; a Moore run emits exactly one more including its initial value; and all generated conversion traces match under the declared alignment. Each property should fail with a short reproducible input word rather than a vague assertion message.

Executable Bounded Trace and Structure Tests

This example enumerates every word over the turnstile's two-symbol alphabet up to length five. It verifies the Mealy trace length and the consistency of a deliberately simple Moore conversion constructed from original state/output pairs. This is not an unbounded proof; it is an effective safety net for regression edits to the executable table or conversion function.

from itertools import product
from collections import deque

MEALY = {
    ("L", "coin"): ("U", "unlock"),
    ("L", "push"): ("L", "alarm"),
    ("U", "coin"): ("U", "refund"),
    ("U", "push"): ("L", "relock"),
}
ALPHABET = ("coin", "push")
INITIAL = ("START",)

next_moore = {}
moore_output = {INITIAL: "init"}
queue = deque([INITIAL])
while queue:
    state = queue.popleft()
    source = "L" if state == INITIAL else state[0]
    for a in ALPHABET:
        target, output = MEALY[source, a]
        destination = (target, output)
        next_moore[state, a] = destination
        if destination not in moore_output:
            moore_output[destination] = output
            queue.append(destination)

for n in range(6):
    for word in product(ALPHABET, repeat=n):
        q, mealy_trace = "L", []
        s, moore_trace = INITIAL, [moore_output[INITIAL]]
        for a in word:
            q, output = MEALY[q, a]
            mealy_trace.append(output)
            s = next_moore[s, a]
            moore_trace.append(moore_output[s])
        assert mealy_trace == moore_trace[1:], word
        assert len(mealy_trace) == n
        assert len(moore_trace) == n + 1
print("bounded conversion traces checked:", sum(2 ** n for n in range(6)))

All 63 words of length zero through five are included. The important point is methodological: a conversion is testable at the same logical response boundary used to define equivalence. Do not compare a Mealy response from the current event against a Moore state output from the preceding event, and do not ignore the reset output unless the contract explicitly does so.

Traceability and Requirements Review

Every output in the table should correspond to a documented requirement, and every requirement concerning a response should identify the event and state under which it applies. A practical requirements matrix can add columns for response value, response timing, error policy, security sensitivity, and verification evidence. It is then possible to trace an output such as refund from its requirement to a Mealy table row, implementation code, test, and monitoring event.

Requirements that specify only a diagram name can hide significant contradictions. “Show open” might mean that an operator has issued a command, that the controller is in an internal unlocked state, or that a sensor has confirmed the gate open. Those are distinct facts and should not share one ambiguous output symbol. Similarly, “retry” can mean re-issuing an idempotent command, generating a new transaction, or re-reading a persistent status; these operations have different side effects.

A formal specification is especially useful during maintenance. When a reviewer changes an output rule to meet a new business requirement, the transducer comparison can identify which previously specified input traces now differ. If the change is intended, update the contract and tests; if it is not, the counterexample reveals a regression.

Applied Scenario 1 — A Building-Access Turnstile

A building operator wants an access gate to respond to credentials, pushes, and denied entries. The Mealy view records event-specific decisions such as unlock, refund, or alarm using the current control state and presented input. This is convenient because two inputs in the same locked state can produce different responses without requiring separate persistent states for every short-lived action. The Moore view is useful for the persistent status displayed to attendants, such as LOCKED, UNLOCKED, or FAULT.

The design must not treat an emitted unlock command as proof that a physical latch opened. A sensor acknowledgment is a separate event, and emergency egress or fire-alarm handling may require independent safety mechanisms. A realistic model might distinguish LOCKED, UNLOCK_PENDING, UNLOCKED, and FAULT, with an output contract for each event and a state-derived status display. The two notations are complementary: Mealy for transition responses; Moore for persistent states visible to staff.

Acceptance criterion: replaying the same event sequence must reproduce both the command trace and the status trace, including repeat-credential and invalid-passage behavior. The test should prove the controller never emits an authorization command on a denied event under the modeled conditions, while separately recognizing that deployment safety depends on physical safeguards beyond the finite model.

Applied Scenario 2 — A Serial Pattern Detector

A digital design team needs to recognize 101 in a serial bitstream, including overlapping matches. A Mealy machine can emit a detection bit on the transition that consumes the final 1. A Moore machine can represent detection in a state entered after reading the completing bit. Both can express the same aligned sequence of detection values, but a circuit designer must decide whether the detector's consumer samples outputs before or after the active clock edge and whether the output is registered.

The requirement should state whether 10101 produces two detections, whether a match output is a pulse or a level, and what happens during reset. These questions are not solved by declaring the machine Mealy or Moore. They are part of the observable trace and clocking contract. An explicit transition/output table allows designers to test overlapping prefixes and to prevent accidental one-cycle shifts in simulation.

Acceptance criterion: for input 10101, the aligned output vector is 0,0,1,0,1. A hardware implementation should additionally meet electrical timing constraints and reset-to-output requirements, which are checked separately from the abstract transducer sequence.

Applied Scenario 3 — A Request-Acknowledgment Protocol

A device receives open and close requests and must answer ack, already_open, or already_closed depending on its current state. The Mealy formulation makes this contract concise: each incoming request induces one response and potentially a state transition. Repeated commands often leave the state unchanged while still requiring a distinct reply. A state-only output map would need additional states or a separate event-response channel to retain those distinctions.

A real protocol introduces complications absent from the toy model. Requests may be duplicated, acknowledgments may be lost, and clients may retry after a timeout. A production design may require bounded retry state or request identifiers; if identifiers are unbounded, the plain finite machine becomes an abstraction rather than a complete data model. The architecture should not declare a request delivered just because the local Mealy output selected an acknowledgment.

Acceptance criterion: each valid request has a defined response from every modeled state, including repeated requests. The protocol's transport and idempotency policies are documented outside the elementary output table, then tested end to end.

Applied Scenario 4 — A Vending-Machine Controller

A vending controller maintains a bounded credit state and processes insert and select events. A Mealy representation emits accepted, ready, insufficient, return_coin, or dispense, while a Moore projection can continuously display the credit level or readiness state. Two different transitions may end in credit 0 while requiring entirely different responses, showing why a final-state-only test is inadequate.

The physical dispenser is not the same as the command to dispense. If a product jam occurs, the controller may need an acknowledgment from a dispensing mechanism, a fault state, and an explicit refund or remediation policy. The simple finite model is therefore a useful starting point for control logic but not a complete financial or safety specification. In a real implementation, monetary values, auditability, and reliable recovery would require additional design.

Acceptance criterion: a paid select emits exactly one dispense intent; an unpaid select never emits that intent. The number of physical deliveries and payment reconciliations must be verified through independent mechanisms.

Applied Scenario 5 — An Asynchronous User Interface

A software team implements a login workflow with persistent states SIGNED_OUT, AUTHENTICATING, and SIGNED_IN. A Moore-style view function derives which screen or status is displayed from the current state. A Mealy-style reducer emits effects such as submit_request, show_error, and record_audit_event in response to user inputs or network replies. The design prevents reading a status from inadvertently repeating a side effect.

The challenge is not just output placement; it is asynchronous ordering. A delayed authentication response may arrive after cancellation, and a second login attempt may supersede the first. The system must define which response is still relevant, possibly using request tokens or additional abstract states. A transition table should include valid cancellation and late-response cases and should reject any result whose correlation context is invalid.

Acceptance criterion: the displayed status, error messages, and external effects remain consistent under repeated clicks, cancellation, and delayed results. Reducer tests can check the pure model, while integration tests verify that external effects run only according to the selected delivery policy.

Applied Scenario 6 — A Safety-Oriented Equipment Monitor

A plant monitor exposes persistent statuses NORMAL, WARNING, and FAULT and produces event-driven notifications as new sensor observations arrive. A Moore machine describes the persistent status output naturally; Mealy responses can report warning_entered, warning_repeated, or fault_detected. If operators need to be notified on each occurrence rather than just each state change, the event channel cannot be reconstructed by watching the current status value alone.

Raw sensor values, sampling uncertainty, time delays, and device failures complicate the design. A finite classifier may turn readings into low, normal, and high symbols, while hysteresis or debounce logic reduces chatter. Safety interlocks should not depend only on notification software, and an externally verified protection mechanism must remain independent where required by the hazard analysis.

Acceptance criterion: tests distinguish threshold crossings from sustained abnormal status, verify safe behavior on invalid sensor data under declared assumptions, and include reset and alarm-acknowledgment requirements. This case highlights how the right design may expose both an edge-oriented event stream and a state-oriented status interface.

Ten-Gate Selection and Verification Framework

The practical choice between Mealy and Moore should be made from a documented output contract rather than from a rule that one notation is always faster, smaller, or easier. The following ten gates form a repeatable review procedure for design, conversion, and implementation.

Gate Decision question Evidence expected
1. Output purpose Is each output an event response, a persistent status, or both? Explicit consumer semantics
2. Input alphabet Are input symbols complete, deterministic, and unambiguous? Enumerated events and classification policy
3. Timing contract Which event owns each output, and when can it be observed? Input/output trace with sampling boundaries
4. Initialization What is visible before the first input and after reset? Reset-state and initial-output requirements
5. Table completeness Is every state/input combination defined? Exhaustive transition/output table
6. State economy Are state splits necessary to preserve incoming outputs? Conversion map and reachable-state analysis
7. Correctness Do implementations preserve all specified output words? Invariants, counterexamples, equivalence checks
8. Hardware/software risks Can glitches, races, retries, or duplicate effects arise? Timing analysis and atomicity/delivery design
9. Error and fault policy How are unknown events, failures, and stale replies handled? Explicit error transitions and recovery rules
10. Lifecycle control How will changes be tested and documented? Regression traces, monitoring, and versioned requirements

A design can pass the formal conversion check yet fail a deployment requirement if the initial output, clock boundary, or side-effect semantics changed. Conversely, two machines with different numbers of states may implement the same output contract perfectly. The gates are intended to expose such distinctions before an implementation is called equivalent or production-ready.

Common Misconceptions and Corrections

“Mealy outputs depend only on the input.” Incorrect: they depend on the current state and input. Different states can emit different outputs for the same input. “Moore outputs occur only when a state changes.” Incorrect under the classical model: a Moore output is associated with every current state, including across self-loops and before the first input. It may be sampled or displayed repeatedly without any state transition.

“Both models always produce the same number of output symbols.” Not under the full-trace conventions used here: a Mealy machine emits n output symbols for n inputs, while a Moore machine exposes n+1 including initialization. A common equivalence convention ignores that initial Moore symbol. “Every Mealy machine is exactly the same hardware as an equivalent Moore machine.” False: functional output alignment does not guarantee equal clock latency, glitch sensitivity, state encoding, power, or resource cost.

“A Mealy machine always has fewer states.” False as a universal claim. A Mealy-to-Moore conversion often introduces states, but a particular application can favor either representation, and minimization results depend on the actual output language. “If the final states match, the implementations are equivalent.” False for transducers: output sequences matter. “Emitting unlock proves the door opened.” False: an output command is not proof of successful external actuation.
