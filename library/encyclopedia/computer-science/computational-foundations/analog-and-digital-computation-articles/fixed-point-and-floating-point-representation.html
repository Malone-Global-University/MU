Finite-Word Computation Is Not Real-Number Arithmetic

A physical computer stores a finite string of bits. The mathematical number intended by that string depends on an encoding rule, a scale, an exponent convention, and the operation being performed. The same sixteen bits can be interpreted as an unsigned count, a signed integer, a Q-format fractional value, or part of a floating-point word. None of those interpretations changes the storage cells themselves; it changes what operations and numerical claims are valid.

Fixed-point representation maps an integer code to a value using a declared scale, producing uniformly spaced representable values within a bounded interval. Floating-point representation stores an exponent and a significand, concentrating representable values near zero and spacing them farther apart at larger magnitudes. Signed integers are a third important baseline. This article compares their range, granularity, overflow, rounding, arithmetic and error behavior rather than treating one type as inherently accurate or universally faster.

Readers should distinguish three levels: a real-world physical quantity, the mathematical or statistical model chosen for it, and the stored numerical approximation. Selecting binary64 rather than binary32 can reduce one source of arithmetic error, but it cannot repair a biased sensor, a missing calibration constant, or an incorrect mathematical model.

The Representation Contract

Before selecting a number format, specify the quantity's unit, minimum and maximum allowed values, smallest meaningful change, mathematical operations, error tolerance, overflow policy, and transfer or storage ABI. Without these properties, a statement such as “use a 16-bit value” is incomplete: sixteen bits might store the integer range −32,768 through 32,767, the Q1.15 fractional interval −1 through almost +1, or a binary16 floating-point word with very different spacing.

For a telemetry counter, exact integer increment and wrap policy may dominate. For audio samples, fractional fixed-point codes may match the converter and DSP datapath. For a scientific solver whose state spans orders of magnitude, floating-point dynamic range may dominate. A rigorous design review documents both representation invariants (the mapping from bits to value) and operational invariants (how arithmetic handles an out-of-range or nonexact result).

A Finite Set Cannot Store Every Real Number

A w-bit word has at most 2w distinct bit patterns. An unbounded continuum of real values therefore cannot be represented one-to-one by any finite word. The representation designer allocates those patterns to a finite set of values and sometimes to special states such as not-a-number. A numerical calculation whose exact result is between representable values must choose an approximation by a specified rounding rule or retain a wider intermediate.

Two distinct issues follow. Quantization error is introduced when a value is mapped into a finite grid. Arithmetic rounding error occurs when an operation's exact mathematical result cannot be stored in the destination format. These errors can interact with conditioning, feedback and repeated steps. A format with finer spacing does not automatically guarantee the accuracy of a whole algorithm; the arrangement of operations also matters.

Unsigned and Two’s-Complement Integers

A w-bit unsigned integer represents 0 through 2w−1. A conventional w-bit two’s-complement signed integer represents −2w−1 through 2w−1−1. The leading bit participates in the weighted two’s-complement encoding and is not a detached sign bit in the sign-magnitude sense. The bit string 11111111 represents 255 as unsigned 8-bit or −1 as signed 8-bit.

A signed word still contains only integers. It can encode fractional measurements if their units are scaled, such as storing cents rather than dollars or microseconds rather than seconds. Once a scale is adopted, the interpretation becomes fixed-point. The integer arithmetic hardware often remains the same, but multiplication and division must account for scale, and two’s-complement wrap is not always the correct application-level overflow policy.

def signed_twos_complement(raw, width):
    raw &= (1 << width) - 1
    return raw - (1 << width) if raw & (1 << (width-1)) else raw
assert signed_twos_complement(0b11111111, 8) == -1
assert signed_twos_complement(0b01111111, 8) == 127
assert signed_twos_complement(0b10000000, 8) == -128

Integer Overflow Policies Are Language and Machine Contracts

If an exact addition falls outside the destination integer range, an implementation must specify what happens. Hardware may retain only low bits, producing modular wraparound. A saturating arithmetic instruction instead clamps to the range limit. Checked arithmetic returns an error or traps. A widening operation may produce a correct result in a larger representation. These are semantically different policies, not interchangeable implementations of the same mathematical addition.

For an 8-bit signed word, 127+1 wraps to −128 under two’s-complement modular interpretation, saturates to +127 under signed saturation, and is rejected by a checked operation. Languages also differ: Python integers grow as needed, while C signed overflow has undefined behavior. Never import an overflow rule from a demonstration language into a hardware interface or control-system safety case without checking the target specification.

def wrap_signed(x, width):
    mask = (1 << width) - 1
    raw = x & mask
    return raw - (1 << width) if raw >= (1 << (width-1)) else raw
def saturate_signed(x, width):
    lo, hi = -(1 << (width-1)), (1 << (width-1))-1
    return min(hi, max(lo, x))
assert wrap_signed(128, 8) == -128
assert saturate_signed(128, 8) == 127

Fixed-Point Numbers: Stored Codes and Scale

Let q be a signed or unsigned integer code and let Δ be a positive scale. The decoded value is x = q × Δ. For a binary fractional format with f fractional bits, Δ = 2−f. For a decimal fixed-point representation of cents, Δ = 0.01 dollar. A binary point is generally implied by a contract; it does not occupy a storage bit. The same stored code decoded with another Δ means another physical or mathematical value.

A fixed point stores a uniform value grid in its declared interval. If a signed sixteen-bit code is scaled by 1/256, the spacing is exactly 1/256 and the representable range is −128 through 127+255/256. If that same code were decoded with scale 1/32768, the interval would instead be −1 through 1−1/32768. This tradeoff is deliberate: each fractional bit doubles fractional resolution but halves the magnitude range for fixed word width.

def decode_fixed(q, fractional_bits):
    return q / (1 << fractional_bits)
assert decode_fixed(384,8) == 1.5
assert decode_fixed(-128,8) == -0.5
assert decode_fixed(384,15) != 1.5

Q-Format Conventions Must Be Declared

The notation Qm.n is common in digital signal processing but not entirely uniform. Under one convention, m counts all integer-side bits including the sign bit, and n counts fractional bits; then a signed Q1.15 word has sixteen bits total. Other references exclude the sign bit from m. Unqualified phrases such as “Q15” can refer to a particular 16-bit fractional storage convention. Thus, always document total width, signedness, fractional bits, scale and endpoints, even when a familiar Q label is used.

In the signed 16-bit, 15-fractional-bit convention, value = signed_code/32768. The minimum code −32768 encodes exactly −1 and the maximum +32767 encodes 0.999969482421875. There is no positive +1 value in that format. Forgetting this asymmetry can cause saturation or sign errors in mixers, controllers and coefficient normalization.

q15_min, q15_max = -(1<<15), (1<<15)-1
assert q15_min/(1<<15) == -1
assert q15_max/(1<<15) == 1 - 2**-15
assert 16384/(1<<15) == 0.5

A Complete Q1.15 Bit-Level Example

Consider the real value 0.75. Multiplying by 215 gives integer code 24,576, or hexadecimal 0x6000. The 16-bit binary pattern 0110 0000 0000 0000 thus decodes exactly to 24,576/32,768=0.75. The negative value −0.5 corresponds to signed code −16,384 and the 16-bit two’s-complement pattern 1100 0000 0000 0000, hexadecimal 0xC000.

These examples show why a bit dump without a type contract is insufficient: the bit pattern 0xC000 means 49,152 as unsigned, −16,384 as two’s-complement signed, or −0.5 when additionally scaled by 2−15. For data exchange, publish byte order and field width separately from the numerical scale. An endian conversion changes byte arrangement, not the underlying mathematical encoding.

q_pos = round(0.75 * (1<<15))
q_neg = round(-0.5 * (1<<15))
assert (q_pos, hex(q_pos)) == (24576, '0x6000')
assert (q_neg, hex(q_neg & 0xFFFF)) == (-16384, '0xc000')

Encoding Fixed-Point Values and Rounding

To encode a real x using quantum Δ, compute the ideal integer code x/Δ and choose a neighboring integer using the rounding rule. Under round-to-nearest, ties-to-even, the selected integer is the nearer code, with exact halfway cases selecting an even code. The signed word must then be checked against its representable endpoints. Simply calling a cast to integer is not necessarily correct: integer conversion commonly truncates toward zero, which introduces a different signed error pattern.

For values within range and away from other exceptional conditions, nearest rounding yields an absolute representation error no larger than Δ/2. This bound applies to a single conversion, not automatically to a long signal-processing chain. Clipping and saturation can produce errors much larger than Δ/2, and repeated biased truncation can accumulate a systematic shift. Ties-to-even minimizes one common tie bias but does not guarantee every data distribution has zero mean error.

def encode_fixed_nearest(x, f, width=16):
    code = round(x * (1<<f))
    lower, upper = -(1<<(width-1)), (1<<(width-1))-1
    if code < lower or code > upper:
        raise OverflowError('fixed-point value out of range')
    return code
assert encode_fixed_nearest(0.75,15)==24576
assert encode_fixed_nearest(-0.5,15)==-16384
assert abs(encode_fixed_nearest(.3,15)/(1<<15)-.3)<=2**-16

Uniform Spacing, Resolution, and Relative Error

For a fixed scale Δ, every pair of adjacent codes is separated by Δ throughout the nominal range. Consequently, fixed-point representation offers a uniform absolute resolution. Its relative error can nevertheless grow when the true value is small: an error of one-half a quantum is a tiny percentage of a large input but potentially a large percentage of a value near zero. At exactly zero, relative error based on division by the true value is not defined.

This property may be desirable when the engineering contract states an absolute accuracy tolerance, such as a specified distance increment or currency subunit. It may be a poor match when the task must preserve an approximately constant number of meaningful digits over an enormous magnitude range. The design question is not whether fixed-point is precise; it is whether its chosen Δ is fine enough at the smallest important signal while its range remains large enough for peak values and transients.

step=2**-8
assert step==1/256
for raw in (-100,0,100):
    assert (raw+1)*step - raw*step == step

Fixed-Point Addition and Subtraction

When two operands use the same scale Δ, adding their stored integer codes and decoding preserves the same scale: (qa+qb)Δ = a+b. No rescaling is needed, although an extra carry bit may be necessary. When scales differ, convert one operand into the other's scale or promote both to a common wider format. Combining 16-bit raw codes from different Q formats as if they represented the same unit can silently corrupt a result without any arithmetic exception.

For 16-bit signed Q1.15, the sum of 0.75 and 0.5 is 1.25, which cannot be stored even though the mathematical addition is uncomplicated. A saturation policy produces 0.999969…; modular wrap instead produces −0.75. Widening to a 17-bit or otherwise larger accumulator can retain the exact combined raw code. The correct policy depends on downstream numerical guarantees and whether clipping is semantically acceptable.

a,b = 24576,16384  # Q1.15 -> .75 and .5
wide_sum = a+b
assert wide_sum==40960 and wide_sum/(1<<15)==1.25
assert wrap_signed(wide_sum,16)/(1<<15)==-0.75
assert saturate_signed(wide_sum,16)==32767

Fixed-Point Multiplication and Scale Restoration

If a=qa2−f and b=qb2−f, then ab=(qaqb)2−2f. The raw integer product therefore has twice the fractional-bit count before rescaling. To return to the original format, round or shift the double-width product by f bits and then check the output range. Throwing away the lower bits without a stated rule is equivalent to committing to a particular rounding bias.

For instance, 0.5 in Q1.15 has code 16,384 and −0.25 has code −8,192. Their raw product is −134,217,728; division by 32,768 yields the destination code −4,096, decoding to −0.125. Signed multiplication must use a wide enough intermediate to hold the full product. Optimized DSP multiply-accumulate instructions may offer special rounding or saturation; consult the actual ISA rather than treating all variants as equivalent.

qa,qb = 16384,-8192
product_wide = qa*qb
result = product_wide//(1<<15)  # exact shift in this example
assert (product_wide, result) == (-134217728,-4096)
assert result/(1<<15)==-0.125

Fixed-Point Division and Rescaling

Fixed-point division requires both overflow and precision planning. With operands in the same scale and desired result in that scale, a typical integer construction computes the numerator qa×2f, divides by qb, then rounds to the chosen destination code. The numerator must be wide enough to prevent overflow before the division. The implementation also needs a policy for a zero denominator, signed minimum divided by −1, and a quotient that exceeds the result range.

A division routine based on truncation toward zero will differ from a mathematically nearest-rounding implementation for non-integral quotients. Signed integer division in Python uses // for floor, not truncation toward zero, and an arithmetic right shift on negative values has similar directional implications. Specify rounding in mathematical terms before choosing an instruction sequence. Tests should include positive and negative half cases, near-zero denominators and the representable endpoints.

from fractions import Fraction
a,b=8192,16384   # 0.25 and 0.5 as Q1.15
quotient_code=round(Fraction(a*(1<<15),b))
assert quotient_code==16384
assert quotient_code/(1<<15)==0.5

Guard Bits and Wide Accumulators

Multiply-accumulate filters often require much more headroom than any single input. A sequence of N same-sign Q1.15 products can sum to a magnitude roughly N times one product, depending on coefficients and signals. Accumulating in the destination word and clipping after every addition discards information and can cause strong nonlinear distortion. A common design instead uses a wide accumulator, delays rounding and applies one final, documented conversion at the output boundary.

For signed integers, a sum of N bounded positive terms may require approximately ⌈log2N⌉ additional magnitude bits beyond the per-term bound, plus attention to signs and intermediate products. That bit-count is only a coarse design starting point: coefficient gains, input correlation, transient conditions and feedback stability determine the real peak. A safe fixed-point signal path establishes worst-case or defensible probabilistic bounds for every intermediate, not only for the final result.

# Four products can exceed signed 16-bit code range, but wide accumulation preserves them.
partials=[20000,20000,20000,20000]
wide=sum(partials)
assert wide==80000 and wide>32767
assert saturate_signed(wide,16)==32767

Saturation, Wraparound, and Clipping Detection

For control and signal chains, saturation can be safer and more intuitive than modular wrap, because a positive physical quantity does not suddenly become negative after reaching the maximum code. Yet saturation is nonlinear: it introduces distortion, can invalidate conservation relationships, and may drive feedback loops into prolonged limit behavior. Wrap can be appropriate for modular counters or cryptographic primitives but often unacceptable for audio amplitude, motor torque or an actuator command.

A design should record whether overflow is prevented, detected, saturated, or wrapped, and identify the point in the pipeline at which the policy applies. A status flag or counter for saturation events can be operationally useful because output clipping may otherwise masquerade as a valid but flattened signal. If a safety-critical output is bounded, the bound needs a physical-units interpretation rather than an unexplained raw integer threshold.

Rounding Modes and Negative Numbers

Arithmetic implementations commonly distinguish nearest-even, nearest-away, toward zero, toward positive infinity and toward negative infinity. For a fixed quantum, these determine which code is selected from adjacent candidates. Negative values are especially revealing: floor(−1.2)=−2, truncation toward zero gives −1, and round-to-nearest gives −1 for this value. Exact ties such as −1.5 require a tie rule; nearest-even gives −2 while ties-away-from-zero also gives −2 here, but the rules differ at −2.5.

Never assume an arithmetic shift or signed division automatically implements nearest rounding. In many two’s-complement machines a right shift replicates the sign bit and acts like floor division by a power of two. A conversion chosen merely for speed may produce a measurable systematic error in repeated calculations. Tests of a rounding routine should include zero, positive and negative values, both sides of half-integers, and extreme codes.

import math
assert math.floor(-1.2)==-2
assert math.trunc(-1.2)==-1
assert round(-2.5)==-2
assert round(-1.5)==-2
assert -3//2 == -2  # floor, not truncate toward zero

Quantization Bias in Repeated Fixed-Point Operations

Suppose a control increment is 0.003 in physical units and a fixed-point accumulator uses Δ=1/256≈0.00390625. Rounding the increment once to one quantum gives 0.00390625; after a thousand repetitions, the stored trajectory advances about 3.90625 instead of the ideal 3.00000 if the same rounded increment is added each time. The discrepancy is not the same as independently rounding a final sum only once. This illustrates systematic per-step bias, not an inevitable property of all fixed-point implementations.

Mitigations include using finer internal scale, retaining fractional residue, deriving the accumulated state from a higher-precision reference, or choosing a numerically stable discretization. Stochastic rounding is another technique in selected low-precision settings, but changes reproducibility and error statistics. A designer should inspect the entire recurrence and its stability, not rely on the fact that each individual conversion had less than half a quantum of error.

step=1/256
per_step=round(.003/step)*step
approx_total=1000*per_step
ideal_total=1000*.003
assert abs(approx_total-ideal_total-0.90625)<1e-12

Range–Resolution Allocation for a Fixed Word

For signed w-bit two’s-complement storage with f fractional bits, the minimum is −2w−1−f, the maximum is 2w−1−f−2−f, and the grid spacing is 2−f. Choosing more fractional bits improves the absolute quantum while reducing the unscaled magnitude range. For example, 16-bit signed Q8.8 has scale 1/256 and range [−128, 127.99609375], whereas Q1.15 has much finer scale 1/32768 but only the [−1, nearly +1] interval.

When selecting f, first bound peak and transient magnitudes, then reserve an explicit margin rather than choosing the narrowest range that holds nominal data. Next check whether the resulting step is small enough at the low end of the meaningful signal. If both requirements cannot be satisfied in the word width, a wider format, block scaling, floating-point format, or algorithmic reformulation is required. Scaling cannot conjure more distinct representations from the same number of codes.

Fixed-Point Format Selection Procedure

A repeatable selection procedure begins with units and required physical range, including fault transients and start-up states. Determine the maximum tolerable absolute quantization error, not merely a vague number of decimal digits. Under nearest rounding, Δ/2 is a useful conversion bound when there is no clipping. Then calculate the word width needed to satisfy both range and resolution with margin; a wider intermediate may still be needed for multiplications, sums or state updates.

Finally specify rounding, saturation, ABI, test vectors and how conversion error enters the application error budget. Evaluate the worst-case signal path and the typical workload separately. If precision requirements vary dramatically with magnitude, floating-point may reduce engineering complexity. If the desired unit quantum is decimal, a decimal fixed-point integer in cents or thousandths can be clearer than a binary fractional Q-format, provided it has sufficient range and reliable decimal conversion.

Why Floating-Point Uses a Movable Exponent

A floating-point number uses a sign, a significand and a scale determined by an exponent. In a conceptual binary format, a nonzero normal value has the form (−1)s × (1.fraction)2 × 2e. The significand contributes a fixed number of precision bits, while the exponent shifts the effective binary point. Nearby values have spacing determined by their exponent range rather than one global quantum.

This is why a floating format can represent tiny and enormous values with the same word width, yet cannot necessarily distinguish small increments added to very large values. Floating point typically maintains a roughly fixed relative precision for normal values but not a fixed absolute precision. It also reserves bit patterns for zero, subnormal values, infinities and NaNs. Engineering reasoning must account for all these categories rather than assuming every bit pattern denotes an ordinary finite real number.

The IEEE 754 Binary Interchange Formats

IEEE 754 defines widely used binary interchange formats. binary32 contains 1 sign bit, 8 exponent bits and 23 stored trailing significand bits. Its normal significand has 24 bits of precision because the leading 1 is implicit. binary64 contains 1 sign bit, 11 exponent bits and 52 stored trailing significand bits, providing 53 bits of normal precision. These are the standard binary32 and binary64 storage encodings; other formats and extended computational environments exist.

The term “single precision” ordinarily refers to binary32 and “double precision” to binary64 in modern programming discussions, but a language's type semantics can have platform-specific details. In particular, Python's built-in float maps to an IEEE binary64 value on most mainstream platforms. A C float typically uses binary32 and C double typically binary64, but a specification or ABI should be consulted. Python code below uses struct.pack to construct binary32 encodings explicitly instead of pretending native Python float operations round to binary32 after every operation.

Exponent Bias and Normal-Number Decoding

Let E be the integer interpreted from the exponent field and F the integer from the stored fraction field. For binary32, normal exponents have 1 ≤ E ≤ 254. Their unbiased exponent is e=E−127, and the decoded value is (−1)s × (1+F/223) × 2E−127. For binary64, normal E ranges from 1 to 2046, its bias is 1023, and the fraction denominator is 252.

A stored fraction field of all zeros represents an exact power of two for a normal number; the implicit leading 1 is what makes that interpretation possible. The exponent field at all zeros and all ones is reserved for special decoding cases. A raw bit-mask decoder must test these fields before applying the normal formula. Using the biased exponent unadjusted in a scaling formula produces errors of many orders of magnitude.

def decode_normal_binary32_bits(bits):
    sign, exponent = bits>>31, (bits>>23)&255
    fraction = bits&((1<<23)-1)
    if not 1<=exponent<=254:
        raise ValueError('not a normal binary32 encoding')
    return (-1)**sign * (1+fraction/(1<<23))*2**(exponent-127)
assert decode_normal_binary32_bits(0x3f800000)==1.0
assert decode_normal_binary32_bits(0x40000000)==2.0
assert decode_normal_binary32_bits(0xbf400000)==-0.75

An Explicit Binary32 Encoding Walkthrough

The number +1.5 is binary 1.1₂×2⁰. It has sign bit 0, biased exponent 127 (the eight-bit pattern 01111111), and fractional field beginning with 1 followed by zeros. The combined bit sequence is 0 01111111 10000000000000000000000, or hexadecimal 0x3FC00000. The implicit leading 1 is not stored; the first stored fractional 1 accounts for the +0.5.

For −0.75, write −1.1₂×2−1. The sign bit becomes 1, the exponent field is 126 and the fraction field again represents +0.5. That encoding is 0xBF400000. These are exact binary fractions. By contrast, the decimal number one tenth repeats forever in base two and cannot be represented exactly with finitely many binary significand bits.

def binary32_hex(value):
    return hex(struct.unpack('>I',struct.pack('>f',value))[0])
assert binary32_hex(1.5)=='0x3fc00000'
assert binary32_hex(-0.75)=='0xbf400000'
assert binary32_hex(0.1)=='0x3dcccccd'

Binary64 Precision and Large Integers

The 53-bit significand of binary64 can represent every integer exactly in the interval [−253, 253]. Beyond that point, adjacent integers may map to the same floating-point value because the gap between representable values grows. For instance, 253+1 is not exactly representable as binary64, and converting that integer to float can round it to 253. This matters for identifiers, sequence counters, timestamps and monetary totals.

A floating-point format should not be used as an exact identifier merely because its maximum finite magnitude is large. “Range” and “integer exactness” are different. A 64-bit unsigned identifier may require 64 significant bits; storing it in binary64 can lose low bits even though no overflow or infinity occurs. Use a suitable integer or textual representation for exact codes, and do not use an approximate floating value as a database primary key.

n=2**53
assert float(n)==float(n+1)
assert float(n+2)!=float(n)
assert int(float(n+1))!=n+1

Subnormal Numbers and Gradual Underflow

When E=0 and F≠0, the binary format uses a subnormal value with no implicit leading 1. In binary32, its value is (−1)s × (F/223) × 2−126. The smallest positive subnormal is 2−149. Binary64 similarly uses exponent −1022 with a 52-bit fraction, giving smallest positive subnormal 2−1074. These values fill the gap between the smallest normal magnitude and zero at reduced significant precision.

Gradual underflow makes many small results behave more smoothly than an abrupt jump to zero. Yet relative error can become very large in the subnormal region because the quantum remains fixed while the value approaches zero. Some processors or performance modes treat subnormals specially or may flush them to zero; those behaviors must be documented when they affect the numeric contract. A software test for tiny numbers should not assume every execution mode preserves every subnormal without verification.

min_subnormal=math.ldexp(1.0,-1074)
min_normal=math.ldexp(1.0,-1022)
assert min_subnormal>0 and min_subnormal<min_normal
assert min_subnormal/2==0.0  # rounding underflows to zero

Signed Zero, Infinities, and NaNs

IEEE binary floating-point formats encode positive zero and negative zero separately. They compare equal numerically, but the sign can affect functions such as reciprocal and certain directional limits in a fully IEEE-compliant arithmetic environment. Positive and negative infinity encode results or inputs outside the finite range under appropriate operations and modes. NaN, or not-a-number, encodes an invalid or unavailable numerical result; ordinary comparisons involving a quiet NaN, including equality to itself, are false.

These special values are not interchangeable with application missing-data semantics. A NaN used as an optional-field marker can propagate through arithmetic and complicate comparison, hashing or ordering. Language handling also differs: Python's 1.0/0.0 raises ZeroDivisionError rather than silently returning an IEEE infinity, while a sufficiently large finite float multiplication can produce infinity. Avoid assuming that an IEEE storage encoding alone dictates a language's exception API or an entire runtime's behavior.

negzero=-0.0
assert negzero==0.0
assert math.copysign(1.0,negzero)==-1.0
nan=float('nan')
assert nan!=nan
assert math.isinf(1e308*1e308)

A Decimal One-Tenth in Binary32 and Binary64

Decimal 0.1 equals 1/10, whose binary expansion is recurring, so neither binary32 nor binary64 can encode it exactly. In binary32 the nearest representable value has bits 0x3DCCCCCD and is approximately 0.10000000149011612. In binary64 the corresponding encoding is 0x3FB999999999999A and is approximately 0.10000000000000000555. The familiar Python display 0.1 is the shortest decimal text that rounds back to that stored binary64 value, not proof of exact decimal storage.

As a result, 0.1 + 0.2 == 0.3 is normally false with Python binary floats. This is not a Python defect: it follows from finite binary representation combined with rounded arithmetic. It also does not mean every decimal fraction is inexact—0.5, 0.25 and 0.125 are exact powers-of-two fractions. Decimal exactness, binary exactness and human-readable decimal formatting are distinct properties.

bits64=struct.unpack('>Q',struct.pack('>d',0.1))[0]
assert bits64==0x3fb999999999999a
assert struct.unpack('>I',struct.pack('>f',0.1))[0]==0x3dcccccd
assert 0.1+0.2!=0.3
assert 0.125+0.25==0.375

ULPs, Spacing, and Units of Error

An ulp, or unit in the last place, is used to describe the local spacing of floating-point values, although careful definitions differ at exponent-bin boundaries and under some mathematical conventions. For normal binary64 numbers in [1,2), the upward spacing is 2−52; for numbers in [2,4), the spacing is 2−51. In binary32, the corresponding gaps are 2−23 and 2−22. Spacing doubles when the exponent increases by one.

For normal, correctly rounded operations with round-to-nearest, the rounding error is at most half the neighboring gap in an ordinary local ulp interpretation. This absolute statement is not a blanket relative-error guarantee near underflow, at infinities or after overflow. APIs such as Python math.ulp() and math.nextafter() are useful for inspecting representability, while error bounds for whole algorithms must still consider their mathematical condition and sequence of operations.

assert math.ulp(1.0)==2**-52
assert math.ulp(2.0)==2**-51
assert math.nextafter(1.0,math.inf)-1.0==2**-52
assert 1.0-math.nextafter(1.0,-math.inf)==2**-53

Machine Epsilon Versus Unit Roundoff

In the common C/Python numerical convention, machine epsilon is the difference between 1 and the next larger representable number. For binary64, ε=2−52; for binary32, ε=2−23. Numerical-error analysis often uses the unit roundoff u=ε/2 for round-to-nearest, so u=2−53 and 2−24 respectively. Some texts use the word epsilon for u instead; quote the definition, not just the symbol.

The frequently used relative model fl(a ⊙ b)=(a ⊙ b)(1+δ), with |δ|≤u, needs assumptions: the result must be in a suitable normal range and the operation must be correctly rounded, among other conditions. It fails as a universal statement when the exact result is zero, subnormal, infinite or subject to other special handling. An analysis that overlooks those conditions can claim a relative bound exactly where the computation is least reliable.

eps=sys.float_info.epsilon
assert eps==2**-52
unit_roundoff=eps/2
assert unit_roundoff==2**-53

Rounding-to-Nearest, Ties-to-Even in Binary Floating Point

The usual IEEE default rounding direction is round-to-nearest, ties-to-even. Of two neighboring representable values, choose the closer; if the exact result lies halfway between them, choose the value whose retained least-significant significand bit is even. Alternative directed modes include toward zero, positive infinity and negative infinity; IEEE 754-2019 also specifies ties-away as a rounding-direction attribute in applicable contexts. Availability of each mode to a particular language may vary.

For example, the numbers immediately above 1.0 in binary64 are separated by 2−52. The exact mathematical midpoint 1+2−53 rounds to 1.0 under ties-to-even because the least-significant retained bit for 1.0 is even. Constructing that midpoint in an already rounded binary64 expression is dangerous: the expression may round before a test inspects it. Exact fractions or integer arithmetic make the proof transparent.

from fractions import Fraction
one=Fraction(1,1)
mid=one+Fraction(1,2**53)
assert mid > one and mid < one+Fraction(1,2**52)
assert float(mid)==1.0  # correctly rounded halfway tie to even

Floating-Point Overflow and Directed Rounding

A floating-point exponent allows a large dynamic range, but a finite upper magnitude remains. The largest finite binary32 value is (2−2−23)×2127; the largest binary64 value is (2−2−52)×21023. Under round-to-nearest, an overflowing positive result generally becomes +infinity, while directed rounding can instead select the largest finite representable value in the appropriate direction. A returned infinity is not the same as a physically justified unbounded measurement.

Overflow can be caused by an unstable algorithm even when the mathematical final answer would fit. For example, an expression that multiplies two huge values before dividing may overflow in the intermediate product, whereas algebraically rearranging the expression can keep all intermediates in range. Such rewrites must still be checked for changes in rounding and cancellation. For high-consequence systems, monitor finiteness and input range explicitly rather than allowing an infinity to silently contaminate later computations.

large=1e308
assert math.isinf(large*large)
assert math.isfinite((large/large)*large)
assert (large/large)*large==large

Five IEEE Exception Categories

The IEEE floating-point model recognizes five major exception conditions: invalid operation, division by zero, overflow, underflow and inexact. These are distinct from a programming language raising an exception object. For instance, an inexact result is exceedingly common and need not halt execution; a library may expose status flags, traps, or neither directly. Underflow signaling has subtleties involving tininess and inexactness; not every subnormal value by itself constitutes a reported underflow exception.

Numerical applications should decide which conditions indicate an error in the physical domain, an expected boundary, or a reason to change strategy. A NaN may signal a failed root or undefined branch; infinity may indicate divergence or unintended division; underflow may erase a necessary small probability. Monitoring should log relevant inputs, rounding modes and computation context. Simply replacing every NaN with zero can conceal a serious failure and violate an algorithm's invariants.

Floating-Point Addition, Alignment, and Absorption

To add floating-point numbers, the hardware conceptually aligns their exponents, combines significands, normalizes and rounds the result. If one operand is much smaller than the other, its low bits can be shifted beyond the available significand precision. Then large + tiny may equal large exactly in the destination format despite the tiny operand being nonzero. The mathematical sum exists; the stored result cannot resolve the difference at that magnitude.

For binary64, adding 1 to 1016 does not change the stored number because the local spacing around 1016 is 2. This matters for high-base timestamps plus tiny durations and for aggregating small adjustments into very large totals. A more suitable origin, unit scale, accumulation strategy or integer representation may preserve the needed increment. Merely printing more decimal digits cannot restore information already lost during arithmetic.

assert 1e16+1.0==1e16
assert math.ulp(1e16)==2.0
assert (1e16+2.0)-1e16==2.0

Floating-Point Arithmetic Is Not Generally Associative

Real-number addition is associative, but finite-precision floating addition generally is not. Consider (1016 + (−1016)) + 1, which yields 1 in binary64, compared with 1016 + ((−1016) + 1), which yields 0 because the inner addition loses the unit increment. Both expressions have the same exact real sum; their finite sequences of rounding differ.

Compilers or parallel reduction algorithms may reorder work under certain flags or execution strategies, potentially changing the low bits or much more when cancellation is severe. “Parallel nondeterminism” is not automatically a bug, but a reproducibility requirement should specify the reduction tree, math flags, rounding environment and tolerance. Floating-point tests that compare only a small example should not assume the result remains bit-identical under a different processor count.

a,b,c=1e16,-1e16,1.0
assert ((a+b)+c)==1.0
assert (a+(b+c))==0.0

Accumulating Tenths: A Repeated-Operation Example

Repeated additions of an inexact binary fraction accumulate rounding in ways that depend on order and magnitude. In Python, summing 0.1 ten times with an ordinary loop can yield a result distinguishable from 1.0 by exact equality, even though it prints close to one. The error should be analyzed as the outcome of representation plus every rounded addition, not merely as “0.1 has a tiny error.” Different summation order and methods can produce different final roundings.

The correct mitigation depends on the contract. Counting integer tenths and dividing only for display can be exact for the counter. Decimal arithmetic can represent 0.1 exactly at the specified decimal precision. Compensated or accurately rounded summation can reduce binary-float accumulation error, but does not change the exactness of the underlying 0.1 value. Always distinguish an algorithm that improves summation from one that changes the representation base.

acc=0.0
for _ in range(10):acc+=0.1
assert acc!=1.0
assert math.fsum([0.1]*10)==1.0
assert sum([1]*10)/10==1.0

Catastrophic Cancellation and Significant Digits

Subtracting nearly equal numbers can produce a small result whose leading significant digits depend on small errors in the operands. For example, under binary64, (1 + 10−16) − 1 evaluates to zero, even though the exact expression equals 10−16, because the increment vanished when 1+10−16 was rounded. Cancellation does not invariably cause error: subtracting two exactly represented values can be exact. The vulnerability lies in subtracting quantities that already carry meaningful relative error.

A stable reformulation can avoid cancellation when a known identity is available. For small x, sqrt(1+x)−1 loses precision; writing it as x/(sqrt(1+x)+1) retains the small numerator. Many mathematical libraries also expose functions such as expm1(x) and log1p(x) specifically to preserve precision near zero. Their benefit arises from numerical analysis and implementation, not from increasing the stored word length.

x=1e-16
naive=math.sqrt(1+x)-1
stable=x/(math.sqrt(1+x)+1)
assert naive==0.0
assert math.isclose(stable,x/2,rel_tol=1e-12)

Conditioning Is Not the Same as Numerical Stability

Conditioning concerns how sensitive a mathematical problem's true answer is to perturbations of its inputs. Numerical stability concerns how the chosen algorithm responds to finite-precision operations. A well-conditioned problem can be solved unstably; a badly conditioned problem cannot generally be made fully insensitive by changing the algorithm alone. The distinction determines whether to reformulate an algorithm, increase precision, obtain better input data, or change the problem specification.

For a difference x−y where x and y are nearly equal, the result can be highly sensitive to relative perturbations of the operands when the intended quantity is small. In contrast, a well-designed algorithm may be backward stable: its computed result matches the exact result for nearby data. Such guarantees are more informative than a universal promise of “sixteen digits of accuracy” from binary64. The relevant error measure must correspond to the physical or decision threshold.

Summation Order, Pairwise Addition, and math.fsum

For a collection of floating values, ordinary left-to-right summation performs a rounding at each addition. Pairwise summation combines values in a more balanced tree and frequently reduces error growth, while math.fsum in Python uses a high-accuracy summation strategy to avoid many simple cancellation pitfalls. Neither tool makes an ill-conditioned mathematical sum intrinsically well conditioned, and exact behavior of alternatives should be tested on the target implementation.

A practical example is the sequence [1016, 1, −1016]. The exact mathematical sum is 1, yet explicit left-to-right floating addition yields 0. An accurately summed result is 1. In finance or safety accounting, even a highly accurate binary-float reduction may be less appropriate than integer subunits or decimal arithmetic because the value contract may require exact cents rather than a small numerical tolerance.

data=[1e16,1.0,-1e16]
sequential=0.0
for value in data:
    sequential+=value
assert sequential==0.0
assert math.fsum(data)==1.0

Compensated Summation and Kahan’s Method

Kahan summation stores a compensation term to track some low-order contributions lost when a small value is added to a much larger running sum. A simple version computes a corrected increment, updates the total and then updates the compensation based on the rounding that occurred. It often substantially improves a long sequential sum at small additional storage cost. Nevertheless, its accuracy can depend on the summation order, intermediate precision and compiler transformations; it is not an unconditional correctly rounded exact sum.

A demonstration with many identical small terms can make the improvement visible. In a production implementation, compare Kahan's method with pairwise reduction, wider accumulation and established language routines such as math.fsum. Choose based on accuracy requirements, speed, parallelization and reproducibility. Test against a higher-precision reference and include adversarial cancellation-heavy sequences rather than relying only on uniformly positive random data.

def kahan_sum(values):
    total=0.0; correction=0.0
    for x in values:
        y=x-correction
        temp=total+y
        correction=(temp-total)-y
        total=temp
    return total
values=[0.1]*10000
assert abs(kahan_sum(values)-1000.0)<1e-12
assert abs(kahan_sum(values)-1000.0)<=abs(sum(values)-1000.0)

Fused Multiply–Add and Intermediate Rounding

A fused multiply–add (FMA) operation computes a×b+c as though the product and addition were evaluated with infinite precision, then rounds once into the specified destination. Separate multiplication and addition usually round the product before adding c, potentially producing a different result. FMA can improve dot-product and polynomial calculations, especially when a large product nearly cancels another term. Its numerical benefit should not be confused with any universal promise that every expression becomes exact.

Whether a language provides a hardware-backed FMA, whether a compiler contracts operations into FMA, and whether the compiler permits reassociation vary. Python environments may expose math.fma depending on version and platform, while the example here deliberately illustrates the mathematical distinction without requiring that API. For reproducible computation, document the contraction policy and arithmetic execution environment. A faster FMA path may change the last bits relative to a non-fused reference, and that difference may be mathematically more accurate rather than a regression.

Floating-Point Comparisons and Decision Boundaries

Exact floating equality is correct when the question is about identical stored values, sentinel patterns or a genuinely exact invariant. It is often inappropriate when checking whether two independently rounded calculations represent the same real-world quantity. A tolerance rule should define absolute and relative terms for the application's scale. For example, |a−b| ≤ max(abs_tol, rel_tol × max(|a|,|b|)) is a common pattern, but tolerances are not a universal substitute for analysis.

Near zero, a pure relative tolerance provides little useful room; an application-specific absolute tolerance is needed. Near a safety threshold, broad tolerance may accidentally approve an unacceptable result. NaNs and infinities require separate explicit policy. A comparison based on an arbitrary number of ulps can be useful for local arithmetic validation but less useful when inputs are measured, correlated or carry model error. Test decision-boundary behavior under the exact production tolerance.

assert not (0.1+0.2==0.3)
assert math.isclose(0.1+0.2,0.3,rel_tol=1e-14,abs_tol=0)
assert not math.isclose(1e-8,0,rel_tol=1e-9,abs_tol=0)
assert math.isclose(1e-8,0,rel_tol=0,abs_tol=1e-7)

Decimal Fixed-Point and Decimal Floating-Point

Binary arithmetic is not the only finite-precision choice. A value such as 12.34 dollars can be stored exactly as the integer 1,234 cents. Alternatively, decimal floating-point arithmetic uses powers of ten and a finite decimal significand, so 0.1 is exactly representable in an adequately configured decimal format. Python's decimal.Decimal supports decimal arithmetic with explicit contexts, precision and rounding; string-based construction is essential when exact decimal intent matters.

Decimal storage does not eliminate all rounding: 1/3 still repeats in base ten, and precision limits remain. The goal is agreement with a domain's declared rounding and unit contract. For money, consider integer minor units or decimal arithmetic with prescribed rounding at legally or contractually defined boundaries. Avoid constructing Decimal from an already rounded binary float if the intent is the original decimal input; Decimal('0.1') and Decimal(0.1) encode different exact decimal values.

from decimal import Decimal, ROUND_HALF_EVEN
assert Decimal('0.1')+Decimal('0.2')==Decimal('0.3')
assert Decimal('0.1')!=Decimal.from_float(0.1)
assert Decimal('2.345').quantize(Decimal('0.01'),rounding=ROUND_HALF_EVEN)==Decimal('2.34')

Converting Between Formats and Double Rounding

Converting a value from fixed-point to floating-point, or from binary64 to binary32, involves a rounding decision unless the source value lies exactly in the destination set. Converting back normally does not recover lost information. For instance, encoding 0.1 in binary32 and widening the stored value to binary64 preserves the binary32 approximation precisely; it does not recreate the original real decimal 0.1. Similarly, converting a fractional float to an integer may truncate rather than round to nearest depending on the language operation.

Double rounding can occur when a value is rounded first to one intermediate precision and then to a narrower precision rather than rounded directly to the final format. Under certain combinations of values and rounding rules, the result differs from direct rounding. A precision pipeline must document intermediate widths and rounding points, especially for DSP accumulators, numeric file interchange, intermediate compiler registers and decimal parsing. Avoid claiming that intermediate widening automatically makes final conversion exact.

stored32=struct.unpack('>f',struct.pack('>f',0.1))[0]
assert stored32!=0.1
assert struct.unpack('>f',struct.pack('>f',stored32))[0]==stored32
assert abs(stored32-0.1)>0

Mixed Precision and Block Floating Point

Systems sometimes store data in a narrow format but compute or accumulate in a wider format. For example, coefficients or activations may be binary16 or binary32, while partial sums use binary32 or binary64. This can reduce memory traffic yet preserve additional guard precision where error is most likely to grow. The effectiveness depends on data distribution, hardware capabilities and the algorithm's conditioning. It should be demonstrated empirically and checked against an adequate reference.

Block floating point shares an exponent across a group of values while storing individual signed significands, exchanging some precision flexibility for simpler computation and compact storage. It resembles fixed-point arithmetic with a periodically adjusted common scale. Scaling can reduce overflow risk, but small values relative to the block maximum may lose significant digits. This format illustrates that the fixed-versus-floating dichotomy is a spectrum of representation designs, not an absolute hardware boundary.

Performance and Power Are Architecture-Dependent

Fixed-point arithmetic can be efficient on embedded processors with integer DSP instructions and limited floating-point hardware, and it can provide predictable bit-level overflow behavior when engineered carefully. Floating-point is often highly efficient on modern desktop CPUs, GPUs and dedicated accelerators. On some devices an integer division may be slower than a floating multiply; on others fixed-point vector operations dominate. Therefore, claims that fixed-point is always faster or floating-point is always wasteful are technically unsound.

Compare implementations under the target instruction set, compiler flags, vector width, memory format, clock rate and energy budget. Include the cost of scale conversions, saturating operations and extended accumulators. A nominally cheap 16-bit fixed operation may require multiple wide instructions for correct rounding, while a supported 32-bit floating operation may be native. The format choice is an end-to-end resource decision, not a count of arithmetic operators in source code.

Determinism, Reproducibility, and Portability

Integer and well-specified fixed-point computations can support exact bitwise reproducibility if word widths, signedness, rounding, overflow and intermediate operations are all fixed. Floating-point operations can also be reproducible under defined formats and ordering, but differences in reduction trees, compiler fast-math options, fused operations, extended precision, math libraries and subnormal handling can change results. A standard format alone is not a promise that two entire programs have identical output bits.

For regulated or scientific systems, specify expected tolerance or exact reproducibility, establish reference vectors and test the target architectures. Serialized numeric values need documented byte order, versioning and interpretation; an endian swap does not imply any rounding, but a cast between float formats does. Test NaN and signed-zero policies where these can cross database, language or network boundaries. Report software version and compiler settings when comparing numerical experiments.

Numerical Error Budget and Physical Measurement

A measured physical value may already have error from sensing, calibration, analog noise, drift, sampling and environmental effects. Digitization adds conversion and quantization effects; subsequent computation adds rounding and algorithmic approximation. These error sources are not interchangeable and need not be statistically independent. The storage spacing of a binary64 value may be vastly finer than the actual uncertainty of the sensor signal. Quoting the full binary64 decimal representation as physical accuracy is false precision.

A defensible error budget expresses tolerances in physical units, identifies systematic versus random contributions, and states how uncertainties propagate through transformations. Correlated bias does not vanish merely by averaging, and saturation violates small-error linear approximations. Choosing a wider format is useful when computational error threatens the budget, but a calibration problem requires calibration. For details of converter effective resolution, see the unit's Quantization Noise and Effective Resolution and Computational Error Budgets and Calibration.

A Representation Selection Matrix

An algorithm's data range, accuracy contract and required operations should determine its representation. Exact counts and identifiers belong in sufficiently wide integer types. Bounded fractional signals on a DSP can suit fixed-point with explicit scales and accumulators. Scientific values spanning large exponent ranges can suit floating point, with careful conditioning and exception handling. Exact decimal monetary amounts often suit integer minor units or decimal formats. Approximate numerical machine-learning workloads may use deliberately reduced precision with wider accumulation.

None of these selections bypasses validation. For an embedded control loop, fixed-point may minimize power but creates scaling and saturation risks. For a simulation, binary64 may be easier to use but does not make the numerical integrator stable at any time step. For a database key, binary64's large numeric range does not ensure exact storage of a 64-bit identifier. The choice should be justified by a measured or proven end-to-end error and resource budget, not by a generic “more bits is better” rule.

Testing Strategy for Numeric Formats

A proper test matrix includes both nominal values and difficult boundaries. For fixed-point, test minimum and maximum codes, half-quantum ties, negative rounding, scale mismatches, wide products, saturation, repeated increments and all-zero signals. For floating-point, test representable powers of two, 0.1, values near exponent transitions, subnormals, signed zeros, infinities, NaNs, cancellation, widely separated magnitudes and alternative summation orders.

A reference oracle may use rational arithmetic for exact finite examples, a higher-precision library for analysis, or known standard test vectors. Random inputs alone are insufficient because many critical cases occupy a tiny portion of the possible bit patterns. Record the rounding environment and the meaning of acceptable error, then verify metamorphic relationships where relevant. Keep hardware validation distinct from mathematical-model validation: a passing software assertion cannot prove analog sensor accuracy or device power integrity.

Worked Investigation 1: Selecting a Temperature-Controller Format

A controller represents calibrated temperatures between −80 °C and +80 °C and requires a code spacing no worse than 0.01 °C. A signed 16-bit fixed-point representation with f=10 fractional bits has Δ=1/1024≈0.0009766 °C, but its range is only [−32, 31.999…] °C, so it fails the range requirement. Choosing f=8 instead gives Δ=1/256≈0.00390625 °C and range [−128, 127.996…] °C, satisfying both stated requirements with room to spare.

A controller must still check whether its intermediate computations remain in range. A difference of −80 and +80 is −160 °C, which cannot fit the same signed Q8.8 representation even though each operand fits. A widened difference or a separately specified temperature-delta format is required. This is a common design error: selecting a representation by individual signal bounds and overlooking arithmetic involving two extreme inputs.

width=16; f=8
quantum=2**-f
minimum=-(1<<(width-1))*quantum
maximum=((1<<(width-1))-1)*quantum
assert minimum<=-80 and maximum>=80 and quantum<=.01
assert -160<minimum  # difference requires a wider representation

Worked Investigation 2: An Exact Currency Ledger

A ledger receives two payments, $12.34 and $0.66. Using signed integer cents produces 1,234+66=1,300 cents, exactly $13.00, with no binary-fraction rounding. Representing each dollar amount in binary64 instead produces approximations of the decimal inputs. This may or may not affect a displayed result in a simple example, but the numerical contract is different from exact minor-unit accounting.

The ledger should specify currency, unit, rounding at exchange-rate and tax boundaries, and overflow controls for the maximum total. Exact cents are not sufficient to represent every type of interest or exchange-rate calculation; a higher-precision internal decimal or rational calculation may be needed before rounding at a prescribed settlement boundary. Never assume that switching from binary float to integer cents removes the need to define when and how rounding occurs.

cents = 1234 + 66

Worked Investigation 3: Q1.15 Audio Mixing and Clipping

Two signals have instantaneous sample amplitudes 0.9 and 0.4. If both are encoded as signed Q1.15, their respective nearest-even codes are 29,491 and 13,107. The wide sum is 42,598, representing approximately 1.3 and exceeding the maximum signed Q1.15 code of 32,767. Saturating the sum produces almost +1; wrapping it yields a negative code, producing a dramatically different waveform. Neither policy recreates the unclipped real amplitude.

An audio designer may prevent clipping by scaling the input mix, using a wider processing format, or dynamically controlling gain before the final output conversion. The correct choice depends on headroom, noise floor, allowed distortion and signal statistics. If the system claims no clipping, it must measure or bound peaks rather than merely showing the mean sample magnitude is modest.

qa=encode_fixed_nearest(.9,15)

Worked Investigation 4: A Large Integer Converted to Binary32

A data logger stores a count of 16,777,217 events. This is 224+1, one beyond the contiguous integer-exactness range of binary32. When converted to binary32 with ties-to-even, the value rounds to 16,777,216. Another adjacent integer can represent a different actual count yet map to the same stored float. A display or API based on this approximate representation may silently misstate event totals.

The remedy is not necessarily binary64 if a 64-bit unsigned counter will eventually exceed its contiguous precision bound as well. Use an integer format that covers the full count, declare wrap semantics and avoid converting through a narrower floating format for serialization or user-interface display. Unit tests should include neighboring integers around powers-of-two precision boundaries.

count=2**24+1

Worked Investigation 5: Cancellation in a Scientific Sum

A simulation sums three contributions: +1016, +1 and −1016. The exact total is 1, but sequential binary64 addition in that order produces 0 because the intermediate 1016+1 rounds to 1016. Reordering the first and last terms first produces 1. An accurately rounded summation utility also recovers 1 for this set. The discrepancy is not an argument to choose a physically implausible precision target without analysis; it reveals a vulnerable accumulation pattern.

Worked Investigation 6: A Control Threshold Near Unity

Suppose a controller enters an alarm state when a computed normalized signal exceeds 1.0. If the intended signal is 1+10−16, converting it to binary64 rounds to 1.0, so a strict value > 1.0 comparison is false. Whether that is acceptable depends on the physical interpretation of the threshold and the acquisition accuracy. A generic tolerance function can change which signals trigger the alarm, and may be inappropriate when the requirement is deliberately strict.

One design might use a fixed-point format with explicit quantum smaller than the critical difference; another might compute a more stable comparison using exact integer sensor codes, or revise the alarm's hysteresis based on measured noise. A threshold's unit, uncertainty, response delay and fail-safe behavior should be specified before numerical tuning. Merely switching to “approximate equality” cannot supply a missing physical safety requirement.

computed=1.0+1e-16
assert computed==1.0
assert not (computed>1.0)
assert 1.0+1e-15>1.0

Worked Investigation 7: Subnormal Sensitivity

A numerical model produces the binary64 value 2−1074, the smallest positive subnormal. It is distinguishable from zero in a conforming binary64 representation, but halving it and rounding to binary64 yields zero. A simulation that depends on this residual may therefore change behavior at the subnormal boundary. The corresponding relative error of this halving operation is 100 percent, even though its absolute error is extraordinarily small.

Before increasing precision, determine whether this tiny quantity is important to the physical or probabilistic model. For products of many probabilities, logarithmic representations can avoid premature underflow. For low-amplitude DSP processing, appropriate scaling can improve retained significance. For execution modes that flush subnormals, actual hardware behavior must also be checked and documented; a mathematical IEEE example is not a substitute for runtime characterization.

tiny=math.ldexp(1.,-1074)
assert tiny>0.0
assert tiny/2==0.0
assert tiny*2>tiny

Worked Investigation 8: Fixed-Point Dot Products and Widened Sums

Consider two short Q1.15 vectors whose elements are 0.5 and 0.25, and 0.5 and −0.25. Their mathematical dot product is 0.5×0.5 + 0.25×(−0.25)=0.1875. The stored code pairs are [16,384, 8,192] and [16,384, −8,192]. Multiplying codes creates products on the 2−30 scale. Summing those wide products first and shifting once yields the exact Q1.15 code 6,144 for this example.

In more general vectors, an accumulator must have enough width for the largest possible sum of products, and the final shift must use the declared rounding rule. Rounding each product individually before the sum can give a different result from rounding once after accumulation. This motivates widened MAC instructions and explicit bit-growth analysis in fixed-point filters and neural-network accelerators.

u=[16384,8192]
v=[16384,-8192]
acc=sum(a*b for a,b in zip(u,v))
code=acc//(1<<15)  # exact division for this example
assert acc==201326592
assert code==6144
assert code/(1<<15)==0.1875

Integrated Numerical Representation Decision Framework

Apply five gates in order. Meaning: specify units and whether the value must be exact. Range: bound inputs, transients, intermediates and outputs. Error: allocate acceptable absolute, relative and application-level error, noting the difference between measurement and computation. Execution: identify hardware arithmetic, memory, power, latency and interoperability constraints. Verification: test exact endpoints, exceptional values, repeated operations and portability.

The result should be a documented format contract—such as “signed 16-bit, f=8, nearest-even conversion, widened multiply, saturated output” or “IEEE binary64, round-to-nearest, detect nonfinite values, pairwise reduction and 10−9 domain tolerance.” A format name without these operational details is an incomplete specification. Revisit the choice if the quantity range, physical calibration, processor or acceptable error changes.

  1. Specify units, exactness and physical measurement uncertainty.
  2. Derive worst-case input and intermediate magnitudes.
  3. Choose width, scale or floating format to meet error and range requirements.
  4. Define overflow, rounding, special-value and serialization semantics.
  5. Evaluate cost on target hardware and compare with independent references.
  6. Record boundary tests and monitor deployed error or saturation.

Common Failure Modes and Their Corrections

Several recurring errors deserve explicit rejection: interpreting raw integer codes without scale, confusing Q-format conventions, relying on signed integer wrap in a controller, shifting a signed negative product without acknowledging floor behavior, and calling machine epsilon the same thing as unit roundoff without stating definitions. On the floating side, “binary64 has sixteen accurate decimal digits” is not a guarantee for arbitrary unstable algorithms, and exact displayed decimal formatting is not evidence of exact underlying storage.

Likewise, using exact float equality for an approximate physical decision may be fragile, but replacing every comparison with an arbitrary tolerance can be equally wrong. Treating a NaN as ordinary missing data can hide invalid operations, while automatically converting infinity to a maximum finite code can conceal overflow. The correction is a full numeric contract, explicit bound calculations, careful operation ordering and reference tests that cover problematic bit patterns.

Review Questions

The following questions are intended to test representational reasoning, not memorization of one hardware platform's typical behavior. They distinguish what follows from a stated format from what still requires an implementation or application contract.

Review Questions and Model Answers

Questions are followed by brief answers. A full technical solution should cite the particular width, scale or rounding mode being assumed whenever a different format would change the answer.

  1. Why can a finite word not represent every real number? It has finitely many codes while real numbers contain infinitely many distinct values.
  2. What converts a signed integer into a binary fixed-point quantity? A specified scale, often 2 raised to the negative number of fractional bits.
  3. What does 0xC000 represent in signed 16-bit Q1.15? Code −16384, representing −0.5.
  4. What is the largest signed Q1.15 value? 32767/32768, or 0.999969482421875.
  5. What is the quantum in signed Q8.8? 1/256, or 0.00390625.
  6. Why must a Q1.15 product use a wider intermediate? Multiplication produces a code scaled by 2^-30 and can need up to twice the operand width.
  7. What are two distinct responses to fixed-point overflow? Saturation and modular wrap, among others such as checked errors and widening.
  8. Why may a signed arithmetic right shift create rounding bias? For negative values it commonly rounds downward rather than truncating toward zero or nearest.
  9. What are the field widths of binary32? One sign bit, eight exponent bits and 23 stored fraction bits.
  10. What are the normal significand precision and bias of binary64? 53 binary precision bits and exponent bias 1023.
  11. How does floating spacing change with magnitude? For normal values, the spacing generally doubles when the exponent increases by one.
  12. How is a subnormal decoded differently from a normal? It has no implicit leading 1 and uses the minimum normal exponent with a fractional significand.
  13. What is the smallest positive binary32 subnormal? 2^-149.
  14. Does binary64 represent decimal 0.1 exactly? No; its binary expansion repeats and is rounded into the nearest binary64 value.
  15. What is the local upward ulp of binary64 at 1? 2^-52.
  16. How is unit roundoff related to binary64 machine epsilon under round-to-nearest? Unit roundoff 2^-53 is half the usual epsilon 2^-52.
  17. Why can an exact integer lose information when converted to binary64? Integers beyond its 53-bit contiguous exactness range may round to the same floating value.
  18. Why can 1e16 + 1 equal 1e16 in binary64? The local representable gap exceeds one, so the addition rounds back to 1e16.
  19. What is catastrophic cancellation? Loss of meaningful significant digits when subtracting close quantities carrying prior approximation error.
  20. What is the distinction between condition and stability? Condition concerns problem sensitivity; stability concerns the algorithm’s numerical behavior.
  21. What can compensated summation improve? It can recover contributions lost through repeated rounding in ordinary summation.
  22. Does math.fsum make decimal 0.1 exactly representable? No; it improves summation but the input binary-float 0.1 remains approximate.
  23. What is the benefit of fused multiply–add? A product and sum are rounded once rather than at separate intermediate steps.
  24. Why are near-zero comparisons often given an absolute tolerance? A relative-only tolerance scales to almost zero around zero.
  25. What happens when a positive subnormal is halved below the minimum quantum? It may round to positive zero.
  26. Why is an IEEE infinity not interchangeable with an unbounded physical measurement? Infinity is a numeric special value and may reflect overflow or invalid assumptions, not physical truth.
  27. When might exact integer cents be preferable to binary floating dollars? When exact minor-unit ledger accounting and specified decimal settlement rules are required.
  28. What must a format decision record besides word width? Units, signedness, scale or float encoding, rounding, overflow, intermediate widths, special cases and tests.
