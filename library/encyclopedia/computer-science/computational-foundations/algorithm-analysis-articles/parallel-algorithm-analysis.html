Definition and Position in Algorithm Analysis

Parallel algorithm analysis characterizes how an algorithm’s work, dependencies, processor allocation, communication, and memory use determine its potential performance when multiple computational resources act concurrently. It asks not simply whether tasks can overlap but how much work they perform in total, what dependencies remain unavoidable, and how resource limits constrain execution. The central theoretical quantities are work W and span S; empirical analysis adds concrete processors, schedules, message costs, contention, and data movement.

The subject belongs to the MGU Algorithm Analysis unit, alongside Recursion Trees and the Master Theorem, Cache and External-Memory Complexity, and Algorithm Benchmarking and Profiling. It focuses on rigorous analysis and comparative guarantees, rather than functioning as a vendor-specific guide to multithreading or GPU programming. A fast parallel implementation can be work-inefficient, while a work-efficient parallel algorithm may be slow on an unsuitable machine.

Four Questions to Ask Before Writing a Speedup Claim

A defensible analysis first specifies the input and output contract, the computational DAG, the resource model, and the comparison baseline. The same function may have distinct behavior under a shared-memory machine, a fixed-size thread pool, a GPU’s SIMT execution model, or a cluster whose workers exchange messages. Asymptotic complexity by itself does not identify the fastest deployment.

  1. What operations are required for correctness, and which can be reordered or combined?
  2. What is the total operation count W, and which dependency path fixes the span S?
  3. How many processors P are available, and which memory, bandwidth, communication, or synchronization assumptions apply?
  4. Against which sequential algorithm and input size is speedup measured, including setup, transfers, and result collection?

The answers should accompany every claimed O-bound. For example, a parallel reduction that claims logarithmic depth assumes a bounded-fan-in associative operator, enough processors to expose each tree level, and an efficient mechanism for communicating partial results. Removing any assumption can materially change its cost.

Parallelism, Concurrency, and Distribution

Parallelism means that computations overlap in time; concurrency means a program comprises potentially interleaving activities, whether or not multiple processors actually execute them simultaneously. Distributed computation places activities across distinct machines or address spaces and typically makes communication and partial failure prominent. A program that launches many asynchronous tasks can still perform almost entirely serial work if most tasks wait for one shared resource.

The analytical distinction matters for both proofs and measurements. A DAG exposes independent ready tasks, whereas a runtime decides which ready tasks actually execute on cores. Thread count is not equivalent to processor count, and processor count is not equivalent to independent hardware execution slots. Hyperthreading, GPU warps, execution ports, memory channels, and virtual-machine quotas can all limit realized concurrency.

Computation as a Directed Acyclic Graph

Model a finite parallel computation as a directed acyclic graph (DAG). Each vertex represents a strand or operation; an edge u → v says v cannot begin until u completes. A strand is a sequential segment with no internal parallelism exposed to the model. For unit-time vertices, W is the number of vertices and S is the number on a longest directed dependency path. With weighted vertices, W is the sum of vertex costs and S is the maximum sum along a path.

A DAG is not the same as a graph depicting which threads happen to run. Its vertices and edges represent required computation and ordering, independent of a particular scheduler. Scheduling adds a separate resource constraint: at most P unit strands may execute simultaneously on P unit-speed processors. A cycle in a proposed dependency graph signals a modeling error or an unresolved cyclic protocol, not a valid finite DAG for Brent-style analysis.

from functools import lru_cache

def dag_work_span(predecessors, weight):
    visiting = set()
    @lru_cache(None)
    def finish(v):
        if v in visiting:
            raise ValueError("cycle in dependency graph")
        visiting.add(v)
        parents = predecessors[v]
        value = weight[v] + max((finish(u) for u in parents), default=0)
        visiting.remove(v)
        return value
    return sum(weight.values()), max(map(finish, predecessors), default=0)

pred = {'A': [], 'B': ['A'], 'C': ['A'],
        'D': ['B', 'C'], 'E': ['D'], 'F': ['D'], 'G': ['E', 'F']}
weights = {x: 1 for x in pred}
assert dag_work_span(pred, weights) == (7, 5)

Work: The Total Price of a Parallel Computation

For a unit-cost DAG, W = T₁ is the time needed to execute all of its operations on one ideal processor, using the same parallel algorithm but suppressing parallel execution. Work accounts for extra coordination operations, repeated calculations, or data copying inserted by the parallel design. If the best known sequential algorithm requires Θ(n) steps but a proposed parallel method requires Θ(n log n) total steps, the method has a work overhead of Θ(log n), even if its critical path is short.

Keep W distinct from Tseq, the running time of a separately optimized sequential baseline. The parallel algorithm might perform much more work than that baseline. A work-efficient parallel algorithm has W = O(Tseq) for a chosen reference sequential bound, usually with matching Θ-bounds when a lower bound is known. Stating both quantities prevents impressive speedup relative to an artificially inefficient serial execution of the parallel algorithm.

Span: The Critical-Path Lower Bound

Span S = T∞, also called depth or critical-path length, is the execution time if every ready strand could run immediately with no limit on processor count. Span measures the longest chain of dependent operations; it is not a sum over every branch. When a parent forks two independent operations and subsequently joins them, the ideal span is fork cost plus the maximum child span plus join cost, not the sum of both child spans.

If a balanced binary reduction has n leaves and a constant-time associative combine at each internal node, S = Θ(log n), while W = Θ(n). A sequential accumulation of the same n values has S = Θ(n) because every addition depends on the preceding accumulator. The required algebraic associativity and numerical reproducibility policies must be identified before reorganizing the operation order. The DAG proof concerns legal rearrangements, not merely where threads are placed.

Work and Span as a Resource Pair

Reporting only O(n) work hides whether the computation offers constant or linear parallelism. Reporting only O(log n) span hides whether the parallel method does n or n² total work. The resource pair (W(n), S(n)) retains both dimensions and permits a lower bound for any processor budget P. For example, map over an n-element array with independent constant-time functions has W = Θ(n) and S = Θ(1) in an ideal all-to-all parallel model, whereas a balanced reduction has W = Θ(n) and S = Θ(log n).

These ideal figures exclude scheduling overhead, allocation, memory transfers, and a finite maximum number of simultaneously executable processors. A fully materialized output may also require Θ(n) storage even when span is constant. State the scope of the pair: task-DAG work/span, bandwidth traffic, auxiliary storage, and messages should be added as separate coordinates when they dominate the actual machine.

The Work Law

If a computation performs W unit-time operations and has P identical processors, a processor can complete at most one unit operation per time step. Consequently TP ≥ W/P, ignoring fractional-step rounding. The law remains valid even if the computation has no dependencies: P workers collectively cannot execute more than P unit operations per step. It is a lower bound, not a runtime prediction.

For W = 1,000,000 and P = 100, every valid schedule requires at least 10,000 idealized time units. A real implementation may run longer because the tasks are unevenly sized, workers communicate, or the memory system saturates. Increasing P decreases this lower bound, but only until another bound—especially span—becomes dominant.

The Span Law

Every dependency chain must execute in order, so TP ≥ S for any finite P, regardless of how many processors are provided. If an input parser has 200 sequential stages each taking one unit, adding processors cannot complete that required chain in fewer than 200 steps without changing its dependence structure. This bottleneck is algorithmic, not simply a scheduler defect.

Together the work and span laws give TP ≥ max(W/P, S). When W/P dominates, the processor budget is relatively small compared with available parallelism. When S dominates, adding processors to the same dependency graph has diminishing potential. The two laws are rigorous under the specified model; hardware effects can add further lower bounds arising from bandwidth, memory contention, and synchronization.

Brent’s Theorem: An Ideal Scheduling Upper Bound

Brent’s theorem, often taught with Graham’s greedy-scheduling argument, states that a work-span DAG of unit strands can be executed on P ideal processors by a greedy scheduler in time TP ≤ W/P + S (up to model-specific rounding and constant-time scheduling assumptions). A sharper unit-strand estimate is W/P + (1 − 1/P)S in common formulations. Thus the ideal schedule is within a constant factor of the lower bound max(W/P, S).

The theorem is not a promise that an arbitrary operating system, runtime, GPU kernel, or distributed platform attains that bound. It assumes the computation’s DAG, ready-work discovery, scheduling, communication, and processor costs fit the idealized model. Those assumptions are especially consequential when tasks are tiny, memory traffic is dominant, or data dependencies cross machine boundaries.

def brent_bounds(work, span, processors):
    if not (1 <= span <= work and processors >= 1):
        raise ValueError("need 1 <= span <= work and P >= 1")
    lower = max(work / processors, span)
    upper = work / processors + span
    return lower, upper

assert brent_bounds(1000, 50, 10) == (100, 150)
assert brent_bounds(1000, 50, 100) == (50, 60)
assert brent_bounds(1000, 50, 1) == (1000, 1050)

Why the Greedy-Scheduling Bound Works

A greedy schedule executes as many currently ready unit strands as P processors permit. Classify a step as complete when all P processors are occupied, and incomplete when fewer than P are occupied. There can be at most W/P complete steps because each such step performs P units of work. At an incomplete step, greediness means every ready strand executes; in particular, a strand along a remaining critical path executes. The longest remaining dependency chain therefore shortens by at least one at each incomplete step.

There are at most S incomplete steps. Adding the two counts yields T_P ≤ W/P + S, subject to integer rounding. This proof also explains when the theorem is useful: it converts an algorithmic DAG bound into a statement about a class of ideal schedulers without requiring a precise schedule trace. It does not bound network startup times, cache-miss penalties, or interference by other processes.

An Explicit Seven-Task Schedule

Consider seven unit-time tasks with dependencies A → {B, C}, {B, C} → D, D → {E, F}, and {E, F} → G. The DAG has W = 7 and critical path A–B–D–E–G of length S = 5. On two processors, one valid schedule takes five steps: run A; then B and C together; then D; then E and F together; then G. No schedule can do better because the critical path is already five steps long.

The theoretical lower bound is max(7/2, 5) = 5, and the coarse Brent upper bound is 7/2 + 5 = 8.5 steps (rounded for an integral-step schedule). Its looseness is not a contradiction; Brent bounds every ideal greedy schedule rather than predicting the exact optimum for this DAG. The result is a useful reminder that the analysis is a feasibility envelope, not a simulated timeline.

Available Parallelism and Parallel Slackness

The ratio W/S is the algorithm’s average parallelism: the number of processors at which the work lower bound W/P becomes comparable to the span lower bound S. A DAG with W = 10⁸ and S = 10⁴ offers average parallelism 10⁴. A machine with P = 64 processors has ample theoretical slack, whereas one with P = 100,000 cannot expect linear scaling from that same DAG.

Parallel slackness is often expressed as W/(P S). Values much greater than one indicate that available parallelism substantially exceeds the machine width. This is a necessary but insufficient favorable condition: ready-task bursts can still be uneven, the memory hierarchy may bottleneck execution, and the scheduling cost may dominate. A small ratio highlights a structural limit before benchmarking starts.

def parallelism_report(work, span, p):
    q = work / span
    return {'parallelism': q, 'slackness': q / p,
            'work_floor': work / p, 'span_floor': span}

r = parallelism_report(100_000_000, 10_000, 64)
assert r['parallelism'] == 10_000
assert r['slackness'] == 156.25

Speedup, Efficiency, and Processor Cost

Define speedup SP = Tbaseline/TP, where the baseline is explicitly identified. Parallel efficiency EP = SP/P. Cost P TP measures aggregate processor-time consumed by the run. If the baseline is T₁ for the same DAG, then the work law implies SP ≤ P in the ideal model; real-world superlinear speedups may be reported when using a different cache footprint or baseline and require explanation.

For example, if a sequential implementation takes 80 seconds and an eight-processor implementation takes 12 seconds, measured speedup is 80/12 ≈ 6.67, efficiency is approximately 0.833, and processor cost is 96 processor-seconds. This does not by itself reveal whether the sequential baseline used equally optimized code or whether the parallel run increased memory use. Compare equal outputs, input sizes, compiler settings, and complete execution boundaries.

def scaling_metrics(t_baseline, t_parallel, p):
    if min(t_baseline, t_parallel) <= 0 or p < 1:
        raise ValueError('positive times and processor count required')
    speedup = t_baseline / t_parallel
    return speedup, speedup / p, p * t_parallel

speedup, efficiency, cost = scaling_metrics(80.0, 12.0, 8)
assert abs(speedup - 6.666666666666667) < 1e-12
assert abs(efficiency - 5/6) < 1e-12
assert cost == 96

Amdahl’s Law and the Fixed-Problem Limit

Amdahl’s law models a fixed workload with a nonparallelizable fraction s of the baseline time and a perfectly parallelizable fraction 1−s. With P workers and no extra overhead, SP = 1/[s + (1−s)/P]. As P grows, speedup is bounded above by 1/s whenever s > 0. A serial fraction of 10% yields a limiting speedup of ten, even with infinitely many ideal processors.

This simple model is valuable for identifying irreducible serial phases, but it assumes the fractions do not change with processor count and ignores new bottlenecks. In practice, synchronization, bandwidth, and allocation may increase with P; some algorithms also restructure the “serial” phase. An observed speedup exceeding the fitted Amdahl curve indicates the assumptions or measurement baseline differ, not that the algebra is false.

def amdahl_speedup(serial_fraction, p):
    if not (0 <= serial_fraction <= 1 and p >= 1):
        raise ValueError('invalid Amdahl parameters')
    return 1 / (serial_fraction + (1 - serial_fraction) / p)

assert abs(amdahl_speedup(0.10, 16) - 6.4) < 1e-12
assert abs(amdahl_speedup(0.10, 1) - 1.0) < 1e-12

Gustafson’s Law and Scaled-Problem Speedup

Gustafson’s scaled-speedup argument examines workloads that grow as more processors become available while holding the parallel elapsed time fixed. If s is the serial fraction of that measured parallel execution time at P processors, the scaled speedup in the simple model is P − s(P−1). With P = 16 and s = 0.10, the scaled speedup is 14.5. This is a different question from Amdahl’s fixed-input speedup.

The symbol s is defined differently in common presentations of the two laws; the 10% figures in the previous examples are therefore not the same measured quantity. Neither law includes unlimited bandwidth, scaling setup costs, nonlinear serial growth, or data-dependent convergence automatically. When the input increases, describe exactly what grows—records, spatial resolution, iterations, or independent requests—and report whether accuracy and output contracts remain comparable.

def gustafson_scaled_speedup(serial_fraction_of_parallel_run, p):
    s = serial_fraction_of_parallel_run
    if not (0 <= s <= 1 and p >= 1):
        raise ValueError('invalid parameters')
    return p - s * (p - 1)

assert gustafson_scaled_speedup(0.10, 16) == 14.5

Strong Scaling Versus Weak Scaling

A strong-scaling experiment keeps total problem size fixed and increases processor count. A weak-scaling experiment holds work per processor approximately fixed while increasing total problem size with P. Strong scaling exposes the critical-path and communication floor of one workload; weak scaling measures whether a growing deployment can preserve a target elapsed time per unit of added capacity. These experiments are not interchangeable.

For strong scaling, graph input size n, machine placement, data distribution, and preprocessing should remain fixed. For weak scaling, specify the scaling function n(P): doubling the workers while doubling independent jobs is not the same as doubling the side length of a three-dimensional mesh. Weak-scaling efficiency is often defined as T(1,n₁)/T(P,nP) with constant work per worker, but the chosen work measure should include communications and setup if those matter operationally.

Serial Fractions, Granularity, and False Bottlenecks

A measured serial fraction may reflect real dependencies, startup overhead, a global lock, allocator contention, queue contention, page faults, or insufficient task granularity. These have different remedies. Amdahl’s law characterizes a fixed split; a profiler identifies which pieces are actually serial and whether they can be removed, batched, distributed, or computed at lower frequency. A single scalar fraction is therefore a diagnostic approximation, not the algorithm’s entire dependency graph.

Suppose 16 threads call a function that atomically increments one shared counter after each processed item. The arithmetic per item can be independent, yet the contended counter limits throughput. Replacing it with per-worker counts followed by a reduction changes the DAG and reduces contention. The reduction still costs communication or synchronization, but its frequency and fan-in are controllable. The improved algorithm can have the same Θ(n) work while a much shorter effective critical path.

Accounting for Parallel Overhead

A useful operational decomposition is T_P ≈ T_useful/P + T_critical + T_scheduling + T_communication + T_contention + T_imbalance, but these components can overlap and must not be naively summed if measurements already include one another. The approximation is a reporting framework rather than a universal performance theorem. Each component depends on the machine, workload, and execution schedule.

Spawning a million one-microsecond tasks is rarely equivalent to giving a million cores one independent unit of work. Task creation and coordination can exceed useful execution. A scalable implementation groups work into chunks, reduces unnecessary barriers, and avoids accidental serialization on shared metadata. It should also distinguish extra instructions due to parallelism from delays that leave workers idle.

Computational Models: From PRAM to Machines

The parallel random-access machine (PRAM) assumes synchronous ideal processors sharing memory; each processor performs limited operations per step under rules governing simultaneous reads and writes. It makes algorithmic dependencies visible without incorporating realistic memory costs. Fork–join DAGs instead expose tasks and synchronization, while a GPU’s SIMT model groups threads into lockstep-like execution cohorts and a message-passing cluster transmits data explicitly.

Model selection changes the meaning of “constant time.” Fetching one shared datum is a constant-cost PRAM step under some concurrency modes but can create a broadcast, a memory bottleneck, or a network exchange in hardware. The model should be strong enough to express the intended technique and weak enough to prevent hidden free resources from explaining the result.

EREW, CREW, and CRCW Memory-Access Rules

PRAM variants differ by simultaneous-access permissions. EREW forbids concurrent reads and concurrent writes of the same shared cell. CREW permits concurrent reads but requires exclusive writes. CRCW permits both, provided concurrent write conflicts obey a specified resolution rule such as common-value, arbitrary-winner, or priority. An algorithm claiming CRCW performance must state which rule applies.

In ordinary threaded software, a race between conflicting unsynchronized writes is generally a correctness problem, not an accepted CRCW scheduling primitive.

BSP and Bulk-Synchronous Supersteps

The bulk-synchronous parallel (BSP) framework organizes execution into local-computation phases, communication phases, and synchronization boundaries. A superstep is modeled using its local work plus communication volume and a global synchronization cost; a common simplified form is max(local_work) + g·h + L, where h is a maximum per-worker communication load, g a cost coefficient, and L a barrier latency. Exact definitions vary by BSP variant.

This model highlights costs omitted by ideal PRAM: one badly loaded worker determines a superstep’s local completion time, data movement has a price, and a barrier prevents progress into the next stage until required participants synchronize. Distributed graph algorithms and iterative numerical methods often naturally fit the BSP vocabulary, but asynchronous alternatives can change both performance and correctness proof obligations.

Fork–Join, Tasks, and Nested Parallelism

In fork–join computation, a parent creates independent child tasks and later waits for a join. The work recurrence adds child work; the span recurrence takes the maximum child span plus the parent’s sequential overhead. For two equally sized recursive children, typical forms are W(n)=2W(n/2)+f(n) and S(n)=S(n/2)+g(n) when both branches may execute concurrently and parent overhead has critical-path contribution g.

Nested parallelism is useful for divide-and-conquer methods, but unlimited recursive task spawning can exhaust runtime queues, degrade locality, or increase overhead. A practical implementation often switches to sequential execution below a size threshold. The theoretical span then includes the sequential base case; the runtime gains efficiency when the threshold is tuned to useful work per task rather than chosen from input size alone.

Task Granularity and Spawn Thresholds

The grain size is the amount of useful computation assigned to a schedulable task. Smaller tasks create more scheduling freedom and can improve balance; larger tasks amortize spawn, synchronization, and metadata overhead. Let a task perform c units of useful work and pay h units of overhead: if c ≪ h, increasing processor count simply multiplies overhead. If tasks are too coarse, their count or duration may limit parallel speedup.

A practical grain-size experiment sweeps chunk size while holding input and worker count fixed, recording throughput, tail latency, and scheduling time. The optimal threshold varies with instruction mix, cache size, input skew, and runtime implementation. Do not infer it exclusively from W/S: that ratio is based on idealized strands and does not price task-management operations.

def chunk_plan(items, grain):
    if items < 0 or grain <= 0:
        raise ValueError('invalid chunk plan')
    return [(a, min(a + grain, items)) for a in range(0, items, grain)]

assert chunk_plan(10, 4) == [(0, 4), (4, 8), (8, 10)]
assert chunk_plan(0, 4) == []

Work Stealing and Dynamic Scheduling

Work stealing allows an idle worker to take ready tasks from another worker’s deque. It is particularly useful for irregular fork–join computation in which future task costs are hard to predict. Under the assumptions of classic randomized work-stealing analysis for suitable multithreaded DAGs, expected execution time has the form O(W/P + S). This is a conditional theorem: its proof requires restrictions on the computation and scheduler, not merely a call to a thread pool.

Stealing introduces queue operations, synchronization, migration, and possible cache coldness. Tasks with large private working sets may become more expensive after migration; tasks blocked on I/O may require different treatment from CPU-ready strands. Real frameworks also impose priority, affinity, cancellation, and fairness policies. Analysis should distinguish a theoretical expected bound from measured stealing frequency, victim selection, and throughput.

Dependence Patterns and Parallel Loops

A loop is safely parallelizable when iterations are independent or when inter-iteration dependencies can be expressed through a valid parallel primitive. Read-only access to a shared array is often benign; writing distinct array slots may also be independent, provided aliasing and memory consistency are handled. In contrast, state[i] = f(state[i-1]) has a loop-carried dependency unless an algebraic transformation changes the computation.

Dependencies can be true (read-after-write), anti (write-after-read), or output (write-after-write). Some apparent dependencies arise only from a storage reuse choice and can be removed by renaming temporaries; true data-flow dependencies cannot be removed without changing the algorithm or semantics. The legality of a loop transformation should be demonstrated, not assumed from the absence of explicit locks.

def disjoint_chunk_coverage(length, chunk_size):
    spans = [(i, min(i + chunk_size, length))
             for i in range(0, length, chunk_size)]
    flattened = [j for lo, hi in spans for j in range(lo, hi)]
    return spans, flattened == list(range(length))

ranges, valid = disjoint_chunk_coverage(17, 5)
assert valid and ranges[-1] == (15, 17)

Data Races, Ordering, and Correctness

A data race occurs when conflicting memory accesses are not properly ordered according to the language’s concurrency rules, typically involving at least one write. Such a race can invalidate a proof that assumes each element is processed exactly once or that an accumulation reads the latest value. The precise semantics depend on the programming language and memory model; invoking “eventual consistency” does not repair an undefined or incorrectly synchronized shared-memory program.

Correctness analysis starts with invariants such as unique ownership of output slots, monotonic work queues, or a single successful compare-and-swap claim per graph vertex. Then it identifies happens-before relations or atomic operations required to preserve those invariants. Once correctness is established, performance analysis can count atomics, lock acquisitions, retries, fences, and failed claims. A program that occasionally returns an incorrect result has no useful speedup guarantee for the original problem.

Atomics, Locks, Reductions, and Ownership

Atomic read-modify-write operations can protect a shared counter, but many workers contending on one location may serialize. Locks can establish multi-operation invariants but also create waiting and deadlock risks. Privatization assigns independent partial state to each worker, followed by a structured reduction; it often replaces Θ(n) contended updates with Θ(n) local work plus a much smaller number of combination steps.

For correctness, the combine operator must be associative under the intended arithmetic semantics, and an identity element must exist for empty partitions. Floating-point addition is only approximately associative, so a tree reduction can change the last bits of the result even with no race. A reproducibility contract may require a prescribed reduction tree, compensated summation, or deterministic ordering rather than arbitrary scheduling.

Barriers, Joins, and Critical-Path Inflation

A barrier prevents participants from passing a point until a synchronization condition holds. It is necessary for algorithms such as a multi-round prefix scan when the next round needs a complete snapshot of the previous round. But barriers can amplify imbalance: the last worker determines when all others resume. Even if each worker performs equal total work, skewed phase costs can cause repeated waiting.

Count barriers separately from arithmetic when evaluating short phases. A model with K global rounds, per-round latency L, and work W may have time at least Ω(KL), in addition to work and span bounds. Some frameworks have implicit barriers at loop boundaries; others allow asynchronous tasks. Removing a barrier is valid only if the dependency proof still holds. The OpenMP synchronization specification provides concrete language for these constraints.

False Sharing and Coherence Traffic

False sharing occurs when workers modify independent variables that occupy the same cache-coherence unit. The variables may be logically independent and the program race-free, yet their cache line repeatedly migrates among cores. This increases latency and memory-system traffic without necessarily adding operations to the abstract algorithm. Aligning or padding worker-local counters can sometimes relieve the problem.

Distinguish false sharing from true sharing, where workers genuinely contend on one logical value. Padding cannot remove a required atomic increment to a single shared total; a different algorithmic aggregation structure is needed. Cache-line sizes and placement depend on the platform, so padding should be evidence-driven. A test reporting identical scalar W and S but very different measured times may be observing coherence and locality rather than a contradiction of the model.

Locality, NUMA, and Memory Bandwidth

On non-uniform memory access (NUMA) systems, data access latency and bandwidth can depend on the location of both the worker and the allocated pages. A parallel algorithm that repeatedly reads distant memory may lose its expected benefit. Cache locality, layout, and memory affinity become part of the performance analysis even though the computational DAG is unchanged.

For a bandwidth-bound streaming kernel that transfers D bytes over a memory interface with sustainable bandwidth b, a fundamental time lower bound is about D/b before additional overlap and hierarchy complications. Increasing worker count after bandwidth saturation yields little benefit. Use measured bytes transferred and hardware counters when possible; the number of source-level array reads does not always equal traffic at DRAM because caches may retain and combine data.

SIMD, SIMT, and GPU Execution

Single-instruction multiple-data (SIMD) operations apply one vector instruction to multiple data lanes. GPU-style single-instruction multiple-thread (SIMT) execution schedules many threads in groups, with masks or control-flow mechanisms handling divergent branches. The abstract work-span pair remains useful but does not account for occupancy limits, registers, shared-memory capacity, launch latency, or memory coalescing.

On GPUs, adjacent threads accessing adjacent addresses can often combine memory requests into fewer transactions; scattered loads can increase traffic. Branch divergence inside a hardware warp may reduce active-lane utilization. Optimization may deliberately increase arithmetic work to improve locality or occupancy. Report effective bandwidth, launch overhead, and occupancy assumptions separately from arithmetic complexity. See NVIDIA’s CUDA Best Practices Guide.

Distributed-Memory Parallelism and Message Passing

In distributed memory, workers exchange data explicitly rather than reading one globally shared address space. An algorithm’s communication volume, number of messages, topology, congestion, and synchronization often matter as much as its local computation. A standard illustrative message model is α + βm for a message of m bytes: α is startup latency, β is per-byte transfer time. This is not an end-to-end network guarantee; routing, overlap, collective algorithms, and contention add conditions.

For example, sending 1024 separate one-kilobyte messages may pay 1024 startup costs, whereas batching them into one appropriately sized message pays startup once, while total bytes are approximately unchanged. Batching may increase latency for the first item or require buffering, so it is not always beneficial. A parallel algorithm designer should optimize the complete latency-throughput contract, not just minimize the number of local instructions.

def message_time_us(message_count, total_bytes,
                    startup_us=3.0, us_per_byte=0.0002):
    if min(message_count, total_bytes) < 0:
        raise ValueError('nonnegative traffic required')
    return message_count * startup_us + total_bytes * us_per_byte

separate = message_time_us(1024, 1024 * 1024)
batched = message_time_us(1, 1024 * 1024)
assert batched < separate
assert abs(separate - (1024*3 + 1024*1024*0.0002)) < 1e-9

Communication Lower Bounds and Collective Operations

A reduction across P distributed workers requires combining information originating on multiple workers. With bounded fan-in and a tree-like communication model, the number of dependent combination rounds is Ω(log P). For a small scalar, a balanced tree can achieve O(log P) message rounds, subject to topology and collective implementation. For very large arrays, communication volume and bandwidth may dominate; ring, recursive doubling, and tree collectives have different startup and transfer characteristics.

The correct model names how many bytes each participant sends and receives, the network’s routing and congestion assumptions, and whether communication overlaps computation. Do not assert a universal αlog P + βm cost for all collective implementations; each algorithm has its own message-volume and round structure. Collective libraries may select different strategies dynamically by message size and processor count.

Parallel Reduction: Associativity as the Key Contract

A reduction combines elements using an associative binary operator ⊕ and an identity e. A sequential left fold over n inputs has W = Θ(n) and S = Θ(n). A balanced binary reduction has W = n−1 combines and S = ⌈log₂ n⌉ for n ≥ 1 in the usual unit-cost binary-tree model. The depth bound follows because a bounded-fan-in gate at depth d can depend on at most 2ᵈ leaves.

Addition of exact integers, minimum, maximum, and Boolean conjunction are familiar candidates. Operators such as subtraction, string concatenation with costly operand copying, or floating-point addition under bitwise reproducibility requirements need extra scrutiny. A mathematical associative operator might not be constant-cost for growing operands. The cost of each combine and the permitted numeric contract must be stated before adopting Θ(n) work.

def tree_sum(values):
    level = list(values)
    if not level:
        return 0, 0, 0
    depth = 0
    while len(level) > 1:
        level = [level[i] + level[i + 1] if i + 1 < len(level) else level[i]
                 for i in range(0, len(level), 2)]
        depth += 1
    return level[0], len(values) - 1, depth

assert tree_sum([1, 2, 3, 4, 5]) == (15, 4, 3)
assert tree_sum([42]) == (42, 0, 0)
assert tree_sum([]) == (0, 0, 0)

Reduction Tree Shape and Processor Budget

For a balanced tree on n inputs, P processors cannot always complete every level in one step. The ideal bounded-fan-in cost is W = Θ(n), S = Θ(log n), hence T_P = Ω(n/P + log n) and an appropriate greedy execution offers a matching O-bound. For n = 1024 and P = 16, the work lower bound is about 1023/16 ≈ 64 operations while the span is ten levels. Processor count rather than depth dominates in that example.

Distributed reductions may need log P communication phases, while SIMD reductions may use lane shuffles or shared-memory staging. If n is not a power of two, unpaired elements are propagated to the next level or padded with the identity. Padding changes the exact number of operations if performed naively, but not the asymptotic work when padded to the next power of two.

Prefix Scan: From Sequential Accumulation to Parallel Primitive

A prefix scan computes every prefix aggregate, not only the final reduction. For inputs x₀, …, xₙ₋₁, an inclusive sum scan returns [x₀, x₀+x₁, …, ∑xᵢ]; an exclusive scan returns the aggregate of items strictly before each position, beginning with the identity. Scans are building blocks for parallel filtering, compaction, counting, radix operations, and segmented computation.

The Hillis–Steele doubling algorithm completes O(log n) synchronous rounds, but every round may update Θ(n) positions, giving O(n log n) work and O(log n) span in the ideal model. This illustrates why a small span alone does not establish work efficiency. Copying the previous round into a snapshot prevents simultaneous in-place updates from corrupting the round semantics.

def hillis_steele_scan(data):
    out = list(data)
    offset = 1
    while offset < len(out):
        old = out[:]
        out = [old[i] + (old[i-offset] if i >= offset else 0)
               for i in range(len(out))]
        offset *= 2
    return out

assert hillis_steele_scan([3, 1, 4, 1, 5]) == [3, 4, 8, 9, 14]
assert hillis_steele_scan([]) == []

Work-Efficient Scan: Upsweep and Downsweep

A balanced-tree scan, often associated with Blelloch’s upsweep/downsweep construction, first builds partial reductions and then distributes exclusive prefixes. On a power-of-two padded tree with n leaves, the upsweep and downsweep together perform Θ(n) combines and have Θ(log n) span. The downsweep replaces the root accumulator with the identity; at each node, the left child inherits the parent prefix and the right child receives the parent prefix combined with the left subtree total.

For arbitrary n, pad to the next power of two with the identity, preserving the original n results. This may perform at most a constant factor more work. An exclusive scan can be converted into an inclusive scan by combining each exclusive prefix with its own input. A correct implementation must also state whether it uses associative integer arithmetic, floating-point semantics, or another monoid. The following sequential Python simulation exposes the parallel tree stages for inspection; its wall-clock running time is not the theoretical parallel span.

def blelloch_exclusive_sum_scan(values):
    n = len(values)
    if n == 0:
        return []
    m = 1 << (n - 1).bit_length()
    tree = list(values) + [0] * (m - n)
    step = 2
    while step <= m:
        half = step // 2
        for end in range(step - 1, m, step):
            tree[end] += tree[end - half]
        step *= 2
    tree[m - 1] = 0
    step = m
    while step >= 2:
        half = step // 2
        for end in range(step - 1, m, step):
            t = tree[end - half]
            tree[end - half] = tree[end]
            tree[end] += t
        step //= 2
    return tree[:n]

assert blelloch_exclusive_sum_scan([3, 1, 4, 1, 5]) == [0, 3, 4, 8, 9]
assert blelloch_exclusive_sum_scan([9]) == [0]
assert blelloch_exclusive_sum_scan([]) == []

Parallel Map, Filter, and Stable Compaction

A pure map applies an independent function to every element. With constant-cost function evaluations and independent output slots, its ideal work is Θ(n) and its ideal span is O(1). A filter must compute predicates and pack matching elements into an output sequence. For a stable filter, one standard method computes a 0/1 flag for each input, scans the flags to obtain output positions, and scatters selected values into unique destinations.

The scan-based stable filter uses Θ(n) work and O(log n) span under the work-efficient scan model, not O(1) span. The proof relies on each selected item receiving a distinct output index, eliminating conflicting writes. The output length k can be determined by the total flag sum. If an implementation dynamically allocates exactly k elements, allocation and memory-transfer costs must be included in the machine-level analysis.

def stable_filter_with_prefix(data, predicate):
    flags = [1 if predicate(x) else 0 for x in data]
    starts = blelloch_exclusive_sum_scan(flags)
    count = sum(flags)
    result = [None] * count
    for x, keep, pos in zip(data, flags, starts):
        if keep:
            result[pos] = x
    return result

assert stable_filter_with_prefix([8, 1, 6, 3, 4, 7],
                                 lambda x: x % 2 == 0) == [8, 6, 4]
assert stable_filter_with_prefix([], lambda x: True) == []

Parallel Divide and Conquer: Two Recurrences

In a forked divide-and-conquer algorithm, work recurrences add both child computations, while span recurrences use the slower branch. Consider a balanced binary tree aggregate that performs one constant-time combine at every internal node: W(n)=2W(n/2)+Θ(1)=Θ(n) and S(n)=S(n/2)+Θ(1)=Θ(log n). The resulting average parallelism is Θ(n/log n).

Now consider a divide-and-conquer method whose two recursive halves may execute together but whose parent executes a sequential Θ(n) combine stage: W(n)=2W(n/2)+Θ(n)=Θ(n log n) and S(n)=S(n/2)+Θ(n)=Θ(n). The algorithm’s average parallelism is only Θ(log n). It has many recursive calls but cannot exploit processor counts proportional to n without redesigning the combine stage. The recurrence must therefore account for the critical path of all nonrecursive work.

Parallel Merge Sort and the Sequential-Merge Bottleneck

Ordinary merge sort splits n items into two subproblems, sorts them, and merges them. If the halves are sorted in parallel but each merge is a sequential linear pass, total work remains Θ(n log n), while the span satisfies S(n)=S(n/2)+Θ(n)=Θ(n). The theoretical parallelism is Θ(log n), meaning simply forking recursive calls does not yield scalable performance on thousands of processors.

A parallel merge can reduce span by selecting pivots, binary-searching their ranks in the other sorted sequence, and recursively merging independent subranges. A straightforward balanced implementation performs O(n) merge work and O(log² n) merge span in an ideal model when split costs are logarithmic; across merge-sort levels this yields O(n log n) work and O(log³ n) span for a corresponding basic method. Specialized approaches can improve these bounds. Claims of O(log² n) whole-sort span require the appropriate stronger merge construction and proof.

def sequential_merge_count(left, right):
    i = j = 0
    out = []
    comparisons = 0
    while i < len(left) and j < len(right):
        comparisons += 1
        if left[i] <= right[j]:
            out.append(left[i]); i += 1
        else:
            out.append(right[j]); j += 1
    return out + left[i:] + right[j:], comparisons

merged, comparisons = sequential_merge_count([1, 4, 7], [2, 3, 8])
assert merged == [1, 2, 3, 4, 7, 8]
assert 3 <= comparisons <= 5

Parallel Quicksort and Partitioning

Quicksort can recursively process its left and right partitions in parallel, but a sequential Θ(n) partition at each level limits its span even when pivots are well balanced. For a consistently balanced partition, the work is Θ(n log n) and the span obeys S(n)=S(n/2)+Θ(n)=Θ(n). A work-efficient parallel partition based on prefix sums and disjoint output destinations can reduce per-level span to O(log n) under ideal primitives.

With balanced partitions, that yields O(log² n) span across O(log n) levels. For randomized pivots, expected work is Θ(n log n); worst-case partitions can still generate Θ(n²) work and Θ(n) or worse span depending on the partition implementation. Expected-depth arguments require explicit probability assumptions. On real machines, partition writes, temporary buffers, cache locality, and task thresholds determine whether the theoretical improvement materializes.

Parallel Matrix Multiplication

For classical dense n × n matrix multiplication, each output entry is a sum of n products, and there are n² independent output entries. The arithmetic work is Θ(n³). If each dot product is evaluated through a balanced reduction with sufficient parallelism, the arithmetic DAG can have O(log n) span, ignoring memory traffic and assuming every scalar multiply/add is constant-cost. A straightforward realization may require substantial temporary storage if all partial products are materialized simultaneously.

On a real CPU or GPU, communication and data reuse usually dominate naive asymptotic span. Tiling improves locality by reusing input blocks; reduction layouts and memory bandwidth constrain throughput. Different algorithms, including Strassen-type multiplication, change the arithmetic work and recursion structure but introduce their own numerical and storage costs. The Cache and External-Memory Complexity article analyzes block transfers; the present analysis supplies the dependency-side perspective.

Wavefront Dynamic Programming

Consider a dynamic program over an m × n grid in which each cell depends only on its upper and left neighbors. Cells in the same anti-diagonal i+j = k do not depend on each other and may execute in parallel. There are Θ(mn) cells, and the longest dependency path from the top-left to bottom-right contains Θ(m+n) cells. Under constant-time cell updates and unlimited workers, W = Θ(mn) and S = Θ(m+n).

The maximum wavefront width is min(m,n), limiting effective processor count. Memory can be reduced with row-based or diagonal buffers, though smaller storage may restrict which outputs can be retained or replayed. If the cell recurrence has diagonal dependencies, the wavefront schedule must be recomputed to ensure every predecessor lies on an earlier wavefront. This model appears in edit distance, sequence alignment, matrix chain variants, and grid-path calculations.

def wavefront_path_counts(rows, cols):
    grid = [[0]*cols for _ in range(rows)]
    for diagonal in range(rows + cols - 1):
        for i in range(rows):
            j = diagonal - i
            if 0 <= j < cols:
                grid[i][j] = (1 if (i,j) == (0,0) else
                              (grid[i-1][j] if i else 0) +
                              (grid[i][j-1] if j else 0))
    return grid

assert wavefront_path_counts(3, 4)[-1][-1] == 10
assert wavefront_path_counts(1, 1) == [[1]]

Breadth-First Search and Frontier-Level Parallelism

Breadth-first search (BFS) visits a graph in increasing distance layers from a source. A level-synchronous parallel algorithm expands all vertices of the current frontier, visits their outgoing edges, and marks newly discovered vertices atomically to prevent duplicate insertion. With suitable adjacency storage, each reached vertex may be expanded once, giving O(V+E) total traversal work for the reachable subgraph under an appropriate edge-processing accounting.

The number of synchronous levels is the source eccentricity plus one, and depends on graph diameter rather than just V. However, reporting span as O(D) without qualification hides the time needed to compact the next frontier and coordinate concurrent claims. Under work-efficient scans and reductions, a typical simplified analysis may attach O(log(V+E)) depth per level, yielding an upper bound on the order of O(D log(V+E)), with model and frontier details stated. High-degree hubs and sparse frontiers create additional scheduling issues.

from collections import deque

def bfs_frontiers(adjacency, source):
    visited = {source}; frontiers = [[source]]
    while frontiers[-1]:
        nxt = []
        for v in frontiers[-1]:
            for w in adjacency.get(v, []):
                if w not in visited:
                    visited.add(w); nxt.append(w)
        if nxt:
            frontiers.append(nxt)
        else:
            break
    return frontiers

graph = {0:[1,2],1:[3],2:[3,4],3:[5],4:[5],5:[]}
assert bfs_frontiers(graph, 0) == [[0], [1, 2], [3, 4], [5]]

Graph Frontiers, Atomics, and Irregular Work

The theoretical cost of parallel graph processing is closely tied to representation. An adjacency-list BFS can process each edge once or a bounded number of times, whereas scanning every matrix row of length V for each visited vertex can take Θ(V²) work. A graph with one hub of degree Θ(E) may produce an enormous task for one worker, while a partition based only on vertex count leaves other workers underused. Edge-based partitioning, degree-aware scheduling, and work-stealing can improve balance.

When two frontier vertices discover the same neighbor, exactly one worker must claim it if unique work queues are required. Compare-and-swap or a suitable atomic test-and-set can enforce that invariant. The number of unsuccessful attempts and cache-coherence effects may affect measured runtime even if asymptotic edge traversal work remains O(V+E). Direction-optimizing variants and graph-specific indexes change the cost model and should not inherit a generic BFS span guarantee automatically.

Parallel Pointer Jumping and List Ranking

Pointer jumping repeatedly replaces a node’s successor pointer with its successor’s successor, doubling the traversed distance each round. In a linked list, the number of rounds is O(log n) when updates use snapshots so all nodes in a round read the previous state. A direct implementation touches Θ(n) nodes per round, so work is O(n log n) and span is O(log n) in an ideal model with concurrent accesses.

The result illustrates the work-depth tradeoff: the sequential list traversal takes O(n) work, so this elementary pointer-jumping algorithm sacrifices work efficiency to reduce depth. More sophisticated list-ranking algorithms reduce expected or deterministic work under stronger assumptions. Care is needed with memory-access rules: many nodes may read the same successor in a round, so the concurrent-read model matters, and an in-place mutation without snapshots could yield inconsistent distances.

def pointer_jump_distances(successor):
    # Acyclic successor array terminating at -1; distance to terminal.
    n = len(successor)
    nxt = list(successor)
    distance = [1 if x != -1 else 0 for x in nxt]
    while any(x != -1 for x in nxt):
        old_nxt, old_d = nxt[:], distance[:]
        for i, j in enumerate(old_nxt):
            if j != -1:
                distance[i] = old_d[i] + old_d[j]
                nxt[i] = old_nxt[j]
    return distance

assert pointer_jump_distances([1,2,3,-1]) == [3,2,1,0]
assert pointer_jump_distances([-1]) == [0]

Parallel Sorting: Work, Depth, and Data Movement

Parallel sorting algorithms are analyzed along three distinct axes: comparisons and data movement (work), dependency rounds (span), and communication between processing units. An ordinary comparison sort can attain Θ(n log n) total work, but distributing an entire sorted sequence may still require costly global permutations or exchanges. Sorting networks such as bitonic networks have O(log² n) parallel compare-exchange depth with O(n log² n) comparators in common constructions, making them regular but not work-optimal compared with Θ(n log n) sequential lower bounds.

Parallel merge sort, parallel sample sort, radix strategies, and distributed sorting often make different assumptions about key range, stability, memory budget, and output distribution. A theoretical O(log² n) depth for a sorting network does not imply that every compare-exchange stage fits in one machine cycle. At scale, synchronization, routing, shuffles, and writes can dominate. Refer to Sorting Algorithm Analysis for sequential and parallel comparison of sorting families.

Parallel Search and Speculation

A search over n independent candidates can evaluate predicates concurrently, with Θ(n) total work and ideal O(1) evaluation span when output is a Boolean OR and all predicate evaluations are constant cost. A final bounded-fan-in reduction to return whether any match exists adds O(log n) span. If the contract requires the first matching index under a defined order, a parallel min-reduction over matching indices can produce the index with O(n) work and O(log n) span.

Early termination affects expected work and latency. A sequential scan stops at the first match and may have substantially lower expected work on easy distributions; running all candidates in parallel can waste work even if completion latency falls. Cancellation is not free, and speculative tasks may already have executed. A good comparison records early-exit behavior, search distribution, predicate costs, and the exact result semantics rather than assuming an all-at-once scan dominates.

Randomized Parallel Algorithms and Expectations

Randomized work stealing, randomized pivot choice, and randomized load balancing often yield expected cost bounds. Distinguish randomness over an algorithm’s internal choices from a distribution over inputs. When stating E[W] or E[TP], identify the random variable and whether the guarantee holds for each fixed input or only on average over a workload distribution. Expected time is not a deterministic worst-case maximum.

A useful parallel algorithm may have excellent expected balance but still occasionally generate a long critical path. Concentration bounds or explicit high-probability claims require the corresponding independence or bounded-difference assumptions. For a task scheduler that consumes random choices, reproducible testing should record seeds and scheduling conditions while acknowledging that a fixed seed does not necessarily fix every interleaving. The related specialist treatment is Randomized Algorithm Analysis.

Dependency-Aware Arithmetic Scheduling

Expression evaluation is a basic parallel scheduling problem. For a computation such as (a+b) × (c+d), the two additions are independent and can occur in parallel; multiplication waits for both. With unit-time operations, W = 3 and S = 2. A single processor requires three operations, while two processors can finish in two stages. For longer arithmetic expressions, balancing the expression tree may reduce depth when the operator permits reassociation.

Associativity conditions are central: real-number algebra permits many reorderings that finite-precision floating-point arithmetic may not preserve bitwise. Expressions with side effects, overflow-sensitive arithmetic, or error requirements cannot be transformed based solely on an abstract algebraic law. A valid parallelization proof must establish semantic equivalence under the actual language and numeric contract.

def expression_dag_cost(left_depth, right_depth):
    # Two independent subexpressions followed by one combine operation.
    return 1 + max(left_depth, right_depth)

assert expression_dag_cost(1, 1) == 2
assert expression_dag_cost(4, 2) == 5

Static Scheduling, Dynamic Scheduling, and Load Balance

Under static scheduling, input regions are assigned to workers before execution. This minimizes runtime decisions when workloads are uniform, but can leave processors idle when task durations vary. Dynamic scheduling assigns work as workers become available, improving balance at the price of queue contention, metadata operations, and possibly worse locality. Hybrid approaches use coarse static partitions with local queues or stealing for exceptional work.

The right unit of balance is task cost, not task count. Giving each worker ten graph vertices can be deeply unbalanced if one worker owns a high-degree hub. In data-processing systems, partition sizes and record decoding times may differ. A practical analysis models the largest assigned load, the sum of all loads, and the scheduler’s ability to redistribute work. The ideal lower bound is at least total work divided by P and at least the largest indivisible task.

def greedy_list_schedule(durations, workers):
    if workers < 1 or any(x < 0 for x in durations):
        raise ValueError('invalid inputs')
    loads = [0] * workers
    for d in durations:
        j = min(range(workers), key=lambda i: loads[i])
        loads[j] += d
    return loads

assert greedy_list_schedule([8, 1, 1, 1], 2) == [8, 3]
assert max(greedy_list_schedule([8, 1, 1, 1], 2)) >= 8

Saturation: More Threads Are Not More Bandwidth

A bandwidth-bound kernel often scales only while memory channels, caches, and queues have unused capacity. Once the sustainable transfer rate is saturated, launching additional workers may worsen performance through context switching, cache thrashing, or contention. This occurs despite abundant theoretical parallelism W/S: the work-span DAG assumes computational resources that the actual memory system cannot provide at arbitrary width.

A practical throughput estimate uses max(compute_work / peak_compute_rate, bytes_transferred / sustainable_bandwidth) as a lower-bound style diagnostic, not a complete runtime formula. The terms refer to compatible units and an identified hierarchy boundary. The full analysis also includes latency for dependent loads, synchronization, and pipeline occupancy. Never infer realized bandwidth simply from the advertised memory clock; it must be measured with a representative access pattern.

Arithmetic Intensity and the Roofline Perspective

Arithmetic intensity is useful arithmetic operations per byte transferred at a specified memory boundary. The roofline perspective places an attainable performance ceiling at the smaller of peak compute throughput and sustainable memory bandwidth times arithmetic intensity. Two algorithms with equal W and S may occupy opposite sides of that ceiling because one repeatedly reuses cached operands while the other streams or scatters data.

For example, if a kernel performs 2 × 10⁹ operations while transferring 10⁹ bytes from DRAM, its arithmetic intensity is 2 operations/byte. At 100 GB/s sustainable bandwidth, its bandwidth-based ceiling is about 200 billion operations/s, but actual execution may be much slower because of instruction dependencies, access inefficiency, or synchronization. The illustrative rate does not imply that a real program can reach the bound.

def roofline_ceiling(peak_ops_per_sec, bandwidth_bytes_per_sec,
                     ops, transferred_bytes):
    if min(peak_ops_per_sec, bandwidth_bytes_per_sec) <= 0:
        raise ValueError('positive machine rates required')
    if ops < 0 or transferred_bytes <= 0:
        raise ValueError('invalid workload')
    return min(peak_ops_per_sec,
               bandwidth_bytes_per_sec * (ops / transferred_bytes))

assert roofline_ceiling(1_000e9, 100e9, 2e9, 1e9) == 200e9

Memory Capacity, Replication, and Parallel Space

Many parallel algorithms improve span by keeping partial results or copies of data in memory. A reduction with one partial accumulator per worker uses O(P) temporary state; a naive matrix-multiplication realization that materializes all products can use Θ(n³) storage; a blocked realization can reuse much smaller buffers. Memory usage must be analyzed alongside work and span because exceeding memory capacity can trigger paging or distributed spills that undermine the intended speedup.

Distinguish peak auxiliary storage from input/output storage and from replicated read-only copies. On a distributed cluster, per-worker memory and total aggregate memory are different resources. Copying a reference table to every worker may eliminate network queries but multiply total storage by P. A rigorous comparison records at least peak local storage, aggregate storage, and the data movement needed to populate replicated or partitioned state.

Numerical Reproducibility and Reduction Order

Exact integer addition without overflow is associative, but floating-point addition generally is not. Different parallel reduction trees can therefore produce different rounding histories. If an application requires bitwise reproducibility, specify a fixed reduction tree or a dedicated reproducible summation method. If numerical tolerance is permitted, specify the error metric and acceptable bounds. Neither policy should be left to unspecified task completion order.

For the list [10¹⁶, 1, −10¹⁶], a left-to-right float sum can lose the unit increment, while a different grouping or a numerically more careful sum can retain it. This is not evidence of a race: the program can be fully synchronized and still produce different valid roundoff results under an approximate arithmetic contract. See also the constraints on reordering signed zeros, NaNs, and infinities in a particular numeric model.

import math
values = [1e16, 1.0, -1e16]
left_fold = 0.0
for value in values:
    left_fold += value
assert left_fold == 0.0
assert math.fsum(values) == 1.0
assert (values[0] + values[2]) + values[1] == 1.0

Profiling Parallel Programs Without Misreading Timings

Benchmark wall-clock completion, not the sum of CPU times, when judging end-to-end speedup. A parallel task may consume 80 CPU-seconds across workers while finishing in 12 elapsed seconds. Depending on measurement APIs, time inside a thread pool and time launching child processes may be counted differently. Record warm-up policy, input size, processor affinity, core frequency, thermal throttling, I/O boundaries, and worker counts.

Use repeated runs and distributions rather than reporting only the best outcome. Record work processed and bytes transferred, not merely a “threads per second” value. If possible, separate data preparation and final result collection, but also report a full end-to-end figure so setup is not hidden. A trace of runnable tasks, idle time, cache misses, and lock contention can help explain a performance gap between an O(W/P + S) model and actual wall time.

Strong-Scaling and Weak-Scaling Experimental Design

A strong-scaling experiment fixes one input and measures TP across processor counts such as P = 1, 2, 4, 8, 16, and 32. It plots speedup and efficiency, annotates memory bandwidth saturation, and checks whether task scheduling is comparable. A weak-scaling experiment increases input size with P to maintain a declared per-worker work budget and then measures how elapsed time changes. Both require multiple repetitions and disclosure of hardware allocation.

Instrument runtime from a well-defined beginning to a well-defined end. If the benchmark is distributed, identify whether input loading, broadcasts, checkpointing, and result writes are inside the timed region. For GPUs, distinguish kernel-only measurements from host-to-device transfers and launch overhead. When comparing different algorithms, report total work, numeric accuracy, and allocation cost as well as time. A faster answer is not equivalent if its correctness contract changes.

def speedup_table(baseline, measured):
    return [(p, baseline / t, baseline / (p*t))
            for p, t in sorted(measured.items())]

Amdahl-Compatible Overhead Models

A measured runtime model may start from T_P = T_seq[s + (1−s)/P] + H(P,n), where H represents overhead that is not already included in Tseq. It is legitimate to use such a model for forecasting, provided its parameters are fitted against multiple measurements and the workload regime is declared. It does not follow that H(P,n) is nonnegative under every benchmark definition, since memory locality or implementation changes may improve some phases.

Suppose Tseq = 100 seconds, s = 0.08, and P = 16. The ideal Amdahl runtime is 8 + 92/16 = 13.75 seconds. An observed 18 seconds may include an additional 4.25 seconds attributed to launch, contention, memory, and imbalance—but decomposition requires profiling; subtracting the ideal formula is not proof of any particular cause. The model is a hypothesis to test, not a breakdown of measured hardware events.

def amdahl_runtime(seq_seconds, serial_fraction, processors,
                   overhead_seconds=0):
    return seq_seconds * (serial_fraction +
                          (1-serial_fraction)/processors) + overhead_seconds

assert abs(amdahl_runtime(100, .08, 16) - 13.75) < 1e-12
assert amdahl_runtime(100, .08, 16, 4.25) == 18.0

Karp–Flatt Serial Fraction as a Diagnostic

For P > 1 and observed speedup SP on a fixed problem, the Karp–Flatt metric is e = (1/S_P − 1/P)/(1 − 1/P). It estimates an effective serial fraction in the simple Amdahl form, combining true serial work and overhead effects into one empirical quantity. If e changes with P, it can signal scheduling, communication, or bandwidth effects that a fixed serial-fraction model misses.

The metric is not a proof that precisely e percent of source code cannot be parallelized. It may even yield values outside the textbook [0,1] range when observed speedup is superlinear or otherwise inconsistent with the simple model. Such values require investigation of baseline fairness, caches, workload changes, and measurement noise, not artificial truncation without explanation.

def karp_flatt(speedup, p):
    if p <= 1 or speedup <= 0:
        raise ValueError('P > 1 and positive speedup required')
    return (1/speedup - 1/p)/(1 - 1/p)

assert abs(karp_flatt(6.4, 16) - 0.10) < 1e-12

Isoefficiency and the Scalability of Problem Size

The isoefficiency perspective asks how problem work W(n) must increase with processor count P to preserve a desired efficiency. In the ideal work-span bound, efficiency approaches one when W/P is much larger than S; equivalently, P·S(n)/W(n) should remain small. This only captures algorithmic overhead implicit in the span, not all communication and scheduling costs of a machine.

For a work-efficient reduction with W(n)=Θ(n) and S(n)=Θ(log n), a rough criterion for maintaining high efficiency is n = Ω(P log n). By contrast, an algorithm with W(n)=Θ(n log n) and S(n)=Θ(n) has average parallelism Θ(log n), so simply enlarging n often gives much slower growth in usable processor count. Full isoefficiency analysis adds overhead terms and solves for input growth under the chosen efficiency target.

Proving Parallel Algorithm Correctness

Parallel correctness proofs should identify the sequential specification, allowed reordering, independence of task effects, and required synchronization. For a tree reduction, an induction on subtree size shows that each internal node combines exactly the elements of its subtree. For prefix scan, an invariant at each upsweep level states that a node stores the total of a known interval; the downsweep invariant states that a node receives the aggregate of all elements preceding its interval.

For parallel graph traversal, prove that a vertex is claimed at most once and that each discovered vertex has a valid source path. For wavefront dynamic programming, prove every dependency lies on an earlier wavefront and all cells on a wavefront are independent. Proving a parallel algorithm correct does not establish its span automatically: a separate DAG analysis must count synchronization rounds and the longest chain of operations.

Analyzing the Cost of One Parallel Primitive

A common error is to label a high-level primitive such as scan, sort, or all_reduce as O(1) because it appears as one call. Complexity depends on the primitive’s contract and implementation. An n-element tree reduction has O(log n) depth in the ideal bounded-fan-in model; an implementation with one serial memory allocator or a barrier per stage can cost more. The cost of a library call is not determined by its syntactic size.

When composing parallel primitives, combine their work additively. Their spans add when one must finish before the next begins; independent branches contribute a maximum. For example, a stable filter whose flags precede a scan and a scatter has W = W_flags + W_scan + W_scatter = Θ(n) and S = S_flags + S_scan + S_scatter = O(log n) under ideal synchronous stages. Include the predicate’s own cost if nonconstant.

A Practical Selection Framework

A sound design review compares candidate algorithms in a repeatable sequence. First determine the best sequential baseline and its resource use. Second derive W and S, including the cost of each parallel primitive and any changed data layout. Third compute the work and span lower bounds for the available P; reject designs with obvious work explosion or an inadequate W/S ratio. Fourth add the machine-specific data movement, worker startup, synchronization, and capacity constraints.

  1. State the exact result contract and arithmetic/reproducibility rules.
  2. Build the dependency DAG and derive work and span by induction or recurrence.
  3. Select the machine model: PRAM, task DAG, SIMT, or distributed message passing.
  4. Estimate theoretical T_P bounds and identify processor saturation.
  5. Account for memory capacity, communication rounds, and bandwidth.
  6. Choose grain size and load-balancing policy, then measure representative workloads.
  7. Explain discrepancies with traces, counters, and controlled experiments.

The framework favors work-efficient, low-span designs when all else is equal, but does not forbid deliberate extra work to reduce critical latency. Parallelism is one resource trade-off, not a universal performance objective.

Worked Investigation 1: Amdahl Limit for a Fixed Financial Batch

A nightly processing batch requires 120 seconds sequentially, including a 15-second order-dependent validation stage and 105 seconds of independent record transformations. Assume only the transformation stage parallelizes perfectly. With eight workers the model predicts T₈ = 15 + 105/8 = 28.125 seconds, so speedup is 120/28.125 ≈ 4.27 and efficiency approximately 0.533. With infinitely many workers the 15-second stage caps speedup at eight.

If 32 workers finish the real batch in 25 seconds, their observed performance should be compared against the model’s prediction of 15 + 105/32 = 18.28125 seconds. The gap may reflect data movement, logging, queues, or input skew, but cannot be assigned to one without instrumentation. Redesigning the validation stage might have greater impact than adding workers, provided the original ordering contract remains intact.

Worked Investigation 2: Tree Reduction on 256 Sensors

A monitoring system needs the maximum of 256 sensor readings. An exact maximum is associative, and a balanced binary tree performs 255 comparisons with span eight unit comparison levels. On eight ideal workers, the lower bound is max(255/8, 8) = 31.875 time units, while Brent gives an upper bound of 255/8 + 8 = 39.875. These are coarse ideal bounds; an integral schedule necessarily takes whole steps.

A sequential linear maximum requires 255 comparisons and can benefit from early caching or vectorization, but its accumulator loop has a 255-operation dependency chain under the simple scalar model. The tree method creates independent partial maxima, potentially requiring an intermediate buffer and synchronization after levels. In a distributed version, communication is additional; a sensor network’s links do not behave like shared registers.

Worked Investigation 3: Filtering Ten Million Records

Suppose ten million records must be filtered while preserving their original order. An embarrassingly parallel predicate evaluation produces a Boolean flag per record, but stable compaction requires determining unique output positions. A scan-based design uses Θ(n) total work and O(log n) ideal span for fixed-cost predicates, plus output writing. A naive technique that lets every selected record count all earlier selections would do Θ(n²) work even if many counts were performed simultaneously.

At n = 10⁷, the output size k changes memory requirements and write volume. A two-pass scheme can count selected records before allocating the final array, but an extra pass may increase memory traffic. The design review should compare required stability, available RAM, predicate cost, and whether records can be streamed in batches. A parallel algorithm with elegant span but excessive intermediate storage may be infeasible.

Worked Investigation 4: DAG Scheduling in a Seven-Stage Pipeline

A pipeline with seven logical tasks has work W = 7 and span S = 5 as developed earlier. Two processors finish in five steps because several dependencies leave a processor idle. Adding a third or fourth worker does not improve the schedule for that DAG: the span lower bound remains five. The correct intervention would change the task decomposition or pipeline dependencies, not merely provision more workers.

If B and C were each further divisible into independent smaller tasks, their durations and the DAG could change. Merely writing `parallel_for` around D, which depends on both, does not shorten the dependency chain. This investigation demonstrates the operational value of measuring the critical path before purchasing more capacity.

Worked Investigation 5: Wavefront Alignment of Two Sequences

A sequence-alignment dynamic program has m = 1000 rows and n = 1500 columns with a constant-cost cell recurrence depending on upper, left, and sometimes upper-left neighbors. There are approximately 1.5 million cells of work, with a critical path of order m+n rather than mn. Cells with constant i+j belong to one wavefront and are independent; the maximum simultaneous width is at most 1000.

A machine with 64 processors may exploit many middle wavefronts but be mostly idle on the first and final few. Blocking can reduce barrier frequency and improve cache locality, yet a block is no longer a unit-time task. The analysis must recompute W and S for tiled operations and include intermediate storage. Padding two sequences or switching to approximate alignment changes the algorithmic problem and must be disclosed.

Worked Investigation 6: Parallel BFS on a Skewed Social Graph

Consider a graph containing one high-degree hub connected to many leaves and long chains elsewhere. Assigning equal numbers of vertices to workers does not balance edge-processing work: the hub may cost Θ(E) while leaves cost O(1) each. A frontier-parallel BFS can distribute adjacency segments or use edge-based tasks, but concurrent discovery of shared neighbors requires atomic deduplication or a deterministic merging phase.

A claimed O(V+E) work bound is insufficient to predict latency. Measure frontier sizes, degree distribution, atomics, memory bandwidth, and number of BFS rounds. A star centered at the source has few rounds but a large first frontier; a path has many rounds but tiny frontiers. These graphs have markedly different available parallelism despite potentially similar total vertex and edge counts.

Worked Investigation 7: Choosing Between CPUs and a GPU

A team compares two workloads: a million independent fixed-size numeric transforms and a small irregular graph search with branching and pointer chasing. The transforms have a simple map-like DAG and contiguous arrays, potentially matching a GPU’s throughput-oriented design. The graph search may have unpredictable frontiers, divergent control flow, and poor coalescing, potentially favoring CPU task scheduling. Neither outcome is guaranteed by the label “GPU” or “parallel.”

The decision budget should include host/device transfer, launch latency, data residency, memory capacity, task synchronization, and latency constraints. If transformed data are already resident on the GPU for later work, the transfer amortization differs from a one-off request. Compare complete wall time, power or monetary cost where relevant, and correctness at realistic workloads. The optimal device can change with batch size.

Common Reasoning Errors and Corrections

  • “P processors divide time by P.” The span, overhead, and shared resource bottlenecks prevent unlimited speedup.
  • “O(log n) span means fast on one core.” Span ignores total work; work may be O(n log n) or worse.
  • “Every loop can be parallelized.” Dependencies, aliases, and side effects may forbid reordering.
  • “A reduction is O(1) because a library call returns one scalar.” Bounded-fan-in reduction has logarithmic depth.
  • “High parallelism guarantees scalability.” Bandwidth and scheduler overhead can dominate.
  • “Expected speedup is a worst-case guarantee.” Randomness and input quantifiers must be distinguished.
  • “More cores always reduce cost.” Processor-time and energy may increase even when latency falls.
  • “A race-free floating-point reduction is bitwise repeatable.” Changing combination order can change rounding.

The general correction is to keep four questions separate: is the transformation correct, what resources does its DAG require, can a finite processor budget schedule it, and how does the implementation behave on actual hardware?

Review Questions and Answer Key

The questions below progress from definitions and proofs to design and measurement. Numerical answers assume the idealized work-span model unless stated otherwise.

  1. What does W measure in a task DAG? Answer: The sum of unit operation counts or weighted strand costs; it equals the DAG algorithm’s ideal one-processor time T₁.
  2. What does S measure? Answer: The maximum total cost along any dependency path, also called critical-path length or T∞.
  3. State the two universal ideal scheduling lower bounds. Answer: T_P ≥ W/P and T_P ≥ S, giving T_P ≥ max(W/P,S).
  4. What ideal greedy-scheduling bound does Brent’s theorem give? Answer: T_P ≤ W/P + S up to the stipulated unit-time and scheduling assumptions.
  5. Why does a greedy scheduler have at most S incomplete steps? Answer: At any underfilled step it executes all ready strands, shortening a remaining critical path by at least one unit.
  6. If W=2000, S=40, and P=20, what are the standard bounds? Answer: Lower bound max(100,40)=100 and coarse Brent upper bound 100+40=140 idealized time units.
  7. What is average parallelism? Answer: W/S; it identifies the processor budget near which span becomes as important as work.
  8. How does W differ from T_seq? Answer: W is one-processor work of the parallel algorithm; T_seq may be a different optimized sequential algorithm.
  9. Define parallel efficiency. Answer: E_P=(T_baseline/T_P)/P, with the baseline and timing boundary stated.
  10. What does Amdahl’s law hold fixed? Answer: The workload size and a fixed serial fraction, under ideal parallelization of the remaining fraction.
  11. Does Gustafson’s law contradict Amdahl’s law? Answer: No. It models scaled workloads with a serial fraction measured relative to parallel runtime, not fixed-size speedup.
  12. What is strong scaling? Answer: Holding the complete problem fixed while increasing processors and measuring runtime or speedup.
  13. What is weak scaling? Answer: Increasing workload with processor count to keep work per processor approximately fixed.
  14. What do EREW and CRCW mean? Answer: EREW excludes simultaneous shared-cell reads and writes; CRCW permits both subject to a specified write-conflict rule.
  15. How do forked child tasks combine work and span? Answer: Their work adds; their parallel span takes the maximum of child spans plus sequential overhead.
  16. Why is false sharing expensive even without races? Answer: Independent writes to one coherence unit can force cache-line transfers and invalidate each other’s copies.
  17. What algebraic property makes a tree reduction legal? Answer: Associativity of the combine operator under the intended arithmetic contract, plus identity for empty groups.
  18. Give work and span of balanced reduction on n inputs. Answer: Θ(n) work and Θ(log n) span for constant-cost bounded-fan-in combine operations.
  19. Why is Hillis–Steele scan work-inefficient? Answer: Its Θ(log n) rounds each process Θ(n) items, totaling Θ(n log n) work.
  20. State work and span of a Blelloch-style scan. Answer: Θ(n) work and Θ(log n) span under the ideal balanced tree model and suitable padding.
  21. Why is stable filtering not just a parallel map? Answer: Selected elements must be assigned unique order-preserving positions, often using a scan and scatter.
  22. What span follows from parallel recursion with a sequential Θ(n) merge? Answer: S(n)=S(n/2)+Θ(n)=Θ(n), even though both recursive halves run concurrently.
  23. What is a wavefront DP’s ideal work/span on an m×n grid? Answer: Θ(mn) work and Θ(m+n) span for constant-cost top/left dependent cells.
  24. Why can parallel BFS performance vary between a star and a path? Answer: A star has very wide frontiers and few rounds; a path has narrow frontiers and many rounds.
  25. State the elementary pointer-jumping work/span bounds. Answer: O(n log n) work and O(log n) span when each of O(log n) synchronous rounds touches n list nodes.
  26. What does α+βm represent in a message model? Answer: Startup latency α plus per-byte transfer cost β for a message of size m, under a simplified model.
  27. What is Karp–Flatt e designed to estimate? Answer: An effective fixed-problem serial fraction from observed speedup, encompassing overhead and bottleneck effects.
  28. What should a parallel performance report include besides wall time? Answer: Processor count, baseline, input and output contract, data placement, bytes, workload variance, and relevant scheduling or contention measures.
