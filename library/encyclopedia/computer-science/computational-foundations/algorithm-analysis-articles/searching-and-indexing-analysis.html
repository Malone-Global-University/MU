Definition, Purpose, and Editorial Scope

A search algorithm locates or establishes the absence of a target in a specified collection. An index is additional organization that lets a search avoid examining every original record when its design matches the query. Searching and indexing analysis compares the entire cost of obtaining answers: inspecting input, building auxiliary structures, maintaining them after changes, retrieving matching records, and producing results. No single bound answers all of these questions.

This article is the tenth Level 5 specialist page of the MGU Algorithm Analysis unit. It extends the Algorithm Analysis overview, concentrating on analytical methods rather than the full engineering of database engines or data structures. The Lower Bounds and Decision Trees article treats lower-bound proof techniques in greater depth; Time-Space Tradeoffs treats broader resource allocation; and the Algorithm Benchmarking and Profiling article owns detailed experimental methodology.

A meaningful comparison specifies an input representation, supported operations, key domain, query distribution, update frequency, dataset scale, comparison or hashing costs, and memory or I/O model. Assertions such as “hashing is O(1)” or “indexes always make queries faster” omit assumptions essential to the conclusion. The objective is a defensible workload-specific decision, not a universal ranking of named methods.

Search Contracts: Membership, Position, Range, and Output

Before analyzing complexity, define what constitutes a correct answer. Membership reports whether a value exists. Exact lookup may return one associated record, every matching record, or a stable identifier. Lower bound returns the first position at which a key could be inserted without violating the ordering relation. Upper bound returns the first position after existing equal keys. A range query retrieves every element in an interval. These contracts are different even if an implementation uses the same underlying data structure.

For a sorted array A of length n, the half-open interval [lo, hi) describes positions lo, lo+1, ..., hi−1. Lower bound for x is the smallest i with A[i] ≥ x, or n if no such position exists. Upper bound is the smallest i with A[i] > x, or n if none exists. Their difference counts equal occurrences.

A range-search cost is often output-sensitive: a tree or ordered index may spend O(log n) finding the range start and Θ(k) emitting k matches, for O(log n + k) under an appropriate RAM model. Listing a million records cannot be O(log n) if every record must be written to the output. Similar considerations apply to top-k, nearest-neighbor, prefix and full-text queries, though their indexing assumptions differ.

Input Size, Workloads, and Computational Cost Models

Let n denote the number of stored records, q the number of queries, u the number of updates, k the number of results returned by a particular query, and B the number of records or bytes handled per external-memory block where relevant. Distinguish key comparisons, hash computations, pointer traversals, memory allocation, disk-block transfers, index writes, and bytes returned. A theoretical unit-cost comparison assumes these operations are bounded-cost; realistic records may have long variable-length keys or expensive normalization.

A workload can be modeled as a mix of read, write and maintenance operations, with their frequencies or distributions stated explicitly. The overall modeled cost can be written Ctotal = Cbuild + q·Cquery + u·Cupdate + Cmaintenance + Coutput for a simplified homogeneous workload. In a real application, individual queries vary in selectivity and output size; a weighted sum or distributional expectation may be more informative than one average. Always state whether build costs are one-time, periodic, or already paid.

Asymptotic bounds compare growth under a defined model. Wall-clock latency also includes cache misses, scheduling, page faults, storage latency, concurrency, and contention. A one-time scan of a small contiguous array can beat a more sophisticated pointer-heavy index even if its asymptotic growth is worse. A good analysis keeps mathematical bounds and observed performance in separate columns.

Linear Search: Exact Comparison Counts

Sequential search inspects records in their original order until it finds a matching key or exhausts the collection. For n records, an unsuccessful search makes n equality checks; a successful search at zero-based position j makes j+1 checks. Worst-case Θ(n) time and O(1) auxiliary space require no ordering or additional index. These are useful guarantees when the dataset is modest or the queries are infrequent.

If each of the n positions is equally likely conditional on a successful search, expected comparisons are (1+2+...+n)/n = (n+1)/2. With hit probability h, and unsuccessful searches always scanning all n entries, the modeled expectation is h(n+1)/2 + (1−h)n. This calculation depends on the stated distribution: a popular item frequently stored near the front produces a different expected cost. The model concerns one list and fixed search ordering, not a universal law.

def linear_find(items, target):
    for i, value in enumerate(items):
        if value == target:
            return i
    return -1

assert linear_find([9, 3, 7], 3) == 1
assert linear_find([9, 3, 7], 4) == -1
assert linear_find([], 4) == -1

Unsorted Input, Early Exit, and Predicate Search

Early exit is legitimate only when the search contract permits it. Equality search in an unsorted list can terminate upon the first match; proving that a value is absent generally requires checking all records. A query to list every matching record must continue beyond the first occurrence, so its cost can remain Θ(n) even for common values. A linear search over already filtered input may also have a lower effective n than a nominal index-backed search over a much larger structure.

Sentinel search moves a termination condition into the data area to reduce per-iteration checks, but it may mutate storage, require spare capacity, or need careful restoration. These are constant-factor optimizations; they do not change Θ(n) worst-case growth. In an environment with potentially expensive key comparisons, precomputing a stable normalized key can matter more than shaving one loop condition.

The correct loop invariant for a first-match scan is that none of the earlier positions contains a match. At return, if the algorithm produces index i, equality holds at i and all earlier positions failed. If the scan reaches the end, every admissible position has been tested. This elementary correctness argument becomes the baseline for more elaborate indexes.

Binary Search on a Sorted Array

Binary search requires an ordered input and a comparator consistent with that order. At each step, an index near the middle of the active interval is inspected and the portion that cannot contain the target is discarded. Because the remaining range shrinks by about half on each iteration, a lookup uses O(log n) key comparisons, apart from the cost of each key comparison. It does not require a separately allocated tree; the sorted array encodes the searchable order.

Using a half-open interval avoids ambiguity about the empty case: initially lo=0 and hi=n; termination occurs at lo == hi. A precise first-position implementation is preferable to “find any occurrence” for duplicate-heavy indexes because it supports both membership and range queries.

def lower_bound(a, x):
    lo, hi = 0, len(a)
    while lo < hi:
        mid = lo + (hi - lo) // 2
        if a[mid] < x:
            lo = mid + 1
        else:
            hi = mid
    return lo

values = [1, 3, 3, 3, 9]
assert lower_bound(values, 3) == 1
assert lower_bound(values, 4) == 4
assert lower_bound(values, 0) == 0
assert lower_bound(values, 10) == 5

Binary-Search Correctness and Termination Proof

For lower-bound search, maintain this invariant: every position strictly before lo contains a value below the target, and every position at or beyond hi contains a value at least the target. It is true initially because both excluded regions are empty. If the middle value is below x, the sortedness premise excludes all positions up to and including mid, so lo=mid+1 preserves the invariant. Otherwise the middle position and all later positions qualify as candidates for the bound; reducing hi to mid is safe.

The nonnegative integer hi−lo decreases whenever the loop executes. When it becomes zero, the invariant places all smaller elements before the common boundary and all greater-or-equal elements at or after it. Therefore the returned position is the lower bound, including empty arrays and values outside the stored key range. This is both a partial-correctness and termination argument.

In fixed-width integer languages, computing (lo+hi)/2 can overflow; lo+(hi−lo)/2 avoids that particular addition overflow when the bounds are valid. Python integers do not exhibit the same fixed-width overflow, but the expression still communicates the safe arithmetic pattern. With long string keys, a logarithmic count of comparisons may still entail comparing many characters.

Duplicate Keys and Search Boundary Semantics

A sorted array can hold repeated keys. An exact-match binary search that returns on equality may choose an arbitrary matching index; it does not guarantee the first or last occurrence. Lower bound and upper bound provide stable boundaries. If lo=lower_bound(A,x) and hi=upper_bound(A,x), the slice A[lo:hi] contains exactly the matches for a total order consistent with the comparator. Membership is lo < n and A[lo] == x under the same equality semantics.

def upper_bound(a, x):
    lo, hi = 0, len(a)
    while lo < hi:
        mid = lo + (hi - lo) // 2
        if a[mid] <= x:
            lo = mid + 1
        else:
            hi = mid
    return lo

values = [1, 3, 3, 3, 9]
assert upper_bound(values, 3) == 4
assert upper_bound(values, 2) == 1
assert upper_bound(values, 10) == len(values)

A range query on a sorted array can find the first key at least left and the first key strictly greater than right, then emit the intervening records. The boundary search costs O(log n) each, and materializing k outputs costs Θ(k); thus O(log n + k) time. The exact inequality directions matter when a range includes or excludes its endpoints.

Python bisect: Logarithmic Location, Linear Insertion

Python’s standard-library bisect_left and bisect_right implement lower and upper insertion boundaries for sorted sequences. Locating an insertion index requires logarithmically many comparisons in the abstract array model. Inserting into a Python list nevertheless shifts subsequent elements, requiring O(n) time in the worst case. The combined insort operation is therefore O(n), not O(log n). This is documented explicitly by the Python Software Foundation.

from bisect import bisect_left, bisect_right, insort

scores = [40, 60, 60, 75]
assert bisect_left(scores, 60) == 1
assert bisect_right(scores, 60) == 3
insort(scores, 68)
assert scores == [40, 60, 60, 68, 75]

Binary search on records with an expensive computed key may repeat key extraction. One strategy maintains a parallel array of precomputed keys or uses an appropriate key callback where available; maintaining parallel representations adds consistency obligations. The public documentation warns that bisect functions are not thread-safe for simultaneous operations on the same sequence. The conceptual lesson is to analyze locate, insert, delete, and consistency separately.

Preprocessing Break-Even: Scan Versus Sort Then Search

Suppose one scan takes a·n modeled work. Sorting once costs b·n log₂ n and each indexed binary lookup costs c·log₂ n. After q queries, a simple scan strategy costs q·a·n, whereas sorting then searching costs b·n log₂ n + q·c·log₂ n, ignoring ties, output, and updates. Sorting breaks even only if q(a·n − c·log₂ n) > b·n log₂ n with a positive denominator. An order-of-growth summary suggests enough repeated queries can amortize preprocessing, but the threshold depends on the constants and workload.

The comparison also changes if the original record order must be preserved. Instead of sorting the records in place, one may sort pointers or pairs of (key, record_id); this consumes additional memory and lookup indirection. Maintaining the sorted representation under random insertion can still cost Θ(n) shifts per update, so a read-only break-even analysis must not be reused without accounting for u updates.

For a static data source with only a handful of lookups, a scan is often attractive. For many exact lookups on a stable ordered collection, binary search can be compelling. If equality lookup dominates and order is not required, a hash index may fit better. A proof of superiority needs explicit work estimates or measurements, not just an asymptotic label.

Batch Search and Reusing Ordered Traversals

If both stored data and the query keys are sorted, a two-pointer merge scan answers many membership or matching queries without running binary search separately for each one. The method advances the pointer whose current key is smaller and reports equality when they meet. Its total traversal cost is O(n+q), excluding output, while q separate binary searches cost O(q log n). Whether the merge approach is superior depends on the relative sizes, the possibility of sorting the queries, and what is returned.

def sorted_membership_batch(data, queries):
    i = 0
    answers = []
    for key in queries:  # Requires nondecreasing query keys.
        while i < len(data) and data[i] < key:
            i += 1
        answers.append(i < len(data) and data[i] == key)
    return answers

assert sorted_membership_batch([1, 4, 4, 8], [0, 1, 4, 5, 8, 9]) == [False, True, True, False, True, False]

Batching is a broad technique in indexing analysis. Ordered query execution can improve locality, coalesce I/O, and reuse results; it can also increase end-to-end latency if the system waits to assemble a batch. A cost model should state whether response ordering matters and whether sorting the queries itself incurs O(q log q) preprocessing.

Searching by a Monotone Predicate

Binary search applies not only to a literal sorted list but also to a monotone Boolean predicate over an ordered candidate domain. If a predicate is false for all positions below some boundary and true thereafter, its first true position can be found logarithmically. Examples include finding the minimum sufficient capacity, the first acceptable timestamp in a monotone log, or the smallest feasible parameter in an optimization problem. The predicate may cost more than O(1), so overall time is O(P(n) log n) if each evaluation costs at most P(n).

def first_true(lo, hi, predicate):
    # Search the integer interval [lo, hi), assuming False...False, True...True.
    while lo < hi:
        mid = lo + (hi - lo) // 2
        if predicate(mid):
            hi = mid
        else:
            lo = mid + 1
    return lo

assert first_true(0, 20, lambda x: x * x >= 50) == 8
assert first_true(0, 20, lambda x: False) == 20

The monotonicity hypothesis must be established, not guessed. A feasibility condition can cease to be monotone if changing a parameter also changes the rules, constraints, or numerical approximation. Never infer a Boolean boundary from a few sampled points when false negatives are possible. This subject connects to Recurrence Relations through the logarithmic sequence of subproblems, but the work of the predicate itself must be analyzed separately.

Exponential Search and Unknown Upper Bounds

When an ordered domain has no convenient known upper bound, exponential search can probe positions 1, 2, 4, 8, and so on until it finds a value at least the target (or a boundary indicating the end). It then performs binary search in the last bracketed interval. If the first qualifying position is p, this requires O(log(p+1)) probes and comparisons, assuming accessible positions and bounded-cost operations. The method may outperform searching a huge predetermined range when the target lies near the beginning.

A correct implementation must define out-of-range behavior; probing into a conventional finite Python list without checking length raises an exception. For streams or remotely accessed stores, each probe may have substantial latency, and an early doubling phase can cause inconvenient access patterns. Exponential search is a strategy for discovering scale, not a substitute for clearly defined ordering and bounds.

Interpolation Search and Distribution-Dependent Performance

Interpolation search estimates a likely target position from numeric key values instead of always choosing the midpoint. Under certain approximately uniform, independent key-distribution models, its expected probe complexity can be O(log log n). That attractive result is not a worst-case guarantee: skewed distributions, many duplicates, clustered values, or an unsuitable key scale may lead to linear behavior. Interpolation also needs guards for equal endpoints and out-of-range targets.

A rigorous comparison identifies the probability model, collision or duplicate assumptions, arithmetic precision, and the cost of random array access. A midpoint search provides a more predictable logarithmic comparison guarantee on sorted data. Interpolation is a useful example of why distribution-sensitive algorithmic analysis must be separated from worst-case analysis.

Information-Theoretic Search Lower Bounds and Their Scope

In a comparison decision tree, locating one of n distinguishable positions requires at least ceil(log₂ n) binary decisions on some path. Searching for an insertion position among n+1 gaps similarly requires sufficient decision-tree leaves to distinguish the possible answers. This establishes a logarithmic worst-case comparison requirement under the chosen model. An equality-only test that asks whether a queried element is identical to one stored item has different branching and lower-bound properties; the operational model must be stated.

Hashing can obtain expected constant-time equality lookup under suitable assumptions because it performs operations beyond pairwise order comparison. Direct addressing can obtain constant-time access for a bounded integer universe by trading extra space for addressing capability. These structures do not violate comparison-based lower bounds; they use stronger computational operations and different resource budgets. See Lower Bounds and Decision Trees for the fuller adversary and information arguments.

From Searching to Indexing: What the Structure Stores

An index associates a searchable key with a location, a collection of record identifiers, or an organized set of records. A primary organization may determine where data physically lives; a secondary index adds another access path. A clustered arrangement stores nearby key ranges near each other in some useful sense; an unclustered index can require additional random access to fetch matching records. Database-product terminology varies, so these are architectural concepts rather than universal implementation labels.

Every index introduces invariants that must remain true after modification: keys correspond to records, duplicates are handled under the declared contract, deleted entries are not exposed incorrectly, and range order is preserved when required. Building an index is itself an algorithm. A sorted index over n arbitrary keys often requires O(n log n) comparison work; a hash index built incrementally can have expected O(n) work under reasonable resizing and hashing conditions. Storage allocation and I/O may dominate in either case.

A key analytical trap is to quote index lookup cost while omitting the row-retrieval cost. For example, finding k record identifiers can be O(log n+k), but fetching k scattered records may incur up to Θ(k) random page reads without caching or locality benefits. The index reduces the search space; it does not eliminate the work needed to access the selected data.

Hash Indexes: Expected Constant-Time Lookup Is Conditional

A hash function maps keys into a finite collection of bucket positions. If keys are distributed adequately and the table maintains a controlled load factor, a lookup can examine a constant expected number of entries. This is typically expressed as expected O(1) time for lookup, insert, and delete in an abstract uniform-hashing model. The expectation may be over random hash-function choices or an explicit key distribution; it should not be attributed automatically to arbitrary deterministic hashes against adversarial inputs.

A collision occurs when different keys map to the same bucket or probe sequence. Collisions are inevitable when the key universe is larger than the number of table positions. Correctness requires an equality check or equivalent key-identification mechanism after hashing; equal hash values alone do not establish equal keys. Worst-case lookup can be Θ(n) when many keys collide, even though average or expected performance is favorable.

def bucket_lookup(buckets, key, bucket_count):
    slot = hash(key) % bucket_count
    for stored_key, value in buckets[slot]:
        if stored_key == key:
            return value
    return None

buckets = [[] for _ in range(7)]
for key, value in [(7, 'a'), (14, 'b'), (4, 'c')]:
    buckets[hash(key) % 7].append((key, value))
assert bucket_lookup(buckets, 14, 7) == 'b'
assert bucket_lookup(buckets, 5, 7) is None

Separate Chaining: Load Factor and Expected Comparisons

Separate chaining assigns a bucket to each hash value and holds colliding entries in a secondary list or comparable structure. With n entries across m buckets, the load factor is α=n/m. Under simple uniform hashing and a linear scan within each bucket, the expected unsuccessful search work is Θ(1+α). The expected successful search work has comparable scale, with constants depending on insertion order and hit distribution. If m=Θ(n), both become expected Θ(1).

Chain length distribution matters more than α alone for tails. One enormous chain creates slow queries even if most buckets remain empty. A table may resize to keep α controlled, but resizing requires reassigning or redistributing existing entries. The associated cost is often amortized over subsequent operations. This is another case where low expected lookup cost can coexist with occasional expensive maintenance.

Open Addressing: Probing and Occupancy

Open addressing stores entries within the table itself and follows a probe sequence when the initially calculated position is occupied. Linear probing, quadratic probing and double hashing have different clustering behavior and applicability conditions. Load factor must remain below one for insertion to be possible; performance commonly deteriorates as occupancy rises. Deletion requires care so that a search does not stop at a vacated slot that lies within another key’s probe path.

Under the idealized uniform-hashing assumption, expected probe counts can be bounded in terms of the load factor—for example, an unsuccessful search has a familiar upper bound of approximately 1/(1−α). Actual implementations can depart significantly from the ideal because of clustering, cache effects, hash quality and workload dynamics. The correct engineering analysis combines occupancy, probe lengths, resize policy, and memory locality rather than asserting that all hash tables behave identically.

Hash Randomization, Universality, and Adversarial Workloads

A family of hash functions is universal if, when a function is chosen randomly from the family, any distinct pair of keys collides with probability at most 1/m for a table of m buckets. This is a probabilistic guarantee about a function family, not a proof that a single chosen hash has no collisions. Random seeding can limit predictability of collisions, but the actual robustness and threat model depend on the implementation.

When arbitrary users can submit keys, intentionally constructed collision sets may create denial-of-service pressure in weakly protected hash tables. Defensive designs include suitable hashing, load-factor management, distribution diagnostics, resource limits, and—in some implementations—alternate collision resolution. A security-sensitive endpoint should not plan capacity from uniform-hashing expectations alone. The same discipline applies when using hashing as an index inside a data processing pipeline.

Direct Addressing, Bitsets, and Sparse Universes

If keys are small integers from a known universe of size U, a direct-address table can map key x to array slot x without collisions. Membership and updates then require O(1) indexed access in the unit-cost RAM model, with Θ(U) storage. A bitset reduces constants by packing one bit per possible key; it still requires storage proportional to the universe size. An enormous sparse universe can make direct addressing wasteful even when queries are extremely fast.

class Bitset:
    def __init__(self, universe):
        self.universe = universe
        self.bits = bytearray((universe + 7) // 8)
    def add(self, key):
        if not (0 <= key < self.universe):
            raise ValueError('outside universe')
        self.bits[key // 8] |= 1 << (key % 8)
    def contains(self, key):
        if not (0 <= key < self.universe):
            return False
        return bool(self.bits[key // 8] & (1 << (key % 8)))

seen = Bitset(100)
seen.add(17)
assert seen.contains(17) and not seen.contains(18)
assert not seen.contains(100)

Compressed bitmaps can exploit long runs, sparse sets or recurring patterns. Their space and operation costs depend on the compression scheme and data distribution. A bitmap index is attractive for some low-cardinality filters and set combinations, but the number of distinct values, update behavior and resulting candidate set sizes must be considered.

Binary Search Trees: Height Controls Cost

A binary search tree maintains the invariant that every key in a node’s left subtree precedes the node key and every key in its right subtree follows it, under a defined duplicate policy. Search, insertion and deletion traverse a path whose length is bounded by the tree height h. Therefore these operations are O(h), not unconditionally O(log n). A balanced tree has h=Θ(log n); a path-like tree can have h=Θ(n).

The same tree can answer ordered queries that ordinary hash tables do not support efficiently: predecessor, successor, minimum, maximum, rank, and range traversal. A range report may take O(h+k) once the appropriate boundary is found, under a typical node-pointer model. Space is Θ(n) for the nodes; constant factors include pointers, balancing metadata and allocation fragmentation.

class Node:
    def __init__(self, key):
        self.key, self.left, self.right = key, None, None

def bst_contains(root, key):
    node = root
    while node is not None:
        if key == node.key:
            return True
        node = node.left if key < node.key else node.right
    return False

root = Node(8)
root.left, root.right = Node(3), Node(10)
root.left.right = Node(6)
assert bst_contains(root, 6)
assert not bst_contains(root, 7)

Balanced Trees: AVL and Red–Black Guarantees

Self-balancing search trees maintain structural invariants through rotations or comparable local restructuring. AVL trees constrain height differences between child subtrees; red–black trees enforce coloring and black-height properties. Both yield logarithmic search-tree height and O(log n) worst-case searches, insertions and deletions in standard implementations. Their constants, rotation schedules and node metadata differ, so one does not dominate the other for every workload.

An ordered index is appropriate when workloads include range scans, predecessor queries or sorted iteration. If a workload needs only equality checks, a hash table may offer smaller expected comparison counts. If memory locality is central, a pointer-based balanced tree can be disadvantaged relative to contiguous arrays or page-oriented trees even with the same logarithmic order of growth. Analysis must distinguish theoretical path length from the cost of following scattered pointers.

B-Trees and B+Trees: Page-Oriented Search

B-trees store many keys or separators per node, increasing fanout so each tree level indexes a large portion of the dataset. A B+tree-like design commonly stores searchable separators in internal nodes and data entries or record references in leaves, often with leaves linked for range traversal. Height can be approximated as O(logF n) where F is effective branching factor and occupancy assumptions hold. In a block-I/O model, the main benefit is fewer page transfers, not a changed Θ(log n) RAM comparison category.

On a page, search may use binary search, a small sequential scan, SIMD-assisted comparisons, or specialized prefix encoding depending on implementation. Splits, merges, page fill factors, write-ahead logging and concurrency controls make update costs more complicated than the textbook search count. Page-oriented trees motivate why “balanced tree” cannot be treated as one performance profile across in-memory and storage-resident systems.

A leaf-range scan finds a starting position through upper index levels and then reads successive leaf pages, usually exploiting ordered locality. Reporting k records may take O(logF n + k/B) logical index-block transfers under suitable occupancy and page layout assumptions, plus any separate record fetches. These are model-specific bounds; cold-cache, remote storage and nonclustered access can dominate actual latency.

Physical Locality: Random Fetches and Block Transfers

Consider two indexes that each identify the same 50,000 matching rows. In the first, rows are physically adjacent; in the second, their locations are scattered across storage pages. Both may have nearly identical comparison counts, yet the second can incur far more page transfers. For magnetic disks, seek cost historically amplified the difference; for solid-state storage, random I/O and parallelism still matter, though the constants differ substantially.

An external-memory analysis counts block transfers rather than elementary comparisons. The effective block size, caching policy, record size, compression, and whether an index contains the requested output fields all change the cost. A cost model that ignores physical locality is particularly misleading for wide records, high-result-count queries, or cold-cache scans.

Composite Keys and Leftmost-Prefix Reasoning

A composite ordered index sorts tuples such as (region, department, employee_id) lexicographically. It can often narrow searches efficiently when predicates constrain the leading indexed columns. The physical column order changes the useful access patterns: an index ordered first by region is not automatically equivalent to one ordered first by employee ID. A query that filters only by a trailing column may need a broader scan or a planner-specific optimization.

For example, a composite (region, year) B-tree is natural for “all records in region R during years 2022–2025” because the region equality constrains a contiguous area followed by a range over year. A query solely on year may not isolate one contiguous range across all regions. Some engines have skip-scan or other execution strategies, but these must be verified for the actual product and workload rather than assumed.

The first principle in composite-index selection is to map common queries to key-order prefixes, range dimensions, output ordering and selectivity. Design must also account for updates and increased index width. An index with more columns may be larger, slower to modify and less cache-resident despite satisfying a wider set of queries.

Ordered Range Queries, Pagination, and Output Sensitivity

An ordered index is valuable for range predicates such as timestamp BETWEEN a AND b, ordered pagination, and nearest-predecessor queries. An index can locate the start with logarithmic page or comparison work and visit the selected section sequentially. If k records are returned, every correct algorithm must spend Ω(k) time to explicitly emit k fixed-size results, regardless of how cheaply it finds the first match.

Offset pagination may scan or skip a large number of index entries even when the page size is small. Keyset pagination instead continues from a last-seen composite key, provided the ordering has stable tie-breakers and changes to the dataset are accounted for. A pagination complexity statement must distinguish locating the next boundary from preserving a consistent view of mutable data; that latter question involves transaction semantics beyond pure search cost.

Index range performance is also sensitive to selectivity. Returning 80% of a table through random row fetches can be more expensive than scanning the table sequentially. An optimizer may correctly choose a scan even when a suitable index exists. This does not refute the asymptotic advantage of small-result indexed queries; it reflects a different measured cost regime.

Covering Indexes and Index-Only Retrieval

An index is covering for a particular query if it contains the information needed to answer that query without fetching the underlying record for the requested fields. Covering is query-relative: an index that covers (employee_id, department) does not automatically cover a query that also requests a large biography field. Covering designs can reduce scattered row access at the cost of storing more bytes in the index and performing more maintenance on updates.

In SQLite’s query-planner documentation, a covering index can eliminate a separate lookup into the base table when all requested columns are in the index. PostgreSQL’s documentation adds a crucial qualification: an index-only scan still requires visibility checks, and its ability to avoid heap access depends on the visibility map and access method. A conceptual claim that “all fields are in the index, so no table read occurs” is therefore too broad for an actual MVCC database engine.

When assessing covering indexes, count index bytes, cache residency, write amplification, output projection and any engine-specific visibility requirements. Avoid confusing the term with a second duplicate of the entire table; a very wide covering index can lose much of its expected benefit.

Inverted Indexes and Multi-Term Retrieval

A conventional forward organization maps each record to its content. An inverted index maps a term or feature to a posting list of record identifiers containing that term. A query for records containing both term A and term B can intersect two posting lists, often in time proportional to their lengths or faster under skip structures. A query for either term can merge or union their postings. Ranking relevant documents introduces additional scores and statistics beyond simple membership.

For sorted posting lists with lengths a and b, a two-pointer intersection needs O(a+b) comparisons in the worst case and O(k) output work for k matches; alternative intersection strategies can exploit a large imbalance in list lengths. Compression, skip pointers, term frequencies, positional indexes and updates complicate the practical performance. A term dictionary may itself be implemented with a hash or ordered structure.

def intersect_sorted(a, b):
    i = j = 0
    result = []
    while i < len(a) and j < len(b):
        if a[i] == b[j]:
            result.append(a[i]); i += 1; j += 1
        elif a[i] < b[j]:
            i += 1
        else:
            j += 1
    return result

assert intersect_sorted([1, 3, 8, 10], [2, 3, 7, 8]) == [3, 8]

An inverted index provides an access path for a specific family of term-based questions, not a guarantee for arbitrary predicates. Tokenization, normalization, language processing and update policies define what a “term” means and must be documented separately from the asymptotic intersection algorithm.

Tries and Prefix-Based Indexes

A trie organizes keys as successive symbols or symbol groups. Exact lookup of a key of length L commonly follows O(L) transitions in a bounded-cost symbol-access model, independent of the number of stored keys when the branching lookup is constant-time. Prefix retrieval first follows the prefix path and then traverses its matching descendants. Reporting k outputs cannot avoid their output cost, and the total traversal cost depends on the shapes and lengths of the stored strings.

Tries trade additional nodes and pointers for prefix search and ordered enumeration. Compressed tries and radix trees collapse chains of single-child nodes, reducing memory in some distributions. Compared with B-trees or hash tables, tries can be advantageous for autocomplete, routing prefixes and dictionary-style lookup, but alphabet size, node representation and cache locality determine the practical result.

def build_trie(words):
    root = {}
    for word in words:
        node = root
        for ch in word:
            node = node.setdefault(ch, {})
        node['#'] = True  # Reserved terminator, not in the word alphabet.
    return root

def has_prefix(root, prefix):
    node = root
    for ch in prefix:
        if ch not in node:
            return False
        node = node[ch]
    return True

trie = build_trie(['cat', 'car', 'dog'])
assert has_prefix(trie, 'ca') and not has_prefix(trie, 'cow')

Bitmap Indexes and Set-Based Filtering

For a column taking a small number of distinct values, a bitmap index can maintain one bit vector per value, marking which records have that property. Combining filters such as “active AND west region” reduces to bitwise operations on the corresponding bitmaps. On packed machine words, combining two uncompressed bitmaps of n positions needs Θ(n/w) word operations for a word width w, plus any output enumeration. This can be efficient even when the result is small.

Compression can reduce memory and accelerate some set operations, but the benefit depends on runs, sparsity and encoding. High-cardinality attributes may require a different design; updates may rewrite compressed blocks or create fragmentation. Bitmap indexes illustrate how a distinct query family can justify an index whose core operation is neither comparison search nor conventional hashing.

Bloom Filters: Memory for Probabilistic Membership

A Bloom filter stores a bit array and applies several hash functions to each inserted key. If a query finds any required bit unset, the key is definitely absent under the standard append-only construction; if all bits are set, the key might be present. Standard Bloom filters therefore have false positives but no false negatives when their assumptions hold, including correct insertion, no unsupported deletions and unchanged hash behavior. They are not sufficient to retrieve an associated value.

With m bits, n inserted elements and h independent idealized hash functions, an often-used approximation for false-positive probability is (1−e−hn/m)h. Near the optimum h=(m/n) ln 2, the minimum false-positive rate is approximately (0.6185)m/n. Real hashes and finite parameters may deviate from these approximations.

class TinyBloom:
    def __init__(self, width=256):
        self.bits = bytearray((width + 7) // 8)
        self.width = width
    def slots(self, value):
        # A teaching example: not a production hash family.
        return [hash((value, salt)) % self.width for salt in (1, 2, 3)]
    def add(self, value):
        for slot in self.slots(value):
            self.bits[slot // 8] |= (1 << (slot % 8))
    def maybe_has(self, value):
        return all(self.bits[s // 8] & (1 << (s % 8)) for s in self.slots(value))

bf = TinyBloom()
bf.add('index')
assert bf.maybe_has('index')

Bloom filters are often placed before a more expensive definitive lookup. Their value depends on the fraction of misses and the cost of a false-positive follow-up. They are especially useful when avoiding disk or network access on negative queries. An observed “maybe” must never be treated as a definitive presence proof.

Write-Optimized Indexes and LSM Trees

A log-structured merge-tree (LSM) family organizes new writes into mutable memory components and appends sorted on-disk runs that are later merged or compacted. The approach can reduce random writes, but it transfers work into compaction, read amplification and space amplification. A point lookup may need to check multiple structures; Bloom filters, fence pointers and caching can reduce those checks. The exact cost depends on level sizes, compaction policy and workload.

LSM structures illustrate why updates and queries must be analyzed together. A workload receiving many inserts but few range queries may favor write-oriented organization. A stable, scan-heavy dataset may favor structures optimized for ordered reads. Asymptotic claims about LSM complexity require specifying the level fanout, buffer size, block size, tiering or leveling policy and treatment of duplicates or tombstones.

The analysis belongs here as a conceptual search/index trade-off; detailed storage-engine compaction, crash consistency, and persistence design remain subjects for data-systems and storage engineering.

Index Creation, Update, and Rebuild Costs

Index creation is part of the total algorithmic cost. Creating a sorted key-to-record mapping from arbitrary records may take Θ(n log n) comparisons, while a suitable radix or distribution method can change the bound for restricted key domains. Populating a hash map often has expected Θ(n) time with adequate hashing and amortized resizing, but adversarial collision patterns or expensive allocations can change this. Constructing a search tree incrementally from presorted input without balancing can produce a degenerate shape.

An update affects every index whose key or predicate references the changed record. One logical insert can therefore trigger an additional tree update, hash update, posting-list mutation and log record, plus possible page split or compaction work. Secondary indexes are not free caches: they consume memory and storage, alter write latency, and increase the amount of state that must remain consistent.

Periodically rebuilding an index can reduce fragmentation or restore desired structure, but it consumes CPU, I/O and temporary space. Treat maintenance scheduling, background compaction, and operational availability as parts of the resource model, without assuming that background work is costless.

Amortized Guarantees Versus Worst-Case Lookup Latency

When an array or hash table doubles in size, one operation may move Θ(n) entries even though a long sequence of insertions has O(1) amortized resizing overhead per insert. A B-tree split can likewise impose a larger individual update cost than an ordinary insertion. Such behavior is a reason to distinguish worst-case operation latency from amortized cost across a sequence. A batch workload may tolerate occasional expensive updates; a strict real-time service may not.

Amortization is not a probabilistic statement and is not identical to average-case analysis. A sequence can have low amortized cost even if an adversary chooses the operations, provided the proof covers all admissible sequences. Hash collision expectations, by contrast, depend on randomization or input-distribution assumptions. For the formal methods, consult the Amortized Analysis specialist article.

Deamortized or incremental maintenance spreads some reorganization work over multiple operations to control spikes. Doing so typically introduces extra state and complexity. The proper choice is based on tail latency, consistency guarantees, maintenance overhead and predictable resource bounds—not solely on average throughput.

Selectivity, Cardinality, and the Choice of Access Path

Selectivity describes the share of records satisfying a predicate. If 10 of one million rows match, an index can dramatically reduce examined records. If 950,000 match and each requires a random row fetch, a sequential scan may be cheaper. Cardinality can refer to distinct values in an attribute or estimated result counts; state which meaning is intended. A filter on a near-unique identifier has different cost characteristics from a filter on a two-value status field.

Indexing decisions should consider correlation among predicates. For instance, “region=west” and “office=Seattle” are not independent filters; multiplying their separate selectivities may seriously underestimate or overestimate the intersection. Histograms and other statistics can improve cardinality estimates, though they become stale after data distribution changes. Query planners exploit such estimates to select between scans and index-driven access.

A theoretical query cost that includes just tree depth omits selectivity, row widths, residual filtering and output construction. These additional costs often dominate once the initial key range is located.

Cost-Based Query Plans and Statistics

A cost-based query optimizer estimates the work of alternative access paths: full table scan, one index range scan, bitmap or posting-list intersection, index-only retrieval, and combinations with sorting or joins. It relies on statistics about row counts, distinct keys, value distributions, correlations and device costs. The selected plan is an estimate under a model, not mathematical proof that the plan is fastest on the actual data.

SQLite’s query-planner guide demonstrates ordered-index lookup, covering indexes, multi-column indexes, and cost selection. Its EXPLAIN QUERY PLAN output distinguishes scan-based and indexed searches. PostgreSQL documents multiple index access methods and warns that indexes impose overhead and require appropriate workload justification. Readers should consult the official documentation for exact product behavior because optimizer capabilities evolve.

For analytical education, a miniature planner can estimate Cscan = αn and Cindex = βlog₂n + γk with input-specific constants. The model predicts an index advantage only when its startup and output costs stay below scanning. Treating a cost number as an absolute time in seconds without calibration is inappropriate.

Cache Hierarchies and Pointer-Chasing Costs

Modern processors fetch memory in cache lines, so touching nearby keys is often cheaper than following unrelated pointers. A linear scan over a compact contiguous array can use prefetching and SIMD-style comparisons, while a pointer-based search tree may incur unpredictable branches and cache misses at each level. Theoretical comparisons can therefore favor a tree yet measured time can favor a scan for sufficiently small or cache-resident data.

Binary search over a large sorted array makes only O(log n) comparisons but visits widely separated addresses during its early steps. Eytzinger layouts, blocked search layouts and cache-conscious tree nodes can improve locality under certain assumptions. B-trees increase fanout in part to align node access with storage blocks or cache structures. The right model depends on the memory hierarchy and working-set size.

This unit records locality as an essential dimension but leaves detailed cache-model proofs to the Cache and External-Memory Complexity specialist page.

Memory Footprint, Index Width, and Write Amplification

An index with O(n) entries can have radically different memory footprints depending on whether it stores integer offsets, full string keys, pointers, balanced-tree metadata, compressed postings or duplicated included columns. A practical analysis should measure total bytes, bytes per indexed record, fragmentation, compression, and temporary rebuild space. A structure that fits in memory may have a different latency profile from the same structure after it spills to storage.

Every maintained index can also amplify writes. Updating a record may modify several index pages and log entries; changing a frequently indexed column can be more expensive than changing a field absent from all indexes. An index deployed to accelerate one reporting query can become a bottleneck for a high-volume ingestion workload. Model these costs explicitly rather than treating indexes as read-only accelerators.

Cost models that compare strategies without respecting memory ceilings, storage budget, or index rebuild windows are incomplete. These constraints can eliminate options independently of asymptotic speed.

Concurrency, Consistency, and Snapshot Semantics

A search result must correspond to a declared consistency model. When the collection is changing, a query may encounter inserts, deletes or key updates during traversal. A read/write lock, versioned snapshot, transactional index, or copy-on-write design can prevent incoherent results, but each carries synchronization or version-retention costs. The asymptotic cost of lookup alone does not establish correctness under concurrent modification.

Database systems may expose isolation levels and multi-version concurrency control (MVCC). An index entry can lead to a row version that is not visible to the querying transaction; the engine must check the appropriate visibility rules. This is one reason a logically covering index may not always avoid fetching other metadata or table pages. The detailed design is system-specific, but the analysis must identify which records are visible and whether pagination is stable across pages.

During concurrent reads, sorted-array insertion can invalidate position-based iterators; hash-table resizing can move entries; and tree rotations can change traversal paths. Production code must use the collection’s documented synchronization model rather than transferring single-threaded proof assumptions unchanged.

Equality, Ordering, Null Values, and Composite Keys

Indexes depend on a consistent key contract. Numeric ordering, locale-aware string collation, case normalization, Unicode equivalence, null handling and floating-point NaN semantics can produce different search results across implementations. A comparator used for binary search must be consistent with the order that was used to construct the index. If the comparator changes after index creation, locating the right subrange is no longer guaranteed.

For a composite key, use a deterministic tuple order and document whether duplicates are allowed. If a record has multiple equal-key entries, returning an arbitrary record may be unacceptable when the contract demands first insertion, newest version or all matches. A unique constraint is a stronger semantic requirement than a fast exact lookup. Maintain stable record identifiers and version rules when the underlying records can move.

Security-sensitive applications should not silently merge keys under incorrect normalization; internationalized names, identifiers and user-provided text require explicit policies. Those semantic decisions precede algorithmic complexity analysis.

Approximate Search and False-Positive Trade-Offs

Not every query requires a perfect exact-match index. Bloom filters deliberately trade a controllable false-positive probability for compact absence checks. Approximate nearest-neighbor structures may trade retrieval accuracy for lower latency or storage, often using randomized or heuristic search. Such methods need a quality contract: false-positive rate, recall, precision, distance approximation, or probability of returning a valid answer.

The correct comparison may be a frontier of competing requirements rather than one scalar runtime. If missing a valid record is unacceptable, a probabilistic negative result from an inappropriate filter may be disallowed. If some false positives merely trigger cheap confirmation, a Bloom filter can be useful. Report both resource savings and the specific error measure; do not label probabilistic results as deterministic guarantees.

Index Maintenance Under Deletes and Reordering

Deleting records introduces additional state. In an unsorted array, removing an item after finding it can sometimes swap in the final element in O(1), but that changes order. In a sorted array, deleting the located item may shift Θ(n) elements. Search trees require structural repair; hash tables may need tombstones or backward-shift techniques; inverted indexes may maintain deletion markers and later compact their posting lists.

A workload dominated by deletes or key modifications may expose maintenance costs unseen in one-time lookup benchmarks. Data structure invariants should be rechecked after every edit, and the published analysis should state whether deletes are supported directly, lazily, or through periodic rebuilds. The same resource accounting applies to reorder operations and changes in collation rules.

Amortized Resizing and Table Occupancy Example

Consider a hash index that doubles its bucket count once the load factor would exceed a fixed threshold. Even if a resize rehashes every stored key, a geometric growth schedule can make the total rehashing work across a long insertion sequence O(n), resulting in O(1) amortized resize overhead per insertion under a suitable model. That does not remove the cost of key hashing or collision resolution, and does not imply O(1) worst-case time for a particular insertion.

def resize_copy_counts(number_of_inserts):
    capacity, size, moved = 1, 0, 0
    for _ in range(number_of_inserts):
        if size == capacity:
            moved += size
            capacity *= 2
        size += 1
    return moved

assert resize_copy_counts(1) == 0
assert resize_copy_counts(9) == 1 + 2 + 4 + 8
for n in range(1, 200):
    assert resize_copy_counts(n) < 2 * n

For an adversarial service with strict per-request latency limits, a worst-case resize spike may be unacceptable despite this amortized guarantee. A system may spread rehashing incrementally, impose load limits, or preallocate capacity at additional memory cost. A correct operational recommendation weighs expected throughput against latency distribution and the cost of maintaining capacity reserves.

Testing Search Contracts with Reference Oracles

Testing should verify not just speed but semantics: empty arrays, missing values, keys below or above the stored range, repeated keys, inconsistent comparators, nulls, and updates. A convenient reference oracle for small problems is an obvious linear scan, because it makes few assumptions. For random sorted lists, compare custom lower- and upper-bound implementations with standard-library bisect under the same ordering semantics.

import random
from bisect import bisect_left, bisect_right

def my_lower(a, x):
    lo, hi = 0, len(a)
    while lo < hi:
        m = (lo + hi) // 2
        if a[m] < x: lo = m + 1
        else: hi = m
    return lo

def my_upper(a, x):
    lo, hi = 0, len(a)
    while lo < hi:
        m = (lo + hi) // 2
        if a[m] <= x: lo = m + 1
        else: hi = m
    return lo

rng = random.Random(1729)
for _ in range(200):
    a = sorted(rng.randrange(12) for _ in range(rng.randrange(25)))
    for x in range(-1, 14):
        assert my_lower(a, x) == bisect_left(a, x)
        assert my_upper(a, x) == bisect_right(a, x)

For mutable indexes, construct operation sequences that interleave insert, update, remove and query steps, then compare answers with a slow reference map or list. Random tests complement, but do not replace, correctness invariants or adversarial boundary tests. When testing a probabilistic structure, verify the deterministic properties separately from estimated error rates.

Instrumenting Comparisons, Probes, and Results

Benchmark time can be noisy, so first count model-specific primitive operations. For linear search, count equality checks. For binary search, count ordering comparisons. For hashing, count probes and collision-chain lengths. For range queries, distinguish entry scans from emitted results and page accesses. Operation counts help explain performance differences before accounting for platform-dependent constants.

def counted_lower_bound(a, target):
    lo, hi, comparisons = 0, len(a), 0
    while lo < hi:
        mid = (lo + hi) // 2
        comparisons += 1
        if a[mid] < target:
            lo = mid + 1
        else:
            hi = mid
    return lo, comparisons

for n in [1, 2, 3, 7, 15, 31, 63]:
    a = list(range(n))
    idx, comparisons = counted_lower_bound(a, n)
    assert idx == n
    assert comparisons <= (n + 1).bit_length()

Instrumentation can change runtime, and comparison counts alone do not capture cache misses or storage I/O. The stronger methodology reports multiple cost measures, input generation, random seeds, distribution of workloads, warm versus cold-cache conditions, and uncertainty around timing estimates. See the separate benchmarking specialist article for full experimental discipline.

Workload Scenario 1: A Small Static Configuration Table

A service stores 40 configuration labels and answers a few lookups per hour. A direct scan requires at most 40 equality checks, has minimal implementation complexity, and needs no extra index. A hash table might lower lookup comparisons, but its allocation overhead and build code may be unnecessary. If the table is compile-time static and already sorted, binary search is also a reasonable low-maintenance option.

The lesson is not that scanning is universally best below a fixed threshold. It is that constant factors, simplicity, and the cost of building and maintaining a structure matter when n and q are small. The decision should consider whether keys can change, whether order matters, and whether the collection already exists in an indexed representation.

Workload Scenario 2: Repeated Point Lookups in a Stable Dataset

An application holds one million immutable records and must answer hundreds of thousands of identifier lookups. A fresh linear scan for every request makes q·Θ(n) comparisons. Building a hash index adds storage and construction work but can reduce typical exact-match lookup cost dramatically under suitable hashing. A sorted array with binary search offers O(log n) comparisons per lookup and avoids hash-collision assumptions, though constructing the sorted order has a cost.

Which index wins depends on the key distribution, hashing cost, memory ceiling, cache behavior, and whether ordered retrieval is also needed. If there is a one-time sort already required for another workflow, its construction cost may be shared rather than charged fully to lookup. A good recommendation quantifies this reuse explicitly.

Workload Scenario 3: Frequent Inserts and Deletes

A live inventory system processes frequent changes as well as point queries. A sorted Python list supports quick binary searches but may spend Θ(n) moving elements on each random insertion or deletion. A hash table can provide favorable expected update and point-lookup performance but offers no intrinsic ordered scans. A balanced tree or B+tree-like structure maintains order with logarithmic structural operations, trading metadata and pointer/page work for range support.

The right analysis counts read mix, update mix, uniqueness constraints, rebalancing or resizing spikes, durability requirements, and memory or storage layout. For a service with strict p99 latency objectives, amortized throughput alone is inadequate. This scenario demonstrates why the term “search data structure” must include update contracts.

Workload Scenario 4: Time-Window Log Investigation

A log archive contains records keyed by timestamp. Queries usually ask for events between two times and return hundreds or thousands of lines. A chronological sorted file or page-oriented ordered index can locate the starting timestamp and scan nearby entries. An equality-oriented hash table would need further organization to answer a time range efficiently.

If the selected period covers most of the archive, a sequential scan may be competitive. If timestamps are heavily duplicated, a composite key (timestamp, sequence_id) can provide a total order for stable pagination. Updating historical records or importing out-of-order events incurs extra maintenance. A responsible analysis identifies both the boundary-search complexity and the cost of reading and returning all requested events.

Workload Scenario 5: Prefix Search in a Large Dictionary

An autocomplete feature needs all terms beginning with a prefix. A trie can follow the prefix characters and enumerate its descendants; an ordered array or B+tree can locate a lexicographic prefix interval and scan it. A plain hash table is effective at exact membership but cannot efficiently list arbitrary prefixes without an additional structure. A term dictionary paired with posting lists becomes useful if the task expands to full-text retrieval.

The comparison includes key length, Unicode normalization, frequency of edits, memory footprint, ranking rules, and the maximum number of suggestions shown. If only ten suggestions are displayed, the index may avoid enumerating every matching term by storing ranked summaries or using bounded traversal—but that changes construction and update costs.

Workload Scenario 6: Memory-Limited Analytical Filtering

An analytics system must evaluate filters over tens of millions of rows with a constrained memory budget. Building a conventional pointer-heavy tree on every attribute may exceed available memory and slow writes. Sorted column scans, compressed bitmap indexes, sparse range summaries, or an index on only the most selective predicates may be preferable depending on cardinality and query mix.

The engineering question becomes “which information is worth materializing?” rather than “which lookup is asymptotically fastest?” Estimate index bytes, build time, update overhead, and number of eliminated row reads. A limited memory budget often makes a targeted covering or compressed structure more valuable than many broad indexes.

A practical selection sequence begins with the answer contract and proceeds to resource accounting rather than selecting a data structure by reputation.

Correctness Proof Checklist for Search and Index Operations

For every search algorithm or index operation, verify the following proof obligations rather than relying on a few passing examples.

  1. Contract: define admissible keys, comparator, duplicate policy, missing-value result and any output ordering.
  2. Invariant: identify which region or structural predicate is maintained—such as a binary-search candidate interval or a BST ordering property.
  3. Progress: prove that a finite measure decreases or that an iteration advances; for hashing, establish termination or bounded probes under occupancy conditions.
  4. Soundness: show that returned results satisfy the query and any declared first/last/range semantics.
  5. Completeness: show that no valid result is excluded, including duplicates and empty or extreme inputs.
  6. Update preservation: demonstrate that insertions, deletions, rotations, splits, tombstones and rebuilds preserve the index invariant.
  7. Concurrency contract: explain how the proof interacts with simultaneous updates and snapshot visibility.
  8. Resource model: state what is counted, distribution assumptions, output size, and whether construction and maintenance are included.

A search method can be efficient and still incorrect if its key semantics, boundary inclusivity, or concurrency rules are wrong. Formal reasoning and executable testing should reinforce one another.

Finding a range costs O(log n) regardless of its size.Reporting k results requires Ω(k) output work.

A Bloom filter positive response proves membership.It may be a false positive; a standard negative response is definitive under its stated assumptions.
Indexing has no cost once the index is built.Updates, logging, compaction, cache footprint, and rebuilds have continuing costs.

Use these corrections as an audit of reasoning, not as a substitute for studying a method’s full assumptions.

Review Answers and Explanations

  1. Name input representation, size, query contract, distribution, update count, model of basic operations, output cost, and memory/I/O constraints.
  2. Under uniform successful positions, expected comparisons are (n+1)/2.
  3. Every excluded left position is less than x and every excluded right position is at least x; the candidate interval shrinks to one boundary.
  4. Locating the insertion point is logarithmic but list insertion can move Θ(n) elements.
  5. Lower bound finds the first not-less-than position; upper bound finds the first greater-than position; their difference counts equals.
  6. Only when the modeled total construction plus q indexed queries is below q scans, including memory and updates.
  7. Sorted data and sorted queries can be advanced with two pointers in O(n+q) total scan work.
  8. Expected hashing relies on collision assumptions or randomization; adversarial collisions can cause linear work.
  9. Longer chains or crowded probe sequences cause more examinations; capacity and distribution control are necessary.
  10. Uncontrolled insertion can create a path-shaped tree of height Θ(n).
  11. Count page transfers, branching factor, occupancy, caching and separately fetched records.
  12. Every returned record or fixed-size result must be emitted, requiring Ω(k) output work.
  13. The trailing component is not necessarily a contiguous ordered range across all values of the leading component.
  14. It carries every projected field and necessary search information for that query; actual engine visibility may still matter.
  15. The engine must establish which row versions the transaction may see; visibility metadata may not be resolved from index contents alone.
  16. It maps terms to record lists; two sorted posting lists can be intersected by two-pointer scan in O(a+b).
  17. Bounded-cost symbol steps yield O(L) navigation in the word length L, plus traversal/output.
  18. It can return false positives, but standard construction has no false negatives for inserted items under stated assumptions.
  19. One logical update generates multiple physical index changes, logging or compaction, increasing write resource use.
  20. A low-selectivity query returns much of the table; scattered row fetches can cost more than sequential access.
  21. Probability refers to random choices or inputs; amortization bounds total cost across operation sequences.
  22. Test empty inputs, extremes, duplicates and missing keys; for concurrent updates use the documented isolation model and consistency invariants.
  23. Latency depends on physical memory accesses and locality, not only the number of logical comparisons.
  24. Measure query/update mix, p99 latency, memory, contention, index size, mutation and maintenance costs, and key distribution.
