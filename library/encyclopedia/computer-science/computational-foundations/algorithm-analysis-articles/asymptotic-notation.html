Definition, Purpose, and Scope

Asymptotic notation describes how one mathematical function is eventually bounded relative to another as an input parameter grows. In algorithm analysis, the function commonly counts elementary operations, memory locations, comparisons, transfers, or another chosen resource. The purpose is to replace implementation-specific detail with a mathematically controlled description of growth—not to predict elapsed seconds for a particular computer.

The five principal symbols are Big-O for eventual upper bounds, Big-Ω for eventual lower bounds, Big-Θ for both, and little-o and little-ω for strict asymptotic separation. These are relations among functions. An algorithm acquires one of these labels only after the analyst has chosen a cost function, a measure of input size, and (where applicable) a best-, worst-, average-, expected-, or amortized-case definition.

This is the first Level 5 specialist article in the Algorithm Analysis unit. It deepens the Algorithm Analysis overview but does not substitute for the separate specialist articles on case analysis, recurrences, or benchmarking. The mathematical examples below are instructional constructions, not measurements of production MGU systems.

Start with a Resource Function, Not a Label

A growth claim is meaningful only for a specified resource function. Write T(n) for the number of primitive operations performed on inputs of length n under a stated model, or S(n) for auxiliary memory. If the work varies among inputs of equal length, one may define T_worst(n) = max{|x|=n} T(x) over valid inputs, provided the maximum exists, or a distribution-dependent expectation. The notation alone does not select among these functions.

Consider a search procedure with an early return. A matching first element may yield constant work; a missing target may require scanning all n elements. A precise statement is “worst-case comparisons are Θ(n), while the best-case comparisons are Θ(1) for nonempty arrays.” Calling the algorithm simply “O(n)” is a conventional shorthand for a worst-case upper bound, not a theorem about every execution's exact duration.

Likewise, resource selection matters. A sorting procedure can perform Θ(n log n) comparisons but Θ(n²) moves under an unusual representation. An algorithm might have Θ(log n) comparisons and Θ(n) preprocessing. State both resources if they affect the engineering decision; one asymptotic label cannot summarize the entire cost profile.

Domain and Nonnegativity Assumptions

For the elementary definitions in this article, take f and g as real-valued functions on sufficiently large positive integers, where f(n) ≥ 0 and g(n) > 0 beyond some threshold. Runtime and operation-count functions naturally satisfy nonnegativity. Some mathematical texts instead allow signed functions by using absolute values; both conventions are valid when stated clearly, but their assumptions must not be mixed mid-proof.

The phrase eventually means that a relation holds for all n ≥ n₀, not that it works for the first few inputs. The threshold n₀ and constants in a proof can depend on the functions but cannot depend on the particular n being bounded. Under discrete integer input sizes, a relation that fails for finitely many small inputs can still hold asymptotically. A relation that fails at arbitrarily large sizes generally cannot be saved by moving the threshold.

A cost function may depend on multiple parameters, such as vertices V and edges E. An expression such as O(V+E) is meaningful only with a specified feasible domain, graph representation, and growth interpretation. This article begins with one parameter and introduces the multivariate caveat later.

Formal Big-O Definition: Eventual Upper Bound

We say f ∈ O(g) if there exist constants c > 0 and n₀ such that 0 ≤ f(n) ≤ c·g(n) for every n ≥ n₀. The constant absorbs a fixed multiplicative difference; the threshold ignores finitely many small input sizes. Thus Big-O concerns the shape of growth, not a literal comparison of the two unscaled expressions.

For example, f(n)=3n²+5n+7 belongs to O(n²). For every integer n≥1, n≤n² and 1≤n², so 3n²+5n+7≤15n². Choosing c=15 and n₀=1 completes a valid witness proof. Much smaller constants also work with a larger threshold; the definition only requires some valid witness.

A loose Big-O label may be true yet unhelpful. The same quadratic polynomial belongs to O(n³), O(n⁴), and O(2ⁿ). None is the smallest natural bound among these examples. When a tight bound has been proved, Θ(n²) communicates more information than a loose upper bound. Big-O itself never means “tightest known bound.”

Formal Big-Ω Definition: Eventual Lower Bound

We say f ∈ Ω(g) when there are constants c>0 and n₀ such that f(n) ≥ c·g(n) for every n ≥ n₀. This lower-bounds the same specified function that appears on the left. It does not automatically constitute a lower bound on every algorithm that solves a problem, which would require a separately defined computational model and a proof about all permitted algorithms.

For f(n)=3n²+5n+7, the inequality f(n)≥3n² for n≥1 proves membership in Ω(n²). The polynomial also belongs to Ω(n) and Ω(1), which are progressively less informative lower bounds. As with Big-O, a valid Big-Ω relation need not be the sharpest possible claim.

Interpret the quantifier for all sufficiently large n carefully. Seeing one unusually expensive input is not a proof that a worst-case cost function is Ω(g) for all sufficiently large sizes, unless the example generalizes to every such size. Conversely, a particular best-case execution's Ω(1) cost is not a claim that the best case ever requires linear work.

Formal Big-Θ Definition: Tight Growth Class

The relation f ∈ Θ(g) holds when there exist constants c₁,c₂>0 and n₀ such that c₁·g(n) ≤ f(n) ≤ c₂·g(n) for all n≥n₀. Equivalently, for the functions under consideration, f∈O(g) and f∈Ω(g). The constants are not required to be the same.

The polynomial 3n²+5n+7 is Θ(n²) because 3n²≤f(n)≤15n² for integer n≥1. In an algorithmic setting, a Θ result describes the growth class of the selected resource function. A bound of T_worst(n)∈Θ(n²) identifies the worst-case cost's order of growth. It does not imply that every possible input of length n requires quadratic time.

Two tight bounds on the same function can be expressed using different yet equivalent comparison functions: Θ(n log₂ n) and Θ(n ln n) denote the same class for n≥2. Logarithm bases differ only by fixed multiplicative factors. In contrast, Θ(n) and Θ(n²) are not interchangeable.

Mathematically, these symbols name sets of functions. The notation f∈O(g) makes set membership explicit. Textbooks commonly write f(n)=O(g(n)) as an accepted shorthand, but that equal sign should not be manipulated as an ordinary numerical equality. It is particularly unsafe to subtract an “O term” as if it were one uniquely defined function.

Little-o: Strictly Slower Relative Growth

We write f∈o(g) if for every ε>0 there exists a threshold n₀ such that 0≤f(n)<εg(n) whenever n≥n₀. With g(n)>0 eventually, this is equivalent to lim[n→∞] f(n)/g(n)=0. In words, no single fixed positive multiple of g is needed to dominate f; eventually any positive multiple will do.

For example, n∈o(n log n) because n/(n log n)=1/log n→0. Similarly, n log n∈o(n²) since log n/n→0. By contrast, 3n∉o(n): its ratio to n remains 3. Nevertheless, 3n∈O(n). Little-o makes a strictly stronger assertion than Big-O.

A crucial distinction is that small ratios at finitely many sample sizes do not establish a limit. Prove the limit, or directly verify the epsilon condition. For irregular or oscillating functions, the ratio might not have a limit, so one must consult the quantifiers rather than assume the ratio settles.

Little-ω: Strictly Faster Relative Growth

The dual relation f∈ω(g) means that for every constant M>0, eventually f(n)>M·g(n). Under eventual positivity, this corresponds to lim[n→∞] f(n)/g(n)=∞, or equivalently lim[n→∞] g(n)/f(n)=0. For example, n²∈ω(n log n); the ratio is n/log n, which grows without bound.

Little-ω is not interchangeable with Ω. The function 5n is Ω(n) but is not ω(n), because 5n/n=5 cannot exceed every positive constant. Likewise, n² is Θ(n²) and not ω(n²), even though its values grow as n increases. The strict relation compares the two functions, not the absolute fact that one function diverges.

Duality is useful for proofs: when f and g are eventually positive, f∈o(g) is equivalent to g∈ω(f). Similarly, f∈O(g) is equivalent to g∈Ω(f). The direction of a lower-bound symbol reverses the argument order, a frequent source of mistaken statements.

Set Inclusion and Logical Implications

Every function in Θ(g) is in both O(g) and Ω(g). Every function in o(g) is in O(g); every function in ω(g) is in Ω(g). The converses need not hold: n∈O(n) but n∉o(n); n∈Ω(n) but n∉ω(n). Membership in both broad sets is exactly the condition for Θ.

These are not five ranks on one linear ladder. Relative to a chosen g, a function may oscillate between two different powers, yielding neither Θ(g) nor a strict relation to g. Statements like “all functions are either O(g) or Ω(g)” can be established under suitable nonnegative-function assumptions via the logical negation of Big-O, but the stronger intuition that every pair has a single neat Θ growth class is false. Do not infer a tight characterization merely because a convenient upper and lower bound have both been obtained at different growth rates.

Proof discipline also requires preserving arguments: f∈O(g) and g∈O(h) imply f∈O(h) by multiplying witness constants and taking the larger threshold. But f∈O(g) does not imply g∈O(f).

Worked Proof: A Quadratic Polynomial Is Θ(n²)

Let f(n)=7n²+11n+13 for positive integers. A complete proof should display numerical constants, not just say that “the highest power dominates.” For n≥1, both n≤n² and 1≤n². Therefore 7n²≤7n²+11n+13≤31n², establishing f∈Θ(n²) with c₁=7, c₂=31, and n₀=1.

The proof is deliberately conservative. One could obtain a smaller upper constant by choosing a larger threshold, but the definition requires existence rather than optimization. Explicit witnesses help students catch an invalid step such as asserting 5n≤n² for every positive n; that inequality only holds once n≥5. Using a single safe threshold for all inequalities makes the proof straightforward.

Generalization: a polynomial with nonnegative coefficients and a strictly positive leading coefficient is Θ(nd) where d is its highest degree. Signed lower-order terms require a sufficiently large threshold to ensure the leading term dominates; a slogan about degree cannot replace that argument when signs vary.

Witness-Finding as a Small Executable Check

Code can verify a proposed bound on a finite range, but it cannot establish an all-future quantifier. The following program checks the explicit algebraic witnesses for the preceding polynomial for one thousand inputs. The proof comes from inequalities, not from the loop running to completion.

def f(n):
    return 7*n*n + 11*n + 13

for n in range(1, 1001):
    assert 7*n*n <= f(n) <= 31*n*n

assert f(1) == 31
print('finite witness check passed')

Use bounded checks as a debugging aid for arithmetic and off-by-one thresholds. If a check finds a violation, the claimed constants or threshold are wrong. If it finds none, the infinite claim remains unproved. This distinction is important in formal analysis and in measured benchmarking: finite evidence can refute a universal claim, but usually cannot prove it.

Limit Test for a Finite Positive Ratio

When both functions are eventually positive and the limit L=lim f(n)/g(n) exists with 0<L<∞, then f∈Θ(g). If the limit is zero, f∈o(g); if it diverges to positive infinity, f∈ω(g). This is a useful shortcut, not a replacement for the definitions. The conditions on the denominator and the limiting behavior matter.

For instance, f(n)=4n²+3n and g(n)=n² have ratio 4+3/n→4, so f is Θ(g). For n log n versus n², the ratio log n/n→0, proving little-o. For 2ⁿ versus a fixed-degree polynomial, standard exponential-growth results make the ratio tend to infinity.

If a ratio does not converge, the limit test is inconclusive. It is invalid to conclude “not Θ” merely from failure of a limit to exist: a bounded oscillating ratio, such as 1+(-1)ⁿ/2, stays between 1/2 and 3/2 and yields Θ even though the ratio has no limit.

Oscillation: Why a Missing Limit Is Not a Missing Bound

Define f(n)=n for even positive n and f(n)=n² for odd positive n. Then n≤f(n)≤n² for all n≥1. Thus f∈Ω(n) and f∈O(n²), but neither Θ(n) nor Θ(n²) holds. The odd subsequence defeats the linear upper bound; the even subsequence defeats the quadratic lower bound.

Now consider h(n)=n·(1+(-1)ⁿ/2). Its ratio h(n)/n alternates between 1/2 and 3/2, so no ratio limit exists, yet (1/2)n≤h(n)≤(3/2)n proves h∈Θ(n). These examples separate two distinct questions: whether the ratio converges and whether the ratio is bounded above and below by positive constants.

A practical analysis should not force a complex input-dependent algorithm into a tidy limit formula. Investigate even/odd sizes, special structural families, and other subsequences. Counterexamples arising infinitely often are particularly useful for disproving a purported eventual bound.

Limit-Test Examples in Python

Computing a few ratios makes the direction of the comparison visible. It does not prove the limit, and floating-point arithmetic becomes unsuitable for extremely large exponentials. The snippet below prints values at selected sizes and keeps the analytic conclusion separate.

import math

def ratio_linear_to_quadratic(n):
    return n / (n*n)

def ratio_nlogn_to_n2(n):
    return (n * math.log2(n)) / (n*n)

samples = (8, 32, 128, 512)
values = [(n, ratio_linear_to_quadratic(n),
              ratio_nlogn_to_n2(n)) for n in samples]
assert all(values[i+1][1] < values[i][1]
           for i in range(len(values)-1))
assert values[-1][2] < values[0][2]
print(values)

The first ratios equal 1/n; the second equal log₂(n)/n. Their convergence to zero follows from mathematics, while the samples illustrate the trend over the chosen sizes. Note that log₂(n)/n is not decreasing from every small n; selecting a sensible range is part of interpreting empirical examples.

Constant Factors: What Is Suppressed and What Is Not

Asymptotic classes ignore fixed nonzero multiplicative constants. For a>0, an²∈Θ(n²). But “constants do not matter” is an incomplete engineering conclusion. At practical scales, a routine performing 0.001n² elementary operations may outperform one performing 1000n log n operations for a substantial range of n; memory locality, allocations, vectorization, and hardware parallelism can widen the gap.

The correct reading is narrower: for sufficiently large n, the order-of-growth comparison dominates fixed leading constants under a common cost model. The crossover point may lie outside the relevant workload range. Real workloads are finite, and the cost of an operation may vary; those facts motivate a separate benchmarking analysis, not a rejection of asymptotic reasoning.

Furthermore, a quantity only counts as a fixed constant if it is independent of the variable tending to infinity. If the alphabet size σ, word length w, number of processors p, or dimension d scales with n, suppressing it without an explicit assumption can change the claimed growth rate.

Logarithm Bases and Their Domains

For every fixed pair of bases a,b>1, the identity logₐ n = (logᵦ n)/(logᵦ a) makes the ratio a constant. Therefore log₂ n∈Θ(ln n) as n→∞. Algorithm texts often omit the base in asymptotic expressions for this reason. A binary search performs a number of halvings proportional to log₂ n; switching to natural logarithms does not alter the Θ class.

One must still distinguish log n from (log n)² and log log n. The former grows strictly slower than the square, and log log n∈o(log n) for sufficiently large n. Parentheses matter: log(n²)=2 log n, whereas (log n)² is a different function.

At small n, logarithms may be zero or undefined; use an appropriate threshold, such as n≥2. Some analyses prefer log(n+1) or max(1, log n) to avoid boundary problems. Such modifications often preserve the same asymptotic growth class, but their exact domains should be stated.

Growth-Rate Reference Hierarchy

For fixed real constants 0<α<β, fixed integer k≥1, and fixed c>1, the usual hierarchy is broadly 1, log log n, log n, (log n)^k, n^α, n^β, cⁿ, and n!, as n becomes large. The exact order among different polylogarithms depends on their exponents, and any finite list omits numerous intermediate functions.

Polynomial versus Polylogarithmic versus Exponential Growth

For any fixed real ε>0 and fixed k>0, (log n)^k∈o(n^ε). A positive-degree polynomial eventually overtakes any fixed power of the logarithm. Similarly, for fixed c>1 and fixed d≥0, n^d∈o(cⁿ). Repeated ratios or elementary calculus can establish the latter; for example (n+1)^d/n^d→1, while c^(n+1)/cⁿ=c>1.

Exponents need close inspection. 2^n is exponential in n, but 2^(log₂ n)=n is linear; the exponent itself can depend on input size. Likewise, n^(log n) is not a fixed-degree polynomial, while (log n)^3 is polylogarithmic. Statements about “exponential algorithms” must clarify which input parameter appears in the exponent, particularly when an input length encodes a numerical value in binary.

Asymptotic categories can be appropriate but coarse. A function of the form n log log n is strictly between linear and linearithmic, and a function like 2^(√n) is superpolynomial but subexponential under common definitions. When accuracy matters, retain the actual function rather than force it into a simplified label.

Bit Length: Numerical Magnitude Is Not Input Length

An algorithm processing an integer N may use an input length of b=⌊log₂N⌋+1 bits rather than the numerical value N itself. A loop that counts from 1 to N takes Θ(N) iterations under constant-cost arithmetic, but relative to the bit length b its number of iterations is Θ(2^b) for b-bit values near the top of their representable range. What looked linear in N is exponential in the standard binary encoding length.

Conversely, repeatedly dividing N by two takes Θ(log N) iterations, which is Θ(b) iterations in the bit-length parameter. That does not imply Θ(b) bit operations if each division processes a growing b-bit integer. Different models may count machine-word operations at constant cost while bit-complexity analysis charges for operand length. Neither model is inherently wrong; each describes a different resource abstraction.

State the input representation explicitly for arbitrary-precision arithmetic, graph encodings, combinatorial search, and pseudopolynomial algorithms. A guarantee in the magnitude of a numeric parameter can be much weaker than a polynomial-time guarantee in the number of input bits.

Case I: Constant, Linear, and Triangular Loops

Operation counting begins with control flow. An empty loop body is not free in actual execution, but under a unit-cost model we can assign a fixed charge to the test and increment. If a loop iterates n times and performs constant work each time, T(n)=an+b for constants a>0, b≥0, and therefore T∈Θ(n). Two independent linear loops yield an+bn+c∈Θ(n), not Θ(n²), because their costs add rather than multiply.

A triangular loop has the outer index i ranging from zero through n−1, with the inner index ranging from zero through i. Its body executes 1+2+···+n=n(n+1)/2 times. Since n²/2≤n(n+1)/2≤n² for n≥1, the cost is Θ(n²). A full n×n nested loop also has Θ(n²) iterations, but its exact count is n², not the triangular number.

When the inner bound is data-dependent, a worst-case bound requires maximizing over allowed inputs. An analyst cannot infer Θ(n²) merely from the visual presence of two for statements; triangular bounds, early exits, and nonlinear index updates must be counted explicitly.

def triangular_count(n):
    count = 0
    for i in range(n):
        for j in range(i + 1):
            count += 1
    return count

for n in range(30):
    assert triangular_count(n) == n*(n+1)//2
assert triangular_count(10) == 55

Case II: Halving and Doubling Loops

A loop whose positive integer state is repeatedly halved usually has Θ(log n) iterations. Starting at n, the states are approximately n,n/2,n/4,...,1. After k reductions, the value is at most about n/2^k; the threshold occurs when 2^k has the same order as n, so k∈Θ(log₂ n). Precise counts depend on whether the loop checks x>1, x>0, and whether integer division rounds down.

Doubling a counter from 1 until it exceeds n similarly takes Θ(log n) iterations. A loop nested inside another logarithmic loop can yield Θ((log n)²) iterations, but if the inner loop's iteration count depends on the outer loop's decreasing state, one must sum its level costs. The syntactic number of loops remains an unreliable substitute for arithmetic.

def halving_steps(n):
    assert n >= 1
    steps = 0
    while n > 1:
        n //= 2
        steps += 1
    return steps

for n in range(1, 1000):
    # floor(log2 n) for positive integer n
    assert halving_steps(n) == n.bit_length() - 1
assert halving_steps(1024) == 10

The code's bit_length() assertion is a precise property of its integer halving convention. The asymptotic conclusion holds for all positive n, but the exact count here is not necessarily the exact count of binary search, whose interval and termination conventions differ.

Case III: Harmonic Sums and the n log n Class

One common source of n log n growth is the harmonic series Hₙ=1+1/2+···+1/n. For positive n, integral comparison yields bounds on the order of log n, so Hₙ∈Θ(log n). Therefore nHₙ∈Θ(n log n). Such terms arise in nested iterations whose inner counts scale approximately like n/i, in average-case analyses, and in some divide-and-conquer recurrences.

The word approximately must be treated as a proof obligation. If the inner count is ⌊n/i⌋, the sum differs from nHₙ by at most n, so both still have Θ(n log n) growth. If the inner count is instead i, the sum is triangular and Θ(n²). Similar-looking loops can therefore belong to different asymptotic classes depending on their precise bounds.

def divisor_style_count(n):
    return sum(n // i for i in range(1, n + 1))

assert divisor_style_count(1) == 1
assert divisor_style_count(10) == 27
assert divisor_style_count(100) == sum(100 // i for i in range(1, 101))

The last assertion checks the arithmetic implementation, not the asymptotic theorem. Proving the Θ(n log n) bound requires comparing the sum with harmonic-series estimates; a numerical plot or one finite evaluation is not enough.

Sequential Composition and Dominant Terms

Suppose a procedure runs stage A for T_A(n) operations and then stage B for T_B(n) operations. Total cost is T(n)=T_A(n)+T_B(n)+O(1) under the same model. If T_A∈Θ(n²) and T_B∈Θ(n log n), then T∈Θ(n²) for eventually nonnegative costs; the quadratic stage dominates. More generally, when functions are nonnegative, the sum is Θ of the larger order if one term asymptotically bounds the other.

Sequential composition is not the same as nesting. A pair of consecutive O(n) loops is O(n), whereas the full Cartesian product of two n-element collections usually triggers Θ(n²) body executions. Also remember that a Big-O upper bound on each stage alone does not certify a tight total bound. For example, two stages both in O(n²) could each perform constant work.

In a pipeline with different input sizes, use distinct variables. Sorting m records and searching n records gives a cost such as Θ(m log m+n) when assumptions justify it; reducing that expression to a single-n form requires a relationship between m and n.

Multiplication and Nested Work

If an outer loop performs n iterations and each iteration independently performs exactly m constant-cost operations, the total is Θ(nm). For a single variable m=n, this becomes Θ(n²). For an outer loop that calls a function whose cost grows with i, the total is instead a sum Σᵢ T_inner(i). It is generally wrong to multiply the maximum inner cost by n and claim Θ merely because this yields a valid O bound.

For example, if T_inner(i)=Θ(i) and i ranges from 1 to n, the sum is Θ(n²). If only one of the n iterations performs Θ(n) work and the rest cost Θ(1), the sum is Θ(n), even though n·max_i T_inner(i) is Θ(n²). The maximum-times-count rule is safe as an upper-bound technique but can be quite loose.

Exact iteration counts also depend on whether expensive work occurs only after a predicate succeeds. An average-case Θ claim would require a model for how often that predicate is true; asymptotic notation by itself supplies no probabilities.

Recurrences: Bounding Recursive Algorithms

Recursive programs lead to cost relations. Binary search on an n-element sorted array performs one comparison and makes one recursive call on at most about half the elements, giving T(n)=T(⌊n/2⌋)+Θ(1) with a constant-size base case. Repeated substitution yields Θ(log n). Merge sort makes two approximately half-sized calls and performs Θ(n) merging work, giving T(n)=2T(n/2)+Θ(n) under a simplified even-size assumption, and Θ(n log n) total work.

The asymptotic notation inside a recurrence must be handled carefully. Writing T(n)=2T(n/2)+O(n) often establishes only an upper bound unless the nonrecursive work also has a matching lower bound. To deduce a tight Θ result, show the necessary assumptions or derive both inequalities. Base cases, rounding, and recursive subproblem count are not optional details when the aim is a formal proof.

The full methods—recursion trees, substitution, Master Theorem conditions, and irregular partition sizes—are developed in Recurrence Relations in Algorithm Analysis and Recursion Trees and the Master Theorem. This section shows how their conclusions connect to asymptotic notation.

Binary Search: Upper and Lower Cost Bounds

With a sorted random-access array and a comparison model, each unsuccessful binary-search step can eliminate about half the remaining candidate positions. After k comparisons, at most about n/2^k positions remain, so the recursive or iterative search uses O(log n) comparisons in the worst case. For an unsuccessful search on appropriate n-element instances, distinguishing the possible insertion intervals requires logarithmically many binary decisions, which yields a matching Ω(log n) worst-case comparison bound under the stated model.

Thus worst-case comparison count is Θ(log n). But a successful target found at the first midpoint can take Θ(1) comparisons, so one cannot claim Θ(log n) comparisons for every call. The bound also assumes constant-time indexed array access; traversing a linked list to find each midpoint changes the overall work. If a comparator analyzes long strings, the cost of one comparison may depend on string length.

Note that lower-bound reasoning for binary search does not automatically prove a lower bound for all conceivable search problems with preprocessing or stronger operations. The precise model defines the claim's scope.

Merge Sort: A Tight Bound with Distinct Resources

Under standard comparison sorting with arrays, merge sort partitions n elements into halves, recursively sorts both halves, and merges in linear work. The recursion depth is Θ(log n) and each level collectively processes Θ(n) elements, yielding Θ(n log n) comparison and element-processing work in the usual model. A proof should account for the leaf work and show that the Θ(n) merge assumption is valid.

Auxiliary space is a different function. A common top-down array merge-sort implementation allocates an auxiliary buffer of Θ(n) elements and maintains O(log n) recursion frames, so its total extra space remains Θ(n) under these conventions. In-place variants and language-specific implementations may have different memory behavior. One should not infer Θ(log n) total extra memory merely from the call-stack depth.

Merge sort demonstrates why two distinct mathematical claims may be required for one algorithm: T_worst(n)∈Θ(n log n) and S_aux(n)∈Θ(n). They are both asymptotic descriptions, but they concern different resources.

Worked Program: Count Comparisons in Two Search Strategies

Instrumenting a program helps connect an abstract cost with a particular implementation. The example counts comparisons rather than microseconds. The linear search's unsuccessful path checks all n positions; the binary search's unsuccessful path halves a sorted search range. These observations are compatible with the respective Θ(n) and Θ(log n) worst-case comparison bounds.

def linear_search_count(a, target):
    comparisons = 0
    for value in a:
        comparisons += 1
        if value == target:
            return comparisons
    return comparisons

def binary_search_count(a, target):
    lo, hi = 0, len(a)
    comparisons = 0
    while lo < hi:
        mid = lo + (hi - lo) // 2
        comparisons += 1
        if a[mid] == target:
            return comparisons
        if a[mid] < target:
            lo = mid + 1
        else:
            hi = mid
    return comparisons

for n in (8, 16, 32, 64, 128):
    a = list(range(n))
    assert linear_search_count(a, -1) == n
    assert binary_search_count(a, -1) <= n.bit_length()
assert binary_search_count([], -1) == 0

This binary-search routine sometimes executes two order/equality tests per visited midpoint, but its counter intentionally records midpoint probes rather than all primitive relational operations. That is a valid cost measure if named accurately. A different instrumentation contract could count both tests and obtain another constant factor without changing the asymptotic class.

Worst Case, Best Case, Average Case, and Expectation

Big-O is not a synonym for worst-case analysis. An analyst can write E[T(n)]∈O(n) for expected runtime under a stated probability model, T_best(n)∈Θ(1) for minimum runtime, or T_worst(n)∈Ω(n) for a lower bound on the worst case. The symbol and the input-case qualifier answer different questions.

Worst-case analysis takes a maximum over the admitted inputs at each size. Average-case analysis weights costs according to an input distribution, and expected analysis may additionally involve the algorithm's own random decisions. A randomized quicksort's expected runtime can be Θ(n log n) while its worst-case runtime remains Θ(n²). There is no contradiction: two different resource functions are being bounded.

Amortized analysis is different again. It bounds total cost across a sequence of operations—often deterministically over every allowed operation sequence—rather than averaging over a distribution of random inputs. The related units on Worst-Case and Average-Case Analysis, Randomized Algorithm Analysis, and Amortized Analysis develop these distinctions in full.

Amortized Bounds Are Not Input Averages

Consider a dynamically resized array that doubles its capacity whenever full. A particular append can cost Θ(n) if n existing elements must be copied during a resize. Nevertheless, over n appends starting from a fixed empty array, the total number of copied elements is below a constant multiple of n, because expansion capacities form a geometric series. Consequently the aggregate total cost is O(n) and the amortized cost per append is O(1) under the model.

This does not assert that each append individually runs in O(1), nor that the expected append time is O(1) under an unspecified distribution. A sequence cost divided by the number of operations is an accounting technique. It can give a worst-case-over-sequences guarantee without assuming randomness.

For a tight statement, one can observe that even an append not triggering a resize must perform at least some constant work, yielding Ω(n) total over n operations. Together with the O(n) aggregate bound, that proves Θ(n) total cost and Θ(1) average amortized cost for the sequence. More intricate structures require accounting or potential-function proofs.

Lower Bounds on a Problem versus a Specific Algorithm

Writing T_A(n)∈Ω(n log n) establishes a lower bound on an algorithm A's specified cost function, not necessarily a lower bound for the problem itself. To prove that every algorithm within a model needs Ω(n log n) resources in the worst case, the proof must range over the allowed algorithms and their inputs. Such lower bounds are stronger and depend on the permitted operations.

For comparison sorting of distinct keys, a deterministic comparison-based sorting algorithm must distinguish n! possible input orders. A binary comparison decision tree needs height at least ⌈log₂(n!)⌉=Ω(n log n), yielding a worst-case comparison lower bound for this model. Algorithms that exploit bounded integer keys, counting, radix operations, or other noncomparison primitives are not constrained in the same way by that decision-tree argument.

This is why the phrase “sorting is Ω(n log n)” is incomplete. Say “comparison sorting of arbitrary distinct keys requires Ω(n log n) comparisons in the worst case” or another appropriately qualified theorem. The sister article Lower Bounds and Decision Trees develops the proof and model boundaries.

Proving Bounds by Comparison and Inequalities

For polynomials and sums, a clean proof often uses elementary inequalities. To show f(n)=2n²+9n+10∈O(n²), observe that for n≥1, 9n≤9n² and 10≤10n², giving f(n)≤21n². To show Ω(n²), use f(n)≥2n². The two witnesses imply Θ(n²).

More generally, to upper-bound a sum of nonnegative costs, bound each summand and then add. To lower-bound a sum, retaining only a positive subset of the terms may suffice. For Σᵢ₌₁ⁿ i, the upper bound Σi≤n·n=n² is immediate, and the last roughly n/2 terms each contribute at least n/2, yielding Ω(n²). This avoids memorizing a closed-form formula.

Such proofs are robust against off-by-one changes and implementation details. Their key weakness is that a convenient inequality may be loose; if an upper bound turns out substantially larger than an established lower bound, investigate whether the gap reflects real algorithmic behavior or merely crude counting.

Bounding by Substitution and Induction

For a recurrence T(n)=2T(n/2)+n on powers of two with T(1)=1, one may guess T(n)≤cn log₂ n+dn and verify it inductively with suitable constants. Another route unrolls the recurrence to reveal log₂ n levels of n work each. A formal upper-bound proof needs a base case and must show that the inductive step preserves the claimed inequality.

An incorrect guess can fail because it is too weak or because its constants leave no slack for a lower-order additive term. Strengthening an inductive hypothesis with an additional linear term, adjusting the threshold, or choosing a larger constant are common remedies. The objective is not to manipulate Big-O symbols blindly but to construct an actual comparison inequality between numerical functions.

Lower bounds may be established with a separate induction, a per-level work argument, or an adversarial input family. When both match, a Θ classification follows. Be careful with ⌊n/2⌋ and ⌈n/2⌉; either treat rounding rigorously or state that the simplified proof is for powers of two before generalizing.

Big-O Algebra: Addition, Multiplication, and Composition

For eventually nonnegative functions, if f₁∈O(g₁) and f₂∈O(g₂), then f₁+f₂∈O(g₁+g₂). If the terms and bounds are nonnegative, their product satisfies f₁f₂∈O(g₁g₂). In both proofs, choose a threshold after which each ingredient's inequality holds and multiply or add the witness constants.

Composition is more delicate. From f∈O(g) it does not automatically follow that f(h(n))∈O(g(h(n))) unless h(n) eventually enters the large-argument region on which the bound holds. Even then, the composition's input domain and monotonicity conditions can matter for further simplification. This caution is important when a preprocessing phase maps an n-element input to a new size h(n).

For tight sums, one may often use Θ(max(g₁,g₂)) when two nonnegative components have matching Θ bounds, because their sum lies between the maximum and twice the maximum up to constants. This does not justify dropping input-dependent parameters or assuming every algorithm's stage cost fits one scalar n.

The Fallacy of Treating Big-O as Ordinary Equality

It is customary to write 3n+2=O(n), but strictly the right side is a collection of functions. More precise notation is 3n+2∈O(n). As a consequence, statements such as “O(n)=O(n²)” are false as set equalities: O(n) is a proper subset of O(n²) for positive integer n under the ordinary definitions.

Algorithm literature also uses expressions such as f(n)=g(n)+O(h(n)). This means there exists a function r∈O(h) for which f=g+r. It does not name one fixed value of “O(h).” One cannot cancel two different anonymous O terms or assume symmetry of this displayed equality. For instance, n=O(n²) holds, but n²=O(n) does not.

When doing proofs, replace O symbols with explicit inequalities or a named remainder function. The reader can then check quantifiers, domains, and constants. Informal symbolic shorthand is acceptable in a correctly interpreted exposition; it becomes dangerous when used as a substitute for mathematical reasoning.

Counterexample: Big-O Is Not a Worst-Case Contract by Itself

Suppose algorithm A has best-case cost T_best(n)=2, worst-case cost T_worst(n)=n², and a distribution-dependent expected cost E[T(n)]=n+O(1). These three functions may simultaneously satisfy T_best∈O(1), T_worst∈O(n²), and E[T]∈O(n). The growth symbols make no choice about which function to discuss.

Even the statement T_worst∈O(n²) does not guarantee that there exists an input incurring Θ(n²) work. It could describe a linear-time algorithm with an intentionally loose upper bound. To establish a tight worst-case bound one needs a matching Ω(n²) argument about the maximum cost for every sufficiently large input size.

For a credible performance claim, list at least the input size, what constitutes one unit of cost, which input family is admitted, whether the bound is upper or tight, and the case/expectation condition. If any are unstated, the formula should be treated as an abbreviated summary rather than a complete specification.

Counterexample: Infinite Subsequence Failures

One failed instance below a proposed threshold does not refute Big-O. One failure for every possible threshold does. Let f(n)=n² on powers of two and f(n)=n otherwise. To disprove f∈O(n), select arbitrarily large powers of two. At those inputs f(n)/n=n, so no constant c can dominate all sufficiently large values.

To disprove f∈Ω(n²), choose arbitrarily large n that are not powers of two. There the ratio f(n)/n²=1/n tends to zero, contradicting any fixed positive lower constant. Nonetheless f∈O(n²) and f∈Ω(n) hold. This is a clear demonstration that widely separated lower and upper bounds do not imply an intermediate neat Θ label.

Subsequence reasoning is especially valuable for algorithms whose costs depend on parity, powers of two, table-resize thresholds, or special input patterns. A finite benchmark grid can miss exactly the sizes that invalidate a claimed bound.

Counterexample: Comparing Algorithms by Their Labels

An implementation with cost T_A(n)=10⁶n is Θ(n); another with T_B(n)=n² is Θ(n²). Although A has the better asymptotic growth, B performs fewer counted operations for positive n below one million. The two formulas cross near n=10⁶ under this simplified uniform operation model. Even that crossover says little about real elapsed time if the operations differ.

Moreover, saying “algorithm A is O(n), algorithm B is O(n²), therefore A is better” is logically incomplete. B might also be Θ(n), because O(n²) is only an upper bound. A reliable asymptotic comparison needs sufficiently informative bounds on both actual cost functions, and usually comparable operation models and input constraints.

def cost_a(n):
    return 1_000_000*n

def cost_b(n):
    return n*n

assert cost_b(1000) < cost_a(1000)
assert cost_a(2_000_000) < cost_b(2_000_000)
assert cost_a(1_000_000) == cost_b(1_000_000)

The example is intentionally arithmetic, not a benchmark. It illustrates why an asymptotic conclusion can be technically correct but operationally irrelevant at the sizes an organization actually handles.

Asymptotic Bound versus Exact and Empirical Cost

An exact operation-count formula, such as n(n−1)/2 comparisons for a specific nested loop, contains more information than the statement Θ(n²). The asymptotic notation groups many such functions and erases lower-order detail. A benchmark adds a different kind of information: elapsed time under a machine, implementation, compiler, input distribution, and measurement protocol.

Three claims should therefore be kept separate. The source program may be proved to execute a particular number of abstract operations; that count may be classified asymptotically; and a concrete implementation may be measured on actual hardware. A compiler can fuse loops, remove unused computations, vectorize a transformation, or change allocations, meaning measured time is not necessarily proportional to a naive source-level count.

Benchmarking should not be treated as the final proof of an asymptotic theorem. Timing results over a limited input range may be dominated by warmup, cache sizes, runtime startup, background tasks, and algorithm crossover points. See Algorithm Benchmarking and Profiling for measurement design.

Space Complexity: Which Storage Is Counted?

A claim that an algorithm uses O(n) space should specify whether it includes the input, output, stack frames, temporary buffers, caches, and persistent indexes. Standard auxiliary-space analysis commonly excludes storage for the input and output but includes working memory, although conventions vary. For a recursive function on n nested elements, call-stack depth alone may be Θ(n) even when each frame has O(1) local storage.

A breadth-first tree traversal can retain a queue proportional to the maximum frontier width, which is at most O(n) nodes for an n-node tree. A depth-first traversal's explicit or implicit stack may be O(h), where h is tree height; a path-shaped tree has h=Θ(n), while a balanced tree has h=Θ(log n). In both cases, total visiting time may remain Θ(n). Runtime and space classes are independent dimensions.

Do not confuse allocation count with peak live memory. A program can allocate O(n) objects over its lifetime and reuse a constant-size buffer, or allocate a single Θ(n)-sized array. Both may involve O(n) total allocation volume but have different peak-space behavior depending on deallocation and reuse patterns.

Cache and External-Memory Models

A unit-cost RAM model often treats one indexed array access as constant work. On modern machines, the time depends on memory hierarchy, prefetching, and locality. An external-memory model instead tracks transfers of blocks containing B elements between slow and fast memory. A sequential scan of n elements requires O(n/B) block transfers under suitable layout and caching assumptions, even though it still inspects Θ(n) elements.

Similarly, cache-aware algorithms may optimize the number of transfers while leaving arithmetic operation counts unchanged. It is therefore possible for two algorithms to share a Θ(n log n) comparison bound and differ substantially in their cache-miss costs. Parallel algorithms introduce yet another resource: total work and critical-path span need separate functions.

These are not exceptions to asymptotic notation. The notation applies to whichever resource function the model defines. The specialist articles on Cache and External-Memory Complexity and Parallel Algorithm Analysis develop the corresponding measures.

Multiple Parameters: Θ(V+E), Θ(nm), and Hidden Constraints

For graph algorithms using adjacency lists, a full traversal is often expressed as Θ(V+E), where V is the number of vertices and E the number of edges, provided all vertices or relevant components are processed and the representation allows neighbor enumeration in proportional time. One cannot replace this with Θ(V²) for sparse graphs without losing information. Under a simple undirected graph model, E≤V(V−1)/2, but that domain restriction does not make V+E always quadratic.

In a function T(n,m), writing O(nm) means there exist c and thresholds such that the inequality holds on the chosen joint domain; the precise threshold convention may vary. Comparing n+m to nm requires the domain: for n,m≥1, n+m≤2nm is true, but along n=1, m growing, the two remain comparable, while their behavior along n=m may differ greatly. Asymptotic equivalence must address the whole intended domain.

If one variable is fixed by the application, say m=10, nm is Θ(n). If m scales as n, the same formula is Θ(n²). Carry both parameters until a justified relationship is available.

Probabilistic Models and Expected Asymptotic Bounds

An expected-cost claim is a statement about a function defined using a probability distribution: E[T_n]=Σₓ P(X_n=x)T(x) for discrete inputs, potentially with additional randomness internal to the algorithm. One can then prove E[T_n]∈O(g(n)) by upper-bounding the expectation. The asymptotic notation itself is deterministic; it is applied to a deterministic function of n obtained after averaging.

A statement such as “expected O(n log n)” should identify the randomness. In randomized quicksort, a random pivot-selection strategy can yield expected Θ(n log n) comparisons under common assumptions for distinct keys, while specific random-choice sequences can still induce Θ(n²) work. In contrast, an average-case claim for deterministic insertion sort depends on an assumed distribution over input permutations.

Bounds with high probability concern tail probabilities, such as P(T_n>cg(n)) becoming small; they are different from expectations. It is possible to have a finite expectation while rare events incur very large costs. See Randomized Algorithm Analysis for the correct probability tools and scope.

How to Prove a Bound: An Editorial Checklist

Begin by naming the input set and the size parameter. State what is being counted and whether the function refers to an individual execution, a maximum, a minimum, an expectation, or an operation sequence. Choose a comparison function appropriate to the observed control flow or recurrence. Write an upper or lower numerical inequality, with constants and threshold, and justify every transformation. Do not substitute a graph of sample points for these quantifiers.

For an upper bound, conservative overcounting is allowed. For a lower bound, identify a subset of unavoidable work or a suitable input family under the declared case definition. If both estimates match, use Θ. If they do not, report the gap rather than silently upgrading O to Θ. For little-o and little-ω, use an epsilon or arbitrarily-large-factor proof, or a valid ratio limit.

Finish by translating the mathematical conclusion back into algorithmic language: “For a sorted array stored with constant-time indexing, the worst-case number of probes in this binary-search implementation is Θ(log n).” That sentence is more useful than the bare label “logarithmic.” It supplies the resource, conditions, and extent of the guarantee.

Worked Scenario I: Catalog Lookup Without an Index

A catalog contains n unsorted records, and a request asks whether a specified exact key is present. If the program scans sequentially, the best case takes one comparison when the first record matches. A missing key requires testing all n records, giving Θ(n) worst-case comparisons. There is no contradiction between the two outcomes; they are different cost functions.

Suppose the organization sorts the catalog once and then performs q lookups. Under conventional comparison-based sorting and binary search on a random-access array, a simplified lifecycle model is Θ(n log n+q log n) comparisons, ignoring updates. If q is tiny, preprocessing may not be worthwhile; for repeated queries, the cost can amortize across uses. If the catalog changes frequently, maintaining sorted order adds further work.

The correct comparison is not “linear search O(n) versus binary search O(log n)” in isolation. The algorithmic contract changes when sorting becomes a prerequisite. The neighboring Searching and Indexing Analysis article treats construction and maintenance costs.

Worked Scenario II: A Logarithmic Routine with Expensive Comparisons

A binary-search implementation finds records by comparing long text keys. Suppose the comparator may inspect up to L characters, so one comparison costs O(L) character examinations. The search takes O(log n) comparator invocations, yielding O(L log n) character examinations in the worst case under this simple upper model. If keys share long common prefixes, this upper bound may be approached; if the first character usually differs, actual cost may be much smaller.

This example exposes a hidden assumption in the expression “binary search is O(log n).” That statement ordinarily counts comparisons on abstract keys of constant comparison cost. For variable-length strings, arbitrary-precision integers, or structured objects, the comparison cost deserves its own parameter. There are also specialized data structures that exploit prefixes and alter the bound.

A sound report should name the counted primitive. Keeping L visible avoids promising a logarithmic number of character operations when only the number of comparator calls is logarithmic.

Worked Scenario III: One Million Operations of Overhead

A data-processing algorithm initializes a large fixed lookup table once per invocation, then processes n records in linear time. Model its work as T(n)=1,000,000+8n abstract operations. This function is Θ(n), because a fixed initial cost is eventually dominated by the linear term. Yet for n=100, the fixed overhead overwhelmingly dominates actual work.

If the system processes 1,000 small batches separately, it may pay that initialization cost 1,000 times. If the table can be reused safely across batches, aggregate performance improves substantially even though the per-record growth class under a large single-batch model remains Θ(n). The relevant input-size and lifecycle model must reflect the deployment pattern.

Thus asymptotic analysis can identify the scalable component but cannot make the overhead disappear. The operational recommendation might be batching or reuse, not choosing a different asymptotic algorithm. This is precisely why analytic bounds and profiling evidence should be used together.

Worked Scenario IV: Index Build versus Query Volume

Assume a static dataset of n items. Building a balanced search index costs Θ(n log n) comparisons; each query then costs Θ(log n) in a worst-case comparison model. A naive unsorted scan costs Θ(n) per query with no preprocessing. For q independent lookups, the simplified totals are Θ(qn) and Θ(n log n+q log n), respectively.

The second total is preferable asymptotically in several regimes, but not necessarily for q=1 or for tiny n. Its extra memory, construction effort, update cost, and access pattern may alter the decision. If a hash index is allowed, average expected lookup could be different, again subject to hash-function and adversarial assumptions.

Keeping q and n separate makes the trade-off legible. An expression reported only in n would hide a major operating driver. The lesson is to bound a complete workload rather than celebrate the complexity of a single isolated operation.

Worked Scenario V: Subsets and Search Pruning

Enumerating all subsets of n distinguishable elements necessarily produces 2ⁿ outputs, so any explicit-output algorithm requires Ω(2ⁿ) output actions even if its internal branching overhead is optimized. A standard binary include/exclude recursion visits Θ(2ⁿ) leaves and Θ(2ⁿ) total nodes, giving Θ(2ⁿ) node visits; if it copies an O(n)-length representation at each leaf, the total character or element-writing cost can be Θ(n2ⁿ).

Pruning may substantially reduce work on some instances of a decision problem, but it does not automatically remove exponential worst cases. Furthermore, solving for one feasible subset and enumerating every subset are different contracts; an output-size lower bound for enumeration does not imply a corresponding lower bound for every related decision variant.

Use the language of the guarantee carefully: “worst-case recursion-tree nodes O(2ⁿ)” is a legitimate upper statement for this particular binary branching routine. “The problem inherently needs exponential time” is a much stronger assertion and usually demands a separate lower-bound or complexity-theoretic argument.

Worked Scenario VI: Memory-Constrained Graph Traversal

A graph traversal with adjacency lists can take Θ(V+E) time when visiting a whole graph. Recursive depth-first search additionally uses stack space proportional to traversal depth, up to O(V). Iterative depth-first search shifts that state to a programmer-managed worklist; its memory bound depends on the exact push and visited-marking policy. A breadth-first search often uses a frontier whose width can be Θ(V).

All three can have linear time in V+E while their peak memory profiles, traversal order, and failure modes differ. The asymptotic notation exposes worst-case growth but does not determine whether a particular implementation breaches a runtime's recursion-depth guard or the system's memory budget at moderate V.

Engineering review should therefore record both T(V,E) and S(V,E), state graph representation and marking policy, and identify relevant depth and width characteristics. A single time-complexity label cannot adjudicate reliability.

Neither the strongest-looking symbol nor the smallest-looking bound is inherently “best.” Select the relation that the evidence actually proves and that the decision requires. An upper bound may be operationally sufficient; a Θ bound may be necessary to distinguish algorithms with comparable performance claims. A lower bound on all allowed algorithms requires a different proof scope from a lower bound on one implementation.

Common Misconceptions and Corrections

MisconceptionCorrection
“O means worst case.”O is an upper-bound relation; worst case specifies a separate cost function.
“O(n²) means the routine always takes quadratic time.”It is compatible with O(n), O(1), and many other smaller growth classes.
“Ω(n log n) for a sorting program proves sorting itself needs that much work.”A problem lower bound requires quantifying over every allowed algorithm in a declared model.
“Θ means exact runtime.”Θ suppresses positive constant multipliers and lower-order terms.
“Little-o and Big-O are interchangeable.”Little-o is strict relative growth; O permits constant-factor equivalence.
“If a ratio has no limit, Θ is impossible.”A ratio can oscillate between two positive constants and still give Θ.
“Two loops mean n².”Sequential loops add costs; nested and data-dependent bounds require explicit counting.
“Logarithmic always means log base two.”Every fixed base greater than 1 changes logarithms only by a constant factor.
“A finite benchmark establishes asymptotic complexity.”Measurements can identify trends or counterexamples, not normally prove eventual universal bounds.
“Constants can be ignored in performance decisions.”Constants are suppressed in asymptotic classification but matter at practical sizes.
“A smaller O expression guarantees an algorithm is faster.”Loose upper bounds and differing work models can make such comparisons invalid.
“Polynomial in N is polynomial in the input length.”Binary input length can be Θ(log N); pseudopolynomial bounds require special care.

Review Questions with Worked Answers

1. Give explicit witnesses for 5n²+2n+1∈O(n²). Answer: for n≥1, 5n²+2n+1≤8n², so c=8 and n₀=1 work.

2. Is that polynomial Θ(n²)? Answer: yes, since it is also at least 5n² for n≥1.

3. Is n∈o(2n)? Answer: no. The ratio is 1/2 rather than tending to zero. It is Θ(2n).

4. Is n log n∈o(n²)? Answer: yes, because (log n)/n→0.

5. Does T(n)∈O(n²) imply T(n)∈Ω(n²)? Answer: no. For example T(n)=n is O(n²) but not Ω(n²).

6. What is the difference between Θ(n) comparisons and Θ(n) seconds? Answer: one is an abstract count; the other is a concrete timing assertion for which the input-size-to-time interpretation and platform would need definition.

7. How many iterations occur in a triangular double loop? Answer: Σᵢ₌₁ⁿ i=n(n+1)/2∈Θ(n²).

8. What is the class of n+n log n for n≥2? Answer: Θ(n log n), because the logarithmic factor eventually dominates the constant 1 in the multiplier.

9. If f(n)/g(n) oscillates between 1 and 3, can f be Θ(g)? Answer: yes. Bounded positive ratios provide direct witnesses even if the ratio fails to converge.

10. Why is a proof with a single finite timing experiment insufficient? Answer: asymptotic definitions require inequalities for every input size beyond some threshold; finite evidence does not establish that quantifier.

11. How does O(V+E) differ from O(V²)? Answer: the first retains sparse versus dense graph variation; O(V²) is a coarser upper bound on simple graphs when E=O(V²), not generally a tight description of traversal work.

12. Is 2^(log₂n) exponential in n? Answer: no; it simplifies exactly to n for n>0.

13. If an algorithm is Θ(n) in numeric value N, is it polynomial in the bit length of N? Answer: not necessarily; Θ(N) can be exponential in log₂N.

14. Can a single append to a doubling array take Θ(n) and still have O(1) amortized append cost? Answer: yes, because the total cost of a long sequence is O(n), even though some individual resizes copy many elements.

15. What proof would show a problem requires Ω(n log n) time? Answer: a lower-bound argument covering all algorithms permitted in the stated model, not just one implementation.

16. Does f∈O(g) imply g∈Ω(f)? Answer: yes for the eventually nonnegative functions and positive comparison functions used here, by rearranging the eventual multiplicative inequality.

17. When is a limit test inconclusive? Answer: when its hypotheses fail or the ratio limit does not exist; direct witness inequalities can still establish O, Ω, or Θ.

18. How should a benchmarking result be written? Answer: specify implementation, workload, size range, metric, platform, repetition and variance, then separate measurements from proven asymptotic bounds.

19. If two stages take Θ(n) and Θ(n²), what is their combined cost? Answer: Θ(n²) for eventually nonnegative costs under a common n and additive sequential composition.

20. Is n²∈ω(n log n)? Answer: yes, since n²/(n log n)=n/log n→∞.
