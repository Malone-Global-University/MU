Definition, Purpose, and Scope

A time-space tradeoff is a change in algorithm design or representation that alters the relationship between computation time and memory consumption. A program may retain previously computed answers to avoid repeating expensive work, allocate an index to accelerate queries, reorganize data to improve locality, or discard intermediate results and recompute them when needed. These choices are not simply “faster uses more memory”: some transformations reduce both, and added memory can make a workload slower through allocation, cache misses, and memory pressure.

This is the twelfth Level 5 specialist article in the Algorithm Analysis unit of the MGU Computer Science Encyclopedia, extending the Algorithm Analysis overview. It treats resource tradeoffs as a general analytical problem across algorithms and data structures; the related Searching and Indexing Analysis, Amortized Analysis, and Cache and External-Memory Complexity articles provide deeper treatment of their separate subjects.

For every claim about an optimization, identify which resource is traded, under what workload, on what computational model, and with what correctness requirement. State whether data is static, mutable, repeated, cached, compressed, approximate, or streamed. A theoretical bound and a production decision are connected, but they are not identical.

The Resource Vector: What Counts as Space?

Memory consumption is not one undifferentiated number. Input storage houses the problem as received; auxiliary working space includes temporary arrays, recursion frames, stacks, queues, and bookkeeping; output space retains results that must be delivered; and persistent derived structures include indexes, precomputed tables, and caches reused across requests. Different textbooks exclude or include input and output when they call an algorithm “in place.” To compare designs, use the same accounting boundary.

A system-level budget also counts allocator and object metadata, hash-table spare capacity, duplicated keys, runtime overhead, memory mapping, and in-flight concurrent requests. A nominal O(n) structure can occupy many times the payload bytes, while a compact O(n) array may fit in cache. Write an explicit resource vector, for example (setup time, query time, update time, peak resident memory, persistent bytes, I/O), before collapsing alternatives to a single score.

Time Bounds, Space Bounds, and Concrete Capacity

Asymptotic notation indicates how resources grow as a size parameter increases. Two algorithms may both use Θ(n) memory but differ dramatically in bytes per item. Conversely, an O(1)-auxiliary-space in-place sort can use more time and more writes than a buffered sorting method that uses Θ(n) additional elements. Any evaluation should state whether n denotes elements, bytes, vertices, edges, states, or queries.

Memory feasibility is often a hard constraint. If available working memory is 128 MiB, a proposed table requiring 400 MiB is disqualified even if its predicted runtime is attractive. Near-capacity operation can trigger swapping, garbage collection, or out-of-memory failure. Algorithmic O(n) versus O(n log n) comparison is still useful, but a correct decision first checks the concrete working set and peak allocations.

Distinguish an upper bound from a guaranteed footprint: O(n) memory may not imply that every input uses linear memory, and an expected bound for a randomized structure does not assert a deterministic upper limit. Where exact limits matter, quantify a worst-case bound or enforce one through capacity controls.

A Lifecycle-Cost Model for Repeated Work

Suppose one option processes each of q requests without an index at cost U(n) per request. Another builds a structure once at cost B(n), then processes each request in cost I(n), and pays maintenance cost M for intervening updates. Their simplified total costs are Cplain(q) = qU(n) and Cindexed(q) = B(n) + qI(n) + M. The indexed choice wins on this model only when q(U(n) − I(n)) exceeds B(n) + M, provided U(n) > I(n).

That equation requires units compatible enough to add. The terms could represent comparisons, estimated CPU cycles, measured milliseconds, or a workload-based weighted cost, but mixing comparisons with milliseconds without conversion is invalid. A complete system analysis adds cache warmth, incremental index construction, concurrent readers, maintenance spikes, output costs, and memory occupancy; the simple model is a screening model, not a universal benchmark.

When query and update frequencies vary over time, integrate costs over the planning horizon instead of multiplying one average request cost. A strategy beneficial for a static archival dataset may be poor for a rapidly mutating working set.

Worked Break-Even Example: Preprocessing Before Queries

Consider a hypothetical static collection of 100,000 items. A sequential unsorted search examines about 100,000 items in a pessimistic unsuccessful case. Suppose preparing sorted access costs 1,700,000 comparison-equivalent units, and a binary-search lookup costs 17 such units. Ignoring all other overhead, the preprocessing plan is advantageous after q(100,000 − 17) > 1,700,000, so the first integer q satisfying this strict inequality is 18 queries. This calculation assumes comparable unit costs and that search can be performed on the prepared representation without paying hidden conversion or query-output costs.

If the dataset changes on each request, or the sorting step must be repeated, the answer may reverse. If the sequence is already sorted, the setup cost may disappear. If a hash index is available, its different construction and expected-lookup model might dominate. The example teaches a decision procedure, not a measured crossover point for Python or a database.

from math import floor

def first_profitable_query(build, scan, indexed):
    if scan <= indexed:
        return None
    return floor(build / (scan - indexed)) + 1

assert first_profitable_query(1_700_000, 100_000, 17) == 18
assert first_profitable_query(200, 10, 10) is None
assert 18 * 100_000 > 1_700_000 + 18 * 17

Lookup Without an Index Versus a Hash Table

For one membership test in an unsorted sequence of n independent keys, an ordinary scan has O(n) worst-case cost and O(1) extra space. Constructing a hash set requires O(n) expected-time insertions and O(n) additional stored entries in a conventional model. Subsequent membership tests are expected O(1) each under standard hashing assumptions, but worst-case behavior can be slower due to collisions or adversarial keys; the set also consumes more memory than an index-free scan.

A hash index is especially attractive for many exact-membership queries over a mostly static dataset. It does not automatically support ordered range queries or predecessor/successor requests. Duplicate keys, object equality, key hashing, and index invalidation must follow the application’s data semantics. To compare total cost, charge index construction and every mutation that must update it.

records = [f"item-{i}" for i in range(1000)]
queries = ["item-4", "item-777", "not-present"]
scan_results = [any(row == key for row in records) for key in queries]
index = set(records)
indexed_results = [key in index for key in queries]
assert scan_results == indexed_results == [True, True, False]
# Both return exact membership; the set retains additional storage.

Sorted Arrays, Binary Search, and Maintenance Costs

A sorted array permits binary search with O(log n) comparisons for a point query and provides efficient access to neighboring keys and contiguous ordered ranges. Sorting a previously unordered collection generally requires O(n log n) comparisons in an appropriate comparison-sort model. Maintaining sorted order by inserting into the middle of a standard dynamic array takes O(n) data movement even though the insertion position is found with O(log n) comparisons.

This distinction is confirmed by the official Python bisect documentation: insertion into a Python list may be linear because moving elements dominates the logarithmic search. A balanced search tree can reduce update work in the abstract comparison model but introduce pointer-heavy memory layouts and significant constant factors. A B-tree or log-structured structure changes the cost balance again and requires an I/O-aware model for database use.

from bisect import bisect_left, insort

values = [2, 5, 7, 10]
pos = bisect_left(values, 7)
assert pos == 2
insort(values, 6)
assert values == [2, 5, 6, 7, 10]
# Search for a location is logarithmic; list insertion moves elements.

Precomputation Tables and Constant-Time Queries

Precomputation evaluates information once and stores a reusable structure. Examples include prefix sums, factorial tables, precomputed powers, cumulative distributions, lookup tables for a bounded domain, and pairwise distances. A prefix-sum array of n values uses Θ(n) derived storage and Θ(n) setup time but can answer a contiguous sum query in O(1) arithmetic operations. Without precomputation, each range sum may scan Θ(k) values for a range of length k.

The result is not free: a point update can invalidate Θ(n) subsequent prefix entries. Dynamic-range workloads may therefore prefer a Fenwick tree or segment tree, which use additional Θ(n) storage and support O(log n) updates and range aggregates under their algebraic assumptions. Always compare the operation mix, not only one attractive query cost.

def prefix_sums(values):
    p = [0]
    for x in values:
        p.append(p[-1] + x)
    return p

def range_sum(p, left, right):
    """Sum values in the half-open range [left, right)."""
    if not 0 <= left <= right < len(p):
        raise IndexError("invalid interval")
    return p[right] - p[left]

items = [3, -2, 7, 4, 8]
p = prefix_sums(items)
assert range_sum(p, 1, 4) == sum(items[1:4]) == 9
assert range_sum(p, 2, 2) == 0

Memoization Trades Repeated Computation for States

Memoization stores results of distinct subproblems so repeated requests for the same state avoid re-executing their recursive computation. If a naive recurrence revisits the same subproblems exponentially often, caching can reduce the total work to the number of distinct states multiplied by the work per state. Its cache requires space proportional to retained keys and values, and recursive execution may require additional stack space.

For a chain of n Fibonacci states, a memoized recurrence evaluates each distinct state once, using Θ(n) cached values and potentially Θ(n) recursive call depth. A bottom-up loop can compute the same nth Fibonacci number with Θ(n) arithmetic operations and only a fixed number of retained big-integer values. This is O(1) number of retained registers, not O(1) total bit memory: the exact Fibonacci values themselves gain Θ(n) bits in magnitude.

Memoization is beneficial only when states are actually reused; caching unique, expensive-to-store results may waste memory. For a full treatment of top-down state identification and cache correctness, see Memoization and Top-Down Dynamic Programming in the Recursion unit, under its appropriate URL shown later.

Worked Fibonacci Comparison: Three Storage Policies

The intentionally naive recursive Fibonacci definition recomputes F(k) whenever a call tree reaches k; its time is exponential while its maximum call depth is O(n). Memoization reduces repeated computations, but retains Θ(n) answers and recursion frames. An iterative recurrence carries only the latest two values and avoids deep call stacks; its arithmetic-operation count is Θ(n), with the caveat that arbitrary-precision additions become more expensive as values grow.

For correctness, each implementation must agree on F(0) = 0 and F(1) = 1. Cache statistics and timing results depend on implementation details and input sizes; do not compare the 35th naive value and 10,000th memoized value as if they were equivalent workloads.

from functools import lru_cache

def fib_naive(n):
    if n < 2: return n
    return fib_naive(n - 1) + fib_naive(n - 2)

@lru_cache(maxsize=None)
def fib_cached(n):
    if n < 2: return n
    return fib_cached(n - 1) + fib_cached(n - 2)

def fib_iter(n):
    a, b = 0, 1
    for _ in range(n):
        a, b = b, a + b
    return a

for k in range(16):
    assert fib_naive(k) == fib_cached(k) == fib_iter(k)
assert fib_iter(30) == 832040

Top-Down and Bottom-Up Dynamic Programming

Top-down dynamic programming evaluates states requested by the original problem, with cache entries created on demand. Bottom-up dynamic programming selects an ordering in which prerequisite states are available when their dependents are computed. For sparse reachable-state graphs, top-down processing may avoid many impossible or irrelevant states; for a dense regular table, bottom-up computation can avoid recursion overhead and may enable state compression.

Neither paradigm inherently has the lower memory footprint. A top-down cache of all reachable states can exceed a bottom-up table; an on-demand cache that stores only a small subset may consume less. A bottom-up approach that keeps the entire table may use more than a carefully bounded recursive memoization strategy. Count actual states retained, dependencies active at once, and whether full solution reconstruction is required.

Rolling Arrays: Retain Only Necessary Dependencies

A dynamic program may require only the preceding row of a two-dimensional table. If a recurrence for row i depends solely on row i − 1, a pair of row buffers can reduce auxiliary storage from Θ(nm) to Θ(m), where m is the number of columns. If cells depend only on the preceding column and the current row in a compatible update order, one row can suffice. This optimization can preserve Θ(nm) computation time while reducing stored intermediate states.

State compression is not automatic. A careless update can overwrite a predecessor before all dependents have read it. A full-table backtrace may also become impossible without storing predecessor choices or recomputing selected states. State compression changes storage and reconstruction requirements even when numerical answers remain the same.

def edit_distance_rolling(a, b):
    # Keep the shorter string along the row dimension.
    if len(a) < len(b):
        a, b = b, a
    prev = list(range(len(b) + 1))
    for i, x in enumerate(a, 1):
        curr = [i]
        for j, y in enumerate(b, 1):
            curr.append(min(prev[j] + 1, curr[-1] + 1,
                            prev[j - 1] + (x != y)))
        prev = curr
    return prev[-1]

assert edit_distance_rolling('kitten', 'sitting') == 3
assert edit_distance_rolling('', 'abc') == 3
assert edit_distance_rolling('same', 'same') == 0

One-Dimensional Knapsack and Update Direction

In 0/1 knapsack, each item may be selected at most once. Replacing a two-dimensional table indexed by item and capacity with a one-dimensional array is valid only if capacities are processed in decreasing order. A descending update uses the previous-item state for the current item’s predecessors. An ascending update can reuse a newly computed value from the same item, silently changing the problem to an unbounded variant.

This is a common correctness cost of space compression: changing memory layout can change the dependency graph as represented in program execution. A proof must identify exactly which row or time step each read represents. The optimized table yields the optimal total value but does not itself retain the full item-choice trace.

def knapsack_01(items, capacity):
    dp = [0] * (capacity + 1)
    for weight, value in items:
        for c in range(capacity, weight - 1, -1):
            dp[c] = max(dp[c], dp[c - weight] + value)
    return dp[capacity]

assert knapsack_01([(3, 5)], 6) == 5  # not 10
assert knapsack_01([(2, 3), (3, 4), (4, 5)], 5) == 7

Answer-Only Computation Versus Solution Reconstruction

Some applications need only the optimal score; others need the selected objects, edit script, path, or provenance of every step. A rolling-array dynamic program may compute the score in linear memory while destroying the evidence needed to reconstruct the chosen solution. One option stores predecessor pointers or decisions; another recomputes subproblems during a backward pass, potentially increasing work. Divide-and-conquer reconstruction can sometimes recover a path with much less retained state but additional passes.

Before claiming an O(m) space solution for a two-dimensional dynamic program, specify whether it returns only a number or a concrete witness. The output itself may require Ω(n) or Ω(m) storage. For example, a minimal edit distance is a scalar, but an edit script may contain Θ(n + m) actions. Memory-accounting conventions should separate output from auxiliary working space rather than hiding the cost.

Cache Size, Eviction, and Least-Recently-Used Policies

Unbounded memoization can retain every unique key for an entire process lifetime. A bounded cache limits entries but introduces eviction; if a useful entry is removed, later requests may recompute it. Common eviction choices include least recently used (LRU), least frequently used (LFU), random eviction, time-to-live (TTL), and workload-specific policies. No policy guarantees good performance on every access sequence.

Python’s functools.lru_cache supports a maximum entry count and provides hit/miss statistics through cache_info(). An entry limit is not a byte limit: cached values can have very different sizes. A cache holding 500 large query responses may exceed a tight memory budget despite its apparently modest entry count.

from functools import lru_cache

@lru_cache(maxsize=2)
def square(x):
    return x * x

for x in [2, 3, 2, 4, 2]:
    assert square(x) == x*x
info = square.cache_info()
assert info.maxsize == 2 and info.currsize <= 2
assert info.hits >= 2
square.cache_clear()

Modeling Cache Hit Rate and Average Cost

Let h be the probability that a cache lookup is a hit under a specified workload, Chit the hit cost, and Cmiss the total cost of a miss including original computation, insertion, and any eviction. An elementary expected-request-cost model is E[C] = hChit + (1 − h)Cmiss. This can be compared with uncached computation cost, adjusted for the memory price and for whether the cache contains stale answers.

Hit rate is not a pure property of cache size. It depends on access distributions, request correlations, reuse distances, eviction policy, dataset changes, and cold starts. A higher hit rate does not always yield a faster program if it is achieved using large bookkeeping costs, compression/decompression, or expensive synchronization.

Latency-sensitive systems need more than mean response cost: rare cache misses may drive percentile latency. For a strong guarantee, analyze or bound the miss path explicitly rather than reasoning only from the average hit rate.

def expected_cache_cost(hit_probability, hit_cost, miss_cost):
    if not (0 <= hit_probability <= 1):
        raise ValueError('hit_probability must be between 0 and 1')
    return hit_probability * hit_cost + (1-hit_probability)*miss_cost

from math import isclose
assert isclose(expected_cache_cost(0.8, 1, 21), 5.0)
assert expected_cache_cost(0, 1, 21) == 21
assert expected_cache_cost(1, 1, 21) == 1

Cache Correctness: Keys, Versions, and Invalidation

An optimization that returns a wrong answer is not a valid speedup. Cache keys must capture all inputs and relevant environmental state that determine the result: arguments, data versions, configuration, permissions, locale, and sometimes time. A cached answer from an earlier database version may be incorrect after updates, even if key equality still holds. Invalidation can use versioned keys, explicit deletion, bounded time-to-live, dependency tracking, or rebuilding, each with a cost and potential race conditions.

Memoization of a pure deterministic function is conceptually straightforward because equal arguments yield equal values. Caching side-effecting operations, mutable objects, authentication decisions, or time-sensitive information requires stronger correctness contracts. The larger tradeoff may be between time saved and consistency complexity rather than between time and raw bytes alone.

def versioned_lookup(records, version, key, cache):
    cache_key = (version, key)
    if cache_key not in cache:
        cache[cache_key] = records.get(key)
    return cache[cache_key]

cache = {}
data_v1 = {'a': 1}
data_v2 = {'a': 9}
assert versioned_lookup(data_v1, 1, 'a', cache) == 1
assert versioned_lookup(data_v2, 2, 'a', cache) == 9
# The caller must supply a version that changes with the data.

Memory Budgets, Eviction Costs, and Peak Allocation

Capacity planning should express memory as a budget inequality: input + output + active workspace + index/cache + per-request duplication + runtime overhead ≤ available memory, with sufficient headroom for uncertainty. A cache may reduce recomputation while competing with the application’s working data for cache or RAM capacity. Eviction itself may require writes, cleanup, synchronization, or expensive object finalization.

A streaming transformation may have a low steady-state footprint but still create a large peak allocation when an intermediate list is materialized. Conversely, an algorithm may store the same O(n) number of elements with sharply different peak occupancy during resizing. Estimate peak live objects and worst-case concurrency, not just the final size of a retained structure.

Hash Tables, Membership Filters, and Probabilistic Answers

A hash set stores keys so exact membership queries are usually fast under hashing assumptions, but memory includes keys, hash-table slots, and load-factor slack. A Bloom filter offers a different service: it stores a compressed probabilistic representation of membership for insertion and queries, allowing false positives but—under standard insertion-only conditions and correctly functioning hashing—no false negatives. A Bloom filter does not identify which key is present, produce a payload, or remove entries safely without a modified design.

The ability to tolerate false positives is a semantic constraint, not a free time-space reduction. A negative response can rule out membership; a positive response requires verification in an exact backing store if correctness requires certainty. Filters are valuable when avoiding expensive negative lookups outweighs their memory footprint and false-positive verification cost.

Bloom-Filter Memory and False-Positive Probability

For a conventional Bloom filter with m initially zero bits, n inserted distinct items, and k independent uniform hash positions per item, a common approximation to the false-positive probability is p ≈ (1 − e−kn/m)k. The optimum k in this model is near (m/n)ln 2, and the required bits per item for target false-positive probability p are approximately m/n ≈ −ln(p)/(ln 2)². These formulas rely on probabilistic assumptions and must not be interpreted as exact guarantees for poor hash functions or heavily changing datasets.

For p = 0.01, the idealized formula gives about 9.59 bits per inserted item and approximately 6.64 hash positions, suggesting an integer choice of 7. A real implementation must budget bit-array metadata, concurrency, serialization, and backing-store verification. False-positive probability also increases as insertions accumulate beyond the capacity for which the filter was designed.

from math import log, exp

def bloom_plan(items, target_fp):
    if items <= 0 or not 0 < target_fp < 1:
        raise ValueError('invalid Bloom-filter parameters')
    bits = -items * log(target_fp) / (log(2)**2)
    hashes = (bits / items) * log(2)
    return bits, hashes

bits, hashes = bloom_plan(10_000, 0.01)
assert 95_000 < bits < 97_000
assert 6 < hashes < 7
p_est = (1 - exp(-7*10_000/bits))**7
assert 0.009 < p_est < 0.011

Bitmaps, Bitsets, and Bounded Integer Domains

If membership keys are integers from a known dense universe of size U, a direct-address bitset uses U bits plus representation overhead and can support constant-time membership operations. A general hash set often stores entire integer objects or table entries, making a bitset attractive when U is not excessive. For a sparse universe of enormous maximum key value, allocating U bits can be prohibitive; a sparse set or compressed bitmap may be better.

Representation changes which size parameter controls storage. A bitset of U possibilities is Θ(U) bits even if only n ≪ U are present, whereas a sparse representation may use O(n) entries. Bitsets also support fast batch intersections and unions with machine-word operations, an advantage not captured by counting one mathematical set operation as one unit without stating the word-RAM model.

class SmallBitset:
    def __init__(self, universe):
        self.universe = universe
        self.bits = 0
    def add(self, x):
        if not 0 <= x < self.universe: raise ValueError('outside domain')
        self.bits |= (1 << x)
    def contains(self, x):
        return 0 <= x < self.universe and bool(self.bits & (1 << x))

s = SmallBitset(32)
for n in (1, 3, 12): s.add(n)
assert [s.contains(i) for i in (1,2,3,12)] == [True, False, True, True]

Compression Versus Decompression Work

Compression transforms data into a smaller representation at an encoding cost and generally adds decoding work. Lossless compression preserves exact data; lossy compression relaxes an accuracy requirement and must disclose the resulting error model. The optimal choice depends on whether the compressed data is stored once and read many times, how much must be decompressed per query, and whether reduced transfer time exceeds CPU decoding overhead.

For storage-bound workloads, smaller bytes may reduce disk or network traffic enough to make the system faster overall. For repeated fine-grained random lookups, a compression format requiring whole-block decompression may increase latency. A useful comparison includes compressed size, encoder time, decoder time, block granularity, random-access support, and memory needed to hold temporary decoded blocks. Compression ratios depend on the data distribution and are not guaranteed by the asymptotic size class alone.

import zlib

payload = (b'ABCD' * 5000) + (b'XYZ' * 5000)
compressed = zlib.compress(payload)
restored = zlib.decompress(compressed)
assert restored == payload
assert len(compressed) < len(payload)
# This example uses highly repetitive data; other inputs may not shrink.

Succinct and Compact Data Structures

A compact representation reduces constants in memory use—for example, storing 32-bit indices instead of 64-bit references when the domain fits. A succinct data structure is a formal concept: it approaches the information-theoretic minimum number of bits for the objects represented, often with a lower-order redundancy term, while providing designated operations. Those stronger guarantees require a specified object family and query model.

Compressed sparse rows (CSR), rank/select bitvectors, compressed tries, and succinct tree encodings illustrate different approaches to representation cost. Their construction and update behavior differ significantly. CSR is well suited to static sparse graphs because adjacency entries are densely packed; inserting an edge can require reorganizing large arrays. The saved bytes can improve locality and sometimes speed, so a smaller structure need not be slower—but locality and operation mix must be measured.

Dense and Sparse Matrix Representations

For an R-by-C matrix, a dense representation stores Θ(RC) numeric entries, whether or not most entries are zero. A sparse coordinate format stores only nonzeros and their row/column indices, giving O(z) stored triples for z nonzeros, plus object and metadata overhead. Sparse storage may be much smaller when z ≪ RC, but zero entries are no longer directly stored and some operations become less convenient or require special algorithms.

SpMV (sparse matrix–vector multiplication) can often be evaluated in O(z + R) work with a suitable compressed representation, while straightforward dense multiplication by a vector is O(RC). Yet a dense representation may be preferable at moderate density due to contiguous storage and vectorization. The switching point is not established by asymptotic notation alone; item sizes, index widths, CPU features, and library implementation matter.

def sparse_matvec(rows, columns, triples, vector):
    if len(vector) != columns:
        raise ValueError('dimension mismatch')
    result = [0] * rows
    for r, c, value in triples:
        if not (0 <= r < rows and 0 <= c < columns):
            raise IndexError('matrix entry out of bounds')
        result[r] += value * vector[c]
    return result

assert sparse_matvec(3, 3, [(0,1,4),(2,0,-2)], [5,6,7]) == [24,0,-10]

In-Place Algorithms Versus Separate Output Buffers

An in-place algorithm modifies its input using a bounded amount of auxiliary storage under a specified model. In-place insertion sort can be implemented with O(1) auxiliary element slots, whereas conventional merge sort uses Θ(n) additional elements to combine runs efficiently. The in-place method is not necessarily faster and may perform more data movement on disorderly inputs; the merge-sort method can offer a stable Θ(n log n) guarantee with an additional buffer.

“In place” does not mean zero memory: loop variables, recursion frames, swap temporaries, pivot bookkeeping, and allocator effects must be accounted for. Also distinguish mutating the input from preserving it. A caller requiring an unchanged input may force a copy before an in-place method, erasing much of its advertised auxiliary-space advantage.

def reverse_in_place(values):
    i, j = 0, len(values)-1
    while i < j:
        values[i], values[j] = values[j], values[i]
        i += 1
        j -= 1

items = [1, 2, 3, 4, 5]
reverse_in_place(items)
assert items == [5, 4, 3, 2, 1]

Allocation, Resizing, and Temporary Peaks

A dynamic array with geometric capacity expansion offers amortized O(1) append under a conventional model but occasionally copies all existing elements to a new allocation. At the moment of expansion, both old and new buffers may coexist, giving a transient peak larger than either steady-state representation. A practical memory budget must account for that peak, not only the final length.

Preallocating capacity can reduce resizing costs when an upper bound on required elements is known, but unused reserved capacity wastes memory if the estimate is excessive. Growing by a fixed additive increment can preserve tighter local capacity while increasing total copying work quadratically over a long sequence. Allocation policy is a genuine time-space tradeoff even if all options present the same abstract dynamic-array interface.

Streaming Results Instead of Materializing Them

When a consumer can process results incrementally, streaming or lazy iteration avoids retaining a full output collection. Computing the sum of a large input can use constant auxiliary accumulator space; collecting an entire list of transformed outputs uses space proportional to the result count. If the output must be returned as a complete collection, its storage is required by the output contract and cannot be dismissed.

Streaming may introduce ordering constraints, inability to revisit earlier items, network backpressure, and different error handling. A generator that yields one element at a time may also retain state inside suspended stack frames or closures. Analyze the maximum number of outstanding items and buffering stages, especially when several operators compose and one downstream stage is slower than the source.

def squares(source):
    for value in source:
        yield value * value

result = sum(squares(range(10_000)))
assert result == (9999*10_000*19_999)//6
# No list of 10,000 square values is materialized.

Online Computation, Batching, and Incremental Maintenance

An online algorithm processes arrivals without knowledge of the future, while an offline algorithm may have the full workload available in advance. Offline sorting, grouping, and batching can reduce repeated work or improve locality, but require holding inputs until the batch is ready and can increase response latency. Online structures often pay incremental maintenance costs that an offline batch could avoid.

For repeated database updates, rebuilding an index after every change is usually wasteful; incrementally maintaining a suitable structure may cost less in total. Conversely, if an index is inexpensive to rebuild and changes arrive in a burst, periodic rebuilding may be simpler and faster. Model update frequency, latency tolerance, consistency, and working-set size together. A batch strategy with superior average throughput may not meet a real-time service-level requirement.

Exact Counting, Approximation, and Sketches

Some memory reductions change the answer contract. A streaming exact distinct-count algorithm for an arbitrary set of keys may need storage that grows with the number of distinct values; approximate cardinality sketches compress observations to a fixed-size synopsis, at the cost of statistical error under stated assumptions. Similar ideas appear in sampling, frequency estimation, and approximate membership filters.

Do not treat an approximate result as equivalent to an exact one. An analytics dashboard estimating unique visitors may accept statistical error, while a security authorization list or financial ledger must generally require exact membership or totals. Identify error probability, approximation bias, update and merge rules, and whether adversarial inputs invalidate probabilistic guarantees.

Recursive Stack Space Versus Explicit Worklists

Recursion stores unfinished computations in activation records. For a depth-first traversal, call-stack usage grows with the maximum active recursion depth, not simply with the total number of nodes visited. An explicit stack can make memory use visible and may avoid a language runtime’s recursion-depth limit, but it does not automatically reduce asymptotic memory use; it may store the same pending states and additional bookkeeping.

A breadth-first traversal typically retains a frontier that can be much wider than a depth-first path. The appropriate space bound therefore depends on branching, traversal order, and whether discovered/visited sets are required. For cyclic graphs, an explicit DFS stack alone does not prevent revisitation: a visited-state policy is needed unless the algorithm relies on another proven invariant.

def depth_first_iterative(graph, start):
    seen = set()
    stack = [start]
    order = []
    while stack:
        node = stack.pop()
        if node in seen:
            continue
        seen.add(node)
        order.append(node)
        stack.extend(reversed(graph.get(node, [])))
    return order

graph = {'A':['B','C'], 'B':['D'], 'C':['D'], 'D':[]}
assert depth_first_iterative(graph, 'A') == ['A','B','D','C']

Breadth-First Versus Depth-First Frontier Memory

For a complete b-ary tree of depth d, DFS maintains a path plus pending siblings, often O(bd) storage with an explicit stack under ordinary implementations, while BFS may retain Θ(bd) frontier nodes near the last level. Both explore Θ(bd) nodes when searching the entire tree. This does not establish that DFS is always preferable: BFS gives shortest paths in unweighted graphs and may discover a shallow solution much earlier.

In arbitrary graphs, a visited set can grow to Θ(V) for either algorithm, and adjacency storage may dominate. DFS is not inherently a constant-memory graph algorithm. When a problem allows regeneration of successors and has bounded depth, iterative deepening DFS offers another tradeoff: low path-space use with repeated expansions across depth limits. Its overhead and guarantees depend on the branching structure and search contract.

Meet-in-the-Middle: Trading Exponential Time for Storage

For certain combinatorial searches, splitting n independent choices into two halves creates roughly 2n/2 candidate results on each side. Storing one half permits efficient matching against the other. This meet-in-the-middle technique can reduce the exponent of the search time but needs exponentially many stored partial results. It is useful only when n is small enough for those intermediate structures to fit.

For subset sum, enumerate all sums in each half. Sort one list and binary-search complementary targets for sums in the other, giving a typical O(n2n/2) generation-work expression if subset sums are recomputed naively, or O(2n/2) generation with incremental enumeration plus O(2n/2log 2n/2) sorting in a straightforward model. The result must be proven against the target, not merely accepted because two partial sums look close.

from bisect import bisect_left

def subset_sums(values):
    sums = [0]
    for value in values:
        sums += [x + value for x in sums]
    return sums

def has_subset_sum_mitm(values, target):
    mid = len(values) // 2
    left = subset_sums(values[:mid])
    right = sorted(subset_sums(values[mid:]))
    for x in left:
        i = bisect_left(right, target-x)
        if i < len(right) and right[i] == target-x:
            return True
    return False

assert has_subset_sum_mitm([4, 7, -3, 9], 13)
assert not has_subset_sum_mitm([2, 4, 8], 7)

Checkpointing and Recomputation

A long computation can retain every intermediate state for fast backward inspection, or save occasional checkpoints and recompute missing intervals when needed. The latter reduces the number of stored snapshots but increases total work. Automatic differentiation and long-running simulations use variations of this technique when full trajectories exceed available memory.

A simple strategy stores every k-th state and recomputes the intervening k steps on demand. If there are T steps, the number of checkpoints is about T/k, and reconstructing one interval may need up to k extra steps. The exact space bound also includes any temporary states required by reconstruction; if every interval is revisited, total recomputation can be substantial. More sophisticated checkpoint schedules are possible, but the correct plan depends on which states must be revisited and how often.

def checkpoints(seed, steps, interval, transition):
    if interval <= 0: raise ValueError('interval must be positive')
    state = seed
    stored = {0: seed}
    for t in range(1, steps + 1):
        state = transition(state)
        if t % interval == 0 or t == steps:
            stored[t] = state
    return stored

saved = checkpoints(1, 10, 3, lambda x: 2*x + 1)
assert sorted(saved) == [0,3,6,9,10]
assert saved[10] == (2**11)-1

Memory Locality Versus Raw Space Consumption

Two structures using the same asymptotic number of bytes can produce very different access patterns. Contiguous arrays encourage sequential access and spatial locality; linked objects can require pointer chasing and more cache misses. On modern processors, fewer cache misses can save more time than reducing a small amount of arithmetic. A smaller compressed structure may even run faster because a larger fraction of it fits in higher levels of cache.

Nevertheless, predicting performance from “cache-friendly” alone is risky. The workload’s access pattern, element size, prefetching, CPU architecture, memory layout, and runtime allocator matter. The formal study of block transfers, cache-aware algorithms, and external-memory bounds belongs to the next specialist article, {link('cache-and-external-memory-complexity','Cache and External-Memory Complexity')}; this page explains why locality often changes the practical time-space balance.

External-Memory Feasibility and Spill Costs

If a working set cannot fit in memory, the algorithm may spill intermediate data to secondary storage, use external sorting, partition its work, or fail. Time–space analysis must then count storage transfers and access patterns rather than treating every read as a constant-cost RAM operation. For block size B, a contiguous scan of n entries may require on the order of n/B block transfers once blocks are packed and accessed sequentially; random accesses can be much more expensive.

Buffers are a resource investment: enough working memory to retain frequently used blocks or merge many sorted runs can sharply reduce I/O. But overallocating buffers may force other components to spill. Avoid converting an asymptotic block-transfer count directly into a wall-clock estimate; real systems include caching, concurrency, device bandwidth, latency, and software overhead.

Parallelism, Concurrency, and Shared Memory Budgets

A speedup obtained from parallel processing may increase peak memory because each worker needs private buffers, stacks, or copies of input. If p workers each allocate W bytes of private workspace, their aggregate temporary demand can approach pW, in addition to shared input, output, and scheduling structures. Some parallel algorithms avoid this by partitioning shared buffers or carefully reusing storage; others sacrifice parallelism to stay within a fixed footprint.

Memory capacity also shapes throughput. A design that is fast for one request may run poorly with 100 concurrent requests because its per-request cache or temporary table is multiplied across instances. State whether a reported memory bound is per operation, per worker, per process, or for the whole service. For formal work/span analysis, see {link('parallel-algorithm-analysis','Parallel Algorithm Analysis')}; here the emphasis is the interaction between memory sharing and runtime guarantees.

Worst-Case Inputs, Adversarial Access, and Robustness

Average-case cache and hash-table analyses do not automatically apply to arbitrary adversarial workloads. A cache with a working set just larger than its capacity may suffer repeated misses, while a hash table may encounter pathological collisions unless the implementation protects against them. A preprocessing method that is ideal under stable data may degrade when an adversary forces frequent updates and invalidations.

Robust analysis records what the input or access distribution is permitted to do. If memory is capped by policy, use a capacity-respecting algorithm with a bounded fallback rather than relying exclusively on expected small occupancy. If the application must meet a latency target, characterize rare rebuilding and cache-miss paths. A probabilistic average does not substitute for a worst-case memory bound where process survival is at stake.

Quantifying Concrete Memory in Bytes

Big-O formulas need concrete dimensional accounting before deployment. A table with 4 million entries of eight payload bytes consumes at least 32,000,000 bytes (about 30.5 MiB) before keys, row descriptors, alignment, and hash-table metadata. If each entry retains an eight-byte key, an eight-byte value, and even a simplified eight-byte slot overhead, the raw estimate rises to 96,000,000 bytes (about 91.6 MiB). Actual Python object-based tables may occupy substantially more; a packed array may occupy less.

Specify decimal megabytes versus binary mebibytes. A hard memory budget should be based on measured or conservatively bounded peak allocations for the actual runtime. A single-purpose bitset of 4 million possible values requires 500,000 payload bytes before container overhead, but it can only represent the chosen bounded-universe membership contract, not arbitrary key-value records.

def mebibytes(byte_count):
    return byte_count / (1024**2)

n = 4_000_000
assert 30 < mebibytes(n*8) < 31
assert 91 < mebibytes(n*24) < 92
assert n // 8 == 500_000  # bitset payload for n bits

A Multi-Resource Cost Function

Many practical decisions optimize a weighted objective rather than one asymptotic dimension. One possible model is J = αT + βM + γI + δE, where T is execution time, M is peak memory, I is I/O traffic, and E is energy or another measured resource. The weights must reflect actual service priorities; arbitrary weights can make any option appear optimal. If a resource is a hard limit, model it as a constraint rather than merely charging a penalty.

For example, an embedded program might minimize response time subject to a 256-KiB RAM cap. A data-analytics batch might minimize total processing cost given an overnight completion deadline. A live service may prioritize a 99th-percentile latency target and a per-request memory limit. The right analysis uses actual constraints and workload distributions instead of declaring one algorithm universally best.

Pareto Dominance and Tradeoff Frontiers

Option A dominates option B when A is no worse in every relevant resource dimension and strictly better in at least one. A nondominated option is on the Pareto frontier: choosing among frontier points requires a preference or constraint, not a claim that one wins all categories. This prevents misleading “faster than” comparisons that ignore extra RAM, slower updates, or accuracy changes.

Comparison must use the same output contract and correctness guarantee. An approximate Bloom-filter query cannot directly dominate an exact set lookup without treating its false-positive probability as an additional dimension or enforcing exact verification. Similarly, a streaming algorithm that does not return a stored full result has a different interface unless consumers can accept incremental delivery.

def nondominated(options):
    # Minimize both time and memory.
    return [name for name, time, mem in options if not any(
        (other_t <= time and other_m <= mem)
        and (other_t < time or other_m < mem)
        for other, other_t, other_m in options)]

choices = [('A',10,10),('B',8,14),('C',12,7),('D',15,15)]
assert nondominated(choices) == ['A','B','C']

A Practical Time-Space Selection Framework

Begin with the required output and permitted error. Next identify sizes: input records n, distinct states s, query count q, updates u, output size k, concurrency p, and available memory M. Calculate each strategy’s construction, request, update, and rebuild costs under the same model. Separate peak working space from persistent derived storage, and identify any data structures that are replicated per worker. Reject infeasible options before comparing throughput.

Then estimate which constraints dominate. For repeat-heavy, low-update workloads, consider indexing or caching. For one-pass pipelines, consider streaming. For dense dynamic-programming tables, ask whether dependencies permit rolling rows. For membership-only queries with tolerated false positives, a filter may reduce expensive backing-store checks. For exact low-memory requirements, investigate recomputation or external-memory techniques. Prototype plausible frontier candidates and validate their actual resource use on representative inputs.

Worked Investigation 1: Static Catalog Search

Scenario: a catalog contains 200,000 entries and will answer 50,000 exact-key queries before its next rebuild. A full scan has worst-case O(n) work per query; a hash index adds O(n) expected construction and storage and offers expected O(1) exact lookup. A sorted-array index offers O(log n) query comparisons after preprocessing and additionally supports ordered range access, but middle insertions can be expensive.

Analysis: count unique keys, record distribution, cache footprint, and result payload size. If queries are exact and updates infrequent, a hash index may justify its storage. If the application also requests price or name ranges, sorted access or a tree can reduce repeated sorting. The optimal plan depends on workload and the memory limit, not only the fact that n is large. Test throughput and worst-case memory after indexing all records.

Worked Investigation 2: A Continually Updated Leaderboard

Scenario: a leaderboard receives one update for every two reads and must report the top 100 scores. Rebuilding a completely sorted list after each update could impose substantial work, while appending unsorted records reduces update work but makes every read scan. A balanced ordered index or heap may support a better compromise, depending on whether it must provide arbitrary rank queries, deletion of old scores, or only the current maximum.

Analysis: explicitly model update frequency, deletion, tie-breaking, retained historical values, and top-k output cost. A heap may report a maximum efficiently but is not a drop-in replacement for an order-statistic tree; reporting the top 100 distinct ranked records may require different maintenance. The memory budget includes both current records and any duplicate or stale entries awaiting cleanup.

Worked Investigation 3: Memory-Constrained Edit Distance

Scenario: compare two strings of length 50,000 each and return only their edit distance. A full grid of (50,001)² scalar cells contains roughly 2.5 billion entries, far beyond a typical small-memory environment. A rolling-row method retains two rows of about 50,001 cells, dropping the number of retained states by several orders of magnitude while retaining O(nm) basic recurrence evaluations.

Analysis: if the application needs the edit script rather than only its distance, rolling rows alone do not provide the necessary backtrace. Decide whether to store predecessor information, recompute portions, or apply divide-and-conquer reconstruction. Even the rolling method may be too slow for 2.5 billion cell updates; space feasibility does not imply acceptable time.

Worked Investigation 4: Streaming Transaction Summaries

Scenario: a processing pipeline must compute aggregate totals over millions of event records and can accept input sequentially. Materializing all parsed events in an intermediate list uses memory proportional to the number of records; an incremental aggregator can retain only a few counters or a bounded group-by map. If the requested output contains all distinct customer IDs, however, the aggregation map may still grow with the distinct count.

Analysis: separate the output cardinality from the input cardinality and check whether updates arrive out of order. Account for temporary batches, parser buffers, concurrency, and error recovery. A streaming design may improve both memory consumption and time by avoiding intermediate allocations, but random revisits or global sorts may still require buffering or external storage.

Worked Investigation 5: Search With a Huge Frontier

Scenario: a broad decision tree has branching factor b = 10 and depth d = 6. A complete final-level BFS frontier may contain one million nodes, even before considering the visited set or the cost of node metadata. DFS can keep a far smaller active path with pending siblings, yet it does not guarantee the shallowest goal first. Iterative deepening may recover shallowest-depth search under unit step costs while revisiting earlier levels.

Analysis: the right selection depends on whether all solutions must be found, whether a shortest path is required, and whether state revisitation or duplicate paths are possible. Estimate bytes per frontier entry, not just node counts. If exploration is an implicit graph rather than a tree, cycle detection and duplicate-state storage may dominate memory for all strategies.

Worked Investigation 6: Fast Negative Membership Checks

Scenario: a remote database receives millions of membership queries, most of which refer to absent keys. An in-memory Bloom filter can quickly reject many misses while directing positive responses to the database for exact confirmation. The filter consumes much less space than a full copy of keys in the idealized model, but incurs construction, refresh, and false-positive verification costs.

Analysis: choose the intended false-positive rate, predicted insert count, hashing assumptions, and update/invalidation policy. A missing insertion can create a false negative relative to the underlying store, violating the usual insertion-only Bloom guarantee because the filter no longer accurately represents the data. If false positives are unacceptable, the backing-store check is mandatory. Measure saved database round trips against memory footprint and refresh traffic.

Worked Investigation 7: Checkpointing a Long Simulation

Scenario: a simulation has 10 million time steps and a large state vector, but a later diagnostic requires revisiting selected historical states. Saving every state is infeasible. Saving a checkpoint every 10,000 steps reduces the number of persistent snapshots to approximately 1,000 plus the initial state; recovering any one skipped state may involve up to about 10,000 recomputation steps.

Analysis: if diagnostics examine only a handful of times, this may be an effective compromise. If every historical state is revisited repeatedly, recomputation could overwhelm processing time. Also verify that the simulation is reproducible: nondeterministic inputs or changing external conditions may make recomputation return different states unless seeds, inputs, and versions are preserved.

Correctness Obligations When Changing Storage

An optimization should be accompanied by a proof that it preserves the required observable result, or by an explicit revised error contract. For memoization, show the cache key identifies the complete state and stored results remain valid. For rolling arrays, show updates read the correct predecessor states. For streaming, show the operator respects order and aggregation semantics. For Bloom filters, state and test false-positive behavior and the insertion/update contract.

Trace a small case through both original and optimized algorithms. Include adversarial cases: empty inputs, duplicate keys, negative values, large ranges, rapid updates, and stale cache entries. Where a memory-saving algorithm uses recomputation, verify that recomputed values are deterministic under the retained state. The proof burden is often more consequential than a small change in asymptotic notation.

Benchmarking Both Time and Memory

To evaluate a candidate, measure construction time separately from steady-state operations and record the distribution of query types, updates, and output sizes. Run repeated trials with controlled versions, warmup policy, random seeds where appropriate, and realistic dataset cardinalities. Track median and tail latency, operation counts if available, throughput, allocations, peak resident memory, and cache size. A single short run on a cold process does not establish a stable tradeoff.

Python’s time.perf_counter() can time wall-clock intervals, while tracemalloc can observe many Python-managed memory allocations; neither alone measures all native allocations and system-level effects. Benchmarking may itself change caching and memory behavior. Explain what was actually measured and avoid interpreting a test of toy data as a general speed claim.

from time import perf_counter
import tracemalloc

def measure_python_allocation(work):
    tracemalloc.start()
    start = perf_counter()
    value = work()
    elapsed = perf_counter() - start
    current, peak = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    return value, elapsed, peak

value, seconds, peak_bytes = measure_python_allocation(
    lambda: sum(range(10_000)))
assert value == 49_995_000
assert seconds >= 0 and peak_bytes >= 0
# Report timing and traced allocations separately.

Common Analytical Mistakes

Comparing one query to an indexed query without index construction: the index may not pay off if there are few reads. Counting only final memory: transient resize buffers, concurrent requests, and reconstruction tables can cause the real peak. Equating fewer bytes with faster access: compression may add decode time or prevent random access. Claiming all DP can use one row: correctness depends on dependency direction and required output.

Equating expected time with guaranteed latency: a long-tail cache miss or hash collision remains possible. Treating approximate structures as exact: a membership filter or sketch changes error semantics. Ignoring mutation: stale caches, rebuilt indexes, and updated prefix sums may erase the benefit. Ignoring word size: bit-level storage and arbitrary-precision arithmetic can make “constant space” ambiguous.

Finally, avoid the opposite mistake: concluding that every improvement must trade time for space. Better algorithms, compact layouts, and removal of redundant computations can sometimes improve both dimensions. The feasible set, not a slogan, determines the actual frontier.

A Reproducible Analysis Checklist

  1. State the exact problem, output, accuracy requirement, and supported operations.
  2. Define n, q, u, state cardinality, output size, and concurrency.
  3. Define the cost model: comparisons, word operations, memory bytes, or block transfers.
  4. Record all auxiliary, output, persistent, and peak-memory requirements.
  5. Derive total workload costs including setup, reads, updates, and invalidations.
  6. Prove that any compressed-state, cached-state, or approximate strategy preserves its promised contract.
  7. Reject options that exceed hard memory, latency, or correctness constraints.
  8. Identify nondominated strategies and compare their crossover points.
  9. Run reproducible tests at representative sizes, including cold and warm states.
  10. Document measurements, assumptions, failure modes, and the decision rationale.

This sequence is suitable for a design review or coursework. It prevents an isolated asymptotic bound from becoming an unsupported platform-level claim.

Review Questions with Answers

These questions test the assumptions behind the tradeoff rather than asking for isolated vocabulary. Each answer states the central point; readers should be able to supply a worked example or bound.

  1. What is a time-space tradeoff? A deliberate change of representation or algorithm that alters computational time and memory use; improvement in one dimension may worsen the other, though not necessarily.
  2. Why distinguish auxiliary space from output space? The algorithm may need to materialize a large result independent of its working memory; different contracts and textbooks count these categories differently.
  3. What costs are missing when comparing only indexed and unindexed lookup time? Index construction, memory, maintenance, invalidation, update frequency, concurrency, and possible I/O or preprocessing costs.
  4. Under the simplified break-even model, when does indexing pay off? When q times the per-query saving exceeds index build and maintenance cost: q(U−I) > B+M, assuming compatible cost units.
  5. Why does a sorted dynamic array not guarantee logarithmic insertion? Finding an insertion point uses O(log n) comparisons, but shifting elements to create a slot may require O(n) moves.
  6. What does a prefix-sum array improve, and what does it make expensive? It enables O(1) contiguous range-sum queries after O(n) setup using O(n) extra storage; a point update can invalidate O(n) suffix entries.
  7. How do memoization and dynamic programming relate? Memoization caches distinct subproblem states on demand; bottom-up DP orders and calculates dependency states, possibly compressing retained memory.
  8. Why is memoized Fibonacci not automatically constant-space? It retains Θ(n) cached values, may use Θ(n) recursive frames, and uses arbitrary-precision integers whose bit sizes grow.
  9. What condition permits rolling-row dynamic programming? Each new row must be computable from a bounded number of predecessor rows whose values can be retained without overwriting needed dependencies.
  10. Why does a 0/1 knapsack one-row update traverse capacities downward? A descending update reads states from the previous item rather than letting the current item be reused multiple times.
  11. What can be lost through DP space compression? Predecessor information and a full table needed for solution reconstruction, sensitivity analysis, or inspection.
  12. What does a bounded LRU cache guarantee? A bound on entry count, not a bound on retained byte size or a universal hit-rate/latency guarantee.
  13. What factors determine cache hit rate? Working-set size, key-frequency distribution, locality and reuse distance, eviction policy, updates, and warmup.
  14. Why can a cache answer become invalid? The cache key may omit a dependency or the underlying data, permissions, time, or configuration may change without invalidation.
  15. What are the usual Bloom-filter error characteristics? Under a correctly maintained standard insertion-only filter: possible false positives, no false negatives; positives require verification if exactness matters.
  16. How does memory for a bounded-domain bitset scale? With the size of the key universe U in bits, not merely the number of present keys.
  17. Why might compressed data be faster than uncompressed data? Reduced transfer traffic or improved cache fit may outweigh decompression work, depending on access patterns and compression format.
  18. Why can an in-place method still need extra memory? It uses temporary variables and perhaps recursion frames; a caller may also copy the input when mutation is forbidden.
  19. What does streaming save? Materialization of intermediate or output collections when the consumer permits incremental processing; some state or output requirements may still grow.
  20. How do BFS and DFS differ in frontier storage? BFS can retain a wide depth frontier; DFS often retains a path and pending siblings, though visited sets may still be Θ(V).
  21. Why is meet-in-the-middle not a polynomial-time solution? For subset sum it typically stores and explores Θ(2^(n/2)) partial states, which is still exponential even though better than exploring all 2^n subsets directly.
  22. What does checkpointing exchange? It stores fewer intermediate states and recomputes omitted states when requested, increasing work in exchange for lower retained memory.
  23. When is approximate counting acceptable? When the application explicitly tolerates quantified statistical error, unlike correctness-critical exact ledgers or authorization decisions.
  24. What is the Pareto frontier? The options not dominated across all chosen resource dimensions; choosing among them requires operational preferences or hard constraints.
  25. Why compare peak memory, not only final memory? Temporary buffers during resizing, compaction, concurrency, or reconstruction can exceed the final resident footprint.
  26. Can a memory-efficient strategy also be faster? Yes. Compact contiguous layouts can reduce allocations and improve locality, and removing redundant work can improve both dimensions.
  27. Why must memory bounds state concurrency? Per-request or per-worker buffers can multiply across many active tasks, exceeding system capacity even if each request fits alone.
  28. What makes a benchmark defensible? Declared hardware/runtime and data distribution, repeatable runs, construction and query timings, updates, peak memory, warmup policy, and relevant tail latencies.

The glossary separates resource-accounting concepts, memory representations, caching mechanisms, and proof terms. The same name may carry additional restrictions in a particular runtime or textbook.

TermMeaning
Amortized costA bound on average cost per operation across a sequence, without assuming a probability distribution over inputs.
Approximate membershipA query contract permitting specified errors such as false-positive answers.
Auxiliary spaceTemporary storage used by an algorithm, separate from its defined input and sometimes output.
Batch processingCollecting operations to execute together, often improving locality or throughput while adding wait time.
Binary searchSearch within sorted keys by repeatedly halving an interval.
BitsetA set representation using one bit per possible key in a bounded universe.
Bloom filterA probabilistic insertion-and-membership structure with false positives under standard assumptions.
Break-even query countThe number of uses needed to recover an initial preprocessing cost through per-use savings.
BufferMemory area holding data temporarily between computation or I/O stages.
CacheStorage that retains results or data to avoid repeated expensive access.
Cache hitA request served from retained data without executing the full underlying computation.
Cache missA request requiring the original computation or backing-store access.
Cache localityTendency of data accesses to reuse nearby or recently accessed storage.
Cache evictionRemoval of a stored entry to reclaim capacity.
CheckpointPersisted intermediate state from which a later computation can resume or be reconstructed.
CompressionEncoding that reduces stored bytes under defined lossless or lossy semantics.
Compressed sparse rowA sparse matrix layout that groups nonzero values by row with compact offsets and indices.
Construction costWork required to build an index, cache, summary, or data structure before its use.
Data distributionFrequency or arrangement of input keys, values, or requests relevant to expected costs.
Dependency graphRelationships showing which computed states or results require others.
Derived storageAn index, prefix table, or memo table computed from original inputs and retained.
Dynamic programmingAlgorithmic strategy that solves interdependent subproblems while reusing their results.
Error contractAn explicit statement of which inaccuracies, if any, an algorithm may return.
Eviction policyRule for choosing which cached item to remove when space is needed.
External-memory modelModel charging movement of blocks between fast and slow memory.
False negativeA negative response for an item that truly belongs to the represented set.
False positiveA positive response for an item that does not belong to the represented set.
Fenwick treeIndex for prefix aggregates and updates, generally supporting logarithmic operations under suitable algebraic structure.
FrontierPending search nodes waiting to be explored.
GeneratorComputation that can yield successive results without materializing all of them at once.
Hash indexTable supporting keyed access under hashing and equality semantics.
Hit rateFraction of eligible lookups served from cached results in a specified workload.
In-place algorithmAlgorithm that modifies or rearranges data with bounded additional storage under a stated convention.
Index maintenanceCost of keeping a derived search structure consistent with changing source records.
Input storageMemory used to hold data supplied to the algorithm.
InvalidationProcess that marks or removes cached entries no longer safe to reuse.
Least recently usedCache-replacement policy favoring retention of recently accessed entries.
Lifecycle costTotal cost including setup, queries, updates, refresh, failure handling, and cleanup over a planning period.
Lossless compressionCompression preserving exact original data upon successful decoding.
Lossy compressionCompression allowing specified information loss to achieve smaller representations.
Memory budgetMaximum permitted memory use under a declared process or system boundary.
MemoizationCaching the output of a function or subproblem by its complete state key.
Meet in the middleSearch technique combining separately enumerated halves of a problem.
Output-sensitive boundComplexity measured partly as a function of the quantity of output produced.
Pareto dominanceBeing no worse on all chosen criteria and strictly better on at least one.
Pareto frontierSet of options not dominated under all chosen resource objectives.
Peak memoryMaximum simultaneously occupied memory during an execution.
Persistent indexDerived data structure retained across many operations or requests.
PrecomputationCalculations carried out ahead of queries to avoid repeated work.
Prefix sumCumulative sum array enabling constant-time subtraction of interval totals.
Probabilistic sketchCompact summary allowing approximate answers under a mathematical error model.
RecomputationRe-execution of previously completed work to avoid retaining old results.
Recursion frameRuntime state for an active function call.
Rolling arrayReuse of a small number of dynamic-programming rows or columns in place of a full table.
Segment treeHierarchical structure for aggregated range queries and point updates under an associative operation.
SelectivityFraction of records satisfying a query predicate.
Sequential scanInspection of records in order, often with low working storage.
Sparse representationEncoding that stores nonzero or present values rather than all possible positions.
Space compressionReduction of retained intermediate states through dependency-aware reuse.
StreamingIncremental production or consumption of data rather than whole-result materialization.
Succinct data structureRepresentation approaching the information-theoretic space minimum while supporting designated operations.
Tail latencyHigh-percentile request duration, reflecting rare slow operations.
Time-space tradeoffAlgorithmic design choice that changes computation and storage requirements together.
Top-down dynamic programmingOn-demand recursive computation with remembered subproblem answers.
Versioned cache keyKey incorporating a version or dependency stamp to distinguish changing source states.
Working setData actively accessed within a relevant time or operation window.
Worst-case boundGuaranteed cost upper bound over all admitted inputs under a stated model.
