Definition, Purpose, and Scope

Worst-case analysis studies the greatest cost an algorithm can incur among inputs admitted by a stated problem specification and input-size measure. Average-case analysis studies a probability-weighted cost across admissible inputs. They answer different questions: the first establishes a uniform ceiling for the chosen resource; the second evaluates behavior under an explicit model of how inputs occur. Neither is a synonym for asymptotic Big-O notation, an observed benchmark average, or the expected runtime of a randomized program without further qualification.

The core discipline is to specify the algorithm, input set, size parameter, resource measure, input distribution (when relevant), and randomness source before reporting a complexity result. For instance, saying that linear search is linear in the worst case is precise only after defining a scan of an array of n positions and counting comparisons or equivalent constant-time steps. Its average comparison count additionally depends on whether the search succeeds, which positions are more likely, and how often targets are missing.

It follows Asymptotic Notation and supports later units on Randomized Algorithm Analysis, Sorting Algorithm Analysis, and Algorithm Benchmarking and Profiling. Its instructional examples are constructed cases, not empirical reports on MGU infrastructure.

Start with an Algorithmic Cost Function

For a deterministic algorithm A and an admissible input x, let C_A(x) count the chosen resource: comparisons, assignments, word operations, bytes moved, or another specified unit. Define n=|x| as the declared size; depending on the task, this might be array length, number of graph vertices and edges, bit length of a number, or characters in a document. The same algorithm has different valid cost functions for distinct resources and machine models.

Two inputs of identical size can take substantially different paths through a program. In a sequential scan, the target might occupy the first position, last position, or no position. A data structure can be balanced or skewed; a partitioning procedure can split nearly evenly or produce one empty partition. A case classification aggregates these per-input costs. It is not a property inferred from a single experiment.

All basic expressions below assume each finite size class has at least one admissible input and the measured cost is nonnegative. For integer arithmetic with large operands, a unit-cost model may obscure bit-complexity differences; for I/O-bound code, comparisons alone may conceal expensive memory transfers. Choose a model appropriate to the decision being made and keep it unchanged across compared alternatives.

Formal Worst-Case, Best-Case, and Average-Case Definitions

Write I_n for the set of valid inputs of size n. For a deterministic algorithm with cost C(x), define the worst-case cost W(n)=max {C(x): x∈I_n} and the best-case cost B(n)=min {C(x): x∈I_n} when these extrema exist. If a maximum does not exist, an extended supremum can be used instead. Both describe an extremum over the same admissible input class, not over arbitrarily altered specifications.

For a probability model D_n over I_n, the average-case cost is A_D(n)=E_{X∼D_n}[C(X)]. For discrete inputs this is Σ_{x∈I_n} P(X=x)·C(x). A uniform average is the special case A_U(n)=(1/|I_n|)Σ_{x∈I_n} C(x) when the finite input set is uniformly sampled. Uniformity is an assumption that should be justified, not a default consequence of the word “average.”

Under these assumptions B(n)≤A_D(n)≤W(n). This inequality does not determine the average from the endpoints: two distributions concentrated on different parts of the input space can produce averages close to either extreme. A published average-case bound must therefore declare its input model as carefully as a worst-case bound declares its input domain.

Case Functions Are Different from Asymptotic Symbols

W(n), B(n), and A_D(n) are functions. By contrast, O, Ω, and Θ compare how functions grow. Thus W(n)∈Θ(n) means the worst-case cost function grows linearly; A_D(n)∈Θ(n) refers to the distribution-weighted mean; and B(n)∈Θ(1) refers to the least costly valid execution. These three claims can all be true for the same procedure.

A worst-case O(n) upper bound does not mean every execution takes exactly proportional time, nor does a mean O(n) guarantee an upper bound on each execution. A strong bound is expressed using a symbol and a case together, such as “for every size-n input, comparisons are at most n,” or “under uniform successful target positions, the expected number of comparisons is (n+1)/2.” Statements that omit the case or model risk conveying more than the proof establishes.

The distinction also applies to memory and I/O. An algorithm can have worst-case auxiliary space Θ(n), but an expected auxiliary-space use substantially smaller under a specific distribution. A safety-critical capacity budget normally needs a credible peak or tail bound rather than only a mean.

When a Worst-Case Bound Is Valuable

Worst-case bounds are particularly useful when the consequence of a slow execution is high, input behavior is difficult to predict, or a service must provide a predictable operation count. They can support design-time capacity estimates and compare alternatives without asserting that typical inputs are uniformly random. For instance, balanced search trees offer logarithmic-height bounds under their balancing invariants, whereas ordinary unbalanced search trees can degenerate to linear height.

The guarantee is only as strong as the computational model and implementation assumptions. A Θ(log n) comparison count is not a fixed response-time guarantee on an operating system with scheduling interruptions, page faults, network delays, or variable-time comparisons. Likewise, an algorithmic bound over a specified size class does not cover malformed inputs outside the declared contract, integer overflow, memory exhaustion, or adversarial manipulation of hidden implementation parameters.

A useful engineering record states the operation count or upper-bound formula, the cases covered, its resource assumptions, and any environmental variation that lies outside the theorem. Robust algorithms often pursue favorable expected behavior while retaining a separately proved worst-case fallback.

Why a Mathematical Average Requires a Distribution

The arithmetic midpoint of best and worst costs is generally not the average. The actual average weights each possible cost by the probability of encountering an input that produces it. If one expensive input is very rare, its contribution may be small; if costly inputs dominate the workload, the mean may approach the worst case. Even distributions sharing a common input size can yield dramatically different mean costs.

For a finite sample space with outcomes x₁,…,x_k, the expected cost is A=Σ_i p_i C(x_i), where p_i≥0 and Σ_i p_i=1. If the analyst groups inputs into classes—for example, successful searches, misses, short queries, and long queries—the law of total expectation aggregates class-specific means with class probabilities. These formulas are mathematical statements about a chosen model; real-world workload probabilities require separate evidence.

Average-case claims sometimes use “random input” to mean a uniformly shuffled array, a uniformly chosen permutation, independent key generation, or a specified synthetic generator. Those are different probability laws. A correct paper or technical article should say which one it uses and why it captures the relevant task.

A Small Probability Model with Unequal Costs

Suppose a three-case procedure needs respectively 1, 3, or 12 comparisons. If their probabilities are 0.7, 0.2, and 0.1, then E[C]=0.7·1+0.2·3+0.1·12=2.5. The worst-case count is 12, the best-case count is 1, and their midpoint 6.5 is not the mean. If the costly case instead occurs with probability 0.5 and the one-comparison case falls to 0.3, then the mean is 0.3·1+0.2·3+0.5·12=6.9.

The algorithm has not changed; its average has, because the distribution changed. Both outcomes remain bounded above by the worst case 12. This is the central reason that an average-case theorem must include a distribution and that an empirical average cannot be assumed to remain stable when usage patterns shift.

costs = (1, 3, 12)
p1 = (0.7, 0.2, 0.1)
p2 = (0.3, 0.2, 0.5)
def expected_cost(costs, probabilities):
    assert len(costs) == len(probabilities)
    assert abs(sum(probabilities) - 1) < 1e-10
    return sum(c*p for c, p in zip(costs, probabilities))
assert abs(expected_cost(costs, p1) - 2.5) < 1e-12
assert abs(expected_cost(costs, p2) - 6.9) < 1e-12
print(expected_cost(costs, p1), expected_cost(costs, p2))

Random Inputs and Randomized Algorithms Are Not Identical

A deterministic procedure can have an average-case analysis when its input is modeled as random. Conversely, a randomized procedure draws random choices internally, so its running time may vary even on a fixed input. Write C(x,r) when both an input x and random decisions r influence cost. Then E_R[C(x,R)] is the conditional expected cost for a specified input; E_X E_R[C(X,R)] averages across both inputs and algorithmic randomness.

These expectations can have different guarantees. An algorithm may have max_x E_R[C(x,R)] ∈ O(n log n) even though some unlucky random sequences lead to Θ(n²) work. That claim is stronger than asserting a good mean only for uniformly random inputs, yet weaker than a deterministic per-execution O(n log n) worst-case bound.

Always mark the probability source, particularly when explaining randomized pivot selection, universal hashing, randomized balanced search structures, or input sampling. The separate Randomized Algorithm Analysis article develops concentration, correctness probabilities, and randomized contracts in greater depth.

Law of Total Expectation for Workload Mixtures

Let H indicate that a search succeeds, with P(H)=p. Then E[C]=p·E[C|H]+(1-p)·E[C|not H]. This expression requires no assumption that successful and unsuccessful searches occur equally often. It decomposes the workload into interpretable categories whose probabilities can be measured or hypothesized.

For more categories K_i forming a disjoint exhaustive partition, E[C]=Σ_i P(K_i) E[C|K_i]. The same method can combine query sizes, device classes, table-load bands, day/night traffic, or data-shape categories. Conditional averages must be computed within the specified category; combining a conditional average with the wrong probability double-counts or omits parts of the workload.

A workload mixture is especially useful for deciding whether an occasional expensive input matters operationally. It makes explicit which costs are rare and what they contribute to total expected work. It does not remove the need to consider a maximum when individual long-running operations can disrupt the system.

Indicator Variables and Expected Counts

An indicator variable takes the value 1 if an event occurs and 0 otherwise. Its expectation equals the event's probability. If the total number of comparisons or expensive operations is the sum of indicators, linearity of expectation gives E[Σ_i I_i]=Σ_i E[I_i] without requiring those events to be independent. This can turn a complicated probability distribution into a collection of simple event probabilities.

For example, in a successful search whose target is uniformly distributed among n positions, the comparison at position i occurs if the target lies at or after i, an event with probability (n-i+1)/n. Summing over i=1,…,n gives (n+1)/2. Directly averaging 1 through n yields the same result, but the indicator method extends to more complicated algorithms where enumerating complete executions is impractical.

Linearity of expectation is not a bound on the maximum. It characterizes a mean, so a proof about indicators must not be promoted to a worst-case guarantee without an additional argument.

Linear Search: Exact Worst and Best Costs

Consider a simple search that scans a nonempty array from index 0 until it finds a target or reaches the end. Count each test of the current element against the target as one comparison. A hit at position j, using one-based indexing, costs exactly j comparisons. A miss costs exactly n. Thus B(n)=1 if at least one valid input has a first-position hit, while W(n)=n if misses or last-position hits are allowed.

A missing-target instance and a last-position hit each attain the worst-case cost in this model. That is a concrete adversarial witness for every n≥1. To assess other resources, note that the implementation uses a constant number of scalar variables in addition to the supplied array; this auxiliary-space claim assumes comparing elements requires constant extra storage.

The input class matters: if the specification requires an existing target and places it first, the worst-case cost within that restricted class is 1, not n. A worst-case proof can only range over inputs that the problem contract actually permits.

def linear_search_with_count(items, target):
    comparisons = 0
    for i, item in enumerate(items):
        comparisons += 1
        if item == target:
            return i, comparisons
    return -1, comparisons
assert linear_search_with_count([4, 8, 15, 16], 4) == (0, 1)
assert linear_search_with_count([4, 8, 15, 16], 16) == (3, 4)
assert linear_search_with_count([4, 8, 15, 16], 99) == (-1, 4)
print('Linear search boundary cases passed')

Linear Search: Uniform Successful Positions

Assume the search is guaranteed to succeed, the sought key has no earlier matching occurrence, and its target position is uniformly distributed across 1,…,n. There are n equally likely comparison counts. Therefore E[C|success]=(1+2+⋯+n)/n=(n+1)/2. The average is Θ(n) even though the first-position best case is Θ(1). Linear worst- and average-case bounds can have the same growth order while differing by a constant factor.

The formula follows from a uniform position assumption, not merely from the word “successful.” An array with popular targets disproportionately placed at the beginning has a lower expected scan length; a workload with popular targets at the end has a higher one. The mean may change after a reordering without the worst-case number of comparisons changing.

For n=8, the conditional average is 4.5 comparisons, whereas the worst-case count is 8. The fractional mean does not imply an execution with half a comparison; it is the expected value across many modeled searches.

def mean_successful_linear_search(n):
    if n <= 0:
        raise ValueError('n must be positive')
    return sum(range(1, n + 1)) / n
for n in range(1, 101):
    assert mean_successful_linear_search(n) == (n + 1) / 2
assert mean_successful_linear_search(8) == 4.5
print('Uniform-success means verified for n=1..100')

Linear Search: Combining Successful Searches and Misses

Let p be the probability that a search succeeds, and suppose that, conditional on success, the target is equally likely to occur in any of the n positions. All misses still require n comparisons. Then E[C]=p(n+1)/2+(1-p)n = n - p(n-1)/2. This formula is exact for the specified simple search and distribution.

At p=1 the result reduces to (n+1)/2; at p=0 it is n; for a 50% hit rate it is (3n+1)/4. Each is Θ(n) when p stays between 0 and 1 as n grows. The hit probability alone is not sufficient if successful positions are skewed, because a different conditional distribution changes the first term.

Example: for n=20 and p=0.6, the expected comparisons are 0.6·10.5+0.4·20=14.3. This result is a workload-dependent mean, while every execution still needs at most 20 comparisons.

def mixed_linear_search_mean(n, hit_probability):
    if n < 1 or not (0 <= hit_probability <= 1):
        raise ValueError('invalid inputs')
    return hit_probability * (n + 1)/2 + (1-hit_probability)*n
assert abs(mixed_linear_search_mean(20, 0.6) - 14.3) < 1e-12
assert mixed_linear_search_mean(20, 1) == 10.5
assert mixed_linear_search_mean(20, 0) == 20
print('Mixture formula correct')

Linear Search: Unequal Target Probabilities

If a successful target occurs at index i with conditional probability q_i, where positions are numbered 1 through n, then E[C|success]=Σ_{i=1}^n i q_i. The uniform formula is recovered only when all q_i=1/n. A realistic workload may instead have a handful of highly popular keys, making the access-weighted mean materially different.

For four possible target locations with probabilities 0.7, 0.1, 0.1, and 0.1, the conditional average cost is 0.7·1 + 0.1·2 + 0.1·3 + 0.1·4 = 1.6. Reverse the order of those probabilities and the mean becomes 3.4. Both lists still have worst-case four comparisons and use the same scan code. The distribution and physical ordering, not the asymptotic worst-case bound, explain the difference.

This observation motivates access-frequency ordering in self-organizing lists and cache layouts. Reordering may itself have a maintenance cost, so a responsible performance analysis includes update frequency and the expense of acquiring accurate frequency estimates.

weights = [0.7, 0.1, 0.1, 0.1]
def weighted_scan_cost(probabilities):
    assert abs(sum(probabilities) - 1.0) < 1e-9
    return sum((i + 1) * p for i, p in enumerate(probabilities))
assert abs(weighted_scan_cost(weights) - 1.6) < 1e-12
assert abs(weighted_scan_cost(list(reversed(weights))) - 3.4) < 1e-12
print('Weighted location costs verified')

Why Frequency-Ordered Sequential Search Helps

For repeated successful searches with stable target probabilities, a static sequential list minimizes expected comparisons by placing keys in nonincreasing order of their access probabilities. The argument is a simple exchange proof: suppose key A with probability p_A is immediately after key B with probability p_B, but p_A>p_B. Swapping them moves A one comparison earlier and B one comparison later, changing expected cost by p_B-p_A<0. Thus any adjacent inversion of probability order can be improved.

The conclusion concerns the successful-search comparison objective under fixed keys and probabilities. It does not state that rearranging a list is always operationally beneficial: insertion order, update work, miss checks, cache locality, and changes in access frequencies may outweigh the expected comparison savings. Nor does it apply without adjustment to a search data structure whose lookup paths are not linear.

More generally, average-case optimization often depends on statistical workload knowledge. Worst-case optimization instead seeks a guarantee across all admitted inputs, including distributions that never occurred in a representative sample.

Best and Worst Cases under Preconditions

An algorithmic guarantee is conditional on the specification. Binary search can take logarithmically many key comparisons on a sorted sequence with random access; it has no correctness guarantee on an unsorted input that violates its precondition. Merge sort has Θ(n log n) worst-case comparisons under a conventional comparison model; an in-place implementation or a hybrid variant can modify constants and memory behavior without changing that broad bound.

It is therefore essential to record sortedness, uniqueness, valid index ranges, integer ranges, graph representation, required stability, and other constraints before deriving input-dependent costs. Once a contract narrows the input set, the maximum and average must be recomputed for that domain. Relaxing the contract after a proof invalidates its original scope.

For untrusted or public-facing inputs, designers should distinguish valid adversarial cases from malformed inputs requiring validation. A poorly specified input model can make a reassuring complexity theorem irrelevant to the actual system.

Binary Search: Favorable and Deepest Search Paths

For binary search on a sorted random-access array, the first probed middle element can match immediately. Other values require successive interval reductions, and a miss continues until the interval becomes empty. The number of probes is determined by which comparisons are encountered, so exact costs depend on the particular target and the implementation's inclusive or half-open interval convention.

The key worst-case fact is that every unsuccessful comparison reduces the number of candidate positions by approximately half. After k reductions, at most roughly n/2^k candidates remain, giving O(log(n+1)) comparisons. A logarithmic worst-case bound also bounds every search's number of comparisons in that model. To describe the average more precisely, one needs a distribution over successful target positions and misses; an average of search-tree depths can then be computed.

This is not an assertion that every binary search execution costs exactly Θ(log n). A middle-element hit can cost one comparison. Nor is the algorithm equivalent to an ordered-tree search on arbitrary pointer-based storage, where finding the middle node may itself be expensive.

def binary_search_count(items, target):
    lo, hi = 0, len(items)
    probes = 0
    while lo < hi:
        mid = lo + (hi-lo)//2
        probes += 1
        if items[mid] == target:
            return mid, probes
        if items[mid] < target:
            lo = mid + 1
        else:
            hi = mid
    return -1, probes
arr = list(range(31))
counts = [binary_search_count(arr, x)[1] for x in arr]
assert min(counts) == 1
assert max(counts) <= 5
assert binary_search_count(arr, 100)[0] == -1
print('Successful search probe range:', min(counts), max(counts))

Binary Search with Unequal Query Popularity

Suppose searches are successful but some keys are requested much more often than others. The expected comparisons are the sum over targets of P(target=x)·depth(x), where a key probed at the root has depth one in the implicit decision tree. Different orderings of query probabilities over sorted keys can change the expected cost without changing the array's size or its worst-case logarithmic bound.

For example, if the middle key is requested 90% of the time, the expected probe count can be close to one; if most requests target a deepest leaf, the mean is close to the worst-case path length. Binary search is excellent for guaranteed logarithmic comparisons, but it does not automatically optimize a highly skewed static query distribution. An optimal binary-search-tree formulation can explicitly account for query probabilities under different storage constraints.

When choosing a search method, distinguish the cost of looking up a key from building the index, maintaining sorted order after updates, or transferring data to memory. A low per-query comparison count is not a complete end-to-end complexity model.

Insertion Sort: The Best and Worst Orderings

Insertion sort processes an initial sorted prefix and inserts each next key into its proper place. With a common adjacent-shift implementation, an already nondecreasing array requires only one successful termination comparison per outer iteration after the next value is checked against its predecessor, giving linear comparisons. A strictly decreasing array forces every new key to move across the existing prefix, requiring 1+2+⋯+(n-1)=n(n-1)/2 comparisons and movements, up to implementation-specific counting conventions.

The asymmetry is structural: input order determines how far each key travels. Insertion sort's best case is Θ(n) and its worst case is Θ(n²) for the familiar array-based variant. The algorithm can be useful for small or nearly sorted arrays despite the quadratic worst case, especially within hybrid sorting methods. Exact performance additionally depends on comparisons, assignments, branch behavior, and storage layout.

A guarantee of linear work on fully sorted inputs does not imply that arbitrary “mostly sorted” workloads are linear without a defined measure of disorder. Inversion count provides one such measure and connects exact data patterns with analysis.

Inversions: A Better Measure of Insertion-Sort Work

An inversion is a pair of indices i<j with a[i]>a[j]. In an insertion sort implemented by moving a key left past greater predecessors, every shift resolves one inversion, so the total number of shifts is exactly the inversion count I. Under a conventional single-comparison-per-key-test loop, the number of key comparisons lies between I and I+(n-1), depending on how often comparisons terminate with a failed key test. Therefore the number of comparisons is Θ(n+I) for n≥2 in that implementation.

For sorted distinct keys, I=0 and work is linear. For reversed distinct keys, I=n(n-1)/2 and work is quadratic. This input-sensitive measure is more informative than naming only best and worst cases, because it relates behavior continuously to a concrete property of the data rather than assigning every input to an extreme bucket.

The inversion result does not carry over unchanged to every insertion-sort variant: using binary search to find insertion positions changes comparison counts but still entails shifts in an array. The operation model must reflect the actual algorithm.

def insertion_sort_counts(values):
    a = list(values)
    comparisons = shifts = 0
    for i in range(1, len(a)):
        key, j = a[i], i - 1
        while j >= 0:
            comparisons += 1
            if a[j] <= key:
                break
            a[j+1] = a[j]
            shifts += 1
            j -= 1
        a[j+1] = key
    return a, comparisons, shifts

def inversion_count(a):
    return sum(a[i] > a[j] for i in range(len(a)) for j in range(i+1, len(a)))
for arr in ([1,2,3,4], [4,3,2,1], [4,1,3,2], []):
    ordered, comparisons, shifts = insertion_sort_counts(arr)
    assert ordered == sorted(arr)
    assert shifts == inversion_count(arr)
    assert shifts <= comparisons <= shifts + max(0, len(arr)-1)
print('Insertion-sort inversion model checked')

Average Inversions of a Uniform Random Permutation

Assume an array contains n distinct keys and all n! permutations are equally likely. For each unordered pair of keys, the probability that their order is reversed is 1/2. There are n(n-1)/2 such pairs; by linearity of expectation, E[I]=n(n-1)/4. No independence assumption among these inversion events is needed for this sum.

The adjacent-shift implementation performs exactly I shifts and at most I+n-1 data comparisons, so the expected number of shifts is n(n-1)/4 and expected comparisons are Θ(n²) under this uniform permutation model. This is a legitimate average-case result, but it does not predict workloads where arrays are usually sorted or nearly sorted.

The proof illustrates an important analysis technique: describe cost as a sum of simple events, compute the expectation of each, and add them. It avoids enumerating the n! full permutations even though all permutations define the distribution.

from itertools import permutations
from fractions import Fraction

def inversion_count(a):
    return sum(a[i] > a[j] for i in range(len(a)) for j in range(i+1, len(a)))
for n in range(2, 7):
    perms = list(permutations(range(n)))
    total = sum(inversion_count(p) for p in perms)
    observed = Fraction(total, len(perms))
    predicted = Fraction(n * (n-1), 4)
    assert observed == predicted
print('Uniform-permutation inversion expectations verified n=2..6')

Average Sorting Performance Is Not a Single Number

Input distributions for sorting can be modeled in many ways: uniformly random permutations of distinct keys, independently sampled values that include duplicates, nearly sorted sequences, arrays with a small alphabet, or concatenated sorted runs. They do not induce the same inversion counts or quicksort partition patterns. A sorting algorithm's mean performance is not a universal property detached from those inputs.

An analysis of comparisons may also disagree with practical wall time. Two sorts with the same asymptotic expected comparisons may differ in memory writes, cache behavior, allocation, branch prediction, and function-call overhead. Stable sorting requirements, noncomparison key models, and external-memory costs further change the relevant choice. The Sorting Algorithm Analysis specialist article addresses those wider evaluation criteria.

A sound summary states at least: which family of inputs is modeled, what resources are counted, whether duplicates are permitted, whether the sort is stable or in-place, and whether the claimed bounds are expected, worst-case, or both.

Quicksort: Why Partition Quality Matters

Quicksort chooses a pivot, partitions the remaining keys, and recursively sorts the two sides. On an array of n distinct elements, a standard comparison partition performs n-1 pivot comparisons at the root. If the pivot is the minimum or maximum, one recursive side has size n-1 and the other zero; the recurrence becomes T(n)=T(n-1)+(n-1) comparisons and yields n(n-1)/2 = Θ(n²). For a balanced split the recursion depth is logarithmic and total comparisons grow on the order of n log n.

With a deterministic first-element pivot rule, sorted or reverse-sorted inputs can repeatedly produce a maximally unbalanced split for a suitable standard partition. These are adversarial witnesses for the quadratic worst case. The exact comparison count depends on the partition implementation; the asymptotic distinction persists for conventional versions.

A common analytical mistake is to assume every partition divides an input in half and label the resulting Θ(n log n) recurrence an “average.” Evenly balanced partitions describe a favorable shape, not a probabilistic proof. Average-case reasoning requires a distribution for pivot ranks or for input permutations.

Random-Pivot Quicksort: Conditional Expected Work

Suppose the n input keys are distinct, each recursive call chooses a pivot uniformly at random from its current subarray, and every call performs one comparison between the pivot and each other key in that subproblem. For the comparison count C_n, the rank of the pivot is uniform over the n positions. Consequently E[C_n]=(n-1)+(1/n)Σ_{k=0}^{n-1}(E[C_k]+E[C_{n-1-k}]), with E[C_0]=E[C_1]=0.

The solution is E[C_n]=2(n+1)H_n-4n, where H_n=Σ_{i=1}^n 1/i. It is Θ(n log n) because the harmonic number grows logarithmically. This result holds for every fixed array of distinct keys under the stated uniform independent pivot-rank choices, not merely for uniformly random input permutations. Yet an unlucky sequence of pivot choices still yields Θ(n²) comparisons.

Real quicksort implementations can use three-way partitions, sampling, cutoffs, or introspective fallback techniques, altering exact comparison counts. Duplicate keys require particular care: a two-way scheme that repeatedly produces poor partitions can behave differently from a dedicated three-way strategy. The formula above belongs to its precisely stated comparison model.

Quicksort Expected Comparisons: A Small Exact Calculation

For n=5, the harmonic number is H₅=137/60, so the random-pivot model gives E[C₅]=2·6·(137/60)-20=7.4 comparisons. The fixed-pivot worst-case chain performs 5·4/2=10 comparisons. This difference reflects the expectation over internal pivot randomness, not a reduction of the worst-case bound.

A dynamic-programming calculation of the expectation checks the recurrence by summing over all possible pivot ranks. For larger n, its result agrees with the closed form up to floating-point rounding. The code below measures the defined theoretical comparison model; it does not benchmark a production sorting library.

def quicksort_expected_comparisons(n):
    e = [0.0] * (n + 1)
    for m in range(2, n + 1):
        e[m] = (m - 1) + sum(e[k] + e[m-1-k] for k in range(m))/m
    return e[n]
def harmonic(n):
    return sum(1/i for i in range(1, n+1))
assert abs(quicksort_expected_comparisons(5) - 7.4) < 1e-12
for n in range(1, 60):
    assert abs(quicksort_expected_comparisons(n) - (2*(n+1)*harmonic(n)-4*n)) < 1e-8
print('Quicksort theoretical mean:', quicksort_expected_comparisons(5))

A Random-Pivot Quicksort Experiment

The following demonstration counts one abstract three-way pivot-versus-key comparison per non-pivot item in a straightforward recursive implementation. Python may use two relational operators to implement that conceptual comparison; those underlying operator calls are not the chosen cost measure. Since each partition creates two new lists, allocation costs and copying are outside this count; this is not an in-place reference implementation. The test runs repeated seeded trials on distinct input keys to illustrate variation in comparisons while preserving sorted output.

Simulation is useful for spotting implementation errors or developing intuition, but a small experimental average is not proof of the harmonic-number formula. The analytic recurrence supplies the proof, and the random generator supplies one finite set of outcomes. If the random source is predictable to an adversary in a security context, worst-case exposure may require additional treatment.

import random

def randomized_quicksort_count(items, rng):
    if len(items) <= 1:
        return list(items), 0
    pivot_idx = rng.randrange(len(items))
    pivot = items[pivot_idx]
    left, right = [], []
    for idx, value in enumerate(items):
        if idx == pivot_idx:
            continue
        relation = (value > pivot) - (value < pivot)  # one abstract 3-way comparison
        if relation < 0:
            left.append(value)
        else:
            assert relation > 0  # example assumes distinct keys
            right.append(value)
    a, count_a = randomized_quicksort_count(left, rng)
    b, count_b = randomized_quicksort_count(right, rng)
    return a + [pivot] + b, (len(items)-1) + count_a + count_b

rng = random.Random(2026)
values = list(range(8))
trials = []
for _ in range(500):
    sorted_result, comparisons = randomized_quicksort_count(values, rng)
    assert sorted_result == values
    trials.append(comparisons)
assert min(trials) <= max(trials)
print('500 trials, mean comparisons:', round(sum(trials)/len(trials), 2))

Worst-Case Quicksort and Adversarial Input Design

Worst-case analysis is not a claim that the worst input is frequent. It identifies a valid stress case that shows the maximum can be high. When pivot selection is deterministic and inputs are externally chosen, an attacker or a naturally structured workload may systematically produce imbalanced partitions. For a fixed first-element pivot, monotonic distinct-key sequences are a simple classroom example.

Random pivot selection breaks the straightforward dependence between input order and pivot rank in the ideal model, yielding good expected comparisons for each fixed input. It does not make the quadratic worst-case impossible. An introspective sort can instead monitor recursive depth and switch algorithms, aiming for an independent worst-case bound. Other protections include three-way handling of equal keys and limiting recursion depth for memory safety.

Applications should record both the bound and the threat model. An average based on naturally occurring input distributions is insufficient when attackers can choose algorithmically hostile inputs or exploit predictable random decisions.

Hash Tables: Assumptions Behind Expected Constant Time

Hash-table operations are often described as expected constant time, but the result depends on hashing strategy, load factor, collision resolution, and assumptions about keys or randomized hash functions. For separate chaining with a sufficiently uniform distribution of keys over buckets, the expected chain length is related to the load factor α=n/m, with n stored keys and m buckets. Keeping α bounded can support expected O(1) search cost under suitable hash assumptions.

In a worst case, many keys collide in the same bucket, creating a chain of length n and a linear search cost. The same data structure can therefore have an expected O(1) operation under a stated hashing model and a worst-case O(n) operation under ordinary chaining. An implementation that resizes periodically must also distinguish individual operation cost from amortized cost across a sequence.

Hashing is a good example of why precise quantifiers matter. “Expected O(1)” could mean averaging over a random hash function for every fixed key set, or assuming a distribution on keys for a fixed hash function. Those are different claims and need different evidence.

Binary Search Trees: Shape-Dependent Search Cost

In a standard unbalanced binary search tree, lookup cost is proportional to the length of the visited root-to-key path. A tree formed by inserting keys in strictly increasing order can become a chain with worst-case height n; an adequately balanced tree has height O(log n). An average under randomly ordered insertions can be better than the pathological case, but a precise theorem must define the distribution over insertion orders and search queries.

Balanced trees use structural invariants to provide stronger worst-case height guarantees. That distinction is especially relevant in systems exposed to arbitrary insertion sequences, because historical averages do not prevent a future skewed workload. The cost of rebalancing and rotations is part of the update algorithm and should be included in its own analysis.

Do not confuse the depth of a randomly selected node in one fixed tree with the search cost averaged over randomly generated trees. Both are legitimate distributions, but they sample different objects and can yield different expected values.

Selection and Sampling Algorithms

A partition-based selection routine that recurses into only the side containing the desired rank often has favorable expected cost when pivot ranks are suitably randomized. However, a sequence of extreme pivots can yield a quadratic total number of examined elements. The general lesson mirrors quicksort: count nonrecursive partition work, define the subproblem-size distribution, and then derive the expectation across the resulting recursion.

Selection also illustrates the distinction between a randomized algorithm and an algorithm whose data are randomly sampled. Uniformly random pivots can be chosen for a fixed input, while a deterministic pivot rule may be analyzed over a random ordering of inputs. Some selection algorithms can achieve deterministic linear worst-case comparisons under a suitable comparison model, though implementation constants and use cases differ.

High-stakes selection services should document not just an expected time but also acceptable latency tails and fallback behavior. A service that repeatedly handles large or adversarial partitions may not be well served by a mean alone.

Graph Workloads: Input Size Is Sometimes a Pair

For graph algorithms, the natural input dimensions often include vertices V and edges E. In an adjacency-list representation, a full BFS or DFS traversal of all vertices and edges has O(V+E) work even though specific source-to-target searches may terminate earlier. In an adjacency-matrix representation, inspecting all potential neighbors of visited vertices can lead to O(V²) work for a full traversal.

Graph search cost varies with connectivity, component sizes, target location, and the chosen traversal order. An average requires a graph distribution—such as one over edge sets—as well as any query distribution. Saying “average over graphs with V vertices” leaves open whether E is fixed, how edges are generated, and whether graphs are directed or weighted.

A multivariate worst-case bound can be more useful than collapsing all graphs to a single scalar n. Meaningful resource analysis also reports representation and memory usage, not merely graph-theoretic counts.

Recurrences in Case Analysis

Recursive programs may have different recurrence relations for different input shapes. A partition-based algorithm can have W(n)=W(n-1)+Θ(n) along worst-case splits, but expected work may average over many split sizes. A balanced recurrence such as T(n)=2T(n/2)+Θ(n) describes a particular decomposition pattern and need not represent the unconditional average of an arbitrary partitioning algorithm.

To derive a worst-case recurrence, maximize over the valid subproblem configurations. To derive an average-case recurrence, weight configurations by their probabilities. Do not replace an expectation with a recurrence for a single representative “average” partition unless a separate argument justifies the substitution. Nonlinear cost functions can make such shortcuts badly misleading.

The next specialist treatments are Recurrence Relations in Algorithm Analysis and Recursion Trees and the Master Theorem. They provide systematic tools for solving the equations once the relevant case model has been defined.

The Difference Between Expected and Amortized Cost

Expected cost is an average over a probability model. Amortized cost allocates the total cost of a sequence across its operations and may provide a deterministic guarantee without any probability distribution. A dynamic array resize can take Θ(n) for one insertion, yet a sequence of appends can have O(1) amortized cost per operation under a standard geometric growth policy. That statement is not a probability-weighted average over randomly chosen inputs.

The two concepts can coexist: a randomized data structure may have expected amortized performance. When reporting such a result, identify both the probability space and the sequence-level accounting. Substituting “average” for “amortized” obscures which guarantee survives an adversarial operation sequence.

Detailed proofs of aggregate, accounting, and potential-function approaches belong to the separate Amortized Analysis article. Here the purpose is to preserve the conceptual boundary in case classifications.

Mean Runtime Does Not Guarantee an Individual Runtime

Expectation provides a central tendency, not an upper bound on each outcome. A random runtime might be 1 unit with probability 0.99 and 1,001 units with probability 0.01; its mean is 11 units, but the rare execution is more than ninety times the mean. Conversely, an algorithm with a slightly larger mean could have a far smaller worst case and be preferable for interactive or safety-sensitive systems.

Describing the input probability model is necessary but does not itself supply a latency percentile. To quantify tail risk, one needs additional information such as a distribution, variance, concentration bound, or direct operational measurements. A system capacity plan can use the mean to estimate total consumption while still requiring peak, queueing, or deadline analysis for operational reliability.

A comparison of algorithms should therefore report the relevant combination of mean, worst-case ceiling, percentile behavior, memory footprint, and sensitivity to assumptions, rather than declaring the algorithm with the smallest expected step count universally superior.

Markov’s Inequality: A Basic Mean-to-Tail Bound

For any nonnegative random cost C and threshold a>0, Markov’s inequality states P(C≥a)≤E[C]/a. Consequently, P(C≥k·E[C])≤1/k for k>0 when E[C]>0. The argument follows because on the event C≥a, at least a units contribute to expectation, so E[C]≥a·P(C≥a).

This bound requires little distributional information but is often loose. If the expected cost is 100 comparisons, Markov permits at most a 10% probability of requiring 1,000 or more comparisons, but it may not reflect the actual tail probability. The inequality does not imply a deterministic cutoff or a guarantee that 90% of executions finish within a fixed number of seconds on an actual machine.

Sharper probability bounds may require independence, variance bounds, martingale structure, or other assumptions. Their treatment belongs primarily to randomized algorithm analysis and probability for computing; the important point here is that an expectation alone does not turn into a strong worst-case promise.

Variance, Percentiles, and Conditional Distributions

Two workloads can share the same mean while having different spread. The variance Var(C)=E[(C-E[C])²] summarizes squared deviations from the mean; a percentile such as q₀.₉₉ identifies a cost threshold exceeded with probability no greater than about 1% under a specified quantile convention. Neither is equivalent to the deterministic worst-case maximum.

For a service with separate small and large request classes, a single all-requests average may hide the cost distribution of the large class. Conditional percentiles by input size or workload category can be more useful than one pooled percentile. Likewise, a low mean comparison count does not rule out memory spikes if rare paths allocate enormous temporary buffers.

Analyze the correct unit: one query, an entire batch, a peak concurrent workload, or a sequence of updates. The distribution of aggregate costs across a batch is not automatically the same as the distribution of costs for one item.

Worst-Case versus Adversarially Chosen Inputs

A worst-case theorem quantifies over all admissible inputs of the stated size, regardless of how they were selected. An adversarial workload means an agent may intentionally choose difficult inputs, perhaps after observing details of the implementation. The mathematical worst-case value itself does not require an attacker, but it is useful when adversarial selection is plausible.

The distinction matters when a randomized algorithm draws fresh private choices: an attacker may choose a fixed input but not know or control the random pivot decisions, in which case a worst-input expected bound can be informative. If random choices are predictable, reused, or leak through behavior, the effective model changes. Robust engineering documents those trust and information assumptions instead of claiming that randomization eliminates all pathological cases.

The same caution applies to crafted hash collisions, highly skewed trees, degenerate parser inputs, and allocation-sensitive workflows. Analyze input validation and resource controls separately from mathematical comparison counts.

Modeling Workload Drift and Changing Frequencies

An average-case statement can become less representative when traffic, user behavior, data ordering, query mix, or key frequencies change. For a time-indexed distribution D_{n,t}, the relevant mean is A(n,t)=E_{X∼D_{n,t}}[C(X)]; there is no reason for it to stay constant if the probabilities change. A shift from mostly successful lookups to mostly misses can raise average scan cost even when source code and data size stay unchanged.

To operationalize a probability model, define workload categories, measure representative frequencies, check the sampling window, and revisit the model after material system changes. Keep the derived formula separate from estimated parameters, so an analyst can update assumptions without rewriting the entire proof.

Historical traces can be biased by time of day, caching, deployment changes, data selection, and missing failed requests. A credible model identifies the gap between observed samples and the population over which a performance claim is intended to hold.

Different Resources May Have Different Case Profiles

A recursive procedure may have expected O(n log n) comparisons but occasionally use Θ(n) call-stack space along a degenerate branch. A hash table may provide expected constant-time lookups while consuming memory proportional to allocated bucket count and changing its peak usage during resize. The worst or expected cost of one resource cannot substitute for another resource without proof.

Memory analysis also needs a counting convention: input storage, auxiliary buffers, recursion frames, cache, output, and persistent indexing structures can be included or excluded under different definitions. A resource report that merely says “space O(n)” without identifying which storage is being counted can obscure the operational constraint.

When a cost has several dimensions, report a vector such as comparisons, writes, peak memory, and block transfers. This is especially useful when a mean comparison improvement raises worst-case memory consumption or when an index saves repeated query work at significant construction and maintenance cost.

Input Size, Value Magnitude, and Bit Complexity

In mathematical algorithms, the magnitude of an integer and the number of bits needed to represent it are different size measures. A procedure that makes O(N) steps for a numeric value N may be exponential in the binary input length b≈log₂N. Average- or worst-case labels cannot be interpreted correctly until the input-size convention is explicit.

Some algorithms also operate on variable-length keys where one “comparison” may inspect multiple characters or bits. If key comparison cost is not constant, then counting comparisons alone can misrepresent time. Correct case analysis may require weighting the cost of each comparison by operand length or by the probability of encountering a long shared prefix.

The article's linear-search and sorting examples use a standard constant-cost comparison model. This is deliberate: the model makes case differences intelligible, but real-world analyses sometimes need a richer resource function.

Algorithm Correctness Is Independent of Average Performance

A procedure can run quickly on average and still return incorrect results. Correctness is usually established through invariants, preconditions, and postconditions, not through favorable timing samples. In probabilistic algorithms that permit an error probability, the correctness distribution must be analyzed separately from runtime: a low expected running time says nothing by itself about the chance of an incorrect result.

Randomized quicksort, for example, retains sorting correctness for every pivot choice in its mathematical model; the random choices change the work. A randomized approximation or sampling estimator may instead have an accuracy or failure probability that also requires analysis. The distinction between Las Vegas (always correct when terminating, randomized runtime) and Monte Carlo (typically bounded resource use with possible error) is useful, though real algorithms can have more complex contracts.

A complete assurance argument includes both the cost bound under its defined assumptions and the correctness argument under the same input contract.

Cost Models versus Benchmarked Time

A theoretical step count abstracts away machine details, while a measured runtime includes implementation decisions, memory hierarchy, interpreter or compiler behavior, allocator behavior, scheduling, and input representation. Worst-case operation counts can compare growth independently of processor clock speed; benchmarks reveal constant factors and implementation bottlenecks that the model does not express.

A sound experiment distinguishes inputs deliberately constructed to exercise worst-case paths, inputs sampled from a justified distribution, and stress tests of memory or concurrency. Use fixed random seeds for reproducibility but do not use only one seed to conclude that a randomized algorithm's tail behavior is acceptable. Count comparisons in instrumented implementations when feasible, and record actual elapsed times as a separate empirical measure.

Wall-clock benchmarks should warm up code where appropriate, avoid overlapping unrelated activity when possible, use multiple samples and size ranges, and report hardware, runtime versions, input-generation procedure, and spread. The separate Algorithm Benchmarking and Profiling article develops these methods.

A Reproducible Input-Generation Experiment

To compare insertion-sort behavior across data patterns, generate the same number of distinct elements under several defined distributions: sorted order, reversed order, and a seeded uniform shuffle. Count comparisons and shifts separately. This contrasts exact analytical edge cases with a model-dependent sample. A single seeded shuffle is an example outcome, not an estimate with a justified confidence interval.

For small arrays the result can be checked against a direct inversion-count function. As n increases, the reversed input exhibits quadratic shifts; the sorted input has zero shifts; and uniformly permuted inputs exhibit quadratic expected shifts by the inversion argument. The experiment should use moderate sizes so it remains educational and inexpensive to run.

import random
def inversion_count(a):
    return sum(a[i] > a[j] for i in range(len(a)) for j in range(i+1, len(a)))

def insertion_sort_counts(values):
    a = list(values)
    comparisons = shifts = 0
    for i in range(1, len(a)):
        key, j = a[i], i - 1
        while j >= 0:
            comparisons += 1
            if a[j] <= key:
                break
            a[j+1] = a[j]
            shifts += 1
            j -= 1
        a[j+1] = key
    return a, comparisons, shifts
n = 25
samples = {
    'sorted': list(range(n)),
    'reversed': list(range(n-1, -1, -1)),
    'shuffled': random.Random(7).sample(range(n), n),
}
for label, values in samples.items():
    result, comparisons, shifts = insertion_sort_counts(values)
    assert result == list(range(n))
    assert shifts == inversion_count(values)
    print(label, 'comparisons', comparisons, 'shifts', shifts)
assert insertion_sort_counts(samples['sorted'])[2] == 0
assert insertion_sort_counts(samples['reversed'])[2] == n*(n-1)//2

Sampling Error and Uncertainty in an Empirical Mean

If the goal is to estimate a workload's unknown mean cost from observations, the sample mean is itself a random quantity. Results depend on sample size, sampling design, time windows, and independence assumptions. Samples drawn from a narrow test fixture do not automatically represent all production traffic. High-variance or rare expensive cases can be missed entirely in small samples, making the estimated mean and upper percentiles unstable.

Separate a theoretical expectation from an empirical estimate: E_D[C] is a property of a specified distribution and cost function, whereas a sample average is a statistic computed from observed cases. Report uncertainty or the limits of coverage for the latter. Avoid implying that an unobserved worst case does not exist merely because no test encountered it.

Benchmark statistics inform the distribution model but do not generally prove an asymptotic bound. A combination of formal case reasoning and representative measurements offers more defensible guidance than either alone.

A Step-by-Step Analysis Procedure

  1. Define the contract. State which inputs are admissible, what size means, and what constitutes a valid result.
  2. Select the resource. Count comparisons, shifts, memory, transfers, or a clearly specified time model.
  3. Derive per-input behavior. Identify branches, loops, recursions, and input properties that change work.
  4. Prove a worst-case bound. Upper-bound every admissible execution; identify a matching family of expensive inputs when claiming a tight bound.
  5. Specify the average model. Define a distribution over input classes, or explicitly state that no defensible distribution is available.
  6. Compute the expectation. Use weighted sums, conditioning, indicators, recurrences, or another justified method.
  7. Separate random sources. Distinguish input randomness from internal algorithmic random choices.
  8. Check tails and other resources. Assess whether the mean conceals important peaks, failures, or capacity costs.
  9. Validate empirically. Exercise constructed worst cases and representative samples, recording deviations from theoretical assumptions.
  10. Publish qualifications. Pair every result with its model, scope, and limitation so it can be reused accurately.

This sequence is deliberately general. It is a checklist for defensible analysis, not a promise that every closed-form expectation can be derived or that every realistic workload distribution is easily measured.

Worked Scenario I: A Search Service with Many Misses

A service scans an unsorted 100-element list. Sixty percent of requests succeed, with successful positions uniformly distributed, and forty percent miss. Under the simple one-comparison-per-element model, conditional successful cost is (100+1)/2=50.5, missed cost is 100, and overall expected comparisons are 0.6·50.5+0.4·100=70.3. A worst-case request always takes at most 100 comparisons.

If the hit rate increases to 90% without changing successful-position assumptions, expected work drops to 0.9·50.5+0.1·100=55.45. The worst-case count remains 100. A reduction of misses affects the mean but not the extremum, illustrating why engineering improvements should specify which cost metric they address.

These numbers describe comparisons, not milliseconds. If a lookup compares long strings or interacts with storage, a richer cost model is necessary.

def mixed_linear_search_mean(n, p):
    return p*(n+1)/2 + (1-p)*n
assert abs(mixed_linear_search_mean(100, 0.6) - 70.3) < 1e-12
assert abs(mixed_linear_search_mean(100, 0.9) - 55.45) < 1e-12
print('Expected comparisons for two hit rates verified')

Worked Scenario II: A Nearly Sorted Import Pipeline

A batch import receives records that are usually already in order, but occasionally reversed by a failed upstream transformation. Insertion sort has excellent behavior when inversion count is small; its cost rises with the number of inversions. A team may correctly measure low mean work on ordinary batches but still face a quadratic worst case on reversed batches.

The right performance statement is conditional: for the adjacent-shift method, shifts equal inversion count, and comparisons are bounded by inversion count plus a linear term. If the upstream contract guarantees a tight upper bound on inversions, one can derive a stronger cost bound for admitted inputs. If it does not, the quadratic worst case remains relevant.

The scenario illustrates the difference between a statistical observation about typical imports and a contractual promise about all valid imports. An algorithm can be the preferred choice for small, nearly sorted datasets while still requiring a fallback for large or unpredictable batches.

Worked Scenario III: Randomized Quicksort on Fixed Inputs

Suppose a dataset of distinct keys is sorted before reaching the sorting routine. A first-element pivot strategy has a quadratic comparison worst case on that monotonic input. A uniformly randomized pivot strategy has Θ(n log n) expected comparisons even for that fixed array because randomness changes which rank becomes the pivot at each recursive call.

This improvement is conditional on the pivot randomization model; it does not eliminate the possibility of a quadratic execution. A response-time-sensitive system may favor an introspective fallback that provides a stronger per-execution bound, while a research analysis may focus on the expected comparison count.

The choice depends on whether the primary decision is average throughput, hard worst-case comparison work, space, or robustness to hostile input patterns. Comparing only the leading asymptotic expectation would omit those requirements.

Worked Scenario IV: A Hash Table with Concentrated Keys

A service uses a hash table with separate chaining and holds its load factor approximately constant. Under an idealized uniform-hashing assumption, expected search work is constant as n grows. But a pathological key set that maps into the same bucket can create a chain of length n; a direct per-operation worst-case claim of O(1) would then be false under ordinary chaining.

A credible assessment states the hash function assumptions, whether the hash is randomly selected, whether an adversary can choose keys, how collisions are resolved, and whether capacity is resized. Engineering alternatives may include collision-resistant or randomized choices, bounded-depth fallback structures, or different indexing methods.

The illustrative model is intentionally simplified; it does not imply every real hash table has these exact guarantees or that randomized hashing automatically protects against every security threat.

Worked Scenario V: Deadline-Sensitive Graph Processing

A graph-processing task must finish within a constrained processing budget. Its typical graph may be sparse and easy, while an admissible dense graph can force much more work. If a traversal is measured on adjacency lists, the full-graph work scales with V+E; for a graph with up to V(V−1) directed edges without self-loops, E can be quadratic in V.

For deadline planning, a useful strategy is to enforce explicit graph-size and edge-count limits, select a representation aligned with expected density, and compute a worst-case operation budget for the permitted domain. A workload average may be appropriate for throughput planning, but it cannot by itself ensure a per-job deadline.

The distinction becomes especially important when graph uploads are untrusted or when unusually large components appear during an otherwise ordinary processing run.

Worked Scenario VI: Choosing Between Two Service Algorithms

Suppose algorithm A costs 10 operation units on 99% of requests and 10,000 units on 1%; its mean is 0.99·10+0.01·10,000=109.9 and its maximum is 10,000. Algorithm B always costs 120 units; its mean and maximum are both 120. Under these stipulated models, A has the lower average work, but B offers a far smaller worst-case work budget.

A throughput-oriented offline batch service may prefer A when the occasional large job is manageable. A real-time endpoint with a tight per-request work budget may prefer B, despite the higher mean. If the expensive event's probability rises to 2%, A's mean becomes 0.98·10+0.02·10,000=209.8, reversing the average ranking.

This fabricated scenario demonstrates why the decision criterion and probability assumptions must be published alongside a result. It does not equate operation units with measured response times.

def two_point_mean(fast_cost, slow_cost, probability_slow):
    return (1-probability_slow)*fast_cost + probability_slow*slow_cost
assert abs(two_point_mean(10, 10000, 0.01) - 109.9) < 1e-9
assert abs(two_point_mean(10, 10000, 0.02) - 209.8) < 1e-9
assert 109.9 < 120 < 209.8
print('Service policy comparison verified')

Common Misconceptions and Corrections

“Average case is halfway between best and worst.”Average means a probability-weighted expectation; its value depends on the distribution.
“Big-O means worst case.”Big-O is an upper-bound relation on whichever cost function the analyst defines.
“Expected logarithmic time means every call is logarithmic.”Expectation is not a deterministic bound on each realization.
“Randomized quicksort cannot be quadratic.”Quadratic comparison paths remain possible under unlucky pivot choices.
“Average inputs are uniformly random.”Uniform randomness is a modeling assumption, not a default law of nature.

Proof Checklist: What Makes a Case Claim Defensible?

Before stating a worst-case theorem, verify that every input in the advertised domain is covered, the resource measure matches the code, the upper bound holds along all branches, and any claimed matching lower bound has a valid witness family for arbitrarily large sizes. Confirm that preconditions such as sortedness or key uniqueness are not silently assumed in an unrestricted claim.

Before stating an average-case theorem, verify that the sample space is explicit, probabilities are nonnegative and sum to one, any uniformity or independence assumptions are justified, and the expected value is taken over the correct randomness. Separate expectation for a fixed input from expectation over input distributions. If using a recurrence, show why the recurrence weights match the induced subproblem distribution.

For practical claims, document the gap between theoretical cost and actual timing, whether the model admits adversarial inputs, how rare costs affect peak capacity, and whether current usage traces support the specified distribution. The most useful result is often a short tuple: worst-case guarantee, distribution-conditioned mean, principal risks, and conditions under which each bound applies.

Review Questions with Worked Answers

  1. What is the formal difference between worst-case and average-case cost? Worst case takes the maximum over all valid size-n inputs; average case weights each per-input cost by a specified probability distribution.
  2. Why does a mean not necessarily equal the midpoint of best and worst cost? Intermediate costs and unequal probabilities determine the expectation; extreme values alone provide no distribution weights.
  3. What is the conditional mean for a successful uniform-position search of n elements? (n+1)/2 comparisons, since the target position is equally likely to be any integer from 1 through n.
  4. How many comparisons does a miss require in a simple n-element linear scan? Exactly n under the one-test-per-element model.
  5. What is the average scan cost if 30% of searches succeed uniformly and 70% miss? 0.3(n+1)/2+0.7n=0.85n+0.15 comparisons.
  6. Why can an access-frequency-ordered list lower mean sequential-search work? Swapping adjacent keys whose probabilities are out of decreasing order reduces the probability-weighted comparison cost.
  7. What is the worst-case asymptotic comparison bound for binary search on a sorted array? O(log(n+1)), because each failed probe removes about half the remaining candidates.
  8. Can binary search's best case be one comparison? Yes; a target at the initial midpoint is found immediately.
  9. What input property controls shifts in adjacent-shift insertion sort? The number of inversions; each shift resolves one inversion.
  10. How many inversions are expected in a uniform random permutation of n distinct keys? n(n-1)/4, by summing the probability 1/2 of inversion for each of n(n-1)/2 key pairs.
  11. Why is a balanced quicksort recurrence not automatically an average-case proof? Balanced partitions are a specific favorable partition pattern; the average requires a probability law over pivot ranks or inputs.
  12. What is the worst-case comparison growth of conventional quicksort? Θ(n²) when partitions repeatedly leave n−1 elements on one side.
  13. What expected comparison order does uniform random-pivot quicksort achieve on distinct keys? Θ(n log n) for each fixed input, under the specified pivot model.
  14. Does randomized expected O(n log n) quicksort prevent quadratic runs? No; a sequence of extreme random pivot choices can still be quadratic.
  15. Why is “hash search is O(1)” incomplete? Collision resolution, load factor, hash-function assumptions, probability source, and case definition are missing; chaining can have linear worst-case lookup.
  16. Why is amortized O(1) append different from expected O(1) append? Amortized bounds account for total sequence cost without needing a probability distribution, whereas expectation averages over randomness.
  17. What can Markov's inequality say when E[C]=50 and C≥0? P(C≥500)≤50/500=0.1, though the inequality may be loose.
  18. Why must an analysis of DFS state the graph representation? Adjacency lists and matrices have different neighbor-inspection costs even for the same graph.
  19. Can a sample benchmark prove a mathematical worst-case bound? Generally no; observing finitely many executions does not cover all admissible inputs.
  20. What is the final reporting discipline for a case analysis? State resource measure, input size and domain, distribution or randomness source, bound, implementation assumptions, and limitations; assess means and peaks separately.

Further exercise A: A 40-element scan has hit probability 0.75 and uniform successful positions. Compute expected comparisons. Solution: 0.75·20.5+0.25·40=25.375.

Further exercise B: For an array of eight distinct keys, determine the expected inversions under uniform random ordering. Solution: 8·7/4=14.

Further exercise C: If an operation costs 1 with probability 0.999 and 10,001 with probability 0.001, give its mean and maximum. Solution: mean 0.999+10.001=11; maximum 10,001. The mean alone is inadequate for a ten-unit per-request budget.
