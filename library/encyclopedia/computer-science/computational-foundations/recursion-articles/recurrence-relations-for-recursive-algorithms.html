Definition, Purpose, and Scope

A recurrence relation for an algorithm expresses the amount of computational work on one input in terms of the work performed on smaller inputs. Recursion is a program-design technique; a recurrence is an analytical model. The two are closely connected but not identical: a recurrence records a chosen cost measure and the structure of recursive work, while the actual program also has control flow, data movement, integer arithmetic, memory allocations, and implementation overhead.

For a simple function that makes one call on an input smaller by one and then performs constant additional work, the model is T(n) = T(n − 1) + Θ(1). For an algorithm that divides a problem into two roughly equal parts and merges the two answers in linear work, the usual model is T(n) = 2T(n/2) + Θ(n), with rounding and base cases understood. The point is not merely to write a formula; it is to derive, justify, and solve that formula for a stated input domain and resource measure.

This is specialist article 7 of 15 in the Recursion unit of the MGU Computer Science Encyclopedia. It extends the Recursion overview and the neighboring Algorithm Analysis subject. The present article owns cost-model construction and recurrence solution methods; detailed geometric recursion-tree design, memoization, and the individual searching and traversal algorithms have their own specialist articles.

Central principle: explain why each term appears, specify what is being counted, and defend the asymptotic conclusion. A correct-looking answer obtained by applying the wrong theorem to the wrong equation is not an analysis.

The Anatomy of an Algorithmic Recurrence

Most algorithmic cost recurrences contain three parts: a base-case cost, a collection of costs for recursive subproblems, and nonrecursive work performed in the current invocation. A generic form is T(n) = T(n₁) + ... + T(nₖ) + f(n), in which the subproblem sizes nᵢ depend on the algorithm and f(n) counts work not included in those subcalls. The total cost is then the sum of the costs across the entire finite recursion tree, not simply the cost of the top invocation.

The current-invocation term may represent a comparison, pivot partition, array merge, loop over child nodes, memory copy, or another operation. It should not include recursive work again or silently exclude a substantial input-dependent operation. For instance, copying an array slice can turn what looks like a constant-time reduction into linear extra work per call, changing the resulting recurrence.

The same program can lead to multiple recurrence relations. A comparison-count recurrence and a bit-operation recurrence for large integers need not have the same asymptotic solution. A stack-space relation also combines child work differently from a time relation.

Define the Size Variable and the Input Domain

Before writing T(n), define exactly what n measures. For a list algorithm it might be the number of elements; for an integer algorithm it might be the magnitude of the integer or its bit length; for a tree algorithm it could be the number of nodes, maximum depth, or both. These size measures are not interchangeable. Euclid's algorithm, for instance, reduces integer values, while bit complexity depends on their binary representation.

Some analyses require more than one parameter. Matrix multiplication uses a dimension and an arithmetic model; a two-dimensional recursive algorithm may need T(n, m); graph traversal naturally uses V and E. When a problem's branching depends on the shape of the input, a single size parameter may support only an upper bound, not an exact count.

Specify admissible values: nonnegative integers, positive powers of two in a first simplified derivation, a connected graph, or a sorted array. Simplifying to powers of two is often a legitimate first step, but the final bound should either handle other input sizes or explain why the algorithm itself restricts its domain. Values outside the domain need not satisfy the stated recurrence.

Base Cases Are Part of the Mathematical Model

A recurrence alone does not determine a unique function unless boundary conditions or other constraints are supplied. The rule T(n) = T(n − 1) + 1 produces different exact values for different choices of T(0). Even when boundary costs affect only a constant factor or additive term asymptotically, they are indispensable to a correct finite calculation and to proving termination.

A base case must correspond to the algorithm's actual stopping condition. A recursive binary search may return on an empty interval, even when its size is zero; merge sort may return immediately on zero or one element. If a recurrence is valid only above a threshold n₀, state T(n) = Θ(1) for n ≤ n₀. Omitting the threshold can accidentally produce undefined terms like T(−1).

The base-case cost should be measured in the same units as the rest of the recurrence. Counting comparisons in one branch but elapsed seconds in another is invalid. When using asymptotic base costs, make the nonnegativity and boundedness assumptions appropriate to the proposed theorem. For a fixed finite set of small inputs, constants typically do not alter growth order.

Recurrence Versus Algorithm: Equality and Bounds

A mathematical equality such as T(n) = 2T(n/2) + cn is warranted only if the algorithm truly creates two equal subproblems and performs exactly the modeled local work under the chosen cost metric. Most real-world descriptions instead justify an inequality such as T(n) ≤ 2T(⌈n/2⌉) + cn, or a recurrence whose additive term is expressed as Θ(n). Those forms are useful, but they assert different things.

If a routine may take fewer steps on favorable inputs, the formula for the worst-case cost should maximize over possible valid inputs and should account for which branch shapes are simultaneously attainable. An easy upper bound can be derived from the maximum cost of each child, but combining independently worst-case child costs can be overly pessimistic when the children's worst cases cannot occur together.

For a tight asymptotic result Θ(g(n)), establish both O(g(n)) and Ω(g(n)) under a consistent model. An upper-bound recurrence cannot, on its own, prove the corresponding lower bound. Whenever the symbol Θ appears in a model, it denotes positive upper and lower bounds for sufficiently large relevant inputs, not merely a casual synonym for “about.”

Asymptotic Notation: O, Omega, and Theta

Big-O bounds growth from above, Big-Omega (Ω) bounds it from below, and Big-Theta (Θ) supplies a tight two-sided bound. These statements refer to behavior as the size tends to infinity within the valid input domain. They typically suppress constant multiplicative factors and lower-order terms. They do not mean that a computation takes exactly the same number of steps at every input size.

For example, T(n) = 3n² + 4n + 7 is Θ(n²); it is also O(n³), but the latter is less informative. A recurrence analysis should target an appropriately tight bound where practical. In particular, saying that merge sort is O(n²) is true but misses its characteristic Θ(n log n) time behavior under its standard model.

Logarithm bases do not matter to constant-factor asymptotic classes, because log₂ n and log₁₀ n differ only by a constant factor. Exponents do matter: nlog₂3 and n² are not asymptotically equivalent. We retain explicit log bases when they reveal how many times a subproblem can be divided before reaching a base case.

A Seven-Step Procedure for Constructing a Cost Equation

A reliable derivation can be organized into a repeatable procedure. First, choose the exact resource to count. Second, identify the size variable and allowed inputs. Third, locate the base case and its cost. Fourth, enumerate recursive calls and their argument sizes. Fifth, count work done before, between, and after calls. Sixth, write the recurrence and state any approximation or worst-case assumptions. Seventh, solve and check the result against the call-tree structure or test measurements.

Run through this procedure for merge sort. At size n, the algorithm splits the data into two parts of sizes approximately n/2, recursively sorts both, and merges in Θ(n) comparisons and moves. Its time recurrence is therefore T(n)=T(⌊n/2⌋)+T(⌈n/2⌉)+Θ(n), with constant cost for a list of at most one element.

Do not place the cost of dividing an already indexed range at Θ(n) automatically: creating actual slices may copy memory, whereas passing index boundaries may not. In merge sort the linear merge already dominates the partition bookkeeping, so both typical choices yield the same time class, but the distinction affects memory accounting and can matter in other algorithms.

Linear Recursion: A Decrementing Counter

Consider a function that receives a nonnegative integer and makes one recursive call on n−1 until zero. Assume each invocation does constant work other than the recursive call. The cost model is T(0)=c₀ and T(n)=T(n−1)+c for positive n. Expanding repeatedly gives T(n)=c₀+nc, which is Θ(n).

def count_down(n: int) -> int:
    if n < 0:
        raise ValueError("n must be nonnegative")
    if n == 0:
        return 0
    return 1 + count_down(n - 1)

assert [count_down(i) for i in range(7)] == list(range(7))

Each non-base call adds one unit to the result, but the algorithm's output value is not the justification for its running time. The relevant observation is that the function performs one additional invocation per decrement. If the program instead performed a loop of length n inside each call, the recurrence would change even though the same argument decrement remained.

The maximum number of simultaneously active calls is n+1, so the standard stack-frame model also gives Θ(n) auxiliary stack space. The time and space happen to have the same growth class here, but that coincidence should never be assumed for recursive algorithms generally.

Factorial: A Linear Cost Under Unit Arithmetic

The textbook factorial recurrence for positive n is n! = n × (n−1)!. A corresponding program makes one recursive call on n−1 and multiplies its result by n. Under the simple model in which each multiplication takes constant time, its running-time recurrence is T(n)=T(n−1)+Θ(1), giving Θ(n) arithmetic operations.

def factorial(n: int) -> int:
    if n < 0:
        raise ValueError("n must be nonnegative")
    if n <= 1:
        return 1
    return n * factorial(n - 1)

assert factorial(0) == 1
assert factorial(6) == 720

This example illustrates the difference between an operation count and a bit-level runtime bound. Factorials grow rapidly, so the integers being multiplied are not fixed-width under arbitrary-precision arithmetic. Actual multiplication costs depend on operand length and the selected multiplication algorithm. Consequently, Θ(n) describes the number of multiplication steps in this implementation, not an unconditional claim about total machine time or memory usage for unbounded n.

The distinction is important in scientific and cryptographic software, where values can contain thousands or millions of bits. An honest analysis states its arithmetic cost model before interpreting a symbolic recurrence as a performance guarantee.

When Local Work Grows: Summing a Linear Cost per Call

Suppose a recursive algorithm removes one item at each call but scans the entire current prefix before recursing. The number of local operations decreases from approximately n to n−1 and so on. Its recurrence is T(n)=T(n−1)+Θ(n). Expansion gives Θ(n+(n−1)+...+1); the arithmetic-series formula shows the sum grows as Θ(n²).

def repeated_prefix_work(n: int) -> int:
    if n < 0:
        raise ValueError("n must be nonnegative")
    if n == 0:
        return 0
    work = sum(1 for _ in range(n))
    return work + repeated_prefix_work(n - 1)

assert repeated_prefix_work(5) == 15

Both this program and the countdown program have a chain of n calls. Their time complexities differ because they do different amounts of work in each frame. Measuring recursion depth alone cannot determine total runtime.

A practical optimization may be to carry forward a running count rather than rescan prefixes. That can change a quadratic recurrence to a linear one without removing recursion at all. Conversely, converting the quadratic algorithm mechanically to a loop without eliminating repeated work can leave its time complexity unchanged.

Unrolling a First-Order Recurrence

For T(n)=T(n−1)+f(n), repeatedly substitute the definition of T into itself. After k steps, T(n)=T(n−k)+f(n)+f(n−1)+...+f(n−k+1). Setting k=n yields T(n)=T(0)+Σi=1n f(i), provided the recurrence holds down to zero. The method turns a recursive cost equation into a summation whose growth can be bounded separately.

Useful standard sums include Σ1=n, Σi=n(n+1)/2=Θ(n²), and Σi²=n(n+1)(2n+1)/6=Θ(n³). The growth of Σ log i is Θ(n log n) by integral comparison or bounding a substantial fraction of its terms between constant multiples of log n.

The derivation is valid for nonnegative contributions under the intended cost model. When studying signed algebraic recurrences unrelated to resource costs, cancellation can change conclusions; runtime work itself cannot become negative. Keeping this distinction avoids importing an unjustified summation estimate into a cost analysis.

Binary Search: Halving with Constant Local Work

A correctly implemented binary search compares the query with a middle element of a sorted range, then continues in at most one half. If direct midpoint computation and comparisons are constant-time, its worst-case running time satisfies T(n)=T(⌊n/2⌋)+Θ(1), with the base case for an empty or one-element range. This is fundamentally different from a two-child divide-and-conquer algorithm: the discarded half does no recursive work.

def binary_search(a: list[int], target: int, lo: int = 0, hi: int | None = None) -> int:
    if hi is None:
        hi = len(a)
    if lo >= hi:
        return -1
    mid = lo + (hi - lo) // 2
    if a[mid] == target:
        return mid
    if a[mid] < target:
        return binary_search(a, target, mid + 1, hi)
    return binary_search(a, target, lo, mid)

values = [1, 3, 5, 7, 9, 11]
assert binary_search(values, 7) == 3
assert binary_search(values, 8) == -1
assert binary_search([], 1) == -1

After k unsuccessful reductions, the remaining range has size at most approximately n/2k. Reaching constant size requires k=Θ(log₂n); constant local work per level then gives Θ(log n) worst-case time. A successful search may terminate sooner, so the best-case search time is Θ(1) under this model.

Recursive binary search may use Θ(log n) frames, while the iterative version can use Θ(1) control space. See Recursive Binary Search for interval invariants and edge cases.

Halving with Linear Local Work: A Geometric Sum

Not all divide-by-two recurrences are logarithmic. If each call spends linear time scanning or copying its current input and then recurses on only one half, the model is T(n)=T(⌊n/2⌋)+Θ(n). The successive local costs form a geometric sum: n+n/2+n/4+... ≤ 2n. Since the first call already requires Ω(n) work, the total is Θ(n).

def scan_then_halve(n: int) -> int:
    if n <= 0:
        return 0
    scanned = 0
    for _ in range(n):
        scanned += 1
    return scanned + scan_then_halve(n // 2)

assert scan_then_halve(8) == 15
assert scan_then_halve(9) == 16

For power-of-two input n=8, the local work is 8+4+2+1=15. Doubling the initial size roughly doubles the total work, despite adding another level to the recursion. In binary search, by contrast, the local cost is constant per level, so doubling input size adds roughly one more constant-time step.

The lesson is that recursion depth and per-level cost must be analyzed together. “Halves the input” describes an argument reduction; it is not by itself a time complexity classification.

Recursion Trees: A Visual Accounting Model

A recursion tree expands each invocation into its children, labeling each node with the nonrecursive work done by that invocation. The total time is the sum of node costs over all levels plus the base-case leaves. This is a mathematical accounting device: it is distinct from a runtime call stack, which contains only the invocations currently active during depth-first execution.

For T(n)=aT(n/b)+f(n) on clean powers of b, level i contains ai subproblems, each of size n/bi. Its combined local work is ai f(n/bi). The height is about logbn and the number of leaves is about alogbn = nlogba.

A useful analysis asks where the work is concentrated: near the root, approximately evenly across levels, or near the leaves. These correspond to the familiar branches of the Master Theorem, but the tree method remains valuable when the theorem's simple hypotheses do not fit. For deeper worked recursion-tree examples, see the separate {href('Recursion Trees and Divide and Conquer','recursion-trees-and-divide-and-conquer')} article.

Same Amount of Work at Every Level

Merge sort supplies the classic equal-level-cost pattern. Its recurrence T(n)=2T(n/2)+Θ(n) has one root that merges n elements; two size-n/2 children whose combined merge work is n; four size-n/4 grandchildren whose combined work is again n; and so forth.

There are Θ(log n) levels of roughly linear work, giving Θ(n log n) total work. This result does not mean one individual invocation uses linear time at every depth. It means the aggregate nonrecursive work across an entire depth level stays proportional to the original input size.

Leaf-Dominated Recursion Trees

Consider T(n)=2T(n/2)+Θ(1). Each internal call does only constant local work, but the number of calls doubles on each level. At the bottom there are Θ(n) leaves, and the whole complete binary recursion tree contains Θ(n) nodes. Thus the total work is Θ(n), even though the recursion depth is only Θ(log n).

More generally, when f(n)=Θ(nd) and the expansion factor satisfies a/bd > 1, the aggregate work per depth level grows as the recursion proceeds. Under the standard balanced recurrence assumptions, the leaves eventually dominate, leading to a total governed by nlogba. The comparison is between the total work per level, not just the cost of one node.

The practical consequence is that bounded recursion depth does not guarantee few recursive calls. An algorithm can have a short stack but exponentially many calls relative to depth because branching creates many completed sibling invocations over time.

Root-Dominated Recursion Trees

Now consider T(n)=2T(n/2)+Θ(n²). The root performs Θ(n²) work; each of its two children does Θ((n/2)²), so together the first child level contributes only about half as much. Every successive level contributes another factor of roughly one half. The sum is bounded by n²(1+1/2+1/4+...)=Θ(n²).

This is a root-dominated pattern: most of the work happens before the problem becomes small, and lower levels add only a constant-factor multiple. Under the usual recurrence assumptions the result is Θ(n²), not Θ(n² log n). The latter would incorrectly assume equal aggregate work at all levels.

Understanding this geometry is useful when deciding whether to optimize combine work or reduce the number of subcalls. If the root's quadratic operation dominates, removing a small amount of overhead from the base cases will not change the asymptotic bottleneck.

Merge Sort: Deriving the Recurrence from Program Behavior

Merge sort first divides its input into two portions, sorts the portions recursively, then combines them into sorted order. A simple implementation constructs new lists at each level. A more memory-conscious implementation passes index ranges and uses a reusable auxiliary buffer. Both commonly have linear-time merging and two half-size recursive subproblems, so their conventional time recurrence is T(n)=T(⌊n/2⌋)+T(⌈n/2⌉)+Θ(n).

def merge_sort(values: list[int]) -> list[int]:
    if len(values) <= 1:
        return values[:]
    mid = len(values) // 2
    left = merge_sort(values[:mid])
    right = merge_sort(values[mid:])
    out = []
    i = j = 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:
            out.append(left[i]); i += 1
        else:
            out.append(right[j]); j += 1
    out.extend(left[i:]); out.extend(right[j:])
    return out

assert merge_sort([6, 2, 5, 2, 1, 9]) == [1, 2, 2, 5, 6, 9]

The balanced recursion tree has Θ(log n) levels and Θ(n) aggregate work per level, for Θ(n log n) time. This is robust to the floor-and-ceiling split, provided parts remain approximately balanced. The output copying and temporary lists use additional heap memory that must be analyzed separately from call depth.

The proof of merge sort's correctness is different from the proof of its running time. Correctness relies on recursively sorted halves and a merge invariant; the recurrence models how much work is spent to produce that result.

The Master Theorem: Standard Divide-and-Conquer Form

The Master Theorem solves a broad family of recurrences of the form T(n)=aT(n/b)+f(n), where a ≥ 1 counts equal-size recursive subproblems, b > 1 describes their size reduction, and f(n) measures nonrecursive work. The key benchmark is p=logba. The three classical cases compare f(n) with np.

For the common polynomial form f(n)=Θ(nd): if d < p, leaves dominate and T(n)=Θ(np); if d=p, level costs balance and T(n)=Θ(np log n); if d > p, the root dominates and T(n)=Θ(nd). The full third case additionally requires a suitable regularity condition, which the ordinary polynomial case satisfies.

These are the standard polynomial comparisons, not a license to insert any possible f(n) into a three-row table. The basic theorem has technical assumptions about asymptotic nonnegative costs, constant subproblem counts and size ratios, boundary conditions, and the gap or regularity required by the case. In cases outside its hypotheses, use substitution, recursion trees, or a more general theorem.

Master Theorem Case One: Recursive Leaves Dominate

The first standard case occurs when the nonrecursive cost grows polynomially more slowly than the benchmark: f(n)=O(np−ε) for some constant ε > 0, where p=logba. Under the theorem's assumptions, the result is T(n)=Θ(np). The positive ε matters: an arbitrarily small logarithmic gap does not automatically qualify as a polynomial gap.

Example: T(n)=4T(n/2)+Θ(n). Here a=4, b=2, and p=log₂4=2. The Θ(n) local work is polynomially below n²; the solution is Θ(n²). The recursion tree's number of leaves is on the order of n², dominating the total.

A common error is to see that the input is halved and immediately conclude logarithmic time. Four half-size calls generate vastly more work than one half-size call. The branch count a and size reduction b must be read together.

Master Theorem Case Two: Balanced Work Across Levels

In the classical balanced case, f(n)=Θ(np), where p=logba. Every recursion-tree level contributes roughly the same total nonrecursive work, so summing over Θ(log n) levels gives T(n)=Θ(np log n).

For T(n)=2T(n/2)+Θ(n), we have p=1 and f(n)=Θ(n), hence Θ(n log n). For T(n)=9T(n/3)+Θ(n²), p=2, again matching the local-work exponent, so the answer is Θ(n² log n). The balanced pattern extends beyond merge sort.

Some extended versions of the Master Theorem include local work Θ(np logk n) and yield Θ(np logk+1 n) under suitable restrictions such as k ≥ 0. If a source states only the elementary three-case theorem, do not use this extension without naming its additional assumptions.

Master Theorem Case Three: Current-Call Work Dominates

The third standard case applies when f(n)=Ω(np+ε) for some positive ε and when the regularity condition holds, commonly written a f(n/b) ≤ c f(n) for some constant c < 1 and sufficiently large n. Under those assumptions T(n)=Θ(f(n)): the root's work dominates the accumulated subproblem work.

For example, T(n)=2T(n/2)+Θ(n²) has p=1 and quadratic local work. The level work halves as depth increases, so T(n)=Θ(n²). Another example is T(n)=3T(n/3)+Θ(n²), for which the child-to-parent local-work ratio is 3/9=1/3 in the clean polynomial model.

Remember that a polynomial size gap is not the only requirement. Contrived, highly irregular nonrecursive cost functions may violate the regularity condition even when they eventually dominate np+ε. In a proof, either verify the condition or use a recurrence method whose assumptions you can establish directly.

Where the Standard Master Theorem Does Not Apply

Several important recurrence families fall outside the equal-fraction template. T(n)=T(n−1)+n subtracts a constant instead of dividing by a constant factor; T(n)=T(n/2)+T(n/3)+n makes unequal-size subcalls; T(n)=T(n−1)+T(n−2)+1 combines overlapping subproblems of sizes just below n; and quicksort can have split sizes depending on the pivot outcome rather than fixed equal parts.

Other recurrences match the algebraic template but not one of the elementary theorem's three clean growth comparisons. For example, 2T(n/2)+n/log n has nonrecursive work just below the benchmark n, but not by a polynomial factor. Labeling it Master case one would be incorrect. Similarly, 2T(n/2)+n log n does not fit the elementary case-two hypothesis f(n)=Θ(n), although an extended logarithmic version or direct summation can solve it.

Choose the tool to fit the recurrence: expansion for decrementing arguments; recursion-tree levels for divide-and-conquer; induction for exact bounds; expectation for randomized branching; and specialized theorems where genuine unequal fractions or more complex functions require them.

An Illustrative Logarithmic Borderline

Consider T(n)=2T(n/2)+n/log₂n for powers of two n ≥ 2, with constant work at the base. At depth i the combined local work is approximately n/(log₂n−i). Reindexing from the bottom, the total nonrecursive work is n Σj=1log₂n (1/j), which is Θ(n log log n), plus Θ(n) leaf work.

The point is not to memorize another formula; it is to see why a standard three-case comparison can miss important intermediate growth. The numerator n is close to the benchmark, yet the denominator changes along the recursion levels, producing a harmonic sum rather than constant aggregate work per level.

This derivation requires the local-work expression to be defined away from log 1=0. Set a small-input base threshold and apply the formula only above it. Boundary definitions and summation limits are not decorative formalities: they determine whether the written recurrence is even mathematically well formed.

Karatsuba Multiplication: Three Half-Size Subproblems

The classical divide-and-conquer multiplication of two long integers splits the operands into halves, computes four products, and combines them. Karatsuba's method reduces the number of size-half multiplications to three by using algebraic identities and performing linear-time additions and subtractions. In a simplified bit-operation model this produces T(n)=3T(⌈n/2⌉)+Θ(n) for operand length n.

The Master benchmark is p=log₂3≈1.585, which exceeds the local-work exponent one. Thus the leaf-dominated case gives Θ(nlog₂3) bit-operation complexity in the standard model. This asymptotic improvement over quadratic long multiplication comes from reducing the branching factor, not making the merge or subtraction stage constant-time.

The model assumes suitable handling of signs, carries, and roughly equal operand lengths, and an implementation's real crossover point depends on constants and memory behavior. For small integers, ordinary multiplication may be faster. This example shows why recurrence reasoning can inform algorithm design: changing four multiplications to three changes the exponent of the dominant cost.

Strassen Matrix Multiplication and Its Arithmetic Model

Traditional block matrix multiplication divides each matrix into quadrants and performs eight multiplications of half-size blocks. Strassen's method reorganizes the algebra to use seven half-size multiplications plus Θ(n²) arithmetic work for additions and subtractions. Under the standard count of scalar arithmetic operations, the recurrence is T(n)=7T(n/2)+Θ(n²).

Here p=log₂7≈2.807, larger than the local-work exponent two, so T(n)=Θ(nlog₂7). This is asymptotically better than the cubic arithmetic-operation count of the straightforward algorithm. It is not an assertion about practical speed for all matrix sizes, and it does not include numerical-stability concerns or every aspect of memory movement.

The lesson parallels Karatsuba: fewer large recursive subproblems can outweigh extra combining work. A recurrence captures that structural advantage, while an end-to-end engineering decision must still consider hardware, data layout, finite-precision behavior, and implementation constants.

Exponentiation by Squaring: One Halved Subproblem

Exponentiation by squaring computes integer powers by repeatedly halving the nonnegative exponent. A recursive implementation computes the power of a half exponent once and reuses it, multiplying by the base only when the exponent is odd. Under constant-cost multiplication, the recurrence is T(n)=T(⌊n/2⌋)+Θ(1), and therefore uses Θ(log n) multiplications for positive exponent n.

def power_by_squaring(base: int, exponent: int) -> int:
    if exponent < 0:
        raise ValueError("exponent must be nonnegative")
    if exponent == 0:
        return 1
    half = power_by_squaring(base, exponent // 2)
    square = half * half
    return square if exponent % 2 == 0 else square * base

assert power_by_squaring(3, 0) == 1
assert power_by_squaring(3, 9) == 3**9
assert power_by_squaring(2, 20) == 2**20

In contrast, a naive function that computes the half power twice, rather than storing it, can satisfy a recurrence like T(n)=2T(n/2)+Θ(1), raising the operation count to Θ(n). A minor-looking source-level difference creates an entirely different recursion tree.

For growing integer values, each multiplication's bit cost also grows, so the logarithmic count is not an unconditional bit-time complexity bound. Separate the number of multiplications from their cost, just as in factorial analysis.

Quicksort: One Algorithm, Several Cost Recurrences

Quicksort partitions an array around a pivot, then sorts the elements on both sides. If the partition step costs Θ(n), the general cost recurrence is T(n)=T(k)+T(n−k−1)+Θ(n), where k is the number of elements placed on one side. The value of k depends on input order and the pivot strategy, so a fixed half-and-half recurrence is not a valid universal model.

In balanced partitions, the model resembles 2T(n/2)+Θ(n), giving Θ(n log n). In a consistently extreme split, one child has zero elements and the other has n−1, giving T(n)=T(n−1)+Θ(n)=Θ(n²). These two cases explain why pivot selection matters.

A three-way partition scheme treats duplicate keys differently from a simple two-way scheme. Performance claims must identify the partition rule and input assumptions. It is also important to distinguish an upper bound on worst-case time from the expected cost of random pivot choices or average cost over a specified distribution of inputs.

Expected-Time Recurrences for Randomized Quicksort

When the pivot is chosen uniformly at random among positions and all keys are distinct, each final pivot rank is equally likely. Let E[T(n)] be the expected runtime over the algorithm's random choices for a fixed size n. A customary expected recurrence has the form E[T(n)] = (1/n) Σk=0n−1 (E[T(k)]+E[T(n−k−1)]) + Θ(n), with consistent base cases. By symmetry, the child sum can be written as (2/n) Σk=0n−1E[T(k)].

The expected comparison count is Θ(n log n) under this model, despite the existence of Θ(n²) worst-case execution paths. Expected time and worst-case time answer different questions; a probabilistic bound must specify what is random and what remains fixed. Randomized quicksort can still encounter a bad sequence of pivot choices, but those paths are unlikely enough not to dominate the expectation.

Simply substituting an “average split of half” into the deterministic balanced recurrence does not constitute a proof of the expected bound. The actual recurrence averages cost over all pivot ranks; the analysis requires appropriate linearity-of-expectation or comparison-probability reasoning.

Naive Fibonacci: Exponential Call-Tree Growth

The mathematical Fibonacci recurrence F(n)=F(n−1)+F(n−2) does not by itself require an exponential-time program. The exponential behavior comes from the naive recursive implementation that recomputes both child values without storing previous results. Its call count follows C(n)=C(n−1)+C(n−2)+1 for n≥2, with C(0)=C(1)=1.

def fibonacci_naive(n: int) -> int:
    if n < 0:
        raise ValueError("n must be nonnegative")
    if n <= 1:
        return n
    return fibonacci_naive(n - 1) + fibonacci_naive(n - 2)

assert [fibonacci_naive(i) for i in range(9)] == [0, 1, 1, 2, 3, 5, 8, 13, 21]

The solution has C(n)=2F(n+1)−1 for n≥1, using the same conventional Fibonacci indexing. Consequently, the number of calls grows as Θ(φn), where φ≈1.618. That is exponential in the numeric argument. Its deepest call chain is only Θ(n), showing again that total calls and maximum simultaneous calls are different resource measures.

In the usual unit-cost integer-arithmetic model, the naive running time follows the same exponential class. If the size measure is the bit length of an integer argument instead, the relationship between numerical n and input length must be stated explicitly.

Memoization Changes the Dependency Model

Naive Fibonacci revisits the same integer arguments repeatedly. With memoization, each distinct subproblem value is computed once and saved. A top-down computation of F(n) then has only n+1 possible states 0,1,...,n; under unit-cost arithmetic and constant-cost cache access it requires Θ(n) work to compute all needed states.

from functools import lru_cache

@lru_cache(maxsize=None)
def fibonacci_memoized(n: int) -> int:
    if n < 0:
        raise ValueError("n must be nonnegative")
    if n <= 1:
        return n
    return fibonacci_memoized(n - 1) + fibonacci_memoized(n - 2)

assert fibonacci_memoized(35) == 9227465
assert fibonacci_memoized.cache_info().misses == 36

The original exponential recursion tree is no longer a faithful count of executed subproblems. The memoized computation is better described by a directed dependency graph whose nodes are distinct argument states. Caching changes the work model from “sum of both recursive branches each time” to “cost per distinct state plus dependency and lookup costs.”

The cache consumes additional space proportional to the number of stored states, and the recursive execution still uses a call chain of linear depth in this implementation. For higher performance or stack safety, bottom-up iteration or logarithmic-time fast-doubling methods may be preferable. See Memoization and Top-Down Dynamic Programming.

Unequal Fractional Subproblems

Some algorithms make recursive calls on different fractions of the input. Consider T(n)=T(⌊n/2⌋)+T(⌊n/3⌋)+Θ(n). It cannot be written as aT(n/b)+f(n) with a single common b and constant a without changing the underlying subproblem sizes. Treating the two children as though each had size n/2 yields a potentially useful upper bound, but that bound need not be tight.

For this particular recurrence, a direct geometric upper bound is possible. The sum of child sizes is at most approximately (1/2+1/3)n=5n/6. At each depth, the aggregate size of all subproblems can therefore decrease geometrically, so the sum of linear local-work terms over all levels is O(n). The root contributes Ω(n); hence T(n)=Θ(n) under ordinary positive-cost assumptions.

This illustration matters because specialized general theorems are not always necessary. First inspect the sum of subproblem sizes, possible overlap, and per-level aggregate work. Simpler bounds often resolve the concrete recurrence transparently.

Akra–Bazzi: A More General Divide-and-Conquer Framework

The Akra–Bazzi theorem extends divide-and-conquer analysis to an important class of recurrences with unequal constant fractional subproblem sizes. A simplified form considers T(x)=Σ aᵢT(bᵢx)+g(x), with positive constants aᵢ, fractions 0<bᵢ<1, and regularity assumptions. It defines p by Σ aᵢ bᵢp = 1, then expresses the growth using xp(1+∫₁ˣ g(u)/up+1 du), within its technical hypotheses.

For T(n)=T(n/2)+T(n/3)+Θ(n), the critical exponent solves (1/2)p+(1/3)p=1, and it lies strictly between zero and one. Because linear current-call work exceeds the np benchmark, the integral term yields overall Θ(n), matching the simpler recursion-tree argument above.

This overview is not a full statement of every Akra–Bazzi side condition, including allowed perturbations and smoothness constraints. The specialized result should be cited and its assumptions checked in a formal proof. It is included here to identify the boundary of the elementary Master Theorem rather than to replace a complete theorem treatment.

Substitution: Guess a Bound and Prove It

The substitution method begins with a plausible asymptotic solution—often inferred from a recursion tree—and proves it inductively. To establish T(n)=O(n log n) for T(n)=2T(n/2)+cn on powers of two, propose T(n)≤C n log₂n for sufficiently large n, adjusting the induction base and lower-order terms as necessary.

Assuming the bound for n/2, obtain T(n)≤2C(n/2)log₂(n/2)+cn = Cnlog₂n − Cn + cn. Choosing C≥c makes the right side at most Cnlog₂n. A separate lower-bound argument, from nonnegative contributions of Θ(n) at every level, proves Ω(n log n); together they give Θ(n log n).

Be careful at n=1, where n log n=0 and a positive base cost cannot satisfy a raw upper bound of the form Cn log n. Begin the induction above a fixed threshold or use a slightly more robust bound such as Cn log₂n+Dn with justified constants. This small technical detail is essential to a valid proof.

Proving Upper Bounds and Lower Bounds Separately

To prove Θ(g(n)), demonstrate both T(n)=O(g(n)) and T(n)=Ω(g(n)). An induction upper bound can take the form T(n)≤Cg(n) for all n≥n₀. A lower bound might be established by counting a compulsory amount of work at the root, at every level, or at the leaves. The two directions may require different arguments.

For T(n)=T(n/2)+cn, the root already incurs cn work, giving an Ω(n) lower bound. An upper bound follows from cn+cn/2+cn/4+... ≤2cn. The result is Θ(n). For merge sort, by contrast, root work supplies only Ω(n); a stronger lower bound needs the repeated linear work across multiple recursion levels, or a standard comparison-sorting lower bound under the appropriate comparison model.

Do not infer Θ merely because one guessed big-O bound matches a familiar textbook answer. The derivation should state what prevents asymptotically less work for the cases or cost class under consideration.

Floor, Ceiling, and Non-Power-of-Two Inputs

Textbook solutions often write T(n)=2T(n/2)+n and momentarily assume n is a power of two. Real algorithms handle odd lengths with ⌊n/2⌋ and ⌈n/2⌉. For a balanced split, the meaningful exact relation is frequently T(n)=T(⌊n/2⌋)+T(⌈n/2⌉)+Θ(n). Its solution remains Θ(n log n) under standard positive-cost assumptions.

Rounding cannot always be discarded harmlessly. If an alleged recursive argument is ⌈n/2⌉ and the base case is only n=0, then n=1 maps to itself. That definition does not terminate. Appropriate base thresholds must be checked before invoking asymptotic theorems.

When translating between the clean mathematical recurrence and real code, verify that both child sizes are strictly smaller for all recursive inputs, that their sum corresponds to the size of the actual partition, and that handling the uneven element costs no more than the modeled local work. These conditions make rounding-based simplification credible.

Input-Dependent Recurrences and Tree Shapes

Balanced and skewed trees can make the same recursive function behave differently even at the same node count. Computing the height of a binary tree makes one call on each child and performs constant local work per node, so total time is Θ(n) for a tree with n nodes. The maximum call depth, however, is Θ(log n) on a balanced tree and Θ(n) on a chain-shaped tree.

If a tree algorithm performs more expensive work at each node—for example, rescanning the entire subtree to recompute its size—then tree shape can affect total time as well. A chain may give T(n)=T(n−1)+Θ(n)=Θ(n²), while balanced branching may give T(n)=2T(n/2)+Θ(n)=Θ(n log n). The algorithm's operation count depends on how local work and child sizes interact.

Do not model every tree algorithm as 2T(n/2). Arbitrary tree children need not be the same size, and some nodes have only one child. A general relation such as T(n)=T(n_L)+T(n_R)+f(n), with n_L+n_R=n−1, better reflects the actual structure.

More Than One Size Parameter and Data-Dependent Work

Some recursive algorithms have two or more changing dimensions. A procedure that reduces either the number of rows or the number of columns may require T(n,m), while a recursive graph procedure may be better bounded as O(V+E) rather than shoehorned into a one-variable recurrence. The relevant work can depend on the number of edges examined, the number of visited states, or an additional numeric range.

A precise model also accounts for data-dependent nonrecursive work. Partitioning an array is usually linear in the current subarray length; comparing two long strings may not be constant time; inserting a value into a balanced search structure may have logarithmic cost. Replacing such operations with Θ(1) without a valid model can understate the true complexity.

Before simplifying, identify whether a cost counts source-level statements, array-element operations, comparisons, arithmetic on machine words, or bit operations. When the input contains objects of varying size, the number of objects alone may be insufficient for a tight time bound.

Recurrences with a Nonconstant Number of Subcalls

The standard Master form assumes a fixed number a of recursive calls per invocation. Some algorithms create a number of children that itself depends on n. A deliberately extreme example might create n calls, each on size n−1, giving T(n)=nT(n−1)+Θ(n). The resulting growth is far beyond the familiar balanced fixed-branching cases.

More realistic backtracking algorithms may branch two ways at each decision for n decisions, leading to a worst-case search tree of Θ(2n) nodes. A permutation enumerator can produce n! leaves. The cost of explicitly writing all outputs establishes a corresponding lower bound, regardless of whether a clever representation reduces intermediate bookkeeping.

For these algorithms, count the search states, branch factor by depth, and pruning rules rather than attempt to force a fixed aT(n/b) formula. The shape of the search space matters more than the mere fact that recursion appears in the implementation.

Depth Is Not the Same as Total Number of Calls

Three separate measures should be tracked: the total number of invocation events, the maximum number of invocations simultaneously active, and the amount of work performed in each invocation. A linear countdown has linear total calls and linear maximum depth. Balanced binary recursion may have linear or larger total calls but only logarithmic maximum depth. Naive Fibonacci can have exponentially many total calls with linear maximum depth.

For the balanced recurrence T(n)=2T(n/2)+Θ(1), a sequential depth-first implementation can execute Θ(n) calls while its call stack has only Θ(log n) frames. A naive conclusion that Θ(n) calls imply Θ(n) stack space would be incorrect.

On the other hand, returning a large constructed object, preserving child outputs, or allocating temporary arrays can increase auxiliary heap space beyond the call stack. The analyst should report each relevant resource explicitly and avoid using “recursive space” as an ambiguous catchall.

A Separate Recurrence for Sequential Stack Space

For sequential recursion, only one child chain is active at a time. If each frame retains constant additional state and child results are released as needed, a useful maximum-stack-space model is S(n)=max(S(n₁),...,S(nₖ))+Θ(1) for the current frame, not S(n)=S(n₁)+...+S(nₖ)+Θ(1). The maximum represents the deepest active path.

For merge sort's balanced call structure, this yields S(n)=S(⌈n/2⌉)+Θ(1)=Θ(log n) frames. For a single chain n→n−1→...→0, it yields Θ(n) frames. A recursive depth-first traversal can have Θ(h) call-stack space where h is tree height, even when its total node-visitation time is Θ(n).

The formula assumes child calls are evaluated sequentially and that pending state per frame is bounded. If each frame retains an Θ(n)-sized copy of its current data, replace the constant by the appropriate allocation and account for retained objects. This is why a cost model needs to identify the resource, not just the recursive call graph.

Auxiliary Heap Space, Retained Results, and Allocations

Space analysis must distinguish auxiliary space from total memory including inputs and outputs. A merge-sort implementation that allocates new arrays can retain several partial lists and an output buffer while recursive frames are active. Even though the call-stack depth is Θ(log n), auxiliary heap requirements are usually Θ(n) for standard merge sort implementations and can vary with the copying strategy.

The equation for peak live memory differs from an equation for cumulative bytes allocated over the entire run. The latter may sum allocations across recursive calls; peak live memory counts objects that remain simultaneously reachable. A procedure may allocate Θ(n log n) total bytes over its execution but require only Θ(n) additional live heap memory at any one time.

When a recursive function returns a newly constructed list for every subtree, partial results can coexist in parent frames. To analyze that situation, track which child objects remain live while the next child is processed, whether old buffers can be released, and whether a cache keeps prior values indefinitely.

Parallel Recursion Changes the Resource Model

If recursive children run concurrently instead of sequentially, maximum stack and heap memory can include multiple active branches at once. For example, a parallel merge sort might launch both half-size sorts simultaneously, using separate execution stacks and buffers. The sequential stack recurrence based on a maximum over child depths would no longer describe aggregate memory across concurrent tasks.

Parallel algorithm analysis often distinguishes work, the total operation count across all processors, from span or critical-path length, the longest chain of dependent operations. For independent parallel children, a span recurrence often uses a maximum over child spans plus the nonparallel overhead, whereas a work recurrence sums both child works. A sequential merge step of Θ(n) can still dominate span even if the two recursive sorts run in parallel.

It is therefore possible for one recursive algorithm to have a total-work recurrence of 2T(n/2)+Θ(n) while its idealized span follows a very different equation. Claims about parallel speedup require a scheduling model, processor availability, communication overhead, and a precise statement of which parts can execute concurrently.

Arithmetic Cost and Bit Complexity

Algorithm textbooks often count integer arithmetic as constant time. This is a useful unit-cost abstraction when operands fit a fixed machine-word size, but it becomes incomplete for unbounded integers. Computing factorial, powers, and Fibonacci values can involve numbers whose bit lengths grow with n. Multiplication and addition on those numbers take more than constant time in bit-level models.

For the naive Fibonacci function, the recurrence counts the number of call events and arithmetic additions. Its exponential branching remains real, but the exact bit-operation cost also depends on the sizes of the Fibonacci values involved. For efficient fast-doubling Fibonacci, the recursion depth is logarithmic in the numeric index, yet large-integer arithmetic dominates precise bit complexity.

Other common hidden costs include comparing variable-length strings, slicing arrays, hashing composite keys, allocating list nodes, and serializing nested objects. A trustworthy recurrence explicitly includes such work or states a well-defined abstraction in which that work is counted as constant.

Measure Call Counts Without Confusing Them with Time

Instrumentation is useful for confirming a recurrence's shape. A simple call counter can reveal exponential branching in naive Fibonacci and logarithmic depth in binary search. However, a call count alone does not determine runtime when different calls perform different amounts of work.

def fibonacci_call_count(n: int) -> int:
    if n < 0:
        raise ValueError("n must be nonnegative")
    calls = 0
    def fib(k: int) -> int:
        nonlocal calls
        calls += 1
        if k <= 1:
            return k
        return fib(k - 1) + fib(k - 2)
    fib(n)
    return calls

assert [fibonacci_call_count(i) for i in range(6)] == [1, 1, 3, 5, 9, 15]

For this implementation, call counts can be compared with the recurrence C(n)=C(n−1)+C(n−2)+1. If a program copies large arrays or performs expensive comparisons, each invocation can consume very different time even though it counts as one call. Measure the relevant local operations or elapsed time independently.

Instrumentation itself incurs overhead and can change memory usage, cache behavior, and interpreter optimization opportunities. It is best used to verify a mathematical structural hypothesis, not to replace mathematical proof.

Numerical Experiments and Scaling Tests

A practical recurrence analysis can be tested against small, controlled measurements. For input sizes n, 2n, and 4n, compare counts of relevant primitive operations. A linear algorithm tends to have a factor near two when size doubles; a quadratic algorithm tends toward four; and an n log n algorithm grows by somewhat more than two. These ratios are heuristic diagnostics, not formal complexity proofs.

def recurrence_merge_work(n: int) -> int:
    if n <= 1:
        return 1
    left = n // 2
    right = n - left
    return recurrence_merge_work(left) + recurrence_merge_work(right) + n

values = {n: recurrence_merge_work(n) for n in (8, 16, 32, 64)}
assert values == {8: 32, 16: 80, 32: 192, 64: 448}

This constructed function is not a benchmark of merge-sort machine time. It evaluates an intentionally chosen recurrence with a unit base cost and a local cost equal to n. Such controlled counters are valuable for checking recurrence expansions, but wall-clock performance also depends on language, data representation, hardware, and external activity.

Always include sufficient sizes to see beyond startup overhead, and remember that asymptotic behavior can appear only after an implementation-specific crossover. A theoretically better algorithm can lose for small problem instances because of larger constants or setup costs.

Worked Scenario One: Choosing Between Two Recursive Designs

Suppose two proposed algorithms solve the same problem of size n. Design A creates one size-half subproblem and performs Θ(n) local work: TA(n)=TA(n/2)+Θ(n). Design B creates two size-half subproblems and performs constant local work: TB(n)=2TB(n/2)+Θ(1). Both have logarithmic maximum depth, and both have Θ(n) total running time under the stated unit-cost model.

These algorithms do not have the same execution profile. A visits only a logarithmic number of recursive nodes but spends progressively less linear work in those calls; B visits linearly many recursive nodes but spends constant local work per node. A may allocate large temporary buffers, while B may create many tiny frames. Platform overhead and memory behavior can favor one or the other despite their shared asymptotic time class.

Decision: use the recurrence to establish the growth class, then examine memory, locality, operation costs, and implementation complexity before claiming one design is superior.

Worked Scenario Two: An Avoidable Quadratic Scan

A developer writes a recursive function that finds an element in a list by taking the current first element, then constructing and scanning a copy of the remaining list on each call. There is only one recursive call, but copying a remaining slice of length n−1 takes linear time. The recurrence is T(n)=T(n−1)+Θ(n), producing Θ(n²) total time.

If the developer passes an index into the same list rather than creating a new remainder slice, the local work can be constant. The recurrence becomes T(n)=T(n−1)+Θ(1), yielding Θ(n) time. Both versions may still have linear call depth and face the same stack limit in a language without guaranteed tail-call elimination.

Decision: optimize the hidden local operation first, then choose recursion or iteration separately based on stack safety, readability, and runtime constraints. This scenario illustrates why an algorithm's verbal description may omit the operation that actually dominates its cost.

Worked Scenario Three: Memoization Before Optimization

A numerical routine computes a recursive sequence by calling the same parameter values many times. A developer sees a wide call tree and initially attempts to make each call execute a few microseconds faster. The recurrence reveals a larger issue: overlapping subproblems are being recomputed, as in naive Fibonacci with T(n)=T(n−1)+T(n−2)+Θ(1).

Caching results by parameter changes the model from repeated visits to a tree of call instances into a graph of distinct states. If there are only O(n) states and each state can be evaluated with constant local work after its dependencies are available, the unit-cost total falls to O(n), with extra storage. This is an algorithmic improvement far larger than a constant-factor reduction in per-call overhead.

Decision: inspect the dependency structure and count distinct subproblems before undertaking local tuning. Ensure cache keys capture all state that can affect the result, and account for cache growth and stack depth.

Worked Scenario Four: A Balanced Tree with a Hidden Depth Risk

An application uses a recursive tree walk. Each node is visited exactly once and has only constant work, so the time bound is Θ(n) in the number of nodes. Tests on balanced trees of thousands of nodes show little stack use: the maximum depth is logarithmic in n. Deployment later receives a chain-shaped tree of the same node count and encounters a recursion-depth failure.

The total-time recurrence was not wrong. The missing analysis was the shape-dependent stack relation S(h)=S(h−1)+Θ(1)=Θ(h), where h denotes tree height. For the skewed tree, h=Θ(n). Replacing recursive traversal with a bounded explicit worklist can remove dependence on interpreter call-stack depth, although the worklist still consumes memory.

Decision: specify worst admissible shape and analyze time and stack memory as separate measures. Testing only on balanced inputs cannot validate robustness against degenerate structures.

Worked Scenario Five: A Claimed Master-Theorem Shortcut

An analyst sees T(n)=T(n/2)+T(n/3)+n and substitutes a=2, b=2 into the Master Theorem, reporting Θ(n log n). The shortcut is invalid because one recursive child has size n/3, not n/2. The replacement equation does give an upper bound in a suitable monotone model, but it is not the original recurrence.

The correct direct argument observes that child sizes sum to at most roughly 5n/6; aggregate size decreases geometrically across generations, so total linear nonrecursive work is O(n). Root cost gives Ω(n), and the tight result is Θ(n).

Decision: verify a theorem's input form before applying it. When the equation does not match, use a direct recursion-tree bound or an appropriate general theorem rather than forcing a template.

A Comparative Selection Framework

The most useful solution method is not always the most sophisticated. Select an analytical method based on the recurrence's shape, not the prestige of a theorem. A transparent direct expansion is often stronger pedagogically and easier to audit than a one-line reference to a general theorem.

Common Errors and Misconceptions

  • “Any halving algorithm is logarithmic.” False. Two or more halved subcalls and expensive combine work can produce linear, n log n, or polynomial time.
  • “Every recursive algorithm takes exponential time.” False. A single decreasing call may take linear time, and binary search is logarithmic.
  • “The call stack stores all nodes in a recursion tree.” False for sequential recursion. Only currently active calls occupy frames, although cached results and other objects may remain live.
  • “An upper recurrence proves a tight bound.” False. A separate lower-bound argument is required for Θ.
  • “The Master Theorem works whenever a problem is divided.” False. Its chosen version has strict hypotheses about subproblem counts, ratios, and local work.
  • “Quicksort always has the recurrence 2T(n/2)+n.” False. Its split is pivot-dependent; worst and expected analyses differ.
  • “Memoization only makes recursion a little faster.” False. It can change exponential repeated-subproblem work into polynomial work by changing the number of executed states.
  • “Constant-time arithmetic applies to arbitrarily large integers.” False under a bit-level model; it is an explicit abstraction.
  • “A space recurrence is the same as a time recurrence.” False. Sequential peak stack depth follows an active path, while time sums executed calls.
  • “Floor and ceiling never matter.” They often do not change growth order in well-behaved balanced recurrences, but they can affect termination and exact cost.

The recurring remedy is to return to program behavior. Count what the algorithm actually does, use an appropriately defined cost model, then select a mathematical method whose hypotheses hold.

Review Questions and Model Answers

  1. What are the three components of a typical cost recurrence? A base cost, the costs of recursive subproblems, and the nonrecursive work in the current invocation.
  2. Solve T(n)=T(n−1)+3 with constant T(0). Expanding gives T(n)=T(0)+3n=Θ(n).
  3. Solve T(n)=T(n−1)+n. The sum 1+2+...+n gives Θ(n²).
  4. Why is recursive binary search not 2T(n/2)+1? Each comparison selects only one half for recursion; the other half is discarded.
  5. Solve T(n)=4T(n/2)+n under the usual hypotheses. log₂4=2, with linear local work below the benchmark; hence Θ(n²).
  6. Solve T(n)=2T(n/2)+n². Quadratic root work dominates under the regularity condition, giving Θ(n²).
  7. Why is the standard Master Theorem inappropriate for T(n)=T(n−1)+n? The subproblem is reduced by subtraction, not by a fixed multiplicative factor b>1.
  8. What is the difference between naive and memoized Fibonacci time? Naive recursion recomputes overlapping states and makes exponentially many calls; memoization computes each distinct state once, giving linear state count under a unit-cost model.
  9. Can a Θ(n)-time recursive tree walk use Θ(n) stack frames? Yes, if the tree is a chain of height Θ(n); a balanced tree has only logarithmic depth.
  10. How do you establish Θ(n log n) rather than only O(n log n)? Prove a matching lower bound, for example by showing linear total work across a logarithmic number of levels under the specified recurrence.
  11. What assumption underlies Θ(log n) arithmetic-operation complexity for exponentiation by squaring? One halved subcall is made per level and arithmetic operations are treated as constant-time units.
  12. What should an analyst do with T(n)=T(n/2)+T(n/3)+n? Use a direct bound or an unequal-fraction theorem; do not pretend that both children have the same size.

For each solved problem, reconstruct the call pattern before selecting a rule. The ability to justify the equation is more transferable than the ability to memorize a solution table.
