Definition, Purpose, and Scope

Depth-first search (DFS) explores a graph by extending one search path through available edges before returning to explore alternatives. In a recursive implementation, each function activation represents a currently active vertex; the call returns once reachable successors have been handled. DFS is a fundamental graph-traversal method used for reachability, connected components, cycle detection, ordering constraints, and the construction of spanning forests.

A graph differs from an ordinary tree because vertices may have multiple incoming edges, may be encountered repeatedly, and may form cycles. Consequently, recursion alone does not prevent revisiting the same vertex. A visited-state mechanism, or an equivalent carefully defined state discipline, is part of a correct general graph DFS.

This is specialist article 11 in the Recursion unit directory of the MGU Computer Science Encyclopedia. Its focus is the recursive DFS mechanism, graph invariants, applications, and resource implications; Recursive Tree Traversal treats acyclic tree structures, while Backtracking and Recursive Search will study deliberate revisiting of alternative candidate solutions.

Graph Vocabulary and Representation

A graph consists of vertices and edges. In an undirected graph, an edge connects two vertices symmetrically; in a directed graph, an arc from u to v is not automatically accompanied by an arc from v to u. An adjacency list stores each vertex's outgoing neighbors. This representation makes DFS practical because it can examine only those edges relevant to the vertex under consideration.

Names such as “visited,” “discovered,” and “finished” describe algorithmic states, not physical marks on vertices. A search has a chosen root, traversal order, and scope. From one root, directed DFS reaches vertices accessible along outgoing arcs; it does not necessarily reach every vertex in the graph.

A Reusable Directed-Graph Example

Consider the illustrative directed adjacency list below. Starting at A, and exploring neighbors left to right, DFS visits A, B, D, E, C, and F. Vertex G remains unvisited because this particular root has no directed path to it. The graph is deliberately small enough to inspect by hand, and each adjacency-list order is explicit.

Illustrative Python 3 example:

graph = {
    "A": ["B", "C"],
    "B": ["D", "E"],
    "C": ["F"],
    "D": ["A"],
    "E": ["C"],
    "F": [],
    "G": ["F"],
}

The edge D → A forms a directed cycle. The graph also has cross-connections: from E to C and from G to F. This model will support step-by-step traces, a complete DFS forest, and comparisons between discovery order and finishing order.

The Minimal Recursive DFS

The core implementation keeps a set of vertices already discovered. It marks a vertex before exploring neighbors; delaying that mark until after the recursive calls can cause an infinite loop on a directed cycle. A recursive call is made only for a neighbor that has not yet been discovered. An isolated root is still visited once.

Reference implementation and deterministic check:

def dfs(graph, start):
    visited = set()
    order = []
    def visit(u):
        visited.add(u)
        order.append(u)
        for v in graph.get(u, []):
            if v not in visited:
                visit(v)
    visit(start)
    return order

graph = {"A": ["B", "C"], "B": ["D", "E"],
         "C": ["F"], "D": ["A"], "E": ["C"], "F": []}
assert dfs(graph, "A") == ["A", "B", "D", "E", "C", "F"]

For vertices and edges reachable from the root, this algorithm examines every discovered vertex once and inspects every outgoing adjacency entry once. Its sequence is deterministic only when the representation's neighbor iteration order is deterministic. It is not generally the unique DFS ordering of the graph.

Why Early Visited Marking Matters

Marking before descent is the central safety rule for a DFS that explores graph reachability. On the example A → B → D → A, the activation for D sees that A is already discovered and does not invoke it again. If the visited mark were applied only when returning, every newly activated A would see itself as “not yet visited” from D and recurse indefinitely.

A discovered state means that an activation has begun; finished means that it has processed all outgoing adjacency entries. These states are not interchangeable. For basic reachability, one visited set is enough; for directed cycle classification or topological sorting, two or three states reveal additional information.

Step-by-Step Discovery Trace

Take the sample graph and follow adjacency order exactly. Call A, mark A; call B, mark B; call D, mark D; skip D → A because A is marked; return to B; call E, mark E; follow E → C, then C → F. When F returns, C and E return, and finally A considers its next neighbor C, now already discovered.

StepActive operationNew discoveryCall stack (outermost to innermost)
1enter AAA
2A → BBA → B
3B → DDA → B → D
4D → A (skip)—A → B → D
5B → EEA → B → E
6E → CCA → B → E → C
7C → FFA → B → E → C → F
8return to A; C already seen—A

The greatest active-call depth here is five, whereas six vertices were discovered. The total number of recursive invocations need not equal maximum simultaneous recursion depth, a distinction explored further in the Recursion unit's call-stack article.

Discovery Order, Finish Order, and Events

DFS emits two conceptually different events per vertex: entry when the activation begins, and exit when its neighbor-processing loop ends. Entry events form a preorder-like discovery sequence; exit events form a postorder-like completion sequence. There is no single traversal sequence that captures both concepts.

Illustrative Python 3 example:

def dfs_events(graph, start):
    seen, events = set(), []
    def visit(u):
        seen.add(u)
        events.append(("enter", u))
        for v in graph.get(u, []):
            if v not in seen:
                visit(v)
        events.append(("exit", u))
    visit(start)
    return events

assert dfs_events({"A": ["B"], "B": []}, "A") == [
    ("enter", "A"), ("enter", "B"),
    ("exit", "B"), ("exit", "A")
]

Exit order is often useful for dependency ordering, strongly connected component methods, and proofs about descendants of a DFS forest. It must not be mistaken for shortest-path order: DFS makes no claim that the first route it finds uses the fewest edges.

Call Stack, Stack Depth, and Unwinding

Every recursive activation stores enough information to resume its neighbor loop after a descendant returns. Conceptually, the call stack records the current DFS path within the DFS forest. The depth cannot exceed the number of distinct discovered vertices in ordinary DFS with early marking; for a long chain, it can grow linearly in the number of vertices.

A language implementation can impose a stricter recursion-depth or memory limit. In Python, a RecursionError can occur for sufficiently deep graphs. Raising the recursion limit is not a general capacity plan because available native stack memory is finite. Explicit-stack DFS is preferable when input depth is uncontrolled; it also avoids dependence on whether the runtime optimizes function calls.

Termination and Reachability Invariants

Assume a finite graph represented by finite adjacency lists. Every recursive call marks one vertex that was not previously marked. Therefore the number of unvisited reachable vertices decreases with every new call, and no vertex can be entered twice. Loops over each finite adjacency list also end; the entire search terminates.

At return from visit(u), every vertex reachable from u through adjacency paths has been discovered, assuming the adjacency relation remains unchanged during traversal. Proof: each outgoing neighbor is either already discovered and eventually processed by its own activation, or is discovered by a new recursive call that explores its descendants. This reasoning uses the global visited-state invariant, not a mistaken claim that every descendant is necessarily first found within u's call.

Correctness Proof for Reachability

Soundness: the start vertex is reachable from itself by a length-zero path. Every additional vertex is discovered via an outgoing edge from a previously discovered vertex. Induction over discovery events shows that every visited vertex is reachable from the start.

Completeness: suppose a reachable vertex remains unvisited at termination. Consider a path from the start to that vertex, and choose its first unvisited vertex y. Its immediate predecessor x on the path was visited. When x's adjacency list was processed, DFS either already had discovered y or called visit(y); either case contradicts y being unvisited at termination. Hence all reachable vertices have been visited.

The proof requires stable adjacency during execution. It does not imply that the routine has found a shortest path or that a single root covers disconnected components.

Time Complexity with Adjacency Lists

Let V count graph vertices and E count the represented edges or directed arcs. A full DFS forest over all vertices takes O(V + E) time with adjacency lists, assuming average-case constant-time visited-set operations and adjacency iteration. Each vertex is marked once and each adjacency entry examined once. For an undirected graph stored by listing both endpoints, each edge typically appears twice; the constant factor does not alter the bound.

From one root, a more precise expression is O(Vr + Er), where Vr are vertices reachable from the root and Er are outgoing adjacency entries examined for them. A dense adjacency matrix instead scans each possible neighbor per visited vertex, leading to O(V²) time for a complete-graph scan. State the representation when stating complexity.

Auxiliary Space and Graph Storage

With the input adjacency structure excluded, a visited set and optional parent or timestamp arrays use O(V) memory. The recursive call stack reaches depth O(V) in the worst case. Thus DFS generally requires O(V) auxiliary space for whole-graph search; it does not require O(E) auxiliary memory merely because it scans E edges.

The input adjacency lists themselves occupy O(V + E) storage; this is separate from traversal overhead. If the implementation stores an entire discovery-event log, additional O(V) space is used, while storing one record for each examined edge can require O(E). In a complete binary tree, depth is logarithmic, but arbitrary graph paths can still be long and should not be assumed balanced.

Directed and Undirected Graphs

Direction changes the meaning of reachability and cycle detection. In an undirected graph, visiting one endpoint can reach its neighboring endpoint in either direction, while in a directed graph a path must respect arc directions. The sample graph's G → F does not make G reachable from A, even though F is reachable from A.

For undirected cycle detection, an edge back to the vertex's parent in the DFS tree is expected and does not constitute a cycle. For directed cycle detection, encountering a currently active (gray) vertex indicates a back edge and hence a directed cycle. Do not apply the undirected parent-only rule to arbitrary directed graphs.

Spanning Trees and DFS Parent Pointers

Record the predecessor that first discovered each vertex. Those predecessor relationships form a rooted DFS tree over the reachable vertices; each discovered vertex other than the root gets exactly one parent. The input graph may contain other edges that are not tree edges.

Illustrative Python 3 example:

def dfs_parents(graph, start):
    seen = set()
    parent = {start: None}
    def visit(u):
        seen.add(u)
        for v in graph.get(u, []):
            if v not in seen:
                parent[v] = u
                visit(v)
    visit(start)
    return parent

assert dfs_parents({"A": ["B", "C"], "B": ["C"],
                    "C": []}, "A") == {"A": None, "B": "A", "C": "B"}

The tree reflects the search order, not a shortest-path tree. In the last example, C has a direct edge from A but its DFS parent is B. If shortest paths in an unweighted graph are required, use breadth-first search instead.

Reconstructing a Discovered Route

Once the parent relation is recorded, reconstruct a route by following parent pointers from a target to the search root and reversing the sequence. The route is valid as long as every recorded parent edge remains part of the graph and the target is discovered. It need not be shortest and can change if the adjacency order changes.

Illustrative Python 3 example:

def route_from_parents(parent, target):
    if target not in parent:
        return None
    result = []
    while target is not None:
        result.append(target)
        target = parent[target]
    return list(reversed(result))

parents = {"A": None, "B": "A", "C": "B"}
assert route_from_parents(parents, "C") == ["A", "B", "C"]
assert route_from_parents(parents, "Z") is None

Parent pointers are also useful for debugging unexpected DFS discovery paths and for constructing tree edges in a graph visualization.

DFS Forests Across All Vertices

A single-root DFS reaches only its root's reachable region. To visit all vertices, iterate over every known vertex and invoke DFS when it has not yet been seen. Each new starting point is a root of a DFS forest. In an undirected graph, each root identifies one connected component; in a directed graph, DFS roots do not generally correspond to strongly connected components.

Illustrative Python 3 example:

def dfs_forest(graph):
    seen, roots, order = set(), [], []
    def visit(u):
        seen.add(u)
        order.append(u)
        for v in graph.get(u, []):
            if v not in seen:
                visit(v)
    for u in graph:
        if u not in seen:
            roots.append(u)
            visit(u)
    return roots, order

graph = {"A": ["B"], "B": [], "C": ["D"], "D": []}
assert dfs_forest(graph) == (["A", "C"], ["A", "B", "C", "D"])

For full correctness, the input domain should either contain each vertex as a key or explicitly include destination-only vertices. Production graph representations often normalize this detail when constructing adjacency lists.

Undirected Connected Components

In an undirected graph, two vertices belong to the same connected component precisely when a path connects them. Each DFS from an unseen vertex discovers its entire component. Running DFS repeatedly over unseen vertices partitions the vertex set into disjoint connected groups.

Illustrative Python 3 example:

def undirected_components(graph):
    seen, components = set(), []
    def visit(u, group):
        seen.add(u)
        group.append(u)
        for v in graph.get(u, []):
            if v not in seen:
                visit(v, group)
    for u in graph:
        if u not in seen:
            group = []
            visit(u, group)
            components.append(group)
    return components

graph = {0: [1], 1: [0], 2: [3], 3: [2], 4: []}
assert undirected_components(graph) == [[0, 1], [2, 3], [4]]

This code assumes the representation is symmetric for undirected edges. If it is not, the output represents reachability according to the provided arcs rather than mathematically defined undirected components.

Discovery and Finish Timestamps

Assign a monotonically increasing timestamp whenever a vertex is entered and whenever its activation finishes. The discovery and finishing times describe a nested interval for each vertex. For vertices in one DFS forest, the intervals are either properly nested when one is a DFS ancestor of the other or disjoint when neither is an ancestor.

Illustrative Python 3 example:

def dfs_times(graph):
    seen, discovery, finish = set(), {}, {}
    clock = 0
    def visit(u):
        nonlocal clock
        seen.add(u)
        clock += 1
        discovery[u] = clock
        for v in graph.get(u, []):
            if v not in seen:
                visit(v)
        clock += 1
        finish[u] = clock
    for u in graph:
        if u not in seen:
            visit(u)
    return discovery, finish

d, f = dfs_times({"A": ["B"], "B": []})
assert (d, f) == ({"A": 1, "B": 2}, {"B": 3, "A": 4})

The timestamps reflect the chosen neighbor and root order. The timestamps are logical event counters, not wall-clock durations, and their numeric values cannot be compared across independently executed traversals without context.

The White, Gray, and Black State Model

A convenient directed-DFS state machine assigns white to unseen vertices, gray to vertices whose activations are on the current recursion stack, and black to vertices whose processing has completed. Transitions follow white → gray → black. In a recursive implementation, a gray vertex has not yet returned to its caller.

An arc to white initiates a tree edge; an arc to gray identifies a back edge to an active ancestor. Arcs to black can be forward or cross edges, depending on the DFS ancestry relation. The distinctions matter for graph proofs and diagnostic tooling, and they should not be inferred from a single visited boolean.

Detecting a Directed Cycle

A directed graph has a cycle if and only if a depth-first traversal encounters an arc to a gray vertex during a complete DFS forest. That arc connects the active DFS path back to a vertex already on that path. Reaching a black vertex is not sufficient evidence of a cycle, because it may have been fully explored along a different branch.

Illustrative Python 3 example:

def has_directed_cycle(graph):
    state = {u: 0 for u in graph}  # 0 unseen, 1 active, 2 done
    def visit(u):
        state[u] = 1
        for v in graph.get(u, []):
            if v not in state:
                state[v] = 0
            if state[v] == 1:
                return True
            if state[v] == 0 and visit(v):
                return True
        state[u] = 2
        return False
    for u in list(state):
        if state[u] == 0 and visit(u):
            return True
    return False

assert has_directed_cycle({"A": ["B"], "B": ["A"]})
assert not has_directed_cycle({"A": ["B", "C"], "B": ["C"], "C": []})

This implementation returns whether a cycle exists. Recovering a witness cycle additionally requires tracking the active path or parent pointers, and careful handling of vertices that appear only as neighbor values.

Detecting an Undirected Cycle

In a simple undirected graph, the recursive procedure tracks the parent edge. When exploring u, encountering an already visited neighbor v other than u's DFS parent establishes a cycle. The parent exception is necessary because the reverse representation of the discovery edge is not a cycle.

Illustrative Python 3 example:

def has_undirected_cycle(graph):
    visited = set()
    def visit(u, parent):
        visited.add(u)
        for v in graph.get(u, []):
            if v not in visited:
                if visit(v, u):
                    return True
            elif v != parent:
                return True
        return False
    return any(visit(u, None) for u in graph if u not in visited)

assert has_undirected_cycle({0: [1, 2], 1: [0, 2], 2: [0, 1]})
assert not has_undirected_cycle({0: [1], 1: [0, 2], 2: [1]})

The parent-vertex test assumes a simple undirected graph, without parallel edge identities. In an undirected multigraph, a second parallel edge to the parent forms a length-two cycle under standard multigraph definitions and must be distinguished by edge ID, not merely by the parent vertex.

Topological Ordering of a Directed Acyclic Graph

A topological ordering places each directed edge u → v with u before v. Such an ordering exists if and only if the directed graph is acyclic. One DFS strategy records vertices at finishing time, rejects any edge to a currently active vertex, and reverses the finish list.

Illustrative Python 3 example:

def topological_order(graph):
    state, finished = {}, []
    def visit(u):
        state[u] = 1
        for v in graph.get(u, []):
            if state.get(v, 0) == 1:
                raise ValueError("directed cycle")
            if state.get(v, 0) == 0:
                visit(v)
        state[u] = 2
        finished.append(u)
    for u in graph:
        if state.get(u, 0) == 0:
            visit(u)
    return list(reversed(finished))

graph = {"compile": ["link"], "test": ["deploy"],
         "link": ["deploy"], "deploy": []}
result = topological_order(graph)
position = {u: i for i, u in enumerate(result)}
assert all(position[u] < position[v] for u in graph for v in graph[u])

Different DFS orders can produce different valid topological orders. This algorithm is an example of why both completion events and active-vertex state matter; blindly reversing finish order on a cyclic graph does not yield a valid dependency sequence.

Directed Edge Classification

In directed DFS, tree edges first discover white vertices; back edges point to gray ancestors; forward edges point from an ancestor to a descendant already discovered through a different tree path; and cross edges connect unrelated DFS branches or trees. Edge classification is relative to a specific DFS run, not a fixed intrinsic edge label.

Acyclic directed graphs have no DFS back edges. For an undirected graph with standard DFS and a simple adjacency representation, the non-tree edge encountered during traversal goes to an ancestor; forward/cross distinctions do not transfer unchanged. The discovery/finish interval theorem can aid classification after a DFS, but using colors at traversal time is simpler for most implementations.

Strongly Connected Components and Their Boundary

Two vertices of a directed graph are in the same strongly connected component when each is reachable from the other. A basic DFS forest alone does not identify these groups. Specialized DFS-based algorithms such as Kosaraju–Sharir and Tarjan combine reachability with finishing-time or low-link information to partition the graph correctly.

Kosaraju–Sharir uses two graph traversals and the edge-reversed graph; Tarjan's algorithm tracks discovery indices, low-link values, and a membership stack. Both run in O(V + E) time with adjacency lists. They are noted here as applications of DFS rather than replaced with a partial or potentially misleading proof of the full algorithms.

Low-Link Ideas and Bridge Detection

In undirected graphs, DFS discovery times and low-link quantities help identify bridges and articulation points. A low-link value captures the earliest discovery time reachable from a subtree using DFS-tree edges and an appropriate back edge. If a child's subtree cannot reach an ancestor of its parent through such an edge, the tree edge to that child is a bridge.

These relationships depend on a precise algorithm, correct handling of parent-edge identity, and graph assumptions. For an undirected simple graph, a tree edge (u, v) is a bridge when low[v] is strictly greater than discovery[u]. Articulation-point tests require a separate condition for a DFS root. These are deeper graph-theory specializations, not substitutes for the basic DFS visited-state contract.

Recursive DFS Versus Breadth-First Search

DFS follows a path deeply; breadth-first search (BFS) processes vertices by increasing number of edges from the root in an unweighted graph. Both can perform O(V + E) work with adjacency lists, but their traversal orders and guarantees differ. BFS constructs shortest-edge-count paths from the root; ordinary DFS does not.

DFS is not “better” merely because its code is shorter. Select the traversal that establishes the needed invariant, particularly when shortest paths, resource bounds, or traversal ordering are essential to the application.

Iterative DFS with an Explicit Stack

An iterative DFS substitutes a programmer-managed list of pending vertices for recursive frames. Marking on push avoids duplicate pending entries in this simple version, but it may produce a discovery order different from the recursive algorithm; reversing neighbor insertion can align certain simple traces, yet it is not sufficient to reproduce all recursion-stack event semantics on arbitrary graphs.

Illustrative Python 3 example:

def iterative_dfs(graph, start):
    stack = [start]
    seen = {start}
    order = []
    while stack:
        u = stack.pop()
        order.append(u)
        for v in reversed(graph.get(u, [])):
            if v not in seen:
                seen.add(v)
                stack.append(v)
    return order

assert iterative_dfs({"A": ["B", "C"], "B": [], "C": []}, "A") == ["A", "B", "C"]

The iterative approach still requires O(V) auxiliary space in the worst case but avoids unbounded recursive Python call depth. Its exact worklist behavior and marking policy must be specified before comparing traces.

Frame-Accurate Iterative DFS

For exact entry/exit ordering, an explicit stack must preserve the current adjacency iterator and pending work in each activation. This is the operational equivalent of suspended recursive call frames. Each frame remembers which neighbor to examine next, so the algorithm does not prematurely mark siblings as discovered.

Illustrative Python 3 example:

def frame_dfs_events(graph, start):
    seen = {start}
    events = [("enter", start)]
    stack = [(start, iter(graph.get(start, [])))]
    while stack:
        u, neighbors = stack[-1]
        try:
            v = next(neighbors)
        except StopIteration:
            events.append(("exit", u))
            stack.pop()
            continue
        if v not in seen:
            seen.add(v)
            events.append(("enter", v))
            stack.append((v, iter(graph.get(v, []))))
    return events

sample = {"A": ["B", "C"], "B": ["C"], "C": []}
assert frame_dfs_events(sample, "A") == dfs_events(sample, "A")

In this complete page, dfs_events is defined in the earlier example. This frame simulation makes the equivalence particularly concrete: the stack contains one stateful iterator for each currently active DFS vertex.

Recursive Generators and Streaming Output

A recursive generator can yield vertices on entry, allowing downstream consumers to process the traversal incrementally. The visited set and active call stack still grow according to explored graph structure; using a generator does not automatically make DFS constant-space.

Illustrative Python 3 example:

def dfs_generator(graph, start):
    seen = set()
    def visit(u):
        seen.add(u)
        yield u
        for v in graph.get(u, []):
            if v not in seen:
                yield from visit(v)
    yield from visit(start)

assert list(dfs_generator({1: [2, 3], 2: [], 3: []}, 1)) == [1, 2, 3]

Stopping iteration early leaves some reachable vertices unexplored, which may be desirable for searching for a target but inappropriate for applications requiring a complete component or full DFS timestamps. Generator suspension also holds active stack and iteration state until the generator is resumed or closed.

Early Exit and Target Search

Some tasks need any valid route to a target, not a full traversal. The recursive function can return a Boolean once a desired vertex is reached, propagating success through its callers. A parent map or current-path list then reconstructs the route. The search remains worst-case O(V + E), but early exit may save work on favorable graphs.

Illustrative Python 3 example:

def dfs_find(graph, start, target):
    seen = set()
    def visit(u):
        if u == target:
            return [u]
        seen.add(u)
        for v in graph.get(u, []):
            if v not in seen:
                suffix = visit(v)
                if suffix is not None:
                    return [u] + suffix
        return None
    return visit(start)

assert dfs_find({"A": ["B"], "B": ["C"], "C": []}, "A", "C") == ["A", "B", "C"]
assert dfs_find({"A": ["B"], "B": []}, "A", "X") is None

This compact pedagogical function builds lists while unwinding, potentially copying path prefixes repeatedly; a parent-based variant is usually more economical for long paths. Neither function supplies a minimum-hop guarantee.

Neighbor Ordering and Reproducibility

DFS is sensitive to adjacency order, root-selection order, and when nodes are marked. A set of neighbors may iterate in an order that changes between runs or runtime environments. If reproducible teaching traces or stable outputs are required, normalize neighbor sequences before traversal, or use a representation with explicitly controlled insertion order.

Sorting every adjacency list may require additional work, so the standard O(V + E) DFS bound no longer describes the entire preprocessing pipeline. State whether an output is an arbitrary valid DFS forest or one defined under a specific deterministic ordering rule. Comparisons of timestamps or parent trees are not meaningful unless that rule is held constant.

Recursion Limits and Hostile Inputs

A chain of thousands of graph vertices can exceed a runtime's safe call depth even though the underlying DFS algorithm uses only linear auxiliary memory. Python exposes a recursion-limit setting, but changing it can risk exhausting native stack resources rather than making recursion unbounded. Iterative DFS is usually the safer choice for user-controlled graph depth.

Untrusted graphs also require guardrails on vertex counts, edge counts, memory usage, and processing budgets. Validating input identifiers and adjacency structure prevents missing-key mistakes and accidental changes in graph semantics. A traversal over a graph modified concurrently must specify snapshot or synchronization guarantees; otherwise correctness proofs based on a fixed adjacency relation may fail.

Many DFS errors arise from using a locally plausible recursive call without stating the global visited-state invariant. Every DFS application should first specify what each state means, which vertices count as processed, and what has been proven on return.

Property-Based and Differential Testing

Testing should check structural properties rather than one expected order alone. For a fixed root, the visited set must equal the set of vertices reachable from that root; no vertex should enter twice; every recorded parent must be an actual graph edge; every tree parent must be discovered before its child; and each discovered vertex must eventually receive a finish event for a complete traversal.

Illustrative Python 3 example:

def reachable_by_bfs(graph, start):
    from collections import deque
    seen = {start}
    q = deque([start])
    while q:
        for v in graph.get(q.popleft(), []):
            if v not in seen:
                seen.add(v)
                q.append(v)
    return seen

for graph, start in [({0: [1], 1: [0]}, 0),
                     ({0: [1, 2], 1: [2], 2: []}, 0),
                     ({0: [], 1: [0]}, 1)]:
    assert set(dfs(graph, start)) == reachable_by_bfs(graph, start)

Cross-checking DFS reachability against an independently implemented BFS is valuable because the two approaches have different control structures. For cycle detection, generate small graphs with known acyclic or cyclic structure; for topological ordering, verify every input edge against the returned position map.

Applied Scenario I: Dependency Validation

A collection of build tasks has directed edges from prerequisites to dependent tasks. Before creating an execution order, check whether any directed cycle exists. If a cycle exists, there is no topological ordering satisfying all constraints; the tool should report the dependency problem rather than output an arbitrary reversed DFS list.

For a directed acyclic graph, collect DFS finish order and reverse it to obtain one valid topological sequence. Distinguish graph orientation: if edges instead point from tasks to prerequisites, the meaning of the returned order reverses. Clearly documenting this direction is more important than choosing DFS over Kahn's queue-based algorithm.

Applied Scenario II: Network Reachability and Islands

Imagine a modeled network with vertices representing systems and undirected edges representing permitted connections. DFS from one machine identifies its reachable component. A full DFS forest identifies isolated groups and therefore supplies a first diagnostic view of disconnected network segments.

When access permissions are directional, however, the corresponding directed graph must preserve those directions; “connected component” is no longer an adequate single notion. An outgoing path may exist one way without a return path. For security or availability assessments, the graph model should distinguish physical links, logical policy, and actual routable reachability.

Applied Scenario III: Detecting a Circular Reference

A collection of configuration objects references other objects by identifier. If cycles are invalid for a particular schema, model each reference as a directed arc and use gray-state cycle detection. A back edge to an active object demonstrates a circular dependency; an edge to a completed object is not proof of a cycle.

In this application it can be useful to record the active path, allowing the validator to report a specific cycle rather than only a Boolean. The algorithm must also distinguish absent referenced objects from valid graph vertices. Missing references are a separate data-validation problem and should not be silently treated as cycle detection.

Applied Scenario IV: Exploring a Large Hierarchy with Cross-Links

A document graph may resemble a tree but contain cross-references and repeated links. A straightforward recursive tree walk could process the same document multiple times or loop through cyclic references. Using a discovered set changes the operation into graph DFS, ensuring that each document identifier is entered at most once.

If editorial requirements instead call for processing every distinct *path*, marking each vertex globally may be too aggressive because it suppresses alternative routes. That problem belongs to path enumeration or backtracking, where state and pruning rules differ. The required output contract determines whether global DFS visitation is correct.

Applied Scenario V: Stack-Safe Graph Inspection

An imported chain-shaped graph has 100,000 vertices. Recursive DFS is mathematically valid but likely to breach the call-stack limit of a typical Python process. An explicit-stack traversal handles the same reachability problem using heap-allocated data structures, though total auxiliary space remains O(V) in the worst case.

For a task requiring exact recursive discovery and finishing times, use the iterator-frame simulation rather than assuming a plain LIFO vertex stack reproduces recursive events. Measure memory under actual graph shape and input limits, and avoid changing the interpreter recursion limit as the default remediation.

Review Answers and Reasoning

  1. Marking on entry blocks a cycle edge from launching a second activation of an already active vertex.
  2. A discovered vertex remains gray and has active pending adjacency work; a finished vertex is black and has processed every outgoing entry.
  3. The active path A, B, C has depth three; the C → A arc is skipped under early marking.
  4. A new activation is made only when the vertex is outside the visited set, and entry immediately adds it.
  5. Directed reachability depends on outgoing arcs; disconnected or unreachable vertices require other roots.
  6. O(V + E) with adjacency lists and constant-average-cost visited-set checks; scanned vertices and edges are counted once up to fixed factors.
  7. The undirected graph stores the discovery edge in both directions, so the return arc to the parent is expected.
  8. An arc to an active gray vertex closes a directed cycle; an arc to black does not.
  9. A DAG has no back edge, allowing the finish-order precedence proof; a cycle imposes contradictory edge precedence constraints.
  10. Let A connect to B and T, and B connect to C and C to T; visiting B first yields A–B–C–T rather than A–T.
  11. Marking all pushed siblings before descending can change which branch first discovers a shared target.
  12. It needs each active vertex's current adjacency iterator and a return/exit event.
  13. Tarjan maintains indices, low-link values, and an SCC stack with membership information.
  14. Scanning all possible neighbors in a matrix generally costs O(V²) for a complete traversal.
  15. Enumerating distinct simple paths requires considering a vertex again along different paths, subject to path-specific cycle prevention.
