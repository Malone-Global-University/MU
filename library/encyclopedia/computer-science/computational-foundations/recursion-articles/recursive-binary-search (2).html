Definition, Purpose, and Taxonomic Scope

Recursive binary search is an algorithm for locating a target in a sorted, index-addressable sequence by comparing the target with an element near the middle of a candidate interval and recursively inspecting only the half in which a match may remain. Each nonterminal call reduces the number of candidates by approximately one half. The familiar sorted-array implementation makes at most a logarithmic number of comparisons in the worst case and has logarithmic call depth when written as ordinary recursion.

Its essential ingredients are an ordering assumption, a candidate interval, a comparison at a midpoint, a correct branch decision, and an empty-interval stopping condition. Recursion is the control-flow representation of the reduction; the real reason the algorithm is efficient is the order information that allows it to exclude candidates without visiting them individually.

This specialist article develops the sorted-array algorithm, its invariants and proofs, exact-match and boundary-search variations, duplicates, testing, representation constraints, performance models, and practical engineering choices. It is a Level 5 child of the Recursion specialist directory. General recursive definitions belong to Recursion; the distinction between single-branch and branching work belongs to the companion articles on recurrences and recursion trees.

Where Binary Search Applies

The conventional algorithm applies when a sequence is sorted consistently with the comparison used by the search. For ascending numerical order, if the middle value is below the target, every element at or to its left is also below the target and may be rejected. If the middle value is above the target, the middle value and everything to its right can be rejected. For descending order these branch directions are reversed.

Efficient binary search also requires inexpensive access to the chosen middle element. A Python list, a fixed-size array, and many random-access vectors support this directly. A linked list does not: moving to its midpoint generally requires traversal, which changes the overall complexity. A binary-search-like strategy can also be applied to a monotone predicate over an integer interval, without storing a sorted sequence, provided monotonicity and reliable midpoint evaluation are established.

Do not confuse binary search on an ordered array with a binary search tree. Their names describe different objects. In an array the midpoint is chosen by index; in a search tree the node structure determines the next comparison. A badly shaped search tree can have linear height even when the data values obey a binary-search-tree ordering rule.

The Ordering Contract and Its Consequences

For ascending order with a strict ordering relation, assume a[i] <= a[j] whenever i < j. Comparisons must apply the same interpretation of order that was used to sort the sequence: for example, lexicographic strings, numeric values, case-folded names, or records ordered by a particular key. If the array is sorted by surname but the algorithm compares employee identifiers, its elimination argument is invalid.

When a comparator is nontransitive, changes over time, or treats otherwise distinct elements inconsistently, the search can be incorrect even if the code follows a textbook pseudocode pattern. NaN in floating-point data is a familiar hazard because comparisons such as x < nan, x > nan, and x == nan are all false for ordinary IEEE-754 NaN values. A production ordering policy should specify how such values are handled rather than pretending they behave like normal numbers.

Sortedness is a precondition, not an outcome of the algorithm. Binary search does not sort, repair, or validate the entire array. Verifying sortedness from scratch costs linear time for an arbitrary sequence, so the common O(log n) claim presumes the ordering was established or maintained separately.

Half-Open Search Intervals

We use the half-open interval [lo, hi): candidate indices start at lo and stop just before hi. Initially lo = 0 and hi = len(a). A valid state satisfies 0 <= lo <= hi <= len(a). The number of remaining candidates is exactly hi - lo. An empty interval is identified by lo == hi.

The half-open convention makes the two recursive subintervals particularly transparent. For a midpoint mid, the left side is [lo, mid); the right side is [mid + 1, hi). Neither contains the examined midpoint. There is no need to invent a sentinel such as -1 for an internal index, although the public exact-match interface may use -1 to mean not found.

The Candidate-Preservation Invariant

The central loop-or-recursion invariant is that, if a matching target exists in the original array and a match has not already been returned, at least one matching index remains inside the current candidate interval. Values outside the interval have been excluded through justified comparisons. The algorithm therefore never discards every possible answer unless no answer exists.

Assume the array is ascending. If a[mid] < target, indices from lo through mid have values below the target, so the search may continue at [mid + 1, hi). If a[mid] > target, indices from mid through hi - 1 have values above the target, so it may continue at [lo, mid). If equality holds, the function can return mid.

Notice the purpose of the invariant: it establishes correctness, not merely speed. Halving an arbitrary range would be fast but unreliable. A candidate can be rejected only because the stored order certifies that the rejected region cannot contain a relevant answer.

Midpoints Without Boundary Errors

A common midpoint expression for indices is mid = lo + (hi - lo) // 2. In Python, whose integers are not restricted to a fixed machine-word size for ordinary indexing arithmetic, (lo + hi) // 2 also computes the midpoint without signed-integer overflow. In languages with bounded signed integers, the difference-based expression is generally preferred when 0 <= lo <= hi and the difference fits the index type.

For a nonempty half-open interval [lo, hi), integer division gives lo <= mid < hi. Thus a[mid] is valid under the bounds contract. An interval of length one has mid = lo; if the element is not equal to the target, the next interval has length zero. For length two, the choice is the lower midpoint; both branches still shrink.

Never calculate the midpoint and index into the array before checking that the candidate interval is nonempty. The case lo == hi is a valid finished search, not a malformed state. In fixed-width integer arithmetic, full-domain search over inclusive integer endpoints requires separate care, particularly at minimum and maximum representable values.

The Empty Interval as the Base Case

The base case for exact-match search is lo >= hi, though legal half-open calls should reach lo == hi rather than lo > hi. At that point no candidate indices remain. Reporting absence is correct because every previous removal was justified by the ordering invariant.

It is a mistake to use only lo > hi as the stopping condition while also treating hi as exclusive. For an empty half-open interval [k, k), that condition is false; the algorithm may then index outside the valid candidate set or fail to make progress. Both a correct base case and strict interval reduction are necessary for termination.

An empty input is a useful boundary test: lo = 0 and hi = 0, so the algorithm must return “not found” without making any midpoint comparison. A robust implementation handles this without special-case code outside the standard recursion contract.

Canonical Recursive Exact-Match Implementation

The following Python implementation makes the interval convention explicit. Its public function returns an index at which target occurs, or -1 if absent. It deliberately does not promise a particular index when duplicates exist.

def recursive_binary_search(a, target):
    """Return an index containing target, or -1 if absent.

    Precondition: a is sorted in ascending order.
    """
    def search(lo, hi):
        if lo == hi:                  # Empty half-open range
            return -1

        mid = lo + (hi - lo) // 2
        if a[mid] == target:
            return mid
        if a[mid] < target:
            return search(mid + 1, hi)
        return search(lo, mid)

    return search(0, len(a))

assert recursive_binary_search([], 8) == -1
assert recursive_binary_search([4], 4) == 0
assert recursive_binary_search([4], 7) == -1
assert recursive_binary_search([2, 4, 6, 8, 10], 8) == 3

Each invocation has one local pair of bounds and makes at most one recursive call. The function returns immediately when it finds an exact match. The work of comparing one midpoint is constant under the conventional unit-cost model for fixed-size values and constant-time array indexing. For comparisons involving long strings or arbitrary-precision objects, the cost of one comparison may depend on the values themselves.

Worked Trace I: A Successful Search

Consider the 15-element sorted array [2, 5, 8, 11, 14, 17, 20, 23, 26, 29, 32, 35, 38, 41, 44], seeking 38. The initial interval [0, 15) gives mid = 7 and value 23. Because 23 is smaller than 38, the first eight elements can be excluded. Next [8, 15) yields mid = 11, value 35. Finally [12, 15) yields mid = 13, value 41; the target must be to its left, and [12, 13) yields mid = 12, value 38.

2[8,15)1135Search right

The trace illustrates that binary search does not scan the excluded values. It decides from the comparison and the sortedness guarantee that those values cannot matter. Notice also that a successful search can require several comparisons; the “one midpoint, one comparison” best case occurs only when the first midpoint already matches.

Worked Trace II: An Unsuccessful Search

Search the same array for 36. The first midpoint is 23 at index 7, so the next interval is [8,15). Its midpoint is 35 at index 11, so the next interval is [12,15). That midpoint is 41 at index 13, so the next interval is [12,13). The midpoint there is 38 at index 12, forcing [12,12). The empty interval proves there is no 36 in the array.

Returning “not found” must be distinguished from returning an insertion position. The unsuccessful exact-match algorithm above returns -1; the lower-bound algorithm developed below would return 12, the correct position at which 36 could be inserted while preserving ascending order. Both results can be correct for their respective contracts.

A trace that ends at lo == hi is a mathematical certificate of absence only when the order and comparison contracts held throughout the search. If the sequence had been modified, or if it had never been sorted correctly, the same sequence of calls would not justify the conclusion.

Correctness by a Candidate-Set Argument

A compact correctness proof has three stages. Initialization: at the first call, the entire original array is the candidate interval, so every possible match is included. Preservation: a comparison either identifies a match at the midpoint or eliminates an interval that cannot contain the target, leaving any remaining match inside the chosen recursive range. Termination: a call returns an index only if the value there equals the target; a call reaches the empty interval only after all candidates have been eliminated.

One can state the proof as induction on the interval length m = hi - lo. At m = 0, absence follows immediately. At positive m, the algorithm examines a valid midpoint. If equal, it returns a correct index. If unequal, the ascending-order property justifies replacing the original problem with one strictly smaller subproblem. The inductive hypothesis establishes the result for that subproblem.

This is a partial correctness proof combined with a termination argument. Merely showing that the function eventually returns does not show that its answer is valid; merely showing that each branch preserves the search invariant does not show that it finishes. The two obligations should be treated separately.

Termination by a Decreasing Variant

The nonnegative integer m = hi - lo is a termination measure. A call begins with m > 0 unless it is in the base case. A recursive call into the left side has length mid - lo, which is smaller than m. A recursive call into the right side has length hi - (mid + 1), also smaller than m.

Because a nonnegative integer cannot decrease strictly forever, the algorithm must reach either a matching midpoint or the empty-interval base case. The proof is stronger than a verbal statement that the interval “gets smaller”: it identifies the exact quantity that decreases and rules out a nonterminating two-element cycle.

A flawed inclusive-endpoint implementation can fail this test. If it recurses on [mid, hi] after determining that the target is larger than a[mid], a two-element interval can repeat unchanged when mid == lo. The fix is to exclude the examined midpoint by using mid + 1, or to adopt a different invariant with demonstrable progress.

The Time Recurrence and Its Solution

At a nonterminal call, binary search does a bounded amount of local work—midpoint arithmetic, an element read, and comparisons—then invokes at most one smaller instance. Under constant-time indexing and key comparison, its worst-case recurrence is T(n) = T(⌊n/2⌋) + Θ(1), with a constant base cost T(0) = Θ(1). The exact smaller size depends on which half is chosen, but both are at most roughly half of the original size.

Expanding the recurrence reveals one constant-cost term per recursion level: T(n) = c + T(n/2) = 2c + T(n/4) = …. After k reductions, approximately n/2^k candidates remain. Solving n/2^k ≈ 1 gives k ≈ log₂ n; therefore the worst-case running time for nonempty arrays is Θ(log n).

There is no additive 2T(n/2) term because the algorithm does not search both halves. This distinguishes it from merge sort and from a full traversal of a recursively divided collection. The recurrence also assumes constant-cost comparisons; for variable-length strings one may express the cost more precisely in terms of both search comparisons and character-comparison work.

Best-Case, Worst-Case, and Exact Comparison Counts

If the midpoint equals the target immediately, the search makes one element comparison and returns, so the best-case time for a nonempty input is Θ(1). A difficult successful search or an unsuccessful search may follow the longest possible chain, giving Θ(log n) comparisons. The longest chain remains logarithmic even when the input size is not a power of two.

With the stated half-open midpoint policy and one midpoint inspection per nonempty call, an unsuccessful search of n elements uses at most ⌊log₂ n⌋ + 1 midpoint inspections for n ≥ 1; the exact count depends on the search path. For n = 0 it uses zero. One may equivalently bound a general successful-or-unsuccessful search by ⌈log₂(n + 1)⌉ inspections, which is a conservative bound but not always tight for every n and variant. Different binary-search conventions and count definitions can yield slightly different formulas.

These are midpoint inspections, not necessarily the number of machine-level comparisons. The three-way Python implementation checks equality and, if unequal, an ordering relation; one invocation can therefore perform two comparison operations. Its asymptotic complexity is unchanged, but exact benchmarking or comparator-call budgets must account for the distinction.

Recursive Stack Depth and Auxiliary Space

The standard recursive implementation retains one activation record for each unfinished call on the active path. Because there is only one subcall per level and the candidate count halves, the maximum number of live recursive frames is Θ(log n) for worst-case searches. In contrast, an equivalent iterative algorithm can keep the two bounds and midpoint in a constant number of local variables, giving O(1) auxiliary space.

The array itself is input storage, not auxiliary storage created by the search. Counting it as auxiliary memory would obscure the resource trade-off. A function that slices a new list at each recursive step has a different allocation profile and can incur much greater total work; the canonical version passes only integer bounds and shares the original sequence.

Tail-position syntax does not guarantee that a runtime will reuse a stack frame. Python does not perform general tail-call elimination for ordinary recursive functions. A search of practical in-memory array sizes usually has shallow recursion, but the iterative form remains attractive for predictable stack usage, language portability, and production coding conventions.

Why Sortedness Matters More Than Recursion

The order of the elements—not recursive syntax—makes it legal to discard half of the candidates. A linear scan over an unsorted array cannot reject unseen elements based solely on the value encountered at one index. Replacing an iterative scan with a recursively written scan would not introduce a logarithmic search guarantee.

Similarly, converting the recursive binary-search function into a while loop does not alter the underlying asymptotic number of midpoint inspections. Both forms rely on the same invariant and cut down the same interval. Their differences concern execution representation and engineering trade-offs: stack overhead, simplicity of stepping through recursive calls, integration with functional code, and runtime-specific optimization.

Binary search must also be evaluated as part of an entire workflow. If data must first be sorted, sorting typically costs Θ(n log n) comparisons, and a single subsequent search does not erase that up-front expense. When many queries reuse the sorted collection, the preparation cost may be amortized across them.

Duplicate Values and the Meaning of Found

In an ascending list such as [3, 5, 5, 5, 8, 11], the ordinary exact-match algorithm may return any of the three positions containing 5. That is acceptable when the specification says only “return an index containing the value.” It is not acceptable when a caller needs the first occurrence, the last occurrence, a count of occurrences, or a stable insertion position.

An arbitrary midpoint match does not establish how many equal values exist on either side. Continuing the search left for an earlier occurrence or right for a later occurrence can provide a logarithmic boundary search under the same sorting assumption. The most reusable interfaces are usually lower bound—first element not less than the target—and upper bound—first element greater than the target.

It is helpful to write down the operation requested by a client before implementing search. “Find a key,” “find the first matching record,” and “find the insertion point after the last equal record” are three different contracts even though they share the same divide-the-interval technique.

Lower Bound: The First Element Not Less Than the Target

The lower bound for target x is the smallest index k with a[k] >= x, or len(a) if every element is below x. The answer always exists as an insertion position in the closed range 0..n, even when there is no exact match.

Maintain a half-open search interval [lo, hi) whose left edge is a possible lower-bound answer. If a[mid] < x, then no index at or before mid can be the lower bound; recurse right. Otherwise the first qualifying element is at mid or earlier, so recurse into [lo, mid). When the interval becomes empty, lo is the lower-bound position.

A stronger invariant clarifies this reasoning: all indices strictly below lo contain values less than x, and all indices at or above hi contain values at least x. Neither region contains an unknown crossing point. When lo == hi, these two established regions meet at the unique boundary. This is a correctness argument for an insertion position, not a comparison-for-equality search.

Recursive Lower-Bound Implementation

def recursive_lower_bound(a, x):
    """First index i with a[i] >= x; returns len(a) if none."""
    def search(lo, hi):
        if lo == hi:
            return lo
        mid = lo + (hi - lo) // 2
        if a[mid] < x:
            return search(mid + 1, hi)
        return search(lo, mid)
    return search(0, len(a))

values = [3, 5, 5, 5, 8, 11]
assert recursive_lower_bound(values, 5) == 1
assert recursive_lower_bound(values, 6) == 4
assert recursive_lower_bound(values, 0) == 0
assert recursive_lower_bound(values, 99) == len(values)

The algorithm does not stop when a[mid] == x, because that midpoint may not be the first occurrence. It continues searching left for a possibly earlier qualifying index. The base case returns a boundary, not a Boolean membership result. The leftmost index is meaningful even when the element at that index is greater than x.

To obtain the first exact match from a lower-bound result, let k = recursive_lower_bound(a, x) and then check k < len(a) and a[k] == x. If true, k is the first matching index; otherwise the target is absent. Failing to check the returned position for equality confuses insertion with successful lookup.

Upper Bound: The First Element Greater Than the Target

The upper bound is the smallest index k for which a[k] > x, or n if no value is greater. The key change from lower bound is the branch test: values less than or equal to the target are discarded to the left, not just strictly smaller values.

def recursive_upper_bound(a, x):
    """First index i with a[i] > x; returns len(a) if none."""
    def search(lo, hi):
        if lo == hi:
            return lo
        mid = lo + (hi - lo) // 2
        if a[mid] <= x:
            return search(mid + 1, hi)
        return search(lo, mid)
    return search(0, len(a))

values = [3, 5, 5, 5, 8, 11]
assert recursive_upper_bound(values, 5) == 4
assert recursive_upper_bound(values, 2) == 0
assert recursive_upper_bound(values, 11) == len(values)

For this variant, the boundary invariant is: all indices less than lo contain values <= x, while all indices at or beyond hi contain values > x. With ascending order, each comparison can safely decide which half cannot contain the first greater value.

Equal Ranges, Counts, and Duplicate Records

For a sorted array, the matching indices for a target form a contiguous, possibly empty range [lower_bound(x), upper_bound(x)). The number of matches is therefore upper_bound(x) - lower_bound(x). For [3, 5, 5, 5, 8, 11] and target 5, that range is [1,4), containing three elements.

The two bound queries each use logarithmic comparisons, so finding the range endpoints is Θ(log n) in the conventional worst case. Listing or copying all matching records requires additional time proportional to their number; a count can be computed from the endpoints without scanning them all. A range query on records ordered by a compound key requires a precise comparison contract for that key.

An insertion into a contiguous array may nevertheless require Θ(n) shifts even when its position was found in Θ(log n) time. Finding an index cheaply does not make every subsequent update cheap.

Exact-Match Search Using a Boundary Search

For applications that need deterministic duplicate handling, one can implement exact-match search in terms of the lower bound:

def first_exact_match(a, x):
    k = recursive_lower_bound(a, x)
    if k < len(a) and a[k] == x:
        return k
    return -1

assert first_exact_match([1, 5, 5, 7], 5) == 1
assert first_exact_match([1, 5, 5, 7], 6) == -1
assert first_exact_match([], 6) == -1

This form produces a simple contract: always return the first matching index or -1. It is also convenient if callers frequently ask for insertion positions, because the underlying routine already computes them. By contrast, stopping at the first equal midpoint can save a few comparisons when duplicate position does not matter.

The choice between a direct equality search and a boundary search is therefore about the specification, not whether one is inherently “more binary” or more theoretically efficient. Both have the same worst-case order of growth for random-access sorted data.

A Recursive Search for Monotone Predicates

Binary search can work without a stored array whenever a Boolean predicate changes only once across an ordered integer domain. Suppose predicate(i) is false on a prefix and true on the remaining suffix. The task is to find the first true position in a known integer interval. This is a boundary-search problem: the algorithm does not need to examine every candidate integer.

def first_true(lo, hi, predicate):
    """First true integer in [lo, hi); hi if none.

    Precondition: predicate is False then True (monotone).
    """
    if lo == hi:
        return lo
    mid = lo + (hi - lo) // 2
    if predicate(mid):
        return first_true(lo, mid, predicate)
    return first_true(mid + 1, hi, predicate)

assert first_true(0, 100, lambda i: i * i >= 2025) == 45
assert first_true(0, 100, lambda i: i >= 101) == 100

The contract requires that the predicate be stable and monotone over the searched domain; otherwise eliminating half the integers is not justified. Unlike array lookup, evaluating the predicate might be expensive—for example, an engineering feasibility simulation—so total cost is O(C · log N) if one predicate evaluation costs at most C and N integers are under consideration.

Binary Search on an Answer

An optimization problem sometimes asks for the smallest resource amount that makes a task feasible. When feasibility changes monotonically from false to true as the proposed amount increases, binary search can identify the threshold without checking every value. Examples include the minimum capacity sufficient to complete a fixed collection of jobs under an agreed allocation rule, or the least uniform threshold that passes a deterministic validation test.

The engineer must first establish a valid domain and prove the monotonicity of feasibility. A tempting condition such as “system performs well enough at budget B” might not be monotone if changing B alters system behavior in discontinuous ways. In that case, a conventional binary-search elimination rule would lack its central justification.

The interval must also account for whether the true region exists at all. Returning the high endpoint is a meaningful “none found” marker only when the caller understands that the endpoint is outside the searched range; the caller should not automatically interpret it as an actual feasible candidate.

Search on Descending Data

For an array sorted in descending order, the exact-match code can retain the same interval arithmetic but reverse the direction of its inequalities. If the midpoint value exceeds the target, then the target—if present—must lie to the right. If the midpoint value is below the target, any match must lie left.

def binary_search_descending(a, target):
    """Return an index of target in descending-sorted a, else -1."""
    def search(lo, hi):
        if lo == hi:
            return -1
        mid = lo + (hi - lo) // 2
        if a[mid] == target:
            return mid
        if a[mid] > target:
            return search(mid + 1, hi)
        return search(lo, mid)
    return search(0, len(a))

assert binary_search_descending([9, 7, 4, 1], 7) == 1
assert binary_search_descending([9, 7, 4, 1], 6) == -1

This is not a special case of the ascending implementation unless the comparison is explicitly abstracted. In generic code, one should specify whether an ordered comparator says “comes before” rather than hard-coding numeric less-than. Lower and upper bound also require definitions tied to the chosen comparator, not a casual reversal of one inequality.

Comparators, Keys, and Record Collections

Real data often consist of records rather than scalar values. For an employee list sorted by employee identifier, the search should compare identifiers extracted from the midpoint record. If the collection is sorted by a tuple such as (department, last_name, first_name), the query and comparator must use the same tuple ordering.

A comparator must be internally consistent. It should not interpret case differently during search and sorting, change how null values rank, or silently switch between numeric and lexical order. For instance, lexical order may place the string "10" before "2", while numeric order places 2 before 10. An array prepared under one rule cannot safely be searched under the other.

The generic lower-bound pattern is often more portable than an equality-first search. It needs only the “comes before target” predicate for the boundary and can perform an equality check afterward using the domain's accepted equivalence rule. That is the conceptual model of many standard-library lower-bound facilities.

Boundary Conventions: Inclusive and Exclusive Ends

Some textbooks use a closed interval [low, high] with high = n - 1 and an empty interval characterized by low > high. This convention is valid if applied consistently. The left call then uses [low, mid - 1] and the right call uses [mid + 1, high].

The two conventions must not be mixed. Passing high = len(a) to a routine that treats high as inclusive can lead to an invalid array access. Passing n - 1 to a half-open routine can leave the last element unexamined. Code reviews should identify the convention from the contract, not infer it from variable names alone.

Fixed-Width Midpoint Overflow and Integer Domains

In a language where indexes are bounded signed integers, (lo + hi) / 2 can overflow even when both bounds are individually valid. Using lo + (hi - lo) / 2 avoids the potentially large sum under the usual nonnegative-index and representable-difference assumptions. C++ offers std::midpoint in modern standard libraries, which is designed to compute a midpoint without arithmetic overflow for supported types.

Overflow hazards are even more pronounced when binary-searching the entire domain of a bounded integer type rather than an array. The computation hi - lo can itself overflow if the bounds span extreme negative and positive values. Robust implementations then need a safe midpoint primitive, a widened integer type, or a carefully justified unsigned arithmetic strategy.

Exact behavior is language-specific: Python integers expand automatically subject to available memory, while C and C++ signed overflow is not a valid way to implement search arithmetic. A compiler- or platform-dependent result must not be treated as a correctness proof.

Index Access, Slices, and Data Movement

The conventional Θ(log n) proof assumes that obtaining a[mid] is constant time and that recursive calls merely pass bounds. Consider a different style that constructs a[:mid] or a[mid+1:] at every call. In Python, list slicing copies references into a new list, incurring work and temporary allocation proportional to the copied slice length. The cumulative copied length across a halving path is Θ(n) in the worst case.

This seemingly small implementation change can raise total work from Θ(log n) to Θ(n), even though the number of recursive calls remains logarithmic. It also complicates reporting the answer as an index into the original array because later calls use newly indexed sublists. Iterators, array views, and slice types vary across programming languages; not every slice operation necessarily copies.

The general implementation principle is to carry an interval or a view with demonstrably cheap indexing rather than repeatedly allocate portions of the original sequence. When a program reports complexity, it should make its data access and copying assumptions visible.

Why a Linked List Changes the Cost Model

A linked list supports cheap access to its first node but ordinarily lacks constant-time access to the node at an arbitrary middle position. Finding a midpoint requires traversing links from some known node. Even if a sorted linked-list algorithm makes only logarithmically many ordering decisions, the total pointer-traversal effort can be linear rather than logarithmic.

For example, if each level traverses about half the remaining list to find its midpoint, the work may resemble n/2 + n/4 + n/8 + …, which is Θ(n). Depending on the exact linked-list representation and implementation, additional traversals or bookkeeping may worsen constants. Binary search is therefore not automatically a good choice for every sorted collection.

Alternatives include a linear scan for small linked lists, transforming the data into a random-access representation for repeated searches, maintaining a balanced search tree, or using indexed structures designed for the workload. The algorithm's value arises from the combination of sorted order and affordable access to partition boundaries.

Data Mutation, Snapshots, and Concurrency

The sortedness precondition must remain valid throughout an individual search. A concurrent insertion, deletion, reordering, or change to a record's comparison key can make the midpoint observations inconsistent. An algorithm that is logically correct over a fixed array is not automatically correct over an unsynchronized, mutating shared collection.

For multithreaded or distributed systems, the appropriate remedy depends on the data model: synchronization, immutable snapshots, versioned data, transactionally consistent views, or a container's documented concurrent-search guarantees. Merely making the recursion iterative does not solve inconsistent reads. A snapshot may also be necessary when membership and returned-record identity must refer to the same version of a dataset.

It is possible to search an immutable sequence whose records refer to mutable objects. If the order-defining fields change, the logical ordering may break without changing the sequence's container shape. The search contract must therefore cover the stability of comparison keys, not only the stability of array length and element positions.

Numeric Precision and Floating-Point Comparisons

Binary search over integers has exact candidate counts and discrete stopping conditions. A floating-point root-finding or parameter-search variant often uses numerical tolerances instead: stop when a value interval is sufficiently narrow or when a residual reaches an acceptable threshold. The chosen stopping rule should distinguish interval width, absolute error, relative error, and evaluation noise.

Floating-point midpoint calculation may cease to make progress if adjacent representable values have no distinct representable midpoint under the chosen expression. Search code should not assume unlimited subdivision of a floating-point interval. Another challenge is a noisy or nonmonotone predicate whose measured result oscillates near the threshold; binary search cannot make a valid branch decision from unreliable observations without additional safeguards.

For an integer-indexed sorted array, these issues appear mainly in the comparison semantics of floating-point keys. For a continuous numerical problem they are central to the design itself. The mathematical reduction is related, but ordinary array binary search and numerical bisection are not interchangeable specifications.

Recursion Versus an Iterative Loop

An iterative binary search uses the same candidate interval and branching rule but updates lo and hi within a loop. It does not need one call frame per halving step and normally has constant auxiliary state:

def iterative_binary_search(a, target):
    lo, hi = 0, len(a)
    while lo < hi:
        mid = lo + (hi - lo) // 2
        if a[mid] == target:
            return mid
        if a[mid] < target:
            lo = mid + 1
        else:
            hi = mid
    return -1

The recursive and iterative versions can be verified with the same invariant, tested with the same fixtures, and analyzed with the same worst-case logarithmic number of midpoint inspections. A recursion-oriented curriculum benefits from inspecting the call structure; production implementations frequently choose iteration because it avoids call overhead and stack growth without complicating the basic algorithm.

Neither form should be described as universally faster independent of runtime or surrounding workload. For the small depth of ordinary array binary search, differences in interpreter overhead, comparator cost, branch prediction, and memory hierarchy can matter more than the abstract choice between a function call and a loop.

Tail Position and Tail-Call Optimization

In the exact-match recursive implementation, each recursive call appears in tail position: the function directly returns its result without further arithmetic or processing. This means the algorithm is a suitable candidate for tail-call optimization in languages and runtimes that support it. But the source being tail-recursive does not prove that the runtime will eliminate frames.

Python deliberately does not guarantee elimination of such calls, and ordinary recursion consumes Python interpreter frames. Other environments make different guarantees or optimization choices; some languages define proper tail calls as part of their execution semantics, while others perform tail-call elimination opportunistically.

The distinction between a tail-recursive function and an iterative resource profile is covered in Tail Recursion and Accumulators and Recursion Versus Iteration. Here, the practical point is that the call stack remains part of the cost model unless a specific runtime guarantee or measured transformation justifies another conclusion.

Library Operations and Their Semantics

Many language libraries already provide binary-search or insertion-point operations. Python's bisect module offers bisect_left and bisect_right, whose semantics correspond to lower and upper bounds on an ascending sequence under the module's ordering model. For example, with [3,5,5,5,8], bisect_left(a,5) returns 1 and bisect_right(a,5) returns 4.

C++ supplies std::lower_bound, std::upper_bound, and std::binary_search over appropriate iterator ranges; the comparison and iterator-category requirements matter to their complexity. Java offers Arrays.binarySearch overloads with specific result conventions, including negative encodings for insertion points when an item is missing.

Built-in routines deserve preference where their contracts match the task, especially when they are optimized and well tested. Their semantics are not identical across languages. An API may return a Boolean, an arbitrary duplicate index, a boundary iterator, or a specially encoded insertion position; adapting results without reading its contract causes subtle defects.

When the Input Is Not Fully Sorted

Some specialized problems provide partial order structure. A rotated sorted array, for example, may contain a sorted run wrapped around a pivot. Under distinct keys, it is possible to use modified midpoint comparisons to identify which side is ordered and still perform logarithmic search. But the decision rule is not identical to ordinary binary search and must be justified under that special input contract.

Duplicates can make the rotated-array problem harder. If left, middle, and right values are equal, a comparison may fail to identify which side is reliably ordered. Under some specifications, worst-case behavior can degrade to linear time. It would be incorrect to promise Θ(log n) worst-case performance for all rotated arrays with arbitrary duplicates using the usual one-branch reasoning.

Similarly, searching an array sorted only within independent blocks or searching a dataset with missing ordering guarantees requires a different algorithm. Extending binary search is a proof task: identify the precise property that still allows a region to be rejected after each observation.

Integer Thresholds, Overflow, and Endpoints

For predicate search over an integer domain [L, R), initial bounds must satisfy L <= R. The result is an integer position in the inclusive interval [L, R], with R representing “no true position found” when the entire predicate region is false. A caller that intends to return a feasible number must explicitly check this sentinel condition.

Predicates with the opposite orientation—true on a prefix and false afterward—require reversing the branch rule or changing the question to “first false.” If the predicate can alternate, no single boundary exists and the algorithm is unsound. A predicate evaluated via a flaky network service also requires a stable snapshot or error-handling strategy; repeated calls alone do not prove monotonicity.

For a full signed integer range, safe midpoint arithmetic deserves special treatment because both L + R and R - L might overflow a narrow integer type. In systems languages one may use a reliable midpoint facility or wider arithmetic. In Python the arithmetic is simpler, but an expensive predicate or very large integer domain can still justify an iterative implementation for control and observability.

Instrumenting a Search Trace

Trace recording is useful for teaching and diagnosis. Rather than mutating shared global counters, pass a callback or collect per-invocation observations during a controlled test. A trace can record (lo, hi, mid, a[mid], branch) at each nonempty call. It should not be confused with a runtime stack trace: a logical algorithm trace records candidate elimination, whereas a stack trace records active function calls at a particular execution point.

A good diagnostic trace answers three questions: did the candidate interval shrink strictly, was the chosen branch supported by the comparison, and did the final answer satisfy the API contract? If an unsuccessful search terminates without returning a false positive, the trace may still be incorrect when sortedness or boundary semantics were violated.

Production logging should avoid exposing sensitive query values or records unnecessarily. For large-scale search services, aggregate counters such as midpoint inspections, comparator errors, and precondition violations are often more operationally useful than logging every lookup target.

Worked Scenario I: Search a Sorted Student Roster

An academic office stores a snapshot of student identifiers in ascending order. A staff member needs to determine whether a particular identifier is present without scanning the entire list. The dataset is read-only during the query, identifiers use one consistent numeric comparison, and a single matching index is sufficient. Standard recursive exact-match binary search is appropriate.

Suppose the sorted identifiers are [104, 118, 126, 140, 151, 165, 179, 191]. Searching for 165 checks index 4 (151), then index 6 (179), then index 5 (165), finding the value after three midpoint inspections. Searching for 170 rejects the midpoint 151, then 179, then inspects 165 before proving the remaining interval empty. The outcome is absence, not the index where 170 should be inserted.

Operational boundary: a match confirms that the identifier occurs in this snapshot. It does not prove identity, current enrollment, authorization to view a record, or consistency with a live student information system. Those belong to institutional data governance and access-control processes, not to the binary-search algorithm.

Worked Scenario II: Locate Duplicate Transaction Amounts

A finance reporting tool maintains amounts in ascending order for a read-only analytics task. The array [20, 35, 35, 35, 45, 60] contains three entries with value 35. An arbitrary exact match may locate index 2, but a report needs the complete range. Lower bound returns index 1, upper bound returns index 4, and their difference is 3.

The result illustrates a strong use for boundary search: no linear scan across every equal value is needed merely to count matches. If the report then needs to retrieve all three records, reading the matching range naturally costs additional time proportional to the range length. For records with duplicate amounts, each record still requires its own identifier and context; equal values do not imply duplicate transactions.

Design choice: order records by the key actually queried, and clarify whether the desired answer is a first occurrence, last occurrence, total count, or individual transaction identity. The boundary-search API makes that distinction explicit.

Worked Scenario III: Find a Minimum Feasible Capacity

A scheduling model can tell whether a given integer capacity is sufficient to process a fixed workload under a fixed allocation rule. Suppose feasibility is false for capacities below 45 and true for capacities of 45 or greater. Searching capacities in [0,100) with a monotone-predicate boundary search returns 45 after only a logarithmic number of model evaluations.

The design requires that increasing capacity never make the same workload infeasible. If the rule changes dynamically with capacity, if simulation outcomes are stochastic, or if a resource constraint has multiple interacting thresholds, that monotonicity assumption may be false. The binary-search answer then cannot be trusted solely because its code terminates.

Cost model: if each feasibility evaluation runs an expensive solver, the number of midpoint evaluations is still logarithmic in the integer search range, but total time includes the solver cost. The algorithm minimizes how many candidate capacities are checked; it does not make each evaluation cheap.

Worked Scenario IV: A Sorted Event Timeline

An event archive is indexed by increasing timestamps. An analyst asks for all events occurring during the half-open time interval [start, end). Applying lower bound to start finds the first event at or after the starting time. Applying lower bound to end finds the first event that lies outside the requested interval. The resulting index interval identifies all matching event records.

If the start and end timestamps are represented in incompatible time zones, have inconsistent precision, or are stored with incorrect ordering assumptions, no midpoint algorithm can repair the semantic error. Time interpretation and timestamp normalization are preconditions for reliable ordering. If events can be appended during the search, a snapshot or a documented consistency model is also needed.

Boundary detail: using an exclusive end is useful because events exactly at end belong to the subsequent time window rather than this one. The indexing formula mirrors the half-open interval semantics used inside the recursive algorithm.

Worked Scenario V: A Search Failure at a Boundary

A developer tests only arrays of eight elements with targets present near the midpoint. The implementation uses hi = n but later treats hi as inclusive. The program appears to work for common successful searches, yet can attempt to read a[n] when searching for a value larger than every stored value.

A minimum effective test set includes an empty array, a one-element array, a two-element array, a target smaller than all values, a target larger than all values, a target absent between two existing values, and duplicates at both ends. In the half-open implementation, searching beyond the maximum should terminate at [n,n) without reading a[n].

Process lesson: off-by-one defects are contract defects. The fix is to state whether endpoints are included, write tests against that contract, and prove a strictly decreasing nonnegative interval length. Ad hoc patches to one failing input are less reliable than restoring a consistent invariant.

Worked Scenario VI: Searching a Large Dataset Repeatedly

A service performs many membership queries against an array that changes only during scheduled updates. Maintaining one sorted snapshot may be worthwhile: each subsequent binary search uses logarithmic midpoint inspections. The service might choose a nonrecursive standard-library lower-bound routine because it exposes a clear insertion-point contract and avoids per-call recursion overhead.

If updates become frequent, array insertion or deletion may dominate costs because shifts can be linear. A balanced tree, a database index, or another maintained data structure might be more appropriate. If exact-key membership dominates and ordering is unneeded, a hash-based structure may offer superior expected lookup performance under suitable assumptions.

Architectural lesson: binary search is a query algorithm within a storage strategy. Evaluating it requires total workload cost: initial sorting, index maintenance, memory access behavior, update frequency, thread safety, and the semantic meaning of a found record.

Property-Based Testing Against a Reference

One of the most effective ways to test binary-search logic is to compare it with a simple, independently specified reference. For a small sorted sequence, linear scanning provides first-match and insertion-position results that are easy to trust. Test generated arrays with repeated values, negative values, varying lengths, and absent targets. Verify for all results that the prescribed partition inequalities hold.

from bisect import bisect_left, bisect_right
from random import Random

rng = Random(2026)
for _ in range(600):
    a = sorted(rng.randint(-20, 20) for _ in range(rng.randint(0, 80)))
    x = rng.randint(-25, 25)
    lo = recursive_lower_bound(a, x)
    hi = recursive_upper_bound(a, x)
    assert lo == bisect_left(a, x)
    assert hi == bisect_right(a, x)
    assert all(v < x for v in a[:lo])
    assert all(v >= x for v in a[lo:])
    assert all(v <= x for v in a[:hi])
    assert all(v > x for v in a[hi:])
    k = recursive_binary_search(a, x)
    assert (k == -1) == (x not in a)
    if k != -1:
        assert 0 <= k < len(a) and a[k] == x

Randomized tests are valuable but not exhaustive. The random seed makes this demonstration reproducible; it does not turn sampling into a mathematical proof. The earlier invariant and termination arguments remain the foundation of correctness. For production systems, also test comparator exceptions, concurrency contracts, index-width boundaries, and runtime-specific behavior as applicable.

A Ten-Gate Search Design and Evaluation Framework

The following framework translates mathematical claims into implementation evidence. A designer can apply the gates before selecting a new search routine, and a reviewer can use them when investigating an incorrect lookup.

GateQuestionEvidence or action
1. Define the resultMembership, any index, first index, range, or insertion position?Write explicit return and absence semantics
2. Establish orderWhat comparator and sorting guarantee apply?Document ascending/descending order and key treatment
3. Select representationIs midpoint access cheap and predictable?Identify array, random-access view, or alternative index
4. Choose interval modelAre bounds inclusive or half-open?State initial, recursive, and empty-range rules
5. Write the invariantWhy does the next range retain the desired answer?Prove eliminated values cannot qualify
6. Prove progressDoes every nonterminal call reduce a nonnegative measure?Show strict reduction of hi-lo or equivalent
7. Model resourcesWhat does one midpoint cost and what storage is used?Account for indexing, comparisons, copies, and stack depth
8. Handle boundariesWhat if the input is empty, absent, or duplicated?Test endpoints, misses, duplicates, and sentinels
9. Guard shared stateCan order or keys change during lookup?Define snapshot, locking, or immutable-data guarantees
10. Evaluate full workloadIs searching the dominant operation?Include sort, update, memory, and access-pattern costs

The selected search method should be the simplest one whose correctness and performance claims match the real representation and workload. Formal proof, tests, and operational measurement are complementary forms of evidence rather than interchangeable shortcuts.

Review Questions and Worked Answers

  1. Why must the array be sorted? Because only a known monotone ordering justifies discarding every value on one side of a midpoint after a comparison.
  2. What is the base case for a half-open interval? lo == hi; the candidate count is zero, so exact-match search returns absence.
  3. Why is mid + 1 used after a midpoint smaller than the target? The midpoint is known not to match and all earlier values are also too small; excluding it guarantees progress.
  4. What is the time recurrence? Under constant-time random access and comparison, T(n) = T(⌊n/2⌋) + Θ(1), yielding Θ(log n) worst-case time.
  5. Why is the auxiliary stack space not constant? An ordinary recursive call chain retains Θ(log n) frames at worst unless the runtime eliminates them.
  6. What does lower bound return if all array elements are smaller than x? The value n, representing the insertion position immediately after the final element.
  7. How do you count duplicate occurrences? Compute upper_bound(x) - lower_bound(x) on an ascending array with consistent comparison semantics.
  8. Can binary search be used on a linked list in O(log n) time simply because it halves candidates? Not generally; finding middle nodes can cost linear traversal across levels.
  9. How do you adapt the algorithm to a monotone predicate? Maintain an interval containing the first true position and recurse left when the midpoint is true, right otherwise.
  10. Why is searching a changing shared array dangerous? The comparisons might refer to incompatible versions of the ordering, so eliminated regions might contain valid results.
  11. How does an arbitrary exact-match result differ from the first match? An equality-based midpoint search may return any duplicate; lower bound finds the earliest index at or above the key, which must then be equality-checked.
  12. Is sorting once always beneficial for one search? No. Sorting can cost Θ(n log n), more than a one-time linear scan over unsorted input.
  13. Why can recursive slicing invalidate Θ(log n) total work? Copying a proportion of the remaining sequence at each call produces a geometric sum of Θ(n) copied elements.
  14. What is the correct result of lower bound on [2,4,4,7] for target 5? Index 3, where 5 could be inserted before 7; it is not an index containing 5.
  15. What must be proved before using binary search on a feasibility function? The predicate must be monotone over the stated ordered domain, and each branch must preserve the requested transition boundary.

Glossary of Essential Terms

Binary search
Search method that repeatedly excludes a portion of an ordered candidate set based on a central comparison.
Recursive call
Invocation of a function by itself, directly or indirectly, on a smaller instance.
Base case
Condition terminating recursive descent without another recursive call.
Candidate interval
Range of indices not yet excluded as possible answers.
Half-open interval
Range including its lower endpoint but excluding its upper endpoint.
Midpoint
Index chosen near the center of the current candidate interval.
Invariant
Property established initially and preserved by every valid search transition.
Sortedness precondition
Requirement that elements appear in a specified consistent order before lookup.
Termination measure
Nonnegative quantity that decreases on each nonterminal recursive step.
Exact-match search
Lookup returning an element or index only when a key equals the target.
Lower bound
Index of the first value not less than a target in an ascending sequence.
Upper bound
Index of the first value greater than a target in an ascending sequence.
Insertion position
Boundary at which a new element may be placed while preserving the chosen ordering.
Duplicate key
A value or ordering key that occurs more than once in the collection.
Comparison model
Assumptions about the cost and semantics of evaluating key relationships.
Random access
Ability to retrieve an element at a specified index without traversing prior elements.
Activation record
Call-specific execution state retained during a function invocation.
Auxiliary space
Additional storage used by an algorithm beyond the input collection and required output.
Tail position
Expression whose result becomes the function's result without further pending computation.
Tail-call optimization
Runtime or compiler transformation that can avoid accumulating frames for certain tail calls.
Monotone predicate
Boolean test that changes in only one direction across the searched ordered domain.
Comparator
Rule used to determine relative ordering of values or record keys.
Stable snapshot
Consistent version of data and ordering used throughout a lookup.
Worst-case complexity
Upper growth behavior for the most demanding valid inputs of a given size.
Property-based testing
Testing approach that checks general claims across many generated inputs.
Sentinel result
Special value indicating a condition such as absence or end-of-range.
