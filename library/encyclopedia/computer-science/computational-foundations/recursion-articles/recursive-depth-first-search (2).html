Definition, Purpose, and Specialist Scope

Recursive depth-first search (DFS) is a graph-traversal procedure that discovers a vertex, explores an undiscovered neighbor by a recursive call, and continues through that neighbor's reachable region before returning to resume the current vertex's remaining neighbors. It is a systematic way to explore a graph using the program's call stack as the record of the active exploration path. The crucial graph-specific feature is a visited state that prevents cycles and converging paths from making the procedure expand the same vertex indefinitely or repeatedly.

DFS answers several different questions. A traversal may enumerate vertices reachable from a starting point, construct a parent or DFS tree, find a route, identify connected components, test for cycles, or provide an ordering needed by another algorithm. These results are related, but not interchangeable. A DFS discovery tree is not necessarily a shortest-path tree; visiting each vertex once does not alone determine whether a directed graph has a cycle; and a graph's edge ordering can change a DFS tree without changing which vertices are reachable.

This is a Level 5 article in the Recursion specialist unit, under Computational Foundations within the Computer Science Encyclopedia. Its parent Recursion overview introduces the general recursive method. Recursive Tree Traversal owns rooted-tree visit orders and aggregates; the present article owns traversal on general graphs with cycles, shared neighbors, directed edges, and disconnected components. Exhaustive constraint-based candidate exploration belongs primarily to Backtracking and Recursive Search.

Graphs, Vertices, Edges, and Reachability

A graph consists of a set of vertices and a collection of edges describing relationships. In an undirected graph an edge connects two vertices in both directions; in a directed graph an arc runs from a source to a destination. For example, a one-way dependency compile → test does not imply a reverse dependency test → compile. The orientation must be modeled correctly before any DFS result can be interpreted.

A vertex v is reachable from a starting vertex s if there exists a path from s to v following the directions of edges where applicable. The standard DFS from s returns exactly this reachable set, assuming every adjacency list is complete and the traversal is allowed to finish. When the graph is disconnected or is a directed graph with inaccessible vertices, some vertices are not visited from s; a full-graph DFS must start new searches from still-undiscovered vertices.

Graphs may contain self-loops, repeated edges, cycles, or multiple routes to the same destination. These features matter for algorithm design. A self-loop does not create a new vertex to visit; parallel undirected edges are both traversable edges even if a simple adjacency list shows the same neighbor twice. Different problems require different edge semantics. The easiest teaching cases use a simple graph, but a robust implementation documents whether duplicate edges are permitted, how they are counted, and what it does with malformed neighbor identifiers.

Adjacency Lists and the Input Contract

An adjacency list associates every vertex with its outgoing neighbors. In Python, a dictionary mapping vertices to lists is a convenient representation. For undirected graphs, the usual representation stores both directions of every edge; for directed graphs, only outgoing arcs are stored. A vertex with no outgoing edges should still appear with an empty list when an application needs to enumerate all graph vertices. A neighbor that is not a dictionary key may otherwise cause a lookup failure.

An adjacency list is usually preferable for sparse graphs. Across all vertices, the sum of adjacency lengths is proportional to the represented arcs: E for a directed graph and typically 2E for an undirected graph. For a graph with V vertices and E logical edges, a complete traversal takes O(V + E) time under constant-average-cost adjacency and set operations. An adjacency matrix changes the neighbor-access cost: checking all possible destinations per vertex takes O(V²) for a complete DFS, even if few edges exist.

The code in this article ordinarily assumes a finite in-memory mapping with hashable vertex identifiers, a stable graph during traversal, and finite neighbor sequences. Where a routine iterates for node in graph, it assumes all vertices are keys. Some routines use graph.get(v, []) as a defensive fallback, but this can conceal corrupted input; production validation should distinguish a legitimate isolated vertex from a misspelled or missing node.

The Recursive DFS Contract

The recursive procedure visit(v) means: when v is first discovered, mark it; then recursively explore each neighbor not yet discovered. Each invocation is responsible for one discovered vertex and suspends while deeper invocations run. On return, the caller continues with the next neighbor after the one just explored. This gives DFS its depth-first behavior and makes the call stack an implicit stack of unfinished adjacency scans.

The discovery mark must precede recursion into neighbors. If marking occurs only after a recursive call returns, a cycle such as A → B → A can cause the calls to follow one another without terminating. With mark-on-entry, every vertex causes at most one substantive recursive expansion; later encounters are recognized as already discovered. Merely checking if v in visited at function entry can also work if the mark occurs immediately afterward, but the invariant should be explicit.

A graph vertex is not a recursive subproblem that may be freely recomputed. In the standard reachability task, its expansion should be deduplicated. In backtracking, by contrast, the same board position or logical value may be revisited under different partial assignments because the search state is larger than one vertex. The correct notion of state determines whether a global visited set is sound.

Canonical Recursive DFS in Python

The following implementation returns vertices in discovery order. Each vertex is added to visited before its outgoing adjacency list is scanned. The method uses graph.get(v, ()) to make a missing adjacency key behave like a vertex with no successors; callers should validate input where missing keys are errors.

from typing import Hashable, Mapping, Sequence

def dfs_order(graph: Mapping[Hashable, Sequence[Hashable]], start: Hashable):
    visited = set()
    order = []

    def visit(v):
        visited.add(v)
        order.append(v)
        for w in graph.get(v, ()):
            if w not in visited:
                visit(w)

    visit(start)
    return order

example = {
    'A': ['B', 'C'],
    'B': ['D', 'E'],
    'C': ['E'],
    'D': [],
    'E': ['A'],
}
assert dfs_order(example, 'A') == ['A', 'B', 'D', 'E', 'C']

For the displayed example, the discovery order is A, B, D, E, C. The final edge E → A closes a directed cycle but does not trigger a second visit to A. Traversal order depends on the input adjacency order; this is a valid result, not the only valid result. The code is intentionally small enough to reveal the core invariant, but a very deep reachable chain can exceed the host language's recursion limit.

A Worked Discovery and Return Trace

Consider the directed arcs A → B, A → C, B → D, B → E, C → E, and E → A. The program begins at A, marks it, and follows its first neighbor B. The A call is now waiting to examine C. B marks itself and follows D; D has no outgoing edge and returns. Back at B, the next neighbor E is undiscovered, so DFS marks E. E sees A but does not recurse because A is already marked. E returns, then B returns. Only then does A inspect C; C is marked, sees that E is already marked, and returns. All calls unwind.

Event Active call path Newly discovered Outcome
Start A A Follow first neighbor B
Descend A → B B Follow first neighbor D
Leaf A → B → D D Return to B
Descend A → B → E E A is already discovered
Return A → B, then A None Resume suspended scans
Finish A → C C E already discovered; return

The stack stores where to resume, not merely the sequence of visited vertices. This distinction matters when translating recursive DFS to an iterative implementation: pushing all neighbors at once can produce a valid depth-first search yet differ from a recursive routine's exact entry and exit order. The remaining sections explain how to preserve that order when necessary.

The Visited Set and Exactly-Once Discovery

The visited set represents vertices that have been discovered, not just vertices whose processing is complete. Three facts follow from mark-on-entry: each vertex is discovered at most once; a rediscovered edge does not create a second invocation for that vertex; and a finite graph terminates because there are finitely many possible first discoveries. For a fixed start, a reachable vertex will eventually be discovered if the algorithm runs to completion and examines every outgoing neighbor.

The invariant is simple enough to audit: immediately before visit(w) is called from v, w is not in visited; immediately after visit(w) starts, w belongs to visited; and no call removes w from the set. The invariant fails if a callback clears visited entries, if the graph mutates unpredictably during the run, or if vertex equality and hashing are inconsistent. Production code should not expose the visited set to arbitrary mutation while traversing.

Several specialized routines require additional state. A directed-cycle detector needs to distinguish a vertex on the current recursion path from one that finished earlier. An ancestor/descendant analysis may record discovery and finish times. A search for all simple paths generally must unmark a vertex when backtracking out of a candidate path; that is a different algorithm with a different state contract and potentially exponential output.

The Call Stack and Suspended Neighbor Scans

At a given instant, recursive DFS has one active frame per vertex on the current DFS path. Each frame stores the current vertex, which neighbors have been scanned, local bookkeeping, and a return continuation. Entering an unvisited neighbor pushes a new frame; finishing a vertex's adjacency list pops a frame. The active frames therefore describe the current DFS-tree path, not every vertex discovered so far.

Let d denote the maximum number of simultaneously active frames and V_r the number of reachable vertices. Then 1 ≤ d ≤ V_r for a nonempty search. A long path of vertices can make d = V_r, even when each vertex has only one outgoing edge. A star-like graph rooted at the center has much shallower recursion, even though it may have many vertices. Graph size and maximum DFS depth are separate resource dimensions.

In Python, standard recursive calls consume interpreter stack frames; Python does not guarantee tail-call elimination, and the recursive DFS loop is not generally in tail position because scanning resumes after a child returns. In environments without guaranteed stack capacity for the expected path depth, the explicit-stack version below is the safer general-purpose implementation.

Termination: A Finite Discovery Measure

A termination argument is based on the finite set of undiscovered vertices, rather than a numerical parameter such as n - 1 decreasing at each call. Every genuine recursive descent visits a vertex not previously marked, so the count of undiscovered vertices decreases by one. Between descents, a frame advances through a finite neighbor list. Once no unexplored neighbors remain in the current frame, that invocation returns.

The proof depends on finiteness and on stable iteration. A generator of neighbors that produces an unbounded stream is not a finite adjacency list; a graph modified during traversal can continually introduce new vertices; and a graph whose neighbors are acquired by live network queries can have an evolving reachable region. In those settings, the program needs explicit limits, a snapshot or consistency contract, and a definition of completion beyond the usual finite-graph DFS theorem.

Reachability Correctness: Soundness and Completeness

Soundness means every discovered vertex is reachable from the start. The start vertex is reachable by the empty path. Whenever a recursive call discovers w from v, the edge v → w extends the already established path to v by one step. Thus every discovered vertex has a path from the start, including the parent path built by the algorithm.

Completeness means every reachable vertex is discovered when the search finishes. Suppose a reachable vertex t was not discovered. Choose a path from the start to t and locate its first undiscovered vertex y. Its immediate predecessor x on the path is discovered. Because the DFS call for x eventually examined every outgoing edge, it examined x → y, and would have discovered y if it were not already visited. That is a contradiction. Therefore all reachable vertices must be discovered.

These arguments establish which vertices DFS finds, not which path is shortest or which discovery order it uses. The order is an implementation-dependent detail determined in part by adjacency iteration, whereas the reachable set is a graph property.

Time Complexity with Adjacency Lists

Under the usual representation and cost assumptions, complete recursive DFS runs in Θ(V_r + E_r) time for the reachable subgraph, where V_r counts reached vertices and E_r counts outgoing adjacency entries examined from them. If an outer loop starts DFS from every unvisited vertex, the full traversal takes Θ(V + E) time. Each vertex is entered once. Each outgoing adjacency entry is inspected when its source vertex is processed. Hash-set membership is expected O(1) on average for ordinary hashable identifiers; adversarial hashing can violate that assumption.

This accounting matters: the number of recursive calls is at most V_r, but the number of neighbor checks can be much larger when there are many edges. In dense directed graphs, E can be Θ(V²); the traversal does not become O(V) merely because every vertex is marked once. In an undirected adjacency list, each undirected edge ordinarily appears twice, but scanning 2E entries remains O(V + E).

The cost of building adjacency lists, sorting neighbors, fetching neighbors from disk, or serializing the result is separate from the traversal itself. Sorting every adjacency list can add costs such as O(Σ deg(v) log deg(v)); scanning a matrix instead of adjacency lists can make neighbor inspection O(V²) for a full traversal.

Auxiliary Memory: Visited State and DFS Depth

Standard DFS may require O(V) memory for visited, O(V) for a complete output order, and O(d) active call frames, where d ≤ V. A parent map adds O(V) entries and discovery/finish timestamps add O(V). Asymptotically, a full in-memory graph traversal with these records uses O(V) auxiliary state excluding the input graph. That total does not mean recursive stack overhead is negligible: deep call chains can fail long before available memory is exhausted.

If the traversal streams events and does not accumulate an order, removing the output list saves memory but not the visited set or call stack. In a genuine tree, the visited set can sometimes be omitted because the structure guarantees no cycles and no reconverging paths; in a general graph it usually cannot. On a very large graph, recording all visited identifiers may itself require a specialized external-memory or compressed representation.

Discovery Order, Finish Order, and the DFS Tree

DFS produces two conceptually distinct event orders. A vertex is discovered when the call begins and marked; it is finished after every outgoing neighbor has been examined and every needed recursive child has returned. In a rooted tree, these correspond to preorder and postorder. On a graph, the DFS tree consists only of the edges through which previously unvisited vertices were first reached; other graph edges remain present but do not become tree edges.

For a single-root search, every reached vertex other than the start has exactly one first-discovery parent. The resulting parent edges form a rooted spanning tree of the reachable set—even if the original graph has cycles or additional edges. In a full-graph search, the result is a DFS forest with one root for each search launched from an undiscovered vertex. The forest is an artifact of the DFS order; it need not be unique for the graph.

The finish order is important for algorithms such as topological sorting on directed acyclic graphs, strongly connected component procedures, and scheduling of dependencies. It is not always interchangeable with the discovery order; a vertex whose neighbors are deeply explored may be discovered early but finish last.

Recording Parents, Discovery, and Finish Times

The following reference routine records a parent map, monotone discovery and finish event numbers, and a DFS forest. This example expects all vertices to appear as graph keys. The event counter is incremented once at entry and once at exit, so the interval [discover[v], finish[v]] is nested around the corresponding intervals of descendant calls.

def dfs_forest_times(graph):
    seen, parent, discover, finish = set(), {}, {}, {}
    roots, clock = [], 0

    def visit(v):
        nonlocal clock
        seen.add(v)
        clock += 1
        discover[v] = clock
        for w in graph[v]:
            if w not in seen:
                parent[w] = v
                visit(w)
        clock += 1
        finish[v] = clock

    for start in graph:
        if start not in seen:
            roots.append(start)
            parent[start] = None
            visit(start)
    return roots, parent, discover, finish

G = {'A': ['B'], 'B': ['A'], 'C': []}
roots, parent, tin, tout = dfs_forest_times(G)
assert roots == ['A', 'C']
assert parent == {'A': None, 'B': 'A', 'C': None}
assert tin['A'] < tin['B'] < tout['B'] < tout['A']

Time entries have no physical-time significance; they are an ordering device. In DFS, two vertices in one tree have properly nested entry/exit intervals if one is an ancestor of the other; otherwise their intervals are disjoint. This property supports ancestor queries and edge classification under the standard sequential DFS model.

Parent Pointers and Reconstructing a Route

When a recursive call first discovers w from v, record parent[w] = v. Starting at a target t, following parent pointers backward leads through the DFS tree toward the root. Reverse that sequence to reconstruct a valid path from the starting vertex to t. A missing target means no route was found from the start, not necessarily that the target is absent from the entire graph.

def dfs_path(graph, start, target):
    parent = {start: None}

    def visit(v):
        if v == target:
            return True
        for w in graph.get(v, ()):
            if w not in parent:
                parent[w] = v
                if visit(w):
                    return True
        return False

    if not visit(start):
        return None
    result = []
    cur = target
    while cur is not None:
        result.append(cur)
        cur = parent[cur]
    return result[::-1]

G = {'A': ['B', 'C'], 'B': ['D'], 'C': ['D'], 'D': []}
assert dfs_path(G, 'A', 'D') == ['A', 'B', 'D']
assert dfs_path(G, 'D', 'A') is None

This function performs an early-exit DFS: it returns True through the active call chain once the requested vertex is reached. Its output is a valid path, but not guaranteed to have the fewest edges. In an unweighted graph, breadth-first search (BFS) is ordinarily preferred when shortest-path length is the requirement. In weighted graphs, the appropriate algorithm depends on edge weights and conditions; DFS alone does not optimize weight.

Recursive Early Exit and Search Completion

A normal DFS completes all reachable adjacency scans; an early-exit routine stops after satisfying a predicate, such as discovering a target. These are distinct contracts. If a search stops early, a partial visited set is not the entire reachable set, and its partial finish order is not a full DFS finishing order. Exposing an incomplete result as though it were a complete graph analysis can invalidate downstream cycle detection, component labeling, and ordering.

A clean implementation makes stopping explicit by returning a status, raising a dedicated internal exception, or using a shared completion flag. Returning from an inner call alone is insufficient if callers ignore the value and continue exploring. Likewise, adding break in only the innermost loop does not unwind every recursive level.

If a predicate depends on external services or mutable state, it may not remain true as the graph changes. Clarify whether the predicate is evaluated once, whether a found target's identity is sufficient, and whether a partial traversal can be safely abandoned or resumed later. A recursive call stack cannot ordinarily be resumed after the function has returned; resumable traversals need explicit state or a language runtime facility that preserves continuation state.

Directed and Undirected Graphs: Separate Interpretations

The same visitation mechanics apply to directed and undirected graphs, but their structural inferences differ. In an undirected graph, exploring from any vertex reaches its entire connected component. In a directed graph, a start reaches vertices along outgoing arcs only; reaching B from A does not imply reaching A from B.

An undirected edge back to the immediate parent is expected because the input stores both directions. Seeing that parent in visited is not by itself a cycle. In a directed graph, an edge to an active recursion ancestor is evidence of a directed cycle, while an edge to a vertex that finished earlier is not. The distinction must be implemented explicitly rather than treating all “already visited” edges as equivalent.

Important: In a directed graph, collecting all vertices reached from each new unvisited starting vertex does not generally compute strongly connected components. Strong connectivity requires mutual reachability, usually found using an additional algorithm such as Tarjan's or Kosaraju's. Full-graph DFS forest roots depend on iteration order and cannot be presented as unique directed components.

Full-Graph DFS and Disconnected Components

To traverse a whole graph, iterate through every registered vertex. When a vertex has not yet been discovered, begin a new recursive call. On an undirected graph, each such traversal discovers precisely one connected component, so the grouped results yield a component partition. On a directed graph, the same routine yields graph-search groups governed by launch order, not strongly connected components.

def undirected_components(graph):
    seen, groups = set(), []

    def visit(v, group):
        seen.add(v)
        group.append(v)
        for w in graph[v]:
            if w not in seen:
                visit(w, group)

    for start in graph:
        if start not in seen:
            group = []
            visit(start, group)
            groups.append(group)
    return groups

undirected = {
    1: [2], 2: [1, 3], 3: [2],
    4: [5], 5: [4], 6: [],
}
assert undirected_components(undirected) == [[1, 2, 3], [4, 5], [6]]

The correctness of grouping depends on the representation genuinely being undirected: each logical edge should appear symmetrically, and all vertices should be registered. A malformed one-way adjacency list can produce order-dependent or misleading “components.” On large datasets, this single pass is O(V + E), excluding the memory needed to store the groups.

Colors: White, Gray, and Black

In many graph-algorithm texts, the DFS state of a vertex is modeled with three colors. White means undiscovered. Gray means discovered and still on the active recursion stack. Black means finished: all its outgoing edges have been examined and its recursive descendants have returned. A Boolean visited set merges gray and black into “seen,” which suffices for ordinary reachability but not for every cycle-classification task.

When a directed DFS examines an arc v → w: a white target may become a tree child; a gray target is an active ancestor and forms a back edge; a black target is already finished and may be a forward or cross target depending on ancestry. The colors have a temporal meaning: a gray vertex can turn black after unwinding, so the test must occur during the traversal, not after it.

A common incorrect cycle detector returns True whenever an edge points to anything in the visited set. A diamond-shaped DAG A → B → D and A → C → D causes D to be seen twice but has no directed cycle. The second encounter reaches a black, completed vertex; it is not a back edge.

Directed-Cycle Detection by the Active Path

For directed graphs, maintain both seen and an active set containing vertices whose calls have begun but not finished. During traversal, an edge to an active vertex closes a directed cycle; an edge to a previously completed vertex does not. The routine must remove a vertex from active when finishing it. With a short-circuiting implementation, callers can return immediately once a cycle is found, so cleanup after that point matters only if the state will be reused.

def has_directed_cycle(graph):
    seen, active = set(), set()

    def visit(v):
        seen.add(v)
        active.add(v)
        for w in graph[v]:
            if w in active:
                return True
            if w not in seen and visit(w):
                return True
        active.remove(v)
        return False

    for v in graph:
        if v not in seen and visit(v):
            return True
    return False

DAG = {'A': ['B', 'C'], 'B': ['D'], 'C': ['D'], 'D': []}
CYCLIC = {'A': ['B'], 'B': ['C'], 'C': ['A']}
assert not has_directed_cycle(DAG)
assert has_directed_cycle(CYCLIC)

Self-loops are detected because a vertex is active when it examines an arc to itself. A graph with several disconnected directed regions needs the outer loop shown above; testing a single start may miss a cycle elsewhere. The algorithm runs in O(V + E) expected time on adjacency lists and uses O(V) auxiliary state plus recursion depth.

Recovering a Directed-Cycle Witness

A Boolean answer is often insufficient for engineering work. Dependency validators, scheduling tools, and code-analysis systems benefit from returning a concrete cycle. Maintain an active-path list and map each active vertex to its index in that list. When v → w targets an active vertex w, the suffix starting at w, followed by w again, is a closed directed route that witnesses the problem.

def directed_cycle_witness(graph):
    state = {v: 0 for v in graph}  # 0 white, 1 gray, 2 black
    stack, position = [], {}

    def visit(v):
        state[v] = 1
        position[v] = len(stack)
        stack.append(v)
        for w in graph[v]:
            if state[w] == 1:
                return stack[position[w]:] + [w]
            if state[w] == 0:
                found = visit(w)
                if found is not None:
                    return found
        stack.pop()
        del position[v]
        state[v] = 2
        return None

    for v in graph:
        if state[v] == 0:
            found = visit(v)
            if found is not None:
                return found
    return None

sample = {'P': ['Q'], 'Q': ['R'], 'R': ['Q'], 'S': []}
assert directed_cycle_witness(sample) == ['Q', 'R', 'Q']

This reference implementation assumes every neighbor is a registered graph key. If a cycle is found, the function returns early without clearing its internal stack; the stack is local to the call and is discarded, so no externally visible state remains inconsistent. If the routine is adapted into a persistent reusable object, ensure early-return cleanup is handled explicitly.

Undirected-Cycle Detection and the Parent Exception

For a simple undirected graph, an encounter with an already visited neighbor is a cycle witness unless that neighbor is the current vertex's parent in the DFS tree. The parent exemption is necessary because every undirected tree edge appears in both endpoints' adjacency lists. For example, an undirected chain A—B—C contains no cycle even though B sees visited A when processing its neighbors.

def has_undirected_cycle_simple(graph):
    seen = set()

    def visit(v, parent):
        seen.add(v)
        for w in graph[v]:
            if w not in seen:
                if visit(w, v):
                    return True
            elif w != parent:
                return True
        return False

    for start in graph:
        if start not in seen and visit(start, None):
            return True
    return False

TREE = {1: [2], 2: [1, 3], 3: [2]}
TRIANGLE = {1: [2, 3], 2: [1, 3], 3: [1, 2]}
assert not has_undirected_cycle_simple(TREE)
assert has_undirected_cycle_simple(TRIANGLE)

Multigraph caveat: if parallel undirected edges are permitted, comparing only w != parent may incorrectly ignore a second parallel edge to the parent; under the usual multigraph definition those two edges form a cycle of length two. Track edge identifiers and skip only the exact reverse traversal of the tree edge, not every edge leading to the parent. Self-loops should be handled according to the chosen graph model; they are cycles in the standard undirected multigraph interpretation. Document whether the graph is simple before applying the compact version above.

Tree, Back, Forward, and Cross Edges

A DFS on a directed graph yields tree edges that first discover vertices, back edges to active ancestors, forward edges from an ancestor to a non-tree descendant, and cross edges between vertices with neither ancestor relationship. Discovery/finish timestamps can be used to distinguish ancestor relationships after traversal. In a standard sequential DFS, directed graphs with a back edge have a directed cycle, and a directed acyclic graph has no back edge.

Edge class Meaning during a directed DFS Typical interpretation
Tree First discovery of the destination Belongs to the DFS forest
Back Points to an active ancestor (including self-loop) Certifies a directed cycle
Forward Points to a finished descendant, but is not its tree edge Additional connection within one DFS subtree
Cross Connects vertices not in an ancestor relation Often a connection to an already completed subtree

For a standard DFS of a simple undirected graph, every edge is either a tree edge or a back edge when described consistently relative to the DFS forest. Do not apply directed forward/cross categories indiscriminately to symmetric arcs in an undirected adjacency representation. Because a DFS call runs to completion before its parent advances, a recursive neighbor of an undirected vertex cannot be a cross-branch unvisited vertex in the way it can in an arbitrary traversal order.

Topological Sorting by Reverse Finish Order

A topological order lists vertices of a directed acyclic graph (DAG) so that every arc u → v puts u before v. DFS offers a direct construction: append a vertex when its call finishes, then reverse the finish list. A dependency will finish after all of its unvisited descendants and will therefore appear before them when reversed. This argument assumes the graph has no directed cycle; if a cycle exists, no topological order exists.

def topological_order(graph):
    state = {v: 0 for v in graph}  # white=0, gray=1, black=2
    finished = []

    def visit(v):
        state[v] = 1
        for w in graph[v]:
            if state[w] == 1:
                raise ValueError('directed cycle: topological order impossible')
            if state[w] == 0:
                visit(w)
        state[v] = 2
        finished.append(v)

    for v in graph:
        if state[v] == 0:
            visit(v)
    return finished[::-1]

DAG = {
    'design': ['build'], 'build': ['test'],
    'test': ['release'], 'release': [],
    'review': ['release']
}
order = topological_order(DAG)
index = {v: i for i, v in enumerate(order)}
assert all(index[u] < index[v] for u in DAG for v in DAG[u])

The topological order may not be unique: independent vertices can appear in several valid positions. In the example, review and design have no edge between them and may be interleaved, subject to their downstream constraints. If the user's actual dependency notation instead points from task to prerequisite, the output must be interpreted or reversed accordingly; the code above assumes an edge points from a prerequisite to the task that follows it.

Why a DAG Is Not the Same as a Tree

A DAG allows a vertex to have multiple incoming edges. In a tree, by contrast, each nonroot vertex has a single parent and no cycles. A diamond-shaped DAG—A → B, A → C, B → D, C → D—has two routes from A to D. Recursive tree traversal that blindly descends along every pointer will process D twice. DFS with a visited set will process D only once, and the first encountered predecessor becomes its DFS parent.

This affects aggregation. Counting unique vertices in a reachable DAG is straightforward with a visited set. Computing the number of distinct paths to a destination is different: suppressing all revisits may incorrectly discard legitimate alternative paths. Computing a shared subexpression's value once may be desirable, but only if the subexpression is context-independent and caching is sound. In each case, decide whether the unit of work is the vertex, the path, the edge, or a larger state tuple.

This is why DFS is a traversal framework rather than a complete specification of every graph problem. Mark-on-discovery is correct for reachability and unique-vertex visitation, but it is not a universal substitute for reasoning about the exact result being computed.

Strongly Connected Components: The Boundary of Basic DFS

A strongly connected component (SCC) in a directed graph is a maximal vertex set in which each vertex can reach every other vertex by directed paths. Computing SCCs requires more than restarting ordinary DFS on undiscovered vertices. In the graph A → B with no return arc, one DFS started at A visits both vertices even though {A} and {B} are separate SCCs.

Two standard DFS-based approaches are Kosaraju's algorithm and Tarjan's algorithm. Kosaraju performs a DFS to obtain finishing times, reverses every edge (the transpose graph), then explores vertices in decreasing first-pass finish order on the transpose. Each second-pass traversal yields an SCC. Tarjan's algorithm uses discovery indices, a stack of currently unassigned vertices, and low-link values; a vertex with lowlink[v] == index[v] identifies the root of a strongly connected component to be popped from the stack.

Both standard algorithms run in O(V + E) time on adjacency lists, but they have different state and implementation requirements. Tarjan's component stack must not be confused with the language call stack or with the temporary active set used by a basic cycle detector. A cycle detector can stop after finding one cycle; SCC analysis must partition all relevant vertices and usually examine the entire graph.

Bridges and Articulation Points in Undirected Graphs

In an undirected graph, a bridge is an edge whose removal increases the number of connected components, and an articulation point is a vertex whose removal increases that count. DFS supplies the tree structure used to find both efficiently. Number vertices by discovery time tin[v] and maintain low[v], the smallest discovery time reachable from v or its DFS descendants by following tree edges downward and at most one back edge upward.

For a simple undirected graph, a DFS tree edge (v, w) to child w is a bridge precisely when low[w] > tin[v]: the entire subtree rooted at w lacks a back edge reaching v or an ancestor of v. A nonroot vertex v is an articulation point if it has a DFS child w with low[w] >= tin[v]; the DFS root is an articulation point only if it has at least two DFS-tree children. The root exception is essential: the ordinary nonroot condition would otherwise misclassify many roots.

These formulas arise from the interplay between DFS ancestry and edges back to ancestors, not from arbitrary graph paths. For multigraphs, skip only the exact parent edge ID when computing low links; using only the parent vertex can mishandle parallel edges. Bridge and articulation routines are best treated as specialized algorithms with their own verified implementations rather than added casually to a simple visitor callback.

Bipartite Testing and DFS Coloring

A graph is bipartite if its vertices can be divided into two groups such that every edge crosses between groups. On an undirected graph, DFS can assign alternating colors, 0 and 1, to every newly discovered neighbor. If the traversal encounters an edge whose endpoints already have the same color, the graph is not bipartite. A self-loop is an immediate conflict, and an odd cycle cannot be two-colored consistently.

def is_bipartite_undirected(graph):
    color = {}

    def visit(v, c):
        color[v] = c
        for w in graph[v]:
            if w not in color:
                if not visit(w, 1 - c):
                    return False
            elif color[w] == c:
                return False
        return True

    for start in graph:
        if start not in color and not visit(start, 0):
            return False
    return True

EVEN = {1: [2, 4], 2: [1, 3], 3: [2, 4], 4: [1, 3]}
ODD = {1: [2, 3], 2: [1, 3], 3: [1, 2]}
assert is_bipartite_undirected(EVEN)
assert not is_bipartite_undirected(ODD)

This example assumes an undirected adjacency-list representation with both directions of each edge. As with component discovery, running it on an arbitrary directed edge set without defining how direction should affect the property can make the conclusion ambiguous. Bipartiteness is ordinarily a property of the corresponding undirected graph; if the input is directed, first specify whether you are ignoring direction.

Iterative DFS: A Valid Explicit-Stack Traversal

The common iterative implementation uses a list as a last-in-first-out stack and pushes neighbors. The following concise routine marks a vertex when it is popped, skipping any duplicates that remain on the stack. Reversing the neighbor sequence makes the first listed neighbor likely to be popped next. This produces a depth-first discovery order for ordinary adjacency-list input, but a stack of unexpanded vertices is not a perfect reconstruction of suspended recursive neighbor iterators in every graph.

def dfs_stack(graph, start):
    seen, order = set(), []
    pending = [start]
    while pending:
        v = pending.pop()
        if v in seen:
            continue
        seen.add(v)
        order.append(v)
        pending.extend(reversed(graph.get(v, ())))
    return order

G = {'A': ['B', 'C'], 'B': ['D'], 'C': ['D'], 'D': []}
assert set(dfs_stack(G, 'A')) == {'A', 'B', 'C', 'D'}

Distinguish algorithmic correctness from trace equivalence. Marking when a vertex is pushed, rather than popped, is also a legitimate way to avoid duplicate stack entries, but it can change discovery order and parent assignments because siblings may all be marked before any descendant is explored. If an exact recursive event trace matters—for example, when recording DFS entry/exit times or reproducing a deterministic DFS tree—store an iterator and an active frame per vertex, as in the next section.

Exact Recursive Semantics with Explicit Iterators

A direct simulation of recursive DFS holds a stack of frames (vertex, iterator). On first entering a vertex, mark and emit its enter event. Inspect the neighbor iterator of the top frame; if the next neighbor is already visited, continue that same frame. If not, enter the child and push its iterator. When a frame's neighbor iterator is exhausted, emit its exit event and pop it. This preserves the same entry and exit order as recursive DFS for the same stable adjacency order.

def dfs_enter_exit_iterative(graph, start):
    seen = {start}
    events = [('enter', start)]
    frames = [(start, iter(graph.get(start, ())))]

    while frames:
        v, neighbors = frames[-1]
        try:
            w = next(neighbors)
        except StopIteration:
            events.append(('exit', v))
            frames.pop()
            continue
        if w in seen:
            continue
        seen.add(w)
        events.append(('enter', w))
        frames.append((w, iter(graph.get(w, ()))))
    return events

def dfs_enter_exit_recursive(graph, start):
    seen, events = set(), []
    def visit(v):
        seen.add(v)
        events.append(('enter', v))
        for w in graph.get(v, ()):
            if w not in seen:
                visit(w)
        events.append(('exit', v))
    visit(start)
    return events

G = {'A': ['B', 'C'], 'B': ['C'], 'C': ['A']}
assert dfs_enter_exit_iterative(G, 'A') == dfs_enter_exit_recursive(G, 'A')

The iterative version still uses O(d) explicit frames and O(V) visited state, but it avoids depending on the language's recursive call depth. In Python, iter(graph.get(v, ())) takes a reference to the existing neighbor sequence rather than copying it. Do not mutate adjacency lists while active iterators are scanning them unless the iteration contract explicitly permits that behavior.

DFS Versus Breadth-First Search

Breadth-first search (BFS) explores vertices in increasing numbers of edges from the start using a queue. DFS follows a path deeply before exploring alternatives, using the call stack or an explicit stack. Both achieve O(V + E) time on adjacency lists for full reachable traversal, but they provide different discovery patterns, parent trees, and frontier-memory profiles.

Decision factor Recursive or iterative DFS BFS
Frontier strategy Last-in-first-out active path First-in-first-out pending vertices
Unweighted shortest path Not guaranteed Guaranteed in edge count
Directed cycle analysis Active-path state offers a natural detector Other methods or in-degree analysis needed
Topological ordering Reverse DFS finish order on DAG Kahn's in-degree algorithm is an alternative
Peak exploration state Depth O(d), plus visited and output Frontier up to O(V), plus visited and output
Natural use Reachability, dependency analysis, back edges, structural exploration Minimum-hop routes, layer distances, level order

Do not claim that DFS is always more memory-efficient: both may retain O(V) visited information and the size of a DFS stack or BFS queue depends on graph shape. DFS recursion can overflow on a deep chain, while BFS can hold a large frontier on a broad graph. Choose by the required result and resource constraints rather than by general slogans about search depth.

Deterministic Neighbor Ordering and Reproducibility

In a deterministic DFS implementation, the adjacency iteration order determines the exact DFS discovery order and tree structure. If neighbors are provided in an unordered container or originate from nondeterministic database queries, two runs may build different valid DFS trees. This does not ordinarily change reachability or the existence of a cycle, but it can change which cycle witness is returned, which valid topological order is produced, and the route recorded by parent pointers.

When reproducibility matters, define a stable vertex order and stable neighbor order—for example, sort unique string IDs once when preparing adjacency lists. Sorting inside every recursive call can obscure performance. For large or expensive identifiers, a reusable ordering key may be needed. Any ordering rule must preserve edge orientation and not silently omit duplicate edge records where duplicate edges carry semantic meaning.

Tests should therefore distinguish invariant properties from order-specific properties. Check that each returned path follows actual edges, that every reachable vertex appears exactly once, and that topological order respects every arc. Require exact output order only when the input order and traversal policy are part of the published function contract.

Depth Limits, Host Recursion Limits, and Operational Safety

A graph with a long simple path can force one recursive call per vertex. CPython enforces a recursion-depth limit and raises RecursionError when that limit is exceeded; its exact effective depth depends on environment and call frames. Raising the recursion limit is not a universal remedy and may risk interpreter or native-stack exhaustion. A tail-call optimization cannot generally erase the recursion frames of DFS, because the caller typically must resume scanning neighbors after each child returns.

A production plan for unknown graph depth should normally consider iterative DFS with explicit frames, input-size limits, cancellation, and careful memory budgeting. Explicit stacks avoid the interpreter recursion limit but do not remove the O(V) worst-case storage bound. They can also make checkpointing or inspection easier, since the current traversal state is represented explicitly rather than hidden in call frames.

When traversing untrusted input, consider more than stack overflow: a deliberately dense graph may consume huge time and memory; a malformed identifier may cause an exception; and a callback may block on external input. Scope estimates and limits should be stated in terms of vertices, adjacency entries, elapsed work, and output size—not just depth.

Graph Mutation, Concurrency, and Snapshot Consistency

DFS normally analyzes a fixed graph. If another thread or service adds and removes edges during traversal, the search may see some changes but not others. The output may then correspond to no single consistent graph state. Mutation during iteration may also invalidate a collection iterator or produce missed or repeated neighbor entries depending on the language and data structure.

An application can enforce a read lock, traverse an immutable snapshot, use versioned graph data, or accept a weaker consistency guarantee and document the result as an approximation. For example, a dependency auditor should usually analyze a stable dependency snapshot before accepting a release; a live web crawler may intentionally keep discovering new links and therefore needs a bounded crawl policy rather than claiming to have reached all pages on an ever-changing web.

Parallel DFS introduces additional complexity. Two workers may discover the same vertex concurrently unless the visited mark is atomic or partitioned safely. Ordinary recursive DFS's sequence of discovery/finish times does not directly carry over to arbitrary concurrent traversal because there is no single nested call chain. A parallel algorithm should be specified and analyzed separately.

Path Enumeration Is Not Ordinary Reachability DFS

Ordinary DFS marks each vertex globally and discovers it once. Enumerating all simple paths, however, must allow the same vertex to appear on different candidate paths while forbidding repeats within one path. A common backtracking algorithm maintains a path and an on_path set; it adds the current vertex on entry and removes it on return. That mark/unmark rule is intentionally different from a reachability DFS's permanent visited mark.

The number of simple paths in a graph can be exponential in the graph size, so O(V + E) traversal bounds no longer describe the total output or computation. Pruning, application constraints, or output limits may be essential. Likewise, searching for an optimal path over weighted edges cannot be solved by accepting the first path found by DFS. The correct algorithm depends on whether the target is a single route, every route, a shortest route, a cycle witness, or a feasible configuration.

To study candidate generation, undo operations, branching constraints, and pruning in depth, continue to Backtracking and Recursive Search. Use the present article's visited-state principles as a starting point, not as an algorithm for every combinatorial search task.

Recursive DFS as a Building Block, Not a Finished Application

DFS is often embedded inside a larger system rather than exposed as a final user feature. A static analyzer may use it to inspect call graphs; a build system may use topological sorting to schedule dependencies; a network investigator may use it to identify reachable devices from a known starting point; a compiler may analyze control-flow relationships; and a graph database may traverse a limited neighborhood to derive a report.

The surrounding system determines whether edges are authoritative, whether nodes represent resources or states, how identities are normalized, and what limits and permissions apply. A reachable file directory does not imply that the current user has permission to open every file; a reachable network host does not imply that a service is operational; a reachable task does not imply it is safe to execute. Graph reachability is a structural claim, not a general claim about authorization, safety, performance, or business readiness.

Record the exact graph model, the intended query, and the nature of the output before selecting one of DFS's many specialized variants. This avoids the common failure of interpreting a graph-traversal result as a stronger semantic statement than the data can support.

Worked Scenario I: Inspecting a Software Dependency Graph

A project models a dependency relation among software components. An edge module → prerequisite means the module directly depends on the prerequisite. Starting DFS from the application module reveals every transitive prerequisite reachable along these arcs; recording parents can produce one explanation chain showing why a particular prerequisite is included. The search is O(V_r + E_r) on an adjacency list, provided the package list is a stable snapshot.

The same graph needs cycle detection before certain build or installation plans can be interpreted as acyclic. Suppose web → auth, auth → crypto, and crypto → auth. Ordinary visited-state DFS explores the vertices without looping forever, but it does not automatically report the cycle. The active-path detector identifies the edge back to auth and can report auth → crypto → auth as a witness.

If the build system wants an execution order, first define the edge direction: edges from prerequisites to dependent tasks make reverse DFS finish order a topological execution order. If stored dependency edges point the other way, the order must be adapted. The direction convention is as important as choosing the DFS algorithm.

Worked Scenario II: Exploring a Network of Locations

A navigation service models streets and intersections as vertices and edges. A recursive DFS starting at an access point determines which intersections are reachable by legal links. On a directed street graph, one-way streets restrict movement; reverse reachability is not implied. Parent pointers can reconstruct a valid route, but the first path discovered may be much longer than alternatives.

If the requirement is to find the fewest street segments in an unweighted graph, BFS provides the relevant guarantee. If roads have lengths, tolls, or travel times, a weighted shortest-path method is more appropriate. DFS remains useful for a simple reachability question: can an emergency vehicle reach the destination at all under the represented closures and directions?

A realistic graph must account for data errors, restricted access, changed road conditions, and edge semantics. DFS cannot infer a real-world restriction that was omitted from its graph. A traversal is as trustworthy as the edges and constraints used to construct the input.

Worked Scenario III: Detecting Islands of Connectivity

A facility maintains an undirected graph of devices linked by operational connections. It has two clusters of mutually connected devices and one isolated device. A full-graph DFS starts at each still-undiscovered device and returns three distinct connected components. This is a direct application of the undirected_components procedure: its output partitions vertices into groups, and no undirected edge crosses between the groups in the provided snapshot.

Finding these components is useful for scoping faults or planning network changes, but a connected component is not a health certificate. A device may be reachable in the model but powered off, a connection may be degraded, and security policy may forbid communication over some structural links. Operational status belongs to additional measurements and systems.

If the links are directed—such as permission to push data in only one direction—ordinary undirected component logic is inappropriate. The engineering team must decide whether it needs weak connectivity (ignoring direction), reachability from a designated source, or strongly connected components (mutual reachability).

Worked Scenario IV: Finding a Cycle in a Workflow

A workflow specification says that approve must precede publish, publish must precede archive, and archive must precede approve. Model each requirement as a directed arc from the prerequisite to the subsequent step. The three requirements form a directed cycle. No topological order can satisfy all three constraints simultaneously.

Running DFS with gray/black state finds the offending back edge and, with a path stack, returns a concrete cycle witness. The workflow manager can then present the precise chain to a human reviewer rather than a generic “invalid workflow” message. A black-edge encounter alone should not be reported as a cycle: a DAG may legitimately have converging tasks or shared downstream prerequisites.

A robust validator should evaluate every disconnected region of the workflow graph, not only a nominated starting step. It should also report invalid references and distinguish the structural impossibility of an ordering from a separate business-policy objection to an otherwise valid order.

Worked Scenario V: Auditing a Hierarchy with Shared References

A document platform stores a nested section hierarchy but also permits several sections to reference the same reusable attachment. The section tree can be traversed by preorder, but the combined structure of sections and references may form a DAG or even contain cycles. If the application wants a unique set of referenced resources, ordinary graph DFS with a visited set prevents duplicate processing. If it wants a report for each occurrence, global deduplication would hide repeated references.

The first question is therefore not “which traversal order?” but “what exactly counts as one result?” For a unique resource inventory, mark by stable resource identity. For an occurrence-oriented report, represent the occurrence or path as part of the state and consider output limits. If resources are shared between sections, calling the entire model a rooted tree may produce incorrect size and ownership assumptions.

This distinction is especially important when permissions, ownership, or version identifiers differ by context. Identity normalization and graph construction are prerequisites to applying the textbook DFS procedure reliably.

Worked Scenario VI: Processing a Deep Chain of Records

A dataset contains a directed chain of 100,000 records, each pointing to the next. The graph is sparse: it has 100,000 vertices and 99,999 directed edges. DFS's theoretical time complexity remains O(V + E), which is linear in this case. Nevertheless, a straightforward Python recursive implementation will normally exceed the default recursion limit well before traversing the chain.

Switching to the explicit-iterator stack from this article preserves exactly the same entry/exit order without creating 100,000 nested Python function calls. The explicit frame stack still grows in proportion to the path length, and the visited set stores every reached record. Stack-safe does not mean memory-free. If records are streamed from disk, the design must account for data access, caching, failure recovery, and persistence of traversal state.

In production, test not only a typical balanced input but also the deepest permitted chain, a self-loop, a large cycle, many disconnected isolated vertices, and malformed adjacency references. These cases expose problems that Big-O summaries alone do not capture.

Testing Matrix and Structural Properties

A useful DFS test suite should cover disconnected graphs, repeated edges, self-loops, directed cycles, directed acyclic diamonds, long chains, and adjacency-order changes. Tests should distinguish graph properties from arbitrary traversal order. A result that changes order after neighbors are sorted may still be fully correct; a result that omits a reachable vertex is not.

Test graph Expected invariant Common defect exposed
Empty graph for a full-graph traversal Empty forest and no components Assumption that a start always exists
One isolated registered vertex Exactly one discovery Missing zero-degree vertex
Directed two-vertex cycle Terminates; directed cycle detected Marking only after returning
Directed diamond DAG No cycle; shared target discovered once Calling any revisited edge a cycle
Undirected single edge No cycle Forgetting immediate-parent exception
Undirected triangle Cycle reported Incorrect visited-state handling
Two disconnected components Every registered vertex covered by outer loop Only searching one start
Long directed chain All vertices reachable; depth risk evaluated Unbounded recursive stack

For parent-based path routines, verify that each consecutive pair is an actual directed edge and the path begins and ends at the requested vertices. For an undirected component partition, verify that every vertex appears in exactly one group and no provided edge spans different groups. For topological order, verify position[u] < position[v] for every u → v; exact order equality is unnecessary unless the application promises deterministic ordering.

Differential and Property-Based Testing

Differential testing checks the recursive DFS against an independently written iterative traversal or a small trusted reference implementation. Their orders may legitimately differ, so compare the sets of reached vertices, component partitions where appropriate, and other shared invariants. For exact event equivalence, compare recursive DFS against the explicit-iterator simulation when both use the same neighbor order and start.

For randomly generated small graphs, an independent reachability oracle can repeatedly expand a set of reachable vertices until no new vertices are found; compare that fixed point with the DFS visited set. A directed-cycle detector can be checked against a separate implementation such as a Kahn-style topological-removal algorithm: an unprocessed residual implies a cycle. On small undirected graphs, adding one edge to a tree can be used to test how cycle detection changes.

Metamorphic tests are also useful. Reordering a vertex's adjacency list should not change its reachability set. Adding an edge from an already reachable vertex to another reachable vertex should not reduce reachability. Duplicating an adjacency entry should not change the set of discovered vertices. Such tests capture structural correctness more robustly than hard-coding a single DFS order.

Common Misconceptions and Corrections

Misconception Correction
Every edge to a visited vertex proves a cycle. Directed DFS requires an edge to an active ancestor; undirected simple DFS excludes the immediate parent edge.
DFS always finds a shortest path. DFS finds a path, but not necessarily one with minimum edges or weight.
A DFS from one vertex covers the graph. It covers only vertices reachable from that vertex. Full coverage needs an outer loop.
All vertices visited from one directed root form an SCC. Reachability in one direction does not establish mutual reachability.
DFS memory is always O(depth). A general graph traversal also typically retains O(V) visited state and sometimes O(V) output.
Tail-call optimization makes recursive DFS stack-safe. Many frames resume neighbor scans after child return, and languages may not optimize tail calls.
Sorting neighbors changes which vertices are reachable. It changes visit order and often the DFS tree, not reachability in a fixed graph.
Recursive and iterative DFS always emit identical orders. Different marking and stack policies can produce different valid DFS orders.
A graph with no cycles is necessarily a tree. An acyclic directed graph can share descendants; an undirected acyclic graph may be disconnected.
A finished DFS guarantees the graph is currently unchanged. The result depends on the graph snapshot and consistency model used during traversal.

The recurring corrective principle is to specify graph orientation, traversal state, intended output, and input stability together. None of these choices can be inferred safely from the single phrase “run DFS.”

Ten-Gate DFS Design and Evaluation Framework

The following gates help decide which DFS variant or alternative belongs in a given problem. A design should make each answer explicit before adopting a traversal in a production workflow.

Gate Decision question Evidence or action
1. Graph model Are edges directed or undirected; are parallel edges and loops allowed? Define and validate representation.
2. Vertex identity What makes two vertices the same? Stable IDs, equality and hashing policy.
3. Result contract Reachability, one path, all paths, cycle, component, or order? Choose the matching algorithm, not a generic visitor.
4. Traversal scope Single start or complete graph? Decide whether an outer loop is required.
5. State semantics Permanent visited marks or active-path marks? Document white/gray/black or on-path rules.
6. Ordering Does the exact discovery or finish order matter? Stable neighbor order and event semantics.
7. Correctness Which invariant proves the output? Soundness, completeness, ancestry, or low-link proof.
8. Resource bound Maximum vertices, edges, and DFS path depth? O(V + E) budget plus explicit-stack choice.
9. Input integrity Is the graph fixed and internally consistent? Validate missing nodes and snapshot policy.
10. Operational use What does the graph result actually authorize or establish? Distinguish structural results from business or safety claims.

For complex applications, a single DFS may be one stage in a pipeline: validate the graph, construct a consistent adjacency representation, compute a DFS-derived result, verify structural invariants, then apply domain-specific policy to the result. Record the boundary between algorithmic fact and domain-specific interpretation.

Review Questions and Model Answers

  1. Why must a DFS vertex be marked before descending? Because an edge back to an active or previously discovered vertex could otherwise trigger another recursive expansion and create nontermination on cycles.
  2. What set does DFS from s discover? Exactly the vertices reachable from s along the graph's permitted edge directions, assuming a finite stable graph and completed traversal.
  3. Why is graph DFS O(V + E)? Every vertex is first-discovered at most once and every adjacency entry of a visited vertex is scanned at most once in a full run, given expected constant-time set membership.
  4. What is the difference between a gray and black vertex? Gray is active on the current recursive call path; black has finished all outgoing adjacency scans.
  5. Does an edge to a black vertex prove a directed cycle? No. A diamond-shaped DAG provides a counterexample with a shared descendant.
  6. How can one recover a path from the start to a target? Store each newly discovered vertex's parent, then follow the target's parent pointers back to the start and reverse the sequence.
  7. When is the parent-edge exception valid for undirected cycle detection? In a simple undirected graph. For a multigraph, distinguish the exact parent edge ID from parallel edges.
  8. What does a full-graph DFS forest represent? Separate rooted DFS trees launched from each still-unvisited vertex; on undirected input these correspond to connected components.
  9. Why is a full-graph DFS forest not an SCC partition in a directed graph? One-way reachability does not establish mutual reachability within each search group.
  10. What changes when iterative DFS pushes all neighbors at once? The traversal can remain correct for reachability but differ in exact discovery, parent, and finish behavior from recursive DFS.
  11. What does reverse DFS finishing order yield on a DAG? One valid topological ordering, with all arcs directed from earlier vertices to later vertices under the chosen edge orientation.
  12. What makes recursion unsafe for very deep graph paths? Active call-frame count can grow linearly in path length and exceed the language runtime's recursion depth or stack capacity.
  13. How does a DFS-based bridge test use low? A child edge (v, w) is a bridge in a simple undirected graph if low[w] > tin[v].
  14. Why doesn't global visited-state DFS enumerate all simple paths? It suppresses revisiting a vertex even when a different candidate path reaches it; path enumeration needs path-local state and may have exponential output.
  15. What would you test for a directed-cycle detector? At minimum a self-loop, a genuine directed cycle, a diamond DAG with shared descendant, and a cycle outside the first starting component.

Glossary of Essential Terms

  • Adjacency list: a representation that lists the outgoing neighbors of each vertex.
  • Adjacency matrix: a table recording whether each ordered pair of vertices is connected.
  • Ancestor: a vertex above another in a rooted DFS tree along parent edges.
  • Articulation point: an undirected-graph vertex whose removal increases the number of connected components.
  • Back edge: an edge from a DFS vertex to an active ancestor in directed DFS.
  • Bipartite graph: an undirected graph whose vertices can be colored with two colors so every edge crosses colors.
  • Black: a vertex whose recursive DFS processing has finished.
  • Bridge: an undirected edge whose removal increases the number of connected components.
  • Connected component: a maximal connected vertex set in an undirected graph.
  • Cross edge: a directed DFS edge whose endpoints are in different DFS ancestry branches or trees.
  • Cycle: a closed route following edges under the graph's direction and graph-model rules.
  • Depth-first search (DFS): a traversal that explores through a neighbor as far as possible before resuming alternative neighbors.
  • DFS forest: the set of DFS trees obtained from a full traversal of a possibly disconnected graph.
  • DFS tree: the first-discovery parent edges of a search rooted at one vertex.
  • Directed acyclic graph (DAG): a directed graph containing no directed cycle.
  • Discovery time: an ordinal timestamp assigned when a DFS first enters a vertex.
  • Edge: a relationship between vertices; a directed edge is often called an arc.
  • Finish time: an ordinal timestamp assigned after a DFS finishes a vertex's adjacency scan.
  • Forward edge: a directed non-tree edge from an ancestor to a descendant in the DFS tree.
  • Gray: a discovered vertex whose recursive call remains active.
  • Low-link value: discovery information encoding how far back a DFS subtree can reach via allowable back edges or stack connections, depending on the algorithm.
  • Parent map: the record of first-discovery predecessors used to reconstruct a DFS tree or route.
  • Reachability: the existence of a path from one vertex to another under allowed edge directions.
  • Recursion depth: the number of simultaneously active recursive calls.
  • Strongly connected component (SCC): a maximal directed-graph vertex set with mutual reachability.
  • Topological order: a vertex ordering in which every directed prerequisite edge precedes its destination.
  • Traversal order: the sequence in which a graph algorithm encounters or completes vertices.
  • Visited set: a collection of vertices previously discovered in a particular DFS run.
  • White: a vertex not yet discovered.

Technical References and Further Reading

  • Thomas H. Cormen, Charles E. Leiserson, Ronald L. Rivest, and Clifford Stein, Introduction to Algorithms, 4th ed. (MIT Press, 2022), chapters on elementary graph algorithms and strongly connected components. A standard source for DFS colors, timestamps, edge types, topological sorting, and graph-traversal bounds.
  • Robert Sedgewick and Kevin Wayne, Algorithms, 4th ed. (Addison-Wesley, 2011), chapters on undirected and directed graphs. Discusses DFS reachability, paths, cycle detection, components, and directed orderings.
  • Steven S. Skiena, The Algorithm Design Manual, 3rd ed. (Springer, 2020), chapters on graph traversal and graph problems. Practical considerations for selecting graph algorithms and analyzing their outputs.
  • Robert E. Tarjan, “Depth-First Search and Linear Graph Algorithms”, SIAM Journal on Computing 1, no. 2 (1972): 146–160. Foundational linear-time DFS-derived graph algorithms, including strong components and biconnectivity.
  • Harold N. Gabow, “Path-based Depth-First Search for Strong and Biconnected Components”, Information Processing Letters 74, nos. 3–4 (2000): 107–114. A later approach to component analysis using depth-first structure.
  • Python Software Foundation, Python documentation: recursion limit and Python documentation: setrecursionlimit. Relevant to the operational distinction between recursive DFS and explicit-stack traversal.

These references provide foundations and further study; the worked examples in this article are self-contained instructional implementations, not assertions that production runtime behavior is identical across languages and environments.
