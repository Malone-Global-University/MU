Definition, Purpose, and Scope

Recursive tree traversal is a method for systematically examining the nodes of a rooted tree by processing a node and recursively processing its child subtrees. It is a representative form of structural recursion: the existing data structure supplies the smaller problems, and a finite empty subtree supplies the base case. Traversal is not one fixed sequence. The position of a node's processing relative to its children's processing determines whether the procedure is preorder, inorder, or postorder, and whether it can compute a property that depends on child results.

A visit is a defined action, such as recording a value, checking a predicate, emitting serialized output, transforming a node, or combining computed attributes. Visiting is conceptually distinct from entering a recursive function: a program may enter a node, traverse children, and only then count the node as visited. This distinction is essential when comparing orders and reasoning about side effects.

This is specialist article 10 of 15 under the Recursion unit of the MGU Computer Science Encyclopedia. It extends the Recursion overview and its sibling accounts of Recursive Definitions and Base Cases, Recursion and Mathematical Induction, and Recursive Call Stacks. The present article owns traversal of trees as hierarchical data; general graph cycles and visited sets belong primarily to Recursive Depth-First Search.

Working contract: unless a section says otherwise, a tree has finitely many distinct nodes, one designated root, at most one parent per nonroot node, and child links that do not form cycles. Ordered children are visited in the order they appear. These preconditions are not automatically true for arbitrary pointer graphs.

Trees, Roots, Children, and Ordered Structure

A rooted tree contains a distinguished root. Every other node has exactly one parent, and a node's descendants are reached through its children. A leaf has no children. The subtree rooted at a node contains that node and all of its descendants. A finite rooted tree therefore decomposes recursively into a root plus zero or more smaller subtrees.

Tree order is an independent property. In an ordered rooted tree, the left-to-right ordering of each node's children matters; traversing those children in a different order changes the output sequence. In an unordered tree, there is no intrinsic sibling order, so a program must either adopt a particular enumeration convention or treat different sibling sequences as equally valid. A binary tree has designated left and right child positions, either of which may be absent; it is not simply an arbitrary tree of at most two indistinguishable children.

Node values do not identify node positions uniquely. Two different nodes can both contain the value 7. This article's output examples list values for readability, but the traversal acts on node identities. When an algorithm relies on child links for membership, parent paths or identity-based tests are often more precise than comparing payload values.

A Reusable Binary-Tree Model

For executable examples, define a small immutable binary node with a value and optional left and right children. Using immutable nodes is convenient for teaching because a traversal cannot accidentally relink the structure while another call is using it. Real applications may choose mutable nodes, object identities, parent links, or indexed arrays; the traversal principles remain the same when the structural preconditions hold.

Consider a concrete ordered binary tree with root A, children B and C; B has children D and E, while C has only a right child F. This intentionally asymmetric example exposes ordering differences better than a single chain.

from dataclasses import dataclass
from typing import Any, Optional

@dataclass(frozen=True)
class Node:
    value: Any
    left: Optional["Node"] = None
    right: Optional["Node"] = None

#           A
#         /   \
#        B     C
#       / \     \
#      D   E     F
root = Node("A",
            Node("B", Node("D"), Node("E")),
            Node("C", None, Node("F")))
assert root.left.value == "B"
assert root.right.right.value == "F"

A missing child is represented by None. In a different language, it may be a null pointer, a tagged empty constructor, or an absent index. The important property is that the empty case is clearly distinguishable from an actual node whose stored value happens to be zero, an empty string, or None.

The Recursive Traversal Template

Every conventional depth-first binary-tree traversal can be described with one framework. If the subtree is empty, return immediately. Otherwise, process the current node at a chosen point before, between, or after recursive child visits. Since the children are strictly smaller subtrees of a finite tree, this produces a terminating decomposition. Each nonempty node is entered once, although the program may make additional calls on empty child positions.

The template exposes three events: entry to a node, the boundary between its left and right subtrees, and exit after both subtrees. Selecting one event as the visit point gives preorder, inorder, or postorder. More sophisticated tree algorithms may use several events at once, for example recording an entry timestamp and computing an aggregate on exit.

def traverse_template(node):
    if node is None:
        return
    # Preorder action could occur here.
    traverse_template(node.left)
    # Inorder action could occur here.
    traverse_template(node.right)
    # Postorder action could occur here.

# This is a structural illustration; it has no output action.
traverse_template(root)

Moving an action changes the algorithm's semantics without changing its basic recursion shape. For example, a file-system-like hierarchy often records a directory before its contents but calculates total descendant size after processing the contents. These are not contradictory orders: they are different actions anchored to different events.

Preorder: Node Before Descendants

Preorder means visit the current node first, then traverse its left child, then its right child. For an ordered binary tree, its form is node → left → right. The parent is therefore always emitted before any of its descendants. Preorder is particularly convenient for enumerating paths, copying top-down metadata, creating outlines, or serializing tree shapes when empty-child markers are included.

In the sample tree, preorder visits A, B, D, E, C, F. It does not sort values or guarantee numerical order. Sibling ordering depends solely on the chosen child sequence. A right-first version is still a preorder in the parent-before-child sense, but it produces a different sequence than the left-first convention used here.

def preorder(node):
    if node is None:
        return []
    return [node.value] + preorder(node.left) + preorder(node.right)

assert preorder(root) == ["A", "B", "D", "E", "C", "F"]

This implementation is intentionally transparent, not the most allocation-efficient: each list concatenation may copy elements, and repeated copying can make the total work exceed linear time. A visitor that appends to one list—or a generator that yields node values—avoids this cost. The next sections distinguish the logical traversal order from the concrete performance of a particular list-building expression.

Worked Preorder Trace and Parent-First Processing

Beginning at A, the procedure records A and descends to B. It records B, then enters D. Since D has no children, the call returns and execution resumes in B, where the right child E is processed. Only after the entire B subtree is finished does the caller at A enter C, whose right child is F.

The order makes every descendant appear after its parent. This property can be exploited to assign a prefix path or inherited environment to a child: by the time the child begins, information derived from the parent has already been computed. The reverse is not true. At the moment the parent is first visited, a property requiring all of its descendants generally remains unknown unless precomputed or accessible elsewhere.

StepActive nodeEventRecorded prefix

A step in this table is a nonempty-node visit, not every function call. Calls on missing children still occur in the simple implementation and immediately return; they are omitted from the trace to keep the conceptual visit order visible.

Inorder: Left Subtree, Node, Right Subtree

Inorder traversal applies naturally to binary trees with distinct left and right positions: recursively traverse the left subtree, visit the node, then traverse the right subtree. Its form is left → node → right. The root may appear in the middle of the result; for the sample tree the inorder sequence is D, B, E, A, C, F.

The word inorder does not by itself mean sorted order. Inorder traversal lists the keys of a binary search tree in nondecreasing order only when that tree satisfies a suitable ordering invariant. The left/right shape alone is insufficient. A tree containing arbitrary labels such as the sample is not sorted merely because the traversal is named inorder.

def inorder(node):
    if node is None:
        return []
    out = []
    def visit(cur):
        if cur is None:
            return
        visit(cur.left)
        out.append(cur.value)
        visit(cur.right)
    visit(node)
    return out

assert inorder(root) == ["D", "B", "E", "A", "C", "F"]

Different authors may define an analogous middle-position visit for n-ary trees, but without an additional convention there is no unique place to put the parent between an arbitrary number of children. That is why this article reserves the unqualified inorder convention for binary trees.

Inorder and Binary-Search-Tree Ordering

For a binary search tree, the conventional invariant states that keys in the left subtree precede the node's key, and keys in the right subtree follow it, with a defined policy for equality. Under a strict no-duplicates policy, every left key is smaller and every right key larger. Under a duplicates-allowed policy, the inequalities and placement rules must be specified carefully; inorder then yields a nondecreasing sequence rather than necessarily a strictly increasing one.

Correctness follows by structural induction. Each child subtree is itself a binary search tree, so its inorder listing is sorted. Every value produced by the left subtree is no greater than the parent under the selected duplicate rule, and every value in the right subtree is no smaller; concatenating the three sequences preserves order. This theorem depends on the stored-value invariant, not on inorder traversal as a general sorting algorithm.

bst = Node(8,
           Node(4, Node(2), Node(6)),
           Node(12, Node(10), Node(14)))
assert inorder(bst) == [2, 4, 6, 8, 10, 12, 14]
assert inorder(root) != sorted(inorder(root))

In production, the cost of traversing the entire tree is linear in its number of nodes, even if the tree allows logarithmic-time search for one key when balanced. Inorder enumeration is not a shortcut around inspecting all requested output items.

Postorder: Descendants Before Node

Postorder visits both child subtrees before visiting the current node, conventionally left → right → node for an ordered binary tree. For the sample, the order is D, E, B, F, C, A. Every child is visited before its parent, so bottom-up facts can be computed as a call returns. This is the natural shape for subtree sums, node counts, heights, syntax-tree evaluation, and safe deallocation when the ownership model requires descendants to be handled first.

Postorder is not simply a reversed preorder traversal. Reversing the sample's preorder gives F, C, E, D, B, A, which differs from postorder. A specially adjusted reversed preorder—with child order swapped—can recreate postorder, but that is a separate technique that must be justified rather than assumed.

def postorder(node):
    if node is None:
        return []
    out = []
    def visit(cur):
        if cur is None:
            return
        visit(cur.left)
        visit(cur.right)
        out.append(cur.value)
    visit(node)
    return out

assert postorder(root) == ["D", "E", "B", "F", "C", "A"]

The important benefit is not merely the output order. When recursion unwinds after both children return, the caller can receive a computed result from each child and combine them into the result for its own subtree, with no separate global accumulator required.

Euler-Tour Interpretation of Traversal Events

Imagine walking around the outer boundary of a binary tree and recording when a node is encountered before its left child, between its left and right child, and after its right child. These three conceptual encounter points correspond to preorder, inorder, and postorder events. One recursive procedure can deliberately perform different actions at each event. The analogy is useful but must not be confused with a graph-theoretic Eulerian circuit, which concerns traversing edges under particular constraints.

A practical instrumentation method places entry and exit events in one function. The example below returns three independent sequences, without running three separate top-level traversals. It also shows that a node can have an entry time and exit time that bracket the complete processing of every descendant.

def three_orders(node):
    pre, middle, post = [], [], []
    def walk(cur):
        if cur is None:
            return
        pre.append(cur.value)
        walk(cur.left)
        middle.append(cur.value)
        walk(cur.right)
        post.append(cur.value)
    walk(node)
    return pre, middle, post

assert three_orders(root) == (preorder(root), inorder(root), postorder(root))

Euler-tour-style event labeling is useful for tree algorithms that need entry and exit timestamps, nested interval ranges, or different parent-first and child-first computations during the same walk. Those advanced uses retain the ordinary structural recursion base case.

Base Cases and the Empty-Subtree Identity

In the familiar optional-child representation, None denotes an empty tree. This is the base case for every recursive traversal. For enumeration it contributes no output; for a sum it contributes zero; for a product it might contribute one; for a maximum it requires either a sentinel or an explicit optional result. The base case must match the mathematical identity of the operation being computed.

Confusing the absence of a child with the stored value of a leaf causes errors. For example, code that uses if not node.value to detect emptiness incorrectly treats nodes containing zero or an empty string as absent. A leaf is still a real node and may need to be counted, visited, or returned even though both children are empty.

Another subtle case is a root that itself is absent. A robust traversal should either return an empty result or explicitly reject a missing root according to its public contract. It should not access node.left before the empty test. A well-chosen base case makes both ordinary leaves and an entirely empty input work without special-case code scattered throughout the recursion.

Structural Induction: Why Every Node Is Visited Once

Assume the input is a finite tree with no shared nodes or cycles. Prove by structural induction that the conventional recursive traversal visits every nonempty node in a subtree exactly once. In the empty case, no nodes exist and the procedure performs no visits. For a nonempty root, the procedure visits that root exactly once. By the inductive hypothesis, the left traversal visits every node in its own subtree once, and the right traversal does likewise.

Since a true tree's left and right subtrees are disjoint and neither contains the root, the union of their visits and the root's visit covers every node exactly once. This argument works for preorder, inorder, and postorder because it concerns which nodes are visited, not the position of the visit event.

Order-specific correctness needs a second argument. For preorder, the root's event is before both subtraversals; for postorder, it is after both; for inorder, it separates the left and right sequences. The base-case and induction pattern is shared, but the claimed ordering differs. See {href('Recursion and Mathematical Induction','recursion-and-mathematical-induction')} for the general proof method.

Termination Through Proper Subtrees

Termination follows from a well-founded measure: the number of nodes remaining in the current subtree. For a nonempty finite tree, each proper child subtree contains strictly fewer nodes than its parent subtree. A recursive call therefore decreases a nonnegative integer. Calls eventually reach empty subtrees, which return without making further calls. No infinite strictly decreasing sequence of nonnegative integers is possible.

The proof assumes that child links do not form cycles and that the node structure is not modified to create one while recursion proceeds. An object graph with a parent pointer treated as another child can violate this assumption immediately. Similarly, two parents that share a child create a directed acyclic graph rather than a strict tree: recursion may still terminate, but the exactly-once property fails unless identity-based deduplication is added.

For lazy or potentially infinite structures, proper-subtree decomposition alone does not prove that an entire traversal finishes. A generator can sometimes produce an initial finite prefix of an infinite structure, but a total traversal over all nodes cannot return in finite time if infinitely many nodes must be enumerated.

Time Complexity: Work per Node

For a well-formed finite tree containing n distinct nodes, a conventional traversal that performs constant work per node takes Θ(n) time. It performs one nonempty-node visit per node, and the empty-child tests add only a linear number of operations. In a binary tree with two child slots per node, there are exactly n + 1 empty child positions when represented as a finite rooted binary tree with missing child pointers, so the null checks do not change the order of growth.

That bound is conditional on the cost of the visitor and the output representation. A visitor that sorts the entire subtree at every node, recomputes descendant height, or repeatedly concatenates large lists can raise total work significantly. Appending one value to a list is normally amortized constant time in Python; repeated list concatenation is not. A simple recursive traversal shape does not automatically establish linear-time behavior for every algorithm using it.

For a generic node with k children, iterating over each child link contributes work proportional to total edges, which is n - 1 in a nonempty tree. If there is a nonconstant per-child operation, include its cost explicitly. This makes Θ(n) a solid baseline for ordinary traversals, not an unconditional bound for every recursive tree computation.

Height and Auxiliary Stack Space

Recursive depth-first traversal uses one active call frame for each node along the current root-to-descendant path, plus a constant number of base-case calls. Define tree height h as the number of edges on a longest root-to-leaf path, with an empty tree assigned height -1. The nonempty call-stack depth is then h + 1. Under a different convention where height counts nodes, the notation changes, but the asymptotic auxiliary call-stack space remains O(h + 1).

A balanced binary tree with n nodes has logarithmic height, yielding O(log n) recursion depth. A degenerate one-child chain has height n - 1, yielding O(n) depth and potentially exceeding a language runtime's recursion limit. Being a binary tree does not guarantee balance, and a randomly shaped or ordered tree does not inherit a logarithmic bound merely from having two child positions.

If a traversal constructs an output list of all n node values, that list requires Θ(n) additional storage independent of stack use. It is therefore misleading to describe the full algorithm as simply “O(h) space” without specifying whether output memory is excluded. For returning a new tree, the new nodes likewise require Θ(n) storage. State the accounting model before comparing memory use.

Subtree Size and Sum as Postorder Folds

A traversal that returns an aggregate demonstrates the difference between visiting and folding a tree. For subtree size, the empty case contributes zero; a nonempty node contributes one plus the sizes of its children. For a numerical sum, the empty case contributes zero and the root contributes its own value plus the child sums. Each node can be handled once, in postorder evaluation order, with a scalar result returned by each call.

A recursive function such as size(node) may look like it “visits the root first” because it executes an if statement upon entry, yet the root's final size is not known until both children return. The order of relevant aggregation is postorder even when entry checks precede descent.

def tree_size(node):
    if node is None:
        return 0
    return 1 + tree_size(node.left) + tree_size(node.right)

def tree_sum(node):
    if node is None:
        return 0
    return node.value + tree_sum(node.left) + tree_sum(node.right)

numbers = Node(5, Node(3, Node(1), Node(4)), Node(9))
assert tree_size(root) == 6
assert tree_size(None) == 0
assert tree_sum(numbers) == 22

Both functions have Θ(n) time and O(h + 1) recursion stack space when node access and arithmetic are constant-time. The sum's numeric type must support the chosen addition and identity; a mixed-type payload tree requires a more explicit conversion or validation policy.

Tree Height, Leaves, and Empty-Tree Conventions

Height and leaf count require precise conventions. With height measured in edges, an empty tree has height -1, a leaf has height zero, and an internal node has height one plus the maximum height of either child. Under a node-counting convention, empty height is zero and a leaf's height is one. Either is coherent; mixing them produces off-by-one errors in balance and depth calculations.

A leaf is a nonempty node with no children. Its count does not equal the number of absent pointers, since every leaf has two absent child positions in a binary node representation, while an internal node can also have an absent child. Leaf counting therefore tests both children after confirming the node exists.

def tree_height_edges(node):
    if node is None:
        return -1
    return 1 + max(tree_height_edges(node.left),
                   tree_height_edges(node.right))

def leaf_count(node):
    if node is None:
        return 0
    if node.left is None and node.right is None:
        return 1
    return leaf_count(node.left) + leaf_count(node.right)

assert tree_height_edges(root) == 2
assert leaf_count(root) == 3
assert tree_height_edges(Node("leaf")) == 0
assert leaf_count(None) == 0

A direct height computation on one root is Θ(n). However, asking for the height of each subtree by independently calling the full recursive height function can repeat work. A postorder pass that returns multiple facts at once—size, height, balance status—usually avoids such recomputation.

Combining Multiple Subtree Attributes in One Pass

Many applications need several properties of a subtree simultaneously. Instead of running a complete traversal for each property or recomputing heights for every ancestor, return a tuple containing all relevant attributes. For example, a binary tree is height-balanced under the common local criterion when, at every node, the heights of its left and right subtrees differ by at most one, and both children are themselves balanced.

Because the balance status depends on child results, a single postorder function can return (size, height, balanced). Its correctness is proved by structural induction: child results are assumed correct, then the parent tuple is computed from them and the node's own contribution. The local balance inequality is insufficient without the recursive condition that both descendants are balanced.

def summarize(node):
    if node is None:
        return (0, -1, True)  # size, edge-height, balanced
    ls, lh, lb = summarize(node.left)
    rs, rh, rb = summarize(node.right)
    return (1 + ls + rs,
            1 + max(lh, rh),
            lb and rb and abs(lh - rh) <= 1)

assert summarize(root) == (6, 2, True)
chain = Node(1, Node(2, Node(3, Node(4))))
assert summarize(chain) == (4, 3, False)

This pass takes Θ(n) time and O(h + 1) stack frames, returning only constant-size attributes per subtree. If a child summary itself contains a full list or set, the combine cost and output memory must be revisited.

Generalized Tree Folds and Recursive Algebra

A tree fold replaces each empty subtree with a base value and combines a node's payload with the already-folded values of its children. It abstracts a large class of bottom-up recursive computations. In functional-programming terminology, similar constructions are often called catamorphisms; for a particular tree type, the fold respects that type's recursive constructors.

The power of a fold is that traversal mechanics remain fixed while the combination operation changes. A tree count uses zero as its empty value and adds one; a height calculation uses -1 and maximum; a nested expression evaluation applies an operator to child values. The fold should have a clear return type, and the combining operation should not depend on hidden mutable state unless that dependence is deliberately part of the contract.

def fold_binary(node, empty_value, combine):
    if node is None:
        return empty_value
    left = fold_binary(node.left, empty_value, combine)
    right = fold_binary(node.right, empty_value, combine)
    return combine(node.value, left, right)

assert fold_binary(root, 0, lambda value, left, right:
                   1 + left + right) == 6
assert fold_binary(numbers, 0, lambda value, left, right:
                   value + left + right) == 22
assert fold_binary(root, -1, lambda value, left, right:
                   1 + max(left, right)) == 2

The simple version evaluates both children even if the parent result might be known early. A short-circuiting existential test, for example, may be more efficiently expressed by a specialized traversal that avoids examining the second subtree once the first has produced a satisfactory result.

Recursive Expression-Tree Evaluation

An expression tree supplies a concrete reason to process children before the parent. In a binary arithmetic expression, internal nodes may represent operators, while leaves hold numbers. To evaluate an operator node, first evaluate its operand subtrees, then combine the results according to the operator. This is postorder computation, even when no list of nodes is explicitly emitted.

Expression trees are structural representations, not necessarily source-code parsers. A recursive-descent parser constructs or interprets a representation according to grammar rules, while a traversal of an existing syntax tree processes nodes already organized hierarchically. Operator precedence is embodied in the tree shape; evaluation does not need to rediscover precedence from the flat token string.

expr = Node("*", Node("+", Node(2), Node(3)), Node(4))

def evaluate(node):
    if node is None:
        raise ValueError("missing expression")
    if node.left is None and node.right is None:
        if not isinstance(node.value, (int, float)):
            raise TypeError("leaf must be numeric")
        return node.value
    if node.left is None or node.right is None:
        raise ValueError("binary operator needs two children")
    a, b = evaluate(node.left), evaluate(node.right)
    operators = {"+": lambda x, y: x + y,
                 "-": lambda x, y: x - y,
                 "*": lambda x, y: x * y}
    if node.value not in operators:
        raise ValueError("unsupported operator")
    return operators[node.value](a, b)

assert evaluate(expr) == 20
assert postorder(expr) == [2, 3, "+", 4, "*"]

This simple evaluator is deliberately limited to three binary operations and numeric leaves. A production evaluator must also define typing, variable environments, errors, evaluation order, overflow or precision concerns, and any permitted side effects. Those semantics cannot be inferred from traversal order alone.

Tree Maps and Shape-Preserving Transformations

A traversal can build a new tree instead of emitting a sequence. A tree map applies a transformation to each value while preserving the original shape and child arrangement. In a persistent or immutable representation, the map returns fresh nodes; the input remains untouched. This makes correctness easy to state: the new tree has the same position structure, and each new value equals the function applied to the original value at that position.

Even if the mapping function is called before child recursion, constructing the new parent node may occur after its mapped children have been built. Therefore the timing of applying a pure function is conceptually separate from the timing of allocating an immutable output node. For an effectful callback, pre/post ordering could become observably different, and the contract must specify which order is used.

def tree_map(node, fn):
    if node is None:
        return None
    new_value = fn(node.value)       # preorder application
    new_left = tree_map(node.left, fn)
    new_right = tree_map(node.right, fn)
    return Node(new_value, new_left, new_right)

upper = tree_map(root, str.lower)
assert preorder(upper) == ["a", "b", "d", "e", "c", "f"]
assert preorder(root) == ["A", "B", "D", "E", "C", "F"]

For a tree of n nodes, a mapping function that runs in O(1) time yields Θ(n) traversal work, Θ(n) new-node memory, and O(h + 1) recursive stack space. If mapped values are large objects or the callback is expensive, include those extra costs explicitly.

Mirroring, Copying, and Shape Changes

Not every tree transformation preserves child positions. A binary-tree mirror recursively swaps the left and right subtrees of each node. Its new tree has the same number of nodes and the same undirected shape, but each left/right decision is reversed. A mirror applied twice should recover the original ordered shape and values; this is a useful metamorphic test.

A simple deep copy reproduces all nodes in the same positions. For immutable nodes, a copy may be unnecessary unless distinct object identities are required. For mutable nodes, cloning can be essential when callers must edit one version without affecting another. The program must define whether shared child objects, mutable payload values, and external references are copied deeply or retained.

def mirror(node):
    if node is None:
        return None
    return Node(node.value,
                mirror(node.right),
                mirror(node.left))

assert preorder(mirror(root)) == ["A", "C", "F", "B", "E", "D"]
assert mirror(mirror(root)) == root
assert tree_size(mirror(root)) == tree_size(root)

In an ordinary finite tree, both transformations are naturally postorder in the sense that a new parent node is constructed from already transformed child trees. When performing an in-place mirror on a mutable tree, care is needed not to visit a swapped child twice or skip one by changing pointers at the wrong moment.

Pruning and Conditional Traversal

Pruning removes or skips portions of a tree based on a predicate. Two meanings must be kept separate: constructing a new filtered tree and avoiding the exploration of an input subtree. The latter is valid only if the predicate or application domain guarantees that the skipped subtree cannot contain a needed result. Arbitrarily deciding that an unexamined branch is irrelevant is not a sound search strategy.

When filtering a tree structurally, the policy for removing an internal node must be explicit. One policy removes that node and its entire subtree; another promotes children; a third retains the node if any descendant meets the condition. These operations create different trees even when they use the same local predicate. For a simple root-pruning policy, rejecting a node drops all its descendants.

def prune_subtrees(node, keep):
    if node is None or not keep(node.value):
        return None
    return Node(node.value,
                prune_subtrees(node.left, keep),
                prune_subtrees(node.right, keep))

kept = prune_subtrees(root, lambda label: label not in {"C"})
assert preorder(kept) == ["A", "B", "D", "E"]
assert tree_size(kept) == 4

This policy is particularly useful for explicit access-control or category hierarchies when denying a parent implies denying all descendants. It is inappropriate if descendants have independently allowed status. Traversal design must reflect the intended hierarchical semantics rather than assuming every pruning rule is interchangeable.

Searching a Tree and Short-Circuit Evaluation

Tree traversal often supports a predicate search: return whether at least one node meets a condition, or return the first matching node in a defined order. Unlike full enumeration, a search can terminate early. A preorder search checks the current node, then the left subtree, then the right subtree; it need not examine the right side if an earlier match has been found.

A first-match result depends on traversal order. Without a key-order invariant, this is not binary search: both subtrees may need inspection in the worst case. With an appropriate binary search tree, a different algorithm can discard one branch on the basis of key comparisons, reducing work when height is small. The distinction is between enumerative traversal and decision-directed search.

def first_preorder_match(node, predicate):
    if node is None:
        return None
    if predicate(node.value):
        return node
    left_result = first_preorder_match(node.left, predicate)
    if left_result is not None:
        return left_result
    return first_preorder_match(node.right, predicate)

found = first_preorder_match(root, lambda value: value in {"E", "F"})
assert found.value == "E"
assert first_preorder_match(root, lambda x: x == "Z") is None

Search returns a node object rather than a value so that “no match” remains distinguishable from a matching node whose payload might itself be None. The worst-case time remains Θ(n) with O(h + 1) stack space, but successful searches can examine fewer nodes.

Traversing General Rooted Trees

Many useful hierarchies are not binary: directories can have many entries, organizational charts can have many direct reports, and document outlines can contain arbitrarily many subsections. A general rooted tree represents each node by a sequence of children. The preorder rule becomes “visit the parent, then recurse through children in their specified order.” The postorder rule becomes “recurse through all children, then visit the parent.”

An ordinary inorder rule does not generalize uniquely. There is no designated point between a left and a right subtree when a node has zero, one, three, or hundreds of children. Specific data structures may define one, but the convention must be stated before using the term.

@dataclass(frozen=True)
class NaryNode:
    value: Any
    children: tuple = ()

outline = NaryNode("Book", (
    NaryNode("Part I", (NaryNode("Chapter 1"), NaryNode("Chapter 2"))),
    NaryNode("Part II", (NaryNode("Chapter 3"),))))

def nary_preorder(node):
    result = [node.value]
    for child in node.children:
        result.extend(nary_preorder(child))
    return result

def nary_postorder(node):
    result = []
    for child in node.children:
        result.extend(nary_postorder(child))
    result.append(node.value)
    return result

assert nary_preorder(outline) == ["Book", "Part I", "Chapter 1", "Chapter 2",
                                  "Part II", "Chapter 3"]
assert nary_postorder(outline)[-1] == "Book"

For an ordered general tree, all descendants of one child appear contiguously before the next child is entered in a depth-first traversal. That property is useful for exporting nested outlines, flattening hierarchical menus, and computing subtree intervals.

Forests, Multiple Roots, and Virtual Roots

A forest is a collection of separate rooted trees. Traversal can process its roots in a documented order or create a virtual root whose children are the original roots. The virtual-root technique often simplifies algorithms, but it changes observable output unless the synthetic root is excluded from enumeration and aggregations.

A forest may arise from disconnected organizational units, a set of independently parsed syntax trees, or a database table containing several hierarchy roots. If the algorithm assumes exactly one root but the input contains several, silently selecting the first may lose data. Conversely, when a hierarchy is expected to be a single tree, finding multiple roots can indicate malformed parent references.

For each tree, ordinary preorder and postorder work unchanged. A forest-level preorder could concatenate all individual preorder sequences in root order. Its time is Θ(total nodes) with recursion depth governed by the tallest tree; an explicit iteration over roots adds little overhead. Any application-specific interpretation of an empty forest should be specified independently from the empty-subtree rule.

Path Accumulators and Ancestral Context

Some traversal tasks need information from the root-to-current-node path, not only the current subtree. A preorder descent can pass a path, current depth, access-control context, or cumulative weight to each child. This is a different kind of aggregation from postorder folds: the value propagates downward from ancestor to descendant rather than upward from child to parent.

When building paths, repeatedly copying a growing tuple or string at every recursive call can add quadratic total allocation on a long chain. A mutable path list with push/pop operations uses O(h) path storage but must be restored reliably when returning. For pure immutable inputs, a tuple of parent references or a linked path structure is another design option. The correct choice depends on whether the path must be stored permanently at each node.

def root_to_leaf_paths(node, path=()):
    if node is None:
        return []
    current = path + (node.value,)
    if node.left is None and node.right is None:
        return [current]
    return (root_to_leaf_paths(node.left, current)
            + root_to_leaf_paths(node.right, current))

assert root_to_leaf_paths(root) == [
    ("A", "B", "D"), ("A", "B", "E"), ("A", "C", "F")]

This teaching version stores every returned path and repeatedly creates tuples, so its time and output memory depend on total path lengths, not simply node count. On a balanced tree, the sum of all root-to-leaf path lengths can be Θ(n log n); on other tree shapes, bounds differ. Do not apply the simple Θ(n) constant-work-per-node estimate without accounting for path copying.

Generators and Lazy Recursive Traversal

A generator can expose traversal results incrementally with yield and yield from. This avoids constructing an output list when the caller needs only a prefix or wants to stream values to another component. The generator's suspended recursive frames still use memory proportional to the active path; “lazy” refers to output production, not automatic elimination of recursion depth.

Generator order is explicit. A preorder generator yields the current node before yielding its left and right subtrees. An inorder generator yields the left subtree first. If a consumer stops early, the remaining subtrees need not be explored. That can materially reduce work for a first-match query, even though fully exhausting the generator takes Θ(n) traversal steps for constant-work processing.

def preorder_values(node):
    if node is None:
        return
    yield node.value
    yield from preorder_values(node.left)
    yield from preorder_values(node.right)

def inorder_values(node):
    if node is None:
        return
    yield from inorder_values(node.left)
    yield node.value
    yield from inorder_values(node.right)

assert list(preorder_values(root)) == preorder(root)
assert list(inorder_values(root)) == inorder(root)
assert next(preorder_values(root)) == "A"

Generators complicate resource ownership when an unfinished traversal retains references or cleanup obligations. A streaming design should specify whether the underlying tree may be mutated during iteration and whether consumers are permitted to abandon the iterator before exhaustion.

Pure Returns, Shared Accumulators, and State Restoration

Recursive traversals can either return values or update shared state. Pure functions often make subtree correctness proofs simpler because each call depends only on its input and returns a result. Shared accumulators can be more efficient for enumeration, where one list is appended to during the walk. The distinction is not a binary choice: a function can pass a collector explicitly without relying on a hidden global variable.

Default mutable arguments deserve special caution in Python. Writing def walk(node, seen=[]) creates a list that persists across separate top-level calls, causing cross-call contamination. A safe API initializes a new list at the public entry point and passes it into a private recursive helper, or uses None as the default and constructs storage inside the function.

When a path or worklist is modified in place, recursive code must restore state after visiting a branch; otherwise a later sibling may inherit incorrect path elements. For code that may raise exceptions, a try/finally cleanup can make restoration reliable. These concerns become especially important in recursive backtracking, where shared state is deliberately changed and undone for each candidate.

Iterative Preorder with an Explicit Stack

Recursion is not required to realize depth-first order. An explicit last-in-first-out stack can store roots of subtrees that still need processing. To reproduce left-first preorder, pop the current node, visit it, push its right child, then push its left child. The left child is popped next because it was pushed last.

For a binary tree, this design maintains a frontier of pending siblings and has Θ(n) time under constant-time visits. The pending stack can be much smaller than the number of nodes on a balanced tree, although its worst-case requirement is O(h + 1) for this particular binary traversal strategy. For a general tree with many children, pushing them all at once may use Θ(n) pending entries even when tree height is small.

def iterative_preorder(node):
    result = []
    pending = [node] if node is not None else []
    while pending:
        cur = pending.pop()
        result.append(cur.value)
        if cur.right is not None:
            pending.append(cur.right)
        if cur.left is not None:
            pending.append(cur.left)
    return result

assert iterative_preorder(root) == preorder(root)
assert iterative_preorder(None) == []

This program still embodies the recursive order: each popped node corresponds to a call that would have begun at that subtree. The explicit stack makes pending work visible and can avoid a language's function-recursion limit, but it does not make the algorithm memory-free.

Iterative Inorder and Left-Spine Descent

An iterative inorder traversal must defer visiting a node until its left subtree has been processed. The conventional algorithm pushes nodes while walking down the left spine. When no further left child exists, it pops the most recent saved node, visits it, and then begins the same process on the popped node's right subtree.

The stack represents ancestors whose left subtree is being processed and whose own visit or right subtree is still pending. The exact invariant is that each pushed node must eventually be visited once after its left subtree and before its right subtree. The algorithm handles a missing root by never entering its main loop.

def iterative_inorder(node):
    result = []
    pending = []
    cur = node
    while cur is not None or pending:
        while cur is not None:
            pending.append(cur)
            cur = cur.left
        cur = pending.pop()
        result.append(cur.value)
        cur = cur.right
    return result

assert iterative_inorder(root) == inorder(root)
assert iterative_inorder(bst) == inorder(bst)
assert iterative_inorder(None) == []

For a skewed tree, the explicit stack can grow linearly in the number of nodes, just as recursive call frames do. For a balanced tree, its size follows the tree height. The central advantage is control over work scheduling, not a universal asymptotic improvement.

Iterative Postorder and Completion Markers

Postorder is slightly less direct to simulate iteratively because a node must be emitted after both child subtrees. One method uses a stack of pairs (node, expanded). When a node is first encountered, push a marker saying its children must be processed, then push the children in reverse of the desired visit order. When the marker returns to the stack top, both children have been completed and the node can be emitted.

This mirrors recursive control flow, in which a paused call frame retains the instruction position to resume after returning from its children. A second method maintains a previous-visited pointer or uses two stacks, but each has its own invariants. Completion markers are especially readable when translating a postorder algorithm that computes child results before parent work.

def iterative_postorder(node):
    result = []
    pending = [(node, False)] if node is not None else []
    while pending:
        cur, expanded = pending.pop()
        if expanded:
            result.append(cur.value)
        else:
            pending.append((cur, True))
            if cur.right is not None:
                pending.append((cur.right, False))
            if cur.left is not None:
                pending.append((cur.left, False))
    return result

assert iterative_postorder(root) == postorder(root)
assert iterative_postorder(None) == []

The marker method pushes each nonempty node at most twice; it therefore performs Θ(n) operations and uses O(h + 1) pending entries for an ordinary binary tree, subject to constant-factor differences. In a general graph, the same method does not resolve shared-node or cycle handling.

Breadth-First and Level-Order Traversal

Level-order traversal visits the root, then all nodes at depth one, then all nodes at depth two, and so on. Its usual implementation uses a first-in-first-out queue rather than the recursive depth-first call stack. For the sample tree, level order is A, B, C, D, E, F, distinct from all three classical depth-first sequences.

Queue size is controlled by the traversal frontier and can be Θ(n) for a broad tree, while a depth-first traversal's call stack is controlled by height. Breadth-first traversal is therefore often preferred when finding the shallowest matching node in an unweighted tree or processing work layer by layer, but it may require more peak frontier memory.

from collections import deque

def level_order(node):
    if node is None:
        return []
    pending = deque([node])
    result = []
    while pending:
        cur = pending.popleft()
        result.append(cur.value)
        if cur.left is not None:
            pending.append(cur.left)
        if cur.right is not None:
            pending.append(cur.right)
    return result

assert level_order(root) == ["A", "B", "C", "D", "E", "F"]

Recursive level-order algorithms exist, including traversing a tree once for each level, but the naive repeated-height method may do unnecessary work. A queue-based implementation expresses the scheduling rule directly and provides linear-time enumeration under standard assumptions.

Traversal Order Selection Framework

Select traversal order based on the required dependency, not on aesthetic preference. When a node needs inherited information from its parent, preorder is a natural choice. When a binary search tree must be listed in key order, inorder is the standard choice. When a parent result depends on fully computed child results, use postorder. When shallowest-first processing matters, use breadth-first traversal instead of imposing depth-first recursion.

Some tasks intentionally use multiple events. A subtree-interval index may record an entry position in preorder and an exit position after descendants; an interactive outline may render a heading before recursively rendering nested sections; a tree fold may pass an environment down and return a synthesized attribute up. These are mixed strategies, not failures of the three basic categories.

Tree Traversal Versus Graph Depth-First Search

A rooted tree is a special kind of graph, but the computational contract is narrower. In a true tree, each nonroot node has exactly one parent and there is one root-to-node path; recursive child descent does not need a global visited set to avoid cycles or duplicate visits. In an arbitrary graph, back edges can lead to infinite recursion and shared targets can be encountered along several paths. A graph DFS generally requires explicit discovery state, typically keyed by vertex identity.

A directed acyclic graph illustrates a useful intermediate case. A naive recursive descent may terminate because it is acyclic, but a shared descendant can be processed more than once. If each distinct vertex should be visited once, mark it upon discovery and skip previously marked vertices. If the goal is to enumerate all paths rather than all vertices, deduplication may be incorrect because the same vertex can validly appear in several paths.

There is no universal answer to “should this traversal use a visited set?” The choice depends on data-structure guarantees and the intended unit of work: node identity, occurrence in a tree-shaped expansion, or distinct path. Shared Subtrees, Cycles, and Parent Pointers

Real object models may provide both downward child links and upward parent links. Traversing all references indiscriminately can repeatedly return to the parent and never finish. A tree traversal should use the designated downward relation; a parent link is metadata, not another child. A schema or explicit direction convention is therefore part of the traversal contract.

Shared subtrees create a different ambiguity. Suppose two parents reference the exact same child object. A naive recursive preorder emits that child twice: once along each incoming path. This may be correct when modeling occurrences in an expanded tree but incorrect when counting unique allocated nodes. Detecting shared objects with an identity set can change the program from an occurrence traversal to a distinct-node traversal.

For untrusted or malformed input, an explicit validation pass can detect cycles, duplicate parent relationships, inaccessible nodes, and broken references. One must choose whether to reject malformed hierarchies, normalize them, or use graph traversal semantics. A global visited set prevents some loops but can conceal an invalid hierarchy; it should not be presented as a complete data-integrity solution.

Depth Limits and Stack-Safe Design

A mathematically correct traversal may still fail in a finite execution environment if the tree is deeper than the language runtime can support. Python exposes an interpreter recursion limit through sys.getrecursionlimit(); increasing the limit is not a universal repair and can jeopardize interpreter stability, depending on available stack and implementation. Production systems should enforce safe input depth where appropriate or use iterative worklists for potentially very deep trees.

An explicit stack does not remove the need for resource governance: a huge number of nodes can still consume substantial time, and a general-tree frontier may be very broad. Consider node-count limits, traversal deadlines, cancellation, access-control boundaries, and input validation in systems processing user-provided trees. When traversing a serialized structure, limits on parser nesting, payload size, and depth can also apply.

Other runtimes have different recursion and optimization properties. Tail-call optimization cannot generally save a conventional recursive preorder or postorder traversal because outstanding sibling subtrees or parent operations remain after a child returns. A production design should rely on documented guarantees of the specific language and implementation rather than assuming that syntactically recursive calls will be optimized away.

Mutation During Traversal and Snapshot Semantics

Traversing a mutable tree while changing child links can alter which nodes are reached, cause repeats, or create cycles. Even a simple callback that removes or reorders children can invalidate assumptions about the next child. A robust interface should state whether the traversal examines a fixed snapshot, holds a lock, copies the structure, tolerates controlled modifications, or forbids mutation during iteration.

In a concurrent application, readers and writers can race on pointer updates. The resulting symptoms may range from inconsistent output to accessing invalid memory in unmanaged environments. Persistent immutable trees make read-only traversal simpler by providing stable nodes across updates, although application-level versioning and memory-management choices still matter. For mutable structures, a version counter may detect some concurrent modifications, but detection alone is not a synchronization protocol.

Traversal visitors may also have external side effects such as sending messages, writing files, or modifying a database. Exception handling and retry policy matter because restarting a traversal can duplicate already performed actions. An idempotent operation, a transaction boundary, or an explicit progress checkpoint may be required. A mathematically exact visit-once argument about nodes does not automatically imply exactly-once external effects.

Typical Defects and Their Repairs

Tree traversal bugs often originate in mismatched contracts rather than exotic algorithms. A missing base case may dereference an absent child; a wrong visit placement produces the wrong sequence; an incorrect child order reverses expected output; and a shared mutable accumulator may leak values between independent calls. A cycle can destroy termination, while repeated list concatenation can turn a conceptually linear walk into a slow implementation.

To debug, write down the structural premise and manually trace a tree containing both left-only and right-only branches. Check how the algorithm behaves for an empty tree, a single leaf, a chain, a balanced tree, duplicate payload values, and a malformed cyclic object when input validation is part of the contract. Verify identity behavior separately from value equality.

Testing Traversal Invariants and Metamorphic Properties

Testing should verify structural properties, not just one memorized example. For a finite well-formed tree, all three depth-first traversals must report n nodes, and if values are unique their sets must match. With duplicate payloads, compare frequency counts or actual node identities rather than sets of values. A postorder fold's size must equal the number of emitted nodes.

Metamorphic tests help because they state relationships that should hold for many inputs. Mirroring twice should reproduce the original ordered tree. A shape-preserving map should not change the node count or height. Recursive and iterative versions of the same order must emit identical sequences. A valid binary search tree's inorder output must be sorted. Depth/height conventions must be tested on empty and singleton trees.

Randomly generated small trees are useful for stressing uneven shapes and missing children, but generation must obey the assumed tree structure. If malformed graphs are in scope, create separate tests for cycles, shared nodes, and parent references. Never treat a test suite over valid trees as proof that the algorithm is safe on arbitrary object graphs.

Executable Cross-Checks on Small Tree Shapes

A small exhaustive family of trees can validate the recursive/iterative agreement and basic structural invariants. The following deterministic generation pattern creates different binary shapes while assigning unique payloads, then compares the traversal methods on all constructed cases. These checks increase confidence in implementation details such as stack-push order and base cases; they do not replace a correctness proof for every possible tree.

def make_chain(n, direction="left"):
    cur = None
    for value in range(n - 1, -1, -1):
        cur = Node(value, cur, None) if direction == "left" else Node(value, None, cur)
    return cur

for n in range(0, 25):
    for direction in ("left", "right"):
        t = make_chain(n, direction)
        assert iterative_preorder(t) == preorder(t)
        assert iterative_inorder(t) == inorder(t)
        assert iterative_postorder(t) == postorder(t)
        assert len(preorder(t)) == tree_size(t) == n
        assert len(inorder(t)) == len(postorder(t)) == n
        assert mirror(mirror(t)) == t

assert tree_height_edges(make_chain(7)) == 6

Chains are especially good at detecting incorrect depth assumptions, but they cannot cover every branching pattern. Supplement them with balanced and irregular trees and, in a production library, automated generative tests that build random child configurations and compare to a simple independent reference procedure.

Applied Scenario I: Rendering a Hierarchical Outline

Suppose a publication platform stores a volume with parts, chapters, and sections as a rooted ordered tree. Rendering an outline naturally uses preorder: emit each heading, then recursively emit its nested children. A downward accumulator carries the depth and section-number prefix, allowing a chapter to be labeled from its ancestor position. Preserving child order is essential because editorial ordering is part of the content.

The output representation determines complexity. If the renderer appends each markup fragment to a builder or stream, visiting each node once normally gives linear traversal overhead plus the cost of formatting and writing content. If it repeatedly concatenates the entire accumulated HTML string, output copying can dominate. If some nodes are hidden by policy, define whether hidden parents cause whole subtrees to be omitted or whether visible descendants may be promoted.

A correct design distinguishes structural title order from access-control enforcement. The traversal may skip unauthorized subtrees, but security must not depend solely on hiding links in the rendered outline. The underlying request handlers must enforce the same permissions independently.

Applied Scenario II: Calculating Directory-Like Subtree Totals

Imagine a tree representing nested folders where file sizes are stored at leaves and folders derive aggregate totals from their contents. The natural calculation is postorder: compute each child's total first, then return the parent's total. If the structure is a general ordered tree, the parent combines results from all children rather than assuming two positions.

Care is needed when real file systems expose symbolic links, hard links, mount points, or directory references. A naive recursive directory walker may follow cycles through links or count the same physical object more than once. That environment is not always a strict tree. A real implementation needs a documented link-following policy, filesystem permissions, I/O error handling, and potentially identity-based deduplication.

Also distinguish the mathematical count of nodes from observed storage usage. Sparse files, compression, allocation units, and linked files can make logical file sizes differ from physical storage occupancy. Tree traversal determines how entries are reached and combined; it does not alone define the accounting semantics.

Applied Scenario III: Evaluating a Nested Formula

Consider an arithmetic expression represented as a tree. A node for multiplication must receive values produced by its child expressions before it can compute its own result. A postorder recursive evaluator matches that dependency. For the expression (2 + 3) × 4, the tree first evaluates the addition subtree, separately obtains the literal four, and finally multiplies the two results.

In a formula engine, some operators short-circuit: a logical AND may not evaluate its right subtree once the left is false. Such evaluation is not a full postorder visit of every node. Similarly, conditional expressions may select only one branch. The evaluator's semantics—not a blanket “always visit both children” template—must govern which recursive calls occur.

A scalable evaluator also handles variable lookup, types, overflow, division errors, untrusted operators, and recursion limits. The tree shape supplies grouping and precedence; it does not replace a language's semantic rules. If expression nodes are shared in a directed acyclic graph, caching repeated subexpressions may change performance but requires care when expressions have side effects or environment-dependent values.

Applied Scenario IV: Transforming and Exporting Syntax Trees

A compiler or document processor may traverse an abstract syntax tree to rename variables, substitute expressions, validate declarations, or generate serialized output. Some passes work top-down because scope and environment information flow from parent constructs to descendants. Others work bottom-up because a parent transformation depends on already rewritten child expressions. Choosing the wrong direction can produce stale or inconsistent assumptions.

A structure-preserving map is appropriate when only payloads change; a rewrite that inserts, removes, or duplicates subtrees needs a more explicit contract. Newly constructed nodes might themselves require transformation. A single-pass algorithm must specify whether rewrites apply only to nodes present in the original tree or also to nodes created during the pass. Without this distinction, repeatedly rewriting newly generated shapes can lead to unexpected expansion or nontermination.

Compilation environments often include parent links, cross-references, and symbol tables. Traversing every reference is not equivalent to descending the syntax-tree ownership relation. Treat cross-references as separate graph edges with their own search and validation policy.

Applied Scenario V: Defensive Traversal of User-Defined Hierarchies

A service accepts an imported hierarchical configuration with potentially millions of nodes or deeply nested entries. A naive recursive implementation may be logically correct on valid input yet exceed runtime stack limits or spend disproportionate resources on adversarial structures. A defensive design validates the node model, enforces size and depth budgets, and chooses an explicit-stack or streaming traversal where the worst-case height is not controlled.

Validation should distinguish a cycle from a shared subtree, and both from two nodes that happen to have equal values. When serializing the structure, bound the output size as well as traversal time. If a callback performs remote operations, rate limiting and cancellation may be required. If traversal is interrupted, document whether partial results are valid and how a subsequent attempt resumes.

Resource budgets are application-specific. No fixed recursion depth or node count is universally safe across programming languages, machines, and deployments. The guiding principle is to make those limits explicit and to avoid relying on undocumented compiler or runtime optimizations.

A Practical Design and Investigation Procedure

Before implementing a recursive tree traversal, identify the tree type and the intended output. Determine whether children are ordered, whether the input is guaranteed acyclic and unshared, and whether output needs to be returned, streamed, or applied as a side effect. Then choose the event at which each piece of work belongs. Preorder answers “what is known before children?”; postorder answers “what is known after children?”; inorder requires binary left/right semantics.

Write an empty-tree base case appropriate to the operation, state the induction hypothesis for a child subtree, and explain how child results yield the parent result. Trace a tree with asymmetrical left and right branches. Calculate time as per-node work plus the cost of output construction; calculate space from both stack depth and stored results.

Finally, address engineering requirements: may nodes mutate, can input be malformed, is the tree extremely deep, and do callbacks have side effects? These questions determine whether a clean recursive implementation is sufficient or whether explicit worklists, validation, and cancellation controls are necessary. Correctness is an end-to-end contract, not only the absence of a syntax error.

Review Questions and Exercises

  1. Define a binary tree and explain why an empty child is not the same as a leaf node.
  2. For the six-node sample tree, write the exact preorder, inorder, and postorder sequences.
  3. Explain why inorder traversal of an arbitrary binary tree does not necessarily produce sorted values.
  4. Prove by structural induction that an ordinary traversal visits each distinct node exactly once in a valid tree.
  5. State a decreasing measure that establishes termination and identify a malformed structure that violates the premise.
  6. Describe how a recursive height computation differs from the definition of height measured in nodes rather than edges.
  7. Compute the time and auxiliary stack bounds for balanced and skewed trees, distinguishing result storage.
  8. Give a postorder function that returns subtree size and height together without duplicate traversals.
  9. Explain why a preorder explicit stack pushes the right child before the left child when left-first output is desired.
  10. Construct an example of shared-child references for which a naive traversal counts one object twice.
  11. Explain the difference between a preorder generator and a function that returns a full preorder list.
  12. Choose an order for parent-derived path labels, child-derived totals, and shallowest-node discovery; justify each.
  13. Identify one way mutable visitor state can corrupt results and show how the design should be changed.
  14. Explain why an explicit iterative stack avoids recursive call depth without guaranteeing constant space.
  15. For a user-supplied hierarchy, list three validation or resource-control measures needed before deployment.

Exercises should be solved using small drawn trees before attempting large programs. Where there is a convention choice—such as height of an empty tree—state the convention and use it consistently. Performance answers must declare whether they include output storage and whether the visitor performs constant work.

Review Answers and Reasoning

  1. A binary tree has distinguished left and right child positions. An empty position contains no node; a leaf is a real node with both positions empty.
  2. Preorder: A, B, D, E, C, F. Inorder: D, B, E, A, C, F. Postorder: D, E, B, F, C, A.
  3. Sorted inorder output requires a binary-search-tree key-order invariant, not merely binary shape.
  4. The empty subtree has no nodes. For a nonempty node, one root visit plus the disjoint, correctly traversed child subtrees covers every node once.
  5. The size of the remaining subtree decreases for proper children. A child link back to an ancestor can invalidate this descent.
  6. For edge height, empty = −1 and leaf = 0. For node-count height, empty = 0 and leaf = 1; the nonempty recurrence is one plus maximum child height under either convention.
  7. Constant-work full traversal is Θ(n) time; stack space is O(h + 1), hence O(log n) for balanced trees and O(n) for chains. A full output list is Θ(n) space.
  8. Return (1 + left_size + right_size, 1 + max(left_height, right_height)) from each call after evaluating its children; the empty result is (0, -1).
  9. Because the stack is last-in-first-out, pushing right first leaves left on top for next processing.
  10. Let both the left and right child pointers of the root reference the same leaf object. A naive traversal reports the leaf twice.
  11. The generator yields values incrementally and can stop early, but suspended recursive frames still occupy stack space.
  12. Path labels: preorder with downward context. Subtree totals: postorder fold. Shallowest discovery: breadth-first search.
  13. A mutable default result list persists across calls. Initialize a fresh collector at each public invocation, or pass an explicit collection.
  14. The explicit stack stores pending nodes in program-managed memory; a wide or deep workload still needs storage for outstanding work.
  15. Validate cycles/shared nodes and child relations; bound node count and depth; enforce cancellation or execution budgets. Exact thresholds are deployment-specific.

These answers describe the standard finite-tree model. For graph-like data, different visited-state and path-enumeration contracts may produce different correct algorithms.
