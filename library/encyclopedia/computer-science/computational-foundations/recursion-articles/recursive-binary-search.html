Definition, Purpose, and Scope

Recursive binary search finds a value or a boundary in an ordered search space by examining a middle position and then searching at most one of the remaining subintervals. Each recursive step uses the ordering property to discard a region that cannot contain the requested answer. This reduction produces logarithmic search depth when candidate intervals shrink by a constant fraction.

The essential requirement is not recursion but a valid decision invariant: after each comparison, the part of the input that remains must still contain every acceptable answer. A conventional exact-match search over a sorted, indexable sequence may return any matching position. A lower-bound search instead returns the first position where an element is not less than the target; this works even when the target is absent and gives deterministic duplicate behavior. These are related but distinct functions.

This is specialist article 9 of 15 in the Recursion unit of the MGU Computer Science Encyclopedia. It extends the Recursion overview, builds on Recursion and Mathematical Induction and Recursion Trees and Divide and Conquer, and prepares the reader to distinguish recursive search of sorted intervals from Recursive Depth-First Search or Backtracking and Recursive Search.

Core design principle: define the candidate interval precisely, state the ordering assumption, give the stopping condition, and prove that every recursive call strictly reduces the interval while preserving the desired result.

The Search Contract Comes Before the Code

Before writing a midpoint expression, define what the procedure promises to return. An exact-match function can return an index or a not-found sentinel; a first-occurrence function must select the smallest matching index; a lower-bound function returns an insertion position whether or not the target is present. These contracts differ on duplicate-rich input, empty input, and unsuccessful searches.

Define the input ordering: for a conventional ascending list, values appear in nondecreasing order, so duplicates are permitted. Assume the comparator defines an appropriate consistent ordering for the data. Comparisons of mixed incompatible types or values such as NaN can violate the premises. Changes to the list during search also invalidate a correctness argument based on a fixed array.

For this unit, examples use a Python sequence supporting constant-time indexed access and a stable, ascending ordering. In implementations that use expensive indexing, the same comparison count does not necessarily imply the same runtime.

Ordered Search Spaces and Precondition Discipline

Classical binary search depends on an ordered or partitioned candidate space. In a nondecreasing sequence, all elements smaller than the target precede all elements at least as large as the target. An arbitrary unsorted sequence lacks this property: examining its center does not license discarding either side. Binary search does not sort the data or discover disorder automatically.

For insertion-point search, the weaker mathematical premise is that a predicate, such as a[i] < x, partitions the positions into one run where it is true and a later run where it is false. Global sorting is a convenient way to establish this property for every possible target, but a single call can be valid on a merely partitioned range.

For exact-match search, it must be safe to infer from a[mid] < x that the desired value cannot occur at or before mid, and from a[mid] > x that it cannot occur at or after mid. This is an ordering argument, not a property of recursive syntax. Explicitly validate or document the precondition at the system boundary rather than sorting inside each search call, which would change the operation's cost and semantics.

Why the Middle Comparison Eliminates Half the Candidates

Let the current candidates occupy index positions lo through hi - 1, with the interval written [lo, hi). Choose a midpoint mid between them. If the middle value equals the target, an exact-match search succeeds. If the middle value is smaller than the target, nondecreasing order shows that every earlier value is also too small; the only possible matches are in [mid + 1, hi). If it is larger, any match must lie in [lo, mid).

This is a genuine elimination, not a guess based on probability. A failed comparison rules out an entire group of positions under the sorted-input assumption. The interval length is reduced to at most about half its previous size, with a small rounding difference. Consequently, a search of one million elements requires only about twenty midpoint decisions rather than inspecting every element.

The recursive version has one active child along each path, so its recursion tree is a chain. It has no second child whose answer must be combined. That makes binary search a particularly clear example of generative recursion and a useful foundation for boundary-search algorithms.

Choosing One Interval Convention

Two common conventions represent the active candidate range differently. An inclusive interval [lo, hi] contains both endpoints, and the empty-range test is lo > hi. A half-open interval [lo, hi) includes lo but excludes hi, and the empty test is lo == hi after preserving lo <= hi. Both conventions can be correct.

Half-open intervals align with Python slicing and represent empty sequences naturally. They also allow a single position n to represent insertion after the final element. This article uses half-open intervals as its primary convention, and includes a separate fully inclusive implementation to explain the differences.

Rule: choose one convention for each function, state it near the function contract, and never import an update rule from a different convention without reconsidering the base case.

A Correct Recursive Exact-Match Implementation

The first implementation returns the index of one occurrence, or -1 when the target is absent. Its recursive helper accepts a half-open interval; the top-level function starts at [0, len(a)). At every midpoint, equality ends the search immediately and an unequal comparison chooses exactly one smaller interval.

def recursive_binary_search(a, target):
    """Return one matching index, or -1; a is sorted ascending."""
    def search(lo, hi):  # candidates are indices in [lo, hi)
        if lo == hi:
            return -1
        mid = lo + (hi - lo) // 2
        if a[mid] == target:
            return mid
        if a[mid] < target:
            return search(mid + 1, hi)
        return search(lo, mid)
    return search(0, len(a))

sample = [2, 4, 7, 9, 9, 11, 15, 20, 27, 31, 40]
assert recursive_binary_search(sample, 15) == 6
assert recursive_binary_search(sample, 8) == -1
assert recursive_binary_search([], 12) == -1
assert sample[recursive_binary_search(sample, 9)] == 9

The helper's value is returned directly. There is no work after the recursive call except delivering the return value, so the recursive call occurs in tail position within this implementation. However, Python does not guarantee tail-call elimination, and one active Python frame may remain for each recursive step. The algorithm remains practical on ordinarily sized in-memory arrays because its depth grows logarithmically.

The initial interval can be empty. The code tests the base case before indexing, so it does not try to access a midpoint of an empty sequence. A function that checks the midpoint first can fail on empty input even if it handles ordinary successful searches.

Worked Trace: Finding a Present Target

Consider the ordered sequence [2, 4, 7, 9, 9, 11, 15, 20, 27, 31, 40] and target 15. The search begins with 11 candidate positions and chooses index 5, whose value is 11. Since 11 is less than 15, indexes 0–5 are excluded. The next interval has indexes 6–10. Its midpoint 8 contains 27, so positions 8–10 are excluded. The process continues until index 6 holds 15.

Now search for 8 in the same sequence. The first midpoint is 11, so the remaining range is [0, 5). Its midpoint is 7, leaving [3, 5). The midpoint is 9, leaving [3, 3). This empty interval proves that there are no matching candidates.

An Inclusive-Endpoint Version for Comparison

Inclusive indexing is equally valid when all conditions are adjusted consistently. In the code below, the initial upper index is len(a) - 1. After testing a midpoint, the left branch ends at mid - 1; the right branch begins at mid + 1. The base case occurs when the lower index has moved beyond the upper index.

def binary_search_inclusive(a, target):
    def search(lo, hi):  # candidates in inclusive range [lo, hi]
        if lo > hi:
            return -1
        mid = lo + (hi - lo) // 2
        if a[mid] == target:
            return mid
        if a[mid] < target:
            return search(mid + 1, hi)
        return search(lo, mid - 1)
    return search(0, len(a) - 1)

for target in [-2, 2, 9, 11, 40, 41]:
    pos = binary_search_inclusive(sample, target)
    assert (pos == -1) == (target not in sample)
    if pos != -1:
        assert sample[pos] == target

Mixing these styles creates classic defects: using hi = mid with an inclusive interval can leave a one-element interval unchanged, while using hi = mid - 1 to implement a lower bound may discard a boundary candidate that must remain in the range.

Midpoint Arithmetic and Integer Safety

For nonnegative valid array positions, the mathematical midpoint can be written (lo + hi) // 2. A safer conventional spelling in fixed-width signed-integer languages is lo + (hi - lo) // 2, which avoids overflowing the sum of two individually valid nonnegative positions. This does not make every possible arithmetic operation safe; it assumes hi - lo itself is valid and is typically applied within the bounds of an allocated sequence.

Python integers do not overflow in this manner, but retaining the second form emphasizes a portable design habit. In languages with explicit indexing types, correct conversions and boundary checks remain necessary. The midpoint is always strictly smaller than hi when lo < hi, so it addresses a valid candidate. With lo <= mid < hi, either mid + 1 or mid yields a strictly smaller interval under the appropriate comparison branch.

For an inclusive interval where lo == hi, the midpoint equals both endpoints. On an unsuccessful comparison, adjusting the chosen boundary by one is therefore essential for progress. Arithmetic safety and termination safety are separate obligations.

The Candidate-Containment Invariant

The central correctness invariant for an exact-match search is: if a matching element exists and the search has not yet returned, some matching position is in the current interval. This statement refers to the possibility of a match, not to the presence of every duplicate. It is initialized when the full array is the candidate interval.

To prove preservation, suppose a[mid] < target. In nondecreasing order, for every i <= mid, a[i] <= a[mid] < target, so none can match. Retaining [mid + 1, hi) preserves every possible matching location. The symmetric argument holds when the midpoint is greater. Equality succeeds directly.

At the base case lo == hi, the interval has no positions. The invariant implies that no matching position remains in the original array; returning -1 is therefore correct. This is a proof of partial correctness. To prove total correctness, a second argument must establish that recursion terminates.

Termination Proof Using Interval Length

Define the nonnegative integer rank r = hi - lo for the half-open interval. A base case is reached when r = 0. If r > 0, the midpoint is a valid integer within the interval. A rightward step replaces the interval by [mid + 1, hi), whose length is hi - mid - 1 < r; a leftward step replaces it by [lo, mid), whose length is mid - lo < r.

Thus every recursive call strictly decreases a nonnegative integer. There is no infinite descending sequence of such integers, so the procedure must terminate. The proof does not depend on a particular target being present. It also shows why a nondecreasing interval-update bug is dangerous: if the rank fails to decrease, reaching a base case is no longer guaranteed.

Correctness and termination fit together as an induction on interval length. The empty interval is correctly reported unsuccessful. For any positive length, a midpoint either provides an answer or leaves a smaller interval preserving the search invariant; the inductive hypothesis then applies.

Cost Recurrence and Logarithmic Search Time

Each non-base call performs a constant number of index operations and comparisons under the RAM model, then recurses into one interval of at most about half the former size. A simplified worst-case recurrence is T(n) = T(floor(n/2)) + Θ(1) for n > 1, with T(0) and T(1) constant. Repeated halving gives T(n) = Θ(log n) for growing n.

This bound counts comparisons or constant-cost operations for indexed access. It does not include sorting the input, fetching remote storage pages, repeated data copying by slicing, comparator costs that grow with key size, or dynamic collection updates. Those costs can dominate in real systems even when the number of candidate positions halves each step.

For n at least one, an unsuccessful exact-match search performs at most roughly floor(log2(n)) + 1 midpoint probes, and may execute one additional empty-range base-case call. For example, a million-element array needs at most about twenty midpoint inspections. The exact count depends on interval rounding, target position, and the decision contract.

Recursion Depth and Auxiliary Space

At most one recursive child is active from each invocation, so the call stack follows a single path. The active frame count for a successful or unsuccessful search is O(log n) with ordinary stack-based procedure calls. The interval indices and the target itself require constant storage per frame; no full copy of the candidate array is needed when only index boundaries are passed.

By comparison, an iterative binary search can update lo and hi within a single activation and use O(1) additional control storage. A language or compiler may optimize a tail-position recursive search into a constant-stack loop, but this cannot be assumed across environments. In Python, recursion depth remains a real runtime constraint, although logarithmic depth makes it modest for realistic in-memory arrays.

Always specify what is counted as auxiliary space. If an implementation forms a fresh slice on each recursive call, copied data may add memory and time costs that are absent from the index-only version. If search decisions retrieve blocks from storage or over a network, I/O and caching behavior may matter more than stack usage.

A Practical Iterative Equivalent

A conventional while loop expresses the same interval invariant without adding a new call frame per reduction. It is often the default in production libraries because it is compact, economical, and does not depend on tail-call optimization. The loop condition lo < hi corresponds to the recursive base case lo == hi.

def binary_search_iterative(a, target):
    lo, hi = 0, len(a)
    while lo < hi:
        mid = lo + (hi - lo) // 2
        if a[mid] == target:
            return mid
        if a[mid] < target:
            lo = mid + 1
        else:
            hi = mid
    return -1

for x in [-4, 2, 4, 7, 9, 15, 40, 42]:
    r = binary_search_iterative(sample, x)
    assert (r != -1) == (x in sample)
    if r >= 0:
        assert sample[r] == x

The recursive and iterative versions are semantically equivalent under this exact-match contract even when they choose different matching indices among duplicates. Their key difference is the mechanism for maintaining pending state: recursive call frames versus loop variables. Neither style excuses incorrect boundary updates.

Duplicate Keys Change the Search Contract

When a sorted array contains repeated target values, ordinary exact-match binary search can return any one of them. The result is valid for membership testing, but not for finding the first record in a duplicate group, determining a span, or providing a stable insertion position. These requirements demand a boundary-oriented variant.

Consider the array [1, 3, 3, 3, 7, 9]. Every index from 1 through 3 satisfies an exact-match query for 3. The lower bound is index 1; the upper bound is index 4; the number of occurrences is 4 - 1 = 3. The leftmost and rightmost exact-match positions are 1 and 3 respectively.

Do not assume the first match returned by a midpoint search is leftmost, even if a particular trace happened to select it. Stable behavior requires that the invariant target a boundary rather than terminating at the first equality.

Recursive Lower Bound: First Value Not Less Than the Target

The lower bound of a target is the smallest index i for which a[i] >= target, or len(a) if no such position exists. Its invariant partitions the sequence into positions known to be smaller than the target, positions known to be at least the target, and the still undecided interval between them.

At each step, if a[mid] < target, the boundary must lie strictly to the right, so recursion chooses [mid + 1, hi). Otherwise the midpoint might itself be the first qualifying position, so the algorithm keeps it and chooses [lo, mid). At the empty interval, the unique insertion boundary is lo.

def recursive_lower_bound(a, target):
    """First index i with a[i] >= target, or len(a)."""
    def search(lo, hi):
        if lo == hi:
            return lo
        mid = lo + (hi - lo) // 2
        if a[mid] < target:
            return search(mid + 1, hi)
        return search(lo, mid)
    return search(0, len(a))

values = [1, 3, 3, 3, 7, 9]
assert recursive_lower_bound(values, 3) == 1
assert recursive_lower_bound(values, 4) == 4
assert recursive_lower_bound(values, 0) == 0
assert recursive_lower_bound(values, 10) == len(values)
assert recursive_lower_bound([], 10) == 0

This is a boundary-finding algorithm, not an exact-match algorithm. Returning index 4 for target 4 in the example says where 4 would be inserted, not that the element already exists. The absence or presence of an exact match can be determined with a separate boundary check.

Recursive Upper Bound: First Value Greater Than the Target

The upper bound is the smallest index where the array value is strictly greater than the target, or the length of the array if there is none. It uses the same half-open interval machinery but places equal values on the side that has already been passed: if a[mid] <= target, search to the right.

def recursive_upper_bound(a, target):
    """First index i with a[i] > target, or len(a)."""
    def search(lo, hi):
        if lo == hi:
            return lo
        mid = lo + (hi - lo) // 2
        if a[mid] <= target:
            return search(mid + 1, hi)
        return search(lo, mid)
    return search(0, len(a))

assert recursive_upper_bound(values, 3) == 4
assert recursive_upper_bound(values, 4) == 4
assert recursive_upper_bound(values, 9) == 6
assert recursive_upper_bound(values, 0) == 0

The lower and upper bounds define a half-open span [left, right) of all occurrences of the target in a normally ordered array. The difference right - left is its frequency. Both algorithms take logarithmically many midpoint comparisons, assuming constant-time indexed access.

Computing the Leftmost Match, Rightmost Match, and Count

Boundary-search primitives should carry the responsibility for duplicate positioning rather than duplicating tricky search logic. Find the lower bound, verify that the position is within the array and actually equals the target, and return the index. The rightmost match is the upper bound minus one after verifying that position holds the target. The occurrence count is the upper bound minus the lower bound.

def first_index(a, target):
    i = recursive_lower_bound(a, target)
    return i if i < len(a) and a[i] == target else -1

def last_index(a, target):
    i = recursive_upper_bound(a, target) - 1
    return i if i >= 0 and a[i] == target else -1

def count_equal(a, target):
    return recursive_upper_bound(a, target) - recursive_lower_bound(a, target)

assert (first_index(values, 3), last_index(values, 3), count_equal(values, 3)) == (1, 3, 3)
assert (first_index(values, 4), last_index(values, 4), count_equal(values, 4)) == (-1, -1, 0)
assert (first_index([], 4), last_index([], 4), count_equal([], 4)) == (-1, -1, 0)

Two separate binary searches still take O(log n) time: multiplying the logarithmic bound by a constant factor does not change its asymptotic class. With custom equality and ordering rules, ensure that comparisons are mutually consistent or the boundary position may not identify a true equal-key record.

Worked Boundary Trace: Duplicates and Insertion Points

Find the lower bound of 3 in [1, 3, 3, 3, 7, 9]. Starting from [0, 6), the midpoint index is 3 and the value equals 3. Equality does not end a lower-bound search: index 3 might have equal predecessors. Therefore the interval becomes [0, 3). The next midpoint index is 1, also equal, so the interval becomes [0, 1). Index 0 holds 1, below the target, so the interval becomes [1, 1) and returns 1.

Boundary Searches as Monotone Predicate Searches

Binary search can be generalized from comparing keys to finding a transition in a monotone Boolean predicate. Suppose a predicate is false for an initial run of integer positions and true for every subsequent position. The objective is to find the first true index. The candidate invariant states that the transition lies in a maintained half-open interval of boundary positions.

For an array-based form, inspect an index between lo and hi. If the predicate is true, the transition occurs at or before that index, so keep the left portion; if false, it must occur after, so keep the right portion. When all positions are false, the answer is n, the index one past the end. When all are true, the answer is zero.

def recursive_first_true(n, predicate):
    """First i in [0, n) with predicate(i), or n.

    Precondition: predicate is false, then true (monotone).
    """
    def search(lo, hi):
        if lo == hi:
            return lo
        mid = lo + (hi - lo) // 2
        if predicate(mid):
            return search(lo, mid)
        return search(mid + 1, hi)
    return search(0, n)

flags = [False, False, False, True, True, True]
assert recursive_first_true(len(flags), lambda i: flags[i]) == 3
assert recursive_first_true(4, lambda i: False) == 4
assert recursive_first_true(4, lambda i: True) == 0
assert recursive_first_true(0, lambda i: True) == 0

A predicate that alternates between true and false violates the premise; no midpoint rule can reliably discard half the positions in that case. A noisy measurement, a changing external service, or a nondeterministic comparator also requires a different design or a stable snapshot.

Binary Search on the Answer Instead of in a Stored Array

Many optimization problems can be transformed into a monotone feasibility decision. Rather than searching a preexisting array of answers, choose a candidate answer x and ask whether a valid solution exists with a value at most x. If feasibility is false below some threshold and true at or above it, the smallest feasible value is a first-true boundary.

For example, suppose several jobs have positive integer workloads and one worker can complete at most capacity units per day. If work can be split under stated rules, a feasibility test may compute the number of days needed for a proposed capacity. Higher capacity cannot make the requirement less feasible. The outer binary search probes capacity; the inner feasibility function evaluates the actual application constraints.

Correctness requires two separate proofs: the predicate must represent the real problem, and it must be monotone in the searched parameter. Search by itself cannot rescue a feasibility model that ignores constraints such as task indivisibility, worker availability, or precedence. The cost is O(log R) predicate evaluations for a discrete search range of width R, multiplied by the cost of each predicate evaluation.

Worked Application: Minimum Feasible Capacity

Suppose ordered shipments of positive weights must be placed on consecutive days, with each day's load no more than a shared capacity. Shipments cannot be split or reordered. Given a maximum number of days, find the smallest integer capacity that permits all shipments to be dispatched. Feasibility is monotone: if a capacity works, every larger capacity also works.

def minimum_shipping_capacity(weights, days):
    if not weights or days < 1 or any(w <= 0 for w in weights):
        raise ValueError("Require positive weights, nonempty input, days >= 1")

    def feasible(capacity):
        used_days, load = 1, 0
        for weight in weights:
            if weight > capacity:
                return False
            if load + weight > capacity:
                used_days += 1
                load = 0
            load += weight
        return used_days <= days

    lo, hi = max(weights), sum(weights) + 1  # hi is exclusive
    # Use the first-true boundary over [lo, hi).
    return recursive_first_true(hi - lo, lambda i: feasible(lo + i)) + lo

assert minimum_shipping_capacity([3, 2, 2, 4, 1, 4], 3) == 6
assert minimum_shipping_capacity([5], 1) == 5
assert minimum_shipping_capacity([1, 2, 3], 1) == 6
assert minimum_shipping_capacity([1, 2, 3], 3) == 3

The implementation delegates the threshold search to the previously established recursive_first_true primitive. The interval starts at the maximum shipment weight, since no smaller capacity can contain the heaviest item, and ends just beyond the total weight, which is always sufficient. Reusing one proven first-true primitive reduces duplicated boundary logic and is simpler to review.

Integer Domains, Threshold Bounds, and Safe Sentinels

When searching an integer parameter, define whether endpoints denote candidate values, exclusive boundaries, or guaranteed feasible and infeasible sentinels. The smallest feasible candidate belongs to the domain only if the feasibility predicate holds there. If the answer might not exist, a sentinel beyond the tested range must be handled explicitly.

One robust pattern searches [lower, upper + 1) and returns upper + 1 when all candidate values are false. Another maintains a known-false left sentinel and a known-true right sentinel and terminates when no unknown integer lies between them. Both can be correct, but their update formulas differ. An incorrect sentinel choice can silently exclude the true answer before the search begins.

The mathematical search domain can be huge even when no array of that size is allocated. A recursive first-true function that operates only on integer boundaries can isolate a threshold among trillions of possible values in a few dozen steps, provided the predicate is inexpensive and deterministic.

What Changes When the Data Are Descending?

A search over descending data is possible, but the ordering comparisons and elimination rules must be reversed. If values are nonincreasing, a[mid] < target implies that candidates larger than the target could appear to the left, not the right. Reusing the ascending-order algorithm on descending input is incorrect even if it sometimes finds a value by chance.

One approach is to reverse the sequence before searching, but doing so takes Θ(n) time and memory for a copied array. A better approach for frequent searches may be to supply an order-aware comparator or explicitly implement descending midpoint logic. Every branch should still have a proof identifying which region can be discarded.

def binary_search_descending(a, target):
    """Exact-match search for a nonincreasing sequence."""
    def search(lo, hi):
        if lo == hi:
            return -1
        mid = lo + (hi - lo) // 2
        if a[mid] == target:
            return mid
        if a[mid] < target:  # larger values lie to the left
            return search(lo, mid)
        return search(mid + 1, hi)
    return search(0, len(a))

reverse_sorted = [20, 18, 18, 11, 7, 2]
assert reverse_sorted[binary_search_descending(reverse_sorted, 18)] == 18
assert binary_search_descending(reverse_sorted, 17) == -1

For custom domain types, the relation must also be transitive and stable during the search. Equality should be compatible with the ordering; otherwise, the search may cross a key that is “equivalent” in ordering but not equal under a separate equality rule.

Searching Records by a Key

Real applications rarely search arrays of bare integers. A collection may contain records ordered by an identifier, timestamp, price, or tuple of fields. To search correctly, derive or compare the same key used when ordering the records. A database-style comparison of pairs such as (date, id) is lexicographic: a record comes earlier if its first component is smaller, or if those are equal and its second component is smaller.

Key extraction can have a cost. If computing a key requires parsing a large document, decrypting a field, or performing external I/O, total time is not simply logarithmic in the number of records. Precompute indexes or cache keys when the workload justifies the extra storage.

def lower_bound_by_key(records, target, key):
    def search(lo, hi):
        if lo == hi:
            return lo
        mid = lo + (hi - lo) // 2
        if key(records[mid]) < target:
            return search(mid + 1, hi)
        return search(lo, mid)
    return search(0, len(records))

records = [(100, "alpha"), (100, "beta"), (120, "gamma")]
assert lower_bound_by_key(records, 100, lambda row: row[0]) == 0
assert lower_bound_by_key(records, 110, lambda row: row[0]) == 2
assert lower_bound_by_key(records, 130, lambda row: row[0]) == 3

Maintaining sorted order is a separate responsibility. If records are appended without respecting their order, or if a sort key mutates while the data stay in place, the index's fundamental precondition is broken.

Search by Composite Keys and Order Equivalence

Sorting by several fields introduces an equivalence question. If the primary key is not unique, searching only that key finds a range of records. If the full tuple is unique, searching the tuple may isolate one record. For a stable total order, both insertion and retrieval must apply the same sequence of comparisons and tie-breakers.

For example, an event log may sort by (timestamp, sequence_number). A search for all events at a specific timestamp can use the lower bound of (timestamp, -infinity) and an upper boundary immediately beyond that timestamp under a suitable domain representation. If using date and id fields instead, choose sentinels compatible with the actual types.

Do not confuse sorting stability with key uniqueness. A stable sorting algorithm preserves original order among equal keys; it does not supply a distinct key value or guarantee a unique binary-search result.

Searching Only a Subrange

A caller may want to search a sorted region inside a larger array. The same recursive routine works when given starting boundaries 0 <= lo <= hi <= len(a). Its return value should remain an absolute array index unless the documented API explicitly promises an offset relative to the subrange.

For example, a monitoring system may reserve the first few records for headers and search only the event region. Beginning at index 4 and ending at index 20 is straightforward, but accidentally initializing hi to the length of the subrange rather than the absolute ending index makes the search inspect the wrong positions.

def binary_search_between(a, target, lo, hi):
    if not (0 <= lo <= hi <= len(a)):
        raise ValueError("Invalid half-open index interval")
    def search(lo, hi):
        if lo == hi:
            return -1
        mid = lo + (hi - lo) // 2
        if a[mid] == target:
            return mid
        if a[mid] < target:
            return search(mid + 1, hi)
        return search(lo, mid)
    return search(lo, hi)

assert binary_search_between([1, 2, 3, 4, 5, 6], 5, 3, 6) == 4
assert binary_search_between([1, 2, 3, 4, 5, 6], 2, 3, 6) == -1

The subrange must itself be nondecreasing; other parts of the array need not be sorted if they are never examined and the caller's contract only concerns the selected interval.

Why Repeated Slicing Can Break the Complexity Claim

A novice implementation may call the recursive function on a[:mid] or a[mid+1:] rather than passing index bounds. In Python lists, slicing creates a new list and copies the selected references. The search still makes logarithmically many midpoint decisions, but copies geometric sizes of data along the path, adding Θ(n) total element-reference movement in a worst-case execution.

If each nested call retains a slice while its child runs, the live memory can likewise sum to Θ(n) in the worst case. Passing lo and hi avoids this copying and preserves the intended Θ(log n) call-stack overhead. It also returns an absolute index without the need to reconstruct offsets from slices.

This illustrates a broad engineering principle: a logarithmic number of recursive calls does not imply logarithmic time unless the nonrecursive work per call is bounded. The recurrence for a slicing implementation resembles T(n) = T(n/2) + Θ(n), giving linear total time under a full-copy slice model.

Comparison Cost Versus Element-Access Cost

Binary search is commonly analyzed in a unit-cost random-access model. A Python list element read is effectively constant time; traversing a linked list to its midpoint is not. If each midpoint lookup in a linked list costs proportional to the current interval length, the search may become linear overall even though the number of comparisons remains logarithmic.

For ordered on-disk data, a B-tree or B+ tree is often preferable to repeated binary search over a conceptual flat linked structure. A hierarchy of block-sized nodes minimizes costly page reads and adapts to update workloads. For remote APIs where each midpoint probe incurs high latency, the choice of data organization, caching, or batching can be more important than the arithmetic number of comparisons.

The performance question should always specify which resource is measured: comparisons, primitive operations, bytes copied, pages fetched, cache misses, network requests, or elapsed time. Those measures are related but not interchangeable.

Search in a Rotated Sorted Array

A sorted array rotated at a pivot, such as [13, 17, 21, 2, 5, 8, 11], is not globally ascending. However, when all values are distinct, at least one side of a midpoint is ordered in a way that can guide elimination. A modified binary search identifies a sorted half and decides whether the target can lie in that half. The method still discards a constant fraction of the interval on each step for distinct keys.

def rotated_search_distinct(a, target):
    """Search a rotation of a strictly increasing sequence."""
    def search(lo, hi):
        if lo == hi:
            return -1
        mid = lo + (hi - lo) // 2
        if a[mid] == target:
            return mid
        if a[lo] <= a[mid]:  # left segment is sorted
            if a[lo] <= target < a[mid]:
                return search(lo, mid)
            return search(mid + 1, hi)
        # right segment is sorted
        if a[mid] < target <= a[hi - 1]:
            return search(mid + 1, hi)
        return search(lo, mid)
    return search(0, len(a))

rotated = [13, 17, 21, 2, 5, 8, 11]
for item in rotated:
    assert rotated[rotated_search_distinct(rotated, item)] == item
assert rotated_search_distinct(rotated, 20) == -1

Duplicates complicate the proof. If the leftmost, middle, and rightmost values are equal, neither half may be distinguishable by comparisons alone; shrinking the interval by one element can produce O(n) worst-case behavior. The displayed implementation explicitly assumes distinct keys and should not be generalized without redesign.

Exponential Search When the Upper Bound Is Unknown

Sometimes a sorted structure supports access by nonnegative integer index, but the caller does not know how far a target could lie. Exponential search tests positions 1, 2, 4, 8, and so forth until it brackets the answer, then performs binary search within that bounded region. If the target lies around position p, the number of probes grows as O(log(p + 1)) under constant-cost access.

A real implementation must handle out-of-range requests safely and specify whether reaching the end is distinguishable from a valid value. For a known finite array, repeated doubling is generally unnecessary because its length is already available. For streams without random access, the doubling strategy may not be directly implementable, so another data structure is needed.

Exponential bracketing changes how the range is discovered, not the logic of the subsequent binary search. Once endpoints are established, the invariant and midpoint rules from the earlier sections still apply.

Binary Search over Real Numbers and Bisection

Binary search over integers always reduces a finite count of discrete candidates, so the interval can become empty. A related continuous method, often called bisection, works with a real-valued interval and repeatedly halves it while preserving a sign change or another suitable bracketing condition. It usually terminates when the interval is sufficiently narrow or after a fixed iteration budget, rather than when integer boundaries meet.

For a continuous function with opposite signs at two endpoints, the intermediate value theorem establishes that some zero lies between them. A numerical bisection implementation should consider floating-point rounding, sign changes, discontinuities, and a clear stopping tolerance. Arithmetic that produces a midpoint equal to an endpoint can prevent further reduction at machine precision.

Continuous root-finding and discrete array search share a divide-and-discard idea but have different correctness premises. A monotone Boolean predicate over integers is not interchangeable with a continuous function whose sign may change multiple times.

Floating-Point Keys, NaN, and Comparator Semantics

Floating-point arrays pose additional ordering hazards. Ordinary finite numbers can be sorted and searched in an appropriate nondecreasing order, but NaN values are not ordered in the usual way: comparisons such as x < nan, x > nan, and x == nan are false. A naive three-way midpoint search can therefore take a branch without a valid ordering justification or return a misleading result.

Floating-point equality also tests exact representational equality, not proximity within a tolerance. If values are computed numerically, a tolerance-based comparison may violate transitivity or partitioning. An approximate-match query should state an error metric and a policy for selecting candidates, rather than simply replacing equality with “within epsilon” inside a conventional binary-search proof.

Safer choices include excluding NaN from the indexed domain, defining a total-order key that places exceptional values deterministically, or searching numeric ranges through well-defined lower and upper bounds. Signed zeros, infinities, and locale-specific string orderings similarly call for explicit comparator contracts.

Standard Libraries and Established Boundary Semantics

Production code often benefits from an established binary-search primitive. Python's bisect_left and bisect_right locate insertion points rather than returning a Boolean “found” flag. C++'s std::lower_bound locates the first position not ordered before a value in a partitioned range; the library's iterator category affects operation costs, and random-access iterators are important for logarithmic iterator movement.

These APIs embody the same boundary contracts developed above. Their comparison semantics and optional key or comparator parameters must match how the data are organized. A library routine cannot compensate for an unsorted collection, a volatile key, or an inappropriate comparison.

from bisect import bisect_left, bisect_right
assert bisect_left(values, 3) == recursive_lower_bound(values, 3)
assert bisect_right(values, 3) == recursive_upper_bound(values, 3)
assert bisect_left(values, 4) == recursive_lower_bound(values, 4)
assert bisect_right(values, 4) == recursive_upper_bound(values, 4)

Performance qualification: using a bound to insert into the middle of a Python list still requires shifting elements, so finding the insertion position is logarithmic while the full list insertion can be linear. Distinguish search cost from subsequent mutation cost.

Binary Search and Data-Structure Choice

An ordinary sorted array offers good spatial locality, compact storage, and efficient repeated searches, but inserting or removing elements in the middle usually requires movement. Balanced search trees can support logarithmic search and updates with greater pointer and allocation overhead. Hash tables usually support expected constant-time equality lookup but do not naturally expose ordered lower bounds or range scans.

For datasets larger than memory, database indexes exploit page-oriented structures to limit disk I/O. A binary search of a large sorted file may also be possible, but its page-access pattern and record encoding matter. A system designer should evaluate update frequency, query selectivity, whether range results are required, concurrency, and storage costs before choosing a structure.

Binary Search Is Not a General Graph-Search Method

Searching a tree or graph by recursively exploring child nodes is not necessarily binary search. A binary tree can contain two children per node yet lack any ordering property that permits discarding an entire subtree after one key comparison. Traversal may need to inspect every node, producing linear work even though the data structure happens to be called a binary tree.

A binary search tree maintains an ordering invariant: nodes in a left subtree compare below a node and nodes in a right subtree compare above it under the chosen convention. Search follows one branch at a time, but its cost is proportional to tree height. An unbalanced binary search tree can have linear height, while a balanced one achieves logarithmic height.

This boundary separates the present article from the unit's planned Recursive Tree Traversal and Recursive Depth-First Search. The shared word “recursive” describes control structure; the information needed to prune search is supplied by the data's order and topology.

Branch-and-Bound and Search-Space Reduction

A branch-and-bound method explores candidate solutions while using proven bounds to eliminate regions that cannot improve the current best answer. It resembles binary search in using information to avoid unnecessary work, but its search space typically branches in many directions and may not exhibit one globally monotone transition point.

Similarly, backtracking explores multiple possibilities and may reverse earlier choices. A conventional binary search does not backtrack: once an ordered comparison rules out a half, that half is discarded permanently under the preconditions. Confusing these strategies can lead to the mistaken belief that any divide-and-conquer search runs in logarithmic time.

The useful unifying concept is sound pruning: discard a region only when an invariant establishes that it contains no acceptable answer, or cannot improve an optimization objective. The number and size of regions left to explore determine actual complexity.

Concurrency, Mutability, and Stable Snapshots

Binary search normally assumes the indexed data remain consistent during the search. If another thread inserts or deletes elements, or modifies the ordering field, the algorithm may examine positions that no longer correspond to one sorted snapshot. Even if each individual read is memory-safe, the overall invariant can fail. Logical correctness therefore requires an appropriate data-consistency strategy.

Depending on the environment, that strategy could be locking, immutable arrays, copy-on-write snapshots, versioned storage, or a transaction providing a consistent read. Merely repeating a search when it fails does not prove correctness in the presence of concurrent writes.

For expensive or remote predicates, a separate issue arises when feasibility depends on time-varying state. A threshold predicate that was monotone at the start may change while probes are occurring. The application must define whether the answer is computed over one snapshot, a transactional view, or a best-effort observation.

Failure Modes: Nonshrinking Intervals and Off-by-One Errors

The most frequent coding defects are not mathematical failures of binary search but inconsistent interval management. Using hi = mid in an inclusive exact-match search can leave [lo, hi] unchanged when lo == mid == hi. Using hi = mid - 1 in lower-bound search incorrectly discards a possible answer at the midpoint. Checking mid before the empty-range test can index outside the array.

A strong diagnostic procedure records lo, hi, mid, comparison outcome, and the new interval. Verify mechanically that the candidate length decreases after every recursive call. Then check whether the invariant still holds: is the answer still in the remaining interval, or has a valid boundary already been excluded?

Verification with Exhaustive Small-Input Testing

Binary search has a finite and manageable set of edge cases at small array sizes. An effective test suite checks lengths zero, one, and two; absent keys below and above the range; all-equal arrays; adjacent duplicates; and targets that fall between values. Small exhaustive tests expose many interval-update bugs before the code is used on large inputs.

from itertools import combinations_with_replacement

for n in range(8):
    for candidate in combinations_with_replacement(range(-2, 4), n):
        a = list(candidate)
        for target in range(-3, 5):
            pos = recursive_binary_search(a, target)
            assert (pos >= 0) == (target in a)
            if pos >= 0:
                assert a[pos] == target
            assert recursive_lower_bound(a, target) == bisect_left(a, target)
            assert recursive_upper_bound(a, target) == bisect_right(a, target)
            assert first_index(a, target) == (a.index(target) if target in a else -1)
            assert count_equal(a, target) == a.count(target)
print("Exhaustive small-case tests passed")

This test does not replace the correctness proof, but it checks thousands of combinations against independently established reference behavior. The point of the exercise is to test the contract, not to time the implementation: performance measurements should be a separate investigation with appropriately sized input and stable conditions.

Property-Based and Metamorphic Testing

Beyond fixed test examples, binary search supports useful properties. A returned exact-match index must be in bounds and contain the target; if an exact match is absent, no array entry can equal the target. For lower bounds, all elements before the answer must be smaller than the target and all elements at or after it must be at least the target. For upper bounds, the analogous strictness condition uses values not greater before the boundary and values greater afterward.

Metamorphic tests check that predictable changes to input produce compatible changes in output. Adding a value below every existing key should shift relevant insertion positions by one; appending a value larger than every existing key should not alter lower bounds for smaller targets. Repeating an existing target increases its count while preserving the left boundary if no smaller keys are inserted.

Property tests become invalid if the generator creates unsorted inputs or incompatible comparators. Write the test preconditions as carefully as the algorithm's preconditions.

Instrumentation: Counting Probes and Recursion Depth

Counting midpoint probes provides direct evidence of logarithmic search growth without relying on wall-clock timing. The following routine returns the selected index, probe count, and maximum recursion depth reached. The empty-range termination call is counted in depth but does not count as a midpoint probe.

def traced_binary_search(a, target):
    probes = 0
    maximum_depth = 0
    def search(lo, hi, depth):
        nonlocal probes, maximum_depth
        maximum_depth = max(maximum_depth, depth)
        if lo == hi:
            return -1
        mid = lo + (hi - lo) // 2
        probes += 1
        if a[mid] == target:
            return mid
        if a[mid] < target:
            return search(mid + 1, hi, depth + 1)
        return search(lo, mid, depth + 1)
    position = search(0, len(a), 1)
    return position, probes, maximum_depth

for n in (1, 2, 4, 8, 16, 64, 256, 1024):
    pos, probes, depth = traced_binary_search(list(range(n)), n + 1)
    assert pos == -1
    assert probes <= (n.bit_length())
    assert depth <= probes + 1

The number of probes grows by about one for each doubling in input size, although exact counts depend on the midpoint rounding. A benchmark that measures only tiny arrays may be dominated by Python function-call overhead; the asymptotic comparison count remains useful but is not the same as an end-to-end latency figure.

Worked Investigation One: A Search Never Terminates

A developer writes an inclusive-interval implementation and, on a midpoint greater than the target, assigns hi = mid. Searching a one-element range where the sole element is greater than the target repeats the identical interval forever. The code contains a base case, but its reduction rule fails to reach it.

Diagnose the failure by computing the rank hi - lo + 1 after each call. It stays at one. The correct inclusive update is hi = mid - 1, which makes the interval empty. Alternatively, switch the entire function to a half-open contract with an appropriately changed base case. The engineering lesson is that a base case without a decreasing rank is not a termination proof.

Worked Investigation Two: A Duplicate-Key Query Returns the Wrong Record

An index contains several records with identical timestamps, and a midpoint equality causes an immediate return. The returned row is a valid matching record but the application's requirement was to retrieve the first event at that timestamp. The implementation satisfies the wrong contract rather than computing an erroneous midpoint.

Replace the exact-match query with a lower bound on the timestamp key and verify equality at the returned index. If all events at that time are needed, compute the upper bound and iterate the resulting half-open span. This is a useful example of why a technically correct membership algorithm can be operationally incorrect for the business requirement.

Worked Investigation Three: A Logarithmic Search Becomes Slow

A recursive function searches a Python list by repeatedly making new sublists, then runs slowly on large inputs. The developer verifies that there are only about twenty recursive calls for one million values and concludes that the implementation must be O(log n). This overlooks the cost of copying the sublists.

Model the actual work: the first slice may copy roughly half the array, the next a quarter, and so forth. The total copied elements can be proportional to the original input size. Rewrite the function to pass integer boundaries into one unchanged sequence. If performance remains problematic, inspect comparator cost, key extraction, memory locality, and the chosen language's call overhead.

Worked Investigation Four: A Threshold Predicate Is Not Monotone

An engineer binary-searches a resource setting on the assumption that larger settings always make a benchmark pass. Measurements are noisy, and some larger settings produce worse outcomes because contention or throttling changes. The predicate therefore alternates between success and failure. The returned threshold changes unpredictably across runs.

First determine whether a monotone property exists at all. If the intended property is monotone in a theoretical model but measurement noise obscures it, use a controlled test protocol, stable snapshots, and appropriately justified statistical treatment. If the real system is nonmonotone, a boundary-based binary search is the wrong algorithm for the global optimization problem.

Worked Investigation Five: Incorrect Search During Concurrent Updates

A service searches a shared sorted array while another worker inserts records. The searched positions shift after midpoint calculations, leading to inconsistent reads or results that no longer correspond to any single version of the array. Atomic reads of individual entries do not guarantee that the collection as a whole stayed ordered during the sequence of probes.

Specify the consistency requirement first. A read-only snapshot, lock, or transactional index may preserve an ordered view for the duration of the search. If stale reads are acceptable, document what guarantees remain; do not claim fully linearizable lookup behavior without an appropriate synchronization design.

Worked Investigation Six: A Fast Probe Does Not Mean a Fast Insertion

An application uses lower-bound search to insert records into a large Python list. Locating the insertion point takes logarithmically many comparisons, but inserting near the front shifts many references. The observed update cost grows with array length despite the efficient search phase.

Separate the operation into two components: find the correct position, then mutate the underlying storage. The second step often costs Θ(n) for an array. For an update-heavy ordered workload, consider a balanced tree, a B-tree, batched sorted runs, or other structure suited to the required operations. Do not label the whole workflow “logarithmic” merely because its index selection is logarithmic.

Design and Investigation Framework

A reliable binary-search design proceeds from a contract and an invariant to code and measurement. Identify whether the objective is membership, first occurrence, insertion point, count, or feasibility threshold. State the search domain and its order or monotonicity assumptions. Pick inclusive or half-open bounds. Derive an elimination rule and a decreasing rank. Then select the appropriate implementation style.

Suggested Study Pathways

Beginning programmers: read the search contract, half-open interval convention, exact-match implementation, and present/absent traces. Then run the examples and explain why a missing key causes the candidate range to become empty.

Students of proofs and algorithm analysis: follow the candidate-containment invariant, termination ranking function, time recurrence, and auxiliary-space sections. Compare Recursion and Mathematical Induction with Recurrence Relations for Recursive Algorithms to distinguish correctness and cost arguments.

Data and application developers: emphasize duplicate keys, lower and upper bounds, record keys, standard-library semantics, and concurrent modification. Work through practical insertions and duplicate timestamps before selecting a collection type.

Algorithmic problem solvers: study monotone predicates, binary search on the answer, capacity feasibility, and threshold-boundary sentinels. Identify the feasibility monotonicity argument independently of the outer binary search.

Systems and performance engineers: compare recursion and iteration, indexing costs, slicing overhead, storage behavior, and probe instrumentation. The objective is to measure the cost of the full operation, not merely its number of comparisons.

Common Errors and Misconceptions

  • “Binary search works on every array.” It requires an ordering or partition property sufficient to justify discarding candidates.
  • “A midpoint equality always returns the first duplicate.” Ordinary exact-match search has no such guarantee.
  • “The empty interval is an implementation accident.” It is the base case establishing an absent target or isolating an insertion boundary.
  • “Either endpoint convention is interchangeable with the other.” Only complete, internally consistent conventions are interchangeable.
  • “A recursive call count of log n makes the entire algorithm log n.” Slicing, indexing, or expensive predicates can increase cost.
  • “Tail recursion is always optimized.” Stack behavior depends on language and implementation guarantees.
  • “Binary search must find a value that exists.” Lower-bound and threshold queries return boundary positions when a literal match is absent.
  • “A binary tree implies binary search.” Without an ordering invariant, a tree lookup may require traversal.
  • “The midpoint can never overflow because it lies inside the array.” Intermediate arithmetic can overflow even when the desired result is valid.
  • “The data can change while the search runs.” The ordering invariant requires an appropriate consistency policy.

Most of these mistakes can be corrected by returning to four explicit statements: the contract, the precondition, the invariant, and the strictly decreasing rank.

Review Questions and Model Answers

  1. Question: What property allows binary search to ignore half of its candidates? Answer: A defined ordering or partition invariant showing that the discarded region cannot contain a qualifying answer.
  2. Question: For a half-open interval [lo, hi), when is it empty? Answer: When lo == hi, assuming valid maintained bounds.
  3. Question: Why should a lower-bound search not stop at equality? Answer: Earlier equal elements may exist; the objective is the first qualifying index.
  4. Question: What is the lower bound of 4 in [1, 3, 3, 7]? Answer: Index 3, even though 4 is absent.
  5. Question: How many occurrences of 3 are in [1, 3, 3, 7]? Answer: upper_bound(3) - lower_bound(3) = 3 - 1 = 2.
  6. Question: What rank proves recursive termination? Answer: The nonnegative candidate count hi - lo, shown to decrease strictly on every call.
  7. Question: What is the time complexity with constant-cost access and comparisons? Answer: Θ(log n) in the usual worst-case model.
  8. Question: What auxiliary call-stack space does a normal recursive implementation use? Answer: O(log n), unlike an ordinary iterative version's O(1) extra control space.
  9. Question: Why may Python list slicing spoil the logarithmic time claim? Answer: Each slice copies references, and the total along a halving path can be linear in the original array size.
  10. Question: What is needed for binary search over a Boolean predicate? Answer: A stable monotone false-then-true partition under the chosen index order.
  11. Question: Why is a rotated-array search not automatically logarithmic with many duplicates? Answer: Equal boundary values can make the sorted half ambiguous and force one-at-a-time elimination.
  12. Question: Why does locating an insertion point in a Python list not guarantee logarithmic insertion time? Answer: The list still shifts elements to make room, often requiring linear work.
  13. Question: What is a useful way to identify off-by-one errors? Answer: Trace intervals on empty, singleton, duplicate, and absent-target cases, verifying strict shrinkage and invariant preservation.
  14. Question: Can an ordinary binary tree be searched by binary search? Answer: Only if a suitable search-order property enables one-branch elimination; an arbitrary binary tree does not suffice.
  15. Question: What must be proved for binary search on a feasible capacity? Answer: Feasibility accurately models the task and is monotone in capacity.
