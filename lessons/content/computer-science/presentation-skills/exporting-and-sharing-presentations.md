Basic Computer Skills / Presentation Skills

## Lesson 9: Exporting and Sharing Presentations

A community center has approved your fictional six-slide presentation about a Saturday Digital Skills Workshop. The organizer asks for a file that can be printed for participants, a colleague wants a version that can be edited next month, and the program coordinator wants a link that invited staff can review without changing the slides. These requests sound similar, but they require different decisions. Sending the same file to everyone could expose private notes, give unwanted editing permission, or produce a format that recipients cannot open.

[[export|Exporting]] a presentation means producing a file in a selected format for a particular purpose. [[sharing|Sharing]] means providing a person or group with a copy of, or authorized access to, information. Exporting usually creates a separate output; sharing can distribute an existing file, grant access to a cloud document, or provide a link. Neither action guarantees that the result is appropriate, private, accessible, or even complete. A reliable presenter learns to choose a deliverable, inspect it, control access, and verify receipt.

This is the final lesson in MGU Basic Computer Skills / Presentation Skills. Lessons 1–8 introduced the idea of a presentation, creation and layout, media, slide organization, design, notes, and delivery. This lesson brings those skills together in a complete handoff process. Microsoft PowerPoint on Windows 11 is the principal desktop example, with Google Slides and LibreOffice Impress included throughout. Features and menu labels may differ by edition, browser, device, subscription, or school/work policy; verify the actual options available in your application rather than assuming every screen looks identical.

**No paid software, real recipient, public upload, account change, or external transmission is required to complete the activities.** The practice project uses invented people, imaginary event details, and a fictional presentation. Paper planning is an acceptable alternative when you do not have presentation software. When using software, keep all practice files private and test sharing settings without sending invitations to real people.

**Level:** Beginner · **Estimated study time:** 115–155 minutes · **Prerequisites:** Presentation Skills Lessons 1–8 recommended · **Practice equipment:** Paper and pencil or an installed/browser-based presentation application; internet and a second device are optional · **Safety:** Do not publish private slides, send practice invitations, expose notes or comments, or alter institutional permissions to complete this lesson. Use authorized recipients and fictional information only.

> **Essential idea:** **Decide who needs the presentation and what they must do with it → keep an editable original → choose an appropriate output format → inspect the output → grant the minimum necessary access → verify the result → manage or withdraw access when appropriate.** Exporting a file is only one part of a responsible handoff.

### Learning objectives

After completing this lesson, you should be able to:

1. Explain the difference between saving, exporting, downloading, printing, publishing, and sharing a presentation.
2. Select among an editable slide file, PDF, video, images, and printed handouts for common audience needs.
3. Recognize common presentation formats, including PPTX, ODP, PDF, and MP4, and explain the practical tradeoffs.
4. Keep an identifiable editable master file and avoid accidentally overwriting it while exporting or creating copies.
5. Follow beginner-level export procedures in PowerPoint, Google Slides, and LibreOffice Impress where features are available.
6. Check slides, links, fonts, image quality, layout, animation, notes, and media in the destination output.
7. Distinguish file attachments, direct-download copies, cloud-sharing links, and published web presentations.
8. Compare viewer, commenter, and editor permissions and select the least access required for a task.
9. Recognize privacy, copyright, accessibility, identity, and version-control risks in a shared presentation.
10. Diagnose common problems such as inaccessible links, missing media, formatting changes, oversize attachments, and unintended access.
11. Prepare and verify a fictional three-format delivery package with a simple recipient-and-permissions plan.

## 1. What do exporting and sharing mean?

The original slides you created in an application form a [[presentation-file|presentation file]]. You can open the file, correct a typo, reorder slides, and save your work. When you [[save|save]], you record the current state in that file or another chosen location. When you [[save-as|Save As]] or create a copy, you generally create a separately named file or version that can be edited independently, although exact behavior depends on the application. When you export, the application prepares an output such as PDF or video using the original slide content. When you share, someone else may receive an attachment, access a cloud document, or open a published presentation.

The most important distinction is **purpose**. A document intended for independent reading does not need the same file capabilities as one intended for editing during a staff meeting. A public PDF handout should not automatically contain the speaker's drafting notes. A team working collaboratively may need edit access to a shared source; an attendee who only wants to study the slides usually does not.

### Six actions that should not be confused

| Action | What it generally does | Typical example | Main risk to check |
| --- | --- | --- | --- |
| Save | Records the current file state | Save changes to the working deck | Saving in the wrong folder or over the wrong version |
| Save As or make a copy | Creates a separately identified working file | Preserve a master and make a staff edit copy | Mistaking the copy for the master |
| Export | Produces an output in another format | Create a PDF handout | Fonts, links, notes, or media may change or disappear |
| Download | Transfers a file from an online service to a device | Download Google Slides as PPTX | The downloaded copy may stop reflecting later cloud edits |
| Print | Produces paper or a printer-ready output | Print two slides per page | Notes, color, page order, and paper use may differ |
| Share or publish | Gives access or makes material available to others | Send an invited-person link or publish slides online | Excessive permissions or unintended public exposure |

A [[download|download]] does not necessarily make the original online file editable by a recipient. A [[link|link]] is not always a downloadable copy. A [[pdf|PDF]] export is not the same thing as setting the source file to read-only; people may still copy visible information, and anyone with the PDF may retain it after a link is closed. The safest routine is to name the action precisely before performing it.

### The original, the output, and the recipient copy

Imagine three documents:

1. `workshop-master.pptx` is the editable master, kept in a private working folder.
2. `workshop-handout.pdf` is an exported copy that participants can read.
3. `workshop-staff-edit.pptx` is an editable copy intended for an authorized colleague.

The PDF and staff copy originate from the master, but they are different files. Changes to `workshop-master.pptx` do not automatically revise PDFs or downloaded copies already sent. You must normally export and distribute an updated version. If you share a cloud document by link, on the other hand, authorized recipients may see later edits to that **same shared document**. The difference between a fixed attachment and a living online file becomes important when facts change or approvals are required.

### What is an editable master?

An [[editable-master|editable master]] is the version you maintain for continuing revisions. It includes the slide objects, structure, and other source features supported by the application. For PowerPoint, a common editable type is `.pptx`; for LibreOffice Impress, `.odp`; and Google Slides commonly exists as an online document in Google Drive. The exact format is less important than knowing **where the source lives, which version is authoritative, who may change it, and whether it is backed up appropriately**.

| Document | Intended use | Editing expected? | Should it replace the master? |
| --- | --- | --- | --- |
| Private source deck | Ongoing maintenance | Yes | It is the master |
| Review copy | Comments or limited discussion | Sometimes | No, unless formally adopted |
| Public PDF handout | Consistent reading and printing | Not normally | No |
| Recorded video | Watching without controlling slides | Not as slides | No |
| Event thumbnail or image | Preview or promotion | Only in an image editor | No |
| Published slide link | Web viewing by an approved audience | Depends on publication settings | Usually no |

A [[version|version]] is a distinguishable state of a file. A revision label or date in a filename can help, but it is not a substitute for a controlled workflow. If two different people edit two independent copies, those copies may diverge; changing one does not necessarily update the other.

### A worked example: three different requests

The workshop organizer says, "I need a printable set of slides for people who do not have presentation software." A PDF is a sensible starting point because it ordinarily displays the pages in a stable layout. The colleague says, "I will update the date and speaker name next month." An editable PPTX or ODP, or appropriate editor access to the shared cloud original, is better suited for that request. The coordinator says, "Let the invited staff read the slides without changing anything." A restricted cloud link with viewer access may fit—provided the coordinator is authorized to see the contents and the settings are confirmed.

Notice that **the same presentation leads to three separate deliverables and three separate access decisions**. The correct answer is not to send the most powerful file to everybody. It is to supply the least complex, least privileged form that meets each legitimate need.

### A simple handoff record

You do not need enterprise document-management software to track a beginner project. A short log can record what was delivered, to whom, in which format, and which version. For a school or employer, follow their actual retention and records policy rather than inventing your own permission to store protected material.

| Field | Fictional record | Why it matters |
| --- | --- | --- |
| Presentation title | Saturday Digital Skills Workshop | Identifies the subject |
| Approved source | Workshop master, version 1.0 | Establishes the authoritative content |
| Deliverable | `workshop-handout-v1.pdf` | Separates a reading copy from the source |
| Intended audience | Registered participants | Defines who should receive it |
| Distribution method | Approved classroom portal | Explains how they obtain access |
| Review date | Before the scheduled workshop | Prompts a final accuracy check |
| Access status | Restricted to course participants | Prevents accidental public distribution |

> **Good habit:** Record the **recipient's need** before choosing the file type or pressing Share. Technology decisions become much clearer when the intended use is stated first.

## 2. Which presentation format should you choose?

A [[file-format|file format]] determines how information is stored and how software interprets it. You often recognize a format by its [[file-extension|file extension]] at the end of the filename. A `.pptx` file and a `.pdf` file may show nearly the same slides to a reader, but they preserve different kinds of information and offer different editing possibilities. No single format is ideal for every audience.

### Common formats at a glance

| Format | Typical extension | Primary purpose | Important limitation |
| --- | --- | --- | --- |
| Microsoft PowerPoint | `.pptx` | Editable slides in PowerPoint and compatible tools | Appearance or advanced features may change in other applications |
| OpenDocument Presentation | `.odp` | Editable slides in Impress and compatible tools | Some PowerPoint-specific features may not transfer perfectly |
| Portable Document Format | `.pdf` | Reading, printing, and relatively stable page layout | Standard exports do not preserve live slideshow behavior or ordinary slide editing |
| MPEG-4 video | `.mp4` | Watching a timed or narrated presentation | Viewers cannot advance or edit individual slides like a deck |
| Image export | `.png` or `.jpg` | Using individual slides as images | Text usually becomes part of an image rather than ordinary editable slide text |
| PowerPoint Show | `.ppsx` | Opening a compatible presentation in show mode | Still a presentation file, not a video or privacy protection mechanism |

A format name alone does not guarantee accessibility, compatibility, or security. A PDF can have tiny text. A PPTX can contain unsupported effects in another program. An MP4 can lack captions. An image may be blurry or difficult for a screen reader to interpret. Choose a format based on the audience's actual task, then test the result.

### Editable slide formats: PPTX and ODP

An [[editable-deck|editable deck]] lets an authorized person work with text boxes, pictures, placeholders, slide order, and other objects. PowerPoint's standard `.pptx` format is widely supported, but a file made in one editor may look different when opened elsewhere. LibreOffice Impress uses `.odp` as its native OpenDocument presentation format and can also save in PowerPoint formats through its supported filters.

A presentation converted between programs may exhibit differences in font availability, layout, text wrapping, animation, embedded media, slide masters, or theme styling. Before asking someone to continue editing, identify the application they will use and have them open a test copy. Do not treat format conversion as proof of exact visual equivalence.

**Editable does not mean unrestricted.** Access permissions can prevent an invited recipient from editing a cloud file, but anyone receiving an ordinary, unlocked downloadable presentation copy may have more ability to inspect or modify that copy. Do not place confidential material in a file and assume a viewer-only setting on another platform will keep it safe after distribution.

### PDF: useful for reading and printing

A [[pdf|PDF]] generally keeps text and objects in fixed pages that look similar on different systems. For a slide presentation, the PDF usually contains one slide per page unless the application offers a handout or notes layout. PDF is often suitable for applicants, attendees, clients, teachers, or anyone who needs to review the content without presentation software.

PDF has limitations. Animations normally become static. A slide with three points revealed one at a time may show all points together in the PDF, or it may follow another application-specific export behavior. Embedded videos do not automatically become playable embedded video in an ordinary PDF. Speaker notes are usually not part of a standard slide-only export; special printing or export configurations can include notes or handouts. Hyperlink behavior and accessibility structure may vary by application and settings.

| Reader's goal | Why PDF may help | What to verify |
| --- | --- | --- |
| Print copies | Stable page dimensions | Margins, paper size, slides per page, grayscale readability |
| Read on a phone | Common reader support | Legibility at realistic zoom levels |
| Quote a title or date | Text may remain selectable | Actual exported text and reading order |
| Open without slide software | PDF readers are widely available | File opens without unusual permissions |
| Distribute a public handout | Format changes are less likely | Hidden information was not included or exposed elsewhere |
| Provide an accessible document | Tagged PDF options may assist | Tags, text order, alt text, contrast, meaningful links |

**PDF does not mean secure or permanently unchangeable.** A recipient may be able to annotate, edit using specialized tools, copy content, capture a screen, or redistribute the file. PDF is a document-delivery choice—not a guarantee of secrecy or immutability.

### Video: a timed presentation that plays back

An [[mp4|MP4]] can be appropriate when you want a narrated explanation or an automatically paced presentation. In supported desktop PowerPoint versions, a video can be created from slides with selected timing and recording options. A viewer can watch the result in a compatible media player without having PowerPoint. The video does not behave like an editable slide deck, and exported audio, animation, or externally linked media must be checked.

Consider this case: an instructor is unable to attend live and wants students to hear a five-minute explanation. A properly recorded video can communicate the narration and timing more effectively than a static handout. But students who prefer reading may still need a PDF or an accessible text summary. A captioned video and a readable handout can complement each other.

| Question | Practical effect on a video export |
| --- | --- |
| Does each slide stay visible long enough? | Timings determine whether a viewer can read comfortably |
| Is narration included? | Recording/export settings determine which voice content appears |
| Do animations appear at the intended moments? | Playback and export settings can change the experience |
| Do linked online videos work? | External media may not be embedded in the exported video |
| Are captions available? | A separate captioning workflow may be needed |
| Is the file reasonably sized? | Resolution, duration, and compression affect file size |

Do not assume Google Slides or LibreOffice Impress have an identical one-click MP4 export workflow to desktop PowerPoint. Their native menu options differ; a recording or separate video-production workflow may be necessary. This lesson does not require video creation.

### Images and printed handouts

An application may allow a slide or slides to be exported to [[image-format|image files]], often PNG or JPEG. These are useful for a newsletter thumbnail, approved announcement, or image-based display. However, exporting slides as images may make small type difficult to read, remove ordinary text selection, and offer less semantic information to assistive technologies. When communicating substantial text, prefer an accessible document or live text alternative rather than supplying images alone.

Printed [[handout|handouts]] can show one slide per page or multiple slide thumbnails per page, depending on the application. A printed page is not necessarily the same layout as a PDF export; review it in print preview. Three slides per page may leave space for notes, while six per page may be too small for some readers. Choose the number based on actual readability, not only paper savings.

### Decision worksheet: choose for the recipient

| Recipient need | Likely starting choice | Delivery consideration |
| --- | --- | --- |
| Read and print the final content | PDF | Test print layout and accessibility |
| Revise slide objects later | PPTX, ODP, or editor access | Confirm software compatibility and authorization |
| Leave comments without changing slides | Commenter access where supported | Check organization policies and recipient identity |
| Watch a narrated talk | Video plus accessible alternative | Test timing, sound, and captions |
| Put one approved slide in a newsletter | PNG or JPEG | Confirm resolution, permission, and alt text for the web page |
| View a continually updated staff deck | Restricted cloud link | Clarify that the shared content may change |
| Study offline without reliable internet | Downloaded copy | Confirm the recipient has the right application and a current version |
| Distribute to a broad public audience | Approved public PDF or published link | Remove sensitive data, verify rights, and secure publication approval |

### Worked example: an instructor requests a handout and a training record

A fictional training coordinator requests "a shareable copy". That phrase is ambiguous. You ask whether the recipient should read, edit, or watch. The coordinator explains that participants need an offline reference, while absent staff should see the speaker's explanation. You make two outputs from one approved source: a PDF for reading and an MP4 only if your software supports a tested recording workflow. If you cannot produce an MP4, you can supply a PDF and written narration notes appropriate for public release—or seek an approved recording method. You **do not** simply rename the `.pptx` extension to `.mp4`; changing the letters of a filename does not convert its contents.

> **Format rule:** Select the simplest format that fully serves the task. When two audiences have different needs, producing two verified outputs is often better than forcing everyone to use one file.

## 3. How do you prepare a presentation for export?

Exporting is most reliable when the source is organized before the process begins. Before making a PDF, video, or downloadable copy, complete a [[preflight-check|preflight check]]. This means reviewing the content, its legal and privacy context, accessibility, and the technical behavior likely to change in a different format. A minute spent inspecting the source can prevent a much more visible problem after distribution.

### Confirm that the correct version is ready

Open the intended master deck. Read the title and last slide. Verify the slide count, date, event name, responsible organization, and source references. If the document is part of a group project, confirm it has been approved for release. A filename that says `final` does not prove a presentation has actually been approved.

A dependable sequence is:

1. **Find the intended master.** Confirm file name and location; do not choose a random attachment from a recent message.
2. **Check the purpose.** Identify the audience, use, and format requested.
3. **Check content approval.** Confirm the presentation may be distributed to those people.
4. **Inspect the last revision.** Look for late changes, outdated figures, temporary labels, and missing slides.
5. **Save the master.** Ensure the latest changes are recorded before creating outputs.
6. **Create an export copy.** Use a descriptive filename and destination instead of overwriting the master.
7. **Open the new output.** Inspect the actual exported file; the absence of an error message does not prove quality.

### Identify content that must not leave the source

Presentations may contain more than what appears on the slide during a slideshow. Speaker notes can contain rehearsal instructions or private names. Comments may contain internal reviews. [[hidden-slide|Hidden slides]] may remain part of an editable deck even when excluded from a normal show. Objects positioned outside the visible slide may still exist in the file. [[metadata|Metadata]] can contain author information or file properties. Different export modes preserve or omit different elements.

| Possible content | Where it may be found | What to ask before distribution |
| --- | --- | --- |
| Speaker notes | Notes pane, Notes view | Are they intended for this recipient? |
| Comments | Comment pane, collaboration tools | Are internal discussions approved for release? |
| Hidden slides | Slide thumbnails or slide manager | Are they meant to be included in this deliverable? |
| Off-slide objects | Editing canvas outside slide boundary | Is unused or confidential material present? |
| Images with personal details | Photos, screenshots, charts | Did anyone authorize this information being shared? |
| Hyperlinks | Text and visual objects | Do the destinations still work and suit the audience? |
| Media files | Video/audio objects or references | Are rights, playback, and export supported? |
| File properties | Details, properties, inspection tools | Could author or organizational metadata be inappropriate? |

In supported desktop PowerPoint, **File → Info → Check for Issues → Inspect Document** can help locate several categories of hidden or personal information. Available checks depend on the version. Inspect the report carefully and use a **copy** when removing data; some removal operations cannot be undone by simply closing a dialog. Document Inspector is helpful but does not find every possible private element or risk. Do a manual review as well. The [official PowerPoint inspection reference](https://support.microsoft.com/en-us/office/collab-files/remove-hidden-data-and-personal-information-by-inspecting-documents-presentations-or-workbooks) describes this process, but the principle applies across software.

### Review accessibility before conversion

[[accessibility|Accessibility]] means that people with different abilities and technologies can obtain and understand the information. A document that looks attractive on the editor's monitor may become difficult to read on paper or in a different format. Use actual content structure and check the exported result rather than assuming the conversion will fix problems automatically.

Key checks include:

- Titles and slide order follow a meaningful sequence.
- Text is readable and uses sufficient contrast against backgrounds.
- Important visuals have useful [[alt-text|alternative text]] or a comparable description where supported.
- Color is not the only method used to distinguish categories, warnings, or results.
- Charts identify the meaning of values, not merely a decorative shape.
- Links have descriptive text and lead to appropriate destinations.
- Audio and video have suitable captions or transcripts when distributed.
- The exported PDF retains searchable/selectable text and appropriate reading order where possible.
- An intended [[tagged-pdf|tagged PDF]] contains usable structure; verify rather than rely on a filename or checkbox.

Microsoft PowerPoint includes an Accessibility Checker in supported versions. LibreOffice's PDF export can offer tagged PDF and PDF/UA options. These features assist preparation but are not proof of complete accessibility. For a high-stakes public release, review with appropriate tools or qualified testers.

### Fonts, images, layout, and linked resources

[[font-substitution|Font substitution]] occurs when an application cannot use the expected font and replaces it with another. This can change line breaks and shift titles or body text. [[aspect-ratio|Aspect ratio]] describes the proportional relationship between width and height; a 16:9 slide may be scaled, cropped, or placed inside a differently sized print page. [[compression|Compression]] can reduce file size but may make pictures less sharp. These technical terms have practical effects even for beginners.

Check these conditions before export:

| Element | Source check | Output check |
| --- | --- | --- |
| Fonts | Use suitable, available fonts; avoid cramped lines | Words and labels are not clipped or rewrapped badly |
| Images | Choose adequately clear images with permission | Pictures are not pixelated or distorted |
| Aspect ratio | Match the intended display or page purpose | Pages are not unexpectedly cropped |
| Embedded audio | Confirm file or recording exists in the source | Playback behaves as intended in an output that supports audio |
| Linked video | Confirm the destination and network need | Recipient can use the intended link or separate media source |
| Charts | Label axes, units, and categories | Values remain readable and understandable |
| Transitions | Do not rely on effects to convey the whole meaning | Static outputs still make sense without effects |
| Links | Check the visible destination and relevance | Links still open in the output format when expected |

A [[linked-media|linked media]] object depends on an external file or web resource; an [[embedded-media|embedded media]] object is included in the presentation package or document in an application-specific way. These are not identical, and exports may handle them differently. A normal PDF of a slide containing a video is likely to show a still visual or a link rather than the original interactive playback. If the video itself is essential, plan another authorized way for recipients to access it.

### Naming, location, and backups

Use a descriptive name such as `digital-skills-workshop-public-handout-2026-11.pdf` instead of `presentation2-final-final.pdf`. A name can include a project, audience, version or date, and format purpose without exposing participant names or private identifiers. Avoid punctuation or characters that some systems do not accept. A simple hyphenated name transfers across platforms more predictably than an unusually long or cryptic filename.

Store the editable master in a controlled folder. Store approved outputs in a clearly separate distribution folder. Where permitted, keep an appropriate [[backup|backup]] or version history. Do not rely on a single email attachment as your only copy. Conversely, avoid accumulating many uncontrolled copies of private documents across devices and online services. The governing institution's policies take priority.

### A two-pass review method

**Pass 1 — content and disclosure.** Read every slide and identify errors, outdated statements, private notes, comments, images, or links. Verify that the audience is allowed to see all material in the intended output. **Pass 2 — output and usability.** Open the PDF, PPTX, video, or image after export and check the actual file's page count, arrangement, readability, and supported functionality. A final check on another device or application can reveal compatibility issues but should use only approved content and systems.

> **Preflight reminder:** The output that matters is the file or link the recipient will actually open—not the pristine deck you saw while editing.

## 4. How do you export a presentation in common applications?

There is no universal Export button that behaves identically in every program. Before following any procedure, identify the application, the edition you have, whether you are working online or offline, and the output you need. Some applications label an action **Export**, some **Download**, and some **Save As**. Where possible, use an existing nonconfidential practice file and create a copy instead of converting the only master.

The next workflows describe common desktop and browser experiences. Buttons can move after application updates. Your goal is to understand the sequence—open correct source, select output type, choose destination or permissions, produce output, and inspect it—not to memorize every menu location.

### Microsoft PowerPoint on Windows: PDF

In desktop PowerPoint for Windows, a standard method is **File → Export → Create PDF/XPS**. Other supported versions may let you choose PDF from Save As. Microsoft documents both approaches. A basic practice procedure is:

1. Open the correct deck and save its latest approved changes.
2. Select **File**, then **Export**.
3. Choose **Create PDF/XPS** if available, then choose **Create PDF/XPS** again to open the publishing dialog.
4. Select a clearly identified folder, such as a practice distribution folder.
5. Enter a new name such as `workshop-public-handout.pdf`.
6. Confirm that **PDF** is the selected output type.
7. Review available options for slide range, publishing content, output quality, and accessibility as appropriate. Do not include notes or hidden slides unless they are approved for that output.
8. Choose the publish or save command and allow the program to complete.
9. Open the resulting PDF in a reader. Count the pages and inspect the first, middle, and last pages, then check links and text quality throughout.

For a standard six-slide deck exported one slide per page, you would commonly expect six PDF pages. However, notes pages, handout layouts, selective slide ranges, or extra output settings can change the count. Use your chosen options to interpret the result. A successful export command is not itself proof that the PDF contains the correct slides.

**Output quality matters.** A standard or print-oriented setting may preserve better images but produce a larger file. A minimum-size or online-oriented option may reduce file size at the cost of quality. If the deck contains photographs, icons, or complex charts, inspect the exported version at realistic reading size. Do not choose a low-quality setting simply because it produces the smallest possible attachment.

### Microsoft PowerPoint on Windows: editable copy

If the recipient needs to edit the slides, retaining `.pptx` is commonly more useful than exporting a PDF. Start by saving an approved copy with **File → Save As** or **Save a Copy**, depending on your edition. Choose the folder and filename explicitly. Confirm that the format is a normal PowerPoint presentation, not a PDF or slideshow-only alternative. Reopen the copy to verify it has the intended content.

When the recipient works in a different application, ask them to inspect the copy. Fonts, custom transitions, embedded media, or design elements may behave differently in Impress, older software, or browser-based editors. If continued joint editing is needed, authorized access to a single cloud file may reduce the confusion of emailing many independent versions.

| PowerPoint delivery need | Common Windows method | Important check |
| --- | --- | --- |
| Printable, non-editing handout | File → Export → Create PDF/XPS | Page range, text, comments/notes exclusion, accessibility |
| Independently editable copy | File → Save As or Save a Copy → PPTX | Source master remains separate |
| Narrated video | File → Export → Create a Video | Recordings, timings, sound, file size, captions |
| Email attachment | Share or attach the approved saved file through an authorized method | Correct file, recipient, version |
| Shared collaborative source | Share through supported OneDrive/SharePoint workflow | Access roles and link scope |

### Microsoft PowerPoint on Windows: MP4 video

Supported desktop PowerPoint versions can create a video from slides. A typical route is **File → Export → Create a Video**. You may be able to select a quality level, decide whether to use recorded timings and narrations, choose the default seconds per slide when timings are absent, and save the output in MP4 format. The exact dialog depends on edition.

Do not confuse video output with a slideshow file. A video has a timeline: it progresses at chosen durations and does not let the viewer open an ordinary slide editor to rewrite the title. A six-slide presentation with ten seconds assigned to each slide, for example, would display those slides for about a minute before accounting for other timing details. Whether animations, audio, and transitions are included depends on recorded content and settings; test the finished file.

After export, play the saved MP4 from beginning to end. Listen with sound enabled and muted, when possible, to verify that any essential spoken explanation also has an accessible alternative. Confirm that the ending is complete and that no unexpectedly blank slide or private spoken aside was captured. If the output is not approved for public access, store and share it with the same care as the original source.

### Microsoft PowerPoint: sharing an online file

In supported PowerPoint editions, a **Share** command can provide a link to a presentation stored in an approved cloud service such as OneDrive or SharePoint. If the deck is only stored locally, the application may ask you to save a cloud copy before link-based collaboration is available. The person creating the link should review the intended recipients, link settings, and whether recipients may view, edit, or download. Options such as **Can view**, **Can edit**, or download restrictions may depend on account and organizational policy.

If a recipient only needs to read, begin with the least privilege that works: view-only. If a designated collaborator must change slide content, editor access may be appropriate after identity and authorization are confirmed. The labels and capabilities are not identical for all personal, educational, and enterprise Microsoft accounts. Do not promise that a specific protection or expiry setting exists without verifying it in the actual interface.

### Google Slides: download as PDF or PowerPoint

Google Slides commonly saves changes to its online document. When you want a separate offline file, choose the **File → Download** menu and an available format. The two common beginner choices are **PDF Document (.pdf)** and **Microsoft PowerPoint (.pptx)**.

1. Open the intended presentation in Google Slides.
2. Confirm you are in the correct file and that recent changes have been saved.
3. Choose **File → Download**.
4. Select **PDF Document (.pdf)** for an ordinary reading/printing file, or **Microsoft PowerPoint (.pptx)** for a separately editable copy.
5. Check the browser's download result and save location. On Windows, files often appear in Downloads unless another destination is selected; actual behavior depends on browser settings.
6. Open the downloaded file in a suitable application and inspect the text, slide count, layouts, and links.
7. If you use a PPTX copy, examine any differences from the original Google Slides document, especially fonts, media, animations, and layout.

A downloaded PDF or PPTX is not the same thing as continued access to the original live Google Slides file. Changes to the online deck do not usually rewrite the already-downloaded file on your device. If an approved correction is made later, download and redistribute a new version as necessary.

**Do not assume standard Google Slides includes the same direct MP4 export workflow as desktop PowerPoint.** Video creation may require a separate recording or production process, and any such process must be suitable for the task and permitted by the organization.

### Google Slides: share without downloading

Use the **Share** control to give other people access to the live Google Slides file. In the available sharing dialog, you may be able to enter specific people or groups, choose a role such as **Viewer**, **Commenter**, or **Editor**, and set **General access** to **Restricted**, organization-only, or **Anyone with the link**, depending on the account and policy. Use Restricted when a file is intended only for named recipients. If work or school sharing rules prevent an action, do not attempt to bypass them.

A sensible fictional process is:

1. Confirm that the slide contents are approved for the intended people.
2. Select **Share** and inspect any existing recipients or general-access settings.
3. Set **General access** to **Restricted** if the file should not be available broadly.
4. Add the approved recipient's identity only if this is an authorized real workflow; in this lesson, **do not enter or invite an actual person**.
5. Select **Viewer** for someone who should only read the presentation.
6. Review the final settings before choosing an actual Send or Copy link action in a real workplace or school task.
7. Test access with an authorized alternate account only when such a test is permitted, then record the outcome.

A [[commenter|commenter]] can generally leave feedback without the same editing privileges as an editor. An [[editor|editor]] can change the content and may have additional collaboration options. A [[viewer|viewer]] primarily reads or opens the file. Details such as downloading, copying, and onward sharing can also depend on owner controls and organization policy. Never assume every viewer can or cannot download based solely on the word "Viewer".

### Google Slides: publishing to the web is a different action

Some Google Slides environments offer **Publish to the web** through a File/Share menu path. This can create a web-viewable presentation or embed that is intended for much wider access than a private collaboration link. **Publication is not the same thing as sending a restricted viewer link.** Published content may be accessible to people outside the intended group and may be discovered or redistributed. Updates and stopping publication may behave differently from ordinary file sharing.

Do not use a publication function to distribute class exercises or private workplace decks. Public publication requires an actual release decision, a rights and privacy review, and the appropriate organizational approval. If the intent is to let one invited colleague read slides, do not choose a public-publishing workflow.

### LibreOffice Impress: PDF export

LibreOffice Impress is a desktop presentation application whose native editable format is typically ODP. To produce a PDF, look for **File → Export As → Export as PDF**, **File → Export**, or the available PDF export control in your installed version. Inspect the PDF export options before confirming. They may include slide range, image settings, accessibility options, and other choices. Some versions offer a tagged PDF or PDF/UA-oriented export configuration.

A safe practice procedure is:

1. Open and save your approved Impress source deck.
2. Identify the PDF export command in the File menu.
3. Choose appropriate output options for your purpose; do not export unintended hidden content or notes.
4. Confirm a destination and descriptive PDF filename.
5. Export the file.
6. Open the resulting PDF in a reader and review all pages.
7. Check text readability, links, images, slide ordering, and any requested accessibility properties.

An Impress PDF usually serves as a document handout, not a complete interactive recording of the original slideshow. Animated reveals and audio/video playback may not appear as they did during a live show.

### LibreOffice Impress: ODP and PPTX copies

To continue editing in Impress, keep the source in an appropriate editable format such as ODP. If an authorized recipient needs a PowerPoint-compatible copy, use **File → Save As** and select a supported PowerPoint presentation filter, where available. Your version may ask you to confirm that you want to use a non-native format. Read the warning rather than clicking through automatically, and keep an untouched ODP source.

| Output from Impress | Likely method | What to inspect |
| --- | --- | --- |
| Native editable deck | Save in ODP format | Master is preserved and reopenable |
| PowerPoint-compatible copy | Save As and choose PPTX filter | Layout, objects, fonts, notes, and compatibility |
| Document handout | Export to PDF | Pages, image quality, accessibility options |
| Separate image files | Supported export or other approved image process | Slide choice, resolution, and dimensions |
| Public distribution | Use an approved external distribution service | No automatic assumption that local Impress supplies cloud-sharing permissions |

LibreOffice Impress does not automatically provide the same cloud permission management as a Google Slides file in Google Drive. A copy placed on a third-party service inherits that service's actual sharing rules. Configure those rules at the service, not by assuming the presentation application itself controls access.

### Browser, mobile, and shared-computer variations

On phones and tablets, some export choices may appear under a three-dot menu, Share, Export, Send a copy, or another location. A web application may offer fewer options than a desktop edition. If the option you need is missing, check whether you are opening the intended application and account, whether the format is supported there, and whether the organization restricts it. Avoid installing random conversion tools or granting broad file access merely to complete a basic class activity.

On a public or shared computer, plan how to remove temporary downloads according to institutional rules and sign out appropriately when finished. Do not leave a document containing private information in a generic Downloads folder where another user may access it. For class practice, stick to the fictional workshop slides and do not use private files at all.

> **Software-independent method:** **Open the approved source → select the intended format → confirm output options → choose destination and name → generate → reopen → inspect.** This remains useful even when a menu label changes.

## 5. How do you deliver a presentation to others?

A format answers "What kind of file is this?" A [[distribution-method|distribution method]] answers "How will the recipient obtain it?" Two people can receive the same PDF by different routes. One may download it from a private class portal; the other may receive an approved email attachment. The method affects access, file size, update behavior, retention, and the ability to correct mistakes after distribution.

### Attachments: sending a separate copy

An [[attachment|attachment]] is a file included with a message, assignment submission, or other delivery. It is usually an independent copy. The receiver may download it, open it with compatible software, and retain it after the original sender changes their local deck. Attachments are often appropriate for an approved, fixed handout when the recipient is known and file size is reasonable.

Before attaching a file, confirm:

1. The file is the approved export rather than the private source or the wrong revision.
2. The recipient address or submission destination is correct and authorized.
3. The format meets the recipient's needs.
4. The attachment is within any applicable size or security limits.
5. The file opens and contains no private notes, comments, or unintended material.
6. The message accurately explains what the file contains and whether replies or changes are expected.

Once a copy is sent, removing your local original does not remove the recipient's copy. Email recall features, where available, are not reliable substitutes for checking the file and recipient before sending. A person who receives an attachment can often forward it, save it, or capture content. Therefore, do not send material you are not authorized to distribute.

### Cloud links: access to a hosted document

A [[cloud-link|cloud link]] points to a file stored on a service rather than attaching a separate file to the message. Some cloud links let recipients view a shared, living document whose contents can change as the owner edits it. Others point to downloadable files or published pages. The link's text does not reveal who can open it; [[access-permission|access permissions]] and the actual hosting configuration determine that.

When sharing a cloud file, distinguish:

- **Specific people:** Named accounts or identities receive authorized access.
- **Organization access:** Members of a particular work or school organization may be eligible, subject to policy.
- **Anyone with the link:** People possessing the link may be able to open the file without individualized approval, depending on the service.
- **Public publication:** Material is intentionally made broadly accessible, potentially through a published web page or embed.

"Anyone with the link" is not the same as a private invitation. Someone can forward that link; copies of the URL may appear in messages or documents. "Restricted" can be more appropriate for a staff review, but the owner must still confirm the right people have access.

### How to write a useful handoff message

A short message should state the presentation's title, purpose, version or date, file format, expected recipient action, and any applicable access instructions. Do not include passwords, recovery codes, unnecessary identity records, or private information in the message merely because the attachment is secure.

**Example for an approved staff workflow:**

> Subject: Digital Skills Workshop — review copy v1.0
>
> Attached is the approved PDF of the six-slide workshop overview, dated November 2026. Please check the event schedule and accessibility of the handout. This copy is for review, not for editing the source presentation. If corrections are needed, send feedback through our approved review process.

**Example for a restricted link workflow:**

> Subject: Digital Skills Workshop — staff viewer link
>
> This restricted link provides viewer access to the approved workshop slides for the invited staff team. The presentation remains centrally maintained, so its contents may be updated after review. Please report any access problems through the established team channel.

These examples are templates, not instructions to send an email as part of this lesson. You can practice writing them offline using fictional addresses and without generating actual links.

### When is a PDF link preferable to a PDF attachment?

| Consideration | Attachment | Restricted cloud link |
| --- | --- | --- |
| Offline use | Recipient can keep a downloaded copy | May require download or internet access |
| Updating information | An earlier copy normally stays unchanged | A linked live file may reflect changes |
| Access after delivery | Sent copy may remain with recipient | Hosted access may be adjusted, but copies may persist |
| Very large files | Attachment limits may interfere | Hosted link may be more practical |
| Recipient permissions | Typically controlled before sending; copy can circulate | Roles and recipients can be managed on service |
| Audit or collaboration | Separate messages may be hard to reconcile | Platform may offer access and activity features |
| Security | Depends on mail system and recipient handling | Depends on host, identity, roles, and link settings |

Neither route is automatically best. For an event poster intended for the public, a public PDF on an approved site could be suitable. For a confidential workplace planning deck, use the organization's designated protected channel with appropriate access and avoid casual personal email.

### Learning portals and official websites

A course platform, employee portal, or approved website may accept uploaded files, links, or assignments. Before uploading, review the destination, audience, file-type rules, size limits, and whether the item will be public. A teacher may request only a PDF to ensure consistent marking, while a technical reviewer might request both an editable deck and a reading copy. Follow the actual assignment or publication standard.

A [[public-website|public website]] has a different level of exposure from a private class portal. Once a presentation is published publicly, copies, previews, search caches, or screenshots may survive even if the author later removes the original. Public publication should be an explicit authorized decision—not a default response to a request that says "share this."

### Confirm receipt without oversharing

When a recipient reports that a link does not work, first check permissions and whether the correct account is signed in. Do not ask the person to send passwords or authentication codes. If a file cannot open, confirm its actual extension, size, the software in use, and whether it downloaded successfully. You can provide a fresh approved output after diagnosing the issue, but avoid creating a public link solely to bypass a restricted-access problem.

One simple confirmation question is: **"Can you open the six-slide handout and see the final Contact and Questions slide?"** This checks file completeness without asking for sensitive details. A more robust professional handoff also records whether the recipient is expected merely to receive, review, approve, or edit the material.

### Example: a mistaken file is attached

A fictional organizer accidentally selects `workshop-staff-draft.pptx` rather than `workshop-public-handout.pdf`. The draft contains internal remarks. The correct immediate response is not to hope nobody notices. Stop further distribution, notify the appropriate responsible person or institution, and follow the organization's incident and correction process. If the message was already sent, do not assert that deleting your own attachment will erase the recipient's copy. For a shared cloud file, access can often be restricted or removed, but previously downloaded or copied content may remain outside your control.

> **Delivery rule:** Choose the delivery route after the format and audience are clear. An accurate file in the wrong hands is still a failed handoff.

## 6. How do you share and review presentations responsibly?

Responsible sharing is a combination of permissions, privacy, rights, accessibility, and verification. The user clicking **Share** should know who is receiving access, what they can do, how long access is intended to last, and how the result will be reviewed. A person with permission to look at a file should not automatically receive permission to change or redistribute it.

### Use the minimum permissions needed

The [[least-privilege|principle of least privilege]] means granting no more access than the recipient needs for the authorized task. A colleague proofreading a slide title may need comment access. A speaker reading the final deck may need view access. A coauthor revising the event agenda may need edit access. Every additional right can create an additional way to change or distribute material.

| Permission or link setting | Typical capability | Appropriate use | Caution |
| --- | --- | --- | --- |
| Viewer | Open and read an authorized file | Event coordinator reviews final content | Some services also allow download/copy unless restricted |
| Commenter | Read and leave feedback | Peer review before approval | Comments may include information not intended for public release |
| Editor | Change content and often collaborate | Authorized coauthor updates a deck | Edits may affect everyone viewing the shared source |
| Restricted | Limits general access to authorized people | Private team presentation | Recipients still need correct identities and permissions |
| Organization-only | Allows access within a defined institution | Approved internal information | Not suitable if content is limited to a smaller team |
| Anyone with link | Permits broader link-based access | Approved broadly distributable material | Link can be forwarded beyond intended individuals |
| Publicly published | Exposes content for public viewing | Approved public teaching or announcements | Publication may outlive the original plan through copies |

Actual options vary. Some owners can block download, print, or copy for certain roles, but these controls are not foolproof protections against screenshots or outside transcription. Do not rely on a setting to prevent all possible redistribution of information visible to a recipient.

### Review every audience, not only the first

A presentation may have several audiences: the coauthor, approver, speaker, event organizer, participants, and the general public. Each may need a different version. A staff working file can legitimately contain editorial comments that should not appear on public handouts. The public version can have simplified language or removed internal contacts. Maintain a clear source of truth, but do not assume the exact same file should be distributed to all groups.

| Audience | Expected activity | Example deliverable | Example control |
| --- | --- | --- | --- |
| Primary editor | Revise content | Master or authorized edit copy | Editor role, controlled source |
| Approver | Examine before release | Review PDF or comment-enabled cloud deck | Restricted access |
| Presenter | Prepare delivery | Deck with approved notes | Appropriate private distribution |
| Workshop participant | Read after session | Accessible PDF handout | Approved portal or distributed copy |
| Remote viewer | Watch explanation | Captioned video or slide link | Approved access and alternate format |
| Public website visitor | Read published information | Approved public PDF | Formal publication review |

### Check identity and access scope before clicking Send

If the sharing dialog lists a person with a similar name to the intended recipient, do not guess. Confirm the correct account through an approved channel. Likewise, a group name such as "All Staff" may include more people than a project team. A sharing interface may remember a previous permission level; inspect it before proceeding. On systems with multiple personal and work accounts, verify which account owns the file and which organizational rules apply.

**Do not use a student exercise to test a real recipient's account.** If you are practicing, write a fictional settings plan. If you are performing authorized work, use official recipient details and institutional rules.

### Comments, notes, hidden slides, and revision information

The visible slideshow is not the whole file. A presentation may contain:

- speaker notes with reminders or unreleased details;
- comments written by reviewers;
- hidden slides not used during delivery;
- old content or media positioned off the slide area;
- hyperlinks to private destinations;
- author metadata or collaboration details;
- slide objects with alternative text or descriptions; and
- media content whose external hosting permissions differ from the slide file's permissions.

A standard slide-only PDF may omit many editing elements, but **never assume every export or attached editable deck will omit them**. Inspect the exact output. If sharing an editable file, review the notes and comments inside that file as part of the release process. If the content is regulated, private, or institutionally confidential, follow the approved review and document-retention procedures.

### Rights, attribution, and source quality

[[copyright|Copyright]] and other permissions govern reuse of creative content. A picture found online is not automatically licensed for republishing in a PDF, web slide deck, or public video. Similarly, a training video or soundtrack may require permission before distribution. Use original material, openly licensed works under their actual terms, or resources for which the organization has suitable rights. Provide [[attribution|attribution]] when required, and do not assume that citing the artist is equivalent to obtaining permission.

Verify factual content separately. A beautifully exported file can contain an incorrect schedule, false statistic, or outdated emergency contact. When a presentation relies on external facts, consult authoritative references appropriate to the topic and check them before distribution. A file format cannot correct a factual error.

### Accessibility at the recipient end

An accessible delivery process considers both the file and the channel. A tagged PDF can help with reading order; it does not make every visual understandable by itself. A screen reader may benefit from correct text structure and image descriptions. A captioned video can serve some viewers who cannot hear audio. A downloadable text-based document may help those who find slides difficult to navigate. Some participants have low bandwidth, limited printing access, or no presentation application.

A practical [[accessibility-check|accessibility check]] may include:

1. Read the slide titles in order and confirm the argument makes sense without animation.
2. Inspect contrast and text size at normal reading and print scale.
3. Confirm that meaningful images, charts, and diagrams have useful explanations.
4. Check that links identify their purpose rather than displaying only "click here."
5. Open the exported PDF with a suitable reader and test text selection and reading order where possible.
6. Review any available tagged PDF options, but verify the result using appropriate methods.
7. Make sure video audio has captions or an appropriate text alternative if video is distributed.
8. Provide an approved alternate format when a participant cannot use the primary file.

A technically valid file is not automatically accessible. If an audience member reports a barrier, ask what kind of access or alternative they need rather than claiming that the export setting proves the content is usable for everyone.

### A final recipient-view test

The best quality check is to experience the result as the recipient would—within the boundaries of permitted accounts and devices. For a PDF, open the exported file, not merely the original deck. For a downloaded PPTX, open the copy in the intended editor. For a cloud link, inspect the selected general-access setting and role, and use a permitted test account only if authorized. For a video, play it through and check audio, captions, and timing.

| Verification item | Pass condition | What to do if it fails |
| --- | --- | --- |
| Correct file | Title, version, and filename match request | Return to master and create correct output |
| Correct content | All approved slides present in intended sequence | Correct source or export range |
| Visual appearance | No clipped text or distorted images | Adjust layout, fonts, or export settings |
| Working functionality | Links or media work where expected | Repair source or provide an alternate route |
| Privacy | No unauthorized notes, comments, or personal details | Stop delivery and remove inappropriate content in a copy |
| Accessibility | Intended users can meaningfully access the information | Improve content and offer approved alternatives |
| Permissions | Exactly the intended access scope and role | Change access before sending |
| Delivery | Recipient can open the intended file or link | Diagnose account, format, file integrity, or permission |
| Version | Recipient knows what edition they received | Reissue with clear label if necessary |

### How to change or revoke access

In a supported cloud-sharing platform, the owner or authorized administrator can often revisit the file's sharing dialog to remove named users, adjust roles, or change general access from a broad setting to **Restricted**. This is a [[revocation|revocation]] of **hosted access**, not a guaranteed deletion of every earlier download, screenshot, forwarded attachment, or copied passage. If content was made public, changing the setting may not remove all external copies or search records immediately—or ever.

For an unneeded group collaboration, reduce or remove access according to the institution's workflow. Do not unexpectedly revoke an authorized colleague's access during an active work process without appropriate coordination. A clearly labeled expiration date in a distribution plan can help, but not all services support automatic expiration; do not invent this feature.

### Full example: the approved workshop package

The community center approves one master deck of six slides. The presenter retains the editable master privately. A participant handout is exported to PDF and checked for all six pages, readable text, and public-safe content. The coordinator receives a restricted viewer link to the approved online review file. The designated editor receives an authorized editable copy or controlled editor access to the appropriate source. The presenter records which version was distributed and confirms that the recipient can open it. This process meets all three needs without handing everyone edit privileges.

> **Final handoff principle:** Good sharing is deliberate, traceable, accessible, and proportionate to the recipient's role. The goal is not maximum exposure; it is successful, authorized communication.

## 7. Guided practice: prepare a presentation delivery package

The following six activities build from selecting a format to completing a realistic distribution plan. Work only with fictional workshop content. You may complete the planning and analysis entirely on paper. If you use PowerPoint, Google Slides, or Impress, use a private practice presentation and **do not actually invite people, post anything publicly, or send files to real recipients**. The model answers are examples of reasonable decisions, not the only possible wording.

### Activity 1: Match an audience request to a format

**Scenario.** You have a six-slide presentation called *Saturday Digital Skills Workshop*. It includes a title, learning goals, materials list, schedule, practice activity, and closing slide. Three fictional people ask for the following:

- Elena wants to print the slides for an attendee who has no presentation software.
- Marco has been authorized to update the workshop date and speaker name in his own copy.
- Priya wants to view the latest approved slides online without editing them.
- A fourth request asks for a timed version with narration for someone who cannot attend live.

**Task.** Create a four-row table on paper or in a document with the columns **Recipient need**, **Candidate format or access method**, **Reason**, and **Risk to check**. For the fourth request, identify what to do if your current software does not have a built-in video exporter. Then explain why sending the editable master to every recipient would be a poor default.

**Success criteria:** Your decisions distinguish a fixed copy from a living cloud document, preserve the master, and identify at least one realistic accessibility concern.

:::answer Show Activity 1 model answers
| Recipient need | Candidate format or access method | Reason | Risk to check |
| --- | --- | --- | --- |
| Elena: print for an attendee | PDF handout | Opens without PowerPoint and has stable pages | Page count, readability, alt text or text alternative, paper layout |
| Marco: revise date and name | Authorized PPTX/ODP copy or appropriate editor access | He needs to change slide objects | Notes, compatibility, permissions, version confusion |
| Priya: view latest approved slides | Restricted viewer link | Can read the maintained online version | Correct account and view-only access |
| Absent learner: watch narrated talk | Verified MP4, plus captions or an accessible alternative | Retains intended timing and narration | Recording availability, captions, sound, duration, permissions |

If video export is unavailable, do not rename a file to `.mp4` or install untrusted software. Use an approved recording tool where permitted, consult the instructor, or supply an appropriate alternative such as a PDF with a readable text explanation. Sending the master to everyone exposes editing elements unnecessarily and can create uncontrolled versions.
:::

### Activity 2: Make and inspect a PDF handout

**Scenario.** Your practice deck has six slides, including a schedule and an illustrated materials list. It is approved for fictional participants. You want one slide per page in a PDF, with no private speaker notes or internal reviewer comments.

**Task with presentation software:**

1. Open a private practice deck or create six very simple slides with fictional text.
2. Save your editable master using a distinct name.
3. Review the slides for accidental private notes, comments, or old placeholders.
4. Choose the PDF export or download method appropriate to your application.
5. Select a clear name ending in `.pdf` and save to a private practice folder.
6. Open the **exported PDF** in a PDF viewer; do not inspect only the PowerPoint or Google Slides editor.
7. Count pages. Check title, schedule, pictures, links, and last slide.
8. Zoom in and out to assess readability, and note any difference from the source.

**Paper alternative:** Draw a six-row checklist for the expected PDF pages, explain how you would verify each, and list two problems that the export process might introduce. Do not claim that the export succeeded unless you actually created and inspected a PDF.

**Success criteria:** You can describe an end-to-end source-to-export check and distinguish a saved file from a verified deliverable.

:::answer Show Activity 2 model answers
A correct PDF handoff begins with a saved master, then a separately named PDF such as `digital-skills-workshop-handout-v1.pdf`. A standard one-slide-per-page export of six slides would normally have six PDF pages. The reviewer checks every page for complete titles, properly wrapped text, legible diagrams, and correct order. The speaker's private notes and reviewer comments are not intended for this handout. Problems to watch for include cropped text, blurred images, and lost animation context. If the PDF has only five pages, the recipient should not receive it until the missing content or selected export range is investigated.

If you did not use software, a complete plan showing all six page checks meets the paper version of this activity.
:::

### Activity 3: Preserve a master and make an editable copy

**Scenario.** The fictional workshop is scheduled again next month. The current master should remain unchanged while Marco prepares an updated date on a separate copy. A PDF cannot conveniently serve as an ordinary editable slide deck for this task.

**Task.** Write down or create two file identities: a private master and a staff-edit copy. Give each a distinct filename that communicates its purpose. If you use PowerPoint, create the copy with Save As or Save a Copy. If you use Google Slides, distinguish a downloaded PPTX from a live shared document; a separate online copy can also be appropriate when permitted. If you use Impress, preserve the ODP master and save a separate ODP or compatible PPTX copy. On the copy only, change the workshop date to a fictional future date. Reopen both files and inspect the title slide.

**Add a compatibility check:** Suppose Marco uses software different from yours. Identify three elements he should inspect after opening the copy. Also explain how you would know which file is approved for public distribution.

**Success criteria:** The master remains intact, the copy has a meaningful name, and you can explain what must be rechecked across applications.

:::answer Show Activity 3 model answers
A sensible naming system is `digital-skills-workshop-master-v1.pptx` for the approved source and `digital-skills-workshop-staff-edit-v2-draft.pptx` for the independent revision. An Impress workflow might instead use `.odp` for the source and `.pptx` for a collaborator copy. Only the draft copy receives the fictional new date. The master still shows the previously approved date.

After reopening the copy in another application, check fonts and line wrapping, the placement and size of visuals, and whether slide layouts and animations still behave acceptably. The staff-edit draft is **not** automatically approved for public release merely because it is newer. A release decision or established approval record should identify the approved version.
:::

### Activity 4: Choose cloud-sharing roles without sending invitations

**Scenario.** The workshop deck is stored in a fictional cloud service with these options: Restricted, Organization, Anyone with the link; and Viewer, Commenter, Editor. The organizer wants three people to interact with it. Elena should read; Marco should edit; Priya should leave feedback without changing slide content. The deck is not approved for publication or organization-wide distribution.

**Task.** Create a permissions plan with a row for each role. State which general-access setting you would choose. Explain why you would not use "Anyone with the link." Identify what you would check before sending real invitations in an authorized workflow. Then explain what a person could still do with information after access is removed.

**Software option:** You may open the Share dialog on a private fictional deck and inspect the available options **without typing recipients, changing permission settings, generating public links, or clicking Send**. Note the labels you actually see; account and policy settings may differ.

**Success criteria:** Your plan applies least privilege, uses Restricted for the intended audience, and acknowledges the limits of revocation.

:::answer Show Activity 4 model answers
| Fictional person | Required action | Suggested role | General access |
| --- | --- | --- | --- |
| Elena | Read approved slides | Viewer | Restricted |
| Marco | Update approved working content | Editor | Restricted |
| Priya | Leave feedback | Commenter | Restricted |

Before an actual invitation, verify the recipients' identities, the file owner, existing sharing settings, organizational permission to share, and whether the editor can alter the live source. "Anyone with the link" is inappropriate because the deck has not been approved for broad access. Removing a person's hosted access may block further viewing of that hosted file, but it cannot guarantee removal of copies, screenshots, or notes they previously made.
:::

### Activity 5: Diagnose a failed handoff

**Scenario.** A fictitious recipient says that the shared workshop presentation "is not working." After asking appropriate questions, you learn the following facts:

- The attachment is named `workshop-public.pdf` but contains only five pages for a planned six-slide deck.
- A text box on the schedule page is cut off.
- The recipient expected to watch an instructional video, but a still PDF was delivered.
- Another recipient reports "You need access" when following a restricted cloud link.
- A staff editor reports that a custom font looks different in their application.

**Task.** For each problem, write the most likely issue, one safe diagnostic step, and one correction that does not compromise privacy. Explain which steps require consulting the master, which require inspecting the export, and which concern the recipient's access.

**Success criteria:** You do not advise changing a filename extension to convert the content, publishing a restricted file to repair access, or providing credentials to a recipient.

:::answer Show Activity 5 model answers
| Problem | Safe diagnostic step | Reasonable correction |
| --- | --- | --- |

## 8. Common misconceptions and troubleshooting

Beginners often treat export and sharing as a single button. That shortcut creates problems because file transformation, recipient identity, access rights, and content quality are separate variables. The following statements correct the most common misunderstandings before the final quiz.

### Misconception 1: "If I save a deck as a PDF, no one can change its contents"

A PDF often preserves the page layout and discourages ordinary slide editing, but it is not an absolute security control. Recipients may annotate, copy text, take screenshots, use PDF editing software, or re-create information. If disclosure would cause harm, do not rely on PDF format alone to restrict it.

### Misconception 2: "A shared link is always private"

The URL by itself does not establish privacy. A link might be restricted to invited people, open to an organization, or accessible to anyone who obtains it. Review the host's general-access rules and named recipients. A restricted link that says "access denied" should be repaired through authorized permission management, not converted into a public link for convenience.

### Misconception 3: "Viewer permission prevents copying under all circumstances"

View-only usually means the person cannot directly edit the hosted source through that role. Some services have additional controls for download, printing, or copying, but none can guarantee that an authorized viewer cannot capture or repeat what they saw. Apply appropriate information-classification rules before giving access in the first place.

### Misconception 4: "Hidden slides are not inside the file"

A hidden slide is generally part of an editable presentation unless deliberately removed. It may not appear during the normal slideshow, but a recipient with the editable file could discover it. Review the actual shared copy and any export settings. Do not hide a confidential slide and assume that hiding it is a deletion method.

### Misconception 5: "Exporting converts every feature perfectly"

A PDF is normally static; a video is time-based; a PPTX copy may be interpreted differently by another editor. Notes, transitions, hyperlinks, external media, and fonts do not necessarily survive all conversions. Inspect the destination format rather than judging the result only from the original.

### Misconception 6: "The latest file is always the approved one"

The most recently modified copy might be a draft. Version timestamps establish sequence, not authority. A reliable delivery process identifies approved content explicitly and keeps experiments and unapproved changes separate from the released version.

### Misconception 7: "Deleting a sent file removes it everywhere"

Deleting your local copy does not remove an email recipient's attachment. Revoking a cloud link can restrict future hosted access, but cannot guarantee deletion of previously downloaded or otherwise captured content. Treat release to another person as a significant action that may not be fully reversible.

### Misconception 8: "A small file is always the best file"

Extreme compression can make screenshots, charts, and text blurry. A very large file can also fail to upload or burden people with limited data. Choose appropriate quality and size and verify readability. The right balance depends on the purpose, audience, and transmission method.

### Misconception 9: "If the exported file opens, it must be accessible"

A PDF can open but have no useful document structure, poorly ordered text, or unreadable images. A video can play but lack captions. A web link can work but require a device or account the recipient does not have. Accessibility is evaluated through actual use and suitable checks, not by the absence of an error dialog.

### A practical recovery framework

When an export or share fails, identify the stage where the problem occurred:

1. **Source stage:** Are the correct slides, facts, and approvals in the master?
2. **Conversion stage:** Did the selected output format preserve the necessary content?
3. **Storage stage:** Is the file located where expected and is it complete?
4. **Authorization stage:** May the intended person access it with the intended role?
5. **Recipient stage:** Can the recipient open and use the actual deliverable?
6. **Correction stage:** Has a new version or permission change been verified and documented?

A useful question is not simply "Why isn't the share working?" but "Is this a file-content problem, a format problem, a permissions problem, or a recipient-application problem?" The more specific diagnosis helps you choose a safer correction.

### Putting the entire course together

The Presentation Skills course has covered the full lifecycle of a basic slide presentation. You begin by deciding what message the slides should convey. You create slides and choose appropriate layouts and themes. You add text and media, organize the argument, and apply clear design rules. You prepare speaker notes when useful, rehearse the delivery, and present the slides to an audience. Finally, you package the approved content, export appropriate formats, share with the intended people, and verify the result. This is a repeatable workflow for classrooms, offices, community organizations, and individual projects.

> **Course-level lesson:** An effective presentation is not finished when the final slide looks good. It is finished when the correct audience can **receive, understand, and appropriately use** an approved version without avoidable confusion or exposure.
