# MGU Departmental Lesson Catalog Standard v1.0

**Status:** Initial production convention, based on the existing dashboard's `schemaVersion: 1` contract (November 2026).  
**Scope:** Static university-wide lesson dashboard at `/lessons/`.  
**Authoritative registration:** `/lessons/catalog.json`.  
**Compatibility:** No dashboard code changes required.

## 1. Data hierarchy

```text
catalog.json
└── departments[]
    └── courses[]
        └── lessons[]
            └── file -> .md content asset
```

`departments`, `courses`, and `lessons` are JSON arrays. **Array order is the visible navigation order**; add records in the desired curricular sequence. Do not rely on file-system ordering or implicit alphabetical sorting.

## 2. Accepted properties

| Level | Required | Optional | Type/meaning |
| --- | --- | --- | --- |
| Root | `schemaVersion` | None | Exact integer `1` |
| Root | `departments` | None | Array, which may be empty |
| Department | `id`, `name`, `courses` | `description` | Identity, display name, course array |
| Course | `id`, `name`, `lessons` | `description` | Identity, display name, lesson array |
| Lesson | `id`, `title`, `file` | `minutes`, `level` | Identity, display title, Markdown path, study minutes, proficiency level |

- For `level`, standard permitted values are `Beginner`, `Intermediate`, `Advanced`.
- `minutes` is a positive whole number (up to 600) for an estimated duration.
- Description fields are prose intended for the directory card; use no HTML or Markdown there.
- The current renderer ignores unrecognized fields. **Do not invent new catalog fields** (e.g., `status`, `tags`, `icon`, `image`, `credits`, `prerequisites`, `departmentCode`) until a future, explicitly implemented schema version supports them. The formal JSON Schema disallows unknown fields to catch typographical mistakes before publication.
- If a record is unfinished, do not register it in the published catalog. Folder presence alone does not publish it.

## 3. Identity and paths

- All IDs use **lowercase ASCII kebab-case**: `a-z`, `0-9`, hyphens; start/end with letter or digit.
- Department IDs must be unique throughout `departments[]`.
- Course IDs must be unique **within their department**; the same course slug may occur under a different department.
- Lesson IDs must be unique **across the entire catalog** because the public route contains only one lesson ID.
- **Never recycle a published ID.** Renaming a visible title does not require changing its ID.
- Lesson paths must be under `content/department-id/course-id/lesson-id.md`, with the segments matching their registered IDs.
- Relative `file` paths are resolved from `/lessons/`. Do not use `C:\\`, leading `/`, `../`, URL strings, spaces, or uppercase letters.
- Use forward slashes in JSON even when editing on Windows.

Example registered lesson:

```json
{
  "id": "what-is-a-computer",
  "title": "What Is a Computer?",
  "file": "content/computer-science/computer-basics/what-is-a-computer.md",
  "minutes": 45,
  "level": "Beginner"
}
```

## 4. URL contract

| View | Public route |
| --- | --- |
| All departments | `/lessons/` |
| One department | `/lessons/?department=computer-science` |
| One course | `/lessons/?department=computer-science&course=computer-basics` |
| One lesson | `/lessons/?content=what-is-a-computer` |

`utm_source` and other referral/tracking parameters are not needed to load a lesson. The older `?lesson=...` parameter currently redirects through client-side route normalization and should not be used in new editorial links. All links generated by the dashboard use `content`.

## 5. Schema, validation and release

`standards/catalog.schema.json` implements structural, type, and pattern rules using JSON Schema draft 2020-12. `tools/validate_lessons.py` performs additional rules that a plain schema cannot reliably express: duplicate IDs, path-to-ID correspondence, file existence, and a subset of Markdown linting.

From Windows PowerShell at `C:\MGU\lessons`:

```powershell
py .\tools\validate_lessons.py
```

A passing validator is a **prepublication gate**, not a replacement for browser and editorial testing.

### Publishing sequence

1. Draft the Markdown file at the canonical path.
2. Copy the appropriate registration object into `catalog.json` in the desired order.
3. Run `py .\tools\validate_lessons.py`; resolve all errors.
4. Check the department, course, and content URLs locally with `py -m http.server 8000` launched from `C:\MGU`.
5. Inspect answer disclosures, quiz results, vocabulary, responsive tables, and content links.
6. Upload the Markdown file and revised catalog. Avoid overwriting `dashboard.js`/`dashboard.css` for ordinary content releases.
7. Verify the public Markdown path and dashboard view; hard-refresh if an old catalog is cached.

## 6. Compatibility and future versions

- **v1.0 is a convention that uses the current `schemaVersion: 1` wire format**, not a new incompatible JSON schema number.
- Do not increment `schemaVersion` simply because a new department or lesson is registered; the current dashboard explicitly requires `1`.
- Adding renderer capabilities or new published catalog fields requires a deliberate dashboard release and coordinated schema update.
- Existing public lesson IDs should be retained; changes to a path can be made without changing public URLs provided the catalog is updated simultaneously.
- Maintain backups and a simple release note for changes to the catalog and content.

## 7. Scale boundaries

The current prototype downloads one nested JSON catalog and builds sidebar links for its entire directory. This is appropriate for the initial departmental rollout, but thousands of lessons will eventually warrant lazy-loaded departmental course lists, search, and versioned catalog caching. These are **future performance improvements**, not requirements for adopting the v1 standard today.
