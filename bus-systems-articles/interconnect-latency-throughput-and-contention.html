Scope and position within computer architecture

An interconnect transfers requests, responses, data, and control information between system components. Its visible performance depends on far more than the headline bit rate of a cable, the clock frequency of an on-chip bus, or the width of a memory channel. A transaction may spend time waiting for an arbitration grant, crossing a bridge, occupying a switch buffer, receiving target service, or contending with unrelated requests. A transfer that uses only a few bytes may be dominated by fixed command costs even when the physical link can move many gigabytes each second. Conversely, a long stream may achieve substantial throughput while individual requests suffer significant queueing delay.

This specialist article belongs to the Bus Systems unit directory in the MGU Computer Science Encyclopedia. It is the unit's 17th planned specialist article, concentrating on performance models and observable bottlenecks rather than re-explaining the electrical design of every link. The articles on Bus Width, Transfer Rate, and Efficiency, Bus Arbitration and Access Priority, and Switched Fabrics and Packet-Based Interconnects provide the detailed protocol and topology foundations. Here, the main question is how much useful work gets through, how long it takes, and why performance changes under load.

All numerical examples use hypothetical, explicitly stated configurations, except where a named standard is identified as an illustrative reference. They demonstrate methods rather than promise performance for any particular chipset, board, endpoint, memory system, or deployed MGU server.

Performance questions and observation boundaries

Before collecting counters, define what is being observed. Is the target the time from a processor's load request to returned data, the time from a driver's DMA submission to completion, the amount of payload crossing a link in one second, or the application's completed operations per second? These quantities can all describe one system but are not equivalent. The application may perform encryption, buffering, copies, and scheduling outside the interconnect; an instrumented link often sees protocol bytes that an application never requested.

A defensible experiment specifies the initiator, destination, route, direction, transaction size, number of concurrent requests, observation clock, operating state, and completion boundary. For example, “device-to-host useful payload bytes per second over the upstream PCIe link during a sustained transfer” is much more precise than “PCIe speed.” A read may traverse both downstream request and upstream response paths, and a CPU-to-device write may terminate at a device buffer before the ultimate media operation occurs. The phrase completed transaction therefore requires a protocol-specific definition.

The core engineering questions are: what service rate can the resource sustain, how much of it reaches the intended workload, how much delay is intrinsic to the route, how much comes from queueing, and whether the bottleneck changes when competing initiators become active. A measurement that does not distinguish those components can lead to expensive but ineffective upgrades.

A vocabulary for latency, throughput, bandwidth, and utilization

Latency is elapsed time between two defined events. Throughput is completed useful work per unit time. Bandwidth is a capacity term, often a theoretical or sustainable upper rate of a particular channel. Utilization is the share of a resource's defined available service capacity that is used over a measurement interval. Transaction rate counts operations per second; payload rate counts useful bytes. Queue occupancy counts pending or in-flight work; it does not itself establish that the link is saturated.

These quantities have different dimensions. Latency can be measured in nanoseconds, microseconds, or milliseconds; payload bandwidth in decimal bytes per second; a packet-processing limit in messages per second; utilization as a fraction or percent. A device reporting 8 GB/s may be delivering data while transactions experience widely varying response times. A peripheral that handles 100,000 tiny requests each second may move only a few megabytes per second because fixed processing overhead dominates.

The complete latency path

A simple additive latency model is T = T_prepare + T_queue + T_arbitrate + T_transport + T_target + T_return + T_complete. The categories must be defined so they do not double-count overlapping pipeline stages. Request construction and driver scheduling may happen before a bus request exists; switch forwarding occurs during transport; controller service includes actions such as DRAM timing, flash-device command handling, or endpoint decoding. Backpressure can appear at several boundaries and often moves waiting time upstream.

The total is not always the sum of isolated device specifications. Independent work may overlap, caches or posted writes can hide a portion of apparent delay, and coherent requests may trigger additional messages whose routes are workload-dependent. The sum is most useful as a critical-path accounting model for one transaction rather than a universal equation for all traffic. Multiple requests can coexist, and a pipelined interconnect can deliver a completion every cycle despite each individual request taking several cycles to travel through it.

Good latency measurements name their start and stop events: asserted request, accepted address, last data beat, target response, interrupt observation, driver notification, or application return. Moving a timestamp boundary can change the apparent latency without changing the hardware. An architect should draw the path and explicitly label where events are timestamped.

Unloaded latency versus loaded latency

Unloaded latency measures a request when other traffic is absent or sufficiently light that queueing is negligible. It exposes propagation, pipeline depth, fixed arbitration cycles, controller service, and protocol overhead. Loaded latency measures the same operation while one or more initiators compete for resources; it adds waiting caused by other operations, scheduler priorities, row conflicts, buffers, and flow control. Loaded latency is frequently the more relevant service-level property.

The unloaded value is not necessarily constant: clock transitions, energy-saving modes, NUMA placement, cache state, translation lookups, and target readiness can vary between samples. Similarly, loaded latency depends on the shape of competing traffic, not merely its average byte rate. A competing stream of short operations may exercise control queues differently from a stream of large bursts. Traffic arriving in synchronized bursts can produce long queues even when the long-term mean demand remains below capacity.

A meaningful investigation therefore measures at multiple imposed loads and records the entire latency distribution. A plot of latency versus offered workload usually identifies the region where extra throughput begins costing disproportionate delay. If the curve changes suddenly at a lower rate than expected, examine shared controllers, address mapping, flow control, and other upstream resources before blaming the advertised link speed.

Serialization, propagation, processing, and queueing delays

Serialization delay is the time needed to place a specified number of bits or bytes onto a link at its usable coding rate, assuming continuous transmission and no additional overhead. Propagation delay is the time for the electrical or optical signal to traverse the physical medium. Processing delay arises in packet classification, address decoding, error checking, switching, or target service. Queueing delay occurs while work waits behind other work or for a credit, port, buffer, or grant.

A short, high-speed interconnect usually has negligible propagation time compared with memory-controller service or software processing, but propagation can become material in long-distance systems. Even locally, an additional retimer, bridge, pipeline register, or switch stage can introduce fixed latency. Serialization scales with transfer size, while fixed handling costs do not. Hence the transfer size is central to interpreting the apparent speed of a link.

One useful approximation for a single uncontented transfer is T ≈ L_fixed + S / B_usable, where S is the payload in bytes and B_usable is its effective byte rate. This is not a substitute for protocol timing, parallel transfer channels, retransmission, or a multi-hop request/response operation; it is an explicit first-pass separation of fixed cost and size-dependent transfer time.

Payload size and protocol overhead

A physical link transports more than application payload. Headers, delimiters, credits, alignment, flow-control traffic, data-integrity fields, and retransmissions consume some link capacity. A useful accounting identity is payload efficiency = useful payload bytes / total transmitted bytes over a carefully defined period. On a packet fabric, “total transmitted” may be counted per hop rather than across the entire network. A 4 KiB application block can require multiple packets, and a small control message may occupy a minimum framing unit.

The more significant the fixed per-transaction overhead, the more strongly performance depends on payload size. Aggregating operations into larger bursts can improve payload efficiency and reduce command-processing overhead; it may also increase interference, occupy shared buffers longer, and worsen latency for small urgent requests. Neither “maximize packet size” nor “minimize packet size” is a universal engineering rule.

Clock frequency is not a throughput guarantee

An interface clock establishes potential transfer opportunities, not guaranteed useful traffic. A 64-bit synchronous data channel offering 200 million transfers each second has a nominal peak of 64 × 200 million / 8 = 1.6 billion bytes per second before idle cycles and overhead. If the receiver accepts only half the transfer opportunities, the accepted payload rate is at most 0.8 GB/s under the stated assumptions. A bridge may run at a higher clock but still provide less throughput if its data width is narrower.

Physical serial links require an additional distinction between symbol rate and payload bit rate. Coding efficiency, error-correction framing, control blocks, link-management traffic, and packet formatting all matter. PCI Express is a helpful example because rates described in GT/s are not automatically equal to application GB/s. A manufacturer’s “bidirectional aggregate bandwidth” is also not interchangeable with the per-direction capacity of one producer-to-consumer workload.

Protocol and implementation variations matter: AMBA AXI offers multiple independent address and data channels, but its observed rate depends on the endpoint and fabric implementation. A high clock is one input to a service-rate calculation, not a measured outcome.

Link width, lane count, and directional capacity

For an ideal parallel payload channel, B_peak = width_bits × transfers_per_second / 8. For a multi-lane serial link, derive the decoded per-lane rate and then multiply by the number of trained lanes; apply any stated formatting and protocol deductions separately. A PCIe endpoint trained at a narrower link width or lower generation than expected will have less physical capacity, but may still be bottlenecked elsewhere.

Full-duplex links can often send and receive simultaneously. If an example link sustains 6 GB/s in each direction, it can have a bidirectional aggregate of 12 GB/s under balanced traffic while no one-way stream can use 12 GB/s. Read transactions often use small request messages in one direction and much larger data completions in the other. Summing the two directions without a clear purpose can misstate throughput.

A shared upstream segment can also limit aggregate device traffic even when each downstream link has ample capacity. For accurate reporting, record link direction, active width, generation or transfer rate, negotiated payload size if relevant, and the measurement boundary. These variables should appear in the performance report alongside the traffic generator and data-size distribution.

Bursts, pipelines, and transfer acceptance

A bus transaction may consist of multiple beats, one or more addresses, and one or more responses. The presence of a transaction on an address channel does not mean useful data has completed. On an AXI-style ready/valid channel, an accepted beat occurs on a clock edge where both valid and ready are asserted; deasserted ready means backpressure and no transfer on that edge. Independent channels and outstanding IDs allow other requests to progress while one response waits, subject to the implementation’s rules.

Pipelining allows a channel to accept work at a greater rate than its single-request round-trip latency would suggest. For instance, a fabricated four-stage path might accept one request each cycle after fill, while each request remains in the pipeline for four cycles. Conversely, a nonpipelined device may be forced to wait for every response before issuing the next request, leaving a high-capacity link idle much of the time.

The critical distinction is acceptance rate versus response latency. Performance measurements should identify stalls at the address channel, data channel, completion channel, and any bridge or endpoint queues. A longer burst can amortize setup overhead but may expose arbitration fairness problems when multiple initiators are active.

Outstanding transactions and latency hiding

An initiator that waits synchronously for every completion is limited by round-trip latency. If a transaction carries S bytes and takes L seconds, the ideal rate from a single strictly serialized outstanding request is approximately S / L. With N independent in-flight transactions, the latency-limited bound becomes N × S / L, provided the destination and fabric can actually overlap them. Actual throughput is bounded by the minimum of this concurrency rate and all available downstream service capacities.

The word independent matters. A pointer-chasing load cannot be issued until the previous load reveals the next address; simply enlarging an issue queue will not create parallelism in that dependency chain. Likewise, some protocols require ordering that limits progress for related operations, and target resources may accept several addresses while servicing them almost serially. A device advertising a high queue depth is not promising that all requests complete simultaneously.

Queue capacity is a system property involving the initiator, fabric, switches, completion credits, target, memory controller, and software. Raising only one limit can have no effect if another component exhausts its available entries. The proper question is how many useful outstanding bytes can be maintained without crossing a different capacity or latency boundary.

Little's law and in-flight work

For a stable system over a suitable interval, Little’s law states that average number of items in the system equals throughput rate multiplied by average time spent in that system: N̄ = λ × W̄. In the context of an interconnect, if a flow completes 500,000 transactions per second and each spends an average 20 µs between two consistently defined observation points, the average in-flight count is 10 transactions. The relationship is useful for checking whether measured concurrency plausibly supports the desired transaction rate.

The law does not assume a specific queue-service distribution, but its application depends on clear population boundaries, a stable observation regime, and compatible arrivals/departures and time averages. An instantaneous hardware-occupancy counter is not interchangeable with the average used in the equation. A long-running burst that steadily accumulates unserviced work violates the equilibrium assumption behind this interpretation.

Applied to bytes, the practical bandwidth-delay product estimates how much data must be outstanding to keep a path occupied: B_usable × L. It provides a target for batching, credits, and prefetch concurrency, not a guarantee that a device can issue or complete that much useful independent traffic.

Multiple resource ceilings and the bottleneck principle

An end-to-end transfer passes through a series of resources: source engine, read path, bridge, upstream link, root complex, memory controller, and destination buffers, for example. Under sustained streaming, long-run useful throughput cannot exceed the sustainable capacity of the narrowest required shared stage, adjusted for traffic expansion or reduction between stages. A simple minimum of raw link rates is only appropriate if each stage carries equivalent bytes and work with no parallel or branching paths.

The smallest isolated specification value is not always the active bottleneck. Address locality can make DRAM service highly efficient or slow; a protocol header adds a different traffic expansion on different links; a cache hit may avoid the DRAM channel entirely; packet copies may double memory traffic. The route should therefore be drawn with separate resource demands per unit of useful work. Roofline-like thinking is helpful: a workload can be limited by transaction processing, memory bandwidth, queue availability, or CPU issue capacity rather than transport bit rate.

The bottleneck can migrate with changes in message size, concurrency, address locality, or policy. Adding a faster PCIe card to a platform already limited by a shared upstream switch may produce little benefit. Engineers should verify each stage before purchasing replacement hardware or reconfiguring workload placement.

Shared segments and oversubscription

Oversubscription occurs when combined offered demand exceeds a shared segment's sustainable service rate. Consider two endpoints each capable of delivering 9 GB/s into a shared 12 GB/s upstream path. Their nominal combined demand is 18 GB/s, which cannot pass through that shared path continuously. A fair scheduler might give each 6 GB/s if both remain backlogged and have equal effective priority, but protocol effects, packet sizes, priorities, endpoint behavior, and destination congestion may produce unequal rates.

The exact location of the shared segment matters. A PCIe switch may have full-speed links to endpoints but fewer or narrower lanes toward the host; a memory controller may combine requests from numerous CPU cores and devices; a NoC router may have a congested output despite unused links elsewhere. Measuring all downstream links without the upstream link misses the aggregate contention boundary.

Offered load is the amount participants attempt to inject. Accepted load is the amount admitted by the fabric. Delivered load is useful work completed at the destination. Above capacity, upstream queues may expand, the fabric may apply backpressure, or sources may throttle. Those behaviors are not interchangeable and must not be interpreted as the same utilization statistic.

Arbitration and service fairness

When multiple initiators request one resource, an arbiter selects which request proceeds. Fixed priority can reduce delay for an urgent class but may starve lower-priority agents under sustained load. Round-robin can improve fairness among backlogged participants, although its behavior depends on grant duration, packet size, and whether service is counted per request, beat, or byte. Weighted policies can reserve approximate shares but do not automatically enforce strict per-operation deadlines.

Arbitration occurs at several scales: CPU-cache request queues, DRAM command schedulers, shared parallel buses, NoC router outputs, switch ports, and storage submission queues. Some systems grant an entire burst; others grant individual flits or beats. A workload with many tiny messages may win many grants while moving little payload, whereas large bursts may occupy a channel longer but have lower overhead per byte.

A good design states whether the objective is maximum aggregate throughput, low urgent-request latency, bounded worst-case service, predictable proportional shares, or starvation avoidance. No single scheduling algorithm optimizes all five simultaneously. Measure each traffic class rather than relying on the aggregate average alone.

Queue locations and backpressure propagation

Interconnects contain queues at initiators, bridges, router inputs, crossbar destinations, controllers, and endpoints. A transaction can wait before being admitted, wait for an output port, or wait for a response buffer to become available. A system-level “latency” figure can conceal which of these queues dominates. When one queue fills, flow control can stop new traffic and propagate blocking toward a source that is not directly attached to the bottleneck.

Backpressure is a safety mechanism, not automatically a defect: it prevents unbounded overflow and can preserve reliability. Nevertheless, poor buffer allocation, inadequate credit return, or a permanently blocked destination can yield severe throughput loss. A high occupancy counter indicates pressure at that queue, but not necessarily that the queue itself is the limiting service resource. The root cause might be a downstream port that rarely becomes ready.

If instrumentation is available, sample both occupancy and the reason for stalled progress. Count valid-but-not-ready cycles on handshake channels, track credit starvation on packet links, and relate them to target service and competing traffic. The direction in which blocking propagates is often a valuable clue to where the bottleneck originates.

Head-of-line blocking

Head-of-line (HOL) blocking arises when the first queued item cannot advance and prevents later items from advancing, even when their desired downstream resources could otherwise serve them. A single FIFO containing packets for multiple outputs is a classic example: a packet targeting a congested output blocks a later packet for an idle output. Head-of-line blocking may also appear in ordered transaction queues, completion handling, or resource-allocation policies that bind unrelated work together.

Virtual output queues, separate traffic classes, and multiple virtual channels can mitigate particular HOL patterns. These structures require more state, arbitration, buffers, and sometimes additional hardware verification. Simply doubling queue depth may increase the time work waits without improving service if the front entry remains blocked. Similarly, unrestricted reordering may violate required memory or device ordering semantics.

When diagnosing HOL behavior, identify the queue's service eligibility rules. A later transaction might be physically able to travel but logically forbidden to pass an earlier request. The remedy must respect the protocol's ordering and completion guarantees, not just move packets faster.

Credit-based flow control and buffer limits

In credit-managed fabrics, a sender can transmit only when it holds permission representing receiver buffer capacity. Credits may be tracked by traffic class, virtual channel, or message type. The sender needs enough credits to cover in-flight traffic and credit-return latency; otherwise, the link may become idle even though the receiver could process more work. Credits prevent buffer overflow but can themselves become a throughput limitation.

Suppose a path can transfer 8 GB/s and the effective credit round trip is 2 µs. The bandwidth-delay product is 16,000 bytes. Maintaining the full rate in this simplified model requires enough usable outstanding capacity to cover at least that data volume, with extra margin for packet granularity and fluctuations. This is not a claim about the credit-allocation rules of any named fabric: some credits account for packet headers and payload separately, and some traffic has multiple buffers or independent credit domains.

Analyze the complete refill mechanism. A larger advertised data-link rate does not help if credits recycle too slowly; conversely, more credits cannot overcome a target that has a low sustainable service rate. Credit counters must be interpreted alongside receiver occupancy, protocol priority, and actual payload completion.

Bursty arrivals, traffic shaping, and tail effects

Average offered demand hides temporal structure. Two devices each averaging 3 GB/s might fit beneath an 8 GB/s shared link when their traffic is smooth, yet produce high instantaneous queues if both emit short 8 GB/s bursts at the same time. A benchmark that reports only average throughput may miss large spikes in the response time of latency-sensitive requests.

Traffic shaping, admission control, and per-class service policies can smooth injection rates and protect critical work. Shaping can lower burst-induced delay while adding its own waiting time at the source. A hard priority class might improve a control path but create starvation risk for bulk transfers. A token-bucket policy limits long-term injected rate and permits bursts within a configured token reserve; it does not itself establish a fixed end-to-end latency guarantee.

Tail latency is often determined by rare congestion episodes, retries, page walks, memory row conflicts, or shared-resource scheduling. Collect percentile distributions at a clearly specified workload and sample population rather than using average latency as a service-level guarantee. Large p99 changes can occur without much change in mean throughput.

Percentiles, averages, and measurement windows

The mean is valuable for work-conservation and Little's-law calculations but is not a summary of worst-case user experience. The median describes the central completion time; p95 or p99 expresses a high-latency percentile of the observed sample distribution. A p99 value of 300 µs means that approximately 99 percent of measurements are at or below that threshold under the reported empirical convention, not that any future request will finish within 300 µs.

Percentiles must be computed from the underlying observations or a valid distribution summary. Averaging per-second p99 values does not in general recover the p99 of all requests. Measurements also depend on sample size, warmup, clock changes, thread pinning, address locality, run length, and background load. An isolated burst may dominate a short collection, while a long averaging interval can mask brief, severe stalls.

Report elapsed wall-clock duration; total successful and failed operations; throughput; latency mean, median, and selected percentiles; request-size histogram; retry counts; workload placement; and traffic direction. When instruments have different timestamp sources, account for synchronization uncertainty rather than asserting sub-nanosecond conclusions from loosely synchronized clocks.

Queueing theory as a model, not a product specification

Queueing models are useful for understanding why delay can increase sharply near saturation. In a simplified M/M/1 queue, with Poisson arrivals at rate λ and exponentially distributed service times at rate μ, stability requires λ < μ and the mean time in the system is W = 1 / (μ − λ). As utilization ρ = λ / μ approaches one, the expected delay becomes much larger than the mean service time. These assumptions are rarely exact for a modern burst-based interconnect.

Real traffic may be non-Poisson and correlated; service times may depend on packet size, DRAM bank conflicts, priority, and routing; multiple servers and independent paths may exist. Deterministic or batch arrivals have different delay properties, and processor pipelines can overlap service. A numerical M/M/1 example should therefore be labeled a teaching model, not a throughput prediction for PCIe, AXI, or any specific memory controller.

Use analytical approximations to ask which parameters matter and to check whether an observed curve is plausible. Use protocol traces, hardware counters, simulation, or controlled experiments to establish what actually happens in a concrete design.

Contention at memory controllers and coherent fabrics

A coherent CPU interconnect transports data and control messages among cores, caches, and home agents. Its load includes demand misses, writebacks, snoops, ownership requests, and sometimes accelerator traffic. Two software threads may saturate a memory controller even while their core-local links look underused. Cache-line bouncing and false sharing can create high coherence-traffic volume despite little useful application-level data movement.

DRAM service adds scheduling constraints: rows must be opened or closed; read/write direction changes introduce turnaround costs; banks can be parallel to a degree, but controller queues and the channel are shared. Thus identical total byte counts may produce different latency and throughput for sequential versus random addresses, one versus several banks, and local versus remote NUMA placement. Latency may rise before bandwidth reaches its theoretical ceiling.

Observability should include read/write bytes per memory channel, local and remote accesses, memory-controller queue pressure when available, and coherent-fabric traffic. These observations belong next to the workload's cache hit rate and address-placement data. Do not attribute a slowdown to the PCIe bus merely because a PCIe device initiated the memory traffic.

Contention in PCIe and device fabrics

A PCIe topology includes endpoints, switches, links, a root complex, and memory-system paths behind it. A link width such as x8 or x16 describes the local trained connection; it does not guarantee that all devices beneath a switch can transfer at their individual peak rates simultaneously. Traffic in opposite directions has different resource consumption, and memory reads require completion packets that share finite buffers and credits.

Small completion payloads, limited read-request concurrency, payload and read-request sizing, and target response time can reduce effective throughput. The source of a memory read might wait for acknowledgments or completions while another engine streams writes efficiently. A downstream PCIe counter may show high traffic while the application remains stalled in software or in the device's command engine.

Capture PCIe link generation and lane width, topology, error/retry counters, and device DMA completion rates when permitted. Interpret these with platform-specific tools. Changing Max Payload Size or Max Read Request Size indiscriminately can affect compatibility, ordering and available credits; any modification should follow device and platform guidance rather than a universal “bigger is better” recipe.

On-chip meshes and multihop service

A network-on-chip can route requests through several switches, each contributing link latency, router pipeline delay, and contention. The shortest path in hops is not necessarily the lowest-latency path under load; a locally congested output may dominate. Packet-based routing permits multiple unrelated transfers to proceed concurrently if they do not require the same links or destination resources.

Topology influences capacity. A mesh may have high aggregate edge bandwidth yet a comparatively narrow bisection between two communicating halves. A central memory-controller node can become a hotspot even when the average router occupancy is low. Routing and virtual-channel allocation can reduce congestion or avoid certain deadlocks but add area, power, and complexity. Multicast or coherence-broadcast traffic may consume link bandwidth in many places for each logical request.

Performance must be assessed using a matrix of source and destination locations, not one scalar bandwidth. Synthetic tests should include uniform random, hotspot, nearest-neighbor and relevant real-application traffic, because each pattern stresses different routers and bisections. Check worst-case latency and fairness in addition to aggregate delivered flits per cycle.

Latency-sensitive and bandwidth-oriented workloads

A small control read might transmit only four bytes but wait on an MMIO round trip; a high-bandwidth DMA can transfer megabytes efficiently once set up. The first workload is sensitive to fixed service and queueing delays; the second is often sensitive to sustained throughput and contention with other large streams. Attempting to optimize both with a single traffic schedule can produce counterintuitive results.

Real-time control often requires bounded response rather than best average bandwidth. Interactive accelerator submissions care about startup and completion latency; batch media processing tends to care about streaming throughput and amortized overhead. The interconnect fabric may use QoS classes, separate queues, or bandwidth reservations, but their benefit depends on the target response time and application demand.

Classify requests by deadlines, size, dependency, and direction. Then evaluate each policy under combined workloads. A memory controller that improves large-burst efficiency might delay small urgent reads. The correct objective function must be chosen at system level: completed work, deadline misses, energy per transfer, or tail latency, not solely peak link utilization.

Adaptive frequency, power states, and thermal effects

Link and processor frequency may vary with negotiated speed, power-management policy, and thermal or electrical conditions. A path that appears to deliver inconsistent bandwidth can be changing its clock or link state, while the workload has not changed. Entering a low-power link state can save energy but impose a wakeup latency; keeping a link continuously active can improve response consistency at an energy cost.

Throttling can be caused by endpoint heat, package power limits, memory-controller temperature, or platform firmware. In such a case, the long-run service rate can be lower than the initial burst rate. A benchmark measured for two seconds may not characterize a fifteen-minute sustained transfer. Clock-frequency normalization and temperature logging are therefore valuable when investigating recurring throughput loss.

Be careful not to infer a physical-layer fault from a workload-dependent slowdown. First compare link-state telemetry, retry/error counters, accepted traffic, CPU frequency, and device temperature over the same timeline. Power and reliability limits belong in the service-capacity model, but their exact implementation is platform-specific.

Reliability, retries, and effective service

Error detection, link replay, end-to-end retries, timeouts, and recovery can consume capacity without delivering additional application payload. A link may report high transmitted byte counts while effective payload completion falls due to repeated retransmissions. Intermittent errors may also create severe tail latency without much effect on a long-run average. Raw line rate and payload throughput must be measured separately when this is possible.

Do not assume that every interconnect performs retransmission at the same layer. PCIe link-layer reliability is not the same as storage-command retry or a software network retry. A completed lower-layer packet does not guarantee success at the application boundary. A controller might report errors and require software to resubmit operations; in other settings, a timeout can trigger a device reset, temporarily preventing any new work.

Investigate errors with the relevant protocol-defined status and counters, comparing the timing of retry bursts against throughput dips. The companion article on Bus Error Detection, Diagnostics, and Recovery provides the dedicated reliability treatment. Here, errors are examined as a source of wasted capacity and variable service time.

Security isolation and performance interference

Resource contention is also an isolation issue. Multiple tenants can share cache, memory controllers, PCIe switches, or interconnect queues even if their address permissions are isolated. A malicious or simply aggressive participant may consume disproportionate service and degrade another participant's latency. The IOMMU can constrain device memory access, but it does not by itself reserve fair bandwidth or remove timing interference.

Performance-based side channels can sometimes infer a neighbor's activity from changes in shared-resource latency. Defensive system design considers both confidentiality and availability: partition or regulate traffic where supported, restrict unauthorized DMA, maintain device reset and fault containment procedures, and verify tenant scheduling under contention. Capacity planning should measure worst-case coexistence rather than extrapolate from isolated tenant benchmarks.

Be precise about guarantees. QoS hints do not inherently enforce bandwidth limits, and prioritization at one hop does not guarantee a bound through every downstream controller. An end-to-end service claim needs evidence that each shared resource follows the necessary policy and that failure scenarios are handled.

Monitoring points and hardware performance counters

The most informative telemetry often comes from multiple layers simultaneously. On-chip fabric counters may report requests, flits, stalls, or buffer occupancy. Memory-controller counters may report read/write bytes and queue pressure. PCIe instrumentation may report link state, lane width, errors, and packet traffic. Drivers can measure queue depth, DMA throughput, and command latency. Applications measure completed useful operations and response-time distributions.

Event names are not standardized across all vendors. One counter may count transaction requests, another accepted beats, and another completed responses. Counter multiplexing, overflow, sampling bias, clock domains, and timebase conversions can distort comparisons. An occupancy counter is not a latency histogram; a “stall cycle” may overlap several causes; and counters collected at different windows cannot always be summed.

Start with a topology diagram and a counter dictionary: location, event definition, units, reset behavior, saturation, sampling interval, and scope. Only then derive rates and correlate them with workload transitions. For processor and memory performance, Intel VTune and Memory Latency Checker provide examples of tools that distinguish bandwidth and latency as load changes; Linux perf can help associate work with performance events where supported.

Controlled benchmark design

A credible benchmark should isolate the source and destination as far as practical, pin threads or devices to known locations when relevant, warm caches and devices appropriately, and exercise several request sizes and queue depths. Record the complete topology and background workload. Run each scenario more than once, preserving raw observations and reporting variation rather than selecting the most favorable result.

Use both unloaded and loaded cases. Vary offered load gradually; then introduce a competing stream to determine how fairness, head-of-line blocking, and priority affect each class. For heterogeneous systems, run CPU-driven reads, device-driven DMA, and storage commands separately before testing them together. Record both directions and verify that traffic generators are not CPU-limited.

A benchmark result must specify whether it measures synthetic peak, sustained application behavior, or service-level latency under realistic contention. A number produced by a cache-resident copy loop is not proof of DRAM bandwidth; a device benchmark may spend substantial time in driver setup; and a storage throughput graph may be limited by the filesystem or media rather than the interconnect.

Interpreting counter correlations without inventing causation

High link utilization and high latency can occur together, but correlation alone does not prove that the link is the root cause. A slow memory controller can fill an upstream queue, making bridge occupancy high while the physical link is underutilized. Alternatively, a fabric with insufficient credits can throttle an otherwise idle target. Performance analysis is a problem of locating a causal constraint along a path.

One practical method is controlled perturbation: change one factor at a time while recording the same metrics. Reduce message size, increase outstanding requests, move the memory allocation, disable one competing workload, or select another path—only when these changes are safe and permitted. A hypothesis is stronger if the predicted bottleneck counter and application response change together as expected. If increasing concurrency improves throughput with stable per-request service, the initial limitation was likely insufficient in-flight work; if concurrency raises latency without throughput growth, another service ceiling may already have been reached.

Keep measurement limits visible. Some hardware lacks per-hop counters; clocks may not be synchronized; and a driver may not expose packet-level telemetry. State what is directly measured, what is inferred, and what remains unknown.

A repeatable investigation sequence

The following sequence is intended as an editorial and engineering framework, not as a command script that can diagnose every platform automatically:

  1. Define the symptom: specify the transaction, payload, direction, observation points, and the performance goal.
  2. Draw the route: show initiators, queues, bridges, links, switches, controllers, and target resources.
  3. Calculate first-order bounds: translate widths, symbol rates, and overhead into capacities; calculate concurrency needs.
  4. Establish a baseline: measure unloaded response times, sustained useful throughput, and error rates.
  5. Increase offered load: measure admitted throughput, queue occupancy, latency percentiles, and backpressure.
  6. Introduce controlled competitors: test contention and fairness while holding the target workload fixed.
  7. Attribute stalls: compare telemetry on both sides of each suspected bottleneck rather than relying on one busy counter.
  8. Test a precise change: adjust placement, batching, outstanding requests, scheduling, or path capacity within platform guidance.
  9. Validate service guarantees: confirm stability, tail behavior, errors, and performance of unrelated tenants.
  10. Document limitations: preserve configuration and counters so the experiment is reproducible.

Worked example 1 — Ideal channel width versus accepted transfers

A hypothetical 64-bit-wide bus offers 200 million beat opportunities per second. Treat each accepted beat as eight useful bytes and ignore framing. The theoretical data rate is 64 × 200,000,000 / 8 = 1,600,000,000 bytes/s = 1.6 GB/s. A trace of 10,000 sample clock opportunities shows 7,500 valid-and-ready accepted beats, 2,000 opportunities blocked because the receiver is not ready, and 500 without valid data. The actual accepted payload rate is 1.6 × 7,500/10,000 = 1.2 GB/s.

The observed acceptance fraction is 75%, but attributing the remaining 25% entirely to congestion would be wrong: 5% of opportunities had no request to send. The blocked fraction is 20%; the idle-source fraction is 5%. If additional traffic raises the valid percentage while ready deassertions increase, the bottleneck may be the receiver or a downstream path. If ready is almost always high but valid rarely appears, investigate source submission or dependencies. This numerical example treats every accepted beat as useful data; an actual protocol may move control and padding as well.

Worked example 2 — Serialization time compared with fixed latency

Suppose a synthetic link can sustain 16 GB/s of payload after all coding overhead, and a request/response operation has a fixed path and endpoint cost of 250 ns, excluding payload transfer time. A 64-byte payload takes 64 / (16 × 10⁹) = 4 ns to serialize. The model predicts approximately 254 ns in the absence of contention. A 64 KiB payload takes 65,536 / (16 × 10⁹) = 4.096 µs to serialize, so the same fixed cost yields roughly 4.346 µs.

The fixed cost dominates the tiny request but is only a small fraction of the larger transfer's total. The lesson is not that real protocols transfer exactly 64 KiB as one unbroken frame; the simplification deliberately holds other factors fixed to expose the size-dependent term. Hardware segmentation, completion latency, credits, maximum payload sizes, and concurrency would alter a real measurement. For a workload of tiny dependent control transactions, reducing fixed latency may be more valuable than doubling link width.

Worked example 3 — Concurrency bound imposed by request latency

A hypothetical request fetches 64 bytes and cannot receive a result sooner than 250 ns after issuance. With only one outstanding request and no overlap, the upper bound is 64 / 250 ns = 256 MB/s of requested bytes. With 32 independent outstanding operations, an idealized concurrency-limited rate is 32 × 64 / 250 ns = 8.192 GB/s. With 64 independent operations, that expression becomes 16.384 GB/s, but a 12 GB/s shared link would cap sustained useful throughput below or at 12 GB/s even before its other overhead.

Increasing request depth from 1 to 32 could therefore yield a large gain in this teaching model; increasing from 64 to 128 might only inflate buffers and queueing. The model assumes independent requests, a target capable of overlap, and a stable latency. A pointer-chasing program fails the independence assumption because it learns each next address from the previous completion. A read-specific fabric may also have separate request and data-return capacity constraints.

Worked example 4 — Little's law applied to a storage or DMA queue

A controlled transfer workload records 400,000 completed requests/s and a mean end-to-end time of 30 µs from accepted submission to observed completion. Little’s law gives an average in-flight population of N̄ = 400,000 × 30 × 10⁻⁶ = 12 requests. If each successful request carries 4,096 useful bytes, the corresponding delivered payload rate is 400,000 × 4,096 = 1.6384 GB/s. This does not imply that an exact queue depth of 12 is always sufficient: arrivals and response times fluctuate, and a bounded buffer must tolerate bursts.

If the measurement reports only nine requests outstanding on average, re-check the timestamp and population definitions before declaring a law of physics violated. Perhaps the count excludes a driver queue or the completion timestamp includes work outside the hardware window. A different average may also reflect changing traffic over the test interval. Consistent boundaries make the throughput–latency–concurrency relationship a useful diagnostic cross-check.

Worked example 5 — Oversubscribed two-device switch

A fabricated platform connects devices A and B through dedicated downstream links, each able to deliver 8 GB/s of useful upstream data. They share one upstream route capable of 12 GB/s after overhead. Alone, either device can reach 8 GB/s if the host memory system keeps up. Together, the offered total is 16 GB/s and the shared route cannot deliver more than 12 GB/s. With equal-rate fair byte scheduling and both permanently backlogged, each might obtain approximately 6 GB/s.

The 6 GB/s estimate is conditional, not an architectural guarantee. Device A may obtain 7 GB/s and B 5 GB/s if priorities or packet lengths differ; a target memory controller might cap the total at 10 GB/s and reduce both further. Measuring each endpoint's local link at full utilization without measuring the shared uplink may create confusion. The topology diagram establishes where the 12 GB/s ceiling applies; the arbitration policy explains how that ceiling is divided.

Worked example 6 — Bidirectional capacity and a misleading aggregate figure

Consider a full-duplex serial interface with sustainable payload capacity of 6 GB/s in each direction. A bidirectional workload sending 5 GB/s from A to B and 4 GB/s from B to A carries an aggregate of 9 GB/s, while using 83.3% of forward-direction capacity and 66.7% of reverse-direction capacity. It would be inaccurate to say that a single forward stream can reach 12 GB/s because “the interface supports 12 GB/s aggregate.”

Now suppose A issues reads whose requests occupy 0.2 GB/s forward and data completions occupy 5.8 GB/s reverse. The reverse data path is almost saturated while the forward request path is lightly used. A single total-utilization counter could hide that imbalance. A good report separates producer, consumer, request direction, response direction, and payload accounting. Protocol overhead and control traffic would reduce the available useful rate in a real deployment.

Worked example 7 — Packet overhead and useful-byte efficiency

A fictitious transport sends packets containing 4,096 payload bytes and 64 bytes of combined headers and other per-packet overhead, with no retransmissions or further alignment. Efficiency is 4,096 / (4,096 + 64) = 98.46%. For a 64-byte payload using the same 64 overhead bytes, efficiency is only 50%. At an equal physical byte rate, the larger-payload flow can transfer nearly twice the useful data per transmitted byte in this simplified comparison.

This calculation does not assert PCIe, AXI, Ethernet, or any named protocol has a universal 64-byte overhead. Actual framing can depend on transaction type, generation, control symbols, padding and the measurement boundary. The scenario illustrates why a packet-per-second ceiling and a bytes-per-second ceiling are separate limits. Larger transfers may also incur more queueing for competing small packets, so evaluate the latency impact of coalescing before deploying it broadly.

Worked example 8 — A burst with fixed setup and per-beat time

A hypothetical peripheral performs an eight-beat burst with 64 bytes per beat. Transaction setup consumes 100 ns, while each beat requires 40 ns of nonoverlapped service. Total modeled service time is 100 + 8 × 40 = 420 ns for 512 bytes, equivalent to 512 / 420 ns ≈ 1.219 GB/s. If the setup is paid for each of eight separate single-beat requests, total time becomes 8 × (100 + 40) = 1,120 ns, yielding only about 0.457 GB/s.

Batched bursts improve this artificial target’s useful service rate by amortizing setup. However, another initiator might have to wait longer while the eight-beat burst occupies a shared resource. In a real pipelined controller, setup and data may overlap between requests, changing the arithmetic. Specify whether the operation blocks other requests and whether transfer acceptance is measured at the initiator, fabric, or final target.

Worked example 9 — Queue delay near saturation

Use a classroom M/M/1 model with an average service capacity μ = 100,000 transactions/s and an arrival rate λ = 80,000 transactions/s. Utilization is ρ = 0.8; mean time in the system is 1 / (100,000 − 80,000) = 50 µs. The service-time mean alone is 1/μ = 10 µs. Under these assumptions the difference—40 µs—is mean waiting, and Little's law predicts 80,000 × 50 µs = 4 transactions in the whole system on average.

If arrivals rise to 95,000/s without increasing service capacity, mean modeled system time becomes 200 µs, despite only an 18.75% increase in arrival rate. This steep rise illustrates why operating near capacity can damage response time. The M/M/1 assumptions are not valid specifications for a bus, where bursts, flow control, correlated arrivals and parallel engines can change the distribution. Use actual measurements before deriving service targets.

Worked example 10 — A packet blocked behind the wrong destination

Imagine an input FIFO containing three packets in order: P1 destined for output X, P2 for output Y, and P3 for Y. Output X is busy for the next five arbitration slots, while output Y is ready now. If the fabric allows only the head of this shared FIFO to compete for service, P2 and P3 cannot advance even though Y could accept them. The observed output-Y utilization is low, while the input queue remains occupied. This is head-of-line blocking, not evidence that output Y lacks bandwidth.

A design with separate virtual output queues could place X-bound and Y-bound packets into different queues, allowing Y packets to proceed under the appropriate ordering and fairness rules. The cost is extra state and scheduling complexity. Simply making the original FIFO deeper might hold more traffic but would not remove the blocked head condition. A diagnostic trace should record destination, queue position, output readiness, and arbitration eligibility for each packet.

Worked example 11 — Bandwidth-delay product and credit starvation

Suppose a credit-controlled route delivers 8 GB/s of useful payload when continuously fed, with a 2 µs time from data injection to effective reuse of the relevant buffer capacity. Its payload bandwidth-delay product is 8 × 10⁹ × 2 × 10⁻⁶ = 16,000 bytes, about 15.6 KiB. If the sender has only 8 KiB of usable outstanding payload capacity and all other assumptions hold, the latency-limited rate is at most 8,192 / 2 µs = 4.096 GB/s.

Increasing the capacity toward 16,000 bytes could remove that particular concurrency bottleneck. Beyond that threshold, additional credits may not improve throughput because the link rate is already reached. Actual fabrics often distinguish packet headers, payload credits, virtual channels, reserve slots, and return-credit timing; one aggregate byte pool is only a teaching abstraction. Count the resources that genuinely constrain issuance instead of blindly increasing buffer allocations.

Worked example 12 — A multihop path with and without contention

An illustrative packet traverses five router stages, each contributing 20 ns of fixed forwarding latency, then reaches a target with 80 ns of nonoverlapped service. Without queueing or response-path cost, the forward portion is 5 × 20 + 80 = 180 ns. During a competing burst, packets wait an additional 60 ns at router 2 and 140 ns at router 4. Their modeled time becomes 380 ns even though none of the physical link rates has changed.

If an alternate route has six 20 ns stages but avoids 200 ns of congestion, its modeled time is 6 × 20 + 80 = 200 ns, lower than the congested five-hop path. This illustrates why shortest path by hops need not be fastest under load. Real adaptive routing must account for ordering, deadlock freedom, link availability and implementation-specific cost; a system cannot simply route every request arbitrarily in pursuit of lower delay.

Worked example 13 — Average latency conceals slow completions

In a constructed experiment, 98% of requests complete in 5 µs, while 2% complete in 200 µs due to occasional congestion. Mean latency is 0.98 × 5 + 0.02 × 200 = 8.9 µs. The median is 5 µs, but p99 falls in the 200 µs group for a sufficiently large sample following that distribution. A report containing only “average latency: 8.9 µs” fails to describe the experience of the slowest 1% of transactions.

Now imagine an optimization that lowers the 5 µs group to 4 µs but leaves the 200 µs tail unchanged. Mean latency improves to 7.92 µs, yet p99 remains near 200 µs. Conversely, reducing the rare congestion episode may greatly improve p99 with only a modest change in average. The relevant metric depends on whether the application values bulk throughput, common-case responsiveness, deadlines, or long-tail service reliability.

Worked example 14 — Sharing bandwidth with a high-priority control flow

A hypothetical 10 GB/s fabric carries a backlogged bulk stream and a control stream that injects 1 GB/s on average but arrives in bursts. Assume the scheduler provides the control stream strict priority and every burst is admitted promptly while it remains below the physical capacity. During a control burst injecting 6 GB/s, the bulk stream can obtain at most roughly 4 GB/s of service if both share the same output and have equivalent per-byte costs. Between bursts, the bulk stream can use much more of the link.

Even though the control stream averages only 1 GB/s, its peak behavior can cause substantial variation in the bulk stream's latency and throughput. A weighted service reservation or shaping policy might make sharing more predictable, but it can also increase control-flow wait time. Evaluation should report per-class byte rates, completion latencies, fairness and deadline misses—not only the link's 100% aggregate utilization during each burst.

Worked example 15 — An end-to-end bottleneck investigation

A DMA engine transfers data from an endpoint through a switch and host memory controller. Benchmarks show 6 GB/s with one device and 6 GB/s total after enabling a second identical device. The endpoint links each advertise more than 6 GB/s, so an engineer initially suspects the switch uplink. However, switch counters show only 6.5 GB/s of aggregate upstream traffic against 12 GB/s of sustainable capacity, while memory-controller telemetry shows a separate sustained 6 GB/s write-acceptance limit for the chosen memory region. That downstream memory service, not the switch, is the likely constraint.

A controlled change moves one device’s target buffer to a different memory controller, and the combined completed rate rises to 10 GB/s while the switch remains below its capacity. This supports the memory-placement hypothesis. The inference still requires checking the altered workload, address mappings, cache effects, and device submission rate. The general method is to measure both sides of each candidate bottleneck, test one causal change, and validate that improved throughput has not introduced unacceptable tail latency or unfairness.

Design choices and practical trade-offs

Optimizing one metric may worsen another. Extra buffering absorbs bursts but increases stored in-flight work and can lengthen tail response. Larger bursts improve payload efficiency but can delay competing small transactions. A faster link may reduce serialization time but leave fixed controller latency unchanged. A wider crossbar improves concurrency at an area, timing, and power cost. Increasing transaction concurrency hides latency but may create queue pressure, replay, and unfairness.

In real-time and safety-critical designs, deterministic access windows and conservative admission rules may be preferable to average-throughput optimization. In general-purpose computing, work-conserving arbitration and deep queues often improve aggregate utilization, but workload isolation still matters. In virtualized and multi-tenant environments, QoS and performance governance should be verified under adversarial or unexpectedly heavy workloads; their marketing labels alone do not establish guarantees.

An architecture decision should therefore compare sustained useful throughput, latency distribution, deadline behavior, resource cost, energy, and recoverability for a documented workload mix. Treat unused theoretical bandwidth as potential headroom, not evidence that end-to-end service can actually consume it.

Specialist glossary

  • Acceptance: Protocol event in which a request or data beat is formally received.
  • Admission control: Policy limiting new work to preserve a resource or service objective.
  • Aggregate bandwidth: Sum of rates across specified directions or paths, requiring precise scope.
  • Arbitration: Selection among initiators or queued operations competing for shared service.
  • Backpressure: Mechanism that slows upstream injection when downstream readiness or capacity is limited.
  • Bandwidth: Maximum or sustainable data-transfer capacity at a defined boundary.
  • Bandwidth-delay product: Transfer rate multiplied by relevant path delay, estimating required in-flight data.
  • Beat: One data-transfer unit under a particular interface timing contract.
  • Bisection bandwidth: Capacity connecting two halves of a network under a specified partition.
  • Bridge: Component joining interconnect domains while possibly translating protocol or timing.
  • Bufferbloat: Excess latency associated with large persistent queues, where applicable.
  • Burst: Transaction or traffic cluster that transfers multiple items over a short interval.
  • Busy fraction: Share of observed opportunities during which a particular resource is serving work.
  • Cache coherence: Coordination of cached copies of shared memory data across agents.
  • Completion: Protocol-defined event indicating a named operation has finished at a specified boundary.
  • Congestion: State where offered demand exceeds or strains available service at one or more resources.
  • Control traffic: Nonpayload messages used for routing, management, acknowledgment, or coherence.
  • Credit: Flow-control permission corresponding to receiver-side buffering or other capacity.
  • Critical path: Sequence of dependent work determining latency of the observed operation.
  • Cycle: Timing interval tied to an interface or processor clock, not universally one transfer.
  • Data beat: Accepted unit of data on a transfer channel.
  • Deadlock: Situation in which agents wait cyclically on resources with no permitted progress.
  • Delivered load: Work actually completed at the defined destination or observation boundary.
  • DMA: Direct memory access, memory transfers initiated by devices or DMA controllers.
  • Duplex: Directionality of a link; full duplex permits simultaneous bidirectional traffic.
  • Endpoint: Terminal device or component of an interconnect route.
  • Fairness: Property describing how shared service is distributed among eligible participants.
  • Flow control: Regulation of injection according to buffer availability or other capacity.
  • Flit: Flow-control unit used in some packet-based fabrics and networks-on-chip.
  • Full duplex: Simultaneous transfer in both directions under separately defined capacities.
  • GB/s: Decimal gigabytes per second, where a gigabyte is 10^9 bytes.
  • GiB: Gibibyte, equal to 2^30 bytes.
  • Head-of-line blocking: Queue restriction in which a blocked front item prevents later serviceable items from proceeding.
  • Histogram: Distribution of observed values grouped into defined ranges.
  • HOL: Abbreviation for head-of-line blocking.
  • In-flight work: Operations accepted but not yet completed at the chosen boundary.
  • Initiator: Agent requesting a transaction or originating a data transfer.
  • IOPS: Input/output operations per second, meaningful with operation type and size.
  • IPC: Instructions per cycle, a processor metric not directly equivalent to link throughput.
  • Latency: Elapsed time between named initiation and completion observations.
  • Latency hiding: Overlapping independent operations so useful throughput exceeds single-operation rate.
  • Little's law: Stable-system relation N̄ = λ × W̄ between average population, throughput, and time.
  • Loaded latency: Transaction response time measured under competing or significant load.
  • Mean: Arithmetic average of a set of observations.
  • Memory controller: Agent organizing and scheduling transactions into memory-technology operations.
  • MMIO: Memory-mapped I/O, device access through mapped address-space locations.
  • MSI-X: Message-signaled interrupt capability with multiple vectors in appropriate PCIe systems.
  • NoC: Network-on-chip, communication network implemented within an integrated circuit.
  • NUMA: Non-uniform memory access, where access cost depends on placement and topology.
  • Offered load: Work that initiators attempt to inject, whether or not it can be admitted.
  • Occupancy: Count or fraction of allocated queue or buffer capacity at a defined instant or average.
  • Outstanding transaction: Accepted transaction awaiting its defined completion.
  • Oversubscription: Aggregate demand greater than usable capacity of a shared resource.
  • P99: 99th-percentile response-time statistic of a specified measured population.
  • Packet: Framed message containing control information and potentially data payload.
  • Payload: User-relevant information within a larger transport or protocol unit.
  • PCIe: PCI Express, serial point-to-point interconnect and switch-fabric family.
  • Percentile: Statistical value describing a cumulative proportion of observations.
  • Propagation delay: Time for a signal to traverse the physical medium.
  • QoS: Quality of service, policies or metrics differentiating traffic treatment.
  • Queue depth: Number of pending or in-flight operations at a defined observation point.
  • Queueing delay: Time spent waiting for service availability rather than being served.
  • Read completion: Response carrying requested data or status under a protocol's rules.
  • Retry: Repetition of an operation or message after a defined failure or recovery event.
  • Serialization delay: Time required to transmit a packet or data unit at a stated effective rate.
  • Service rate: Rate at which a resource can complete defined work under given conditions.
  • Skew: Relative timing difference between signals or clock edges, relevant to physical timing.
  • Stall: Period during which an operation cannot make expected forward progress.
  • Sustained throughput: Completed useful payload or work rate maintained over an interval.
  • Tail latency: Behavior of the slow end of the response-time distribution.
  • Throughput: Completed useful work per unit time at a defined boundary.
  • Traffic class: Set of operations given a common scheduling or QoS policy.
  • Transaction: Protocol-defined request and associated response or completion behavior.
  • Unloaded latency: Response time with negligible competing queue pressure.
  • Utilization: Used share of a precisely defined resource's service capacity or opportunities.
  • Virtual channel: Separate logical buffering/flow-control class over shared physical links.
  • Virtual output queue: Input-side queue separated by desired output to reduce particular HOL effects.
  • Working set: Data or operations actively involved in workload over a relevant interval.
