Reproducibility

A computational result is much more useful when another person—or the original modeler months later—can reconstruct how it was produced. Reproducibility means preserving enough information about the model, data, parameters, numerical settings, software environment, random processes, and workflow that the same computational experiment can be run again. It turns a simulation from an isolated output into an auditable and repeatable scientific or engineering process.

The Central Idea

Reproducibility connects a reported result to the full chain of choices that produced it.

The basic structure is

\[ \boxed{ \text{model} + \text{data} + \text{parameters} + \text{software} + \text{workflow} \longrightarrow \text{reproducible result} }. \]

If any essential part of that chain is missing, the result may be difficult or impossible to reconstruct.

What Is Reproducibility?

In computational modeling, reproducibility means that the same computational procedure can be repeated using the documented inputs and settings to obtain the same or appropriately equivalent result.

Reproducibility depends on preserving:

  • the model specification;
  • the implementation version;
  • input data;
  • parameter values;
  • initial and boundary conditions;
  • numerical settings;
  • random seeds when randomness is used;
  • software and library versions;
  • the exact workflow used to generate outputs.

Repeatability, Reproducibility, and Replication

These terms are sometimes used differently across fields, but it is helpful to distinguish three ideas.

  • Repeatability: rerunning the same implementation under the same conditions produces the same result.
  • Reproducibility: the computational result can be regenerated from the documented workflow and inputs.
  • Replication: an independent implementation or experiment reaches a compatible conclusion.

All three strengthen confidence in computational work.

Why Reproducibility Matters

Reproducibility supports:

  • verification;
  • debugging;
  • auditing;
  • collaboration;
  • comparison between model versions;
  • scientific review;
  • regulatory or engineering documentation;
  • long-term maintenance of computational projects.

Without reproducibility, even a correct result can become difficult to trust later.

A Result Needs Context

A number such as

\[ 0.734 \]

has little computational meaning by itself.

To interpret it, we may need to know:

  • which model produced it;
  • which data were used;
  • which parameter values were selected;
  • which output variable it represents;
  • which units apply;
  • which run or seed produced it;
  • which numerical resolution was used.

Model Versioning

Computational models evolve.

Equations may change, bugs may be corrected, parameters may be renamed, and algorithms may be improved.

Every reported result should therefore be associated with a specific model or code version.

A version identifier might take a form such as

\[ \texttt{v1.4.2}. \]

Why Version Numbers Matter

Suppose version \(1.3\) used one boundary rule while version \(1.4\) corrected that rule.

If an old result does not record its model version, it may be impossible to know which implementation generated it.

Versioning makes computational history traceable.

Source-Control Ideas

Source-control systems help preserve the history of changes to computational code.

A useful record can show:

  • what changed;
  • when it changed;
  • who changed it;
  • which version produced a particular result;
  • how to return to an earlier implementation.

Reproducibility improves when model results can be linked to a specific revision.

Input Data Provenance

Data provenance records where input data came from and how they were transformed before entering the model.

Useful provenance information includes:

  • source;
  • collection date;
  • original format;
  • units;
  • filtering rules;
  • missing-data handling;
  • normalization or scaling;
  • derived variables;
  • version or checksum.

Raw Data Versus Processed Data

It is useful to distinguish original data from transformed data.

A reproducible workflow might follow

\[ \boxed{ \text{raw data} \rightarrow \text{cleaning} \rightarrow \text{transformation} \rightarrow \text{model input} }. \]

Each transformation should be documented or scripted so that the final inputs can be regenerated.

Parameter Records

Every simulation should preserve the parameter values used.

If the parameter vector is

\[ \boldsymbol{\theta} = (\theta_1,\theta_2,\ldots,\theta_k), \]

then the complete vector should be associated with the run.

Default values should not be assumed silently.

Initial Conditions

Dynamic models may depend strongly on their initial state.

If

\[ \mathbf{x}(0)=\mathbf{x}_0, \]

then \(\mathbf{x}_0\) is part of the computational experiment.

Reproducibility requires recording the initial conditions just as carefully as the model parameters.

Boundary Conditions

Boundary conditions can materially alter numerical solutions.

A record should specify whether a boundary is:

  • fixed;
  • periodic;
  • reflecting;
  • absorbing;
  • flux-controlled;
  • time-dependent.

Boundary details should never be left to memory.

Numerical Settings

Two runs of the same mathematical model can differ numerically if they use different computational settings.

Important settings may include:

  • grid spacing \(\Delta x\);
  • time step \(\Delta t\);
  • mesh resolution;
  • solver tolerance;
  • maximum iteration count;
  • integration method;
  • convergence criterion;
  • interpolation order.

Solver Tolerances

Iterative algorithms often stop when an error or residual becomes sufficiently small.

A stopping rule may be

\[ \|r_k\|<\varepsilon, \]

where \(\varepsilon\) is a numerical tolerance.

Different tolerances can produce different runtime and accuracy, so the tolerance should be recorded.

Random Seeds

Stochastic simulations depend on pseudorandom-number sequences.

A random seed initializes that sequence.

If the same code, generator, seed, and execution conditions are used, the same pseudorandom sequence can often be reproduced.

Seed values should therefore be stored with stochastic runs.

Seed Policies

A reproducible stochastic experiment should define how seeds are assigned.

For example,

\[ s_r=s_0+r, \]

where \(r\) is the run number.

Another strategy is to store an explicit seed list.

The important principle is that seed assignment should be deliberate and recorded.

Random Streams

Complex simulations may use separate random streams for different mechanisms.

For example:

  • initialization;
  • movement;
  • failure;
  • transmission;
  • measurement noise.

Separating streams can make experiments easier to debug and compare.

Software Environment

Reproducibility may depend on the software environment in which the model runs.

Important information can include:

  • operating system;
  • programming-language version;
  • library versions;
  • compiler version;
  • solver packages;
  • hardware architecture;
  • parallel-computing settings.

Dependency Versions

A library update can change numerical behavior.

For example, version \(A\) of a solver may use a different algorithm or default tolerance from version \(B\).

Recording dependency versions reduces ambiguity when results are reproduced later.

Environment Locking

A computational environment can be described explicitly with a list of exact software dependencies.

Conceptually,

\[ \text{environment} = \{ \text{language version}, \text{libraries}, \text{solver versions}, \ldots \}. \]

Recreating the same environment reduces differences caused by software drift.

Run Identifiers

Each simulation should have a unique identifier.

A run ID allows output files, logs, parameter settings, and error messages to be connected to one computational experiment.

A run table might contain:

  • run ID;
  • model version;
  • parameter set;
  • seed;
  • start time;
  • completion status;
  • output location.

Run Metadata

Metadata are data about the computational run itself.

Useful metadata include:

  • runtime;
  • machine or environment;
  • number of iterations;
  • convergence status;
  • warnings;
  • memory use;
  • output summary;
  • failure reason if the run did not complete.

Logs

A log records what happened during execution.

Logs may capture:

  • configuration values;
  • initialization steps;
  • solver progress;
  • warnings;
  • errors;
  • checkpoint times;
  • final status.

Logs are especially valuable when a result cannot be reproduced immediately.

Deterministic Workflows

A reproducible pipeline should minimize undocumented manual choices.

Instead of:

“open the file, edit several values, click run, copy the output,”

prefer a scripted sequence such as

\[ \boxed{ \text{load} \rightarrow \text{transform} \rightarrow \text{simulate} \rightarrow \text{analyze} \rightarrow \text{report} }. \]

Configuration Files

Model settings can be separated from program logic.

A configuration file may store:

  • parameter values;
  • input paths;
  • time horizon;
  • mesh settings;
  • solver options;
  • random seeds;
  • output choices.

This makes experiments easier to reproduce without editing source code.

Single Source of Truth

Reproducibility improves when each important setting is defined in one clear place.

If the same parameter appears in several scripts, spreadsheets, and manual notes, inconsistencies can arise.

A single authoritative configuration reduces this risk.

Automated Pipelines

An automated pipeline executes the same sequence of steps every time.

This reduces variation caused by manual intervention.

A computational pipeline may automatically:

  1. load data;
  2. validate inputs;
  3. run simulations;
  4. store outputs;
  5. generate summary statistics;
  6. create figures;
  7. record metadata.

Checksums and File Integrity

Large datasets or important input files may be identified by a checksum or hash.

If the file changes, the checksum changes.

This allows a reproducibility record to confirm that the exact intended input file was used.

Data Snapshots

External datasets may change over time.

If a model uses a live or regularly updated data source, reproducing an old run may require preserving the specific data snapshot used at that time.

Recording only the data source name may not be enough.

Reproducible Parameter Sweeps

Parameter sweeps generate many runs, so reproducibility becomes especially important.

Each run should remain traceable to:

  • its parameter combination;
  • its repetition number;
  • its random seed;
  • its model version;
  • its numerical settings;
  • its output files.

Reproducible Monte Carlo Simulation

A Monte Carlo result depends on both the probability model and the random-number sequence.

A reproducible report should record:

  • input distributions;
  • dependency assumptions;
  • number of trials;
  • random seed or seed policy;
  • sampling algorithm;
  • summary statistics.

Parallel Computation and Reproducibility

Parallel execution can complicate exact reproducibility.

The order in which computations finish may vary between runs.

Floating-point addition is not perfectly associative:

\[ (a+b)+c \]

may differ slightly from

\[ a+(b+c). \]

Therefore, parallel reductions can produce tiny numerical differences.

Exact Versus Numerical Reproducibility

Reproducibility does not always require bit-for-bit identical output.

In some numerical workflows, a reproduced result may be considered equivalent if differences remain within an accepted tolerance:

\[ |y_{\text{new}}-y_{\text{reference}}| \le\varepsilon. \]

The tolerance should be defined before comparison.

Floating-Point Effects

Different processors, compilers, libraries, or operation orders can produce small differences in floating-point results.

These differences may be harmless, but they should be distinguished from larger discrepancies that indicate a real change in the model or implementation.

Checkpoints

Long-running simulations may periodically save their internal state.

A checkpoint can include:

  • current simulation time;
  • state variables;
  • random-number state;
  • iteration count;
  • solver status.

Checkpoints support restart and help reproduce failures that occur late in a run.

Audit Trails

An audit trail preserves the history of how a computational result was created.

A strong audit trail can answer:

  • which inputs were used;
  • which code version was executed;
  • which parameters were selected;
  • which outputs were generated;
  • which transformations were applied afterward.

Provenance Graph

A complex workflow can be viewed as a dependency graph.

For example,

\[ \text{raw data} \rightarrow \text{processed data} \rightarrow \text{simulation} \rightarrow \text{summary table} \rightarrow \text{figure}. \]

Reproducibility improves when each output retains a clear link to its upstream inputs and transformations.

Documentation

Good computational documentation should explain:

  • what the model does;
  • how to run it;
  • what inputs are required;
  • what outputs are produced;
  • what assumptions are built in;
  • what numerical methods are used;
  • what limitations are known.

Documentation should be written for someone who did not create the model.

Reproducible Figures

A figure should ideally be generated directly from stored data using a documented plotting procedure.

Manual adjustments that are not recorded can break reproducibility.

The figure-generation workflow should preserve:

  • source data;
  • filtering steps;
  • axis definitions;
  • units;
  • aggregation rules;
  • plotting code or configuration.

Reproducible Tables

Summary tables should also be generated from defined computational steps rather than manually copied values.

If a reported mean is

\[ \bar{x} = \frac{1}{N} \sum_{i=1}^{N}x_i, \]

the exact dataset and filtering rule used to compute that mean should be known.

Regression Tests

Reproducibility supports regression testing.

A trusted model version can store reference outputs.

After code changes, the same test cases are rerun and compared with the reference values.

Unexpected differences reveal that behavior has changed.

Reference Outputs

A reference output should be associated with:

  • a known model version;
  • a fixed input set;
  • fixed parameters;
  • known numerical settings;
  • a defined comparison tolerance.

Otherwise, the reference itself may be ambiguous.

Reproducing a Failure

Reproducibility is valuable not only for successful runs.

If a model fails under one configuration, preserving the run state allows the failure to be recreated and studied.

Important information may include:

  • the exact input;
  • the failing parameter set;
  • the seed;
  • the model version;
  • the error message;
  • the last checkpoint.

Archiving

Long-term reproducibility requires preserving important project artifacts.

An archive may contain:

  • source code;
  • data snapshots;
  • configuration files;
  • environment specifications;
  • documentation;
  • representative outputs;
  • validation records;
  • licenses or usage notes.

Common Error: Recording Only Final Outputs

Saving a plot or final number without the configuration that produced it is not a reproducible workflow.

Results should remain linked to their model, data, parameters, and numerical settings.

Common Error: Relying on Default Settings

Software defaults can change between versions.

Important settings should be specified explicitly rather than relying on whatever default happens to be active.

Common Error: Overwriting Data or Results

If each new run replaces the previous output file, the history of the experiment is lost.

Unique run identifiers or versioned output directories help preserve traceability.

Common Error: Using Unrecorded Manual Steps

A workflow that depends on undocumented clicking, copying, renaming, or editing is difficult to reproduce.

Important transformations should be scripted or documented explicitly.

Common Error: Forgetting the Random Seed

A stochastic simulation may be impossible to reproduce exactly if the seed or random-number state is not recorded.

Seed information should be treated as part of the run configuration.

Common Error: Ignoring Software Versions

The same source code can behave differently under different library or compiler versions.

Environment information is therefore part of the computational record.

Common Error: Confusing Reproducibility with Validity

A model can be perfectly reproducible and still be wrong.

Reproducibility shows that the computational procedure can be repeated.

It does not establish that the model is scientifically valid or appropriate for its intended purpose.

A Reliable Reproducibility Workflow

  1. Assign a model or code version.
  2. Preserve the exact input data or a traceable data snapshot.
  3. Record all parameter values.
  4. Record initial and boundary conditions.
  5. Record numerical settings and solver tolerances.
  6. Define and store the random-seed policy.
  7. Record software and dependency versions.
  8. Assign a unique run identifier.
  9. Store logs and run metadata.
  10. Automate data preparation, simulation, analysis, and reporting where practical.
  11. Generate tables and figures from reproducible scripts or configurations.
  12. Preserve reference outputs for regression testing.
  13. Archive the materials needed to rerun the experiment.

What to Remember

Reproducibility turns a computational result into a reconstructable experiment.

  • model and code versions should be recorded;
  • input data need clear provenance;
  • parameters, initial conditions, and boundary conditions belong in the run record;
  • numerical settings and solver tolerances matter;
  • random seeds are essential for stochastic repeatability;
  • software environments and dependency versions can affect results;
  • run IDs, logs, metadata, and audit trails support traceability;
  • automated workflows reduce undocumented manual variation;
  • reproducibility strengthens verification but does not replace validation.

The central principle is: preserve enough information that the path from inputs to reported output can be reconstructed, rerun, and audited.
