I have 24 English language dictionaries and 15 foreign language dictionaries planned. So far I have only begun work on the general-english dictionary. Here is the evolution: Back in August 2025 I started with just one general English dictionary at /library/dictionary/. After about a month I stopped because focus switched to creating glossaries for corporate science classes, namely economics-101 located at maloneuniversity.org/department/corporate-science/economics-101/glossary/. 


When I returned to building the standard dictionary, I pursued obtaining wordlists. I utilized wordnet.exe from Princeton, I used PowerShell prompts to download github lists, and other methods. This led to excessively long lists that had broken words and mispellings. Some words were just gibberish. These lists were unacceptable because they deviated for the original goal of providing useful words in  a simple format. Overwhelming users with junk words just to have a bigger dictionary is not intelligent. Quality over quantity matters here.


That defines the first problem which was "what words to include".
The next problem was the multi-dynamic issue of formatting entry pages:


The English language contains over 600,000 words! If I created a webpage for each word that would be too much code to maintain.
Buiilding a full database to complex and also too much code to maintain.
The solution was to use an index.html to list words, an entry.html to diplay definitions, and json files to store word-definition pairings.
Json files are like mini databases. They store tabular data. The type of data you find on websites that have entry forms like name, address, phone number, email etc. In computer slang these forms are called "dictionaries" and are a perfect fit for building literal online dictionaries.
They map an entry word to its definition and store it as a record. When you search for a word on the index page the page uses a json file to display available words. Then when you click on a word link the entry page loads tabular data fron the json file to display the entry data.


This solves the issue of dealing with too many individual entry pages. Using a json file requires only one html page to load all words. 

Using one json file per letter allows the dictionary to load faster and makes maintaining the code easier.
That solves load and maintenance times.

At this point the system was stable. The final problem was what data was displayed on the entry page.
I would write entries for words in the json files only to change the fields causing me to have to do complete rewrites each time. This forced me to stop writing definitions and finalize the entry template for each word in the json. 


With the template finalized the entries became searchable.
This is when I paused production and focused on other features of the website.
