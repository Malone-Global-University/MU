Problem

MGU's original instructional lesson prototype was developed as a self-contained HTML page combining instructional content, styling, interactive vocabulary, expandable answer keys, quizzes, and JavaScript functionality.

Although the prototype functioned, its architecture was unsuitable for university-wide production.

Every additional lesson would require substantial HTML authoring and potentially duplicate presentation code. Maintaining consistent styling, assessment behavior, navigation, and accessibility across hundreds or thousands of lessons would become increasingly difficult.

The initial dashboard prototype also lacked a complete departmental navigation hierarchy. Visiting the dashboard root automatically opened the Computer Science lesson instead of presenting a university-wide departmental directory.

Additional issues included:
- Provisional styling that did not match MGU's established website branding.
- Redundant lesson directories (lessons/lessons/).
- Inconsistent terminology in URL parameters.
- No formal department, course, and lesson registration convention.
- No standardized Markdown authoring specification.
- No centralized validation process for lesson content.

Intended Goal

Establish a scalable, centralized lesson-delivery system serving all MGU academic departments through one dashboard.

The correct architecture must:

1. Separate instructional content from presentation and application logic.
2. Store lesson content independently in Markdown files.
3. Use a centralized JSON catalog to register departments, courses, and lessons.
4. Provide hierarchical navigation from dashboard to department, course, and individual lesson.
5. Support interactive vocabulary definitions, expandable answer keys, and automatically graded quizzes.
6. Integrate with MGU's existing university header, logo, navigation, breadcrumbs, and footer.
7. Preserve stable public lesson URLs independently of physical Markdown file locations.
8. Establish consistent authoring and validation standards for mass production.
9. Support static hosting without requiring a database or application server.

Root Cause

The original lesson system was based on individual HTML documents rather than a reusable content-delivery architecture.

Instructional content, interface styling, and interactive behavior were tightly coupled within each lesson.

This design created unnecessary duplication and made university-wide maintenance dependent on editing individual pages.

The initial dashboard implementation partially resolved the problem but required additional development to establish:

- Content-driven navigation rather than automatic lesson loading.
- A consistent relationship between catalog identifiers and file locations.
- Shared institutional branding.
- Formal catalog and Markdown syntax conventions.
- Automated quality assurance before publication.

The underlying problem was the absence of a standardized separation between content, catalog data, application logic, and presentation.

Rules Going Forward

1. One centralized dashboard: Departmental lessons must use the shared MGU lesson application rather than independently duplicated dashboards.

2. Content independence: Instructional content must remain separate from HTML, CSS, and JavaScript application files.

3. Markdown-first production: New instructional lessons should be authored in Markdown using the approved MGU standard.

4. Centralized registration: Every published lesson must have an entry in catalog.json.

5. Stable identifiers: Department, course, and lesson IDs must follow lowercase kebab-case conventions. Lesson IDs must be globally unique.

6. Standard directory hierarchy: Lesson files must follow content/department-id/course-id/lesson-id.md.

7. Stable public routes: Use ?content=lesson-id for individual lesson navigation. Physical content-directory changes must not require changes to published lesson URLs.

8. Schema compatibility: Preserve catalog schemaVersion: 1 until an intentional, tested schema migration is approved.

9. Shared branding: Dashboard styling must remain consistent with MGU's university-wide design and shared components.

10. Reusable interactivity: Vocabulary popovers, expandable answer keys, quizzes, and other interactions must be implemented centrally rather than independently scripted inside each lesson.

11. Mandatory validation: Run py .\tools\validate_lessons.py before publishing newly registered or revised instructional content.

12. Controlled deployment: Maintain local source files, validate changes, test locally, and publish through the established website deployment workflow.

13. Preserve working infrastructure: Future enhancements must not unnecessarily modify functioning Markdown content, catalog records, URL routing, or dashboard components.
