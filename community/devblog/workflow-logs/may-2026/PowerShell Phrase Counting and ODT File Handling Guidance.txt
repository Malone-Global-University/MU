WORKFLOW NOTE

Title
PowerShell Phrase Counting and ODT File Handling Guidance

Date
2026-05-21

Area
PowerShell text-processing workflow; local document analysis utilities

Problem
There was uncertainty about how to count phrase occurrences using PowerShell when working with a file stored at `C:\MGU\desk\lessons\math\blank.odt`. The issue was that `.odt` files are not plain-text documents, so standard text-search commands may not behave as expected.

Intended Goal
Provide a reliable method for counting phrase occurrences in files using PowerShell while clarifying the limitations of `.odt` document formats and outlining workable alternatives.

Root Cause
The `.odt` format is a compressed document container rather than a raw text file. Standard `Get-Content` operations are designed primarily for readable text formats such as `.txt`, `.html`, `.md`, or `.json`.

Steps Taken

1. Explained the basic PowerShell phrase-counting command using `Get-Content`, `Select-String`, and `.Matches.Count`.
2. Applied the command specifically to the file path `C:\MGU\desk\lessons\math\blank.odt`.
3. Clarified that `.odt` files are ZIP/XML-based containers and may not produce meaningful results with direct text reads.
4. Recommended alternative workflows:

   * Use built-in document search (`Ctrl + F`)
   * Export the document to `.txt` or `.html`
   * Extract and inspect the internal `content.xml`
5. Provided an example using an exported `.html` file for accurate phrase counting.

Key Change
The workflow shifted from treating `.odt` as a plain-text document to treating it as a structured compressed document requiring extraction or conversion before reliable phrase analysis.

Outcome
The phrase-counting process became clearly defined for both standard text files and `.odt` documents. The user now has a reproducible PowerShell method along with awareness of format-specific limitations.

Validation
Validation was performed conceptually by comparing expected PowerShell behavior against the actual structure of OpenDocument files. The workflow correctly distinguishes between readable text formats and ZIP/XML document containers.

Rules Going Forward

* Use `Get-Content -Raw` directly only on true text-based formats.
* Treat `.odt`, `.docx`, and similar office formats as structured archives rather than plain text.
* Convert office documents to `.txt` or `.html` before large-scale text-processing operations when practical.
* Use XML extraction workflows for exact internal document analysis.

Notes
The same structural limitation applies to `.docx` files because they are also ZIP/XML-based containers. Future automation pipelines could include automatic extraction of `content.xml` for direct phrase-frequency analysis inside office documents.
